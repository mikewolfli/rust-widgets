# Exemptions for tools/check_transition_durations_are_tokens.sh (BLUE22 §6.7).
#
# The rule, the literal shapes it matches, and the full statement of what it proves and does not
# prove are in that script's header. Read it first.
#
# Format, one record per line, whitespace-separated (the reason may contain spaces):
#
#     src/path/to/control.rs    <why this file's duration literals are not interaction transitions>
#
# A bare path is not an entry: an exemption with no reason is an unexplained licence, which this
# project forbids. The first field is matched against the path the scan produces, so a moved file
# stops being exempt rather than silently staying so.
#
# The exclusion that is NOT in this file, because it is a definition rather than an exemption:
# `src/style/animation.rs` and `src/theme/` are where durations are *supposed* to be written down.
# Flagging them would be flagging the token system itself, so the scan skips them by directory.
#
# ─────────────────────────────────────────────────────────────────────────────
# These entries are hover DWELL timings, not interaction transitions.
#
# The distinction is what the rule is about. A transition duration is how long a control takes to
# animate between two of its own states — a toggle sliding, a highlight fading — and BLUE22's point
# is that those must come from `theme.motion` so a theme, a reduced-motion preference or a test
# harness can re-price them together. A dwell timing is how long the pointer must rest before a
# transient surface appears or disappears; it is a *behavioural setting of the control*, it is
# already caller-settable (`set_show_delay` / `set_hide_delay`), and shortening it does not make the
# control move differently — it makes it appear sooner. Folding it into `theme.motion` would put two
# different concepts behind one token and would make "the animation is fast" and "the tooltip is
# eager" the same setting.
# ─────────────────────────────────────────────────────────────────────────────

# Verified: `show_delay` and `hide_delay` are public, settable fields (`set_show_delay`,
# `set_hide_delay`), and the constants are only their documented defaults. No transition reads them.
src/widget/dialog/tooltip.rs    hover dwell timings with their own settable properties, not transitions

# ─────────────────────────────────────────────────────────────────────────────
# This entry is a FRAME STEP, not a transition duration.
#
# `ANIMATION_FRAME_DELTA_MS` is not how long anything takes; it is how much time one *sample* is
# worth. The paint path in `draw_bridge::draw_of` advances a host-owned control by it because that
# entry point has no clock, and every control's `tick` accumulates the step against a target, so the
# step paces the motion and cannot overshoot or re-price it. Reading it from `theme.motion.fast`
# would be a category error that also misbehaves: `fast` is a whole-transition duration (100 ms), and
# advancing by 100 ms per paint would make a 200 ms hover take two frames — the cut this step exists
# to avoid. The transition's own duration still comes from the theme, through `TransitionTempo` inside
# each control, which is what the rule is about.
#
# Verified: the constant is read only by `draw_of`'s single `widget.tick(ANIMATION_FRAME_DELTA_MS)`
# call, and no control reads it as a duration.
src/widget/draw_bridge.rs    the per-frame sample step of the paint path, not a transition duration

# ─────────────────────────────────────────────────────────────────────────────
# These two entries are NO-THEME FALLBACKS for a looping animation, not hardcoded durations.
#
# Both controls price an *indefinite* animation (a progress ring's revolution, a skeleton's
# shimmer pulse) from the theme's `slow` token scaled by a multiple, because a loop is not a
# state change: `slow` is sized for a transition that ends, and a ring completing a revolution
# in 300 ms reads as a stutter rather than as progress. So both already follow a theme, which is
# the whole point of the rule.
#
# The literal is what the control uses when the theme carries **no** motion tokens at all
# (`motion_tokens()` returns a zero `slow`, which happens in a build with no theme palette).
# A control that animated nothing in that case would be a control that stopped working in a
# `mini`/`embedded` build, so a fallback is the honest answer -- and its value is the one the
# preset's `slow` produces, written down so the no-theme picture matches the themed one.
#
# Verified: each constant is read in exactly one place, the `slow == 0` arm of its period
# accessor, and both accessors are reached from that control's own `tick`.
src/widget/display_widgets/progress_circle.rs    no-theme fallback for a looping animation; the themed path reads theme.motion.slow
src/widget/display_widgets/skeleton_loader.rs    no-theme fallback for a looping animation; the themed path reads theme.motion.slow

# ─────────────────────────────────────────────────────────────────────────────
# This entry is an IDLE DWELL, not a transition duration.
#
# `SCROLLBAR_IDLE_DELAY_MS` is how long the bar stays fully opaque after the last interaction
# before it *begins* to fade. It is the same distinction as the tooltip entry above: a delay before
# a state change, not the duration of one. The fade itself is priced by the theme — the driver's
# `MotionSlot` supplies the transition, and its value flows through `theme.motion` the way every
# other control's does — so the motion still follows a reduced-motion preference or a re-tempoed
# theme. What the theme does not price, and should not, is how long the user's hand may rest before
# the bar considers itself idle; folding that into `motion` would make "the animation is fast" and
# "the bar hides promptly" the same setting.
#
# Verified: the constant is read only in the idleness accumulator that decides *when* to aim the
# opacity driver down; the driver's own duration comes from its `MotionSlot`.
src/widget/display_widgets/scrollbar.rs    an idle dwell before the fade begins, not the fade's duration
src/widget/display_widgets/arc.rs    the no-theme fallback for a looping revolution; the themed path reads theme.motion.slow (see SPIN_SLOW_MULTIPLE)
src/widget/display_widgets/color_well.rs    the dwell window that groups a double click, not an interaction transition
src/widget/display_widgets/icon.rs    the frame step of a multi-frame icon animation, a data duration, not a transition
src/widget/input_widgets/text_entry/lineedit/model.rs    the multi-click grouping window, a dwell timing rather than a transition
src/widget/menu_toolbar/tool_button.rs    the hover dwell before a delayed popup opens, not the popup's transition duration

# ── Not durations at all: rates and clocks ──
#
# These three were reported by the name heuristic (`…_MS` / `…PER_MS`) rather than by
# being a transition. A rate is a speed, not a length of time: scaling it by a theme's
# motion token would change how *fast* the pointer outruns the surface instead of how
# long a movement takes, so it has no place in `motion`.
src/widget/cupertino/date_picker.rs    `FLING_DECAY_PER_MS` is a decay rate per millisecond (0.03), not a duration: it is the exponential factor the fling velocity is multiplied by each millisecond
src/widget/misc_widgets/drum_column.rs    `SETTLE_PX_PER_MS` is a settle speed in pixels per millisecond (0.35), not a duration: the column's remaining distance divided by it gives the time, and a theme token there would re-price the distance
src/widget/input_widgets/text_entry/input_companions.rs    `NOMINAL_FRAME_MS` is the animation clock's nominal frame period (16.0 ms, i.e. 60 Hz) used to advance progress by whole frames, not a transition duration

# ── Dwell timings ──
#
# Same distinction as the tooltip/scrollbar entries above: how long the user's hand
# must rest before the surface appears is a behavioural setting of the control, and it
# is deliberately not repriced by a theme's motion scale.
src/widget/display_widgets/image_view.rs    `WHEEL_PREVIEW_HOLD_MS` is the dwell the wheel-zoom preview stays on screen after the wheel stops, not a transition
