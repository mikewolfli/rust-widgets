## 2. Phase C-0 — 【阻断】`as_draw_mut` 桥接补齐（原则 #66）

**目标**：使「实现了 `Draw` ⇒ 可经 `dyn Widget` 被绘画」在编译期成立，
覆盖从 **6/168** 提升到 **全部**。

### C-0-1 问题定性（本轮实测复核）

```text
$ grep -rhn "impl Draw for" src/ --include=*.rs | sed 's/.*for //;s/[ <{].*//' | sort -u | wc -l
167

$ grep -rn "fn as_draw_mut" src/ --include=*.rs | wc -l
7 ← 6 个控件手写 + 1 个 trait 默认实现（返回 None）
```

而 `widget::runtime::render_frame` 的唯一取绘画通道是 `Widget::as_draw_mut`
（`src/widget/runtime.rs:198`），返回 `None` 即无帧可贴 → **空白面且无报错**。

### C-0-2 实现方式（方案 2：宏，零成本）

**为何不用 blanket impl**（计划方案 1）：`impl<T: Draw> Paintable for T` **能编译但不可用**——
trait 选择需要**具体类型**，而 `&mut dyn Widget` 已把类型擦除；blanket impl 只能经泛型约束
`W: Draw + Widget` 触达，而 `Box<dyn Widget>` 不满足。**这正是 `as_draw_mut` 存在的原因。**

**采用方案**：`src/widget/draw_bridge.rs` 提供 `impl_draw_bridge!()` 宏，在控件**自己的
`impl Widget` 块内**展开为：

```rust
fn as_draw_mut(&mut self) -> Option<&mut dyn Draw> { Some(self) }
```

- 零运行时开销（原则 #28）：无查表、无 `TypeId`、无 thread_local。
- 在**具体类型可见处**生成，因此 `Some(self)` 是全函数，不可能错。
- 用 `#[macro_use]` 挂在 `widget::draw_bridge` 模块上，各控件文件无需额外 import。

### C-0-3 批量注入（一次迁移，脚本已删除）

本轮用一个 brace-aware 的临时脚本（`scripts/insert_draw_bridges.py`）定位每个
`impl Widget for X` 的匹配右花括号，仅当同文件存在 `impl Draw for X` 时插入桥调用：

```text
159 bridges inserted across 155 files
```

**脚本已在迁移完成后删除**（原则 #59「删除即删除」）：它是一次性迁移工具，
保留一个无人引用的「向每个文件插入」脚本会误导后人重复执行；永久机制是
`impl_draw_bridge!` 宏本身（新控件只需在自己文件里写一行）。

### C-0-4 覆盖度审计（编译期等式，原则 #19）

```text

既有 Widget 类型 ................ 166
Widget 实现 Draw 的数量 ......... 166 / 166 ← 全部
Draw 实现 Widget 的数量 ......... 166 / 167
```

**结论：不变式 `Widget + Draw ⇒ 可绘画` 成立，零例外。**

> 「不绘画的控件」，实测**不存在**（所有 `Widget` 都实现 `Draw`）。以实测为准（原则 #64）。

### C-1-3c 一个设计决定：`property_names()` 必须含共性四属性

迁移中发现两类写法不一致：部分控件只返回自己的属性。但**旧 `*_PROPERTIES` schema 表
包含 `enabled`/`tooltip`**——即「已发布属性」本来就包含共性部分。若只返回自有属性，
消费方（schema 生成器、文档、属性编辑器）会误以为 `enabled` 不存在。

**裁定**：`property_names()` 必须发布**自有 + 共性四**（`enabled`/`visible`/`tooltip`/`geometry`）。
实现方式：`property_names_of![..., BASE_PROPERTY_NAMES]`（宏末位标记展开为四个字面量，
因为 `'static` 切片无法在 `const` 中拼接）。共更新 79 + 14 处调用点。

## 4. 阶段顺带修复的架构缺陷（计划外，原则 #2/#3/#11）

### 4.1 「能力契约」被误置于 device profile 门禁之下

**现象**：`cargo check --no-default-features --features embedded` 报 **47 个错误**，全部形如
`cannot find 'capability' in 'widget'`。

**根因**：`src/widget/mod.rs` 把整个 `capability` 模块 gate 在
`any(desktop, tablet, mobile)`；而 C-1 新加的 `Widget::properties_dyn` 钩子（在
`widget_trait.rs`）及已迁移控件的 `impl WidgetProperties` 都引用它。**是我在 C-1 引入的回归**，不是既有问题。

**修复**（回到根因，而非给调用点逐个打补丁）：能力契约与其 profile 相关部件分离——

| 组件 | 门禁 | 理由 |
|---|---|---|
| `properties_trait`（契约） | **无**（全档） | `Widget` 全档存在，契约随它 |
| `types` / `coercion`（纯类型与转换） | **无**（全档） | 无设备依赖；`coercion` 内部对 `Date`/`Time` 等逐项 `full_widgets` 门禁 |
| `properties` / `access` / `constructors` / `registration` / `WidgetFactory` | `widgets_unstripped` | 逐个枚举具体控件，仅在完整控件集下存在 |
| `capability::tests` | `widgets_unstripped` | 测的是工厂 |

同时把 `alignment_to_str` / `check_state_to_str` / `orientation_to_str` 三个**纯转换**从
`access`（device 门禁）移入 `coercion`（全档），`access` 改为 `pub use` 转发。

**证据**：

```text

修复后：cargo check --no-default-features --features embedded
```

## 6. Phase B-1 — `Platform` trait 去控件化（原则 #56 / #53）

**目标**：`Platform` 只描述「宿主能力」，不再暴露控件级构造；控件语义全由 `src/widget/` 表达。

### B-1 修正后的执行顺序（原则 #60）

计划 §6.3 的 Step 7 把 B-1 排在 D 之后。本轮实测发现**顺序需要修正**：

```text
 删 create_label 的实现 → E0046: not all trait items implemented
```

#### 缺陷 2：属性派发的 fall-through 条件过宽（**我在本轮引入**）

**现象**：自写的两个契约测试失败：


```rust
match widget_property_get(widget, name) {

}
```

## 8. 右键上下文菜单（用户指定任务）

### 8.1 现状取证：右键根本无人响应

```text
$ grep -rn "button == 2" src/widget/ --include=*.rs | grep -v test
（空）

$ grep -rn "WidgetKind::ContextMenu" src/ --include=*.rs
 仅有 kind 定义 / 路由表 / 无障碍角色 / JSON 映射
 → 没有任何代码会 “右键打开它”
```

三个真实缺口：

| 编号 | 缺口 | 证据 |
|---|---|---|
| **CM-1** | 鼠标按键是**裸数字**，没有具名常量 | `Event::MousePress { button: u32 }`；各处写 `button == 1`，右键没有可 grep 的名字 |
| **CM-2** | 菜单**没有 “在指针处打开” 的能力** | `Menu` 只有 `add_action`/`clear`，无任何定位 API；`open_at` 不存在 |
| **CM-3** | 菜单**不会因点击外部而关闭** | `handle_event` 只在 `MousePress { button: 1 }` 命中条目时 `hide()`；左键点别处 → 菜单永不消失 |

### 8.2 实施（原则 #54：同语义只实现一次）

**① 具名按键常量**（`src/event/types.rs`）

```rust
pub mod mouse_button {
 pub const PRIMARY: u32 = 1;
 pub const SECONDARY: u32 = 2; // 右键
 pub const MIDDLE: u32 = 3;
}
```

理由：一个从未接触本项目的开发者应能写出 “我要判断右键”，而不是查 “2 是什么意思”。
`src/event/mod.rs` 已 re-export（`pub use types::mouse_button;`）。

**② `Menu::open_at(position, viewport)` —— 唯一实现，不新建 `ContextMenu` 类型**

`WidgetKind::ContextMenu` 本就解析到 `Menu`（`factory_name_for_kind` 映射为 `"menu"`，
`menu_capability` 的 alias 也包含 `"context_menu"`），因此右键行为应长在 `Menu` 上，
而不是再写一个平行菜单类型（否则就是原则 #54 禁止的同语义双份）。

新增能力：

| API | 作用 |
|---|---|
| `open_at(position, viewport)` | 在指针处打开，**边际钳位**以保证整菜单可见 |
| `invoker_position()` | 记录**未钳位**的原始点击位置（两个不同事实） |
| `contains_point(point)` | 命中区按**实际绘制高度**（`popup_height()`）而非 `geometry().height` |

**③ 真实缺陷修复：`Menu` 默认可见（原则 #12 反例）**

实现过程中测试失败并暴露了一个真问题：`BaseWidget` 默认 `visible: true`，
于是**刚创建的菜单（含 `WidgetKind::ContextMenu`）会立即按存储几何把自己画出来**——
一个永远弹开的菜单，而且无法创建为关闭的。

```text
修复前：open_at_places_the_popup_at_the_pointer → FAILED（assert!(!menu.is_visible())）
修复后：78 个 menu_toolbar 测试全绿
```

裁定：菜单是 **popup**（按需出现），不是拥有固定绘制区的控件；`Menu::new` 现在 `hide()`，
而菜单栏自身的打开路径不受影响。

**④ 关闭语义**：**任意按键**的外部按下都关闭菜单（不再只管条目命中）：

```rust
Event::MousePress { pos, button: 1 } => { /* 命中条目则 emit；未命中但仍在 popup 内 → 不关 */ }
Event::MousePress { pos, .. } => { /* 其它按键：popup 外则 hide */ }
```

理由：用户实际用**左键点别处**来关菜单；只处理右键会让菜单卡住。
popup 内边距上的点击仍算 “内部”，不关闭（否则点菜单边缘会先关掉它）。

**⑤ `widget::runtime` 层的打开入口**

上下文菜单是 “在**另一个**控件上的指针位置” 打开菜单：目标控件知道位置，菜单拥有 popup，
只有注册表能同时触达两者。故提供：

```rust
pub fn open_context_menu(menu_id, position, viewport) -> bool;
pub fn open_context_menu_for_event(menu_id, event, viewport) -> bool; // 只认 SECONDARY
```

两者都**返回 `bool` 并 `log::warn!`**，而不是静默 no-op：误绑右手键处理器时立即暴露
（对应 §4.2 的 “假能力” 教训）。

### 10.3 本轮顺带修掉的真缺陷（原则 #2 冰山法则）

#### 缺陷 A：Cargo feature 别名方向反了（**两个已发布 feature 都编译不过**）

```text
$ cargo check --no-default-features --features macos-legacy
 error: cannot find SelectedMacOSPlatform
$ cargo check --no-default-features --features cocoa-legacy
 error: cannot find MacOSPlatform
```

**根因**：`src/platform/macos/` 的模块 gate 写的是 `feature = "cocoa-legacy"`，
而 `Cargo.toml` 写的是 `cocoa-legacy = ["macos-legacy"]`——**别名指向了相反方向**。
Cargo feature 别名**不是对称的**：开 `macos-legacy` 不会开 `cocoa-legacy`，
于是依赖被拉进来了（`dep:cocoa`），但模块 gate 从未激活，报“类型不存在”。

**修复**：别名必须指向**被 gate 的名字**。

```toml
macos-legacy = ["cocoa-legacy"]
cocoa-legacy = ["dep:cocoa", "dep:objc"]
```

**同时修掉的连带不一致**（否则 `desktop` 会断）：

| 位置 | 问题 | 修复 |
|---|---|---|
| `macos_bridge.rs` | `#[cfg(any(feature = "macos", feature = "macos"))]`——**自重复**，永不匹配单独 `cocoa-legacy` | `#[cfg(feature = "macos")]` / `all(not(macos), cocoa-legacy)` |
| `accessibility/mod.rs` | 用 `macos-legacy`，与 `macos/mod.rs` 的 `cocoa-legacy` 不一致 | 统一到 `cocoa-legacy` |
| `clipboard_stubs.rs` | 同上 | 同上 |

**证据（四个组合全绿）**：

```text
$ for f in desktop macos-legacy cocoa-legacy macos; do
 cargo check --no-default-features --features "$f"; done
 desktop Finished
 macos-legacy Finished
 cocoa-legacy Finished
 macos Finished
```

#### 缺陷 B：`Menu` 默认可见（弹出的菜单无法创建为关闭态）

`BaseWidget` 默认 `visible: true`，而 `Menu` 是 **popup**（按需出现），于是刚创建的菜单
（含 `WidgetKind::ContextMenu`）会立即把自己画出来——一个永远弹开的菜单。

```text
修复前：open_at_places_the_popup_at_the_pointer → FAILED（assert!(!menu.is_visible())）
修复后：79 个 menu_toolbar 测试全绿
```

#### 缺陷 C：属性派发 fall-through 过宽（契约被旧表推翻）

`UnknownProperty` 是**契约的判定**（“我有契约，但没有这个属性”），却被当作
“契约没覆盖，去问旧表”——结果旧表**推翻**了契约，`geometry` 的只读判定被覆盖。

**修复**：只有 `UnsupportedOnWidget`（= “此控件根本没有契约”）才委托旧路径。

### 10.4 QA 门禁重写（Phase C'，原则 R8）

计划 §2.8 预告“多个门禁以双档为前提，全自绘后会失败或失去意义”。本轮实测**其中有三个是真缺陷**：

| 门禁 | 故障 | 根因 | 修复 |
|---|---|---|---|
| `check_control_route_matrix` | `ValueError: Parsed 0 routed WidgetKind preferences` | 解析器只会读双层 `match` 的臂；路由殫缩为单返回值后无臂可读 | 改为读函数返回的常量；保留“若将来恢复 `match` 则报错”的完整性检查 |

**不作弊的证明**：三个门禁都是**按新架构的语义重写**，而非“改成永远通过”：

- 路由门禁：若真有后端恢复 `match`，解析器会**再次报错**，而不是静默报告“全部自绘”。

### 11.6 新发现的真缺陷：macOS surface resize 不重绘（BLUE14 F-5 复发）

重写 Apple 门禁时，`[B]` 检查发现 `src/platform/macos/canvas.rs` 的
`resize_surface` 用的是**单参 `setFrame:`**：

```rust
// 修复前
msg_send![view, setFrame: NSRect::new(...)];
msg_send![view, setNeedsDisplay: YES]; // 事后补一刀

// 修复后
msg_send![view, setFrame: NSRect::new(...) display: YES];
```

根因：`NSView` 实现的是 **`setFrame:display:`**；AppKit 不会为帧变化自动安排重绘。
单参调用依赖事后那句 `setNeedsDisplay:` 补救，而该消息在 resize 路径下并非总是到达。
这与 BLUE14 F-5 是同一类错误（当时是 `NSWindow` 的 `setFrame:` 缺 `display:`）。
门禁现在按名字检查双参选择器，**防它再次回来**。

### 12.3 59 个控件补齐契约（拆 3 批并行，互不重叠的写入集）

按目录切成 3 批（display+overlay+input / nav+container+dialog+misc / cupertino+menu+view），
每批只改自己的文件。每个控件的做法固定：

```rust
impl Widget for X { … impl_draw_bridge!(); impl_widget_property_hooks!(); }

impl WidgetProperties for X {

}
```

> **关键点**：`get` 读**控件自身真实状态**，而不是照抄旧 dispatch 的硬编码默认值。
> 例如 `CupertinoDatePicker.selected_date` 旧路径永远返回 `"2025-01-01"`，
> 现在读真实日期并按 ISO 格式化。

### 12.5 `visible` 四控件特例（schema 补全的正确边界）

给 155 张 schema 表补 `enabled/visible/tooltip/geometry` 时发现：**4 个控件的 `visible`
不是 base 可见性**，而是「弹出层/状态文字是否显示」：

`Tooltip`、`Popover`、`ModalBottomSheet`、`StatusBar`

因此默认值不能在开头一刀切：

```rust
"visible" if !matches!(kind, Tooltip | Popover | ModalBottomSheet | StatusBar) => {
 return Some(CapabilityValue::Bool(true));
}
```

> 若统一返回 `true`，这 4 个控件的默认值就是**错的**。这是「补全 schema」与
> 「尊重控件语义」的边界，写进代码注释以免后人再踩。

### 12.6 42 处 `UnknownProperty` → `ReadOnlyProperty`（原则 #30 的机械执法）

`UnknownProperty` 与 `ReadOnlyProperty` 回答**不同问题**：

- `UnknownProperty` —「没有这个属性」
- `ReadOnlyProperty` —「有这个属性，但不可写」

把只读属性回成 `UnknownProperty` 会让属性编辑器显示成「控件坏了」而不是「只读框」。
修法分两类：

| 类 | 控件 | 处置 |
|---|---|---|
| 真有 setter，只是没接线 | `FileDialog`/`FontDialog`/`InputDialog`/`ProgressDialog`/`DateTimeEdit`/`PieMenu`/`WebEngineView` | **接真实 setter**（比标只读更有价值）|
| 派生值，确无 setter | `Roller.item_count`、`MenuBar.entry_count/active_index/hovered_index`、各 `row_count`/`column_count`/`has_model` 等 | 显式 `Err(ReadOnlyProperty)` |

新增 `expect_datetime` 编解码对（`coercion.rs`），与既有 `expect_date`/`expect_time` 同构：
`DateTime` 的 `Display` 输出 `"<date> <time>"`，逆函数就该能解析它。

`SwipeToDismiss.is_dismissed` 同因由 `UnsupportedOnWidget` 改为 `ReadOnlyProperty`。

## 16. 第十轮（同日续跑）— `Signal::emit` 取证：补测试、抓 2 个真缺陷、否决一个优化

> 起因：质疑「信号槽是否最优」。原计划是「直接优化 `emit`」，
> 但改用**先取证**的路线。结果：**未改一行优化代码，却抓出 2 个真缺陷**，
> 并用基准证明原定的优化是**负收益**，从而避免了它。

### 16.1 方法：先补测试，再谈优化（原则 #18/#63）

`emit` 是全库约 **529 处** `.emit()` 调用的公共路径，且其 take/restore 设计
承载着一个微妙不变量：回调执行期间被**取出**（好让锁释放），
但 handle **留在** map 里（好让回调能 `disconnect` 自己）。

**此前该行为零测试覆盖**：`core_signal.rs` / `generic_signal.rs` / `hub.rs`
各有 **0 个测试**（仅 `mod.rs` 有 10 个，覆盖优先级/阻塞/作用域）。

新增 **12 个行为测试**（10 + 2）。首次运行 **3 个失败**，逐个取证如下。

### 16.2 缺陷一：`CustomSignalHub::emit` 持锁调用回调 → **死锁**（真 bug）

```rust
// 修复前 — src/signal/hub.rs:33
pub fn emit(&self, name: &str) {
 if let Some(signal) = self.signals.lock()...get(name) { // 锁被持有
 signal.emit(); // 回调里再 emit → 二次 lock
 } // Mutex 不可重入 → 永久阻塞
}
```

**根因**：`Mutex` 不可重入，而锁跨越了回调执行。

**症状**：无 panic、无日志，**整个线程静默卡死**。定位时我一度误判为
「编译慢」并去等超时——这是方法论错误。**正确做法是读代码**：
`hub.rs:33` 一眼就能看出是标准重入死锁，无需运行任何测试。

**修复**（先 clone `Arc`，再释放锁）：

```rust
pub fn emit(&self, name: &str) {
 let signal = {
 let signals = self.signals.lock().unwrap_or_else(|e| e.into_inner());
 signals.get(name).cloned() // 锁只覆盖查找
 };
 if let Some(signal) = signal {
 signal.emit(); // 锁外调用
 }
}
```

> **冰山法则核查**：`hub.rs` 共 9 处 `signals.lock()`。逐处检查后确认
> **仅 `emit` 一处**在持锁期间进入可能重入的调用；`disconnect`/`clear`/`len` 等
> 在锁内只做 map 操作，安全。

### 16.3 缺陷二：`emit` 的重入语义与注释不符

原注释声称：*"Callbacks may safely call … `emit` on the same Signal"*。
实测（探针取证）：**重入 emit 会静默跳过**正在栈上的那个槽——
外层已把回调 `take()` 走，内层 `take()` 得到 `None`。

| 阶段 | 结论 |
|---|---|
| 行为**是否正确** | ✅ **正确**。它让递归终止；否则「处理信号时 emit 同一信号」将无限循环 |
| 注释**是否正确** | ❌ **错误**。它只说了「不死锁」（确实），未提「不投递」 |

**处置**：**改文档不改行为**，并新增测试 `a_re_entrant_emit_skips_the_slot_still_on_the_stack`
把语义锁死——同时断言「嵌套 pass 确实运行了」与「跳过了栈上的槽」，
以免将来有人把它「修」成递归投递。

### 16.4 我自己写错的 2 个测试（原则 #64：不掩盖）

| 测试 | 我的错误 | 真相 |
|---|---|---|
| `a_slot_may_disconnect_itself…` | 闭包 `move` 走了 `h`，捕获的是 `0`，不是 `connect` 返回的 handle | 用 `Arc<AtomicU64>` 正确共享后 **自断开完全正常**（`disconnect` 返 `true`，槽被移除）|

> 还是**测试期望错**，再动手。第 1 个我差点去「修」本来正确的 take/restore 设计。

### 16.6 优化提案：**实测否决**（本轮最重要的结论）

按数据推出「单槽免快照」的优化——n=1 时跳过 `Vec`，理论可省 ~47 ns。
**写原型、同数据结构、同循环、同一次运行对比**：

| 场景 | 现行（快照） | 快路径 | 差值 | 判定 |
|---|---:|---:|---:|---|
| 1 槽 | 60.7 ns | 57.4 ns | **−3.3 ns** (−5%) | 微胜 |
| 2 槽 | 81.3 ns | 99.2 ns | **+17.9 ns** (+22%) | **回退** |
| 4 槽 | 129.4 ns | 154.3 ns | **+24.9 ns** (+19%) | **回退** |

**为何预期 47 ns 只兑现 3.3 ns**：`HashMap::len()` + `keys().next()` 对单元素 map
的开销**接近** `collect()`；而新增的分支让**所有 n>1 场景变慢**。

**结论**：3.3 ns 对 16.67 ms 帧预算是 **0.00002%**。改动**净负收益**，
**不实施**。原型文件与临时 bench 注册已删除（`git status` 确认 `Cargo.toml` 与
`benches/` 均无残留）。

### 16.7 最终回答「是否有更完美的方案」

**有，就是本轮走的这条路：先补测试取证。**

实测依据：本步**未改一行优化代码**，却
① 修掉 `hub` 的真死锁；② 纠正 `emit` 的错误注释并锁死语义；

而 `emit` 会平白慢 20%。
