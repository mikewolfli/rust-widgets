## 2. Phase C-0 — 【阻断】`as_draw_mut` 桥接补齐（原则 #66）

**目标**：使「实现了 `Draw` ⇒ 可经 `dyn Widget` 被绘画」在编译期成立，
覆盖从 **6/168** 提升到 **全部**。

### C-0-1 问题定性（本轮实测复核）

```text
$ grep -rhn "impl Draw for" src/ --include=*.rs | sed 's/.*for //;s/[ <{].*//' | sort -u | wc -l
167

$ grep -rn "fn as_draw_mut" src/ --include=*.rs | wc -l
7        ← 6 个控件手写 + 1 个 trait 默认实现（返回 None）
```

而 `widget::runtime::render_frame` 的唯一取绘画通道是 `Widget::as_draw_mut`
（`src/widget/runtime.rs:198`），返回 `None` 即无帧可贴 → **空白面且无报错**。

### C-0-2 实现方式（方案 2：宏，零成本）

**为何不用 blanket impl**（计划方案 1）：`impl<T: Draw> Paintable for T` **能编译但不可用**——
trait 选择需要**具体类型**，而 `&mut dyn Widget` 已把类型擦除；blanket impl 只能经泛型约束
`W: Draw + Widget` 触达，而 `Box<dyn Widget>` 不满足。**这正是 `as_draw_mut` 存在的原因。**

**采用方案**：`src/widget/draw_bridge.rs` 提供 `impl_draw_bridge!()` 宏，在控件**自己的
`impl Widget` 块内**展开为：

```rust
fn as_draw_mut(&mut self) -> Option<&mut dyn Draw> { Some(self) }
```

- 零运行时开销（原则 #28）：无查表、无 `TypeId`、无 thread_local。
- 在**具体类型可见处**生成，因此 `Some(self)` 是全函数，不可能错。
- 用 `#[macro_use]` 挂在 `widget::draw_bridge` 模块上，各控件文件无需额外 import。

### C-0-3 批量注入（一次迁移，脚本已删除）

本轮用一个 brace-aware 的临时脚本（`scripts/insert_draw_bridges.py`）定位每个
`impl Widget for X` 的匹配右花括号，仅当同文件存在 `impl Draw for X` 时插入桥调用：

```text
159 bridges inserted across 155 files
```

**脚本已在迁移完成后删除**（原则 #59「删除即删除」）：它是一次性迁移工具，
保留一个无人引用的「向每个文件插入」脚本会误导后人重复执行；永久机制是
`impl_draw_bridge!` 宏本身（新控件只需在自己文件里写一行）。

### C-0-4 覆盖度审计（编译期等式，原则 #19）

```text
Draw 类型 ....................... 167
既有 Widget 类型 ................ 166
Widget 实现 Draw 的数量 ......... 166 / 166   ← 全部
Draw 实现 Widget 的数量 ......... 166 / 167
```

**结论：不变式 `Widget + Draw ⇒ 可绘画` 成立，零例外。**

> 计划 §10.1 预计「168 个 Draw 类型」，本轮实测为 **167**；计划预计存在
> 「不绘画的控件」，实测**不存在**（所有 `Widget` 都实现 `Draw`）。以实测为准（原则 #64）。

### C-1-3c 一个设计决定：`property_names()` 必须含共性四属性

迁移中发现两类写法不一致：部分控件只返回自己的属性。但**旧 `*_PROPERTIES` schema 表
包含 `enabled`/`tooltip`**——即「已发布属性」本来就包含共性部分。若只返回自有属性，
消费方（schema 生成器、文档、属性编辑器）会误以为 `enabled` 不存在。

**裁定**：`property_names()` 必须发布**自有 + 共性四**（`enabled`/`visible`/`tooltip`/`geometry`）。
实现方式：`property_names_of![..., BASE_PROPERTY_NAMES]`（宏末位标记展开为四个字面量，
因为 `'static` 切片无法在 `const` 中拼接）。共更新 79 + 14 处调用点。

```rust
        match name {
            "text"    => Ok(CapabilityValue::String(self.text().to_string())),
            "pressed" => Ok(CapabilityValue::Bool(self.is_pressed())),
            "default" => Ok(CapabilityValue::Bool(self.is_default())),
            _         => base_property_get(self, name),   // ← 共性回退
        }
    }
    fn set(&mut self, name: &str, value: CapabilityValue) -> Result<(), CapabilityAccessError> {
        match name {
            "text"    => { self.set_text(expect_string(value)?); Ok(()) }
            "pressed" => { self.set_pressed(expect_bool(value)?); Ok(()) }
            "default" => { self.set_default(expect_bool(value)?); Ok(()) }
            _         => base_property_set(self, name, value),
        }
    }
    fn property_names(&self) -> &'static [&'static str] {
        property_names_of!["text", "pressed", "default"]
    }
```

## 4. 阶段顺带修复的架构缺陷（计划外，原则 #2/#3/#11）

本轮在推进 A/C-0/C-1 时发现并修复了 3 个缺陷，均回到根因，不留在后续阶段。

### 4.1 「能力契约」被误置于 device profile 门禁之下

**现象**：`cargo check --no-default-features --features embedded` 报 **47 个错误**，全部形如
`cannot find 'capability' in 'widget'`。

**根因**：`src/widget/mod.rs` 把整个 `capability` 模块 gate 在
`any(desktop, tablet, mobile)`；而 C-1 新加的 `Widget::properties_dyn` 钩子（在
`widget_trait.rs`）及已迁移控件的 `impl WidgetProperties` 都引用它。**是我在 C-1 引入的回归**，不是既有问题。

**修复**（回到根因，而非给调用点逐个打补丁）：能力契约与其 profile 相关部件分离——

| 组件 | 门禁 | 理由 |
|---|---|---|
| `properties_trait`（契约） | **无**（全档） | `Widget` 全档存在，契约随它 |
| `types` / `coercion`（纯类型与转换） | **无**（全档） | 无设备依赖；`coercion` 内部对 `Date`/`Time` 等逐项 `full_widgets` 门禁 |
| `properties` / `access` / `constructors` / `registration` / `WidgetFactory` | `widgets_unstripped` | 逐个枚举具体控件，仅在完整控件集下存在 |
| `capability::tests` | `widgets_unstripped` | 测的是工厂 |

同时把 `alignment_to_str` / `check_state_to_str` / `orientation_to_str` 三个**纯转换**从
`access`（device 门禁）移入 `coercion`（全档），`access` 改为 `pub use` 转发。

**证据**：

```text
修复前：cargo check --no-default-features --features embedded
        error: could not compile `rust_widgets` (lib) due to 47 previous errors
修复后：cargo check --no-default-features --features embedded
        Finished `dev` profile [unoptimized + debuginfo] target(s)
```

### 4.2 `StubPlatform` 的假能力：任何控件都「支持」三态

**现象**：`cargo test --no-default-features --features embedded --lib` 有 1 个失败
（**先于本轮改动已存在**，子代理取证确认）：

```text
platform::contract_tests::contract_tristate_refused_on_non_checkable ... FAILED
  embedded-runtime-stub: a label is not checkable
```

**根因**：`StubPlatform::set_widget_tristate` 只检查「控件存在」，对 `Label` 也返回 `true`；
而真实后端（`platform/macos/platform_impl.rs:2307`）会校验 kind：

```rust
if !matches!(handle.kind,
    HandleKind::CheckBox | HandleKind::RadioButton | HandleKind::ToggleButton) {
    return false;   // macOS 正确拒绝
}
```

即：**stub 报告了一个它并不具备的能力**——正是原则 #12（假修复）/#37（能力缺失必须诚实）禁止的。

**修复**：新增 `StubPlatform::is_checkable_kind()`，与真实后端同样的三个 kind；
`set_widget_tristate` 拒绝非 checkable，`is_widget_tristate` 同样返回 `None`
（读侧与写侧一致，否则会用一个存储的 `false` 暗示问题本身有效）。

**证据**：

```text
修复前：test result: FAILED. 1478 passed; 1 failed
修复后：cargo test --no-default-features --features embedded --lib -q
test result: ok. 1479 passed; 0 failed
```

### 4.3 测试与全自绘架构相反

`src/widget/runtime.rs` 的 `native_widgets_do_not_claim_the_draw_bridge` **断言 `Button` 不可绘画**，
与 BLUE15 #55（每个控件都由库自绘）直接相反。按用户指令「与最新架构不一致的 test 必须改造」，
已**替换**为 `built_in_controls_claim_the_draw_bridge`（断言 `Button`/`CheckBox`/`Label` 可绘画）。
