## 2. 批 1 —— 基类（收益最大：一次修好全部 188 个控件）

### 2.1 A-1 【BLOCKER】`set_enabled` / `set_hovered` / `set_pressed` 的重解析形状

**取证：先行进程的形态有一个真缺陷。**

它把重解析写成 trait 默认方法加 `where Self: Sized`：

```rust
fn set_enabled(&mut self, enabled: bool) where Self: Sized { … }
```

**这在本仓不成立**：`where Self: Sized` 让方法**无法通过 trait object 调用**，而本仓到处
把控件当 `Box<dyn Widget>` / `&mut dyn Widget` 持有（`draw_bridge`、mount registry、
factory、`CarouselPage::content`）。8 个调用点被迫退化成 `<dyn Widget>::set_enabled(..)`：

```text
src/widget/capability/properties_trait.rs:86
src/control_backend/custom/create_widgets_helpers.in.rs:197
src/widget/container_widgets/carousel.rs:1005
src/widget/base_widgets/{button,radiobutton,toggle_button}.rs
src/widget/display_widgets/switch.rs
```

**根因**：默认方法体里的 `&mut Self → &mut dyn Widget` 是一次 **coercion**，coercion 需要
`Sized`；而 coercion 的目标（trait object）本身就要求 concrete — 这是一个**逻辑死结**：
要么加 bound（对象不安全），要么让控件**自己**完成 coercion。

**修法（选后者）**：新增一个**对象安全**的 trait 方法 `set_state_theme_hook(&mut self)`，
默认空实现；每个控件在自己的 `impl Widget` 块里覆盖为
`crate::style::reapply_active_theme_state(self)`（此时 `Self` 是具体的，coercion 合法）。
三个默认方法改调 `self.set_state_theme_hook()`。

```rust
// src/widget/widget_trait.rs
fn set_state_theme_hook(&mut self) {}          // 对象安全，默认空

fn set_enabled(&mut self, enabled: bool) {
    if self.base().is_enabled() == enabled { return; }   // 幂等，见 A-1 计划
    self.base_mut().set_enabled(enabled);
    self.set_state_theme_hook();
}
```

**注入到全部 185 个控件**：一次性 codemod（脚本已删除，不留在仓库），按
`fn base(&self) -> &BaseWidget { … }` 块定位，紧接其后写入 hook 覆盖。
185 个文件命中，其中 `draw_bridge.rs` / `properties_trait.rs` 的命中落在**文档注释**里，
已手工撤回（写进文档串会被编译成多余代码，是 codemod 的已知陷阱）。

### 2.2 A-1 的两个**真缺陷**：`Button` / `CheckBox` 的 override 绕过重解析

**注入测试后实测暴露（不是推测）**：

```text
---- a_state_change_after_theming_re_resolves_the_state_key ----
left: Some(rgb(33,150,243))            ← button:disabled **没有**生效
right: Some(rgb(7,8,9))
```

**根因（两个，都在 override 里）**：

1. `Button::set_enabled` 覆盖了 trait 默认，转调 `set_enabled_state`，而后者只写 base、
   不调 hook ⇒ `button:disabled` 不可达。
2. `Button::set_hovered` / `set_pressed`（及 `Switch` / `RadioButton` / `ToggleButton` 的同名
   方法）**先自己写了 base 字段**，再委托 `<dyn Widget>::set_*`；trait 默认的幂等 early-return
   因此看到「值已相等」而直接返回 ⇒ **hook 永不执行**。这是「委托 + 幂等」组合出来的
   顺序缺陷，正是原则 #39.1（`handle_event` 顺序是真契约）的同类。

**修法**：override 不再自己写字段，**整体委托**给 trait 默认（默认内既有幂等写、又有 hook）：

```rust
pub fn set_hovered(&mut self, hovered: bool) {
    <dyn Widget>::set_hovered(self, hovered);   // 写字段 + 重解析，early-return 在默认里
}
```

`Button::set_enabled_state` 加 `was_enabled != enabled` 守卫后调 `self.set_state_theme_hook()`。
`CheckBox::set_enabled` 同样补 hook。

### 2.3 B-1 【BLOCKER】主题 `padding` / `margin` / `spacing` 到达控件

**取证**：`theme/manager.rs:401-402` 写入 `padding: Padding::all(spacing.medium)` /
`margin: Margin::all(spacing.small)`；`style/primitives.rs` 的 `merge_theme` 与 `merge`

```rust
if self.margin  == Margin::default()  { self.margin  = other.margin;  }

// merge_theme() theme_derived 分支：整体替换（第二次主题应用必须换掉上一次的几何量）
self.padding = other.padding;
self.margin  = other.margin;
self.spacing = other.spacing;
```

`spacing` 是 `Option<u32>`，沿用既有 `Option` 规则。

## 16. 顺带修出的**预存在快照缺陷**（冰山法则，本轮的第二个大收益）

图标雪碧图接进 `check_svg_snapshots.sh` 后，门禁报出 **4 个控件快照**与重新生成不一致。
它们与图标无关，而是**预存在**的；逐一取证后分两类：

### 16.1 真缺陷：`switch.svg` 快照定格在**动画中途**

```text
已提交：  track fill rgba(75,82,76)   ← off→on 端点色的混合（travel ≈ 0.10）
重新生成：track fill rgba(100,181,246) ← 稳定的 on 色
```

**根因**：`sample_fill` 打开 switch 的 `set_checked(true)`，**启动了 travel 动画**；导出器接着
画**下一帧**，于是快照定格在 travel ≈ 0.10 处 —— 一个用户**永远停不住**的中间帧。它不是 off 态
也不是 on 态。A-2 修复把 ON 端点从 `Success` 强调色换成主题声明的 `switch:checked` 填充，于是同一个
中途混合算出了不同颜色（**修复让预存在缺陷变得可见**，不是修复造成了它）。

**修法**：导出器新增 `settle()` —— 在画之前把可收敛的动画推到静止点。四个**永远动**的控件
（`spinner`/`skeleton_loader`/`code_editor`/`terminal_view`）没有静止点，被画在**固定相位**
（`MAX_SETTLE_TICKS`），这正是“可重现的快照”对永动动画应有的定义。

**连带发现**：`switch.svg` 与 `switch_on.svg` 修后**逐字节相同** —— `sample_fill` 本就把 switch 打开，
所以默认文件已经展示了 on 态，`switch_on` 是“多一个文件、不多一条信息”的产物。按原则 #4 删除该
extra appearance（extras 7 → 6），并在 `EXTRA_APPEARANCES` 注明 switch 的**off** 态仍是真实缺口。

### 16.2 善意位移：B-1 的几何变化（计划 §7 已预告）

`calendar` / `command_link` 的快照变化是**几何位移**：B-1 让主题的 `padding`/`margin` 真正到达控件，
于是控件内的元素按主题间距移动（`calendar` 的高亮 rect `x=206 → x=26`，`command_link` 文字左移 8px）。
计划 §7 明写“会大范围移动快照的一步放最后”，这正是那一步。逐条审阅后接受并重生。

### 16.3 第三个真缺陷：`icons` feature 在 CI 中**从未被编译**

继续扫描时发现：`.github/workflows/ci.yml` 的每个作业都只跑 device profile（`desktop`/
`tablet`/`mobile`/`mini`/`embedded`）或 `gtk-native`/`wasm`，**从不包含 `icons`**。

这意味着 `tests/icon_census_test.rs` 与 `tests/icon_data_integrity_test.rs` 的 `#![cfg(feature = "icons")]`
在 CI 中**永远为假** —— 两个测试文件被编译为空，无论图标数据或 draw 路径怎么坏都 **不可能失败**。
“不跑的测试不是测试”（原则 #11 的同精神）。

**修法**：`ci.yml` 新增两步 —— `cargo test --features "desktop,icons"` 与对应 `clippy -D warnings`。
`desktop,icons` 是唯一能同时到达 draw 路径与数据的组合（`icons` 单独没有 device profile，
SVG 后端与文本层都不在）。

### 17.1 §8.4 `ROW_ROWS` —— 一个 332 项的恒等表

原文档称“a macro expansion cannot do arithmetic on a `static`”，所以生成了
`ROW_ROWS = [0, 1, 2, …, 331]` 供宏做 `EVENT_SCHEMAS[ROW_ROWS[start]..ROW_ROWS[start+len]]`。

**先取证再动手**（原则 #1）：写 `examples/probe_row_rows.rs` 实跑，`const fn` 索引 `static`
**编译通过且结果正确** —— 原断言为假。又验证该表确为恒等：`vals == list(range(len(vals)))` → `True`。

**修法**：`CONTROL_STARTS` 的 `start`/`len` **本就是绝对索引**，所以宏直接写
`&EVENT_SCHEMAS[start..start + len]`。同步改**生成器**（`derive_event_payloads.py` 的 `HEADER`
模板与 `render()`），否则下次重生会把删除又写回来（**实测确实如此** —— 第一次只改了生成物，
`--check` 又把它恢复成 `ROW_ROWS` 形式，这正是“生成器是唯一真相”的价值）。

### 17.2 §8.5 魔数键码 —— 41 处字面量、19 个文件

新增 `src/event/key_codes.rs`：`ENTER`/`LINE_FEED`/`ESCAPE`/`BACKSPACE`/`DELETE`/`SPACE`/
`TAB`/`LEFT`/`UP`/`RIGHT`/`DOWN`/`HOME`/`END`/`PAGE_UP`/`PAGE_DOWN`。

**为什么是常量而不是 `Key` 枚举**：`Key` 是**语义**词汇（有 `from_key_code` 解析器），
但让每个处理器在**每个按键事件**上跑一遍 ~120 臂的 `match` 去回答“这是不是 Enter”，
是事件循环热路径上的浪费。常量是“已知形状”的廉价形式；语义判断仍走 `Key`。

**为什么值可信**：每个常量都等于 `Key::from_key_code` 映到对应变体的值，由
`event::key_codes::tests::every_constant_agrees_with_the_shortcut_parser` **对拍断言**；
三个别名（`LINE_FEED`↔`ENTER`、`DELETE` 的 `127` 拼法）另有第二个测试钉住。
这就是 C-7 那类“两张表必须一致”的形状，只是这次用测试而不是门禁。

**同源清理**：`keyboard.rs` 的 `16`/`0` 也具名（`SHIFT_CODE`/`NO_KEY`，本地常量，
因为 Shift 是**板上**键、由板的布局表赋值，不是框架约定）。

**迁移验证**：全仓 `grep '\*key == <digit>'` 现只剩 `key_codes.rs` 的文档举例。

### 17.3 第三个真缺陷：`check_implicit_size_uses_metrics` 因**行号键**而长期错报

齿轮键门禁在终点报出 **1 FAIL**（`check_implicit_size_uses_metrics`，`failed=101`）。
逐一取证后：**不是本轮引入的**，而是一个长期存在的门禁设计缺陷。

**根因**：豁免表 `tools/implicit_size_exemptions.txt` 以 `path:行号` 为键。实测：

```text
226 个豁免条目中  156 个行号已失效
```

任何在 `size_hint` 之上的编辑（一个 import、一个常量、一段文档）都会使该行号漂移，
豁免随之失效，门禁把已登记的债务重新报为新发现。**一个永远失败的门禁等于没有门禁**
（与原则 #59“门禁必须可读完”同精神）。

**为何“重指向行号”不是修法**：下一次编辑又坏。

**修法**：把键从 `path:行号` 改为 `path:所属类型`（新增 `owner_of()`，从 `size_hint` 处
**向上**数花括号定位最近的 `impl` 头）。这保留了原设计意图——
“同一文件里的第二个 `size_hint` 不能继承第一个的豁免”——因为键里带着**类型名**，
而类型名不随无关编辑漂移。

**反向注入已证**：删掉 `Dial` 那一条豁免 ⇒ 门禁立即红
（`dial.rs:268: size_hint derives its answer without ControlMetrics`，`failed=1`）；
恢复后 `failed=0`。

**本轮的连带影响**：我在 `keyboard.rs` / `search_bar.rs` 加常量与 import 时，
确实把这两条旧键弄失效了——这正是旧键法不可用的直接证据。

### 17.4 第四个真发现：D-10 / D-11 实际上**未修**（前轮误报为已完）

按“完成率回写”复查 D 组逐条时发现：**D-10 与 D-11 在本计划中从未真正实施**。
表格里写的 11/11 是错的——**这就是为什么必须逐条核对而不是相信汇总。**

#### D-10 两个后端对行盒的推导**不一致**

```text
src/render/pipeline/containers.rs:81   effective_line_height() * scale          ← 无下限
src/render/svg/backend.rs:982         effective_line_height().max(1.0) * scale ← 有下限
```

**实测差异**（探针）：`size = 0` 时，软件后端 `ascent = 0`，SVG 后端 `ascent = 1`。
两者 `height` 都是 1，但 **baseline 位置不同** —— 一个控件按其中一个后端量出行盒，
在另一个后端就会画偏。两份文件的注释都写着“the two backends must agree”，而**无任何东西在检查它**。

**修法**：把推导提到 `TextMetrics::for_font(font, scale)`（`src/render/core/types.rs`），
两处后端各自改为 `TextMetrics { width, ..TextMetrics::for_font(..) }`。
**钳制只在唯一一处**，正如计划 §D-10 要求的“抽一个共享 helper”。

**反向注入已证**：把软件后端改回无下限写法 ⇒
`both_backends_agree_on_a_fonts_line_box` 红，并**指名**该字体与倍率：

```text
assertion `left == right` failed: the software and SVG backends disagree about the line box
for Font { family: "Sans", size: 0.0, ... } at 1x
```

#### D-11 两处 `unreachable!()` 仍在

计划说“同 crate 的 `image/cache.rs:749-751` 已采用『写出该分支』的写法”，要两处照做。实测两处都**仍是 panic**：

1. `image/format.rs:303` `ImageData::Rgba8(_) => unreachable!()` —— 改为写出这个幂等分支
   （`ImageData::Rgba8(d.clone())`）。即使今天到达不了，它的代价只是一个早退已付的 `clone`，
   而收获是：守卫被拍扁后**不会变成绘制路径上的崩溃**。
2. `image/decoder.rs:213` `_ => unreachable!("decode_animation validates the format before dispatch")`
   —— 改为**返回与调用方同一条错误**。保证因此只在**一处**陈述：调用方的 `match`，
   而不是一个 `match` 加一个 panic。

**反向注入已证**：`a_static_format_is_refused_by_the_animation_decoder_without_panicking`
断言 PNG 输入返回含 “GIF or WebP” 的错误而非 panic。
