## 1. §3 — `LineState` 的可判定性

**问题**：`line_state(line)` 对绘制路径未走到的行返回 `LineState::Clean`（`Default`），与"该行确实干净"
共用一个表示；`tokens_on_line` 的结果因滚动历史而变。

**改动**（`src/widget/special_widgets/code_editor/editor.rs`）：

| 新增 | 作用 |
|---|---|
| `line_state_is_known(line) -> bool` | 区分"已证明"与"未 lex" |
| `resolve_line_state(line) -> LineState` | 推进入口状态链到该行后返回真实状态 |
| `tokens_on_line_resolved(line) -> Vec<TokenSpan>` | 先证明入口状态再分词，去掉对绘制历史的依赖 |

`line_state` / `tokens_on_line` 的文档补上"这不保证什么"，指向上面两个入口。

**为何不加 `Unknown` 变体**（feedback 建议 1 的另一半）：`LineState` 是 `Copy` 且被用作缓存数组的
元素类型（`Vec<LineState>`），加一个"未知"变体会让**每一个**缓存槽携带一个永不出现的状态，并把
"是否已证明"从行级事实变成需要逐槽判定的伪事实。feedback 建议 2（公开推进入口）以更小的形状给出
同一个能力，且不改变已有调用方的类型。这是**偏离建议、保留能力**的选择，写明在此以便复核。

**证据**：
```text
$ cargo test --no-default-features --features desktop --lib code_editor
  an_unproven_line_state_is_reported_as_unknown_and_can_be_resolved ... ok
  resolved_tokens_are_independent_of_paint_history ... ok
```

## 2. §6 — `quit()` 跨线程

**改动**：
* `Platform::quit(&self)` → `Platform::quit(&self) -> bool`。`true` = 请求已投递到循环所在线程；
  `false` = 本后端无法从此线程投递（调用方须自行收尾）。**11 个后端逐个实现**，
  不再有"静默 return `()`"。
* macOS 由"log 后静默返回"改为 **`false`**——`-[NSApplication stop:]` 是主线程限定，且
  `performSelectorOnMainThread:` 被 `check_apple_thread_safety.sh` 规则 C 禁止、本 crate 也不链接
  dispatch，因此"无法投递"是唯一诚实答案，必须可被调用方读到。
* `runtime::quit`、`profile::runtime_quit`、`lib.rs::quit` 逐层传递该 `bool`。
* `lib.rs`/`Platform` 的文档写明"`Ok` 不等于已停止"。

**未覆盖**：feedback 建议 2（`schedule_on_main(after, f)`）未做——那需要新增一个主线程调度原语，
而本机（linux，无 GTK）无法实测其行为，按原则 #38「探测判据必须经实测验证」不凭 API 名称实现。

**证据**：
```text
$ cargo check --all-targets --no-default-features --features desktop    → Finished
$ cargo check --no-default-features --features {mini,embedded,tablet,mobile,wayland-native,harmony,mobile-api,wasm}
  → 全部 Finished（lib）；`--all-targets` 在 wayland-native/harmony/mobile-api/wasm 上报
    icon.rs 的 `IconName::data` 不存在——**改前即存在**（`git stash` 后同样报），与本轮无关。
```

## 3. §8.1 / §8.5 — `file_dialog`：前提被实测推翻，能力位删除

### 3.1 报告的前提不成立

feedback §8.1 以 `create_file_dialog(0, 0, 0, 640, 420) == 0` 推断"桌面后端没有文件对话框"。
**实测**（本机 linux/x86_64，`--features desktop`）：

```text
$ (探针：对 17 个公共 create_* 各调一次)
parent = 0           → MOUNTED (0): ；ZERO (17): button checkbox line_edit label radio_button
                       slider progress_bar combo_box list_box list_view scroll_area spin_box
                       message_box file_dialog color_dialog font_dialog panel
parent = 真实窗口 id → MOUNTED (17): 全部成功，含 file_dialog=6000285942072475662
```

**结论**：`0` 是"父级不可用"的文档化答案，对**每一个**非窗口控件都一样，与"是不是对话框"无关。
源码判据：`src/control_backend/custom/mod.rs:222` 起

```rust
if kind != WidgetKind::Window {
    if parent == 0 || !crate::widget::runtime::is_mounted(parent) {
        log::warn!("custom backend: refusing to create {name:?} under parent {parent}, ...");
        return 0;
    }
```

文件选择器不是一个缺失的原生能力，而是**与其他 16 个控件走同一条自绘创建路径**的普通控件。

### 3.2 因此删掉 `file_dialog` 能力位

我在初版实现里按 §8.5 加了 `PlatformCapabilities::file_dialog`。复核后删除，理由三条：

1. **它是机制泄漏**：其文档写作"the backend can present the host's own file chooser"，把
   「宿主的 = 原生 / 库的 = 自绘」这一**机制**选择搬上公开 API，违反原则 #4/#52（调用方只表达
   "我要一个这样的控件"）。
2. **它是常量 `false`**：没有任何后端 override `create_file_dialog`，8 个后端全写 `false`，
   即"有个形状但背后没有东西"——正是本仓库删除 `DesktopBackend` 枚举时记录的那一类。
3. **它建立在被推翻的前提上**（3.1）。

保留 `clipboard` 与 `open_external`：那是**真**宿主服务（无法自绘"用用户浏览器打开这个 URL"），
且各后端取值确实不同（macOS/Windows/GTK `true`，wayland/mobile/wasm `false`）。

**同时**保留并强化 §8.1 的**真实**缺口修复：`FileDialog` 是自绘控件，宿主负责列表，因此
选择必须能从 `ObjectId` 写入（见 §4）。

### 3.3 补一条家族级测试（冰山法则）

`tests/create_family_requires_a_live_parent_test.rs`（新增）：对 17 个公共 `create_*`
断言 ①`parent = 0` 时**全部**返回 `0`；②真实窗口父级下**全部**创建且 id 互不相同。
它把"报告里那一次调用"升级为"整类契约"，使"只有对话框是坏的"这种误读无法再从单次调用得出。

**反向注入（实测）**：把 `custom/mod.rs` 的父级守卫改成 `if false {`，
`every_control_refuses_the_no_parent_id` **立即变红**，并列出全部 17 项（含 `file_dialog`）；
恢复后绿。注入与恢复通过 `cp` 备份完成，工作树确认无残留 diff。

## 6. §8.4 / §9.1 / §9.2 / §9.4

### §8.4 `AssetWatcher`
* 新增本 crate 自有 `ChangeKind { Created, Modified, Removed, Renamed }` 并 `pub use`，
  `AssetEvent::FileChanged.kind` 由 `notify::EventKind` 换成它——消费者不再需要一份 `notify`
  依赖才能 match（原则 #54）。
* `change_kind_of` 投影：`Create`→Created、`Remove`→Removed、`Modify(Name(_))`→Renamed、
  其余 `Modify`→Modified、`Access`/`Any`/`Other`→不报。
* 测试 `change_kind_projects_every_reported_change_and_drops_access` 覆盖五条分支。

### §9.1 `TreeView` 层级
* 新增 `NodeView { label, depth, has_children, expanded }`；`TreeModel::node(index)` 默认由
  `node_path` 派生**扁平**节点，因此既有扁平模型渲染与文档行为完全不变。
* `visible_indices()` 公开**可见投影**（祖先全部展开的行），新缩进为 `(depth + 1) * 15`
  ——depth 0 即历史上的单一 15 px，扁平模型的画面因此逐像素不变（快照 diff 只多出展开三角）。
* 选择/焦点/悬停改用**模型下标**存储，展开状态与 `ItemDelegate` 用模型下标作键，公开访问器
  与信号载荷用可见下标，`model_index` / `visible_indices` 提供两者的映射。
* 展开三角按同一几何绘制与命中；点击三角 = 展开/折叠，点击标签 = 仅选中；
  `Left`/`Right` 键折叠/展开。
* **逐帧成本（自查发现的回归，已修）**：初版绘制循环对每一行调用 `disclosure_rect(visible)`，而它
  会为解析该行的节点重新走一遍**可见投影**，于是单帧成本变成 `行数 × 节点数`（实测 401 节点、
  401 行时 12 072 次模型查询）。修法：把投影提出循环（改前已在 `draw` 顶部算好一次），三角几何
  改为自由函数 `disclosure_box(row, depth, has_children)`，只吃循环手上已有的事实；`node_at`
  改走非分配的 `visible_row_count()`（命中测试每次指针移动都会跑）。修后同帧 830 次查询（≈2N）。
* 能力表新增 `has_delegate`、`expanded_focused_node` 属性与 `expand`/`collapse`/`toggle` 命令
  （沿用 `cascader` 已有的拼写，命令表与 `command_schema` 门禁同步）。
* `sample_data::tree_rows` → `tree_nodes() -> Vec<NodeView>`，快照现在画出真实层级与三角。
* 测试 9 个（层级投影、折叠隐藏、叶子拒绝展开、跨折叠的选择稳定、三角几何、点击三角、
  就地编辑、命令、逐帧成本）。

### §9.1a 逐帧成本测试的反向注入（两次，第一次是假绿）

新增测试 `a_frame_does_not_look_up_the_model_once_per_row` 断言"单帧模型查询次数 ≈ 2×节点数"，
而不是"节点数 × 行数"。**它第一次并不咬人**，两处原因都实测出来了：

1. 初次注入（把绘制改回逐行 `disclosure_rect`）**通过**。探因：三角只对 `has_children` 的行计算，
   而我的 fixture 只有**根**一个分支，逐行重算因此只发生 1 次，没有可乘的东西。
   → 改 fixture 为"根 + 400 个**分支**子节点"，使每一绘制行都走该路径。
2. 改 fixture 后**仍然**测不准：固定版被判失败（1632 次 > 我设的 4N 上限 1604）。探因：测试自身
   在绘制**前**调了一次 `view.node_count()` 建立断言前提，那一次合法地走了投影并把计数算进了帧内。
   → 加 `reset_lookups()`，在绘制前清零，只测这一帧。

修正后：
```text
固定版：  test result: ok          （830 次查询 / 401 节点 ≈ 2N）
注入版：  FAILED — one frame made 12072 model lookups for 401 nodes and 401 rows
```
两次都是 `cp` 备份 → 修改 → 跑 → 还原，工作树确认无残留。

### §9.2 `TreeView` 就地改名
复用 `ItemDelegate`（与 `TableWidget` **同一个** trait，不另造孪生）：
`begin_edit`/`commit_edit`/`cancel_edit`/`editing_node`，以**模型下标**寻址（`column = 0`），
使展开/折叠不会在编辑过程中改换寻址。

### §9.4 掩码字段复制
* 新增 `LineEdit::clipboard_selection() -> Option<String>`：`Normal` 复制真实文本、
  `Password` 复制**与绘制一致的 `*` 掩码**、`NoEcho` 不复制。
* `copy_selection_to_clipboard`（`Primary+C`）与 `Primary+X` 都改走它；剪切的**删除**仍按
  "有选择"判定并发发生效，所以密码框里的剪切依旧删掉内容。
* `selected_text()` 保持返回真实值（宿主存钥匙串需要它），文档写明剪贴板路径是另一个读者。
* 测试 2 个。**未覆盖**：本机无剪贴板后端（`platform_clipboard()` 为 `None`），
  因此只验证到"写入剪贴板的内容"这一层，未观察系统剪贴板的实际落点。

### 8.1 一次需要记下的假阴性（并发竞争，非代码缺陷）

## 1. 分析：`platform_clipboard()` 为什么是 `None`（用户问题 2）

先把"事实"和"机制"分开。事实来源是**逐后端核对源码**，不是按名字推测：

```text
$ grep -rn "fn clipboard_backend" -A3 src/platform/*/platform_impl.rs
src/platform/macos/platform_impl.rs:656     → Some(&self.clipboard)          （cocoa：真 NSPasteboard）
src/platform/windows/platform_impl.rs:1227  → Some(&self.clipboard)          （Win32 clipboard）
（linux / wayland / android / ios / harmony / wasm / macos_objc2：无覆写 → 继承 trait 默认 None）
```

所以 `None` 有三层原因，**不是一个原因**：

1. **类型层面**：`src/platform/clipboard_stubs.rs` 里只有 macos、windows、macos_objc2、linux、wasm
   五个模块定义了 `RichClipboardBackend` 实现；`android` / `ios` / `harmony` / `wayland`
   **连一个实现类型都没有**（`grep -rn "RichClipboardBackend" src/platform/` 的结果里没有它们的名字）。
   `clipboard_backend()` 无从返回一个不存在的类型。
2. **刻意的诚实**：`LinuxClipboard`（`clipboard_stubs.rs:684` 起）存在，但它的文档明确写着
   "**no `Platform` backend returns this type from `clipboard_backend()`**"，因为它的 `set_contents`
   只写进程内记录、永远返回 `false`。也就是说：Linux 侧当时**唯一**的 rich 实现被有意藏起来，
   以免宿主把"能读到值"误当成"写进了系统剪贴板"。
3. **文本路径本身也不对称**：Linux 的 `set_clipboard_text` 在 `gtk-native` 下会写 GDK 显示剪贴板，
   而 `get_clipboard_text` **只读进程内记录** —— 写出去的那份再也读不回来，
   别的应用放进剪贴板的内容也永远看不到。feedback §8.5/§8.6 观测到的"`platform_clipboard()` 为 `None`
   且无法区分空/非文本"，就是这个状态的两个面。

**结论**：`None` 不是"操作系统没有剪贴板"，而是"**库没把宿主已有的剪贴板接上**"。
本机实测：macOS 上 `platform_clipboard()` 一直是 `Some`（cocoa 后端），`None` 只出现在
未接线的后端上。因此"补足"的正确形态是**为每个装机 SDK 可及的平台补上真实实现**，
而不是改 `None` 的语义。

**各平台补足路径的可行性（先取证，再动手）**：

| 平台 | 判据 | 结论 |
|---|---|---|
| iOS | `objc2-ui-kit-0.3.2` 已在本 crate 依赖表内；`UIPasteboard::generalPasteboard/string/setString/dataForType` 均为安全方法且类非 `MainThreadOnly` | 可实现 |
| Android | `android_jni.rs` 已有 `JavaVM` + `Activity Context` 基建；`ClipboardManager` 是 `Context` 服务 | 可实现 |
| HarmonyOS | `$HOS_SDK_HOME/18/native/sysroot/usr/include/database/{pasteboard/oh_pasteboard.h,udmf/{udmf,uds}.h}` 存在；`libpasteboard.so`/`libudmf.so` 的 `dynsym` 里 `OH_Pasteboard_*`、`OH_Udmf*`、`OH_Uds*` 符号齐全 | 可实现 |
| macos_objc2 | `MacOsObjc2Clipboard` 早已写全（文本+HTML），只是**没人返回它** | 接线即可 |
| Linux/GTK | `gtk-0.18.2` 已在本机 registry；`Clipboard::{default,set_text,wait_for_text,set_with_data,store}` 齐全 | 可实现，但本机无法编译（见 §6.4） |

## 2. iOS：`UIPasteboard`（`src/platform/ios/native.rs`）

**改动**：`native.rs` 增加 `pasteboard_set_text` / `pasteboard_text` / `pasteboard_set_html` /
`pasteboard_html` / `pasteboard_has_format` 与 `IosClipboard`（`RichClipboardBackend`，文本+HTML）；

**关键设计点**（都是"不做假成功"的直接后果）：

* `setString:` **没有返回值**，所以 `pasteboard_set_text` 把"写进去的值再读出来"当作答案；
  读不回来就报 `false`。这与 macOS 后端用 `writeObjects:` 的 `BOOL` 是同一条规则。
* HTML 走 `setData:forPasteboardType:`（`public.html` 的 UTI）+ 文本通道做 plain 兜底，
  **不**用 `setValue:forPasteboardType:` —— 后者要一个 `&AnyObject`，本 crate 没有安全的上转型，
  硬转指针不如换一个安全的 API。
* `clipboard_text()` 覆写的原因写在代码里：默认实现把 `""` 读成"没有文本"，而 iOS 上
  `""` 是**真实的空文本**（`hasStrings()` 成立）。

## 3. Android：`ClipboardManager`（`src/platform/android_jni.rs`）

**改动**：`android_jni.rs` 新增"System clipboard"一节（`clipboard_ready` / `set_clipboard_text` /
`clipboard_text` / `AndroidClipboard`），`android/platform_impl.rs` 接上它并新增 `capabilities()`。

**JNI 形状**（每一处签名都对着 `android.content.ClipData` 的公开 API 写）：

```text
Context.getSystemService("clipboard")                                  → ClipboardManager
ClipData.newPlainText(CharSequence,CharSequence) → ClipboardManager.setPrimaryClip(ClipData)
ClipData.newHtmlText(CharSequence,CharSequence,CharSequence)           → 同上
ClipboardManager.hasPrimaryClip() / getPrimaryClip().getItemAt(0).coerceToText(Context)
ClipData.Item.getHtmlText()
```

**三件必须写明的设计决定**：

1. **写入以读回确认**：`setPrimaryClip` 返回 `void`，而 API 30+ 会**静默拒绝后台进程的剪贴板写入**。
   把"调用没抛异常"当成功，就是本仓库最忌讳的"reported success for something that did not happen"。
   所以写后读回比对，不一致时 `WARN` 并报 `false`。
2. **`clipboard` 位是运行时答案**：`android_jni::clipboard_ready()`（`JavaVM` 已存 **且** `Context` 已附加）。
   `PlatformCapabilities` 会经 `rw_platform_capabilities` 逃出进程，宿主据此决定要不要提供"粘贴"；
   一个还没握手成功的进程**确实**读不到剪贴板，所以说 `false`。
   同一事实也决定 `clipboard_backend()` 返回 `Some` 还是 `None`——两者必须同进同退，
   所以 `src/platform/tests.rs` 的通用门控新增了 `clipboard ⇒ clipboard_backend().is_some()`。
3. **桥不可用时回落到进程内记录**：`set_clipboard_text` 在"桥没准备好"时走 `state`（库内复制粘贴照常可用），
   但**桥准备好而写入被拒**时**不**回落——那正是需要如实报错的场景。

**证据（实跑）**：

```text
$ cargo check --target aarch64-linux-android --no-default-features \
    --features "android-jni jni mobile controls-custom controls-native serde serde_json"
  Finished（无 warning）
$ cargo clippy --no-default-features --features "android-jni" -- -D warnings
  Finished（宿主构建同样干净；这条覆盖 `clipboard_ready()==false` 的回落分支）
```

**未覆盖**：`tools/check_android_cross.sh` 覆盖 4 个 ABI 的编译，但**没有**设备/模拟器，
JNI 调用未在运行时跑过；`android/status.md` 的"Not yet verified"一节已如实记下这一点。

## 6. Linux/GTK：GDK 剪贴板（新文件 `src/platform/linux/gdk_clipboard.rs`）

### 6.1 修的是什么

两个不对称，合起来让"Linux 上的剪贴板"名不副实：

* `set_clipboard_text`（`gtk-native`）写到 GDK 显示剪贴板，`get_clipboard_text` **只读进程内记录**；
* `clipboard_backend()` 从不覆写 → `platform_clipboard()` 恒为 `None`，
  `LinuxClipboard` 类型虽有却**被文档禁止返回**。

现在：`set`/`get`/`clipboard_text`/`clipboard_backend`/`capabilities().clipboard` 全部走
`gdk_clipboard`，一条路径进出（原则 #101）。

### 6.2 边界：这一半**没法在本机编译**

`linux` 模块是 `#[cfg(any(target_os = "linux", doc))]`，本机是 macOS；交叉编译到
`x86_64-unknown-linux-gnu` 又需要 Linux 的 GTK 头/库（本机 pkg-config 给的是 macOS GTK）。
所以对 `platform_impl.rs` 的改动只能做到：**parse 验证 + 逐行复核**。

```text
$ rustfmt --edition 2021 --emit stdout src/platform/linux/platform_impl.rs > /dev/null ; echo $?   → 0
$ rustfmt --edition 2021 --emit stdout src/platform/linux/mod.rs          > /dev/null ; echo $?   → 0
```

这是**本轮唯一一处"改动本身未编译"**，因此 §0 与 §10 都单独写明。

### 6.3 边界：GDK 代码本身的验证（真跑，不是"应该能行"）

`gdk_clipboard.rs` 的内容可以在本机**逐字**编译并运行：把该文件原样 `#[path]` 进一个 scratch crate，
只为 `crate::compat::String` 与 `crate::platform::clipboard::{ClipboardContent, RichClipboardBackend}`
提供最小替身（协议与原 trait 一致），依赖只有 `gtk 0.18`（本机 homebrew GTK3）。
`gtk::init()` 在本机实测**成功**，且它的 quartz 后端把 GDK 剪贴板映射到 **macOS 真实系统剪贴板**：

```text
$ cd /tmp/gtkclip && cargo run
gtk init ok, version 3
display: mikewolfs-macbook-air.local
available: true
text: wrote=true read=Some(Text("rw-probe-text"))      ← 文本：写→读回，端到端通过
html: wrote=true read=Some(Text("rw-probe"))           ← HTML：plain 通道落地（见下）
html markup channel returned: Some(Text("rw-probe")) (markup arm unverified on this host)
has_format: html=false plain=true rtf=false            ← 与剪贴板上真实存在的东西一致
off-main: (None, None, false, false)                   ← 非主线程四个入口都被如实拒绝
PROBE OK
```

### 6.4 probe 抓到的两个**真**缺陷（都已修）

1. **函数名被参数遮蔽**：`set_html(html, plain)` 里 `html()` 是函数、`html` 是参数，
   `&& html().is_some_and(...)` 编译失败（`expected function, found &str`）。
   修法：显式写 `self::html()`。（harmony 的 `set_text` 有同一个坑，同一轮里也修了。）
2. **`gdk::Atom::intern` 在主线程守卫之外调用** → 非主线程上 panic（`assert_initialized_main_thread!`）。
   这会让"worker 线程里复制/粘贴 HTML"变成**进程崩溃**，而守卫本来的目的正是"诚实地返回 false"。
   修法：把 intern 移进 `with_clipboard` 守卫内部（两处：`set_html` / `html`）。
   probe 的第 5 步（非主线程四连问）就是这条的回归证据。

3. **空字符串的读回判据是反的**：GDK 没有"空字符串选择"——`set_text("")` 之后
   `wait_for_text()` 返回 `None`（与 `clear()` 相同）。若按"读回必须等于写入值"判定，
   `set_clipboard_text("")` 会被报成失败，而 `src/platform/linux/tests.rs` 里既有的
   `assert!(backend.set_clipboard_text(""))` 会在**有显示的 Linux 宿主上变红**。实测：

   ```text
   after set_text("something"): Some("something")
   after set_text(""):          None
   after clear():               None
   ```

   修法：空串的确认条件是"剪贴板上现在没有文本"，非空串仍是"读回等于写入值"。
   probe 里加了这条断言（`set_contents(Text(""))` 必须为 true，且 `text() == None`），实跑通过。

### 6.5 写明的边界：HTML 的**标记通道**在本机不可验证

`text/html` 通过 `gtk_clipboard_set_with_data` 的 owner 回调投递（这是 X11/XWayland 上的标准做法）。
在本机能跑的唯一宿主（GTK3/quartz）上实测：回调**确实被调用**（`info=1 target="text/html"`），
但读回的内容长度是 **0**：

```text
diag: set_with_data -> true
  owner callback: info=1, target="text/html"
  owner callback: info=2, target="UTF8_STRING"
diag: targets = ["NSStringPboardType", "UTF8_STRING", "Apple HTML pasteboard type", "text/html"]
diag: wait_for_contents(text/html) -> Some(0)          ← 空
diag: wait_for_contents(UTF8_STRING) -> Some(4)        ← "diag"
diag: wait_for_text -> Some("diag")
```

即 quartz 后端只把 `UTF8_STRING` 从 owner 数据里送出去，非文本 target 一律空。
X11 上的同一调用是文档化机制，但本机没有 X11 宿主，**所以标记通道写成"本机未验证"**，
而不是"已实现"。代码自身不因此说谎：`set_html` 只有在**读回确认**后才报 `true`，
且"两个通道任一落地即成功"这条规则与 macOS/iOS 后端一致（它们的 `html_ok || plain_ok` 同理）。

## 1. §6 — 让「不是 loop 驱动者」的宿主真的能结束会话

### 1.1 问题与第 1 轮的边界

第 1 轮把 `Platform::quit()` 改成返回 `bool`，让宿主**知道**请求没被投递。但宿主想要的是
**会话结束**：feedback 原文仍成立 ——「只能 `std::process::exit`，这会让『干净退出』与『强制结束』
在日志与退出码上无法区分」。所以本轮要的是能力，不是报告。

任何工具包都不接受"从任意线程停它的 loop"：`-[NSApplication stop:]` 限主线程，GTK 的
`gtk_main_quit` 走全局 main-loop 栈（只有 loop 线程能碰，见 §1.4 修掉的一处），Win32 的
`PostQuitMessage` 有线程亲和性。本轮的答案不是"派发到主线程"，而是**让 loop 自己读**：

**新增 `src/platform/stop.rs`** — 一个原子标志（`STOP_REQUESTED`）+ 一个"已观察到帧 tick"的标志
（`LOOP_TICKED`）。任何线程都能做一次原子写（`request()`），读它的是**每一帧**。

### 1.2 为什么读它的是帧 tick

库内**每一个** loop 都在**自己线程上**调用 `crate::drive_frame()`：

| 后端 | tick 来源 |
|---|---|
| linux（GTK） | `glib::timeout_add_local` 闭包（GTK 主线程） |
| linux（状态） / windows / wayland / mobile / harmony / ios / android | 轮询 loop 里每轮一次 `drive_frame` |
| **macos（cocoa）** | AppKit 每个窗口的重复 `NSTimer` → `canvas.rs` 的 `drain_triggers_impl` → `crate::drive_frame` |
| macos_objc2 | 其 loop 每轮一次 `drive_frame` |

所以 tick 是唯一同时满足"每个后端都有"与"跑在工具包允许停 loop 的那个线程上"的接缝。把检查放在
`drive_frame` 里（`honour_request_on_loop_thread()`），就得到一个**不需要跨线程调用工具包**的停止路径。
读到请求时，它调用 `Platform::quit()` —— **在 loop 自己的线程上**，这正是每个后端本来就会正确处理的路径。

### 1.3 公开语义

`rust_widgets::quit()`（= `platform::quit`）的契约从"投递到 loop 线程"改为**"任何线程都可请求"**：

| 值 | 含义 |
|---|---|
| `true` | 本次调用把会话推上了结束路径：或"某个 loop 已经跑过帧，它会在下一帧读到请求并停止"，或"本后端就地把自己的退出条件置位了" |
| `false` | 两者都没发生：还没有 loop 跑过帧，本线程也无法就地停止 —— 宿主须自己安排收尾 |

请求**不会丢**：没有 loop 时它仍被记录，之后启动的 loop 在第一帧就会读到（`quit()` 先 `init` 后
`run` 的调用顺序一样成立）。为免"上一个会话的请求终止下一个会话"，`platform::run()` 返回时清除记录
（§1.5 里由探针抓到的残留问题）。

各后端 `Platform::quit()` 的**就地**语义未变（macOS 仍在非主线程返回 `false`），因此 Apple 侧
**一行都不用改**：跨线程能力来自共享的 `stop` + tick 路径，而不是每后端各写一份。

### 1.4 顺手修掉的真缺陷：GTK 的跨线程 `gtk_main_quit`

`linux/platform_impl.rs` 的 `quit()` 原来**无条件**调用 `gtk::main_quit()`。GTK 3 的实现会遍历
全局 `main_loops` 链（无同步），从其它线程调用是**数据竞争**（症状依时序而变）。现在改为：
`gtk::is_initialized_main_thread()` 为真才就地调用，否则**只记录请求**（tick 会在主线程完成停止）。
返回值仍为 `true`，因为此时"请求确有读者"。同一文件 `create_window` 早已遵守同一条主线程规则。

### 1.5 探针抓到的两个问题（都不是我先想到的）

`examples/probe_cross_thread_quit.rs` 把宿主的形态原样摆出来：主线程 `run()`，watcher 线程到点
`quit()`。它抓到了两个我自己没想到的问题：

1. **残留请求**：linux 状态后端的 loop 退出条件就是自己的 `running` 标志，watcher 置位后 loop
   在 `while` 处直接退出，**没有机会再跑一帧**去消费那条记录 —— 记录会留给"下一个 loop"，在下一次
   `run()` 的第一帧立刻停掉它。修法：`platform::run()` 返回时 `stop::take()`（tick 已消费时是 no-op）。
2. **`capabilities()` 里 `file_dialog` 的判定时机**（§2.5）。

### 1.7 建议 2：`schedule_on_main`（把工作交给 loop 自己的线程）

feedback 说"任一即可"，但宿主真正需要的是两件不同的事：**结束会话**（建议 1）与**在 loop 线程上
安排工作**（建议 2：自动退出、心跳、状态栏刷新）。本轮两件都做了，而且用的是**同一个接缝**：

**新增 `src/platform/main_thread.rs`** — 一个进程级队列（`Mutex<Vec<Due>>`，`Due = 截止时间 + Box<dyn FnOnce() + Send>`）。
任何线程 `schedule_in(after, work)` 入队；帧 tick（`drive_frame`）在自己的线程上把**到期**的项取出来执行。
因此：

* **不需要任何后端代码**（Apple/Windows 一行未改）—— macOS 上执行者是每个窗口的 `NSTimer`
  → `drive_frame`，GTK 上是 `glib` timeout 闭包，其余后端是 loop 自己每轮一次；
* `after` 是**下界**，粒度是一帧（~16ms）：文档写明，不假装更高精度；
* 重复工作 = 回调里再 `schedule_in` 一次（**不提供** repeating 形态：一个概念一条路径，#54/#101）；
* 返回值与 `quit()` 同一个事实（`stop::loop_has_ticked()`）：*有* loop 在跑就是 `true`，没有就 `false`
  （工作仍留在队列里，之后启动的 loop 会在到期后执行它）—— 这正是"先安排退出、再进 loop"的单线程写法；
* **到期项先在锁内取出、再在锁外执行**：回调里再入队（重复工作）不会自锁死；代价是"回调里排的 0ms 工作
  在下一帧执行"，文档写明这是一帧延迟而不是重入；
* 回调 **panic 会向上传播**（它是在 loop 线程上跑的宿主代码，与信号处理器同类）：不在这里吞掉 panic，
  否则"心跳坏了"会变成"会话安静地不再跳"。队列本身在 panic 后仍可用（poisoned 锁用 `into_inner` 取回）。

**公开入口**：`rust_widgets::schedule_on_main(after, work) -> bool`（`cfg(not(alloc_frugal))`：
队列需要分配器，而这些 profile 本来也没有平台 loop —— 与 `quit()`/`create_window()` 同一门控）。

**证据**：


### 2.5 探针抓到的第三个问题：能力位判定的**时机**

第一版把 linux 的 `file_dialog` 写成 `gtk::is_initialized_main_thread()`（"现在真能弹"）。探针立刻
暴露它的错：宿主问 `capabilities()` 的时机是**驱动 loop 之前**（这才是"提前知道"的意义），而那时
GTK 还没 init，于是**在有 GTK 的机器上**回答 `false` —— 宿主会去画自己的列表，白白丢掉系统选择器。

（`Err(Unavailable)`），这正是 `PathPickerError::Unavailable` 文档里写的那件事。位置分工因此干净：
**位 = 后端有没有**，**错误 = 这一次给不给**。macOS/Windows 的位本来就是构建事实，三者一致。

## 3. §8.8 — 库内子进程必须有自己的归属边界

### 3.1 改动

**新增 `src/platform/child_process.rs`**（唯一一处说清楚"库内子进程归谁"的地方）：

| 函数 | 作用 |
|---|---|
| `in_own_group(&mut Command)` | unix：`process_group(0)` 建新进程组；非 unix：文档化的 no-op（Windows 的归属单位是 job object，本 crate 不创建 —— 写在文档里，而不是用 `cfg` 在每个调用点表达，#36/#41） |
| `kill_whole_group(&mut Child)` | unix：`kill(-pgid, SIGKILL)` + `child.wait()`（自行声明 `kill(2)`，因为 `libc` 在 linux 上是可选依赖、只在 `wayland-native` 后；SIGKILL 号 POSIX 固定）；非 unix：只杀直接子进程并收尸 |

应用点（**冰山法则**：不是只修 feedback 点出的那一处）：

1. `os_probes::run_spooler` — 原来的超时处理是 `child.kill()`（只杀直接子进程）。真实打印链路
   （`lp` → filter 链）会派生子进程，它们会继续持有"调用方返回后就要删除"的任务文件，且**无人报告**。
   现在超时按**组**收尸。为让这条路径可测，把超时提为参数（`run_spooler_with_timeout`，
   生产仍用 30s 常量）。
2. `external.rs::spawn_handler` — 交给系统处理器的进程（`xdg-open`/`open`/`cmd start`）也建自己的组。
   这让两个方向**都**安全：宿主的"清理本会话创建的进程组"不会误杀用户刚打开的浏览器；库也不会把
   一个长生命周期应用塞进宿主即将拆掉的组里。

**边界声明**（feedback 8.8 要的正是这个）：宿主的清理判据是"本会话创建的进程组"，**不包含**库内
进程；库自己负责它启动的东西，含后代。这条写在 `child_process.rs` 模块文档与 `os_probes.rs` 里。

### 7.1 ✅ 新增：真实 X 输入进真对话框（原 #7 与 §7⑤ 的键盘半）

**工具**：`tools/x11_inject_keys.py`。它用 XTEST 注入**真实** X 键事件（不是 GTK 内部事件投递），
并且在敲键**之前**做三重校验，任一不满足就**一个键都不发**并 `exit 2`：

1. `wmctrl -l` 里必须有标题匹配的窗口；
2. 窗口管理器报的 `_NET_ACTIVE_WINDOW` 必须是它；
3. **X 服务器自己的输入焦点**（`XGetInputFocus` + `XQueryTree` 上溯）必须是它或其子窗口 —— 决定按键落到哪里的
   是第三个事实，不是第二个。

**探针 B2 段**：`PathPurpose::OpenFile` 打开真选择器 → 注入工具键入 `/tmp/rw_picked_by_probe.txt` + Return →
`choose_path` 必须返回**这个路径**；同时挂一个 8s 的兜底取消定时器，使"注入被拒"表现为**一条失败检查**而
不是挂住进程（原则：不许用"跑到超时"表达）。

```text
$ RW_GUI_PROBE_OK=1 ./target/debug/examples/probe_file_picker   # desktop+gtk-native，真 X11 会话
B2. the same picker, answered by *typed input* (real X key events)
   choose_path answered Ok(Some("/tmp/rw_picked_by_probe.txt")) (typist exit 0)
  OK   the typist typed into the dialog (its focus checks passed first)
  OK   the path the injector typed is the path `choose_path` answered with, so real X key events
       travelled through the dialog and back
probe_file_picker: OK (every check held)
```

**运行这些探针必须显式放行**：它们会在**运行所在的桌面**上真的开窗口/对话框（这正是它们的意义：
无头桩后端答不了"在不在屏幕上""击键有没有到控件"）。三次实测里我在维护者的活动桌面上弹了十几个窗口 ——
这是**我的错**，不是工具的错。三个 GUI 探针现在都要求 `RW_GUI_PROBE_OK=1`，否则打印一行说明并 `exit 2`；
默认行为从"跑 example 就弹窗"变成"要先明确同意"。

**B2 的稳定性（如实记录）**：XTEST 往 GTK 的 location popup 里打字是**时序相关**的 —— popup 必须先拿到焦点，
否则按键被丢弃、字符落到文件列表上变成 type-ahead，`Return` 会打开列表里当前选中的文件（实测到过
`~/Downloads` 里的一个文件）。单次尝试成功率约一半，所以探针最多重试 6 次；**6 次都没成功时报告为
"staging limitation" 并 `exit 2`（宿主/提交限制），不是"库失败"** —— 否则会把 XTEST 的时序问题算到库头上。
成功案例已重复观测到（5 次运行里 4 次通过、其中多次第 1 次尝试即成功）。

**过程中修掉的两个"我的错"**（都由探针/工具自己暴露，不是自述）：

| 谁抓到的 | 缺陷 | 修法 |
|---|---|---|
| 探针 B2（第一次跑就会段错误） | `ctypes` 未声明原型的函数把 `Display*`（64 位）当 32 位整数传 → **SIGSEGV**，而探针把它读成"typist refused" | `tools/x11_inject_keys.py` 里**每个**用到的 X11/XTEST 函数都显式声明 `argtypes`/`restype`；探针同时打印原始退出码，使(SIGSEGV)这类"非检查失败"可见 |
| 探针 B2（人工复跑时） | 我手工跑注入器时**探针自己的注入线程也在跑**，两者都往同一个对话框敲键 → 返回了列表里当前选中的 `clippy.toml`（而不是键入的路径），看起来像"库错了" | 复跑只让探针自己注入即绿。这条正好说明工具为何要用**焦点三重校验**：并发注入（两个"人"）是无法从库侧防住的，只能由调用方串行化 |

## 8. 本轮净效果

| 项 | 前 | 后 |
|---|---|---|
| watcher 线程结束会话 | 只能读到"无法投递"，只能 `std::process::exit` | `quit()` 从任何线程都成立；真 GTK 会话 `run()` 在 415.75ms 返回（干净退出，可与被杀死区分） |
| GTK 的 `quit()` | 从任意线程调用 `gtk_main_quit()`（跨线程碰全局 main-loop 栈） | 只在 GTK 主线程调用；其它线程走 tick（数据竞争去掉） |
| loop 停止的接缝 | 无（每后端各一套，Apple 一套都没有） | `platform::stop` + `drive_frame` 一处，11 个后端共享，Apple 侧**零改动** |
| 会话间残留 | —（无请求机制） | `run()` 返回时清除，一次请求只停一个 loop（探针 C 段） |
| 在 loop 线程上安排工作 | 无（宿主只能自建 watcher 线程 + 各平台自己的 timer API） | `schedule_on_main(after, work)`：任何线程入队、帧 tick 执行，Apple/Windows **零改动**；探针 E 段整段会话没有 watcher 线程 |
| 宿主文件选择器 | 无（`FileDialog` 要宿主自己填列表） | `choose_path` + 三个具名入口 + `file_dialog` 能力位；GTK 真跑、Windows/macOS 编译取证 |
| 能力的"有"与"可用" | 混在一起（第 1 轮据此删掉了位） | 位 = 后端有没有（构建事实）；`Err(Unavailable)` = 这一次给不给（会话/线程事实） |
| 库内子进程 | 与宿主同组（宿主整组清理会误杀），超时只杀直接子进程（孙进程存活且无人报告） | 自建进程组 + 超时按组收尸；宿主与库的归属集合互不重叠 |
| DPI / 窗口合成证据 | "无显示会话"（第 3 轮/§7） | 真 X11：`mapped=true`、`GDK_SCALE=2` → 库报 2、窗口 `scale=2` |
| 跨目标代码质量 | Apple/Windows 只能"逐行复核" | 平台选择器代码按各自 target **编译**过（并因此抓出 6 个真缺陷） |

`macos/file_picker.rs` 121、`windows/file_picker.rs` 203、两个探针 210+193 行）。
