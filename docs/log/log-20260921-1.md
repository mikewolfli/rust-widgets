## 2. `run_all_gates.sh` 跑死的原因与修复

### 2.1 取证（规则 #64：先复现，不靠推测）

用户现象：`bash tools/run_all_gates.sh 2>&1 | tail -8` 长时间无输出，看起来「跑死」。

实跑：`bash tools/run_all_gates.sh --summary`（逐门禁打印，带进度）——

```
tools/check_profiles.sh FAIL 1800s
```

**发现**：`check_profiles.sh` 卡到 **1800s 上限**（`GATE_BUDGET` 的默认值），
即它不是「卡在开始」，而是「单个门禁吃满上限」。因为 `run_all_gates.sh` 默认是
**串行**的，一个门禁吃满 30 分钟，其余门禁全部排在它后面，
叠加 `| tail -8` 把中间输出全部缓冲掉，用户看到的就是「一直不动 = 跑死」。

### 2.2 根因

`check_profiles.sh` 的 `[6b/9]` 步要做 `windows` profile 的交叉编译，
而本机**没有 MSVC 工具链**（`lib.exe` 不存在，mingw gcc 亦不存在）。
`cc-rs` 在找不到 `lib.exe` 时不是立刻报错退出，而是**逐个候选编译器重试**，
每次重试都走一遍完整的 `cargo` 依赖解析 —— 于是单步就吃掉十几分钟。

这不是「代码缺陷」，而是**环境缺失 + 门禁未做前置探测**的组合：
脚本明知道需要 MSVC，却等到 `cc` 失败才报，白白花掉整个预算。

### 2.3 修复

| 动作 | 文件 | 说明 |
|---|---|---|
| ① 前置探测 MSVC | `tools/check_profiles.sh` | 新增 `have_windows_linker()`：在 `[6b/9]` 之前先判断 `lib.exe`/`link.exe`/`x86_64-w64-mingw32-gcc` 是否存在；不存在则**立刻**报 `unsupported host`，不再触发 `cc-rs` 的重试风暴 |

**要点**：这是**根因修复**（不触发昂贵重试），不是「把超时调大」。
调大超时只会让「跑死」从 30 分钟变成 60 分钟，问题仍然存在。

### 2.4 实跑验证（贴输出）

修前：`check_profiles.sh` 吃满 `GATE_BUDGET=1800s`，`run_all_gates.sh` 因串行而整体停滞。

修后：

```
$ RW_GATE_TIMEOUT=1800 timeout 1700 bash tools/check_profiles.sh
exit=0
 60:[6b/9] SKIPPED: unsupported host -- the x86_64-pc-windows-msvc target
133:All profile checks passed.
```

**本机确无该工具链**（`command -v lib.exe link.exe x86_64-w64-mingw32-gcc` → `exit=127`），
所以 SKIP 是**如实回答**，不是掩盖失败。

### 2.5 🔴 顺带抓到的真实缺陷：`drain_triggers` 漏 pick 的 profile

第一次修完 `[6b/9]` 后，`check_profiles.sh` **仍然 exit=101**，但错误换了一条：

```
error[E0433]: cannot find `app` in `crate`
 --> src/platform/android/platform_impl.rs:100:20
 100 | crate::app::drain_triggers();
note: found an item that was configured out
 291 | #[cfg(full_widgets)]
 292 | pub mod app;
```

**根因**：`drain_triggers` 原先**只定义在** `src/app/handle.rs`，而 `crate::app` 受
`full_widgets` 门控；`mini` 下 `full_widgets` 为假 ⇒ `crate::app` 不存在。
但**11 个平台后端**（Linux/Windows/macOS/cocoa-legacy/Wayland/wasm/Android/iOS/
Harmony/macos_objc2/Android-JNI）都在事件循环里调用它，且**全部未加 `cfg`**。

这与 T-11 挖出的 Android `c_char` 缺陷**是同一类**：
一条**没有任何 job 编译过**的代码路径 —— 只有跑 profile 矩阵才会暴露，
单跑 `desktop` 永远看不到。

**修复（根因，非逐点补丁）**：

| 动作 | 说明 |
|---|---|
| `drain_triggers` 移到**crate 根**（`src/lib.rs`，紧邻它消费的 `poll_widget_trigger_event`） | 队列不是「控件集」特性，而是后端上报「用户缩放了窗口」的手段，所以排空函数应与其依赖**同宽门控** |
| 函数**在全部 profile 定义**，`alloc_frugal` 分支返回 `0` | 若改成给函数加 `cfg`，就必须给 **11 个调用点**各加一次 `cfg`；重复 11 遍的门控必然会漏一个 —— 这正是本缺陷的成因。条件收拢到一处 |
| `src/app/handle.rs` 保留 `pub use crate::drain_triggers;` | `crate::app` 是已发布的入口，既有调用方按此命名 |
| 11 个后端调用点改指 `crate::drain_triggers()` | 均为机械替换 |

**实跑验证**：

```

$ cargo check --no-default-features --features mini,wasm → Finished（0 error）
$ cargo check --no-default-features --features embedded → Finished（0 error）
$ cargo check --features desktop → Finished（0 error）
$ bash tools/check_profiles.sh → exit=0, "All profile checks passed."
```

### 3.2 🔴 缺陷 A：窗口子树**坐标空间不一致**（本轮最主要的发现）

**现象**：control demo 里所有控件「看不见」——只能看到窗口背景。
实测 ComboBox 矩形 `(20,142,180,26)` 内**只有一种颜色** `rgb(18,18,18)`，
正是窗口背景色；而主题给 ComboBox 解析出的填充色是 `rgb(69,69,69)`。

**取证链**：

```
# 1. 主题解析（新写双外观探针 examples/theme_resolve_dump.rs）
$ cargo run --example theme_resolve_dump --features desktop
── dark ── window background: rgb(18,18,18)
combo_box rgb(69,69,69) rgb(225,225,225) rgb(130,130,130) w=Some(1)

# 2. 控件的 style 确实拿到了主题值
$ cargo run --example style_probe2 --features desktop
combo raw_id = 6000285942072475649
bg = Some(Color { r: 69, g: 69, b: 69, a: 255 }) <-- 有值
border = Some(Color { r: 130, g: 130, b: 130, a: 255 }) w=Some(1)

# 3. 但渲染出来的像素里没有它
$ cargo run --example style_probe4 --features desktop
window bg = Some(18,18,18) border = Some(130,130,130) w=Some(1)
 geom=Rect { x: 100, y: 100, width: 1120, height: 620 }
inside combo box (20..200, 142..168):
 [18, 18, 18, 255] x4680 <-- 只有窗口背景，ComboBox 的 69,69,69 不见了
pixel(0,0) = [130, 130, 130, 255] <-- 角落是「边框色」
pixel(bottom-right) = [130, 130, 130, 255]

# 4. 坐标空间对照
$ cargo run --example style_probe5 --features desktop
window geom = Some(Rect { x: 100, y: 100, width: 400, height: 300 }) <-- 屏幕坐标
combo geom = Some(Rect { x: 20, y: 142, width: 180, height: 26 }) <-- 客户区坐标
```

**根因**：`Window` 的几何是**屏幕坐标** `(100,100)`，而它的子控件是**客户区坐标** `(20,142)`。
`render_frame_tree` 用 `frame_origin(id)` = **窗口自己的 x/y** 作为偏移：

```
combo 实际落笔位置 = (20,142) + (-100,-100) = (-80, 42) → 画布左外侧，被裁掉
```

窗口自身的 `fill_rect(rect)` 用绝对矩形 `(100,100,1120,620)`，
偏移后正好回到 `(0,0)`，所以**只有窗口背景是对的**，
其余每一个子控件都被平移到画布之外 —— 这正是「控件看不见」的机械原因。

**另一处同源缺陷**：`pixel(0,0)` 是 `rgb(130,130,130)`（边框色）而不是背景色，
说明边框笔画覆盖了整个画面。原因是 `Window::draw` 的 `draw_rect_stroke` 同样用绝对矩形，
且描边**画在填充之上**、又跨越整幅画布。

**为什么之前的门禁没抓到**：既有测试断言的是「几何正确」「layout 被重跑」，
没有一条断言**渲染出来的像素里能看见控件**。
几何对、像素错，是两件事。

**修复方向（根因，非补丁）**：
子控件的几何是客户区坐标，那么窗口树的原点也必须是**客户区原点**，
而不是窗口的屏幕坐标。即 `frame_origin` 对窗口应取 `(0,0)`，
或让窗口的几何在注册时就归一到客户区原点。

### 3.2.1 ✅ 缺陷 A 的修复（已实施 + 反向注入验证）

| 项 | 内容 |
|---|---|
| 文件 | `src/widget/runtime.rs` —— `frame_origin(id)` |
| 修法 | 窗口（`WidgetKind::Window`）返回 `(0,0)`；非窗口仍返回自身 `x/y` |
| 理由 | 根的父空间就是它自己，窗口的子控件已在客户区原点；
非窗口的自绘面仍需把自己的矩形平移回自身原点 |

```rust
fn frame_origin(id: ObjectId) -> (i32, i32) {
 match MOUNTED.try_with(|map| {
 map.borrow().get(&id).map(|entry| (entry.widget.kind(), entry.widget.geometry()))
 }) {
 Ok(Some((crate::widget::WidgetKind::Window, _))) | Ok(None) | Err(_) => (0, 0),
 Ok(Some((_, geometry))) => (geometry.x, geometry.y),
 }
}
```

**新门禁**：`tests/window_tree_paints_visible_controls_test.rs`（3 条测试）
断言「窗口树渲染后，每个控件的像素**可区分于窗口背景**」。

**⚠️ 这个门禁第一版假通过**——窗口建在 `(0,0)`，而偏移为 0 时缺陷不可观测，
于是「还原缺陷后测试仍然 PASS」。这正是 blue19 §T-19 反复警告的那类缺陷。
修法：把窗口建在 **`(100,100)`**（即 demo 的真实位置），并写明原因。

**反向注入实测**（把 `frame_origin` 改回旧实现）：


### 3.2.2 ✅ 缺陷 B 的修复

`Window::draw` 原用**绝对矩形**描边（`draw_rect_stroke(rect, ..)`），
而描边会覆盖它经过的**每一个**像素 ⇒ 窗口边框画在整个客户区之上。
修法：只填客户区背景（归一到客户区原点），去掉自绘边框与标题栏
——两者都是**窗口管理器**的职责（与之前已去掉的标题栏同理）。

### 3.2.3 🔴 缺陷 C：主题切换后旧配色不更新（`merge` 只能填 `None`）

**取证**：新门禁里「切到 dark 后窗口背景必须不再是 light」一条最初 FAIL，
角落像素仍是 `240,240,240`。

**根因**：`WidgetStyle::merge` 的语义是「只填 `None` 字段」，
这是「调用方显式值不被覆盖」的实现方式。
但它**无法表达「换掉上一个主题写进去的值」**——控件一旦被主题写过，
那些字段就不再是 `None`，新主题无处可写 ⇒ `light → dark` 切换**看起来没发生**。

**修复**：给 `WidgetStyle` 加 **来源标记** `theme_derived`：

| 情形 | 行为 |
|---|---|
| `theme_derived == true`（主题是唯一作者） | 整体替换上一版主题的取值 |
| `theme_derived == false`（调用方也改过） | 退回 `merge` 的「只填 `None`」规则，调用方值不被覆盖 |
| 调用方调 `with_background` / `with_text_color` / `with_font` / `with_border` | **清除**标记（此时调用方也是作者） |

新增 `WidgetStyle::merge_theme` 承担上述两分支，`theme::apply_active_theme` 改用它。

**两个方向都测试**（缺一不可——只满足一边会把「配色不更新」换成「调用方值丢失」）：

- `reapplying_after_a_switch_replaces_the_previous_themes_colours`
- `a_callers_colour_survives_repeated_theme_applications`

**反向注入实测**（把 `merge_theme` 第一分支改回 `merge`）：

### 3.2.4 🔴 缺陷 D：`list_box`/`scroll_area` 等被归类为「背景色」（不可见）

**取证**（`theme_resolve_dump`，加自动标注后）：

```
kind background ...
list_box rgb(18,18,18) <-- same as window background
panel rgb(18,18,18) <-- same as window background
frame rgb(18,18,18) <-- same as window background
scroll_area rgb(18,18,18) <-- same as window background
message_box rgb(18,18,18) <-- same as window background
tool_bar rgb(18,18,18) <-- same as window background
status_bar rgb(18,18,18) <-- same as window background
```

**根因**：`WidgetRole::for_kind_name` 的角色表**没有**为这些 kind 给行，
全部落到 `_ => Self::Surface`，而 `Surface` 解析为 `theme.colors.background`
——**与窗口同色**。于是它们在渲染上「没有范围」：几何正确、样式"正确"、屏幕上什么都没有。

**修复**：把「可选中字段」移出 `Surface` 通吃分支，归为 `WidgetRole::Input`：

```rust
"listbox" | "listview" | "tableview" | "treeview" | "scrollarea" | "textbrowser"
 | "plaintextedit" => Self::Input,
```

`Input` 解析为 `Colors::input_background()` —— 从背景向前景走一步，
**浅色主题上更浅、深色主题上更深**，两种外观下都与窗口可区分。

**新门禁**：`theme::tests::selectable_fields_are_inputs_not_bare_surfaces`，
断言每个 kind 既是 `Input`，其填充也 **≠ 窗口背景**。
**反向注入**：把该组 kind 移回 `_` 分支 → 该测试 FAIL（实测）。

> `panel` / `frame` / `message_box` / `tool_bar` / `status_bar` **故意保留** `Surface`：
> 它们确实是“裸表面”语义（容器/背景板），与窗口同色是**正确的**。
> 这类控件靠 `border`（`rgb(130,130,130)`）划出边界，实测可见。
