## 2. 🔴 头条 A：`enabled` 契约的**结构性盲区**（T-5 深挖）

### 2.1 门禁本来「全绿」，但只覆盖了一半的传播路径

```
$ python3 tools/check_enabled_is_honoured.py
EventHandler impls found: 172
  guarded by `is_enabled()`: 145
  allowlisted as non-interactive: 27
✅ enabled contract: every input-handling control consults `enabled`
```

它检查的是 **`handle_event`（入口）**。而**容器**没有入口——它的缺陷在
**发射端（出口）**：

```rust
// 修复前：StackedWidget::set_current_index
pub fn set_current_index(&mut self, index: usize) {
    if index < self.widgets.len() && self.current_index != index {
        self.current_index = index;
        self.base.request_redraw();
        self.current_changed.emit(index);   // ← 禁用时照常广播
    }
}
```

**为什么这是缺陷而不是设计**：`current_changed` 的订阅者做的是
「重新加载/保存这一页的内容」。控件被禁用意味着**这一页用户看不到**，
于是订阅者会**对一个用户不可达的变化做出响应**——正是原则禁止的
「reported success for something that did not happen」。

**`StackedWidget` 在旧门禁里是「有理由的豁免」**，理由是
「passive: its handler only delegates to the base」——**这句话是真的**，
它错在**只看了一个方向**。这是「豁免理由为真」与「契约被守住」之间的空隙。

### 2.2 取证：把被动/容器文件全部重新分类，**8 个**文件有发射型 mutator

新建 `tools/check_enabled_is_honoured_containers.py`，**从姊妹门禁导入** `NON_INTERACTIVE`
（不复制——两份清单必然漂移，原则 #54），然后逐文件找
「`pub fn x(&mut self)` 且 `self.<signal>.emit(`」的组合：

```
Passive/container files with ungated emitting mutators: 8
❌ 14 programmatic emit(s) ignore `enabled` in allowlisted file(s):
   stackedwidget.rs::set_current_index()      emits `current_changed`
   cupertino/core.rs::dismiss()               emits `dismissed`
   cupertino/core.rs::set_value()             emits `value_changed`
   cupertino/core.rs::set_selected()          emits `selected_changed`
   arc.rs::set_value() / set_range()          emits `changed`
   lcd_number.rs::set_value()                 emits `overflow` / `value_changed`
   meter.rs::set_value() / set_range()        emits `changed`
   progressbar.rs::set_value()                emits `value_changed`
   status_bar.rs::show_message()/clear_message() emits `message_changed`
   window.rs::close()                         emits `closed`
```

### 2.3 逐条判定（**不是**全部加守卫——那会让 `enabled` 变成噪声）

| 位置 | 判定 | 理由 |
|---|---|---|
| `stackedwidget::set_current_index` | ✅ **加守卫** | 页面变化是**用户可见**的过渡；禁用 = 看不到 |
| `status_bar::{show_message,clear_message}` | ✅ **加守卫** | 状态文本是**用户可见**的；禁用时不该广播用户看不到的文本 |
| `arc` / `meter` / `progressbar` / `lcd_number` | ➖ **书面豁免** | 读数的值变化由**数据**驱动，禁用不该冻结宿主跟随数据的信号；`lcd_number::overflow` 是**诊断**，压制它恰好隐藏宿主最需要看到的情况 |
| `cupertino::set_value` / `set_selected` | ➖ **书面豁免** | 指针路径**已在 `handle_event` 中守卫**；这里是**编程**路径，宿主双向绑定时需要信号 |
| `cupertino::dismiss` | ➖ **书面豁免** | 关闭通常是**超时**而非点击；且 `dismiss` 本身已以「可见」为前置条件 |
| `window::close` | ➖ **书面豁免** | 这是**生命周期事实**，不是窗口内的用户动作；压制它会**泄漏**它存在所要释放的资源 |

> **判定依据统一为**：这个信号报告的是**用户动作**（→ 加守卫），
> 还是**事实/诊断/程序化状态**（→ 豁免并写明）。豁免必须有**机器可查的书面理由**，
> 且 4 条豁免各有测试背书（§2.4）。

### 3.1 取证：两套机制**完全不相交**，且零门禁

JSON 侧认的 8 个键：on_click on_change on_close on_double_click
                     on_focus on_blur on_selection_changed on_value_changed
capability 表发布：326 pairs / 186 distinct names

**三条具体缺陷**（§2.4 已列，本轮逐条验证）：
① 硬编码键名清单 → 新增已发布事件，JSON 侧**不会**自动支持（违反规则 #101）；
② `ButtonHandle::from_raw(widget_id)` 强转 → 该路径**只对按钮形态成立**；
③ **零门禁** → 可静默漂移。

### 3.2 修复：一条「已发布名」路由 + 一条**有明确分工**的兼容路由

新增 `src/json/event_route.rs`，把「键 → 触发器」的对应**变成数据**：

```rust
pub const MARKER_KEYS: &[(&str, JsonTriggerMarker)] = &[
    ("on_click", Clicked), ("on_change", ValueChanged), ("on_close", Closed),
    ("on_double_click", DoubleClicked), ("on_focus", FocusGained),
    ("on_blur", FocusLost), ("on_selection_changed", SelectionChanged),
    ("on_value_changed", ValueChanged),
];
```

`src/json/loader.rs` 的 **~90 行重复代码**（8 个 `if let Some(ref name) = ...` 块，
每块重复构造 `EventHandlerContext`）收敛为**表驱动**的 `bind_declared_events`：

```jsonc
{ "button": { "text": "Go",
              "events": { "clicked": "on_go" },   // ← 新：按已发布名，capability 校验
              "on_close": "on_quit" } }            // ← 旧：触发器意图，保留
```

**分工（写进模块文档，规则 #101 要求「职责边界写入文档」）**：

| 键 | 是什么 | 为什么存在 |
|---|---|---|
| `events: { "<已发布名>": "<handler>" }` | **已发布路由** | 名字由 capability 表校验；**新增一个已发布事件即自动可声明**，无需改 loader |
| `on_*` | **兼容路由** | 同一个 handler 通过**标记**到达：`on_close` 意为 `Closed`、`on_selection_changed` 意为 `SelectionChanged`——这些是**触发器意图**，不是已发布名；`on_double_click`/`on_focus`/`on_blur` 存在是因为指针路径无法区分它们 |

**顺带修掉的两个真实缺陷**：
1. **位置耦合**：旧代码用两个返回 `Option<String>` **元组**的函数，调用点**按位置解构**。
   `extract_extended_event_handlers` 返回 6 元组——**在中间插一个键就会静默接错触发器**，
   没有任何东西能发现（元组没有名字）。两个函数**已删除**，改为**按名读取**。
2. **两份键清单**：loader 的「不是属性」模式里**又手写了一遍**那 8 个键。现在同源。

## 4. T-3：类型兼容规则**数据化** + 悬空决策 D5/D6 裁定

### 4.1 D5/D6 裁定（`blue19.md` 留白，本轮补齐并写入代码）

| # | 裁定 | 理由 |
|---|---|---|
| **D5** | **事件绑定写在 JSON，不写 CSS** | CSS 是**外观**通道（`src/style/css.rs`），JSON 是**结构**通道（`src/json/`），库已划这条线（`blue19.md` §0.1.1）。把绑定放进 CSS 会让两通道重叠，且**主题切换重放样式表会重建订阅**。CSS 在这里也**无事可做**——它没有「目标属性」的概念 |
| **D6** | **连线目标可为属性；命令仅限「无载荷」** | 兼容性问题是「这个事件的值能否到达这个目标」，属性用**类型**回答。需要载荷的命令必须被**给**一个载荷，而命令的**参数类型不在 capability 表里**——验证这种连线只能靠猜 |

⇒ 落点为 `WireTarget::PayloadFreeCommand`（唯一的命令形态），理由**写在文档里**。

### 4.2 规则数据化（`src/widget/capability/wire_rules.rs`）

```rust
pub const WIRE_RULES: &[WireRule] = &[ rule(Some(K::Bool), K::Bool, Direct, "..."), ... ];
pub fn compatibility(source: Option<PropertyValueKind>, target: WireTarget) -> WireCompatibility;
```

**为什么必须是数据而不是 `match`**（这是规则 #101 的第二个实例）：
规则有**两个消费者**——运行时（加载工程时校验）与**生成器 T-23**
（生成期就要决定发直接赋值还是发转换，因为**生成出来的程序无法问一个生成器
已经知道答案的问题**）。运行时里的 `match` 对生成器**不可见**，
两者必然漂移成「设计器接受了、生成物拒绝」。

**关键设计决定：白名单方向** —— 表**未列出**的组合一律 `Rejected`。
反向默认（未列出即接受）会让**将来新增的 kind 静默产生跑不通的连线**。

**拒绝必须带理由**：`WireCompatibility::Rejected(&'static str)` 带字符串，
因为「灰掉一条连线而不说为什么」**教不会用户任何东西**，
「拒绝生成而不说为什么」产出**无法处理的构建错误**。

**逐条裁定**（8 条同类型直通 + 4 条整数扩宽 + 8 条「格式化为文本」）：

| 源 → 目标 | 判定 | 理由 |
|---|---|---|
| 同 kind → 同 kind | `Direct` | 值已经是目标的类型 |
| `Int`/`UInt` → `Float` | `Direct` | 整数可精确表示为浮点 |
| `Int` ↔ `UInt` | `Direct` | 本库范围内可容纳 |
| 任意标量 → `String` | `Converted` | **唯一的扩宽**：格式化，不会失败 |
| **`String` → `Int`/`UInt`/`Float`** | ❌ **`Rejected`** | **解析会失败**，而失败没有定义的结果——`blue19.md` §3.3 点名要求的拒绝分支 |
| `None`（无载荷）→ 任意属性 | ❌ `Rejected` | 无载荷事件说「发生了」，不说「值应该变成什么」；**发明那个值就是工具在替用户决定** |
| `None` → 无载荷命令 | `Direct` | 这是**动作**而非赋值，正是 D6 放行该目标的原因 |

**测试 8 条**（含**拒绝分支**与**规则表自检**）：

## 5. 🧠 本轮方法论：**三个门禁里有两个的第一版是假门禁**

> 这是本轮最有价值的产出，因为它是**可复现**的：
> 我**独立**写了两条「看起来在检查、实际不检查」的门禁，都在**反向注入时当场暴露**。

### 5.1 假门禁 A：`check_wire_rules_are_data.py` v1

**v1 的步骤 [3]**：「`compatibility` 函数体里是否出现 `WIRE_RULES`？」

**反向注入结果**：

```
INJECTED: for candidate in WIRE_RULES.iter().take(0) {   ← 提到名字，读 0 条
INJECTED EXIT: 0     ← 门禁全绿！
```

**为什么它必然失败**：`.take(0)` **提到了符号**，所以「符号是否存在」为真，
而函数已经退化成硬编码答案。**检查符号存在 = 检查我自己刚写的字符串。**

**v2 的要求**（现在通过）：

```python
if not re.search(r"for\s+\w+\s+in\s+WIRE_RULES\s*\{", code):      # 必须是直接迭代
if re.search(r"WIRE_RULES[^\n]*\.(take|skip|rev)\s*\(", code):    # 不得截断
for field in ("source", "target"):
    if not re.search(rf"\.{field}\s*==", code):                    # 两个字段都必须参与比较
```

**v2 的反向注入**：

```
--- take(0):  exit=1  ❌ 2 findings（不直接迭代 + 截断）
--- no-walk:  exit=1  ❌ 1 finding（不读表）
CLEAN EXIT: 0
```

> 「最小**承重**形状」的这一条判据，可以推广到所有「X 是否被真正使用」的门禁。

### 5.2 假门禁 B：`check_json_event_route.py` 的**解析器** bug（另一种形态）

**症状**：门禁报 **21 个 finding**，其中 20 条形如「某条规则没有理由」——
**而每条规则都有理由**。

**根因**：我用非贪婪正则取 `rule(...)` 的参数：

```python
re.findall(r"\brule\s*\(([^;]*?)\)\s*,", rules)   # ← 在第一个内层 ')' 就停
```

参数里含**嵌套调用** `Some(K::Bool)`，所以它在 `Some(K::Bool` 处截断，
自然找不到后面的理由字符串。

**修复**：按**括号配平**扫描，而不是正则。

> **教训（与 5.1 不同的失效模式）**：5.1 是「检查的东西不承重」，
> 5.2 是「**检查器自己有 bug**，报出 20 个假缺陷」。
> 后者更危险——它会让开发者**去改本来正确的代码**。
> 这也是为什么门禁**必须先在已知为真的代码上跑通**再提交。

### 5.3 测试的「看起来在测」问题：T-8 的一条测试推翻两次

`an_unpublished_name_is_not_wired` 的两个失败版本：

| 版本 | 断言 | 为什么是假的 |
|---|---|---|
| v1 | `!fire("on_typo", Clicked)` | 我**自己在测试里注册了** `on_typo`，所以它恒为 `false` |
| v2 | 通过 `runtime::with_widget` 取控件再 `emit` | `JsonLoader::load` **不挂载**到 runtime，`with_widget` 返回 `None` |

**最终版本**（诚实且可失败）：断言 **capability 层面**的事实——
`connect_event("button","clikced")` **必须 `is_err()`**，
而 `clicked` **必须 `Ok`**——并在测试文档里**写明为什么不做更强的断言**。

> **这是本轮最诚实的一条**：与其写一条**永远通过**的断言冒充覆盖，
> 不如把**可观测的边界**写清楚，让后来者知道这里的验证深度到哪。

### 5.4 一个**自引入**的缺陷：`Window::close()` 改坏了

修 `close()` 时我写 `self.base.set_visible(false)` —— `BaseWidget` **没有**这个方法

## 11. 一句话结论

**BLUE19 的主体（事件类型化 → JSON 往返 → 绑定规则 → 自动接线 → 镜像判定 → JSON 路径合并）
已全部完成，完成度 35% → 83%**；剩下的是 D7-b 衍生的模式 2 生成器（T-23/T-24），
属**新增能力**而非未闭环项，其**全部前置条件已在本轮就位**。

**本轮真正抓到的缺陷不在「事件」上，而在两个**盲区**里**：

1. **门禁只查入口不查出口** —— `enabled` 契约覆盖了 `handle_event`，
   于是容器的**发射端**成了盲区（`StackedWidget`、`StatusBar` 两处真实缺陷）。
2. **门禁自己可以是假的** —— 本轮三个新门禁中**两个的第一版是同义反复**
   （「检查符号存在」与「解析器在嵌套括号处截断」），
   **只有反向注入能抓住它们**（`WIRE_RULES.iter().take(0)` → 门禁全绿）。

> 这两条合起来说明一件事：**「门禁全绿」只在门禁本身被反向注入验证过之后才有意义。**
> 本轮新增的 4 个门禁**全部**带反向注入步骤，且**都实测 FAIL 再恢复 PASS**。
