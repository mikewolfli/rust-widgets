## 1. 依赖强制升级（用户追加指令）

### 1.1 `getrandom` 解析失败（已修）

**错误**：`rust_widgets` 依赖 `getrandom` 的 `js` feature，但 0.4 没有该 feature。

**根因**：`Cargo.toml` 的 `[target.'cfg(target_arch = "wasm32")'.dependencies]` 把别名 `getrandom02` 指向了 **0.4** 却要求 `js`。`getrandom` 的浏览器后端特性在 **0.2 叫 `js`**，0.3 起改名 `wasm_js`（原则 #43）。该别名服务的是 `boa_engine → rand 0.8 → rand_core 0.6 → getrandom 0.2` 的传递依赖，因此必须指向 0.2。

**修复**：`Cargo.toml`
```toml
getrandom02 = { package = "getrandom", version = "0.2", features = ["js"] }
getrandom = { version = "0.4", features = ["wasm_js"] }
```
**证据**：`cargo check --lib` → `Finished dev profile`。

## 11. DM-06/07/08/09/11/12 的确认最优方案（架构决策，待执行）

经全局核对四种候选后，确认唯一不会引入新缺陷的方向：

| 候选 | 结论 |
|---|---|
| A. 容器继续持有 `Box<dyn Widget>`，loader 把已挂载控件 detach 后交出去 | 否：事件/绑定按 registry id 寻址，detach 后槽内容不可交互；且子树仍在 MOUNTED 会形成孤儿子树。 |
| B. 为槽位新增 `MountedId` 适配器（代理到 registry） | 否：控件同时留在树里会被树绘制器二次绘制；移出树又丢失 hit-test 路径，且 `Widget::base_mut` 无法安全代理。 |
| C. 槽内容改为“未挂载组合树” | 否：子控件仍按 id 绘制/路由，未挂载即不可用。 |
| **D. 容器内容模型改为 `ObjectId`，registry 保持唯一所有权** | **是**。与 `TabWidget::add_tab(title, Option<ObjectId>)` 的既有形态一致，绘制/事件/焦点都走同一条树路径，不需要第二套所有权。 |

**执行顺序（供下一轮按序落地，避免半接线）**：
1. 单槽容器：`scrollarea`、`collapsible_pane`、`safe_area`、`dialog`、`bottom_sheet`、`modal_bottom_sheet`、`popup_window` → 新增 `set_content_id(ObjectId)` 并让 draw/hit-test 走 `draw_bridge`/`widget_at`；
2. 多槽容器：`stacked_widget`、`accordion`、`wizard`、`dock_widget`/`dock_area`、`splitter`、`toolbox`、`navigation_stack`；
3. `adaptive_scaffold` 的 `body/fab/drawer/...` 与 `mdi_area` 子窗；
4. 每完成一族，loader 增加对应 `"slot"`/`"pages"` arm 并登记 `is_loader_owned_key`；
5. 每族同步增加“JSON 声明 → 内容可交互”的集成测试。

该重构跨 16 个容器及其 draw/event 路径，且计划原文要求"不改容器 API"，两者冲突；本轮不做半成品，避免产生新的不可交互控件。

## 14. DM-11 收官：`navigation_stack` 内容路由

### 14.1 为什么它最后做

上一轮判它“不能做干净”，因为 `pages: Vec<Box<dyn Widget>>` 且控件自己逐页 `draw` + `push_clip`。本轮换了个角度看：**`stacked_widget` 已经用“id 页 + 写几何 + 隐藏非当前页”跑在生产里**（它的 `registry` 只有测试/示例会设，生产靠树绘制器）。同一套模型可以直接搬到 `navigation_stack`，动画也不用丢。

### 14.2 实现

- `pages: Vec<PageSlot>`，`enum PageSlot { Owned(Box<dyn Widget>), Mounted(ObjectId) }`。一个列表而不是两个，因为 `replace_top`/`insert`/`pop_to` 寻址的是**位置**而非存储方式；两个列表会在每次变更时错位。
- 新增 `push_id(ObjectId)` / `page_id(index)`；`pop`、`pop_to`、`pop_to_root`、`replace_top` 对 `Mounted` 槽统一走 `release_slot`（解链 + 隐藏）。
- `sync_mounted_pages()`：写入 id 页的矩形与可见性，偏移量算法与 `draw` 里 owned 页完全一致（入页 `slide × width`，出页 30% 反向视差）。只显示顶部两页（settle 后恰好一页）。
- `tick` 在 `was_moving` 时调用 `sync`：settle 那一帧 `tick` 已经报“停了”，用 `moving` 会跳过这次同步，导致出页多留一帧。
- loader 新增 `navigation_stack` 路由：`children` 依序 `push_id`（首个为根，后续依次入栈）。

**为什么偏移写进几何而不是 paint context**：owned 页由本控件自己画，可以用 `push_offset`；mounted 页由**树绘制器**画，它不认那个 context，所以同样的视觉必须表达成矩形。算术只在一处，两种页不会滑出不同距离。

### 14.3 证据

## 16. RD-04 接线闭合（GPU 管理子系统）

### 16.1 GPU 管理是干什么的（先回答“收益在哪里”）

`src/gpu/` 不是一个“备用渲染器”，而是一层**硬件自适应管理**，把四件分散的事聚到一处：

| 组件 | 职责 | 消费它的真实问题 |
|---|---|---|
| `GpuManager` + `AdapterInfo` | 适配器事实、操作模式（Hardware/Software）、降级后端警告、浏览器强制核显提示 | 宿主无法回答“我现在是不是软件渲染 / 是否跑在降级后端” |
| `gpu::performance`（`AdaptivePerformanceMonitor` / `PerformanceTrapDetector` / `QualityLevel` 跟踪） | 帧时、稳定性、连续好/坏帧、陷阱归类与改善建议 | 没有真实帧输入时，它就是一堆永远 zeros 的状态 |
| `GpuStagingBufferPool` + `GpuUploadBatcher` | 按 GPU 类型配置的环形暂存池、小上传合并、溢出回退链 | 上传预算与合并策略的宿主面 |
| `backend_ladder` | `Primary` → GLES → 软件的降级阶梯 | `WgpuRenderer` **已经在用**它选后端 |

所以“有收益”成立：**不是算了白白浪费，而是算完没人看**。删除会把宿主也需要的事实（模式、警告、帧时、建议）一并删掉；正确做法是把它们接到真实帧路径上。

### 16.2 为什么不能接第二条选卡路径

`GpuManager::new()/with_strategy()` 会自己跑 `AdapterSelector::select_adapter_with_fallback`，而 `WgpuRenderer::new_async` 已经用 `backend_ladder::select_adapter_with_gl_fallback` 选过了。两条路径同时跑就是原则 #101 说的“同一概念的第二条实现”。因此接线采用 **`GpuManager::from_adapter_info`**：拿 `wgpu` 已经报的适配器事实构造，**不重新选卡**。

### 16.3 改动

1. `GpuManager::from_adapter_info` 从 `async fn` 改为 `fn`：它本来就没有 await 点，而这个关键字恰好让“在异步构造函数里建管理器”变成嵌套执行器的坑。`new`/`with_strategy` 保持 async（选卡真的会 await）。
2. `WgpuRenderer` 新增字段 `gpu: GpuManager`，在 `from_device` 里由 `AdapterInfo::from_wgpu(&adapter_info)` 构造；建不出来就报构造错误，**不静默塞一个 stub**。
3. `render_draw_commands_rgba8` / `render_draw_commands_cached_rgba8` 用 `begin_frame()`/`end_frame()` 夹住整帧（无论成败都记录——失败的帧也是宿主等过的帧，瞒着监测等于把陷阱探测器弄瞎）。
4. `begin_frame` → `GpuStagingBufferPool::next_frame()`，环形游标每帧推进，池子在帧路径上而不是旁边。
5. 新公开访问面（宿主读同一份事实，不第二次探 GPU）：`gpu_adapter_info`、`gpu_operation_mode`、`gpu_performance_stats`、`gpu_buffer_pool_stats`、`gpu_warnings`、`gpu_recommended_actions`、`should_degrade_quality`、`should_upgrade_quality`。
6. 文档重写：`gpu/mod.rs` 的 Reachability 补真实消费者；`buffer_pool.rs` 写清“环形游标每帧推进、区域分配器为何仍无仓内调用方”（`wgpu` 的 `write_buffer`/`write_texture` 自己暂存，第二道环只会**多**一次拷贝）。

## 18. RD-04 复测：显式上传环（方案 A）是否真的更快？

用户要求"选 A 之前先验证是否有加速"。本轮把 `GpuStagingBufferPool` 恢复出来，并写了一条**在真实 wgpu 设备上**的对照测量（`src/gpu/buffer_pool_ring_tests.rs`，随 `gpu-wgpu` 特性集跑在 `cargo test --lib` 里，无 GPU 时打印 skipped）。

### 18.1 测量设计（保证可比）

| 维度 | 做法 |
|---|---|
| 同一设备 / 同一批次 | 一次 `request_adapter`+`request_device`，三列复用同一组目标缓冲 |
| 同一字节数 | 每帧 4 个目标缓冲，各上传 64 KiB / 512 KiB / 2 MiB（= 一帧的 uniform/instances/circle/path 形状） |
| 同一提交形状 | 两列**每帧都建一个 encoder 并 submit 一次**（基线原来用空 `submit`，会更便宜，已修正） |
| A 的最强形态 | 每个环槽**独立** staging buffer + 4 槽轮转，槽只在被复用时 `map_async`+`poll` + 重映射；一次 map/unmap 覆盖该帧全部目标 |
| 校验不做假 | 三列跑完后各自 `copy_buffer_to_buffer` → 读回，逐字节等于源载荷；"更快"不可能靠少传字节 |

### 18.3 结论：**A 是负收益，不是加速**

1. **环的编码/提交本身确实便宜 2.8–5 倍**（66 vs 168 µs、105 vs 349 µs、202 vs 1005 µs）。这是真的：`write_buffer` 每次都要做 staging 记账。
2. **但环必须为每帧付一次"槽可重写"的等待**：`map_async` + `device.poll(Wait)` 在 Metal 上是 **351 / 485 / 833 µs**，比它省下的编码时间高一个量级。净结果 +149% / +69% / +3%。
3. **这个等待是结构性的**，不是实现没写好：persistently mapped 的 buffer 在被 `copy_buffer_to_buffer` 读之前**必须 unmapped**（wgpu 校验），所以每帧至少一次 unmap + 一次 remap；槽再多也只是把同一个 round trip 摊到不同槽上，每帧仍有一次。`wgpu` 自己的 staging belt 之所以快，是因为它**成批** push/unmap，把多次 map 摊到多帧——要复现这一点，等于把 belt 重写一遍（原则 #101 明确禁止）。
4. **池子本身再叠加 0–10% 开销**（同样的环，只是偏移量由 `allocate` 给出）。它的唯一增量价值是"分配 (slot, offset)"这一行算术。

**判定**：按"正收益才保留"的标准，A **不成立**。RD-04 维持上一轮的删除结论，且现在这个结论有本机实测支撑，不再是"看起来没用"。

### 18.5 归档结论（供 RD-04 引用）

> 显式上传环对本 crate 的上传形状**不是加速**：它的编码成本低 2.8–5 倍，但每帧必须为“槽可重写”付一次 `map_async` + `Device::poll`（Metal 上 350–830 µs），净结果慢 2–149%。`wgpu` 的 staging belt 靠**成批** push/unmap 摊还这次映射；复现它等于重写 belt（原则 #101）。因此 `GpuStagingBufferPool` / `GpuUploadBatcher` 按 RD-04 的删除分支处理，`GpuManager`（适配器事实、性能采样、建议）保留并逐帧驱动。
