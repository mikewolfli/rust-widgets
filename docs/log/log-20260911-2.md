## A. 结论（先说结果）

**验证主机本身就是 macOS 主机**：macOS 15.7.3（BuildVersion 24G419）、arm64、rustc 1.98.0、Xcode 26.2（iOS 26.2 Simulator runtime）。

因此 blue14 §二 中两条被判为「无 Apple 运行环境」的 A 类未完成项，**本轮在本机真机闭环**：

| 原项 | 原判定 | 本轮实测 |

| A 类 #4 iOS 模拟器/真机视图行为 | 无 Apple 运行环境 | ✅ **iOS 26.2 模拟器 9/9 断言 PASS**（真实 `UIWindow`/`UIButton`/`UILabel`/`UITextField`） |

## C. 四个主机可见的真实缺陷（F 类）

### F-1 cocoa-legacy 后端全部 AppKit 调用无主线程守卫 → 测试进程 SIGABRT

**修复前（可验证）**：在 macOS 上执行 `cargo test --lib --features desktop`：

```
running 3836 tests
fatal runtime error: Rust cannot catch foreign exceptions, aborting
error: test failed, to rerun pass `--lib`
Caused by:
  process didn't exit successfully: `.../rust_widgets-...` (signal: 6, SIGABRT: process abort signal)
```

用 `--test-threads=1` 定位到首个触发点：

```
test bindings::binding_impl::tests::c_abi_widget_lifecycle_roundtrip ...
fatal runtime error: Rust cannot catch foreign exceptions, aborting
```

lldb 抓到：

```
[threadmgrsupport] _TSGetMainThread_block_invoke():Main thread potentially initialized incorrectly
fatal runtime error: Rust cannot catch foreign exceptions, aborting
* thread #2 ... stop reason = signal SIGABRT
frame #0: libsystem_kernel.dylib`__pthread_kill + 8
```

`src/bindings/binding_impl.rs:1110` 的 `rw_create_window(...)` → `MacOSPlatform::create_window`
（`src/platform/macos/platform_impl.rs:66`）无条件执行 `NSWindow::alloc(nil)`。Rust 单元测试在
worker 线程上运行，AppKit 在非主线程构造 `NSWindow` 抛出 **Objective-C 外来异常**，
Rust 无法捕获 → 进程中止。原注释「Cocoa APIs require the main thread, guaranteed by the
platform contract」**没有运行时强制**。

**复现**：`git stash` 后重跑仍在（属既有缺陷，非本轮引入）。

**修复**：
1. `types.rs` 新增主线程守卫：

```rust
pub(crate) fn is_main_thread() -> bool {
    // SAFETY: `+[NSThread isMainThread]` is a thread-safe class method that is
    // safe to call from any thread and never raises.
    unsafe { msg_send![class!(NSThread), isMainThread] }
}
```

2. 离线（非主线程）路径统一回退到 **state-only handle**（`ptr == 0`），保留 id/文本/几何语义，
   与 `macos_objc2` 的 `MainThreadMarker::new()` 既有模式、以及本文件已有的
   `create_native_dialog` 守卫一致：

```rust
if !super::types::is_main_thread() {
    return self.register_state_only_handle(HandleKind::Window, title, x, y, width, height);
}
```

3. 父级校验语义保留：无父级/未知父级仍返回 0（`c_abi_widget_lifecycle_roundtrip`
   断言 `rw_create_button(9999, …) == 0`）。
4. `add_to_parent_window`/`sync_list_box_native` 跳过 nil 接收者 —— 否则 cocoa crate 会在
   `msg_send!` 到 nil 时以 `null pointer dereference occurred` **非解绑 panic** 中止进程
   （这是修复第一版守卫后暴露的第二个中止点）。

**验证**：

```
$ cargo test --lib --features desktop
test result: ok. 3836 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 1.00s
```

### F-2 objc2 原生 FFI 用别名 feature 门控 → `--features macos` 静默退化

**修复前（可验证）**：`Cargo.toml` 的 OS 后端轴定义是 `macos = [...]`，而
`objc2-macos = ["macos"]` 是**单向别名**（启用 `macos` 不会启用 `objc2-macos`）。
`macos_objc2` 的 43 处原生路径却门控在 `feature = "objc2-macos"`。实测：

```
$ cargo run --example apple_appkit_probe --features macos
backend = macos-objc2-preview
[FAIL] native_window_registered: NSApplication.windows.count = 0

$ cargo run --example apple_appkit_probe --features objc2-macos
backend = macos-objc2-preview
[PASS] native_window_registered: NSApplication.windows.count = 1
```

即**文档记载的 `--features macos` 下，`create_window` 走不到 `create_ns_window`，静默退化为 state-only**
（违反规则 #25 FFI 接线完整性 / 规则 #12 禁假修复：这是「看起来像有原生实现」）。

**修复**：43 处 `feature = "objc2-macos"` → `feature = "macos"`（规范名）。因别名是 `objc2-macos → macos`，
`--features objc2-macos` 仍然有效，两个入口现在**行为一致**。

**验证**：两个入口均 `native_window_registered = 1`、`native_menu_bar` 装上 `mainMenu`（见 §D）。

### F-3 objc2 `set_native_text` 的 `performSelector:withObject:` 返回类型错误

**修复前**（被 F-2 掩盖，F-2 修复后暴露）：

```rust
let _: () = msg_send![object, performSelector: selector, withObject: &*value];
```

`performSelector:withObject:` 返回 `id`，而声明为 `()`。objc2 运行时**校验声明签名**，实测：

```
thread 'main' panicked at src/platform/macos_objc2/native.rs:147:29:
invalid message send to -[NSButton performSelector:withObject:]: expected return to have type code '@', but found 'v'
```

即**任何一次设置控件文本都会中止**。**修复**：改为分派类型化消息，去掉 `performSelector:`：

```rust
if selector == sel!(setStringValue:) {
    let _: () = msg_send![object, setStringValue: &*value];
} else if selector == sel!(setTitle:) {
    let _: () = msg_send![object, setTitle: &*value];
} else {
    let _: () = msg_send![object, setAccessibilityLabel: &*value];
}
```

**验证**：两个后端探针的 `widget_text_roundtrip` 均 PASS（`get_widget_text = "Clicked"`）。

### F-4 `full` / `--all-features` 在 macOS 上重复定义 `create_native_platform`（E0428）

## C-2. 第 9 轮补审 —— 探针加强后暴露的 2 个「静默无操作」缺陷

**动机（规则 #12/#19）**：首轮探针只断言「对象已创建」与「state 往返」，
**无法区分「真实 FFI 接线」与「state-only 桩」**。补上「变更是否真到达原生对象」的断言后，
又暴露 2 个真实缺陷。

### F-5 objc2 把视图 selector 发给 `NSWindow` → 方法不存在 → 中止

**修复前（可验证）**，用一次性探针从 worker 线程变更已创建的窗口：

```
created window=1 button=2 on ThreadId(1)
thread '<unnamed>' panicked at src/platform/macos_objc2/native.rs:109:21:
invalid message send to -[NSWindow setFrame:]: method not found
worker panicked
```

根因：`set_native_frame` 无条件发 `setFrame:`，而 `NSWindow` **不响应** `setFrame:`
（窗口用 `setFrame:display:`）；`set_native_hidden` 同理（窗口用 `orderOut:` /
`makeKeyAndOrderFront:`，非 `setHidden:`）。**修复**：

```rust
let is_window: bool = msg_send![object, isKindOfClass: class!(NSWindow)];
if is_window {
    let _: () = msg_send![object, setFrame: rect, display: true];
} else if msg_send![object, respondsToSelector: sel!(setFrame:)] {
    let _: () = msg_send![object, setFrame: rect];
}
```

四个 setter（`frame`/`hidden`/`enabled`/`text`）同时补上主线程守卫。

**验证**：

```
[PASS] native_window_frame_applied: NSWindow frame updated to 400x300 = true
[PASS] native_window_visibility: after_hide=false after_show=true
```

（这两个断言在修复前对 objc2 后端**会失败**；cocoa-legacy 因早已做窗口/视图分派而一直通过。）

### F-6 iOS `set_native_text` 对 `UIButton` 是静默无操作

**修复前（可验证）**：探针新增 `native_text_applied` 后：

```
[PASS] text_roundtrip: rw_get_widget_text = Tapped
[FAIL] native_text_applied: UIButton title = Tap        ← 原生标题从未更新
```

根因：原循环用 `respondsToSelector:` 探 `setTitle:forState:`——该 selector 是**双参数**，
单参数探针永远返回 false，于是落到同义可响应的 `setAccessibilityLabel:`，
**可见的按钮标题一直被写到了无障碍标签上**。这是 F-3 的孪生体（同一段循环的另一种破坏方式）。

**修复**：改为类型化分派（`setTitle:forState:` → `setText:` → `setAccessibilityLabel:`）。

```
[PASS] native_text_applied: UIButton title = Tapped      ← 修复后
```

> **方法论教训**：若首轮探针停在 `rw_get_widget_text` 的 state 往返，F-6 会被当成已闭环（假修复）。
> 探针现已对**原生属性**直接断言：`NSWindow.frame`/`NSWindow.isVisible`、`UIButton.titleForState`。

## C-3. 第 9 轮补审 —— 「环境性失败」实为代码缺陷（`libvorbis` 硬编码）

**背景**：§C 的 F-4 验证曾记录 `--all-features` 有「1 个环境性失败」：
`Encoding to Ogg should succeed: Err("Encoder 'libvorbis' not found")`，
并标注「与平台代码无关（未触碰 `src/audio/*`）」。**该归因本身未经充分取证，本轮推翻。**

### 取证：环境到底能不能修

```bash
$ brew deps ffmpeg | grep -i vorbis
(空 — libvorbis 不在 ffmpeg 的依赖列表)
$ brew cat ffmpeg | grep -i vorbis
(空 — formula 根本不引用 libvorbis)
$ otool -L $(which ffmpeg) | grep -i vorbis
(空 — 二进制未链接 libvorbis)
$ ffmpeg -encoders | grep -i vorbis
 A..X.D vorbis    Vorbis          # 只有内建 vorbis，且标记 X = experimental
```

**结论**：`brew install libvorbis` **无法**修好该测试——Homebrew 的 ffmpeg 从不编译
libvorbis 支持，装独立库不会改变已编译二进制里的编码器表。
因此失败是**代码硬编码外部可选依赖**所致，任何「无 libvorbis 的 ffmpeg」都会失败。

### 根因（`src/audio/ffmpeg_encoder.rs`）

```rust
// 修复前
AudioFormat::Ogg => Ok(("ogg", "libvorbis", 128_000)),   // 硬编码外部库
```

改为运行时探活后，又暴露**两个必须同时解决的前置条件**（一次性都能编过才算修好）：

1. **experimental 标志**：内建 `vorbis` 被 FFmpeg 标记为 experimental，
   `open_as` 报 `Experimental feature`，需显式 opt-in（CLI 等价 `-strict -2`）。
   已确认 `ffmpeg-next 9.0.0` 提供该 API：
   `codec/context.rs:102 pub fn compliance(&mut self, value: Compliance)`，
   且 `codec/Compliance::Experimental` 已导出；`encoder::Audio` 经 `DerefMut` 可达 `Context`。
2. **采样格式差异**：内建 `vorbis` **仅支持 `fltp`（planar）**，而 `libvorbis` 接受 `flt`（packed）；
   原代码固定传 `flt` ⇒ `Specified sample format flt is not supported` → `Invalid argument`。
   现改为从 `codec_audio.formats()` 中优先选 packed F32（零转换），否则取首个支持的格式，
   由既有 resampler 完成转换。

### 修复后行为

| 项 | 修复前 | 修复后 |
|---|---|---|
| Ogg 编码器 | 硬编码 `libvorbis` | `libvorbis` → 内建 `vorbis` 回退 |
| 采样格式 | 固定 `flt` | 按编码器实际支持选择（`fltp` 时走 resampler） |
| experimental | 未处理 | 内建 `vorbis`/`opus` 自动 opt-in |
| Opus | 硬编码 `libopus` | `libopus` → 内建 `opus` 回退 |

### 验证（非假修复）

```
$ cargo test --lib --features "desktop,video-codecs" test_encode_all_formats_succeed
test result: ok. 1 passed; 0 failed          # 修复前：FAILED (Encoder not found)

$ cargo test --lib --all-features

$ cargo test --lib --features full
```

### 新增回归测试（`ffmpeg_encoder::tests`）

| 测试 | 锁定的事实 |

## I. 第 9 轮补审之三 —— 换方向：FFI 健全性审计（unsafe / 类型身份）

前面各轮都在查「功能有没有接线」，本轮改查 **`unsafe` 边界的正确性**（平台 FFI 最容易在此处
「测试全绿但运行时崩」）。方法：不用意见，用工具与复现。

### I-0 基线与排除项（证明先）

| 检查 | 结果 |
|---|---|
| `unsafe` 块总数 | 238 |
| `unsafe_op_in_unsafe_fn`（Rust 2024 默认）告警 | **0** —— 未在 `unsafe fn` 里裸做 unsafe 操作 |
| `unsafe impl Send/Sync` 总数 | 9 |

### I-1 `unsafe impl Sync for NativePtr` 是多余的不安全承诺

`macos_objc2/native.rs` 与 `ios/native.rs` 的 `NativePtr(*mut c_void)` 同时 `unsafe impl Send + Sync`。
实测（逐个注释掉后重新编译）：

| 组合 | 编译 |
|---|---|
| 原样（Send + Sync） | ✅ |
| 去掉 `Sync` | ✅ **仍通过** |
| 去掉 `Send` | ❌ `E0277: *mut c_void cannot be sent between threads safely` |

即：**`Send` 必需（static `Mutex<HashMap>` 要求），`Sync` 完全多余**。
而 `Sync` 恰好放宽了「`&NativePtr` 可跨线程共享」这层约束 —— 即 AppKit/UIKit 对象可被任意线程读到指针，
正是 F-1/F-5 能发生的结构性前提。已移除两处 `Sync`（保留 `Send`），并在注释中说明理由。

> 同类仍待处理的（**需对应平台验证，本轮未动**）：
> `ime_windows.rs` 的 `TsfThreadMgr`（无 Windows 机器）、`android/types.rs`、`linux/types.rs`、
> `json/events.rs`、`widget/registry.rs`、`memory/allocators.rs`、`video/ffmpeg_decoder.rs`。

### I-2 真实缺陷：`ime_macos` 的 `ImeCtx` 被定义成四个不同的局部类型

**发现**：`ImeCtx` 在**四个不同函数作用域内**各声明一次（`try_activate_nstextinputcontext`、
`sync_nstextinputcontext`、`focus_in`、`focus_out`）。它们同名、同布局，
但 `Any::downcast_ref` 按 **`TypeId`** 匹配，**不看内存布局** —— 所以四个是四个不同类型，
`token.downcast_ref::<ImeCtx>()` **永远返回 `None`**。
原注释「the repr(C) layout guarantees downcast_ref works」是错的。

**实测证明**（最小复现）：

```
token value TypeId : TypeId(0x8a710b0c2879d0d14a6edc3caaa9afa8)
local ImeCtx TypeId: TypeId(0xe77e611133586ea066d0e40771b3b9ff)
consumed (downcast ok)? false
--> false means the bridge never reaches its NSTextInputContext
```

**影响**：3 条原生路径全部静默失效（与 F-6 同类「假接线」）：

| 位置 | 应当调用 | 修复前实际 |
|---|---|---|
| `sync_nstextinputcontext` | `invalidateCharacterCoordinates` | 永远 early-return |
| `focus_in` | `activate` | 永远不执行 |
| `focus_out` | `deactivate` | 永远不执行 |

**修复**：把 `ImeCtx` 提升为**模块级唯一定义**，新增 `ime_ctx_from_token()` 统一转换。

**新增回归测试**（`ime_macos::tests`，+2）：

- `ime_token_downcasts_back_to_ime_ctx` —— 断言 token 能 downcast 回 `ImeCtx` 且指针值往返一致；
- `ime_token_rejects_foreign_type` —— 断言无关类型不会被误认。

**负向验证**（规则 #16）：把代码改回「局部 struct」旧写法后：

```
ime_token_downcasts_back_to_ime_ctx ... FAILED      ← 测试如期抓到旧缺陷
```

已恢复修复，测试再全绿。

### I-3 冰山扫描（同类模式）

全项目 `downcast_ref` 扫描：其余全部使用**模块级类型**（`&str`/`String`/`WindowsPlatform`/
`WaylandPlatform` 等），**无同类问题**。函数内 `struct` 仅剩 `ios/native.rs` 的 `ButtonTarget`，
它是 `define_class!` 宏类型、走 ObjC 运行时而非 `Any::downcast`，不适用。

## J. 第 9 轮换方向之二 —— 错误路径与资源泄漏审计

与 §I 同属本轮换方向审计，主题为**错误处理路径的资源释放**。

### J-1 `ffmpeg_encoder` 编码失败时泄漏临时文件

**根因**：`ffmpeg_next::format::output_as` 会**立即在磁盘创建文件**，而后续有大量 `?` 提前返回
（resampler 构造、编码器打开、帧发送、包写入……）。原实现只在**成功**路径末尾 `remove_file`
⇒ **任何失败都泄漏文件**。

**实测复现**（修复前）：

```
before: []
encode result: Some("Failed to create resampler: Invalid argument")
after : ["rust_widgets_audio_enc_80794_0.mp3"]
LEAKED_COUNT=1
```

**修复**：新增 `TempFileGuard`（RAII），`Drop` 删除文件，覆盖所有退出路径。
**验证**（同一探针，修复后）：`after : []`，`LEAKED_COUNT=0`。

**新增回归测试**：

- `temp_file_guard_removes_file_on_drop` —— 确定性验证 guard 契约；
- `test_failed_encode_leaves_no_temp_file` / `test_successful_encode_leaves_no_temp_file`。

**负向验证**：注释掉 guard 的 `Drop` 删除后，`test_failed_encode_leaves_no_temp_file` **如期 FAILED**。

### J-2 `ffmpeg_decoder` 写入失败时泄漏（同类模式）

`FfmpegDecoder::new` 先 `File::create`，再 `write_all` / `flush`；这两步的 `?` 会在文件已创建后提前返回。
原清理逻辑**只覆盖** `from_path` 失败（且注释自称「If construction failed, clean up」，实际漏了写入失败）
⇒ 写入失败时文件不会被删。

**修复**：同样用 RAII guard；成功时 `disarm()`（所有权交给解码器的 `_temp_path`，其 `Drop` 负责清理）。
新增 2 个回归测试。**负向验证**同样通过（关闭 guard 后测试如期 FAILED）。

### J-3 测试隔离问题（过程中暴露并修正）

为验证 J-1/J-2 写的「临时目录前后快照」断言在 `--all-features` 下**间歇失败**：
同一测试二进制内多个模块（audio/video）并发编码，共享 `TEMP_COUNTER` 与系统 temp 目录，
互相把对方的 in-flight 文件当成泄漏。

处置（不掩盖、不跳过）：

1. 将模组内所有会调用编码的测试串行化（`ENCODE_TEST_LOCK` / `DECODER_TEST_LOCK`）；
2. 断言改为**确定性契约**（guard 的 `Drop` 行为）+ 对具体路径的检查；
3. 新增 `temp_path_in(dir, ext, count)` seam，使路径可推导且不依赖并发时机。

**验证**：连续 10 次 `--all-features` 全绿（修复前为间歇失败）。

## P. 第 9 轮换方向之七 —— H-2 闭环：逐个验证 `unsafe impl Sync` 是否**真的必要**

用户追问「全部解决没？」。回答前先对 **H-2（残留的 `unsafe impl Sync`）** 做逐个`
**实证**验证，而不是靠推理声称「其余待平台验证」。

### P-0 方法：删除-编译法（不是读代码猜）

对每一个残留的 `unsafe impl Sync`，**注释掉该行后编译**：

- 若 **编译失败** ⇒ 该 `Sync` 是 **load-bearing（必要的）**，保留；
- 若 **编译通过** ⇒ 该 `Sync` 是 **多余的不安全承诺（真实缺陷）**，删除。

这比「读注释判断」可靠——注释会过期，编译器不会。

### P-1 验证结果矩阵

| # | 类型 | 文件 | 删除后编译 | 结论 |
|---|---|---|---|---|
| 1 | `EventHandlerContext` | `src/json/events.rs` | **0 errors** | ❌ **多余（已删）** |
| 2 | `LinuxPlatform` | `src/platform/linux/types.rs` | **0 errors**（desktop / full / all-features 均通过） | ❌ **多余（已删）** |
| 3 | `TsfThreadMgr` | `src/platform/ime_windows.rs` | **0 errors**（含 `x86_64-pc-windows-gnu` 真机交叉编译） | ❌ **多余（已删）** |
| 4 | `AndroidPlatform` | `src/platform/android/types.rs` | **55 errors** | ✅ **必要（保留）** |
| 5 | `NativePtr`（ios / macos_objc2） | — | 本就**只有 `Send`** | ✅ 早已正确 |

**发现的真实缺陷：3 个多余的不安全承诺**（原本声称「待平台验证」，实为**本机即可判定**）。

### P-2 为什么危险（不是纯洁癖）

`unsafe impl Sync` 的语义是「**允许 `&T` 跨线程共享**」。对含裸指针的类型而言：

- `EventHandlerContext::user_data<T>() -> Option<&T>` 从**无主、无类型**指针返回 `&T`；
  同时 `user_data_mut<T>() -> Option<&mut T>` 返回 `&mut T`。若 `&EventHandlerContext` 可跨线程共享，
  两个线程就能分别拿到指向**同一对象**的 `&T` 与 `&mut T` ⇒ **数据竞争（UB）**。
- `LinuxPlatform` 内含 `gtk::*`（`!Sync`），GTK 要求所有调用发生在调用 `gtk::init` 的线程上。
  多一个 `Sync` 就多一条绕过该约束的合法路径。
- `TsfThreadMgr` 持有 TSF COM 对象，COM 是**单元线程**模型。

⇒ 这三个 impl **不提供任何收益**，只扩大不安全面。删除是**净安全收益**（与 H-2 已记录的理由同源）。

### P-3 保留的判断依据（`AndroidPlatform` 为何不同）

删除后 **55 个 E0277**（`*mut c_void cannot be shared between threads safely`），说明该 `Sync`
被**真实代码路径需要**（`jvm` 字段使类型含裸指针，且平台实例需跨线程共享）。故**保留**，
并在注释中保留原有的 SAFETY 依据（规则 #22：区分真实需求与虚假承诺）。

## K. 第 9 轮换方向之三 —— 并发安全 / panic 安全 / i18n 时序抖动

### K-1 i18n 热重载：mtime 精度依赖（真实健壮性缺陷）

**先取证再断言**：上轮 `tablet` 的间歇失败被归为「时序抖动」，本轮先验证真因。

实测（macOS/APFS）mtime 为纳秒级，连续写入可区分：

```
mtime1 = SystemTime { tv_sec: 1789182620, tv_nsec: 567245975 }
mtime2 = SystemTime { tv_sec: 1789182620, tv_nsec: 567278225 }
strictly greater? true
write gap = 36.042µs
```

⇒ 抖动**不是**本机 mtime 精度问题。但代码确实存在**同类健壮性缺陷**：
`check_and_reload` 仅靠 `modified > last_modified` 判定变更。在 mtime 粒度粗的文件系统
（ext3 / 部分网络挂载 / 某些容器 FS）上，同一 tick 内的两次写入 mtime 相同，
**变更会被静默漏检**，热重载不触发。

**佐证**：测试里原本有两处 `sleep(100ms)`，其中一处注释直言
「Give the file system time to register a different modification time」——
这正是为规避该缺陷而加的补丁。

**修复**：引入 `FileFingerprint { modified, len, hash }`，按 mtime → 长度 → 内容哈希（FNV-1a）
依次比较，不依赖文件系统时钟推进。

**新增回归测试**：`test_i18n_reload_detects_change_with_identical_mtime`——
写入**等长不同内容**的 payload，并把 mtime **回拨**到加载时记录的值（使 mtime 与长度均不变），
断言仍能检测到变更。
**负向验证**：恢复为 mtime-only 后，该测试**如期 FAILED**。

**顺带清理**：删除两处多余的 `sleep(100ms)`（它们不参与任何同步，仅拖慢测试）。
i18n 测试耗时由 **0.11s → 0.01s**。

### K-2 `static mut` 数据竞争（测试夹具，真实 UB）

`src/undo/stack.rs` 的测试夹具用 `static mut NEXT_ID: u64` 在 `unsafe` 块内 `+= 1`。
Rust 测试**多线程并行**运行，这是一个**真实的数据竞争**（且 `static mut` 在 Rust 2024 是硬错误）。

**修复**：改为 `AtomicU64` + `fetch_add`，消除 `unsafe`。

### K-3 panic 安全：双向绑定重入标志会被 panic 永久卡住

`TwoWayListener::on_value_changed` 先 `syncing.swap(true)` 防重入，函数末尾 `store(false)` 复位。
**缺陷**：若中间任何一步 panic（或 unwinding），末尾的 `store(false)` 不会执行
⇒ `syncing` **永久为 true** ⇒ 该双向绑定**从此静默失效**。

**修复**：改为 RAII guard（`SyncingGuard`），`Drop` 时复位，覆盖包括 panic 在内的所有退出路径。

**新增回归测试**（3 个）：`syncing_guard_clears_flag_on_panic`（真实 unwinding）、
`syncing_guard_clears_flag_on_normal_exit`、`two_way_listener_propagates_and_rearms`。
**负向验证**：禁用 guard 后，两个 guard 测试**如期 FAILED**。

### 已核验无缺陷的方向（取证后排除）

| 检查 | 结果 |
|---|---|
| `catch_unwind` 在 C ABI 边界 | 105 个 `extern "C" fn`中，实际逻辑均经 `c_try!`/`c_try_void!`（`rw_free_rust_string` 为转调，继承保护）——**无缺口** |
| `rw_free_string` 指针契约 | null 有保护；`CString::from_raw` 立即 drop；契约已在文档注释中明确——**健全** |
| 锁顺序反转 | `TwoWayListener` 已明确「先释放 source 再锁 target」并注释说明；其余多锁获取绝大多数在测试代码内（每测试独立 mutex） |
| 全局可变 static | 除已修的 `static mut` 外，均为 `OnceLock`/`LazyLock`/`Mutex`/`Atomic*`——**无可变静态** |

### 已知限制（已登记，非缺陷）

`panic = "abort"` 出现在 `release-embedded` 与 `release-mini` 两个 profile（嵌入式惯用选择，省体积）。
**后果**：这两个 profile 下 `catch_unwind` **不生效**，C ABI 的 panic 保护退化为进程 abort。
这是设计取舍而非缺陷，但使用这两个 profile 的调用方应知悉。
