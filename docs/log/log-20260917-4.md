### 2.2 `WidgetAndDraw` 的归属（用户要求 6 的延伸）

### 2.3 🔴 我自己引入的一个真实回归（被构建门禁抓到）

删除 `create_tile_view` 时，它的 `#[cfg(not(alloc_frugal))]` 属性被一并带走，
导致紧随其后的 `create_tooltip` **失去 cfg 门控**，`mini` 档立即报错：

```
error[E0599]: no variant, associated function, or constant named `Tooltip` found
    --> src/control_backend/custom/create_widgets_modern.in.rs:1168:51
```

**根因**：属性前缀只属于紧邻的下一项；用正则批量删函数时，前一项的 `#[cfg]` 会「粘」到后一项上。

**教训（本轮经验）**：批量删除带 `#[cfg]` 的项时，**必须逐档构建验证**。
编译器只在被门控掉的那一档报错，桌面档全绿 —— 与原则 #48 同类的「错误命令/错误档位会漏报缺陷」。

### 3.2 缺口二：滑动翻页缺「速度」判据

`blue17.md:263` 原文要求「位移阈值 **+ 速度**」，实现只有位移
（修复前 `grep -n "velocity|speed|Instant" carousel.rs` → **0 命中**）。

**修复设计（本轮判断选择，用户要求 5）**：

| 判断项 | 选择 | 理由 / 反例 |
|---|---|---|
| 时间源 | `std::time::Instant` | `SystemTime` 会被 NTP 回调产生负速度；`instant` crate 会新增依赖 |
| 采样点 | 每次 `MouseMove` 记 `last_x`+`last_moved_at` | 用整段手势总时长会把「快─停」误判为慢 |
| 速度函数 | `now` **由调用方传入**（纯函数） | 内部 `elapsed()` 会让测试必须 `sleep` 才能断言 |
| 击发阈值 | 400 px/s | 约等于手机上每秒 1/4 屏宽；更低会与点击手抖重叠 |
| 反抖动下限 | 宽度的 2% | 一帧内几像素抖动可算出极大瞬时速度 |
| 上限 | **10 × 宽度/秒** | 见 §3.3 |
| 判定顺序 | **先距离，后速度** | 距离达标者永远翻页；速度规则只**增加**可识别的甩动 |

### 3.3 🔍 一次被自己的测试推翻的取值（取证过程保留）

初版上限写成「1 × 宽度/秒」，测试立即失败：

```
100px in 250ms must read as 400px/s, got 300
```

**根因**：300px 宽控件上，上限 300px/s **低于** 400px/s 的击发阈值 ——
即**上限把真实甩动钳到了阈值之下，速度规则永远不可能触发**。这是设计错误，不只是测试写错。

**修正**为 10 × 宽度/秒，并补一条**直接断言两常量序关系**的回归测试：

```rust
assert!(real_flick >= FLICK_VELOCITY_PX_PER_SEC, "…must not be capped below it");
```

**教训**：凡引入两个相互比较的常量，必须有一条测试**直接断言这个序关系**，
否则改任一个都会静默失效。

## 5. BLUE18 Phase E′ — 多平台门控（本轮核心）

### 5.1 E′-1 `tools/check_view_platform_gate.sh`

**判据必须是可执行的，不能是 grep**。原因写进脚本：

> grep 构建日志里的 `src/view` 也会匹配到无关诊断里的路径；grep `src/lib.rs` 的
> `cfg` 文本只证明文本在，不证明它有预期效果。

所以判据是**名字解析**：编译一个 `use rust_widgets::view::VIEW_GATE_PROBE;` 的探针 ——
能解析 ⟺ 模块在编译单元里。

**探针为什么带 `cfg` 守卫**：一个无条件的 `use` 会让 `mini`/`embedded` 的
`--all-targets` 构建在**本该没有该模块**的档位上失败，即门禁自己制造它要检测的故障。
所以提交版本用与库相同的表达式守卫导入；门禁运行时写入一份**强制无条件导入**的临时副本，
读完退出码后再恢复（`EXIT` trap 保证崩溃也不残留）。

### 5.2 🔴 E′-5 反向注入 —— 门禁第一次**没有 FAIL**（关键取证）

按计划把 `src/lib.rs:117` 改成 `#[cfg(any(desktop, tablet, mobile))]`（漏掉 `widgets_unstripped`），
预期门禁 FAIL。**实测：门禁仍然 PASS。**

**为什么**（本次实测得出的结论，写入脚本注释）：

| 档位 | `any(desktop,tablet,mobile)` | `all(any(…), widgets_unstripped)` |
|---|---|---|
| `desktop` / `tablet` / `mobile` | true | true（设备档永不 stripped） |
| `mini` / `embedded` | **false**（这两个档不含设备 feature） | false |
| `desktop,mini` 混合（规则 #48 禁止） | true | **false** ← 唯一差异 |

**即：在所有合法单档构建上，两种写法行为完全相同；差异只出现在规则 #48 明令禁止的混合档。**
所以**纯行为探针无法区分它们**，只有行为的门禁就是一个**不可能失败的门禁** ——
这正是 E′-5 要排除的失效模式。

**修复**：门禁增加**第 [4] 步源码判据**，断言 `pub mod view` 的 cfg 仍含 `widgets_unstripped`
与三个设备 profile，并在注释里**如实说明它是源码检查、不是行为证明**：

> 它不声称证明运行时行为，因为它保护的行为在合法构建上不可观测。
> 与 [1]–[3]（在**可观测**处证明表达式效果正确）互为盲区覆盖。

## 6. BLUE18 Phase E / F — 门禁与闭环

### 6.1 E-1 `tools/check_view_keys_are_unique.{py,sh}`（规则 #88）

`src/view/node.rs:124` **已经引用了**这个门禁名，但工具不存在（G8，属原则 #91 同类问题）。

**为什么静态检查**：`View::build` 是任意函数，会按状态分支，一次运行只走到它走到的分支。
**跑一遍并遍历输出，对未走到的分支什么也证明不了** —— 只在空列表分支里重复的 key
能通过每个测试，却仍会在生产里破坏身份。

**实现要点（含两次自我修正）**：

| 版本 | 问题 | 修正 |
|---|---|---|
| v1 | 「扫描到下一个 `;`」把相邻语句并成一条链，130+ 误报 | 改为按语法跟随 `.method(..)` 调用 |
| v2 | 一个链内部的 `.child()` 嵌套本是**不同兄弟集**，却被当成一个 | 记录为已知局限；对**验证重复检测本身**的 3 个测试加显式豁免表（附理由） |

### 6.3 F-2 `tests/view_data_binding_closure_test.rs` + `src/view/reactive.rs`（G5 端到端闭环）

**🔴 本轮自检发现的一处「声称强于实现」**：`blue18.md` D-2 要求
「`Binding<T>` 的监听器**驱动** `update`」，而初版测试只是**计数通知**、然后**手动**调 `update` ——
这证明了「引擎能写属性」，但**没有**证明「监听器驱动更新」。按原则 #13（禁止不完整修复）已补全。

**真正实现** —— 新增 `src/view/reactive.rs`（`ReactiveHost`），解决一个**契约矛盾**：

| 类型 | trait 约束 | 原因 |
|---|---|---|
| `BindingListener` | **必须 `Send`** | binding 可被工作线程 set |
| `ViewEngine` + 所有控件 | **`!Send`** | `widget::runtime` 注册表是 thread-local（控件持有 GPU/OS 资源） |

「订阅一个持有引擎的闭包」**不可能同时满足两者**。这不是要绕开的限制，而是契约本身，
它点名了唯一正确的形状：

```text
  worker 线程                        UI 线程
  ────────────                        ────────
  binding.set(v)
    └─ 监听器触发   ──队列──▶  host.pump()
                                  └─ view.build()
                                     └─ diff → apply   （碰控件）
```

**为什么用队列而不是原子标志**：标志会**丢失中间值** —— 一次 pump 前的两次 set 会坍缩为一次重建，
使「这次改动产生几个 patch」变成依赖时序的数字，测试与推理都不可靠。
队列保持生产者计数精确，合并变成调用方的**显式决定**而非传输层的副作用。

**为什么用 `event::queue::BlockingQueue`**：它的 `push(&self)` 在容量满时**不阻塞**，
`try_pop` 非阻塞抽取 —— 正好是「生产者永不阻塞 + UI 线程每帧排空」需要的两个操作。

**测试**（`reactive.rs` 5 条 + 端到端 2 条）：

| 测试 | 断言 |
|---|---|
| `a_worker_thread_set_reaches_the_ui_thread` | **跨线程**：`std::thread` 里 `set`，UI 线程 `pump` 后控件属性更新（用 `Barrier` 而非 `sleep`，不依赖时序） |
| `pump_conducts_one_update_per_set` | 两次 set → 两次重建；末尾状态生效 |
| `the_queue_preserves_the_producer_count` | 5 次 set → 5 次重建（队列不坍缩） |
| `a_closed_or_full_queue_still_counts_the_notification` | 能区分「已观测但未应用」与「从未观测」 |
| `a_binding_set_queues_and_pump_applies_it` | 无变更时 `pump()` 返回 0 |
| `binding_set_reaches_the_live_control_through_the_view_engine` | `set("second")` 后**真实控件**的 `text` 为 `"second"`（经 `ReactiveHost`，非手动 `update`） |
| `a_binding_driven_update_keeps_the_unchanged_control_identity` | 两次文本更新后父子 `ObjectId` **不变**，`replaced_subtrees == 0` |

**为什么断言不分步（计划 F-2 的明确要求）**：分步断言（先查监听器触发、再查产生了 patch、
再查属性变化）会把测试强度花在中间步骤上，可被逐个满足 —— 例如「监听器触发」为真而写入仍被拒。
断言落在**终态**，中间值进失败信息。

| `demo/code_editor`（独立 crate） | `CodeEditor::new` | ❌ 不涉及 |
| **`view_counter`**（本轮新增） | **`ViewEngine` + `WidgetFactory`** | ✅ **已经就是新架构** |

**判定依据（三条实测）：**

1. **零引用已删控件**：`grep -rn "PagerPageView\|TileView" examples/ demo/` → **0 命中**，
   所以删除不影响任何 demo。
2. **demo 不依赖被改的结构**：八个 `demo_*` 均为「单个控件 + SVG/渲染输出」，
   不涉及树构建、diff 或响应式——而 `view` 层是**纯加法**（规则 #86），
   不改 `add_child` / `create_*` / 属性契约的任何语义。
3. **新架构已有示范**：`examples/view_counter.rs` 就是声明式保留循环的 demo，
   已接入 `tools/smoke_demos.sh`（实测 15 项全 PASS）。

**为什么不应把旧 demo 「改造」成 view 层**：那些 demo 演示的是**控件本身**
（Button 能点、CodeEditor 能编辑），而 `view` 演示的是**结构如何随状态变化**。
把前者改成后者会让它们不再演示原来那个东西，且违反原则 #28（为无消费者处引入间接层）。
二者是两个不同的问题，各自保留是正确的。

**唯一真正相关的项**：`demo/control` 是一个**多控件组合** demo（行式布局 + 事件日志，451 行），
它是「把 `Control` 改成 `View::build`」的候选——但其现有形式本身是有效的命令式用法，
且改造属于**新增演示**而非修复。已登记为未来选项（同规则 #93 的触发条件：出现真实需求）。
