## 2. 根因修复：控件能力工厂（T1）

**根因**：`WidgetFactory::new_with_defaults()` 每次调用重建约 190 个控件的注册表（每个注册做 `normalize_key` 的 `String` 分配 + 2 次 `HashMap` 插入）。属性读写、hover 换肤、视图 diff、JSON 加载全部走这条路径。

**修复**：

- `src/widget/capability.rs`
  - 新增 `WidgetFactory::shared() -> &'static Self`，用 `OnceLock` 只构建一次；工厂构建后只读（扩展表必须自建 `new()`）。
  - 新增 `with_kind_canonical_name()`：用线程本地 scratch `String` 复用，消除 `capability_by_kind` 每次调用的 `String` 分配。
  - `factory_name_for_kind` 改走 `shared()`。
- 热调用点全部改走 `shared()`（共 **38 处生产调用**）：
  `app/handle.rs`、`control_backend/custom/{mod,create_widgets}.rs`、`json/{loader,event_route,mod}.rs`、
  `view/{apply,diff}.rs`、`lib.rs`、`designer/generator.rs`、`widget/{census,draw_bridge}.rs`、
  `widget/container_widgets/{tabwidget,scrollarea,groupbox}.rs`、`widget/menu_toolbar/{menu,status_bar,tool_bar}.rs`、
  `widget/nav_widgets/tab_view.rs`、`widget/input_widgets/{spinbox,combobox}.rs`、
  `widget/special_widgets/split_button.rs`、`signal/event_bridge.rs`、`bindings/binding_impl.rs`。
- `src/json/mod.rs::schema_factory()` 改为返回 `&'static WidgetFactory`，不再按属性/事件逐个重建。

**闭合条目**：`CORE-01`、`WBASE-01`、`WBASE-11`、`BIND-01`、`BIND-02`、`BIND-04`。

**回归测试**：`the_shared_factory_is_built_once_and_matches_a_fresh_registry`
（断言两次 `shared()` 指针相等，且注册表内容与 `new_with_defaults()` 完全一致）。

## 14. 第三批：`REND-01` 的全部放大点（“每次调用重建布局”）

### 14.1 做了什么

问题文件的 `REND-01` 列出了 8 个“同一个反模式”的控件。第二批只改了 ToolBar，本批把剩下的
**全部**改完：每个调用点原本在 `draw` / 命中测试 / `size_hint` 里现建
`CompositeBuilder` + `FlexLayout` + N 个临时 `label` + 一个 `Vec<Rect>`，而这些行/列全部是
`FlexStart`/`FlexEnd` + 固定 gap + 最多一个 `fill` 列——解算器的整个答案就是一次累加。
现在每个控件把自己的行关系写成一个私有函数（名字说明它算的是什么），绘制、命中测试和测试
读同一份结果：

| 文件 | 新推导 | 原本每次调用的开销 |
|---|---|---|
| `menu_toolbar/status_bar.rs` | `segment_boxes`：永久段宽 `max(reserve, padding)`，贴尾边；临时段从 `padding` 起、止于永久段前一个 `padding` | 2 个 label + composite + layout + `Vec` |
| `special_widgets/split_button.rs` | `column_widths`：箭头列保持自身宽，触发列取余量；过窄按比例分摊 | 同上 |
| `input_widgets/combobox.rs` | `column_widths`：指标列 = 图标 + 尾部内缩，值列取余量 | 同上 |
| `input_widgets/spinbox.rs` | `row_widths`：步进列固定，值列取余量；过窄按比例分摊 | 同上 |
| `container_widgets/groupbox.rs` | `title_columns`：指示列 `indicator_reserve()`，标题取余量（保留整段余量给 `Center`/`Right`） | 同上 |
| `nav_widgets/tab_view.rs` | `tab_sizes` + `tab_run`：一次累加，过满时先均摊到 `TAB_MIN_WIDTH`、仍不够再等比缩放 | 每 tab 一个 label + composite + layout |
| `container_widgets/tabwidget.rs` | `tab_run`：一次累加（本批完成） | 每 tab 一个 label |

### 14.2 顺带修掉的真实缺陷（两个 profile 早就给出不同答案）

`mini`/`embedded` 编译不过 `WidgetFactory`，因此这些控件都有“精简 profile 直接算术 / 完整
profile 走布局”的双臂。逐条对照后发现两边**不是同一个关系的两种写法**：

- `TabView::tab_run`：精简臂从 `(0, 0)` 累加，而完整臂把 `strip` 交给布局——控件不在原点时 tab 被画到
  `(0,0)`，命中测试也同样错位（所有既有测试都用 `x = 0`，所以一直未暴露）；精简臂也**不压缩**，
  拥挤的条带会伸出控件（完整臂会压缩）。现已合并成一个推导，坐标含 `strip.x/strip.y`、拥挤时按 G-1 缩放。
- `GroupBox`：精简臂把标题宽钳到实测文本宽，于是 `Center`/`Right` 对短标题完全无效果；完整臂给的是整段余量。统一为后者。
- `ComboBox`：精简臂值框从 `padding` 起、宽度少一个 padding；完整臂从 band 左缘起。而完整臂的 `text_box` 高度只给了行高，`text_line` 在其中居中 → 值文本顶部对齐，而指标是垂直居中的（两套箱高、两个对齐基准）。统一为“值从 band 左缘起、框高取 band 高（竖向居中）”。
- `SpinBox`：窄带时完整臂按比例分摊、精简臂只钳列宽（值列会被压到 0）。统一为按比例分摊。
- `MessageBox`：文档声称这个行通过布局拿到了设备缩放，但它用的是 `Layout::arrange`（不带 context，scale 恒为 1），文档不成立；改为直接推导并把这句话改对。
- `StatusBar`：`set_size_grip_enabled` 的文档写着“当前无视觉变化”，而它同时影响 `size_grip_rect` 与 reserve；`SplitButton` 的 `ARROW_COLUMN_TEXT` 在布局移除后成为死常量。两者均已校正/删除。

### 14.3 顺手修掉的抖动（30% → 0%）

全量跑出了一次 `tests/window_resize_relayout_test.rs:343` 失败。**先隔离、后归因**：
单跑该文件 10 次 → 3 次失败（`FAILED. 7 passed; 4 failed` / `10 passed; 1 failed` 交替），
失败断言是“子控件还停在创建时的 640x480”。

根因（读代码确认，不是猜测）：`poll_widget_trigger_event` 的队列是**进程级**的，而
`dispatch_trigger` 写入的 `WINDOW_STATES` / `LAYOUTS` 是 `thread_local!`（`src/app/handle.rs:1995`、
`:4799`）。并发测试的 `pump()` 会先取走本测试的事件，把它应用到**自己线程**的窗口记录上；
本测试再 `pump()` 已无事件可派，布局就不会重跑。这正是“一个进程级队列 + 线程级状态”的
跨测试互斥问题，宿主机上（创建与派发同线程）不会发生。

修法与该仓库已有惯例一致（`src/app/app_core.rs` 的 `app_init_test_lock`）：在本测试文件加一个
文件级 `Mutex` 守卫，所有测试持有它；`pump()` 的注释同时写清“为什么可以全排空”与前提。
修后连跑 15 次全绿。

### 17.1 `REND-13`：驱动自己持有 scratch 缓冲（已闭环）

`advance` 与 `advance_by` 原本一模一样地每帧建 3 个 `Vec`：`was_running`（飞行中集合）、`snap`
（`(id, progress)` 快照）、`finished`（要移除的）。现在驱动多了两个私有字段 `in_flight` /
`snapshot`，两个入口都先 `clear()` 再 `push`，**容量跨帧保留**；`finished` 这一遍直接复用
`in_flight`（此时它已完成快照任务），所以原来三个分配全没了。

借用问题用字段解构解决：`let Self { animations, property_animations, in_flight, snapshot, .. } = self;`
——Rust 允许对同一个 `&mut self` 的不同字段分别借用，所以循环里可以同时写 scratch 和读/改两
张表，不需要“先把 id 收进一个临时 Vec”。

第一个循环从 `for id in &was_running { if let Some(e) = animations.get_mut(id) }` 改成
`for (id, entry) in animations.iter_mut()`：效果相同（仍是在调用 `update`/`advance_by` 期间持有
表的可变借用），少了一轮 N 次哈希查找，也不会再漏掉采集后才被加入的条目。

### 17.2 `MEDIA-15`：通知集合就是那张表本身（已闭环）

`Binding::set` 原本 `mem::take(&mut inner.listeners).into_iter().collect::<Vec<_>>()` 把
`HashMap` 拆成一个 `Vec`，通知完再逐个 `entry().or_insert` 装回去——每次发布 1 次 `Vec` 分配
- 2N 次哈希操作。现在 `NotifyGuard` 直接持有 `HashMap`：take 出来，迭代，然后 `mem::take` + `into_iter`
装回。**分配从 1 次降到 0 次**，N 次恢复哈希仍在（那是 map 语义自身的代价），但不再有拷贝。

一个跨 profile 的坑（实跑发现）：`crate::compat::HashMap` 在精简 profile 下是 `BTreeMap`，它
**没有 `drain()`**。所以两处恢复循环写成 `for (key, listener) in core::mem::take(&mut map)`，
`HashMap`/`BTreeMap` 都支持。语义不变（拥有型迭代），`mini`/`embedded` 重新编译通过。

重入/吊牌语义完全保留：`notifying` 仍在同一个临界区抬起，`unsubscribed_during_notify` 仍决定
哪些键不恢复，`pending_replays` 仍驱动重放（这些是原注释里逐条记录的历史缺陷，改存储容器不能动它们）。

## 22. 第十一批：`WDGT-09`（绘制循环里的线性选中查找）

### 22.1 先验证：两个控件的情况不同

- `multi_select_combo_box.rs`：`selected` 是 `BTreeSet<usize>`，`insert`/`remove`/`contains` 已是 O(log n)——
  问题文件把 `self.selected.contains(&i)` 当成线性查找，实际不是。**无需修改**。
- `listbox.rs`：`selected_indices` 确实是 `Vec<usize>`，`is_selected` 是真线性查找，而 `draw` 对每个可见行都问一次。

### 22.2 一个前提先不成立：所谓“已排序”的不变量

问题文件说 `select_with_modifiers` 已用 `sort_unstable` 维持有序，因此可以直接 `binary_search`。
但读完全部写入点后发现它**不是全局不变量**：

| 写入点 | 是否保持有序 |
|---|---|
| `insert_item` / `remove_item`（偏移调整） | 是（逐元素 ±1） |
| `clear` / `select`（Single、Extended） | 是（空或单个） |
| `select_with_modifiers` | 是（push 后 `sort_unstable`） |
| `select`（**Multi**） | **否**：直接 `push` 到尾部 |

所以直接上 `binary_search` 会引入错误，并且这是现存的可见缺陷：先用 Multi 选行 3 再选行 1，
公开的 `selected_indices()` 返回 `[3, 1]`（而其他路径都按行序发布）。

### 22.3 改了什么

1. 新增 `ListBox::add_to_selection(index) -> bool`：`binary_search` 定位后 `insert`，保持有序且不重复。
   `Multi::select` 改用它。
2. `is_selected` 改为 `binary_search(..).is_ok()`：每帧每可见行从 O(选中数) 降到 O(log 选中数)。
3. 注释里写清“顺序是一个不变量”，并列出它为什么必须成立（公开访问器的顺序 + 二分查找的前提）。

回归测试 `the_selection_is_published_in_row_order_however_it_was_built`：故意逆序选择（3 → 1 → 4），
断言发布为 `[1, 3, 4]`、三个都读作已选、其余不是、重复选择不重复、Ctrl 追加仍落在行序上。

### 25.2 `REND-15`：一次未变的 `View` 重建应当是 O(变化路径)，而原来是 O(整棵树)

原始症状：`View` 每帧重新求值后调 `diff`，即使什么都没变也要走完整棵树——每个节点一次 `matches`/`consumed` 位置匹配、
每条 child list 一次 key map、每层若干 `Vec` 分配。

| 编号 | 改法 | 位置 |
|---|---|---|
| **B1** | 顶层相等短路：`old == new` 直接返回 `DiffReport::default()` | `diff.rs::diff` |
| **B2** | 未变子树跳过：`diff_children` 里 `unchanged = old.children[old_index] == *child`，未移动且相等就 `continue`（不建 path、不递归） | `diff.rs::diff_children` |
| **B3** | `same_control_kind` 同拼写短路：两个 `&str` 已经回答了“同一个控件”时不再让工厂 `normalize_key` 出两个 `String` | `diff.rs::same_control_kind` |
| **B4** | `PositionalKeys` 备忘：每个 child list 对每个**不同拼写**只做一次工厂解析/规范化，而不是每 child 两次 | `diff.rs::PositionalKeys` |
| **B5** | 位置匹配 pass **惰性化**：新 child list 里没有无 key 子节点时，整段 pass 2（bucket map + 每 child 一个 `VecDeque` + 每 child 一次 key 解析）直接跳过 | `diff.rs::diff_children` |

**B1 的语义后果（写进模块文档，不能只写在日志里）**：`DiffReport::positional_matches` 与 `duplicate_keys` 描述的是
**走过的那部分**；未变的树报 0 是诚实的（没有任何身份被拿去冒险）。要静态地问“这棵树里有没有重复的兄弟 key”，
用 `Node::duplicate_sibling_keys()`。

**B2 为什么是“O(变化路径)”的关键**：跳过的不只是属性比对，而是整条子树递归、它的 path `Vec` 分配、它的 key map 与 LIS。

### 25.3 新缺陷（`REND-15` 的冰山）：`spacer` 在视图引擎里没有挂载分支

**证据链**（顺序即发现的顺序）：

1. `apply::insert_subtree` 有 `spacer` 分支（BLUE22 · F-7）；`view/diff.rs` 的四处文档也在讲 `spacer`。
2. 但 `ViewEngine::mount_children_named` **没有**这个分支：挂载一个含 `spacer` 的视图直接报 `UnknownWidgetType`，
   间距的子树**从未被创建**。
3. 另一半更糟：`spacer` 不产生控件、路径上也没有 id，于是 `diff` 对这块间距每次都发 `Patch::Insert`——
   **每帧给它的内容再插一份副本**，旧的从不移除。

**修复**（三处，缺一不可）：

| 位置 | 改动 |
|---|---|
| `src/view/mod.rs` | 新增 `pub(crate) is_transparent_node(&Node)`（`spacer`，大小写不敏感）与 `pub(crate) mounted_slots(&Node)`（一个 gap 仍占一个 slot 的算术，`mount`/`reindex`/`diff` 共用一份） |
| `src/view/engine.rs` | `mount_children_named` 增加 `first_slot` 参数并返回下一个空闲 slot；透明子节点**不调 `create`**，而是在同一 `node_id` 上按运行中的 slot 递归；`reindex_by_identity` 换成 `reindex_children(.., first_slot, ..)`，让 gap 的子节点**按 key** 定位而不是按位置（按位置会认错兄弟） |
| `src/view/diff.rs` | `diff_node` 早期分支：两侧都是透明节点且有 `parent_id` 时**原地** `diff_children`；旧透明节点被换掉时先为它托管的控件发 `remove_node`；`diff_children` 增加 `base`；新增 `insert_new` / `remove_node` 两个按 slot 而非按 id 寻址的助手；**被移动的透明子节点**描述为 `remove_node` + `insert_new`（它没有 id，`Move { id: 0 }` 会被 `apply` 拒绝） |

### 25.4 基准：**测出来的**前后差异（含被否定的假设）

新增 `benches/capability_bench.rs::sample_view_tree()`（201 节点：window > 40 行 > 5 label，全部带唯一 key）
与两个基准 `view_diff_idle_201_nodes`、`view_diff_one_changed_leaf_201_nodes`。

逐项关闭再测，得到的是**真数字**而不是“应该更快”：

| 状态 | idle | 一个叶子变化 |
|---|---|---|
| 四项全关（“前”） | 7.4479 µs | 8.9936 µs |
| 只关 B2（未变子树跳过） | 3.6582 µs | 10.584 µs |
| 只关 B4（备忘） | 3.6726 µs | 9.8545 µs |
| 只关 B1（空闲短路，B5 在） | 6.7639 µs | 7.8605 µs |
| **最终（B1–B5 全开）** | **3.7468 µs** | **9.9078 µs** |

结论（三条，按证据说）：

1. **空闲重建 −49.7%**（7.45 → 3.75 µs，1.99×）。这是 `REND-15` 点名的场景，也是每帧重算 `View` 的常态。
2. **一个叶子变化 +10.2%**（8.99 → 9.91 µs）。这是 B1 的代价，不是噪声：B1 要在根上做一次深比较，
   而这次比较会走过变化点**之前**的 20 行，之后 B2 又会比较同样这 20 行。
   能不能两头都要？**在当前数据结构下不能**：避免重复比较需要一个缓存“结构指纹”的字段，那是公开结构体 `Node` 的破坏性变更，
   而任何缓存都要跟 `props` 的每次写入同步失效——风险远大于 1 µs。故按“空闲是常态”取舍，并在 `diff` 的文档里把这个数字写死，
   让后来的人不用重新测量就知道这是刻意的。
3. **B2 单独看是净赚**（10.584 → 9.9078，约 6.4%）：它把“未变兄弟”的递归、path 分配、key map、LIS 全部省掉；
   关掉它反而比全关还慢，正说明它省下的东西比 B1 探针贵。

B4 在改成惰性（B5）之后**只服务于无 key 列表**：带 key 的列表根本不再构造那个备忘，所以上表里它的差值（0.5%）是噪声。
保留它的理由从“每 child 省两次分配”变成“无 key 列表里每 child 省一次工厂解析”，范围更窄也更准确——注释已按此改写。

### 27.3 `BIND-08`：按规范化名比较的四份（实为八份）实现

### 27.4 `MEDIA-07`：**删除** `Image::from_bytes_rgba8_shared`（分析后再清理）

清理前的取证：

1. `grep -rn from_bytes_rgba8_shared src/ tests/ benches/ examples/` → 只有定义本身，和一个 `let _ =` 丢弃返回值的测试；
2. 它进缓存后仍 `(*decoded).clone()` 把像素拷贝进 `Image`——**名字承诺 sharing，实现做整图拷贝**；

### 27.5 `REND-12`：**删除**声明侧表（它拖着全局锁在生产路径上）

问题文件写的是“`get_declarations` 无调用者且实现低效”。实读后真实代价更大：

1. `CssParser::parse` 对**每条规则**调用 `store_declarations(&rule.selector_text, rule.declarations.clone())`：

4. `StyleRule` 本身只有 `selector`/`name`/`specificity`，声明从来就不在 sheet 里，一直只在这个侧表里——

### 28.3 `WBASE-06`：帧缓存拆出返回 `Rc` 的形式

### 29.1 `REND-03`：缓存命中不再克隆整个 `ShapedText`

### 29.2 `REND-10`：渐变与文本不再为了“拥有”而拷贝

**(a) `fill_gradient`**：`RenderContext::fill_gradient` 原本对每次渐变绘制构造 `RenderCommand::DrawGradient { gradient: gradient.clone() }`。

### 31.1 `WDGT-16`：TabWidget 的宽度测量缓存

原状：`tab_width_hints(&self)` 每次调用对每个 tab 跑 `estimate_text_width`；draw 和
`MouseMoved` 的命中测试都走它，于是每次指针移动都是一次 O(n) 的簇切分/字形步进。

这样“漏接一个失效点”不会产生脏缓存（这正是首轮 §10.3 迟迟不做它的原因）。
新增测试 `tabwidget_widths_are_cached_and_invalidated_by_their_inputs`：
重复调用复用、改标题重测、改字体重测、改宽度只改变溢出下限而不重测。

## 32. 第二十一批：`PLAT-03` ≡ `MEDIA-04` 打印提交异步化（契约经用户确认）

### 32.1 采用的契约

用户确认选择：**“返回 job 句柄 + 完成回调，库接管临时文件所有权”**。落实为：

- 提交立即返回 [`PrintJobHandle`]；
- 完成/失败通过句柄的 `wait()`/`status()` **和** `PrintJobCallback` 两条通道报告；
- 临时文件由库在 worker 里创建、在成功/失败路径删除，调用方永远看不到路径；
- `submit` 本身失败（例如线程启动失败、页码范围非法）→ 立即 `Err`，**不再调用回调**，
  所以一次提交不可能收到两个结果。

### 32.2 新增公开 API（`src/print/print_impl.rs`，经 `print::*` 导出）

| API | 作用 |
|---|---|
| `PrintJobHandle` | `id()` / `status()` / `is_finished()` / `wait()`；`Clone`，`Debug` |
| `PrintJobCallback` | `Box<dyn FnOnce(Result<(), String>) + Send + 'static>`，在 worker 上执行 |
| `Printer::print_with_settings_async` | 借用文档：渲染在调用线程，写盘+提交在 worker |
| `Printer::print_with_pagination_settings_async` | 同上，显式 pagination |
| `Printer::print_with_result_async` | 默认 pagination、无 settings |
| `Printer::print_with_settings_owned_async` | `Box<dyn PrintDocument + Send + 'static>`：**渲染+写盘+提交全部在 worker** |
| `print::print_to_printer_async` | 原始文本路径的异步版 |

旧的 `print_with_*_result` / `print_to_printer` / `print()` **保留**，实现改为
`async(...).wait()`：行为与错误语义不变，只是把“同步”变成显式的选择。

### 32.3 实现要点

- 每个 job 一个 `rw-print-{id}` 工作线程；状态 `Queued → Printing → Completed | Failed`；
- 结果先写入 `Mutex<Option<Result<…>>>`，再以 `Condvar` 唤醒；`wait()` 在同一把状态锁上
  check-then-wait，不会丢唤醒；
- 回调在 `finish` 之后执行；回调 panic 被 `catch_unwind` 捕获并 `log::error!`，不会让
  worker 静默消失；
- `submit_system_print_job` 在 worker 内写 `.ps`、调用 `spawn_print_job`、最后 `remove_file`，
  两条路径都清理；
- 借用版异步 API 之所以仍在调用线程渲染：`&dyn PrintDocument` 不保证 `Send`；需要
  “整条链都离开 UI 线程”的调用方使用 `print_with_settings_owned_async`；
- `print_to_printer_async` 复制 content 到 worker，原始临时文件名改为
  `rw_print_output_{pid}_{ts}_{seq}.txt`（补上序号，消除同毫秒碰撞）；
- 平台层的 `spawn_print_job` 仍有 30s 上限的 `try_wait` 轮询（Unix）和 powershell（Windows），
  但它们现在运行在 worker 上；UI 线程不再等待。pidfd/`wait_timeout` 优化未引入：它是后台线程的
  安全上界，不值得为此新增依赖，这一理由记录在此。

### 32.4 新增测试（6 条，`print::print_impl::tests`）

| 测试 | 断言 |
|---|---|
| `a_submitted_job_completes_the_handle_and_invokes_the_callback` | 成功结果同时到达 `wait()` 与回调 |
| `a_failed_job_reaches_the_handle_and_the_callback` | 失败结果到达两条通道，状态为 `Failed` |
| `a_panicking_worker_still_finishes_the_handle` | worker panic 被捕获并转为 `Failed`，`wait()` 不会永久阻塞 |
| `synchronous_printing_waits_for_the_async_job` | 同步包装确实等到 worker 落盘 |
| `the_public_async_entry_point_submits_a_memory_job` | 公开异步入口 + 回调 + 内容标记 |
| `the_owned_async_entry_point_renders_and_submits_off_the_caller` | settings 进入 worker 渲染出的 payload |

内存后端的全局 job 数组是进程级的，因此这些测试用**唯一 `color_mode` 标记按内容匹配**，
并只在“清空/取出”类测试之间用 `memory_job_test_lock()` 串行化——与仓库既有的
`print_settings_orientation_reaches_the_output` 采用同一条规则，避免按位置/数量断言。

### 36.1 `MEDIA-03`：内存源不再落盘；视频/音频/图片解码移出调用线程

**① 内存视频源不再写临时文件**（`src/video/ffmpeg_decoder.rs`）

ffmpeg-next 9.0 提供自定义 AVIO：`StreamIo::from_read_seek(Cursor<Vec<u8>>)` +
`format::input_from_stream`。内存字节现在直接交给解复用器，临时文件、`TempFileGuard`、
`TEMP_COUNTER`、`Drop` 里的删除全部删除；`Cursor` 可 seek，所以 `VideoDecoder::seek` 语义不变。
新增两条测试：成功/失败构造后临时目录中都不存在 `rust_widgets_ffmpeg_<pid>_*`。

**② 视频解码线程**（`src/video/engine.rs`）

`VideoEngine` 原先在 `tick_frame` 里同步 `decoder.read_frame()`（1080p 软解 10–30 ms 直接卡帧）。
现在：

- 解码器（`Box<dyn VideoDecoder + Send>`）移入命名线程 `rust-widgets-video-decode`；
- 有界队列 `sync_channel(8)` 做 read-ahead（8 帧 1080p RGBA ≈ 64 MiB 上限）；
- 帧所有权通过通道转移，`VideoEngine` 只持有 `pending`；
- **世代令牌**：每次 `seek` 递增 `generation`，worker 给每个事件打上当时的世代，引擎丢弃旧世代
  的帧/结束标志，因此 seek 后不会先显示一帧旧画面；
- `seek` 等待 `Seeked` 应答，保留“解码器 seek 失败要向调用者报错”的契约（`FailingSeekDecoder`
  测试仍然通过）；
- 队列空时仍阻塞等待一帧——这与旧同步行为一致，保证启动/解码器跟不上时**不劣化**，稳态则命中
  队列、不阻塞。

新增测试 `frames_are_decoded_off_the_calling_thread`（解码器记录 `ThreadId`，断言从不在调用线程读）
与 `a_seek_drops_frames_decoded_for_the_old_position`。

**③ 音频加载异步**（`src/audio/engine.rs`）

`load_async(Vec<u8>)` 在 `rust-widgets-audio-decode` 线程解码，结果经通道回填；
`poll_load()`（每帧轮询）/ `wait_for_load()`（一次性阻塞）安装缓冲；`load()` 保持同步签名。
线程无法创建时退回同步解码并经同一通道交付——失败模式是“更慢”，不是“永远不加载”。
测试用内联生成的 8 采样 16-bit WAV（仓库不再需要二进制夹具）覆盖成功、失败与同步路径。

**④ 图片解码异步**（`src/image/decoder.rs`）

新增 `decode_async(Vec<u8>) -> ImageDecodeJob`（`wait()` / `try_take()`），实现仍是同一个
`decode()`；`decode_to_rgba8` 等同步入口不变。测试用 crate 自己的 PNG 编码器生成夹具，
覆盖往返与失败上报。

### 36.2 `REND-01`：ToolBar O(N²) 消除 + flex scratch + `FlexLayout` 结果缓存

- `ToolBar::draw` 与 `hit_item` 现在各自调用一次 `item_bands()`；此前 `draw` 对每个 item 调
  `item_rect`、`item_rect` 又重建整张 band 列表，绘制与鼠标移动都是 O(N²) 且每帧 N 次分配。
  私有的 per-index helper 已删除（`item_bands` 是唯一入口）。
- `FlexLayout` 收缩循环里每轮 `collect::<Vec<i32>>()` 的 scratch 删除，改为两遍就地计算。
- `FlexLayout` 增加**按输入自失效的结果缓存**：`cache: RefCell<Option<FlexCache>>`，key 是对
  `direction/wrap/justify/align/gap/padding/items/child_sizes` + rect + scale + touch + 全部
  `ChildInfo` 的 FNV 哈希。之所以不用脏标记：这些字段是 `pub`（`items_mut` 还返回 `&mut Vec`），
  加 setter 失效钩子必须把它们改为私有（公开 API 破坏）；以输入做 key 则“改任何字段 ⇒ key 变 ⇒
  重算”，陈旧命中不可表示。
- 构造内部 solver 时手工逐字段复制（不再 `..self.clone()`），避免每次布局都克隆缓存。
- 新增测试：重复 `update` 命中同一 key、改 `gap` 后 key 与结果都变、不同 `ChildInfo` 不复用旧盒子。

实测（`cargo bench --bench capability_bench -- flex_arrange`，40 子项）：

### 37.1 发现并修复：wgpu 颜色 arena 的动态 offset 步长硬编码 256（`src/wgpu_backend/renderer.rs`）

**缺陷（REND-02 实现中的潜伏问题）**：`RenderCache::UNIFORM_STRIDE` 写死 `256`，而 WebGPU 规范
要求动态 uniform offset 是**设备** `min_uniform_buffer_offset_alignment` 的倍数——256 只是常见
后端的值。报告 512 的设备上，`set_bind_group` 的每个 offset 都会被校验拒绝，绘制直接失败。
本机（Iris Xe / RTX 3080 Ti）恰好是 256，所以 §36.3 的 4 个 GPU 测试全绿——**测试通过不代表
该假设在所有设备上成立**。

**修复**：

- 新增 `RenderCache::uniform_stride(device)`：取
  `device.limits().min_uniform_buffer_offset_alignment`，抬到能容纳 16 字节颜色
  （`max(16)`）并向上取整到对齐倍数；
- `UniformArena` 增加 `stride` 字段，`ensure_uniform` 用它算容量并把实际步长存进 arena；
- `render_fill_rect_gpu` 不再读常量，改用 `uniform.stride`（上传布局与绘制 offset 同源，
  不会出现两处不一致）；`UNIFORM_STRIDE` 常量删除。

本机 alignment=256，行为与修复前等价；512 对齐设备从“必败”变为正确。
