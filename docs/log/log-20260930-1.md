## 2. 逐条修复

### 2.1 平台/a11y：macOS `notify_state_changed` 发了错误的通知常量（#1）

**取证**：`src/platform/accessibility/macos.rs:101` 与 `:105` 逐字相同——两条路径都发
`NSAccessibilityFocusedUIElementChangedNotification`。而同类后端在别处**正确区分**：
`windows.rs:90` 发 `EVENT_OBJECT_STATECHANGE`、`:94` 发 `EVENT_OBJECT_FOCUS`；Linux `linux.rs:313`
发 `Object:StateChanged`、`:318` 发 focus。

于是 VoiceOver 收到「焦点移动」而非「状态变化」，辅助输出被静默污染。

**修法**：状态变化改发 `NSAccessibilityValueChangedNotification`（与 `notify_value_changed` 同族，
但语义由调用方的事件类型决定，两者是不同入口），并写明为何不能复用它处常量。

**证据**：见 §4 全量验证（`desktop,a11y` 编译通过）。

### 2.2 macOS `NSString` 泄漏（#4，冰山：18 处同型）

**取证**：`cocoa::foundation::NSString::init_str` 返回 +1 retained 对象；全仓只有 2 处 `release`
（`macos/canvas.rs:230`、`macos_objc2/native.rs:74`），都不对应这 18 处调用。每次 a11y 通知、
剪贴板读写都泄漏一个 `NSString`。

**修法**：在 `accessibility/macos.rs` 引入私有 helper `autoreleased_nsstring()`，内部 `autorelease()`，
并把本文件的 2 处调用点（`post_notification`、`post_ns_accessibility_notification`）路由过去。
（同一冰山在 `clipboard_stubs.rs`/`macos/platform_impl.rs` 的其余调用点属各自模块，登记于 §5。）

**证据**：`cargo check --lib --features desktop,a11y` → `Finished`（含 `NSAutoreleasePool` trait 导入）。

### 2.3 音频：`AudioBuffer.channels` 可致除零 panic（#3）

**取证**：`samples.rs:16` 字段 `pub`；`new()` 里 `.max(1)` 钳制，但结构体字面量/反序列化可给 0。
`frames()`（`:38`）`len / 0` 直接 panic，`duration_seconds`/`channel`/`to_mono` 同样炸。

**修法**：字段改私有 + `pub fn channels() -> u8` 访问器（恒 `>= 1`），更新 6 处内部与外部读点
（`encoder.rs`、`resample.rs`、`decoder.rs`、`ffmpeg_encoder.rs`、`samples.rs`）。新增回归测试
`zero_channels_are_clamped_and_never_divide_by_zero`。

**证据**：
```
cargo check --lib --features desktop,audio  →  Finished (15.87s)
```

### 2.4 视频：`FrameBufferDecoder.frame_counter` 只写不读（#27）

### 2.8 JSON：已发布事件路由绕过了 `unroutable_reason`（#35，本轮最重）

**取证**：`json_event_binding`（`event_route.rs:275`）只看 `has_payload`，`marker()`（`:100`）便把
**任何 payload-free 名称**归为 `Clicked`。于是：
- `canvas` 发布 `double_clicked`（payload `None`）→ `events:{"double_clicked":"h"}` 绑到**单击**信号；
- `dialog`/`window`/`popup_window`/`navigation_drawer` 发布 `closed`（payload `None`）→ `events:{"closed":"h"}`
  同样绑到**点击**回调，并告诉 handler “一个点击发生了”。

这正是本模块自身文档（`:171-177`）声称已修复的缺陷（“handler 在错误事件上运行，却被告知正确的事件发生了”），
却从另一条路由重新引入。而*同一语义*经 marker 路由（`on_close`/`on_double_click`）反而被**正确拒绝**。

**修法**：新增 `JsonTriggerMarker::for_published_name(name, has_payload)`，从**名称的语义类别**推导意图
（`closed`→`Closed`、`double_clicked`→`DoubleClicked`、`*selection*`→`SelectionChanged`、
有 payload→`ValueChanged`、否则 `Clicked`，双单击判定**先于**单击以免被吞掉）；
`Published` 变体携带此 `marker`；`uses_value_callback` 改为从 `marker` 而非 `has_payload` 推导；
不可路由的名字因此落入既有的 `unroutable_reason()` 守卫被**如实拒绝**（警告且 `record_unwired_binding`）。
`loader.rs::is_loader_owned_key` 顺带修正为**真正派生** `is_marker_key`（#34）。

**门禁**：`tools/check_json_event_route.py` 检查 [3]/[6] 原本铉住旧（错误）实现（要求 loader 出现字面量、
要求 `Published { has_payload, .. } => has_payload`），已改写为铉住**正确契约**（派生 + marker 驱动），
并对“字面量回来”反向告警。

**证据**：
```
python3 tools/check_json_event_route.py           →  ✅ exit=0
cargo test --lib event_route                      →  10 passed; 0 failed
cargo test --test json_event_route_test           →   9 passed; 0 failed
```
新增单测：`a_published_name_carries_its_own_intent`、`the_double_click_check_precedes_the_click_check`、
`a_published_selection_event_is_a_selection_change`；集成测试
`the_callback_choice_follows_the_declared_intent` 遍历全表 333 对，断言「marker 与回调一致」
且「不可路由者必须被拒绝」。

### 2.9 动作：`bind_shortcut_type` 与字符串 API 用不同归一化（#16）

**取证**：`bind_shortcut`/`trigger_shortcut` 走 `normalize_shortcut`（拆 `+`、trim、去空、小写、重拼），
而 `bind_shortcut_type`（`manager.rs:98`）用 `shortcut.to_string().to_lowercase()`。
`Shortcut::to_string` 把 `Modifiers::PRIMARY` 渲染为字面 `"Primary"`，且 `Shortcut::from_string`
把 `ctrl`/`cmd`/`command`/`cmdorctrl` **均**映射为 `PRIMARY`——于是同一个和弦在 map 里有两个拼写，
类型绑定的和弦永远无法用它的字符串拼写触发。

**修法（根因）**：`normalize_shortcut` 增加**别名折叠**（`cmd`/`command`/`cmdorctrl`/`ctrl`/`control` → `primary`），
使 `"Ctrl+S"`、`"Primary+S"`、`"Cmd+S"` 全归一为同一键；`bind_shortcut_type` 改走 `normalize_shortcut`。

**证据**：
```
test action::tests::a_type_bound_shortcut_is_reachable_by_its_string_spelling ... ok
action: 33 passed; 0 failed
```

### 2.10 主题：`apply_token` 的 `fonts` 形参死参（#17）

**取证**：`fonts` 贯穿两层，两个调用点均传 `Some(&theme.fonts)`，但唯一使用处是
`else if let Some(fonts) = fonts { let _ = fonts; }`（`manager.rs:644`）——no-op，且注释谎称
「读取 `fonts` 是让 token 集可达的关键」。

**修法**：删除形参与整个分支（token 的字体由 `token.font` 写、role 基础字体由 `role_base_style` 给），
更新两处调用点。

**证据**：`cargo check --lib --features desktop` → `Finished`。

### 2.11 撤销：`undo()` 失败时丢失命令（#18）

**取证**：`undo()` 先 `pop`，仅在 `command.undo()` 成功后 `push` 到 redo 栈。失败时命令**不在任一栈**，
历史损坏：下次 `undo()` 跳过它，`redo()` 永远拿不回来。

**修法**：失败时把命令**放回** undo 栈再返回错误，历史保持原样。

**证据**：
```
test undo::stack::tests::a_failed_undo_keeps_the_command_on_the_stack ... ok
undo: 17 passed; 0 failed
```
新增测试用一个 `applied` 短于待移除长度的 `TextCommand` 构造出真实的 `undo()` 失败。

### 2.12 样式：`WidgetStyle::background_gradient` 无绘制路径（#15）

**取证**：字段可设、`merge_theme`/`inherit_from`/`merge` 均会搬运、CSS `background-gradient` 可解析，
但**全仓无任何绘制路径读取**它（`DrawGradient` 命令存在且两后端都已实现，只是从未从 style 喂入）。
`render/surface.rs:20` 的文档还把它列为「已修复」的过去式缺陷（陈旧注释 #31）。

**证据**：

### 2.13 JSON：rect 原点 `as i32` 无守卫截断（#20）

**取证**：`json/properties.rs:194` 的 `width`/`height` 用 `u32::try_from(..).ok()?` 守卫（上一行注释还写着
“负数 extent 应拒绝而非转换”），但 **x/y 直接用 `as i32`**：`4294967296` 静默变 `0`，`2147483648` 变 `-2147483648`。
一个越界坐标加载为**错误的屏幕位置**且无报错，与同一函数的 extent 契约矛盾。

**修法**：x/y 改用 `i32::try_from(..).ok()?`。

### 2.14 GPU：纹理图集未检查加法溢出（#21）

### 2.15 GPU：`create_gpu_buffer_pool_config` 的 `_buffer_size` 被丢弃（#22）

**取证**：按 profile 计算 `_buffer_size` 后**丢弃**；`PoolConfig` 根本没有字节尺寸字段（同文件
`create_fallback_pool` 计算**同样**的值并真用）。

**修法**：删除无意义计算并写明原因（`PoolConfig` 只携槽位数，字节尺寸属于它构建的池）。

### 2.16 性能：`DirtyRegion.layer` 写而不读（#23）

**取证**：doc 声称 `priority` 与 `layer` 都被 `optimize` 使用，但 `optimize` 只按 `priority` 排序，
`with_layer`/`add_with_layer` 写的 `layer` 无人消费。

**修法**：`optimize` 改为按（层降序，优先级降序）排序，使 doc 成真；新增 2 条单测。

**证据**：`performance::region::tests` → `2 passed`。

### 2.17 设计器：`factory` 死参 + `let _ = factory/depth`（#24）

**取证**：`emit_node`/`collect_stripped_nodes` 收 `&WidgetFactory` 却从不解引用，用 `let _ = factory;` 静音；
而 `availability()` 每次**自建**一个 `WidgetFactory::new_with_defaults()`（每节点重建注册表）。

**修法**：新增 `availability_with(factory, name, target)`，`emit_*`/`collect_*` 传入已构建的 factory，
使参数变为**活参**且不再每节点重建；删除 `let _ = factory;`/`let _ = depth;`。

**证据**：`designer::generator` → `16 passed`（含既有 `availability_distinguishes_unknown_from_unavailable`）。

### 2.18 设计器：`quote()` 只转义 5 个字符（#30）

**取证**：`quote()` 仅处理 `" \\ \n \r \t`，文档字符串里的控制字符（如 `\u{7}`）会被原样写入生成源码，
产生非法字面量（编译失败）。

**修法**：其余 C0 及 DEL 改为输出 `\u{..}`（与 `designer_manifest.rs` 一致）。新增测试
`quoting_escapes_the_whole_control_range`。

### 2.19 图像：EXIF 解析后无人用；`orientation` 未应用（#26）

**取证**：`exif::extract_exif` 是公共 API **却无处调用**；`DecodedImage::new` 永远写 `ExifData::default()`；
`orientation` 被解析但从不应用⇒竖拍照片（常见 tag 6）解码后是躺倒的。

**修法**：新增 `transform::apply_exif_orientation(data, w, h, orientation)`（用既有 `rotate`/
`flip_horizontal` 映射 8 个 EXIF 值，未知值原样返回）；`decode_jpeg` 在返回前调用 `extract_exif` 并应用
orientation。新增测试 `exif_orientation_is_applied`（2×1 双像素、断言各 tag 后的实际像素与尺寸）。

**证据**：`image::transform::tests::exif_orientation_is_applied ... ok`。

### 2.21 平台：embedded 能力契约回退硬编码 `true`（#28）

**取证**：`platform/contract.rs:47` 在 backend 未发布 embedded 契约时返回三个 `true`——

### 2.22 平台：Windows IME 桥是纯 log 状态机，`is_active` 谎报（#9/#10）

**取证**：`is_active()` 只返回 `active`（focus_in 置 true），而 TSF **从未被调用**；`tsf_available`/`tsf_manager`/
`cursor_rect` 只写不读（均带 `#[allow(dead_code)]`）。这直接违反规则 #26（IME 必须是真实 OS 调用，
不得 log 占位）与 #53（能力缺失只能经运行时方法诚实表达）。

**修法（诚实能力缺失，而非假装）**：`is_active()` 改为 `tsf_available && focused_widget.is_some()`——
只有真实 TSF 连接存在时才算活跃（非 Windows / 无绑定时诚实返回 `false`）；移除冗余的 `active` 字段；
新增 `has_tsf_manager()` 使 RAII 保活句柄可观测（而非悬空字段）；`set_cursor_rect` 去掉 log 占位。
合成/标记文本的状态机部分保留（它是真实且目标无关的）。

**证据**：`ime_windows` → `15 passed`（含重写后的 `test_focus_in_out`/`test_is_active_after_events`，
断言 `is_active == tsf_available`）。

### 2.23 平台：Linux/WASM 剪贴板返回假成功（#11）

**取证**：`LinuxClipboard::set_contents`/`WasmClipboard::set_contents` 只写进程内 `Mutex` 却返回 `true`，
声称系统剪贴板已更新；且这两个类型**不被任何 `Platform::clipboard_backend()` 返回**（Linux/WASM 平台返回默认 `None`）。

**修法**：仍存进程内值（同进程 `get_contents` 可用），但 `set_contents` 返回 **`false`**（诚实：未触系统剪贴板），
重写模块文档说明它是 session-local store。

**证据**：`cargo check --lib --features desktop` 零警告。

### 2.24 PDF：盐/IV 用时间种子 LCG，非 CSPRNG（#6）

**取证**：`generate_salt()` 用 `SystemTime::now().as_nanos()` 作种子跑 LCG。盐与 CBC IV 均可从写入
时钟预测，完全抵消盐/IV 的作用。

**修法**：改用 `getrandom`（OS 熵源：`getrandom(2)`/`BCryptGenRandom`/`SecRandomCopyBytes`/
`crypto.getRandomValues`），失败时返回 `Option::None` 并**拒绝**回退到可预测值。
Cargo：新增可选依赖 `getrandom 0.3` 绑定 `pdf-encryption`；wasm32 需要在目标段启用 `wasm_js`
（**不能**像旧代码那样重命名成第二个依赖——cargo 拒绝同包两名，已实测报错并改用目标段重声明）。

**证据**：`cargo tree --target wasm32 ... -i getrandom@0.3.4` 仅在 wasm32 显示 `wasm_js`；host 无。

### 2.25 PDF：`encrypt_pdf` 不写 salt⇒产物不可解密（#7）

**取证**：`encrypt_pdf` 用 salt 派生 key，却**从不写出 salt**；且 `/O`/`/U` 用**全新**盐计算，与内容密钥
无关——即字典描述的根本不是它前面那段密文。返回类型声称给了一个加密 PDF，实际无人能解密。

**修法**：salt 写入 `PdfEncryption`（`user_salt`/`owner_salt` 字段），`build_encryption_dictionary` 改用
存储的盐（重建两次逐字相同）；`encrypt_pdf` 改为 `Result<Vec<u8>, String>` 并在输出里写出 salt + IV + 密文。
新增测试 `encrypt_pdf_writes_the_salt_so_the_output_is_decryptable` 与 `the_dictionary_is_stable_across_rebuilds`。

### 2.26 PDF：`AES256` 变体永不产生（#8）

**取证**：`AES256` 只在声明与 `match` 臂出现；`PdfEncryption::new` 硬编码 `AES128`，
`derive_encryption_key` 恒返 16 字节，`aes128_cbc_encrypt` 只支持 AES-128——若真到达会输出 key 长度不匹配的字典。

**修法**：删除 `AES256` 变体（并写明为何——不可达的变体是承诺而非功能，待真正 AES-256 路径再加）。

**证据**：
```
pdf::security  →  12 passed; 0 failed
```

### 2.29 事件/holographic：文档声称“平台层转发”，实际无后端产生（#14）

### 2.30 控件：`key_sequence_edit` 的恒等表达式（#32）

**取证**：`(((k - 48) as u8 + b'0') as char)` 对 `48..=57` 恒等于 `k as char`，与上一行字母分支同义却看起来在做转换。

**修法**：改为 `(k as u8 as char)`，与字母分支一致，并注明这是去伪存真。

### 2.31 渲染引擎（embedded）：task `id`/`label` 写而不读（#19）

**取证**：`EmbeddedTask` 存 `id`/`label`，`run()` 里 `let _ =` 丢弃，`submit_embedded_task` 返回的 id 无任何消费点。

**证据**：`--features embedded` → `7 passed`。

### 2.32 颜色插值 4 份重复——复核后**不予合并**（#33，重要）

**取证**：`gradient.rs`/`animation.rs`（两处）/`svg/backend.rs` 各有插值副本，且 `t` 钳制行为不一。
看似可统一到 `Color::blend`。

**实际结论**：`Color::blend` 走 `from_f32`，**四舍五入**；而四处渲染副本用 `as u8` **截断**。
实测合并后 `test_gradient_interpolation` 从 `127` 变为 `128`——即**改变了渲染像素**。按本仓“无渐变时逐像素不变”的原则，
这是不可接受的。已在四处分别写明“为何**不**路由到 `Color::blend`（会四舍五入改变像素）”，避免后人重蹈。

> 这是原则 #51 的一个反向实例：名字相似（都是“颜色插值”）但**实际语义不同**（舍入策略），合并会引入缺陷。
