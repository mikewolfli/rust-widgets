## 1. 第 1 项：三个门禁

### 1.1 `check_locking.sh` — `widget/runtime/frame.rs`

- 根因：`resize_trace_enabled()` 用 `static ENABLED: OnceLock<bool>` 记忆一次 `std::env::var` 探测。门禁的判据是「widget 层不得出现锁」，`OnceLock` 的初始化就是一次内部同步。
- 修复：改为 `thread_local! { static ENABLED: Cell<Option<bool>> }`，仍是**每线程一次**探测，但无锁、无进程级同步。文档写明「每帧由 app resize 路径调用，widget 层必须保持无锁」。
- 证据：`bash tools/check_locking.sh` → `Locking audit passed.`

### 1.2 `check_enabled_is_honoured.sh` — `widget/companions/tests.rs`

- 根因：测试夹具 `WheelProbe::handle_event` 未先判 `is_enabled()`，被门禁判为「输入处理不尊重 enabled」。
- 修复：夹具首行 `if !self.base.is_enabled() { return; }`（与生产控件的契约一致，不是放行）。
- 证据：`234` 个实现被识别为「guarded by is_enabled()」，`45` 个 allowlist；`cargo test --lib companions` 143 passed。

### 1.3 `check_control_rendering.sh` — 三类问题

**(a) `progress_circle` 真缺陷（真修复）**

- 症状：`census` 判其「主题盲」。根因是轨道（groove）与弧用同一个 `Accent` 角色 → 数值在自己轨道上不可见；且 `progress_color` 在构造期捕获，切主题后不重解析。
- 修复（`src/widget/display_widgets/progress_circle.rs`）：
  - 新增 `progress_color_is_explicit` / `track_color_is_explicit` 两个显式标记；
  - 新增 `resolved_track_color()`：显式 → 调用方自绘（非 `theme_derived`）背景 → `palette_shared().surface_container` → 构造期字面量；
  - 新增 `resolved_progress_color()`：显式 → `resolved_theme_style_shared("progress_bar").background_color` → 字面量，并**每帧重解析**；
  - 轨道/弧/中心文字全部走解析值；两个 setter 标记 `*_is_explicit`。
  - 新用例 `the_groove_and_the_arc_follow_the_appearance`（light≠dark、groove≠arc、显式色跨切换保留）。
- `src/widget/sample_fill.rs`：删除 `set_track_color(Color::rgb(224,224,224))`（该固定灰正是主题盲的来源），注释说明为何不再覆盖。

**(b) `image_view` / `masonry_layout` 计入「文档数据类」豁免**

- 判定依据与既有 `carousel` 同族：它们渲染的是**调用方提供的数据像素/卡片内容**，不是主题装饰。
- `tools/control_color_exemptions.txt` 增两行（4 字段格式）并写清理由；**配套强制**补测：
  - `image_view::tests::the_placeholder_follows_the_appearance`（空图，light/dark SVG 不同）；
  - `masonry_layout::tests::the_panel_chrome_follows_the_appearance_beneath_data_coloured_cards`（无卡片，light/dark SVG 不同）。
  - 豁免因此不能掩盖回归。

**(c) 门禁脚本自身缺陷**

- 症状：脚本在 [1/4] 之后静默退出，只打印 3 步。根因：`cargo run --example control_rendering_census --no-default-features --features desktop` 因该 example 的 `required-features = ["desktop","code-editor","markdown-editor","builtin-languages"]` 失败，命令替换失败 + `set -e` 终止。
- 修复：引入 `CENSUS_FEATURES="desktop,code-editor,markdown-editor,builtin-languages"`，两处调用统一使用。
- `tools/control_rendering_baseline.txt` 用正确 feature 集重生成（注：该文件在本轮之前已陈旧，与 HEAD 直接跑差异 166 行属既有漂移，非本轮回归；`progress_circle` 行现为 `yes`，`image_view`/`masonry_layout` 显示 `NO` 且已豁免）。
- 证据：`checked=242 skipped=0 failed=0`，脚本 `GATE_EXIT=0`；census 测试 8/8。

## 2. 第 3 项：`full` / `tablet` / `mobile` 的 profile 测试

### 2.1 编辑器 feature 门控（用户报告项）

- 根因：这些 profile 不启用 `code-editor` / `markdown-editor`，而若干用例无条件断言编辑器控件存在。
- 修复：把「无条件期望」改成「与注册表同一 `cfg!` 门控」，并**保留**「若本 build 声称注册却查不到即失败」的反向断言（防重命名被跳过掩盖）：
  - `widget/capability/tests.rs`：新增 `compiled_here(name)`；`default_factory_registers_core_capabilities`、`factory_creates_registered_widgets_by_alias`、三个表驱动循环、markdown 写块全部按 feature 判定。
  - `widget/capability/properties_tests.rs`、`widget/sample_fill/tests.rs`、`bindings/binding_impl/tests.rs`：同族处理。
  - `tests/capability_event_surface_test.rs`：`EMITTED` 表里的 `("code_editor","fold_changed")` 按 `cfg!(feature = "code-editor")` 跳过，并断言该 build 里它确未注册。

### 2.2 `sample_fill` 的下转测试

- 症状：`every_filled_name_downcasts_to_the_type_the_registry_builds` 报 `markdown_outline_panel is claimed as fillable but the factory cannot build it`。
- 修复：跳过条件由「硬编码三名字」改为**从注册表自身门控推导**（`markdown_outline_panel` ↔ `markdown-editor`；`find_bar` ↔ `code-editor | markdown-editor`），并断言「门控关掉时它确实不在注册表」。这样「本 build 启用了该 feature 但控件缺失」仍会失败。

### 2.3 `platform::contract_tests` / `teardown_tests` / `app::handle::tests`

- 根因（**不是并发竞态**，先按单线程复现确认）：全局 `PLATFORM` 是 `OnceLock`，而 `--features full` 在非 OpenHarmony 宿主上解析为 `harmony-state-backend`；它的宿主模型是**一个窗口**（`supports_multiple_windows() == false`，第二个 `create_window` 按 BLUE28 B28.43 返回 `0`）。任一用例留下窗口，后续用例就会得到 `0` 并报「这个宿主不能创建窗口」——对**行为正确**的后端给出的假结论。
- 修复：新增 `platform::runtime::fresh_native_platform()`（`#[cfg(all(test, not(alloc_frugal)))]`），让这些用例各自拥有**同一后端类型的新实例**（空窗口表）。这正是被测对象——「这个宿主解析到哪个后端、它能做什么」——而 singleton 只是共享容器。
  - 断言强度不变：`assert_ne!(window, 0, "every host must be able to create a window")` 原样保留。
  - 真正需要多窗口的两条用例改为**查询能力**：`destroy_widget_keeps_widget_set_stable_across_churn` 的批次 = `supports_multiple_windows() ? 40 : 1`；`destroy_widget_does_not_disturb_siblings` 在单窗口宿主上改为断言「第二个活窗口被拒绝（B28.43）→ 销毁后槽位可再用且 id 不复用」，即同一命题在该模型下的可检验形式。
  - `app/handle/tests.rs` 三处创建窗口的用例同样改用私有实例。

### 2.4 `platform::tests` 的跨线程退出用例

- 根因：`a_request_from_another_thread_ends_a_running_loop` 的前提是「进程默认后端在非 loop 线程上 `quit()` 返回 `false`」。`harmony`（以及 ohos 目标）的 state 后端**从任意线程**都能停自己的 loop，因此返回 `true`，不记录请求 → 被暂存的 `LoopingPlatform` 永不停止。
- 后果不止一条用例：那个永不退出的 loop 线程在整个测试二进制生命周期里持续 `drive_frame`，把**进程级 trigger 队列**里的注入事件偷走，导致 `widget::runtime::tests::drive_frame_drains_input_before_advancing` 在 `full` 下失败（单跑通过）。
- 修复：把 `feature = "harmony"` / `target_env = "ohos"` 加入该组用例的门控（8 处 `#[cfg]`），并在文档里写明「state 后端在中途返回 `true`，所以暂存式编排不成立」及本次实测后果。
- 证据：该用例在 `full` 下不再编译；`drive_frame_drains_input_before_advancing` 全量跑通过。

### 2.5 `platform::wasm` 的 surface 用例

- 根因：BLUE15 Phase B-1 之后，**任何**后端对 `create_button` 都返回 `0`（控件由库自绘），该用例仍用 `create_button` 造「后端认识的子控件」再去 `invalidate_surface`。
- 修复：删掉该段落，保留窗口 id 可重绘的断言（`invalidate_surface` 的文档本就是「库重绘**窗口**以显露其帧内的子控件」），并写清为什么不再有子 id。

### 2.6 `meta`：`full` 是 CI 矩阵项

复核 `.github/workflows/ci.yml`：`profile: [full, embedded, mini]` 且执行 `cargo test --no-default-features --features "$profile" -q`；`test-profiles.yml` 执行 `tablet`/`mobile`。第 9 章旧记录里「CI 矩阵为 full/embedded/mini，待 CI 复核」本次已按实际 workflow 复核完毕。

## 3. 清扫中发现并修复的存量缺陷（同族 / 冰山法则）

> 以下均为**先 `git stash` 回 HEAD 复跑确认存量**，再修。它们是把 profile 测试从「编译失败」推进到「可运行」后暴露出来的真实缺陷。

### 3.1 两个 profile 的**编译**阻断（CI 的 embedded/mini job）

### 3.2 `mini` 的三处测试编译错误

3. `src/widget/base.rs`：`a_full_mode_frame_repaint_does_not_bump_the_structure_epoch` 使用 `crate::widget::runtime`（`not(alloc_frugal)`）与 `Box`。→ 该用例加 `#[cfg(not(alloc_frugal))]`（命题本身就是「注册表的 structure epoch」）。

## 4. 控件效率：逐帧零分配（用户「全局+局部优化」项）

`tests/key_normalization_allocations.rs::painting_a_steady_state_frame_allocates_nothing` 会对**全部可构造控件**采样 4 帧稳态并断言 0 分配。该用例在 `desktop` 与 `tablet` 上各有一批存量红点（说明 paint 路径存在真实逐帧分配）。

**测试本身的改进**（先做，才能一次看清全貌）：原先「第一个 offender 就断言失败」，每修一个都要整跑一轮才知道下一个。改为**收集全部 offender 后统一断言**，一次运行给出完整清单。这符合仓库「一次运行应告知全部事实」的取向。

修复的 5 处逐帧分配（模式统一：把缓冲**存在控件上**，`clear()` 保留容量）：

| 控件 | 位置 | 根因 | 修复 |
|---|---|---|---|
| `date_edit` / `date_time_edit` / `time_edit` | `measure_pattern_zones` | 每次测量新建 `scratch`/`literal` 两个 `String`；而测量**每帧**都跑（它产生的 key 才决定是否需要重建） | 两缓冲移入 `SectionZoneCache`（三个控件共用），`measure_pattern_zones` 改为直接 `&mut cache` 并在内部比较/回写 key+zones |
| `freeform_shape` | `draw_polygon` / `draw_heart` | 每帧 `collect()` 出绝对坐标 `Vec`；心形每帧新建 64 点 `Vec` | 新增 `polygon_scratch: RefCell<Vec<Point>>`，两变体共用一个缓冲（一次绘制只有一个变体在画） |
| `line_number_gutter` | `draw` | 每帧 `String::new()` 写行号 | 增 `label_scratch: RefCell<String>`（`draw` 持有 `&self` 借用，故用 `RefCell`） |
| `line_chart`（`tablet`/`mobile` 回退路径） | `draw_backdrop_without_engine` | 注释写着「one buffer reused across all ten labels」，但缓冲建在调用内 → 每帧仍分配一次 | 增 `label_scratch`，并按 `#[cfg(not(feature = "chart"))]` 门控（只有该 build 编译这条回退路径，否则 dead_code） |
| `mac_toolbar` | `overflow_rect` / 轴标签 | ① `overflow_indices()` 返回自己 `Vec`，`overflow_rect` 只问「是否为空」却 `clone()` 整表；② `elide_to_width` 省略时返回 `Cow::Owned`，每个被省略标签每帧一次分配 | ① 就地读缓存空性（陈旧回退用 `any` 不分配）；② 新增 `text_utils::elide_to_width_into(text, max, measure, &mut out) -> bool`（同一次二分，探测与结果写同一缓冲），`mac_toolbar` 用一个驻留 `label_scratch` |

顺带把 `MacToolbar` 三处重复的「缓存是否仍然有效」判定合并为 `layout_is_current()`（第 4 处重复正是缓存与命中测试漂移的入口）。

证据：`desktop`、`tablet`、`mobile` 下该用例全绿（覆盖全部可构造控件）。

- 修复：只放宽 manifest 的 `StringList` 臂——元素可以是字符串，或**由标量组成的行**；顶层裸数字仍被拒（`StringList` 不等于「任意列表」）。`NumberList`/`ColorList` 的严格性不动。

## 8. 追加：Cascader 过滤态（字段绘制查询串 + 组合串内联锚点）

- 复核结论：**主张的修复已在代码中，但只闭了一半**。字段确实在过滤期间显示查询串（`draw_field` 的 `filtering` 分支），组合串也确实画在查询之后；然而「离开过滤态」的每条路径都只清 `filter`、**不清 `preedit`**，且绘制侧只判 `preedit` 非空、不判 `filtering`。两者合起来会产生一个用户可见的后果：输入法组合中途按 Escape / 关列表 / 关过滤后，**关闭态的字段仍把残留的组合串画在选中值后面**——用户从未确认、也无法删除的幽灵文字。

### 8.1 接线补齐（5 条退出路径 + 绘制侧双保险）

`filter` 被清空的所有位置现在同步清 `preedit`：

| 位置 | 语义 |
|---|---|
| `collapse()` | 关闭列表（Escape / 外部点击 / 任一提交路径都走它） |
| `expand()` | 重新打开：新会话不应复活上一次的组合 |
| `set_filterable(false)` | 过滤功能关闭 |
| `set_options(..)` | 整棵树被替换（查询与组合一并失效） |
| 选中某一行的路径 | 浏览移到新层级，新层级按定义没有查询 |

绘制侧：`if !self.preedit.is_empty()` → `if filtering && !self.preedit.is_empty()`。组合串**属于**过滤态，所以这里既是防御（某条未来路径漏清也不会画到选中值上），也让「字段显示查询串」与「组合串跟在查询后」两条规则在同一个条件上闭合，不可能各自漂移。

锚点：`max_x` 由「字段右边界」收窄到「文本盒右边界」`line_rect.right()`。查询串本身是 `draw_text_fitted_ellipsis` 画的（可能被省略），而锚点用的是**未裁剪**的测量宽度——旧写法于是能把组合串推到省略号之后，甚至推到 chevron 下面。

### 8.2 用例（4 条，均已做变异验证）

| 用例 | 断言 | 变异验证 |
|---|---|---|
| `the_field_paints_the_query_while_filtering` | 查询取 `"Province"`（保留两条行，所以覆盖层不可能变）→ 两帧的差异**全部落在字段带内**（`< 32 * width * 4` 字节） | 把 `display` 改回选中值 → 失败（差异为空） |
| `a_composition_is_drawn_after_the_query_it_belongs_to` | 同一组合串：无查询时首个差异字节 = 字段文本原点；有查询时严格更靠右 | 把锚点改回 `line_rect.x` → 失败 |
| `leaving_the_filtering_mode_drops_the_pending_composition` | 状态（`preedit` 为空）+ 绘制（关闭态与「从未组合过」的控件逐字节相同）+ `set_filterable(false)` 分支 | 去掉任一 `preedit.clear()` → 状态断言失败 |
| `choosing_a_row_drops_the_pending_composition` | 选中分支清组合，且新层级 `filter` 为空 | 同上 |

### 8.3 未变（对应「静止外观与 API 不变」）

- 公开 API 零变化：没有新增/删除/改名任何 `pub` 项。
- 非过滤态外观零变化：`display`/占位符/颜色/字号/锚点的既有分支未动；`filtering` 为假时组合串不可能非空，所以新增的 `filtering &&` 在静止态是恒真的语义等价。
