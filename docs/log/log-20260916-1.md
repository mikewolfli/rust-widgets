## 0. 基线：`desktop` 在 Linux 上「编译都过不去」

计划 §8「完成率回写」记录的基线是三档 profile 全部 `Finished`。在本机重跑第一条命令即失败：

```text
$ cargo check --no-default-features --features desktop
error[E0433]: cannot find `canvas` in `super`
  --> src/platform/linux/platform_impl.rs:97:16
   |
97 |         super::canvas::mount_canvas(self, parent, id, rect)
   |                ^^^^^^ could not find `canvas` in `super`
note: found an item that was configured out
  --> src/platform/linux/mod.rs:24:16
23 | #[cfg(all(target_os = "linux", feature = "gtk-native", widgets_unstripped))]
24 | pub(crate) mod canvas;
（共 4 个 E0433：mount_canvas / resize_canvas / unmount_canvas / repaint_canvas）
```

**根因（取证，非推测）**：`canvas.rs` 的模块门控是

```rust
// src/platform/linux/canvas.rs:22
#![cfg(all(target_os = "linux", feature = "gtk-native", widgets_unstripped))]
```

而调用点只写了 `#[cfg(widgets_unstripped)]`，**少了 `gtk-native`**。二者在
`--features desktop`（不含 `gtk-native`）下分离：模块被编译掉、调用点保留 → 4 个 E0433。

这与第 16 轮的 `from_platform_caps` 残留是**同一个病**（原则 #17「迁移幻觉」）：
一处改了门控、另一处漏改。**且两轮各自只在一个宿主上才看得见**——
Windows 上 `gtk-native` 永远不激活（非 `target_os = "linux"`），Linux 上 `desktop` 默认不带它。

> **为何计划与第 16 轮都没抓到**：计划的取证口径是「三档 profile 构建」，
> 但真正决定这行代码死活的第三个维度是 **OS 后端 feature**（`gtk-native`），
> 而它既不在 `desktop` 的组合里，也不在 CI 的 profile 矩阵里。缺的是一条
> 「在 Linux 上带着 GTK 后端真的编译一遍」的判据。

### 1.2 4 条 gtk-conditional dead code（原则 #10）

| warning | 判据 | 处置 |

### 2.1 根因：`LinuxPlatform` 的剪贴板从未接线（原则 #2 冰山法则）

取证：**其余 7 个后端全部把剪贴板委托给 `state`**，只有 Linux 继承了 trait 默认体。

```text
$ grep -rn "fn set_clipboard_text" src/
src/platform/types.rs:1599          fn set_clipboard_text(&self, _text: &str) -> bool { false }   ← 默认体
src/platform/macos/platform_impl.rs:268   → self.state.set_clipboard_text(text)
src/platform/macos_objc2/…:131            → self.state.…
src/platform/harmony/…:136                → self.state.…
src/platform/wasm/…:164                   → self.state.…
src/platform/wayland/…:439                → self.state.…
src/platform/ios/…:207                    → self.state.…
src/platform/android/…:269                → self.state.…
src/platform/stub.rs:493                  → self.state.…
                                          ← LinuxPlatform：无覆盖，命中默认体
```

而 `BackendState::set_clipboard_text`（`state.rs:849`）**早已实现**完整的进程内镜像，
只是**没有人调用它**。后果是：同一句 `set_clipboard_text` 在 7 个后端可用，
在 Linux 上静默无效——库内部的复制/粘贴（`lineedit` 的 Ctrl+C/Ctrl+V）随之全部失效。

**处置**：按第 16 轮 `widget_accessor_routing_test` 已确立的「单一接入口」口径，
让 Linux 与其余后端一致地委托 `state`；`gtk-native` 下额外投递到 GDK 显示器剪贴板。

```rust
// src/platform/linux/platform_impl.rs
fn set_clipboard_text(&self, text: &str) -> bool {
    #[cfg(all(target_os = "linux", feature = "gtk-native"))]
    {
        // 见 §4：GTK/GDK 只能在主线程使用，故先问 is_initialized_main_thread()
        if gtk::is_initialized_main_thread() {
            if let Some(display) = gtk::gdk::Display::default() {
                if let Some(clipboard) = gtk::Clipboard::default(&display) {
                    clipboard.set_text(text);
                    clipboard.store();
                }
            }
        }
    }
    self.state.set_clipboard_text(text)
}
fn get_clipboard_text(&self) -> String { self.state.clipboard_text() }
```

修复 §1 后，把门控对齐所暴露出的下一个问题做完整验收——`--features "desktop,gtk-native"`：

```text
$ cargo check --no-default-features --features "desktop,gtk-native"
error[E0433]: cannot find module or crate `glib` in this scope   （canvas.rs:66，x8）
error[E0433]: cannot find module or crate `gdk` in this scope    （canvas.rs:72，x5）
error[E0433]: cannot find module or crate `cairo` in this scope  （canvas.rs:219，x3）
error[E0599]: no method named `lock_guard` found for `std::sync::Mutex<_>`  （canvas.rs，x4）
error[E0599]: the method `move_` exists for reference `&gtk::DrawingArea`…
error[E0133]: call to unsafe function `WidgetExtManual::destroy` is unsafe…
```

逐条取证与处置：

| 缺陷 | 根因（取证） | 处置 |
|---|---|---|
| `glib::` / `gdk::` / `cairo::` 未解析 | 三者都不是本 crate 的直接依赖，只有 `gtk` 被声明；`gtk 0.18` 通过 `pub use gdk/gdk_pixbuf/glib/cairo` 再导出。**全仓仅 `canvas.rs` 使用裸名**（`grep -rn "[^:]glib::"` 只命中此文件） | 改为 `use gtk::{cairo, gdk, glib};`，与已声明的依赖对齐 |

| `move_` 方法不适配 `&DrawingArea` | gtk-rs 0.18 中 `FixedExt::move_` 定义在**父容器** `Fixed` 上，不在子控件上 | 取 `area.parent()` 下行转换为 `gtk::Fixed` 后调用 |
| `destroy()` 是 unsafe | gtk-rs 0.18 的 `WidgetExtManual::destroy` 要求「调用方确保在 GTK 主线程」 | 显式 `unsafe {…}` 并写明 SAFETY 依据（本模块所有入口都在主线程，见 §4） |

## 4. `gtk-native` 运行时：一个真实进程崩溃（SIGSEGV）+ 11 例失败

编译通过后跑测试，得到本轮**唯一的崩溃级**问题（也是最初被误判为「跑死」的真凶）：

```text
$ cargo test --no-default-features --features "desktop,gtk-native" --lib -q
test result: FAILED
Caused by:
  process didn't exit successfully: `…rust_widgets-…` (signal: 11, SIGSEGV: invalid memory reference)
```

用 `--test-threads=1` 隔离后，崩溃变为可读的失败：

```text
thread 'platform::contract_tests::id_allocation_stays_consistent_across_churn' panicked at
  gtk-0.18.2/src/rt.rs:122:9:
Attempted to initialize GTK from two different threads.

thread 'widget::input_widgets::lineedit::…_clipboard_copy_paste_cut' panicked at
  gdk-0.18.2/src/auto/display.rs:301:9:
GDK may only be used from the main thread.
```

### 4.1 根因（实测，非推测）

GTK 3 把进程绑定到**唯一一个主线程**：

- `gtk::init()` 每进程只能成功一次，第二个线程再调即 **abort**（`gtk-rs` 主动 panic）；
- `gtk::Window::new` 内部是 `assert_initialized_main_thread!()`（`gtk-0.18.2/src/auto/window.rs:30`），
  非主线程调用即 panic；
- GDK 的 `Display::default()` 同样限定主线程。

而 Rust 测试框架**给每个 `#[test]` 分配各自的 worker 线程**。逐个单跑**全部通过**：

```text
$ cargo test … --lib -- --test-threads=1 platform::teardown_tests::destroy_widget_is_authoritative_and_idempotent
test result: ok. 1 passed; 0 failed; … finished in 0.04s
```

——「单跑绿、并跑崩」证明这是**并发下的主线程约束**，不是单点逻辑错误。

### 4.2 处置：照搬 macOS 的既有先例（原则 #2 / #37）

**关键取证**：macOS 后端面对**完全相同**的约束（AppKit 同样主线程独占），
其解法已存在于仓库中并写有注释：

```rust
// src/platform/macos/platform_impl.rs:173-181
fn create_window(&self, title: &str, …) -> u64 {
    // Off-main (e.g. the C ABI called from a worker thread or unit tests),
    // never construct `NSWindow`: AppKit raises a foreign exception that
    // aborts the process. Register a state-only handle instead so every
    // caller still receives a valid, text/geometry-consistent widget id.
    if !super::types::is_main_thread() { … state-only handle … }
```

Linux 采用**同一条既有模式**（不新造机制，原则 #28/#51）：

| 位置 | 修复 |
|---|---|
| `LinuxPlatform::create_window` | 非 GTK 主线程 → 记 debug 日志并返回 state-only 窗口（仍是有文本/几何的合法 id），不再构造 `gtk::Window` |
| `LinuxPlatform::init` | 用**进程级 mutex 保护「检查 + 初始化」的原子性**；已有其他线程拥有 GTK 时不再调用 `gtk::init()`（`is_initialized()` 先查后调本身是竞态，正是崩溃来源） |
| `LinuxPlatform::set_clipboard_text` | GDK 段先问 `is_initialized_main_thread()`（§2 已述） |
| `canvas.rs::mount_canvas` | 非主线程直接 `return false` + `log::error!`，让 `mount_surface` 走它**已有的** `false` 契约，而不是崩溃 |
| `linux/tests.rs::ensure_gtk` | 同时处理「无显示器」与「GTK 已属于别的线程」两种不可用情形，均回退到诚实的 state-only 断言 |

### 4.3 一处被修正的错误断言（我自己的）

修复过程中我先加了一个 `gtk_test_guard`（进程级互斥，序列化 GTK 测试）。
**实测证明它不必要**：去掉后连跑 3 次仍全绿——真正起作用的是 §4.2 的「非主线程降级」。
按原则 #28（不为「看起来稳妥」保留无用抽象），**已整体删除**该 guard 及其宏。

同时发现 `gtk_native_backend_lifecycle` 的回退分支断言有误：

```rust
// 修复前：assert_eq!(backend.backend_name(), "linux-state-backend");
//   → backend_name() 是**编译期** feature 决定的事实（此处编译了 gtk-native ⇒ "gtk"），
//     与「GTK 是否在本线程初始化成功」是两件事，该断言把两者混为一谈。
// 修复后：断言编译期身份 + 真正可观测的运行时事实（窗口 id 合法、native_handle 为 None）。
```

### 5.1 `android_jni`：测试的**度量方法**错了（不是常量错）

```text
assertion `left == right` failed: NATIVE_METHOD_COUNT must be updated…
  left: 9        right: 7
```

初看像「常量过期」，**取证后相反**：

```text
$ grep -c 'pub extern "system" fn Java_rust_1widgets_RustWidgets_' src/platform/android_jni.rs
7                                   ← 真实导出数
$ grep -c "Java_rust_1widgets_RustWidgets_" src/platform/android_jni.rs
9                                   ← 测试用 matches() 数出来的
```

那多出的 2 个来自**测试自己**的字面量与模块文档。也就是说 `NATIVE_METHOD_COUNT = 7` 是**对的**，
错的是 `source.matches(前缀)` 这种粗暴计数。处置：锚定到声明行。

```rust
const PREFIX: &str = "pub extern \"system\" fn Java_rust_1widgets_RustWidgets_";
let exported = source.matches(PREFIX).count();
```

> 教训与第 16 轮一致：**门禁/测试本身的判据也要被审视**（原则 #64）。
> 若照「常量过期」的直觉去把 7 改成 9，就会在 ABI 上报出一个**假的**方法数，
> 让按 9 编译的宿主在首次调用时链接失败。

### 5.3 `--all-features` 下 3 个 example 编译失败

`--all-features` 会**同时**打开 `desktop`（device profile）与 `mini`（`alloc_frugal`），
于是 `app` 模块与 `get_platform` 被编译掉，而 example 引用了它们：


处置：沿用仓库既有写法（`examples/menu_shortcut_runtime.rs:135` 的
`#[cfg(not(...))] fn main()` 回退桩），把 3 个 example 的 `main` 与其导入门控在
**与其依赖模块相同的条件**上，并补一个如实说明「本构建下不适用」的桩 `main`。

## 6. Wayland：菜单模型「有消费者、无生产者」（原则 #17）

`--all-features` 下 `wayland::tests::menu_system` 失败。取证后是**删除面未收尾**：

```text
$ grep -rn "WaylandHandleKind::MenuBar|Menu\b" src/platform/wayland/
platform_impl.rs:286   matches!(… kind_of(menu_bar) …, Some(MenuBar))   ← 消费
platform_impl.rs:299   matches!(… kind_of(parent_menu) …, Some(Menu))   ← 消费
（无任何 insert_widget(WaylandHandleKind::MenuBar | Menu, …)）           ← 无生产
```

`attach_menu_bar_to_window` 与 `menu_add_item` 都**先校验父节点 kind**，
而 `MenuBar`/`Menu` 两个变体**从未被构造**，因此这两个方法只能恒返回 `false`/`0`——
即「声明了能力、永远走不通」。这与第 16 轮 `windows/accel.rs`「表永不存在的加速键」同型。

**决定性证据**：**已有的测试**（`wayland/tests.rs:233`）**本来就要求它们工作**：


## 10. 两项登记项的**收尾**（本轮第二轮，用户要求「多轮解决掉这 2 个问题」）

§10 原先把这两项登记为「未修复 / 需别人决定」。第二轮把二者都做完了，下面记录做法与证据。

### 10.1 ✅ Gap B 已修复：库创建的窗口现在能承载控件

#### 根因（精确到行）

一个窗口同时存在于**两个互不相识的 id 空间**：

| id 空间 | 产生者 | 谁认识它 |
|---|---|---|
| widget registry id（如 `0x5345_4C46_…`） | `widget::runtime::register`（`runtime.rs:103`） | 库的全部访问器、`is_mounted` |
| platform id（如 `1`） | `Platform::create_window`（各后端 `BackendState`，从 1 递增） | `Platform::mount_surface`（**只能**它，因为只有它能拿到原生 `HWND`/GTK 窗口/`NSWindow`） |

`create_window` 返回前者，却**从未**向平台要后者；而 `mount_widget_of_kind` 对 `Window`
更是直接 `register` 就返回（`custom/mod.rs`）：

```rust
// 修复前
if kind != Window { /* 校验 parent */ }
crate::widget::runtime::register(widget).unwrap_or(0)   // ← Window 到此为止，平台完全不知情
```

于是 `mount_surface(parent=库窗口id, …)` 在平台上查不到该父节点 → 拒绝。
**「库自己的窗口」无法承载「库自己的控件」**，而 `Platform::create_window` 那条路却正常——
这正是它被读成「控件不显示」而不是「id 不通」的原因。

#### 修法（3 处，均为「接线」而非新机制）

1. **`widget/runtime.rs`**：新增 `HOST_WINDOWS` 关联表 + `set_host_window` / `host_window_for`；
   `unregister` 同步清除关联（否则 id 复用会继承**陈旧**的宿主窗口）。
2. **`control_backend/custom/mod.rs`**（唯一创建源，原则 #65）：创建 `Window` 时顺带调
   `Platform::create_window` 并记录关联。后端返回 `0`（state-only / 非主线程）时**不记录**，
   于是「无宿主」仍是诚实答案而非假成功（原则 #12）。
3. **`lib.rs::mount_widget_object`**（唯一挂载实现）：挂载前把父 id 经 `host_window_for` 翻译一次。
   放在这里是因为它**同时**持有 widget registry 与 platform handle，是唯一能完成翻译的位置。

#### 验证（修复前 / 修复后对照，实测）

## 12. 这些缺陷都与操作系统有关吗？（就地澄清，原则 #2）

**不。** 与第 16 轮同构，判据不是「在哪台机器上看到的」，而是「出问题的行有没有 `cfg(target_os)`」。

### 12.1 真正与操作系统绑定（修在 `src/platform/` 内）

| 缺陷 | 绑定证据 |
|---|---|
| §1 `canvas` 门控漂移 | 门控含 `feature = "gtk-native"`，而该 feature 只在 Linux 有意义 |
| §3 `glib`/`gdk`/`cairo` 裸名 | 均为 GTK 系 crate 再导出，仅 Linux 后端使用 |
| §4 GTK 主线程约束（SIGSEGV） | `gtk-rs` 源码级契约（`assert_initialized_main_thread!()`、`rt.rs:122`） |
| §6 Wayland 菜单生产者缺失 | 位于 `src/platform/wayland/`，且 Wayland **协议层无菜单**是该后端的固有事实 |

### 12.2 与操作系统**无关**（全平台同样坏，只是没人跑过）

| 缺陷 | 判据（可复现） |
|---|---|
| §2 剪贴板未接线 | 代码在 `linux/platform_impl.rs`，但**成因是「7 个后端都委托 state、只有它没委托」**；同样的漏接线在任何后端都同样致命。`lineedit` 的复制/粘贴是全平台功能 |
| §5.1 `android_jni` 计数判据 | 测试文件内置的**度量方法**错误，与 JNI/Android 运行时无关 |
| §5.2 `harmony` 触发事件未接线 | 纯 Rust 委托缺失；同型 4 个后端都已接 |
| §5.3 example 在 `--all-features` 下不编译 | `alloc_frugal` 与 device profile 的**组合**问题，与 OS 无关 |
| §7 两个「宿主假设」测试 | 断言把「后端能力」写成常量；**第 16 轮在 Windows 上遇到的是同一类** |
| §8 clippy `bool_assert_comparison` | 工具链版本相关（1.98 报），与平台无关 |

> **操作系统的差异解释了「为何在本轮第一次看见这些」，不解释「为何它们是缺陷」。**
> 真正由 OS 决定的只有 §11.1 那 4 项；缺口主体（§11.2）在第 16 轮的 Windows 上、
> 在本轮的 Linux 上、在任何平台上都一样存在——**根因始终是同一件事：
> 删了旧层、没有接完调用方（原则 #17），加上判据只覆盖了一部分构建组合。**

> 两轮合起来把 BLUE15 的验证面从 **1 个 profile × 1 个 OS** 扩展到
> **3 个 profile × 2 个 OS × 5 个 feature 组合**，也因此抓到了单宿主取证结构性看不见的缺陷：
> 第 16 轮 15 类、本轮 11 类。

## 13. 结论

1. **BLUE15 在 Linux 上「未完成」**，且与第 16 轮在 Windows 上发现的**不是同一批**缺陷。
   本轮抓到的 4 个功能阻断项（`canvas` 门控、`gtk-native` 不可编译、GTK 主线程 SIGSEGV、
   剪贴板未接线）全部在 macOS 取证下**结构性不可见**。

2. **两轮指向同一个根因，但各有各的形态**：
   - 第 16 轮：`from_platform_caps` 残留（删了旧函数、漏改调用点）；

     Wayland 菜单缺生产者、Harmony 触发事件未接。
   **全部是原则 #17「删了旧层/加了新层，没有接完调用方」**，只是漏的位置不同。

3. **本轮产出**：阻断项 1 个、`gtk-native` 路径从「不可编译」修到 4036 全绿、
   一个真实进程崩溃（SIGSEGV）根除、剪贴板断链修复、Wayland 菜单生产者补齐、

## 15. 一句话总结

**本轮把 BLUE15 的验证面从「1 个 profile × 1 个 OS」扩到「3 profile × 2 OS × 6 个 feature 组合」，
并在此基础上升级到 2.0.1。** 抓到的 11 类缺陷全部属于同一根因家族（原则 #17：删了旧层/加了新层、
没接完调用方），其中 4 类是受影响平台上的功能阻断项；两项遗留登记（Gap B、`gtk-native` CI 覆盖）
也已闭环，各有能失败的回归门禁背书。版本升级采用**分类取证**而非全库替换，
历史语义与无关版本串均保持原样。

1. **BLUE15 在 Linux 上「未完成」**，且与第 16 轮在 Windows 上发现的**不是同一批**缺陷。
   本轮抓到的 4 个功能阻断项（`canvas` 门控、`gtk-native` 不可编译、GTK 主线程 SIGSEGV、
   剪贴板未接线）全部在 macOS 取证下**结构性不可见**。

2. **两轮指向同一个根因，但各有各的形态**：
   - 第 16 轮：`from_platform_caps` 残留（删了旧函数、漏改调用点）；
   - 本轮：`canvas` 门控漂移（改了模块门控、漏改调用点）、剪贴板未接线（7 个后端接了、漏 1 个）、
     Wayland 菜单缺生产者、Harmony 触发事件未接。
   **全部是原则 #17「删了旧层/加了新层，没有接完调用方」**，只是漏的位置不同。

3. **本轮产出**：阻断项 1 个、`gtk-native` 路径从「不可编译」修到 4036 全绿、
   一个真实进程崩溃（SIGSEGV）根除、剪贴板断链修复、Wayland 菜单生产者补齐、
   Harmony 事件接线、`--all-features` 从 5 failed 修到 0、
   4 类判据错误修正、2 个 example 在 `--all-features` 下的门控、6 条 warning 清零。

4. **复验结果**：5 个 feature 组合 + `--all-features` **零 warning / 零失败**；
   6 个配置 clippy `-D warnings` 通过；`cargo fmt --check` 通过；`cargo doc -D warnings` 0 错误；
   3 个交叉目标（windows-msvc / wasm32 / android）0 issue；**门禁 15 PASS / 0 FAIL / 1 宿主门控**；
   两个运行时探针 PASS。

5. **原先登记的两项已全部闭环**（§10）：
   - **Gap B 已修**：库创建的窗口现在能承载控件（`App::new_window` → `mount_widget_by_name`
     由 `Err(refused)` 变为 `Ok(…)`），并配了**已验证能失败**的回归门禁；
   - **`gtk-native` 已入 CI**：新增 `linux-gtk` job（含重复运行以压出并发时序缺陷），
     并注入历史回归确认门禁确实会红。

6. **剩余不可验证项都是环境限制，不是代码问题**（§11）：iOS 交叉编译缺 cross-CC/target，
   `check_apple_native.sh` 与 `full,mobile-api` 两例需 Darwin 宿主。**均已显式登记，不冒充完成。**
