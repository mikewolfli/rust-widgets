### 5.2 全量里的 6 个 FAIL：逐个复跑与根因

全量运行期间观察到**另一个 `run_all_gates.sh` 进程**（同一仓库、同一 target），两个全量会争用 cargo 锁，并互相改写门禁临时文件（`tools/view_platform_gate_probe.rs` 由 `check_view_platform_gate.sh` 生成/还原）。6 个失败在无并发的干净环境逐个复跑，全部通过：

| `check_mode_consistency.sh` | FAIL 27s | **PASS**（7/7 树一致 + 反向注入变红） | 并发/瞬时 |

| `check_ios_cross.sh` | FAIL 19s | **PASS**（aarch64-apple-ios + -sim 均 Finished） | 并发/瞬时 |
| `check_harmony_cross.sh` | FAIL 224s | **PASS**（6/6，含 loongarch64 Tier 3 说明） | 并发/瞬时 |
| `check_profile_builds.sh` | FAIL 96s | **PASS**（desktop/tablet/mobile/embedded/mini，2942 tests） | 根因见下，已修 |

**`check_profile_builds` 的真实根因（已修复）**：`crate::i18n::init()` 是幂等的——已存在 manager 时直接返回，**不是重置**。多个 i18n 测试却把它当“Reset global state”用，于是某个测试安装的定制 catalogue 泄漏给后续测试；并行跑 mobile profile 时，`calendar.month.1`/`common.button.cancel` 会翻译成 key 本身。

修复：
- `src/i18n/global.rs` 新增 `#[cfg(test)] reset_for_tests()`：把 `GLOBAL_I18N` 置 `None` 并递增 `language_generation`（生产路径 `init()` 的幂等语义不变）；
- `src/i18n/tests.rs` 中 7 处“Reset global state”由 `init()` 改为 `reset_for_tests()`。

复跑证据：`cargo test --lib --no-default-features --features mobile i18n::` → **79 passed / 0 failed**；`bash tools/check_profile_builds.sh` → **2942 passed / 0 failed**，五个 profile 全绿。

## 6. 负优化自查（原则 #18 / R12 教训）

- **所有新缓存都写了完整键**：
  - fitted label = 源文本 + 可用宽度 + 完整 `Font`（族/字号/字重/斜体/字距/词距）+ DPI；
  - 动作行 = 标签内容 hash + 数量 + 完整 `Font` + DPI + band + place；
  - 按钮行 = 标签内容 + 完整 `Font` + DPI + rect；
  - 动作标签 = 模式 + `language_generation`；
  - 共享翻译 = key + `language_generation`；
  - 路径 = 平移 + 顶点内容 + `closed`；
  - `header_menu.items` = sortable + filterable + sort_state；
  - `AboutDialog.identity` = (application_name, version)。
- **缓存有界**：fitted 64、action row 4、button row 4、path 16、label 32、wrap cache 由单卡自有上限；不存在随会话无界增长。
- **没有第二套机制**：`draw_text_fitted_cow` 与新 `*_ellipsis` 共享同一个 `fit_text_parts`；`visible_column_spans` 与 `with_visible_column_spans` 共享同一个 `span_run`；公开 `items()` / `label()` / `identity_lines()` 等仍委托到缓存实现。
- **没有改名**：既有属性/方法/事件/字段名全部保持；仅新增增量入口。
- **没有死代码**：临时探针与改写脚本已删除；`trim_number` 在改 `trim_number_into` 后无调用方，已删除（测试仍覆盖 `label()` 的三位小数/整数/百分比拼写）。

# 11. 第 17 轮：全量门控实跑 + 「一小时跑不完 / 像死机」的根因与修复（2026-11-06 续）

## 11.1 用户问题与结论

用户问：全量门控是否死机、为何从未见过一次成功、为何一小时还跑不完。

**结论：不是死机，也不是单点卡住。** 实测 128 个门控串行跑完，`TIMEOUT=0`、`NOT-RUN=0`，门控耗时合计 **3461 s（57.7 min）**。三个原因叠加才造成「一小时必挂」的观感：

1. **整轮预算与实测成本只差 4%。** `run_all_gates.sh` 默认 `RUN_BUDGET=3600`，实测 3461 s，加上每门控的 digest/mktemp 开销后贴着上限。任何一次稍慢就触发 `NOT-RUN` 尾巴 → 退出码 1。`NOT-RUN` 是「没跑到」，但外部看起来与「跑挂了」无法区分。
2. **缓存键把 runner 自己的预算变量也算进去了。** `lib_cargo_cache.sh` 的 environment digest 覆盖**全部导出变量**，而 runner 文档明确建议用 `RW_GATE_TIMEOUT` / `RW_RUN_TIMEOUT` 覆盖预算来跑冷树。一旦覆盖，所有 `rw_cargo_cached` 步骤 **100% 未命中**，于是每次全量都是冷跑。（实测见 11.2。）
3. **单个门控的宿主误判白烧 4 分钟。** `check_android_runtime.sh` 用 `emulator -list-avds | head -1` 选 AVD，在 x86_64 宿主上选到 arm64 的 `rw_test`；emulator 秒退（`System image must match the host architecture`），但启动等待仍等满 180 s 才放弃 → 该门控 238 s 全部无效。

## 12. 全量图标接线闭合（方案 A：names 全量 / data 全量 / fallback 分层）（2026-11-06 续）

**结论**：§11.3 记录的「图标集扩充未完成」已闭合。`IconName` 从 75 个令牌扩到 **4,323** 个

### 12.2 过程中发现的真缺陷（本轮最重要的发现）

全量 vendor 后重跑「每个令牌画出不同图」的测试时，`battery_vert_020` 与 `battery_vert_005`
渲染出**逐字节相同**的 SVG。诊断（临时探针 + 逐尺寸比对 24/48/96/240/480/960/1920）发现根因不在
测试：**pinned 上游树里有 73 个 SVG 用的是 24 单位、y 向下的旧编码**（66 个根本没有 `viewBox`，
7 个写 `0 96 960 960`），而 `data.rs` 把 `grid` 硬编码成 960。这 73 个图标被按 960 缩放后塌成
x∈[0, 0.6px] 的一条竖线 —— 一个「能编译、能过测试、画出来是空白」的缺陷。

修复（三步，都在生成链上闭合）：
1. 这 73 个（`vendor_material_symbols.LEGACY_GRID`）改从 Material Symbols release tree 取 960 单位版本；
   几何不重编码，`copied verbatim` 的声明保持为真。
2. `gen_icon_data.py` 现在**校验** `viewBox == "0 -960 960 960"`，不符就按文件名报错 —— 这正是
   原来能漏掉的那一步。
3. 同时确认 pinned 树里另有 73 个名字（`RELEASE_ONLY`：`place`/`people`/`help_outline` 等退役写法）
   根本不存在，也取自 release tree。

合计 **146 / 4,323** 个轮廓来自 release tree 而非 pinned commit，`data.rs` 头与 `NOTICE` 都记录了这一点。

### 12.5 仍然存在的已知边界（不是未完成项）

1. **146 个轮廓来自 release tree**（73 个 pinned 缺失 + 73 个 pinned 只有旧 24 单位编码）。
   已显式记录、可审计；若要 100% 贴 pinned，需要在生成器里对那 73 个做坐标重编码 —— 那会让
   「copied verbatim」变成假话，因此不做。

   这是 `mini`/`embedded` 不带 12 MB 常量所换来的代价，已在 `NOTICE`、crate README 与 `fallback.rs` 头部写明。

   `IconSource::Builtin` 的载荷随之变宽。没有持久化格式依赖枚举判别值（文档里存的是 token 字符串），
   `ALL`/`ICON_DATA` 的顺序由测试按名字校验。
