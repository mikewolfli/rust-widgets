## 2. 🔴 头条：上一轮的 `KIND_LIST_VIEW`「修复」是无效修复（原则 #12/#17）

### 4.1 🔴 `svgz` 的编码与解码互不匹配（本轮新发现，且已端到端修复）

这是本轮第二重要的发现，而且它是**测试直接抓到**的：

```rust
// encoder.rs（修复前）
ImageFormat::Svg | ImageFormat::Svgz => encode_svg(image), // Svgz 输出纯 XML

// decoder.rs（修复前，resvg 分支）
let tree = resvg::usvg::Tree::from_data(data, ..) // data 是 gzip 字节！
// 错误消息却写 "the decompressed SVGZ payload" —— 但从未解压
```

三方事实互相矛盾：

- `ImageFormat::Svgz.mime_type() == "image/svg+xml-compressed"`、`extension() == "svgz"`
 —— **声明**是 gzip 压缩的 SVG；
- `detect_format` 用 `1F 8B 08` 前缀把输入路由到 `decode_svgz` —— **假定**输入是 gzip；
- 但编码器**输出**未压缩 XML，解码器**不解压**。

后果：
1. 本库产生的 `.svgz` 文件，任何外部工具都打不开；
2. 本库自己的 `decode(encode(img, Svgz))` 往返失败；
3. `encoder.rs` 里那条测试 `assert!(s.starts_with("<svg"))` **把 bug 写成了契约**，
 所以它一直“通过”。

修复（三处齐动，缺一不可）：

1. `encoder.rs` 新增 `encode_svgz` + `gzip_compress`：`miniz_oxide` **只提供 raw DEFLATE 与 zlib 容器，没有 gzip 帧**，
 因此手写 gzip 外壳（`1F 8B 08 00` + 零 mtime + XFL/OS + DEFLATE + CRC32 + ISIZE）。
 CRC 复用 PNG 编码器已有的 `crc32`（PNG 与 gzip 同为 `0xEDB88320` 反射多项式）。
2. `decoder.rs` 新增 `gzip_body` + `gunzip_bounded`：剥掉 10 字节头与 8 字节尾，
 再交给 `decompress_to_vec_with_limit` 解 raw DEFLATE。**两个分支共用**这一个helper。
3. 测试改为断言真实契约（gzip magic、trailer CRC/ISIZE、往返还原）。

验证：

```text

test image::decoder::tests::svgz_roundtrip_through_encode_and_decode ... ok
test image::decoder::tests::svgz_payload_over_the_document_cap_is_refused ... ok
```

### 5.1 回调注册表：panic 即永久失注 + 嵌套注册 panic

```rust
// 修复前
let cb = CLICK_CALLBACKS.with(|map| map.borrow_mut().remove(&widget_id));
if let Some(cb) = cb {
 (cb.borrow_mut())(); // ← 用户回调 panic 则下一行被跳过

}
```

两个缺陷都是构建看不出来的：

1. **回调 panic 导致注册永久丢失**。`remove` 是为了让重入的 `remove_callbacks`

**反向注入验证**（证明新测试真能拦住）：把 click 路径改回「调用后再 insert」后，

## 7. 缺陷类 F：`svgz` 编解码互不匹配（本轮头条之一，已端到端修复）

见 §4.1。三类事实互相矛盾：格式声明（`image/svg+xml-compressed`、扩展名 `svgz`）、
`detect_format` 的 gzip 前缀路由、以及编码器实际输出未压缩 XML、解码器不解压。
后果是本库产生的 `.svgz` 外部工具打不开，自己的往返也失败，
而 `encoder.rs` 的测试 `assert!(s.starts_with("<svg"))` **把 bug 写成了契约**。

## 9. 第 4 轮：schema 真实性与命令可兑现性（本轮新发现）

第 3 轮把 `set_*` 命令接到属性路由后，新增门控测试
`tests/capability_schema_truthfulness_test.rs` 又挖出**第二类**同类缺陷：
**schema 自己的可写标记与控件的 `set()` 相反**。

### 9.1 缺陷：`writable: true` 但 `set()` 拒绝

用「按类型/按名称构造合法值 → 真调 `set()`」的探针扫全部 187 个 capability，
得到 20 条声明可写但被拒绝的条目。逐条看源码后分类：

| 类别 | 条目 | 真相 | 处置 |
|---|---|---|---|
| **schema 过度声称**（真只读） | `splitter::pane_count`、`wizard_dialog::current_step`、`popover::text`、`order_book::show_spread`、`quote_board::row_height` | `set()` 确实返回 `ReadOnlyProperty`，而 schema 写 `true` | schema 改 `(true, false)`，并**删除**指向它们的命令（`set_pane_count`、`set_current_step`）——命令的 `OutOfRange` 会把调用方送去一个 schema 拒绝的写 |
| **声明类型与 `set()` 不符** | `depth_chart::bid_color` / `ask_color` | schema 写 `PropertyValueKind::String`，而 `set()` 解构 `CapabilityValue::Color`，任何写入都 `TypeMismatch` —— **属性通过 ABI 完全不可写** | schema 改为 `Color`（与 `stroke_color`、`icon::color` 一致） |
| **探针伪阳性**（值本身不合法） | `*/series`（需数字串）、`divider/orientation`（需 `horizontal`/`vertical`）、`list_view::focused_row` / `tree_view::focused_node` / `quote_board::selected_index`（索引超出空控件的行数）、`data_grid::sort_specs`/`filters`（需元素类型）、`mention::trigger`、`otp_input::separator`、`navigation_stack::current_page` | 控件**正确**拒绝，不是缺陷 | 不动 |

最后一行是故意的记录：探针无法区分「schema 说谎」与「这个值此刻不合法」，
所以正式测试断言的是**可判定的结构事实**，不是写入尝试。

### 9.2 新增门控（3 条，均带反向注入验证）

`tests/capability_schema_truthfulness_test.rs`：

1. `every_set_command_is_recognised_by_its_control` —— 每个已公布的 `set_X` 做一次
 **无载荷调用**，只接受 `Ok(())` 或 `OutOfRange`。
 `ReadOnlyProperty` / `TypeMismatch` / `UnsupportedOnWidget` 对一个无载荷调用都是
 **不可能的答案**（那两个错是描述「值被拒绝」，而根本没有值），所以它们暴露了断链。
 这条同时让两种合法形态通过：属性路由（`set_text`）与控件自己的 `command()` 覆盖
 （`set_range` 同时写两个属性、`set_items` 拿集合）。
2. `every_published_command_is_recognised_by_its_control` —— 无载荷命令（`clear`、`toggle` …）
 不得回答 `UnknownCommand`。
3. `every_capability_publishing_a_surface_is_constructible` —— 公布了命令/事件的
 capability 必须真能构造出来，否则承诺无法被触达。

**反向注入**（证明测试有效）：把 `set_pane_count` 重新加回 splitter 的 `commands:` 后：

```text
$ cargo test --no-default-features --features desktop --test capability_schema_truthfulness_test
line publishes `set_pane_count` but a payload-free call answers UnsupportedOnWidget
test result: FAILED. 2 passed; 1 failed
```

这同时证明了两件事：测试能拦住该缺陷，以及**上一轮的修复真的起作用**
（修复前 `set_pane_count` 会因前缀规则被放行，不会有任何失败）。
