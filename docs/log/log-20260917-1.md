## 1. 三项增强的取证（改动前）

### 1.1 JSON GUI：**26/155**，且 `infer_kind` 已能命名 `create_widget` 造不出来的控件

| 指标 | 实测 | 取证 |
|---|---:|---|

| `WidgetKind` 变体总数 | **167** | `src/widget/kind.rs`（`tools/check_widget_kind_count.sh` 亦印证） |
| 工厂注册的构造器 | **154** 次注册 / 143 个不同 kind | `src/widget/capability/registration.rs:15-204` |

最尖锐的一类：`infer_kind` 能命名、`create_widget` 却拒绝构建的 **9 个常编译 kind**
（`Arc` / `Spinner` / `Roller` / `Dropdown` / `TextArea` / `Keyboard` / `TileView` /

### 1.2 CSS / 主题：**整套主题子系统零生产调用者**

| 类型 | 生产调用点 | 取证 |
|---|---:|---|
| `ThemeManager`（含 `resolve_style`） | **0** | 全仓 `grep` 仅命中自身 `#[cfg(test)]` |
| `ThemeStateManager` / `Theme::dark()` | **0** | 同上 |
| `StyleSheetManager` / `global_stylesheet_manager()` | **0** | 仅命中 `stylesheet.rs` 自身的测试 |
| `Widget::apply_css` | **0** | 一个默认 trait 方法，**全仓无任何调用者** |
| `CssParser::get_declarations` | **0** | 无读者 |
| `Selector::match_rules` | **0** | 无调用者 |

**结论：主题、样式表、CSS 声明注册表构成一条完全断开的链**。控件读取 `WidgetStyle`，
但 `WidgetStyle` 的值只由手写 setter 与每控件的硬编码回退（`unwrap_or(Color::rgb(..))`）
填充，**没有任何 `Theme` 到达过控件**。

另有两个具体缺陷：

- `style/mod.rs:27-30` 的 `animation_group` 文档注释**逐字重复两遍**（Rust 会拼接，故渲染成重复句）。
- `css.rs::widget_kind_from_str` 只认 **30/167** 个 kind，未识别时**回退到 `WidgetKind::Window`**
  —— 即 `Stepper { … }` 这类规则会静默命中**所有窗口**。
- `Theme::fonts` 有 9 个 token，`resolve_style` **一个都没读**（该字段完全不可达）。

### 1.3 图标：**系统已存在**，唯一真缺陷是主题色

审计（见 §5）结论：`Icon` 已在工厂注册、C ABI 之外的上层可达、有 31 个图标、22 个测试。
唯一缺口：`Icon::new` 硬编码 `color: Color::PRIMARY`（`icon.rs:220`），是**唯一不随主题变化**的控件。

## 2. 修复一：JSON GUI 走能力契约（原则 #24 / #52 / #67）

### 2.1 新增 `src/json/properties.rs` —— 名称驱动的属性应用

原 `apply_properties` 是**逐键手写**的 `if let` 序列（13 个通用键），每控件的其它属性散在
`create_widget` 的各 arm 里。新增模块改为**按名称查控件自己的属性契约**
（`WidgetProperties`，BLUE15 Phase C-1 的成果），因此：

- 控件新增属性**无需改本模块**（原则 #67）；
- 未识别的键被**报告**而非静默丢弃；
- 类型不符被**拒绝**（`CapabilityValue` 的类型由 schema 声明，不做隐式转换）。

```rust
// src/json/properties.rs
pub(crate) fn apply_widget_property(
    widget: &mut dyn Widget, key: &str, value: &Value,
) -> ApplyOutcome { /* Applied / NotAProperty / Rejected */ }
```

### 2.2 `create_widget` 增加工厂兜底

在原 24 个 arm 之后新增一个兜底臂：不认识的名字改问能力注册表
（`widget_factory.create(name, geometry, "")`）。**这使控件集合从「loader 记得多少」
变为「工厂注册了多少」**，且未来新增控件**自动**可从 JSON 使用。

### 2.3 效果（实测）

```text
$ （临时探针，逐名遍历工厂的 widget_names()）
FACTORY_NAMES=155 JSON_OK=155 FAIL=0
```

**26 → 155**：工厂注册的**每一个**名字现在都能从 JSON 构造。该数字已被固化为测试断言
（`every_factory_registered_name_is_constructible_from_json`，断言「全部」而非阈值——
阈值会让下一个新注册的控件静默掉出 JSON 面）。

## 3. 修复二：CSS 解析增强

### 3.1 未识别的 kind 不再静默变成 `Window`

`CssSelector::to_selector` 由 `-> Selector` 改为 `-> Option<Selector>`，`widget_kind_from_str`
由 `-> WidgetKind` 改为 `-> Option<WidgetKind>`。`CssParser::parse` 跳过 kind 未知的规则
并告警，**其余规则照常登记**。

```text
（新测试）
unknown_kind_selects_nothing ................................ ok
an_unknown_kind_never_becomes_a_window ...................... ok   ← 钉住该回归
a_compound_selector_with_an_unknown_kind_selects_nothing .... ok
parse_skips_only_the_rule_with_an_unknown_kind .............. ok
```

### 3.2 声明注册表：从**无界增长**改为**有界 + 有序**

原实现是 `HashMap<String, Vec<..>>`，**只写不读、永不淘汰**（热重载场景下无界增长），
且迭代顺序未定义（依赖 cascade 顺序的调用方拿到随机顺序）。改为有序 `Vec` 并按
`MAX_STORED_RULES` 淘汰最旧项：

```text
stored_declarations_round_trip .............................. ok
the_registry_is_bounded ..................................... ok   ← 钉住上界
declarations_come_back_in_insertion_order ................... ok
```

### 3.3 新增 `CssWatcher` —— CSS 文件热重载（实现文档已承诺但不存在的 API）

审计发现 cookbook 在 **3 种语言**里都记录了 `CssWatcher`，而它在 `src/` 中**零命中**——
且被写进 `tools/fix_cookbook_api_reference.py` 的「不存在的名字」重写表，即**门禁在替
文档欺骗打掩护**（原则 #18）。

本轮**实现它**而非删除文档（`src/style/css_watcher.rs`，335 行，7 个测试）：

| 方法 | 语义 |
|---|---|
| `new(path, name)` | 按**名称**注册，故重载是**替换**而非叠第二份 |
| `set_poll_interval(ms)` | 默认 500ms；`0` = 每次检查 |
| `poll() -> Result<bool>` | 变化时恰好返回一次 `true`；**文件不存在返回 `Ok(false)`**（可在生成文件写出前就开始监视）|
| `reload()` | 忽略 mtime 强制加载 |

**解析失败的文件被上报且不注册**（否则一次错误编辑会替换掉可用的样式表）。
同时从 `fix_cookbook_api_reference.py` 的重写表中**移除** `CssWatcher` 条目——
现在文档与代码真的对上了。

## 4. 修复三：主题系统（从「无调用者」到「被实际应用」）

### 4.1 单一真相：`global_theme_manager()` + `resolved_theme_style()`

`ThemeManager` 是不可达的孤立值。新增进程级注册表（`OnceLock<Mutex<..>>`），
并**预置 light + dark 两个预设**——这一步把此前完全不可达的 `Theme::dark()` 变成可用的开关。

### 4.2 `resolve_style` 重写：角色表取代 13 个硬编码字符串

原实现是 `match class_name` 的 13 个字面量，未命中落 `_` 臂。改为
**7 个 `WidgetRole`**（`Surface`/`Primary`/`Text`/`Input`/`Accent`/`Choice`/`Danger`）
由 `WidgetRole::for_kind_name()` 解析，未知名 fallback 到 `Surface`——**与旧的 `_` 臂同解**，
即分类是新行为的**超集**而非变更。

### 4.3 补齐三个不可达面（实测）

| 缺口 | 之前 | 之后 |
|---|---|---|
| `Theme::fonts`（9 个 token） | **一个都不读** | `resolve_style` 设 `style.font` |
| 前景色对比度 | 硬编码白字 | WCAG 2.x 相对亮度选黑/白 |
| 输入框底色 | 硬编码白 | `Colors::input_background()` 由主题底色推导（深色主题不再刺眼）|
| 状态变体（hover/pressed/…） | 无 | `resolve_style_for_state(class, state)`，覆盖键 `"button:hover"` |
| `ThemeStyleToken` 覆盖面 | 5 字段 | +`font`/`opacity`/`shadow`/`touch_target`（`ShadowToken`/`[u32;2]`，schema 只含原语） |

### 4.4 真正接线：主题成为解析链的第一层（原则 #17：禁止迁移幻觉）

JSON loader 的 `apply_declared_styles` 现在按**递增优先级合并三层**：

```text
① 活动主题（resolved_theme_style）
② 全局样式表（global_stylesheet_manager）
③ 节点内联 CSS（apply_css）+ 显式 JSON 键
```

每层用 `WidgetStyle::merge` 合并，**更具体的层胜出**。这是主题第一次真正到达控件。

```text
（新测试，全部实跑）

switching_appearance_changes_the_resolved_style ............ ok  ← 断言「不同」而非字面量
the_resolved_style_carries_the_theme_font .................. ok
an_explicit_json_key_wins_over_the_theme ................... ok
a_theme_style_token_overrides_only_what_it_names ........... ok
```

## 7. 任务三：图标系统是否需要集成 —— **结论：不需要，系统已存在**

用户要求「只要给个结果」。以下是取证后的结论。

### 7.1 结论

**不需要「集成」一个图标系统 —— 已经有一个，且是完整的。** 唯一值得修的真缺口是
**主题色**（已在 §5 修掉）。SVG 输入解析、SVG 光栅化、图标字体**均不需要新增**。

### 7.2 取证

| 维度 | 实测 | 取证 |
|---|---|---|
| `IconName` 覆盖 | **31 个变体** | `src/widget/display_widgets/icon.rs:32-95` |
| 绘制方式 | **33 个 `fn draw_*`**，全部过程式（无路径数据表） | `icon.rs:298-1218`，约 900 行 |
| 工厂可达 | ✅ `register(icon_capability(), create_icon)` | `registration.rs:154` |
| 控制后端可达 | ✅ `WidgetKind::Icon` 在路由表内 | `control_backend/routing.rs:175` |
| 公开导出 | ✅ `pub use display_widgets::icon::{Icon, IconName}` | `widget/mod.rs:230` |
| 无障碍分类 | ✅ 与 `Avatar`/`QRCode` 同组 | `platform/accessibility/types.rs:599` |
| 测试 | **22 个**（含 SVG 导出冒烟） | `icon.rs` tests |
| C ABI / 语言绑定 | ❌ 零覆盖 | `bindings/` 与 `include/` 中零命中 |

### 7.3 为什么「SVG 图标输入」也**不必新增**

`src/image/` 已有 **真实**的 SVG 解析与光栅化（经 `resvg`）：

| 项 | 位置 | 状态 |
|---|---|---|
| `resvg = "0.48.1"` | `Cargo.toml:319` | 可选依赖，已在 |
| `svg-rasterizer` feature | `Cargo.toml:191` | 已定义，已并入 `image` |
| `resvg::usvg::Tree::from_data` | `src/image/decoder.rs:1652`（`decode_svg`）| 真实 XML 解析 |
| `resvg::render` + `tiny_skia` | `decoder.rs:1661-1663` | 真实光栅化 |
| `ImageFormat::Svg` / `Svgz` | `src/image/format.rs:56,58` | 枚举已备 |

即：`src/render/svg/backend.rs` 是**导出器**（`RenderCommand` → SVG 文本），
而**导入器**在 `image/` 里，且 `Image` 已接到 `ImageView` 与 `Button`。
应用要显示一个 SVG 图标，今天就可以 `ImageView(Image::decode(svg_bytes))`。

### 7.4 明确**不做**的两项（并登记理由）

| 项 | 处置 | 理由 |
|---|---|---|
| 图标字体（Font Awesome / Material codepoints） | **不做** | 本库定位是「纯 Rust 跨平台自绘」（`Cargo.toml:4`）；图标字体需**捆绑一个带授权的字体二进制**，并依赖字体整形放置 PUA 码位。收益可被已有的过程式 `Icon` + `image/` 的 SVG 管线覆盖，代价是打破「无捆绑二进制资源」的姿态。|
| 把 900 行过程式绘制重构为路径数据表 | **暂不做** | LOC 账（每新增一个图标要改 **5 处**）确实指向重构，但**该控件至今零真实使用者**（全仓唯一使用点是内部 `tools/widget_gallery.rs`）。为零调用者的代码做重构，顺序是反的——等真有图标集需求时按其要求驱动。|

### 7.5 一处登记：BLUE11/BLUE12 的「字体图标」条款应作废

`docs/plans/blue11.md:1034` 与 `blue12.md:337` 把 Icon 描述为「SVG/字体图标」，
而实现（无论过去或现在）两者都不是——是过程式几何。**该条款应显式记为 won't-do**，
以免路线图长期暗示「未完成的工作」。本轮仅在日志登记，未改动历史计划文档。

## 12.1 主题 JSON 夹具 + 门禁（关闭第 19 轮最大的「未验证」面）

### 问题

`Theme` 有 `Serialize`/`Deserialize`，`ThemeManager` 有 `save_theme`/`load_theme`，
但**全仓零夹具**。主题文件的字段就是**用户可见的格式 API**，改一个字段名会静默破坏
所有用户的主题文件，而测试全绿。

### 实现（关键决定：**生成**而非手写）

先手写夹具，**结果立刻被证明是错的**——我在 JSON 里凭空写了
`{"family":"Arial","size":14.0,"weight":400}`，而真实 `Font` 的字段是
`family`/`size`/`weight`/`bold`/`italic`（且全是私有字段，serde 表示由类型决定）。

> **这是一个方法论修正**：夹具若手写，它就**成了 schema 的第二份描述**，必然漂移。
> 改为由 `themes/generate.sh` 调用库自己的 `save_theme` 生成——文件**按构造**
> 不可能与结构体不一致。

```

tests/theme_fixture_test.rs   3 条测试
```

新门禁的第 3 步是**「重新生成后逐字节相同」**——这正是「夹具没有漂移」的定义，

## 13. 四项缺口的取证与修复

### 13.1 【P0】主题只对 JSON 路径生效 —— 走 C ABI 的控件完全不受主题影响

**取证（缺口的真正形状）：**

### 13.3 【P1】CSS 有 3 个 `WidgetStyle` 字段不可达

**取证：**

```text
CSS 能设的属性: color / background-color / border-* / padding / margin / font-* / opacity
WidgetStyle 字段: 上面这些 + background_gradient + shadow + touch_target   ← 3 个不可达
```

一个样式表**无法表达完整的样式记录**。补齐三个属性，并各自处理了实际语义：

| 属性 | 设计决定 |
|---|---|
| `background-gradient` | 接受 `linear-gradient(<angle>deg, <color> [<pos>], ...)`；位置支持 `50%` 与 `0.5` 两种写法；未标位置的停靠点**均匀分布** |
| `shadow` | `<x> <y> <blur> <color>`，颜色可前置（CSS 两种顺序都接受）；**`none` 是值不是错误**，用于清除低优先级来源设的阴影 |
| `touch-target` | `44px 44px` 两值形式 |

**两处刻意不做（并让报错说清楚）：**

- **radial / conic 被按名拒绝**，而非静默画成 linear —— 它们需要中心点与半径，
  而 CSS 不携带这些几何。报错写出「only linear-gradient(...) is supported」。
- **`parse_signed_length` 与 `parse_length` 分开**：后者把负值钳到 0（对尺寸正确），
  但 `-2px 2px` 是合法的阴影偏移，钳掉等于**静默挪位**。新增专门的带符号解析。

**验证**：`style::css` 测试 32 → **46**，含「负偏移必须保留」「`shadow: none` 清除」
「malformed 值必须报错而非忽略」「不支持的几何必须点名」。

## 13.8 一句话结论

用户问「是否要做到最完整、最完美」，我答「**方向不该扩张，但已有机制有真实接线缺口**」。
本轮把四个缺口全部修掉，它们**全属「可达性」而非「功能完整度」**：

1. 主题此前只接到**零消费者**的 JSON 路径，现接到 **C ABI 与窗口 API 两个主漏斗**
   （实测颜色随主题变化，7 条测试钉住）；
2. CSS 补上 `background-gradient` / `shadow` / `touch-target`，样式表终于能表达

3. README 显式声明 CSS/Theme/JSON 三块**不经 C ABI 暴露**（100 个 `rw_*` 中 0 个），
   消除文档欺骗；
4. JSON 布局 6 → **10** 种，且换行/网格用**几何断言**验证而非「能构造」。

**与我上一轮论证的关系**：上一轮的「不该追规范级完美」结论不变（Qt 的 QSS 裁剪、
QML 另建运行时都是判例）；本轮修的是**另一类问题** —— 已实现的东西是否处处生效。
两类判据不同，因此「不做更多」与「必须补这些」并不矛盾。

> （放 `target/` 下，不随发布物走），可复现上述所有数字。

### 24 个无同名注册 kind 的最终三态分类（§12.7）

| 类别 | 数量 | 代表 | 为何不注册 |
|---|---:|---|---|
| 别名 kind（`pub type`）| **15** | `Panel`→`GroupBox`、`ColumnView`→`TreeView` | 本是同一控件 |
| 基类 / 容器 kind | **2** | `Frame`、`Panel` | 仅供继承 |
| 子项 kind | **1** | `MenuItem` | 由父 `Menu` 创建 |
| 已被特化名取代 | **2** | `ColorDialog`（现 `color_picker`）| **值得补别名** |
| WebEngine 系列 | **11** | `WebEngineView`（现 `web_view`）| 11 kind ↔ 1 后端 |

**结论：24 个中只有 2 个值得补别名，其余 22 个是架构分类，不应“补齐”。**

### 由此新增的任务：E-5（机器可读的 kind 三态标记）

根本问题：**“这是别名”与“这是基类”只存在于开发者的头脑与自然语言注释里。**
没有机器可读标记，就无法区分「有意不注册」与「忘了注册」——这正是我连错两次的原因。

新增门禁要求每个 kind 命中且仅命中三态之一：`Registered` / `AliasOf(other)` /
`BaseOrChild`（**需新增显式源码标记**），并反向注入验证。

## 14.7 一句话结论（终版）

用户问「有什么常用控件是缺的」，三轮取证后的答案是：

1. **真缺的常用控件只有 4 个**（`NumberPicker` / `OtpInput` / `Pagination` / `Banner`）；
2. **6 个已完整实现、却忘记注册进工厂**的特化控件 —— 它们让 JSON GUI 与 CSS 在 6 个控件上成了死路；
3. 我自己在本轮**连错三次**（29 → 35 → 24 → 最终 6），根因分别是：拿 C ABI 当 Rust 库的主判据、
   `grep` 带引号搜标识符、以及**把 kind↔工厂名当成一对一**。三次都保留了更正记录。

**最终一句话**：控件**不应增加数量**；要增加的是**“哪些能造出来”的确定性**。
