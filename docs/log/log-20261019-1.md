## 2. §十六：`create_window` 的文档与实际效果

### 2.1 代码事实

`rust_widgets::create_window` → `backend_for_kind(WidgetKind::Window).create_window` →
`control_backend/custom` 的 `create_window` 挂载窗口控件；`adopt_widget_box` 调用
`attach_window_host_if_needed`，后者向 `Platform::create_window` 请求真实顶层窗口并记录
`set_host_window(widget_id, host)`。

因此当前契约是：

1. `create_window(...)` 创建**真实但隐藏**的顶层窗口；
2. `show_widget(id)` → `set_widget_visible(id, true)` → GTK `show_all()`（Win32 为 `ShowWindow`）。

`src/lib.rs` 的文档已改为这个顺序，示例包含 `show_widget`：

```rust
let window_id = rust_widgets::create_window("My App", 100, 100, 800, 600);
// Build the window's controls first, so the first frame includes them.
rust_widgets::show_widget(window_id);
```

这与反馈给出的“选项 2”等价，但不需要宿主直接调用 `platform::get_platform().create_window`：
库的挂载路径已经完成那一步，宿主只需 `create_*` + `show_widget`。

### 2.2 运行时证据

`examples/probe_keyboard_focus.rs` 在真实 X11 会话中：

- `create_window(title, 140, 140, 520, 260)`；
- 创建 `LineEdit`/`Button` 后 `show_widget(window)`；
- `tools/x11_inject_keys.py` 通过 `wmctrl`/`xwininfo` 找到标题匹配的**已映射顶层窗口**，
  并按窗口内坐标点击字段。

输出（完整见 §3）：

```text

runtime gui mode   : NativeInteractive
OK   the library created a window
injector           : x11_inject_keys: typed 3 character(s) into 0x4200003 ...
```

`xwininfo` 能给出该窗口的客户区几何并允许按相对坐标点击，证明 `show_widget` 之后窗口真实可见、
尺寸正确；如果窗口仍是 10×10 未映射 helper，注入器会以 `exit 3` 拒绝。

## 3. §十七：GTK 键盘焦点、`ValueChanged` 与真实 IME

### 3.1 修法

| 缺口 | 落点 | 说明 |
|---|---|---|
| 指针按下不移动焦点 | `src/widget/runtime.rs::dispatch_pointer_event` | `starts && widget_wants_keyboard_focus(target)` 时调用 `focus_on_pointer_press(target)` |
| 全部控件默认不可聚焦 | `src/widget/widget_trait.rs::Widget::is_focusable` + `src/widget/kind.rs::WidgetKind::wants_keyboard_focus` | 默认按 kind 判定；交互控件加入 tab 顺序，容器/装饰不加入 |
| GTK `DrawingArea` 从未 `grab_focus` | `src/platform/linux/platform_impl.rs::create_window` | 构造时 `set_can_focus(true)`，`connect_map` 时 `grab_focus()`；首次按下也 `focus_area_if_enabled` |
| 按键路径分叉（area vs toplevel） | 同上 | 按键由 toplevel 单一 dispatcher 处理，返回 `Stop`，避免 GTK 第二个 IM context 重复消费 |
| `ValueChanged` 不触发 | `src/widget/input_widgets/lineedit.rs` | 键盘/`TextInput`/`ImeCommit` 在文本实际变化后注入 `WidgetTriggerKind::ValueChanged`；未挂载控件不注入 |
| 没有 toolkit IM context | `src/platform/linux/canvas.rs::ImeContext` + 窗口路径 | `gtk::IMMulticontext`，随库内焦点 `focus_in/out`，`filter_keypress` 先于控件；preedit/commit 走 `platform::ime::deliver_*` |

`Event::ImePreedit` 现在会更新 `LineEdit` 的 composition（不改变 value），`ImeCommit` 先清
preedit 再插入文本，因此提交后不会残留下划线预览。

## 4. §十一：移动端剪贴板承载应用自定义 MIME

### 4.1 Android（`src/platform/android_jni.rs`）

`ClipData.newPlainText`/`newHtmlText` 只能写固定类型，因此自定义类型走构造路径：

```text
ClipDescription(label, [content_type])
+ ClipData.Item(payload)
→ ClipData(description, item)
```

- 写入：`set_clipboard_type(content_type, data)`；`setPrimaryClip` 后读回并逐字节比较。
- 读取：`clipboard_type(content_type)`；先在 `ClipDescription` 里核对 MIME，再读 `Item.getText()`。
- 协商：`clipboard_has_type(content_type)` 只读描述，不碰载荷。
- 载荷编码：`ClipData.Item` 没有字节字段，使用 **ISO-8859-1 一对一映射** 把任意字节放进
  `CharSequence`；读取时逐字符还原。UTF-8 不能覆盖任意字节序列，因此不使用。
- `AndroidClipboard::{set_contents, get_contents, has_format, set_contents_with_type,
  get_contents_for_type}` 全部接入；`get_contents` 先看 custom 再看 text/html，避免把自定义载荷
  误报成普通文本。

纯函数测试（host 上可跑）：

```text
cargo test --no-default-features --features "desktop,android-jni" --lib \
  a_custom_payload_round_trips_through_the_text_channel
   1 passed
```

覆盖 `0..=255` 全部字节的往返，以及“非本编码文本返回 `None`”。

### 4.2 HarmonyOS（`src/platform/harmony/pasteboard.rs`）

UDMF 的固定 UDS 只有 plain text / HTML；自定义类型走 general entry：

```text
OH_UdmfRecord_AddGeneralEntry(record, type_id, bytes, count)
OH_UdmfRecord_GetGeneralEntry(record, type_id, &entry, &count)
OH_UdmfRecord_GetTypes(record, &count)          // 枚举自定义类型
OH_Pasteboard_HasType(pasteboard, type_id)
```

- `type_ids_for_mime`：先试 MIME 本身，再通过 `OH_Utd_GetTypesByMimeType` 追加平台注册的 UTD id，
  以兼容被平台规范化的类型。
- `first_custom`：枚举 record 的类型，跳过 `general.plain-text`/`general.html`，再用
  `OH_Utd_Create` + `OH_Utd_GetMimeTypes` 把 UTD id 映射回 MIME。
- 写入同样读回比较；`data.len()` 超过 `u32` 时如实拒绝。
- 载荷只复制一次，`GetGeneralEntry` 返回的指针被视为 record 拥有的内存，不释放。

### 4.3 iOS（`src/platform/ios/native.rs`）

`UIPasteboard.setData:forPasteboardType:` 接受调用方给出的类型名：

- `pasteboard_set_custom(content_type, data)` 写入并读回比较；
- `pasteboard_custom(content_type)` 按类型读取；
- `pasteboard_custom_type()` 只把**含 `/` 的 MIME 名**视为应用自定义类型，避免把
  `public.png` 这类 UTI 误报成 MIME；
- `IosClipboard` 的五个入口全部接入。

### 5.1 参照 winit 补齐的移动端平台事实

winit 源码：`/home/mikeli/workspace/winit`（master，拆分后的 `winit-android` / `winit-uikit`）。
只借用它已验证的平台入口，不引入其依赖或事件循环。

| 项 | winit 的入口 | rust-widgets 落点 |
|---|---|---|
| Android DPI | `AndroidApp::config().density() / 160` | `AndroidPlatform::dpi_scale_factor()` 读 `DisplayMetrics.densityDpi / 160`；`capabilities().dpi_scaling` 跟随 `JavaVM`+`Context` 握手 |

| iOS DPI | `UIScreen` 的 scale（winit 的 monitor 用 `nativeScale`） | `dpi_scale_factor()` 用 `UIScreen.scale`；本 crate 的 `Display` 契约是 logical bounds + scale，与 `nativeScale`+native bounds 不是同一坐标系，选择在注释中写明 |
| HarmonyOS | winit 当前没有 OHOS 后端 | 保留本仓库自己的 `OH_NativeDisplayManager` 实现；`dpi_scale_factor()` 读 `densityPixels`，host 构建不声称 |


> 运行中修掉一处只在设备上暴露的缺陷：`Display.getRectSize` 在 API 34 上抛异常并留下

## 5. §十二：移动端显示器枚举、窗口归属与变更版本号

| 平台 | 实现 | 关键事实 |
|---|---|---|
| Android | `android_jni::display_info` + `AndroidPlatform::{displays, display_of_window, display_generation}` | `WindowManager.getDefaultDisplay()`；`getRealMetrics` 为 bounds，`getRectSize` 为 work area；`densityDpi/160` 为 scale；`Display.getDisplayId()` 为 id |
| HarmonyOS | `src/platform/harmony/displays.rs` | `OH_NativeDisplayManager_CreateAllDisplays`、`GetDisplayPosition`、`GetDefaultDisplayId`；`densityPixels` 为 scale；`availableWidth/Height` 为 work area |
| iOS | `ios/native.rs::displays` + `IosMobilePlatform::{displays, display_of_window, display_generation}` | `UIScreen.screens()`/`mainScreen()`（仅主线程）；bounds/scale/primary；无安全区矩形 API 时 work area = bounds，并在模块注释写明 |

共同点：

- 没有读数时返回空列表 / `None` / `0`，不虚构一块屏（原则 #37/#45）；
- `display_of_window` 先把 widget id 翻译成 platform handle id（`host_window_for`），再判断 kind；
- `display_generation` 从与 `displays()` 相同的字段做 FNV-1a，可跨帧比较。

**边界**：物理拔屏、旋转、改 DPI 的现场判据仍需设备/人在屏前；移动端只有编译/类型检查证据。

## 8. 未覆盖与边界（逐条写明，不用“只剩具名项”糊过去）

1. **HarmonyOS / iOS 的自定义 MIME 与显示器没有设备运行证据。** 两者均为交叉编译、真实链接或
   类型检查；Android 已在 x86_64 模拟器上通过 `nativePlatformProbe` 的 8 项断言。
2. **物理显示器变化未做现场判据。** 拔屏、改 DPI、旋转后 `displays()` 变短/`scale` 变化，
   仍需人在屏前或设备旋转。
3. **macOS 运行态未复跑。** `quit()` 跨线程、cocoa 帧心跳、FSEvents 删除分类与自定义 MIME
   的代码在树内并有前轮实机证据，但本轮没有 macOS 主机。
4. **Windows GUI 运行态未跑。** 只有交叉编译（含 C 依赖链接所需头文件/库），没有 GUI 会话。
5. **iOS 自定义 MIME 的 UTI/MIME 语义需实机确认。** 代码把含 `/` 的类型名当作 MIME，
   其他 UTI 不被误报为 `Custom`；真机上 `setData:forPasteboardType:` 是否原样保留 MIME 名
   仍需一次 Simulator/真机验证。
6. **HarmonyOS / iOS 的设备探针尚未扩展。** Android 已通过模拟器运行；OpenHarmony 无设备，
   iOS 无 Simulator，因此这两个平台没有对应的 `nativePlatformProbe` 运行结果。
7. **§8.7 取消令牌**仍是观察项，反馈本身写明“不请求改动”。
