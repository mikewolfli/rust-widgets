# 第 49 轮（2026-09-19）— 全库超级深度 + 超级广度扫描：发现一个修一个 → 版本 2.4.2

## 0. 一句话结论

基线 `cargo check --no-default-features --features desktop` 为 `Finished`，但五路并行取证
（假实现/死信号 · 平台门控泄漏 · panic/溢出/unsafe · 控件接线完整性 · 文档/测试/重复代码）
挖出 **7 大类、40+ 个真实缺陷**，其中最重的一条是**能力表 `commands:` 有一半是空头支票**：

- **346 / 503 个已公布的 command 根本没有实现**（`Label::set_text`、`Menu::clear`、
  `Table::clear_selection`、`WebEngineView::reload` …）——而**本该拦住它的测试自己也是坏的**：
  它匹配 `UnknownCommand`，但 `invoke_command` 永远不返回该值（内部转成
  `UnsupportedOnWidget`），所以失败列表恒为空、断言永不触发。
- 两个手势控件是**假的**：`SwipeToDismiss` 的 `MousePress` 分支只有注释，`MouseMove` 丢弃坐标，
  `swipe_offset` 只由测试直接写私有字段；`RefreshControl` 的 `update_pull` 没有任何事件调用点。
- `KIND_LIST_VIEW` 门控用错别名 → `tablet`/`mobile` 上 `create_list_view` 静默产出 **`Panel`**。
- `crate::asset` 被按 profile 门控，`tablet`/`mobile` 上整个模块消失（而文档无条件指向它）。
- `--all-features` 被 CI/`CONTRIBUTING.md`/设计文档当作检查项，但它**永远编译不过**。
- cookbook 用**三个语言**教了两个**根本不存在的模块**（`rust_widgets::embedded`、
  `platform::virtual_keyboard`），约 1320 行示例无法编译。
- `check_apple_thread_safety.sh` **自 2.4.1 起在 CI 里一直红着**（本轮修好并转绿）。

每条修复都附定点证据（`cargo check` / 单测 / 反向注入 / 实跑门禁）。

## 1. 方法论（原则 #1/#16/#56）

1. 先跑一次可信基线 → `Finished`（上方已实跑）。
2. 五路并行只读取证（子代理，各自 disjoint 范围），每条结论要求 `file:line` + 证据，
   不许推测。
3. **我自己逐条复核子代理的结论**，不直接采信。复核抓到 3 处子代理误报：
   - `switch`/`cupertino_switch` 的 `events: ["toggled"]` **不是**缺陷（`switch.rs:49` 确实 `emit`）。
   - `MousePhase` 去重后若只按 `widgets_unstripped` 门控，会在 tablet/mobile 变死代码。
   - 子代理给 `virtual_table` 的 `fetch_visible_window` 返回 `ReadOnlyProperty`，
     与 `tests/capability_command_surface_test.rs` 的契约（只接受 `Ok`/`OutOfRange`/
     `UnsupportedOnWidget`）冲突。
4. 逐轮只跑「定点证据」（单条 `cargo test <filter>` / `cargo check` / 反向注入），
   全量门禁留到全部轮次结束一次性跑（原则 #56）。
5. 目标：修到连续 2 轮无新发现。

## 2. 缺陷类 A（头条）：`commands:` 是半个库兑现不了的承诺

### 2.1 取证：测试匹配了一个永远不会出现的错误值

`src/widget/capability/properties_tests.rs` 里 `published_commands_are_recognised_by_their_control`
原本只收集 `Err(CapabilityAccessError::UnknownCommand)`，然后断言的却是 `recognised >= 5`
——**算出了失败清单却从没检查它**（清单只进了 `log::debug!`）。

更关键的是：`src/widget/capability.rs:809-816` 会把 trait 默认返回的 `UnknownCommand`
**翻译成** `UnsupportedOnWidget`：

```rust
Err(CapabilityAccessError::UnknownCommand) => {
    log::warn!(...);
    Err(CapabilityAccessError::UnsupportedOnWidget)   // ← 测试根本没匹配这个
}
```

所以那 7 个（后来发现是 346 个）名字**一次都没被记进 `unknown`**。断言必然通过。

### 2.2 修复

1. 测试改为同时匹配 `UnknownCommand | UnsupportedOnWidget`，并把断言改成 `unknown.is_empty()`
   （保留 `recognised >= 5` 的非空性下界）。
2. 让修复可持续：在 `WidgetProperties::command` 的**默认实现**里落实「`set_*` 是带载荷动词」
   这一约定（返回 `OutOfRange`，值由属性路由给）。120+ 控件不必各写一份必然漂移的 `match`。
   仅此一项就从 157 → 366 个被识别。
3. 其余约 90 个**无载荷**命令逐个接到控件真实方法上（`clear`、`clear_selection`、
   `next_page`、`select_row`、`undo`、`toggle`、`show`、`dismiss`、`accept`、`reject`、
   `trigger`、`open_menu`、`zoom`、`submit`、`cancel_drag`、`activate_selected`、
   `load_url`、`fetch_visible_*` …）。
4. 剩下 **7 条从能力表删除**，因为它们命名的方法根本不存在（`grid.select_cell`、
   `grid.clear_selection`，以及 5 个没有 overlay API 的 finance 图表上的 `add_overlay`
   ——只有 `CandlestickChart` 实现了它）。**硬造实现去满足表格才是本项目禁止的假修复**；
   删掉承诺才是诚实修复。

### 2.3 附带修好的 `TextEdit` 属性契约

`TEXT_EDIT_PROPERTIES` 把 `text`/`placeholder_text`/`max_length`/`read_only`/`line_wrap`
标成 `false, false`（不可读不可写），但控件有**真的** setter，且 `TextEdit::set` 只转发给
`base_property_set` → `rw_widget_property_set(id,"text",..)` 返回 `UnknownProperty`。
已实现 `get`/`set` 的五个分支并把 schema 改为 `true, true`，同时补进 `property_names`
（否则 `schema_and_contract_publish_the_same_names` 会失败——它确实失败了，这是它该做的）。

### 2.4 取证（实跑 + 反向注入）

```text
$ cargo test --no-default-features --features desktop --lib published_commands
test result: ok. 1 passed（503/503 全部被识别或如实报告需要载荷）

$ cargo test --no-default-features --features desktop --test capability_command_surface_test
test result: ok. 4 passed   （handled == total == 496）
```

**反向注入**（证明修好的断言真的能失败）：把 `list_box` 的 `clear` 改回 `UnknownCommand` 后，
测试立刻报出 239 条未兑现命令 —— 未修之前同样的破坏**不会**被发现。

## 3. 缺陷类 B：手势控件是假的（原则 #12/#13）

### 3.1 `SwipeToDismiss` 检测不到滑动

```rust
Event::MousePress { pos: _, button } => {
    if *button == 1 {
        // Start tracking swipe          ← 只有注释，函数体是空的
    }
}
Event::MouseMove { pos } => {
    // ... For testing purposes, we set the offset directly ...
    let _ = pos;                          ← 坐标被丢弃
}
```

`swipe_offset` 的唯一写入者是测试自己：`swipe_to_dismiss.rs:397` `sw.swipe_offset = -120.0;`
——**测试直接写私有字段，正好把一个不工作的交互藏起来**。

修复：新增 `drag_origin_x`，`MousePress` 记录起点、`MouseMove` 累加 `pos.x - origin`、
`MouseRelease` 判定阈值后归零；`TouchBegin`/`TouchMove`/`TouchEnd` 走同一条拖拽路径
（tablet/mobile 一致性）。测试改成发真实事件序列。

### 3.2 `RefreshControl` 的下拉永远累加不起来

`update_pull(delta)` 存在，但 `handle_event` 的 `MouseMove` 分支只有注释；
`pull_distance >= threshold` 因此**无法通过输入抵达**，`refresh_triggered` 不可能因手势触发。

修复：`MouseMove`/`TouchMove` 喂 `update_pull`（origin 随样本推进，单次累加），
并新增「向上拖不产生负值」「未按下的移动被忽略」两条测试。

### 3.3 取证（实跑）

```text
$ cargo test --no-default-features --features desktop --lib swipe_to_dismiss
test result: ok. 11 passed   （含 2 条真实拖拽 + 触摸拖拽）

$ cargo test --no-default-features --features desktop --lib refresh_control
test result: ok. 12 passed   （含 3 条真实拖拽事件驱动）
```

## 4. 缺陷类 C：门控用错别名 / 能力被当成 profile（原则 #41/#53）

### 4.1 `KIND_LIST_VIEW` → tablet/mobile 上静默变成 `Panel`

```rust
// src/widget/kind.rs：变体自己的门控是 widgets_unstripped
#[cfg(widgets_unstripped)]
ListView,

// src/lib.rs：却问的是 desktop_surface
#[cfg(desktop_surface)]
const KIND_LIST_VIEW: widget::WidgetKind = widget::WidgetKind::ListView;
#[cfg(not(desktop_surface))]
const KIND_LIST_VIEW: widget::WidgetKind = widget::WidgetKind::Panel;   // ← tablet/mobile 走这里
```

`tablet`/`mobile` 不是 desktop surface，但**确实**带 `ListView`。于是
`create_list_view(..)` 返回一个合法的 id，背后却是 `Panel`——**静默错误控件**。
修复：两端都改用 `widgets_unstripped`，与变体自身门控一致。

### 4.2 `crate::asset` 被 `desktop` profile 门控

唯一依赖是 `desktop-runtime`（`notify` + `crossbeam-channel`），而 `tablet`/`mobile`
也启用它。改成按能力门控后，**实跑证明是真实行为变化**：

```text
# 修复前：tablet 上 rust_widgets::asset::AssetWatcher 不存在
# 修复后：
$ cargo run --no-default-features --features tablet --example asset_probe
asset path resolves
```

同时把 `docs_paths_tests.rs` 里**照抄同一个错误门控**的守卫测试改成跟随正确门控
（照抄错误门控正是它当初没能发现问题的原因）。

### 4.3 `platform/mod.rs` 的 `any(macos, macos)`

`#[cfg(any(feature = "macos", feature = "macos"))]` —— 同一个特性写两遍，
于是 `--features macos-legacy`（只开 `cocoa-legacy`）两个分支都不匹配，
`macos_objc2` 模块**从明确要求了 macOS 后端的构建里消失**。
同型缺陷在 `macos_bridge.rs` 已修过，这里漏了；改为 `any(macos, cocoa-legacy)`。

### 4.4 取证（实跑）

```text
$ for p in desktop tablet mobile mini embedded; do cargo check --no-default-features --features $p; done
5/5 Finished，0 warning
```

## 7. 缺陷类 F：门禁自身是坏的 / 论文与实践不符

### 7.1 `check_capability_matrix_truthfulness` 空转

只校验 ✅ 单元格，而生成器 `CELLS = [CUSTOM] * len(PLATFORMS)` 一个 ✅ 都不产出
→ **检查 0 个单元格，永远不可能失败**，并且打印一行绿色通过。
修复：显式报告「本次未校验任何 ✅ 单元格」并点名真正覆盖 🟦 的是
`check_control_route_matrix`（StateBacked vs Placeholder）。**不假装它在检查东西。**

### 7.2 `check_event_model_signal_first.sh` 静默跳过 `demo/`

路径表里写的是 `demos`（目录真名是 `demo`），循环把不存在的路径**悄悄丢掉**，
于是这个扫描从来没覆盖过 `demo/`。修复：路径不存在直接 `exit 2`。

### 7.3 `check_apple_thread_safety.sh` 自 2.4.1 起一直红着

`activate_menu_item` 用了规则 C 明令禁止的 `performSelector:withObject:`。
修复不是放宽规则，而是换成语义更正确的 AppKit 文档化入口
`NSApplication -sendAction:to:from:` —— 真实菜单点击就是走这条，且 `from:` 参数会带上
sender（菜单 action 处理器期望的正是这个，而 `performSelector:` 把 item 当普通实参传）。
门禁已转绿。

### 7.4 `--all-features` 被当检查项，但它编译不过

CI 第 215/218 行、`CONTRIBUTING.md`、`docs/plans/platform_differences.md` 都要求它，
README 还称其为 “regression tripwire”。实测：

```text
$ cargo check --all-features
error: could not compile `rust_widgets` (lib) due to 833 previous errors
# 其中 537 个是 cannot find type `String`/`Vec`
```

根因：`--all-features` 同时开 `desktop` 与 `mini`，`mini` 切到 `no_std`，
绝大多数代码解析 `String`/`Vec` 所依赖的 `alloc` prelude 随之消失。
**一个永远构建不过的命令不可能拦下任何回归**，它只是让 CI 长期红着、让文档中的
贡献者流程无法执行。修复：CI 与文档全部改成 **profile 矩阵**
（`--no-default-features --features <profile>` × 5），并删除 `platform_differences.md`
中「混合开启也能 build 通过」这一与事实不符的表述。

### 诚实记录：一个**未修**的既有测试隔离缺陷

`cargo test --no-default-features --features desktop` 在某一次并行运行中出现过
`window_resize_relayout_test::the_reported_client_size_is_readable` 失败，随后 **3 次连续全量运行
均为 0 失败**，该二进制单独运行 6 次也均为 9/9 通过。

已取证判定为**既有的测试隔离问题，不是本轮引入的回归**，因此按要求**不在本轮修复**
（原则：不修无关缺陷，但必须如实报告）：

1. 该测试**从不调用** `command()`（`grep -n "invoke_command\|.command(" tests/window_resize_relayout_test.rs`
   无结果），而本轮的 `window.rs` 改动只新增了一个 `command` 分派分支；
2. 失败断言依赖**进程级**控制后端分配出的 window id：
   `assert_eq!(rust_widgets::window_client_size(win.raw_id()), Some((1024, 768)))`，
   而该文件自己也在注释里写明「平台单例是 `OnceLock` 记忆化的」，并用 `Box::leak` 覆盖它
   —— id 与尺寸在跨测试并发时可能互相覆盖。

**建议**（留给专项轮次）：给该测试文件加串行守卫（项目已有 `check_test_guard_uniqueness.sh`
与既定的锁约定），或让 `window_client_size` 的断言绑定到该测试自己注入的后端实例而非共享后端。
