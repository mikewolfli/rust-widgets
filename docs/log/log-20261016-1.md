## 1. §四 复核：`quit()` 的线程检查（无改动）

按第七节要求逐条复核固定修订上的差异。HEAD 上的现状（`grep` 核对）：

* `Platform::quit` 的返回类型已是 `bool`（调用方能区分“请求有读者 / 没有”）；
* **GTK**（`src/platform/linux/platform_impl.rs:558`）：`runtime.running` 置 `false`；GTK 主线程上才直调
  `gtk::main_quit()`，**否则**改走 `crate::platform::stop::request()`（记录请求，由同一文件帧回调在循环线程兑现）——
  正是反馈建议的形状；
* **Windows**（`src/platform/windows/platform_impl.rs:826`）：置 `runtime_running` 后调 `PostQuitMessage(0)`，
  并在文档写明“Win32 该调用是**线程相关**的、只是唤醒手段；真正结束循环的是那个标志”，返回 `true`；
* **macOS**（`src/platform/macos/platform_impl.rs`）：非主线程 `quit` 拒绝并说明，保留守卫。

**结论**：本节无新改动；后续 re-pin 时按符号复核即可。

## 2. §九.1 新增：暴露“系统处理器是否存在”

**现象（反馈）**：`capabilities().open_external` 回答的是“后端有没有 `open_external` 实现”（Linux 硬编码
`true`），不是“处理器程序是否已安装”；调用方只能在**真的交出一个目标**时才知道 `NoHandler`。

**实现**（按反馈建议的第一种）：

1. 共享探测 `src/platform/external.rs::program_is_on_path(program)`：读 `PATH`（`std::env::split_paths`，
   不假设 `:`/`;`；Windows 再按 `PATHEXT` 试后缀），逐个 `metadata` 判“是可执行普通文件”。
   **为什么是扫 PATH 而不是 spawn**：探测 `xdg-open`/`open` 本身就是“真去打开一个目标”，有副作用；而
   原则 #38 的 spawn 判据适用于“探测即操作前提”（打印客户端）的情形，这里相反。
2. 新 trait 方法 `Platform::has_external_handler() -> bool`，默认 `false`（诚实缺失，原则 #37）；
   在 `linux`（`xdg-open`）、`macos`（`open`）、`windows`（`cmd`，经 `PATHEXT`）各重写一行。

**判据**：新增单测 `platform::external::tests::the_handler_existence_query_answers_without_running_anything`
（本机 `xdg-open` 在 `PATH` 上 → `true`；绝对不存在路径 → `false`）。

**宿主可迁移性**：到位后 `host::open_url` 可无损迁到 `Platform::open_external`（反馈 §九.1 的“换接缝留待该查询到位”）。

## 3. §十.3 FSEvents 把“删除”报成 `Modified`

**现象（反馈）**：删除被监视文件后，macOS 上 `kind` 是 `ChangeKind::Modified`；Linux 的 inotify 报 `Removed`。

**实现**：把 `src/asset/watcher.rs::change_kind_of` 的签名从 `(&EventKind)` 改为 `(&EventKind, &Path)`，
在 `Modify` 分支加入**路径证据**：`path.exists()` 为真 → `Modified`，否则 → `Removed`。
`Modify(Name(_))` 仍先判为 `Renamed`（改名不能因“旧名已不在”而丢失）。调用点改为**逐路径**归类
（一条 notify 事件可带多条路径，结果可不同）。

**为什么不用按平台分支**：`notify` 归一的是**事件种类**而非文件系统的结果，路径是否已存在是调用点已有的
证据；用它在共享层判定，宿主无需按平台分叉（原则 #35/#36）。

**证据（本机实跑）**：
* 单测 `change_kind_projects_every_reported_change_and_drops_access`（改：`Modify`+存在→`Modified`，
  `Modify`+不存在→`Removed`，`Modify(Name)`→`Renamed`）；
* 新增**端到端**用例 `a_deletion_is_classified_as_removed_not_modified`：真建目录、建文件、删除，断言
  该路径被归为 `Removed`（与反馈“macOS 与 Linux 同一断言”一致）。

## 4. §十一 剪贴板承载“应用自定义 MIME 类型”

**实现**（按反馈建议的两种都提供）：

1. `ClipboardContent::Custom { content_type: String, data: Vec<u8> }`；`content_type()` 返回类型由
   `&'static str` 改为 `&str`（自定义类型编译期未知）。旧调用点全部为日志/相等比较，逐一复核无碍
   （原则 #21 例外③：新增可读能力）。
2. `RichClipboardBackend` 新增字节级接缝 `set_contents_with_type(&str, &[u8]) -> bool` 与
   `get_contents_for_type(&str) -> Option<Vec<u8>>`，默认经结构化变体推导；`ClipboardContent::raw_bytes`
   明确 `Image`/`Files` 返回 `None`（其 MIME 不命名本库持有的字节，返回即误标）。
3. **Linux/GTK 原生实现**（`src/platform/linux/gdk_clipboard.rs`）：`set_typed`/`typed`/`holds_target`
   用 GDK 的 owner-provided **selection target**（与 `text/html` 同一机制，按需 intern 任意 MIME atom），
   写后回读确认；`set_contents(Custom)`、`set_contents_with_type`、`has_format`、`get_contents_for_type`
   都走这一条路径。

**判据（本机实跑，真 X11 会话）**：新探针 `examples/probe_clipboard_custom.rs`
（`RW_GUI_PROBE_OK=1`，`--features desktop,gtk-native`）——写入 `application/vnd.rustage.nodes+json` 的字节后
`has_format` 为真、`get_contents_for_type` **逐字节**取回；结构化 `Custom` 路径同样往返成功；
对未持有的 `text/plain` 回答 `None`。

**其余后端的诚实行为**：macOS/Windows/iOS/Android/Harmony 的 `set_contents` 命中 `other =>` 分支，
`set_contents_with_type` 因此**如实返回 `false`**，不假装成功；`MockClipboard` 完整往返。
**原生承载的边界见 §6**。

## 5. §十二 显示器枚举、窗口归属与变更信号

**实现**：

1. 类型（`src/platform/types.rs`）：`DisplayId(u64)` 新类型（避免与 widget/window id 混用）；
   `Display { id, bounds: Rect, work_area: Rect, scale: f32, is_primary }`（复用 `core::Rect`，原则 #54）。
2. trait 方法（都有诚实默认）：
   * `displays() -> Vec<Display>`，默认空（=“本后端不上报显示器”，与 `dpi_scaling: false` 一致）；
   * `display_of_window(ObjectId) -> Option<DisplayId>`，默认 `None`；
   * `display_generation() -> u64`，默认 `0`（=“不上报变更”），非 0 才可跨帧比较。
3. 访问器：`platform::runtime::{displays, display_of_window, display_generation}` 并 re-export。
4. **Linux/GTK 实现**（新文件 `src/platform/linux/gdk_displays.rs`）：读 GDK 的
   `n_monitors`/`monitor(i)`/`monitor.is_primary()` 的 `geometry()`/`workarea()`/`scale_factor()`；
   `display_of_window` 由 `gtk::Window::position()` → `monitor_at_point` 归到同一索引；
   `display_generation` 用 FNV-1a 对当前配置派生一个**可重查的版本号**（GDK3 无稳定 monitor id，
   已就此写明边界）。GTK 主线程规则照旧（非主线程诚实返回空/`None`/`0`）。

**判据（本机实跑，真 X11 会话）**：新探针 `examples/probe_displays.rs`（同前门禁）实测：

```text
A. displays()          count: 1  id=0 bounds=(0,0) 2560x1440 work=(0,0) 2560x1413 scale=1 primary=true
B. display_of_window   window … is on display Some(DisplayId(0));  无此窗口 → None
C. display_generation  10498802906854224080（非 0）
=== 0 check(s) failed ===
```

工作区比边界矮 27px（真实面板），窗口归属与枚举一致——即反馈判据“真实会话上 `displays()` 至少返回一项、
能把窗口对到某块屏”在本机成立。**拔屏/改 DPI 的现场判据需要人在屏前**，见 §9。

### 5.1 macOS 原生实现与“跨编译探针”（含门禁抓到的真实缺陷）

**macOS 实现**（新文件 `src/platform/macos/displays.rs`，接在 `MacOSPlatform` 上）：读
`+[NSScreen screens]`/`-[the reference window screen]`；`DisplayId` 用 `deviceDescription[@"NSScreenNumber"]`
（the platform UI framework 的 `CGDirectDisplayID`，稳定）；`bounds`/`work_area` 取 `frame`/`visibleFrame`，
`scale` 取 `backingScaleFactor`，`is_primary` 取 `screen == +[NSScreen mainScreen]`；
`generation` 同 Linux 一样由配置派生。矩形报告**不做坐标系转换**（the platform UI framework 主屏左下角为原点，
而本后端本就按 the platform UI framework 坐标建窗），已写入模块文档。

**探针（比 include 更硬的做法）**：本机实测
`cargo check --lib --features "cocoa-legacy,macos" --target <darwin>` **能编译整个 macOS 后端**
（不需要 Apple 工具链）。故把探针落为门禁 `tools/check_macos_cross.sh`：对
`x86_64-apple-darwin` 与 `aarch64-apple-darwin` 各自 `cargo check --lib`。这比早期的
“include 单文件 + 桩模块”覆盖面大：`platform_impl.rs`/`file_picker.rs`/`canvas.rs`（未剥离 profile 时）
与新的 `displays.rs` 一起被编译。

**门禁首次冷跑即抓到真实缺陷（不是注入）**：`aarch64-apple-darwin` 编译失败——
`objc` 0.2 把 `BOOL` 定义为 `c_schar`（除 aarch64 外），aarch64 上却是 `bool`
（`objc-0.2.7/src/runtime.rs`），因此 `file_picker.rs:65/68` 的 `1 as BOOL` 在 Intel 过、
Apple Silicon 不过。这两行正是 `feedback-20261015.md` §十.1 声称已被 `8178d048` 修好的那两行——
（因为当时只检了 x86_64）修得并不完整。已改用 `cocoa::base::YES`（架构正确的常量）；
`grep -rn 'as BOOL' src/` 作为冰山扫描，全仓仅此两处、已清零。

**注入验证**：往 `displays.rs` 插入一行类型错误，`check_macos_cross.sh` 报
`error[E0308] … --> src/platform/macos/displays.rs:106:31`；还原后双 ABI 均 exit 0（记录在
`tools/gates_reverse_injection.md`）。

**边界**：仅**编译**验证；macOS 上的**运行**（真实屏枚举、拔屏）仍需 Mac 实机。
`--all-targets` 与完整 `desktop` 特性集在交叉编译时需要 Apple 的 `CC`（`alloca`、`minimp3-sys` 为目标编 C），
已在门禁头部写明为宿主限制而非缺陷。

## 6. §十.2 cocoa 有界会话“不 tick”：分析（本轮未改动代码）

源码事实：cocoa 后端（`src/platform/macos/canvas.rs:1243`）在**每个窗口创建**时用
`scheduledTimerWithTimeInterval:` 装一个重复 `NSTimer`，其 `tick:` → `crate::drive_frame`，
而 `drive_frame` 正会调用 `platform::stop::honour_request_on_loop_thread`
（`src/widget/runtime.rs`）。也就是说**有一个窗口时帧回调是存在的**，与反馈“一次帧回调都没发生”在源码上
不吻合。

因此本轮**不改** cocoa 代码（原则 #1：无实机证据不宣称修复）。可归纳的唯一源码级缺口是**更窄**的情形：
**没有任何窗口的会话不会 tick**（没有窗口就没有那个 timer）。需要 macOS 实机才能确认反馈的完整现象是
（a）timer 未装（例如窗口走了不含 `#[cfg(widgets_unstripped)]` 的创建路径）、还是（b）timer 装了但
`tick:` 未被 the platform UI framework 派发。**解除条件**：在 macOS 上跑 `rustage --launch --exit-after-ms 300`，
观察是否出现 `LoopEnd::HostEnded`，并按需在 `run()` 之前无条件装一个**进程级**帧 timer
（把“至少按后台节拍调用帧回调”的建议落到 `run()`，而不是依赖窗口）。这一条留待有实机的一轮。

## 9. 未覆盖与边界声明（逐条写明，不用“只剩具名项”糊过去）

1. **§十一 的原生承载**：本机只验证了 Linux/GTK（GDK selection target）与进程内 `MockClipboard`。
   macOS（`NSPasteboard` 自定义 type）、Windows（自定义 clipboard format）、iOS/Android/Harmony 仍**如实拒绝**
   `set_contents_with_type`（返回 `false`）。在那些宿主上实现需要各自一轮 + 实机，未凭 API 名盲写（原则 #1/#38）。
2. **§十二 的 Windows 原生枚举**：macOS 已实现（编译双 ABI 验证，运行待 Mac 实机）；Windows
   （`EnumDisplayMonitors`+`GetMonitorInfoW`）**未实现**，其 `displays()` 走诚实默认（空）。
   原因：本机是 Linux，无法编译/运行其原生代码；据此盲写会在无法验证的平台上引入回归风险。
3. **拔屏 / 改 DPI 的现场判据**：需要人在屏前（反馈 §十二 承认同类）。本轮证明“枚举出一块真实屏、窗口对到它、
   版本号可读”；**未**证明“物理拔掉副屏后列表变短”——那需要一次真实的拔插。
4. **§十.2 cocoa**：见 §6，需 macOS 实机。
5. **rustage 侧迁移未在本轮发生**：本文件只做上游（rust-widgets）改进；re-pin 后的宿主迁移不在本轮范围。
