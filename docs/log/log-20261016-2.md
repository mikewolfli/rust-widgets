## 1. §十二 Windows 原生显示器枚举（新文件 `src/platform/windows/displays.rs`）

**为什么是这一项**：上一轮 `log-20261016-1.md` §9.2 明确写着「§十二 的 Windows 原生枚举……`displays()`
走诚实默认（空）」——即反馈的判据「在真实桌面会话上 `displays()` 至少返回一项」在 Windows 上**从未成立**。
本轮在 Windows 实机上把它补上。

**实现**（`src/platform/windows/displays.rs` + `impl Platform for WindowsPlatform`）：

* `EnumDisplayMonitors` 遍历显示器，回调走 `GetMonitorInfoW(MONITORINFOEXW)` 取 `rcMonitor`/`rcWork`/
  `MONITORINFOF_PRIMARY`/`szDevice`；
* `scale` = 用该显示器的设备名 `CreateDCW` 建 DC 后 `GetDeviceCaps(LOGPIXELSX)/96`——这是
  `Platform::dpi_scale_factor`（主屏 `GetDC(NULL)`）的逐屏推广，DPI 感知模式不同则如实反映该模式的值；
* **`DisplayId` 用设备名的 FNV-1a 哈希**，不用 `HMONITOR`：句柄可能被 Win32 复用，而设备名（`\\.\DISPLAY1`）
  在显示器挂着期间稳定，且 `display_of_window` 能由窗口所在显示器重新算出同一个 id，两处自然对齐；
* `display_of_window(hwnd)` = `MonitorFromWindow(hwnd, MONITOR_DEFAULTTONEAREST)` → 取设备名哈希；
  与 GDK 的 `monitor_at_point` 的「最近显示器」语义一致；`None` 只在句柄为空/无法读取时给；
* `display_generation()` 由当前配置 FNV-1a 派生（与 Linux/macOS 同形），非 0 才可跨帧比较；
  **枚举不到任何显示器时返回 0**（trait 契约里的「本后端不上报变更」），不拿空集的哈希冒充一次观测；
* **线程**：Win32 的这三个调用任意线程可调，故**不加**主线程守卫（不像 GDK/the platform UI framework）。

**trait 接线**（`src/platform/windows/platform_impl.rs`）：

* `displays()` → `super::displays::displays()`；
* `display_of_window()` 分两个 cfg 变体：`widgets_unstripped` 走既有的 `window_hwnd_for_widget_id`
  （同时解析平台 id 与控件注册表 id，和 `set_widget_visible`、绘制路径同一套翻译）；stripped 档没有注册表
  id，走 `get_native_handle` 直取平台 id；
* `display_generation()` → `super::displays::generation()`。

**证据（本机真会话，`cargo test -- platform::windows`）**：

```text
test platform::windows::tests::windows_backend::displays_are_enumerable_and_a_window_is_located_on_one ... ok
```

该用例断言：`displays()` 非空、`is_primary` 恰好 1 个、每台 `bounds`/`work_area` 有正尺寸且 `scale > 0`、
一个真实创建的窗口能落到某个已枚举 id 上、`display_generation() != 0`、对 id `0` 回答 `None`。

## 2. §十一 Windows 自定义 MIME 剪贴板（`src/platform/clipboard_stubs.rs::windows`）

**为什么是这一项**：上一轮 §9.1 写着「§十一 的原生承载：macOS、Windows……仍**如实拒绝**」。
本轮把 Windows 这一半补上，用 Win32 的注册剪贴板格式（`RegisterClipboardFormatA`）承载任意 MIME——
这正是 `CF_*` 常量未定义的类型的官方机制。

**实现**：

1. `set_contents(ClipboardContent::Custom { content_type, data })`：以 MIME 名注册格式后
   `SetClipboardData`；空载荷也分配至少 1 字节（`GlobalAlloc(GHND, 0)` 可能返回 null）；
   写入失败时 `GlobalFree`（`SetClipboardData` 失败不接管所有权），不泄漏；
2. `has_format(content_type)`：`text/plain`→`CF_UNICODETEXT`、`text/html`→`HTML Format`，
   **其余**→ 按名注册后 `GetClipboardData` 判空；
3. `get_contents_for_type(content_type)`：原生按类型读——`text/plain` 取文本字节、`text/html` 取
   **片段**（不是 CF_HTML 信封，与 `ClipboardContent::Html::raw_bytes` 一致）、其余取注册格式的原始字节；
4. 抽出 `read_html_fragment()` 供 `get_contents` 与 `get_contents_for_type` 共用（消除重复读取）。
   其余后端（macOS/Windows 之外）行为不变，仍走 trait 默认、如实拒绝。

**证据（本机真会话，`RW_GUI_PROBE_OK=1 cargo run --features desktop --example probe_clipboard_custom`）**：

```text
=== clipboard custom-type probe ===
backend: WindowsPlatform
A. set_contents_with_type / has_format
   set_contents_with_type -> true
  OK   the custom type was stored
  OK   has_format answers true for the custom type
B. get_contents_for_type
   get_contents_for_type -> 46 byte(s)
  OK   the payload comes back byte-for-byte
  OK   a type the clipboard does not hold answers None
C. the structured Custom route lands in the same place
   set_contents(Custom) -> true
  OK   a structured Custom write is readable by name
  OK   its bytes come back unchanged
=== 0 check(s) failed ===
```

同时把 `examples/probe_clipboard_custom.rs` 的**可承载平台**从「仅 Linux/GTK」扩到「Linux/GTK 或 Windows」
（`run_staging_probe` 在两者都跑；macOS 仍打印诚实拒绝），否则该探针在 Windows 上会打印「本后端没有原生
自定义剪贴板」——那在改动后已不是事实（原则 #18 文档必须与代码一致）。

**一次如实记录的波动（原则 #1/#59）**：探针**首次**运行 `has_format` 报 1 处 FAIL，而隔离单测（`set→has→get`
同进程连做）为 PASS、**重跑探针 0 失败**。判据是 `has_format` 里 `OpenClipboard` 成功但 `GetClipboardData`
为空，仅可能是**外部进程在两次调用之间抢占了剪贴板并 `EmptyClipboard`**（Windows 剪贴板是会话级单例；
探针文档本就写明「换一台没人用剪贴板的机器」）。这是 Windows 剪贴板模型固有的竞态，不是本项目代码可消除的
缺陷；已按原样记录，不粉饰。

## 3. 冰山扫描发现的两处同类问题（原则 #2）

### 3.1 `clipboard_text()` 在 Windows 上把「空文本夹」与「无文本」合并（§8.6 同类）

`feedback-20261015.md` §二 的对照表把 §8.6（`clipboard_text() -> Option<String>`）标为「已实现」，但实现的是**共享函数**；
Windows 后端**没有** override 它，于是走 trait 默认——而默认从合并式 `get_clipboard_text()` 派生，把「剪贴板放着一个
空文本」与「剪贴板没有文本」都报成 `None`。这正是该条反馈要消除的合并。Linux/GTK、Android、iOS、HarmonyOS 都已
各自 override 精确回答，Windows 是唯一漏掉的桌面后端。

**修法**：抽出 `windows/platform_impl.rs::read_clipboard_text() -> Option<String>`（null 句柄→`None`，存在句柄→
`Some(内容)`，空内容即 `Some("")`），`get_clipboard_text` 改为 `read_clipboard_text().unwrap_or_default()`（语义不变），
新增 `clipboard_text()` override 返回它。单测
`clipboard_text_distinguishes_an_empty_text_clip_from_no_text` 实跑 PASS（写完 `""` 读回 `Some("")`，并保存/还原原剪贴板）。

### 3.2 `windows/file_picker.rs` 缺 `compat` 导入 → `mini`/`embedded` 在 Windows 上编译失败

扫 profile 时（`cargo check --features mini`）暴露：该文件用 `Vec<u16>`/`String::from_utf16_lossy` 却只 import 了
`std::os::windows::ffi::OsStrExt`/`std::path::PathBuf`。`mini` 是 `no_std`，std 前奏被抑制，两个名字都找不到——
**这是既有缺陷**（`git status` 确认本轮未改该文件），且 Windows 是主机时 `check_profiles.sh` 的 cross 步骤才第一次
真正编译到它。修法是补一行 `use crate::compat::{String, Vec};`（与 `platform_impl.rs` 同一写法），
`cargo check --features mini/embedded --all-targets` 随即转绿。

## 4.1 “全量挂起”的真凶：Windows 原生 TSF/IME 探针（既有缺陷，本轮修复）

**为什么修**：用户点名“找出全量测试里那个挂起的 `widget::` 用例”，并选择“顺带修掉 Windows 原生 IME/TSF 探针”。

**定位（原则 #1，逐步收窄）**：

1. 单线程 `-- widget:: --test-threads=1` → **4288 项 20.39s 跑完**，`widget::` 既无死循环也不慢——
   **“挂起的 `widget::` 用例”并不存在**，挂起另有其因。
2. 单线程跑**全量** → 进程在 `platform::ime_windows` 处 `exit 0xc0000005 (STATUS_ACCESS_VIOLATION)`；
   并行则表现为**不结束**。真凶是 TSF 探针。
3. 加临时 `eprintln!` 标记后单线程复现：输出停在 `c1 c2 c3`（`CoCreateInstance`/`Activate`/`CreateDocumentMgr`
   均成功返回），而 `CreateContext` 之后的 `c3.5`/`c4` 从不打印——越界发生在 `ITfDocumentMgr::CreateContext`。

**根因**：`tsf::create_thread_mgr` 在探针路径里建了**完整编辑上下文**（`CreateDocumentMgr`→`CreateContext`→`Push`→
挂 `ITfTextEditSink`/`ITfThreadMgrEventSink` 汇）。但没有 `ITextStoreACP` **文本存储**的上下文不是合法编辑目标，
这些调用在 Windows 上直接越界。`grep` 证明 `create_thread_mgr`/`destroy_thread_mgr`/`TsfConnection` **全仓库仅探针调用**，
即这套机械只有探针一个消费者、也只有它会崩。

**修法（收缩到“能证明正确的边界”，原则 #37）**：探针只回答“本线程能否 `create`+`activate` 一个 TSF 线程管理器”——
这正是 `has_native_ime()` 该回答的问题。改动：

* `tsf::create_thread_mgr()` 收缩为 `CoCreateInstance` → `Activate`；`TsfConnection` 只剩 `thread_mgr`；
* `destroy_thread_mgr` = `Deactivate` + `Release`；
* 删除探针无法安全执行且无其他消费者的机械（原则 #4）：`ITfDocumentMgr`/`ITfContext`/`ITfThreadMgrEventSink`/`ITfTextEditSink`
  的 vtable、`ComLink` 与汇回调、`advise_sink`/`unadvise_sink`/`query_itf_source`/`pop_all`/`guid_eq`、
  `TsfCreateError::Context`；同步删掉只描述它们的 `tsf_layout_tests` 用例与全部临时 `eprintln!` 标记；
* **保留** STA 守卫（`CoInitializeEx(APARTMENTTHREADED)`；线程已在 MTA 则如实拒绝为 `false`，绝不去碰 TSF）与
  `PROBE_LOCK` 串行化（两者是诊断阶段有效的防护，且探针自身仍需要）。

**证据（本机，全部实跑）**：

```text

cargo test --lib … desktop -- platform::ime_windows      # 并行，连跑 3 次 → 每次 21 passed; 0 failed；无挂起/无崩溃
cargo test --lib --no-default-features --features desktop               → 7345 passed; 5 failed; finished in 169.93s
cargo clippy --lib … desktop -- -D warnings                            → Finished，零警告
cargo clippy --lib … mini    -- -D warnings                            → Finished，零警告
```

## 4.2 上节残留的 5 项：同一根因——宿主文本缩放 157%，已修

**根因（一条）**：本机 `HKCU\Software\Microsoft\Accessibility\TextScaleFactor` = **157**（实查：
`Get-ItemProperty 'HKCU:\Software\Microsoft\Accessibility' -Name TextScaleFactor` → `157`），即用户把系统“文本大小”
设为 157%。于是 `platform::profile::text_scale() = 1.57`，`Font::scaled` / `LayoutContext::default()` 按它缩放，
而**这 5 条用例把期望写死成了 100% 的值**。代码是对的，问题在于测试期望与一处几何口径没跟上这个事实。

| 用例 | 根因 | 修法 |
|---|---|---|
| `theme::tests::resolved_style_carries_the_theme_font` | `role_base_style` 故意把 body 字体 `scaled(effective_text_scale())`，测试却拿**未缩放**的 `fonts.body` 比 | 期望改为 `fonts.body.clone().scaled(environment().effective_text_scale())`（测试） |
| `json::loader::tests::the_resolved_style_carries_the_theme_font` | 同上 | 同上（测试） |
| `widget::…::tabwidget_a_crowded_strip_gives_every_tab_its_full_share` | tab 条用 `CompositeBuilder::arrange`（**会**按 text-scale 放大 gap）组条，但条带带宽按**未缩放**的 `TAB_SPACING` 算 → 溢出 1px → 收缩把 49 画成 48 | `tab_width_hints`/`tab_run` 改用与布局同一口径的 `scaled_tab_spacing()`；测试的 `TAB_SPACING` 位置断言同改（代码+测试） |
| `widget::…::tabwidget_a_strip_that_fits_declares_each_tab_as_fixed` | 同上（带宽少 1px → 40 画成 39） | 同上 |
| `layout::flex::tests::the_hint_channel_and_the_legacy_path_agree_on_the_same_sizes` | 无 context 的 `FlexLayout::arrange` 用 `LayoutContext::default()`（**非名义**，带 text-scale），而 `update` 是名义 → scale≠1 时不一致；且 `arrange` 自身文档写明应按“名义数值” | `FlexLayout::arrange` 改用名义 context（`layout_scale=1.0, font_scale=1.0`），与文档和 `update` 一致；`arrange_with_context` 仍按设备缩放（代码） |

**证据（本机实跑）**：

## 5. §十.2 cocoa 有界会话「不 tick」：仍不改（需 macOS 实机）

沿用上一轮分析：cocoa 后端在**每个窗口创建**时用 `scheduledTimerWithTimeInterval:` 装重复 `NSTimer`，
`tick:` → `crate::drive_frame` → `platform::stop::honour_request_on_loop_thread`。源码上「有窗口就有帧回调」，
与反馈「一次帧回调都没发生」不符；唯一更窄的源码级缺口是**无窗口的会话不 tick**。要确认反馈的完整现象
（timer 未装还是未被派发）必须在 macOS 上跑 `rustage --launch --exit-after-ms 300` 看是否出现
`LoopEnd::HostEnded`。本轮主机是 Windows，无实机证据，**不改** cocoa 代码（原则 #1：无实机证据不宣称修复）。
解除条件不变：有 Mac 实机的一轮里，在 `run()` 之前无条件装一个进程级帧 timer 并把结果实测。
