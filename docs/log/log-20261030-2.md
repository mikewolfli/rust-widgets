## 1. B29.01｜质量档位（L0）

### 1.1 改动

- 新增 `src/wgpu_backend/renderer/policy.rs`：
  - `pub enum RenderQuality { ByteExact, Antialiased }`（`Default = Antialiased`，见 §7 D-1）。
  - `quality_refuses_stream(quality, commands)`：`ByteExact` 时拒绝两类流
    ① 含 `FillCircle / DrawCircle / DrawArc / StrokeRoundedRect`（边缘羽化）；
    ② 流内没有整帧不透明 `Clear`（透明目标上的预乘存储差异，与 AA 无关）。
    `FillRoundedRect` **不在**①中：它按参考实现的同一行 span 绘制，本来就逐字节相同。
  - 语义只描述意图，公共类型/方法名不出现 `gpu`/`cpu`/`sdf` 机制词（原则 #52、计划 §2.2）。
- `renderer/stream.rs`：新增 `gpu_claims_stream` / `gpu_delivers_pixels`，三条入口
  （owned / cached / texture）都**先问意图**，再问调度器；两条像素入口再问成本门控。
- `renderer/frame.rs`：`render_quality()` / `set_render_quality(..)`，字段 `quality`。

### 1.2 判定口径

- `ByteExact` 下，含圆流与无 clear 的半透明流**逐字节等于**
  `rasterize_draw_commands_rgba8`；`Antialiased` 下含圆流至少有 1 个边缘字节不同，
  但内部/外部形状仍一致；纯矩形流在两档下输出相同（档位不误伤效果 A）。
- 反向注入：删掉 `ByteExact` 分支 ⇒ `byte_exact_keeps_an_edge_feathered_stream_on_the_reference_rasteriser`
  与 `byte_exact_keeps_a_translucent_stream_on_the_reference_rasteriser` 立即变红
  （二者都先断言 `quality_refuses_stream(ByteExact, ..) == true`，再断言像素等于参考）。

### 1.3 用例（`cargo test --lib --features desktop,gpu-wgpu wgpu_backend`，127 passed）

- `renderer::tests::byte_exact_keeps_an_edge_feathered_stream_on_the_reference_rasteriser`
- `renderer::tests::byte_exact_keeps_a_plain_rectangle_stream_byte_identical`
- `renderer::tests::antialiased_lets_the_edge_of_a_circle_differ_from_the_reference`
- `renderer::tests::both_qualities_draw_a_plain_rectangle_stream_identically`
- `renderer::tests::byte_exact_keeps_a_translucent_stream_on_the_reference_rasteriser`
- `renderer::policy::tests::byte_exact_refuses_edge_feathered_shapes`
- `renderer::policy::tests::byte_exact_refuses_a_transparent_target_without_an_opaque_clear`
- `renderer::policy::tests::a_translucent_clear_does_not_make_the_destination_opaque`
- `renderer::policy::tests::a_filled_rounded_rectangle_is_not_an_edge_feathered_shape`

**未覆盖**：`ByteExact` 不对纹理入口做「AA 形状之外」的额外限制——它复用同一条
`gpu_claims_stream`，因此纹理入口也遵守同一意图；本轮没有为纹理入口单独造 AA 用例，
其行为由 `gpu_claims_stream` 的共享实现与上述像素用例间接覆盖。

## 2. B29.02｜像素回读成本门控（L2）

### 2.1 改动

- `renderer/policy.rs::CostGate`：
  - 白名单 = **该流中最大的合格形状**：
    - `Gradient`：渐变命令自身矩形的面积；
    - `Blend`：非 `Normal` 模式下绘制、且 `draws_under_blend` 接受的命令的裁剪后包围盒面积。
  - 两个常数，均带出处：
    - `COST_GATE_AREA_THRESHOLD = 900_000` px（计划 §1.1「面积 ≥ ~1 MP」+ 720p 实测
      921 600 px；1 MP 会排除唯一测到 GPU 胜出的帧，故取略低值）；
    - `COST_GATE_HYSTERESIS_PERCENT = 10`（计划 §2.1 的 ±10% 迟滞）。
  - 迟滞作用于「本次面积 vs 上次面积」：同一形状类别、面积变化 ≤10% 时沿用上次选择，
    画面尺寸轻微抖动不再逐帧换路。
- `renderer/stream.rs`：`gpu_delivers_pixels` = 调度器可覆盖 **且** 门控选择加速路径；
  两条像素入口使用它；**纹理入口不门控**（计划 §2.4）。
- `renderer/frame.rs`：`cost_gate_enabled()` / `set_cost_gate_enabled(..)`。默认开；
  关闭后恢复「可覆盖即 GPU」的旧行为，供 bench 测原始 GPU 列与宿主重新标定。

### 2.2 实施中发现并修复的测量缺陷（冰山下的一条）

第一版 bench 用「`selected` 计时 < `cpu` 计时 × 0.95」判 winner。实跑暴露问题：
当门控把流留在 CPU 时，`selected` 与 `cpu` **都是 CPU 光栅器**，二者只差 `cpu` 列多追加的
一条 `SetBlendMode`（以及噪声），于是 320×200 出现 `rects-2000 → gpu` 的假胜场，720p 出现
`rects-200 / images-8 / blend-small → gpu`。这不是门控错了，是**用计时判断“选了哪条路”**错了。

修复：新增只读查询
`WgpuRenderer::selects_accelerated_pixels(width, height, commands) -> bool`，返回与两条像素
入口**完全相同**的决策（意图 → 调度器 → 门控），bench 的 winner 列改用它。它不绘制、不改像素，
也不是第四条交付入口；理由写入 blue29 §6。

### 2.3 验收（实跑，`cargo bench --features desktop,gpu-wgpu --bench wgpu_bench`）

`winner` 列（= `selects_accelerated_pixels` 的答案）：

## 3. B29.03｜公开「等待设备」入口

### 3.1 改动

- `renderer/frame.rs`：`pub fn wait_idle(&self) -> Result<(), String>`。
  - 内部 `device.poll(PollType::Wait { submission_index: None, timeout: Some(GPU_READBACK_TIMEOUT) })`；
  - 名字只描述意图，不暴露队列/栅栏（计划要求）；超时沿用回读的 10 s（D-3）。
- `benches/wgpu_bench.rs`：新增 `texture+wait` 列（`with_draw_commands_texture` 后调用
  `wait_idle`，drain 仍在计时区外）。

### 3.2 判定口径与证据

- 用例 `renderer::tests::wait_idle_leaves_the_pending_frame_ready_to_read_back`：
  纹理入口提交一帧 → `wait_idle` → 读回 A → 再 `wait_idle` → 读回 B → 断言 A == B，
  且 A == 参考光栅 = **没有新帧、也没有丢帧**。
- `texture+wait` 列实跑非零，且给出了“未等待”列低估的 GPU 完成时间，例如 720p `clear`：
  `texture 20.5 µs` vs `texture+wait 289.2 µs`（差 ≈ 269 µs 的完成等待）。

**未覆盖**：`wait_idle` 是设备级等待（等所有已提交工作），不提供“只等某一帧”的栅栏；
本轮按计划只解决“能否等”，不引入 present/swapchain。

## 10.1 先说三处「Plan 与代码事实不一致」的地方（不猜，取值并写明）

1. **`Platform::frame_presentation_supported()` 的签名**。计划写无参，实现取
   `frame_presentation_supported(&self, window: ObjectId)`。理由：能力就是「这个窗口现在能不能被
   命名」，无参版本必然回答「本进程某时能」，与 `raw_window_handle(window)` 的实际答案会分离——
   这正是 #99 说的「镜像漂移」。多一个实参也在 #41/#53 的允许范围内（运行时查询，不是 API 分叉）。
2. **`SurfaceError` 在 wgpu 30 已不存在**。获取结果改成 `CurrentSurfaceTexture`
   （`Success/Suboptimal/Timeout/Occluded/Outdated/Lost/Validation`）。因此：
   `Timeout/Outdated/Lost/Validation` 由获取路径产生，`OutOfMemory/DeviceLost` 只能来自 configure
   与设备丢失观察，`Occluded` 是本版本新增的真实分支（显示器休眠/会话未合成）。
   模块文档已写死这条对应关系，避免读者按计划的旧名字找不存在的分支。
3. **`choose_config(...) -> SurfaceConfiguration`**：本层返回自己的 `PresentationConfig`，末端由
   presenter 映射到 `wgpu::SurfaceConfiguration`。理由：纯函数要能在没有 `wgpu` 的测试里运行，
   而 `wgpu::SurfaceConfiguration` 带着 `color_space`/`view_formats` 这类设备概念。字段一一对应。

## 10.3 B29.08｜`FramePresenter` 与配置

新增 `src/render/present/`（`mod.rs` 只声明/导出）：

| 文件 | 内容 |
|---|---|
| `intent.rs` | `FramePresentation { Default, Exact, Smooth }` + 线程局部意图表 `request/requested/forget` |
| `config.rs` | `SurfaceFormat/SurfaceAlpha/PresentMode/SurfaceCapabilities/PresentationConfig` + 纯函数 `choose_config` |
| `status.rs` | `SurfaceFailure/RecoveryAction/PresentationStatus/PresentHealth`（三层升级预算） |
| `damage.rs` | `PresentDamage`（行带合并、裁剪、超限退化全帧） |
| `smooth.rs` | `GpuPaintBackend`（记录器）+ `classify/census`（48 变体普查） |
| `presenter.rs` | `FramePresenter::{new,configure,resize,present,status,wait_idle,stats,mark_damage,...}` |

**格式优先级的依据**（`config.rs` 文档 + 单测）：CPU 帧是 sRGB 字节。`*Unorm` 目标按字节存储、
合成器按 sRGB 解释 ⇒ 写什么读回什么；`*Srgb` 目标把写入当线性再编码 ⇒ 同字节会变。所以
`ByteExact` 先 `*Unorm`、`Antialiased` 先 `*Srgb`（线性空间混合的边更好看）。这解释了
`choose_config` 为什么必须收 `quality` 实参——它是两档唯一的差别（有单测钉住）。

**通道序**：渲染到 `Bgra8*` 目标时**格式本身**完成分量映射，着色器再 swizzle 就是双重映射。
首版写了 swizzle，真机立刻暴露：256000 字节里 64000 字节不同（正好一个象限）。删掉 swizzle 后
逐字节相同。读回时按 `needs_channel_swap` 反向映射，只用于对拍。

**颜色空间实测**（计划要求「禁止用看起来对放过」）：`needs_srgb_decode` 在 `*Srgb` 目标上把
sRGB→线性预转换，再由目标编码回原字节；本机 `ByteExact` 选到 `bgra8-unorm`，因此走的是
「零变换 + 格式映射」这条最强路径，实测逐字节相同。

## 10.4 B29.09｜`Exact` 上屏（真机闭环）

`present()` 的顺序：损伤行上传 → 一帧全屏 blit（从镜像纹理画满整个目标，因为呈现目标的上一帧
内容未定义）→ `queue.present`。**为什么部分上传也要整帧重画**：不重画的部分会闪烁；贵的部分是从
CPU 搬像素，那部分才是损伤要省的。

**真机证据**（`bash tools/run_present_macos.sh`）：

```text
present_smoke: backend=cocoa
present_smoke: target 320x200 format=bgra8-unorm alpha=opaque present=auto-vsync
present_smoke: first frame byte-identical (256000 bytes)
present_smoke: band update byte-identical (256000 bytes)
present_smoke: resize byte-identical (64000 bytes)
present_smoke: stats offered=304 presented=303 skipped=1 rows=616
run_present_macos: PASS
```

- `band update`：只上报 16 行损伤（`rows_uploaded` 累计 616 行 = 400 首帧 + 16 + resize 后 200），
  读回仍是 **256000 字节全帧一致** ⇒ 镜像纹理 + 整帧重画是对的。
- `stats`：304 次 offer / 303 次 present / 1 次 skip（未损伤那次）/ 300 个损伤帧不丢。
- `resize`：320×200 → 160×100 后仍逐字节一致。

**探针第一次跑出的是 `occluded`**（显示器休眠）。处理方式：探针有界重试 40×100 ms，仍不可见就
`SKIP(host-limited)` 并写明原因（原则 #103）；`run_present_macos.sh` 先 `caffeinate -u -t 2`
唤醒显示器（宿主动作，不写进库）。这是"宿主限制必须被检测并说出"的实例。

## 10.6 B29.11｜尺寸 / 错误 / 预算

`PresentHealth`（无 GPU 依赖，9 个用例）：

| 失败 | 动作 | 预算 |
|---|---|---|
| `Occluded` | 跳过本帧 | 不消耗预算（不是故障） |
| `Timeout` / `Validation` / `Other` | 连续跳过，达 `PRESENT_TIMEOUT_BUDGET=3` 升级为重配 | — |
| `Outdated` | 重配 | `PRESENT_RECOVERY_BUDGET=2` 次后升级为重配→重建 |
| `Lost` / `OutOfMemory` | 重建 | 2 次后 `Stop` |
| `DeviceLost` | 立即 `Stop`（回落 `Default`） | — |

上限保证。**未覆盖**：真机只跑了 resize；最小化/恢复/全屏/跨屏/关窗没有逐项跑（`resize` 的 0 尺寸

## 11.3 画布接线（B29.13 macOS）：先把「能不能接」测出来，再接

**前置事实（读 vendored 源码，不是猜）**：`wgpu-hal 30` 的 Metal 后端用

所以「在 `drawRect:` 里 present」在结构上可行，但会留下一个永久子层。

**接线（`src/render/present/sink.rs` + `src/platform/macos/canvas_present.rs`）**

- `sink::present_window_frame(window, handle, display, frame, size, scale, quality, damage)`
  → `Presented` / `Skipped` / `Unavailable`。画布拿 `Presented` 就不再 blit（同帧一条路径），
  其余情况 blit。
- 目标懒创建、每窗口一个、按**公有窗口 id** 键；创建失败记一次 `Unavailable` 并**不再重试**
  （否则每帧一次适配器探测）。
- 拒绝原因按窗口「变了才记一行」（`log::warn`），不刷屏也不静默。

**三处只有真机才暴露的问题（都已修，都记在计划 B29.13）**

① **首帧必然 `occluded`**：`drawRect:` 第一次运行时窗口还没被合成器显示，Metal 获取被拒。
   处理就是计划 B29.11 的既定策略——本帧跳过、画布 blit，下一帧再试。探针第 0 步拒绝、
   第 1 步成功（`canvas presented 1 frame(s) through the target (step 1)`）。
② **子层不移除 ⇒ 切回 `Default` 会永久停在最后一张 GPU 帧**。第 1 轮「切回 Default 计数不涨」
   只证明了不再 present，**没有**证明画面正确——这是本轮自己发现的漏判。修法：
   `canvas_present::set_presented_layer_visible(view, false)` 在 blit 前隐藏、present 前显示。
③ **TLS 析构里 drop `wgpu` 对象 ⇒ 退出时 abort**。实测栈顶：
   `Entry → FramePresenter → wgpu Surface`，`panic in a destructor during cleanup`，exit 134。
   修法：持有目标表的 `thread_local!` 用 `ManuallyDrop`，presenter 只在 `forget_window`
   （窗口销毁，视图仍有效）时释放；退出时由 OS 回收，任何析构都不再碰它。

**顺带修掉的一个真实缺陷（第 1 轮引入的）**：`cocoa` 后端的 `raw_window_handle` 我上一轮改成
「先翻译到 host」，这会让**挂载 surface 的 canvas id** 解析成窗口内容视图——单个 surface 的帧会
被画满整个窗口。改为「先按自身查、查不到再翻译到 host」，并在文档里写明两个 id 各自的用途。

# 第 4 轮：`Smooth` 的交付路径（presenter 层）真机闭环

## 13.1 为什么需要共用设备

呈现目标必须拥有自己的 `wgpu` 设备：surface 只能在创建设备时与它绑定，换一台设备就画不进去。
而命令流是由 `WgpuRenderer` 的管线画的，它原本 `WgpuRenderer::new()` 自建 instance/adapter/device。
所以「把命令流画进窗口」的前置条件是：**管线能建在调用方给的设备上**。

改动（机械但必要）：

| 改动 | 位置 |
|---|---|
| `WgpuRenderer::from_device(device, queue, adapter_info)`：只建管线，不建设备 | `src/wgpu_backend/renderer/build.rs`（新文件，1328 行） |
| `new_async` 变成「建 instance/adapter/device」+ 调 `from_device` | `frame.rs`（1976 → 708 行） |
| `encoded_target_view()`：把命令流画进的那张纹理暴露成 view | `frame.rs` |
| `FramePresenter::present_commands(&[WgpuDrawCommand])` + `present_commands_and_read_back` | `present/presenter.rs` |

为什么不是「渲染器画自己的纹理、再整帧回读上传」：那会 GPU→CPU→GPU 走一圈，比 `Exact` 更慢，
也就失去了 `Smooth` 的意义。现在的路径是 GPU→GPU：命令流在自己的颜色/模板纹理里画完（管线需要
模板附件，surface 没有），再用一次全屏 pass 贴到 surface 上。

## 13.2 真机证据（两个 macOS 后端）

## 13.3 仍然不能从画布触发 `Smooth`（这是实测结论，不是托辞）

`widget::runtime` 的帧路径硬绑 `SoftwarePaintBackend`：帧/层缓存、损伤重放、`take_frame_rgba`
都在那条路上（`render.rs` 的 `paint_widget_layer` / `paint_widget_direct` 签名就是
`&mut SoftwarePaintBackend`）。没有「把控件树画进任意 `PaintBackend`」的入口，所以画布手上只有
像素，没有命令流；`Smooth` 意图因此仍按 `Exact` 交付。

`Smooth` 用它取流、`census` 判断、`bridge_render_commands` 转换、`present_commands` 交付，

# 第 5 轮（2026-10-30 夜 → 10-31）：把「60 s 空闲零提交」从「代码保证」推到真机计时

本轮的目标只有一个，而且是上一轮自己写下的欠账（§7.7 未完成第 4 条）：
「60 s 空闲计时 / 最小化恢复：判据已由代码保证，未逐项实跑」。
结论是：**那句「由代码保证」在当前形态下不成立**。presenter 的 `Idle` 早退只有
在调用方如实报告损伤时才生效，而画布做不到——真机一跑就暴露了。

## 14.1 真机先红：同一帧被提交了 4 次

上一轮把 `caffeinate -u -t 15` 写进 `tools/run_present_macos.sh`，而探针的空闲观察期是 60 s。
15 s 后显示器睡下去，窗口服务器把窗口判 `occluded`，于是「恢复」那一步红在宿主条件上：

```text
present_smoke: idling for 60 s with no invalidation
present_smoke: FAIL 4 frames were presented while the window was idle (2 before the wait): an idle window must submit nothing
```

把窗口延长到 `-t 180`（显示器在观察期内不睡）之后，「恢复」不再红，但空闲期**第一次真的收到了
AppKit 的曝光重绘**，于是暴露出真正的缺陷：**60 s 内 4 次 present，全是同一帧**。

这不是宿主抖动，而是判据缺了一半：`present` 的早退分支要求「damage 为空」，
而画布只能看到 `drawRect:` 的 dirty rect，不知道内容有没有变。

## 14.2 根因：AppKit 的重绘 ≠ 内容变化

`drawRect:` 会在以下**都不改一个像素**的场合被调用：

1. 曝光（另一个窗口移开、切 Space、`orderFront`）；
2. 遮挡/可见性变化（`occlusionState` 翻转）；
3. 后备存储被回收（窗口长时间在后台）。

这些场合 AppKit 传的 dirty rect 通常是整个 bounds，而 `dirty_row_range` 对
「整视图」和「不可解析」都回答 `None`；`present_through_target` 把 `None` 解释成
「当作全帧损伤」（这是 B29.09 的正确语义：**宁可多传，不可少传**），于是
`present_window_frame` → `mark_full_damage` → 取 surface → 全帧上传 → present。

一条因果链，三个环节都各自正确，合起来就是「空闲也在提交」。

## 14.3 判据：用帧缓存自己的答案，不猜

画布确实**无法**从 `drawRect:` 读懂「内容变了没有」，但它手里的 frame 就是答案：

`widget::runtime::render_frame_tree_cached_shared` / `render_frame_cached_shared` 的行为是

- 内容没变（epoch 未动、尺寸未变、缓存命中）⇒ `return Rc::clone(previous)`，**同一个 `Rc`**；
- 内容变了 ⇒ 新画一帧、`Rc::new`，缓存换新。

所以「同一个 `Rc`」就是「没有一个像素变化」，而且是**画家自己说的**，不是猜的。

### 为什么不是 memcmp

256000 字节的窗口比较一次是微秒级，4K 窗口是 33 MB/次，而 `drawRect:` 在拖动、
动画时是每帧调用 —— 用 `memcmp` 换一个「本来就不该发生」的分支，是拿确定的成本
换不确定的收益。指针比较是 O(1)，且不占额外像素内存。

### 为什么指针比较不会误判

误判只有一种可能：两次**不同**的分配拿到同一个地址。这在本设计里不可能：

- 表 `SHOWN` 持有它用来比较的那一帧，所以那个地址在整个条目生命周期内不会被释放；
- 帧缓存换新帧时，旧帧的 `Rc` 至少还被 `SHOWN` 持有，新分配的地址必然不同；
- 表被 `forget_window`（窗口销毁）显式清理，不会留下跨窗口的旧句柄。

反向的漏判（同一帧被判成新帧）只会导致多一次 present，是安全方向。

### 两个必须存在的细节

1. **只记录成功的帧**：被拒的帧（`occluded` / `timeout`）不在目标上，同样的像素下次必须重试。
   所以 `note_frame_shown` 只在 `WindowPresentOutcome::Presented` 之后调用。
2. **质量档算进身份**：`Exact` 与 `Smooth` 对同一份源码像素会栅格化成不同像素，
   所以同一帧 + 不同 quality 不算命中（否则切换质量会毫无反应）。

# 15. 第 5 轮（续）：B29.10 画布侧取流 —— 把「具名下一步」做成代码

§13.3 写的缺口是：`widget::runtime` 的帧路径硬绑 `SoftwarePaintBackend`，画布手上只有像素、
没有命令流，所以 `Smooth` 意图只能按 `Exact` 交付。§13.3 同时写下了最小切口：
`paint_tree_into(id, size, clear, &mut dyn PaintBackend)`。这一节把它落地。

## 15.1 三个新入口，各有各的理由

| 入口 | 位置 | 为什么需要它 |
|---|---|---|
| `paint_tree_into(id, size, clear, &mut dyn PaintBackend)` | `widget::runtime`（`render.rs`） | 整树直画进任意后端。这是计划点名的切口 |
| `paint_widget_into(id, size, clear, &mut dyn PaintBackend)` | 同上 | 画布对 **mounted surface** 用的是 `render_frame`（只画自己），不是 `render_frame_tree`；两画布都要能取流 |
| `smooth_commands(&[RenderCommand]) -> Result<Vec<WgpuDrawCommand>, SmoothGap>` | `render::present::sink` | 把「普查门 + 桥接」合成**一个无设备可测**的判断，理由写成一句日志 |

交付口是 `render::present::present_recorded_commands(...)`：它先过 `smooth_commands`，再在
**同一个** `with_presenter`（本轮从 `present_window_frame` 抽出来的共享体）里 `present_commands`。
两条交付路径因此共用「建一次目标 / 记住失败 / 先 resize」这一份实现，而不是各写一遍。

## 15.2 为什么 `paint_tree_into` 不接层缓存

层缓存的意义是「没变的子树不重画」。但它的输出是**像素**（`SoftwareSurface` 的层），而复用
一层就等于跳过那次绘制——**命令流里就缺了这段**。命令的消费者没有「跳过」这个概念：它只有
「画这些命令」。所以取流必须整树直画，这是本函数与 `render_frame_tree` 唯一的实质差别，
也是它存在的原因（帧缓存同理：`paint_tree_into` 既不读也不写 `LAST_FRAME`/`LAST_TREE_FRAME`，
调用方可以任意顺序要像素与命令）。

**证据不是断言，是对拍**：

```text
cargo test --lib --features desktop painting_a_tree_into_any_backend
test painting_a_tree_into_any_backend_draws_the_frame_the_tree_path_draws ... ok
```

用例搭一个三层嵌套树（父级 `children_clip` 裁剪子级、子级再挂一个偏移的孙级），
把 `paint_tree_into` 的输出与 `render_frame_tree`（**带**层缓存的那条路）**逐字节比较**。
它同时钉住四件事：根先画、子节点顺序、裁剪继承、帧原点平移。

## 15.3 门禁与回落：一次都不能「大概对」

计划 B29.10 的原文是「`Smooth` 帧内出现任一 `ForcesCpu` ⇒ 整帧走 `Exact`（不混用两条路径）」。
代码里是两个门，顺序固定，理由都具名：

1. **普查**（`census`）：有任一 `ForcesCpu` ⇒ `SmoothGap`，理由形如
   `1 command(s) force the CPU (DrawText)`；
2. **桥接**（`bridge_render_commands`）：第一个转不过去的命令 ⇒ `SmoothGap`，
   理由是该命令的下标与变体名。

拒绝时画布**不丢帧**：同一份像素立刻走逐字节路径 `present_window_frame`。所以
「`Smooth` 不可达」的后果是**质量档没满足**，不是**画面坏了**——这是两条路径共用一个帧缓存的
直接好处。回落每窗只记一行（`note_smooth_fallback`，理由变化时才记），并可用
`smooth_fallback_reason(window)` 查；命令路径有自己的计数器 `presented_command_frames(window)`，
它与像素计数器分开，因为两者回答的是不同问题。

`examples/present_smoke.rs` 新增第三阶段：建一个**没有子控件**的窗口（窗口自身的 chrome 是
最小的真实树，也是今天唯一有机会走通 GPU 的那一种），设 `Smooth`，请求重绘，然后三种答案：

```text
present_smoke: canvas delivered N frame(s) as draw commands (Smooth)     → 命令路径真的上线了
present_smoke: SKIP(smooth-unbridged) … ({reason})                       → 具名回落，不是失败
present_smoke: FAIL the Smooth intent neither delivered commands nor said why   → 才是不合格
```

之所以要有第三种（FAIL）分支：`SKIP` 只能是**有理由**的，否则「什么都没发生」会伪装成跳过。

# 16. breprs 协同核实（3D 内核 + UI 宿主）

本节回答用户提问：「breprs 的 wgpu 也使用了 L1~L3 多级渲染，请核实一下」——
**核实结果是：该前提不成立**。下文行号均为对 `~/Desktop/workspace/breprs` 现行源码实地读取。

## 16.1 breprs 的 L0~L3 是 CPU 线程档，不是渲染分级

| 事实 | 证据 |
|---|---|
| `L0/L1/L2/L3` 标题写明是 CPU 性能档 | `breprs/src/platform/mod.rs:13` `# CPU performance tiers (L0 / L1 / L2 / L3)` |
| GPU 能力独立检测 | 同文件 `:19` `GPU capability is detected independently — see GpuTier`；枚举 `:595`，默认 `GpuTier::None` |
| L0~L3 只决定线程数 | `:298-306` `tier_threads()`：`L1Low => host.min(2)` / `L2Middle => host/2` / `L3High => host` |
| 3D 上屏是单 pass 单 present | `src/gpu/rendering.rs:293 render_frame()` → `:297 get_current_texture()` → `:323` 一次 `begin_render_pass` → `:383 queue.present` |

结论：breprs 的 wgpu 路径**没有**「多级渲染 / 分层上屏」。

⚠️ 命名撞车：本库 blue29 §0 的 `L0~L3` 是**决策层**（质量意图→交付面→成本门控→回退），
与 breprs 的 CPU 线程档毫无关系。3D 软件文档中必须带库名前缀（`rw:deliver-L2` / `breprs:perf-L2`）。

## 16.2 主从裁定：breprs 配合本库

依据是「谁已经拥有不可让渡的资源」，不是偏好：

| 能力 | breprs | 本库 |
|---|---|---|
| `raw-window-handle` | **0 命中**（连依赖都没有） | 全平台后端 |
| surface | `rendering.rs:126 with_surface(config, surface: Surface<'static>)` 只被动接收；字段 `:73 surface: Option<Surface<'static>>` | presenter 自建 + 平台画布接线 |
| 事件循环 / 输入 | 无 | 已有 |
| 损伤/遮挡/空闲零提交 | 无 | B29.11/B29.12 已真机 |
| present 策略 | `:154 present_modes[0]`（直接取第一个） | `AutoVsync` + `fallback_present_mode` |

因此：**breprs = 几何/算法内核（无窗口、无 surface、无事件循环、不上屏）；本库 = 宿主与唯一 present 方。**

## 16.3 硬约束：必须共用同一台 Device/Queue

本库已经写死过这条结论——`src/render/present/presenter.rs:388-394`：

> handing the commands to a second renderer with its own device — cannot work, because a swapchain
> texture belongs to the device that created it.

两库现在各自建 device（breprs `rendering.rs:77/83/94`；本库 `FramePresenter::new`），
但**版本一致**（`wgpu = 30.0.1`：`breprs/Cargo.toml:164`、本库 `Cargo.toml:905`），
且两边都已有借设备先例：本库 `presenter.rs:689 WgpuRenderer::from_device`、
breprs `src/gpu/surface_acceleration.rs:100 with_device(Arc<wgpu::Device>)`。
**缺的是入口，不是能力。**

|---|---|---|
| `DrawRectStroke` → 现有 `StrokeRect` | `(3,3)` 期望 200、实际 255 | 参考的矩形描边是**居中**线刷（向外扩 `w/2`），`StrokeRect` 的带在内部；不是同一形状 |
| `DrawLine` → 现有 `DrawLine` | 同上（刷子偏移 +1、1px 被扩成 2px） | 旧变体的刷子几何与参考不同，不能映射 |
| `FillRoundedRect` → `Mapped` | 角部期望 241、实际 255 | 参考在角上是 2×2 覆盖率抗锯齿，GPU row span 是硬边；降为 `MappedWithDivergence`（§1.2 C） |
| `DrawPath` → `Mapped` | 边界像素期望 255、实际 200 | 扫描线与 GPU fan 的边界包含规则不同；降为 `ForcesCpu`（见 17.3） |
| `DrawImage` → `Mapped` | 半透明像素 126 vs 127 | 1 LSB 合成差；降为 `MappedWithDivergence`（§1.2 B） |
| `DrawImageScaled` → `DrawImage` | 期望 76、实际 95 | 参考走**双线性** `draw_image_quad`，GPU 图像管线是最近邻；不能映射 |

这就是原则 #19 想要的顺序：**先让测试说不行**，再决定是修映射还是改分类，而不是先写"应该可以"。

## 17.2 新增的两个 GPU 载体（不是"只改分类"）

`WgpuDrawCommand` 增加三个变体，全部有 CPU 参考实现与 GPU 管线实现：

| 变体 | 为什么必须新增 |
|---|---|
| `StrokeRectCentered` | 四条边按参考的 `draw_line_with_width` 刷子（`cx - w/2`, `w × w`）逐印戳展开；旧 `StrokeRect` 的带在内部，差一像素 |
| `DrawLineCentered` | 同上，单段；使 1px 线与 3px 线都逐字节相同 |
| `DrawTextCoverage` | 承载**已 shaped** 的文字覆盖度。旧的 `DrawText` 按固定 8×8 网格排字，比例字体会错位 |

`DrawTextCoverage` 的覆盖度由 `render::text::coverage` 生成：

1. `shape_line`（与软件面同一个 shaping）；
2. `TextMetrics::for_font`（同一个行盒）；
3. 每个 cluster 用 `paint_active_at_weight` 画进 `advance × line height` 的格子；
4. `glyph_coverage_byte` 应用与软件合成器相同的 sRGB 覆盖度斜坡。

因此 GPU 只做「覆盖度 × 颜色 + source-over」，字形、间距、行盒都不重写（原则 #101）。

**半透明矩形类命令（顺带修掉的真 bug）**：rect 管线是 `REPLACE`，直接写会丢掉 dest；
而桥接此前把半透明 `FillRect` 归为 `Mapped`，GPU 会把 `[20,30,200,160]` 原样写入（对拍发现 95 字节差）。
现在 alpha < 255 的 rect/line/rounded/arc 都走 offscreen run，`BLEND_COMPOSITE_FS` 的
straight/premultiplied 分支补上了 `blended*a + dest*(1-a)` 与 alpha 合成；不透明命令仍走直接路径。

## 17.3 分类与对拍（逐个家族的判据）

| 家族 | 分类 | 对拍证据 |
|---|---|---|
| `FillRect` / 剪贴 / 混合状态 | `Mapped` | 原有用例 + `a_bridged_rectangle_frame_paints_the_same_bytes_on_the_gpu` |

## 18.1 先红后绿：两次被测试否决/钉住的映射

本轮沿用上一轮的做法：先写对拍，让错的映射变红，再改实现。

**① 虚线描边的笔刷宽度（红 → 绿）**

`DrawPathDashed` 的参考实现（`paint.rs:850`）是把折线交给 `for_each_dash_segment`，再对每段调用
`draw_line_with_width`。桥接时我把宽度误写成 `*width + 1`（模拟「笔刷差一」这类错），测试立刻变红：

```text
frame differs in 219/6144 bytes; first at Some((3, 5, 255, 30)) (x, y, expected, actual)
assertion `left == right` failed: open: a dashed stroke must match the reference
```

恢复 `*width` 后逐字节相同。这条实验的作用是证明这个用例**不是空转**：它确实比较了每一个像素。

**② 填充折线的填充规则（红 → 绿）**

`DrawPath { filled: true }` 的参考实现是 `fill_polygon` → `fill_scanlines(.., FillRule::EvenOdd)`。
我先把它映射到 `FillPathNonZero`（non-zero，几何同样是一把扇），用五角星（中心被穿越两次）做判据：

```text
assertion `left == right` failed: the bridged fill must keep the even-odd rule, not the non-zero one
  left: [30, 120, 210, 255]     ← non-zero 把中心五边形画上了
 right: [255, 255, 255, 255]    ← 参考（even-odd）中心是空的
```

改成 `WgpuDrawCommand::DrawPath { filled: true }`（后端那个 `even_odd: true` 的变体）后转绿。
**这条映射不能靠「看起来差不多」决定**：它差的是整块区域，不是边缘一像素。

## 18.2 六个家族的对拍判据

`the_dashed_antialiased_and_filled_arc_families_match_the_reference`（GPU 实跑，不是模拟）：

| 家族 | 判据 | 实测 |
|---|---|---|
| `DrawPathDashed`（开/闭，宽 1/2） | 逐字节 | 0 字节差 |
| `DrawPath`（描边，开/闭） | 逐字节 | 0 字节差 |
| `DrawPath`（填充，五角星） | 中心必须为空 + 差异只在多边形边界 2 px 内 | 111 字节差，全部在边界带 |
| `DrawLineAA` | 参考必须有软边（非空转）+ 每字节差 ≤1 LSB + 差异只落在软边像素上 | 132 个软边像素，54 字节差，worst 1 |
| `DrawLineStrokeAA`（宽 3） | 同上 | 186 个软边像素，136 字节差，worst 1 |
| `DrawArc { filled: true }` | 差异只在扇多边形边界 2 px 内 | 28 个扇顶点，90 字节差 |
| `BoxShadow`（blur 0，含负偏移/扩散） | 逐字节 | 0 字节差 |
| `BoxShadowRounded`（blur 0） | 差异只落在圆角 rim（SDF |d| ≤ 1.5） | 84 字节差 |
| `BoxShadow`（blur 4） | **必须拒绝** | `classify` = `ForcesCpu`，`bridge` 返回 `Err` |

「差异只在边界」用的是**距离**而不是颜色谓词：`distance_to_polygon_boundary` 计算像素中心到扇边界
最短距离，`rounded_rect_signed_distance` 计算到圆角矩形边界的带符号距离。这样写的好处是：
一个把中心也画错的映射无法靠「颜色恰好一样」蒙混过关（18.1 ② 已实证）。

| 家族 | 已有的载体 | 为什么够用 |
|---|---|---|
| 虚线 / 折线描边 | `DrawLineCentered` | 参考就是逐段 `draw_line_with_width`；上一轮已证逐字节 |

## 18.4 端到端：真机命令路径（第 6 轮欠的那一格）

第 6 轮的 `Smooth` 阶段新建一个窗口，本机窗口服务器把它长期报成 `occluded`，于是探针只能报
`SKIP(host-limited)`——**那是关于窗口的答案，不是关于命令流的答案**。本轮把探针改成驱动
「刚刚用像素路径成功上过屏的那个窗口」，并且把「流可画但 surface 拒绝」按 `last_refusal` 具名报成
`SKIP(present-refused)`。

结果两个后端都拿到了窗口级证据：

```text
present_smoke: smooth phase set intent=Smooth
present_smoke: canvas delivered 2 frame(s) as draw commands (Smooth)
    cocoa: PASS
    objc2: PASS
run_present_macos: PASS (failures: none; per-backend skips are named above)
```

被交付的那棵树**带一个标签**（`wired`/`smooth: a`），所以这一格证明的不再是「空窗口的 chrome 能上 GPU」，
而是「真实控件树的取流 + 桥接 + 上屏」整条链。这一格同时闭合 §7.8 的「命令路径真机证据未取得」
与 §7.9 的「wired phase 因 occluded 报 SKIP」。

**副产物（诚实记下）**：第一次改完探针，`Smooth` 阶段报的是
`SKIP(present-refused) ... (occluded)`——因为当时它还在新建的窗口上跑。这条输出本身就说明
`present_recorded_commands` 已经把流交给了 presenter（否则会报 `smooth-unbridged` 并给出类名），
只是 surface 拿不到。换成驱动已上屏的窗口后就不再出现。

## 18.5 性能：本轮没有更快的路径，只有更少的回落

- `DrawPathDashed` / `DrawPath`（描边）：不再逐命令回落 `Exact`，**整帧**得以留在 GPU；代价是桥接时
  多做一次展开（与参考同一个 kernel，段数相同）。
- AA 线：CPU 侧仍要按参考的采样栅格算覆盖度（与参考同价），省下的是**合成**与**回读**；
  掩码有 4 M 像素上限（`LINE_COVERAGE_LIMIT`），超过就具名回落——不拿一次巨型分配赌性能。
- 无模糊阴影：`FillRect` 走实例化矩形管线，比 `Exact` 的软件填充便宜。
- 缓存与测量无变化（第 6 轮的覆盖度缓存、tooltip 单次测量仍是本轮的性能基线）。
