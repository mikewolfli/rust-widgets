## 根因与实现

### 原有问题

1. `Icon` 将每条 outline contour 独立提交为 `DrawPath`。软件后端逐轮廓做奇偶填充，SVG 后端也为每轮廓发出独立 `<path>`；后绘制的内轮廓会覆盖应为空的 counter。
2. 既有扫描线填充在每一行新建交点 `Vec`；旧 polygon 填充存在随扫描线重复分配的热点。
3. `Icon` 的既有字符串 setter 无法表达“已解析的静态几何”，直接注册几何又会错误依赖有容量限制的名字注册表。

### 交付

- 在 `render::core` 增加 `CompoundPath` 和分类构造错误。构造时检查轮廓至少 3 点、范围有效、非空且不重叠；旧 `DrawPath` 语义不变。
- 增加 `RenderCommand::FillPathNonZero`，贯通立即软件后端与 SVG 后端。软件路径以 winding 方向决定填充，并在多行之间复用交点缓冲；SVG 将复合轮廓序列化到一个 `<path fill-rule="nonzero">`。
- 为独立的 `WgpuDrawCommand` 增加同名非零填充分支、轮廓范围错误返回和孔洞/非法范围测试；另新增 `src/wgpu_backend/bridge.rs`，将 `FillPathNonZero`、clip push/pop 和 blend mode 转为独立 WGPU 命令。桥接边界外的 `RenderCommand` 会显式报 unsupported；这仍不是完整 `PaintBackend`/GPU shader 执行接线。
- 新增 `IconSource::{Builtin, StaticGeometry}`。`Icon` 可读写 typed source；typed Builtin 不再把 token 重复分配到旧字符串字段，getter 按需返回规范 token。调用旧 `set_icon` 会清除 typed source，clear 会清除 typed 与旧字符串状态，避免旧值重新生效。自有静态几何不经注册表。
- 内置图标与 fallback 几何按复合路径一次提交；解析/提交失败有日志。更新 Icon census 与 SVG 导出，增加暗/亮 `icon_info` counter 基线。
- 按复合 path 的新序列化语义修正 Rating、底部导航栏的 SVG 测试断言；修正 Linux IME 一条与同文件公开契约相冲突的旧测试（契约是“已聚焦且已连接”，不是仅有焦点即 active）。

### 尚未交付

- 尚无独立 `IconRef` / `IconPaintOptions` 或统一借用式绘制与测量 API；静态内容之外的共享几何/共享像素来源也未实现。
- 尚无 flatten 缓存、连续帧分配基线/门禁或跨 100 个消费者的共享成本实测。本轮不声称已满足 U1/U2 的性能目标。
- 未将 U1 API 接入按钮、ToolButton、Action、菜单、集合、导航、JSON/view、生成器或原生平台。
- 本轮生成和验证的是 Icon 相关 SVG 快照/普查，不构成方案要求的完整平台视觉矩阵。

### 本轮新增实现

- 继续为 `DropdownMenu` 增加按当前 item index 设置 typed `IconSource` 的 API。索引不存在时返回带 `index`/`len` 的 `IconItemError`；绘制时 typed source 占用原图标列、增加真实图形输出；传入 `None` 可回到旧文本图标。

### 续记（2026-10-12，U5 结构化描述接线）

#### 实现

- 新增持久化 `IconSpec::{Builtin, Resource}` / `IconColorMode`，并保留运行时 `IconSource` 与描述层的职责边界。普通属性 setter 没有资源 resolver 时拒绝 `Resource`，运行时 `StaticGeometry` 的反射读取返回不可持久化错误；不把资源 ID 当路径，也不为运行时几何伪造资源身份。
- 在 capability value/kind、Button/ToolButton/Action 的属性 get/set/schema/default、JSON strict object parser、manifest round-trip、designer Builtin 生成与 Resource unsupported 报告、C ABI 和 Python/Node 编码路径接入 IconSpec。Manifest 协议升为 3；读取较旧版本的兼容路径保留。
- C ABI 新增 `RW_VALUE_ICON_SPEC = 10`，描述 wire 编码为 `builtin|name` 或 `resource|color_mode|escaped_id`；资源 ID 中 `%` 与 `|` 使用 `%25` 与 `%7C`。生成头文件通过生成器同步。
- 首轮完整 Rust 测试暴露 ToolButton schema 和 Button 默认值表漏项；补齐后通过完整库测试。首轮 ABI 测试因示例头文件未重新生成失败，按既有生成流程更新头文件后通过。Python ABI 测试最初把无 resolver 的 Resource 拒绝误判为失败，修正断言为 Builtin 往返成功且 Resource 明确拒绝后通过。
- 为 `view` 补充真实 Node diff → Patch apply 测试：Builtin 描述写入成功；Resource 写入在错误报告中保留 `ResourceResolutionRequired`，且不会覆盖已应用的 Builtin 值；移除声明会生成 Null reset 并清空来源。
- 对 Action JSON 同时声明旧 `icon_text` 与新 `icon_source` 的情况增加冲突检测：两项都不应用，避免依赖 JSON key 顺序由最后写入者静默胜出。该检测只作用于控制属性契约同时发布这两个字段的控件。
- JSON setter 和值 kind 转换失败现在分别记录属性名、输入值与底层错误/转换阶段；loader 的外层拒绝提示改为中性诊断指引，不再把所有失败都错误归因于类型错误或只读属性。
- profile 门禁发现 `ToolBox` 的 icon tile helper 仍被 `image` cfg 包住，但新的静态 `IconSource` 在无 `image` profile 也会走同一绘制分支。移除不再正确的 cfg，并将样式推导单测扩展为不依赖 `image` 的测试；同时把仅供 designer generator 使用的 JSON 转换 helper re-export 限定到 `designer` feature，清除了 tablet/mobile 中新增的 unused-import 警告。

#### 兼容性及明确边界

- `CapabilityValue` 与 `PropertyValueKind` 是公开 enum；新增 `IconSpec` 变体会使外部 exhaustive match 需要更新。应在发布说明中标为源码兼容性变更，并仅在适用的主版本窗口发布；本轮不擅自修改 crate 版本号。
- `IconSpec::Resource` 的显式解析接入 `JsonLoader::load_with_icon_resolver`、`view::apply_with_icon_resolver` / reserved+overlay 变体，以及 `ViewEngine::mount_with_icon_resolver` / `update_with_icon_resolver`：宿主提供 resolver，将稳定资源 ID 和颜色模式解析为真实、已验证的 `IconSource`；解析发生在借用目标控件之前，失败进入 JSON property rejection 诊断或 view 错误报告且不覆盖原图标。默认 JSON `load`、普通 capability setter 和默认 view API 仍拒绝 Resource；尚无权限策略、异步结果版本冲突处理或跨入口资源矩阵。
- `IconResourceResolver` 是内容解析契约，不把 ID 当路径，也不自行伪造像素/动态几何；颜色模式的具体支持由 resolver 决定，unsupported 必须以错误返回。当前 drawable 输出仍限于已有 `IconSource`，没有共享像素或异步资源对象。
- 新增 view 测试覆盖资源更新成功、resolver 明确失败且保留既有来源、以及插入子树声明属性时恰好调用一次 resolver。读取解析后的 Builtin 值通过控件 capability getter 验证。
- Node 绑定运行时探针尚未通过：本机缺少 `ffi-napi`。未安装依赖，也未通过语法检查冒充运行时覆盖。
- Records schema 缺少互斥/one-of 约束，不能完整表达 Builtin/Resource union；此次采用显式结构化 value variant，而非把 JSON stringify 成 String。Resource 的生成暂报告 unsupported，不生成假 setter。

### 续记（2026-10-12，容器/标签/分段控件的图标死状态收口）

#### 本轮发现的问题

对 `src/widget/` 做「声明了 icon 字段但整文件没有任何 icon 绘制调用」的结构化扫描（脚本按行匹配 `*icon*` 字段声明并检查 `paint_icon`/`draw_icon*`/`draw_image` 是否出现），得到唯一命中集合。据此确认三处 **真实死状态**（字段可设、从不绘制，且文档声称会绘制）：

1. `ContainerWidgets::TabWidget` 的 `Tab::icon: Option<Image>`：有 setter/getter，draw 从不读取。
2. `ContainerWidgets::MdiArea` 的 `MdiSubWindow::icon: Option<Image>`：同上。
3. `MiscWidgets::SegmentedButton` 的 `Segment::icon: Option<String>`：文档写「displayed as a simple geometric shape」，实际从不绘制。

另有一处 **以文字冒充图标**：`NavWidgets::TabView` 把 `TabPage::icon` 直接 `format!("{} {}", icon_name, title)` 插进标题，于是 `icon: Some("settings")` 绘出的是字面单词 `settings`，正是方案 §19.5 禁止的「通过显示文字回查图标」。

`DisplayWidgets::EmptyState` 的 `icon: String` 走文本通道（默认 emoji），本身不是死状态，但属于 §19.5「其他内容」迁移项。

#### 本轮交付

- **共享解析重构（先去重，再接线）**：`draw_icon_named` 的「名字 → 图标」解析被抽成 `resolve_named_icon`，新增 `icon_token_is_drawable(name) -> bool` 作为**测量侧**判据。绘制与占位测量从此读同一份解析，不会各自漂移（原则 #23）。`NamedIcon::Outline` 变体与对应 match 臂按 `#[cfg(any(feature = "icons", widgets_unstripped))]` 精确门控，与 `draw_outline_in` 同条件——无轮廓路径的构建里该变体「不可表示」，而不是「存在但未用」。
- **`Tab`**：新增 `icon_source: Option<IconSource>` 与 `set_icon_source`/`icon_source`/`clear_icon_source`/`has_icon`。typed source 与旧 `Image` 是**同一个活动状态**（后设者胜、互相清除），`clear_icon_source` 两种形式一起清，避免清空后被旧值复活。`set_icon` 在赋值时把非 RGBA8 图一次性归一化为 RGBA8（`icon_source::normalize_rgba8_image`，与 MdiSubWindow 共用同一 helper），因此绘制路径只借用字节，不做逐帧转码。
- **`TabWidget`**：`set_item_icon_source(index, Option<IconSource>)`，越界返回 `IconItemError::IndexOutOfBounds { index, len }`（该集合只有位置身份，不为此私造第二套选择模型）。draw 在标题带前保留 `TAB_ICON_SIDE + TAB_ICON_GAP` 的图标槽，typed source 走 `paint_icon`、旧 `Image` 走借用 RGBA8 的 `draw_image`；`tab_width_hints` 对带图标项加同一额度，**测量与绘制同源**。
- **`MdiSubWindow`**：新增同形的 typed source 与活动状态规则；`MdiArea::set_item_icon_source(ObjectId, ...)` 复用该集合**已有的**稳定身份（子 `ObjectId`），缺失返回 `ItemNotFound`、重复返回 `AmbiguousItemId`。图标在**两种呈现**里都绘制：`SubWindowView` 的标题栏与 `TabbedView` 的页签，共用一个 `draw_subwindow_icon` 自由函数，因此两种视图不会对「该画哪个」产生分歧。
- **`TabView`**：`TabPage::icon` 改为「先按图标解析、解析不到才按旧文本前缀」。解析成功时绘制 glyph 并把标题带右移，解析失败时行为与原来逐字一致（emoji/符号不丢）。`tab_widths` 用 `icon_token_is_drawable` 加同一额度，所以预留宽度与实际 glyph 一致。由于 `TabPage` 字段是**公开**的，按 §19.6 不在此引入 typed 条目模型（推迟到明确的不兼容版本）。
- **`SegmentedButton`**：`Segment::icon` 从死状态变为真实绘制；glyph + gap + 文案作为**一个整体居中**，所以新增图标不会把文案挤离中轴。未知名字串沿用 crate 既有「已知 token 绘 glyph、否则绘文字」约定，而不是静默丢弃。
- **`EmptyState`**：`icon` 命中本 crate 的图标 token 时绘制几何，否则保持原文本通道（默认 emoji 不变）。预留的 `icon_height` 盒不变，因此整栈布局不受影响；`draw_icon_named` 返回 false 时回退文本，不出现静默空白。

#### 本轮发现的问题

- 方案 §19.2 指出的 U2 缺口「从现有解码缓存取得内容时复用其共享条目」仍未闭环：`image::cache` 只提供 `file_rgba8_or_none -> Arc<Vec<u8>>`，**尺寸被丢掉**。`ToolButton::resolved_icon` 因此只能在注释里写明「decoded extent is dropped」，并且把像素再存一份到控件自己的 `Arc<Vec<u8>>` 字段里。
- 同一原因导致第二处缺陷：由于不知道源图宽高，图标只能被**拉伸**填满预留槽（方案 §19.4 明确要求「非正方形图片默认保留宽高比，不拉伸」）。这不是新来源才有的问题，旧的 `set_icon(path)` 路径一直如此。

#### 本轮交付

- **缓存保存并返回尺寸**：`PixelEntry` 增加 `width`/`height`（与 `bytes` 一样旁挂，缓存本身就是「控件取走像素后唯一还记得尺寸的地方」），`insert_pixels`/`get_pixels` 随之携带尺寸。新增 `pixels_rgba8_sized_or_none` 与 `file_rgba8_sized_or_none`；旧的 `pixels_rgba8_or_none`/`file_rgba8_or_none` 保留原签名，改为薄包装，因此 `avatar` 等既有消费者零改动、零行为变化。缓存记账（`used_bytes`、LRU、逐出计数）不变。
- **共享句柄从缓存零拷贝构造**：`SharedIconPixels::from_cached_bytes` / `from_cached_file` 直接包装缓存自己的 `Arc`，只做尺寸校验；校验失败**记录错误**而不是静默 `None`（否则会与「文件不存在」混淆）。`from_cached` 为私有收口，两个公开入口共用。
- **统一 fit 规则**：新增 `icon_source::fit_image_into(source_w, source_h, slot)`（`contain` + 居中）。`SharedIconPixels::fit_into` 委托它。正方形源图 + 正方形槽的返回值与槽**完全相同**，所以对现存每个图标都是字节级无变化；非正方形源图不再被拉变形。
- **ToolButton 去重并接线**：`icon_pixels` 字段由 `Option<Arc<Vec<u8>>>` 改为 `Option<SharedIconPixels>`，`resolved_icon()` 改走 `SharedIconPixels::from_cached_file`。像素现在是**缓存的那一份分配**，而不是每个按钮再存一份；宽度/高度也不再被丢弃。两条像素路径（显式共享句柄、旧路径解码）都改为按 `fit_into` 绘制，不再各自决定如何填槽。
- **TabWidget / MdiSubWindow 的旧 `Image` 槽**同样改用 `fit_image_into`，因此「把这张图放进这个图标槽」在本 crate 只有一条规则（原则 #23）。

#### 兼容性说明

- 正方形图标的输出与改动前完全一致（`fit_into(slot) == slot`），`check_svg_snapshots.sh` 全绿亦证实无提交快照受影响。
- 非正方形图标的输出由「拉伸变形」变为「等比适配」，这是方案 §19.4 明确要求的行为；本记录不把它说成 bug-for-bug 兼容。为此新增的定点断言直接读 SVG `<image width= height=` 属性，确认 8x4 图在槽内保持 2:1。

### 续记（2026-10-12，旧 `Image` 图标槽与 typed 清除语义的同类收口）

#### 本轮发现的问题

把上一轮的结构化扫描推广到「旧图标字段是否真的被绘制」与「typed setter 的清除语义」，发现同一类缺陷的另外三处，且都能复现为可视差异：

1. **`TabBarTab::icon: Option<Image>` 是死状态**。`compute_tab_width` 只对 `icon_source.is_some()` 计入图标宽度，`draw_tab` 也只绘制 typed source——旧 `Image` 既不计宽也不绘制，而且 `TabBar` **没有任何 API 能设置它**（`TabBarTab` 公开、有 `pub fn new`，却无法插入到 `TabBar`）。
2. **`ToolBoxItem::icon: Option<Image>` 会画出假图标**。draw 里 `has_legacy_image` 参与布局（占出图标格），但绘制分支是 `if let Some(source) = item.icon_source { .. } else { 画一个"代表性小圆点" }`。于是 `set_icon(Some(image))` 的结果是：图标格被占、里面画的是装饰圆点，**调用方设的图从未出现**。
3. **`set_icon_source(None)` 不能清除旧槽**：`TabBarTab`/`ToolBoxItem` 都写作 `if source.is_some() { self.icon = None; }`，所以显式清除会留下旧 `Image`。这与方案 §19.6「用户明确清除：变 Empty，绝不能继续保留上次图标」直接冲突，也与 `Button`/`MenuButton`/`Tab`/`MdiSubWindow` 已确立的语义不一致。
4. **`RibbonItem::set_icon_source` 不回退旧文本**：`Action`、`Fab` 都在 typed set 时 `icon_text.clear()`，只有 `RibbonBar` 不清；于是「set typed → clear typed」会把更早的文本图标复活，违反「最近一次显式设置生效」。已核对 `Fab` 的 `icon_text` 同样是**有初始种子**（`"+"`）的字段，因此「清种子」不是 `RibbonBar` 独有的取舍，而是本 crate 的既有规则。

同时确认这**不**是问题的一类：`BottomNavigationBar`/`AdaptiveScaffold`/`NavigationDrawer`/`Cupertino`/`PieMenu`/`MenuButton` 使用 `item_icon_sources: Vec<Option<IconSource>>` 作为**presentation 覆盖**、缺省回落到条目自身内容。这正是 §19.6 推荐的兼容阶段做法（「类型化覆盖作为明确的 presentation 状态」+「旧 add/replace/update 对该条目的 typed presentation 有明确清除或替换规则」），且 `add/insert/remove/clear` 都同步维护该向量。故本轮**不**改动它们，并在记录中写明理由，避免后人按「index 侧表一律要拆」误改。

#### 本轮交付

- 新增共享绘制接缝 `widget::draw_icon_image(context, &Image, slot) -> bool`（`#[cfg(feature = "image")]`）：一条规则处理「旧 `Image` 图标槽」的归一化后用、按 `fit_image_into` 适配、逐帧借用不转码；不可绘制（非 RGBA8/空）返回 `false` 而不画替身。
- **`TabBar`**：新增 `Tab::has_icon()`；`set_icon_source` 去掉 `is_some()` 守卫并真正清旧图；`set_icon` 在赋值时归一化；`compute_tab_width` 与 `draw_tab` 改用 `has_icon()` 并新增旧 `Image` 的绘制分支；补 `tab(index)`/`tab_mut(index)` 访问器，使旧图标字段**可达**（与 `TabWidget` 的同名访问器一致）。
- **`ToolBox`**：新增 `ToolBoxItem::has_icon()`；`set_icon_source` 无守卫清旧图；`set_icon` 归一化；draw 用 `has_icon()` 布局，并把「代表性小圆点」占位分支替换为真实 `draw_icon_image`——该占位分支在两条来源都处理之后已不可达，故删除而不是保留死分支。
- **`RibbonBar`**：`set_icon_source` 同步 `icon_text.clear()`，与 `Action`/`Fab` 同一规则。

### 续记（2026-10-12，集合条目 `icon_source` 的结构化落盘通道（U5/U6））

#### 本轮发现的问题

方案 §19.10 要求「增加结构化 `icon_source` 属性」，而条目级 typed 图标此前只有方法入口。逐层追查后发现真正阻断点不是控件，而是**两处转换层**：

1. `src/json/properties.rs::records_from_json` 显式拒绝 `Value::Object`/`Value::Array` 行字段（注释写「no control declares one today, so it is refused rather than guessed at」）。于是即使某个控件的行 schema 声明了 IconSpec 字段，文档里的 `{"kind":"builtin","name":"info"}` 也进不来——记录层读不到，控件再完整也无用。
2. `src/designer/generator.rs::record_field_expr` 同样只接受标量，因此生成器会把这样一行报成「not a record list」缺口，与 loader 行为不一致（正是 B26.02 禁止的「两个前端描述不同控件」）。

同时 `records.rs::value_matches_kind` **已经**支持 `PropertyValueKind::IconSpec` 字段，说明缺口只在「谁把 JSON 对象变成那个值」这一层。

#### 本轮交付

- **`records_from_json` 按声明 kind 读取复合字段**：新增 `declares_icon_spec_field(schema, name)`，仅当该行的 schema 明确把该字段声明为 `IconSpec` 时才把对象交给 `icon_spec_from_json`；其它复合值仍拒绝。判据是**声明**而非 JSON 形状，所以把对象塞进声明为 `String` 的字段依旧被拒。
- **带 schema 的转换入口**：新增 `to_capability_value_with_record_schema(value, kind, record_schema)`；原 `to_capability_value` 委托它并传 `None`，**所有既有调用点与测试零改动**。属性 apply 路径与生成器预检改为传各自已查到的行 schema。
- **生成器按 schema 发射**：`record_field_expr(value, name, schema)` 对 IconSpec 字段发射 `CapabilityValue::IconSpec(IconSpec::Builtin(IconName::from_name("info")...))`；resource 描述不发射而返回 `None`，由调用方按既有规则记成生成缺口，不写出无法兑现的程序。
- **`Chip` 条目 typed 图标（端到端）**：`CHIP_ITEM_SCHEMA` 增可选 `icon_source: IconSpec`；`Chip` 以**条目稳定 id** 为键持有覆盖（`item_icon_sources: Vec<(String, IconSource)>`），`set_items` 会剪掉已消失 id 的覆盖，避免「删除后重建同 id 继承旧图标」；新增 `set_item_icon_source(id, Option<IconSource>)` / `item_icon_source(id)`；`get("items")` 把图标写进记录，`set("items")` 用文档为准重建覆盖（缺字段即「没有图标」）；`chip_width` 计入图标额度、draw 在标签前绘制 glyph，两者同源。
- **`IconItemError` 增两个字符串身份变体** `UnknownItemId` / `DuplicateItemId`：`MenuItem` 的 id 是数字、chip 的 id 是宿主文本，这是两种真实身份；把数字载荷拓宽成字符串会强迫现有调用方转换它们本来就正确的类型。因此 `IconItemError` 由 `Copy` 改为仅 `Clone`（携带 `String`）。

### 1. U1：`measure_icon` / `validate_icon`（方案 §19.4 / §19.3）

方案 §19.4 要求「测量与绘制必须使用同一尺寸/比例规则」，§19.3 要求校验分**两阶段**（源验证 / 准备-绘制验证）。此前 crate 只有 `paint_icon`（第二阶段）与 `draw_icon_named` 的 `bool`（测量侧），测量与绘制各写一份方框推导。

#### 交付

- **一条方框规则**：新增私有 `glyph_box(slot)` = `contain` + 正方形 + 居中，并让 `draw_outline_in` 与 `draw_fallback_in` **都**经由它。此前 `IconPlacement::new(rect.x, rect.y, rect.width as f32, grid)` 用 `slot.width` 驱动**两个**轴，于是 40×12 的槽会画出 40×40 的图标——比调用方预留的盒子高 28 px，靠后端的裁剪兜底。crate 内所有控件传的都是正方形槽（`Icon::icon_rect`、`ToolButton::icon_rect`、`TAB_ICON_SIDE`、`SUBWINDOW_ICON_SIDE`、`CHIP_ICON_SIDE`、分段/标签槽），因此对它们**行为不变**，对未被覆盖的非正方形情形是修复。
- **`IconMetrics { bounds, source_extent }`** + **`measure_icon(source, slot) -> Result<IconMetrics, IconPaintError>`**：调用方在绘制前就能知道内容落在哪。空槽测量为空（`IconMetrics::is_empty()`），**不是**错误——`paint_icon` 对空槽回答 `SkippedEmptySlot`，同理不使用失败表示「没地方」。无几何的源才是错误（`EmptyGeometry` / `UnsupportedSourceForProfile`），避免把「源坏了」当成「没有空间」。
- **`IconSourceMetadata { grid, contour_count }`** + **`validate_icon(source) -> Result<IconSourceMetadata, IconPaintError>`**：只做**第一阶段**，即源的属性——grid 非零、每个 `d` 可解析（同时拒掉非有限坐标与解析器不表达的特性）、轮廓数落在 `MAX_OUTLINE_CONTOURS` 内且至少 1。
  - **明确不承诺**：**点数**预算不是源的属性——展平器按固定设备容差细分曲线，所以 24 px 能过的源在 400 px 可能超预算；而一个整体小于一个像素的源在 24 px 根本不产生轮廓，却是完全合法的数据。两者都归 `paint_icon` 按实际尺寸报告（`InvalidGeometry` / `EmptyGeometry`）。轮廓数**是**源属性（每条 `d` 子路径一个，不被设备取整改变），所以在此检查。
- 新增 `IconPaintError::ZeroGrid`：宿主构造的 `IconData` 可以带 `grid: 0`，展平器把它当零缩放（不 panic，但会把整幅轮廓塌到一个点）；命名它之后校验报告能说清**为什么**，而不是笼统说「空」。
- `paint_icon` 的 Builtin 回退分支改成**诚实结果**：`draw_fallback_in` 返回 `false`（两张表都不认识该 token）时返回 `Err(EmptyGeometry)`，不再无视返回值假装 `Drawn`。§19.4 明令「不把 false 同时用于空槽/未知名/失败」，而原实现把「什么都没画」报成了「画了一个图标」。

### 2. 注册表详细拒绝原因（方案 §19.8）

方案 §19.8：「原 API 返回 bool 无法附完整原因；可以新增详细 try-register 接口，旧 bool wrapper 保留，同时按标准诊断规则暴露拒绝原因。」

## 续记（U2 峰值/预算证据 + 全仓 test-code warning 清零）

### 1. U2：共享句柄真的共享缓存分配（I03）+ 缓存预算是真实上界

`tests/image_decode_cache_test.rs` 此前只验证「12 个工具栏按钮只解码一次」与「预算为 0 时每次都解码」。本轮补齐方案 §19.13 I03 所要求的「创建后 clone 不深拷贝数据」与「缓存预算稳定」的**字节级**证据：

- **三处入口必须指向同一份分配**：`file_rgba8_or_none`（无尺寸）、`SharedIconPixels::from_cached_file`（有尺寸）与 `SharedIconPixels::from_shared_rgba8`（包装前者）三者取得的是**同一个** `Arc`。判据是 `Arc::ptr_eq`（`shares_allocation_with`），不是「看起来一样」；并顺带断言尺寸（1×1）穿过这条接缝没有丢失——这正是 U2 新增尺寸通道要保证的事。
- **预算是有 teeth 的上界**：以「恰好一条 1×1 RGBA8 条目」为预算，连续请求 4 种**不同颜色**（不同内容 → 不同缓存键，因此真的会产生 4 个条目）后，`stats().bytes` 始终 `<= 预算`，且 `evictions > 0`。`evictions > 0` 这一条是关键：它排除了「实际上什么都没存所以没超」的假通过。
- **零预算不等于失败**：预算为 0 时句柄仍能构造（宿主宁可花 CPU 也不花内存是合法配置），只是无法共享。
- 新增夹具 `coloured_png(rgba)`：用 crate **自己的编码器**产出真实 PNG，而不是手工拼字节——手写的 deflate 流「看起来对」但在 inflater 里会失败，这是该文件既有注释已经记下的教训。

### 3. 关于 `measure_icon` 的消费者（记录判断，避免后人误判为死代码）

`measure_icon` 是方案 §19.4 指定的公开测量入口。**crate 内没有把它接进现有控件的布局**，这是**有意**的，理由如下：

- crate 内所有控件的图标槽本来就是正方形（`Icon::icon_rect`、`ToolButton::icon_rect`、`TAB_ICON_SIDE`、`SUBWINDOW_ICON_SIDE`、`CHIP_ICON_SIDE`、分段/标签槽），而 `draw_outline_in`/`draw_fallback_in` 已统一经由 `glyph_box`，所以"绘制落在哪"已经只有一处答案；把这些控件改成调用 `measure_icon` 会产生**零可观测变化**的重构（还要为一个本来没有 `Result` 的推导引入 `Result` 分支），风险大于收益，属于用户明确禁止的「跑偏」。
- 它的真实价值在**非正方形槽**——也就是宿主直接调用公开 `paint_icon` 的情形，此时 `measure_icon` 是唯一能事前知道内容落在哪的途径。
- 它的正确性由**像素级**断言保证（不是消费者数量）：`measure_icon_is_square_contain_and_matches_where_the_glyph_is_drawn` 把 glyph 画进 64×40 表面，要求每个非透明像素都落在测量报告的方框内；去掉共享 fit 规则后该断言实测失败（`ink at (36, 25) escapes the measured box 24..36 x 20..32`）。

### 交付

新增 `tests/icon_source_equivalence_test.rs`（含两行版权头），实现方案 §19.13 的 I01「同一个 Builtin 用于 Icon、Button、ToolButton → 同色同尺寸 glyph 一致」。

**做法**：每个入口都与**共享绘制器**比较，而不是与其他入口比较（两个同样错法的控件彼此也会「一致」）。对每个控件：

1. 用同一个 `IconSource::Builtin(Save)` 赋给控件；
2. 把控件渲染成 SVG，取出**图标几何**——判据是后端自己的溯源标记：复合图标填充是唯一带 `fill-rule="nonzero"` 且**不带** `data-text` 的元素（`SvgPaintBackend` 的 `DrawText` 分支给轮廓文字打 `data-text` 标签），因此不靠「命令字母像不像图形」猜；
3. 用该控件**自己发布的槽**（`Icon` 的几何、`Button::icon_rect()`、`ToolButton::icon_rect()`）调用 `paint_icon` 生成参照；
4. 两份顶点列表都平移到首顶点为原点后**必须完全相同**；
5. 额外断言**包含性**：顶点跨度必须落在声明的槽内，所以控件不能画出它预留的范围。

比较只针对**顶点**，颜色不参与——§19.4 把着色归控件，各控件按主题解析自己的墨色，因此参照调用传常量不影响结论。

末尾另有一条真·跨控件断言：把 `Icon` 与 `ToolButton` 都做成 16 px 槽（后者本就是 `TOOL_BUTTON_ICON_SIZE`），两者顶点列表必须相等。

### 本续记的方法论要点

这是本次会话第三次遇到「门控报出的是假缺陷」（前两次是 `declaration_alignment_census` 陈旧、a11y 生产者模式陈旧）。三例的共同特征是：**失败信息的指向与真实原因之间存在一层未被检查的间接**（陈旧产物／旧方法名／旧允许清单）。处理方式一致：先在**最靠近判据**的一层取证据（错误码、产物时间戳、git 历史、独立 worktree 复算），再决定改代码还是改规则；三例最终都不是代码回归。

缺口是实打实的，而且是方案自己点名的：§19.3.1 说现有 census 与快照「两套断言都检不出这个缺陷」，因为 census 记的是 `info contours=4 ink=4` —— 其中 `ink = contours` **是一行赋值**（`examples/icon_census.rs` 原文 `let ink = contours;`），它不是一个测量，孔被当成独立墨迹。测试侧只有 C5 对 `info` 的**一个像素**做检查，方案要求的「带孔 token 的 ink 段数」全局断言不存在。

### 实测基线（先量后改）

用一次性探针（已删除）在 24px、`desktop,icons` 下对全部 69 个 token 量了三件事：着色像素数、中线不透明段数、以及「逐轮廓填充会画而环绕填充不画」的像素数。

```text
info      contours=4  painted=154  runs=3  plug_risk_px=108
settings  contours=3  painted=204  runs=3  plug_risk_px=10
mail      contours=4  painted=182  runs=3  plug_risk_px=84
star      contours=2  painted=129  runs=2  plug_risk_px=4
user      contours=4  painted=129  runs=0  plug_risk_px=8
fullscreen contours=4 painted=84   runs=0  plug_risk_px=0
TOTAL plug_risk_tokens=33  plug_risk_px=1784  mismatch_px=0
```

两个关键事实：

1. **`mismatch_px=0`**：把 SVG 后端发出的复合路径解析回来，用**独立的交叉数环绕实现**逐像素（跳过距边 <1px 的像素）与软件后端实际像素比对，69 个 token 全部一致。这是「像素就是环绕填充」的直接证据，而不是「共享了同一个函数」的间接证据。
2. **`plug_risk_px=1784`（33 个 token）**：逐轮廓填充会比环绕填充多画 1784 个像素——换成旧实现，这 1784 个像素就是被盖掉的孔。抗空洞断言有了真实的分母。

方案 §19.13 I16 点名的四个环状 token 在两种量法下都成立：`runs` 分别为 3/3/3/2（实心圆盘会是 1），且各自 `plug_risk_px > 0`。

### 交付

**1. census 生产者改测量（`examples/icon_census.rs`）**

`ink` 从「`contours` 的副本」改为**软件后端实际着色的像素数**，并新增 `runs`（中线不透明段数）：

```text
info	contours=4	ink=154	runs=3	sha256=b8911437...
star	contours=2	ink=129	runs=2	sha256=79274591...
settings	contours=3	ink=204	runs=3	sha256=867ae081...
mail	contours=4	ink=182	runs=3	sha256=b23aeb4a...
```

两个字段各管一件事：`ink` 是「有没有画」（C1/C4 的判据，`contours` 那条只是重复 C1），`runs` 是「画成一个环还是画成一个盘」——它对读者可肉眼核对，而实心圆盘缺陷在**像素总数**上只表现为变大，在 `runs` 上表现为 3→1。文件头写明 `ink` 为什么必须是测量、`runs=0` 是什么意思（中线不穿过图形，如 `user`/`fullscreen`，由 `ink` 兜住）。

**2. 测试侧三条新证据（`tests/icon_census_test.rs`）**

* `C5` 从「`info` 一个像素」扩为「方案点名的四个环状 token 中线必须 ≥2 段」＋原有像素检查，并断言这四个 token 都在 census 里（否则断言会静默变成空转）。

* 文件头把「C1–C4 为什么看不见这个缺陷」逐条写明（4 个轮廓两种实现都是 4；四张图两种实现都互不相同；census 对自己一致；覆盖检查两种实现都通过）。

**3. 重生成 `tools/icon_census.txt`**：69 行全部更新（列由 4 变 5）。

`tools/check_profiles.sh` 在 [6b/9]（windows-msvc 交叉）失败，错误落在 C 编译而非 Rust：

取证（不猜）：

3. 它不影响图标工作，也不是被掩盖的假缺陷：`check_profiles.sh` 的 [1/9]–[9/9] 都跑完了，只有矩阵最后一项红。

这是上一轮 `glyph_box`（正方形 contain 居中）的**真实后果**，而上一轮把它描述成「对所有控件行为不变」。读代码核对：`Stepper` 的 mark 槽是 `inset = min(w,h)/4` 从 48×44 的按钮里抠出来的 → **26×22，不是正方形**，所以新规则把字形从 26px 缩到 22px 并居中。**上一轮那句「每个控件传进来的槽都已经是正方形」是错的**（原则 #18：文档必须与代码一致），注释已按事实改写，并写明这一个可见变化与其理由。

顺带核对新输出是否正确（不是「变了就算」）：

```text

minus 条 y 59..61 中心 60  = 按钮 38..82 中心 60     ✓ 垂直居中（旧输出 y 61..63 中心 62，偏低 2px）
plus  条 x 208..220 中心 214 = 按钮 190..238 中心 214 ✓
```

### 1. 工具链：xwin splat 让 `--target x86_64-pc-windows-msvc` 真正可编译

本机原本的状态（上一条续记记过）：`cc --target=x86_64-pc-windows-msvc -c probe.c` 报

`clang-cl`/`llvm-lib` 来自 Homebrew LLVM（`/opt/homebrew/opt/llvm/bin`，默认不在 PATH 上）。

这是这一步存在的意义（脚本自己的注释写过：「hundreds of lines of Windows backend code that no job
had ever compiled」）。24 个错误 / 1 个 warning，分布在 6 个文件：

```text
11 error[E0433]: cannot find `runtime` in `widget`        （types.rs 里对 widget::runtime 的引用）

 4 error[E0433]: cannot find `canvas` in `super`          （types.rs / platform_impl.rs）
```

根因与上一条续记里 `mini,macos` 的**同一类**：`windows/mod.rs` 已经把 `canvas` 模块按

同时记录一个方法论发现：**在这台 macOS 上，`mini,<backend>` 矩阵看不到 Windows 后端的代码**——
`--features mini,windows` 的 `target_os` 仍是 macOS，`platform/windows/**` 整体被 cfg 掉，
所以它一直是「通过」。只有真正带上 `--target x86_64-pc-windows-msvc` 的这一步能看见，
这也正是 xwin 必须打通的原因。

### 4. 修法：沿用文件里已有的模式，按 profile 如实收口

没有发明新机制，而是把作者已经用在 `WM_KEYUP`/`WM_SETFOCUS`/`set_widget_visible` 上的模式补全：

* `types.rs`：给 11 个 arm 加 `#[cfg(widgets_unstripped)]`（`WM_PAINT`、鼠标 6 个、`WM_MOUSEWHEEL`、
  `WM_MOUSELEAVE`、`WM_KEYDOWN`、`WM_CHAR | WM_UNICHAR`、`WM_SIZE`）——编掉后由 `_ => DefWindowProcW`
  接管，即「没有树可路由」时的诚实答案；`WM_CLOSE` 只把**回调路径**编掉，窗口照旧关闭；
* `types.rs`：10 个「每个调用者都在上述 arm 里」的函数/常量随之同条件编掉
  （`paint_window_tree`、`window_widget_for`、`widget_id_by_native_handle`、`invalidate_window`、
  `forward_window_mouse/wheel/char`、`paint_target_for`、`MOUSE_PRIMARY`、`use MousePhase`）；
* `types.rs`：消息常量 import 按「只会被编掉的 arm 匹配」拆成两条——否则 stripped profile 上是
  **未使用 import**，而「未使用 import 对下游 `-D warnings` 消费者就是构建失败」；
* `platform_impl.rs`：`SW_HIDE/SW_SHOW` 只在 `set_widget_visible` 的 gated 体里用，import 同条件；
* `ime_windows.rs`：`tsf` 是**嵌套模块**，子模块不继承父模块的 `use`，所以 `Box` 必须在 `tsf` 里
  自己 import（先加在父模块没用——编译器立刻回报「unused import」，这条线索正好确认了原因）。

### 1. 16 处相邻重复的 `#[cfg]` 属性（扫描类 A：属性块重复）

扫描方式：对 `git ls-files '*.rs'` 的每个 item **属性块**（连续的 `#[…]` 行）统计重复字符串。

```text
$ (python3 扫描，输出 item 起始行 + 重复次数)
benches/event_bench.rs:1   2x #[cfg(not(target_arch = "wasm32"))]
benches/event_bench.rs:35  2x …
benches/event_bench.rs:38  2x …
benches/layout_bench.rs:1 / 43 / 46
benches/render_bench.rs:1 / 123 / 127 / 132 / 136
benches/signal_bench.rs:47 / 205 / 219
src/widget/capability/properties.rs:2325  2x #[cfg(not(alloc_frugal))]
src/widget/mod.rs:353                    2x #[cfg(widgets_unstripped)]
total items with duplicate attrs: 16
```

修法：一个"删除与**紧邻上一行**完全相同的属性行"的脚本——它只可能合并两个**完全相同**的
属性（不相同的永不相邻），因此不会误删 `#[cfg(a)] #[cfg(b)] #[cfg(a)]` 这类合法组合。结果：

```text
benches/event_bench.rs 3, benches/layout_bench.rs 3, benches/render_bench.rs 5,
benches/signal_bench.rs 3, src/widget/capability/properties.rs 1, src/widget/mod.rs 1
6 files changed, 16 deletions(-)          # 只有删除，没有插入
重新扫描 → remaining: 0
cargo check --benches --no-default-features --features desktop → Finished
```

为什么值得修：相同条件 AND 之后语义不变，所以这不是行为缺陷；但重复属性会让**任何按文本
扫描 cfg 的工具报告该 item 两次**，并把真正的授权行埋在噪声里。`src/widget/mod.rs` 那一处尤其
典型——它是回答「stripped profile 上 `Icon`/`paint_icon` 还是不是 public」时读者要看的那一行，
却是两个久远的提交（`56bd371c3` 与 `a16b389d0`）各加了一次。

### 2. §19.8 的验收句此前没有任何用例（扫描类 B：方案原句 vs 现有测试）

## 续记（U5/§19.10：给独立 `Icon` 控件补上 typed `icon_source` 属性）

### 1. 扫描发现：`Icon` 是唯一「存了 typed 源却没有属性通道」的控件

方案 §19.5 把「独立图标 `Icon`」列为第一类接入项，§19.10 要求「增加结构化 `icon_source` 属性」。
对全仓做一致性扫描（把每个模块的 public item 逐个对账、把「存了 `icon_source` 字段的控件」与

```text

发布 icon_source 属性    ：Button / Action / MenuButton / ToolButton / Fab        ← 缺 Icon
```

`Icon` 是**唯一**缺口：它持有 `Option<IconSource>`、有 `set_icon_source`/`clear_icon_source`、
绘制也走 `paint_icon`，但属性契约里只有 `icon_name`（一个 `String`）。后果是文档/designer/JSON
**无法给一个 `Icon` 指定 typed 源**，只能给旧名字串；已有测试
（`a_control_with_no_hand_written_arm_loads_via_the_factory`）正好用 `{"icon": {...}}` 从文档
构造 `Icon`，所以这条通道是真实可达的，不是理论缺口。

### 2. 交付

* `ICON_PROPERTIES` 增 `icon_source: IconSpec`（`properties_other.in.rs`）；
* `capability_by_kind` 的 `WidgetKind::Icon` 分支给默认值 `Null`（与另外五个 owner 同形）；
* `Icon` 的 `get`/`set`/`property_names` 增该属性：`Builtin` 写入并回读；`Resource` 无 resolver
  时返回 `ResourceResolutionRequired`；`StaticGeometry` **读取时**返回

  与「`Icon` 只有一个活动图标状态，清 typed 源同时清旧名字」的既有 setter 规则一致；

## 续记（用户指令「这个 matrix 太慢了，请清理审查后再重新跑」）

### 1. 先证伪最容易的假设（事实驱动，不猜）

「慢」第一直觉是 `target/` 太大（实测 **133 GB**：`debug/incremental` 42→50 GB / 2042 个会话、
`debug/deps` 51 GB / 116242 个文件、`debug/examples` 4.6 GB）。但**量一下就不是它**：

```text
$ /usr/bin/time -p cargo check --no-default-features --features mini   # 已 fresh，纯指纹开销
Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.06s
real 0.09
```

no-op 0.09 s ⇒ 目录体积不是主因（它只是磁盘风险）。所以继续找真实成本。

### 2. 真正的成本：门控的**缓存键**

`tools/lib_cargo_cache.sh` 的 `_rw_cargo_cached` 每个步骤都要先算 source digest（**命中也要算**，
因为键要先算才知道命不命中）。实测：

```text
$ bash -c '. tools/lib_cargo_cache.sh; time _rw_source_digest'
real 8.623s          # 2814 个文件 / 1104 MB
```

`check_profiles.sh` 一次跑 ≈ 25 个 `rw_cargo_cached` 步骤 ⇒ **纯算键就 ~3.5 分钟**，而
`run_all_gates.sh` 会跑更多这样的脚本。两个真实缺陷：

1. **剪枝清单漏了 `.xwin-cache/`**。它是 **1.0 GB** 的 MSVC 下载缓存，被一次 cwd=仓库的 `xwin`
   调用重新生成在**仓库内部**（`.gitignore` 里已经写明它是「downloaded .msi/.cab/.vsix blobs,
   **not source**」，且全仓无人读它）。旧剪枝清单只有 `target`/`.git`/`.venv`，于是这 1 GB 每次
   都被 `cat` 进 sha256。
2. **循环里每个文件 fork 一个 `cat`**。macOS 上约 2 ms 一次 ⇒ 1900 个文件 ≈ 4 s。

### 3. 修法（都在门控里，不动被测代码）

* 剪枝清单加 `.xwin-cache`，并把**为什么判据不受影响**写进注释：真正喂给编译器的是 **splat**
  ——一个**外部**路径（`XWIN_SPLAT` / `~/xwin-splat`），它的位置已经通过「导出的环境变量」
  参与键值；下载缓存的内容不可能改变 `cargo` 的判定。
* 把「逐文件 `cat`」换成**一条 `xargs -0 cat` 批次**；同时把**文件名列表本身**也放进摘要流，
  所以**改名**依旧会使键失效（不是只比内容）。

```text
$ bash -c '. tools/lib_cargo_cache.sh; time _rw_source_digest'
real 0.127s          # 1923 个文件 / 39 MB      ← 8.623s → 0.127s（68×）
```

### 4. 正确性证明（摘要必须仍然"会失效"，这是这个文件唯一不能出错的性质）

```text
deterministic:                        YES
new untracked file detected:          YES
content change detected:              YES
rename detected:                      YES
restore returns the original digest:  YES
a change inside a pruned cache does not change the digest:  YES
```

缓存往返也实测（第一条是真跑 cargo，第二条是命中并**打印**了复用行，保持可审计）：

```text
--- first call  --- real 0m0.895s     Finished `dev` profile …
--- second call --- real 0m0.177s     (cargo result reused from cache: cargo check …)
```

（副作用：键值集合变了，所以修好后的**第一次**整轮必然是冷跑；这是设计使然，不是回归。）

### 5. 顺带发现并清理的仓库卫生问题：一个**已提交**的 4.5 MB Linux ELF

审查摘要输入时按体积排序，发现仓库根有一个 `rust_out`：

```text

$ grep -rn rust_out  (全仓)          → 零引用
$ git log --diff-filter=A -- rust_out
8e1f0ed6 code review                 # 8f0f 提交里被误提交
```

它是 `rustc` 不带 `-o` 时的默认输出名，属于「误提交的构建产物」这一类。处理：从索引与工作树
一并移除（`git rm --cached` + `rm`，保留删除作为可提交的变更），并把 `rust_out` 加进
`.gitignore` 已有的「Stray lint/build dumps」小节——那一节本来就在处理同一个类（`clippy_output.txt`），
所以这是**补同类的漏**，不是新规矩。同时删掉仓库内那 1.0 GB 的 `.xwin-cache/`（仓库自己的先例：
`docs/log/log-20261007-1.md` 记过「验证后已删除 … 工作树无残留」）。

### 6. 重跑结果（用户要求的「重新跑」）

```text
$ time bash tools/check_profiles.sh          # 冷跑（键全变，cargo 也冷）
[1/9] … [9b/9] 全过；All profile checks passed.
real 2m17.8s
$ time bash tools/check_profiles.sh          # 热跑（23 个步骤命中缓存）
23 行 "cargo result reused from cache"；All profile checks passed.
real 0m40.3s
```

对比修订前：同一脚本超过 4 分钟仍未结束（当时被中止），且**每一步**都要先付 8.6 s 的算键成本。

#### 6.1 一次 17 分 33 秒的离群值：先量时间，再判断归属

修好之后又出现过一次 `real 17m33.8s`。按"先证伪、再归属"的规矩，先看 CPU 时间：

```text
real 17m33.8s   user 2m7.1s   sys 1m48.5s      ⇒ 约 4 分钟在干活，约 13.5 分钟在**等待**
```

`user+sys` 只有 4 分钟，说明这 17 分钟**不是**门控在算（也不是编译），而是**外部阻塞**
（构建目录锁竞争或同一台机器上的其他 I/O）。两点独立证据：

1. 换成带时间戳重跑，**每一步的输出间隔都是 1 秒级**：

```text
[12:22] [1/9] …  [12:23] [2/9] …  [12:24] [3/9] …  [12:26] [6a/9] …  [12:27] [6b/9]（windows 交叉，真跑）…
[12:28] [7/9] [12:28] [8/9]  ← 这一步 36 s（check_view_platform_gate + check_view_keys_are_unique）
[13:04] [9/9] [13:05] [9b/9] [13:06] All profile checks passed.
```

2. 紧接着连跑两次，稳定复现：

```text
run 1: real 39.55  All profile checks passed.  cache replays: 0
run 2: real 39.32  All profile checks passed.  cache replays: 0
```

结论：**17m33s 不可复现，不是门控或被测代码的问题**，本轮的修复本身是把每步的固定成本从 8.6 s
降到 0.13 s。

#### 6.2 为什么上面两次是 0 次缓存命中（并被记录为设计后果，不是缺陷）

门控缓存键包含源码摘要，而**本日志文件自己也在摘要范围内**——我在写日志的同一时间段里跑门控，
所以每次写入都让键失效。于是"边写日志边跑"的现实成本是 **~40 s**（cargo 热、门控冷），
而 2m18s 是"改过 `.rs` 之后第一次跑"的真实成本。这是摘要"保守"的**设计后果**（该文件自己写明：
它做的不是跳过工作，而是不重复输入相同的工作），本轮**没有**借机把 `docs/` 移出摘要——
`docs/` 没有被证明对每个门控都是非输入，而"陈旧结论"恰好是这个缓存唯一不能犯的错。

### 7. 记录一个本轮自己踩的坑（避免后人重犯）

第一版把带反引号的注释搬进了 `$( … )` 里，`bash -n` 直接报
`unexpected EOF while looking for matching '`——命令替换内部的扫描与成对反引号互相干扰。
修法是把注释留在**函数体层级**（与原文一致），让 `$( )` 里只剩那条管道。这个坑不值得写进注释，
但值得写进日志：`bash -n` 是这类改动的第一道门，改完先跑它。

### 8. 磁盘现状（已报告，未擅自删）

`target/` 仍占 133 GB，其中 `debug/incremental` 50 GB（2042 个会话）明显是无界增长。本轮**没有**
删它：它是合法的缓存，删掉只会让**下一次**编辑-编译变慢（而它并不影响本轮要修的"matrix 慢"）。
诚实记录：若要收敛磁盘，应加一条 `cargo clean` 策略（例如按 profile 保留最近若干会话），
这属于独立的清理任务，不在 blue27 范围内。
