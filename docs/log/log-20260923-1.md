## 2. P0-5 `visual_focus` + `FocusReason`（从零设计事件层）

BLUE22 §E.7-10 指出：`FocusReason` 全仓 **0 命中**，且计划只写了函数签名、
**没写它从哪个事件字段来** ——「这是 P0-5 的真实工作量」。本轮补上这段施工细则。

### 2.1 设计：reason 必须随事件走，不能事后查询

```rust
// src/event/types.rs
pub enum FocusReason { Pointer, Tab, BackTab, Shortcut, Programmatic }
impl FocusReason {
    pub fn draws_focus_ring(self) -> bool;   // Pointer => false
    pub fn is_keyboard(self) -> bool;
}

pub enum Event {
    FocusGained { reason: FocusReason },     // 原为 unit variant
    ...
}
```

**为什么是载荷而不是 `current_focus_reason()` 查询**（本轮的关键决定）：
控件必须在**处理事件的那一刻**决定「要不要画环」，而绘制发生在更晚的帧。
一个共享查询在当时可能已经在描述「另一次移动」了。这与原则 #97
（「已发布不等于会响，差异必须可查询」）同源 —— 但这里的差异是**时序性**的：
查询得到的是「现在」，控件要的是「我为什么被聚焦」。

### 2.2 三条入口，reason 各不相同

| 入口 | reason | 画环？ |
|---|---|---|
| `focus_on_pointer_press(id)` | `Pointer` | ❌ |
| `focus_next(forward)` | `forward ? Tab : BackTab` | ✅ |
| `focus_on_keyboard_activation(id)` | `Shortcut` | ✅ |
| `focus_widget(id)` | `Programmatic` | ✅ |

`focus_widget(id)` **保持原签名**（内部转发 `Programmatic`），既有调用点零改动
—— 这是原则 #21「不破坏现有 API 签名」的具体执行。

### 2.3 焦点环几何（共享原语，不是控件各自算）

```rust
pub const FOCUS_RING_WIDTH: u32 = 2;
ControlMetrics::focus_ring_rect(rect)   // 内缩 2px，保证不画出矩形外
ControlMetrics::focus_ring_radius(r)    // 同步收窄，方角保持方角
```

**为什么画在里面**：本仓不把子控件裁剪到布局槽内，所以画在矩形外的环会盖住邻居
—— 工具栏上控件只隔 `spacing` px，那个重叠是看得见的。Qt 的 `focusFrame` 是向外撑的，
那是因为它有裁剪；本仓没有，所以取反。

### 2.4 按钮接入（`button.rs`）

| 新增/改动 | 说明 |
|---|---|
| 字段 `focus_reason: FocusReason` | 与 `focused` 并列（对应 Qt 的 `activeFocus`/`visualFocus`） |
| `visual_focus()` | `focused && focus_reason.draws_focus_ring()` —— **单一判定点** |
| `focus_ring_color(bg)` | 主题有 `outline` 就用它，否则取背景的反色。**不再与 border 同色**（修 BLUE21 §七 B） |

## 3. P0-6 / P0-7 按钮交互契约（`released` != `clicked`）

按 BLUE22 §6.4 的四段契约重写 `EventHandler`：

| 事件 | 结果 |
|---|---|
| press（primary、enabled） | 取 grab，`pressed=true`，发 `pressed` |
| move | `pressed = contains(point)`（**跟随指针**） |
| release（内含） | `pressed=false`，发 `released` + `clicked` |
| release（外） | `pressed=false`，发 `released` + **`canceled`**，**不发 `clicked`** |
| ungrab（失焦 / 禁用） | 清 grab，`pressed=false`，发 `canceled` |

### 3.1 发现并修复的关键缺陷：`pressed` 不能同时当「画笔」和「归属」

第一版只加了 `contains(point)` 判定，测试立刻变红：

```text
dragging back must restore pressed
```

**根因**：`MouseMove` 的臂写成 `if self.pressed`，而「拖出」已经把 `pressed` 置了 false
⇒ **那条本该恢复状态的 move 被自己挡住了**。

**两类事实被混为一谈**：

| 事实 | 载体 |
|---|---|
| 「该不该画凹陷」 | 跟随指针进出 —— 是 `pressed` |
| 「这次手势归不归我」 | 从 press 到 release 一直为真 —— 需要**另一个位** |

这正是 Qt 的 `explicitDown` / grab（`qquickabstractbutton_p.h:31-32`）分开的原因。
本轮新增 `grabbed: bool` + `cancel_gesture()`：

```rust
pub fn press(&mut self)   { self.grabbed = true; self.set_pressed(true); }
pub fn release(&mut self) { self.grabbed = false; self.set_pressed(false); }
pub fn cancel_gesture(&mut self) { ...发 canceled... }   // 唯一的「取消」定义点
```

`cancel_gesture` 被多条路径共用（失焦、禁用、未来 ungrab），
**避免各写一遍漂移出几种「取消」**。

### 3.2 `MouseLeave` 的裁定（一个必须想清的分岔）

| 方案 | 后果 |
|---|---|
| A. leave ⇒ 取消手势 | 拖出后拖回**无法**完成；用户拿不回按钮 |
| B. leave ⇒ 只清 `pressed`，保留 grab | 拖回可恢复，release 落点决定结果 |

**选 B**，与 Qt `handleMove` 一致（`pressed` 随 `contains(point)`，grab 不动）。
`MouseLeave` 在指针刚越界时就触发，此时取消等于宣告「拖出即作废」——
而平台惯例（以及 Qt/Flutter）都是**以 release 落点为准**。

### 3.3 顺带修的两个同类问题（冰山法则）

| 缺陷 | 证据 |
|---|---|
| **`Button` 不筛鼠标键** ⇒ 右键也触发动作，而右键是宿主开上下文菜单用的 | CheckBox/RadioButton 均已 `button == 1`，Button 是离群者 |
| **`Button` 不做命中检测** ⇒ 直接派发的 press 会武装 latch | 新增 `button_activates()` |

键位也收敛为具名函数 `is_keyboard_activation(key)`（`13|10|32`），
不再在每个控件里各写一遍数字。

### 3.4 定点验证

```text

running 59 tests ... test result: ok. 59 passed; 0 failed
```

**本轮新增 9 条**（全部钉住契约的**否命题**，与第 65 轮 §9.6-10 的教训一致）：

## 4. P0-10 `Colors` 扩面 + `Default`

### 4.1 新增 7 个角色（全部带 serde 默认值）

| 角色 | 修什么 |
|---|---|
| `outline` | 焦点环与分隔线不再同色（BLUE21 §七 B） |
| `outline_variant` | 次级分隔 |
| `scrim` | 暗色主题下遮罩**变亮**而不是变黑（BLUE21 B23） |
| `surface_container` / `_high` | 卡片/面板与背景分层 |
| `inverse_surface` / `on_inverse_surface` | 反色表面 + 在其上的墨 |

照抄 `info` 的现成写法：`#[cfg_attr(not(alloc_frugal), serde(default = "fn"))]` +
`const fn default_*() -> Color`（`#[cfg(not(alloc_frugal))]`）。

### 4.2 新增 `impl Default for Colors` —— **这是让「加角色」变便宜的关键**

BLUE22 §E.3 指出：加一个角色要改**每个 `Colors { .. }` 字面量**，
而字面量数量无界。这就是「色彩角色面一直停在 11 个」的机制原因。

修法：补 `Default for Colors`，并把两个预设改为**结构体更新语法**：

```rust
// Theme::default()
colors: Colors { background: ..., primary: ..., ..Colors::default() },
```

⇒ 下次加角色的改动面变成：`struct` 一行 + `default()` 一行 + `dark()` 一行（若需要）。
`Default` 也断言了**每条字段都必须有可渲染值**，不留 `Color::default()` 的透明黑。

### 4.3 `SemanticColor` 刻意**不**扩

`SemanticColor` 的注释明说是**状态**令牌的闭集（info/success/warning/error），
并由 `every_semantic_token_is_reachable` 守住。新增的 7 个角色是**结构性**的
（分隔、遮罩、表层），不是「状态」—— 把它们塞进状态闭集会让「状态」这个概念失真。
**这是有意的不扩，不是遗漏。**

### 4.4 两个 profile 都已同步

`src/style/theme.rs` 的 `Colors` 镜像（无 device profile 时的替身）同样加了 7 个字段，
否则 `mini`/`embedded` 编译失败。

## 5. P0-8 状态过渡原语 `Transition`（一处分摊到所有控件）

### 5.1 问题：同一个推导正在被第 N 次重写

`Button` 已经内联了约 50 行「插值一个 0→1 进度」的代码，其中包括引擎回调所有权
要求的 `Rc<Cell<_>>` 舞蹈。开关要加动画、复选框要加悬停过渡，若各自再写一遍，
就是同一推导的第 3、4 份拼写 —— 正是规则 #101 命名的失败形态。

### 5.2 新增共享原语（`src/style/animation.rs`）

```rust
pub enum TransitionTempo { Fast, Normal, Slow }   // 对应主题的 Motion 令牌
impl TransitionTempo {
    pub fn duration_ms(self, theme: &Theme) -> u32;
    pub fn easing(self, theme: &Theme) -> EasingFunction;
    pub fn reverse_easing(self) -> EasingFunction;   // 反向各自一条曲线
}

pub struct Transition { progress: f32, tempo: TransitionTempo }
impl Transition {
    pub fn new() -> Self;
    pub fn with_tempo(tempo: TransitionTempo) -> Self;
    pub fn progress(&self) -> f32;
    pub fn reset_to(&mut self, progress: f32);
    pub fn tick(&mut self, target: f32, delta_ms: u32) -> bool;   // 全仓 tick 契约
}
```

三条设计要点，每条都对应一个真实缺陷形态：

| 决定 | 理由 |
|---|---|
| 时长**每帧**从主题读 | 主题中途切换时，在途过渡按新节奏收尾，而不是被旧节奏困住 |
| 目标由**调用方每帧给出** | 悬停途中按下 ⇒ **重瞄**同一进度而非从零重启（一次动作而非两次淡入） |
| 前向/反向**各自一条曲线** | 反向用前向的 `EaseOut` 会让值**慢慢离开**，读起来像卡顿 |

### 5.3 开关接入（P0-8 真的动起来）

`Switch` 新增 `travel: Transition`（`Slow` = 300ms），并把**绘制**与**逻辑**分离：

| 字段 | 含义 | 对应 QML |
|---|---|---|
| `checked` | 逻辑状态，用户动作**立即**改变 | `position` |
| `travel.progress()` | 绘制状态，手柄滑动的位置 | `visualPosition`（`qquickslider.cpp:395`） |

轨道颜色也由 travel **混色**（`off_track.blend(&on_track, travel)`），所以轨道变色与
手柄滑动是**同一个动作**。`travel = 0` 时结果与旧外观逐像素相同 ⇒ **未 tick 的快照不变**。

## 6. P0-2 三个验证控件 + 形状统一

按 BLUE22 §9.1「先 3 个验证再铺开」，本轮完成 `switch` / `radio_button` / `progress_bar`
三个，并把它们的**几何推导全部改为走共享原语**。

| 控件 | 改动 | 原缺陷 |
|---|---|---|
| `switch` | 轨道 `ControlMetrics::center_in(rect, SWITCH_TRACK)`；thumb = `SWITCH_THUMB_RADIUS*2` | 三处独立常量（`52`/`32`/`2`）与 `size_hint(50,28)` 互不相关 |
| `radio_button` | 新增 `indicator_geometry()`，**绘制与命中同源** | 命中区是「矩形中部的方框」，绘制是「标签行上的圆」——按角落是**在内命中、在外可见** |
| `progress_bar` | `ControlMetrics::centered_band(rect, PROGRESS_HEIGHT)` | 局部 `const BAR_HEIGHT` 与表重复 |

### 6.1 三个「同一事实多处推导」的实证修复

1. **`radio_button` 的绘制与命中不同源**（最严重）：hit_area 用 `rect.height/2` 定位，
   draw 用标签行定位。修法是把两者都改为调用 `indicator_geometry(&line)`。

## 8. P0-1b 尺寸通道：`Hints` + `Layout::arrange(&[ChildInfo])`（**根因修复**）

BLUE22 §B.4.1 判定：**B.3 尺寸通道是根因**，B.4 组装桥是结果。
§B.3 的原文：

```rust
// src/layout/types.rs:107
fn update(&self, rect: Rect, widgets: &mut dyn FnMut(ObjectId, Rect));
// 只持 ObjectId，没有 &dyn Widget ⇒ 布局无法问「这个子控件想要多大」
```

### 8.1 新增 `src/layout/hints.rs`

```rust
pub struct AxisHints { pub min: u32, pub pref: u32, pub max: u32 }
impl AxisHints {
    pub fn new(min, pref, max) -> Self;   // 构造时即归一化
    pub fn fixed(size) / at_least(min) / at_most(max) / unconstrained() -> Self;
    pub fn clamp(&self, value: u32) -> u32;
    pub fn is_fixed(&self) -> bool;
}
pub struct Hints { pub width: AxisHints, pub height: AxisHints }
pub struct LayoutParams { pub fill: bool, pub stretch: u32, pub margins: EdgeOffsets }
pub struct ChildInfo { pub id: ObjectId, pub hints: Hints, pub params: LayoutParams }
// + axis(), total_preferred(), total_minimum(), max_preferred(), placement_order(), filling()
```

### 8.2 三个关键设计决定（每条都对应一个真实缺陷形态）

| 决定 | 理由 |
|---|---|
| **`min <= pref <= max` 在构造时归一化** | Qt 允许未归一化，因此每次读取前要跑 `normalizeHints`/`expandSize`/`boundSize`（`qquicklayout.cpp:1218-1288`）。**让非法状态不可表示**比事后修正便宜 |
| **选 Qt 的三值，不选 Flutter 的 4 个对轴函数** | Flutter 自认 `IntrinsicWidth` 是「a speculative layout pass」且「O(N²) in the depth of the tree」（`basic.dart:3804-3807`）；min/pref/max 是控件一次算好的定值，布局直接读，**无往返**。代价是不能表达「宽依赖高」——本仓控件几乎全是定高，文本有独立测量入口 |
| **`fill` 与 `min` 分开声明** | 滑块与按钮的 `pref` 可以相同，但滑块**该**被拉宽、按钮**不该**。无法从尺寸区分 ⇒ 必须独立一位（Qt 的 `Layout.fillWidth`） |

### 8.3 `arrange` 的默认实现**必须**转发 `update`

BLUE22 §E.7-4 把它列为「执行时不得妥协」的一条。本轮严格遵守：

```rust
fn arrange(&self, rect, children: &[ChildInfo], out) {
    let _ = children;
    self.update(rect, out);       // 15 个布局不必同时改完
}
```

### 8.4 `Widget::hints()` 的默认实现：**忠实翻译**而非「全 0」

BLUE22 §B.5.2 原稿写「默认返回全 0」。本轮**改进了这一点**，理由是可验证的：

```rust
fn hints(&self) -> Hints {
    let preferred = self.size_hint();
    Hints { width: AxisHints::at_least(preferred.width),
            height: AxisHints::at_least(preferred.height) }
}
```

**为什么不能是全 0**：一个布局原先 `size_hint()` 拿到 `50×28`，若采用新通道后被告知
「任意尺寸」，**每个既有布局都会明显变松**——这让「采用新通道」变成一次可见的行为退化。
忠实翻译是唯一能让迁移**逐控件、零行为变化**的形状。

`default_layout_params()` 默认 `fill: false`（不拉伸），同样是保守答案：
一个默默吸收剩余空间的控件会让所有既有布局重排。

### 8.5 `FlexLayout::arrange` 实装——证明通道真的通了

BLUE22 §B.10 判据 2：**「单测：一个不知道尺寸的布局能仅凭 `&[ChildInfo]` 完成排布」**。

```rust
fn arrange(&self, rect, children: &[ChildInfo], out) {
    // 按 id 附上提示；未描述的控件回退到 child_sizes（增量迁移）
    let sizes = self.items.iter().map(|item| { /* hints.preferred() + margins */ });
    // 走**同一个** solver：sizes 放进一个临时布局，避免 &self 变 &mut self
    let solver = FlexLayout { child_sizes: sizes, ..self.clone() };
    solver.compute_rects(content_rect, None)
}
```

**为什么用临时布局而不是 `&mut self`**：`arrange` 取 `&self`。一个必须被改写才能提问的布局
无法在两个子控件之间共享、也无法放在 `&` 后面——这正是旧 `set_child_sizes(&mut self)`
强加给每个调用方的形状。

### 8.7 归一化顺序的一个实测教训

第一版 `new()` 写成 `let min = min.min(max.max(pref)); let max = max.max(min).max(pref);`，

反过来会把「至多 30」悄悄变成「正好 50」。已把顺序写进注释，
并加了一条**遍历 5 组输入断言不变式**的测试，而不是只测两个特例。

BLUE22 §E.7 明确要求「共享抽象必须带来真实消除才接入，否则保留并写明原因」。

| helper | 判定 | 处置 |
|---|---|---|
| `ControlMetrics::drawn_box` | **纯 `center_in` 别名，零消费者，零消除** | **删除**，并在模块文档写明为何删 |

### 10.4 由「零尺寸元素」清理暴露的真缺陷（第 3 起）

清理 `masked_edit` 的空 `<text></text>` 时发现它**不是渲染问题**：

```rust
// set_text 的循环遍历 self.segments
for seg in &self.segments {
    if let MaskSegment::Input { kind } = seg { ... }
}
// 未设 mask 时 segments 为空 ⇒ 循环 0 次 ⇒ 整个字符串被静默丢弃
```

而 `set_mask` 的文档明说「**If the mask is empty, no formatting is applied and all
input is accepted**」。⇒ `set_text("Sample")` 之后 `raw_text` 仍是空，
**控件什么都没画**。

**为什么这条缺陷能长期存活**：那个「可读性」测试只断言「文本元素的 fill 可解析」，
而**空 `<text>` 元素同样有 fill** ⇒ 测试通过。这正是第 65 轮 §7.4
「测试假绿的最常见形状」的又一实例——**断言在断言一个不该存在的东西**。

修法：`segments.is_empty()` 时 `raw_text = text`（按文档语义），并加注释写明
这段代码曾经做了什么。

### 12.3 由该修复**暴露**的一个门控缺陷（值得记录）

改完 gate 之后 `check_control_has_tests.sh` 报 **181/186**，5 个控件「没有测试」：
`FindReplaceDialog`、`MaskedEdit`、`MiniChart`、`SearchBox`、`SwipeToDismiss`。

**根因不是控件没测试，而是门禁的正则太窄**：

```python
# check_control_has_tests.py（修前）
re.finditer(r"#\[cfg\(test\)\]", text)          # 只认字面 #[cfg(test)]
```

`#[cfg(all(test, full_widgets))]` **不匹配**，于是整个测试模块被读成「不存在」，
一个**有测试的控件**被报成无测试。

**这是双向的假答案**：门禁的注释自己写明「它曾报 179/179 而 `Toast` 无测试」（假绿），
而这次是假红。修法是放宽为

```python
r"#\[cfg\(([^\]]*\btest\b[^\]]*)\)\]"           # `test` 必须在合取里，但不必是唯一项
```

**验证**（不是猜）：用 `importlib` 直接调用门禁的函数，确认 5 个控件的测试源码
**只**来自它们自己那个被 gate 的模块 ⇒ 门禁真的覆盖了它们，
删掉那个模块就会变红。

### 12.4 `run_all_gates.sh` 的「跑死」问题（用户明确指出）

用户反馈「门控要加合理 timeout，要不都跑死了」。取证后发现**不是缺 timeout，
而是三个具体缺陷**：

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 1 | `GATE_BUDGET` 默认 **1800s** | 58 个门禁最坏 **29 小时**——外部看与死机无异 | 降到 **900s**（实测最慢门禁 22~35s，冷启动 ~4min） |
| 2 | **没有整轮预算** | 「多个门禁都很慢」与「第一个卡死」在外部**完全一样** | 新增 `RUN_BUDGET`（默认 2700s）：耗尽即停发新门禁并**逐个列出未跑到的** |
| 3 | `rw_kill_tree` 在无 GNU `timeout` 的 macOS 上只 `kill -PID` | **`cargo` 子进程存活并持有 target-dir 锁** ⇒ **下一个门禁阻塞在锁上**——timeout 反而**制造**了挂死 | 新增 `pkill -P` 递归杀后代，SIGTERM→SIGKILL 两段，事后检测残余并**告警** |

**第 3 条是最关键的一条**：`lib_timeout.sh` 的注释原本就承认
「macOS bash 3.2 没有进程组」，但**结论是只杀 pid**——而那正好留下
`cargo` 继续持锁。**「超时反而造成挂死」**，这是 timeout 机制自身的缺陷。

**反向验证**（不是声明）：

```text
$ bash -c '. tools/lib_timeout.sh; rw_run_bounded 2 bash -c "sleep 60 & sleep 60"'
rw_run_bounded: timed out after 2s, killing pid 23969
bash: line 1: 23973 Terminated: 15          sleep 60
status=124
$ pgrep -f "sleep 60"      → 无输出
OK: no surviving descendants

$ RW_RUN_TIMEOUT=1 RW_GATE_TIMEOUT=2 bash tools/run_all_gates.sh --summary
check_android_cross.sh        NOT-RUN
check_apple_native.sh         NOT-RUN
...  （逐个列出未跑到的门禁）
```

### 12.5 `NOT-RUN` 是一个**独立**的类别

整轮预算耗尽时，未跑的门禁报 `NOT-RUN`，**既不算 PASS 也不算 FAIL**。
理由与原则 #59.4 同源：**超时/未完成不等于通过，也不等于缺陷**。
把它计进 PASS 就是「报告了没发生的事」；计进 FAIL 就是把「没跑」说成「坏了」。
摘要行现在同时给出四个计数，未跑的还附带**重跑命令**。

## 1. 🔴 `HorizontalAlignment` 在 SVG 后端被**整个丢弃**（用户问题 ① 的根因）

### 1.1 取证（不是推理，是实跑）

`RenderContext::draw_text` 的契约是：`origin` 是该对齐方式下的**锚点**，
软件栅格器按 `adjusted_origin_x` 把笔位左移（`primitives.rs:630-634`）：

```rust
HorizontalAlignment::Left   => origin.x,
HorizontalAlignment::Center => origin.x - (metrics.width / 2) as i32,
HorizontalAlignment::Right  => origin.x - metrics.width as i32,
```

而 SVG 后端**把这个字段丢掉了**（原 `backend.rs:276`）：

```rust
RenderCommand::DrawText { origin, text, font, color, .. } => {   // ← `..` 吃掉了 alignment
```

于是**全仓每一个居中/右对齐的标签，在 SVG 输出里都是左对齐**，而栅格输出里是居中的。

探针实跑（修复前）：

```text
<text x="100" ...>ABC</text>     ← Left
<text x="100" ...>ABC</text>     ← Center（应为 88）
<text x="100" ...>ABC</text>     ← Right（应为 75）
```

### 1.2 证据链：这是用户看到「靠左」的**唯一**原因

`button.svg` 里 `Sample` 在 `x=12`，而按钮框是 `0..240`。代码本身是**对的**——
`button.rs` 同时有水平居中和垂直居中——但 `draw_text_fitted(.., Center)` 发出的
`Center` 被后端丢弃，于是渲染成左对齐。

**关键判断**：`button.rs` 用的是 `HorizontalAlignment::Left` + 手工 `label_x`，
所以它**不是**这个缺陷的受害者；它的 x=12 是**第二**个缺陷（§2）。
先修后端，才能判定哪些控件的「靠左」是真的。

### 1.3 修复

`src/render/svg/backend.rs`：把对齐在**后端内**解析成绝对 `x`，与栅格器用同一套测量
（`estimate_cluster_advance`），因此两个后端的笔位逐像素一致。

> **为什么不发 `text-anchor="middle"`**：那会把对齐的**解析权**交给 SVG 引擎，而栅格器
> 仍在 Rust 里解析——同一条规则两份实现，一旦推进量模型不同就会分歧。发绝对 `x`，
> 一个规则一个归属。

### 1.4 判据（含反向注入）

新增 `svg_backend_honours_horizontal_alignment`：

```rust
assert_eq!(x_of(&region(HorizontalAlignment::Center)), origin.x - width / 2, ...);
assert_eq!(x_of(&region(HorizontalAlignment::Right)),  origin.x - width,     ...);
```

**反向注入**（把对齐重新丢弃）：

```text

  left: 100
 right: 79
test result: FAILED
```

✅ 测试确实能失败，证明它钉住的是真行为。

## 2. 🔴 按钮文字「靠左」：`BUTTON_PADDING_H` 被当成左锚点

### 2.1 诊断

后端修好后，`button.svg` 的 x 仍是 12（真实的左对齐）。`button.rs` 把
「水平内边距」直接当成**左起点**：

```rust
let label_x = rect.x + dimensions::BUTTON_PADDING_H as i32;   // ← 左锚
context.draw_text(Point { x: label_x, y: line.y }, .., HorizontalAlignment::Left);
```

**垂直方向本来就是对的**（`text_line` → 按钮 40..80、文字盒 53..67，中心都是 60），
所以用户看到的「居中」问题**只在水平方向**。这与用户「上下左右居中」的直觉一致：
`BUTTON_PADDING_H` 应当是**最小内缩**，不是左锚点。

**对标**：Qt Quick 的 `Button.qml` 其 `contentItem` 的 `Text` 是
`horizontalAlignment: Text.AlignHCenter`；Flutter M3 的 `TextButton`/`ElevatedButton`
同样居中子元素。左贴边在任何宽度的按钮上都是错的。

### 2.2 修复

以 `ControlMetrics::content_box(rect, {left: PAD, right: PAD, top: 0, bottom: 0})` 求
**内缩后的盒子**，再在其中居中（`draw_text_fitted(.., Center)`）。`BUTTON_PADDING_H`
仍是同一常量，但角色从「左锚」变成「最小内缩」——它与 `size_hint` 用的
`EdgeOffsets::symmetric(V, H)` 是同一条推导，所以**绘制尺寸与上报尺寸不可能分歧**。

### 2.3 判据（含反向注入）

| 测试 | 断言 |
|---|---|
| `the_label_is_centred_in_the_button` | `x == content.x + (content.width - text_w)/2`，且 `x != rect.x + BUTTON_PADDING_H` |
| `a_label_wider_than_the_padding_keeps_the_padding` | 装不下的标签不得越过按钮自身的 padding |

快照证据：`button.svg` / `button.light.svg` 的 `x` 由 `12` → `95`。

## 3. 🔴 calendar 日期数字不在单元格正中（用户问题 ② 的根因）

### 3.1 诊断：两个独立缺陷

**缺陷 A — 日期数字是「左上角 + 固定 3px」，不是居中**

```rust
context.draw_text_fitted(
    Rect::new(cx + 3, cy + 3, today_band.width - 3, (inner_y - (cy + 3)).max(0)),
    .., HorizontalAlignment::Left,     // ← 左对齐 + 顶部锚

```

census 几何下（240×120）：nav 0..30、weekday 表头 30..54、网格 54..120，
`cell_w = 240/7 = 34`、`cell_h = 66/6 = 11`。于是「1」画在 `x=6`（`cx+3` 再加

**缺陷 B — 表头 7 个列名与 7 列数字不在同一列**

**这个前提是假的**：`estimate_cluster_advance` 对窄字符收 **0.6 em**，所以
`"Mon"` 在 11px 下推进 **20px**，不是 36px，34px 的列**装得下**。
这个基于错误前提的 workaround 本身**就是缺陷**：在一个比列宽 33px 的盒子里左对齐，

### 3.2 修复

| 位置 | 修法 |
|---|---|
| 日期数字 | `context.text_line(cell_rect, &font)` 取单元的行盒，再 `Center` 居中 |
| 表头列名 | 界定到**本列**（`cell_w`），再 `Center` |
| nav 标题/箭头 | 三者共用 `context.text_line(nav, ..)`，不再各带一个字面量 `+7` |

同时**删掉了那条假前提的注释**，改为记录真实测量模型——否则下一个人会照着错误前提
再写一遍 workaround。

## 4. 同批扫描发现并修复的**其它真缺陷**（原则 #2 冰山法则）

### 4.1 `empty_state`：图标与标题**重叠 28px**

图标用 `draw_centered(icon_y + icon_size, ..)`（把参数当**盒底**），
标题用 `title_y = icon_y + icon_size + gap`（把同参数当**盒顶**）——
同一个 y 在同一段代码里被当成两种东西。48px 图标的盒覆盖 `48..96`，
标题画在 `y=60`，即**图标的盒内 28px 处**，`empty_state.svg` 里标题横穿邮箱图标。

修法：整段栈统一到渲染器契约（`origin.y` = 字形盒**顶边**），
行高与间距全部由 `measure_text` 推导，`icon_height/title_height/line_height`
三个量既参与 `stack_height` 也参与各自绘制，**不可能分歧**。

**反向注入**：恢复 `icon_y + icon_size` →

```text
"Nothing here" starts at y=60, inside "📭"'s box (48..96)
test result: FAILED
```

### 4.2 `keyboard`：30px 键帽里的字钉在顶边

代码注释写着「centred both ways」，但用的是 `draw_text_fitted`——
**它只做水平对齐，`y` 取 `bounds.y` 不变**。`keyboard.rs:565` 的注释自己就写着
「The label is centred both ways」，而 `draw_text_fitted` 的文档明说是
「fit horizontally, align horizontally」。改为 `draw_text_line`（两个方向都居中）。

快照证据：124 个键的 y 由 `2` → `8`（`(30-14)/2`）。

### 4.3 `gantt_widget` / `timeline_widget`：同一处「注释声称居中、代码是顶部锚」

两处注释都写「centred through the shared primitive」，但都传 `row_height`（24）
给 `draw_text_fitted`，而字体是 14 —— 于是每个任务名钉在所属行的顶边。
改为 `draw_text_line`。

### 4.4 `arc_helpers`：小圆弧退化成**零长度线段**，115px 的弧只剩 3 个像素

这是本轮**最意外**的一处。`draw_arc_segments` 的采样数写死 `40`：

- 相邻采样点的距离是 `radius * sweep / 40`，小半径/短弧下**四舍五入到同一像素**；
- `point_on_circle` 把每个端点取整 ⇒ 发出的 `<line>` **首尾相同**，画不出任何墨；
- spinner 的几何（r=48、sweep=2.4）真实弧长 ≈115px，取整后只剩 **3 个不同坐标**
  —— `spinner.svg` 里是一块楔形，不是弧。

`progress_circle.rs:301` 的注释**自己记录过这个现象**，是用「先取整成像素再判」的
workaround 绕过去的——**绕的是症状**。本轮修根因：

1. 采样数改为**由弧长推导**（`arc_sample_count`，1 采样/像素，上限 40）；
2. 端点取整后重合的弦**直接跳过**（零长度线是无墨的绘制指令，违反「不发出零尺寸元素」）。

**判据 + 反向注入**（两个都是真注入）：

| 测试 | 注入 | 结果 |
|---|---|---|
| `an_arc_never_emits_a_zero_length_chord` | 去掉弦的跳过判断 | FAILED |
| `the_sample_count_follows_the_arcs_pixel_length` | 采样数写死 40 | FAILED |

全仓扫描：零长度 `<line>` 由 **2** → **0**；零尺寸 `rect` **0**；空 `<text>` **0**。

### 4.5 `src/layout/flex.rs`：三个**共享基础设施**缺陷（被 §5 的组合控件逼出来的）

这三个不是「重构」，是**功能缺陷**，且影响所有走 `arrange` 的布局：

| # | 缺陷 | 后果 | 证据 |
|---|---|---|---|
| **a** | 没有子控件要 grow 时，`剩余空间` **整块塞给最后一个孩子** | `justify_content` **永远拿不到剩余空间** ⇒ `FlexEnd` 右对齐**不可达** | 3 个 60px 按钮在 240px 带里应右对齐到 240，实测 `x=0`、且末个按钮被加宽 60px |
| **b** | shrink 分支先 `max(min_main)`，随后又「cap at available」**穿过地板** | 子控件被压到**低于自己申报的最小值**（甚至到 0） | 两个 100px 按钮在 120px 带里各得 **57px**——比要绘制的标签还窄 |
| **c** | `consumed` 在已含 margin 的 `solved_main` 上**再加一次 leading margin** | 空隙**双倍计**，剩余空间被吃光 ⇒ `FlexEnd` 失效 | 220px 的行在 240px 带里真实剩余 20px，被算成 8px（更宽的 gap 下算成 0） |

**修法**：

- **a/b**：尊重地板，宁可**溢出**也不违反子控件的最小值。
  CSS flexbox 的 `min-width: auto` 与 Qt 的 `implicitMinimumWidth` 是同一选择：
  **可见的溢出**优于**看起来正常的省略号**（一个比标签还窄的按钮，其标签会省略）。
- **c**：剩余空间 = `带宽 - 占据量`，而「占据量」= 各子控件外框之和（已含 margin）+
  布局自身的 `gap`（单独一项），**不重复计 margin**。
- 地板注入时把**子控件自身的 margin 加回**：`hints.width.min` 描述的是**盒**，
  而 solver 说的是**外框**——不加回就会画出 `min - margin` 的宽度。

**判据 + 反向注入（三个都做了）**：

| 测试 | 注入 | 结果 |
|---|---|---|
| `justify_content_distributes_the_leftover_it_is_given` | 剩余空间重新塞给最后一个孩子 | FAILED |
| `a_child_is_never_squeezed_below_its_own_minimum` | 去掉 `max(min_main)` | FAILED |
| `justification_measures_the_leftover_including_the_gaps` | `consumed` 重新加一次 margin | FAILED |
| `a_margin_is_a_gap_and_not_a_reduction_of_the_childs_own_size` | 地板不加回 margin | FAILED |

> **a/b/c 是「被组合控件逼出来的共享缺陷」**——这正是 BLUE22 §B.3 的论点：
> 组合控件不能自己算几何，因为算了就会绕过布局；而一旦真的走布局，
> 布局里沉睡的缺陷才会暴露。**不接通道，这三个永远发现不了。**

即第 67 轮附录 F-1 记录的「组合控件仍无一使用真实布局」**仍未改变**。本轮改这一点。

### 5.2 新增 `CompositeBuilder`：只做四件事，**零布局算法**

```rust
pub struct CompositeBuilder {
    layout: Box<dyn Layout>,      // ← 排布算法全在 src/layout/，此处一行都没有
    children: Vec<Child>,
    padding: EdgeOffsets,
    floor: Size,                  // ← QML 的 implicitBackgroundWidth
}
```

四个入口：`add()`（工厂创建 + **读子控件自己的 `hints()`**）、`hints()`（固有尺寸向上传播）、
`arrange()`（去掉 padding 后交给布局，回写几何）、`child_ids()`。

**为什么子控件不是 `Box<dyn Widget>` 存在这里**：组合控件必须把子控件交给**宿主**
（进控件树、被绘制、被命中），而 `BaseWidget::children` 已经是它们的主人。
存第二份就是**一个孩子两个所有者**——正是 `set_parent` 自己的文档警告的那种情形。
所以 builder 存 `ChildInfo` 并**返回**它创建的盒子，所有权归调用方。

**`hints()` 的两条臂**（§B.9 的机械表述）：

- **主轴可加**：一行的宽度 = 三个按钮 + 间距之和 ⇒ 取 `sum`；
- **交叉轴竞争**：一行的高度 = 最高的孩子 ⇒ 取 `max`。

聚合一**不自己写**，改用 `src/layout/hints.rs` 已有的
`total_bounds`/`total_minimum`/`max_preferred`——**这是 §B.5.2 已经提供好的**。

> **实证教训（写进记录）**：第一版 `hints()` 自己 `sum(child.hints.width.pref)`，
> **漏掉了 margin**。而 margin 正是子控件声明「我前面有间隙」的唯一方式 ⇒
> 三个 6px 间隔的按钮报出的宽度**少了 12px**，行会按一个装不下自己孩子的宽度被摆放。
> 测试直接抓到（208 ≠ 228）。这正是原则 #101「同一概念只有一条实现路径」的反面教材。

### 5.3 `ActionRow`（§B.7 的 `dialog_with_actions` 样板）

右对齐由 **`justify_content = FlexEnd`** 表达——**没有任何一行算 x**。
间距挂在每个孩子的 **leading margin** 上（首个不带）：两侧都挂会**付两次**，
首个子控件带 margin 则是「保留了却永不花掉」的空间。

**判据**：

| 测试 | 断言 |
|---|---|
| `the_action_row_is_right_anchored` | 行的右缘 == 带的右缘；相邻按钮间距 == `gap`；`preferred_width == 72+64+72+2*6` |
| `a_row_wider_than_its_band_does_not_shrink_below_the_floor` | 宁可**溢出**也不低于各自地板 |
| `an_empty_action_row_is_empty` | 空行占据 0 宽，不伪造按钮 |
| `a_missing_control_does_not_break_the_row` | profile 未发布的控件被跳过，计数器一致 |

### 5.4 🚫 **明确不合并**的一处（原则 #51）

`src/widget/dialog/message_box.rs` 的 `action_row_geometry`（被 8 个对话框用）
**没有**改用 `ActionRow`，因为两者要求**真的不同**：

| | `ActionRow` | dialog 的 `action_row_geometry` |
|---|---|---|
| 按钮尺寸 | 控件自己的 `hints()`：`max(64, label*8+24)` | `Hints::fixed(DIALOG_BUTTON_WIDTH)`：**等宽**标准命令 |
| 输出 | 各按钮矩形 | 矩形 **+ 行跨度 + `leading_inset`**（消息区必须让位的量） |

第二行是实质差异：`OK`(72) 与 `Cancel`(64) 不等宽会让对话框按钮行**参差**，
所以那条路径用**单一常量**定宽。要合并就得加模式开关，而「一个名字两种行为」
正是本仓反复删除的缺陷形态。**两者的真正共享面是布局**（都 `FlexEnd` + leading margin），
所以它们**都依赖 §4.5 那三个 `FlexLayout` 修复**——一个布局、两套策略，耦合在正确的位置。
该判断**写进了 `composite.rs` 的模块文档**，供后人复核。

## 9. ⚠️ 本轮的一次**严重操作失误**（必须记录）

用户指令是「记录在 `docs/log/log-20260923-1.md`」。该文件的**上半部分已经是第 67 轮的
完整日志（1014 行）**，而我把 `write_file` 当成「新建」用了，**整文件覆写**，
把第 67 轮记录从 1014 行压到 479 行。

**发现方式**：`git diff --stat` 报 `305 insertions(+), 840 deletions(-)` —— 一个只该**追加**
的操作出现了 **840 行删除**，这个数字本身就是警报。

**恢复**：原文件已在 HEAD 提交（`33879fea`），故 `git show HEAD:…` 完整取回，
再把本轮内容**追加**为新的 `# 第 68 轮` 一节（标题层级同步降一级以免与文档标题竞争）。

**教训（与第 67 轮 §9「绝不用 `git checkout` 清理工作区」同一类）**：

> **`write_file` 是「创建」也是「覆写」，用之前必须先确认目标是否已存在内容。**
> 历史日志这类**只增不改**的文件，正确动作是**读—追加—写回**，
> 而不是直接写。判断依据不是「我记得它是空的」，而是 `ls`/`wc -l` 的实测。
> 若当时工作区未提交，这份 67 轮记录就会**永久丢失**——比第 67 轮那次回退事故更不可逆。

## 11. 一句话结论

**渲染器之间的契约、和布局里沉睡的三个缺陷，是本轮真正的收获。**

用户报的两条（按钮靠左、日历错行）都定位到了根因：
一条是 **SVG 后端丢弃 `HorizontalAlignment`**（影响全仓每一个居中标签），
一条是**日历把日期画在单元格左上角、且表头基于一个错误的前提**。
按冰山法则扫同类，又挖出 `empty_state` 重叠、`keyboard`/`gantt`/`timeline` 的
「注释说居中、代码是顶部锚」、以及 `arc_helpers` 让 115px 的弧只剩 3 个像素。

接 BLUE22 §B.5.2/§B.7 时，**组合控件一旦真的走布局，就逼出了 `FlexLayout` 里三个
共享缺陷**（`justify_content` 不可达、地板被穿过、空隙双倍计）。
这印证了 BLUE22 §B.3 的判断：**不接尺寸通道，这些缺陷永远发现不了**。

最后 `control.md` 把 188 个控件按 17 个分组可视化，并由门禁保证它与快照同批更新。
