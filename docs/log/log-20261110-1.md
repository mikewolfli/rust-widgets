## 9. 追加：用户反馈「code_editor 默认支持的语言没有了」的定位与修复

### 9.1 定位（先取证，不改代码）

1. **语言定义与关键字表没有丢**：`LanguageId` 仍是 21 个变体；`keywords()`/`type_names()` 的实现
   与 `HEAD` 的 `code_editor/syntax.rs` **逐字节相同**：

   ```text
   $ awk '/pub fn keywords/,/^    }$/' <HEAD syntax.rs>  vs  editor/syntax/language.rs → diff 空
   $ awk '/pub fn type_names/,/^    }$/' ...                                    → diff 空
   变体数：HEAD 21 / 现在 21
   ```

2. **默认构建仍带全世界语言**：

   ```text
   $ cargo build --lib -v | grep -o 'feature="[a-z-]*"' | sort -u
   … feature="builtin-languages" … feature="code-editor" … feature="markdown-editor" …
   ```

3. **真正丢失的位置是「只给 device profile」的构建**，以及**用这种构建跑注册表驱动的工具**：
   - `cargo run --no-default-features --features desktop --example export_control_svgs`
     （`control.md:33` 与示例自身文档长期给出这条命令）现在只导 240 个控件，
     `code_editor`/`markdown_editor` 两张卡（及其高亮语语言展示）整个消失；
   - `demo/wasm_gallery` 用 `default-features = false, features = ["mobile", "wasm"]`，
     它的画廊是「每个已注册 capability 一张卡」，于是移动端画廊也丢了两张编辑器卡；
   - README / CONTRIBUTING / cookbook 的贡献者命令同样只写 `desktop`，按文档验证会**静默少测**
     约 700 条编辑器用例。

   根因是 BLUE31 §1.5 把两个控件与 lexer 改成独立 feature（`desktop` 不再隐含它们），而下游/工具
   仍按旧假设只写 profile。这是本轮引入的**下游接线缺口**，不是语言实现缺失。

### 9.2 修复（让缺口变成编译期可见，并恢复默认覆盖面）

| 位置 | 修复 |
|---|---|
| `Cargo.toml` `[[example]] control_rendering_census` / `export_control_svgs` | `required-features` 增加 `code-editor,markdown-editor,builtin-languages`：注册表驱动工具在缺 feature 时由 Cargo **跳过**，不会再静默产出 240/242 的残缺画廊 |
