| 原则 | 违反点 |
|---|---|

### B-3. 合并方案（移动 + 重写 mod.rs）

移动（`git mv`，保留历史）：

```text
src/chart/adapter.rs → src/widget/chart_widgets/adapter.rs
src/chart/charts.rs  → src/widget/chart_widgets/charts.rs
src/chart/layout.rs  → src/widget/chart_widgets/layout.rs
src/chart/svg.rs     → src/widget/chart_widgets/svg.rs
src/chart/types.rs   → src/widget/chart_widgets/types.rs
src/chart/tests.rs   → src/widget/chart_widgets/tests.rs
src/chart/mod.rs     → 删除（git rm）
```

**命名冲突处理（关键设计决定）**：

引擎的 `LineChart`/`BarChart`/`PieChart` 与控件的同名。合并后**不**把引擎类型 re-export 到
`chart_widgets` 根，因此：

- `chart_widgets::LineChart` → 恒为**控件层**（裸名归控件）
- `chart_widgets::charts::LineChart` → **引擎层**（需限定路径）

这满足原则 #49「同名不同层的类型必须写清分层注释」，且不需要改名（不破坏 API，原则 #21）。

重写 `src/widget/chart_widgets/mod.rs`，模块文档明确写出两层职责，并保留原有 profile 门控
（引擎 5 模块保持 `not(any(mini, embedded))`，控件 4 模块保持 `not(mini)`，与原
`#[cfg(feature = "chart")]` 下的可达性一致）：

```rust
#[cfg(not(any(feature = "mini", feature = "embedded")))]
pub mod adapter;
#[cfg(not(feature = "mini"))]
pub mod bar_chart;
#[cfg(not(any(feature = "mini", feature = "embedded")))]
pub mod charts;
#[cfg(not(any(feature = "mini", feature = "embedded")))]
pub mod layout;
#[cfg(not(feature = "mini"))]
pub mod line_chart;
#[cfg(not(feature = "mini"))]
pub mod pie_chart;
#[cfg(not(feature = "mini"))]
pub mod sparkline;
#[cfg(not(any(feature = "mini", feature = "embedded")))]
pub mod svg;
#[cfg(not(any(feature = "mini", feature = "embedded")))]
pub mod types;

#[cfg(all(test, not(any(feature = "mini", feature = "embedded"))))]
mod tests;
```

`src/lib.rs` 删除顶层 `pub mod chart;`，原地留注释说明引擎新路径。

### B-4. ⚠️ 过程中发现并闭环的自引入缺陷

**F-1（最严重）：迁移幻觉 —— 10 个测试被静默丢弃**

首次 `cargo check --lib` 通过后跑测试，得到：

```text
test result: ok. 3995 passed; 0 failed   ← 合并前是 4005
```

**少 10 个测试**。原因：`src/chart/mod.rs` 中的 `#[cfg(test)] mod tests;` 未在新
`mod.rs` 中重建，`tests.rs` 虽已移动却**从未被编译**——`cargo check` 不可能发现。

这正是原则 #17（禁止"迁移幻觉"）的典型形态：文件在，代码在，但**没被调用**。

修复：在新 `mod.rs` 补回并由 profile 门控：

```rust
#[cfg(all(test, not(any(feature = "mini", feature = "embedded"))))]
mod tests;
```

**F-2：`MemoryChartContext` 位置判断错误**

首版 re-export 写成 `types::MemoryChartContext`，编译报错——实际定义在 `svg.rs`。已按
编译器提示改到 `svg`。

**F-3：`tests.rs` 的裸名歧义**

原 `use crate::chart::*;` 展开后裸名 `BarChart`/`LineChart` 会指向引擎类型（与控件同名）。
改为显式限定导入：

```rust
use crate::widget::chart_widgets::charts::{BarChart, LineChart};       // 引擎
use crate::widget::chart_widgets::svg::{MemoryChartContext, SvgChartContext};
use crate::widget::chart_widgets::types::{ChartSeries, DataPoint};
use crate::widget::chart_widgets::Chart;
```

**F-4：`rustfmt` 因路径变长而需要重排**

路径从 `crate::chart::charts` 变长后跨过行宽限制，`bar_chart.rs`/`line_chart.rs`/
`svg.rs`/`types.rs` 出现格式差异。已用 `rustfmt` 收敛（**仅**我改动的文件）。

### B-5. 新增结构守卫测试（防止再次分裂）

新增 `tests/chart_module_layout_test.rs`（4 个测试），钉住合并后的形状：

## D. ⚠️ 任务 2 过程中发现并修复的真实缺陷

### D-1. 缺陷：tri-state CheckBox 的状态机是坏的

**发现方式**：扩充 demo 时打印 `tri-state CheckBox` 的状态，观察到
`state=Unchecked` 但语义上我已调用 `set_checked(true)` —— 不符合预期，遂取证。

**取证：读源码定位根因**（`src/app/handle.rs`，修复前）：

```rust
pub fn set_checked(&self, checked: bool) {
    CHECKBOX_STATES.with(|map| {
        let mut map = map.borrow_mut();
        let state = map.entry(self.raw_id()).or_default();
        state.checked = checked;
        if !state.tristate {                                  // ← 根因
            state.check_state =
                if checked { CheckState::Checked } else { CheckState::Unchecked };
        }
    });
    crate::platform::get_platform().set_widget_checked(self.raw_id(), checked);
}
```

**缺陷有两处，都是逻辑错误（原则 #5）：**

1. **`if !state.tristate` 守卫**：`check_state` 在 tri-state 模式下**永不更新**。
   于是 `set_tristate(true)` 之后再 `set_checked(true)`，会得到
   `is_checked()==true` 与 `check_state()==Unchecked` **互相矛盾**的状态。
2. **`PartiallyChecked` 不可达**：`CheckState` 有三个值，但**没有任何 API 能设置中间态**，
   `check_state()` 只会在默认值 `Unchecked` 上打转 —— 三态控件实际上只有两态。

**独立复现（真实公开 API，非模拟）** —— 临时集成测试，实跑输出：

```text
is_tristate=Some(true) check_state=Unchecked is_checked=true
thread '...' panicked at tests/tmp_checkstate_repro.rs:16:
assertion `left == right` failed: tri-state box must reflect set_checked(true)
  left: Unchecked
 right: Checked
```

### D-2. 修复（根因修复，非表面补丁）

把 `check_state` 改为**权威字段**，`checked` 由它派生；并新增可达中间态的 API：

| 改动 | 内容 |
|---|---|
| `check_state` 权威化 | `is_checked()` = `check_state() == Checked`（中间态不算 checked） |
| `set_checked` 改走 `set_check_state` | 无条件落到确定态，不再有 `if !tristate` 守卫 |
| **新增 `set_check_state(CheckState) -> bool`** | 可设置 `PartiallyChecked`；**非 tri-state 时返回 `false` 且不改变状态**（诚实拒绝，而非静默降级） |
| `set_tristate(false)` 时收敛 | 若当前是 `PartiallyChecked`，**收敛为 `Unchecked`**（控件只能显示两态时不留陈旧态） |
| 删除 `checked` 字段 | 修复后不再被读取（消除死状态，原则 #4） |

`PartiallyChecked` 推送原生时按 "on" 处理（Win32 `BS_AUTO3STATE` / AppKit
`NSControlStateValueMixed` 对 checked 标志的表现），精确状态保留在 handle 内。

### D-3. 回归测试（新增 5 个，`tests/check_box_tristate_test.rs`）

| 测试 | 钉住的行为 |
|---|---|
| `plain_checkbox_tracks_set_checked` | 两态双向跟随 |
| `tristate_checkbox_reflects_set_checked_after_enabling_tristate` | **缺陷本身**：tristate 下 `set_checked` 必须生效 |
| `tristate_checkbox_can_reach_partially_checked` | 中间态可达，且不计为 checked |
| `partially_checked_is_refused_without_tristate` | 无 tri-state 时拒绝且**不改变状态** |
| `disabling_tristate_collapses_mixed_state` | 关 tri-state 时中间态收敛为 Unchecked |

**验证测试有约束力**：修复前 D-1 的复现测试 `FAILED`；修复后 `5 passed; 0 failed`。

### D-4. 冰山扫描（原则 #2：修一个点，扫同类模式）

**扫描：还有谁有"三态/中间态"这类只写一半的状态机？**

```bash
grep -rn "PartiallyChecked\|check_state\|tristate" src/ tests/ --include=*.rs
```

| 命中 | 判定 |
|---|---|
| `app::CheckState` / `CheckState::PartiallyChecked` | 本次修复对象 |
| `base_widgets::checkbox::CheckState` | **同名不同类型**，独立的 widget 层枚举，有自己的 `set_state`；`access_write_base.in.rs` 已正确接线，无缺陷 |
| `Switch` / `RadioButton`(base) 的 `checked` | 纯 bool 控件，无三态语义，不适用 |
| `ProgressBar::set_indeterminate` | 已闭环（demo 实证 `indeterminate=Some(true)`） |

**结论**：三态状态机的缺陷是**孤例**，`app::CheckBoxHandle` 是唯一同时暴露
`checked: bool` 与 `check_state: CheckState` 的地方，已修复；无同类待修项。

> 附注：`app::CheckState` 与 `base_widgets::CheckState` 同名，分属 handle 层与 widget 层。
> 本次未合并（职责确实不同，且合并会破坏 API，原则 #21）。**记录为观察项**，供后续评估是否
> 需要按原则 #49 补分层注释。
