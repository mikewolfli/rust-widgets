## 2. 逐条修复

### 2.1 【阻断】白板根因：关联建立晚于首帧绘制

**文件**：`src/control_backend/custom/mod.rs`（`adopt_widget_box`）

**缺陷（端到端取证）**：

```
app.new_window → crate::create_window → mount_named_widget → adopt_widget_box
   ├─ register(widget)                        → registry id
   ├─ add_child(parent)
   ├─ request_repaint_subtree(id)             ← 需要 HOST_WINDOWS 关联才能生效
   └─ attach_window_host_if_needed(id)        ← 关联在这里才写入（太晚）
         └─ WindowsPlatform::create_window
               └─ ShowWindow + UpdateWindow   ← 同步触发 WM_PAINT，此时关联为空
                     └─ paint_target_for → widget_id_for_host_window(platform_id) == None
                           └─ 空白客户区
```

**修法**：把 `attach_window_host_if_needed` 提到 `add_child` **之后**、`request_repaint_subtree`
**之前**。两个约束都要满足：

- 必须在 `attach` 之前 `add_child`：平台建窗时会立即绘制一次，那一次必须已经能看到即将加入的子控件。
- 必须在 `request_repaint_subtree` 之前 `attach`：那次请求靠关联才能解析到窗口。

**验证**：见 §3。

### 2.2 输入：`WM_CHAR` / `WM_UNICHAR`（数字与 IME 全部失效）

**文件**：`src/platform/windows/types.rs`（新增 `forward_window_char`）、
`src/platform/windows/canvas.rs`（新增 `forward_char`）

`WM_KEYDOWN` 的 `wParam` 是**虚拟键码**：A 是 `0x41`，但数字 `1` 是 `0x31`、`.` 是 `0xBE`、
`+` 是 `0xBB`、IME 组合态是 `0xE5`（`VK_PROCESSKEY`）。把键码当字符转发，等于让文本框
把输入的数字打成一行无关的拉丁字母，而 IME / 死键 / 任何非拉丁布局**一个字符都收不到**。

Win32 翻译后的字符走 `WM_CHAR`（`WM_UNICHAR` 亦然），这才是文本控件该消费的消息。
`TranslateMessage` 在 `run()` 里本来就调用了，只是没人接这个结果。

新增的两处实现都做三件事：丢弃 C0 控制字符与 `0x7F`（它们是**命令**，`WM_KEYDOWN` 已经送过）、
用 `char::from_u32` 拒绝代理项半体、经 `focused_widget()` 定向投递
`Event::text_input(..)`。

### 2.3 生命周期：`WM_CLOSE`

**文件**：`src/platform/windows/types.rs`

`DefWindowProcW` 的默认 `WM_CLOSE` 会 `DestroyWindow`，而 `WM_DESTROY` 不带任何 widget 身份，
于是**用户点标题栏的 X** 不会跑任何 `on_close`，而 `WindowHandle::close` 会跑。
`src/app/handle.rs::WindowHandle::close` 的文档写着「the signal is the one path a close is
announced on, so there is no second table to keep in step」——路由 OS 关闭到 `crate::close_widget`
才让这句话对两条路径都成立。

### 2.4 输入：`WM_KILLFOCUS` / `WM_MOUSEWHEEL` / `WM_RBUTTON*` / `WM_LBUTTONDBLCLK`

**文件**：`src/platform/windows/types.rs`、`src/platform/windows/canvas.rs`、
`src/platform/types.rs`（`MousePhase` 扩展）

- `MousePhase` 新增 `SecondaryPress` / `SecondaryRelease` / `DoubleClick` 三个变体：
  按钮选择的是**事件种类**，把它编码进 phase 可以避免「本该右键却派发了左键」这类事故。
- `WM_MOUSEWHEEL` 单独处理（**不是** `forward_window_mouse`），因为 Win32 有两处不同：
  delta 在 `wParam` 高字（`GET_WHEEL_DELTA_WPARAM`，单位 `WHEEL_DELTA`=120），
  而点位在 `lParam` 里是**屏幕**坐标。直接当像素用会让一格滚 120 行；不转 client 坐标
  则会滚到指针**屏幕位置**下那个（通常完全无关的）控件。
- `WM_KILLFOCUS` 是 window 上 `SetFocus` 的精确逆操作：不清理则切到别的应用后，
  最后焦点的控件继续画焦点环、继续闪光标。

### 2.5 `set_widget_visible`：`show()`/`hide()` 不再静默 no-op

**文件**：`src/platform/windows/platform_impl.rs`

trait 默认是空实现，Windows 未覆写，因此 `WindowHandle::show()`（`demo/control` 调用它，
并在注释里声称「不调用则窗口永不可见」）在 Win32 上是**静默 no-op**。
窗口之所以看得见，只是因为 `create_window` 恰好传了 `WS_VISIBLE` —— 一个宿主**无法控制**
自身可见性的窗口：`hide()` 关不掉，建时就隐藏的窗口也再拿不回来。

新实现接受两种 id 空间（`window_hwnd_for_widget_id` 解析 registry id 与 platform id），
并且**排除 canvas 子窗口**（它是表面不是窗口，由 mount/unmount 管理），
最后调 `invalidate_for_handle` 让显示出来的窗口立刻重绘。

### 2.6 `widget_id_by_native_handle`：从 O(n) 持锁扫描改为 `GWLP_USERDATA`

**文件**：`src/platform/windows/types.rs`

原实现：

```rust
match self.menu_state.handles.lock() {
    Ok(handles) => handles
        .iter()
        .find_map(|(widget_id, native)| ((*native as HWND) == hwnd).then_some(*widget_id)),
    ...
}
```

调用者：`WM_SIZE`、`WM_NOTIFY`、`WM_GETMINMAXINFO`、`WM_MOUSELEAVE`、`WM_KEYDOWN`、
`forward_window_mouse`（即**每一次** `WM_MOUSEMOVE`/`WM_LBUTTONDOWN`/`WM_LBUTTONUP`）、
`WM_PAINT`（经 `paint_target_for`）。全都是消息线程，全都持锁，全都线性。

改为 Win32 惯例做法：`bind_native_handle` 写 `SetWindowLongPtrW(hwnd, GWLP_USERDATA, id)`，
反向查询是一次 `GetWindowLongPtrW`，**无锁、O(1)**。

注意：`get_native_handle`（id → `HWND`）**必须保留 map** —— Win32 无法从 id 找到窗口，
这个方向没有任何 API 可问。两个方向的信息量不同，因此一个用 `GWLP_USERDATA`、一个用 map，
注释里写清了原因（否则后人会「顺手」删掉 map 造成回归）。

### 2.7 死脚手架清理：`Win32MenuState`

**文件**：`src/platform/windows/types.rs`、`src/platform/windows/platform_impl.rs`

取证（`grep -rn` 全仓）：

| 字段 | 写入者 | 读取者 | 结论 |
|---|---|---|---|
| `menu_command_to_item` | **无** | `WM_COMMAND` | 删除（分支永不成立） |
| `pending_menu_events` | 同上唯一路径 | **无** | 删除 |
| `control_command_to_widget` | `bind_control_command` | `WM_COMMAND` | **保留**（真实生产者+消费者） |
| `pending_widget_events` | `notify::enqueue_control_notify_event`、`WM_NOTIFY` | 触发轮询 | **保留** |
| `handles` | `bind_native_handle` | `get_native_handle` 等 | **保留**（§2.6） |

同时修正 `capabilities()` 上那段悬空引用：原文写「see the notes on those fields」，
而 `types.rs` 里那四个字段**一条文档注释都没有**。现在字段有文档，正文也指向真实存在的说明。

`WM_COMMAND` / `WM_NOTIFY` 两臂**保留**并补上说明：它们服务的是**宿主自建的**原生控件
（库自己因为自绘每一个 `WidgetKind`，从不产生这些消息），这是真实路径，不是脚手架。

### 2.8 锁策略统一：`canvas.rs` 的 `expect()` → `MutexExt::lock_guard`

**文件**：`src/platform/windows/canvas.rs`

三处 `expect("...lock poisoned")` 位于 `canvas_wnd_proc` 可达路径上。
在 `extern "system"` 回调里 panic **无法跨 FFI 边界 unwind**，Rust 会直接 abort 整个进程 ——
一个可恢复的簿记故障被放大成应用崩溃。同后端的 `windows::types` 一直是
`Ok/Err` + `log::error!`，两套策略并存必然漂移。

改用仓内既有的 `crate::core::MutexExt::lock_guard()`（`src/core/mutex_ext.rs` 已有，
语义就是「忽略 poison 继续用内部值」），并在 `canvases()` 上写明为何容忍 poison。

### 2.9 `WM_MOUSELEAVE` 两处语义对齐

**文件**：`src/platform/windows/canvas.rs`

window 侧已改为**路由** `MouseLeave` 事件；canvas 侧仍是全局 `clear_hover`。
同一物理动作（指针离开）在两个表面上语义不同，必然漂移（这正是 `blit_frame` 自己的文档
警告的「two copies will drift」）。canvas 侧改为同样路由
`Event::MouseLeave`，并且把 canvas 原点算进去（`canvas_origin(hwnd)`）以满足绝对坐标约定。

### 2.10 调试残留与性能：`eprintln!` 集群

**文件**：`src/platform/windows/types.rs`、`src/widget/runtime.rs`

删掉 4 处 `eprintln!`（`[CLICK]`、`[PAINT]`×3、`[TREE]`、`[TREE-SLOW]`）与配套的
`Instant::now()` 计时。这些不是「日志」而是**临时诊断**：它们直接写 stderr（绕过 `log`）、
在**每次 `WM_PAINT` / 每次鼠标移动**都在消息线程上做字符串格式化，而且 `[CLICK]` 那条
会在用户每次左键点击时打印。

`paint_window_tree` 同时改用 `render_frame_cached`（按 size 缓存、只重栅格化受损区域），
替代每帧全量重绘的 `render_frame_tree`；注释说明了「仍非局部呈现（`StretchDIBits` 呈现整幅位图），
省下的是绘制而非传输」。

### 2.11 门控阻断项：`flex.rs` 的语句级文档注释

**文件**：`src/layout/flex.rs` 1187–1222

`let realize = ...` 之前挂了一整块 `///` 文档注释。rustdoc 不为语句生成文档，

### 2.12 门控阻断项：`paint_window_tree` 的单模式 `match`

**文件**：`src/platform/windows/types.rs`

```rust
match super::canvas::client_size(hwnd) {
    Some((width, height)) => { ... }
    None => {}
}
```

`clippy::single_match` 报错（`-D warnings` 下是硬错误）。改为 `if let Some(..)`，
顺带让「查不到尺寸就直接 `EndPaint` 返回」变成结构上的提前退出而不是空 `None` 臂。

### 2.13 跨后端同类缺陷：surface-only 后端的 `invalidate_surface`

**文件**：`src/platform/types.rs`、`src/platform/state.rs`、
`src/platform/mobile.rs`、`src/platform/harmony/platform_impl.rs`、
`src/platform/macos_objc2/platform_impl.rs`

这**不是** Windows 专属问题，是本轮 iceberg 扫描挖出的同类集群：

`mobile` / `harmony` / `macos_objc2` 的 `invalidate_surface` 都是
`self.state.invalidate_surface_record(id)`，而该方法的第一行是
`if self.surface_rect(id).is_none() { return false; }` —— 只认**已挂载的 surface**。

但库请求重绘时通常给的 id 是**窗口**：`widget::runtime::request_repaint_subtree`
明确先失效窗口再失效控件，因为窗口的帧才是绘制普通子控件的地方
（`windows/types.rs::paint_window_tree` 与 Linux 的 `connect_draw` 都是这个道理）。
于是这些后端上「事件处理了、ledger 记了、屏幕没变」——静默失效。

修法（原则 #53：能力差异是运行时事实，不改 API 形态）：

1. `BackendState` 新增 `record_repaint_request(id)`：判定依据是
   **本后端是否认识这个 widget**（`contains_widget`），而不是「是否是已挂载 surface」。
   窗口与已挂载 surface 一视同仁地入队，只有当 id 什么都不指时才返回 `false`。
2. 三个后端覆写 `invalidate_surface` 为 `record_repaint_request`。
3. `PortablePlatform`（`StubPlatform` 承担）本就是默认实现 —— 其默认值也是 `false`，
   但它 `supports_surfaces()` 也是 `false`，所以不构成谎报；本轮在 trait 文档里把
   「`supports_surfaces` 只承诺 `mount_surface`，不承诺『容器帧绘制子控件』」写清楚。

**文档补强**：`Platform::invalidate_surface` 的文档原来只有一句「Returns `false` when `id`
is not mounted on this backend」，完全没提窗口是合法参数。现在写明：

- 为什么窗口 id 是合法参数（自绘 → 窗口的帧绘制子控件）；
- 哪些后端接受窗口（三桌面后端 + 上述四个 surface 后端）；
- 返回 `false` 的确切含义。

### 5.3 新增：8 个 surface C ABI 函数

**文件**：`src/bindings/binding_impl.rs`、`src/lib.rs`、`src/platform/types.rs`、
`src/platform/{mobile,harmony/platform_impl,macos_objc2/platform_impl}.rs`

| 新函数 | 作用 |
|---|---|
| `rw_mount_surface` | 把 widget 挂到表面上，返回是否被接受 |
| `rw_resize_surface` | 更新已挂载表面的矩形 |
| `rw_unmount_surface` | 释放表面 |
| `rw_invalidate_surface` | 标记表面（或窗口）需要重绘 |
| `rw_supports_surfaces` | 本后端能否承载库自绘控件 |
| `rw_take_pending_repaint` | **拉队列**：取出下一个待重绘的 widget |
| `rw_render_surface_frame` | **产像素**：渲染一帧 RGBA，交宿主 blit |
| `rw_report_window_resize` | 宿主上报客户区尺寸，触发 layout 重跑 |

设计要点（都写进了 Rust doc）：

- `rw_render_surface_frame` 的像素缓冲**经出参返回**而非返回值：
  `c_try!` 的错误通道对 `*mut u8` 没有 `CAbiSafe` 实现，且这是刻意的
  （裸字节指针无法经宏的数值 fallback 往返）。走 `bool` + 出参让帧路径与其它函数
  共用同一套错误处理，不必为一次调用另立一套更弱的约定。
- 缓冲所有权移交宿主，用 `rw_free_bytes(ptr, len)` 释放 —— 与 `rw_poll_drop_event`
  的 payload 同一约定、同一个 free 函数。
- `out_stride` 显式发布而非让宿主硬编码 `width*4`：哪天某个后端按行对齐填充，
  硬编码的宿主会把图撕裂。
- 这 8 个函数**不只服务 Harmony**：`android` / `ios` / `macos_objc2` 都以同一个
  「record + 队列」存储回答 `supports_surfaces() == true`，同一套调用即可驱动。

`Platform` trait 新增 `take_pending_repaint`（默认 `None`），四个 surface 后端覆写为
`self.state.take_pending_repaint()`。

设计要点（均写入模块 doc）：

1. **手写 `extern "C"` 而非 bindgen** —— 声明几十行，crate 无 bindgen 依赖；
   头文件版本与每个函数的 `@since` 都记在注释里。
2. **枚举显式 `from_raw` 映射，不 `transmute`** —— `repr(C)` 映射 SDK 枚举，
   越界值 `transmute` 是 UB；保留 `Unknown`/`None` 分支。
3. **`touch` 是正交能力** —— `Event::Touch*` 本身 gate 在 `feature = "touch"`，
   所以触摸臂带同一 gate，无该能力时 `debug` 丢弃（与 Windows `WM_TOUCH` 一致）。
4. **线程守卫** —— widget runtime 是 thread-local，ArkUI 回调在其主线程；
   非该线程的回调**拒绝**并记 log，而非静默丢事件（否则会污染另一套 registry）。
5. **`on_surface_changed` 不跑 layout** —— 只入队 `Resized`，让消息循环重跑；
   在 ArkUI 布局中途重入控件树布局正是卡顿来源。
6. **取消手势映射为 `TouchEnd`** —— 否则识别器会永远停在“手势进行中”。
7. **`numPoints == 0` 也处理** —— 部分 SDK 层级单点事件只填顶层 `x`/`y`，
   不处理会让单击丢失。

#### 5.19.3 Wayland 的 `dpi_scaling` 测试：断言本身是错的

```

  left: true   right: false
```

测试断言的是 `caps.dpi_scaling == (dpi_scale_factor() != 1.0)`。**这个关系是错的**：

#### 5.19.7 一个值得记住的陷阱：过期门控缓存会重放旧失败

`Platform::create_*` 全部返回 `0`，**不是缺口**。它们在 `types.rs` 里就有明确说明：

> Every method below has a default that reports "this host creates no such control".
> That is the truthful answer now that the library paints every `WidgetKind`: the host
> supplies a window and a drawing surface, not controls.

同理 `supports_web_engine`（无后端实现，全 `false`，且有调用方 `web/web_engine.rs:88`）、
`parse_shortcut`（零实现零调用者，遗的死 trait 表面）、`native/embedded_capability_contract`
（由 `family()`/`capabilities()` 派生，逻辑上无需覆写）—— 均非缺陷。

#### 5.22.2 真正的缺陷：C ABI 的 combo/list **读**走了 Platform

自绘架构下，combo/list 的 items 存在**控件自己身上**
（`ComboBox::items`、`ListBox::items`），由 `widget_access` 与 controls 访问。

但 C ABI 的路由是**分裂**的：

| 方向 | 路由 | 结果 |
|---|---|---|
| `rw_combo_box_add_item` | `get_control_backend()` | ✅ 真的存进控件 |
| `rw_combo_box_set_current_index` | `get_platform()` | ❌ 永远是 trait 默认 `false` |
| `rw_combo_box_current_index` | `get_platform()` | ❌ 永远是 `-1` |
| `rw_combo_box_item_count` | `get_platform()` | ❌ 永远是 `0` |
| `rw_combo_box_item_text` | `get_platform()` | ❌ 永远是空串 |
| list_box 同四项 | `get_platform()` | ❌ 同上 |

后果：C / Python / Java 宿主**成功添加了 items**，然后被告知盒子是空的、选不中。
这是「分脑」形态的静默失效 —— 写进去的东西读不回来，且没有错误可看。

**修法**：这 6 个读/写查询改走 crate 级函数（`crate::combo_box_*` / `crate::list_box_*`），
它们本来就是正确的自绘实现。

#### 5.22.3 回归测试又抓出第二个真缺陷：越界索引被当成成功

新增两个 C ABI 往返测试后，`combo_box` 那条断言失败：

```
assertion failed: an out-of-range index is refused
  rw_combo_box_set_current_index(combo /* 3 items */, 99) 返回 true
```

根因在控件层：`ComboBox::set_current_index` **静默忽略**越界索引
（它是模型 setter，忽略是合理的 —— 删 item 时就靠这个保持稳定），
但 capability 的属性 setter 无条件返回 `Ok(())`。

这是**两回事**：模型 setter 可以宽容，**属性契约**的调用方问的是「写进去了没有」。
对一个被丢弃的索引答 `Ok`，既造成了上面的 `true`，也破坏了属性编辑器依赖的往返
（写 `n` 读回 `n`）。

**修法**（`combobox.rs` / `listbox.rs`）：越界返回 `CapabilityAccessError::OutOfRange`；
`Null`（清空选择）始终成功 —— 「没选中」是任何 item 数的盒子都能持有的状态。

#### 5.22.4 新增的回归测试

`src/bindings/binding_impl.rs` 新增两条，断言的是**往返**而不是单点值：

- `combo_box_items_round_trip_through_the_c_abi`：加 3 项 → 读 count == 3 →
  逐项读文本 → 选中 → 读回索引 → 越界被拒且**不清除**已选。
- `list_box_items_round_trip_through_the_c_abi`：同上，并验证 remove 后后面的项**上移**
  （宿主删除按钮依赖的性质）。

为什么断言往返而不是单点：单断言 `count == 2` 对于一个自己存 items 的后端也会通过；
**写入走一个入口、读取走另一个入口**才能钉住两边一致 —— 而这正是被破坏的性质，
也是任何一边移动就会再次破坏的性质。
