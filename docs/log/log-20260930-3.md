## §1 🔴 desktop 致命缺陷：Windows 用户拖拽窗口**永不重排**（白板根因之一）

### 1.1 现象与假设

用户报告 "Windows 下都是白板"。上一轮认定已修（"Windows 空白根因：
`attach_window_host_if_needed` 顺序"）。本轮不采信，独立追 `WM_SIZE` 全链路。

### 1.2 取证：id 空间不匹配

链路三方各自的 id 来源（**逐行读代码，非推测**）：

| 环节 | 文件:行 | id 是什么 |
|---|---|---|
| 窗口创建 | `src/platform/windows/platform_impl.rs:992` | `state.create_widget(...)` → **平台 id**（`BackendState::next_id` 从 **1** 开始） |
| 写入 `GWLP_USERDATA` | `platform_impl.rs:996` → `types.rs:776` | 上面那个 **平台 id** |
| 读回 | `types.rs:896-904` `widget_id_by_native_handle` | 读 `GWLP_USERDATA` → **平台 id** |
| `WM_SIZE` 消费 | `types.rs:210`（**修复前**） | `platform.widget_id_by_native_handle(hwnd)` → **平台 id** |
| 队列校验 | `control_backend/custom/create_widgets_helpers.in.rs:76-79` | `is_mounted(window_id)` → 要求 **注册表 id** |

而同一个 `wnd_proc` 里**其他每一条**窗口消息都做了第二次跳转：

- `WM_KILLFOCUS`（`types.rs:195`）→ `window_widget_for(hwnd)`
- 鼠标各臂（`types.rs:480`）→ `window_widget_for(hwnd)`
- `paint_target_for`（`types.rs:672`）→ `window_widget_for(hwnd)`
- `WM_CHAR`（`types.rs:186`）→ `window_widget_for(hwnd)`
- `WM_GETMINMAXINFO`（`types.rs:296`）→ 平台 id，但查的是 `platform.state`（同为平台 id 空间）→ **自洽**

`window_widget_for`（`types.rs:434`）正是那个补齐的第二跳：

```rust
unsafe fn window_widget_for(hwnd: HWND) -> Option<u64> {
    crate::widget::runtime::widget_id_for_host_window(widget_id_by_native_handle(hwnd)?)
}
```

**`WM_SIZE` 是唯一漏掉第二跳的臂。**

### 1.3 为什么这个 bug 能长期存活（关键，也是它能被复现的原因）

`BackendState::new()` 的 `next_id` 从 **1** 开始（`src/platform/state.rs:238`），
而控件注册表的 id 也从**小整数**开始分配。于是：

- 对"第一个平台窗口恰是第一个注册表控件"的应用，**两个 id 空间数值相同** → 断言通过，缺陷隐形。
- 一旦分配顺序不同（多窗口、先建别的控件、控件被回收），平台 id 指向的要么是空，
  要么是**另一个活着的控件**。

而失败是**静默的**：

```rust
// 修复前 types.rs:220
crate::queue_resize_trigger(widget_id, width, height);   // 返回值被丢弃
```

`queue_resize_trigger` 对 `!is_mounted` 的 id 返回 `false`（`create_widgets_helpers.in.rs:79`）：
**事件不入队、尺寸不记录、任何日志级别都没有输出**。用户看到的就是
"拖大窗口，控件一个都不动" —— 正是白板观感。

这与 GTK 后端**已经踩过并记录过**的坑是同一个（`linux/platform_impl.rs:656-670` 注释：
"reporting the platform id made every resize a silent no-op"）。修复模式在仓库里是现成的。

### 1.4 修复

```rust
// src/platform/windows/types.rs  WM_SIZE 臂
WM_SIZE => {
    if let Some(widget_id) = unsafe { window_widget_for(hwnd) } {   // ← 补齐第二跳
        ...
        if width > 0
            && height > 0
            && !crate::queue_resize_trigger(widget_id, width, height)
        {
            log::warn!(
                "[windows] WM_SIZE for widget {widget_id} ({width}x{height}) was not \
                 accepted by the backend; the window layout did not re-run"
            );
        }
    }
    DefWindowProcW(hwnd, msg, wparam, lparam)
}
```

两处改动，各自独立必要：
1. **id 空间**：用 `window_widget_for` 补齐第二跳 —— 让 resize 真的送达 layout。
2. **失败可见**：`queue_resize_trigger` 返回 `false` 时 `log::warn!` ——
   把"静默失效"变成"可诊断"，这正是让本缺陷潜伏至今的那一层。

## §2 🔴 所有平台：resize 重排**丢弃设备上下文**（DPI / 字号 / 触摸下限）

### 2.1 取证

`apply_window_layout`（`src/app/handle.rs`）是**唯一**决定顶层控件摆放的地方，
它调用的是**不带上下文**的 `update`：

```rust
layout.update(Rect::new(0, 0, width, height), &mut |widget_id, geometry| { ... });
```

`LayoutContext` 在 `src/` 下的生产构造点**只有一处**：
`src/widget/composite.rs:495-500`（`CompositeBuilder::arrange`，走 `arrange_with_context`）。

后果——逐 layout 复核哪些**真的读**上下文（读 `src/layout/*.rs` 逐个确认）：

| Layout | `update_with_context` | 读什么 |
|---|---|---|
| `BoxLayout` (`box_layout.rs:186`) | ✅ 覆写 | `layout_scale`/`font_scale` 缩放间距与边距 + `min_touch_size` 触摸下限 |
| `FlexLayout` (`flex.rs:1303`) | ✅ 覆写 | 同上（含触摸下限） |
| `WrapLayout` (`wrap.rs:405`) | ✅ 覆写 | 缩放间距与内边距 |
| `KeyboardAwareLayout` (`keyboard_aware.rs:200`) | ✅ 覆写 | 仅转发给内层 |
| 其余 11 个 layout | ❌ 继承默认 | 默认转发 `update`，行为不变 |

所以：**窗口顶层若用 `BoxLayout`/`FlexLayout`/`WrapLayout`（demo 的标准做法），
用户 resize 后间距/边距不缩放、触摸下限不生效；而同样一个 layout 嵌套在
`CompositeBuilder` 里却缩放了。** 同一个设备，同一个 layout，两套结论。

### 2.2 修复

`Layout::update_with_context` 取 `&self`、对象安全、`LAYOUTS` 本就存
`Box<dyn Layout>`，因此是**严格增量**改动（未覆写的 layout 继承默认 → 转发 `update`，
行为与修复前逐字节相同）。两处都改（窗口 + 面板递归）：

```rust
// src/app/handle.rs  apply_window_layout
let context = crate::layout::types::LayoutContext::default();
LAYOUT_CONTEXT_SCALES.with(|map| {
    map.borrow_mut().insert(window_id, context.layout_scale.max(context.font_scale));
});
...
layout.update_with_context(Rect::new(0, 0, width, height), &context, &mut |id, geometry| { ... });

// src/app/handle.rs  apply_panel_geometry（同样的缺陷，深一层）
let context = crate::layout::types::LayoutContext::default();
layout.update_with_context(rect, &context, &mut |widget_id, geometry| { ... });
```

`LayoutContext::default()` **不是字面量**（`layout/types.rs:90-98`）：它读
`platform::profile::text_scale()` 与 `recommended_touch_target()`，所以这是设备事实。

新增 `WindowHandle::layout_context_scale()` 作为**可查询**的诊断出口
（原则 #97 精神：事实必须可查询，不能靠推断）。

### 2.3 验证 —— 含"测试本身是否有效"的复核（重要）

新增 2 个测试，并**反向验证它们真的能抓到缺陷**（这一步不可省）：

先按最直觉的写法写了"断言几何"的版本 → 反向验证时**在缺陷代码上依然通过**。
追因（实测，非推测）：

## §3 🟠 `dispatch_trigger` 丢弃无法解析尺寸的 resize，且无任何日志

`src/app/handle.rs` 的 `Resized` 分支原本没有 `else`：

```rust
if let Some((width, height)) = crate::window_client_size(widget_id) { ... }
```

尺寸解析不出来时，事件被**消费并丢弃**，无日志、无计数、无返回信号。
这正是 §1 的缺陷能潜伏多年的原因之一：后端入队被拒（`false` 被丢）与
出队解析失败（无 `else`）**两处都是静默的**。

修复：补 `else` 分支 `log::warn!`，把"后端报告了 resize"与"layout 真的重排了"
区分开，让宿主能从自己的日志里诊断。此项是 §1 的**配套**——只有两处都不静默，
下一个同类缺陷才会在第一次运行就被发现。

## §4 🔴 鸿蒙 XComponent 桥：**已绑定但输入全死**（`set_mounted_widget` 无调用者）

### 4.1 取证

用户明确要求"鸿蒙绕靠 ark gui，是在 xcomponents 绘制控件"，并要求"把 XComponent 桥接
的缺口补上"。上一轮交付了 `xcomponent.rs`（1019 行，真实 FFI + 真实 SDK 链接）。
本轮不满足于"能编译能链接"，追问一句：**回调真的会送到控件树吗？**

`grep -rn "set_mounted_widget" src/` 的结果：

```
src/platform/harmony/xcomponent.rs:539:pub fn set_mounted_widget(widget_id: ObjectId, rect: Rect) -> bool {
src/platform/harmony/xcomponent.rs:992:        assert!(!set_mounted_widget(4242, Rect::new(0, 0, 100, 100)));
```

**只有定义，只有自己的测试，零生产调用者。**

而每一个输入回调都以它为门：

```
src/platform/harmony/xcomponent.rs:684:    let Some(widget_id) = mounted_widget() else { return; };   // touch
src/platform/harmony/xcomponent.rs:775:    let Some(widget_id) = mounted_widget() else { return; };   // mouse
src/platform/harmony/xcomponent.rs:824:    let Some(widget_id) = mounted_widget() else { return; };   // hover
src/platform/harmony/xcomponent.rs:857:    let Some(widget_id) = mounted_widget() else { return; };   // key
src/platform/harmony/xcomponent.rs:900:    if let Some(widget_id) = mounted_widget() { ... }          // focus
src/platform/harmony/xcomponent.rs:913:    if let Some(widget_id) = mounted_widget() { ... }          // blur
```

`mounted_widget()` 读的是**桥自己的记录**，而 `Platform::mount_surface`
（`harmony/platform_impl.rs:246`）只写 `state.mount_surface_record(id, rect)` —— 两条记录
互不相通。

**结论**：桥 `bind()` 成功、C ABI 报成功、回调注册成功，然后**每一个事件都在第一行
返回**。控件画得出来、永远不响应，任何日志级别都没有输出。

这正是原则里"上报了并未发生的事"的形状：`rw_harmony_bind_xcomponent` 的文档
（`binding_impl.rs:2745`）写着 "returns `true` ⇒ input callbacks are live"，
而实际上 live 不了。

### 4.2 修复

把"显示"与"可交互"两半接上：

```rust
// src/platform/harmony/platform_impl.rs
fn mount_surface(&self, _parent: u64, id: u64, rect: Rect) -> bool {
    let recorded = self.state.mount_surface_record(id, rect);
    #[cfg(all(feature = "xcomponent", not(alloc_frugal)))]
    {
        if !super::xcomponent::set_mounted_widget(id, rect) {
            log::debug!("[harmony] mount_surface: widget {id} 已显示但尚未绑定 XComponent...");
        }
    }
    recorded
}
```

`resize_surface` / `unmount_surface` 同步跟随（后者只清"当前正在显示的**这个**"，
卸载别的 surface 不能静默断掉屏上那个的输入）。

**为什么桥的拒绝不是硬失败**：宿主可能在 ArkTS `onLoad` 之前 mount，此时确实没有
XComponent，`set_mounted_widget` 诚实地返回 `false`。此时 surface 记录照写（控件**真
的**在显示，宿主可以稍后重新 bind），只是输入要等桥就绪 —— 因为输入没就绪就拒掉整个
显示路径，是本末倒置。

## §5 🟠 鸿蒙：键盘**修饰键被硬编码为 0**（Ctrl/Shift 快捷键永不生效）

`xcomponent.rs` 原来写死：

```rust
let event = crate::event::Event::KeyPress { key: code as u32, modifiers: 0 };
```

SDK 其实**有**这个能力，只是没绑。查真实头文件取证：

```
$ grep -n GetKeyEventModifierKeyStates \
    $OHOS_SDK/sysroot/usr/include/ace/xcomponent/native_interface_xcomponent.h
765:int32_t OH_NativeXComponent_GetKeyEventModifierKeyStates(
        OH_NativeXComponent_KeyEvent* keyEvent, uint64_t* keys);   // @since 20

$ grep -A 12 ArkUI_ModifierKeyName \
    $OHOS_SDK/sysroot/usr/include/arkui/ui_input_event.h
  ARKUI_MODIFIER_KEY_CTRL  = 1 << 0,
  ARKUI_MODIFIER_KEY_SHIFT = 1 << 1,
  ARKUI_MODIFIER_KEY_ALT   = 1 << 2,
  ARKUI_MODIFIER_KEY_FN    = 1 << 3,
```

**关键证点（不查就会写错）**：ArkUI 的位序与本库控件层**不同**。
本库约定见 `windows/canvas.rs::current_modifiers`：`SHIFT=1, CTRL=2, ALT=4`。
ArkUI 是 `CTRL=1, SHIFT=2, ALT=4`。**原样透传会把 Ctrl 和 Shift 对调**——
按 Ctrl 触发 Shift 的语义，是个更隐蔽的 bug。因此逐位显式映射。

`FN` 位没有控件层对应物，**丢弃**而非折进别的键：它是硬件层修饰键，猜一个等价物等于
凭空生成用户没做的输入。

调用失败时报 `debug` 并返回 `0`（诚实方向：丢修饰键是错误动作，未修饰键至多是旧行为）。

验证：

```

$ llvm-nm -u lib.so | grep GetKeyEventModifierKeyStates
  U OH_NativeXComponent_GetKeyEventModifierKeyStates    ← @since 20 符号真实链接通过
```

## §6 🟠 鸿蒙：hover-leave 把**组件原点当成指针坐标**

```rust
// 修复前
let position = surface_offset();     // ← 组件在 ArkUI 树里的**原点**
let event = crate::event::Event::MouseLeave { pos: position };
route_pointer_event(widget_id, &event, position);
```

`route_pointer_event` → `dispatch_pointer_event` **用这个点做命中测试**
（`widget::runtime.rs:801` `let target = widget_at(root, point);`）。而 `surface_offset()`
是组件在**ArkUI 父容器**坐标系里的位置——根本不是控件树的坐标系。两个后果：

1. leave 被投给原点处（通常是根）的控件，不是真正被 hover 的那个；
2. `dispatch_hover_transition`（`runtime.rs:952`）**本来就会**在命中目标变化时对上一个
   hover 控件发 `MouseLeave`，因此这是**第二个、射错方向的** leave。

修复：记住鼠标臂最近一次的真实指针位置，leave 时用**它**；从未记录过就没进过组件
内部，无 leave 可言。`is_hover == true` 分支显式空操作并写明理由（hover 高亮属于具体
控件，由 `MouseMove` 驱动；此处合成 enter 只会高亮一个猜出来的坐标）。

## §7 其余平台修复

### 7.1 `mobile.rs::run()` 只打日志、不 drain（resize 入队后永不投递）

其兄弟后端 android / ios / harmony / wasm 的 `run()` 都是 `drive_frame` 循环；
`mobile.rs`（mobile API 在非移动宿主上的 preview 后端）只 `log::info!`。
而它的 `queue_resize_trigger` **会把事件入队**（转发给 control backend）——
于是事件进了队列、**永远没人取**。

修复：补上与兄弟后端一致的 tick 循环，并加 `initialized`/`running` 两个原子量
（`run` 不能依赖调用方先调 `init`，`quit` 要能停一个已在跑的循环）。

验证：`cargo check --lib --no-default-features --features mobile` ✅

### 7.2 `embedded`：`drain_triggers` **弹出即丢弃**，却仍 `dispatched += 1`

`embedded` 是 stripped profile：触发器队列**存在**，但 `full_widgets=false` →
`crate::app` 不存在 → 没有 `dispatch_trigger` 可投。原代码：

```rust
while let Some(event) = poll_widget_trigger_event() {
    #[cfg(full_widgets)]   { app::dispatch_trigger(...); }
    #[cfg(not(full_widgets))] { let _ = (...); }
    dispatched += 1;        // ← 无论有没有投递都加一
}
```

于是 `embedded` 对一个**没有到达任何 layout** 的 `Resized` 事件返回 `1`。
返回值是宿主判断"投递是否发生"的**唯一**信号——这与原则中"上报了并未发生的事"
完全同形。

修复：只有真正 `dispatch_trigger` 的那一支才计数；无路由时返回 `0` 并 `log::debug!`
说明消费了什么、投递了什么（"消费了、但什么都没投递"）。

**同时修掉由此暴露的 `unused_mut`**：`let mut` 只在 `full_widgets` 下有变化，
用 `#[cfg]` 分开两个绑定，让编译器在**每个** profile 下都检查真实的那一侧，
而不是拿 `#[allow(unused_mut)]` 把一侧的真话盖住。

验证：desktop / tablet / mobile / embedded / mini **五档全过**，零 warning。

### 7.3 Wayland：configure 事件归给**单槽**窗口 id（多窗口归错）

```rust
// 修复前：一个 Cell，被每次 create_window 覆写
static CONFIGURED_WINDOW: Cell<ObjectId>;
fn record_configured_window(id: ObjectId) { ...set(id) }
```

两个 toplevel 时，第二个 `create_window` 覆盖第一个的 id → **之后每个 configure
都报到最后创建的那个窗口上**：错窗口的尺寸被记录、错窗口的 layout 用另一个窗口的尺寸
重排，而真正被 configure 的窗口永不重排。且**不可检测**——`window_client_size`
优先返回已记录的尺寸，错的记录看起来是权威的。

修复：`xdg_toplevel` **proxy** 是合成器在回调里真正指名的对象，因此以它为键
（`proxy.id().protocol_id()`），存 `HashMap<usize, ObjectId>`。
`create_window` 记 `record_configured_window(&toplevel, id)`，dispatch 里
`configured_window_id(proxy)`。

验证：`cargo check` + `cargo clippy -D warnings --features "wayland-native desktop-runtime"` ✅

## §9 🔴🔴 **Windows 白板的真正根因**：`WM_PAINT` 调错了绘制入口（单控件 vs 整棵树）

### 9.1 取证

这是本轮最重大的一条。用户说"Windows 下都是白板"，之前定位到两处（`attach_window_host_if_needed`
顺序、`WM_SIZE` id 空间），但都不足以解释"白板"。本轮直接追"像素是怎么上去的"。

Windows 的绘制链：`WM_PAINT` → `paint_window_tree`（`windows/types.rs`）。

```rust
// 修复前 types.rs:420-438
// `render_frame_cached` rather than `render_frame_tree`.
...
let Some(frame) = crate::widget::runtime::render_frame_cached(
    widget_id, Size::new(width, height), crate::core::Color::WHITE,
)
```

而同一文件**自己的注释**写着（`types.rs:47`）：

> This arm is the Windows half of the window-level painter the Linux backend already
> has; **both call `render_frame_tree`, which walks the window's child list.**

**注释写的是 A，代码做的是 B。** 查 `render_frame_cached` 的真实语义：

```
render_frame_cached  →  render_frame_incremental  →  render_frame

// src/widget/runtime.rs:2873  — render_frame 的全部绘制动作
let painted = with_widget_mut(id, |widget| {
    let Some(drawable) = widget.as_draw_mut() else { return false; };
    backend.begin_frame(clear);
    { let mut context = RenderContext::new(&mut backend);
      context.push_offset(-origin.0, -origin.1);
      drawable.draw(&mut context);        // ← 只画这一个控件
      context.pop_offset(); }
    true
})?;
```

对比 `render_frame_tree`（`runtime.rs:2932`）——它才走 `direct_children_of`：

```rust
let mut stack: Vec<ObjectId> = direct_children_of(id);
```

**全仓调用点对比（grep 实证）**：

| 调用点 | 用哪个 |
|---|---|
| `linux/platform_impl.rs:534`（GTK 窗口绘制器） | ✅ `render_frame_tree` |
| `tests/window_tree_paints_visible_controls_test.rs:46` | ✅ `render_frame_tree`（**直接调**，绕过 Windows 臂） |
| `examples/style_probe{3,4,6,7}.rs` | ✅ `render_frame_tree` |
| **Windows `WM_PAINT`** | ❌ `render_frame_cached` → `render_frame`（单控件） |

### 9.2 为什么这必然导致白板

Windows 下普通控件（`create_button` / `create_label` / …）**没有原生控件**，也**不是 mounted
surface**（surface 才会拿到子 `HWND` 并被 `canvas.rs` 单独画）。所以窗口自己的绘制器是
唯一能画它们的东西。而它只画了窗口根控件：结果是背景 + 窗口 chrome 铺满客户区，
**按钮、标签、下拉框一个都没画** —— 正是用户看到的白板。

### 9.3 为什么整套测试是绿的

这是本条的**关键教训**：`tests/window_tree_paints_visible_controls_test.rs` 自己
**直接调 `render_frame_tree`**（注释里写得很清楚："renders the window's tree through
*the same entry point the Linux backend's painter uses*"）。

它测的是 **Linux 的调用方式**，而 Windows 臂用的是另一个函数。
**测试覆盖了函数，没覆盖接线。** 1120×620 的 demo 场景、三个控件、像素级断言，
全绿，而 Windows 上什么都没画。

### 9.4 修复

```rust
// src/platform/windows/types.rs
let Some(frame) = crate::widget::runtime::render_frame_tree(
    widget_id,
    crate::core::Size::new(width, height),
    crate::core::Color::WHITE,
) else { ... };
```

并重写那段错误注释，说明：
- 为什么**必须**走树（普通控件在 Windows 无原生控件、非 surface）；
- 为什么**可以**舍弃 size-keyed 缓存（旧代码为了"避免每次 expose 全量重栅格化"而用缓存入口，
  但**陈旧/不完整的帧是错的图**，而重栅格化只是慢；正确性优先于速度）；
- 清色必须覆盖客户区 —— `render_frame_tree` 自己的 `begin_frame(clear)` 会做，**即使没有
  任何子控件绘制**也会做。

### 9.5 新增回归测试（针对"接线"而非"函数"）

新增两个测试到 `tests/window_tree_paints_visible_controls_test.rs`：

1. `the_per_widget_painter_leaves_out_the_windows_children` ——
   断言 `render_frame` **只画一个控件**（按钮矩形内只有 1 种颜色）。
   这是**反向半边**：如果 `render_frame` 哪天真走了树，那么两个入口等价，
   Windows 臂就不可能写错——所以这个性质必须被钉住。
2. `the_window_entry_point_contains_its_children_and_the_per_widget_one_does_not` ——


> 它们钉住的是"契约本身"，而不是"Windows 臂是否调对了"——后者只能靠代码审查 +

## §10 🟠 同类扫描（冰山法则）：`set_widget_text` 不触发重绘

修 §9 时按原则第 2 条扫同类模式：**"改了状态却不 invalidate"**。

## §13 🔴 新门禁抓到的真实缺陷：无 device profile 时**桥根本没有入口点**

### 13.1 事件经过（重要教训）

把 `xcomponent` 加入 `tools/check_harmony_cross.sh` 时，新断言报了 FAIL：

第一反应是"门禁写错了"。**先取证再断言**（原则 #2/#4）：用 `compile_error!` 探针
证明 `xcomponent` feature **确实**到达了 `rustc`；再查头文件确认符号名无误。

`rw_harmony_bind_xcomponent`（ArkTS 侧唯一入口）住在 `bindings` 里。而我之前的验证命令

- `desktop-runtime` 不是 `desktop`

于是桥**编译了但没有导出入口点**，整个 `libace_ndk.z` 也就不需要链接。

### 13.2 这是"假验证"，必须自己揭穿

本轮早期我两次看到过"aarch64 链接出 21 个符号"并当成通过——那是在**另一个 feature 组合**

### 13.3 门禁最终形态与结果

顺带修一个新测试自身的真实缺陷：`tests.rs` 里 `"Play".to_string()` 在 `mini`

- **macOS cocoa / objc2 无窗口级绘制器**：`grep render_frame_tree src/platform/macos*/`
  **零匹配**。唯一会画的是 `mount_surface` 里创建的 canvas 视图

- **`window_hwnd_for_widget_id` 的 `unwrap_or(id)` 回退**（`windows/mod.rs:38-46`）：

### 15.1 版本的真实来源

`src/core/types.rs:280` 用 `env!("CARGO_PKG_VERSION")` 解析，**不是手写字面量**，

本轮把 `Cargo.toml` 与所有已发布文档、锁文件统一到 **2.8.3**：

（"which 2.8.2 did"），改了就成了错话。

### 15.2 新门禁：`tools/check_version_consistency.sh`

**为什么需要**：版本号在 README、三个 cookbook 语言版本、两个 changelog 副本里各写一遍，
而编译器只读 `Cargo.toml`。**没有任何门禁核对它们是否一致** —— 一次漏掉某个语言版本的
发布升级，会发出一个"让你依赖一个从未发布的版本"的 README，用户在第一条命令上就撞到。

**检查项**：`[1]` Cargo.toml 可解析 → `[2]` 每个已发布文档都提到该版本 →
`[3]` changelog 最新条目即该版本 → `[4]` 四个锁文件 pin 该版本。

**刻意不做的事（重要）**：第一版还试图断言"文档里不得出现其它版本号"，结果对**三处完全正确**
的写法误报：

| 误报 | 真实含义 |
|---|---|
| `getting-started.md` 的 `version = "0.1.0"` | **读者自己的** crate 版本（教程代码） |
| `api-reference.md` 的 "Since 2.0.0 …" | 历史叙述，描述某行为从哪版起改变 |
| `language-bindings.md` 的 `"ffi-napi": "^4.0.3"` | npm 依赖版本 |

**一个会误报的检查会训练读者忽略它**，真正的漂移就淹没在噪声里。因此门禁只断言
**肯定事实**（当前版本出现在该出现的地方），负向判断留给 review —— 并在脚本头写明
这是**有意弱于它看起来能做的**，因为机械检查分不清"教程版本"与"陈旧指针"。
（与 `check_status_docs_name_real_types.py` 头部的自述同一纪律。）

**已加入 CI**（`.github/workflows/ci.yml`），与 ABI 门禁同组；顺带把一直未被 CI 调用的
`check_changelog_sync.sh` 也接了进去。
