# 第 14 轮（2026-09-13）— 接线控件创建路由：开发者只看到「控件」

> 用户目标（原话）：
> 「我的目的是面向开发者，看到的只有控件，不论原生还是自绘，而原生自绘由 backend 决定。
> 不必强行所有操作系统层面都统一，只是面向开发者统一。」
> 「所有的接线修改，请按你的最优最完美方案处理，立即修复改进。」
>
> 本轮把 `control_backend` 路由**真正接线**，并在过程中发现并修复 3 个既有缺陷。
> 所有结论均有实跑证据。§G 记录未做项。

## A. 诊断：架构设计完整，但从未接线

### A-1. 取证：`control_backend` 是零消费者的完整架构

```bash
for s in ControlBackend ControlBackendKind ControlRoutePreference \
         route_preference_for_widget_kind custom_control_backend native_control_backend; do
    printf "%-40s " "$s"; grep -rn "$s" src/ demo/ tests/ | grep -v "^src/control_backend/" | wc -l
done
```

结果：**全部为 0**。

而该目录包含：

| 组成 | 规模 |
|---|---|
| `ControlBackend` trait | 202 个方法 |
| `NativeControlBackend` | 105 处 `get_platform()` 转发 |
| `CustomPaintControlBackend` | 166 个 `create_*`（独立状态模型） |
| `routing.rs` | `WidgetKind` → `NativePreferred`/`CustomRequired` 分类表 |
| `dispatcher.rs` | `get_control_backend_for_widget(kind)` —— 注释自称 **"the canonical create-time selection entry"** |

**而 `lib.rs` 的每个 `create_*` 都直连 `platform::get_platform()`，从不查询路由表。**

### A-2. 这不是无意的死代码

`git log` 与 `docs/plans/blue14.md` §D-4 显示：上一轮**特意**把 `DatePicker`/`TimePicker`/
`DateTimePicker` 从"已接线但不被调用"修成转调各自平台方法 —— 即在 `control_backend` 内部做了
维护，却**从未把它接到公开创建路径上**。

这是原则 #17（禁止"迁移幻觉"）的架构级形态：不是文件没搬，是**整层决策逻辑没被调用**。

### A-3. 为什么这次的表现形式是「开发者看到两套概念」

因为路由没接线，`Platform` trait 被迫自己承担"原生还是自绘"的决策，于是开发者可见的
表面裂成两个入口：

```rust
create_button(...)            // → Platform::create_button
mount_custom_widget(...)      // → Platform::mount_custom_widget   ← 另一条路
```

`mount_custom_widget` 这个名字本身就是泄漏：它要求调用方先知道"这个控件没有平台原语"。
**这正是原则 #52 禁止的机制词汇。**

## B. 修复：把创建路径接到路由表

### B-1. 核心改动：`lib.rs` 的 23 个创建函数改走 dispatcher

```rust
/// Resolve the backend that should create a widget of this kind.
///
/// A widget kind may map onto a real platform primitive (a `Button` on Win32/
/// AppKit/GTK) or have no primitive at all (`Chart`, `CodeEditor`, …), in which
/// case the platform layer supplies the surface. **Which of the two happens is a
/// backend decision and must not leak to callers**: this function is the single
/// place the creation path asks for it, so the choice cannot drift between call
/// sites.
#[cfg(not(feature = "mini"))]
fn backend_for_kind(kind: widget::WidgetKind) -> &'static dyn control_backend::ControlBackend {
    control_backend::get_control_backend_for_widget(kind)
}
```

调用点从

```rust
platform::get_platform().create_button(parent, text, x, y, width, height)
```

变为

```rust
backend_for_kind(widget::WidgetKind::Button).create_button(parent, text, x, y, width, height)
```

覆盖：window / button / checkbox / line_edit / label / radio_button / slider /
progress_bar / combo_box / list_box / panel / message_box / file_dialog / color_dialog /
font_dialog / spin_box / list_view / scroll_area / menu_bar / menu / tool_bar / status_bar。

**取证**：

```bash
grep -c "backend_for_kind" src/lib.rs        → 23 处调用点
grep -c "platform::get_platform().create_" src/lib.rs → 0
```

### B-2. 新增统一语义入口 `create_widget_of_kind`

这是「开发者只看到控件」的直接兑现：一个函数，两种落地方式，调用方不分支。

```rust
pub fn create_widget_of_kind(
    kind: widget::WidgetKind,
    parent: ObjectId, text: &str, x: i32, y: i32, width: u32, height: u32,
    widget: Option<Box<dyn widget::Widget>>,
) -> ObjectId {
    match control_backend::route_preference_for_widget_kind(kind) {
        // 平台有原语：创建它，忽略传入的 widget 对象。
        ControlRoutePreference::NativePreferred => backend_for_kind(kind).create_widget(...),
        // 平台无原语：把 widget 对象托管到平台提供的承载面。
        ControlRoutePreference::CustomRequired => { /* register + mount */ }
    }
}
```

要点：
- **调用方拿到同一个 `ObjectId`**，不关心走了哪条路。
- 无原语且未提供 widget 对象时**返回 0**（诚实拒绝），不伪造 id。
- 挂载失败时 `unregister`，不留孤儿 widget。

## C. 过程中发现并修复的 3 个既有缺陷

### C-1. 缺陷：trait 的 `create_widget(kind_str, …)` 两个后端都没实现

**发现方式**：我给新入口写的测试失败：

```text
assertion `left != right` failed: a primitive-mapped kind must still create a widget
  left: 0
 right: 0
```

**取证**：

```bash
grep -n "fn create_widget" src/control_backend/native.rs   → 无
grep -rn "fn create_widget" src/control_backend/custom/    → 无
```

两者都落到 `trait_def.rs:33` 的默认实现 —— **无条件返回 `0`**。

**处置**：在 `NativeControlBackend` 实现真实的按名分发（21 个规范名 → 对应 `Platform::create_*`），
未知名字记 warn 并返回 `0`（不静默）。这样按名创建是**真实可用**的，而不是永远拿到 `0`。

### C-2. 缺陷：`embedded` 下 dialog/menu/view 的 `create_*` 引用不存在的 `WidgetKind` 变体

**发现方式**：接线后 `cargo check --lib --no-default-features --features embedded` 报 10 个错误：

```text
error[E0599]: no variant named `MessageBox` found for enum `WidgetKind`
error[E0599]: no variant named `ListView` found for enum `WidgetKind`
...
```

**根因**：这些变体在 `widget/kind.rs` 中被 `#[cfg(not(any(feature = "mini", feature = "embedded")))]`
门控（即 `full_widgets`），但 `lib.rs` 的 `create_message_box` 等只门控 `not(mini)` —— 于是
`embedded` 下"函数在、变体不在"。**这是既有不一致，只是之前函数不引用变体所以没暴露。**

**❌ 我先尝试的错误修法**：把这 9 个函数改成 `#[cfg(full_widgets)]`。
**为什么错**：这会让这些函数从 `embedded` 的公开 API **消失**，是破坏性变更（原则 #21 禁止）。

**✅ 正确修法（原则 #53：能力差异用运行时表达，不上升为 API 形态）**：
函数保持 `not(mini)` 门控（API 面不变），用一个 **profile 感知的 kind 别名**替代直接引用变体：

```rust
/// `WidgetKind::MessageBox` where available, else the always-present fallback.
#[cfg(full_widgets)]
const KIND_MESSAGE_BOX: widget::WidgetKind = widget::WidgetKind::MessageBox;
#[cfg(not(full_widgets))]
const KIND_MESSAGE_BOX: widget::WidgetKind = widget::WidgetKind::Panel;
```

`Panel` 在每个 profile 都存在且是容器面，作为降级替身；调用点仍是一句无条件表达式。
共 9 个别名（MenuBar/Menu/ToolBar/StatusBar/ListView/MessageBox/FileDialog/ColorDialog/FontDialog）。

### C-3. 缺陷：`kind_name` 依赖 `WidgetFactory`，在 `embedded` 不存在

**发现方式**：同一次 `embedded` 构建：

```text
error[E0433]: cannot find `WidgetFactory` in `widget`
```

**处置**：`kind_name` 的 primary 路径用 `WidgetFactory::capability_by_kind(kind)`（与工厂分发
同一张表，保证不漂移），并对 `embedded`/`mini` 提供 `Debug` 名回退：

```rust
#[cfg(any(feature = "desktop", feature = "tablet", feature = "mobile"))]
if let Some(capability) = widget::WidgetFactory::new_with_defaults().capability_by_kind(kind) {
    return capability.canonical_name.to_string();
}
alloc::format!("{kind:?}").to_lowercase()
```

## G. 诚实边界（未做 / 未验证项）

1. **`mount_custom_widget` 仍作为独立公开函数存在**。
   它与 `create_widget_of_kind` 的 `CustomRequired` 分支职责重叠。本轮**未合并**，因为：
   ① `create_widget_of_kind` 已覆盖"按 kind 创建"的主路径；
   ② `mount_custom_widget` 面向"我已经有一个 `Box<dyn Widget>`，直接给我托管"的场景，
   两者参数形态不同，强行合并会让签名变复杂。
   **记录为后续项**：可考虑给 `mount_custom_widget` 加 `#[doc(hidden)]` 或标注为底层 API。

2. **`SelectionMode` 三处重复未合并**（上一轮遗留）。
   取证：`app::SelectionMode`(Single/Multi/Extended/None)、
   `list_view::SelectionMode`(Single/Multi/Extended)、
   `listbox::SelectionMode`(NoSelection/SingleSelection/…)。
   三者**变体集合不一致**，合并需要决定以哪套为准并调整调用点 —— 属独立小任务，本轮未做，
   以免与接线改动混在一起难以回滚。

3. **未在本机验证 Windows / Linux 原生呈现**：Windows 仅 `cargo check` 交叉编译，
   Linux/GTK 未实跑。§E-4 证据全部来自 Cocoa。

4. **`EchoMode`/`ChartType`/`ViewMode` 的"同名"经取证判定为不同层不同语义，未合并**：
   - `EchoMode`：`platform::EchoMode`(3 变体，跨层 API 类型) vs `lineedit::EchoMode`(4 变体，含 `PasswordEchoOnEdit`)
   - `ChartType`：mini_chart(2) / special_widgets(4) / chart engine(5) 三处变体集不同，属分层而非重复
   - `ViewMode`：list_view(List/Icon/Details/Thumbnails) vs mdiarea(SubWindowView/TabbedView) —— 语义不同，仅命名撞车
   **判定依据是变体集合实测，不是名字相似**（原则 #51）。

5. **未复现的 flaky 测试**：本轮未出现；历史记录现象（`log-20260913-2.md` §P-5）仍
   **未修复、未掩盖**。
