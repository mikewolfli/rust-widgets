## 2. 要求 3：金融控件核查与修复

### 2.1 起点：一个「根本编译不过」的后端（实跑发现）

按用户「金融控件好像有问题」的指引，先**实跑**而不是读代码：

```
$ cd demo/finance && cargo build
error[E0599]: the method `position` exists for reference `&gtk::gdk::Event`,
 but its trait bounds were not satisfied
 --> src/platform/linux/canvas.rs:174:41
```

**根因（证据链）**：
- `gtk-0.18.2/src/auto/widget.rs:3899`：
 `fn connect_touch_event<F: Fn(&Self, &gdk::Event) -> ...>` —— 回调收到的是**通用** `gdk::Event`。
- `gdk-0.18.2/src/event_touch.rs:21`：`pub fn position(&self)` 定义在**具体类型** `EventTouch` 上。
- 因此 `event.position()` 在通用类型上**不存在**；该文件在 `gtk-native` 下从未编译通过
 （这就是用户说的「金融控件有问题」的第一层——Linux 桌面 demo 根本构建不起来）。

**修复**：先用 `event.downcast_ref::<gdk::EventTouch>()` 收窄，再读 `position()` / `event_sequence()`。
**验证（实跑）**：`cd demo/finance && cargo build` → `Finished dev profile`；
`cargo test` → 12 passed（本轮后为 15，见 §5）。

### 2.2 🔴 真缺陷 A（全库级）：`render_frame` 未扣除控件绝对原点

这是本轮**最重要的发现**，且**影响所有自绘控件**，不限于金融。

**取证（实跑探针，见反向注入 §2.5）**：把 `CandlestickChart` 放在 `(12, 42)`，
用 200×120 的 frame 渲染：

```
修复前：first painted pixel = (20, 44) ｜ blank rows at the top = 42 ｜ painted = 42.0%
修复后：first painted pixel = (8, 2) ｜ blank rows at the top = 2 ｜ painted = 56.7%
```

**根因（证据链）**：
- 控件几何是**绝对坐标**（`src/widget/runtime.rs:448-453` 模块文档明写；
 `widget_at` 也按绝对坐标命中，见 `:505-507`）。
- `render_frame`（`runtime.rs:1414`）建立的是 `size.width × size.height`
 （即**控件自身盒子**）的后备缓冲，而 `RenderContext::new`（`surface.rs:196-197`）
 初始 offset 为 `(0, 0)`。
- 于是控件在 `(12, 42)` 处绘制时，像素落在自己 frame 的 `(12, 42)` 之外的位置：
 **顶部留出与 `geometry.y` 等高的空白带，右下角被裁掉**。
- **为什么全库测试没抓到**：`runtime.rs` 的测试 fixture（`sample_editor` 等）
 一律用 `Rect::new(0, 0, ..)` —— 原点为 0 时该缺陷恰好不可见（冰山法则 #2 的典型）。

**修复**：`render_frame` 与 `render_frame_incremental` 在绘制前
`context.push_offset(-origin.0, -origin.1)`；增量路径必须在**裁剪矩形之前**推入，
因为裁剪矩形同样是绝对坐标。新增私有助手 `frame_origin(id)`。

**影响面（诚实陈述）**：任何 `geometry.x/y != 0` 且走 `mount_surface`/`render_frame` 的
自绘控件此前都会错位；金融 demo 的 7 个面板全部命中，故用户会看到「金融控件有问题」。

### 2.3 🔴 真缺陷 B：`DepthChart` 用一个档位集合算刻度、用另一个画曲线

**取证（实跑探针）**：一个 `quantity = 0.0` 的档位（**交易所常态**）即可让**整条曲线消失**：

```
修复前：colours in the pane = [[18, 22, 28, 255]] ← 只剩背景色
 curve() = [DepthPoint { price: 99.0, cumulative: 100.0, side: Bid }]
修复后：pane 含 [38, 166, 91, 255]（bid 曲线色）✅
```

**根因（三个耦合点，均在 `depth_chart.rs`）**：
1. `draw_step_curve` 的循环用 `continue` 跳过不可用档位，而 `previous` **只在绘制过的点上赋值**
 → 若唯一的可用档位是第一档，则**一个线段都不画**（曲线整体消失）。
2. `max_cumulative()` 与 `price_bounds()` 仍把被跳过的档位计入
 → 刻度被「永不绘制」的数据撑开，NaN 档位更会让 `price_bounds` 返回 NaN 而直接 `return`。
3. 单一价格的边界（`high <= low`）直接 `return`，使单档位/单侧书**必然空白**。

**修复（根因，而非补丁）**：新增 `plottable_levels(side)` 作为**唯一的档位集合**，
供 `max_cumulative` / `price_bounds` / `curve()` / 绘制循环**共用**；
单点情况画一条从基线到其总量的竖线；退化价格区间按 `PriceAxis` 同样的约定加宽。

### 7.1 问题：三个 demo 的坐标全是硬编码字面量（实跑取证）

|---|---|
| `demo/control` | 每个控件的 `(x, y, w, h)` 都是 `new_button("X", 20, 20, 150, 32)` 这类字面量；工具栏/状态栏宽度写死 `760` |

### 7.2 接入方式（三个 demo 各自的正确结构，由 API 约束决定）

关键约束（取证而得，不是风格选择）：

- **窗口只能有一个活动布局**（`WindowHandle::set_layout`：「Only one layout can be active at a time」）；
- **布局项只能是控件 id**，没有「子布局」这种项 → 布局不能直接嵌套；
- **`PanelHandle` 与 `WindowHandle` 可 `set_layout`**；`ToolBarHandle` / `ScrollAreaHandle` **不可**；
- **`GridLayout` 的格子不能跨列**，而 **`BoxLayout` 纵向模式会把每项都给到全宽**。

所以三个 demo 采用了各自匹配的结构：

| demo | 结构 | 为什么 |
|---|---|---|
| `control` | 窗口级纵向 `BoxLayout`（控件区 `Panel` + 日志标题 + 4 行日志）；`Panel` 内部挂 `GridLayout` 7×3（列权重 3:3:2） | 日志需要**全宽**，而网格格子不能跨列；`Panel` 是唯一能承载子布局的容器 |
| `code_editor` | 窗口级纵向 `BoxLayout`：工具栏（固定 36px）+ 编辑器（伸展，权重 10）+ 状态栏（固定 26px） | 编辑器是挂载型控件，但其 `ObjectId` 可参与布局 |
| `finance` | 两列各自一个纵向 `BoxLayout`（左 45:15:20:20，右 30:34:36）；`Layout::compute` 把布局算出的高度**读回**后再统一配 x/宽度 | 面板仍需**共享索引轴**（同 x 同宽），这部分不能交给布局；而「哪个面板多高」交给布局 |

### 7.3 测试发现的**两处真实缺陷**（新测试当场抓到）

| # | 缺陷 | 现象 | 根因 | 修复 |
|---|---|---|---|---|
| 1 | `code_editor` 初始矩形与布局不一致 | `editor_rect()` 高度 592，布局给 614 | 布局的坐标空间是**菜单栏之下的客户区**，高度里本无菜单栏；`editor_rect()` 多减了一次 `MENU_H`，且漏算 `STRIP_GAP` | 高度不减去 `MENU_H`，并计入 `STRIP_GAP * 2` |
| 2 | **`control` 日志区只有一列宽**（414px 而非 1120px） | 测试 `the_log_area_spans_the_full_width` FAILED | 原设计把所有东西都塞进 `GridLayout`，而**网格格子不能跨列** | 改为外层 `BoxLayout`（纵向会给全宽）+ 控件区用 `Panel` 承载网格 |

### 7.6 🔴 后续修复：`code_editor` 缺少项目树，编辑器独占了整个宽度

> 用户反馈：**「code_editor 好像有问题，code 编辑和左侧 project tree 宽度比例不对」**

#### 取证：根本没有项目树（实跑）

即：这个 demo **从来只有一个全宽的编辑器**，左侧没有任何树控件。用户看到的
“宽度比例不对”= 比例实际是 `0 : 1`（旧日志：`[Mount] CodeEditor rect=(0,64, 980, 614)`，
宽度就是整个窗口）。

#### 修复：项目树 + 权重化分栏

| 项 | 做法 |
|---|---|
| 项目树 | `TreeView` + `VecTreeModel`（`src/widget/view_widgets/tree_view.rs`），11 行目录结构，用缩进表达层级（模型暴露的是可见行序列） |
| 宽度比例 | `SPLIT_WEIGHTS = (1, 4)` —— 权重而非像素。写死“树 240px”会让窗口变宽时多出的宽度尽归编辑器，树越来越窄 |
| 两侧下限 | 树 `TREE_MIN_W = 140`、编辑器 `EDITOR_MIN_W = 320`；空间不够时 `BoxLayout` 按比例摊派（依赖 §4.1 修好的 “Σmin > 可用宽度” 路径） |
| 窗口尺寸 | 980×680 → **1100×720**，给工具窗口合理的初始比例 |
| 状态栏 | 改为横跨整个窗口，而不是只对齐编辑器 —— 它报告的是整个应用的状态 |

#### 一次性应用两层布局（避免“只应用了一层”）

窗口只能有一个活动布局，且布局项只能是控件 id（无「子布局」项），所以分两层：

1. **外层** `build_window_layout`：纵向三行（工具栏 / 分栏 / 状态栏）；
2. **内层** `build_split_layout`：横向两栏（树 / 编辑器），按 `SPLIT_WEIGHTS` 切。

两层的桥梁是 `split_row_rect_in()` —— 它**跑一遍外层布局再把分栏行的矩形读回来**，
而不是再抄一遍“工具栏 + 间距”的减法。所以两层不可能对同一块区域持有不同看法。
`apply_layout()` 把两层封在一起，确保不会出现“改了一层忘了另一层”。

> 面板占位会退化成“首次手动设一次几何”，窗口布局随后就不驱动分栏了。
> 改用保留 id `SPLIT_ROW_ID = u64::MAX` 占位（对不存在的 id 调 `set_widget_geometry` 是无操作）。

### 7.7 🔴 后续修复：`control` 控件全部不可见 + 改为标签页版式

> 用户反馈：**「demo 的 control 有问题，怎么控件都没列出来，而且，能否多布置一些 control，
> 采用 tab 切换，在不同 tab 里布局不同控件啊」**

#### 7.7.1 根因：控件全部被算成 0×0（两个库级缺陷叠加）

运行日志显示 20 个控件**全部创建成功**，所以问题不在创建。逐个检查几何才现原形：

```
cell <id> must be laid out with a real size, got Rect { x: 0, y: 0, width: 0, height: 0 }
```

两个缺陷叠加导致：

| # | 缺陷 | 位置 | 说明 |
|---|---|---|---|
| 1 | **`new_window` 不记录窗口尺寸**，导致 `set_layout()` 静默无效 | `src/app/app_core.rs:253` | `apply_window_layout` 从 `WINDOW_STATES` 读窗口大小，而该表**只**由 `WindowHandle::set_geometry` 写入。`new_window(..)` 不写，所以创建后立即 `set_layout(..)` 时表里没有尺寸 → 直接 `return`。**没有任何日志或错误。** |
| 2 | **`apply_panel_layout` 读错了几何来源** | `src/app/handle.rs:2173` | 它从镜像表 `PANEL_STATES` 读面板矩形，而窗口布局通过 `set_widget_geometry` 定位面板——**不写那个表**。所以面板被正确摆放，但它的子布局仍按创建时的 `(0,0,0,0)` 计算，且**永不重算**。 |

两者叠加的完整链条：

```text
new_panel(0,0,0,0) → PANEL_STATES 记下 0×0
panel.set_layout(grid) → 用 0×0 算所有格子 → 全部 0×0
win.set_layout(outer) → WINDOW_STATES 无尺寸 → 直接 return
（什么都没发生） → 控件全在，但全是 0×0，即“没列出来”
```

#### 7.7.2 修复（两处，都是库级）

| 修复 | 做法 |
|---|---|
| `new_window` 记录尺寸 | 新增 `WindowHandle::record_created_geometry(..)`（镜像表对本模块私有，构造函数路径写不进去），在 `new_window` 中调用。**`new_window(..)` 后立即 `set_layout(..)` 现在真的生效。** |
| 面板布局按实际几何重算 | ① `apply_window_layout` 定位一个子控件后，若它挂了布局（`widget_hosts_a_layout`），再跑一次它的子布局（`apply_panel_geometry`）；② `apply_panel_geometry` 为空面积时**只记录不布局**（否则会把子控件几何覆盖成 0）。 |

> 📌 曾经的尝试：改为读 `runtime::geometry_of(panel)`。**不可行** —— 该注册表只装 *mounted* 控件，
> 而 `create_panel` 建的是后端原生控件，查不到。所以镜像表仍是必要的，关键是两个写入方
> 都要汇入同一个函数。

#### 7.7.3 版式改造：标签页 + 每页自己的布局

按要求改为 **6 个标签页**，每页一个 `Panel`，**每页挂自己的 `GridLayout`**：

| Tab | 标题 | 网格 | 控件（数量） |
|---|---|---|---|
| 1 | Buttons | 2×3 | Click Me / Toggle / Disabled + Save / Reload / Clear（**6**） |
| 2 | Toggles | 4×2 | CheckBox / Tri-state / Checked + Radio ×3（**6**） |
| 3 | Text | 4×2（列 3:2） | LineEdit ×3（普通/密码/只读）+ SpinBox + 预填（**5**） |
| 4 | Selection | 3×2 | ComboBox ×2 + ListBox（**3**） |
| 5 | Range | 3×2 | Slider 横向 + Slider 纵向 + ProgressBar + indeterminate（**4**） |
| 6 | Containers | 2×2 | ScrollArea + Panel + Frame + MessageBox（**4**） |

共 **28 个控件**（原 20），且每页的网格形状可以不同（2×3 / 4×2 / 3×2 …）。

**切换机制**：页面彼此重叠（同一块矩形），切换 = 目标页 `set_visible(true)`、其余 `set_visible(false)`。
不需要重算几何，所以切换是瞬时的。

**三层布局各管一件事**：

```text
窗口 BoxLayout（纵向） ── 工具栏 / 标签条 / 页面区 / 日志 / 状态栏
 ├─ 标签条 BoxLayout（横向）── 6 个等宽标签按钮

```

只有当页面区不是一个 `BoxLayout` 项（否则它们会纵向排开），而是只把**第一页**
作为“尺寸代理”交给纵向布局，其余页面在布局跑完后对齐到同一矩形（`align_pages`）。
矩形来自 `page_area_rect()` —— 跑一遍同一个布局读回答案，而不是另抄一遍减法。

| 方向 | 原实现 | 现在 |
|---|---|---|
| **程序**调用 `set_geometry(w,h)` 改窗口 | ✅ 会重跑布局 | ✅ 不变 |
| **用户拖拽窗口边缘**改大小 | ❌ **不会** | ✅ 已补全 |

原实现的缺口：`WindowHandle::set_geometry` 会重跑布局，但**用户拖动窗口边框**走的是
另一条路——**操作系统**改窗口，然后通知后端。这条路上**没有任何东西到达布局层**，
所以每个子控件都停在为旧尺寸算出的几何上。

这与 wxWidgets 的 `wxSizer` 语义对齐：`wxSizer` 也不是自己监听窗口，而是
`wxEVT_SIZE` 到来时 `SetSize`/`Layout`。本库现在补的正是**那个事件源**。

### 11.2 新增的公共契约（不破坏既有 API，规则 #21）

- `WidgetTriggerKind::Resized = 5` —— 新增枚举值，原有 0..=4 不变。
- `queue_resize_trigger(window_id, w, h) -> bool` —— 唯一的「用户改了窗口大小」入口。
- `window_client_size(window_id) -> Option<(u32, u32)>` —— 读回尺寸（事件只带 id，
 尺寸必须另行读回）。

### 11.3 🔴 关键架构发现（实跑取证，写下来避免后人重犯）

**窗口尺寸的权威存储在 ControlBackend，不在 BackendState。**

最初把记录放进 `BackendState`（`src/platform/state.rs`），测试直接失败：
`window_client_size` 返回 `None`、`queue_resize_trigger` 返回 `false`。

根因（读源码确认，非猜测）：app 层轮询的是 **control backend 的队列**
（`src/lib.rs:1407` → `control_backend::get_control_backend().poll_widget_trigger_event()`），
而 `create_window` 也走 **ControlBackend**（`CustomPaintControlBackend`），**不是** Platform。
所以窗口从不进入 `BackendState`，写在那里的尺寸没有人会读到。

修正：记录移到 `CustomControlState.window_client_sizes`，platform 侧方法**转发**。
`dispatch_trigger` 也不再调用 `get_platform().window_client_size()`（必返回 `None`），
改用 `crate::window_client_size()`。

### 11.4 🔴 本轮新发现并修复的真缺陷（3 个，都不是「接线」而是逻辑错）

#### 缺陷 A：**回收的 widget id 继承了死窗口的尺寸**

widget id 由 `widget::runtime::NEXT_ID` **按线程**分配，起点固定。于是同一线程上
后建的窗口会拿到**和先建窗口相同的 id**；而 `window_client_sizes` 是**进程级** map，
键就是 id。结果：**新窗口报告的是另一个已消失窗口的尺寸**。

实测取证（构建两个窗口，第二个从未 resize）：

```
PROBE-A-resized id=...649 size=Some((1300, 600)) ← A 被 resize 到 1300
PROBE-B-created id=...649 size=Some((1300, 600)) ← B 复用了同一个 id！
```

`window_client_size` 先命中这个 map、再回退到几何，所以**这个陈旧值压倒了正确的几何**
（B 的真实几何是 `640×480`）。

修复两处（都是根因，不是补丁）：
1. `create_window` 创建时**清除该 id 的记录** —— 让「这个窗口是否被 resize 过」
 成为**窗口**的属性，而不是**那个整数**的属性。
2. `destroy_widget` 释放时**移除该 id 的记录**（与 IME / accessibility 同处清理）。

#### 缺陷 B：**id 分配按线程 → 两个线程产出相同 id**

不只是测试问题：control backend 是**进程级单例**，宿主若跨线程建窗口，
第二个线程的窗口会读到第一个线程的记录。这与 11.4-A 是同一类错误的两个入口。

修复：id 改为**全局唯一**的**块分配**（`reserve_id_block` + `AtomicU64` 高水位）。
每线程预留 `0x1_0000` 个 id 的块并本地发放——**常见路径仍是无锁的线程本地读**，
但进程内一个 id 永远只对应一个窗口。耗尽时**报告失败**而非回绕复用
（回绕会让新窗口命中旧记录，正是缺陷 A）。

#### 缺陷 C：`gtk-native` 下 `code_editor` demo **必然 panic**

```
thread '<unnamed>' panicked: GTK may only be used from the main thread.
```

根因：demo 用 `app.run_async()` 把平台循环丢到**后台线程**，而 GTK 3 绑定唯一主线程，
`gtk::main()` 必须跑在主线程。

原注释写的是「平台循环跑后台、主线程轮询」，这在 GTK 下**方向正好相反**。
修复：**主线程跑平台循环**，**轮询搬到后台线程**（`poll_*` 只读队列、不需要平台 API，
因此可以安全地跨线程）。退出时用 `AtomicBool` + `join` 保证最后几个菜单触发不丢。

实测：修复后 `panicked` 计数 **0**，且分栏几何为
`ProjectTree rect=(0,38,220,654)` / `CodeEditor rect=(224,38,876,654)`，即 **220:876 = 1:4**。

### 11.6 各平台 resize 通知的**诚实**接线状态（规则 #17/#18）

| 平台 | OS 回调 | 状态 |
|---|---|---|
| **Linux / GTK** | `connect_size_allocate` | ✅ 已接线 |
| **Windows** | `WM_SIZE` + `GetClientRect` | ✅ 已接线 |
| **macOS** | `windowDidResize:`（`NSWindowDelegate` + associated object 存 id） | ✅ 已接线，**但本机无法编译验证**（见下） |
| **Wayland** | `xdg_toplevel` `Event::Configure` | ✅ 已接线 |
| **WASM** | `ResizeObserver` 观察 canvas（**非** `window.onresize`） | ✅ 已接线 |
| **Android** | 无库可订阅的回调（归宿主 `OnLayoutChangeListener`） | ✅ 新增 JNI 入口 `nativeNotifyResize`，**由宿主上报** |
| **iOS** | 无（`UIWindow` 填满 scene，变化归宿主的 view controller） | ⚠️ **由宿主上报**，注释已写明「本后端不持有 UIKit 句柄，故无法订阅」 |
| **Harmony** | 无（变化归宿主 ArkTS `onAreaChange`） | ⚠️ **由宿主上报**，同上 |

**WASM 为什么用 `ResizeObserver` 而不是 `window.onresize`**：库的客户区是 **canvas**，
不是浏览器窗口。页面可以只改 canvas 尺寸而窗口不变（侧栏展开、flex 布局），
也可以窗口变了但 canvas 没换尺寸。`ResizeObserver` 报告的正是**那个真正变小的元素**。

**iOS / Harmony 不假装有回调**：这两个后端刻意不持有 UIKit / ArkUI 句柄
（`create_window` 的注释已说明），凭空订阅就要去持有它声明不持有的对象。
所以诚实标注「宿主上报」，并由 `window_client_size` 回退到创建尺寸，
使「宿主没上报」这件事**不会表现为异常**。

### 11.12 一句话结论（第 11 节）

用户问「layout 能否让控件随窗口缩放」——**答案是「原本两半只做了一半」**：
程序改尺寸有效，**用户拖窗口边框无效**。补全过程连带挖出 **7 个真缺陷**
（3 个运行期逻辑错、4 个编译级），其中「回收 id 继承死窗口尺寸」与
「id 按线程分配」是**同一类错误的两个入口**，只修一个仍会被测试放过——
这正是原则 #89 反向注入的价值：它证明了**天真的修复是假的**。

现在 8 个平台（含 WASM）都有 resize 通知路径：5 个由 OS 回调驱动，
Android / iOS / Harmony 三个**诚实标注为宿主上报**（因为它们确实没有库可订阅的回调，
而假装订阅就要去持有各自注释里声明**不持有**的原生句柄）。

收尾：**5+ 档 profile 全绿 + 库 4915 条全过 + demo 53 条全过 + 门禁 31/32**
（唯一 FAIL 需 macOS 主机）+ **macOS 明确标注未在本机验证**。
