## 2. cookbook 与实际项目对齐（实质内容，不只是数字）

### 2.1 新增 Media 模块章节（三语）

`api-reference.md`（en / zh-CN / zh-TW）此前声称“module-by-module 覆盖整个公开 API”，但没有
`audio` / `video` / `image` 三个模块。本轮各语言新增 `Media Modules (`audio`, `video`, `image`)`
章节，内容严格取自源码签名：

- `AudioEngine`：`new`、`load`、`load_async`、`is_loading`、`poll_load`、`wait_for_load`、
  `play`/`pause`/`stop`、`set_volume`/`volume`、`tick`、`current_samples`、`duration_seconds`、
  `play_to_device`（`audio-output`）；
- `VideoEngine`：`open`、`with_decoder`、`metadata`/`duration`、`play`/`pause`/`stop`、`seek`、
  `tick_frame`、`next_frame`/`step_frame`、`take_dropped_frames`、`clock`/`clock_mut`；
- `image::decoder`：`decode`、`decode_async` → `ImageDecodeJob::wait`/`try_take`、
  `decode_to_rgba8`、`decode_animation`、`detect_format`；
- 三个模块的特性门（`audio`/`video`/`image`）与 2.8.14 起的“后台解码 + 同步回退”契约。

TOC 相应插入第 33 项，后续三项顺延（33→34、34→35、35→36）。

`pdf-encryption`、`js-engine`、`web-http`。

### 9.1 性能：信号发出链（CORE-N02）

`Signal::connect` 的公开签名是 `FnMut(Arc<T>)`，所以每次 `emit` 都 `Arc::new(value)`，延迟投递再分配一次。`Signal` 是已发布 API（2.8.14），按原则 #21 不能破坏签名。

实现为非破坏式双调用约定：

- `SlotCallback::{Owned,Borrowed}` 共存于同一槽表；`Owned` = 原 `Arc<T>` 回调，`Borrowed` = 新增 `connect_ref(FnMut(&T))`。
- `EmitValue` 先借用 `emit` 已拥有的值；只有当真正触达 `Owned` 槽时才 `shared()` 惰性构造**一次** `Arc`，后续槽复用。
- 延迟队列 drain 用 `call_owned(T)` 直接 move 进 `Arc`，不再 clone。
- 事件转发热链全部迁到借用槽：`EventSignalBinder::forward_unit/forward_mapped`、`CustomSignalHub::connect`、`EventSignalRef::unit/mapped`。**事件路径每次 emit 少 1 次堆分配。**
- `GenericSignal` 的所有 `connect*` 内部也改走借用槽：单位信号（`redraw_requested`、`layout_requested`、`clicked`、`closed` 等）的 `emit` 不再分配 `Arc<()>`，且**零调用点改动**。

边界（实测）：全仓 435 个 `connect` 调用中 **373 个在测试模块**，生产仅 **48 个**（显式 `Arc<T>` 13 个）；它们多数要把拥有载荷交给用户回调，保持 Owned 语义是正确选择。

### 9.2 性能：事件循环等待（CORE-N04）

原实现 `lock(&queue).dequeue_timeout(wait)` 在**持有队列互斥锁**期间阻塞最多 16 ms。现改为：

```text
generation = frame_wait::generation()   // 先取唤醒代际
queued = lock(&queue).dequeue()          // 短锁
if none:
    frame_wait::wait_after(generation, wait)   // 锁外等待
    lock(&queue).dequeue()                     // 再检查
```

代际在检查前读取，关闭了「检查为空 → 生产者在窗口内入队 → 等待睡满」的丢唤醒窗口；等待由 `EventSender::post_with_priority` 的 `wake()` 唤醒。

### 9.3 性能：i18n 与对话框绘制（CORE-N05）

### 11.1 决策：开关保留，默认开启

§10 的默认关闭有一个真实代价：产品一旦打开 `App`，菜单永远是「接线前」的样子，模块等于死代码；而把它改成需要宿主手动打开的 opt-in，用户实测就是一个**没有任何调用者的开关**——用户明确否决了这种形态。

裁决为 **Option A**：

- **产品默认 = 开启**：`MenuConfig::new()` 直接 `enabled: true`，`reset_to_defaults()` 同样回到开启（重置策略 ≠ 退出策略）；
- **开关仍然存在**：宿主若要逐字节的接线前渲染，一次 `menu_config::set_enabled(false)` 即可，不必重置八个字段；
- **验证路径不受宿主硬件影响**：导出/普查显式安装固定的验证策略。

### 11.2 确定性：`MenuConfig::verification()`

新增两组固定记录：

- `HardwareCapabilities::verification()`（`src/menu_config/types.rs`）：Integrated GPU、无 VRAM 测量、GPU/CPU 各 60、8 GiB、非电池、Medium；
- `MenuConfig::verification()`（`src/menu_config/config.rs`）：`enabled = true`，然后调用 `apply_hardware_defaults()` **由上面的能力记录推导**，而不是再手写一遍八个值。这样「策略」和「它声称模拟的硬件」不可能漂移（§10 的重复定义是同类风险）。

全局安装入口（`src/menu_config/manager.rs`，经 `mod.rs` 导出）：

```rust
pub fn install_policy(config: MenuConfig);
pub fn use_verification_policy();
```

`install_policy()` 用 `MenuConfigManager::from_config()` 包装，`auto_adjust = false`——否则后续 `refresh_hardware_detection()` 会重新探测宿主并把钉死的策略悄悄换掉。`init()` 只在槽为空时填充，因此**先安装的策略能活过 `App::init`**。

**顺手修掉的真实 bug**：`refresh_hardware_detection()` 原来在重建后写 `user_overrides.enabled = Some(true/false)`。但进入该分支的前提正是 `!has_user_overrides()`——所以这是一条**假覆盖**。开关默认关闭时它只是「刷新一次后永久把开关钉成 true」；默认开启后更直接：开关值本来就是 true，于是变成「写一条与默认值相同的覆盖 → `has_user_overrides()` 永远为真 → 后续所有刷新全部失效」。现在只重建 `MenuConfig::new()`，并加测试 `refresh_hardware_detection_keeps_the_default_and_records_no_override` 钉住。

调用点：`examples/export_control_svgs.rs::main`、`examples/control_rendering_census.rs::main` 在构造任何控件之前安装（`#[cfg(feature = "advanced-widgets")]` 守护）。

**刻意没有做的事**：没有在 `MenuConfig::new()` 里加 `#[cfg(test)]` 分支返回固定策略。原因有实证：`hardware_detection_delegates_to_platform_backend` 依赖真实的 `new()` 去证明探测走了 `Platform` 后端，而集成测试是独立 crate（库不以 `cfg(test)` 编译），那个分支既救不了它们也骗了单元测试。

## 15. 第九轮（2026-10-22）：LAY 批次 2/3/4 收口 + 全量验证

### 15.1 本轮目标

第八轮结束时，LAY 还剩三处结构性工作：flex 的 `AlignContent`/行-列 gap、`flow`/`wrap` 的 `arrange`、以及 `flow`↔`wrap` 的断行收敛（N08）。本轮把它们与 N10 的逐格对齐一起做完，并在**全部批次结构完成后**只跑一次全量。

### 15.2 N08 的结论：收敛的是实现，不是类型

第八轮的失败尝试是「让 JSON `flow` 直接构造 `WrapLayout`」。失败原因是真实的，但结论被过度推到了类型层：声明式运行时 `apply_layout` 调用的是 `Layout::update`，**没有 hints 通道**，而 `WrapLayout` 当时只从 `set_child_size` 取尺寸 → 所有子项 0×0。

本轮改为收敛**算法**：

- `wrap.rs` 新增 `pub(crate) fn break_lines` / `place_lines`，把断行判定、行内对齐（含负 spacing、SpaceBetween/SpaceAround 的余量分配）、交叉轴块对齐集中到一处；
- `WrapLayout` 传入 `set_child_size` 的尺寸，`FlowLayout` 传入 `child.size_hint()` 的尺寸；
- `FlowLayout` 的 `layout_horizontal` / `layout_vertical` / `apply_alignment`（约 190 行）删除，`layout_sized` 只负责把「尺寸从哪来」接上；
- JSON `flow` 仍构造 `FlowLayout`（类型不变，避免 0×0），但已经不存在第二份断行实现。

证据不是「看起来一样」：`flow_and_wrap_agree_on_the_same_sizes` 对 5 种对齐 × 2 个方向 × 3 种 spacing（0/+5/−3）× 4 个尺寸逐 id 比对矩形；`FlowLayout` 既有的 27 条语义测试（负 spacing、SpaceAround 对称性、逐行对齐、padding 饱和等）在替换后全绿。

### 15.3 N01：hints 的三块补齐

- `ChildInfo::resolved_size(fallback)`：per-axis「hint 有 pref 就用，没有就回退」。这是 `wrap`/`flow` 能同时服务「已迁移」和「部分迁移」调用方的关键——`AxisHints::unconstrained()` 的 `pref == 0` 表示「没意见」，不能当成「要 0 像素」。
- `WrapLayout::arrange`：size 表来自 hints，经临时 sized layout 复用 `compute_rects`，不复制求解器。
- `FlowLayout::{arrange, update_with_context}`：`arrange` 优先 hints、回退 `size_hint`；`update_with_context` 补上 `max(layout_scale, font_scale)` 的 gap/padding 缩放（此前 flow 在缩放窗口里保持标称间距）。

### 15.4 N05：flex 的三处降级

- `AlignContent`（FlexStart/FlexEnd/Center/SpaceBetween/SpaceAround/Stretch），默认 `FlexStart` 刻意**不是** CSS 的 `stretch`：本布局历史上就是「行从交叉轴起点开始、余量不用」，改默认会让每个已有换行布局位移。`Stretch` 显式启用。
- `row_gap` / `column_gap` 按 CSS 语义落在轴上：`Row` 方向的 `row_gap` 是**交叉轴**（行间）间距，`column_gap` 是主轴间距；`gap` 仍是两者回退值。
- `WrapReverse` 用「正向算偏移 + 镜像」实现，`FlexStart` 仍表示「行开始的那一侧」，而不是「永远靠上」。
- `Baseline` 的降级说明保留（`AlignItems::Baseline` 文档已写明等同 FlexStart）。

### 15.5 N10 与两个新发现

- `GridLayout::set_cell_alignment` / `cell_alignment`：逐格按 hints pref 收缩并定位；`Left/Right` 只改横轴、`Top/Bottom` 只改纵轴、`Center` 双轴；`remove_widget` 清理悬挂项。
- **新发现（已修）**：`arrange_body` 只做单行打包，而 `update_with_context` 转发到这里 → 窗口级换行 flex 在每次设备感知布局时退化回一行。现在 `wrap != NoWrap` 走同一个 wrapped 求解器，并换算 margins、应用触控下限。
- **新发现（已修）**：`break_lines` 原先每个候选都重算整行宽度（一行 n 项 → O(n²)），改为运行和；这是本轮唯一的算法级性能改动，行为由 flow/wrap 两侧测试共同钉住。

### 15.6 明确不做

- `LAY-N11`（拆 `flex.rs`）：与用户「拆分任务取消」裁定冲突，维持放弃。
- 不给 `center`/`aspect_ratio`/`keyboard_aware`/`constraint`/`absolute`/`splitter`/`uniform_grid` 写 `arrange` 覆盖：它们的盒子不由「子项想多大」决定，理由逐条写入 issue §22.7。

## 16. 第九轮补充：CORE-N02 复核（2026-10-22）

用户问「CORE-N02 这项啥意思」。复核后有两件事：一是这项的**原始缺陷确实已修**；二是旧文档里那句「约 400 个控件内部 connect」把**测试代码当成了控件代码**，需要纠正。

### 16.1 原始缺陷与当前机制

- 修复前：`Signal::emit` 第一行就是 `emit_inner(Arc::new(value))`——每次 emit 一次堆分配，连 `bool`/`i32`/`()` 也不例外。
- 现在：`EmitValue::{Borrowed,Shared}` + `SlotCallback::{Owned,Borrowed}`。emit 以借用起步；只有真的触达 `connect(FnMut(Arc<T>))` 的槽才 `clone + Arc::new`，且**一次 pass 只构造一次**。单位信号（`GenericSignal`）内部固定借用槽，所以 `clicked`/`closed`/`redraw_requested`/`layout_requested` 全程零堆分配。
- 并发延迟投递：队列存 `T` 而不是 `Arc<T>`（保持 `T: Send` 就能 `Send + Sync`），drain 时 `call_owned(T)` 直接 move 进 `Arc`，不多一次 clone。
- 单订阅快路径不建 snapshot；多订阅 snapshot 是 thread-local 复用。

### 16.2 「回调需要拥有载荷」的准确含义

`connect` 的公开类型是 `FnMut(Arc<T>)`，这是**语义承诺**：回调可以把载荷存起来、送去别的线程、做 `Arc::ptr_eq`、或投进延迟队列。这些用法都要求载荷活过 `emit`，所以 `Arc` 属于契约本身，不是可以“优化掉”的浪费。只读订阅方用 `connect_ref(FnMut(&T))` 显式 opt-in。

### 16.3 实测数字（纠正旧句子）

| 口径 | 总数 | 测试模块 | 生产 |
|---|---|---|---|
| `.connect(` | 450 | **439** | **11** |
| `connect` 家族（含 `_ref`/`_once`/`_scoped`/`_with_priority`） | 516 | **480** | **36** |

生产 36 处中 19 处是信号模块自己的定义/转发；16 处是真实信号订阅（1 处 `ActionRegistry::connect` 不是信号方法）。真实订阅里：

- `app/handle.rs` 5：2 个 `GenericSignal`（`clicked`/`closed`）+ 3 个 `connect_ref`（菜单）；
- 6 个视图控件 `connect_scoped`：全是 `GenericSignal::data_changed`；
- `capability` / `CustomSignalHub`：单位信号；
- `Action::triggered`：单位信号；
- **只有 `Action::toggled` / `enabled_changed`（`Signal<bool>`）仍走 `Owned`**，因为它们的公开签名就是 `Arc<bool>`。

所以“约 400”是测试模块的调用数，不是控件内部连接数；控件绝大多数是 emit 方。CORE-N02 因此从 PARTIAL 改为 **✅ FIXED（具名 API 边界）**。

### 16.4 两个可选项的处置

- **✅ 已实施**：`Action::connect_toggled_ref` / `connect_enabled_changed_ref`（`src/action/types.rs`）。只读订阅方走借用槽，不再为 `bool` 分配 `Arc`。
- **⏸ 评估后不做**：值变更走 `dispatch_trigger` 时，`get_widget_text` 每次触发产生 1 个 `String`，之后所有回调借用同一个 `&str`（CORE-11 的残留）。去掉它需要给 `ControlBackend`/`Platform` 加「写入调用方缓冲」方法（默认实现仍会分配，`native`/`macos` 另需覆写）+ `dispatch_trigger` 的 thread-local 暂存与重入回退，跨 6 个文件换来每个交互事件一个小 `String`；该路径不是每帧热路径，收益不值这个公共 API 面。
