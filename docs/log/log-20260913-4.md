## A. 任务 1：消除「自绘/原生」实现细节泄漏

### A-1. 问题定性（先取证）

`self_drawn` 描述的是**渲染机制**，不是**调用者意图**。它却出现在 crate 根公开 API：

```text
$ grep -rn "self_drawn\|SelfDrawn" src/ --include=*.rs | wc -l
119
```

**受害者实证** —— `demo/code_editor/src/app.rs` 修复前第 5-7 行，被迫向使用者解释
平台机制，**这正是原则 #35/#39 禁止的**：

```rust
//! 1. **自绘控件挂载**——`CodeEditor` 没有对应 OS 控件，通过
//! `WindowHandle::mount_self_drawn` 交给原生画布（macOS `NSView.drawRect:` /
//! Windows `WM_PAINT` / Linux `GtkDrawingArea::draw`）渲染。
```

一个只想放个代码编辑器的开发者，被迫知道三种 OS 的绘制回调名。

### A-2. 命名决策：`self_drawn`（机制）→ `custom`（意图）

选 `custom` 而非新造词的理由：`control_backend` 已确立 `CustomRequired` /
`custom_paint` / `custom_control_backend` 术语，改名后全项目一致，不引入第二套词汇。

| 旧名（机制） | 新名（意图） |
|---|---|
| `mount_self_drawn` | `mount_custom_widget` |
| `resize_self_drawn` | `resize_custom_widget` |
| `unmount_self_drawn` | `unmount_custom_widget` |
| `request_self_drawn_repaint` | `request_custom_repaint` |
| `supports_self_drawn` | `supports_custom_widgets` |
| `SelfDrawnHandle` | `CustomWidgetHandle` |
| `SelfDrawnMountError` | `CustomWidgetMountError` |
| `impl_self_drawn!` | 删除（零调用点，见 §B-1） |

`Platform` trait 的 5 个方法同步改名（macOS / Windows / Linux / Stark / Harmony 后端全部对齐）。

### A-4. 新增原则（把这次的教训固化成规则）

`docs/plans/principle.md` 新增 3 条，并把规则 #4 改写：

- **#4（改写）**：平台策略不变：控件优先映射到平台既有能力，映射不到时由 platform 层提供
 承载面。**调用方只表达"我要一个这样的控件"，不表达"用原生还是自绘"**。

- **#53（新增）🚫 能力缺失只能通过运行时 trait 方法表达，不得上升为 API 形态**。
- **#54（新增）🚫 同语义枚举全仓只能有一份定义**。

## B. 任务 2：缺陷清零

### B-1. 缺陷：`impl_self_drawn!` 宏是零调用点死代码（原则 #4）

**取证**：

```text
$ grep -rn "impl_self_drawn!" src/ demo/ tests/ examples/ --include=*.rs
（仅命中定义本身 src/widget/draw.rs:46）
```

同时它的文档是**错的**（原则 #18「文档欺骗」）：注释声称

```rust
/// Every widget that has an `impl Draw for X` belongs in its `impl Widget for X`:
```

但实际 6 个自绘控件（`chip` / `snackbar` / `terminal_view` / `gantt_widget` /
`code_editor` / `color_picker`）**全部手写 `as_draw_mut`**，无一使用该宏：

```text
$ grep -rn "fn as_draw_mut" src/ --include=*.rs | wc -l
7 ← 6 个控件 + 1 个 trait 默认实现
```

**处置**：删除宏（无消费者 + 文档误导），保留正确的 `Draw` trait 文档。

### B-2. 缺陷：`CheckState` 同语义枚举有两份（原则 #23 / 新 #54）

**取证**：

```text
src/app/handle.rs:22 pub enum CheckState { Unchecked, Checked, PartiallyChecked }
src/widget/base_widgets/checkbox.rs:12 pub enum CheckState { Unchecked, PartiallyChecked, Checked }
```

两份**变体集合完全相同、语义一致**，只差声明顺序。危害：① 新增变体只改一处必漂移；
② 调用方被迫做无意义转换。

**处置**：`app::CheckState` 改为 `pub use crate::widget::base_widgets::CheckState;`

```rust
/// Re-exported from [`crate::widget::base_widgets::CheckState`] — the widget layer
/// owns the canonical definition, and the handle layer names the same three
/// states. Keeping one enum means a value read from a handle and one read from a
/// widget are the same type; there is nothing to convert and nothing to drift.
pub use crate::widget::base_widgets::CheckState;
```

更关键的是：**这个缺陷现在会变成编译错误**，见 §C-2 新增的回归测试。
