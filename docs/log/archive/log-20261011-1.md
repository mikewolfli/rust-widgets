### 设计要点（回答计划"交付与验收"栏）

- **协议版本与库版本分开**：协议版本只在文档*形状*变化时递增；库版本每次代码变化都变。
  读方用协议版本判断"是否理解该文档"，这是库版本答不了的问题。历史：v1 = 原六键；v2 = 加四键。
- **旧格式可读**：无 `protocol` 键的文档按 v1 读（`a_protocol_one_document_is_still_readable`）。
- **未知版本显式拒绝**：`protocol > 2` 时整体拒绝并报 "newer"，不部分读取
  （`a_future_protocol_version_is_refused`）。小数/负数/字符串协议值同样拒绝
  （`a_malformed_protocol_value_is_refused`）。
- **相同输入稳定序列化**：新键按固定顺序写在文档头部，`every_control_manifest_round_trips_byte_for_byte`
  仍逐字节通过。
- **目标事实分开记录 profile 与 triple**：`TargetSpec{profile, triple}`，二者互不蕴含。
  triple 由 `build.rs` 从 `TARGET` 捕获，OS 知识不进 capability 层（原则 #35/#36/#47）。

## §3 B26.03 — 带参数 schema 的命令能力（✅ 已完成）

### 交付物

| 文件 | 变化 |
|---|---|
| `src/widget/capability/command_schema.rs` | **新增**。`CommandEffect`（3 类副作用）、`CommandSignature`（PayloadFree/OneValue/Composite）、`CommandSchema`；**派生**式 schema（`set_foo` → 属性 `foo`；34 个复合 setter 查表；114 个动词查表）；`describe_command`。全套单元测试。 |
| `src/widget/capability/properties_tests.rs` | 新增 `every_published_command_has_a_typed_schema`（503 条已发布命令全覆盖）与 `a_set_command_schema_agrees_with_the_controls_property_list`（schema ↔ 活跃控件 `property_names()` 交叉核对，265 条）。 |
| `src/widget/capability/designer_manifest.rs` | `commands: Vec<String>` → `Vec<DesignerCommand>`（name/signature/parameter/kind/arity/element/effect）；读写器同步；`designer_command_from`。 |
| `src/widget/capability.rs` | 导出 `command_schema` 模块。 |

### 设计要点：为什么是"派生"而非手写表

290 个命令名，若手写 290 行表就是**第二份事实**，必然漂移（原则 #54/#101）。因此 schema
**派生**自已决定命令行为的两个源头：

1. **`set_foo` 约定**：`WidgetProperties::default_command` 本身就把 `set_foo` 解析为属性 `foo`。
   schema 查同一个 `capability.properties`，因此**不可能与派发器分歧**。
2. **动词表 + 复合表**：这是约定答不了的部分（`toggle` 无同名属性；`set_range` 的参数是一对）。
   两张表各一份声明，且 `every_published_command_has_a_typed_schema` 在中找到未分类名即失败。

### 真实缺口修正（冰山：修一处扫同类）

新测试在 503 条命令上暴露并修复了 **froze 类真实缺陷**：

1. **58 条 `set_*` 命令无属性路由** —— 实为**复合载荷 setter**（`set_range`=一对、`set_items`=列表、
   `set_series`=集合）。原有 schema 若按"一个属性"描述，会告诉设计器"可用单值连线驱动"，
   而实际它会回 `OutOfRange`。新增 `CommandSignature::Composite` + 34 项复合表描述真实形状。
2. **`file_dialog` 契约与 schema 分歧** —— schema 声明 `mode`/`directory`/`selected_file`，
   但活跃控件 `property_names()` 只有 `title`/`modal`。且 `mode` 的 token 表是
   `["text","integer","double","item"]`（**从另一个对话框抄来的，任何文件对话框都不接受**）。
   **修复**：契约补 `mode`/`directory`/`selected_file`（含 `get`/`set`/`property_tokens`），
   token 改为真实的 `["open_file","open_files","save_file","select_directory"]`，schema 的
   readable/writable 改为与实现一致。
3. **`progress_dialog` 契约与 schema 分歧** —— schema 声明 `value`/`minimum`/`maximum`
   （只读），但 `property_names()` 未列，且它发布 `set_value`/`set_range`。**修复**：契约补三属性
   （可读写，`i32` 越界报 `OutOfRange`），schema 改为可写。

### 设计要点

- **三档知识**：`BuiltVerified`（当前构建就是目标，已实构建）/ `Describable`（当前构建可查，但
  与目标不同）/ `Unknown`（未验证）。折叠中档进"支持"正是把 desktop 事实冒充 mini 声明的缺陷。
- **"未知" ≠ "不支持"**：`Unverified` 表示"没人查过"，调用方可继续但须标注；`Unsupported` 是
  "已查证缺失"，调用方不应提供。把前者折进后者会让库拒绝它无权拒绝的东西。
- **生成器探针永不说 `BuiltVerified`**：`TargetProfile` 只分 Default/Stripped，无法命名目标 triple，
  故探针最多 `Describable`。这是诚实的——声称已实构建需要目标构建真的跑过。
- **每个探针行必带目标**：`describe()` 无条件打印 `profile`+`triple`，让"未归属的支持声明"不可能出现。

### 设计要点（回答计划"先确定 key 唯一性、生命周期和重建规则"栏）

- **key 唯一性**：key **以兄弟为作用域**（两个列表可各有 `"total"`），同一父下必须唯一；
  重复使两个请求者都不可映射（diff 报 `duplicate_keys`）。
- **生命周期/重建规则**：`TreeIndex` 是**快照**，仅在其描述的那棵树不变时有效。重建 = 再次
  调用 `tree_index()`。**失效可检测**：快照记录 `generation`，引擎每次 mount/update +1；
  比较两者即知是否过期。删除/替换后旧映射**立即失效**（旧 id 不再出现在新快照）。
- **`ObjectId` 不可持久化**：它是运行时句柄，仅在控件存活期有效，引擎可能复用其值，**绝不**写进
  工程文件或跨会话比较。设计器用 **key**（或文档路径）作持久身份，运行时经本索引解析成 `ObjectId`。
- **路径非稳定**：插入兄弟会移动其后所有节点的路径，因此路径是快照。用 key 解析跨重建的节点。

## §6 B26.07 — 增量更新的定位与失败观测（✅ 已完成）

### 交付物

| 文件 | 变化 |
|---|---|
| `src/view/apply.rs` | `ApplyReport` 新增 `is_partial()` / `failed_entirely()` / `completed()`；`ViewError` 新增 `affected_id()` / `location()`。2 个新测试。 |
| `src/view/engine.rs` | 新增 `ViewEngine::locate_error(error, index)`：把失败的 `ObjectId` 经 `TreeIndex` 解析为稳定 `"widget#key"`（无 key 则 `"widget@path"`）。1 个新测试。 |

### 设计要点（回答计划"能否从报告关联受影响稳定节点、识别失效映射及区分部分应用错误"栏）

- **关联受影响稳定节点**：`locate_error` 把报告的 `ObjectId` 接到 `TreeIndex`，产出
  `"widget#key"`——宿主据此在自己的模型里高亮失败节点。报告带 id，索引带位置，二者**join**。
  取索引而非每次重建：一批多错一棵树，`O(nodes)` 而非 `O(errors × nodes)`。
- **失效映射**：`locate_error` 对已从新树移除的 id 返回 `None`（诚实——被删节点在新树无位置），
  绝不返回过期位置把宿主指向错误控件。
- **区分部分应用**：`is_partial()`（有成功有失败）vs `failed_entirely()`（全失败）vs
  `is_clean()`（全成功）。三者语义不同、处置不同：全失败=树不是视图要的树；部分失败=树对了，
  只差一处。折叠它们会让宿主丢弃好树或隐藏真失败。
- **不改既有行为**：新增方法都是**只读**查询；`mount`/`update` 的行为、`ApplyReport` 既有字段与
  语义均未改动（原有 235 个 view 测试全部通过）。

  bool 声明范围、string 声明长度。验证器只认与声明 kind 相符的变体。
- **同一验证器服务三条路径**：`validate_property_value` 是 capability 写入 / JSON 加载 / 生成预检
  的**单一**答案；三条路径调用它而非各自从原始 `constraints` 重新推导。
- **错误含属性名和拒绝原因**：`ConstraintViolation{property, value, range}` 的 `Display` 与
  `CapabilityAccessError::ConstraintViolation{property, reason}` 都带全。
- **`Eq` 的有意放弃**：`PropertySchema` 由 `Eq` 降为 `PartialEq`（`RangeSpec` 含 `f64` 无全序）。
  全仓无对 schema 的 map/set 键控，故是零影响变更（已注释说明）。
- **诚实的空默认**：构造器默认空约束，属性"无约束"即声明"无约束"，而非读起来像真边界的宽松默认。

### 设计要点（回答计划"提供可发现、可校验的参数/子项 schema…非法转换报告丢失/不支持字段"栏）

- **可发现、可校验的参数 schema**：`LAYOUT_KIND_SCHEMAS` 是每种布局参数的**单一声明**，面板、校验器、

## §9 B26.08 — 编辑器文本与源码定位原语（✅ 已完成）

### 探针结论（计划要求"按真实代码编辑探针确认现有 CodeEditor 是否缺少…"）

对 `CodeEditor` 现有 API 的实测（`editor.rs` 的 70+ `pub fn`）表明：**文本读写、范围坐标

1. **无文本版本号** —— 异步消费者（linter/indexer）无法检测"我算出的位置是否已过期"。
2. **无版本守卫的范围编辑** —— 自动修复（格式化/quick-fix）从快照算出替换，稍后应用时若用户已
   输入，盲目写入会破坏文档。

### 交付物

| 文件 | 变化 |
|---|---|
| `src/widget/special_widgets/code_editor/editor.rs` | 新增 `revision: u64` 字段（`set_text` 与 `record_and_settle_inner` 两处提交点 +1，no-op 不 +1）；`revision()`；`replace_range(expected, start, end, text) -> Result<u64, EditRejection>`（版本守卫的范围编辑，含范围归一化与 UTF-8 字符列）。 |

| `src/widget/special_widgets/code_editor/mod.rs` | 导出 `EditRejection`。 |
| `src/widget/special_widgets/code_editor/tests.rs` | 8 个新测试。 |

### 设计要点

- **单调计数器而非哈希**：哈希会碰撞，碰撞意味着把过期结果当成新鲜的接受——恰是版本号要防的失效。
- **两个提交点都要 +1**：`set_text` 不经过 `record_and_settle_inner`，故单独 +1；两处都只在文本
  **真的变了**时 +1（no-op 不 +1），否则宿主会因"未变却报变了"而白白失效缓存。
- **版本守卫是安全顺序的唯一解**：计算与写入无法原子时，让编辑器拒绝过期编辑，而非应用它。
- **坐标是字符列**：与编辑器其余 API（`TextPosition`）一致；字节偏移会随周围编码变化并可能落在
  多字节字符中间。
- **两种拒绝语义不同**：`StaleRevision` → 重读重算；`ReadOnly` → 停止请求。折叠会让调用方永远重试
  只读编辑，或放弃刷新后本可成功的编辑。

## §12 复核发现的修复（逐项 + 证据）

### §12.1 A1 — 约束语义：写路径一律拒绝，文档不再自相矛盾

- `types.rs`：`Constraint::Range` 的文档原是"对钳制型控制拒绝写入会拒绝控制能接受的值"，与本仓实际策略

- `properties_other.in.rs`：`progress_circle.value` 的注释改为诚实描述（控制**设界**（会钳制），所有写入路径
  一律拒绝越界，而不是写入一个控制会改写的值）。

### §12.2 A2 — 让"同一验证器服务三条路径"成为事实

### 设计要点：为什么是"记录列表"这一个形状

- 计划要求"先用具体控件和数据流定义**最小**类型"。真实数据流只证明了一种形状：**有序、以 id 为键的
  记录列表**（`chip.items` / `timeline_widget` / `segmented_control` 都是这一种）。因此只加了这一个值形状。
- **不**加单个记录、**不**加嵌套记录：没有控件需要它们，而位置型形状已由 `CapabilityValue::Tuple` 承载
  （`heatmap.set_cell` 是三元组、`range_slider.range_changed` 是二元组），所以嵌套在记录字段里被**拒绝**
  而不是猜测。
- **身份是字段不是位置**：`RecordSchema.id_field` 让"移动后选择/滚动锚点/未提交编辑仍指向同一条"成为
  可表达的事实；`ids_unique`/`ids_required` 是校验器强制的策略。
- **库不持有业务状态**：`RecordList` 是调用方拥有的值，控件在 `set` 里转成自己的 `ChipItem`；计划
  "优先定义应用接缝而不在控件库持有业务状态"由此满足。
- **值不带 schema，属性带 schema**：JSON / ABI / manifest 三个边界都无法命名 `&'static` schema，因此它们
  产生的列表带 `EMPTY_RECORD_SCHEMA`，由 `validate_against(属性自己的 schema)` 判定。这样同一套校验器
  服务三条路径，而"用值自带的 schema 判定"（会让调用方拿自己没发布的规则过关）被排除。
- **列移动是数据操作**：`move_field` 把某字段移到指定位置，**所有**持有该字段的记录一起移动（未持有的
  记录保持原样，因此不变量是"共享字段的相对顺序一致"而不是"每条记录等长"）。

### 18.1 R1 — `splitter.orientation` 与 schema 不一致

**修法（一份事实来源，而不是两处对齐）**：`src/json/layout.rs` 新增

```rust
pub(crate) const AXIS_TOKENS: &[(&str, Orientation)] = &[ ... ];
fn orientation_of(token: &str) -> Option<Orientation>
fn parse_axis(value: Option<&Value>) -> Orientation     // 读 AXIS_TOKENS
```

`src/json/layout_schema.rs` 的 `is_axis_token`（`ParamKind::Axis` 的判定）读**同一份** `AXIS_TOKENS`。
`splitter` 分支不再写自己的 `match`，改调 `parse_axis`；`flow`/`wrap` 不变。于是"校验器接受"与"解析器
如何理解"在构造上不可能分叉。

**为什么这不算"改变既有行为"**：`"column"` 此前被 schema 判为合法、被 `splitter` 读成 Horizontal——即
**文档（cookbook 与 `LayoutParam` schema）承诺 Vertical，实际却按 Horizontal 布局**。修的是"承诺与实现
不一致"，不是"把 A 改成 B"；且 `flow`/`wrap` 早已按 `parse_axis` 认 `column`，故 `splitter` 是唯一不一致者。

新增用例（覆盖"每个 token × 每个取轴布局"这一整类，而不是只补 `column` 一格）：

| 用例 | 覆盖 |
|---|---|
| `every_axis_token_parses_to_the_orientation_it_names` | `AXIS_TOKENS × {splitter, flow, wrap}`，逐对断言解析结果等于该 token 声明的轴 |
| `the_schema_accepts_exactly_the_tokens_the_parser_understands` | 双向包含：解析器认的 token schema 必须接受；并逐一断言 `columns`/`vert`/`Horizontal`/`""`/`row` 仍被拒绝 |

**反例注入**：把 `splitter` 分支恢复成原来的内联 `match`，`every_axis_token_parses_to_the_orientation_it_names`
立即失败：

```
assertion `left == right` failed: `splitter` with orientation `column`
  left: Horizontal
 right: Vertical
```

### 18.4 顺带修正：`tools/cookbook_api_scan.py` 的枚举体扫描（真实缺陷）

在为新 API 写 cookbook 时，门禁报了两条**假**发现（`` `Constraint::Range` — 定义为不存在 ``）。定位到
扫描器构造 `enum_bodies` 的正则：

```
\b(?:pub(?:\([^)]*\))?\s+)?enum\s+(?P<name>[A-Za-z_][A-Za-z0-9_]*)[^{]*\{
```

它匹配的是**散文**：`types.rs` 的一句文档注释 "…on the schema enum rather than separate fields…" 让
`enum` + 名字捕获到 `rather`，其 `[^{]*` 随后跨过所有真实声明直到下一个 `{`。于是那一段里的枚举
（含 `Constraint`）**一个都没被捕获**，变体判定退化为"找不到"。

这使扫描器在**两个方向**上都错，而假阴性那半更危险：看不见枚举体 → 无法校验任何 `Owner::Variant` 断言，
真正的漂移（如 `Constraint::Rang`）同样不会报。修法是锚定到"声明独占一行"并禁止跨越 `;` 或另一个 `enum`：

```python
r"^[ \t]*(?:#\[[^\]]*\]\s*)*"
r"(?:pub(?:\([^)]*\))?\s+)?enum\s+(?P<name>[A-Za-z_][A-Za-z0-9_]*)"
r"(?:(?!\benum\b)[^{;])*\{"      # re.MULTILINE
```

验证：

- 修正前后**已存在**的 cookbook 断言一条都没新增失败（`checked=216 failed=0`）——说明此前的假阴性没有
  掩盖真实的文档错误；
- **反例注入**：把 en 版 cookbook 的 `` `Constraint::Range` `` 改成 `` `Constraint::Rang` ``，修正后的
  扫描器报出变体级发现：`` `Constraint::Rang` — `Constraint` declares no variant named `Rang`, and no
  such method, constant, type or field exists ``（修正前该断言根本到不了这一步）。恢复后 `failed=0`。
