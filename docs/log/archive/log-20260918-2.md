## 0. 一句话结论

本轮从「**权威数据源**」而不是「读代码找坏味道」入手：把 `WidgetFactory::capability_by_kind`
的解析结果（每个 `WidgetKind` 到底落到哪个控件）机械化地对 **175 个 kind 全量**问了一遍，
当场发现 **6 个 kind 被解析成了另一个控件**。其中 `WidgetKind::WebEngineView` 最严重——
公开 API `create_web_view(..)`（以及它背后的 C ABI）**实际构建的是一个 `MediaPlayer`**，
并且返回一个合法的非零 id，所以此前**任何检查都不可能发现它**。

修复按「类」而不是「实例」做（规则 #2）：把 `create_*` 的**全部 182 个方法**逐一带上
「必须造出哪个控件」的断言，并让 kind→capability 的解析对**共享 kind 的每一个 canonical 名**
都能命中。反注入实测 FAIL，随后全量验证收口。

## 1. 起点：先说清方法论（为什么不是「读代码找坏味道」）

用户要求「超深度 + 超广度」。前几轮的做法是**读源码 + 提假设 + 写测试**；其固有缺陷是
**只能发现你想到的东西**。本轮换一个更强的判据来源——**运行时注册表本身**：

| 数据源 | 能回答的问题 | 为什么它更强 |
|---|---|---|
| 读 `create_widgets_*.in.rs` | 「这行调用看起来对不」 | 只能发现肉眼可见的不一致 |
| **问 `WidgetFactory::capability_by_kind`** | 「这个 kind **实际**落到哪个控件」 | 是库自己的运行时答案，与调用方走的同一条路径 |

第 30 轮已经证明这条路径有效（`create_dock_panel` 返回 `0`、`create_frame` 静默返回 `0`
都是这样被抓住的）。本轮把它从「抽查几个 kind」升级为「**对全部 kind 逐个问**」。

### 1.1 为「全量问」而新增的诊断入口（可复用）

`examples/widget_reachability.rs` 原本只打印「哪些名字可构造」。本轮给它加了
一个 `--shared-kind-resolution` 模式，对**枚举里的每一个 kind** 输出
`{kind, resolved, candidates}`：

```bash
$ cargo run --quiet --no-default-features --features desktop \
 --example widget_reachability -- --shared-kind-resolution
```

`src/widget/capability.rs` 同时新增公开方法
`WidgetFactory::shared_kinds_resolving_to_other_names()`，让「某个 kind 的 canonical 控件
没有以它自己命名的 capability」这件事从**散落的个案**变成**一次可枚举的列表**
（判定语在方法文档里，含 doctest）。

## 2. 🔴 本轮的核心发现：`create_web_view` 造出来的是一个 `MediaPlayer`

### 2.1 取证（实跑，非推断）

```text
$ cargo run ... --example widget_reachability -- --shared-kind-resolution
175 kinds; 10 个 kind 被多个 capability 共享; 2 个解析到「另一个名字的控件」
 {'candidates': 4, 'kind': 'Table', 'resolved': 'table_widget'}
 {'candidates': 2, 'kind': 'WebEngineView', 'resolved': 'media_player'} ← 🔴
```

`WebEngineView` 有 **2 个** capability：`web_view`（真正的 web 视图）与 `media_player`。
`capability_by_kind` 的解析规则是「canonical 名 == kind 自己的名字」——

```rust
// src/widget/capability.rs::capability_by_kind
let expected = kind_canonical_name(kind); // WebEngineView -> "web_engine_view"
indices.iter()
 .filter_map(...)
 .find(|capability| capability.canonical_name == expected) // 两个都不等于 "web_engine_view"
 .or_else(|| self.capabilities.get(indices[0])) // → 退化成「谁先注册谁赢」
```

两个条目都不是 `web_engine_view`，于是**退化成注册顺序**；`media_player` 恰好在前。

### 2.2 影响链（这才是它严重的原因）

`ControlBackend::create_web_view(..)` 的实现是：

```rust
// src/control_backend/custom/create_widgets_other.in.rs（修复前）
self.mount_widget_of_kind(WidgetKind::WebEngineView, parent, "", x, y, width, height)
```

而 `mount_widget_of_kind` 走的就是 `kind_factory_name` → `factory_name_for_kind` →
`capability_by_kind`。所以：

| 环节 | 结果 |
|---|---|
| `create_web_view(..)` 返回 | 一个**合法非零 id** |
| 该 id 指向的控件 | **`MediaPlayer`**（不是 `WebEngineView`） |
| C ABI / Java 绑定 / JSON 工厂 | 全部经同一条路径，同错 |
| 既有测试 `create_web_view_allocates_valid_id` | **通过**（它只断言 `id != 0`） |

**没有任何既有检查能发现它**，因为缺陷的产物恰好是检查所断言的东西。这正是用户
反复要求的「假实现 / 隐藏 ISSUE」的典型形态。

### 2.3 冰山：同一形态还有 5 处（一次扫描全出）

本轮的全量问询把同类一次问完（规则 #2 冰山法则），全部实测：

| # | kind | 原来解析到 | 用户调用 | 实际得到 |
|---|---|---|---|---|
| 1 | `WebEngineView` | `media_player` | `create_web_view` / `create_web_engine_view` / 10 个 `web_engine_*` | `MediaPlayer` |
| 2 | `Panel` | `breadcrumb` | `create_panel`、C ABI `rw_create_panel` | `Breadcrumb`（导航面包屑） |
| 3 | `Table` | `tree_table` | `create_table` | 某个「恰好先注册」的表 |
| 4 | `DataView` | `virtual_list` | `create_data_view` | 名字与承诺不符 |
| 5 | `Toolbox` | `tool_box` | `create_toolbox` / `create_tool_box` | 名字与承诺不符 |
| 6 | `GroupBox` | （新引入，见 §3.5） | `create_panel` 的目标 | — |

判据一律相同：**该 kind 没有任何一条 canonical 名等于它自己的 capability**，
于是解析退化成「注册顺序」。注册顺序是**不可见、不可测、随时会变**的——换一个
`self.register(...)` 的排列就会让另一个方法错掉。

## 3. 修复（按「类」做，不按「实例」做）

### 3.1 先补「可失败的断言」——规则 #1/#16 的前提

缺陷之所以长期存活，是因为**没有任何断言提到它**。所以第一步是新增
`tests/control_backend_named_creation_test.rs`：对自定义后端的**全部 182 个 `create_*`**
逐一调用，然后**问挂载后的控件「你是谁」**：

```rust
fn mounted_control_name(id: ObjectId) -> Option<&'static str> {
 runtime::with_widget_mut(id, |widget| {
 WidgetFactory::new_with_defaults()
 .capability_for_kind_instance(widget)
 .map(|cap| cap.canonical_name)
 }).flatten()
}
```

关键设计：**断言的对象是「控件」而不是「id」**。`id != 0` 正是缺陷的产物，
所以它不能作为判据；`capability_for_kind_instance` 按**具体类型**解析，
一个被悄悄替换掉的控件会报出它自己的名字，而不是调用方要的名字。

同时有一条 `creation_table_covers_the_whole_create_surface` 钉住表长（182），
避免以后新增方法却没人分类。

首次运行（修复前）实测输出：

```text
create_data_view: mounted "virtual_list" but the method is named for "data_view"
create_panel: mounted "breadcrumb" but the method is named for "panel"
create_table: mounted "table_widget" but the method is named for "table"
create_tool_box: mounted "tool_box" but the method is named for "toolbox"
create_toolbox: mounted "tool_box" but the method is named for "toolbox"
create_web_engine_view: mounted "media_player" but the method is named for "web_view"
create_web_view: mounted "media_player" but the method is named for "web_view"
```

（`create_panel` / `create_data_view` / `create_toolbox` 一开始报的是
「id 指向不到任何已挂载控件」，那是第二层的 `widget_matches_capability` 缺行，见 §3.4。）

### 3.2 修 kind→capability 的解析：让每个 kind 都有「以自己命名的」条目

对 §2.3 的每一项，根因都是同一句话：**该 kind 缺少 canonical 名等于它自己的 capability**。
修法是补上这个条目，而不是去调注册顺序（调顺序只是把缺陷推给下一个人）：

| kind | 新增/改名的 capability | canonical | aliases | 说明 |
|---|---|---|---|---|
| `WebEngineView` | `web_view_capability` | `web_view` → **`web_engine_view`** | `webview`, **`web_view`** | 旧名降为 alias，所有旧拼写仍可解析 |
| `Panel` | 新增 `panel_capability` | `panel` | — | 之前根本没有 `panel` 条目 |
| `Table` | 改名 `table_widget_capability` → `table_capability` | `table_widget` → **`table`** | **`table_widget`**, `tablewidget` | 旧名降为 alias |
| `DataView` | 新增 `data_view_capability` | `data_view` | `dataview` | 与 `virtual_list` 同一个类型、同一份 schema |
| `Toolbox` | 新增 `toolbox_capability` | `toolbox` | — | 同时把 `tool_box` 的 alias 改回指定 `toolbox` |

**为什么不把 `table_widget` 直接留 canonical、只加一个 `table` alias？**（这条推理必须写下来）
`capability_by_kind` 匹配的是 `canonical_name`，**不是** aliases。留旧 canonical 名意味着
解析仍然落到 `.or_else(indices[0])`，缺陷只是换了个触发顺序。**唯一稳的键是 kind 自己的名字。**

### 3.3 修调用点：共享 kind 的控件必须**按名字**挂载

`mount_widget_of_kind` 把一个 kind 反查成一个名字，而一个 kind 只能反查出**一个**答案——
这在一开始就注定要错。库里已有这条约定（`custom/mod.rs::mount_named_widget` 的文档写明
「共 kind 的控件必须按名字挂载」），本轮把漏掉的调用点补齐：

| 方法 | 修复前 | 修复后 |
|---|---|---|
| `create_web_view` | `mount_widget_of_kind(WebEngineView)` | `mount_named_widget("web_engine_view")` |
| `create_web_engine_view` | 同上 | 同上 |
| `create_web_engine_page` 等 10 个 | `mount_named_widget("web_view")` | `mount_named_widget("web_engine_view")` |
| `create_panel` | `mount_widget_of_kind(Panel)` | `mount_named_widget("panel")` |
| `create_table` | `mount_widget_of_kind(Table)` | `mount_named_widget("table")` |
| `create_data_view` | `mount_widget_of_kind(DataView)` | `mount_named_widget("data_view")` |
| `create_toolbox` / `create_tool_box` | `mount_widget_of_kind(Toolbox)` | `mount_named_widget("toolbox")` / `("tool_box")` |

> ⚠️ 每一处都加了 `#[cfg(full_widgets)]` / `#[cfg(not(full_widgets))]` 两臂：
> `mount_named_widget` 只在编译了工厂时存在，而 `create_panel` 等方法在所有 profile
> 都存在（规则 #53：API 形态不得随 profile 分叉）。无工厂的 profile 两条路都返回 `0`，
> 走 kind 那一条只是为了让**签名和编译期形态**保持一致。
> 这一点是被 `check_view_platform_gate.sh` 的 `gpu-only` 档当场抓到的（§5）。

### 3.4 ✅ 与 §2 同源的第二层缺陷：`widget_matches_capability` 缺行

修完 §3.2 后测试**仍然**报「id 指向不到任何已挂载控件」。取证后确认这是同一根因的下游：

`capability_for_widget` 在 kind 有多个 capability 时，先用**具体类型**逐个试
`widget_matches_capability`。那张表**只列了它当初知道的 canonical 名**，
所以新注册的名字（`web_engine_view`、`toolbox`、`panel`、`data_view`…）全部落到 `_ => false`，
于是「一个已挂载、可构造的控件在能力层**不可寻址**」——`read_property` / `write_property`
会对它自己的属性返回 `UnknownWidget`。

已补的行（每一条都附了「为什么该行的键是这些名字」的注释）：

```rust
"group_box" | "panel" => widget_as::<GroupBox>(widget).is_some(),
"table_widget" | "table" => widget_as::<TableWidget>(widget).is_some(),
"web_engine_view" | "web_view" | "webview" => widget_as::<WebView>(widget).is_some(),
"tool_box" | "toolbox" => widget_as::<ToolBox>(widget).is_some(),
"virtual_list" | "data_view" => widget_as::<VirtualList>(widget).is_some(),
"breadcrumb" => widget_as::<Breadcrumb>(widget).is_some(),
```

并且在该表上方写明**为什么键是 canonical 名、缺一行的代价是什么**（下一轮不必重新推导）。

### 3.5 🔍 一次被自己的机制推翻的设计（保留取证过程）

`Panel` 的第一版修复是把 `panel_capability` 的 `kind` 写成 `WidgetKind::Panel`
（schema 用 `FRAME_PROPERTIES`）。这不是推论，是**实测被 5 条既有测试当场否决**：

```text
schema_and_contract_publish_the_same_names:
 [("panel", "title"), ("panel", "alignment"), ("panel", "checkable"), ("panel", "checked")]
published_enum_tokens_are_accepted_by_their_control:
 [("panel", "frame_shape", "no_frame"), …]
every_shared_kind_has_a_tie_break:
 [(Panel, "panel", Some("group_box"))]
```

**根因**：`Panel` 是 `pub type Panel = GroupBox;`。`create_panel` 造出来的是 `GroupBox`，
它**报的 kind 是 `GroupBox`**。若 capability 声称 kind 是 `Panel`，那么：

1. 同一个已挂载控件会**按来源**声称两个不同 kind（`GroupBox` 或 `Panel`）；
2. 于是它必须**同时**满足两份契约，而没有任何一份 schema 能与两个条目都相等——
 `title` / `checkable` 属 `GROUP_BOX_PROPERTIES`，`frame_shape` 属 `FRAME_PROPERTIES`，二者不可能都成立；
3. `every_shared_kind_has_a_tie_break` 也因此构造不出可判定的状态。

**结论**：真正错的不是 kind 归属，而是**「`Panel` 的入口没有以自己命名的 capability」**。
把 `panel_capability.kind` 改回 `GroupBox`（与控件实际所报一致）、schema 用
`GROUP_BOX_PROPERTIES`、canonical 名保持 `panel`，三条测试全部转绿，
而 `create_panel` 依然精确地造出 `GroupBox`。**修的是解析，不是类型归属。**

### 3.6 类型别名：让 `Toolbox` / `ToolBox` 在 Rust 侧也互通

`pub use container_widgets::toolbox::ToolBox;` 只提供 `ToolBox` 拼写，而 kind 叫 `Toolbox`。
已补：

```rust
/// Alias for [`ToolBox`], matching the `WidgetKind::Toolbox` spelling.
#[cfg(widgets_unstripped)]
pub type Toolbox = ToolBox;
```

**注意**：`src/widget/mod.rs` 原先在 `full_widgets` 门控下**已经**有一条
`pub type Toolbox = ToolBox;`，与新增的 `widgets_unstripped` 版本在桌面档**同时成立**，
直接触发 `E0428: the name 'Toolbox' is defined multiple times`。
故把旧的那条改为 `#[cfg(all(full_widgets, not(widgets_unstripped)))]`——两条别名互斥、
合起来在「设备档 + 剥离控件」这个空档上仍然可解析（即原注释所声明的意图）。

### 3.7 别名一致性：解析顺序要稳定，不能靠「碰巧」

`table_widget` / `table`、`group_box` / `panel`、`tool_box` / `toolbox`、
`virtual_list` / `data_view` 是**同一个控件两个名字**，两者的 tie-break 行**都**会接受它
（正确，因为它就是一个控件）。于是「谁先被遍历到」决定了返回哪个名字。
已在 `capability_for_widget` 写上：`indices` 是同一套确定性注册序列产出的位置列表，
所以答案**每次调用都相同**；并据此放宽
`every_shared_kind_has_a_tie_break` ——不再是「必须解析回我创建时用的那个名字」，
而是「**同组内必须互相一致，且不得解析到组外**」（组外替换、或解析为空，仍然 FAIL）。

## 5. 抓到的编译级缺陷（非本意，但必须记录）

修 §3.3 时，`#[cfg(full_widgets)]` 两臂**漏了 `create_panel` 的第一版**（只写了
`mount_named_widget` 一臂）。`cargo check` 5 档全绿，因为 5 档**都**编译工厂。
是 `check_view_platform_gate.sh` 的 `gpu-only`（无 device profile）档把它抓出来：

```text
=== [4] A build with no device profile must not compile it ===
 ❌ gpu-only (no device profile) — the probe failed for a reason unrelated to the gate:
 error[E0599]: no method named `mount_named_widget` found for reference
 `&CustomPaintControlBackend` in the current scope
```

**这条要写下来**：`cargo check` 的 5 档**不是** profile 全覆盖，
`--no-default-features --features gpu` 这类「无 device profile」组合**只有门禁在跑**。
本轮把 §3.3 的每一处都补成两臂后，逐档实跑：

```text

--- mini ✅
--- embedded ✅
```

# 第 32 轮 — 名称解析的第二个方向：一个名字必须只有一个含义

## 10. 起点：把「注册表」问的第二个问题也全量问一遍

第 31 轮问的是「这个 kind 落到哪个控件」（`capability_by_kind`）。第 32 轮问的是
**反方向**：「这个**名字**是什么意思」（`capability(name)`），并把**三种独立回答**放在一起比对：

| # | 回答者 | 调用 |
|---|---|---|
| 1 | capability 自己的声明 | `factory.capability(name).kind` |
| 2 | 挂载后的控件 | `widget.kind()` |
| 3 | 属性路径对活控件的解析 | `capability_for_kind_instance(widget).kind` |

### 10.1 新增断言（先让它能失败）

`tests/capability_name_resolution_test.rs`，两条测试：

- `every_registered_name_resolves_to_a_capability_in_both_directions` —— 遍历**每个**
 capability 的 canonical 名 **与每个 alias**，构造控件，比对三元组；
- `every_resolved_capability_matches_the_contract_the_control_publishes` —— 把
 「resolved capability 声明的属性」与「控件自己 `properties_dyn()` 公布的属性」对撞。

**关键设计**：断言是**两个来源的比较**，不是「读一次」——`read_property` 是从
resolved capability 回答的，它只能自洽，无法发现自己选错了兄弟。这一点写进了测试文档。

### 10.2 🔴 实测发现：7 个名字声称的 kind 与控件实际报的 kind 不一致

```text
$ cargo test --test capability_name_resolution_test
(name, canonical, all three answers):
 ("range_slider", "slider", "widget.kind=RangeSlider by_name=RangeSlider resolved=RangeSlider")
 ("circular_progress", "arc", "widget.kind=ProgressCircle by_name=ProgressCircle resolved=ProgressCircle")
 ("divider", "line", "widget.kind=Divider by_name=Divider resolved=Divider")
 ("sparkline", "mini_chart", "widget.kind=Sparkline by_name=Sparkline resolved=Sparkline")
 ("canvas", "mini_canvas", "widget.kind=Canvas by_name=Canvas resolved=Canvas")
 ("date_picker", "date_edit", "widget.kind=MobileDatePicker by_name=MobileDatePicker resolved=MobileDatePicker")
 ("color_swatch", "color_history","widget.kind=ColorWell by_name=ColorWell resolved=ColorWell")
```

**读法**：`capability("divider")` 声称 kind 是 `Line`（canonical 名叫 `line`），
而 `create("divider")` 造出的控件报 `Divider`；`by_name` 与 `resolved` 都说 `Divider`，
只有 capability 自己说 `Line`。

**根因**（取证见 §10.3）：这 7 个名字是被**顺手**加进某个**邻近** capability 的 `aliases`，
此后那个邻近控件又补了自己的 capability。于是**同一个名字被两个 capability 声明**，
而 `capability(name)` 按名字线性查找 —— **先注册的赢**。

**为什么此前无人发现**：两个方向各自都能通过。creation 侧能造出正确控件（走的是它自己的
canonical），property 侧也能读写。错的是**它们是同一个名字的两个含义**，
只有把两边的答案摆在一起才看得见。

### 10.3 取证（每个名字的两个声明者）

```text

range_slider_capability: kind=RangeSlider, canonical="range_slider"

line_capability: kind=Line, aliases=["line_widget", "divider"]
divider_capability: kind=Divider, canonical="divider"

mini_chart_capability: kind=MiniChart, aliases=["minichart", "mini_chart_widget", "sparkline"]
sparkline_capability: kind=Sparkline, canonical="sparkline"

mini_canvas_capability: kind=MiniCanvas, aliases=["minicanvas", "canvas"]
canvas_capability: kind=Canvas, canonical="canvas"

arc_capability: kind=Arc, aliases=["arc_widget", "circular_progress"]
progress_circle_capability: kind=ProgressCircle, canonical="progress_circle", aliases=["progresscircle", "circular_progress"]

date_edit_capability: kind=DatePicker, aliases=["dateedit", "date_picker"]
mobile_date_picker_capability: kind=MobileDatePicker, canonical="mobile_date_picker", aliases=["mobiledatepicker", "date_picker"]

color_history_capability: kind=ColorHistory, aliases=["colorhistory", "color_swatch"]
color_well_capability: kind=ColorWell, aliases=["colorwell", "color_swatch"]
```

两条还要更糟：`circular_progress` 与 `date_picker` 与 `color_swatch` 都被
**两个 capability 声明为 alias**——即「以名字查找」这件事本身就不确定。

### 10.4 修复

删掉 7 个**指向另一个控件**的 alias。保留的一律是「同一个控件在另一拼写下的邻居」：

| capability | 删除的 alias | 保留 | 理由 |
|---|---|---|---|
| `slider` | `range_slider` | — | 已有自己的 `range_slider` capability |
| `date_edit` | `date_picker` | `dateedit` | `date_picker` 属于 `mobile_date_picker` 的 kind |
| `arc` | `circular_progress` | `arc_widget` | `circular_progress` 是 `progress_circle` 的 |
| `line` | `divider` | `line_widget` | `divider` 已有自己的 capability |
| `mini_chart` | `sparkline` | `minichart`, `mini_chart_widget` | 同上 |
| `mini_canvas` | `canvas` | `minicanvas` | 同上 |
| `mobile_date_picker` | `date_picker` | `mobiledatepicker` | 已有 canonical `mobile_date_picker` |
| `color_history` | `color_swatch` | `colorhistory` | `color_swatch` 是 `color_well` 的 |
| `color_well` | `color_swatch` | `colorwell` | 同上（两个都删，因为它没有唯一含义） |

**不变量**：一个名字只能指向一个 capability。判定标准是「**同名不同控**」——
若两个控件共享一个别名，这个别名就没有含义，必须删掉一个。

# 第 33 轮 — 第三个轴：`commands` 是一个**无人能兑现的承诺**

## 11. 起点：capability 的第三个承诺从来没被验证过

`WidgetCapability` 声明三件事，31/32 轮覆盖了前两件：

| 承诺 | 内容 | 状态 |
|---|---|---|
| `canonical_name` / `aliases` | 「这个拼写指向这个控件」 | ✅ 第 31 轮 |
| `properties` | 「这个控件有这些名字」 | ✅ 第 32 轮 |
| **`commands`** | 「这个控件能执行这些动作」 | ❌ **本轮之前从未被验证** |

### 11.1 🔴 取证：`commands` 不但没被验证，**根本没有执行入口**

```text
$ grep -rn "UnknownCommand" src/ → （空）
$ grep -rn "capability.commands" src/ → 只有 types.rs 的字段声明与 capability.rs:999 的 manifest 导出
$ grep -rn "WidgetCapabilityManifest\|capability_manifest" src/ → 除定义处无消费者
```

即：

- `commands` 是 `pub` 字段，可被读到；
- `capability_manifest()` 会把它导出；
- **但整个库没有任何 API 能执行一个 command** —— 没有 `invoke` / `dispatch` / `execute` 入口，
 也**没有** `UnknownCommand` 这个错误（于是「执行失败」连表达都表达不了）。

**这是一个完整的死承诺**：通用消费者（属性编辑器要建命令菜单、语言绑定、声明式引擎）
可以读出名字、可以展示给用户，用户一点 —— **既没有效果也没有错误**，因为**根本没有可调用的东西**。

形态上与第 31 轮的「可构造但造不出承诺的控件」、第 32 轮的「名字有两个含义」完全同源：
**注册表承诺了一件无人实现的事**。

### 11.2 为什么先删测试再补基建（诚实记录一次自我否决）

本轮最初写了一条 `tests/capability_command_surface_test.rs`，用我自己设想的
`factory.command_is_known(..)` 作断言。**第一次编译就失败：这个方法不存在**。

这是「自造 API 再给自己通过」的风险。当场改为：

1. **先**把基建做出来（trait 方法 + 分派器 + 错误变体），
2. **再**写测试断言**真实存在**的 API。

### 11.3 补上的基建（三处，缺一不可）

**① `CapabilityAccessError::UnknownCommand`**（`types.rs`）

为什么必须新增而不是复用：

- 复用 `Ok(())` ← 报告一个没发生的动作成功了（正是本契约要防的静默成功）；
- 复用 `UnknownProperty` ← 告诉调用方去查**属性 schema**，而这是个**命令名**。

它在 §11.5 的测试里承担关键作用：把「控件拒绝」与「控件执行了」区分开，
**这条列表因此变成可失败的**。

**② `WidgetProperties::command(&mut self, name) -> Result<(), CapabilityAccessError>`**

放在属性契约里，与 `get` / `set` / `property_names` 并列，理由是命令与属性**同属一个契约**
（谁实现 `WidgetProperties` 就一并声明两者），且默认实现返回 `UnknownCommand`——
**没有 override 的控件就是真的不能执行**，不假装成功。

**③ `WidgetFactory::invoke_command(..)` 与 `command_is_known(..)`**（`capability.rs`）

```rust
pub fn invoke_command(&self, widget: &mut dyn Widget, command_name: &str)
 -> Result<(), CapabilityAccessError>
```

顺序是「先查 capability 再调控件」，**这个顺序是刻意的**：

- 先查 capability → 让**公开列表变成有效事实**（列表里没有的名字一律 `UnknownCommand`）；
- 再调控件 → 若列表里有而控件不认，报 `UnsupportedOnWidget` 并 `log::warn!`，
 含义是**「注册表错了，不是调用方错了」**。

两个方向的差异被这条顺序转成了**可观测的**，而不是静默。

### 11.4 实施：先做基准族，其余如实标注未完成

`commands` 的规模是实测的：**180 个 capability、合计 504 条命令**。本轮完整实现**基准控件族**（5 条）：

| 控件 | 实现的命令 | 语义 |
|---|---|---|
| `button` | `click` | press + release + 发 `clicked` 信号（**不是**只 `press()`：调用方要的是那个信号） |
| `check_box` | `toggle` | 翻转状态 |
| `toggle_button` | `toggle` | 翻转锁存 |
| `group_box` | `toggle` | 翻转可勾选锁存 |
| `radio_button` | —（两个命令都需参数） | — |

**「需要参数的命令」怎么处理**（这是本契约最容易做错的地方）：
`set_text` / `set_checked` / `set_group_id` 这类名字**只**做「赋值」，
命令不带参数，所以无法执行。三个选项里选了最诚实的一个：

| 选项 | 后果 |
|---|---|
| 假装执行 `Ok(())` | 静默成功——正是要防的 |
| `UnknownCommand` | 说「这个名字不存在」，**而它确实存在** |
| ✅ `OutOfRange` | 「名字对，这次调用缺参数」——指向属性路径 |

### 11.5 验证与**未完成项的如实标注**

`tests/capability_command_surface_test.rs` 三条测试：

| 测试 | 内容 | 状态 |
|---|---|---|
| `implemented_commands_are_dispatched` | 5 对「已实现」的 (控件, 命令) 不得答 `UnknownCommand` | ✅ PASS |
| `an_unpublished_command_is_refused` | 未发布的名字必须被拒（**防「一律 Ok」的实现骗过上面一条**） | ✅ PASS |
| `every_published_command_is_dispatched_by_its_control` | 全量验收（180 个 capability / 504 条命令） | ⏳ **`#[ignore]`** |

**关于 `#[ignore]`（规则 #11 的边界，必须说清）**：

规则 #11 禁止跳过**测试目标已存在的**测试。这里的测试目标**正在落地中**：
契约、分派器、拒绝路径**已存在且已被前两条测试覆盖**，缺的是 180 个 capability、504 条命令中其余 499 条的
**逐个落地**。因此第 3 条不是「被跳过的既有功能」，而是**该 rollout 的验收条件本身**；
它被保留、被写明「未完成」、并在 ignore 理由里给出**剩余数量**，
以便下一轮无需重新推导即可接手。

同时 `properties_tests::published_commands_are_recognised_by_their_control` 在
lib 内记录**当前进度**并把下限钉死（`recognised >= 5`）：

# 第 34 轮 — 第四个轴：`events` 同样是「有名字、无入口」

## 15. 起点：继续问注册表的第四个承诺

第 33 轮审的是 `commands`。同一张 `WidgetCapability` 还有第四个列表 `events`。
先量规模：

```text
$ python3 - <<'PY' （临时脚本，已删）
159 capabilities publish 281 events
 button ['clicked', 'pressed', 'released', 'state_changed']
 check_box ['toggled', 'state_changed']
 slider ['value_changed', 'slider_moved']
 ...
```

**159 个 capability 公布了 281 个事件名。**

### 15.1 🔴 取证：与 `commands` **同形**，但后果不同

```text
$ grep -rn "capability.events\|cap.events" src/ --include=*.rs
 src/widget/capability.rs:1101: events: capability.events.to_vec(), ← 唯一的读取点：导出 manifest
```

即：`events` 也是「只有声明、只有导出、无人使用」。但它与 `commands` **不是同一个缺陷**，
这个区别决定了修法：

| | `commands` | `events` |
|---|---|---|
| 本质 | 一个**可被调用**的动作 | 一个**由控件在交互后自行发出**的后果 |
| 「无人使用」的含义 | 没有调用入口 → 必须**补入口** | 调用方无法要求控件发事件 → 入口没有意义 |
| 真正缺的东西 | `invoke_command` | **从「公布的名字」到「真正会响的信号」的桥** |

所以事件这一侧的缺口更根本：**名字是惰性数据**。一个通过注册表发现控件的消费者，
读到了 `"selection_changed"`，想订阅它 —— **没有任何 API 能把这个名字变成一个订阅**。

### 15.2 关键发现：机制**已经存在**，缺的是桥

```text
$ grep -n "pub fn connect" src/signal/hub.rs
 59: pub fn connect<F>(&self, name: impl Into<String>, slot: F) -> ConnectionHandle
 159: pub fn connect_once<F>(...)
```

`signal::CustomSignalHub` 就是一个**按名字寻址的信号注册表**
（`connect(name, slot)` / `emit(name)` / `disconnect(name, handle)`）。

所以本轮**不新建机制**，只搭桥（原则 #28：别为「看起来完整」造多余的抽象）：
把「capability 公布的事件名」接到「hub 的具名信号」上。

### 15.3 实施：`connect_event` / `event_is_subscribable`

```rust
pub fn connect_event<F>(&self, control_name: &str, event_name: &str,
 hub: &CustomSignalHub, slot: F)
 -> Result<ConnectionHandle, CapabilityAccessError>

pub fn event_is_subscribable(&self, control_name: &str, event_name: &str,
 hub: &CustomSignalHub) -> Result<(), CapabilityAccessError>
```

设计决定与理由：

| 决定 | 理由 |
|---|---|
| **先校验名字是不是这个控件公布的** | 这一步让「公布的列表」变成**有效事实**：订阅者只能挂到真实存在的事件上，而不是挂到一个永不触发的名字上 |
| **`hub` 作参数，不用全局** | hub 的归属者是「分发事件的那一方」（应用 / 测试 / 平台后端），库层不该自造全局态；作参数也让测试不需要进程级状态 |
| **反向校验复用 `UnknownCommand`** | 事件也是一种「控件能做的动作」，只是调用方不能主动触发；再加一个语义相同的第四个变体会违反规则 #54 |
| **`event_is_subscribable` 走真实连接再断开** | 与 `connect_event` 共用同一条校验路径；若另写一份判断，二者必然漂移 |

### 15.4 测试重点：断言**投递**，不只断言名字

这一点是本轮最容易做错的地方 —— 前三条测试**只要「校验名字然后丢掉 slot」就能全过**，
而那种实现在调用方看来是「拿到 handle、永远不被回调」，
**正是第 33 轮命令契约要防的「为没发生的事报成功」**。所以加了投递断言：

```rust
factory.connect_event("list_box", "selection_changed", &hub, move || { count += 1; })?;
assert_eq!(count, 0, "the slot must not run before an emit");
hub.emit("selection_changed");
assert_eq!(count, 1, "an event subscribed to through its published name did not receive 
 the emit, so the bridge validated the name without connecting the slot");
```

`tests/capability_event_surface_test.rs` 共 5 条：

| 测试 | 内容 | 结果 |
|---|---|---|
| `every_published_event_name_is_subscribable` | **281 个事件名**逐个订阅 | ✅ PASS |
| `an_unpublished_event_name_is_refused` | 未公布的名字必须被拒（**防「一律 Ok」实现**） | ✅ PASS |
| `an_unknown_control_has_no_events` | 未知控件不归退到公共列表 | ✅ PASS |
| `a_published_event_subscription_actually_delivers` | **端到端投递**（防「校验后丢 slot」） | ✅ PASS |
| `a_published_event_with_a_payload_is_reachable_by_name` | 带载荷的事件同样可达（281 个里大多数带载荷） | ✅ PASS |

| # | 注入内容 | 期望 | 实测 |
|---|---|---|---|
| 1 | 删掉 `connect_event` 里的事件名校验 | 测试 FAIL | ✅ FAIL（`the bridge accepted an event name the control does not publish`） |

# 第 35 轮（追加任务）— alias 全量清理：314 → 188

## 16. 你的问题与直接回答

> 控件 alias 是否需要全部删除，本项目全新、无用户，免得多个 alias 重复、内部属性混乱、控件名称写死。

**回答：不需要全删，但确实有大量是垃圾——本轮删了 127 条（40%），并加了门禁防止回潮。**

判据不是「名字看着多余」，而是**能不能构造出反例证明它不做事**。

### 16.1 决定性事实：`normalize_key` 已经吃掉分隔符差异

```rust
// src/widget/capability/coercion.rs:651
pub fn normalize_key(input: &str) -> String {
 input.chars()
 .filter(|ch| !matches!(*ch, '_' | '-' | ' ')) // ← 丢掉 _ - 空格
 .flat_map(|ch| ch.to_lowercase())
 .collect()
}
```

而工厂**所有名字查找都先过这一层**（`capability()` / `create()` 都调 `normalize_key`）。
于是：

```
normalize_key("checkbox") == normalize_key("check_box") == "checkbox"
```

**结论：`aliases: &["checkbox"]` 这一行，对查找没有任何影响。**
它们两个本来就在同一个 key 上。

### 16.2 四类 alias 与各自处置

实测（临时脚本，已删）：

| 类别 | 数量 | 处置 | 依据 |
|---|---|---|---|
| **分隔符变体**（`checkbox` / `combobox` / `lcdnumber` / `toolbar` …） | **124** | ✅ **删除** | `normalize_key` 已等价；**可证明为无操作** |
| **同名被两个 capability 声明**（`table_widget` 的 alias） | **1** | ✅ **删除** | 归一化后与 canonical `table` 同 key，是第三份拷贝 |
| **重复 capability**（`toolbox` 与 `tool_box`） | **1 个 capability** | ✅ **删除** | 同一个 key 两个条目 → 答案由注册顺序决定 |
| **真正的同义词/缩写**（`btn` / `gauge` / `scroll_wheel` / `k_line` / `shimmer` / `web_view` / `toast` / `input` / `sheet` / `pull_to_refresh` …） | **188** | ⛔ **保留** | 归一化**无法**产生这些拼写，它们是真的第二个名字 |

### 16.3 为什么不「全部删除」（这是本轮最重要的判断）

**全删会真的破坏已公布的 API**。以下是本轮**实测**仍可解析的名字（若全删即失效）：

```
pull_to_refresh knob input / text_input
sheet / modal_sheet combo chart_widget
notification page_numbers waterfall_layout
```

平台能力矩阵文档都以它们为键。全删 = 破坏性变更（违反原则 #21/#26），
而收益为 0 —— 它们**没有造成**任何归一化冲突（§16.4 已证明碰撞数为 0）。

### 16.4 先证明「无名字失效」，再落盘

删除前先写死判据：

> 对每一条被删的 `(canonical, alias)`，若 `normalize_key(alias) == normalize_key(canonical)`，
> 则该 alias 与 canonical 占**同一个 key**，删除**不改变任何查找**。

## 22. `events` 的发射端：`signal::EventSignalBinder`

### 22.1 先说清缺口（这是第 34 轮没做完的一半）

```text
$ grep -rn "CustomSignalHub" src/ --include=*.rs | grep -v "^src/signal"
 src/widget/capability.rs:864: …（只是文档注释）
 src/widget/capability.rs:902: hub: &crate::signal::CustomSignalHub, ← connect_event 的参数
```

即：`connect_event` 能让调用方按**公布的名字**在 hub 上订阅，**但控件的真实信号从未接到 hub**。
`Button` 发的是它自己的 `clicked`（`GenericSignal`），与 hub 没有任何关系。

**后果与第 33 轮 `commands` 完全同形**：调用方能订上一个永不触发的名字，
拿到 handle、看着控件被点击、**永远不会被回调，且任何地方都不报错**。

### 22.2 为什么不做成「自动」，而是一个 binder

控件的信号是**有类型的**：`clicked` 是 `GenericSignal`，`value_changed` 是 `Signal1<i32>`，
`toggled` 是 `Signal1<bool>`。而 `CustomSignalHub::emit(name)` **不携带值**。

所以桥接必须**逐个事件决定「载荷去哪」**，而这个决定属于调用方：
不用值的一方不该为此付代价，用值的一方应当**显式**给出映射，而不是收到一个静默的有损默认。

于是 `EventSignalBinder` 是「可复用的那一半」：它持有订阅并在析构时一并摘除。

```rust
let mut binder = EventSignalBinder::new(hub);
binder.forward_unit("clicked", &button.clicked_signal()); // 无载荷
binder.forward_mapped("value_changed", &slider.value_changed, // 有载荷
 move |value| { /* 显式处置 */ });
```

### 22.3 🔴 自建的 binder 里抓到一个**真实的订阅泄漏**

写测试时 `dropping_the_binder_unsubscribes` 当场 FAIL，
根因是我自己第一版的 `unbind_all`：

```rust
// 错误版本
for (name, handle) in self.handles.drain(..) {
 hub.disconnect(&name, handle); // ← handle 来自「控件的信号」，不是 hub 的
}
```

`handle` 是 `signal.connect(..)` 返回的，属于**控件的信号**；hub 里没有这个 key，
`hub.disconnect` 返回 `false` 且**什么都没摘掉** —— 每次重建控件就多一个常驻订阅者。

**修复**：记住 handle 属于哪个信号，从**源信号**上摘：

```rust
enum ForwardSource {
 Unit(GenericSignal), // 无载荷，直接持有
 Typed(Box<dyn Fn(ConnectionHandle) + Send>), // 有载荷，`T` 在闭包里被擦除
}
```

`Signal<T>` 是泛型、无法像 `GenericSignal` 那样直接存，
所以**在 `T` 仍然已知的那一点**构造断开闭包并擦除类型。

# 第 37 轮（用户追问）— `embedded_target_fps_clamps` 偶发失败：根因取证与修复

## 26. 结论先行

**能找出原因，而且原因不是「时序抖动」，是一个确定的逻辑缺陷。** 此前把它记为「偶发」
是**错的**，本轮纠正。

```text
根因：同一个进程级全局（embedded engine 的 target FPS）
 被两个**不同模块各自的** test mutex 保护
 → 两把锁锁同一个资源 = 互斥为零
注入取证（把它从「偶发」变成「必现」）：
 left: 120 right: 72
```

## 26.1 第一步：先看这个测试到底在断言什么

```rust
// src/render_engine/embedded.rs
#[test]
fn embedded_target_fps_clamps() {
 let _guard = test_guard();
 set_embedded_target_fps(DEFAULT_EMBEDDED_TARGET_FPS);
 assert_eq!(set_embedded_target_fps(0), MIN_EMBEDDED_TARGET_FPS);
 assert_eq!(set_embedded_target_fps(999), MAX_EMBEDDED_TARGET_FPS);
 assert_eq!(set_embedded_target_fps(72), 72);
 assert_eq!(embedded_target_fps(), 72); // ← 失败点（曾报 left: 120）
 set_embedded_target_fps(DEFAULT_EMBEDDED_TARGET_FPS);
}
```

它**已经有** guard，也**已经有**「先置回默认值」与「事后清理」——说明作者已经意识到
这是进程级单例。所以问题不在「有没有加锁」，而在「**锁是不是同一把**」。

## 26.2 第二步：grep 取证——谁在改同一个全局

```text
$ grep -rn "set_embedded_target_fps" src/ --include=*.rs | grep -v "^src/render_engine/embedded.rs"
 src/render_engine/embedded_engine.rs:97: set_embedded_target_fps(120);
 src/render_engine/embedded_engine.rs:118: set_embedded_target_fps(120);
 src/bindings/binding_impl.rs:3187: let _guard = ...embedded_test_guard(); ← 已迁移
```

`embedded_engine.rs` 也在改同一个全局，**且自己声明了一把锁**：

```rust
// src/render_engine/embedded_engine.rs（修复前）
fn test_guard() -> crate::compat::MutexGuard<'static, ()> {
 static GUARD: OnceLock<Mutex<()>> = OnceLock::new(); // ← 第二把锁
 GUARD.get_or_init(...)
}
```

而共享 guard 自己的文档里就写着这段历史：

```rust
// src/render_engine/embedded.rs:384-388（原文）
/// The lock has to be **shared across modules** ... each used to take its own
/// module-local `OnceLock`. Two locks over one resource exclude nothing, which is
/// how `embedded_target_fps_clamps` came to fail depending on scheduling.
```

即：**这个缺陷曾被修过一次，但只迁移了 `binding_impl.rs`，漏掉了 `embedded_engine.rs`。**
——正是「修一个点必须扇同类模式」（规则 #2 冰山法则）没做完的后果。

## 26.3 第三步：不靠运气复现，而是**把窗口撑开**（关键手法）

先跑 12 次：**12/12 全过**。所以「再跑几次看看」这条路走不通——窗口是**纳秒级**的，
靠自然调度基本碰不上。

于是**主动把竞争窗口从纳秒撑到毫秒**，在断言中间注入 400ms：

```rust
assert_eq!(set_embedded_target_fps(72), 72);
std::thread::sleep(std::time::Duration::from_millis(400)); // 注入
assert_eq!(embedded_target_fps(), 72);
```

实测立刻失败，并且**报出的值就是另一模块写进去的 120**：

```text
thread 'render_engine::embedded::tests::embedded_target_fps_clamps' panicked at src/render_engine/embedded.rs:419:9:
assertion `left == right` failed
 left: 120
 right: 72
```

**这就是「假设」与「取证」的区别**：120 正是 `embedded_engine.rs:97/118` 的值，
不是别的测试、也不是环境问题。根因确证。

## 26.4 修复（两处）

**① `embedded_engine.rs` 不再自建锁，改为委托共享 guard**

```rust
fn test_guard() -> crate::compat::MutexGuard<'static, ()> {
 crate::render_engine::embedded::embedded_test_guard()
}
```

**② 两个测试结束后把 FPS 恢复默认值**

这是同一污染的另一半：这两个测试把 FPS 提到 120 只是为了让自己的循环跑快一点，
但**不恢复**就等于把 120 留给下一个测试。之前靠 `embedded_target_fps_clamps`
自己「先置默认」抵消，那是**掩盖**而不是修复。现在两边都自觉。

为了让「恢复」引用同一个常量而不是重写 `60`，把 `DEFAULT_EMBEDDED_TARGET_FPS`

## 26.5 修复后：**同一个实验**必须不再失败（否则修得不彻底）

## 26.6 防复发：新增门禁 `check_test_guard_uniqueness.sh`

只修这一个文件等于没修（规则 #2）。新增门禁把「同一全局只能有一把 test 锁」

- 识别方式：**看返回类型**（`-> MutexGuard<'static, ()>`）而**不是看名字**。
 这一点是刻意的——本轮抓到的那个 guard 就叫 `test_guard`，**名字与共享 guard
 (`embedded_test_guard`) 不同**，任何靠名字匹配的检查都会恰好漏掉它。
- 允许**委托**（局部包装函数），禁止**自建** `static OnceLock<Mutex<()>>`。
 `src/i18n/macros.rs` 就是一个正确的委托包装，不应被误报。
- 不报 `OnceLock<Mutex<T>>` 存**状态**的单例（registry / config）：它们是单例本身，不是锁。

## 26.8 本轮教训（值得写下来）

1. **「偶发」不是结论，是「还没取证」**。本轮把它当成待查项而不是已知噪声，
 结果发现它是一个**确定的**逻辑缺陷，而且**曾被修过一次、只修了一半**。
2. **低概率竞争不该靠多跑几次复现，应当主动撑开窗口**。12 次全过很容易让人
 写下「疑似环境问题」；注入 400ms 一次就出，且报出的值直接指认了写者。
3. **修复必须用「原来会失败的同一个实验」验收**。修复后仍注入同样的 400ms，
 不失败才算生效——否则只是碰巧没撞上。
4. **门禁的识别依据不能是名字**。本轮的缺陷恰好是「名字不同、语义相同」，
 靠名字匹配的检查会漏；改看返回类型才抓到。
