## 1. 批 1 —— P0-1 状态来源上提（BLUE23 §2.2）

### 1.1 做了什么

把「指针 hover / 按下 / 手势归属 / 焦点原因」四个**每个控件都该有的事实**，
从各控件的私有字段**上提**到 `BaseWidget`（`src/widget/base.rs`），
并让 [`Widget::widget_state`] 的默认实现从这四个事实推导。

| 字段 | 谁写 | 语义 |
|---|---|---|
| `hovered: bool` | `MouseEnter` ⇒ true / `MouseLeave` ⇒ false（运行时合成） | 「指针在我身上」 |
| `pressed: bool` | `MousePress`（命中且 enabled）⇒ true；`MouseMove` 跟位置；`MouseRelease` ⇒ false | 「该画凹陷」 |
| `grabbed: bool` | 同上，但 `MouseMove` 不清 | 「手势归我」 |
| `focus_reason: Option<FocusReason>` | `FocusGained { reason }` / `FocusLost` | 「焦点在不在，为何而来」 |

新增访问器：`is_hovered/set_hovered`、`is_pressed/set_pressed`、`is_grabbed/set_grabbed`、
`focus_reason()`、`draws_focus_ring()`、`set_focus_reason()`。

`widget_state()` 默认实现（保持单值、保持优先级文档一致）：

```rust
fn widget_state(&self) -> crate::style::WidgetState {
    use crate::style::WidgetState;
    if !self.is_enabled() { return WidgetState::Disabled; }
    let base = self.base();
    if base.is_pressed() { WidgetState::Pressed }
    else if base.is_hovered() { WidgetState::Hover }
    else if base.draws_focus_ring() { WidgetState::Focused }
    else { WidgetState::Normal }
}
```

### 1.2 删除的重复字段（冰山法则 #2）

`blue23.md` 判据 3 要求「`hovered: bool` 只允许 BaseWidget 一处」。实跑列出全部第二来源并逐一处置：

| `base_widgets/radiobutton.rs` | `focused` / `focus_reason` / `hovered` | 全删，`visual_focus()` 改调 `base.draws_focus_ring()` |
| `display_widgets/switch.rs` | `focused` / `focus_reason` / `hovered` | 全删；保留自己的 `pressed`（**提交守卫**，语义不同，见下） |
| `menu_toolbar/tool_button.rs` | `hovered`（另保留 `pressed` 提交守卫） | 删 hover；`pressed` 改用 base |

> **保留 `pressed` 的两处（`switch` / `tool_button`）是裁定，不是遗漏**：
> 它们的 `pressed` 是「一次落在本控件上的按下尚未释放」的**提交守卫**，
> 而 `BaseWidget::is_pressed` 是「该画凹陷」的**画笔**。二者在「指针移出后」不同：
> 画笔清除、守卫保留以便识别后续的 release。计划 §2.2 的表格把两者都叫 `pressed`，
> 实录在此更正为**守卫另存**，并在字段文档里写明差异。

### 1.3 🔴 由本项**逼出的一个真缺陷**（必须记录）

上提后立刻出现 1 个新缺陷、被既有测试抓住：

**信号消失**。`BaseWidget::handle_event` 在 `MousePress` 里**先**把 `pressed` 置真，
于是 `Button::set_pressed(true)` 里那句「值相同则 return」直接吞掉了 `pressed_signal`——
按钮按下**不再发出任何信号**。5 条既有测试立刻变红
（`event_mouse_up_releases_and_clicks` / `a_release_inside...` 等）。

**根因**：`base.pressed` 同时承担了两个角色——「画笔」与「信号边沿闩锁」。
两者语义不同：画笔是**连续量**（移出即清），边沿是**一次性的**（每个变化只发一次）。

**修法**（不是回退）：
1. 二进制控件新增一个**信号闩锁** `signaled_pressed: bool`，只用于决定「这次变化发不发信号」；
   它从不参与绘制，只与 base 的画笔比较，**不可能漂移**。
2. 控件的 `handle_event` **先**处理自己的手势，**再**调 `self.base.handle_event(event)` 记录原始事实——
   这样 release 分支读到的 `is_grabbed()` 还是按下时的值（base 尚未清除）。

> 这条修正比「照计划表格直接改」更准确：计划假设 base 只记录、控件只读；
> 实际是 base 记录 + 控件发信号，两者必须各有一个闩锁。**记录在案，供后续控件参考。**

## 4. §3 动效总线（P0-4 / P0-5）

### 4.1 P0-4 `Widget::tick` / `is_animating` 上提（§3.2）

在 `Widget` trait 新增两个方法，默认 `false`/`false`（纯加法，180 个不动的控件无需改动），
并把**已有的** 11 个固有 `tick` 接到 trait 实现上（每处只加一次委托）：

| 控件 | 固有 `tick` 签名 | 桥接 |
|---|---|---|
| `button` | `u32 -> bool` | 直接委托 |
| `switch` | `u32 -> bool` | 直接委托 |
| `floating_label` | `u32 -> bool` | 直接委托 |
| `lineedit` / `tag_input` / `inplace_editor` | `u32 -> bool` | 直接委托 |
| `code_editor` | `u32 -> bool` | 直接委托 |
| `spinner` | `u32 -> ()` | 包一层，返回 `active` |
| `lottie` / `animated_image` / `rive` / `hero_animation` | `u64 -> bool` | 边界 `u32 → u64` |
| `video_player` | `f64 -> bool`（秒） | 边界 `ms → s` |

> trait 契约统一为 `u32` 毫秒；媒体控件用 `u64`/`f64` 是因为它们用的是**媒体时钟**
> （位置而非帧差），在边界处转换而不是强行统一其内部时钟。

### 4.2 P0-5 `tick_animations`：唯一的帧驱动（§3.3）

`src/widget/runtime.rs` 新增：

```rust
pub fn tick_animations(delta_ms: u32) -> bool;  // 推进所有正在动的控件，返回是否还需下一帧
pub fn has_animating_widgets() -> bool;         // 不动则不扫
```

**为什么必须是唯一一处**：每个控件自建定时器 ⇒ 100 个定时器且与帧率不同步；
每个后端各调一次 ⇒ 同一按钮一帧被推进两次、速度随调用点翻倍。
「谁在被推进」由**控件自述**（`is_animating()`）决定，不由运行时维护动画名册——名册会「注册未注销」泄漏，自述不会。

### 4.3 🔴 由本项**逼出的第二个真缺陷**（立即修正，未拖延）

`Button::is_animating` 初版写成 `progress() != self.interaction_target` ——
但 `interaction_target` **只在 `tick` 里更新**，所以一个刚被 hover 的按钮在两帧之间
`is_animating()` 返回 **false**，总线**永远不会启动它的帧**（测试 `the_bus_...` 立即变红）。

**根因**：`is_animating` 读的是**过期的 tick-time 字段**，而不是**当前状态推导的目标**。
**修法**：改为 `progress() != self.interaction_target_progress()`（从状态推导）。

> 这是「不跑就以为对」的典型形状：单测逐条过、总线一定死。记录在案。

### 4.6 本轮随手修掉的两个**门禁自身**缺陷（当时修，不记录后拖）

1. **`state_source_scan` 的重注入路径**：注入插在文件末尾，而末尾在 `#[cfg(test)]`

> 两个都是「门禁绿了但其实没比较」——本仓已为此立过规矩（#108、log-230923-1 §44），

## 17. G-2b + G-4b —— 字形来源抽象与点阵 CJK（先拿中文，代价最小）

### 17.1 抽象（`src/render/text/glyph_source.rs`，新建）

把「这个字符长什么样」从函数提升成**两个类型**：

| 类型 | 回答的问题 |
|---|---|
| `GlyphSource` | 「你有这个字符吗？像素是什么？」—— 未覆盖时返回 `None`，**不**返回方框 |
| `FontStack` | 「我有几个 face，谁说了算？」—— 先命中者胜 |

三个关键决定：

1. **`None` 而不是方框**。若一个字面把「未覆盖」答成方框，回退链就永远到不了第二个 face。
   豆腐块（`TOFU`）因此**不是一个 `GlyphSource`**，而是解析器在没有来源时的兜底。
2. **位序是数据的一部分**（`BitOrder::{LsbFirst,MsbFirst}`）。`font8x8` 是 `1 << x`（左=bit 0），
   Unifont 的 `.hex` 是 `0x8000`（左=bit 15）。命名差异，而不是在加载时把 85 KB 转换一遍。
3. **行内 / 借用二选一**（`GlyphRows::{Inline8,Borrowed}`）。`font8x8` 按值返回 8 字节，
   大表必须借用——一个 enum 同时表达，零分配。

### 17.2 数据（`src/render/text/cjk_bitmap_data.rs`，生成）

| 项 | 数值（实测） |
|---|---|
| 字形数 `N` | **2361** |
| `ROWS` | 75552 = N × 32（16 行 × 2 字节，MSB-first） |
| `CODEPOINTS` | 9444 字节，**严格升序且唯一**（二分查找的前提） |
| 生成文件体积 | 494228 字节；数组数据 84996 字节 ≈ 83 KB |

覆盖范围：`U+3000..=U+303F` / `U+3040..=U+30FF` / `U+4E00..=U+5548` / `U+FF00..=U+FFEF`。
**刻意不含 ASCII**：8x8 face 已覆盖，且默认构建的快照必须逐字节不变。

### 17.3 接线：三处消费点合一

`glyph_rects`（光栅器与 SVG 后端**共用**的几何推导）改为走栈，并按**返回位图的
`width/height`** 分格，而不是硬编码 8：

```rust
let (glyph, _) = crate::render::text::resolve(ch);
let gw = glyph.width as i32;   // 8 或 16
let gh = glyph.height as i32;
```

默认构建的栈只有 `[font8x8]`，所以 8×8 的算术逐条重现原式 —— **不靠「差不多」，是同一个表达式**。

## 18. G-3 —— 双向文本，以及顺手合并的三处重复

### 18.1 `unicode-bidi` 接入（`src/render/text/bidi.rs`，新建）

规则是 UAX #9 的 **L2**，但施加在**簇的置换**上而不是字符串上：

```rust
// 从最高位级到最低**奇数**位级，反转每一段「该位级及以上」的连续簇
for level in (lowest_odd..=highest).rev() { … order[start..i].reverse(); … }
```

三个决定：

1. **只重排簇，不重排字符**。字符级反转会把基字与其组合记号拆开，把记号画到它不属于的字母前面。
2. **纯 LTR 行返回恒等置换**。这是 376 份快照不受影响的原因，也是「不是差不多，是恒等」的证明。
3. **`unicode-bidi` 用 `default-features = false, features = ["hardcoded-data"]`**，于是 `mini`/`embedded`
   也能带上（`cargo check --features mini` 实测通过）。逻辑不是数据，所以它**默认开启**。

### 18.2 顺手合并的三处「同一事实的第二份抄写」（原则 #51）

做 G-3 时发现：SVG 后端有一份 `shape_text` 的**副本**。若只给光栅器加重排，两个后端就会
一个 RTL 一个 LTR —— 静默不一致。于是把「一行的簇从哪来」合并成一处，并连带清掉两处同类重复：

| 重复 | 证据 | 合并后 |
|---|---|---|
| 软件光栅器与 SVG 后端各有一份聚类循环 | `containers.rs` / `backend.rs` 两个 `shape_text` 几乎逐行相同 | `text::line::shape_line`（后端只提供 `scale`） |
| `widget::metrics` 自备一套推进模型与**不同的**宽字符表 | `metrics.rs` 注释自陈「Mirrors `src/render/pipeline/pixel_ops.rs`」 | `text::for_each_cluster` + `estimate_cluster_advance` |
| 两处宽字符范围表**范围不同** | render: `0x2E80..=0xA4CF`；metrics: 另有 `0x20000..=0x3FFFD` | 一张并集表，两处共用 |

第二行是真缺陷：`metrics` 的聚类**不合并 emoji 的 ZWJ 续接**，所以 `👨👩👧` 被量成 2 em、
被画成 1 个簇——「量宽」与「画宽」用两把尺子，正是 crate 自己记录过的旧伤。

合并后 `estimate_text_width` 走 `for_each_cluster`（一个复用缓冲，无逐簇分配），
`estimate_cluster_advance` 成为唯一推进模型，`is_wide_scalar` 从 `text` 导出。

## 21. G-1 塑形层 + G-4c 矢量子集（真 advance / kerning / 阿拉伯连写）

### 21.1 依赖选型（实测）

| crate | 版本 | 为什么是它 |
|---|---|---|
| `unicode-bidi` | 0.3.18 | 见 §18；`no_std` 可用 |
| `rustybuzz` | 0.20.1 | 纯 Rust 的塑形；**不用** `harfbuzz-sys`（需 C 工具链与交叉 sysroot，会让 Android/iOS/wasm 门禁变红） |
| `ttf-parser` | 0.25.1 | 读 face 的字符表（`covers` 与字形索引） |

### 21.2 矢量子集生成器（`tools/gen_font_subset.py`，新建）

两个 face，均为 OFL，均**先声明许可再运行**（与 `.hex` 生成器同一道门禁）：

| face | 上游 | 子集体积 | 字形数 | 布局表 |
|---|---|---|---|---|
| `latin`（Open Sans） | `google/fonts` ofl/opensans | **35896** 字节 | 309 | GSUB + GPOS |
| `arabic`（Noto Naskh Arabic） | `google/fonts` ofl/notonaskharabic | **70576** 字节 | 566 | GSUB + GPOS |

三个工程决定：

1. **载荷用 `include_bytes!`，不写成 Rust 数组**。36 KB 写成 `0x00,` 字面量约 150 KB 源码——
   比它描述的那份二进制更糟。
2. **可变字体先 instance 到单一 wght**，再去掉 `DSIG`。不这样，一个只用一种字重的标签要背上八种字重的 delta。
3. **`recalcTimestamp=False`**。fontTools 默认在保存时把 `head.modified` 盖上当前时间，于是两次运行
   产出两个不同文件、`--check` 永远不可能一致。修掉后 `--check` 幂等（实测）。

### 21.3 塑形层（`src/render/text/shaping.rs`，新建）

`RustybuzzShaper` 实作既有的 `TextShaper` trait。四个决定：

1. **face 每次调用时解析**，而不是存进字段。face 内部有可变布局缓存、因此**不是 `Sync`**，
   而 `TextShaper: Send + Sync`。用锁会让每次测量都付一次锁的代价；解析一个表目录只是几十次读。
2. **按 `Font::family()` 选 face**，而不是「第一个覆盖文本的 face」。后者会让**每个**标签的
   advance 在打开 feature 的那一刻改变——度量即布局，那叫意外，不叫升级。默认构建里
   两个 face 都不存在，于是模型照旧。
3. **簇的推进按字节区间归属**：把每个字形的 advance 记到它所属的簇上，而不是按数量数过去——
   一个跨字符的簇会被数错。
4. **`None` 就是 `None`**：没有 face 时回退模型，绝不编造字形。

## 22. 剩余与裁定：G-5 抗锯齿轮廓光栅化 / G-6 彩色 emoji

**已交付**：G-1（塑形层）、G-2b（`GlyphSource`）、G-3（bidi）、G-4a（许可门禁 + NOTICE）、
G-4b（点阵 CJK）、G-4c（矢量子集打包，两个 OFL face），以及 G.8 的六道门禁。
G-5 里「**真实 advance + kerning**」这一半已由 §21 交付（实测 W > i、阿拉伯连写生效）。

**未交付，且如实记录**：G-5 的「抗锯齿」一半与 G-6（彩色 emoji）。

技术上的阻断点只有一个，且是**接口级**：

- 抗锯齿需要**每像素覆盖率**，而 `GlyphSource` 现在返回的是 `&'static [u8]` 的**1 位**行数组；
  覆盖率是运行时算出来的、不能是 `'static`，于是要么拥有它（每字形一次分配 + 缓存），
  要么把 trait 改成「由调用者提供缓冲、就地光栅化」——后者会同时要求 SVG 后端改发**轮廓**
  `<path>`（它现在与光栅器共用 `glyph_rects` 的像素矩形）。
- G-6 还需要在同一个抽象里表达**彩色**字形（CBDT/sbix），即第二种像素格式。

也就是说：这两期不是「再写一点」，而是**重画本层的分配契约与 SVG 的发射模型**。
按用户指令 #6（不降级、要完整）与 #12（精炼高效）的取舍，本轮**不半途开工**——
半成品的两个字形表示会让「一条推导」这条刚立起来的规矩当场失效。
这是一个需要独立一轮的、边界清楚的重构，其入口已经就位：
`GlyphBitmap`/`GlyphSource` 是唯一的字形入口，加一层覆盖率/轮廓只是它的第二个实现者。

> 依据原则 #7（无占位、无空实现）与 #1（结论必须有证据）：与其留一个说「已支持抗锯齿」
> 而实际走方框的实现，不如不留。本节的措辞不是「还没做完」，而是**明确未做**。

## 24. 一句话结论

**文本层从「一个返回 `[u8; 8]` 的函数」变成了「一份数据 + 一条回退链 + 一笔算法」。**

默认构建一个字节都没变（376 份快照逐字节相同），而中文、双向文本、阿拉伯连写
各自只差「开一个 feature」。三条不可让的约束全部成立：

1. **默认不带任何字体数据** —— 实跑：无 profile 启用 `fonts-*`，且门禁反向注入可证；
2. **塑形能力与字体数据正交** —— `fonts-cjk-bitmap`（数据、不需塑形）与 `text-shaping`（引擎、无数据无用）是两个独立 feature；
3. **字形从不常驻 RAM** —— 点阵按需二分 + 32 字节窗口；矢量按需解析、无缓存、无全局可变状态。

本轮同样修掉了计划未记载的 **第三条字形路径**（GPU），并把同一事实的四份抄写合并成一份
（聚类循环、推进模型、宽字符表、字形几何）。G-5 的抗锯齿一半与 G-6 如实留白，
阻断点是接口级的、入口已就位（§22）。
