## 0. 一句话结论

**用户指令 #11（「对照 `snapshots/svg/` 逐图修正」）不是一次抽查，而是一次新维度的取证：
两张快照（栅格 / 矢量）对同一个控件给出的答案不一致，本身就是缺陷。**

本轮据此新增第 5 条渲染判据 **P5「画出的每个元素都必须落在控件自己的矩形内」**，
它一次抓出 **68 个控件** 的外形缺陷，全部修完（`failed=0`）：

- **两个坐标系混用**（`group_box`/`panel` 标题用**父空间**坐标画到**本地空间**，`tab_bar`

- **一条 41 处调用的通用文本绘制无任何宽度约束**；
- **`popover`/`fab`/`slider`/`sparkline`/`meter` 等把描边、圆盘、阴影的「半宽」算漏**。

**并且它同时纠正了我自己第一版判据的两处错误**（§3）：文本宽度按「1 em/字符」估算
（把 106 px 的标题量成 182 px）、`stroke-width` 缺省值当成了半宽。**判据的错必须和代码的错

（规则 #18）。修完后 P5 的净增缺陷是 **68 个真缺陷、0 个假缺陷**。

## 2. 第 1 层新增判据 P5（第 5 条，覆盖全部 188）

### 2.1 为什么 P1–P4 看不见它（这是本轮的核心论证）

| 判据 | 读什么 | 为什么看不见「画到框外」 |
|---|---|---|
| P1 | 栅格的非背景像素数 | 栅格**有边界**：越界像素被裁掉，框内像素照常计数 → 计数**正常** |
| P2 | 栅格的主色 | 同上；主色来自框内像素，与越界无关 |
| P3 | 两种外观的栅格主色 | 同上 |
| **P5** | **SVG 的绝对坐标** | SVG **无边界**：越界元素原样出现在文档里 → 一眼可见 |

**同一个控件，两个后端给出不同答案，这就是缺陷**：一个把它裁掉（用户看不到），另一个
把它画出来（快照里悬在画面之外）。`group_box` 正是这样 —— 标题 `y = -8`，**一半以上字形在
框外**，而 P1–P4 全绿。

### 2.2 P5 的判据（写成相对形式，规则 #103）

```
对每个控件（按 canonical name，188 个）：
 以 CENSUS_RECT = (0,0,240,120) + dark 外观渲染为 SVG
 对文档里每个图元（rect / circle / line / text / path）求包围盒
 要求包围盒 ⊂ 控件矩形（允许 0.5 px 描边半宽）
```

- **相对**：判据是「在框内」，不是「等于某个坐标」；
- **分类**：不求「正好 240×120」，只求「不越界」——数据色控件的外形自由度不受影响；
- **双向断言**：`tools/control_overflow_exemptions.txt` 里的豁免一旦**不再越界**即测试失败
 （与 `KNOWN_INVISIBLE` / `KNOWN_THEME_BLIND` / 两张豁免表同构）；
- **`unmeasurable` 也失败**：求助包围盒的图元被记为「测不出」，**不得静默放过**
 （规则 #107：跳过的输入不是通过的输入）。

### 2.3 反向注入（规则 #19/#64，实测）

```
$ python3 - <<'PY' # 把 group_box 的标题改回「以边框线为中心」
 ... Rect::new(x, rect.y - text_height / 2, ...) ...
PY
$ cargo test --test control_rendering_census_test p5_... -- --nocapture

$ cp /tmp/groupbox.bak src/widget/container_widgets/groupbox.rs # 还原
$ cargo test --test control_rendering_census_test

```

**实测 FAIL → 还原后 PASS**，判据可失败。

## 3. 判据自身的两处错误（P5 第一版，当场修正）

**门禁的错与代码的错同样是缺陷。** 第一版 P5 报出 68 个控件，逐个核对后发现其中 **25 个是
误报** —— 错在我的判据，不在控件。

| # | 判据错误 | 现象 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | 文本宽度按「**1 em / 字符**」估算 | `font_preview` 的 24 pt 标题被量成 **1042 px**，要求 40 个控件截断**本来放得下**的文本 | 渲染器的 `estimate_cluster_advance` 实际是：宽标量 1 em、空格 0.33 em、**其余仅 0.6 em** | 判据里镜像该模型（`glyph_advance`/`is_wide_scalar`）；`September 2026` 从 182 px 修正为 **106 px** |
| 2 | `stroke-width` 缺省值当成**半宽** | `<line … stroke-width="1">` 在 `x = 0` 处被判越界 | `stroke` 的缺省值写成 `0.5`，但它被当作**半宽**使用；缺省应表达「1 px 宽，半宽 0.5」，而**任何**贴边的线都必然判越界 | 缺省改为表达「宽度 1」；贴边容忍从 0.25 px 提到 0.5 px |

**教训（值得单独记下）**：**判据偏严与偏松是同一类错误。** 偏松会假通过（规则 #107），
偏严会逼着开发者去「修」没坏的东西 —— 本轮若不纠正，就会有 ~15 个控件的文本被无谓截断，
而「主题化」这个真问题被淹没在噪声里。

## 4. 抓出并修复的真实缺陷（按根因归类，非按文件）

### 4.1 🔴 坐标系混用：本地空间 ↔ 父空间（2 处）

| 控件 | 病处 | 判据/后果 |
|---|---|---|
| `group_box` / `panel` | `title_rect()` 返回 **父空间** 的 rect（`y = rect.y - text_height/2`，即边框线上方），`draw()` 却把它当**本地空间**坐标画 | 字形盒下移半行 ⇒ 标题 `y = -8`，**一半以上在框外**（快照实测） |
| `splash_screen` | logo 块放在 `text_y - logo - 16`，而 `text_y` 本身由**框中心**推出 → 框矮时 logo 起点为负 | logo 整个画在控件上方（`y = -20`） |

**修法**：`group_box` 的标题带**移进框内**（中心线落在上边框上，保住经典分组框外观），
并把擦边框的宽度按 `TITLE_PADDING` 从两端**钳在框内**（原来会盖到右邻居）；
`splash_screen` 改为**整栈居中**且仅在放得下时画 logo。

### 4.2 🔴 估算宽度与真实宽度不一致（`tab_bar`，2 个控件）

`compute_tab_width` 用 `text.len() * 8` 估算（**`len()` 数字节**），而 `draw_tab` 用
`Font::default()`（14 pt，1 em/cluster）绘制 ⇒ 布局与绘制用了**两套宽度模型**。

**修法**：
- 估算函数改为与渲染器**同一个模型**（`chars × font_size`），并**同时**作为字体声明
 （`TAB_FONT_SIZE`），使两处不可能漂移；
- 新增 `measured_title_widths`，`draw()` 先用 `context.measure_text` 测一遍全部标签
 （与 `group_box` 的 `cached_title_width` 同构），此后布局用**真实度量**；
- `Tab 1` 的 tab 宽度 52 → **50**（`3×14 + 12` 恰好，右侧不再留空头）。

### 4.3 🔴 `+ ascent` 居中：把字形下移半行（8 个控件）

**这是本轮影响面最广的一条。** 渲染器把 `origin` 当作**字形左上角**（向下画一行），
而代码把它当作**基线**，于是「居中」写法写成

```rust
let y = box_y + (box_h - text_h) / 2 + metrics.ascent; // ← ascent 在行盒之内！
```

`ascent` 是行盒**内部**的上升高度，不是行盒**之上**的空白，所以这行把字形下移了 `ascent`
（≈ 0.8 行）。受影响：

| 控件 | 后果（实测） |
|---|---|
| `date_range_picker` | 日期数字整体下移，**最后一行（第 6 周）落到框外** |
| `mobile_date_picker` / `cupertino_date_picker` | 第 5 行被推到底边之外，只画出上缘 |
| `animated_image` / `lottie_widget` / `rive_widget` / `video_player` | 空态文案 `y` 偏下 |
| `empty_state` | 换行消息的最后一行越底边（`[72,112..169,126]`） |
| `fab` | 图标下移半行（另见 §4.4） |

**修法**：统一为 `y + (box_h - text_h) / 2`，并**去掉 `+ ascent`**。

### 4.4 🟠 描边/圆盘/阴影的「半宽」算漏（6 个控件）

| 控件 | 病处 | 后果 |
|---|---|---|
| `line` / `divider` | 描边**以弦为中心**，厚度 `t` 向两侧各伸 `t/2`；弦落在 `rect.y` 上 | 2 px 线在 `rect.y - 1` 处画出一行，**框外** |
| `slider` | 行程 = 全宽，手柄**居中** ⇒ 最小值时手柄中心在 `rect.x` | 手柄**左半在外**（`[-8..8]`） |
| `sparkline` | 末点圆盘 `r = 3` 居中在**最后一点**（贴在右边/下边）；折线起点未缩排描边半宽 | 圆盘右半在外（`[236..242]`） |
| `fab` | `radius = min(w,h)/2` 正好内切，**阴影又偏移 (3,3)** | 阴影在右下两侧溢出（`[61,1..181,121]`） |
| `popover` | 卡片已在右下边，阴影仍偏移 2 px | `[12,2..242,122]` |
| `meter` | `radius = min(w,h)/2 - 4`，270° 弧的**最左点比矩形左边界再左一个半径** | 弧本身超出 `[103,-35..215,99]` |

**修法**：全部改为「**先算绘制后的实际范围，再让范围适配盒子**」：
`line` 按 `thickness/2` 缩排弦的两端与位置；`slider` 行程改为 `width - 2×(size/2)`；
`sparkline` 的绘图区缩排 `max(描边半宽, 圆盘半径)`；`fab` 半径扣掉阴影偏移；
`popover` 阴影仅在偏移后仍在框内时绘制；`meter` 半径与圆心由**弧的保留带**推出。

### 4.5 🟠 `map_view` 硬编码浅色配色（第 59 轮清单遗留项）

`map_view` 在 `control_color_exemptions.txt` 里登记为 `map-content`（「瓦片是地理内容」），
**但控件根本没有瓦片管线** —— 它画的四样东西（面板、边框、网格、状态行）全是硬编码浅色，
所以**暗色窗口里的地图是一块白板，且任何主题都改不动它**。这四项**是 chrome**（它们围绕
地理内容，而不是地理内容本身）。

**修法**（规则 #108 的正面执行）：四项改读主题；**真正的数据**（网格步长、marker 颜色 ——
编码「地点」与「选中」）保留。随之**删除**那条已失效的豁免（门禁的双向断言**自己报出了
它**：`these data-colour exemptions are no longer needed: ["map_view"]`），并在文件里补
「Removed on evidence」说明 —— 与 `mini_chart`/`meter` 的先例同构。

> **这条是「指令 #6：不完整就补全，不要降级」的实例**：本可以继续把它留在豁免表里
> （门禁就不红），但那等于**把一个真缺陷合法化成「设计如此」**。

### 4.6 🟠 文本宽度无任何约束（~40 个调用点）

`RenderContext::draw_text` 只负责「把字符串画上去」，**从不问放不放得下**。字符步进是
`font.size()`，所以 14 pt 字体每字 14 px —— 一个长标签就这么一路画到控件之外。栅格后端
在画布边缘裁掉它（所以看不见），SVG 后端原样输出（所以一眼可见）。

**修法（根因，非逐点）**：在 `RenderContext` 上新增**一个**入口

```rust
pub fn draw_text_fitted(
 &mut self, bounds: Rect, text: &str, font: &Font,
 color: Color, alignment: HorizontalAlignment,
) -> crate::compat::String
```

- **传矩形而不是最大宽度**：每个调用点手里**本来就有**控件的（或单元格的）矩形，
 传 `bounds` 使「忘记设边界」在签名层面就不可能；
- 放得下则原样绘制，放不下则以 `…` 截断；
- 定位（左/中/右）基于**矩形**，所以居中标签截断后不会漂移；
- 返回**实际绘制的字符串**，调用方据此排布后续元素（`tag_input` 的光标、
 `code_editor` 的左标签、`font_preview` 的样例沿用此机制）。

**连带修掉的 3 个同源问题**（冰山法则）：

| 控件 | 问题 | 说明 |
|---|---|---|
| `tag_input` | 光标位置 `input_buffer.len() * 7` | `len()` 数字节（CJK 标签偏移 4 倍），且 7 ≠ 真实步进；改为按**实际绘制文本**度量，并钳在输入框内 |
| `hero_animation` | 用**一次** `draw_text` 画**两行**字符串（含 `\n`） | 渲染器一次只画**一行**；`\n` 被当成缺字，且起点按**两行合计宽度**算出（故为负）。改为逐行绘制 |
| `code_editor` | 左标签与右侧行列号**各自**从两边定位，中间无约束 | 改为**同一状态带**内两侧排布、各自截断 |

### 4.7 判断取舍：`line` 的 2 px 描边（指令 #5）

`Line` 在 120 px 高、2 px 厚的几何下，2 px 线**无论如何都要占满整高**，二者不可兼得：

| 方案 | 后果 | 选择 |
|---|---|---|
| A. 缩排弦的两端 | 线短 1 px，**但仍居中于矩形内** | ✅ **选此** |
| B. 抬升弦的位置 | 线**偏出矩形中线**，`Line` 的语义（居中分隔线）被破坏 | ❌ |

**理由**：`Line` 的契约是「在矩形中画一条居中的线」。牺牲 1 px 长度不改变契约，
移动中线会改变契约。

## 11. 一句话结论

**用户说「大部分都有问题」，是对的；而根因不是 188 个控件各错一次，是四条判据看不见的那个维度。**

坐标系混用（2）、估算与度量不一致（1）、`+ ascent` 误读（8）、
大元素的半宽算漏（6）、文本无宽度约束（~40）、硬编码浅色（1）。

**本轮最该记住的一条**：**判据的错和代码的错要一起修 —— 而且判据的错更容易伪装成「通过」。**

而反过来，若判据偏松（如第 58 轮「窗口建在 (0,0)」），它会安静地放过真缺陷。
**偏严与偏松是同一类错误，代价同样是不再有人相信门禁。**

### 12.1 `wizard_dialog`：4 个缺陷（逐条实测）

| # | 缺陷 | 取证 | 修法 |
|---|---|---|---|
| 1 | **导航按钮被布局了两次** | `draw` 按 72 px 列算出 `8 / 80 / 160`，`handle_event` 按固定 80 px 算出 `8 / 60 / 152` ⇒ **Back 偏移 20 px、Next 偏移 8 px**，两个按钮不在它们显示的位置响应 | 抽出 `nav_button_rects()`，绘制与命中判定**共用同一个**函数 |
| 2 | **标签贴在按钮上沿** | 文本原点 = 字形**左上角**，把按钮矩形直接传进去使 12 px 字形落在 36 px 按钮的 `78..90`（按钮中心是 96） | 用 `button.y + (height - line_box)/2` 居中 |
| 3 | **填充色读错 token** | 读 `theme.background_color`，而 `wizard_dialog` 归类为 `Surface` ⇒ 该 token **就是对话框自己的底色**，于是主按钮渲染成灰色 `139,139,139` | 改读 `theme.colors.primary`（动作色的正确来源，与 `fab` 同构） |
| 4 | **一个按钮看起来是两个控件** | 最后一步改用 `success` token，`Next`（primary）与 `Finish`（success）是两套调色板 | 两个状态共用同一个动作 token，只换标签 |

**修后实测**：`Finish` 填充 `100,181,246`（暗）/ `33,150,243`（亮）—— **随主题变化**，证明它读的是主题动作色。

> **回答用户的判断「是否他应该也是不受 theme 控制的？」**：**不是。**
> `wizard_dialog` 在两张豁免表里**都没有登记**，它的按钮是**外观色/动作色**（①类），
> **必须**随主题变化。它看起来「不受主题控制」的原因不是设计如此，而是**读错了 token** ——
> 这恰恰是必须修的缺陷。真正**不该**受主题控制的只有 **③ 数据色**
> （图表系列、K 线涨跌、色相环、地图瓦片、解码画面），它们**编码信息本身**，换成主题色会抹掉信息。

写了一个一次性探针（对每张快照判断「单行文本的字形盒是否越出它所标注的容器底边」），

|---|---|

| `badge` | `(pill - glyph)/2 + ascent` —— **多加了一个 `ascent`** |

### 12.3 🔴 我自己引入的回归，被 P5 抓住（重要）

修 `number_picker` 时，我把 `row_center - text_h/2` 作为原点，**但循环的边界判断仍在比较

## 13. 追加：第三轮（用户：「wizard 中间那个按钮没文字」）

### 13.1 用户看到的不是「没有文字」，是 **1.03:1 的对比度**

取证：`Back` 按钮的文字**确实被发出**了，但它的填充与文字几乎同色 ——

```
Back button fill : (139,139,139)
Back label fill : (137,137,137) ← 每通道仅差 2
对比度 : 1.03:1 ← 等于「没有文字」
```

用户说「没文字」是**准确的**：一个对比度 1.03:1 的标签，人眼看到的就是一块空白。

**根因**：同一个按钮的填充与文字用了**两套互不相干的变暗公式**：

```rust
back_color = button_fill.blend(&ink, 0.5); // → 139,139,139
label = ink.blend(&surface, 0.45); // → 137,137,137
```

两者各自都不算错，**但合起来必然撞车** —— 而「必然」是指没有任何一处代码在保证它们不撞车。

**修法（根因，非调色）**：禁用态改用**与启用态同一对函数** ——
填充由按钮基色推出，文字取**该填充自己的 `contrast_color()`**，再向表面压暗一档。
于是对比度**由构造保证**，而不是靠两个常数恰好凑开。同一个模式也应用到 `Next`/`Finish`。

**修后实测**：

| | 填充 | 文字 | 对比度 |
|---|---|---|---|
| 修前 | `139,139,139` | `137,137,137` | **1.03:1** |
| 修后（暗） | `40,40,40` | `176,176,176` | **6.80:1** |
| 修后（亮） | `214,214,214` | `79,79,79` | 同理可读 |

### 13.2 🔴 由该反馈挖出的一个**快照本身的缺陷**（比按钮更值得记）

为了自动找出「标签与自己的背景同色」，写了一次性对比度探针。第一版报 **21 个控件**，
逐个核对后发现**大部分是探针自己的错**（又一次「判据的错」）：

| 判据错误 | 现象 | 根因 |
|---|---|---|
| 取「**第一个**包含该标签的填充矩形」 | `label`/`panel`/`message_box` 等全报在白色上 | 画布底色矩形包含**所有**东西，必然命中 |
| 同面积时取第一个 | 仍报白色 | SVG **按文档顺序绘制**，同面积的**后者**才是实际背景 |

两条都修（取**最小**面积；同面积取**后者**）后降到 12 个 —— 而这时剩下的**才是真的**。

> **方法论教训（第二次出现）**：**判据偏严与偏松是同一类错误。**
> 探针第一版把 9 个正常控件报成缺陷，若照单全改，就会「修好」没坏的东西。

### 13.3 🔴 真正修掉的一个**快照工具缺陷**

探针降噪后，`label` / `action` 仍在报 —— 取证发现**不是控件的问题，是导出器的问题**：

```rust
// src/widget/svg.rs（修前）
backend.begin_frame(crate::core::Color::WHITE); // ← 永远白色
```

`Label` / `Separator` 等控件**按设计不画背景**（在真实窗口里，背后是父控件画的面）。
但导出器把**暗色主题的近白文字**画在**白底**上 ⇒
`label.svg`（暗）是一片空白，而 `label.light.svg`（亮）看着完全正常。

**同一控件、两张快照给出矛盾答案** —— 这与本计划的中心判断同源：
**两个后端/两种视角对同一事实给出不同答案，本身就是缺陷。**

**修法（根因）**：`render_widget_to_svg` 增加 `render_widget_to_svg_on(widget, geometry, backdrop)`，
导出器传入**活动主题的背景色**。透明控件于是落在它真实所处的面上：

```
label.svg 修前: 白底 + 近白文字 = 空白 修后: 18,18,18 底 + 225,225,225 文字 ✓
label.light.svg 修前: 白底 + 黑字 = 正常 修后: 240,240,240 底 + 黑字 ✓
```

### 13.4 顺带修掉的**真·主题盲**缺陷（探针降噪后暴露的）

| 控件 | 病处 | 修前 | 修后 |
|---|---|---|---|
| `chart` / `bar_chart` / `line_chart` | 坐标轴三色写死为**浅色图表的调色板** | 轴标签 `80,80,80` 在 `18,18,18` 面上 = **2.3:1**；网格线反而最亮 | 抽出 `axis_chrome()`，三色沿「表面→墨色」推导 |
| `pie_chart` | 切片标签写死 `DARK_GRAY` | **1.8:1** | 由活动表面推出（**切片色不动** —— 那是数据，规则 #108 ③） |
| `search_box` | 输入文字写死 `30,30,30` | **1.7:1** | 由主题 ink 推出，占位符再压暗 |
| `search_bar` | 文字写死 `40,40,40` **且** 多加了 `ascent` | **1.5:1** + 下移半行 | 由字段色推出 `contrast_color()`；居中改 `(h - line_box)/2` |

### 13.5 门禁对我这次修改的两次「反向拦截」（说明门禁在有用地工作）

1. **P5 抓到新回归**：修 `number_picker` 时守卫仍比较 `row_center`（字形盒的**代理**），
 导致上方行原点为负 ⇒ `number_picker: [115,-3..124,12] escapes the box`。

2. **P3 报出失效豁免**：`axis_chrome()` 修好后，`line_chart` 的主色变成主题轴色 ⇒
 它那条 `series-palette` 豁免**已不再豁免任何东西**，门禁主动报出并要求删除。
 已删除并在文件里补「Removed on evidence」说明（与 `mini_chart`/`meter`/`map_view` 同例）。

### 13.6 如实记录的**未完成项**

对比度探针降噪后仍剩若干「<3:1」项，经逐条核对后**未在本轮修改**，理由如下：

| 控件 | 对比度 | 判断 |
|---|---|---|
| `code_editor` 语法着色 | `1.25:1`（`43,55,74` 于 `69,69,69`） | **真缺陷，但是设计决定**：`SyntaxPalette::default()` 是**整套浅色配色**（背景 `252,253,255`、栏底 `246,248,252`…），而编辑器本体底色来自主题。给整套调色板加一套暗色变体是**新功能**，不是本轮的外形修正 —— 已如实记录，未半途改 |
| `cupertino_date_picker` | `1.55:1` | 滚轮选中行文字压在**强调色带**上，需重新设计选中态配色 |
| `calendar` 星期表头 / `tag_input` / `emoji_picker` / `image_gallery` 占位符 | `2.3–2.9:1` | **占位符/次级文字按设计就该比正文淡**；2.3:1 可辨。提高它们会削弱「这是提示而非值」的语义，故**不改** |
| `pie_chart` 白字压黄切片 | `1.85:1` | 切片色是**调用方给的数据**，文字色都应对该切片色取 `contrast_color()`；属后续项 |

> **为什么停下来**：这三类是「改调色板设计」而非「修错误」，且规则 #108 明确要求
> **不得笼统地把数据色主题化**。混在一起改会让本轮的验证失去意义。
