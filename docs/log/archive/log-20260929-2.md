### 2.1 取证：那一行**自认的**未闭环

`src/widget/icon_fallback_data.rs` 的**自己**的文件头写着（L6–L15，逐字）：

```text
there is no generator for this table: `tools/gen_icon_data.py` writes `icon_data.rs` and
nothing else, so an earlier header that named it as this file's producer was wrong. The
flattening is mechanical (parse the `d`, walk the contours) and is applied by hand when a
```

这是一个**已被记录、但从未闭环**的欠账。它的代价是可量化的：

- 该表是 69 个图标 × 最多 246 个顶点的手抄多边形（实测见 §2.3）；
- 它的**唯一**作用是「不带 `icons` feature 的构建」里的图标几何；

  也就是说，**同一份数据被两条路径读取，其中一条是手工转录**（原则 #101 的形态）。

### 2.2 探针：先证明「能生成」，再动手（原则 #1、#51）

新增 `examples/probe_icon_roundtrip.rs`：对每个图标取它的 **真** `IconData`（经公开的
`IconName::data()`，不用 crate 私有表），用 `flatten_paths` 展平，**再把自己展平出来的折线
重新编码成 SVG `d`、重新过同一条解析链**，逐顶点比对。

```text
$ cargo run --example probe_icon_roundtrip --no-default-features --features "desktop,icons"
icons=69 worst_points=244 (calendar, budget 1024) roundtrip_mismatch=0 vertex_moved=0 max_delta=0
```

**结论**：

1. 最坏情形 **244 个顶点**（`calendar`），远在 `MAX_OUTLINE_POINTS = 1024` 的预算之内；
2. 展平后的折线经 `d` 往返 **逐顶点精确相等**（0 位移），所以「由数据生成fallback」可以做到
   **与渲染路径同源**，不是近似。

### 2.3 🔴 过程中的**两个真缺陷**（本轮的实收获，如实记录）

探针一开始报 `roundtrip_mismatch=4 vertex_moved=69 max_delta=880`。逐个排除后，落到两个**库缺陷**
（不是探针问题）：

#### 缺陷 A：`IconPlacement::map` 把 y 平移**写死成常数 960**

```text
src/render/path/flatten.rs:90（修前）
    Pt::new(self.origin_x + x * self.scale, self.origin_y + (y + GRID_TOP) * self.scale)
                                        ^^^^^^^^^^^^^ GRID_TOP 是 const 960.0
```

网格的 `viewBox` 是 `0 -960 960 960`，设计 y ∈ [-grid, 0]（**负向上**），框顶 = -grid、框底 = 0。
把设计原点（y=0）平移到框底，正确的式子是 **`device_y = origin_y + (design_y + grid) * scale`**。

**所以平移本身是对的，错的是那个 `grid`。** 它被写成了常数 `960`，而它必须是**调用方的 grid**：

| 调用方 | 期望的平移 | 修前得到 |
|---|---|---|
| bundled 图标（grid = 960） | +960 | +960 ✓ **看不见** |
| `register_icon_on_grid(.., 24)`（grid = 24） | +24 | +960 → **偏下 936 单位 = 40 个框高** 🔴 |

`register_icon_on_grid(.., 24)` 是**明文文档化**的支持路径（模块文档点名 Lucide / Tabler / Feather 的
24 单位 viewBox），而它会把图标画到离请求矩形 40 个框高的地方——一个**完全不可用**的缺陷。

**为什么此前无人发现**：仓内所有 bundled 图标的 grid 都是 960，而唯一的**非 960 使用形式**
（`register_icon_on_grid`）**没有任何测试**。即：缺陷藏在「参数化声明了、但门控从未走过」的那一格。

**修法**：把 `grid` 做成 `IconPlacement` 的字段，平移用它（而不是常数），并删掉 `GRID_TOP`：

```text
src/render/path/flatten.rs（修后）
pub struct IconPlacement {
    pub origin_x: f32,
    pub origin_y: f32,
    pub scale: f32,
    /// The design grid this placement maps from, so the y translation can use it.
    pub grid: f32,
}

    fn map(&self, x: f32, y: f32) -> Pt {
        Pt::new(self.origin_x + x * self.scale, self.origin_y + (y + self.grid) * self.scale)
    }
```

模块文档里那条公式也改正（它把 `y_max` 当作 0 讲得含糊，而现在 `grid` 是变量）：

```text
修前： device_y = origin_y + (y_max + design_y) * scale     // y_max = 0, so (-960..0] -> [0..960)
修后： device_y = origin_y + (design_y + grid) * scale      // design y is negative-up: -grid is the top
```

> **我自己的误判（记录以免重犯）**：我先把这条公式写成了 `device_y = origin_y - design_y * scale`，
> 并在日志初稿里把它描述为「180 度旋转」。那是**错的**：`-y` 会把 grid 的顶部映射到框底，
> 才是真的 180 度旋转。已有的 `a_square_outline_flattens_to_four_corners` 把我这个误判当场抓了出来
> （它断言 `M0-960` → 设备 `(0, 0)`，即**顶部→顶部**，与 `+grid` 一致）。教训：改坐标约定前，
> 先去读**已有的、已通过的**断言，它们往往就是那份约定的取证。

#### 缺陷 B：`flatten_paths` 输出的折线**重复了闭合顶点**

#### 缺陷 B：`flatten_paths` 输出的折线**重复了闭合顶点**

同一次探针里量到：一个 4 个角的方框，展平后给的是 **5 个顶点**（首尾重复）。收尾沿本来就是
fill 隐式闭合的那条边，再带一个重复首点是冗余；对「把这条折线**再编码出去**」的消费者
（census、fallback 生成器）会造成数据漂移。

**修法**：在「顶点数 < 3 丢弃」之前，丢掉**恰好等于首点**的末尾顶点（只有精确相等才丢，
因为 `M0 0L10 0L0 0` 是一条真实的退化轮廓）：

```text
src/render/path/flatten.rs（新增）
    if cursor > start_index && points[cursor - 1] == points[start_index] {
        cursor -= 1;
    }
```

**验证**：`M0 0L10 0L10 10L0 10L0 0Z`（5 个顶点）⇒ `count=1 used=4`。

### 2.4 🔴 我自己犯的错（记录以免重犯 —— 原则 #19）

探针**最初报的 4 条 mismatch 与 `max_delta=880` 里有很大一部分是我探针自己的 bug**，
在把它当成库缺陷之前必须先排除。三个错误：

1. **拿设计坐标比设备坐标**：`IconPlacement(0,0,960,960)` 下 `(x, y)` 设备点对应设计点
   `(x, -y)`？——**不，这条本身是我写错的**（见错误 3）。当时我按 `(x, -y)` 比，
   `max_delta` 从 880 掉到 40，所以我以为对了。
2. **把「轮廓表」当成「连续切片」**：`flatten_paths` **丢弃**顶点数 < 3 的退化轮廓，但**不回收**
   它们的顶点，所以后一条轮廓的 `(start, end)` 与上一条之间**可能有空洞**。我却用
   `contours.last().end` 当总点数，并按**平坦下标**逐点比两条链的顶点——于是比较的是
   `[0..10)` vs `[0..8)`，报出「每条轮廓都丢了 2 个点」。改为**逐轮廓**比较后，
   真相立刻显示出来：**两条链的轮廓集合完全相同**。
3. **把 y 约定想反了**：我认定 `device_y` 应当**取负**（因为设计 y 是“负向上”），
   并据此把 `map` 改成了 `origin_y - y * scale`。**这是错的**：`-y` 才是真的把图上下颠倒，
   而正确的平移就是 `+grid`。抓出这个错误的是**仓库里原本就绿的那条**
   `a_square_outline_flattens_to_four_corners`（它断言 `M0-960` → 设备 `(0,0)`，即顶→顶）。

**教训**（写给下一个用这个探针的人）：

- 当探针报「差异」时，**先证明差异不是探针造出来的**。本例里 90% 的数字是探针的，
  只有「grid 被写死」和「重复闭合点」是库的。
- **改坐标约定前，先去读已有的、已通过的断言**。它们往往就是那份约定的取证；
  我把一个错约定写进代码和日志，是一条已有断言（而不是我的推理）把我拉回来的。
- **本节的探针文件已在收尾时删除**（`examples/probe_*.rs`）：它们是取证工具，不是交付物；
  保留会变成又一份无人维护的“生成物”。可复跑的等价验证已落到单测（§2.8）。

### 2.6 交付：`tools/gen_icon_fallback.py`

新增生成器，与 `gen_icon_data.py` **同源**（同一个 `read_vendor`、同一个 `PATH_RE`、同一份
`tools/material_symbols/<token>.svg`），并保留三项与 `gen_icon_data.py` 对位的不变量：

| 不变量 | 强制方式 |
|---|---|
| 每个 token 都有几何 | 无 vendor 文件即拒绝 |
| 无两个 token 同图（`Close == Cross` 类） | 每 token 的顶点表取 sha256，碰撞即拒绝 |
| 顶点落在设计网格内 | 注释记录坐标约定，由 `flatten.rs` 的唯一映射消费 |

输出形态：**多边形**而非 `d`——因为 fallback 存在的**理由**就是「不带 `icons` 的构建不链接 SVG 解析器」；
输出 `d` 会把解析器又拉回来，反而破坏这个切分。曲线以固定深度 `SUBDIVIDE_DEPTH = 4` 采样。

```text

$ python3 tools/gen_icon_fallback.py --check

```

**该生成器的 `--check` 被证明会红**（原则 #494 要求的反向注入）：改一个坐标单位（`382 → 383`）即报
`FAIL … is stale`；恢复后重新绿。

### 2.8 回归测试：把 grid 常数缺陷钉住

缺陷 A 在原测试套里**无任何测试能抓**（39 个图标测试全绿）。新增
`icon.rs::tests::a_non_960_grid_is_placed_inside_its_box`，在 **`IconPlacement` 层**断言：

```text
一个 24 单位网格、24 px 画在 (10, 20) 的三角，每个顶点必须落在 x 10..34 / y 20..44 内；
尖点（设计 y = -24，即网格顶行）必须是设备 y 最小者，且恰在框顶 y = 20。
```

**为什么把测试放在 placement 层而不是渲染层**：`IconPlacement::new(x, y, size, grid)` 就是 grid 流进
映射的地方，而 `map` 是受测对象。走渲染层需要先注册一个非 960 的图标，会把两个无关的设置塞进
一条测试；而只走 bundled 图标则**碰不到缺陷**（那里 grid 恰好就是 960）。

**反向注入**（把 `map` 换回写死常数 `960`）：

```text
---- a_non_960_grid_is_placed_inside_its_box stdout ----
panicked at src/widget/display_widgets/icon.rs:1085:
a 24-grid icon must land inside its box, but a vertex is at Point { x: 10, y: 971 }
```

即：一个要画在 (10, 20)、高 24 的图标，顶点落到了 **y = 971**（偏下 40 个框高）。恢复修复后绿。

**同时，本轮还借助一个已有断言自我纠正了一次误判**（见 §2.3.1 的评注）：
`a_square_outline_flattens_to_four_corners`（原本就在且原本就绿）断定了正确的 y 约定，
所以“应当翻转 y 轴”那个想法被当场否掉——行内注释里已记录这一点。

### 3.2 根因：`widget_at` **完全跳过**了根节点的边界检查

```rust
// src/widget/runtime.rs（修前）
if current != root && !widget_accepts_point(current, point) {
    return None;
}
```

这个 `current != root` 是**有意**的，注释也交代了理由（窗口几何持有的是向 OS 申请的 `x`/`y`，
而子控件写在客户端坐标里；两者不同空间，拿窗口矩形测客户端点会在**每一次点击**上失败，
`demo/control` 的窗口建在 `(100,100)` 而点击落在客户端 `(95,36)`）。

但它把两个不同的命题混成了一个：

- 「用窗口矩形测客户端点」是错的；
- 「根本不测根节点」也是错的。

后果：一个**远在窗口之外**的点穿过子控件搜索、**把根当成最深的命中返回**——
正是函数文档里写明该返回 `None` 的那个输入（`Returns None for ... a point outside it`）。

### 3.3 修法（两个空间只差一个原点，所以把边界改成**相对该原点**）

```rust
// src/widget/runtime.rs（修后）
pub fn widget_at(root: ObjectId, point: Point) -> Option<ObjectId> {
    let origin = with_widget(root, |widget| widget.geometry())?;
    let local = Point::new(point.x - origin.x, point.y - origin.y);
    let root_rect = Rect::new(0, 0, origin.width, origin.height);
    let mut current = root;
    loop {
        let children = with_widget(current, |widget| widget.children().to_vec())?;
        if current == root {
            if !root_rect.contains_point(local) {
                return None;
            }
        } else if !widget_accepts_point(current, point) {
            return None;
        }
        …
```

**为什么这是根因修复而不是绕过**：窗口空间与客户端空间**只差根自身的原点**，所以
`point - origin` 就是客户端点。当根是客户端容器（`origin == (0, 0)`——布局引擎建出的树与下面所有
测试都是这种）时，它**就是**普通的包含判定；当根是窗口时，它是「客户端坐标下的包含」，正是
`point` 被文档规定的空间。两个命题因此分开了：仍然不拿**窗口矩形**测客户端点，但仍在**客户端空间**里
给根一个边界。

### 6.2 🔴 缺陷：`idle_ticks > 30 * 60 * 2` 与其注释**互相矛盾**

```rust
// demo/code_editor/src/app.rs（修前）
            } else {
                idle_ticks += 1;
                // 事件循环空转超过 30 秒无任何事件也退出，避免无法关闭的孤儿进程。
                if idle_ticks > 30 * 60 * 2 {
                    poll_log.append("[App] 长时间无事件，自动退出");
                    break;
                }
            }
            std::thread::sleep(std::time::Duration::from_millis(16));
```

**实测算术**（不是推测）：

```text
old: 30 * 60 * 2 = 3600 tick × 16 ms = 57.6 秒   ← 注释声称 30 秒
```

即那个表达式**从来不代表任何真实时长**：`30 * 60` 是「分钟数 × 60」的中间量，
又乘了 2，得到 3600；按 16 ms 一 tick 算恰好是 57.6 秒。这是一个把**tick 数**
当**秒数**写的经典错误，且因为无测试能观察它（要等 57.6 秒）而长期存在。

### 6.3 修法：把「多长时间」与「多少 tick」分成两个事实

```rust
/// 事件泵的轮询间隔。
///
/// 约 60 Hz：快得人眼看不到延迟，又慢得不会把一个核心跑满。菜单与控件触发都是**队列**
/// （`poll_menu_triggered` / `poll_widget_trigger_event`），所以这个间隔只影响**延迟**，
/// 不影响**是否丢失**事件。
const POLL_INTERVAL: std::time::Duration = std::time::Duration::from_millis(16);

/// 一次事件都没有的连续空闲超过这个时长，事件泵就自动退出。
///
/// # 为什么需要一个上限，而不是一直等
///
/// 主线程跑的是平台循环（`App::run`），它只在窗口关闭时返回。若宿主关窗的事件没有到达
/// 本进程，平台循环会一直不返回，而本泵线程就会**永久空转**，留下一个关不掉的孤儿进程。
/// 这个上限是那条路径的兜底。
///
/// # 它必须由 `POLL_INTERVAL` 算出来，不能写成拍脑袋的 tick 数
///
/// 这里原本写的是 `idle_ticks > 30 * 60 * 2`，注释却写着「超过 30 秒」。按 16 ms 一 tick
/// 算，`30 * 60 * 2 = 3600` tick 实际是 **57.6 秒**；而 `30 * 60` 也不是秒数，
/// 是「分钟数 × 60」这个中间量——即那个表达式**从来不代表任何真实时长**。
/// 现在把两个常数分开：上限说「多长时间」，`ticks()` 把它换算成 tick，二者不会漂移。
const IDLE_EXIT_AFTER: std::time::Duration = std::time::Duration::from_secs(30);

/// [`IDLE_EXIT_AFTER`] 换算成多少个 `POLL_INTERVAL` tick。
fn idle_ticks_before_exit() -> u32 {
    // 向上取整，并保证至少 1：一个比轮询间隔还短的上限会立刻退出，那不是「空闲太久」。
    let interval = POLL_INTERVAL.as_millis().max(1) as u64;
    let ticks = (IDLE_EXIT_AFTER.as_millis() as u64).div_ceil(interval);
    ticks.clamp(1, u64::from(u32::MAX)) as u32
}
```

调用点也一并改（并在日志里带上**真实时长**，而不是一个形容词）：

```rust
                if idle_ticks > idle_ticks_before_exit() {
                    poll_log.append(format!(
                        "[App] 空闲超过 {:?} 无事件，自动退出",
                        IDLE_EXIT_AFTER
                    ));
                    break;
                }
```

**为什么这是根因修复**：把「时长」与「换算」分成两个**各自可读**的事实后，
以后改 `POLL_INTERVAL` 不会静默改变退出时长，改退出时长也不会影响轮询节奏。

### 8.4 🔴🔴 `check_no_write_only_fields.sh` —— **门禁本身有两个真缺陷**

这一条不是「缺记录」，是「这个门禁**在我注入的每一种缺陷上都报绿**」。逐个追下去，
它有两个独立的缺陷：

#### 缺陷 C：**根本不统计 struct literal 写入**

```python
ANY_ACCESS  = re.compile(r"\.([a-z_][a-z0-9_]*)\b")        # 只认 `.field`
MUTATOR     = re.compile(r"\s*(=[^=]|\.(?:push|...))")
```

判据是「某个字段 `writes > 0 && reads == 0`」，而 `writes` **只从 `.field` 后缀计数**。
一个字段最常见的**首次写入**形式是 struct literal：`Self { field: 0 }` / `WidgetStyle { field: .. }`——
它写的是 `field: 0`，没有任何 `.field`，所以 `writes == 0`，字段直接**被跳过**。

**实测**（把探针字段真的声明 + 真的写 + 从不读）：

```text
$ （在 ProgressBar 上声明 probe_write_only_field 并在 Self{..} 里赋值 0）
$ python3 tools/check_no_write_only_fields.py
  [1/1] no write-only fields in widget/style/layout (2 allow-listed)
✅ every field is either read or explicitly exempt      ← 真缺陷报绿
```

**修法**：加一个 struct-literal 初始化器的模式，把它计为**写入**；
并用一个 shorthand 模式（`Self { field }`）计为**读取**（那种形式既写又从外层作用域取值，
本身不可能造就一个写而不读的字段）：

```python
# A struct-literal initializer: `field: value` inside a `Braces` expression. …
INIT_FIELD = re.compile(r"\b([a-z_][a-z0-9_]*)\s*:\s*[^:=]")
# A shorthand initializer: `Self { field }` … recorded as a read.
INIT_SHORTHAND = re.compile(r"(?<![.\w])([a-z_][a-z0-9_]*)\s*[,}]")
```

#### 缺陷 D：**读侧只看三个目录，写侧看全库（不对称）**

即使只修 C，它立刻报出 8 条，其中 2 条是**假阳性**：

```text
src/style/gradient.rs: `end_point` is written but never read (principle #99)
src/style/gradient.rs: `start_point` is written but never read (principle #99)
```

而它们**真的被读**：

```text
src/render/svg/backend.rs:1077-1080
    gradient.start_point.x, gradient.start_point.y,
    gradient.end_point.x, gradient.end_point.y
```

根因：`src/render/` **不在扫描目录里**（只扫 `src/widget` / `src/style` / `src/layout`），
所以一个在 `src/style/` 声明、由 `src/render/` 消费的字段被当成无人读。
而 `.field` 的**写**计数又不是按文件限定字段来源的——不对称。

## 10. 第十轮：字体 —— 派生构造函数**丢掉**文本缩放字段（用户第 8 条）

### 10.1 取证：一个在实时路径上的真缺陷

`src/core/font.rs` 里 7 个「从字体派生出字体」的构造函数共享一个形状：

```rust
// 修前

    Self::with_weight(&self.family, size, self.weight, self.italic)   // ← 重建！
}
pub fn scaled(&self, scale: f32) -> Self {
    Self::with_weight(&self.family, self.size * scale, self.weight, self.italic)
}
… with_weight_value / with_bold / with_italic / with_family / scaled_down 同样
```

而 `Font::with_weight` 是**从头构造**：它的字段初始化里 `letter_spacing: 0.0, word_spacing: 0.0,
line_height: 0.0`。所以**每一个**派生构造函数都会把这三个字段清空。

**这不是理论缺陷，它在一条实时路径上**：

```text

    font: Some(
        theme.fonts.body.clone()
            .scaled(crate::style::environment::environment().effective_text_scale()),
    ),
```

主题解析**每次**都要按「文字缩放」派生一遍 body 字体。于是：一个为阅读节奏把 body 配成
`line_height(21.0)`（14 px 的 1.5 em）的主题，在宿主开启文字缩放的那一刻**把行高丢回 1.0 em**。
1.5 em 与 1.0 em 在行距上是整整半行的差，而那正是无障碍文字缩放最常见的场景。

**为什么无测试能抓**：已有的三条字体测试分别验证「默认字段无副作用」「builder 与 setter 的钳制一致」
「word_spacing 过 serde 往返」——**没有一条检派生构造函数保留字段**。

### 10.3 修法：给派生一条**不会丢字段**的单一路径

```rust
    pub fn with_size(&self, size: f32) -> Self {
        self.derived(size, self.weight, self.italic)
    }
    pub fn with_weight_value(&self, weight: u16) -> Self {
        self.derived(self.size, weight, self.italic)
    }
    pub fn with_bold(&self, bold: bool) -> Self {
        let weight = if bold { Self::BOLD_WEIGHT } else { Self::REGULAR_WEIGHT };
        self.derived(self.size, weight, self.italic)
    }
    pub fn with_italic(&self, italic: bool) -> Self {
        self.derived(self.size, self.weight, italic)
    }
    pub fn with_family(&self, family: impl Into<String>) -> Self {
        self.derived(self.size, self.weight, self.italic).with_family_name(family)
    }
    pub fn scaled(&self, scale: f32) -> Self {
        if !scale.is_finite() || scale <= 0.0 { return self.clone(); }
        self.with_size(self.size * scale)
    }
    pub fn scaled_down(&self, scale: f32) -> Self {
        if !scale.is_finite() || scale <= 0.0 { return self.clone(); }
        self.with_size(self.size / scale)
    }

    /// Rebuilds this font at `weight`/`italic`, **preserving the text-scaling fields**.
    fn derived(&self, size: f32, weight: u16, italic: bool) -> Self {
        let mut derived = Font::with_weight(&self.family, size, weight, italic);
        derived.letter_spacing = self.letter_spacing;
        derived.word_spacing = self.word_spacing;
        derived.line_height = self.line_height;
        derived
    }
```

**两个关键设计决定**（都写进了注释）：

1. **不修改公共的 `Font::with_weight`**。它是「从一个 family 名新建一个字体」的构造函数，
   **没有前值可保留**；把保留逻辑塞进去会改变它的语义。所以新增一个**私有的**派生漏斗。
   （第一版我给这个私有函数也取名 `with_weight`，导致 `E0592`/`E0599`——
   它与公共关联函数重名，`self.with_weight(...)` 解析不到方法。已改名为 `derived`。）
2. **`scaled` / `scaled_down` 改成转发到 `with_size`**，而不是各自重建。
   这样“缩放”与“改尺寸”是**同一个**行为，只剩一个几何实现。

## 11. 第十一轮：事件 —— `AnimationFrameRequest` 的**承诺能力不存在**（用户第 8 条）

### 11.1 取证：一个只写不读的 `id` + 一个不存在的 API

而全仓对 `AnimationFrameRequest` 与 `id` 的引用只有：

**两件事同时不成立**：

2. 文档承诺的 **cancel 入口全仓不存在**——它不是「没测」，是**根本不存在**。

（「名字合法」不等于「那件事存在」）。

### 11.2 修法：把「可取消」做成类型事实 + 一条真正在跑的路径

**存储**（新增字段，共享给循环线程）：

```rust
    /// Ids of `request_animation_frame` requests that have been cancelled.
    ///
    /// Cancellation is checked at **dispatch** time rather than by removing the event from the
    /// queue: the queue is a lock-protected priority structure shared with the loop thread, and
    /// a removal would have to race the `dequeue_blocking` that already holds the mutex.
    cancelled_anim_frames: Arc<Mutex<Vec<u64>>>,
```

**公共 API**（新增，不改签名）：

```rust
    pub fn cancel_animation_frame(&mut self, request: AnimationFrameRequest) -> bool {
        let mut cancelled = lock(&self.cancelled_anim_frames);
        if cancelled.contains(&request.id) {
            return false;
        }
        cancelled.push(request.id);
        true
    }
```

返回值的语义写进了文档：`true` = **本次调用是那次取消**；重复取消同一个请求返回 `false`
（状态没变就不该报“变了”）；已派发完的请求也返回 `false`。

**编解码只在一处**（新增 free fn，使生产者与取消检查不可能对布局有分歧）：

```rust
/// The request id carried by an animation-frame event, or `None` for any other event.
fn animation_frame_id(event: &Event) -> Option<u64> {
    let Event::Custom { name, payload } = event else { return None };
    if name != ANIMATION_FRAME_EVENT_NAME { return None; }
    let bytes: [u8; 8] = payload.as_slice().try_into().ok()?;
    Some(u64::from_le_bytes(bytes))
}
```

**接线**：在循环的两个派发阶段（Normal 与 Idle，因为帧事件可能以任一优先级入队）
各插一道检查，命中则 **`continue`（不派发）**：

```rust
if animation_frame_id(event).is_some_and(|id| take_cancelled(&cancelled_anim_frames, id)) {
    continue;
}
```

`take_cancelled` **消费**掉条目（`swap_remove`）——id 永不复用，留着只会让集合单调增长。

### 11.3 测试：断言在**行为**上，不在返回值上

新增 `test_cancelled_animation_frame_never_dispatches`，在**同一个循环里放两个请求**：

```rust

… el.start() / sleep / el.stop() …

```

**为什么必须有第二个请求**：否则「全都不派发」（比如循环根本没跑）也会让测试绿。
这条把「取消生效」与「循环停止工作」两个原因区分开——是「测试不能为错误的原因通过」的具体落实。

### 11.5 诚实的边界

- 取消集合用 `Vec<u64>` 线性查找。取消次数是「每个请求最多一次」的 UI 量级，
  而 `request_animation_frame` 的派发频率是每帧一次——用 map 会让一个微秒级的路径多一层哈希，
  不符合原则 #28。这一选择写进了字段注释。
- `cancel_animation_frame` 取 `&mut self`（与 `request_animation_frame` 的 `&self` 不同）。
  这是**有意**的：`&mut self` 使「取消与另一个取消/修改循环的调用」不能在编译期重叠，
  而 `&self` 会迫使我在内部靠 `Mutex` 携带全部同步责任。代价是取消需要在能拿到 `&mut` 的地方调用，
  而这正是请求方（拥有循环的那一层）的位置。

## 14. 修掉的真缺陷（15 条，每条都有判据）

### 14.1 控件层

**缺陷 1 —— `QRCode` 的三个定位图案只在左上角是图案（原则 #5：不完整实现）**

`src/widget/misc_widgets/qr_code.rs:143`。`in_finder` 判定**正确地**覆盖了三个角，但紧接着的形状判定用**左上角局部**的 `row`/`col`：

```rust
let is_outer = row == 0 || row == 6 || col == 0 || col == 6;   // 只对左上角成立
let is_inner = (2..=4).contains(&row) && (2..=4).contains(&col);
```

右上（`col` 14–20）与左下（`row` 14–20）既不满足 `col==0/6` 也不满足 `(2..=4)`，于是整块被画成数据噪声。实测：左上 33 个黑模块，右上 14，左下 14。

修法：加 `finder_corner(row, col) -> Option<(base_row, base_col, flip_row, flip_col)>`，形状判定改为**镜像后的角局部坐标**（镜像而非平移，才是真 QR 的几何——图案是对称的）。同时把 `_is_sep` 这个**算了就丢**的变量变成真的分隔符（第 8 行/列涂白，且**不推进**数据位流）。

判据：`all_three_finder_patterns_are_identical` + `finder_patterns_are_ringed_by_a_light_separator`（新增两条，前者断言三角互为镜像**且**等于规范 7×7 环+3×3 心）。

**缺陷 2 —— `Tooltip::preferred_size` 用 UTF-8 **字节数**当字符数**

`src/widget/dialog/tooltip.rs:298`：`(self.text.len() as f32 * char_width)`。`len()` 是字节数，ASCII 下恰好相等，CJK 下一个字符 3 字节 ⇒ 估宽 3 倍。实工具提示走 `context.measure_text`，两者不一致。

修法：改 `chars().filter(|c| !c.is_control()).count()`，并把文档从「measures the text」改成「estimates from the character count」，因为 `size_hint` 拿不到 render context。判据：`tooltip_preferred_size_counts_characters_not_bytes`（4 汉字 vs 4 ASCII 必须等宽，并断言 `"你好世界".len() == 12` 以钉住「曾差 3 倍」）。

**缺陷 3 —— `Icon::size_hint` 无视自己的 `size`（只写不读的另一种形态）**

`src/widget/display_widgets/icon.rs:545`：恒定 `Size::new(24, 24)`。`set_size` 是文档化的、会 `request_redraw` 的属性，但唯一消费它的路径（布局问 `size_hint`）永远听到 24。

修法：返回 `self.size.round().max(1.0) as u32` 的方盒。判据：icon 测试组 41 条全绿。

### 14.2 布局层

**缺陷 4 —— `WrapAlignment::SpaceAround` 是第二个 `SpaceBetween`（原则 #13+#18）**

`src/layout/wrap.rs:186`（横向）与 `:275`（纵向）：起手恒为 `content.x`，从不留前导半格，于是「around」名不副实。**顺带发现第二个真缺陷**：旧的 `spacing` 只按 `leftover / n` 分配，**没有把已配置的 `spacing` 算进 `used`**，而换行决策算了 ⇒ `SpaceAround` 的多项行会**溢出右边界**。

修法：抽出 `spacing_for(alignment, available, sizes_sum, count, base_gap) -> Spacing { gap }`——两个对齐都从「先扣掉每对之间的基础间距」出发，`SpaceAround` 的前导格由**实际绘制的 slack**（含截断后的 gap）对半开得到，所以整数截断不会把行推偏。判据三条：`space_around_leaves_a_half_gap_at_each_end`、`spacing_alignments_never_overflow_the_line`、`space_around_is_symmetric_in_the_vertical_direction`、`a_single_item_line_is_only_centred_not_pushed`。

**缺陷 5 —— `FlowAlignment::Center/End` 用**整棵树**的总宽平移每一行（换行时整块跑出容器）**

`src/layout/flow.rs:229`：`total_width` 对**全部**子项求和，然后把同一个 offset 加到每一个子项上。不换行时恰好正确（只有一行），一旦换行就错：`End` 下 `offset_x` 可强负，早行被推出左边界。

修法（`apply_alignment` 重写为**逐行**）：按 `major 轴回到 content 原点` 把 items 切回各行，每行独立算 `sizes`/`gap`/`slack`/`start_offset`；次轴保持原语义（每项按剩余量偏移）以保证**单行布局与旧行为逐字节一致**（`a_single_line_still_uses_the_whole_set_alignment` 钉住）。判据：`wrapped_rows_are_aligned_per_line_not_against_the_whole_set`。

**缺陷 6 —— `SplitterLayout::add_widget` 与 `add_pane` 复制粘贴（原则 #101）**

`src/layout/splitter.rs:127`。两处把同样的两个值 push 进同样的两个向量，正确性依赖两份保持同步（而模块自己的回归测试正是钉这个）。修法：`add_widget` 直接调 `add_pane`，`remove_widget` 调 `remove_pane`——**一个 body**。

**缺陷 7 —— `KeyboardAwareLayout::animation_duration` 只写不读（原则 #99）**

`src/layout/keyboard_aware.rs:22`。字段有 getter/setter、进了 `Debug`、有自己的测试，但**没有任何绘制路径读它**：偏移是一次性施加的，文档承诺的动画不存在。

修法：**实现它**（而不是删掉——键盘让位动画是移动端真实需求）。加 `current_offset`/`elapsed_ms`、`tick(delta_ms) -> bool`（沿用本仓 `tick` 契约）、`is_animating()`；`EaseInOut` 插值；`set_keyboard_offset` 从**当前位置**出发（中断的收起可平滑反向，不回跳）；`set_animation_duration(0)` 立即收敛；`update`/`update_with_context` 读 `current_offset`。**`new(inner, 0)` 保持旧的瞬时行为**，所以既有调用方语义不变。判据五条（滑动/反向/关动画/同值不重启/旧行为），14 条全绿。

**缺陷 8 —— `AbsolutePosition::to_rect` 的 `parent_size` 恒被忽略，「锚点」名不副实（原则 #18）**

`src/layout/absolute.rs:68`。参数 `_parent_size` 未用，文档也承认，但 `TopRight`/`BottomRight` 这些名字读起来就是「贴父右/下边」。

修法：**不改既有拼写**（快照与调用方依赖它），而是① 把文档写清「锚点相对子项自身」，② 新增 `to_rect_in_parent(parent_size, child_size)` 提供真正的父相对锚定，③ 给 `Anchor` 加 `horizontal()`/`vertical()` 轴分解（九变体是两轴的积，避免九条 match 各写一遍）。判据：`anchored_in_parent_pins_to_the_parents_edges`（同时断言新旧两种拼写**确实不同**）、`every_anchor_decomposes_onto_its_axes`。

**缺陷 9 —— `FormLayout::remove_row` 对从未放入的 `items` 做 retain**

`src/layout/form.rs:63`。`rows`（label/field 对）与 `items`（独立项）是**两个互不相交的存储**，所以 `items.retain(|(id,_)| id != label && id != field)` 永远摘不掉刚删的行，只会**额外**误删一个 id 恰好相同的独立项。修法：删掉该语句，并在文档里写清两个存储的职责与「独立项要走 `remove_widget`」。

### 14.3 事件层

**缺陷 10 —— `Event::Resize` 已发布、有构造器、有消费者，却**没有生产者**（原则 #97）**

`src/event/types.rs:255`。全仓 producer 只有 `badge` 的测试与 `code_editor` 的一个 match 臂；真正的用户 resize 走 `WidgetTriggerKind::Resized`，那条路**只重跑布局，从不投递事件**。所以 code editor 那句「重算可见行」永远不执行。

修法：在 `handle.rs` 的 `Resized` 分支里，**布局重跑之后**再投递（顺序很重要：处理者要读到新几何）。新增 `runtime::dispatch_resize(id, w, h) -> usize`，走 `direct_children_of` 递归整棵子树——因为「容器变了」需要知道的是**嵌套控件**（code editor 在窗口里）。返回命中数，让调用方分得清「没挂载」与「都通知到了」。判据：`a_container_resize_reaches_a_nested_child`（window+panel+button 三层，命中 3；未挂载 id 命中 0）。

**缺陷 11 —— 五个 gamepad `Event` 变体：零生产者、零消费者（原则 #5）**

`src/event/types.rs:449`。`GamepadPress`/`GamepadRelease`/`GamepadAxis`/`GamepadConnected`/`GamepadDisconnected`：五个变体、五个构造器、五个构造器测试，全仓再无第三处引用。没有后端读手柄 API，没有控件 match 它们。修法：**删除全族**（本仓范围是 desktop/tablet/mobile UI），原地留注释说明**为什么删**，并靠新门禁防止回归。

**缺陷 12 —— `Event::ImePreedit`/`ImeCommit` 有消费者无生产者（原则 #97）**

`src/event/types.rs:240`。`code_editor`、`tag_input`、`search_bar` 都 match 它们，而平台 `ImeBridge`（真正的 OS 组合调用）与控件事件层**之间没有任何东西**把它们连起来——那些 match 臂只有测试能到达。修法：`platform/ime.rs` 新增 `deliver_composition(id, &ImeComposition) -> bool` 与 `deliver_commit(id, text) -> bool`，把 bridge 的两种回调翻译成两个事件并投递；放在 platform 而不是 bridge 方法上，是为了让每个后端都拿到同一条投递而不必各自实现。判据：`an_ime_composition_and_commit_reach_the_focused_widget`（真实挂载、断言收到的 preedit/commit 内容与光标）。

**缺陷 13 —— 新增门禁 `check_event_variants_have_a_producer`：把这一类变成不可复发**

`tools/check_event_producers.py` 只覆盖**手势**事件（它从识别器模块派生清单），所以 `Event` 枚举的其余部分从未被审计——上面两个缺陷正是坐在那个盲区里。

新增 `tools/check_event_variants_have_a_producer.{py,sh}`：遍历**每一个** `Event` 变体，要求「生产站点」（复用 `check_event_producers` 的判定：非 match 臂、非 pattern、非 `#[cfg(test)]`、非声明文件本身），或「本仓确实不能生产、由宿主生产」的**逐条声明**（`HOST_PRODUCED`，必须写理由）。构造器 `Event::timer(..)` 这类也算生产者（walk 到实际字面量）。**反向注入已实测**：注入一个无生产的 `GateProbeVariant` ⇒ 门禁变红并点名。

### 14.4 字体 / 图标

**缺陷 14 —— `estimate_text_width` 的文档说自己是「渲染器的模型」，实际只是无 face 的回退（原则 #18）**

`src/widget/metrics.rs:61`。文档断言「It **is** the renderer's model」，但带 face 的构建（所有 desktop/tablet/mobile）里渲染器走 `shaping::cluster_advances` 读真字体的 `hmtx`/`GPOS`，两者**不一致**：本仓自己量过 `i` 是 3.53 px 真实 vs 8.40 估算。

修法：① 真的走渲染器那条两级阶梯（`#[cfg(feature = "text-shaping")]` 时用 `cluster_advances`，否则用扁平模型），② 文档改写清楚两级各自是什么、为什么扁平模型不够（按比例字体错、只在总量上相互抵消——所以**居中**的文字会偏），③ 新增 `render/text/line.rs::measure_text_width_for_test` 暴露渲染器自己的测量值，把测试从「把 0.6 em 模型抄成数字」改成**断言两者相等**。原测试 `the_text_estimate_reproduces_the_renderers_advance_model` 曾死钉 `"abcd" == 34`；那恰好会**逼着**估算继续用与渲染器不同的尺子——正是该测试要防的事。改为断言「估算 == 渲染器的测量」，并另加 `the_fallback_advance_model_matches_the_renderers_fallback`。

**缺陷 15 —— 门禁 `check_generated_files_have_a_runnable_producer` 是**清单驱动**，清单本身漏了整族**

`tools/check_generated_files_have_a_runnable_producer.sh`。它证明图标表可复现，但**字体表（更大、更易手改）不在清单里**，且没有任何机制发现「一个新文件自称生成却没登记」。修法两步：

1. 加 **[4/4] 反向检查**：仓库里任何带 `GENERATED FILE`/`Produced by \`tools/` 头的源文件，必须在 `PAIRS` 或 `HAND_MAINTAINED` 里有名。
2. 补全清单：`event_payloads.rs`（自称生成却没登记）+ 九个 `.ttf` 字形产物 + `cjk_bitmap_data.rs`。

**这一步立刻抓到一个真缺陷（缺陷 16）**。

**缺陷 16 —— `gen_emoji_subset.py` 的确定性开关放错了对象 ⇒ 产物不可复现（原则 #38：判据要实跑）**

`tools/gen_emoji_subset.py:188` 写的是 `options.recalc_timestamp = False`（**subsetter 的 options**），而 `TTFont.save` 读的是 `TTFont.recalcTimestamp`。所以那个开关**是空操作**：连续两次运行产出的 `.ttf` 有 3 个字节不同（`head.modified` 时间戳），`--check` **永远不可能通过**。另外两个字形生成器（`gen_font_subset.py`、`gen_cjk_shards.py`）是把 `recalcTimestamp=False` 传给 `TTFont` 的，所以只有这一个漂移。

修法：`TTFont(str(source_path), recalcTimestamp=False)`，并把「为什么是 TTFont 而不是 options」写进模块文档。验证：连续两次生成 `cmp` **逐字节相同**，`--check` 报 `both files are up to date`。

> 这条是本轮**最有份量**的发现形态：它不是因为「有人写错了一个常量」而存在，而是因为**没有任何门禁跑过这个文件的 `--check`**——缺陷 15 修好之后，第一条被它抓出来的就是这个。与 `log-20260924-2 §17` 同形：**门禁的价值不在它现在绿，而在它让别人的错误变成红**。

### 14.5 JSON 载入器

**缺陷 17 —— `width`/`height` 单独出现时被静默丢弃（原则 #18：文档与代码相反）**

`src/json/loader.rs:1238`。几何简写只在 `x`、`y`、`width`、`height` **四个全在**时才生效；而 `is_loader_owned_key` 把它们都列为「载入器自己处理」，于是名称驱动的属性通道也跳过它们。结果：`{"button": {"width": 200, "height": 40}}` **按默认尺寸加载且不报任何警告**——与模块文档「未被识别的键会点名报警」正好相反。

**缺陷 18 —— `apply_size_constraints` 在同一对象上被调两次（原则 #101）**

`src/json/loader.rs:378`。`apply_properties` 内部已调（`:1320`），外面又调一次。今天是幂等的——**这正是它隐形的原因**，也正是日后某次「让它不再幂等」的改动会静默出错的原因。修法：删掉外层那次，并在原处写明约束在这一步之内完成。

**缺陷 19 —— `on_double_click`/`on_focus`/`on_blur`/`on_close` 被绑到**错误的**回调（原则 #95/#97）**

`src/json/event_route.rs:174`。`DoubleClicked.trigger_kind()` 返回 `Clicked`（路由回调载不动更细的区分），于是 `uses_value_callback()` 为 false，`on_double_click` 被绑到 `on_click`——**单击**信号。处理者于是「在第一次单击就跑，并被告诉这是一次双击」，且真双击永远到不了它。`on_focus`/`on_blur` 绑到值回调、`on_close` 绑到单击回调同理。讽刺的是，该文件自己的文档正是用「which is how `on_double_click` came to be wired to a callback that could never report a double click」来**说明这次修复**——而修复从未落实。

修法：`JsonTriggerMarker::unroutable_reason() -> Option<&'static str>`，`bind_one` 在绑定前拒绝（`log::warn!` 点名键与原因 + 计入 `record_unwired_binding`，与「句柄绑到死 id」共用同一个可观测计数）。**拒绝比近似诚实**：一个跑不起来的处理者比一个报错更糟，因为文档会加载成功。判据：`a_marker_with_no_signal_to_reach_is_refused`、`the_routable_markers_stay_routable`，并把 `tools/check_json_event_route.py` 的第 3 检查扩展为「必须存在 `unroutable_reason` 且 `bind_one` 必须查它」。

## 17. 缺陷 23 —— 断点（`Breakpoint`）在生产路径上是**死接线**（原则 #18/#22/#97）

这是本轮**最重**的一条，单列一节。

`src/view/breakpoint.rs` 的模块文档写「the framework supplies the fact」，`Node::breakpoint` 的文档写「the framework supplies the fact —— the same division `Node::child_if` uses」。**框架什么都没提供**：

```text
$ grep -rn "with_breakpoint|Breakpoint::of" src/ --include=*.rs
  src/view/breakpoint.rs   ← 定义 + 自身测试
  src/view/node.rs         ← 文档示例 + 自身测试
（生产代码零命中）
```

`ViewEngine::mount_with` / `update_with` 直接调 `view.build_with(ctx)`，从不包一层 `with_breakpoint`；全仓没有「视口尺寸 → tier」的机制。于是 `Breakpoint::current()` **永远是 `Expanded` 默认值**，每一个 `.breakpoint(..)` 子树永远被包含——**窄布局分支在真实程序里不可达**。而门禁 `check_breakpoints_are_not_in_draw.sh` 与计划判据 21 都只验证了「类型存在 + 自身单测」，所以全绿。

**取证先于断言（原则 #51）**：我先确认这不是「设计上由宿主负责」——`with_breakpoint` 是 `pub`，但**没有任何 API 让宿主把视口告诉引擎**，`ViewEngine` 也没有 viewport 字段。所以现状不是「分工」，是**缺了中间那一段**（与 BLUE24 §6.1 描述的 a11y 缺陷同形：「①推导在、③桥在、②中间那段不在」）。

**修法（在引擎上建立事实，而不是给 `View::build` 加参数）**：

```rust
impl ViewEngine {
    pub fn set_viewport(&mut self, size: crate::core::Size) { self.viewport = Some(size); }
    pub fn viewport(&self) -> Option<crate::core::Size> { self.viewport }
    fn build_in_force(&self, view: &dyn View, ctx: &Context) -> Node {
        let tier = self.viewport.map(Breakpoint::of)
            .unwrap_or_else(Breakpoint::current);
        crate::view::with_breakpoint(tier, || view.build_with(ctx))
    }
}
```

**两个入口都 funnel 到 `build_in_force`**，于是「tier 对每一次构建都生效」是**一个函数**的性质，而不是两个调用点「必须保持一致」的希望——正是 `Breakpoint::current` 的文档警告的那种跨构建泄漏。`viewport` 默认 `None` ⇒ tier 为 `Expanded` ⇒ **渲染视图声明的全部子树**（既有的、也是「没有信息」的诚实答案），所以**既有行为逐字节不变**。

**判据（四条，全部实测）**：

| 判据 | 断言 |
|---|---|
| `a_reported_viewport_selects_the_breakpoint_subtree` | 360×800 ⇒ 只剩 `phone`；1400×900 ⇒ 只剩 `sidebar` |
| `without_a_viewport_every_declared_branch_is_included` | 未报告时 `viewport() == None`，最宽档渲染全部 |
| `crossing_a_tier_boundary_is_reported_as_a_structural_change` | 跨档产生 `Insert`/`Remove`，而非属性写入（证明选的是**子树**而非坐标） |
| 既有 31 条 engine 测试 | 全绿（无回归） |

**文档同步**：`Node::breakpoint` 的「the framework supplies the fact」改为如实说明两条供给途径（`ViewEngine::set_viewport` 或显式 `with_breakpoint` 作用域），并说明两者都没有时是 `Expanded` 而非猜测的窄档。

> **仍未做的诚实边界**：`ViewEngine` 目前是 `pub` API 但**仓内无生产消费者**（只有 `designer::generator` 的**生成代码**用它，生成代码里也还没调 `set_viewport`）。所以这条修复把「断点可达」从 `false` 变成 `true`，但**还没有一个真实应用在用**——`demo/` 三个 demo 都是命令式构建，不走 `ViewEngine`。这一条登记在 §19，不假装成「端到端已通」。

### 18.4 全量跑出的唯一失败，及其真因

第一次全量报 `quote_board::a_heading_is_placed_with_the_advance_model_it_is_drawn_with` 失败：

这个测试同时断了两件事：① 标题宽度 == `estimate_text_width`，② 「7 px/字符的旧猜测与实际测量相差 ≤ 2」。

继续钉 ≤ 2 等于**禁止**诚实的测量。改为钉那个真正促成替换的性质：**扁平模型给窄字形和宽字形同一个宽度，真实测量不会**（断言 `measure("W") > measure("i")`）。这不是放宽，是换成正确的判据（原则 #19）。

| 28 | `check_locking.sh` | `icon_data_set.rs` 的 `static REGISTRY: Mutex<..>` 被当作 widget 状态 | 按门禁自己的契约加**具名**豁免条目（含理由），并让脚本打印「已豁免哪一份」 |
| 29 | `check_control_feature_visible_in_own_snapshot.sh` | 两个硬编码 SVG 子串标记**早在 HEAD 就已失效**（`M13 5h`/`M88 5h` 全仓不复存在），另有一个随字体度量修正而变（`width="62"`→`59`） | 改用不随字体度量摆动的真实特征标记（两个标题 run + 第二个 tab 的几何 + 24px 带） |

**每一步都先 `git stash` 验证是「预先存在」而不是我引入的**（原则 #19）——五条全部在 HEAD 上实测为红。

> 这一批与缺陷 15/16、§17 的 `Breakpoint` 是同一种东西：**它们不是某个函数写错了，
> 而是「判断项目是好的」的那把尺子本身断了**。一个不能通过的门禁脚本，比没有门禁更糟——
> 它让人以为有人在看。`check_profiles.sh` 覆盖「5 profile 对齐 CI」，却从未绿过。

### 18.7 缺陷 24 —— 三个只有 `mini`/交叉编译才暴露的编译缺陷（原则 #48：验证命令本身也是判据）

> **本条在收尾时扩大成了三个缺陷。**跑 `tools/check_profiles.sh`（它用 `--all-targets`，与 CI 对齐）
> 时发现该门禁**整个不可通过**：`--all-targets` 会连 examples 一起编译，而三个网关缺陷叠在一起：

#### 缺陷 25 —— 两个 example 未按 `full_widgets` 门控 ⇒ `check_profiles` 永不可过

`examples/probe_draw_only.rs` 与 `examples/verify_batch3.rs` 都直接 `use
rust_widgets::widget::special_widgets::code_editor::…`，而 `special_widgets` 是 `full_widgets` 才有的
模块。两者**没有 `[[example]]` 条目**（靠 cargo 自动发现），于是 `--all-targets` 在 `mini`/`embedded`
下编译它们的必然失败：

```text
error[E0433]: cannot find `special_widgets` in `widget`
   --> examples/verify_batch3.rs:16:27
```

修法：按本仓既有约定加 `[[example]] … required-features = ["desktop"]`（**不是** 内层 `#![cfg]`——
那会让 example 没有 `main`，报 `E0601`，而 `Cargo.toml` 里 census probe 的注释早已记下这一点）。
两个一起改，因为「一个不可通过的门禁脚本不算门禁」。

#### 缺陷 26 —— `mini,i18n` 调用了一个被门控掉的函数

```rust
#[cfg(feature = "i18n")]              // 调用点
if has_os_runtime() { … start_i18n_hot_reload_from_env(); }

#[cfg(all(feature = "i18n", not(feature = "mini")))]   // 定义
fn start_i18n_hot_reload_from_env() { … }
```

两个门控**不一致**，于是 `--features mini,i18n` 直接 `E0425: cannot find function`。修法：把调用点
补上同样的 `not(feature = "mini")`，并把「为什么这两个 cfg 必须一致」写进注释。

**这一步之后 `check_profiles.sh` 首次 `exit=0` / `All profile checks passed`** —— 也就是说，在修这三条之前，
本仓那条「5 profile 对齐 CI」的门禁脚本**长期是红的**，且没人看见（它不在默认 `cargo test` 里）。

> 这三条合起来是本轮**最有价值的一类**发现：它们不是「某个函数写错了」，而是
> **判断「项目是好的」的那把尺子本身断了**。与缺陷 15/16 同形。

`cargo check --lib --no-default-features --features mini` 通过，但 `--tests` **不**通过。两个原因：

1. **`glyph_source.rs::diag_face_parse_cost`** 是一个标着「TEMP DIAGNOSTIC」的测试，却**没有门控**，直接使用 `font_assets::outline_face_for` 与 `ttf_parser`——两者只在有 outline face 时存在。在 `mini` 下这个测试文件根本编不过。
   修法：按它**测量什么**来门控（`#[cfg(feature = "text-shaping")]`），并把「TEMP DIAGNOSTIC」改写为「保留原因 + 为何这样门控」。
2. **`event/loop.rs::animation_frame_id`** 的两个调用点都在 `not(alloc_frugal)` 块里，所以 `mini` 下它是死代码并告警（这是**上一轮**修 `AnimationFrameRequest` 时留下的）。
   修法：helper 与调用者同门控。

> 这一条的教训是**判据选取**：`cargo check --features mini` 绿 ≠ mini 能跑测试。测试也是要编译的代码，它自己的门控错了只有 `--tests` 才看得到。已记入本轮的「仍留」：**profile 矩阵应包含 `--tests`**。
