## D. 过程中发现并修复的真实缺陷（F 类）

### F-1. CUPS `lp --version` 退出码非 0 导致的打印能力漏报（自引入，已闭环）

**发现过程**：写完 `has_print_support()` 后实跑探针，macOS 上返回 `false`，但本机确实装了 CUPS。

**取证**：

```console
$ which lp lpr
/usr/bin/lp
/usr/bin/lpr
$ lp --version; echo "exit=$?"
lp：错误 - 未知选项“--version”。
用法：lp [options] [--] [file(s)]
...
exit=1
```

**根因**：CUPS 的 `lp` **不支持** `--version`，它会打印用法并以状态 1 退出。
用 `status.success()` 作为「是否存在」的判据是错的——退出码 1 恰恰证明二进制存在并运行了。

**修复**：判据改为「能否 spawn」（`output().is_ok()`），只在 `ErrorKind::NotFound` 时才算缺失。
抽出共享函数 `platform::types::unix_print_clients_available()`，4 个 Unix 后端统一调用。

**验证（非假修复）**：修复前后实例对比——

```console
$ cargo run --example rw_platform_probe --features macos
# 修复前
has_print_support = false
# 修复后
has_print_support = true
```

**新增回归测试**：`platform::tests::unix_print_probe_detects_cups_client_despite_nonzero_version_exit`
——断言「若 `lp`/`lpr` 能 spawn，则探测必须返回 true」，锁死这个反直觉的判据。

**沉淀为规则 #38**：探测结果判据必须实跑验证，不得凭 API 名称推测行为。

## R. 新发现 R-1：`print_impl.rs` 的「双函数体」OS 分支（真违规，严重）

**问题**：我用更宽的模式重扫时发现 **4 处**早先被漏掉的 `cfg(target_os)`：

```rust
// src/print/print_impl.rs:740 / 765
#[cfg(any(target_os = "macos", "linux", "windows"))]
pub fn print_page_dialog() -> Result<bool, String> { /* 真实控制台确认 */ }

#[cfg(not(any(target_os = "macos", "linux", "windows")))]
pub fn print_page_dialog() -> Result<bool, String> {
 Err("print dialog is not supported on this platform".to_string())
}

// src/print/print_impl.rs:774 / 805 —— 同样的双函数体模式
```

**为何早先漏掉**：我最初的扫描带了 `grep -v tests.rs` 与具体字符串过滤，
而 `print_page_dialog`/`print_to_printer` 不在最初的 7 处清单里。
**教训（已沉淀为原则 #41）**：双函数体写法把 OS 知识固化为两套函数体，
扫描时必须找 `cfg(not(any(target_os...)))` 这种**否定形式**，而不只是 `cfg(target_os = "x")`。

**为何是架构问题**（不仅是风格）：
- 新增一个平台必须**改 print 层代码**（加进白名单），违反开闭原则。
- 能力事实（有无打印后台）实际上已由 `Platform::has_print_support()` 提供，
 两者可能**不一致**（如 Linux 上 GTK 编译了但没装 CUPS）。

**修复**：合并为**单一函数**，入口处询问 backend 能力：

```rust
pub fn print_page_dialog() -> Result<bool, String> {
 if !crate::platform::get_platform().has_print_support() {
 return Err("print dialog is not supported on this platform".to_string());
 }
 // ... 控制台确认逻辑 ...
}

pub fn print_to_printer(content: &str, settings: &PrintSettings) -> Result<(), String> {
 if !crate::platform::get_platform().has_print_support() {
 return Err("system printer is not supported on this platform".to_string());
 }
 if content.is_empty() {
 return Err("cannot print empty content".to_string());
 }
 // ... 写临时文件 + spawn_print_job ...
}
```

**行为保持**：macOS/Linux/Windows 上 `has_print_support()` 为 `true`（已实测），
与旧白名单一致；其它平台为 `false`，与旧 `Err` 一致。

**新增回归测试**：`print::print_impl::tests::print_entry_points_gate_on_backend_capability_not_target_os`
——断言入口依据**后端能力**而非编译期 OS 列表（两个分支都验证）。

**这是工具链限制，非代码缺陷**：CI 在 `ubuntu-latest` 上跑，其 clang 支持 wasm32，

`getrandom` 错误在本机已彻底消失（只剩 C 工具链这一项）。

**问题**：

```rust
fn default_config_dir() -> PathBuf {
 let base = dirs::config_dir().unwrap_or_else(|| PathBuf::from("."));

}
```

# 第 10 轮续五（2026-09-12）— wgpu 降级：新增 OpenGL ES 回退

## AO. 任务

增加 wgpu 降级 OpenGL ES 支持。

## AP. 问题现状（修复前）

全部 GPU 初始化点都用 `wgpu::Backends::all()` 一把梭，共 4 处：

| 位置 | 调用 |
|---|---|
| `src/wgpu_backend/renderer.rs:26` | `Instance::new(backends: Backends::all())` |
| `src/gpu/adapter.rs:33` | `GpuType::detect_primary()` |
| `src/gpu/adapter.rs:284,306` | `enumerate_adapters` / `select_adapter_with_fallback` |

后果：
1. **无法得知实际落在哪个图形 API**——`all()` 把主/次/软件后端混在一起，`request_adapter` 返回什么都算成功。
2. **无显式降级阶梯**——主机没有 Vulkan/Metal/DX12 驱动但可用 OpenGL ES（ANGLE/EGL）时，行为不可预测。
3. **无降级信号**——即使跑在软件回退上，调用方也拿不到任何提示。

## AQ. 实现：有序降级阶梯

新增 `src/gpu/backend_ladder.rs`（约 360 行含测试）。

### AQ-1. 三档阶梯

```rust
pub enum GpuBackendTier {
 Primary, // Vulkan / Metal / DX12 / browser WebGPU
 OpenGlEs, // GL：OpenGL ES（Linux/Android）、WebGL、ANGLE（Win/macOS）
 Software, // CPU 回退，仅末级
}

pub const BACKEND_LADDER: &[(GpuBackendTier, wgpu::Backends)] = &[
 (GpuBackendTier::Primary, wgpu::Backends::PRIMARY),
 (GpuBackendTier::OpenGlEs, wgpu::Backends::GL), // ← 本次新增的支持
 (GpuBackendTier::Software, wgpu::Backends::empty()),
];
```

**依据**（读 wgpu-types 30.0.1 `src/backend.rs:91` 取证，非推测）：
- `Backends::PRIMARY` = `VULKAN | METAL | DX12 | BROWSER_WEBGPU`
- `Backends::SECONDARY` = `GL`
- `GL` 官方说明：“Supported on Linux/Android, the web through webassembly via WebGL,
 and Windows and macOS/iOS via ANGLE”

### AQ-2. 阶梯遍历

```rust
pub async fn select_adapter_with_gl_fallback(
 instance: &wgpu::Instance,
 power_preference: wgpu::PowerPreference,
 compatible_surface: Option<&wgpu::Surface<'_>>,
) -> Option<(wgpu::Adapter, GpuBackendTier)>
```

逐个 rung 尝试，返回首个成功的适配器及其 tier。`force_fallback_adapter` **仅**施于末级——
提前请求 CPU 适配器会掩盖可用的硬件 GL 路径。

### AQ-3. wasm32 特殊处理

`ladder_for_target()`：`wasm32` 上阶梯收敛为单级（`BROWSER_WEBGPU`），因为 `wgpu` 在
**创建 Instance 时**就决定 WebGPU 支持，而非创建适配器时（原则 #42：架构约束不同于 OS）。

### AQ-4. 降级可见性

`GpuBackendTier::is_degraded()` / `label()`，renderer 启动时告警：

```rust
if tier.is_degraded() {
 log::warn!("[wgpu] using degraded backend tier: {} ({:?}, adapter '{}')", ...);
}
```

`AdapterInfo::backend_tier()` / `is_degraded_backend()` 供宿主查询。

## AR. 过程中发现并修复的 2 个真实缺陷（自引入）

### AR-1. `WGPU_BACKEND` 被静默忽略（严重，违反原则 #13/#18）

**发现过程**：写探针实测 `WGPU_BACKEND=gl`，得到：

```console
$ WGPU_BACKEND=gl cargo run --example gl_ladder_probe --features gpu-wgpu
chosen backend= Metal ← 用户要 GL，却给了 Metal，且无任何提示！
```

**根因**：`wgpu` 在 **Instance 创建时**应用 `WGPU_BACKEND`。我的 `instance_backends()`
为了保持各 rung 可达而把阶梯∪pin 取并集，于是 `request_adapter` 返回默认（主）适配器，
pin 被完全架空。

**修复**：pin 存在时改用 **枚举 + 过滤**，而非 `request_adapter`：

```rust
if let Some(pinned) = backends_from_env() {
 let mut candidates = instance.enumerate_adapters(pinned).await;
 if candidates.is_empty() {
 log::error!("[gpu] WGPU_BACKEND pinned {pinned:?} but no adapter exposes that backend");
 return None; // 诚实返回失败，绝不替换
 }
 // 多个候选时优先硬件适配器
 candidates.sort_by_key(|a| a.get_info().device_type == wgpu::DeviceType::Cpu);
 ...
}
```

**修复后实测**：

```console
$ WGPU_BACKEND=gl cargo run --example gl_ladder_probe --features gpu-wgpu
no adapter on any tier
renderer unavailable: wgpu adapter request failed: WGPU_BACKEND pinned Backends(GL),
 which this host does not provide
```

不再静默替换，错误信息含 pin 值。本机 macOS 无 ANGLE 故 GL 不可用，
在 Linux/Android/Windows-ANGLE/wasm 上则会正常解析到 GL 适配器。

### AR-2. `Instance` 被 pin 收窄导致回退路径不可达

**问题**：最初直接把 `with_env()` 结果交给 `Instance::new`，一旦 `WGPU_BACKEND=gl`
就把实例收窄到单一后端，使其它 rung **不可达**，变成不可恢复的死路。

**修复**：新增 `instance_backends()` 返回**阶梯 ∪ pin 的并集**，保证实例能抵达每一级；
pin 只影响**选择**（见 AR-1），不影响实例的能力范围。

## BB. 真实缺陷：`not(mini)` 与模块门控不对等（已修复）

### BB-1. 根因

`widget/mod.rs` 中，包含完整控件的模块门控是：

```rust
#[cfg(all(
 any(feature = "desktop", feature = "tablet", feature = "mobile"),
 not(any(feature = "mini", feature = "embedded"))
))]
pub mod view_widgets; // 同样适用于 advanced/special/chart/nav/menu/media/...
```

但多处**引用**这些模块的代码只用了较窄的 `not(feature = "mini")`：

```rust
// src/widget/capability.rs（修复前）
#[cfg(not(feature = "mini"))]
use crate::widget::view_widgets::data_grid::DataGrid; // ← embedded 下模块不存在
```

两个条件在 `embedded` 下**不等价**：`not(mini)` 为真，而模块门控为假。

### BB-2. 关键发现：`full_widgets` 与 `not(any(mini,embedded))` 也不等价

这是本轮最重要的技术发现。二者差异出现在**既无 device profile、也无 mini/embedded** 时
（如 `--no-default-features --features gpu`）：

| 条件 | `--features gpu` 下 |
|---|---|
| `not(any(mini, embedded))` | **true** |
| `any(desktop, tablet, mobile)` | **false** |
| `full_widgets`（两者合取） | **false** |

所以修复不能简单把 `not(mini)` 改成 `not(any(mini,embedded))`，必须用完整的合取条件。

### BB-3. 最优方案：单一 cfg 别名（build.rs）

与其在 100+ 处复制同一个合取表达式（这正是产生错位的土壤），改为在 `build.rs` 定义**唯一真相**：

```rust
fn declare_cfg_aliases() {
 println!("cargo:rustc-check-cfg=cfg(full_widgets)");

 let has_profile = ["desktop", "tablet", "mobile"]
 .iter().any(|f| feature_enabled(f));
 let is_stripped = ["mini", "embedded"]
 .iter().any(|f| feature_enabled(f));

 if has_profile && !is_stripped {
 println!("cargo:rustc-cfg=full_widgets");
 }
}
```

于是所有门控与引用都写成 `#[cfg(full_widgets)]`——**结构上不可能再出现错位**。

**实测验证别名行为**（用探针程序，非推测）：


### BL-1. 关键实现：`ChartContextAdapter`（新增 `src/chart/adapter.rs`）

拦路问题是两个 trait 的单位不同且无人桥接：

| | 单位 |
|---|---|
| `ChartContext` | `f32` 几何 + `f32` 线宽（分辨率无关，兼顾 SVG） |
| `RenderContext` | `i32` 像素 + `u32` 线宽（软件光栅/原生后端要求像素精确） |

- `draw_arc`/`draw_ellipse` 无原生图元，用**折线/多边形逼近**，分段数随尺寸与弧度自适应

# 第 10 轮续八（2026-09-12）— 图表去重收尾：剩余三个控件全部接入

## BQ. 任务

把 `LineChart` / `PieChart` / `Sparkline` 也接到共享引擎，彻底消除三处重复。

## BR. 逐项处理（均先取证再动手）

### BR-1. `LineChart` —— 接接入（真重复）

**取证**：与 `BarChart` 完全同类的手写件：`plot_area()`、`for i in 0..=4` 网格循环 ×2、
Y/X 轴刻度标签循环 ×2。全部是 `chart/` 已有的能力。

**改造**：
- 删除手写的轴/网格/刻度代码，改用 `compute_cartesian_layout` + `draw_cartesian_axes`
 + `draw_y_ticks` + `draw_x_ticks`（经 `ChartContextAdapter`）
- `plot_area()` 保留但加 `#[cfg(not(feature = "chart"))]`（供 tablet/mobile 回退）
- 保留全部公开 API 与行为

### BR-2. `PieChart` —— 接接入（真重复，且是新发现的）

**取证**：发现真正重复的不是颜色调色板（`chart/` 的 palette 是私有且控件用调用方传入的颜色，
不算重复），而是 **扇区几何**：控件手写了 `fill_pie_sector` + `fill_triangle_scanline`
（约 90 行光栅器，固定 `segments = 60`），而 `chart/` 的 PieChart 另有一套弧多边形逼近。

**改造**：在 `chart/charts.rs` 新增共享几何构造器：

```rust
pub fn sector_polygon(
 center: Point, outer_radius: f32, inner_radius: f32,
 start_angle: f32, end_angle: f32, steps: u32,
) -> Vec<Point>
```

统一顶点环约定：外弧正向 → 内弧反向（甜甜圈），或→ 单顶点（实心楔形）。

- **`chart/` 自己的 PieChart 也改用它**（dogfooding，保证两边真的一致）
- 控件的 `fill_pie_sector` 改为消费该多边形，只保留“多边形→扫描线填充”这一步转换，
 **不再自己算角度**
- 分段数从固定 60 改为**随弧度与半径自适应**（`sweep * radius / 6`）

### BR-3. `Sparkline` —— **有意不接**（取证后判定）

**取证**：

```console
$ grep -n 'plot_area\|draw_cartesian\|draw_y_ticks\|draw_x_ticks\|draw_legend\|margin\|Font' \
 src/widget/chart_widgets/sparkline.rs
（空 —— 无任何可共享的轴/网格/刻度/边距代码）
```

Sparkline 的**定义**就是“没有图表装饰”：无边距、无轴、无网格、无刻度标签、无图例——
而这些恰好就是 `chart/` 提供的全部。强行接入只会：
- 多一层适配器开销
- 给它保留它本不该有的边距

唯一重叠是值域解析，但语义也不同（sparkline 铺满整个矩形，引擎是拟合到内缩的绘图区）。

**处理**：**不接入**，并在模块文档写明原因（防止后人“好心”迁移），符合原则 #28（无收益不引入开销）。

## BS. 可靠性处理（跨 trait 边界的新发现）

改造中发现 `PieChart` 的甜甜圈分支需要区分两种顶点环约定。已在 `sector_polygon` 注释中
明确写下：**外弧正向，内弧反向**，并用 `half = ring.len() / 2` 切分配对。
新增的 2 个像素级测试直接验证两种模式都真的产生覆盖：

| 测试 | 验证 |

| `pie_chart_donut_mode_produces_ring_pixels` | 甜甜圈模式下内弧分支同样产生覆盖 |
