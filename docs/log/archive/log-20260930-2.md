## 2. 逐条修复

### 2.1 platform/runtime：GUI 模式从“名字断言”改为“运行时证据 + 名字”

**文件**：`src/platform/runtime.rs`（`runtime_gui_mode_for`）

**缺陷（两个方向，都被 `_ => PreviewOrStub` 掩盖）**：

1. `"harmony-desktop"` 仍在匹配列表中，但后端已在上一轮改名为 `"harmony-state-backend"`——该分支是**死代码**。
   之所以没人发现，是因为**同一个 arm 里也写了新名字**，而且两者答案相同。这是巧合不是设计。
2. `"android-state-backend"` / `"ios-state-backend"` / `"wasm-state-backend"` / `"portable"` /
   `"unknown-runtime-stub"` / `"macos-fallback-stub"` **完全没列**，全部落到 `_` arm。
   `_` 恰好给出 `PreviewOrStub`——**对的答案，错的原因**：
   一旦哪个后端的诚实模式变成 `NativeInteractive`，它会静默错报。
3. 真正的逻辑缺陷在 `"cocoa" | "WindowsPlatform" => NativeInteractive` 这一行：**从名字断言“能开窗”**，
   没有任何运行时证据。名字是后端自己挑的字符串，改名不会编译失败。

**修复**：名字只用来筛“这条原生窗口路径在本 build 里编译进来了吗”（`gtk`/`wayland` 还要看
`target_os` + native feature），**交互性必须另有 `capabilities().dpi_scaling` 证据**
（没有显示器的后端没有东西可缩放，报告 `false`）。
没有证据时降级为 `PreviewOrStub`——失败的诚实方向：
告诉用户“不会出现窗口”而其实能开窗，只损失一次困惑；
告诉用户“会出现窗口”而其实没有，损失整个会话（原则 #2：结论要证据，不要名字）。

**验证**：

```
cargo test --lib --features desktop platform::tests::
  -> 19 passed; 0 failed
  (含新增 a_native_name_without_dpi_evidence_is_not_called_interactive ... ok)
```

新增测试用一个 `backend_name() == "cocoa"` 但 `capabilities()` 全 false 的
**矛盾后端**，同时断言「有名字无证据 → 不是交互式」与「普通 stub → 也是 PreviewOrStub」，
两条一起才排除“对所有东西都返回 PreviewOrStub”也能通过的可能。

### 2.3 capability 谎报集群（objc2 / windows / macos / wasm）

**为什么这是一个缺陷类而不是四条孤立 bug**

`PlatformCapabilities` 的五个 flag 是**承诺**，宿主读它来决定“要不要向这个后端要原生菜单 /
要不要按屏幕缩放布局 / 要不要先把控件树建起来”。没有一个测试曾经把 flag 与它承诺的方法对过账，
所以四个后端在四个 flag 上同时说谎，并且互相抄袭——objc2 的注释直接写着
“honours the same four host integrations as the legacy macOS backend”，而 legacy 后端也一个没实现。

这是“冰山法则”的典型：**改一处，要查同一模式**。逐条取证：

| 后端 | flag | 它承诺的方法 | grep 结果 |
|---|---|---|---|
| `macos_objc2` | `ime` | `ime_bridge()` | 未覆写 → `None` |
| `macos_objc2` | `accessibility` | `accessibility_bridge()` | 未覆写 → `None` |
| `macos_objc2` | `native_menu` | `create_menu_bar` / `menu_add_item` / … | **0 命中**，且 `macos_objc2/tests.rs` 自己断言 `create_menu_bar(..) == 0` |
| `macos_objc2` | `dpi_scaling` | `dpi_scale_factor()` | 未覆写 → `1.0` |
| `windows` | `native_menu` | 同上 | **0 命中** |
| `macos` | `native_menu` | 同上 | **0 命中** |
| `macos` | `dpi_scaling` | `dpi_scale_factor()` | 未覆写 → `1.0`（但 `ime`/`accessibility` 确实有实现，**这两个保留 true**） |
| `wasm` | `supports_surfaces` | `mount_surface` / `resize_surface` / `unmount_surface` / `invalidate_surface` | **0 命中** |

**修复**：每个 flag 改为“**记录实现，不记录 OS 有没有该功能**”，并逐条写出取证依据。
`macos` 的 `ime`/`accessibility` 确实有实现，**没有一起改**——不能因为“看着像”就把真实能力也删掉
（原则 #51 的反向：合并/修改前必须先 grep 取证到底重复/缺失了什么）。

**`wasm` 的额外问题**：那段 doc 注释写的是 `unmount_surface` 的行为（“Release the surface
attached to this backend's canvas id. The trait method is about display surfaces…”），
却贴在 `supports_surfaces`（这是个**问句**）上面——注释错位。

**文档同步**：这个矩阵公开在 cookbook 的三份翻译里（en / zh-CN / zh-TW），
且 `docs_paths_tests.rs` 有一份转写副本。四处全部同步，并把测试注释里那个**语义错误**
记下来：第一版错在抄错数字，第二版错在**误解了列的含义**。

**验证**：

```
cargo test --lib --features desktop docs_paths
  -> 10 passed; 0 failed
     (published_os_capability_matrix_matches_the_trait_default ... ok
      documented_matrix_matches_real_backends ... ok)

cargo test --lib --features desktop --features wasm wasm::
  -> 11 passed; 0 failed
     (nothing_advertises_a_surface_capability_it_has_not_implemented ... ok)
```

`wasm` 的测试从 `assert!(p.supports_surfaces())` 改为**两半一起断言**：
`!supports_surfaces()` **且** `!mount_surface(...)`。只断言 `false` 太弱——
一个“忘了声明自己真有能力”的后端也会返回 `false`，第二条断言才钉住
“false 的原因确实是没有实现”。

### 2.4 platform/harmony：`poll_widget_triggered` 只修了一半（注释自述“修了对称性”，实际只修了一侧）

**文件**：`src/platform/harmony/platform_impl.rs`

**缺陷**：`poll_widget_trigger_event` 的 doc 注释写着：

> leaving this to the trait default made the pair below silently asymmetric —
> `inject_widget_trigger_event` returned `false` and this always returned `None`,
> so no injected trigger could ever be observed.

这段话**准确描述了一个真实的不对称**，但只补了第三项（`inject_*`）与第一项
（`poll_widget_trigger_event`），“the pair”里的**第二项 `poll_widget_triggered` 根本没补**。
它仍是 trait 默认的 `None`。

两侧是同一个队列的两个视图，trait 文档明确把它们写成同一个事件流：

```
/// Returns the next pending widget activation. Default: none are produced.
fn poll_widget_triggered(&self) -> Option<ObjectId> { None }
/// Returns the next pending typed widget activation. Default: none are produced.
fn poll_widget_trigger_event(&self) -> Option<WidgetTriggerEvent> { None }
```

**取证**：所有同类状态后端**两个都覆写**——`AndroidPlatform`、`IosMobilePlatform`、
`AndroidMobilePlatform`、`StubPlatform`；只有 Harmony 覆写了一个。
结果：注入一个 trigger 后，`poll_widget_trigger_event()` 能拿到事件，
而 `poll_widget_triggered()` 返回 `None`——**同一个控件，一道门里在、另一道门里不在**。

`platform::tests::consistency_compat_poll_widget_triggered_is_single_delivery_shim`
正是为钉住这条不变式而存在的，但它只测了 `StubPlatform`，所以 Harmony 逃过了门禁。

**修复**：`poll_widget_triggered` 从 typed 事件**派生**，而不是再 drain 一次队列，
以保证两者真的是同一个 FIFO：

```rust
fn poll_widget_triggered(&self) -> Option<ObjectId> {
    self.poll_widget_trigger_event().map(|event| event.widget_id)
}
```

**新增回归测试**：`harmony/tests.rs::the_two_trigger_views_share_one_queue`。
刻意**交叉**断言（先 id 视图再 typed 视图，再反序），因为要钉的性质不是
“两个都能返回东西”（两个独立队列也满足），而是“它们**是同一个队列**”。

### 2.5 附带发现：`print_impl` 两条断言把“后端名 + 消息散文”当成契约

改了 Harmony 的后端名之后，`print_entry_points_gate_on_backend_capability_not_target_os`
立刻变红——**这不是改名引入的 bug，是它自己本来就悬空**。取证：

```text

            no system print support, so page selection cannot be offered")
```

第二条断言写死了一句**代码里从来不存在的**错误消息（`grep` 全仓 0 命中）。

### 2.6 组合控件核心缺陷：`tab_run` 把「内容自己的总和」当成布局的可用空间

**文件**：`src/widget/nav_widgets/tab_view.rs`（`tab_run`）

**这是本轮最重要的组合控件缺陷，也是“假迁移”的教科书形态。**

`tab_run` 表面上已经完全“迁移”到 `CompositeBuilder` + `FlexLayout`——
门禁 `check_composite_assembly_rules.py` 也判它通过。但取证后发现**它把手工累加器从
`x` 坐标挪到了矩形宽度上**：

```rust
// 修复前
let total: i32 = widths.iter().sum();
let run = Rect::new(0, 0, (total + TAB_SPACING * widths.len() as i32).max(0) as u32, height);
row.arrange(run, &mut |_, rect| placed.push(rect));
...
let along = widths.get(index).copied().unwrap_or(TAB_MIN_WIDTH) as u32;
let created = row.add_sized(&factory, "label", &tab.title,
                            crate::core::Size::new(along, height), LayoutParams::new());
```

三处独立缺陷，全部取证如下：

**缺陷 A：band 宽度由“子控件的总和”导出 ⇒ 挤压分支永不进入。**
`run.width` 恒等于 `sum(widths) + gap*n`。求解器里
`remaining = available_main - total_intrinsic - gaps`，于是 `remaining` **恒为 0**，
`compute_main_sizes` 的 `remaining < 0`（shrink）分支**永远不执行**。
`TAB_MIN_WIDTH` 的文档写的是“narrowest a tab may be **drawn**, so a one-character caption
is still a tap target”——它从来没作为**下限**到达过布局。

**缺陷 B：`add_sized` 把量出来的宽度同时当作 min/pref/max。**
`add_sized` 内部是 `Hints::fixed(size.width, size.height)`。后果有二：
1. 测量的宽度变成**地板**，不是愿望 —— 与缺陷 A 一起，让挤压在两层都不可能；
2. `FlexLayout::arrange_with_context` 中 `size_is_stated` 读到 `min == max`，
   把它判为“组合控件声明的尺寸”，于是**豁免于 `grow_to_min_touch_size`**——
   即标签页在移动端**拿不到触摸下限**。而 `add_sized` 的文档说明的合法场景是
   “a column of a control whose size the composite owns”，标签宽度显然不是这一类。

**缺陷 C：`Rect::new(0, 0, 0, 0)` 兜底 + 不自洽的 `unwrap_or(TAB_MIN_WIDTH)`。**
布局返回的矩形数少于标签数时，兜底塞 `Rect::new(0, 0, 0, 0)`——一个调用方必须
像真盒子一样平移、却无法与真盒子区分的原点。而 `unwrap_or(TAB_MIN_WIDTH)` 又暗示
“缺失就是最小宽度”，两条兜底互相矛盾。

**修复**（四处一起改，因为它们是同一个缺陷的四个面）：

1. `run` 改为**传入真实的 `strip`**：
   ```rust
   let run = strip;
   ```
   布局于是回答调用方**真正的问题**（“我有的这块地方能放多少”），
   而不是一个“按构造恰好放得下”的同义反复。
2. `add_sized` → `add_with_hints`，声明真实的 `min`/`pref`/`max` 三元组：
   ```rust
   let declared = Hints {
       width: AxisHints::new(TAB_MIN_WIDTH as u32, along.max(TAB_MIN_WIDTH) as u32, u32::MAX),
       height: AxisHints::fixed(height),
   };
   ```
   测量的宽度是**愿望**，`TAB_MIN_WIDTH` 是**地板**，上限留空（band 有限，不会溢出）。
   这与 `tab_widget` 自己的 `tab_width_hints` 是同一形态（BLUE22 · G-1）。
3. 兜底改为 `Rect::new(strip.x, strip.y, 0, height)`——零宽但**在条带内**，
   读作“未布局”，与真盒子可区分。
4. 因为 `run.x == strip.x`，调用方的平移从“假定从 0 开始”变成真实的 `+= strip.x`。

**连带修复的布局层缺陷（被上面的新测试逼出来的，见 2.7）。**

**测试策略（重要）**：新增 `a_strip_too_narrow_for_its_tabs_keeps_them_inside_it`，
刻意用 **90 px 的条带 + 三个长标签**构造“装不下”的场景。
另一条既有测试 `a_tab_is_as_wide_as_its_own_caption_needs` 断言的是**测量宽度**，
所以它的 fixture 必须**够宽**（改为 900 px）——这两条测试测的是**相反的两件事**，
fixture 宽度在修复前是无所谓的（band 恒等于内容），修复后变成承重的。

> **冰山法则**：同一个“band 由内容总和导出”的形态在仓里还有一处——
> `menu.rs::item_bands` 用 `Rect::new(0, 0, width, self.popup_height())`，
> 而 `popup_height()` 正是上面循环刚注册的那些行高之和。两处都改了。

### 2.7 布局层：`grow_to_min_touch_size` 会把子控件推到内容原点**之前**（2.6 的新测试逼出来的）

**文件**：`src/layout/flex.rs`（`arrange_body` 内的 `slide` 闭包）

**发现路径**：写完 2.6 的测试后它仍然红，报：

```text
tab 0 must stay inside the strip, or it is painted off the control:
  Rect { x: 0, y: 0, width: 171, height: 40 } in Rect { x: 0, y: 0, width: 90, height: 40 }
```

打探针（`eprintln!` 打印 `available_main` / `sizes` / `solved` / `mins`）确认
**布局拿到的 `available_main` 是 441 而不是 90** —— 证明 2.6 的缺陷 A 是真的
（band 由内容总和导出）。修掉 A 之后探针变成 `avail_main=300`，压缩生效了，
但暴露出**第二个独立缺陷**：`Stretch` 轴上的子控件其 `x` 会跑到内容原点左边。

**根因**：`slide` 闭包的第一行是

```rust
// No room to slide into: the slot already owns the band.
if slot_extent >= band_extent {
    return origin;
}
```

这个前提在**它跨越的那个轴**上是对的，被错误地套用到了**另一个轴**：

- `Stretch` 轴上的子控件拿到 `child_rect` = 整条 band（`stretch_cross`），
  于是那一轴 `slot_extent == band_extent`，`slide` 直接返回 `origin`；
- 但 `grow_to_min_touch_size` **两个轴都长**，且 `Rect::new(x - (w - w)/2, ...)` 是**居中**增长；
- 结果：一个在 `x = 0, width = 87, height = 40` 的标签页，
  在 `height` 方向被撑到触摸下限时，`x` 被重新居中到 **`x = -5`** ——
  画到了自己控件的左边，而 SVG 后端发出绝对坐标、这一层不裁剪，于是表现为
  “标签从条带左侧外面开始”。

**修复**：给 `slide` 的结果再套一层**只往右钳**的 `clamp_origin`：

```rust
let clamp_origin = |origin: i32, band_origin: i32| origin.max(band_origin);
```

**为什么不干脆无条件钳进 band**：因为那会在另一个方向出错 ——
`grow_to_min_touch_size` 保证地板，若地板本身大于 band，
“钳进 band”会**缩小**这个盒子，正是 G-1 已经裁定过要用“等比缩放”而不是“钳制”来解决的矛盾。

**修复后的规则是**：**保留增长后的尺寸，只把原点挪回 band 内 —— 且只挪到“刚好不为负”。**
因地板大于可用空间而必然溢出的盒子，保留远端溢出，但不再从**近端**冒出去 ——
近端才是读者真正丢内容的方向（内容原点之前的东西会被画在控件背后）。

**验证**：新增测试在修复前红、修复后绿（见 2.6），
且 `cargo test --lib --features desktop widget::` 3966 条全绿 ——
说明这条改动没有破坏既有的触摸下限测试
（`a_plain_child_is_grown_to_the_profiles_touch_floor`、
`flex_layout_update_with_context_scales_gap_and_padding` 等）。

### 2.10 门禁升级：`check_composite_assembly_rules.py` 新增 rule-9 检查

**文件**：`tools/check_composite_assembly_rules.py`

**为什么必须加**：2.6 那个缺陷**完全通过了现有门禁**。
`check_composite_assembly_rules.py` 只检查两条：

- rule 1：子控件必须来自 `WidgetFactory::create`；
- rule 2：子控件必须由 `Layout` 摆放（不得 `rect.x + 字面量`）。

`tab_view` 两条都满足 —— 它确实走了工厂、确实走了 `FlexLayout`。
**缺陷在于它给布局的 band 是由内容总和导出的**，于是布局的压缩分支永不执行。
这正是 §B.5.1 说的“不是修复，是换了地址”：手工累加器从 `x` 坐标挪到了宽度上。

**新增检查** `check_rule_9_band_is_the_callers_room`：
在传进 `arrange` 的那个 rect 的**构造处**查找“凭空造出的 band”
（`Rect::new(0, 0, <标识符>[,)]`，允许 `as u32` 转型），
并要求同一函数体内**没有** `geometry()` —— 有就说明 band 是从控件真实矩形推导的。

**新增反向注入** `inject_rule_9`：把 `tab_view` 的 `let run = strip;` 还原成
`Rect::new(0, 0, widths_total as u32, height)`，要求门禁报错。

**这个检查经历了三次收紧，每次都记在这里，因为“门禁本身出错”比“代码出错”更隐蔽**：

| 版本 | 写法 | 结果 |
|---|---|---|
| v1 | `arrange(` 之后 220 字符窗口 | **漏报** —— `let run = ...` 在窗口外一行 |
| v2 | 从上一个 `fn ` 到 `arrange` 的整个函数体 | **误报 2 处** —— `tabwidget`、`menu`，把已修好的设计报成缺陷 |
| v3（定稿） | 只看传进 `arrange` 的那个 rect 的**绑定处**，并排除同函数含 `geometry()` 的情形 | 0 误报、0 漏报，反向注入可检出 |

v2 的误报特别值得记：`tabwidget` 的 `tab_width_hints()` **确实**做了正确的取整
（拿 tabs 总和与 `rect` —— 控件的**真实** extent —— 比较，超了就算出 `share`，
并把 `share` 作为 hint 三元组声明）。它的“凭空 band”是**取整决定之后**的算术，
而不是取代取整；`tab_view` 的缺陷恰恰是顺序反了。**把一个已经修好的设计报成

### 3.1 flex.rs：我的 clamp 破坏了 `flex_layout_update_with_context_scales_gap_and_padding`（我自己引入的）

**复核结论**：`REFUTED`，并且给出了实测输出：

```text
test layout::flex::tests::flex_layout_update_with_context_scales_gap_and_padding ... FAILED
panicked at src/layout/flex.rs:1698:9:
assertion `left == right` failed: a grown child must stay centred on its allocated slot
  left: 20
 right: 14
```

**根因**：我第一版写成 `origin.max(band_origin)`，**无条件**把原点钳进 band。
但那条测试断言的是一个**跨满整条 band 的 slot 被触摸下限撑开时保持居中**
（`flex.rs:1698` 明确写着 “a grown child must stay centred on its allocated slot”），
而我的 clamp 把居中结果压回了边缘。

**我的第二个错误（比第一个更值得记）**：修这个时我写成“主轴上不钳、交叉轴上钳”，
用 `is_main_axis: bool` 区分 —— **但 `slide` 的判据根本不是“哪个轴”，而是
`slot_extent >= band_extent`**。而且我还把参数传错了：
`slide(origin, slot_extent, slot_extent, ..)` —— 同一个值传给了 `extent` 和 `slot_extent` 两个形参。
于是 `tab_view` 的测试在修了 flex 之后**又红了**（`tab 2` 越界 2 px）。

**定稿的修复**：判据改成**比较“增长后的盒子”与 band**，而不是比较 slot 或轴：

```rust
let realize = |origin, box_extent, slot_extent, band_origin, band_extent| -> i32 {
    if box_extent >= band_extent {
        // 盒子本身就占满了 band：保留文档化的居中溢出（`flex_layout_update...` 钉的就是这条）
        return origin;
    }
    // 盒子装得下，就不许被顶出 band —— 不论是因为 slot 跨满（`slide` 会拒绝动手）
    // 还是因为原点钳制。
    let latest = band_origin + band_extent as i32 - box_extent as i32;
    origin
        .clamp(band_origin, latest.max(band_origin))
        .max(slide(origin, box_extent, slot_extent, band_origin, band_extent))
};
```

这个判据同时满足了两个**看似矛盾**的性质：
- 盒子真的 ≥ band（G-1 的矛盾地板情形）→ **保留溢出**，不缩小（否则就是 G-1 已裁定禁止的“钳制”）；
- 盒子 < band 但 slot 跨满（`Stretch` 轴）→ **钳进来**，因为 `slide` 因为 *slot* 而拒绝，
  而 `Stretch` 已经解决过的居中又被做了一遍。

**为什么不能只看“哪个轴”**：轴上没有信息。同一个 `Stretch` 轴，
一个 40 px 高的 band 里放一个 4 px 的盒子要钳，放一个 60 px 的盒子要保留——
区分它们的唯一事实是**盒子与 band 的大小关系**。

### 3.2 `runtime_gui_mode_for`：我的修复让真实的 cocoa 后端得到错误答案（我自己引入的）

**复核结论**：`REFUTED`。

**根因**：我在 §2.1 里把 `macos` 的 `dpi_scaling` 改成了 `false`（那是对的，见 §2.3），
但 `runtime_gui_mode_for` 的新判据是 `native_capable && capabilities().dpi_scaling`。
于是真实的 `cocoa` 后端变成 `true && false` → `PreviewOrStub`。
**而这个后端是真正会开 AppKit 窗口的**（`init()` 调 `NSApplication::sharedApplication` +
`finishLaunching`，`run()` 调 `NSApp().run()`），
并且正是**出厂 `desktop` profile 在 macOS 上选中的那个**（`Cargo.toml` 的 `desktop` 含 `cocoa-legacy`）。
demo 会打印 `runtime_gui_mode()`，于是 macOS 用户会被告知“不会出现窗口”——
**我为了修“从名字断言”而引入的错误，恰恰是同一类错误的反面。**

**这是本轮最值得记的一条**：一个修复的正确性不能只看“新代码对不对”，
还要看**它与同一轮其它修复的相互作用**。两条各自正确的改动在一个判据上相遇，
就产生了第三条谁都没测到的行为。测试只覆盖了合成的 `NameOnlyCocoa`，
真实的 `cocoa` 因 `#[cfg]` 在本机不可达 —— **不可达的行不会被测试，也就不会失败。**

**定稿的修复思路**：`dpi_scaling` 不是“能不能开窗口”的证据。
能开窗口的证据是**原生窗口创建路径被编译进来了**，而这是
`cfg!()` 能问的（`gtk`/`wayland` 已经这么做了），加上“这个名字确实是原生后端”。
因此改为：名字判定 + `cfg!` 的编译期证据，`capabilities()` 不再参与。
（见 §3.4 的最终形态与测试。）

### 3.4 `tab_view`：我的 band 修复导致坐标被**翻译两次**（会重复付账的那类）

**复核结论**：`PARTIAL`。

`tab_run` 现在把 `strip` 整个交给布局，而 `FlexLayout::arrange` **在 band 自己的坐标里**发出子矩形，
所以返回值已经带了 `strip.x`。但两个调用方还按旧的“原点 (0,0)”假设处理：

| 位置 | 旧行为 | 后果 |
|---|---|---|
| `draw` | `tab_bar_rect.x + local.x` | 每个标签画在 `2 * strip.x` |
| `handle_event` | `pos.x - strip.x` 再与 `box_rect.left` 比 | 命中区同样偏 `strip.x` |

两者**互相一致**，所以“点击的标签 == 绘制的标签”这条（子断言 c）仍然成立 ——
但两者都相对控件的真实几何偏了 `strip.x`。
**所有标签测试都用 `Rect::new(0, 0, ..)`，`strip.x == 0`，所以这个 bug 完全不可见。**

**修复**：`draw` 不再平移（直接用布局给的矩形），`handle_event` 直接用 `pos.x`。
并把 `tab_run` 的文档从“strip 坐标，原点在条带左上角”改为事实描述（绝对坐标）。

## 6. 第四批：capability-flag 类的**穷尽扫描**与门禁化

用户要求继续扫描这一类。这次不再逐个抓，而是**先建矩阵**——
把 `capabilities()` 的每个 flag 与它承诺的方法做全对账。

### 6.1 全后端 × 全 flag 对账矩阵（取证命令已固化）

```
for f in linux wayland windows macos macos_objc2 android ios harmony wasm mobile; do
  grep -c "fn dpi_scale_factor" / "fn ime_bridge" / "fn accessibility_bridge" <backend>
  grep -A8 "fn capabilities" <backend>      # 读它自己声明的值

```

| 后端 | `dpi_scale_factor` | `ime_bridge` | `accessibility_bridge` | 声明 | 结论 |
|---|---|---|---|---|---|
| linux | ✅ | ✅ | ✅ | dpi=条件, ime/acc=true | **诚实** |
| wayland | ✅ | ❌ | ❌ | dpi/ime/acc=true | **谎报 2 项** ← 本轮新发现 |
| windows | ✅ | ✅ | ✅ | 全 true | 诚实 |
| macos | ❌ | ✅ | ✅ | dpi=false, ime/acc=true | 诚实（上一轮已修） |
| macos_objc2 | ❌ | ❌ | ❌ | 全 false | 诚实（上一轮已修） |
| ios | ❌ | ❌ | ❌ | 全 false | 诚实（上一轮已修） |
| harmony | ❌ | ❌ | ❌ | 全 false | 诚实 |
| wasm | ❌ | ❌ | ❌ | 全 false | 诚实 |
| android / mobile | — | — | — | 全 false | 诚实 |

**新发现（第 7 例）：`wayland` 声明 `ime: true` / `accessibility: true`，两个方法都没覆写。**
它之所以活到最后，恰恰因为**它旁边有一个诚实的 flag**——`dpi_scale_factor()` 真的读了
`GDK_SCALE` / `QT_SCALE_FACTOR` / `RUST_WIDGETS_DPI_SCALE`。**一个诚实项旁边的两个谎报，
读起来像是“这个后端查过了”。** 而 `native_menu: false` 旁边还写着一段理由充分的注释，
更加强了这种错觉。

修复时保留 `dpi_scaling: true`（有真实测量，原则 #37 划线在“值不是取来的”，不在“取得不够直接”），
只把两个无方法支撑的改为 `false`，并把理由写清。

### 6.2 第 8 例——也是更大的一例：`typed_widget_trigger` 在 4 个后端是空头支票

矩阵顺带暴露了一个此前没人看的地方。`typed_widget_trigger` 是**唯一一个 trait 默认就是 `true`**
的 flag，理由是“它由库实现，不由宿主实现”——这个理由对“能力为何能存在”成立，
对“**这个后端接线了没有**”不成立。它其实是两行对共享队列的转发：

```
for f in linux wayland windows macos macos_objc2 android ios harmony wasm mobile; do
  grep -c "fn poll_widget_trigger_event\|fn inject_widget_trigger_event\|fn poll_widget_triggered"
done
# linux=0  macos=0  macos_objc2=0  wasm=0        ← 四个声明 true 却一行没写
# wayland=3 windows=3 android=3 ios=3 harmony=3 mobile=3   ← 六个写了
```

**这四个后端都持有 `BackendState`**（共享队列就在里面），只是从没转发。
而且**可达**：`NativeControlBackend::poll_widget_trigger_event` 直接转发到
`get_platform()`（`control_backend/native.rs:243`），
所以在 GTK / cocoa / objc2 桌面上注入一个 trigger，API 会接收然后**悄悄丢掉**——
正是 trait 文档说自己要避免的 “reported success for something that did not happen”。

**修复**：四个后端各补两行转发（`poll_widget_trigger_event` / `inject_widget_trigger_event`
→ `self.state.*`），外加 `poll_widget_triggered` 从 typed 视图派生，保证“一个队列两个视图”。
与 `harmony` / `android` / `ios` / `wayland` / `windows` / `mobile` 已有的写法完全一致，
所以队列实现仍然只有一份。

### 6.3 把这一类变成门禁：`tools/check_capability_flags_match_their_methods.{py,sh}`

**为什么必须写门禁**：这个缺陷类**六次都是靠人眼发现的**，每次都是碰巧。
它没有编译错误、没有失败测试、没有运行期症状——直到宿主去用那个 bit。
所以本轮停止逐个修，改为让第 7 次不可能发生。

**门禁做什么**：对每个定义了 `capabilities()` 的后端，从源码读出每个 flag 的**字面拼写**，
与“同一文件里是否定义了它承诺的方法”对账：

| flag | 承诺的方法 |
|---|---|
| `ime` | `ime_bridge` |
| `accessibility` | `accessibility_bridge` |
| `native_menu` | `create_menu_bar` 等 5 个中任一 |
| `typed_widget_trigger` | `poll_widget_trigger_event` / `inject_widget_trigger_event` |
| `dpi_scaling` | `dpi_scale_factor` |

外加一条元检查 `check_every_backend_is_listed`：**任何新出现的、定义了 `capabilities()`
却既不在 `BACKENDS` 也不在豁免名单里的文件会让门禁失败**——
手维护名单的典型失效模式（新后端静默逃过检查）被堵住。

**这一轮门禁自己也被推翻过一次（记下来）**：第一版额外把 `dpi_scaling: true` 这个**字面量**
判为“伪造值”。它立刻报了 `windows` 和 `wayland` —— 而这两个**都是诚实的**：
Windows 真的调 `GetDeviceCaps(LOGPIXELSX)/96.0`，Wayland 真的读环境变量。
那条规则会**要求正确代码改写来迎合门禁**，正是“门禁在断言修复的拼写而不是修复本身”。

## 7. 第五批：把「声明了却没有实现」这个**形态**本身门禁化

### 7.1 `supports_surfaces()` —— 与 flag 同形的第二处（已通过，顺势纳入门禁）

`supports_surfaces()` 是「声明有 X」→「承诺 `mount_surface` 存在」的**同一个形态**，
而且**这个缺陷已经真的发生过一次**：`wasm` 报 `true` 却没有 `mount_surface`（第 104 轮修）。

全后端对账（`supports_surfaces` 值 ⟺ 是否定义 `mount_surface`）：

```
linux true/1  wayland true/1  windows true/1  macos true/1  macos_objc2 true/1
android true/1  ios true/1  harmony true/1  mobile true/1  wasm false/0
```

**现已全部自洽**。把这条检查加进门禁 `SUPPORTS_CLAIMS`，
并**验证它能复现原始缺陷**——把 wasm 的 `supports_surfaces` 改回 `true`（删掉 `mount_surface` 的前提），
门禁报出：

```
wasm: answers `supports_surfaces()` with `true` but defines none of ('mount_surface',)
      — the trait documents the flag as reportable only once the method is implemented,
      and a host that trusts it builds a UI it cannot display
```

### 7.2 `DesktopBackend` —— 一个**零消费者**的公开枚举（已删除）

`grep -rn "DesktopBackend::" src/ bindings/` → **0 命中**。全仓只有两处引用：
它自己的定义，和 `lib.rs` 里把 `pub use` 它导出的那一行。

它不是契约，是一个**看起来像**契约的类型。而且它是**错的**——
四个变体 `Win32 / Cocoa / Gtk / HarmonyDesktop` 既不覆盖 `wayland`，也不覆盖 `macos-objc2`，
而这两个都是本 crate 真的在发布的桌面后端。信它的调用方会静默漏掉两个后端。

对照它的孪生 `MobileBackend`：后者是**真契约**——
`MobilePlatformExtension::mobile_backend()` 的返回值，`runtime.rs` match 它来选
`android-mobile` / `ios-mobile` / `harmony-mobile`。所以只删前者，留下后者，
并在后者的 doc 里写清为什么没有 `DesktopBackend`。

**真正回答「这是哪个桌面后端」的是 `Platform::backend_name()`** —— 每个后端都实现它，
能力矩阵和 `runtime_gui_mode_for` 也已经在用它。一个与权威来源重复的枚举是「一个事实两个来源」
（原则 #54），而这个已经漂移了。

### 7.3 `text_scale()` —— 文档承诺了三个平台设置，代码一个都没实现

```rust
/// A backend answers this from its own platform's setting — Android's `fontScale`,
/// iOS's `UIContentSizeCategory`, Windows' text-scaling percentage.
fn text_scale(&self) -> f32 { 1.0 }
```

取证：`grep -rn "fn text_scale" src/` → **没有任何后端覆写**（只有 `types.rs` 的默认、
`profile.rs` 的访问器、以及若干测试 provider）。所以每个后端都返回 `1.0`。

**代码是诚实的**（`1.0` = “本后端不报告偏好”，`profile::text_scale()` 把它 clamp 到 `1.0..=3.0`）；
**文档是不诚实的**——它把三个平台设置列成已实现。
一个读者想确认“这个后端尊重系统字号偏好么”，读完会得出“三个平台都尊重”的结论。

修复：文档改为陈述事实（**目前没有任何后端覆写**），并补上每端实现它需要什么
（Windows 读系统文本缩放比例、iOS 读 `UIContentSizeCategory`、Android 读 `Configuration.fontScale`）。

## 11. 「能实现但未实现」：托管宿主**无法把触摸送进控件**（已实现）

用户要求把能实现但未实现的尽快完成。先建"未实现"清单，再逐条判定**能否在无对应主机时诚实地实现**。

### 11.1 取证：文档写了宿主必须调用的函数，**四条都不存在**

```
grep -rnE "⬜|Not wired" src/platform/*/status.md
src/platform/android/status.md:72  | Input delivery into widgets | ⬜ Not wired | the Activity must forward ... into dispatch_pointer_event |
src/platform/ios/status.md:54      | **Input delivery into widgets** | ⬜ Not wired | the host must forward its touch/key events |
docs/plans/harmony_integration.md  | 步骤 4 ... ArkTS 的触摸/按键回调 → rw_dispatch_pointer_event(id, ...) |

grep -rn "rw_dispatch_pointer_event" src/ include/     # 修复前
（空）
```

**三份集成文档都要求宿主调用 `rw_dispatch_pointer_event`，而这个符号在 `binding_impl.rs`
和 `include/rw_generated.h` 里都不存在。**

后果不是"少一个便利函数"：桌面三后端的点击由库在自己的消息循环里路由
（`windows/types.rs` 的窗口过程、`linux/platform_impl.rs` 的 GTK 处理器），
而**掌控自己事件循环的宿主（ArkUI / Android Activity / iOS 触摸 / 浏览器页面）永远不会被回调**。
没有这个入口，`mount_surface` 之后的控件**可见但完全不可交互**——文档描述的集成步骤，
在整条调用链上没有任何一层实现它。

另外确认了这一层确实完全没有宿主侧输入 API：`lib.rs` 无 `pub fn dispatch*`，
`app::WindowHandle` 无 input 相关方法，C ABI 无任何 `*event*`/`pointer`/`touch`/`key` 转发入口。

### 11.2 实现（三个层次，一层不缺）

**Rust 层**（`src/lib.rs`）——新增 4 个函数（含 `mini` 分支）：

| 函数 | 作用 |
|---|---|
| `dispatch_pointer_event(root, event, point)` | 命中测试后路由；宿主不必知道点到了哪个控件 |
| `dispatch_event(widget_id, event)` | 直接投递，不走命中测试（宿主已知目标时用） |

**C ABI 层**（`src/bindings/binding_impl.rs`）——正是宿主实际调用的那一层：

| 符号 | 说明 |
|---|---|
| `rw_dispatch_pointer_event(root, event_code, x, y, button)` | 事件码 `1` press / `2` release / `3` move / `4` enter / `5` leave |
| `rw_dispatch_event_to_widget(widget_id, event_code, x, y, button)` | 同一套事件码，直接投递 |

**未知事件码返回 `false`，而不是"当作 move 处理"。** 这一点是刻意的：
把无法识别的事件降级成 move 是最"安全"的默认，**也是最坏的**——
一个把 press 写错成 `0` 的宿主，会让每次点击静默变成悬停：控件高亮、永不激活，而且**没有任何报错**。
所以编码器返回 `Option<Event>`，调用方对 `None` 明确拒绝。

**生成头文件**：`include/rw_generated.h` 增加两行声明；README 计数 140 → **142**。

### 11.3 把符号加入 `check_abi.sh` 的必需清单

光有实现不够——它必须**不会再消失**。`tools/check_abi.sh` 的必需符号列表加入
`rw_dispatch_pointer_event` / `rw_dispatch_event_to_widget`，
并在文件头写明原因（"三份文档要求调用、而它们直到 2026-09-30 才存在"）。

### 11.4 回归测试：断言**端到端往返**，而不是"返回了 true"

`a_host_can_deliver_a_pointer_event_through_the_c_abi`

```
创建窗口 → 经 C ABI 创建按钮 → 订阅 BaseWidget::clicked 信号
  未知事件码      → false（拒绝，而非降级为 move）
  move 命中控件   → true
  press 在控件外  → false（越界必须如实上报，不能静默丢弃）
  press 内 + release 外 → 计数仍为 0（取消而非激活）
  press 内 + release 内 → 计数恰为 1（激活一次）
  直接投递        → 到达；未知码仍拒绝
```

**反向验证**（把路由器改成"命中测试后丢弃事件、返回 true"，即"报成功但什么也没做"）：

```

（恢复实现后）test result: ok. 6429 passed
```

**这条测试本身错了两次，都记在注释里**——两次都是**我的断言写错，而不是实现错**：

1. 第一次断言"点击会推入 platform trigger 队列"。**不会**：真实点击让控件发出**自己的
   `clicked` 信号**，那个队列装的是**宿主注入**的 trigger（这也是 `SurfaceHandle::on_click`
   文档里"widget emits its own signals rather than a platform click callback"的依据）。
2. 第二次断言"控件外的 release 也会被投递给捕获者"。**不会**：`Button::press` 只设自己的
   `grabbed` 标志（用于画成按下态），**从不调用 `capture_pointer`**，所以 `capturing_widget()`
   是 `None`，release 与其它事件一样走命中测试。

两次都说明同一件事：**在断言之前先把机制查清楚**，否则测试会去"修"正确的行为。
