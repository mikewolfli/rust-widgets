## 2. 🔴 头条 A：一次属性写入 abort 宿主进程（`f32::clamp` 边界）

### 2.1 取证（修复前的实测输出）

```
$ cat /tmp/rwprobe/src/main.rs # 走公开 API，与 JSON / C ABI 同一条路
let factory = WidgetFactory::new_with_defaults();
let mut w = factory.create("cupertino_slider", Rect::new(0,0,200,40), "").unwrap();
println!("max before = {:?}", factory.read_property(w.as_ref(), "max"));
factory.write_property(w.as_mut(), "min", CapabilityValue::Float(3.5))

$ cargo run --quiet
created; kind=CupertinoSlider
max before = Ok(Float(1.0))

thread 'main' panicked at core/src/num/f32.rs:1566:9:
min > max, or either was NaN. min = 3.5, max = 1.0
```

### 2.2 为什么这是**必然**而非极端

`cupertino_slider` 的构造值是 `(min, max) = (0.0, 1.0)`，而 `min` 是
`PropertySchema::new("min", Float, true, true)`（可写），`set_min` 的文档明确写
"re-applying the clamp to the current value"。因此**两个文档化的公开调用按任意顺序
执行**就会 abort。参数顺序不是 GUI 库可以附加的前置条件。

### 2.3 同类模式（冰山法则）：13 处，不是 1 处

`grep` 出所有「界限来自两个**可变字段**」的 clamp 点，逐个确认不是常量界限：

| 控件 | 文件 |
|---|---|
| `cupertino_slider` | `cupertino/core.rs` |
| `lcd_number` | `display_widgets/lcd_number.rs` |
| `meter`（3 处） | `display_widgets/meter.rs` |
| `scroll_bar`（2 处） | `display_widgets/scrollbar.rs` |
| `arc`（2 处） | `display_widgets/arc.rs` |
| `slider`（3 处） | `display_widgets/slider.rs` |
| `progress_bar` | `display_widgets/progressbar.rs` |
| `progress_dialog` | `dialog/progress_dialog.rs` |
| `stepper` | `container_widgets/stepper.rs` |
| `spin_box` | `input_widgets/spinbox.rs` |
| `dial` | `advanced_widgets/dial.rs` |
| `range_slider`（6 处） | `input_widgets/range_slider.rs` |
| `VideoEngine::seek` | `video/engine.rs`（`duration` 是 **public 字段**，容器解析失败可为 `NaN`） |

### 2.4 修复：单一接缝 `src/widget/numeric.rs`

不逐个控件写 `if min > max { swap }`（14 份会漂移），而是新增
`src/widget/numeric.rs`，提供 `ordered_clamp` / `_f64` / `_i32` / `_u32` / `_usize`：

- 把界限当作**无序的一对**，取小者为下界 → 交叉界限得到夹紧值而非 panic；
- 任一边界为 `NaN` 时**忽略该边界**（`NaN` 不是区间端点）；两边都是 `NaN` 时原样返回；
- 声明顺序下与 `std::f64::clamp` **逐位一致**（有测试钉住），因此对正确调用者是
 零行为变更的 drop-in 替换。

### 2.5 定点证据（修复后）

```

$ cargo test --no-default-features --features desktop --lib cupertino
running 57 tests ... test result: ok. 57 passed

$ cargo test --no-default-features --features desktop --lib widget::numeric
running 6 tests ... test result: ok. 6 passed
```

### 2.6 反向注入验证（原则 #12）

把 `cupertino_slider` 的 `ordered_clamp` 改回 `.clamp`：


## 3. 🔴 头条 B：Apple 四后端探针接错内核 → 全线返回 `None`

### 3.1 取证（修复前，本机 macOS 实测）

```
$ cargo run --quiet # 探针直接调用 Platform trait
backend=cocoa
family=Desktop
total_memory_mb=None
is_on_battery=false
process_memory_utilization=None
process_cpu_utilization=None
```

四后端（`macos/`、`macos_objc2/`、`ios/`、`mobile.rs`）的四个探针**全部**转发到
`crate::platform::os_probes`。该模块的模块文档自己写明：

> Linux-kernel system probes shared by every `/proc`- and `/sys`-based backend.

它解析 `/proc/meminfo`、`/sys/class/power_supply`、`/proc/self/status`。
**Apple 内核不挂载这三个文件**，于是每次查询都走 `ok()?`/`let Ok(..) else` 的
降级分支，返回 `None`/`false`。

### 3.2 为什么长期无人发现

因为 `None` 和 `false` 是**合法返回值**。`Platform::total_memory_mb` 的文档甚至
主动要求「必须把 `None` 当作未知，绝不允许用 `4096` 这类编造值替代」——于是
「诚实返回 None」与「探针接错内核所以永远 None」在**返回值上不可区分**，
没有任何断言会失败。而 trait 的同一份文档又承诺 macOS 走 `sysctl hw.memsize`、
进程内存走 `ps`——**文档与代码相反**（原则 #18）。

### 3.3 修复：新增 `src/platform/darwin_probes.rs`

按内核分层，与 `os_probes`（Linux 内核）并列：

| 函数 | 实现 | 依据 |
|---|---|---|
| `total_memory_mb` | `sysconf(_SC_PHYS_PAGES) × _SC_PAGESIZE` | 与 `sysctl hw.memsize` 同量同义，且无需额外 FFI 绑定 |
| `is_on_battery` | `pmset -g batt` 是否含 `'Battery Power'` | 系统自带；`'AC Power'`（台式机）与 Linux 空目录同答 `false` |
| `process_memory_utilization` | `ps -o rss=,vsz= -p <pid>` | 与 Linux 的 `VmRSS/VmSize` 同义同比例 |
| `process_cpu_utilization` | 返回 `None` | macpset/ps 无稳定的一次性采样；**不编造** |

`libc` 依赖加在 `[target.'cfg(target_os = "macos")']` 与 `ios` 段（**非 optional**：
无条件编译的探针挂在 optional 依赖上就是下一次编译错误的种子）。

### 3.4 定点证据（修复后，同一探针）

```
backend=cocoa
total_memory_mb=Some(16384) # ← 之前是 None
is_on_battery=true # ← 之前是恒 false（本机确实在用电池）
process_memory_utilization=Some(1.2663635e-5) # ← 之前是 None
process_cpu_utilization=None # 诚实：无稳定来源
```

16 GiB / 电池状态 / RSS 比例均为**真实测量值**，非编造。

### 3.5 新增测试（防回归）

`src/platform/darwin_probes_tests.rs`，5 条，**全部钉住"测量值"而非"无 panic"**：

| 测试 | 断言 |
|---|---|
| `total_memory_is_measured_and_plausible` | 返回 `Some`，且在 256 MiB–4 TiB 之间 |
| `process_memory_utilization_is_a_fraction` | 返回 `Some`，且在 `(0, 1]` |
| `battery_answer_matches_the_pmset_banner` | 重新跑 `pmset` 并要求探针与横幅**一致**（不假设本机电源状态） |
| `ps_selector_is_bsd_spelled` | `["-o", "rss=,vsz="]` 且 `ps` 输出的首个 token 可解析为数字 |
| `parse_error_message_names_the_offending_output` | 失败信息含原始输出与期望字段名 |

第 3 条的写法值得说明：它不硬编码 `true`/`false`（那会让测试依赖本机是否笔记本），
而是**重新执行文档化的命令并比对**——钉住「答案来自 `pmset`」这一契约。

## 5. 🔴 WASM 后端谎报能力，且门禁结构上抓不到

### 5.1 取证

`src/platform/wasm/platform_impl.rs` 原为：

```rust
fn family(&self) -> PlatformFamily {
 PlatformFamily::Desktop
}
```

`capabilities()` 未覆写，于是走 `types.rs` 的默认实现——**该默认按 family 推导每个
flag**，`Desktop` 得到四个 `true`。运行时实测：

```
family=Desktop
capabilities=PlatformCapabilities { dpi_scaling: true, ime: true, accessibility: true,
 native_menu: true, typed_widget_trigger: true }
```

而 `README.md:232` 一直印着：

```
| **Web (WASM)** | `wasm-state-backend` | Embedded | ❌ | ❌ | ❌ | ❌ | ❌ |
```

即：**文档说没有，代码说有**。且同族的另一个无主机后端 `portable/mod.rs:134` 明确
写着 `FAMILY = Embedded` 并附理由「报告 Desktop 会让自适应代码为无法兑现的主机选择
桌面默认值」——wasm 恰好做了它警告的事。

### 5.2 为什么门禁没抓到（根因，比缺陷本身更重要）

`src/docs_paths_tests.rs` 的 `published_os_capability_matrix_matches_the_trait_default`
**从不构造任何后端**。它把 README 声明的 family 喂给
`default_capabilities_for(family)` 造一个**合成结构**，再拿它和 README 比对：

> 把声明当作自己的期望值 —— 这种断言**在结构上无法被证伪**。

所以 README 的 `Embedded` 一行被原样回喂，测试永远通过。

### 5.3 修复（两层）

**(a) 后端说真话**：`family()` → `Embedded`，并**显式覆写** `capabilities()` 给出四个
`false`。显式而非继承，是为了让未来改动 `default_capabilities_for` 不能悄悄重新授予
浏览器没有的能力。

**(b) 门禁通过构造真后端来验证**：新增
`documented_matrix_matches_real_backends`，**真的 `Box::new(...)` 构造本机可构造的
每个后端**，调用 `capabilities()`/`family()`，与按 `backend_name()` 索引的 README 行
逐字段比对；无法构造的后端（别的 OS / feature 关掉）按名字跳过，并断言**至少构造到
一个**，使「什么都没检查」不可能通过。

### 5.4 反向注入验证（证明新门禁真的有效）

把 wasm 的 `family()` 改回 `Desktop`：

```

```

```

```

## 6. 🔴 跨目标门控收束：让「门控放底层」名副其实

第 3 节的探针修复引入了新的门控需求，本轮把门控**收敛到最底层并统一依据**：

### 6.1 发现的门控不一致（逐个实测）

| 模块 | 原门控 | 问题 |
|---|---|---|
| `platform/ios/platform_impl.rs` | 无（`ios/mod.rs` 无条件声明） | Apple 探针在非 Apple 目标上编译 → OpenHarmony `mini` 3 个 E0433 |
| `platform/ios/types.rs` | 无 | 与 `platform_impl` 分离后成为孤儿 → 5 个 `never constructed/read` warning |
| `platform/macos_objc2/` | `feature = "macos"\|"cocoa-legacy"` | 在 Windows 目标上仍编译 → 3 个 E0433 |
| `platform/mobile.rs` 探针 | 直连 `darwin_probes` | Windows/OHOS 上 E0433 |

### 6.2 处置：**门控下沉到探针模块**，调用方零 `cfg`

这是本轮对原则 #36「OS 相关逻辑落到底层」的具体落实。做法：

1. `darwin_probes` 自身 `#[cfg(target_vendor = "apple")]` —— 依据是**内核**（Darwin），
 不是 OS 列表；
2. `ios/{platform_impl,types}` 同样按 `target_vendor = "apple"` 门控，
 与 `darwin_probes` **同一个判据**（不再出现第二套条件表达式）；
3. `platform/types.rs` 新增 **运行时无关的三对分发函数**，
 把「本机内核选哪个探针」这件事收在一处：

```rust
pub(crate) fn host_memory_probe() -> Option<u64> {
 #[cfg(target_vendor = "apple")]
 { crate::platform::darwin_probes::total_memory_mb() }
 #[cfg(not(target_vendor = "apple"))]
 { crate::platform::os_probes::total_memory_mb() }
}
```

`mobile.rs`（Android 适配器，却要在任意宿主上编译以便单测）只调 `host_*_probe()`，
**自身一个 `cfg` 都没有**。`macos_objc2` 加 `target_vendor = "apple"` 与其
`platform_impl` 的探针依赖对齐，并在模块文档中写明代价：

> Known trade-off: this means the module's own state-machine unit tests do not run on
> a non-Apple host. That is the honest cost of the probe change.

（不隐瞒：这是用「非 Apple 宿主上不跑状态机单测」换「探针正确」。）

### 6.3 定点证据：四目标 × 五 profile 全部 0 error / 0 warning

| target | desktop | tablet | mobile | mini | embedded |
|---|---|---|---|---|---|
| host（aarch64-apple-darwin） | ✅ | ✅ | ✅ | ✅ | ✅ |
| `aarch64-apple-ios` | — | — | ✅ | ✅ | — |
| `x86_64-pc-windows-gnu` | ✅ | — | ✅ | ✅ | ✅ |
| `aarch64-unknown-linux-ohos` | (见下注) | — | ✅ | ✅ | ✅ |
| `wasm32-unknown-unknown` | — | — | — | — | ✅ |

> **注**：OHOS 的 `desktop` 失败于 `minimp3-sys` 的 `'stdlib.h' file not found`——
> 交叉 sysroot 缺 C 头文件，属**环境**问题（与前一轮记录一致），不是本仓库代码缺陷；
> 同一 target 的 `mobile`/`mini`/`embedded` 均通过，说明门控本身是对的。

### 6.4 顺带修掉的两处

- **`tests/zz_audit_probe_test.rs`**：上一轮遗留的探针文件，文件头自己写着
 `Throwaway audit probe. DELETE ME.`，且 `use rust_widgets::menu_config::...` 未加
 feature 门控 → `mini`/`embedded` 构建直接失败。其覆盖的
 `UserOverrides` 七字段 round-trip **在 crate 内确无等价测试**（`tests.rs` 只测
 setter 与钳制），因此不是删除而是**升格**为
 `menu_config::tests::persistence_round_trips_every_user_override`（含 `clear()`
 真的删文件），再删原文件。
- **Windows `has_print_support`**：原实现 `Command::new("cmd").args(["/C", "print /? 2>NUL"])`
 并以 `status.success()` 判定。两个问题：`print` 是 `cmd` **内建**不是可执行文件，
 `2>NUL` 是 `cmd` 方言重定向；更重要的是**在外层进程里问自己的事**——`spawn_print_job`
 走 `Start-Process -Verb Print`，那是**本进程**的环境解析的动词，问子 `cmd` 答的是
 子进程的事实。改为 `windows_shell_spawnable()`：测**能否 spawn**
 （原则 #38 的判据），与 unix 侧 `unix_print_clients_available` 同一规则。

## 7. 🟠 控件 `enabled` 契约：不可交互的外观必须跟上

### 7.1 先修正取证范围（诚实记录）

子代理报「147/187 控件 `draw` 忽略 `enabled`」。复核后：

```
$ for f in $(grep -rln "impl Draw for" src/widget/ --include=*.rs); do
 grep -q "is_enabled()" "$f" || echo "$f"; done | wc -l
32
```

且这 32 个里多数是**容器/图表/装饰件**（`divider`、`line`、`safe_area`、
`masonry_layout`、`qr_code`、7 个 finance 图表……），对它们而言「禁用」没有可交互
语义，外观不变是**正确**的。子代理把「未引用 `is_enabled()`」等同于「本应引用」。
**按原则 #19 记录为误报，并把范围重新界定为「接受输入却不管 enabled」的控件。**

### 7.2 重新界定后确证的缺陷

以 `cupertino_segmented_control` 为最清晰样本：

```rust
// handle_event：完全没有 enabled 检查
Event::MouseRelease { pos, button } => {
 if *button != 1 || self.segments.is_empty() { return; }
 ...
 if index < self.segments.len() && index != self.selected_index {
 self.selected_index = index;
 self.value_changed.emit(index); // ← 禁用状态下仍然发射
 }
}
```

即 `set_enabled(false)` **对该控件完全无效**：点击照收、选中照改、信号照发。
而 `LineEdit`/`Slider`/`MessageBox` 都先查 `is_enabled()`——所以这是**不一致**，
不是有意策略。绘画侧同样固定用 `Color::WHITE` / 固定灰，禁用外观不可辨。

### 13.1 🔴 `negotiate_capability_contract` 的 fallback 编造全 true 契约

与 §5 的 WASM 属**同一类**（合成值冒充能力），但更隐蔽：

```rust
// src/platform/contract.rs（修复前）
fn fallback_native_capability_contract() -> NativeCapabilityContract {
 NativeCapabilityContract { dpi_scaling: true, ime: true, accessibility: true,
 native_menu: true, typed_widget_trigger: true }
}
```

关键在于 `native_capability_contract()` 的实现：

```rust
fn native_capability_contract(&self) -> Option<NativeCapabilityContract> {
 if matches!(self.family(), PlatformFamily::Desktop) { Some(self.capabilities()) }
 else { None } // ← 非 Desktop 永远 None
}
```

即：**能走到 fallback 的只可能是非桌面后端**，而 fallback 告诉它「你有 DPI 缩放、
IME、无障碍树和原生菜单」。这个 fallback 不是默认值，而是一个**与其自身检查相反的断言**。

**修复**：改为 `default_capabilities_for(family)` —— family 是后端总会报告的事实，
也是 `capabilities()` 默认实现所依据的那一个。`mini`（`alloc_frugal`，无运行时后端）
同理改为 `default_capabilities_for(Embedded)`。

**反向注入验证**（关键 —— 第一版测试是无效的）：

第一版测试断言的是 `default_capabilities_for(...)` 本身，也就是**修复所使用的同一个函数**，
所以把修复撤掉它照样通过。重写为通过 `with_platform()` 装入**真实的非桌面 StubPlatform**，
再调用**真正的入口** `negotiate_capability_contract(Full)`：

### 13.2 🔴 `macos_objc2` 的 `supports_surfaces()` 与 cocoa 后端不一致

`macos_objc2` 完全没有实现 `mount_surface` / `resize_surface` / `unmount_surface` /
`invalidate_surface` / `supports_surfaces` 五个方法，于是继承 trait 默认的 `false`；
而 `macos/platform_impl.rs` 把同一个方法覆写为 `true`。两者由同一个
`macos_bridge::SelectedMacOSPlatform` 按 **feature flag** 二选一 —— 宿主不控制那个 flag。

后果：宿主在构建 UI 前询问 `supports_surfaces()`，可能因为链接的是 objc2 后端而被回答
「本后端无法显示任何东西」，而**同一台机器**上的 cocoa 后端回答「可以」。

**修复**：实现全部五个方法（复用 `BackendState` 的 surface 记录，与 android/harmony
后端同构），并新增测试把两个后端的答案钉成同一个。

```
$ # 注入缺陷（supports_surfaces -> false）
test objc2_surface_contract_matches_the_cocoa_backend ... FAILED
 this backend paints every WidgetKind itself, so it must advertise surfaces
$ # 恢复
test objc2_surface_contract_matches_the_cocoa_backend ... ok
```

测试不止断言布尔值，而是一路跑完 mount → resize → invalidate → unmount，并断言
**第二次 unmount 返回 false**（「报告如实缺失」而不是永远成功）。

用户实测报出：

```text
warning: ignoring test `view_platform_gate_probe` as
 `tools/view_platform_gate_probe.rs` is not included in the published package
```

### 根因

`Cargo.toml` 同时做了两件互相矛盾的事：

1. 用显式 `[[test]]` 声明一个 **crate 外部**的目标：

```toml
[[test]]
name = "view_platform_gate_probe"
path = "tools/view_platform_gate_probe.rs" # 在 tools/，不在 tests/
```

2. 用显式 `include` 白名单打包，而其中**只列了 `tools/widget_gallery.rs`**：

```toml
include = [ "build.rs", "src/**/*", "tests/**/*", ... ,
 "tools/widget_gallery.rs", # ← 只有这一个 tools/ 文件
 "LICENSE", "README.md", ... ]
```

于是 `tools/view_platform_gate_probe.rs` 被两头夹掉：既不在 `tests/`（自动发现不会覆盖它），
也不在 `include` 白名单里。

### 为何危害远大于一条警告

声明了却不在包里的目标，对**从发布包构建的人根本不存在**：

- `cargo test` 静默地少跑一个 test target，消费者无从得知少了一个门禁；
- 从 `include` 里删掉一行**不产生任何编译错误**，因此这个漂移在有人读到警告之前不可见；
- 而 `tools/view_platform_gate_probe.rs` 本身是 `check_view_platform_gate.sh` 的探针，
 它“被静默删掉”正好会让那个门禁的覆盖变成空头支票。

### 修复（两层）

**(a) 让它真的进包**：`include` 新增该文件，并在 `Cargo.toml` 里写明**为何** `tools/` 下恰好这两个
文件要进包（因为它们是**被声明的 Cargo 目标**），其余 `tools/` 继续排除（门禁与生成器不属于
crate 的构建面）。

```text
$ cargo package --allow-dirty --no-verify 2>&1 | grep -ciE 'warning|ignoring test'
0
$ cargo package --allow-dirty # 完整打包 + 验证构建
 Packaged 696 files, 11.4MiB (2.5MiB compressed)
 Verifying rust_widgets v2.4.5
 Finished `dev` profile ... in 13.05s
```

**(b) 新增门禁堵住整类**（根因修复，不只修这一例）：
`tools/check_declared_targets_ship.sh` 直接比对两个事实——
`Cargo.toml` 里所有显式 `path = "..."` 目标 **对比** `cargo package --list` 的实际文件清单。

它不跑完整的 `cargo package`（那会编译 tarball），只用 `--list`，并经 `rw_run_bounded` 加上界
（原则 #58），避免卡在 index 锁上。

**反向注入验证**（证明它不是空门禁）：把 `include` 里那一行删掉——

```text
--- [4] Every declared target path must be packaged ---
 ✅ ships: examples/view_counter.rs
❌ 'tools/view_platform_gate_probe.rs' is a declared Cargo target but is NOT in the published
 package; add it to the 'include' list in Cargo.toml (otherwise 'cargo package' warns and
 consumers lose the target)
❌ check_declared_targets_ship: 1 problem(s)
```

恢复后：`✅ all 4 declared target(s) are packaged`。

### 附带核实：四个声明目标现在全部在包里

```text
SHIPS examples/view_counter.rs
SHIPS tools/view_platform_gate_probe.rs
SHIPS tools/widget_gallery.rs
SHIPS examples/embedded_host.rs
```

### 13.8 流程教训 —— 已写入原则 #58–#60

本轮的真实代价不是任何一个代码缺陷，而是**流程缺陷**：我用无超时的手写 for 循环跑 30 个门禁，
脚本卡死后连续多轮毫无进展，最终由用户中断两次。

已写入 `docs/plans/principle.md`：

- **#58** 任何可能阻塞的命令都必须设超时，没有例外；未设超时的长命令视为**流程缺陷**；
- **#59** 禁止裸跑「全量门禁 + 全量测试」的长串行循环；优先定点；**禁止在循环外层套 `timeout`
 命令**（实测与脚本内部的 `rw_run_bounded` 相互干扰，把 30 个全部误报失败，而单独跑均为 `exit=0`）；
 超时结果必须如实上报为「结果未知」，**不等于**失败也**不等于**通过；
- **#60** 长命令前先问「能不能做更小的等价验证」，先跑最能暴露问题的那一格。

本轮实际采用的正是 #60：4 次窄验证（`cargo check` 单 profile、单门禁 `--filter`、
单个 `cargo test <filter>`）就拿到了全部所需证据，没有一次是全矩阵跑。

## 14. 下一轮建议方向（尚未穷尽）

按原则「连续 2 轮无新发现才终止」，本轮为第 1+2 轮，**仍有新发现，未达终止条件**。
已修完扫出的全部 68 项。建议下一轮从以下未穷尽方向取证：

1. **`enabled` 契约的收尾**——`ime_preedit`、`qr_code`、`badge` 等仍无 `enabled` 检查，
 需逐个判定「禁用是否有语义」后决定修或**在模块文档写明为何不适用**（原则 #51）。
 建议顺便加一条**门禁**：枚举所有处理输入事件的控件，要求每个要么引用 `is_enabled()`，
 要么在 allowlist 中并附理由。
2. **语言绑定（Python/Node/C++）与 130 个 `rw_*` 的逐参数契约**——本轮只验了头文件重新生成
 后**无漂移**（130 声明 / 8 value kind），每个函数的参数个数与所有权尚未逐个比对。
3. **`events:` 声明与控件真实发射点的三方对齐**——capability 声明的每个事件名是否都有真实
 发射点，尚未逐名核对。
4. **Android/HarmonyOS 的原生探针**——目前 Android 的内存/电量走 `/proc`（其内核确实是
 Linux，故**正确**），但按 Android 平台惯例应走 JNI `ActivityManager`/`BatteryManager`；
 需先取证 `/proc` 在 Android 10+ 的 SELinux 策略下是否仍可读。
5. **`demo/`、`examples/`、`cookbook/` 三语言版本的可编译性**——本轮只做了静态审阅。
6. **其余主机门限门禁的实跑**——`check_apple_native` 本轮已实跑通过（本机 macOS）；
 `check_harmony_cross` 因未装 `cargo ohos` 子命令而未跑，需按脚本提示安装后实跑。
