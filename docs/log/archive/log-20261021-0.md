## 2. feedback-20261020 逐项复核

### 2.1 §0.1 embedded 编译回归（闭环）

**修复前（2.8.11）**：`create_tab_widget`/`create_splitter`/`create_grid_widget`/`create_dialog`
用 `#[cfg(not(alloc_frugal))]` 门控，而 `WidgetKind::{TabWidget,Splitter,Grid,Dialog}`
用 `#[cfg(widgets_unstripped)]` 门控；embedded 两个条件一真一假，出现四个 `E0599`。

**2.8.12 的修复**：四个构造器改为 `#[cfg(widgets_unstripped)]`，与变体同一谓词（原则 #47）。

**本轮实测（macOS aarch64）**：

```text
mobile:   Finished `dev` profile [unoptimized + debuginfo]

```

命令：`cargo check --no-default-features --features <profile> --lib`（原则 #48：不带默认
`desktop`）。§0.1 在 macOS 上不再复现。

### 2.2 §0.2 GTK 键码 / §0.3 GTK 双击（代码复核）

本机是 macOS，无法复跑 GTK。源码证据：

- `src/platform/linux/canvas.rs:667` `pub(crate) fn logical_key(keyval: u32, control_chord: bool) -> u32`；
  非打印键在平台边界规范化为框架键码（Return/Escape/Backspace/Delete/方向键/Home/End/Page/F1–F12）。
- `src/platform/linux/canvas.rs:124-138` `DoubleClickTracker` 按 GTK 的
  `gtk_double_click_time` / `gtk_double_click_distance`（`:769`/`:773`）合成
  `Event::mouse_double_click(...)`，不再把双击当成两次普通按下。

结论：2.8.12 的实现位置与反馈请求一致；**运行证据仍属于 Linux 宿主**（`log-20261020-4.md`）。

### 2.3 §0.4 `create_widget_of_kind` 返回 0（代码复核 + 宿主边界）

`src/lib.rs:1353-1381`：当 `!supports_surfaces()` 时，**先**走
`control_backend::get_control_backend().mount_widget_box(...)`，并在非 Window kind 且父 id
未挂载时显式返回 0。surface 路径只在 `supports_surfaces()` 为真时执行。两条创建路径的成功
判据因此一致。

**本机边界**：macOS legacy 后端 `supports_surfaces()` 为 `true`（
`src/platform/macos/platform_impl.rs:155`），而 `mount_surface` 需要 the platform UI framework 主线程。`cargo test`
的工作线程不是主线程，所以用 `create_widget_of_kind` 做运行断言会得到 0；这验证的是宿主
限制，不是缺陷。按原则 #103 记录为 host-limited，没有写成通过，也没有伪造测试。

### 2.4 §0.5 / §3.3 失效区域与缩放重绘（代码复核）

- macOS：`src/platform/macos/canvas.rs:984 window_canvas_for` 先由控件/窗口解析 host window，
  再查 `window_canvases`；`invalidate_surface_impl`（`:1171`）对它 `setNeedsDisplay:`。
- Linux：`src/platform/linux/types.rs:90 window_painters` 在
  `src/platform/linux/platform_impl.rs:1340` 写入、`:773` 删除，`invalidate_surface` 读取它。
- `Resized` 分支（`src/app/handle.rs:1216`）重跑布局后显式请求重绘，不再依赖指针事件。

## 3. Tab 系列：一次只显示一个 panel

### 3.1 设计基准：a native toolkit 的 notebook

参考 `~/Desktop/workspace/native-toolkit-source/src/notebook.cpp`：

- `gtk_notebook_insert_page(notebook, win->m_widget, pageData->m_box, position)`（`:524`）把每个
  页面放进同一个 notebook；
- `gtk_notebook_set_current_page(...)`（`:244`）只切换当前页；非法选择回退到
  `m_oldSelection`（`:97`）。

即：**所有页面同属一个父容器，默认只激活一个，其余保持 inactive/hidden，切换只改变激活项**。
本轮按这个模型核对并修复本库。

### 3.2 发现的缺陷

1. **JSON 声明的 `tabwidget` 子节点没有成为页**（真实缺陷）。
   `src/json/loader.rs` 的 children 循环只 `instantiate_node` 并让父 id 指向 tab widget：
   - tab strip 的 `tab_count == 0`；
   - 每个子 panel 都是普通可见子控件，全部画在同一个矩形上——正是用户描述的
     “一个 panel 里同时展示所有子 panel”。
   另外 `current_index` 在构造时应用，那时候还没有页，写入被 `TabWidget::set_current_index`
   合法地忽略。
2. **`Tab` 的页字段可绕过容器模型**：`tab_mut().set_widget(...)` 只改字段，不链入/不放置/不隐藏。
3. **移除/替换页后旧页仍标记为 visible**：`remove_tab`、`set_tab_widget` 只解除父子链。
4. **移除/插入导致索引偏移时不发信号**：订阅者按索引寻址会指向相邻页。
5. **`tab_rect` 每调用一次就重跑整套 flex 布局**：draw 与命中测试按 tab 数循环，呈 O(n²)。

### 3.3 修复

- `src/json/loader.rs`：`tabwidget` 的直接 `children` 逐个 `TabWidget::add_tab(title, Some(id))`；
  标题取 `title` → `text` → `id` → 控件类型；页全部创建完后再应用 `current_index`。
- `TabWidget::set_tab_widget(index, Option<ObjectId>)`：解链旧页并隐藏、链入新页、`sync_pages`
  （当前页填充内容区，其余隐藏）。
- `remove_tab` / `insert_tab`：索引变化时 `current_changed.emit(new_index)`；删除页时隐藏它。
- `TabWidget::tab_rects()`：一次 `tab_run()` 得到全部矩形；draw、命中测试、`tab_rect`
  都从这一个结果读取。原 `tab_rect` 的坐标推导原样保留（含 West/East 的 y 轴放置）。
- `sync_pages`/`place_current_page` 去掉 `#[cfg(not(alloc_frugal))]` 空实现——该模块只在
  `widgets_unstripped` 下编译，门控本来就是死条件（原则 #5/#47）。
- `TabView` 保持“内容由控件自己拥有，只画选中页”；补 `tab_count` 属性（见 §4.1）。

**TabView 的边界**：`TabPage::content` 是 `Box<dyn Widget>`，控件拥有它，因此
“把所有页作为树子节点、只显示一个”在 TabView 上表现为“只绘制选中页”，其余页不进入本帧。
若宿主使用 registry 路径，则只对 `content_widget_id()` 这一个 id 绘制/转发；不会绘制未选中页。
这与 a native toolkit 的可见结果一致，但实现机制不同（值拥有 vs 树子节点），已在模块文档与本日志写明。

## 4. 高级 / 组合控件扫描

扫描范围：`src/widget/advanced_widgets/**`、`src/widget/container_widgets/**`、
`src/widget/nav_widgets/**`、`src/widget/dialog/**`、`src/widget/composite.rs`。

### 4.1 属性契约缺口

| 控件 | 缺口 | 处理 |
|---|---|---|
| `TabWidget` | `set_tab_shape` 存在、JSON 读取 `tab_shape`，但 `WidgetProperties` 无 `get`/`set` 臂，schema 也没有该行；命令表无 `set_tab_shape` | 加 `get`/`set`/`property_names`/`TAB_WIDGET_PROPERTIES`/commands；token 为 `rounded|triangular|rectangular`，非法 token 返回 `OutOfRange` |
| `TabView` | `tab_count()` 方法存在，schema/属性层没有 | 加只读 `tab_count`（与 TabWidget/TabBar 一致） |
| `TabWidget`/`StackedWidget` | 删除/替换页后旧页 `visible` 仍为 true | 见 §4.2 |

`tab_shape` 默认值加入 `capability/access.rs`（`"rounded"`），使
`schema_defaults_are_readable_and_writable_when_declared` 通过。

**审计结论（不改）**：`TabBar` 的 `set_tab_text`/`set_tab_shape`/`set_tab_position`/`set_tab_enabled`
是按**单个 tab** 操作的内容方法，`TabBar` 的 schema 明确发布的是 `tab_count/current_index/
closable/movable/tab_min_width/tab_max_width/direction`；两者不是同一个粒度，强行把每个 item
方法提升为控件属性会造出第二条索引语义（原则 #101）。`TabWidget` 的 `set_tab_shape` 不同：
它是**整个控件**的形状，本来就该是属性，所以补的是它。

**单测**（`src/widget/container_widgets/tabwidget.rs`）：

```text
tabwidget_shape_round_trips_through_the_property_contract
  names 包含 tab_shape
  set "triangular" -> TabShape::Triangular
  get == "triangular"
  set "Rounded" -> Err，形状保持 Triangular

tabwidget_remove_tab_announces_the_index_shift
  current 2，remove(0) -> current 1，current_changed 收到 1
```

### 4.2 移除/替换内容仍可见（冰山法则）

发现的是一类问题，不是一个点：容器解除父子链，但没有清 `visible`。树遍历从根不可达时它
不会画，但**按 id 渲染的宿主**仍会把它画在新内容之上；模型也会回答
`is_widget_visible == true`，与“已不是内容”矛盾。

修复位置（旧内容隐藏，新内容显示）：

| 文件 | 方法 |
|---|---|
| `base_widgets/frame.rs` | `set_widget` |
| `container_widgets/dockwidget.rs` | `set_widget` |
| `container_widgets/scrollarea.rs` | `set_widget` |
| `container_widgets/splitter.rs` | `add_pane` / `remove_pane` |
| `container_widgets/stackedwidget.rs` | `remove_widget` |
| `container_widgets/toolbox.rs` | `remove_item` / `clear` |
| `container_widgets/mdiarea.rs` | `remove_sub_window` |
| `dialog/dialog_widget.rs` | `set_content_widget` |
| `dialog/popup_window.rs` | `set_content_widget` |
| `container_widgets/tabwidget.rs` | `remove_tab` / `set_tab_widget` |

`mini` 没有 widget runtime，`frame.rs`/`scrollarea.rs` 的调用点显式
`#[cfg(not(alloc_frugal))]`，避免引用不存在的 `crate::set_widget_visible`（这是本轮把
`mini` 从 5 个错误修回通过的原因）。

**反向验证**：`a_tab_widget_replaces_a_page_without_leaving_the_old_one_visible` 在未清
`visible` 时失败于 `the old page is hidden`；加入 `set_widget_visible(old, false)` 后通过。

## 5. 性能：全局 + 局部

### 5.1 基线（release，本机 Apple Silicon）

`cargo bench --bench render_bench -- --quick`：

```text
render_frame_tree 1280x800 9-widget tree   2.5784 ms
render_frame_tree 1280x800 100-widget tree 14.567 ms
```

单控件探针（临时测试，release）：

```text
resolved_theme_style      2.525 µs/call
draw_text_fitted         78.934 µs/call
measure_text              1.724 µs/call
shape_text                1.720 µs/call
single Button frame      88.902 µs/call（含 register）
clear+alloc 1280x800      1.057 ms/call
```

根因排序（实测，不是推测）：

1. **矢量字形每帧重新光栅化**：`VectorSource::paint_in_face` 每次分配
   `cell × SUBSAMPLES(8)` 的 winding scratch 并跑一遍轮廓填充，没有任何 coverage 缓存。
   一个两字符标签 ≈ 79µs，几乎是按钮绘制成本的全部。
2. **每帧每控件解析主题**：`resolved_theme_style` 每次拿全局 manager 互斥锁、分类 role、
   重建 `WidgetStyle`（含 `Font` 的堆 `String`）。
3. **文本测量/整形重复**：`draw_text_fitted` 先 `measure_text`（内部整形）→ 再
   `measure_text(fitted)` → `draw_text` 再整形；同样内容每帧 3 次。
4. **每条文本两条堆分配**：`RenderContext::draw_text` 为每个标签构造
   `RenderCommand::DrawText { text: String, font: Font }`，软件后端立即吃掉命令、不保留。
5. **每个字形一次 coverage 分配**：`draw_text` 内 `vec![0u8; max_cell]`。
6. **窗口每次 expose 全树重画**：macOS `drawRect:` 调 `render_frame_tree`，无上一帧缓存。
7. **TabWidget O(n²)**：`tab_rect(i)` 每次重建 flex 布局；draw/命中都按 tab 循环。

### 5.2 改动

| 位置 | 改动 | 不变式 |
|---|---|---|
| `render/text/raster.rs` | 线程局部 coverage 缓存（键：face 字节地址 + char + cell），512 项 FIFO；命中直接 memcpy | coverage 只依赖 face/字符/设备 cell；配色与位置无关 |
| `theme/manager.rs` | 线程局部 resolved-style 缓存（256 项）+ 全局 `THEME_REVISION`；所有 mutation 入口 bump revision | revision 不一致即视为 miss，漏 invalidation 不会返回旧样式 |
| `render/pipeline/containers.rs` | `measure_text` 缓存（2048 项，双 64 位指纹键）；`shape_text` 缓存（512 项） | 键含 family/size/weight/bold/italic/letter/word/line-height/scale；runtime font 变更 bump `TEXT_METRICS_EPOCH` |
| `render/pipeline/primitives.rs` | `draw_text` 只整形一次；复用 surface 上的 coverage scratch | 宽度 = `shaped.advance().round()`，行高 = `TextMetrics::for_font`，与原值一致 |
| `render/backend/paint.rs` | 新增 `PaintBackend::draw_text` 借用入口；软件后端直接绘制 | 默认实现仍是旧的 owning command，录屏/延迟后端不变 |
| `render/backend/surface.rs` | `RenderContext::draw_text` 改走借用入口 | 不再为每条文本分配 `String`+`Font` |
| `widget/runtime.rs` | `render_frame_tree_cached` + 线程局部 `TreeFrameEpoch` | 内容 epoch 不变则直接返回上一帧；绘制期间的自请求归入下一帧 |
| `platform/macos/canvas.rs` | 窗口 `drawRect:` 改用 `render_frame_tree_cached` | surface 路径仍用 `render_frame_cached` |
| `container_widgets/tabwidget.rs` | `tab_rects()` 一次求解 | 绘制/命中/几何同一结果 |

缓存失效点：

- `mark_dirty_rect`、`request_repaint_because`：bump 窗口内容 epoch（每次 `request_redraw`
  与属性写都会经过）。
- `ThemeManager::{set_high_contrast, register_theme, set_theme}`：bump theme revision。
- `runtime_fonts::{register_face, clear_faces}`：bump text measurement epoch。

### 5.4 剩余固定成本（未计入这次收益，也不藏）

1280×800 的一帧仍有约 1.1ms 的固定成本：`SoftwarePaintBackend::new` 分配 front+back 各 4MB，
`begin_frame` 再填 4MB。9 控件树从 2.58ms 只降到 1.94ms，就是因为它被这部分主导。
`render_frame_tree_cached` 在“无内容变化”的 expose 上完全跳过它（直接返回上一帧字节）；
真正变化的帧仍要支付。进一步优化需要复用 surface 或把 clear 限制在 damage 区间，属于下一轮，
本轮没有用“看起来更快”的近似替代正确性。

## 9. 未覆盖 / 边界

1. **GTK/X11 运行**：§0.2/§0.3 只做源码复核；双击/键码的真实 X11 证据仍是 Linux 宿主的
   `log-20261020-4.md`。
2. **Windows 交叉**：本机 `cc` 交叉编译 `minimp3-sys` 时找不到 MSVC 的 `stdlib.h`；
   `xwin` 头文件未在本 shell 配置。按原则 #103 记为 host-limited，没有改代码绕过。

   工作线程无法为 §0.4/§0.5 提供运行断言。宿主真实窗口证据见既有日志。
4. **`audit_theme_tokens.py` 超时**（>5 分钟，本机未完成）；不把超时写成通过。
5. **23 个既有 `#[ignore]`**：本轮未新增、未删除、未把它们算入完成率；其目标仍存在。
6. **剩余性能固定成本**：见 §5.4；本轮没有为了数字去复用 surface 或跳过 clear。
7. **TabView 机制差异**：页面由控件拥有而非树子节点；可见结果一致（只画一个），但“按 id
