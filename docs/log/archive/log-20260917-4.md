### 2.3 🔴 我自己引入的一个真实回归（被构建门禁抓到）

**教训（本轮经验）**：批量删除带 `#[cfg]` 的项时，**必须逐档构建验证**。

### 3.2 缺口二：滑动翻页缺「速度」判据

`blue17.md:263` 原文要求「位移阈值 **+ 速度**」，实现只有位移
（修复前 `grep -n "velocity|speed|Instant" carousel.rs` → **0 命中**）。

**修复设计（本轮判断选择，用户要求 5）**：

| 判断项 | 选择 | 理由 / 反例 |
|---|---|---|
| 时间源 | `std::time::Instant` | `SystemTime` 会被 NTP 回调产生负速度；`instant` crate 会新增依赖 |
| 采样点 | 每次 `MouseMove` 记 `last_x`+`last_moved_at` | 用整段手势总时长会把「快─停」误判为慢 |
| 速度函数 | `now` **由调用方传入**（纯函数） | 内部 `elapsed()` 会让测试必须 `sleep` 才能断言 |
| 击发阈值 | 400 px/s | 约等于手机上每秒 1/4 屏宽；更低会与点击手抖重叠 |
| 反抖动下限 | 宽度的 2% | 一帧内几像素抖动可算出极大瞬时速度 |
| 上限 | **10 × 宽度/秒** | 见 §3.3 |
| 判定顺序 | **先距离，后速度** | 距离达标者永远翻页；速度规则只**增加**可识别的甩动 |

### 3.3 🔍 一次被自己的测试推翻的取值（取证过程保留）

初版上限写成「1 × 宽度/秒」，测试立即失败：

```
100px in 250ms must read as 400px/s, got 300
```

**根因**：300px 宽控件上，上限 300px/s **低于** 400px/s 的击发阈值 ——
即**上限把真实甩动钳到了阈值之下，速度规则永远不可能触发**。这是设计错误，不只是测试写错。

**修正**为 10 × 宽度/秒，并补一条**直接断言两常量序关系**的回归测试：

```rust
assert!(real_flick >= FLICK_VELOCITY_PX_PER_SEC, "…must not be capped below it");
```

**教训**：凡引入两个相互比较的常量，必须有一条测试**直接断言这个序关系**，
否则改任一个都会静默失效。

### 5.1 E′-1 `tools/check_view_platform_gate.sh`

**判据必须是可执行的，不能是 grep**。原因写进脚本：

> grep 构建日志里的 `src/view` 也会匹配到无关诊断里的路径；grep `src/lib.rs` 的
> `cfg` 文本只证明文本在，不证明它有预期效果。

所以判据是**名字解析**：编译一个 `use rust_widgets::view::VIEW_GATE_PROBE;` 的探针 ——
能解析 ⟺ 模块在编译单元里。

**探针为什么带 `cfg` 守卫**：一个无条件的 `use` 会让 `mini`/`embedded` 的
`--all-targets` 构建在**本该没有该模块**的档位上失败，即门禁自己制造它要检测的故障。
所以提交版本用与库相同的表达式守卫导入；门禁运行时写入一份**强制无条件导入**的临时副本，
读完退出码后再恢复（`EXIT` trap 保证崩溃也不残留）。

### 5.2 🔴 E′-5 反向注入 —— 门禁第一次**没有 FAIL**（关键取证）

按计划把 `src/lib.rs:117` 改成 `#[cfg(any(desktop, tablet, mobile))]`（漏掉 `widgets_unstripped`），
预期门禁 FAIL。**实测：门禁仍然 PASS。**

**为什么**（本次实测得出的结论，写入脚本注释）：

| 档位 | `any(desktop,tablet,mobile)` | `all(any(…), widgets_unstripped)` |
|---|---|---|
| `desktop` / `tablet` / `mobile` | true | true（设备档永不 stripped） |
| `mini` / `embedded` | **false**（这两个档不含设备 feature） | false |
| `desktop,mini` 混合（规则 #48 禁止） | true | **false** ← 唯一差异 |

**即：在所有合法单档构建上，两种写法行为完全相同；差异只出现在规则 #48 明令禁止的混合档。**
所以**纯行为探针无法区分它们**，只有行为的门禁就是一个**不可能失败的门禁** ——
这正是 E′-5 要排除的失效模式。

**修复**：门禁增加**第 [4] 步源码判据**，断言 `pub mod view` 的 cfg 仍含 `widgets_unstripped`
与三个设备 profile，并在注释里**如实说明它是源码检查、不是行为证明**：

> 它不声称证明运行时行为，因为它保护的行为在合法构建上不可观测。
> 与 [1]–[3]（在**可观测**处证明表达式效果正确）互为盲区覆盖。

## 6. BLUE18 Phase E / F — 门禁与闭环

### 6.1 E-1 `tools/check_view_keys_are_unique.{py,sh}`（规则 #88）

`src/view/node.rs:124` **已经引用了**这个门禁名，但工具不存在（G8，属原则 #91 同类问题）。

**为什么静态检查**：`View::build` 是任意函数，会按状态分支，一次运行只走到它走到的分支。
**跑一遍并遍历输出，对未走到的分支什么也证明不了** —— 只在空列表分支里重复的 key
能通过每个测试，却仍会在生产里破坏身份。

**实现要点（含两次自我修正）**：

|---|---|---|
| v1 | 「扫描到下一个 `;`」把相邻语句并成一条链，130+ 误报 | 改为按语法跟随 `.method(..)` 调用 |
| v2 | 一个链内部的 `.child()` 嵌套本是**不同兄弟集**，却被当成一个 | 记录为已知局限；对**验证重复检测本身**的 3 个测试加显式豁免表（附理由） |

「`Binding<T>` 的监听器**驱动** `update`」，而初版测试只是**计数通知**、然后**手动**调 `update` ——
这证明了「引擎能写属性」，但**没有**证明「监听器驱动更新」。按原则 #13（禁止不完整修复）已补全。

**真正实现** —— 新增 `src/view/reactive.rs`（`ReactiveHost`），解决一个**契约矛盾**：

| 类型 | trait 约束 | 原因 |
|---|---|---|
| `BindingListener` | **必须 `Send`** | binding 可被工作线程 set |
| `ViewEngine` + 所有控件 | **`!Send`** | `widget::runtime` 注册表是 thread-local（控件持有 GPU/OS 资源） |

「订阅一个持有引擎的闭包」**不可能同时满足两者**。这不是要绕开的限制，而是契约本身，
它点名了唯一正确的形状：

```text
 worker 线程 UI 线程
 ──────────── ────────
 binding.set(v)
 └─ 监听器触发 ──队列──▶ host.pump()
 └─ view.build()
 └─ diff → apply （碰控件）
```

**为什么用队列而不是原子标志**：标志会**丢失中间值** —— 一次 pump 前的两次 set 会坍缩为一次重建，
使「这次改动产生几个 patch」变成依赖时序的数字，测试与推理都不可靠。
队列保持生产者计数精确，合并变成调用方的**显式决定**而非传输层的副作用。

**为什么用 `event::queue::BlockingQueue`**：它的 `push(&self)` 在容量满时**不阻塞**，
`try_pop` 非阻塞抽取 —— 正好是「生产者永不阻塞 + UI 线程每帧排空」需要的两个操作。

**测试**（`reactive.rs` 5 条 + 端到端 2 条）：

| 测试 | 断言 |
|---|---|
| `a_worker_thread_set_reaches_the_ui_thread` | **跨线程**：`std::thread` 里 `set`，UI 线程 `pump` 后控件属性更新（用 `Barrier` 而非 `sleep`，不依赖时序） |
| `pump_conducts_one_update_per_set` | 两次 set → 两次重建；末尾状态生效 |
| `the_queue_preserves_the_producer_count` | 5 次 set → 5 次重建（队列不坍缩） |
| `a_closed_or_full_queue_still_counts_the_notification` | 能区分「已观测但未应用」与「从未观测」 |
| `a_binding_set_queues_and_pump_applies_it` | 无变更时 `pump()` 返回 0 |
| `binding_set_reaches_the_live_control_through_the_view_engine` | `set("second")` 后**真实控件**的 `text` 为 `"second"`（经 `ReactiveHost`，非手动 `update`） |
| `a_binding_driven_update_keeps_the_unchanged_control_identity` | 两次文本更新后父子 `ObjectId` **不变**，`replaced_subtrees == 0` |

**为什么断言不分步（计划 F-2 的明确要求）**：分步断言（先查监听器触发、再查产生了 patch、
再查属性变化）会把测试强度花在中间步骤上，可被逐个满足 —— 例如「监听器触发」为真而写入仍被拒。
断言落在**终态**，中间值进失败信息。

## 13. 追加轮：命名边界 + 门控收敛 + 文档重写

### 13.1 `rw_` 前缀收敛到 ABI 边界（用户提问「是否全仓库简写」）

**结论：不统一简写。** `rw_` 是 **C ABI 的命名空间前缀**，不是本库的缩写。取证：

| 位置 | `rw_` 数量 | 性质 |
|---|---|---|
| `src/bindings/binding_impl.rs` | 117 | ✅ C ABI 本体 —— C 是扁平全局命名空间，前缀**必需** |
| JNI 绑定 | 59 | ✅ 调同一 ABI |
| `src/` 其余 | 38 处 token | 分类见下 |

那 38 处里绝大多数是**正确的**：文档注释引用 ABI 函数名（如
「reachable through `rw_widget_property_names`」）、测试临时路径前缀
（`/tmp/rw_spool_probe_*`，其目的就是不易撞名）。

**真正的问题只有一处**：`src/platform/windows/types.rs` 的 `rw_wnd_proc` ——
一个内部 Win32 回调借用了 ABI 前缀。已改名为 `wnd_proc`（3 处引用同步）。

**为什么不给全部 Rust API 加前缀**（逐一否决）：

| 若这做 | 后果 |
|---|---|
| 改 crate 名 `rust_widgets` → `rw` | `Cargo.toml` 的 `name` 与 `use` 路径是同一标识符，无法只改一处；已发布到 crates.io，等于破坏全部下游（原则 #21）；且 `.rs` 472 处 + `.md` 1360 处 |
| 给 1576 个 `pub struct` 加 `Rw` 前缀 | `WidgetKind::RwButton`、`impl RwWidget`…… 是 C 风格而非 Rust 风格（原则 #28：不为「看起来像 LVGL」而引入负担） |

**新增门禁** `tools/check_rw_prefix_is_abi_only.sh`，3 项断言：
① `src/bindings/` 之外不得出现 `rw_*` 的**定义**（`fn`/`struct`/`const`…）；
② ABI 导出（`#[no_mangle]`/`#[export_name]`）只允许在 `src/bindings/` 与 JNI 桥；
③ 豁免名单不得陈腐（若 `RwError` 被改名，必须同步删除豁免）。

**判据为何是「定义位置」而非「每个 token」**：初版写「`src/bindings/` 外禁止任何 `rw_`」
→ **38 命中，其中 34 处是正确写法**。一份 34 条的豁免名单没人会读，
等于把门禁豁免到失效。

**豁免（写进脚本并附理由）**：`RwError`/`RwResult` —— 已在 `api-reference.md` 作为
文档化声明出现、35 个调用点，改名属破坏性变更换一个命名偏好，不值得。

**反向注入**：把 `ReactiveHost::pump` 改名为 `rw_pump` → `EXIT=1`（报出
`src/view/reactive.rs:123`）→ 恢复后 `EXIT=0`。
**交叉验证**：`cargo check --target x86_64-pc-windows-gnu --lib` → `Finished`（改名未坏 Windows 档）。

### 13.2 门控从「手写合取」收敛为「单个别名」（用户要求 2：不要繁琐）

`build.rs` 新增 3 个别名，全部手写的设备档合取消失：

| 新增别名 | 条件 | 替换掉的写法 |
|---|---|---|
| `device_profile` | `desktop\|tablet\|mobile` | `any(feature = "desktop", feature = "tablet", feature = "mobile")` ×4 |
| `desktop_surface` | `desktop && !embedded` | `all(not(embedded_surface), feature = "desktop")` 及其取反 ×**各 5 次** |
| `declarative_view` | `full_widgets && !no-declarative-view` | 新的视图层门控 |

其中 `desktop_surface` 最刺眼：同一串 15 个 token 的合取**出现 10 次**（5 对 if/else，
用于挑选 `WidgetKind`）。

**同时把已存在的 `full_widgets` 用在应当用的地方**：
`src/lib.rs` 的 `pub mod json` 与 `pub mod app` 原本手写同一串合取，现为 `#[cfg(full_widgets)]`。

**验证**：`src/` 中此类冗长合取 `grep` → **0 命中**；5 档构建全部 `Finished`。

### 13.3 声明式层新增「默认编译 + 可选关闭」门控（用户要求）

新增 Cargo feature **`no-declarative-view`**（opt-out）：

```bash
cargo build --no-default-features --features desktop,no-declarative-view
```

**为何是 opt-out 而非 opt-in**：Cargo 的 feature 列表无法表达「默认开、除非点名」；
写成 opt-in 会迫使**所有现有调用方**追加一个 feature 才能保持现状 ——
对一个今天已经可用的能力来说，那是破坏性变更。

**`build.rs` 的 `rerun-if-env-changed` 必须包含 `NO_DECLARATIVE_VIEW`**：
该脚本把它转成 `rustc-cfg`，漏掉的话在已构建的树上开关该 feature 会复用缓存的别名，
看起来「毫无效果」。

**门禁扩为 5 步 / 12 项断言**（新增第 [2] 步三档关闭态、第 [5] 步别名判据）：

```
[1] 三档默认编译 ✅✅✅ [4] 无 profile 档不编译 ✅
[2] 三档 opt-out 后不编译 ✅✅✅ [5] 门控用单个别名 + build.rs 定义 + 开关接入 ✅✅✅
[3] mini/embedded 不编译 ✅✅
```

**反向注入**：把门控改回 `all(any(desktop,tablet,mobile), widgets_unstripped)`（丢掉 opt-out）
→ **4 项 FAILED**（三档关闭态 + 别名判据）→ 恢复后 `EXIT=0`。

**受影响的下游已同步到同一别名**：`tests/view_data_binding_closure_test.rs`
（原用 `#![cfg(feature = "desktop")]`，会在 tablet/mobile 上跳过）、
`examples/view_counter.rs`、`tools/view_platform_gate_probe.rs`
（原手写同一合取 —— 探针与它要探测的代码不能各写一份）。

| `DepthChart` | 控件 | 累积深度曲线。阶梯函数而非平滑线：某价位的数量在该价位是常量，插值会画出并不存在的数量 |
| `OrderBook` | 控件 | 盘口五档。两侧均按「最优价优先」排序，不信任 feed 到达顺序 |
| `QuoteBoard` | 控件 | 行情表。`QuoteSort::None` 还原**调用方**顺序，而非把上次排序结果倒置 |
| `IndicatorChart` | 控件 | 振荡指标面板。6 种模式，有界模式用**固定** `0..=100` 轴（否则 70 线会随窗口移动，「超买」含义每次都变） |
| `finance::indicators` | **纯函数** | 15 个指标：`sma`/`ema`/`wilder_smooth`/`rsi`/`macd`/`bollinger_bands`/`stochastic`/`atr`/`trailing_extremes`/`donchian_channel`/`vwap`/`money_flow_index`/`on_balance_volume`/`series_extent`/`has_drawable_values`/`align_left` |
| `finance::types` | 数据模型 | `Bar`/`PriceSeries`/`BookLevel`/`OrderBook`/`Quote`/`PriceLine` |
| `finance::layout` | 几何 | `IndexAxis`/`PriceAxis`/`PlotArea` —— 多面板共享一套映射，对齐是算术而非约定 |

**指标为什么不做成控件**：一条均线没有几何、没有状态、没有平台调用。
做成控件要多 15 个 `WidgetKind`、15 个 capability、15 个 constructors，且每个都无法脱离窗口测试。
做成函数则算术可单测（53 条测试），而绘制在消费它的图表里只实现一次 —— 这正是 #24 的含义。

### 15.4 本轮发现并修复的真实缺陷（原则 #2 冰山法则）

**（1）`view_platform_gate_probe.rs` 被提交成了「强制版」** —— 这是**先前就存在**的缺陷，
我的 `WidgetKind` 变更只是让它显形。取证方式：`git stash` 后干净树上复跑，**同样失败**。

- 现象：`cargo check --no-targets --features mini --all-targets` 永久失败，
 `check_profiles.sh` 第 5、6 步（mini/embedded）报 `unresolved import rust_widgets::view`
- 根因：`tools/check_view_platform_gate.sh` 的注释写明「committed probe `cfg`-gates its import
 so that a normal `--all-targets` build stays green」，但**提交的文件里没有 `cfg`** ——
 是某次门禁运行被中断（`trap` 未执行）把重写后的强制版留下了
- 危害：读起来像源码缺陷，实则是残留物；且**该门禁自身永远无法通过**
- 修复：按注释恢复 `cfg(declarative_view)` 门控，并补一条 `#[cfg(not(...))]` 测试，
 使「谁再去掉这个 cfg」会在 mini/embedded 上失败而不是让 crate 编译不过
- 验证：`check_profiles.sh` 从「9 步中 2 步失败」变为 **9/9 全过**

**（2）`check_platform_capability_matrix.py` 的总数句自欺** ——
原句 `Total widgets: {len(WIDGETS)} (matches {len(WIDGETS)} WidgetKind variants)`
在「行集恰好等于变体数」时才成立。9 个 `WebEngine*` 是**包装类型**而非 kind
（`tests/blue9_r6_platform_capability_test.rs` 明确记录），所以该句只是碰巧为真。
改为同时说明两个数字。

> 过程中我一度误删了这 9 行，`widget_kind_variants_are_exhaustive` 立刻报错并**指出正确做法**
> ——`WebEnginePage is excused as a WebEngine wrapper but has no matrix row; if it was
> deleted, drop it from WEB_ENGINE_WRAPPERS too`。我按提示**回滚了删除**并改用正确修法。
> 这正是「门禁必须能失败」的价值：它挡住了我的错误修改。

**（3）4 处文档 `WidgetKind` 计数过期**（169 vs 175），由 `check_widget_kind_count.sh` 抓到。

**（4）3 个属性契约缺口**，每个由不同门禁指名：
- `every_factory_widget_declares_a_property_contract` → 6 个控件无 `WidgetProperties`，
 每次属性读写都返回 `UnsupportedOnWidget`
- `published_enum_tokens_are_accepted_by_their_control` → schema 公布的 token
 控件自己的 parser 不接受（如 `volume_chart.color_mode`），即「公布了没人能写的值」
- `schema_defaults_are_readable_and_writable_when_declared` → 声明了默认值却读不出来

修复后删掉了一个自相矛盾的属性：`rising_color` 声明可读可写，但**永不接受写入**
（颜色是 crate 级常量，与其他面板共享）。一个永远写不进去的东西不是属性，
是带 getter 的常量 —— 于是移除，而不是留着骗人。
