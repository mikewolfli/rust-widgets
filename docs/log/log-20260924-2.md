## 1. 批 0 收口 —— `check_elevation_is_not_one_value` 是**假红**（一个门禁缺陷）

### 1.1 症状

```text
$ bash tools/check_elevation_is_not_one_value.sh
[1/3] the resolution path exists and is addressable
[2/3] the resolution path does not bake one shadow for every control
  FAIL  role_base_style builds a Shadow literal instead of reading a level:
          6:        // This used to build one `Shadow { x: 0, y: 2, blur: 6, .. }` and hand it to every
```

**报告的第 6 行是被报告者自己的注释。** 代码在第 344 行读的是
`theme.elevation(surface.elevation, Color::BLACK)`，逐字满足门禁想断言的事实。

### 1.2 根因（两条，都在门禁的抽取器里）

```bash
BODY="$(awk '/fn role_base_style/{inside=1} inside{print} inside && /^    }$/ && NR>1 {if (seen) exit; seen=1}' "$MANAGER")"
```

1. 模式是 `fn role_base_style`，**没有行首锚点**。`resolve_base_style` 的 rustdoc
   里写了「This was a **second, byte-for-byte copy** of `role_base_style` …」，
   命中就在那里 —— 抽取从真正的 `fn` **上方约 30 行**开始，于是注释、别的函数全部被吞进 `BODY`。
2. 抽取到第一个 `    }` 就退出，而它因为起点错位，退出点也发生在真正的函数**之前**。

**这是一个「测量工具缺陷」而不是代码缺陷**，与 log-20260924-1.md §46 记的
「66 个不读主题文件」同源 —— 我把这一类正式命名为：

> **门禁读到自己的解释，是最难发现的假红形态**：它永远无法被修绿，
> 因为让它变红的那段文字正是记录「它为什么存在」的那段文字。

### 1.3 修法（**三处**，缺一不可）

| # | 修什么 | 为什么 |
|---|---|---|
| 1 | 抽取模式加行首锚点 `^    fn role_base_style` | 只在签名处开始，不再命中 rustdoc |
| 2 | 抽取后校验首行**确是**签名 | 起点错位从「静默错误」变为「显式 FAIL」，不留模糊 |
| 3 | 匹配前 `sed 's://.*::'` 去掉行注释 | 门禁检查**活代码**，注释里引用旧字面量是文档，不是缺陷 |

同时给脚本补了一段说明为什么注释要被剥离，避免后人「好心」去掉它。

### 1.4 验证（**两个方向都做**，原则 #2 冰山法则）

```text

（零命中）
```

即计划 §0A.1 取证 1 的判据**仍然成立**：`tick_animations` 有定义、有调用它的
`has_animating_widgets`，而**没有任何宿主会去排那一帧**。

### 2.2 改了什么（一处新增，九处接线）

**新增：`src/widget/runtime.rs` 的 `drive_frame` + `FrameOutcome`。**

```rust
pub struct FrameOutcome {
    pub events_dispatched: usize,
    pub controls_ticked: usize,
    pub repaints_submitted: usize,
    pub needs_another_frame: bool,
}

pub fn drive_frame(delta_ms: u32) -> FrameOutcome {
    let events_dispatched = crate::drain_triggers();   // 步 1：输入先落地
    tick_animations(delta_ms);                          // 步 2：恰好推进一次
    let controls_ticked = count_animating_widgets();
    let needs_another_frame = animation_bus_needs_another_frame();  // 步 3
    FrameOutcome { events_dispatched, controls_ticked,
                   repaints_submitted: take_frame_repaint_count(),
                   needs_another_frame }
}
```

**顺序的三条理由写进了 rustdoc**，而且每条都不能换（计划 §1.2 的理由逐条落地）：

1. **排空输入** —— 动画的目标值来自状态，状态来自事件。反过来的话，本帧的 hover
   要等下一帧才动。
2. **显式推进一次** —— 放在绘制之前，所以本帧画的是推进后的状态。
3. **汇报是否还需要下一帧** —— 取值在 1–2 **之后**，于是「观察到沉降的那一帧」报
   `true`（沉降要被画一次），「其后那一帧」报 `false`（空闲窗口停止付费）。
   这一条是「丝滑不以耗电换」的全部机制。

**`repaints_submitted` 是「记账」而不是「在这里提交」**：脏区在**被发现的地方**提交
（`request_repaint` / `mark_dirty_rect` / 平台原生重绘），否则一个控件帧内重绘要等到下一帧。
所以驱动者只**统计**本帧已发生的提交。计数点**只有一个**：`mark_dirty_rect` 的
`if recorded` 分支与 `request_repaint` 的 `if invalidate_surface(..)` 分支 ——
**不是**包在公共入口上（那会把脏区臂计两次，这是一个我在写的时候先想错、再改对的地方）。

**接线：九个平台循环，一处一改（只改「谁拥有时钟」这件事）。**

| 后端 | 现在 | 改为 |
|---|---|---|
| Linux `gtk-native` | `timeout_add_local(16ms, drain_triggers)` | 同一定时器改调 `drive_frame(16)`，闭包仍返 `Continue` |
| Linux 无 GTK | `while running { sleep(16) }`（**空循环**） | `while running { drive_frame(16); sleep(16) }` |
| macOS | `NSTimer` 回调 `drain_triggers()` | 同一回调改调 `drive_frame(16)`；间隔改用同一个常量 |
| Windows | 消息泵后 `drain_triggers()` | 同一位置改调 `drive_frame(16)` |
| Wayland | 协议派发后 `drain_triggers()`，另有 session-less 臂与 pump 回调 | 三处都改调 `drive_frame(16)` |
| Android / iOS / Harmony / wasm | `while running { drain_triggers(); sleep(16/10) }` | 同上，改调 `drive_frame(16)` |

每个后端新增一个 `const FRAME_INTERVAL_MS`，理由写在常量上：**sleep 长度与交给
`drive_frame` 的 delta 必须同一个数**，否则每个过渡按两者的**比值**运行，而没有任何东西会发现。
Linux 无 GTK 的臂原来是一句 `thread::sleep(16)` —— 一次什么都不做的唤醒 ——
现在它真的推进帧，这正是 §1 判据 5「屏幕上真的动了」的端到端前提。

### 2.3 我没有做的一件事，以及为什么（比做了什么更重要）

**没有用 `ControlFlow::Break` 在空闲时停掉 GTK 的心跳。**
看起来更省电、更像计划里那句「睡到下一个事件」，但它有一个致命副作用：
**`glib::timeout_add_local` 的闭包是这仓唯一的输入排空点**。返回 `Break` 会
连**排空**一起停掉 —— 一个静止窗口会停止收到「让它再次动起来」的事件，
即用户 hover 上去以后**永远不再有帧**。

计划对 `mini`/`embedded` 的说明（「`drive_frame` 对它们是空操作，不提供 stub」）
我遵守了：这两个 profile 没有 `widget::runtime`（`#[cfg(not(alloc_frugal))]`），
所以 `drive_frame` 在 crate 根上也是 `#[cfg(not(alloc_frugal))]` 的 re-export，
**不提供 stub** —— 与 `draw_bridge` 的同一处理。

### 2.4 新门禁：`tools/check_single_frame_driver.sh`（BLUE24 §1 判据 6）

门禁断言**两条结构性事实**，不是运行时观察：

```text
[1/3] the frame driver exists                        → runtime::drive_frame 在
[2/3] the animation bus has exactly one driver       → tick_animations 的每个调用点都在 drive_frame 内
[3/3] the frame driver owns the input drain          → drain_triggers 的每个调用点都在 drive_frame 内
```

**计两份门禁的价值在于它是结构性的**：只要有一个后端自己调 `tick_animations`，
就是 §1.1 列出的「每个后端各写一个 tick」（一帧两次）那一类；只要有一个后端自己
调 `drain_triggers`，§1.2 固定的顺序就被拆成两处、无从检查谁先谁后。

## 3. 批 2 —— 属性动画：`PropertyDriver`（BLUE24 §2）

> 计划 §2.3 的三步：**原型（Button）→ 第二个（Switch/ToggleButton）→ 推广**。

### 3.1 先分析：计划要的类型和已有的 `Transition` 差在哪（**不是重写**）

计划 §2.2 把 `PropertyDriver` 写成新类型，但 §2.1 自己说「本仓需要的是后者」
（`Transition` 的形态），「把 `Transition` 的形态补全为属性驱动并让它成为唯一形态」。
所以**不是**新写一份插值，而是补上两件 `Transition` 缺的事：

| 缺什么 | `Transition` 的形态 | `PropertyDriver` 的形态 |
|---|---|---|
| **目标存哪** | `tick(target, delta)` 每次传，调用方**自己缓存** | 存在类型里，`set_target` 是唯一写入者 |
| **命名** | `TransitionTempo`（构造时配置） | `MotionSlot`（**type alias** 到 `TransitionTempo`） |

**关键决定（我推荐的方案）**：

1. **插值不重写** —— `PropertyDriver::tick` 内部构造一个 `Transition` 并转发。
   理由：仓里只有**一处**知道曲线、步长与 snap 容差（`Transition::tick` 那段
   70 行注释解释的坑），第二份实现必然漂移（原则 #101）。
2. **`MotionSlot` 是 `type alias`，不是新枚举** —— 原则 #54「同语义枚举全仓只能有一份
   定义」。计划写的是 `enum MotionSlot`，但仓里已有 `TransitionTempo` 三变体同义；
   写第二份就是引入一个必然漂移的副本。alias 同时满足计划的**名字**要求与 #54 的
   **唯一性**要求。
3. **`current` 不 clamp** —— `Transition` 会把 `progress.clamp(0,1)`，而 `PropertyDriver`
   要能表达「像素位移」（计划 §10A/§2.2 明说属性有两类：标量进度与像素位移）。
   alias 过去的 `Transition` 内部仍 clamp 其自己的字段，但 driver 的 `current` 不被压。

### 3.3 🔴 迁移暴露的一个**真缺陷**：`is_moving` 需要一个「已瞄准」的前提

而 `dismiss()` 从没 `set_target` ⇒ **`dismiss()` 之后 `is_animating()` 为 false**，

## 17. 本轮最有份量的一条：旧门禁报出了一个**新的真缺陷**

收尾把本轮涉及的 11 条门禁一起跑，其中 **`check_single_frame_driver` 变红**（其余 10 条绿）：

```text
FAIL  drain_triggers is called outside the frame driver:
        src/lib.rs:348:    FrameOutcome { events_dispatched: drain_triggers(), ..FrameOutcome::default() }
```

### 17.1 根因

`src/lib.rs` 新增了一个 `#[cfg(alloc_frugal)]` 的 `drive_frame`（`mini`/`embedded` 用），
其理由是「共享的平台循环要调一个 `drive_frame`」—— **这个理由成立**（原则 #53：能力差异是
运行时事实，不是两套签名）。但它的**实现**写了 `drain_triggers()`，而这条函数在本 crate 里
有**且仅有一个**主人：帧驱动者。

在本 profile 下 `drain_triggers()` 确实返回 `0`（无触发队列），所以行为上无害；
但**结构上**它是第二个「排空」路径，而 §1.2 固定的顺序（输入 → 推进 → 汇报）正是靠
「排空只有一处」才可检查。一个日后从这臂复制到桌面臂的人会静默引入
「一帧两次排空」—— 而那正是门禁存在的理由。

> 这是一条**教科书式的例子**：门禁的价值不在它现在绿，而在它在**别人改代码时**变成了红。
> 上游进程把「共享循环需要入口」与「入口应该排空」两件事混为一件，门禁把后者单独拎了出来。

### 17.2 修法（根因，不是绕过）

`alloc_frugal` 的 `drive_frame` 改为真正的诚实空操作：

```rust
#[cfg(alloc_frugal)]
pub fn drive_frame(_delta_ms: u32) -> FrameOutcome {
    FrameOutcome::default()   // 本 profile 无动画总线、无触发队列：每一个字段都是真话
}
```

rustdoc 里写清楚了两条理由（① 排空只有一个主人；② 本 profile 的排空本来就是 no-op，
调它会让代码「看起来做了事」而实际什么都没做——诚实比像样重要）。

**验证**：

```text
$ bash tools/check_single_frame_driver.sh
check_single_frame_driver: OK (one driver, no competing call sites)
$ cargo check --no-default-features --features mini       → Finished
$ cargo check --no-default-features --features embedded   → Finished
```

### 17.3 与本轮其余工作的关系

本轮把 §4/§3/§6/§5/§9 做到绿，而**这条红是本轮工作范围之外的**（另一进程引入）。
本轮的处置依据与 §10 一致：它是**结构缺陷**（且是「一处事实两处抄写」这一类），
修法无第二解，且它挡住了一条本轮产出的门禁的绿灯 —— 所以修，但不改任何行为语义。

本轮共享面已停稳，所以尝试了 §12 的 U-10（把 `SurfaceStyle` 的四个维度接进 `ThemeStyleToken`）。
**先取证再动手**，结果发现它比计划描述的更靠前一个问题：

```text
$ grep -rn "role_surface_style\|SurfaceStyle\|BevelSpec" src/widget/base_widgets/button.rs
（零命中）
$ grep -n "pub bevel\|pub material\|pub hairline" src/style/primitives.rs
（零命中 —— `WidgetStyle` 没有这三个字段）
```

**根因**：§10A 的类型与角色默认都在（`render/surface.rs`，测试完整），但
**控件层还没有任何消费者**——`role_base_style` 只读到了 `surface.elevation`（转成
`theme.elevation` 的阴影），`bevel` / `material` / `hairline` **没有字段可以承载**，
也没有控件去画。

所以正确的顺序是：

| 步 | 内容 | 前置 |
|---|---|---|
| §10A 第 1 步 | 类型 + 角色默认（**已在**） | — |
| **第 1.5 步（本轮发现的缺口）** | `WidgetStyle` 加三个字段 + **每个控件的 draw 读它** | 无 |
| §10A 第 2 步（U-10） | token 接线 + 两个预设 | 第 1.5 步 |

**本轮没有把 token 类型加上去**，因为那会造出**四个无读取者的字段** —— 正是本仓反复出现的
“声明了没消费者”（§A.11.2 的死状态表、BLUE23 §6.1 的 tonal palette）。加了 token 而不接
消费者，是把一个已知形态重新制造一遍（原则 #4 / #13）。所以**如实退回**并在本节登记缺口。

> 这一条的价值在于它把 U-10 的「前置」从「共享面空闲」修正为「`WidgetStyle` 有承载字段」：
> 共享面已经空了，但真正的前置是**中间那一段**（与 BLUE24 §6 的 a11y「中间缺一个泵」
> 是同一个形状 —— 两端都在，中间不在）。

## 27. U-10 第 2、3 步：`WidgetStyle.surface` 承载 + 100 个控件消费

§26 末尾登记的顺序是：① 类型与角色默认（已在）→ ② `WidgetStyle` 加字段 + 各控件 draw 读它
→ ③ token 接线 + 两个预设。本节把 ② 与 ③ 做完。

### 27.1 中间那一段：`RenderContext::face`

控件层要读 `surface`，但**不能**直接收 `&WidgetStyle` —— 每个控件的 `style()` 借用形态不同
（有的 `self.base.style()`、有的先 `let style = self.style()` 再改、有的在 `&mut self` 上），
统一传 `&WidgetStyle` 会让 100 个调用点各自和借用检查器搏斗。

所以入口取的是**解析后的值**，全部是 `Copy`：

```rust
pub fn face(&mut self, rect: Rect, fill: Color, surface: SurfaceStyle, radius: u32, shadow_tint: Color)
```

| 设计点 | 取值 | 理由 |
|---|---|---|
| 参数取「解析后的值」而非 `&WidgetStyle` | `SurfaceStyle` / `u32` / `Color` 都是 `Copy` | 避开 100 个控件各不相同的 `style` 借用差异 |
| **恒等元 = `fill_rect`** | `Elevation::Flat` + `radius 0` + `Material::Solid` ⇒ 只发一条 `FillRect` | 任何控件在「没有面声明」时画出的**与改造前逐字节相同** |
| **不画描边** | 描边留在控件里 | 描边常是**语义色**（error/hover 的强调），不是面的属性 |
| 顺序 | 阴影 → 填充 → 斜角 → 描边 | 阴影必须在面**之下**；斜角在填充**之上** |

### 27.3 反复出现的「多分支控件只读一个字段」

人工迁移时发现 `freeform_shape/shape.rs` 有**同一个绘制缺陷**的两个实例：

```rust
let rect = self.geometry();
match self.shape {
    Shape::Rectangle => self.draw_rounded_rect(context, rect, radius),  // 用了 radius
    Shape::RoundedRect { radius } => self.draw_rounded_rect(context, rect, radius), // 用了 radius
    _ => self.draw_scanline_shape(context, rect),  // 没有 radius
}
```

**这不是一个 bug，是一个形态**：`Face::Open` 被登记为「未画」，但矩形与圆角矩形**读了**
radius，只是读在了另一个分支里。逐个修会留下剩下的。所以同类的读法统一走 `context.face`，
`radius` 从 `style().border_radius` 取 —— 一处规则覆盖全部分支。

同一形态的第二个实例：`code_editor/render.rs` 的 `draw()` 开头

```rust
context.fill_rect(rect, chrome.surface);   // 编辑器主体
```

它**没有**用文档自己的 `palette`/主题色，而是用 `style.background_color` —— 说明作者**本意**
就是「这是控件的一个面」，只是当年没有 `face`。所以它也归入统一读法。

### 27.4 一个真实的判据缺陷：`radius` 传了字面量 0

人工迁移时我给 `code_editor` 的活动标签、`emoji_picker` 的标签条传了字面量 `0`，
理由是「它们是子区域不是控件的面」。**跑出来是 0 个 `rx=`** —— 于是加了临时探针：

```rust
if std::env::var("RW_FACE_PROBE").is_ok() {
    eprintln!("FACE_PROBE radius={radius} rect={rect:?} surface={surface:?}");
}
```

```
FACE_PROBE radius=0 rect=Rect { x: 6, y: 2, width: 104, height: 24 } surface=…{ elevation: Flat, … }
```

**字面量 `0` 是在替一个自造的理由说话**。同一批批处理迁移出来的 93 个控件传的都是
`self.style().border_radius.unwrap_or(0)`，只有我手写的 3 处传 `0` —— 这种不一致本身就是证据：
**一个主题声明了 `borders.radius`，它的标签页就该是圆的**。改成解析值后 `rx=` 出现，行为与
其余 97 个控件一致。探针随即删除（不留调试代码）。

> **原则 #10 的实例**：我没有先问「这个子区域该不该圆角」，而是先给了一个方便我自己的值，
> 再用探针把这个**假设**照出来。判据是**探针数据**，不是我的理由。

### 27.5 一条规则取代一张 22 行的表：`Theme.flat_surfaces`

批处理迁移后快照变化**不只是圆角，还多了阴影**：

```
-  <rect x="0" y="0" width="240" height="120" fill="rgba(30,30,33,1.00)" />
+  <rect x="0" y="2" width="240" height="120" fill="rgba(0,0,0,0.24)" />   ← 新增阴影
+  <rect x="0" y="0" width="240" height="120" rx="4" ry="4" fill="…" />   ← 新增圆角
```

163 份受影响。**根因**：扁平预设的扁平化表只覆盖 **22 个 kind**，而 `role_surface_style`
的 `_ =>` **兜底是 `Elevation::Level2`**（历史阴影）—— 所以 `adaptive_scaffold` / `app_bar`
这些没被枚举的 kind，在**自称扁平**的预设里仍然浮起。

**这是「把规则写成数据」的教科书形态**：一条「本预设是扁平的」规则，写成了 22 个 kind 名的
列表，于是它只对**写列表的人想到的** kind 成立。修法不是补全列表，是**把规则还给规则**：

```rust
// src/theme/manager.rs — role_base_style
let surface = if theme.flat_surfaces {
    crate::render::SurfaceStyle::solid()
} else {
    crate::render::role_surface_style(kind_name)
};
```

配套：
- `Theme.flat_surfaces: bool`（`src/theme/types.rs`），**有完整 rustdoc** 解释它取代了什么
- `Theme::default()` / `Theme::dark()` = `true`（两个出厂预设就是本仓既有外观）
- `Theme::dimensional()` = `false`（拿回整个 role 表）
- 删掉 `flat_surface_overrides()` 的 22 行表；`preset_surface_overrides()` 保留签名但**只返回空表**，
  并有**测试**钉住「一个预设不携带 class 级表面表」—— 这样「预设对状态有意见、对面没意见」
  这个半句话状态不会悄悄回来

`themes/*.json` **减 330 行、增 2 行**（`"flat_surfaces": true` 各一行）。

### 27.7 顺手发现并修好的：三个「声明了但从来没被看过」的 frame 面

用 §27.4 的探针思路继续查，`frame` 的三条绘制路径**没有出现在变化集里**。取证：

```
$ cat snapshots/svg/frame.svg
  <rect x="0" y="0" width="240" height="120" fill="rgba(18,18,18,1.00)" />       ← 背景
  <rect x="0" y="0" width="240" height="120" fill="none" stroke="…" … />          ← 只有描边
```

`FrameShape` 的 `#[default]` 是 `Box`，它**只画描边、完全不画填充**。所以：

- `draw_panel_frame`（填充 + 描边）
- `draw_styled_panel_frame`（填充 + box frame）
- `draw_win_panel_frame`（填充 + 3D 白/灰斜面）

这三条**能画一个面**的路径，在 **377 份快照里一份都没有**。一个控件有三条声明过的绘制路径、
只跑过一条 —— 正是 BLUE24 §10A.6 判据 6「每个声明的面都必须可审阅」说的那种覆盖缺失。

**修法**：把三个 shape 加进 `EXTRA_APPEARANCES`（它本来就是为「默认构造到不了的状态」
设计的），并通过控件自己的 `FrameShape::from_name` 解析 —— 这样表里的字符串和实际画出的
shape **不可能**不一致（不一致会得到「名字说是 A、画的是默认」的快照，这是该分支唯一要排除的失败）。

```rust
("frame", "_styled_panel", "styled_panel"),
("frame", "_win_panel", "win_panel"),
("frame", "_panel", "panel"),
```

同时把 extra 的渲染从「1 张（暗）」改为「2 张（暗 + 浅）」。理由：默认 shape 的明暗对比
**不能**说明 `draw_win_panel_frame` 的白/灰斜面在浅色下什么样 —— 那个斜面的**全部目的**
就是「凸起的错觉」，只在暗色下看一眼等于没看。

新增 6 份 `frame_*.svg`（3 shape × 2 外观）+ 1 份 `group_box_checked.light.svg`：

### 27.8 门禁自身的两处修正（**都是门禁的缺陷，不是代码的**）

改完之后 `check_svg_snapshots.sh` 报：

```
[3/5] count, naming and drawing content
  FAIL  expected 380 committed SVGs (188 controls x 2 appearances + 4 extra state(s)), found 384
```

**这是门禁的账算错了**：extra 现在渲染成**一对**（暗 + 浅），而门禁的公式是 `CONTROLS * 2 + EXTRAS`。
修的是公式，不是注释掉检查：

```bash
# 一个 extra 渲染成**一对**，和默认外观一样。
EXPECTED=$((CONTROLS * 2 + EXTRAS * 2))
```

（`EXTRAS` 本身是**从 `EXTRA_APPEARANCES` 表解析出来的**，不是硬编码 —— 所以「哪些文件存在」
和「声明了哪些状态」仍然是同一个事实。）

第二处：`decorate()` 的 `state_word` 原来同时当**门禁读的标记**和**人读的说明**用。
我一开始把说明写成 `" (styled_panel)"`，结果 `group_box_checked.svg` 的出处行被改成了
`state:  (checked)` —— **一份已提交快照因为一个和任何控件绘制都无关的原因改变了**。
拆成两个参数：`state_word` 是裸 token（`checked`），`caption` 是人读的散文。

第三处（顺带）：`src/theme/mod.rs` 的 `theme_with_overrides` 助手继承 `Theme::default()`，
于是**默默继承**了 `flat_surfaces: true`，把测试的前提（「一个什么都不说的主题拿到 role 表的
raised 键」）变成了假 —— `a_state_level_bevel_override_reaches_a_pressed_button` 真的红了。
助手现在显式 `flat_surfaces: false`，并写清为什么：

> 助手的承诺是「一个除了它说的以外**没有意见**的主题」。`Theme::default()` 是**扁平**预设，
> 而扁平现在是一条**规则**（不是 kind 表），继承默认等于**夹带一个调用者没声明的意见**。

### 27.11 U-12：从「前置不足」改判为「等待需求方」

U-12（背景采样）是本计划唯一**需求侧不明确**的条目，§12.1 现已把闸门写清楚 ——

**实测判断**：本仓 377 份快照**没有一份**表现出浮层下的内容变化（都是无背景的单控件渲染）。
所以在**本仓内** U-12 现在没有消费者 —— 它唯一的真实需求来自**宿主应用**（例如设计器的浮层面板）。

## 28. U-14：文字「不好看」的真实根因（度量 + 光栅化），以及 U-13 的闸门

### 28.1 根因一：SVG 后端的字形路径**从未被走到**（已修）

```
family="Open Sans"   -> outline_selected=true
family="sans-serif"  -> outline_selected=false
```

**本仓所有主题声明的字体名是 `"Arial"` / `"Courier New"` / `"sans-serif"`，而本仓发布的字体叫 `"Open Sans"` / `"Noto Sans SC"`。**

SVG 后端走的是 `text::outline(ch, cell, font.family(), ...)`，而 `outline` 内部用 `face_for_family(family)` 按**名字**查。名字对不上 → 返回 `None` → 后端**回退到位图路径**，于是全部 377 份快照里每一个拉丁字形都被画成 **8×8 位图的 1 像素小矩形**（`label.svg` 里一个 `Sample` 是 133 个 `h1v1h-1z` 子路径）。

**而同一份构建下，运行时光栅器画的是真正的矢量轮廓**：

```
$ paint_active('H', cell, ...) 
runtime: source=Open Sans ink=Coverage source_cell=None
VectorSource::covers('H') = true
active_faces = ["Open Sans"]
```

也就是说：**快照和像素对同一个控件给出了不同的画面。** 这正是该后端自己的模块文档说它存在的意义所在——"一个后端与光栅器对「哪个 face 在起作用」的答案不一致，是它唯一要防止的事"。

**修法**：把 face 选择变成**一处共享规则**。

- `font_assets::outline_face_for(ch)` —— 按 **coverage** 选 face（"谁的 glyph 表里有这个字符"）
- `VectorSource::face_for` 与 SVG 后端的 `outline_by_coverage` 都调它
- `outline()`（按 family，保留）与 `outline_by_coverage()`（按 coverage，新增）**共用** `outline_in_face()`，所以两个选择器不可能画出不同形状的同一 face

### 28.2 根因二：度量问错了 face，退化成**扁平 0.6 em**（已修）

这是用户看到的 `wi` 重叠的真正原因。

`shape_line` 会调 `shaping::cluster_advances` 拿**真实度量**（`hmtx` + `GPOS` kerning）——但它的第一行也是 `face_for_family(font.family())?`，同样返回 `None` → **整个函数短路** → 全部退化为 `estimate_cluster_advance` 的 **扁平 0.6 em**：同一个宽度给 `i` 和 `w`。

实测（14 px，Open Sans 自己的 `hmtx`）：

```
 ch   real(px)  estimate    drift         'widget' 的 pen 位置
  w     10.25      8.40    +1.85          0.00 /  0.00
  i      3.53      8.40    -4.87         10.25 /  8.40   ← 下一个字形早 1.85 px 开始
  d      8.57      8.40    +0.17         13.79 / 16.80   ← 再下一个晚 3.01 px
  g      7.72      8.40    -0.68         22.35 / 25.20
  e      7.86      8.40    -0.54         30.08 / 33.60
  t      5.47      8.40    -2.93         37.94 / 42.00
```

**`w` 和 `i` 重叠 1.85 px，而 `i` 之后的间隙又宽了 3.01 px** —— 这就是用户描述的"有的地方挤、有的地方松"。`ill` 更极端：3 个字母预留 25.2 px，实际只有 10.6 px，**2.4 倍**。

注意总量几乎相等（43.41 vs 50.40），因为**过估和低估互相抵消**。**逐字形不抵消，而逐字形才是眼睛看到的。**

**修法**：`face_for_metrics(text, font)` —— **先按 family**（保住文档承诺的"指名了就用那个"），family 查不到时**按 coverage 兜底**。这不是"悄悄重排"，因为相关的问题不是"调用者有没有指名 face"，而是"**这个字符的墨会从哪个 face 出来**"——`VectorSource` 按 coverage 选，忽略 family，所以 `"Arial"` 的文本在这份构建里**就是 Open Sans 画的**。用 0.6 em 给它定尺寸，就是"用 A 度量、用 B 绘制"，本仓已经为此付过一次代价。

修完实测：

```
  widget: 预留 50.4 px → 43 px
  Sample: 预留 50.4 px → 48 px
     ill: 预留 25.2 px → 11 px（真实 10.60）
```

### 28.3 根因三：SVG 后端的裁剪把字形**切掉了**（已修）

改成走 outline 之后，快照里出现了一个新现象：**`Sample` 里 `m` 整个字变成了位图方块**，而 `S`/`a`/`p`/`l`/`e` 是矢量。

实测定位：

```
$ outline_by_coverage 逐字符，cell 8x16
'S': x=[0.82,8.01] (cell w=8)  溢出 0.01 → 整个 contour 被丢弃
'm': x=[1.37,13.52] (cell w=8) 溢出 5.52 → 整个 contour 被丢弃
'e': x=[0.89,8.15] (cell w=8)  溢出 0.15 → 整个 contour 被丢弃
```

旧的裁剪规则是**「只要有一个顶点出格就整条 contour 丢掉」**。而 cell 的宽度是**估算的 advance**（8.4 px），字形的实际墨宽常常更宽——于是 `"Sample"` 里 6 个字形有 4 个退回位图，**一个字里混了两种字体**。

**修法**：真正的多边形裁剪，Sutherland–Hodgman，对 cell 的四条边各做一次。关键是它**保持绕向**（遍历顺序就是输入顺序，交点**插在**相邻顶点之间），所以 `fill-rule="nonzero"` 的挖空语义仍然成立——`o` 的内圈还是洞，不会被填成实心块。

修完实测：

```
$ grep -o 'M[0-9]* [0-9]*h1v' snapshots/svg/label.svg | wc -l
	   0                     ← 不再有任何位图矩形
$ python3: subpaths = 9, all closed = True    ← 6 个字形，9 条闭合轮廓（a/p/e 各带一个内圈）
```

### 28.4 根因四：**8 号字看起来很小很细**——这是光栅化，不是字形格式（已修）

这是最后一条，也是最容易被误诊的一条（见 §28.5）。

`blend_pixel` 把**线性覆盖率**直接当 alpha 用。但：覆盖率是**线性面积分数**（"这个像素有百分之多少被轮廓盖住"），而 8 位帧是 **sRGB**，人眼对 sRGB 的响应约为 `1/2.2` 次幂。于是 0.5 的覆盖率应该读作中灰，却被写成 `128/255`，眼睛收到约 `0.22`——**不到应得的一半**。

实跑本仓自己的覆盖率输出：

```
coverage 0.25: 线性混合 →  64, γ 校正 → 136   （差 72）
coverage 0.50: 线性混合 → 128, γ 校正 → 186   （差 59）
coverage 0.75: 线性混合 → 191, γ 校正 → 224   （差 33）
```

**每一条抗锯齿边缘都太暗，而且误差在覆盖率最小处最大**——正是细笔画和小字号所在的区间。这就是"很小很细"的量化解释。

**修法**：`srgb_ramp()` —— 256 项查找表（`powf` 放不进逐像素循环），在**字形**混合处经过它。实测效果：

```
12 px，逐字形墨量（覆盖率之和）
   e   30 px  raw 4178 → corrected 5518  (+32%)
   i   10 px  raw 1494 → corrected 1908  (+28%)
   a   31 px  raw 4001 → corrected 5600  (+40%)
   l   10 px  raw 2294 → corrected 2398  (+5%)
   m   23 px  raw 3753 → corrected 4574  (+22%)
```

`l` 只涨 5% 而 `a` 涨 40%，看着像 bug，实测直方图后确认**正确**：

```
'l': 10 px  →  224..255 占 8 个   （直竖笔画，本来就接近满覆盖，γ 曲线在高处是平的）
'a': 31 px  →   96..127 占 10 个  （弧形腔体，覆盖率分布在中段，正是 γ 抬升最多的地方）
```

**竖直笔画不需要帮忙，弧形笔画需要。** 这个不对称是判据成立的证据，不是缺陷。

**关键约束：这个改动只作用于字形墨，不作用于几何图形。** 第一次尝试改的是共享的 `blend_pixel`，结果**打红了两个测试**（`aa_sample_level_changes_line_edge_coverage`、`scene_composition_supports_scircle_commands`）——那是线段和圆的 AA 行为，线与圆的覆盖率是**距离推导的斜坡**，已经针对落点调过，校正它们是另一个问题、需要另一份证据。所以收敛为 `glyph_coverage_weight()`，只在文字路径上调用。

## 29. U-14 续：`word_spacing`，以及我自己引入的一个竞态（被 flake 抓出来）

### 29.1 `word_spacing`：补上缺的那一半旋钮

§28.2 修好度量之后，空格作为独立 cluster 拿到了**真实宽度**（Open Sans 的 space 是 0.273 em，而旧估算值是 0.33 em，差 21%）。所以默认词距**已经对了**。

但 `letter_spacing` 是**唯一**的间距旋钮，它作用于**每一个** cluster 间隙。于是一个想放宽**词距**的调用者，**必然同时放宽字距**——这是两件不同的排版事，一个数字表达不了。

**做法**（镜像 `letter_spacing`，四处：字段 / getter / setter / builder，外加 serde）：

```rust
// Font
#[cfg_attr(feature = "serde", serde(default))]
word_spacing: f32,
```

关键设计点：

| 决定 | 理由 |
|---|---|
| 默认 `0.0` = **face 自己的 space glyph** | 这才是**跨语言正确**的答案。空格宽度是**字体的属性**，不是排版的属性——交给 shaper 报，拉丁/阿拉伯/CJK 都对。**用固定 em 分数就是重犯 0.6 em 那个错误** |
| 加在**真实度量之后**，而不是覆盖它 | 覆盖会丢掉 face 的值。`0.0` 时 face 的值就是全部答案，这是默认，也是跨脚本正确的那个 |
| 只加在 `is_whitespace` 的 cluster 上 | 与 `estimate_cluster_advance` 判断"这个 cluster 不上墨"用的是**同一个谓词**，所以"有 advance 但没墨"和"词边界"是**一个问题**而非两个要保持同步的问题。不间断空格**不是** whitespace，正确——它按定义就不该拿到词边界的间隙 |
| 加在 `shape_line` 里（measure 与 draw 的**唯一**共用路径） | 只在 `draw_text` 加会让 tracked 文字**量得比画得窄**——本仓为此付过一次代价（§G.5） |

**实测验证**（14 px）：

```
'a b' 默认              = 20 px
'ab'  默认（无空格）    = 16 px
'ab'  word_spacing 6.0  = 16 px   ← 字母不动
'a b' word_spacing 6.0  = 26 px   ← 一个间隙 +6
'a  b' word_spacing 6.0 = 36 px   ← 两个间隙各 +6（每个词边界都加）
'ab'  letter_spacing 6.0 = 22 px  ← 与 word_spacing 明确区分
```

`a  b` 那一行是重要的：**两个空格拿到两个间隙**。一个"把间距加到整行总宽"的实现会通过单空格测试，却在所有多空格的句子上出错。

**测试**（3 个，都通过）：默认惰性、只动空格不动字母、每个词边界都加、builder+serde 往返（含"旧主题缺字段仍能加载"）。

### 29.2 一个我自己引入的竞态 —— 而且是 flake 抓出来的

全量跑的时候，**5981 passed / 1 failed**，而**再跑一次就过了**。这是最危险的一类信号，不能当噪声放过。

**定位过程**：连跑 6 次全绿 → 连跑 8 次、每次打印失败名单 → 抓到一次：

```
widget::runtime::tests::drive_frame_drains_input_before_advancing
```

但读这个测试后确认它**写得是对的**（用 delta、并在注释里说明了队列是共享的："what this asserts is that the frame counted what its drain took, not that it took exactly one thing"）。它注入到**进程级** trigger 队列，而 `platform/tests.rs`、`platform/mobile.rs` 也往同一后端注入——高并发下计数不可预测。

**但真正的问题在我自己的代码里。** 排查本轮引入的全局状态时发现了 gamma 表的初始化：

```rust
static INITIALISED: AtomicBool = AtomicBool::new(false);
static mut RAMP: [u8; 256] = [0; 256];
if !INITIALISED.load(Acquire) { unsafe { /* write RAMP */ } INITIALISED.store(true, Release); }
```

**这是容易写错的形状**：标志与数据是**两个独立位置**，正确性依赖于读写之间的 ordering，以及"只允许一个 writer"——而两个线程同时看到 `false` 会**都**跑初始化（这里之所以良性，只因为写的值完全相同）。

**修法：把竞态从设计里去掉，而不是靠 ordering 论证它安全。**

改为 **每个表项一个 `AtomicU8`**，并把"计算"并入首次读取：

```rust
static RAMP: [AtomicU8; 256] = [const { AtomicU8::new(0) }; 256];
if !READY.load(Acquire) {
    for (index, slot) in RAMP.iter().enumerate() {
        let value = ((index as f32 / 255.0).powf(1.0 / 2.2) * 255.0).round() as u8;
        slot.store(value, Relaxed);   // 每次写入自身是原子的
    }
    READY.store(true, Release);
}
unsafe { &*(addr_of!(RAMP) as *const [u8; 256]) }
```

这样：**没有半写窗口**（每个表项原子）、**任意线程可跑初始化**（值相同，幂等）、**`u8` 数组与 `[AtomicU8; N]` 在目标平台上布局相同**（`u8` 无内部填充）。

**验证**：连跑 **20 次，0 失败**。

> 这条值得记下来的理由：**flake 是证据，不是噪声**。第一次看到"失败一次、再跑就过"时很容易归因为"环境问题"——而实际上它指向的是一段真实的、我自己写的、有竞态的初始化代码。它甚至可能不是那次失败的直接原因（那个测试的共享队列是既有的），但**排查过程中找到的这段代码确实需要修**。

> 的命中数**必须只降不升**（当前 43），且每个命中必须在白名单里附理由

门禁 `check_surface_style_is_declared_not_hand_rolled.sh` 把它实现成「天花板 + 白名单 + 白名单条目必须有理由且不许陈旧」。
现状是 `CEILING=42`（`frame.rs` 迁移到 `Bevel` 后从 43 降了一次），而**白名单的 42 条没有一条再动过**。

### 31.1 先读白名单，而不是先动手

白名单自己的把三类分开写了（这是前一轮做对的地方）：

| 类 | 是什么 | 能不能迁移 |
|---|---|---|
| **A** | 真正的斜角（一条亮边 + 一条暗边） | ✅ 能，`Bevel` 就是为它存在的 |
| **B** | 单面的**色调台阶**（zebra/hover 带） | ❌ 不能，只有一侧、没有方向，`Bevel` 表达不了 |
| **C** | **disabled/secondary** 渲染 | ❌ 不能，`Color::disabled_variant_of` 已命名该关系 |

**所以「把 42 变成 0」是错的**（原则 #51：共享抽象必须带来真实消除才接入）。
真正该做的是：**把标成 A 的那几个迁移掉，并把标错类的纠正过来。**

### 31.2 A 类里真正的斜角：`frame.rs` 的两条

实测 A 类白名单里 `frame.rs` 占了决定性的位置，它有三条绘制路径：

| 路径 | 本轮之前的形态 | 处置 |
|---|---|---|
| `draw_box_frame` 的 `Raised` 臂 | ✅ 已是 `Bevel::from_base(border).with_direction(Raised)` | — |
| `draw_box_frame` 的 `Sunken` 臂 | 🔴 **手抄了 4 条 `draw_line` + 两个 `blend(…, 0.5)`** | ✅ 迁移为 `Bevel::from_base(border).with_direction(Inset)` |
| `draw_win_panel_frame` | 🔴 **16 条 `draw_line`**（外凹 + 内凸的双斜角） | ✅ 迁移为两条 `Bevel::stroke`（`Inset` 外 + `Raised` 内） |

**迁移的判据是「快照逐字节不变」**，不是「看起来对」：

```text
$ bash tools/check_svg_snapshots.sh
  PASS  regeneration reproduces every committed byte
check_svg_snapshots: checked=188 skipped=0 failed=0
```

`Sunken` 臂的等价推导（这是必须写下来的那一步）：

```text
旧:  top/left    = border.blend(BLACK, 0.5)
     bottom/right = border.blend(WHITE, 0.5)
Bevel::from_base(border) ⇒ light = blend(WHITE, 0.5), shade = blend(BLACK, 0.5)
Bevel::with_direction(Inset) ⇒ leading(top/left) = shade ✓, trailing(bottom/right) = light ✓
```

`plain` 与 no-theme 两臂也逐个对上：`plain` → `from_tones(border, border, border)`（四边同色）；
no-theme → `from_tones(rgb(128,128,128), rgb(255,255,255), rgb(128,128,128))`
（`Inset` 下 `shade` 是左上、`light` 是右下，与旧的 `light_color`/`dark_color` 变量名正好相反，
这正是「方向由名字携带时最容易反」的地方——`Bevel` 把它变成 `with_direction` 一个 token）。

### 31.3 一个**白名单自己标错类**的发现：14 个「A 类」根本不是斜角

白名单里四条的注释写的是「A-bevel: a two-line bevel（migratable）」——
`chip.rs` / `command_palette.rs` / `timeline_widget.rs`，外加 `stepper.rs` 等。
本轮读代码后发现它们**全部不是斜角**：

```rust
// chip.rs:369（command_palette / timeline / stepper / toast / gantt / kanban … 同形）
let border = style
    .border_color
    .or_else(|| theme.as_ref().and_then(|t| t.border_color))
    .unwrap_or_else(|| background.blend(&Color::BLACK, 0.15));
```

这产出的是一个**边框颜色**，不是「一条亮边 + 一条暗边」——没有成对、没有方向。
它与 `Color::border_of` 是一回事。而**全仓有 14 处写出完全相同的这句**：

```text
$ grep -rn "blend(&Color::BLACK, 0.15)" src/widget/ | wc -l
14
```

**所以这是真实的重复**（原则 #51 的前置成立）：一个关系被抄了 14 遍。

### 31.4 修法：给关系起名，而不是把 14 处挪个地方

加到 `src/core/color.rs`（**palette 层**，正是白名单 Pattern B 注释自己说的「a `shade(color, step)` helper in the palette layer」）：

```rust
pub const BORDER_STEP: f32 = 0.15;

pub fn border_of(fill: Color) -> Color {
    fill.blend(&Color::BLACK, Self::BORDER_STEP)
}
```

14 处全部改为 `.unwrap_or_else(|| crate::core::Color::border_of(background))`。
门禁从 **42 → 28**（少掉的正好是这 14 个）。

**这里有一个我差点写错的地方，记下来**：第一版 rustdoc 与单测声称「alpha 被保留」，
理由是 `disabled_variant_of` 保留了 alpha。实跑立刻打红：

```text
$ cargo test … core::color::tests::border_of_steps_a_fill_toward_black_and_keeps_its_alpha
panicked at src/core/color.rs:666: assertion `left == right` failed
  left: 147   right: 128
```

`blend` **会一起插值 alpha**（与不透明的 `BLACK` 混合把 `128` 拉到 `147`），
而旧表达式 `fill.blend(&Color::BLACK, 0.15)` 本来就**不**保留 alpha。
所以「保留 alpha」既不是我实现的、也不该是——那会**超出「重命名」的范围变成行为改动**。
修法是改文档和测试去说真话（并把这条边界写成注释），**不是**去改 `border_of` 让它符合我写错的文档。

### 31.5 白名单与门禁的同步（**陈旧条目必须删**）

## 36. §13 结论段的三处自相矛盾，以及写入 `blue24.md` §14 的对账步骤

用户指着 `blue24.md` §13（结论段）问「这段怎么解决」。先量，再答。

### 36.1 取证：不是文案问题，是同一个文件里四张表的行数互不相等

```text
$ awk '/^## 0B/,/^## 1\./' docs/plans/blue24.md | grep -c '^| [0-9]'
8                                    ← §0B 缺口总表 = 8 行
$ awk '/^## 10\. /,/^## 10A/' docs/plans/blue24.md | grep -c '^| \*\*批'
9                                    ← §10 批次表 = 9 批
$ awk '/^## 13\./,/^---/' docs/plans/blue24.md | grep -nE '(^|[。；：] ?)[一二三四五六七八九十]件事'
6:三件事本仓**都已有零件**，缺的是把它们接到**进程边界**上：
```

三处事实，逐条可核：

| # | 症状 | 数字证据 |
|---|---|---|
| 1 | 「**三件事**」后面跟了 **5** 条 bullet | 1451 行 vs 1453–1458 行 |
| 2 | 「本计划只做**四件**……的事」后面列了 **5** 个短句 | 1465 行 vs 1466 行 |
| 3 | **整个 §5 自适应**在结论段里没出现 | 5 条 bullet 与 5 个短句里都无「尺寸 / 自适应 / Breakpoint」 |

**这不是错别字**：它是「先写了 BLUE23 的 3 条、后追加 §10A 第 5 条时忘了改总数」与
「§8、§5 后加时同样忘了改」的活化石。所以它属于原则 #18 的等价形态——
**不是文档与代码不一致，是文档与文档自己不一致**（同一份计划里 8 / 9 / 3 / 4 四个数各说各话）。

### 36.2 修法的选择：不把 3 改成 5，而是把「数」交给结构

两条路，我推荐了 **(A)** 并把步骤写进了计划：

| 方案 | 做法 | 为什么 |
|---|---|---|
| **A（推荐）** | **删掉**两处写死的计数词（不写新数字），把「四件事」换成一张 `它必须 → 由谁交付 → 判据` 的五行表，补回 §5，并在段首加一行指回 §0B 的锚 | 改对数字仍要求下一个人**记得同步两处**；删掉数字后条数由**结构**决定，**不可能再错**。与 §10A.5「一条规则取代一张 22 行的表」同形 |
| B | 只把 3→5、4→5 改对，补 §5 | 治标：数字仍要人维护，且第 3 个硬伤（漏 §5）不会被系统性防住 |

**为什么补 §5 是补漏而不是润色**：§5 同时是 §0B 第 4 行的一半与 §10 批 8 的全部。
它补进「它会跟着系统设置变」那一格，理由是**尺寸与缩放同属「设备事实」**——
一个说「字多大」，一个说「树多宽」，输入都来自 §4 的 `EnvironmentProvider`。两者不该分两句。
