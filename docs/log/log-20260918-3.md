## 1. 🔴 缺陷 A（阻断级）：本机 macOS 构建完全损坏

### 1.1 三条编译错误（实跑取证）

| 位置 | 错误 | 根因 |
|---|---|---|
| `src/platform/macos/platform_impl.rs:271` | `cannot find type NSRect` | 该文件用 `NSRect` 但 `use cocoa::foundation::{...}` 里没有它 |
| `src/platform/macos/canvas.rs:871` | `expected usize, found &Class` | `decl.register()` 返回 `&Class`，`OnceLock<usize>` 的闭包忘了 `as usize`（同文件 `canvas_view_class` 第 133 行是**对的**，说明是抄漏） |
| `src/platform/macos/canvas.rs:868` | `invalid cast` | Rust 1.98 起禁止 `unsafe extern "C" fn` → 安全 `fn` 的强制转换（E0605） |

### 1.2 第三条不是"加个关键字"能解决的

`objc::declare::ClassDecl::add_method` 的 `MethodImplementation` **只为安全** `extern "C" fn` 实现。
而 Rust 现在禁止把 `unsafe extern "C" fn` 项转成安全版本。三条路都试过并取证：

| 尝试 | 结果 |
|---|---|
| `window_did_resize as extern "C" fn(..)` | `E0605`: 不准 `unsafe fn` → safe `fn` |
| `window_did_resize as unsafe extern "C" fn(..)` | `E0277`: `MethodImplementation` 不为 `unsafe extern "C" fn` 实现 |
| **安全 trampoline 包一层** | ✅ 编译通过 |

最终采用 trampoline：注册的是**安全** `extern "C"` 函数，内部 `unsafe { ... }` 调用真正的
`unsafe fn`。这也是唯一既满足 `objc` 的 trait bound、又满足 Rust 1.98 转换规则的写法。

### 1.3 顺带抓到的两个静默缺陷

**① `window_did_resize` 里的 downcast 结果被丢弃**（不是本轮引入，是复核时发现）：

```rust
if let Some(platform) = super::platform_impl::active_platform() {
    if let Some(macos) = platform.as_any().downcast_ref::<super::types::MacOSPlatform>() {
        crate::queue_resize_trigger(widget_id, width, height);   // ← macos 没用
    }
}
```

`queue_resize_trigger` 是**自由函数**（`crate::` 前缀），不经过 `platform`。所以这段代码的真实语义是
"当且仅当当前后端是 macOS 时才通知"——而它在 macOS 后端自己的回调里，**条件恒真**。
两个 `if let` 的唯一作用是把调用包起来。已改用直接调用并写明理由。

**② 由此产生的死代码**：`active_platform()` 全仓**只有这一个调用点**，删掉后即死。
按原则 #4（零消费者不得长期存在）删除，连带其 `Vec` import。

### 1.4 取证（实跑）

```text
$ cargo check --all-targets
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 4.51s
    （0 error, 0 warning）
```

## 2. 🔴 缺陷 B（阻断级）：`mini` / `embedded` 两个档在 macOS 上编译不过

`check_profiles.sh` 第 5、6 步（`--no-default-features --features mini/embedded --all-targets`）
实测 **33 个错误**，全部来自同一个文件。

### 2.1 根因：`src/platform/macos/accelerator.rs` 直接用了 `std` 的 `String`/`ToString`

```text
error[E0425]: cannot find type `String` in this scope   --> src/platform/macos/accelerator.rs:48:58
error[E0599]: no method named `to_string` found for reference `&'static str`
→ 33 errors
```

该模块 `#![cfg(target_os = "macos")]`，**对 profile 不设防**——它会给 `mini` per-arch 编译。
而 `mini` 档的 `String` / `ToString` 要走分配桥（`src/compat.rs`），不能靠 `std` 前奏。

**这条正踩在原则 #36/#37 上**：`src/platform/` 是允许有 OS 门控的地方，
但**不允许**在 `src/platform/` 里把 `std` 前奏当作理所当然——平台后端同样要能在 `mini` 下编译。

### 2.2 修复

顶部加分配桥导入，测试模块补 `use crate::compat::String;`（测试模块不继承父模块的 import）。

### 2.3 同类模式全扫（原则 #2 冰山法则）

`grep` 全仓 `src/platform/` 下对 `String`/`Vec`/`ToString` 等**未经 `crate::compat`** 的直接依赖，
确认 `accelerator.rs` 是唯一漏网的（其余平台文件都已走 compat）。已扫，无第二例。

## 3. 🔴 缺陷 C（阻断级）：`gpu`-only 档编译不过 + 一个假的 trait 实现

`check_profiles.sh` 第 9 步（`--no-default-features --features gpu`）实测：

```text
error[E0433]: cannot find module or crate `fmt` in this scope    src/render/backend/scene.rs:197,198
```

### 3.1 根因

按原则 #10 必须零 warning，所以加了精确门控。这是"修一个点扫同类"的一次实地体现。

## 5. 🟠 缺陷 E：`check_perf.sh` 在 macOS 上是**空转**（门禁假装通过）

### 5.1 取证

```text
$ bash tools/check_perf.sh
=== Performance regression gate ===
  (tolerance: 3x the recorded baseline)

[1/2] render_frame 400x300
（然后什么都没有，退出码非 0）
```

单独跑那条命令：

```text
$ timeout 600 cargo bench ...
sh: timeout: command not found      ← EXIT=127
```

**根因：`timeout` 是 GNU coreutils 的东西，BSD userland 没有。** macOS 上不存在，`gtimeout` 也没装。
`set -e` 让脚本在第 5 行就死掉，但因为它死在第 2 步（`[2/2]`）打印之前，
输出看起来像"正在跑"，实际上**一个基准都没测过**。

### 5.2 为什么这条比"顺手修个脚本"更重要

`run_all_gates.sh` 把这个脚本算作一个门禁。它在 macOS 上**永远 FAIL**（退出码非 0），
但它 FAIL 的理由和"性能回归"**毫无关系**。这正是原则 #48 说的"命令本身也是判据"——
一个坏掉的命令会把不存在的缺陷报成真缺陷，也会把真缺陷掩盖掉。

### 5.3 修复

按存在性解析：`timeout` → `gtimeout` → 无上限（并**打印一行说明**，不静默）。
用 `${TIMEOUT_CMD:+$TIMEOUT_CMD}` 形式是因为 `set -u` 在 bash 3.2（macOS 默认）下
拒绝展开空数组 `"${ARR[@]}"`。

### 5.4 修好之后**真的在测**（实跑）

```text
$ bash tools/check_perf.sh
note: no `timeout`/`gtimeout` on this host; the benchmark runs unbounded.
=== Performance regression gate ===
[1/2] render_frame 400x300
  170700 ns  (baseline 194000 ns, limit 582000 ns)  OK
[2/2] dispatch_pointer_event 9-widget tree
  139 ns  (baseline 153 ns, limit 459 ns)  OK
Performance gate passed.
```

**这才是"修复"该有的样子**：修复前无输出，修复后有真实测量值。

## 11. 🟠 功能性缺陷：声明了、公布了、但**永远不会发射**的信号

用 4 个子代理做广度取证（控件实现完整性 / 平台门控 / 注册接线 / 测试与休眠代码），
每条结论我都自己读源复核过。共性根因是同一个：

> **`commands` 与 `events` 两条轴公布了远多于实现的承诺，而本该守住承诺的门禁
> 要么被削弱（commands：地板设成 5），要么是同义反复（events：拿同一个列表校验自己）。**

先修**逐个控件**的具体缺陷（可独立验证），再处理系统性的两条轴。

### 11.1 `KanbanBoard::card_activated` —— 有文档、有类型、永不发射

**取证**：`grep` 全仓 `.emit(` 无一处发 `card_activated`。

**根因（读事件链得出）**：`handle_event` 的 `MousePress` 分支无条件 `begin_card_drag`；
释放时 `finish_card_drag` 走 `session.drop_on(...)`，未越过阈值则 `!effect.is_accepted()`
→ 直接 `return false`，**卡片的 id 被丢掉**。所以"点击而不拖"这条路径产生了**零个信号**。

**修复**：在 `finish_card_drag` 里先判 `session.is_active()`；未激活即视为**点击**，
从 `drag_origin` 取回卡片 id 并 `card_activated.emit(id)`。用共享状态机自己的
`is_active()` 判定，而不是在这里重新推导阈值常量。

**为什么不直接 emit**：`drop_on` 会改动棋盘状态，必须先分清"点击"与"拖放"
再走各自分支——否则一次点击会被当成一次被拒绝的拖放，卡片 id 仍然丢失。

**新增断言（3 条，均实跑）**：

| 测试 | 断言 | 反向注入实测 |
|---|---|---|
| `kanban_click_without_drag_emits_card_activated` | 订阅者**收到** id `"a"` | 删掉 emit → FAIL（`left: None, right: Some("a")`） |
| `kanban_drag_does_not_emit_card_activated` | 真拖拽**不**报激活 | — |
| 原有 `kanban_drag_below_threshold_stays_a_click` | 保留 | — |

### 11.2 `DockWidget::dock_location_changed` —— 信号有了，**状态根本不存在**

**取证**：`DockWidgetArea` 枚举存在、信号存在并已发布到 capability，但
`grep dock_location` 的**全部**命中是：字段声明、构造初始化、属性表、以及**它自己的测试**。
**结构体上没有任何 dock 区域字段，也没有任何 setter。** 调用方无从制造那个"跃迁"。

**更严重的是那个测试本身**：

```rust
// 修复前
let receiving = Arc::new(Mutex::new(DockWidgetArea::NoDockWidgetArea));
...connect(...);
dw.dock_location_changed.emit(DockWidgetArea::LeftDockWidgetArea);  // ← 自己 emit
assert!(received.load(Ordering::SeqCst));                            // ← 自己断言
```

它**在信号自身上 emit 再断言收到**——只证明 `Signal1` 会投递（这对全仓每个信号都成立），
并在 `DockWidget` 完全没有该功能时**照样通过**。这是"测试自我实现"的教科书样本。

**修复（补全功能，不是改测试）**：

| 新增 | 说明 |
|---|---|
| 字段 `dock_location: DockWidgetArea` | 默认 `NoDockWidgetArea` |
| `pub fn dock_location()` | 读取 |
| `pub fn set_dock_location(area)` | **只在真跃迁时发射**；不在 `allowed_areas` 内则拒绝并 `log::warn` |
| `DockWidgetAreas::contains(area)` | 把允许集从"6 个 bool"变成可判定的谓词 |
| `set_allowed_areas` 收紧时自动脱坞 | 不允许的当前位置必须迁出并通知 |

**为什么拒绝而不是静默接受**：`allowed_areas` 是宿主声明的约束；把控件停在不被允许的位置
正是这个集合要防的不一致。`NoDockWidgetArea` 永远允许，否则控件会被困在
宿主已撤销的区域里。

**测试改造（4 条，全部改为驱动真实 setter）**：`test_signal_accessors` 的 dock 段现在
调 `set_dock_location` 而非 `emit`；另加"重复应用同一区域必须沉默"、
"禁止区域必须被拒"、"收紧允许集必须脱坞并通知"。

**反向注入**：删掉 `self.dock_location = area;` → **4 条测试全 FAIL**。

### 11.3 `ListBox` 的 `SelectionMode::Extended` —— 注释写着"先跟 Multi 一样"

**取证**：

## 12. 🔴 缺陷 I（静默功能性 bug）：`i18n` 被错误地门控在 `desktop` 上

这是子代理"平台门控"审计里最有价值的一条，我逐条复核并**实跑验证**过。

### 12.1 根因：能力 feature 被当成 profile feature 用

`Cargo.toml` 把 feature 分成两类：**profile**（`desktop`/`tablet`/`mobile`）与
**能力**（`i18n`/`print`/`touch`/`chart`…）。**两者不是嵌套关系**：

```toml
tablet = [ …, "i18n", … ]      # ← tablet 启用 i18n，但**不**启用 desktop
mobile = [ …, "i18n", … ]
```

而两处代码把 i18n 调用挂在 `desktop` 上，写成**互补门控的两套函数体**
（正是原则 #41 禁止的形态）：

```rust
// src/widget/base.rs（修前）
pub fn set_translated_tooltip(&mut self, key: &str) {
    #[cfg(feature = "desktop")]
    { self.tooltip = crate::compat::mini_string_from(crate::i18n::translate(key)); }
    #[cfg(not(feature = "desktop"))]
    { self.tooltip = crate::compat::into_mini(key); }        // ← tablet/mobile 走这里
}
```

```rust
// src/widget/dialog/message_box.rs（修前）
#[cfg(feature = "desktop")]      pub fn translated_label(&self) -> String { /* tr!(..) */ }
#[cfg(not(feature = "desktop"))] pub fn translated_label(&self) -> String { self.label().to_string() }
```

**后果**：`tablet`/`mobile` 构建**初始化了翻译目录，却从不使用**——
按钮标签与 tooltip 原样返回目录键。用户看到的是 `common.button.cancel` 而不是 `Cancel`。
这是**静默**的：编译通过、测试全绿、无任何警告。

### 12.2 为什么这不是"作者有意简化"

`src/platform/profile.rs:433-441` **自己写明了正确的判据**：

> `feature = "i18n"` is a **capability** feature, not a profile gate

并且 `init_optional_subsystems()` 用的就是 `#[cfg(feature = "i18n")]`。
也就是说：**同一个仓里，初始化的门控是对的，使用的门控是错的。**

还有第三条证据：`crate::tr!` 在 `src/lib.rs` **已经有**针对无 `i18n` 的 fallback 存根，
其文档写明它存在是"so call sites need no `cfg` of their own"。
两套手写门控是对一个**已存在机制**的重复实现。

### 12.3 修复

删掉两套互补函数体与两处 `cfg`，改为**单一体无条件**调用——
无 `i18n` 的档由 `tr!` 自己的存根处理（原则 #37：缺省实现要诚实，不要双份签名）。

### 12.4 取证（实跑，三档对比）

探针：调用 `StandardButton::Ok.translated_label()` 与 `set_translated_tooltip("common.button.cancel")`。

| 档 | 修复前 | 修复后 |
|---|---|---|
| `desktop` | `"OK"` / `"Cancel"` | `"OK"` / `"Cancel"` |
| `tablet` | `"common.button.ok"` / `"common.button.cancel"` ❌ | `"OK"` / `"Cancel"` ✅ |
| `mobile` | `"common.button.ok"` / `"common.button.cancel"` ❌ | `"OK"` / `"Cancel"` ✅ |

上表"修复前"列是**反向注入实测**得出的 —— 把 `base.rs` 改回 `into_mini(key)`、
在 `tablet` 档重跑，tooltip 确实回到 `"common.button.cancel"`。

### 12.5 测试（4 条新增）

修复前 `translated_label` 与 `set_translated_tooltip` **零测试覆盖**（`grep` 全仓无命中），
这本身就是它们能然存活的原因。新增：

| 文件 | 测试 | 断言 |
|---|---|---|
| `message_box.rs` | `translated_label_resolves_through_the_catalogue` | `Ok` → `"OK"` |
| `message_box.rs` | `translated_label_is_not_the_catalogue_key` | `Yes` → **不是** `"common.button.yes"` |
| `base.rs` | `test_translated_tooltip_stores_the_translation_not_the_key` | → `"Cancel"` 且 **不是** 键名 |
| `base.rs` | `test_translated_tooltip_falls_back_to_the_key_for_unknown_keys` | 未知键仍可显示 |

### 12.6 防复发：新增门禁 `check_capability_feature_gates.sh`

**为什么不能靠构建测试**：坏掉的档**能编译**。错的是 `cfg` 里把能力与 profile
配成对，这是**源码文本**的属性。所以门禁读文本，并诚实地声明自己是源码检查。

两道判据：
1. **通用**：扫描全仓 `#[cfg(...)]`，报告**同时**含 profile 名与能力名的行
   （能力列表从 `Cargo.toml` 读出，不硬编码，所以不会过期）。
2. **定点**：本次实际出错的两处，断言 i18n 调用**不处于** profile 门控之下。

**反向注入（实测 FAIL）**：加回 `#[cfg(feature = "desktop")]` + `#[cfg(all(feature = "desktop", feature = "i18n"))]`
两个探针后，两道判据**均报告 ❌**（`base.rs:282` 与 `base.rs:280`）。

门禁已注册进 `tools/run_all_gates.sh`（该脚本 `for gate in tools/check_*.sh` 自动发现，无需登记）。

## 2. 🔴 缺陷 1：`LCDNumber::overflow` 信号是假的（声明+广告+绘制，但永不发射）

### 2.1 取证（读源码，非推测）

`src/widget/display_widgets/lcd_number.rs`：

- `pub overflow: GenericSignal`（L63）——声明了。
- `lcd_number_capability()`（`properties.rs:238-245`）`events: &["value_changed", "overflow"]`——广告了。
- `Draw::draw`（原 L326-331）`if self.check_overflow() { fill_circle(黄色) }`——绘制了。
- 但 `set_value` 先 `clamp(min,max)` 再存，`check_overflow()` 计算 `value < min || value > max`，
  而存储值**永远在范围内** → `check_overflow()` 永远 `false` → 黄色圆点永远画不出、信号永远不发射。

**三处代码互相矛盾**，且 doc 注释自己承认「nothing ever emits it」「Treat as declared-but-inert」
——这正是原则 #12/#13 禁止的「假修复/不完整实现」。

### 2.2 修复（让整条链路变真）

1. 新增字段 `overflowed: bool`（最近一次 `set_value` 是否越界）。
2. `set_value`：在 clamp **之前**判定 `out_of_range`；越界则 `overflowed = true` + `overflow.emit()`；
   在范围内则 `overflowed = false`。存储值仍 clamp（保留既有契约）。
3. `check_overflow()` 改为返回 `self.overflowed`（粘性，直到下次范围内 set 清除）。
4. `draw()` 的黄色圆点因此真正可达（`check_overflow()` 为 true 时渲染）。

### 2.3 测试（新增 1 条 `lcd_overflow_is_emitted_and_sticky`）

断言：越界 `set_value` → `overflow` 发射 1 次 + `check_overflow()` true + 值被 clamp；
再越界 → 发射 2 次（粘性）；范围内 `set_value` → `check_overflow()` false、不再发射。

# 第 47 轮 — 「175 还是 175？」深挖出的三重真实缺陷：门禁空转 + 路由表死锁 + 4 个控件未接线

## 42. 起因

用户追问「控件数量还是 175？」。第 46 轮已把 3 处散文数字（`README.md` ×3、`README.zh-CN.md` ×3）
从 175 改成 179，但用户的怀疑是对的 —— 只是**真正的 175 不在文档里，在代码里**。

本轮遵循原则 #2（冰山法则：修一类而非一处），逐层下潜，共挖出 **3 个独立缺陷**，
其中 2 个是「看起来在守、其实没守」的假门禁。

## 43. 缺陷一：门禁 `check_widget_kind_count.sh` 空转（vacuous gate）

### 取证

第 46 轮我把该门禁重写为「接受文件列表作为参数」，然后**用无参数方式调用它**：

```text
$ bash tools/check_widget_kind_count.sh
WidgetKind variants (parsed from src/widget/kind.rs): 179
✅ check_widget_kind_count: documented variant counts match the enum
```

`sys.argv[2:]` 为空 → 扫描 0 个文件 → 恒过。**这是比没有门禁更糟的假门禁**：
它对外宣称的覆盖范围（README + codemap）根本不存在。且 CI `.github/workflows/ci.yml:114-118`
正是以**无参数**方式调用它，所以 CI 上同样是空转的。

### 修复

- 文件列表**硬编码**在脚本内（22 个文档：README×2 + codemap + capability matrix + cookbook 3 语言 × 6 章）。
- 若解析到 0 个文件则**直接 FAIL**，杜绝再次空转。
- 匹配模式从原「167 后跟特定词」扩展为 5 条：`N kinds` / `N variants` / `N 种` / `N 變體` /
  `N (full)|（完整）`；且用 `\s` 跨行匹配，捕捉换行折行的声明
  （如 cookbook 的 `All 179\n   widget kinds`）。
- 仅匹配 3 位数字，`28 ... always available` 之类的子集声明不会被误判。

### 反向注入验证（原则 #16 要求负向证明）

```text

$ bash tools/check_widget_kind_count.sh

❌ README.md:638 states '175' but the enum has 179: Injected stale claim: 175 kinds.
```

## 44. 缺陷二：`src/control_backend/routing.rs` 路由表死锁在 175（真正的 175）

### 取证

用户问「还是 175？」时，代码里确实有 175 —— 而且是**测试断言的常量**：

```text
src/control_backend/routing.rs:52:    const EXPECTED_WIDGET_KIND_COUNT: usize = 175;
```

实测解析：

```text
array entries: 175        <- 路由数组条目数
enum variants: 179
MISSING from routing array: ['TreeTable', 'Breadcrumb', 'SignaturePad', 'DropZone']
```

### 根因（这是重点，不是「忘了加 4 个」）

该测试的结构是：

```rust
let all = [ /* 175 个变体，手工维护 */ ];
assert_eq!(all.len(), EXPECTED_WIDGET_KIND_COUNT);   // 常量也是手工维护的 175
```

它**比较同一个手工台账的两个半边**。枚举涨到 179 时，数组和常量都还是 175，
断言依然通过 —— **一个不可能失败的检查不是检查**。同样的漂移在 167 → 171 时已经发生过一次
（源码注释里自己记着），当时承诺的 `check_kind_reachability.sh` 门禁**从未被创建**。

### 修复：用编译器取代手工计数

改为**穷尽 `match`，无通配臂**。`WidgetKind` 的 151 个变体全部只门控在 `widgets_unstripped`，
而该测试模块本身就门控在 `widgets_unstripped`，因此在模块内可以无 `#[cfg]`、无通配地
列出全部 179 个变体：

```rust
match kind {
    WidgetKind::Window | WidgetKind::Dialog | /* ...全部 179 个... */ | WidgetKind::DropZone
        => ControlRoutePreference::CustomRequired,
}
```

新增变体若无路由决策 → 测试目标**编译失败**（E0004），不再有任何数字需要同步 ——
缺陷类别被消除，而非仅仅被检出。

### 反向注入验证

```text
$ # 删除 DropZone 臂
$ cargo check --no-default-features --features desktop --all-targets
error[E0004]: non-exhaustive patterns: `kind::WidgetKind::DropZone` not covered
error: could not compile `rust_widgets` (lib test) due to 1 previous error
```

已还原。
