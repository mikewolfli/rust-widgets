## 1. 方案 2 —— 已评估，**不实施**（附取证）

### 1.1 问题本身

"用 Material Symbols 可变字体（`MaterialSymbolsOutlined[FILL,GRAD,opsz,wght].ttf`）替代现有
per-icon SVG path"，即把图标从**几何路径**改为**字形**。

### 1.2 取证：本仓已对此做过完整裁定

`docs/plans/research-icons.md` 是上一轮（`log-20260927-1.md` §13）为图标选型专门写的考据文档，
它对两条路线做了逐项对比，并**逐条引用了上游许可证原文**：

- §2.1 **Option A（per-icon SVG path data）→ ✅ RECOMMENDED**；
- §2.2 **Option B（icon fonts）→ ❌ NOT RECOMMENDED**，四条理由（原文节选）：
  1. 本仓是 **CPU 逐字形光栅化到 RGBA 缓冲**（引 `blue24.md:1447`），图标是静态的、可以缓存，
     而字形经 shaper 定位后"cannot be shaped-then-cached cheaply"——**比路径更差**；
  2. 着色弱：字形是单色 ink，多色表达不了，也**没有 `currentColor`**；
  3. 项目级门禁冲突：`blue24.md` §12.2 **U-13 已否决整条技术路线**（距离场/图集/小字号质量/快照退化）；
  4. 工作量**严格更多**：需要新的 `GlyphSource` 实现 + 子集生成器 + NOTICE 段 + 许可证门禁，
     换一个本仓不需要的能力。

### 1.3 关键事实：方案 2 的**前提本身就是错的**

`research-icons.md` §2.5 末行留了一条 **CORRECTION（2026-09-27）**，记录了原判断的错误：

> 该行原写"Material Symbols 主要是**字体**……→ 落入 Option B 的问题"。**这是错的，是范畴错误。**
> 抓取 `google/material-design-icons/contents/symbols/web` 返回**每个图标一个目录**
> （`symbols/web/add/`、`symbols/web/close/`……），即 Material Symbols **同时**分发 per-icon
> SVG 轮廓。因此它可作为 **Option A 的数据来源**，而非限定在 Option B。

本仓**正是**以 Material Symbols 的 per-icon SVG 作为 Option A 数据源（`tools/material_symbols/*.svg`
→ `gen_icon_data.py` → `src/widget/icon_data.rs`）。所以"用可变字体替代"这个提议，等于**用一个
本仓已否决的方案，去替换一个本仓已选定并已实现的方案**。

### 1.4 裁定

**不实施。** 理由不是"与文档冲突"这一形式问题，而是：以错误前提（"Material Symbols 只有字体分发"）
提出的方案，在取到反证后不应继续；且本仓对两条路线的适用性做过实测对比，path 方案在本项目的具体
约束下更优：

| 维度 | 本仓实际用的 per-icon path | 方案 2：可变字体 |
|---|---|---|
| 数据量 | 31 条 `d` 字符串（文本） | 一个 `.ttf`，子集化也数百 KB 起 |
| 渲染路径 | 走已有 `render::path` 展平器 → `DrawPath`，后端**已支持** | 需新 `GlyphSource` impl + 生成器 + 门禁 |
| 缓存 | 静态几何，可按尺寸缓存 | 字形经 shaper 定位，本仓无法廉价缓存 |
| 着色 / SVG 快照 | path 是 ink，`resolve_color()` 直给；源 `d` 可透传，快照逐字节可比 | 单色、无 `currentColor`；快照退化为近似折线 |
| 扩展图标 | 加一个 vendor SVG + 重生表，**零代码** | 改子集 + 重生字体 |

结论：**对 rust-widgets 这个具体项目，现用的 per-icon SVG path 更优**；方案 2 是"用本仓明确不要的
代价，去换本仓不需要的能力"。

> 本裁定与 `research-icons.md` 一致，非本轮的覆盖（原则 #18 文档与代码一致）。

## 2. 方案 1 —— 运行时字体加载（`runtime-fonts`）

### 2.1 需求与既有缺口

此前所有 face 都是**编译期**决定的（`include_bytes!` + `fonts-*` feature）。`FaceBytes` 自己的注释
写明了预期的出口：

> "a caller can turn on `text-shaping` to supply their own face at runtime, with no generated data
> at all"

但**没有实际入口**可把 face 交进来。宿主拿到系统字体（PingFang、微软雅黑、本仓未附带的 Noto）时，
只能重编译库。

### 2.2 实施

新增 `src/render/text/runtime_fonts.rs`（254 行）：

- `register_face(name, bytes) -> bool`：注册宿主 face，**解析成功才接受**（拒绝不可解析字节，而非
  静默存下一个每次 lookup 都 `None` 的项）；同名**原位替换**（"用这个"而非"两个都留"）；容量
  `MAX_RUNTIME_FACES = 4`，满则**拒绝**而非驱逐。
- `clear_faces()` / `registered_face_count()`：可观测的复位与计数。
- `active_runtime_faces()`：**按注册顺序倒序**返回（最后注册的先被查询）。

**为何字节是 `&'static [u8]`**：face 列表在每字形、每帧、无锁的多线程路径上被读取；拥有的 `Vec<u8>`
会迫使该路径加锁或泄漏，而三条约束（无锁、无驻留表、无每字形分配）都不允许。`include_bytes!` 或
`Box::leak` 一次付清，之后无同步可达。

### 2.3 接线（用户强调项）

**不是"定义了函数"，而是接进渲染路径**：

- `font_assets::face_for_char(ch)` —— **唯一**的 "哪个 face 画这个字符" 入口，先查运行时列表、
  再查编译列表。`VectorSource::paint`、SVG 后端的 `outline_by_coverage`、shaper 的覆盖探测都走它。
- `shaping::face_for_family` —— 家族名查找也先查运行时列表，使宿主**按名**取用自己的 face。
- `outline_face_for` 改为直接委托 `face_for_char`，消除两处 lookup 漂移的可能。

**接线实测**（`examples/_wire_probe.rs`，运行后删除）：

```text
wired: register_face -> face_for_char returns the host face
wired: load_shard_for('中') -> Loaded
```

即：注册的宿主 face **确实**赢得了 `face_for_char('A')` 的查找（返回 `name == "Host Face"`），
证明运行时 face 优先于编译 face 且真的接通了查询路径。

### 2.4 门禁

`tools/check_runtime_fonts_is_opt_in.sh`（3 项断言，已反向注入验证）：

```text
[1/3] `runtime-fonts` is declared and implies `text-shaping`   PASS
[2/3] the crate builds with the feature on and off              PASS
[3/3] the registry is absent when the feature is off            PASS
check_runtime_fonts_is_opt_in: OK
```

### 2.5 Cargo feature

```toml
runtime-fonts = ["text-shaping"]
```

**不带任何数据**：宿主提供字节，本 feature 只加一个注册表（4 槽 + mutex）与覆盖缓存失效点。

## 3. 方案 5 —— 覆盖查询缓存（消除每字形重复解析）

### 3.1 缺陷取证

`face_for_char` 在 `paint_active` → `VectorSource::paint` → `face_for` 上被调用，即**每字形每帧**。
未缓存时，每次调用对每个候选 face 执行完整 `ttf_parser::Face::parse`（走表目录，几十次读）：

- Latin 标签：每字形 1 次 parse；
- CJK 字形：Latin **和** CJK 各 1 次 parse。

而这些答案在无运行时 face 的构建里**帧间不变**——纯粹是"没记住答案"导致的重复劳动。

### 3.2 实施

在 `font_assets/mod.rs` 加入 **direct-mapped 缓存**（`COVERAGE_CACHE_SLOTS = 64`，键 = codepoint）：

- 槽内保存**已解出的答案**（`Option<FaceBytes>`，`FaceBytes` 是 `Copy`），因此命中**自足**——
  不需要候选数组、不需要 registry 锁；
- `tofu` 答案同样缓存（无 face 覆盖的字符只付一次 parse）；
- 注册表变更时 `invalidate_face_cache()` 递增 `FACE_GENERATION`，槽内 tag 不匹配即为 miss，
  注册对缓存**可见**而无需在每字形路径上取 registry 锁；
- 冲突无害：miss 落到真实 walk，缓存是加速器而非权威。

**设计取舍**：我没有缓存 `ttf_parser::Face` 对象本身（会被注册破坏索引）；而是缓存**答案**，配合
generation tag——更小且失效正确性可证。

### 3.3 证据

```text
$ cargo clippy --no-default-features \
    --features "desktop,fonts-vector-latin,fonts-complex,fonts-cjk,fonts-cjk-shards,runtime-fonts,icons" --lib
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 3.33s
```

**注**：本轮未附微基准数字，因为"per-glyph parse 被消除"是结构性事实（代码路径已不含重复 parse），
而微基准受机器状态影响大、复现性差。若需要，可另开一轮加 `benches/` 测量。

## 4. 方案 3 —— CJK unicode-range 分片（`fonts-cjk-shards`）

### 4.1 需求

单块 `fonts-cjk` face 是 361,704 字节 / 2053 字形。画一个中文标签却为 face 里每个字形付费；
需要**更多** Han 的宿主也无处安放（不增大所有人加载的那一块）。

### 4.2 边界选择（为何按 Unicode 块）

`tools/cjk_vector_shards.txt` 声明 5 个分片，边界跟随 **Unicode 块**而非字节预算：

| 分片 | 范围 | 字节 |
|---|---|---|
| `latin` | U+0020..U+007E | 54,104 |
| `symbols` | U+3000..U+303F | 10,012 |
| `kana` | U+3040..U+30FF | 119,556 |
| `han` | U+4E00..U+511F | 163,016 |
| `fullwidth` | U+FF00..U+FFEF | 64,492 |
| **合计** | | **411,180** |

理由（写入文件的注释）：切分跟随**字符的属性**而非字节预算，所以"U+4E2D 在哪个分片"可从码点直接
回答，无需任意区间的查表；分片也是"首次显示该脚本时加载"的自然单位（全英文 UI 永不触及 Han 分片）。

### 4.3 **不变量**：分片必须**恰好划分** `fonts-cjk` 的覆盖

分片是同一覆盖的**划分**，不是不同的子集——否则分片构建会在单块构建能渲染的地方画 tofu。
生成器 `tools/gen_cjk_shards.py` 在并集 ≠ `tools/cjk_vector_codepoints.txt` 时**拒绝生成**。

### 4.4 实施

- `tools/gen_cjk_shards.py`：每分片一个 `cjk_shard_<id>.{rs,ttf}` + 索引 `cjk_shards.rs`；
  表按**码点顺序**输出（`shard_for` 的 `find` 只有在区间升序且不交时才无歧义）；
- `cjk_shards.rs`（生成，146 行）：`Shard { id, name, bytes, range }`、`SHARDS`、`shard_for(ch)`、
  `active_shards()`、`total_bytes()`；
- `src/render/text/font_assets/cjk_shard_loader.rs`（209 行）：`load_shard_for(ch)` 查 `shard_for`
  并把该分片字节**注册进运行时表**（依赖方案 1）——这就是"按需加载"的落点；
  `ShardLoad::{Loaded, NotInThisBuild, NotCovered, RegistryFull}` 三态以上回报，区分"无分片覆盖"
  与"本构建不带该分片"；
- `load_shards_for_text(text)`：按字符串一次加载所需分片。

### 4.5 接线验证

```text
wired: load_shard_for('中') -> Loaded
```

（分离出来跑时返回 `Loaded`；分片确实被注册进运行时表。）

### 4.6 门禁

`tools/check_cjk_shards_cover_the_face.sh`（4 项断言，已反向注入）：

```text
[1/4] the shard list parses and is disjoint                     PASS  (5 shards, 1391 codepoints)
[2/4] the shards partition the fonts-cjk coverage                PASS  (1391 == 1391)
[3/4] the committed shard files match the list                   PASS
[4/4] the crate builds with the shards on                        PASS
check_cjk_shards_cover_the_face: OK
```

**反向注入**（把 `symbols: 3000..303F` 改为 `3000..301F`）：

```text
[2/4] the shards partition the fonts-cjk coverage
  32 codepoint(s) in the face but in no shard: U+3020, U+3021, ... U+3029
  FAIL  the shards do not partition the face
```

→ 门禁确实能报红并**指名**缺失码点。

### 4.7 feature 设计

```toml
fonts-cjk-shards = [5 个分片 feature]   # 元 feature
fonts-cjk-shard-{latin,symbols,kana,han,fullwidth} = ["text-shaping"]
```

`fonts-cjk`（单块）**保留**：它是"一次全部驻留"的答案；分片是同一覆盖的拆分，宿主按"一次全要还是
一次要一个脚本"选择。

### 4.8 与既有门控的整合（原则 #47）

`fonts-cjk` 与分片是**同一能力**（`VectorSource` 能画的 CJK 轮廓），因此所有"有 CJK 轮廓 face 吗"
的门控必须接受任一。该析取在 20+ 处出现，故在 `build.rs` 定义别名：

```rust
println!("cargo:rustc-check-cfg=cfg(cjk_outline_face)");
// fonts-cjk ∨ 任一 fonts-cjk-shard-*
if cjk_outline { println!("cargo:rustc-cfg=cjk_outline_face"); }
```

并将 `svg/backend.rs`、`raster.rs`、`text/mod.rs`、`glyph_source.rs`、`font_assets/mod.rs` 的
能力门控改为 `cjk_outline_face`。**数据门控**（`CJK_FACE` 常量、`active_faces` 数组长度）仍是
`fonts-cjk`——分片经运行时注册，不进 `active_faces`。

## 5. 方案 4 —— fallback 与数据同源

### 5.1 缺陷取证

`icon.rs` 原有 **31 个手写 `draw_*` 方法**（约 900 行）作为 `icons` feature 关闭时的 fallback。
这是**第二真相源**：`research-icons.md` §2.4 记录了它导致的真实缺陷——

> `Close == Cross`：`icon.rs` 用**一个**方法画两个名字，两个不同 token 产生逐字节相同的图。

即两份实现已经漂移过一次。

### 5.2 实施：fallback 从同一份 SVG **派生**

扩展 `tools/gen_icon_data.py`，新增 `render_fallback()` + 一个简化 SVG `d` 展平器
（`flatten_path`，支持 `M m L l H h V v C c Q q T t Z z` 及隐式重复），产出
`src/widget/icon_fallback_data.rs`（304 行）：

- 每个 token 一条 `IconFallback { name, grid, contours: &[&[(i16,i16)]] }`；
- 几何是**同一份** `tools/material_symbols/<token>.svg` 的粗展平——**派生而非手抄**，所以两条路径
  不可能对同一 token 描述不同形状；
- 粗粒度是**有意的**：fallback 不能链接 SVG 解析器（否则 `icons` 关闭的构建反而背了 parser），
  故用固定细分的展平。

`icon.rs` 中：

- 删除 31 个 `draw_*` 方法（**-993 行**，1839 → 1046 行）；
- `draw_fallback()`：查 `ICON_FALLBACK`，用与 `draw_outline` **相同**的 grid→device 映射填充多边形；
- `draw_icon()`：`icons` 开 → 数据路径（不变）；否则 → `draw_fallback()`。

### 5.3 接线验证

默认构建（`icons` 开）**仍走数据路径**，SVG 快照逐字节不变——见 §6.2。无 `icons` 构建走 fallback，
测试断言其产出真实轮廓（`<path>`）而非占位（`?`）。

### 5.4 测试

- `a_tokened_icon_still_draws_without_the_data`（无 `icons` 构建）：断言 `<path>` 存在且非占位；
- `the_fallback_table_is_complete_and_distinct`：表与 `IconName` 等长、顺序一致、每条有 ≥3 点轮廓、
  且**无两条逐字节相同**（`Close == Cross` 规则施加到 fallback）。

```text
test result: ok. 14 passed; 0 failed   (desktop，无 icons)
```

## 8. 追加任务 2 —— 方案 5 的微基准（`benches/font_bench.rs`）

### 8.1 设计：为何是 `cached` vs `uncached` 而非绝对耗时

单独的绝对耗时不说明任何问题——它无法区分“缓存有效”与“解析本来就便宜”。因此基准测量的是
**同一 lookup 的有/无缓存之比**，比值才是缓存的效果。

为使该比值成立，新增 `#[doc(hidden)] pub fn face_for_char_uncached(ch)` 作为对照（bench 是外部
crate，`pub(crate)` 无法跨越）。并加测试 `the_cached_and_uncached_lookups_agree` 钉死“两者返回
完全相同”，否则基准会静默变成苹果比橘子——缓存若因槽位/世代 bug 返回了不同的 face，所有计时
看起来都“合理”。

三个测量组：
1. `face_for_char/repeat` —— 单字符反复查（缓存的目标场景）；
2. `face_for_char/caption` —— 一段**不同**字符的短标题循环（真实标签的形状，且验证 direct-mapped
   槽在标题长度内不冲突）；
3. `paint_active 16x16` —— 缓存所在路径的端到端（`paint_active` → `VectorSource`），
   含 CJK 字形（走两个 face：Latin 说否、CJK 说是）。

### 8.2 实测结果（`cargo bench ... --bench font_bench -- --quick`）

```text
face_for_char/repeat/cached      time: [22.188 ns 22.250 ns 22.265 ns]
face_for_char/repeat/uncached    time: [662.67 ns 669.62 ns 697.44 ns]
                ^ 约 30× 差距

face_for_char/caption/cached     time: [178.61 ns 180.24 ns 186.76 ns]
face_for_char/caption/uncached   time: [5.6634 µs 5.6917 µs 5.8048 µs]
                ^ 约 31× 差距

paint_active 16x16/latin 'A'     time: [127.97 µs 129.08 µs 133.51 µs]
```

**解读（诚实）**：
- lookup 层：缓存把 ~670 ns 的重复 `ttf_parser::Face::parse` 变成 ~22 ns 的槽读取（**~30×**），
  8 字符标题从 ~5.7 µs 降到 ~180 ns（**~31×**）。这证实方案 5 的缺陷判断属实且收益显著。
- `paint_active` 层：~129 µs 中查找只占约 0.5 µs，**光栅化才是主成本**。故缓存主要收益在
  **不伴随光栅化的查找路径**（测量/布局/`source_for`），而非绘制本身。该结论如实记录，
  不夸大为“绘制快 30×”。

### 8.3 接线与可运行性

- `Cargo.toml` 新增 `[[bench]] name = "font_bench"`，`harness = false`；
- `benches/run_benchmarks.sh` 新增 `run_bench_featured`（该 bench 需要 `fonts-vector-latin` 等
  face feature 才有可查对象），计数 5 → 6；
- `benches/font_bench.rs:146` 的空 `main` 与 wasm32 分支保留：bench 目标在任何配置都必须有 `main`
  （否则 `cargo check --all-targets --target wasm32` 报 E0601），与本仓其余 bench 同一约定。

### 13.6 一个**重要的过程教训**（诚实记录，原则 #19）

## 15. 修正 —— `tooltip` 测试的**假修复**（原则 #12）

### 15.1 背景：那个 fail 被"修"了，但修得不诚实

上轮结尾我发现全量测试曾有过一个失败：`tooltip::tests::a_shown_bubble_inverts_against_its_window`。
随后它"变绿"了（并发工作推进所致）。用户要求核实并修正。

### 15.2 取证：功能是对的，但**测试没验证它声称的东西**

独立探针（用 `render_widget_to_svg_on` + 主题真实背景）实测：

```text
=== DARK  ===  window=rgba(18,18,18)    bubble=rgba(228,225,229)   → 真反色 ✅
=== LIGHT ===  window=rgba(240,240,240)  bubble=rgba(49,48,51)      → 真反色 ✅
```

**控件本身的绘制是正确的。** 但测试有真缺陷：它用 `render_to_svg` 渲染，而该函数的背板是
**硬编码的 `Color::WHITE`**（见其自身文档）。后果：

- dark 态下"窗口"恒为纯白（亮度 1.0），气泡是浅灰（0.76）——**两者并非反色**；
- 断言却通过了，因为它**只看气泡的绝对亮度**（`> 0.5`），**从未读过窗口**。

一个叫 `inverts_against_its_window` 的测试不读窗口，就等于**没验证它声称守护的不变量**。
这正是原则 #12「禁止假修复」所指：测试绿了，但它声称验证的东西没被验证。

### 15.3 修正

1. 改用 `render_widget_to_svg_on(&mut tooltip, bounds, window)`，其中 `window` 取自
   `theme_manager().current_theme().colors.background`；
2. 新增**前置断言**：该外观的窗口必须确实是对应的深/浅（否则测试无意义）；
3. 新增**关系断言**（测试名所承诺的那条）：
   `assert!((bubble > 0.5) != (window_lum > 0.5), ...)` —— 气泡与窗口必须在中点**两侧**；
4. 把亮度计算提为命名 helper（`luminance` / `is_dark` / `luminance_of_inset_rect`），
   消除原来嵌在测试里的 `fn bubble_luminance` 重复件。

### 15.4 验证（含反向注入）

```text
$ cargo test --lib a_shown_bubble_inverts
test result: ok. 1 passed; 0 failed

# 反向注入：把气泡强制等于窗口色（破坏反色）
$ # src/widget/dialog/tooltip.rs:  let bubble_color = window_fill;
test result: FAILED. 0 passed; 1 failed
  断言：window 与 bubble 均 fill="rgba(18,18,18,...)"，反色关系被打破
```

→ 修正后的测试**能证红**，即它真的在验证"反色"这个不变量。
