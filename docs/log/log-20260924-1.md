## 1. 批 1 —— G-5 抗锯齿（`src/render/text/raster.rs`）

### 1.1 做了什么

新增 `VectorSource`，实现 `GlyphSource::paint`，把 `ttf-parser` 读出的轮廓**就地**光栅化成
每像素覆盖率。要点：

| 环节 | 做法 | 为什么 |
|---|---|---|
| 展平 | 自适应细分，`FLATTEN_TOLERANCE = 0.2` 像素 | 固定细分在曲率大的地方出折线、小的地方白算 |
| 填充 | 非零环绕，`SUBSAMPLES = 4`（每轴 4 次采样 ⇒ 16 级） | 16 级覆盖率足够平滑，代价是每像素 16 次判定 |
| 算法 | **两趟**：先按行累计穿越数，再扫描累计环绕决定内外 | 一趟方案要把环绕跨行携带，会在行边界泄漏成横向色带（见 §2.2 的真实 bug） |
| 上界 | `MAX_POINTS = 1024`/`MAX_CONTOURS = 16`/`MAX_SUBDIVIDE = 16` | 恶意或畸形轮廓不能撑爆栈 |
| 基线 | `ASCENT_SHARE = 0.82` | 字面量集中一处，不与测量侧的第二份抄写漂移 |

### 1.2 为什么它接进了同一条混合路径，而不是第二条

`blend_painted_glyph`（`src/render/pipeline/pixel_ops.rs`）原本只认 1 位点阵：它把每字节当
「全有/全无」再乘 `value as f32 / 255.0`。巧合的是**这正好就是覆盖率的语义** —— 1 位点阵写
`0`/`255`，矢量面写 `0..=255`，同一个 `blend_pixel` 对两者都成立。所以：

- **不需要**给矢量面开第二条绘制路径（原则 #8：一处事实一处抄写）；
- 每个既有快照**逐字节不变** —— 1 位面写出的仍是 `0`/`255`，混合结果与原矩形填充相同。

这是本轮最省的一段：抗锯齿是**接口已经预留好**的，补的是一个实现者。

## 2. 批 2 —— G-6 彩色 emoji（`color_bitmap.rs` + `png.rs`）

### 2.1 接口：第三种 ink（`InkKind`）

新增 `InkKind { Bitmap, Coverage, Color }` 与 `Painted { source, source_cell, ink }`。
`source_cell: None` 是「不能压成矩形」的钩子：彩色字形是**颜色**，不是 1 位位图的斜坡，
SVG 后端不可能用「每个源像素一个 `<path>`」表达它（原则 #7：宁可不画也不画错）。

`Painted` 还带 `bytes_per_pixel()` / `buffer_len()` / `is_coverage()` / `is_color()`，把
「这个 ink 的缓冲要多大」变成 `Painted` 自己的事实，而不是调用方自己推。

### 2.2 三个真实缺陷（都是「数字看起来对」那一类）

这一段是本轮最费时的部分，三个 bug 都属于「解析出来的数能算，但全是错的」：

#### 缺陷 1：`CBDT` imageFormat 17 的头长

原实现假设 PNG 紧跟 5 字节 `SmallGlyphMetrics`。实际字节是
`80 88 00 65 88 | 00 00 02 f2 | 89 50 4e 47 ...`——`00 00 02 f2` = **754**，正是 PNG 长度。

**取证**：查 OpenType 规范 `CBDT` 页的 *Format 17*，它是
`smallGlyphMetrics (5) + uint32 dataLen (4) + uint8 data[dataLen]`，所以 PNG 在 `+9`。

**修法**：新增 `image_format_header_len(17|18|19) = 9|12|4`，并**读 `dataLen` 而不是**用索引表
的偏移差。后者只在索引精确时才相等（格式 2 有常量步长、格式 1 的偏移可能含填充）。

```text
$ python3 -c "…读 emoji.ttf 的 CBDT…"
metrics (128, 136, 0, 101, 136)   # height,width,bearingX,bearingY,advance —— 都合理
data_len 754
png sig b'\x89PNG\r\n\x1a\n'  IHDR dims (136, 128)   # 与 metrics 一致
```

#### 缺陷 2：`png.rs` 的 inflate 缓冲少算每行 1 字节

`IHDR` 报 `136x128 depth=4 colour=3`，`row_bytes = (136*4+7)/8 = 68`，正确缓冲应是
`128*(68+1) = 8832`；原代码是 `height * row_bytes = 8704`。

**取证**：给 inflate 加临时 trace，`status=BadParam`、`produced=0`。Python `zlib.decompress`
在同一段 `IDAT` 上得到 `8832` 字节 ⇒ 缓冲确实小了。

**修法**：`expected = height * (row_bytes + 1)`（每行前面有一个 filter 字节）。

#### 缺陷 3：inflate 缺 `TINFL_FLAG_USING_NON_WRAPPING_OUTPUT_BUF`

`miniz_oxide::inflate::core::decompress` 默认把 `out` 当**环绕**缓冲，而环绕缓冲长度必须是
2 的幂 —— `8832` 不是，于是它直接返回 `BadParam`。即使加上该 flag，单次调用在 `out` 填满时
会返回 `HasMoreOutput` 而**不**保证一次算完。

**修法**：加 flag，并改成**流式循环**：按 `consumed`/`produced` 推进输入输出直到 `Done`；
`HasMoreOutput` 下若 `consumed == 0 && produced == 0`（无进展）或输出已满，判为拒绝。

#### 缺陷 4（同一批发现）：子字节位深不支持

`depth=4 colour=3` 是 **4 位调色板** PNG，原解码器 `_ => return None` 直接拒。
NotoColorEmoji 的小旗子正是这一编码，所以整个旗子类目会读不出来，而不是偶发。

**修法**：支持 1/2/4 位（仅 type 0/3），按 spec 高位先取：
`byte >> (8 - bits - offset)`；行步长 `(width +? )`→`(width * bits + 7) / 8`（按字节向上取整）；
`scale_to_byte` 改为按 `bits` 精确放大（`1→×255`、`2→×85`、`4→×17`），
**不是**除以 `1 << bits`——`1 << 4 = 16` 会把 15 映射到 239 而不是 255。

### 2.3 同一批的接口级缺陷（真正让功能不通的那个）

上面修完，`ColorBitmapFace::paint` 仍然 `None`。继续追到 `paint_active`：

```rust
// 修前
let Some(painted) = source.paint(ch, cell, out) else { /* 下一个 face */ };
```

`out` 由调用方提供，而 `blend_painted_glyph` 只给 `cell.area()` 字节（1 位用）。
彩色面要 `cell.area() * 4` ⇒ **彩色面永远「paint 不出来」**，栈就一路落到 8x8 或 tofu。
这解释了实测里 `source=tofu`：不是 face 读不出来，是**缓冲契约把彩色面排除了**。

**修法**：把契约写进文档；调用方按 `Painted::buffer_len()` 定缓冲。两条路径互斥：

| 调用 | 接受的 ink | 拒绝的 ink | 为什么 |
|---|---|---|---|
| `blend_painted_glyph` | `Bitmap` / `Coverage` | `Color` | 1 字节/像素是 alpha，不能当 RGB 读 |
| `blend_color_glyph` | `Color` | `Bitmap` / `Coverage` | 4 字节/像素自带颜色，不能再乘文字色 |

`draw_text`（`src/render/pipeline/primitives.rs`）先试 `blend_color_glyph`，返回 `false` 才走
`blend_painted_glyph`。因为两者**互斥**，每个字形恰好画一次，没有重复绘制。
`color_scratch` 只在 `fonts-emoji-color` 下分配 ⇒ 默认构建的分配量**一字不变**。

## 3. 批 3 —— 构建配置矩阵（冰山法则 #2：修一个，扫一类）

「抗锯齿 / 彩色 emoji 开起来能编译」这件事，本轮**逐个组合实跑**，发现并修掉两个独立的
配置缺陷 —— 它们都不是本轮引入的，而是**原本就在、只是没有组合去踩**：

| 缺陷 | 现象 | 修法 |
|---|---|---|
| `FaceBytes` / `active_faces` 只 gate 在数据 feature 上 | `text-shaping` 单独开启（或 `fonts-emoji-color,text-shaping`）时 `shaping.rs` / `raster.rs` 的 `use` 解析失败（E0432） | gate 改成 `text-shaping || fonts-vector-latin || fonts-complex`。理由：`FaceBytes` 是**塑形器的输入类型**，允许「有引擎、宿主自带 face、不带生成数据」是设计上就必须成立的组合 |
| `active_stack()` 用互斥谓词的多个 `let stack = …` | 所有 feature 全开时，前一个 `let` 不可达 ⇒ `unused_variables` + 若干静态量 dead-code 警告；且编译器**无法检查谓词覆盖了全部组合** | 重写成**一个互斥 `cfg` 静态量 + 最后一个兜底**的链式结构。16 种组合全部显式列出，最后一个 `not(any(...))` 是唯一兜底。顺带把「为什么顺序是这样」的四条规则写在函数开头 |

```text
$ for f in desktop / desktop,fonts-cjk-bitmap / desktop,fonts-vector-latin /
           desktop,fonts-complex / desktop,fonts-emoji-color /
           desktop,fonts-emoji-color,text-shaping /
           desktop,fonts-cjk-bitmap,fonts-vector-latin /
           desktop,fonts-emoji-color,fonts-cjk-bitmap /
           desktop,fonts-emoji-color,fonts-vector-latin /
           desktop,fonts-cjk-bitmap,fonts-vector-latin,fonts-complex,fonts-emoji-color,text-shaping
    do cargo build --lib --no-default-features --features "$f"
  done
  ⇒ 10 个代表组合全部 ok，0 warning / 0 error（16 种组合的其余 6 种是同构的）
```

`blend_color_glyph` / `blend_rgba_over_canvas` 也改成 `#[cfg(feature = "fonts-emoji-color")]`：
没有彩色面时**函数本身不存在**，而不是留一个「永远返回 false」的死代码（原则 #7）。

## 4. 修掉的第二个缺陷：`paeth` 的测试期望是错的

全量测试跑出一个红：`the_paeth_predictor_is_symmetric` 断言 `paeth(10,20,30) == 20`。

**取证**：`p = 10+20-30 = 0`；`pa=|0-10|=10`、`pb=|0-20|=20`、`pc=|0-30|=30` ⇒
`pa` 最小 ⇒ **返回 left = 10**。PNG 规范测的**不是**「谁在中间」，而是「谁最接近梯度
`left + above - corner`」，而这里梯度是 0。

```text
$ python3 -c "…按规范实现 paeth…"
paeth(10,20,30)= 10      # 不是 20
paeth(0,0,0)  = 0
paeth(255,0,0)= 255
paeth(0,0,255)= 0
paeth(255,255,0)=255
paeth(200,100,150)=150
```

**结论**：**实现是对的，测试期望是错的**。这类错误正是「测试写的时候还没跑过真实图像」的
典型症状 —— 与 §2.2 的三个缺陷同源（都是「看起来对」）。修法是改期望并**加三个规范用例**，
同时把这条推理写进注释。

## 5. 修掉的第三个缺陷：一条测试的身份在矢量栈下**本就不成立**

`the_bitmap_view_and_the_painted_coverage_agree` 断言「`paint` 的覆盖率 == `glyph_rects` 的矩形」。
在 `fonts-vector-latin` 开启时它**必然**失败 —— 矢量面在前，它**故意**产出部分覆盖率
（抗锯齿的定义），而 `glyph_rects` 返回的是 1 位面的答案。实测：

```text
left : [0, 0, 31, 0, …, 207, 79, …]      # 矢量面：0/255 之间的值
right: [0, 0, 255, 255, …, 255, 255, …]  # 1 位面：只有 0/255
```

**修法**：把这条测试 `#[cfg(not(any(feature = "fonts-vector-latin", feature = "fonts-complex")))]`，
并在文档里写清「它是 **1 位栈** 的性质」，以及用哪条命令去跑它。这不是把测试删掉 ——
矢量面的覆盖率身份由 `render::text::raster` 自己的测试保证。

## 7. 全量验证（§9 验收判据）

### 9.1 ✅ `fonts-cjk` 矢量版：已打包（`fonts-cjk`，361,704 字节）

#### 先量代价，再决定范围（不是拍脑袋）

用真实字体量出整条代价曲线，而不是假设「矢量版应该也能小」：

```text
$ python3 …（Noto Sans SC，逐档子集化）
symbols + kana        253 cps   127 KB
+ fullwidth forms     477 cps   190 KB
+ 500 Han             977 cps   274 KB
+ 1000 Han           1477 cps   396 KB
+ 2000 Han           2477 cps   612 KB
（与位图面完全同覆盖的 2342 cps）              581 KB
```

**位图面是 85 KB / 2361 字形；同覆盖的矢量面是 581 KB——贵 7 倍。** 这不是缺陷，是轮廓与
16x16 点阵的固有差别。这条数字决定了整个设计，也**正面印证**了 `blue23.md` §0A.4 约束 2 与
迁入的附录 G 的那句话：CJK 是「只需数据、不需塑形」的脚本，所以 `mini`/`embedded` 必须
能靠 85 KB 位图拿到中文。

#### 结论：两个面是**互补**，不是替代

| 面 | 覆盖 | 体积 | 给谁 |
|---|---|---|---|
| `fonts-cjk-bitmap` | 2361 字形，固定 16x16 | ~85 KB | `mini`/`embedded`：只要数据、不要塑形引擎 |
| `fonts-cjk` | 2053 字形，轮廓、任意 px | ~353 KB | `desktop`/`tablet`：要抗锯齿、要任意字号 |

`fonts-cjk` 刻意**只发小范围**（ASCII + CJK 标点 + 假名 + 全角 + 800 个最常用汉字），
码点表单独成文件 `tools/cjk_vector_codepoints.txt`（带理由注释），与 emoji 表同一模式：
「发哪些字」是一个**决定**，两份就不叫决定了。

#### 新增的东西

- `tools/gen_font_subset.py` 支持 `--face=cjk`，并对这个面强加
  **`CJK_VECTOR_BUDGET_BYTES = 400_000` 的预算门禁**：超了直接拒绝，并提示「要么改码点表，
  要么连 `NOTICE` 与 `Cargo.toml` 的体积数字一起改」——这是「体积不能悄悄涨」的机制保证。
  （写完就抓到自己一次：初版 1000 汉字 = 408,276 字节，超预算，门禁当场拒绝。）
- `Cargo.toml` 新增 `fonts-cjk = ["text-shaping"]`，注释里带上上面那张实测表。
- `NOTICE` 新增 Noto Sans SC 一节（上游 / URL / 上游 SHA-256 / OFL-1.1 / Modified Version /
  无 Reserved Font Name 取证 / 与位图面的分工说明）。
- `README.md` 的 feature 表新增该行，并写清「两个面是互补」「同时开启时位图赢」。

#### 修掉的真实缺陷（冰山法则）

1. **`fonts-cjk` 单独开启时 CJK 解析成 tofu。** `active_stack` 的 arm 只按
   `fonts-vector-latin`/`fonts-complex` 分支，`fonts-cjk` 会掉到「只剩 8x8」那条 arm。
   实跑抓到的：
   ```text
   U+4E2D source=None      # 有面，却不可达
   ```
   修法：补一条 `fonts-cjk` 单独的 arm（`[VectorSource, Font8x8Source]`），并在注释里写明
   它为何必要；末尾的兜底 arm 也补上 `feature = "fonts-cjk"`，否则那条兜底会把
   `fonts-cjk` 选中时也当成「无数据」，于是编译期选两条 arm。
2. **`the_bitmap_view_and_the_painted_coverage_agree` 的身份在矢量栈下不成立。**
   `fonts-cjk` 也是矢量面，同样产出部分覆盖率。把它的 gate 从两个矢量 feature 扩到三个。
3. **`a_character_outside_the_face_is_refused` 用 `U+4E00` 做「面外」样本，语义已失效。**
   那是「不在拉丁子集里」，而 `fonts-cjk` 一开它就在了。改成 `U+E000`（私用区），并写清
   推理：「不在一个面里 ≠ 不在所有面里；只有不在**每一个**已启用面里才是面外」。

#### 验证

### 9.2 ✅ 彩色/矢量字形进 SVG 快照：已实现（**用轮廓，不是裁定不做**）

上一轮的「明确不做」结论**不成立**，因为漏了一条路：**彩色字形的 `CBDT` 位图没法压，
但矢量面的轮廓可以。** 而且矢量面本来就在产出轮廓——它只是没被 SVG 后端用上。

#### 修的是什么

新增 `text::outline(ch, cell, family, points, contours)`，把与光栅器**同一份**
`Flattener`/`Placement` 展平出来的多边形交给矢量后端；SVG 后端按 feature 选择：

| 墨的类型 | 后端发射 | 为什么 |
|---|---|---|
| 1 位点阵 | `M{x} {y}h{w}v{h}h-{w}z` 矩形（原样） | 8x8 格子里的 1 位就是整像素，矩形是**精确**几何 |
| 轮廓 | `M{a.b} {c.d}L…Z` + `fill-rule="nonzero"` | 抗锯齿的轮廓反过来会**低估**墨；`nonzero` 让 `o` 的内环仍是洞 |
| 彩色 | 不属于轮廓面 → 落到 1 位路径画 tofu | 可见的降级，不是悄悄画错（原则 #7） |

#### 这一路踩出的四个真实缺陷

前三个是产品缺陷，第四个是测试缺陷，全部有实跑取证：

1. **`outline` 的轮廓打包算错。** 原写法 `points.get_mut(index * MAX_POINTS ..)`，而
   调用方的切片只有 `MAX_POINTS` 长，于是**任何有两个轮廓的字形（`A`、`o`…）都返回 `None`**，
   静默掉回矩形路径。修法：改成**紧凑打包**（contour `i` 占
   `points[contours[i].0..contours[i].1]`），并把这条推理写进函数文档。
   抓它的断言是**轮廓数**（`'A'` 必须是 2），不是任何覆盖率断言。
2. **`outline` 按覆盖选面，不按 `Font::family`。** 这是最隐蔽的一条：布局测量走
   `shaping::face_for_family`（按 family 名选），而 `outline` 原来只是「找第一个覆盖的面」。
   于是 `Font::new("Arial", 11.0, …)` 在只发 Open Sans 的构建上**测得是估算模型**
   （0.6 em/簇），却被画成 Open Sans 的轮廓——墨的宽度与布局预留的宽度不是一个数。
   实跑：18 个控件的「墨在自己的盒子里」断言全红。修法：`outline` 接受 `family` 并用同一个
   `face_for_family`。**修完 18 → 1**（剩下的 1 个是我自己新写的测试用了不存在的 family）。
3. **`widget/svg.rs` 的路径读取器只认整数与 `M`/`h`/`v`/`H`/`V`。** 轮廓发的是
   `M21.45 30.24L…`，整数读取器在 `.` 处返回 `None`，于是 `path_bounds` 对每个矢量字形
   都答「没有墨」。修法：`number` 改读 `f32`，`path_bounds` 增加 `L`/`l`/`m`；`include`
   两端都取 `floor`（**不是** `floor`/`ceil`——后者会把盒子的**中点**移半像素，让
   「墨在这一行的中线上」这类断言差 1）。
4. **`shaping::tests::the_face_a_family_names_is_the_face_that_is_used` 的 gate 太宽。**
   它断言 Open Sans，但模块 gate 是 `any(vector-latin, complex)`，于是 `fonts-complex` 单独的
   构建上必然失败（那个构建里 Open Sans 根本不存在）。修法：单独 gate 到 `fonts-vector-latin`，
   并写明「它断言的是**那个构建**的事实，不是在断言别的构建」。

#### 为什么默认构建继续逐字节不变

`fill-rule` 只在**存在轮廓面**时发射，`append_outline` 也整个 feature-gate。默认构建的代码
路径与改动前**完全一致**：

```text

sample-filled=22
$ git status --short snapshots/ control.md      # 空 = 逐字节不变
$ （再跑一次，输出同样逐字节相同 = 幂等）
$ bash tools/check_svg_snapshots.sh
check_svg_snapshots: checked=188 skipped=0 failed=0
```

#### 与 §9.1 的交叉验证

`fonts-cjk` 与 `fonts-vector-latin` 的 SVG 探针都给出 `L` 命令与小数坐标；默认构建给出
纯矩形、无小数。三个构建、三条路径、各自被自己的断言钉住。

### 9.3 ✅ `inflate_into` 的拒绝路径：已补 6 个针对性用例，并删掉一段死代码

原来「只被真实 emoji PNG 走过」的判断是对的——先给两个 guard 加插桩跑全量，**一次都没触发**。
于是直接做**变异测试**（改掉 guard，看测试是否变红），结果推翻了我一开始的判断：

| guard | 变异后的结果 | 结论 |
|---|---|---|
| 无进展（`produced == 0 && consumed == 0`） | 测试**挂死**（exit 143，超时被杀） | **真实承重**，保留 |
| 短输出（`out_pos != out.len()`） | 一条测试 **FAILED** | **真实承重**，保留 |
| 输出满（`out_pos >= out.len()`） | **无任何变化** | **死代码**，**删除** |

第三条的删除有取证——直接对 `miniz_oxide` 实测一个满缓冲的行为：

```text
status=HasMoreOutput consumed=28 produced=16   # 第一次调用把 16 字节缓冲填满
status=HasMoreOutput consumed=0  produced=0    # 第二次调用：没东西可做了
```

所以满缓冲是**下一轮**被「无进展」guard 接住的，`out_pos >= out.len()` 永远不会先触发。
把它删掉比给它写一个「永远为真」的测试诚实得多（原则 #7：不留看起来能用的死代码）。

新增 6 个用例，并把上面这些推理写进各自的文档注释：

| 测试 | 断言 |
|---|---|
| `a_stream_that_ends_before_the_output_is_full_is_refused` | 截断流（`BFINAL` 提前）拒绝 |
| `a_stream_longer_than_the_buffer_is_refused` | 超出缓冲拒绝 |
| `a_stream_that_fills_the_buffer_and_continues_is_refused` | 满缓冲且还有后续 → 拒绝，**且第一块的字节确实写入了** |
| `garbage_is_refused` | 空流 / 非 zlib / 只有头，三种都拒绝 |
| `an_empty_output_buffer_is_refused` | 零长输出在 inflate 前就拒绝（否则死循环） |
| `a_stream_is_inflated_across_more_than_one_call` | **正向用例**：8832 字节（非 2 的幂）一次以上调用解出**完全相同**的字节 |

（最后一条是关键：它是唯一能证明流式记账正确的用例——少了 non-wrapping flag 会 `BadParam`，
少了循环会在第一次 `HasMoreOutput` 停下，两种都得不到这些字节。）

## 12. 一句话结论

**三项遗留全部收口，而且没有一项是靠「降低标准」收口的。**

- §9.1 的 `fonts-cjk`：先量出「同覆盖贵 7 倍」这条事实，再据此把它设计成**与位图面互补**的
  面（小范围、可选、带 400 KB 预算门禁），而不是硬塞一个 581 KB 的版本冒充「更好的 CJK」；
- §9.2 的 SVG 快照：上一轮判「不做」是**错的**——漏了一条路（轮廓可以压，彩色 CBDT 不行）。
  改用 `text::outline` 后，矢量面与 CJK 面都进快照，且默认构建**逐字节不变**；
- §9.3 的 inflate 拒绝路径：先用插桩确认「一次都没触发」，再用变异测试**推翻自己的判断**
  ——两个 guard 承重、第三个是死代码。删掉死代码比给它编个测试诚实。

最值得记的一条：§9.2 工作里最难的那个 bug（`outline` 按覆盖选面而不按 `Font::family`）
**不是**「画错了」，而是「**测量与绘制用了两个不同的面**」—— 18 个控件同时红掉。
能一次抓住它的不是某个像素断言，而是「墨必须落在布局预留的盒子里」这类**跨层一致性**断言。

### 14.1 先量准确数字，不引用计划

上一轮 §0A.1 记的是「剩余 47 个（`ime_macos` 21 / `macos_objc2` 10 / `ios` 9 / `android` 7）」。
逐个数一遍，**其中两组其实本来就能跑**：

### 14.2 根因：一个 `cfg` 把整块测试也关掉了

两个模块都写着同一句话：

```rust
// src/platform/mod.rs（修前）
#[cfg(all(any(feature = "macos", feature = "cocoa-legacy"), target_vendor = "apple"))]
```

而它需要 `libc`，只有 Apple 目标有。但**代价是连 `tests.rs` 一起关掉了**——而 `tests.rs`
里的 10 条断言**只碰 `Platform` trait 接口**，一行 AppKit 都没有。

`ime_macos.rs` 早就在用正确的写法：模块无条件声明，**只在 AppKit 调用点**加 gate。
所以这不是新发明，是把这个既有模式应用到另外两个模块。

### 14.3 修法：把 gate 从「模块」下移到「调用点」

```rust
// 修后（三个探针各自如此）
fn total_memory_mb(&self) -> Option<u64> {
    #[cfg(target_vendor = "apple")]
    { crate::platform::darwin_probes::total_memory_mb() }
    #[cfg(not(target_vendor = "apple"))]
    { None }
}
```

**两个分支是同一个谓词的正反，所以任何主机上恰好编译一个。**

「非 Apple 分支会不会被真实代码走到？」——不会，需要看两处**选择**规则仍然在：

```text

$ grep -n "target_os = \"ios\"" src/platform/runtime.rs
fn create_native_platform() -> Box<dyn Platform> {   // #[cfg(all(..., target_os = "ios", ...))]
    Box::new(IosMobilePlatform::new())               // ⇒ 选择仍限 iOS
}
```

也就是说：**类型和它的测试到处都能编译，但后端只在对应宿主上被实例化。**

## 15. ✅ ITEM 0「编译期路由闭合」：缺的那半条已补（并发现它差一个字就失效）

### 15.1 现状：编译器**真的**在拦

这就是 ITEM 0 说的「编译期强制」，它**已经成立**。所以剩下的问题不是「加一个检查」，
而是「这个检查有多脆」。

### 15.2 脆在哪：一个通配 arm 就让它彻底失效

穷举 `match` 是整个保证的唯一载体。而**追加一行**就是它死掉的方式：

```rust
WidgetKind::DropZone => ControlRoutePreference::CustomRequired,
_ => ControlRoutePreference::CustomRequired,     // ← 这一行让上面全部作废
```

实跑——加了这一行之后，**本项目没有任何东西能看出来**：

```text
$ （追加 `_ =>` arm）
$ cargo test --lib --features desktop control_backend::routing
test result: ok. 2 passed; 0 failed          # 全绿
$ bash tools/check_control_route_matrix.sh
Control route matrix generated …             # 仍然 0 missing（运行时矩阵看的是 routing.rs 的
                                             # 解析结果，而解析器仍然能解析出 180 条路由）
```

**结论：运行时门禁证明不了编译期保证。** 它俩量的是不同的东西。

### 15.3 修法：门禁检查的是「**不存在**通配 arm」

新门禁 `tools/check_routing_match_is_exhaustive.sh` + 扫描器 `tools/routing_match_scan.py`：

1. `route_is_library_painted` 还在，**且**里面还有一个 `match`；
2. 那个 `match` 里 **没有** `_ =>` arm；
3. 函数体里没有字符串字面量（否则它自己的注释剥离器就不可信，这点如实报出来而不是假装扫过）。

**关键设计**：它断言的是一个**缺席**，因为「函数存在」会被它要防的那个编辑满足。
这是本节能立住的原因——一个检查必须**不可能被它防的变异满足**。

反向注入：扫描器跑在一份「追加了 `_ =>`」的副本上，必须报 finding：

```text
while covering nothing: adding a `WidgetKind` variant would then be routed silently.
matches=1 wildcards=1 findings=1
$ bash tools/check_routing_match_is_exhaustive.sh; echo exit=$?

```

而正常树上：


## 18. 🔴 顺带修掉一个**缓存引入的假失败**（`check_generated_sources`）

全量门禁跑到第二轮时出现 `FAIL: check_generated_sources.sh`，且**只在缓存热的时候出现**。

### 18.1 取证：先确认不是自己的改动

```text
$ bash tools/check_generated_sources.sh
FAIL: examples/generated_project commits no generated source.
$ ls examples/generated_project/src/generated/
（目录不存在）
$ git status --short examples/generated_project/
 D examples/generated_project/src/generated/ui_default.rs      # 被删了
 D examples/generated_project/src/generated/ui_stripped.rs
```

### 18.2 隔离：一句话就能证明是缓存

```text
$ rm -rf target/gate-cache && bash tools/check_generated_sources.sh
generated-source checks passed.                 # 过了，且目录完好
$ RW_GATE_NO_CACHE=1 bash tools/check_generated_sources.sh
generated-source checks passed.                 # 也过了
```

⇒ 与我的改动无关，是**缓存本身**的问题。

### 18.3 根因：`rw_cargo_cached` 会重放**输出**，但不会重放**副作用**

`designer_generate` 是一个**会产生文件**的生成器，而门禁的 `REGENERATE_IN_PLACE` 是：

```bash
rm -rf "$PROJECT_DIR/src/generated"          # 先删
GENERATE "$PROJECT_DIR" "$PROJECT_DIR/project.json"   # 再生成 ← 走 rw_cargo_cached
```

缓存命中时，`GENERATE` 把上次的 stdout（`created …`）重放出来，**命令根本没运行**。
于是目录被删掉、没有重建、下一步就报「commits no generated source」。

`lib_cargo_cache.sh` 的文档把缓存定位成「不重复做输入相同的工作」，这个前提对
`check`/`test`/`clippy` 成立（它们只写 `target/`），对**生成器不成立**。

### 18.4 修法：生成器不走缓存

```bash
GENERATE() {
  # **不走** rw_cargo_cached：designer_generate 会写 $root/src/generated/*.rs，
  # 而缓存重放输出但不重放副作用。$root 还可能位于树外的 scratch 目录，缓存键
  # 会指向 project 而不是那份副本。
  rw_run_bounded "$GATE_TIMEOUT" cargo run --quiet \
    --no-default-features --features desktop,designer --example designer_generate -- …
}
```

并在 `lib_cargo_cache.sh` 的文档里把这条**约束**写清（「只用于纯步骤」），
连同上面那次的实测经过——否则下一个人会把同一个生成器再接回缓存。

### 18.5 验证：连跑两次 + 注入仍在

```text
$ bash tools/check_generated_sources.sh; echo $?      # 预热后第 1 次
0       目录完好
$ bash tools/check_generated_sources.sh; echo $?      # 第 2 次（缓存已热）
0       目录完好
$ bash tools/check_generated_sources.sh | grep detected
    detected: the edited document generates different bytes      # 注入 (a) 仍然生效
    detected: the lint step refuses the needless `mut`           # 注入 (b) 仍然生效
```

**一个门禁不能因为「缓存让它更快」而变成假绿或假红** —— 这条与文件顶部
「⚠️ The one thing this must never do」是同一件事的两个方向。

## 23. §4.1 —— `group_box` 的勾：缺陷比原文记的更深一层

### 23.1 先看清「框填充的对比色」为什么算不出来

修前的代码是：

```rust
let box_color = style.border_color.unwrap_or(Color::rgb(100, 100, 100));
context.draw_rect(checkbox_rect, box_color);            // ← 只描边，没有填充
if self.checked {
    let tick_color = style.background_color              // ← 有主题时是 Some(theme.background)
        .unwrap_or_else(|| box_color.contrast_color())  // ← 无主题时：算的是**描边色**的对比色
        .contrast_color();
```

实测（本轮第一条测试，**在加任何断言之前**先跑旧实现）：

```text
$ cargo test --lib --features desktop groupbox::tests::the_tick
panicked: on a dark appearance the tick must be the light extreme, not (0, 0, 0)
```

**这是本轮第一条真实缺陷。** 它只在**没有主题**时出现，所以：

* 有主题时 `style.background_color` 是 `Some(theme.background)`，这条分支**恰好**给对
  （暗态背景暗 ⇒ 对比色白）；于是 `group_box_checked.svg` 看起来是对的；
* 无主题时走 `box_color.contrast_color()`，而 `box_color` 是**描边**的中灰 `(100,100,100)`，
  `relative_luminance > 0.179` ⇒ 返回**黑**。

**「框填充」在原实现里根本没有指涉物** —— 这就是条款里「勾取框填充的对比色」这句话
在源码里落不下去的原因。修法不是改颜色，是**先让框有填充**。

### 23.2 修法：抄 `CheckBox` 的推导（一处事实一处抄写）

`src/widget/base_widgets/checkbox.rs:445` 早已这样做：`surface = style.background_color
.unwrap_or(WHITE)`，`field` 是该面对，`check_color = field.contrast_color()`。
`GroupBox` 的指示器是**同一个东西**（一个可勾选的方框），所以逐字相同：

```rust
let box_color = style.border_color.unwrap_or(Color::rgb(100, 100, 100));
let field = style.background_color.unwrap_or(Color::WHITE);   // ← 新增：框自己的填充
context.fill_rect(checkbox_rect, field);                      // ← 新增：把它画出来
context.draw_rect(checkbox_rect, box_color);
if self.checked {
    let tick_color = field.contrast_color();                  // ← 现在有指涉物了
```

### 23.3 测试：断言的是**两个发射值之间的关系**，而且两种外观各跑一遍

写这条测试踩了两次坑，都记下来，因为它们是「测试看起来在测、其实没测」的标本：

| 版本 | 写法 | 变异测试的结果 |
|---|---|---|
| v1 | 自己算 `box_color.contrast_color()` 再和自己比 | 注入 `Color::BLACK` **仍然通过** ⇒ **不承重** |
| v2 | 无条件断言 `tick == WHITE` | 在**无主题**下会**要求一个 bug**（正确的对比色是黑） |
| v3（本轮） | 从**SVG 文档**读出发射的填充与描边，断言 `tick == fill.contrast_color()`，并对**明暗两态各跑一次** | 注入黑 ⇒ 红；注入白 ⇒ 红（对另一态） |

v3 还多一条**聚合**断言 `assert_ne!(seen_ticks[0], seen_ticks[1])`：
两个外观给出**同一个常数**的勾色，说明它没跟着填充走 —— 这条正是「常量混不过去」的保证。

两种外观的安装方式与导出器**逐字相同**（`install_preset_appearances()` +
`apply_theme_to_widget()` + `render_widget_to_svg_on(…, backdrop)`），
所以单测与 `group_box_checked.svg` 描述的是**同一张图**。

### 23.4 反向注入（两条都做）

```text
$ （注入 `let tick_color = Color::BLACK;`）
  tick stroke 0 ((0, 0, 0)) must be the contrast colour of the box fill (30, 30, 33) ...
  left: (0, 0, 0)   right: (255, 255, 255)          ⇒ FAILED

$ （注入 `let tick_color = Color::WHITE;`）
  tick stroke 0 ((255, 255, 255)) must be the contrast colour of the box fill (243, 237, 247)
  left: (255, 255, 255)   right: (0, 0, 0)          ⇒ FAILED
```

**一条断言被两种相反的常量各自击穿** —— 这就是「它测的是关系而不是值」的证据。

### 23.5 快照

```text
group_box.svg（暗态、未勾选）    : 指示器有填充，**0 条 `<line>`**（勾不画）
group_box_checked.svg（暗态、勾选）: 指示器填充 rgba(30,30,33)，勾 stroke rgba(255,255,255)
group_box.light.svg（浅色）      : 指示器填充 rgba(243,237,247)
```

`sample_fill.rs` 的 `group_box` 臂现在 `set_checked(false)`，与
`EXTRA_APPEARANCES` 的 `_checked` 态**分工**：默认文件是「调用者拿到的样子」，
额外文件是「用户切过去的样子」。两态都不再被另一态的存在暗示。

## 24. §5.1 —— `scrim`：缺陷**就在为了修它而引入的 token 里**

### 24.1 判据 15 的第一手实测

```text
$ head -6 snapshots/svg/bottom_sheet.svg      # 修前
  <rect x="0" y="0" width="240" height="60" fill="rgba(255,255,255,0.15)" />
$ # 背景是 rgba(18,18,18) ⇒ 合成 (18*0.85 + 255*0.15) ≈ 53
```

**暗态的模态遮罩把背板照亮了：`18 → 53`。** 这正是 BLUE21 B23 描述的缺陷，
**换了一个形式回来**：B23 的修法是「引入 `scrim` token，朝绝对暗色混」，
而暗态预设**把该 token 写成了白色薄幕**：

```rust
// src/theme/manager.rs（修前）
// A dark theme cannot dim by *darkening*: the scrim has to be a light veil over a dark surface,
// which is the whole reason the role exists rather than an inline translucent black.
scrim: Color { r: 255, g: 255, b: 255, a: 38 },
```

那句注释是**论证反了**：B23 表格里列的四个平台（Material `Colors.black54`、UIKit、
参考工具包、主流声明式实现）**没有一个把背板往前景方向调**。
「暗色主题不能靠变暗来 dim」是错的——它能，而且必须。

### 24.2 修法

```rust
scrim: Color { r: 0, g: 0, b: 0, a: 130 },   // themes/dark.json 同步
```

**为什么不是浅色的 `a=82`**：B23 的第二条发现是「两者落到 121/122，几乎同一个数」——
那是「该表达式是两套预设的**巧合**而不是派生量」的特征。暗色面更暗，要达到同等分离度
就需要更重的幕，故 `130 > 82`；这条**关系**进了断言，而不是把 130 写死。

### 24.3 两条断言（都写成关系）+ 反向注入

```text
$ bash -c '（改回白幕）; cargo test … modal_bottom_sheet::tests'
the_scrim_composites_darker_than_the_backdrop ... FAILED
   the Dark scrim must dim the page: Color { r: 18, … } -> Color { r: 53, … } (scrim …) is a lift
the_two_appearances_do_not_share_one_scrim_number ... FAILED
   a near-black backdrop needs a heavier veil than a light one (dark rgba(255,255,255,38), light rgba(0,0,0,82))
```

修后两条都绿；`bottom_sheet.svg` 的遮罩变成 `rgba(0,0,0,0.51)`（压暗，不是提亮）。

> **被删掉的旧断言**：`the_scrim_reads_its_role_and_darkens_the_backdrop` 里写着
> 「a dark one dims by a light veil」——它**把缺陷写成了期望**，所以白幕在它面前是全绿的。
> 这就是「测试和实现共享同一个错误假设」的标本：它断言的是 `scrim != window`
> 和**回落**的亮度，两个都对，而用户看到的那一层从没被比较过。

## 25. §4.3 —— `scroll_area` 的滚动条下限：`10` 与全仓 `48` 打架

```rust
// 修前
let thumb = proportional.clamp(10, track_len as u64) as u32;
// 修后
let thumb = proportional
    .max(dimensions::SCROLLBAR_MIN_LENGTH as u64)
    .clamp(1, track_len as u64) as u32;
```

`10` 比槽还窄（`SCROLLBAR_THICKNESS = 8` 的槽里放 10 px 的拇指——不是一个能抓的把手），
而全仓早就有一个 `dimensions::SCROLLBAR_MIN_LENGTH = 48`。**同一个问题两个答案**，
本条把 `thumb_metrics` 接到既有常量上（`draw_sticky_band` 本来就是这么读常量的）。

**「最小长度是分数而非常量」** 这条语义也在：`proportional` 仍是主体，
常量只是它的**地板**（`.max(...)`），并被 `clamp(1, track_len)` 限制在轨道内
（比地板还短的轨道不会溢出自己的槽）。

新增三条测试，其中一条是**性质**断言（写成 `const` 块，失败在编译期）：

```rust
const { assert!(dimensions::SCROLLBAR_MIN_LENGTH >= dimensions::SCROLLBAR_THICKNESS) };
```

反向注入（下限改回 `clamp(10, …)`）⇒ `thumb_metrics_proportional_and_tracks_scroll` 与
`thumb_metrics_never_collapses_below_minimum` **同时变红**（`left: 40 / 10, right: 48`）。

> **如实记**：本节**不产生快照 diff**。`scroll_area` 的 240x120 快照没有可滚动内容，
> `chrome.horizontal` / `chrome.vertical` 都是 `None`，所以滚动条根本不画。
> 这条判据在**源码级**（单元测试），不在图上——不假装 377 张快照里能看到它。

## 30. `toggle_button`（A.2，P0）—— 状态枚举缺两态，用户悬停/按下**毫无反馈**

### 30.1 实测确认缺陷（先量，再改）

```text
$ grep -n "enum ToggleButtonState" -A 8 src/widget/base_widgets/toggle_button.rs
pub enum ToggleButtonState { Normal, Checked, Disabled }      # 只有 3 态

$ grep -n "is_pressed\|hovered" src/widget/base_widgets/toggle_button.rs
:149 pub fn is_pressed(&self) -> bool { self.base.is_pressed() }   # 维护了…
（而 `draw` 里 `state()` 只看 enabled/checked，**两个瞬时态都到不了枚举**）
```

计划记的「有 `pressed` 字段但 `draw` 不读」准确。后果是：**控件矩形内的每一次悬停、
每一次按住都不画出任何区别**，用户只能靠松手后 latch 翻转那一下才知道点到了。

### 30.2 修法（三步，与计划的 ①②③ 一一对应）

**① 状态枚举补上 `Hover` / `Pressed`** —— 并且**顺序是决定**，不是排版：

```rust
Disabled > Checked > Pressed > Hover > Normal
```

`Checked` 与 `Disabled` 是**持久事实**，`Hover`/`Pressed` 是**瞬时事实**，
所以持久者优先，瞬时者作为 draw 层的**叠加**（这正是 `Widget::widget_state` 的文档描述的
那条分层规则）。这个顺序同时保证 `state` 属性对既有读值**向后兼容**：
一个 checked+hovered 的按钮仍然报 `"checked"`。

**② 接 M1/M2** —— M1 是零代码的（读 `BaseWidget`）；M2 已经在预设里
（`toggle_button:hover` / `:pressed` / `:disabled` 三个键，`preset_states.rs` 早已生成）。

**③ 接 M3** —— 抄 `Button` 的原型：一个 `Transition` 字段 + `interaction_target_progress()`
+ `tick` + `is_animating`，并把它**上提到 `Widget` trait**（一行，否则宿主拿着
`&mut dyn Widget` 推不动它 —— 那正是 §3 那条总线存在的理由）。

### 30.3 踩到的两个真坑（都记下来，因为它们是同类工作的固定陷阱）

#### 坑 1：`theme_manager()` 是 `MutexGuard`，**画的时候不能再取**

第一版把守卫绑在局部（`let manager = theme_manager(); let theme = manager.current_theme();`），
然后下面调用 `layer_color(...)` / `semantic_color(...)` —— 它们内部**再取同一个非重入锁**。

```text
$ cargo test … toggle_button::tests::the_interaction_transition
（挂死，120 s 超时被杀）
```

修法：**先把要用的三个角色取成值，再放掉守卫**：

```rust
let (outline, outline_variant, disabled) = {
    let manager = crate::style::theme_manager();
    match manager.current_theme() {
        Some(active) => (Some(active.colors.outline), Some(active.colors.outline_variant), Some(active.colors.disabled)),
        None => (None, None, None),
    }
};   // ← 守卫在这里释放
```

`slider.rs` 的既有注释早就写着这条规矩（「The theme read is a separate manager lock,
taken and released inside `resolved_theme_style`, so it is not held across the draw —
the global manager's mutex is not re-entrant」）。**它是对的，而我第一次没照做。**

#### 坑 2：快照里第一个 `fill="rgba("` 是**底板**，不是控件的面

渲染辅助函数读第一个 `fill="rgba(`，于是对**每个**控件都返回同一抹底色：

```text

(255, 255, 255)      # 底板，不是 toggle_button 的面（应为 240,240,240 或主题面）
```

后果极隐蔽：帧断言会变成「拿一个常量和自己比」。改成读**第二个**填充元素后拿到真实值
（`(243,237,247)`，浅色主题的 `surface_container`）。这与 §23.3 里 `group_box` 那条教训**同源**：
**断言必须读「控件画了什么」，而不是读一个恰好存在的值。**

### 30.4 反向注入（两向都做）

### 30.5 三帧判据（§9 判据 10 的形态）

计划要求「button 在 t=0/100/200 三帧填充色互异」。toggle button 的形状不动，

| 帧 | 断言 |

## 34. 🔴 本轮最重要的发现：**四个 `:checked` 状态键从来没有被任何控件报告过**

### 34.1 怎么发现的

做 `check_box`（A.2，P0）时先查计划 ①「补 `:checked`/`:error` 覆盖」，结果发现
**这些键早就存在于两套预设里**：

```text
$ python3 -c "…读 themes/{dark,default}.json 的 overrides.styles…"
themes/dark.json     26 checked/selected: ['check_box:checked', 'chip:checked',
                                          'radio_button:checked', 'switch:checked']
themes/default.json  26 （同上）
```

于是问题变成「它们有没有消费者」，而答案是**没有**：

```text
$ grep -rn "WidgetState::Checked\|WidgetState::Selected" src/ --include=*.rs
src/theme/manager.rs:477:        WidgetState::Checked => "checked",     # 只有「名字 → 字符串」的映射
src/theme/manager.rs:478:        WidgetState::Selected => "selected",
（**没有任何一处** `return WidgetState::Checked` 或 `Selected`）
```

### 34.2 根因：trait 默认实现只知道**四个原始标志**，没有一个表示「已锁存」

```rust
// src/widget/widget_trait.rs:397（默认实现）
fn widget_state(&self) -> WidgetState {
    if !self.is_enabled() { return Disabled; }
    if base.is_pressed() { Pressed } else if base.is_hovered() { Hover }
    else if base.draws_focus_ring() { Focused } else { Normal }
}
```

`Disabled` / `Pressed` / `Hover` / `Focused` —— **没有一个是「latch」**。
所以 `apply_active_theme` 的查找键 `"check_box:checked"` **永远拼不出来**，
`resolve_style_for_state` 永远落到 `Normal`，预设里那 4 个键 × 2 套 = **8 个状态覆盖
是「声明了、文档了、从未生效」**。

这与 §5.5 那条 token 门禁要防的状态**完全同形**，只是发生在**状态层**而不是 token 层：
「7 个角色加了但只有焦点环用一个」的孪生兄弟。

### 34.3 第三个缺陷：**导出器把主题应用在状态之前**，于是快照看不到状态覆盖

修完 `CheckBox::widget_state` 后重生成快照，`check_box.svg` **一个字节都没变**。
继续追，发现导出器的顺序是：

```rust
apply_theme_to_widget(widget);              // ← 先定主题（此时 state == 构造器默认 Normal）
sample_fill::apply(name, widget);           // ← 再 set_checked(true)
```

`apply_active_theme` 读的是 `widget.widget_state()`，所以**主题是按 `Normal` 解析的**，
`:checked` 的填充根本没进 `style`。`sample_fill` 明明把 `check_box` 勾上了，
图画出来却用的是静止色 —— **一个「看着对、其实没生效」的典型**。

修法：**把主题应用移到状态设置之后**（两处循环都改，含 `EXTRA_APPEARANCES` 那个）。
这也正是运行时的顺序要求：**样式是为「控件当前所处的状态」解析的**。

### 34.4 修完之后的证据


### 34.5 修法（一处定义，四处落位 —— 冰山法则）

| 控件 | 报告的状态 | 理由 |
|---|---|---|
| `check_box` | `Checked`（含 `PartiallyChecked`） | 锁存；预设为「on」画一种强调填充，混合态也是 on（三态答案由控件自己的横杠与 `a11y_state` 承载） |

| `switch` | `Checked` | 锁存；开关的**全部含义**就是它报的位置 |
| `chip` | **`Selected`**（不是 `Checked`） | 它是**集合**不是锁存：多个成员可同时选中，整个控件没有单一的 on。报 `Checked` 是声称一个它没有的形状 |

**同时把预设的 `chip:checked` 改成 `chip:selected`** —— 让「声明的状态」与

### 36.1 实测


### 36.2 第 3 处是**同一个方向缺陷的第三份拷贝**

`rgba(128,128,128,60)` 是**半透明的中灰**。中灰没有方向：

| 外观 | 遮罩效果 | 后果 |
|---|---|---|
| 浅色面（`rgb(240,240,240)`） | 变**暗** | 读起来像「重了」 |
| 暗色面（`rgb(18,18,18)`） | 变**亮** | 读起来像「亮了」——**在本来最看不清的那个外观上增加了对比** |

这与 §24 的 `scrim`（BLUE21 B23）、§34 的 `frame` 遮罩是**同一个缺陷的三个落点**。

`dimensions::DISABLED_VEIL_ALPHA = 140` —— 与预设状态覆盖的 `DISABLED_FADE`(0.55) 同值，
所以「禁用的标签 / 禁用的框 / 禁用的按钮」三者退隐程度一致。

| 版本 | 写法 | 结果 |
|---|---|---|
| v1 | 比较**启用墨**与**禁用墨**到面的距离 | 两者**都是 `(225,225,225)`** —— 主题为两种状态都解析了 `text_color`，所以**墨路径根本不同**。测试红，暴露了我对「禁用是靠遮罩实现的」这一点理解错误 |
| v2 | 比较**遮罩自己的填充**与面 | ✅ 通过，且反向注入（改回灰）变红 |

v1 的失败是**有价值的**：它证明「禁用的区分由遮罩独自承担，不由墨色承担」——
这条事实进 `frame`/`label` 的注释了。

### 37.2 **没修什么，以及为什么**（这一节比上一节更重要）

计划记 `frame` 有 **29 个字面量**，是本组最多。实际 28 处，其中 **20 处是三处斜角**
（`draw_box_frame` / `draw_win_panel_frame` 等的 highlight/shadow），它们**本来就是派生的**：

```rust
border.blend(&Color::rgb(255, 255, 255), 0.5)   // 从 border 亮出去 → 高光
border.blend(&Color::rgb(0, 0, 0), 0.75)        // 从 border 暗下去 → 阴影
```

`draw_win_panel_frame` 的既有注释已经论证过这一点（「它是凸起边缘的**幻觉**，
所以与 `draw_box_frame` 不同，刻意**不**从 border 派生」）。
**把一个已论证的设计判成缺陷，是另一种跑偏。**

剩下 8 处是**无主题时的回落值**（`rgb(236,233,216)` 等）。我一度把它们改成
「主题角色优先、字面量兜底」，**但变异测试证明这个改动不承重**：

```text
$ （把 `style.background_color.or(surface)` 改回 `style.background_color.unwrap_or(字面量)`）
test a_panels_fill_moves_with_the_appearance ... ok      # 仍然通过！
$ （打印实际解析值）
RESOLVED dark=(30,30,33) light=(243,237,247)             # 正是 surface_container
```

**根因**：`apply_active_theme` 把 `frame` 归类到角色后**已经**把 `surface_container` 填进
`style.background_color` 了，所以那 8 个回落值在**有主题的构建里永远够不到**——
它们只服务「无主题」这一条路径，而在那条路径上它们是对的。

**处置：把这 8 处的改动全部回退。** 理由写在 `frame` 那条测试的文档注释里
（「一个不能失败的再推导不是测试」），以免下一个人重犯同一个错。

### 37.3 新测试保留了，但断言的对象改了

新增 `a_panels_fill_moves_with_the_appearance`，它现在断言的**不是**「字面量被替换了」
（那不可证），而是**真正没有被覆盖的那部分**：

> 导出的 `frame` 用的是**默认的 `Box` 形状**，它不画面 —— 所以两条 panel 臂
> 只有「调用者主动要形状」才可达，而**没有任何快照这么做过**。

## 39. `swipe_to_dismiss`（A.2 最后一个）—— dismiss 是**硬切**：一个「它走了」的手势以「它回来了」收尾

### 39.1 实测

```rust
// 修前
pub fn dismiss(&mut self) {
    if !self.is_dismissed {
        self.is_dismissed = true;
        self.swipe_offset = 0.0;      // ← 这一行
        self.dismissed.emit(());
    }
}
```

用户把一行拖出屏幕大半、松手 → 阈值过了 → **该行先跳回原位（`swipe_offset = 0.0`）、
然后消失**。整个手势的意思是「我把它移走了」，而视觉上的收尾动作是「它回到座位上」。
`grep fn tick` 在该文件 = 0 命中（计划记的「无动画驱动」准确）。

### 39.2 修法

```rust
exit: crate::style::Transition,      // 新增：0.0 在原位，1.0 完全离场

fn tick(&mut self, delta_ms: u32) -> bool { self.exit.tick(self.exit_target(), delta_ms) }
fn drawn_offset(&self) -> f32 {      // 手势位置 + 离场位移，**派生**而不是第二个可变字段
    if self.exit.progress() <= 0.0 { return self.swipe_offset; }
    self.swipe_offset - self.base.geometry().width as f32 * self.exit.progress()
}
```

三个设计决定：

| 决定 | 理由 |
|---|---|
| `dismissed` **立即**发信号，只有离场被动画化 | **决定**是模型马上要知道的事实；一个要等帧循环才听到「这行没了」的订阅者是错的 |
| 手势位置与离场位移**分开**（派生 `drawn_offset`，不写回字段） | `reset_swipe`（撤销手势）因此不需要推理一个半完成的离场；两个写者不会失步 |
| 离场方向**恒向左** | 平台惯例里「移除」就是向左；程序化 `dismiss()` 没有手势方向，从零偏移推一个方向是**发明**调用者没表达过的偏好 |

`draw` 的 `return` 从「按 `is_dismissed` 标志」改成「按 `exit.progress() >= 1.0`」——
**所以一个在 `tick` 之前取的快照（progress=0）与未 dismiss 时逐字节相同**
（这也是本轮 `git status snapshots/` 为空的原因）。

### 39.3 三帧判据的两个坑（都是我自己踩的）

1. **第一版辅助函数读「第一个 `M` 原点的 x」**。座着时读到 `0`，移动后读到 `156` —— 断言报
   「must travel leftward: from x=0 to x=156」。原因：一次字形运行是**一个 `<path>` 里很多子路径**，
   第一个子路径在运行被偏移后**不是最左的那个**。
   改成取**所有 `M` 原点的最小值**（`leftmost`），并加了「`M` 后面必须紧跟数字或 `-`」的过滤，
   以排除属性名与 `xmlns` URI 里的 `M`。
2. 中间一度想用 `sw.child_mut_for_test()` —— **那个方法不存在**，是我编的。
   改成在测试里**先 `set_child` 一次**，辅助函数只负责读像素。

### 39.4 反向注入


## 51. 🔴 门禁 `check_control_rendering.sh` 的**两个既有失败被修好**

### 51.1 接手时它已经红了（非本轮引入）

`git stash` 后重跑可以证明：**HEAD 上 `known_theme_blind_matches_the_census` 与
`p3_chrome_follows_the_appearance_unless_exempted_as_data` 就是红的**，报：

```text
these controls render identically in light and dark and are not recorded as theme-blind nor exempted as data colours: ["check_box", "bottom_sheet", "modal_bottom_sheet"]
```

### 51.2 根因一：**census 把主题应用在状态之前**

`census_all_controls` 原本是「先 `apply_active_theme`，后 `sample_fill::apply`」。
`sample_fill` 对 `check_box` 调 `set_checked(true)`，而 `apply_active_theme` 靠
`widget.widget_state()` 解析 `"<kind>:<state>"` —— **所以 light 那一遍把控件当 `Normal`
上妆、却当作 `Checked` 去画**：

```text
light 盒子填充 = 180,180,180（未选中的 Input 字段）
dark  盒子填充 = 100,181,246（选中态的 primary）
```

于是 P3 声称在比 "light ≠ dark"，**实际比的是「未选中 vs 选中」**，根本看不见主题。
这与 §34.3 修过的**导出器顺序**缺陷同形（“主题应用在状态之前”），是同一根因的第二处落位。

**修法**：内容先、主题后，两遍一致。

### 51.3 根因二：`count_ink` **只看 RGB，看不见 alpha**

`bottom_sheet` 默认**关闭**，只画 scrim。两份 SVG：

```text
light: <rect ... fill="rgba(0,0,0,0.32)" />
dark : <rect ... fill="rgba(0,0,0,0.51)" />
```

**它们确实不同**（主题在 alpha 通道上表达遮罩浓度，这是所有平台的做法）。
但直方图键是 `(r,g,b)`，两者都记成 `0,0,0` ⇒ P3 报「主题盲」。**测量假象，不是缺陷。**

**修法**：直方图键改 `(r,g,b,a)`；
- 半透明像素（`a != 255`）**一律算 ink**（叠在填充上，用户看到的是混合结果）；
- `dominant_differs_from`（P2）**先按 alpha 合成到背景再比**，否则半透明层会被误报为「任何表面上都可见」；
- `format_rgb` 只在**非不透明**时打印 alpha（`r,g,b@a`），不透明时逐字保持 `r,g,b`
  —— 这样基线文件不会因为一个处处是 255 的通道而整篇变动，把真正动过的行淹掉。

修完后：

```text
check_control_rendering: checked=188 skipped=0 failed=0
[1/4] PASS control_rendering_census_test (P1/P2/P3/P4/P5)
```

### 51.4 连带：**三条豁免不再豁免任何东西**（门禁自己报的）

```text
these data-colour exemptions are no longer needed — the control now follows the appearance, so remove them from tools/control_color_exemptions.txt: ["audio_visualizer", "video_player", "font_preview"]
```

三条的**主体仍是 content**（信号渐变 / 解码帧 / 字形样本），但豁免是按 **dominant 色**判定的，

## 52. 🔴 本轮最深的缺陷：**选中态的墨被用在了页面上的标签**

### 52.1 怎么发现的

修完 §51 的 census 顺序后，`check_box` 仍然 `differs = NO`，dominant 两态都是 `0,0,0`。
逐元素 diff 两份 SVG：

```text
light 盒子 = rgba(33,150,243,1.00)   ← :checked 的 primary
light 标签 = rgba(0,0,0,1.00)
dark  盒子 = rgba(100,181,246,1.00)  ← :checked 的 primary
dark  标签 = rgba(0,0,0,1.00)        ← ❗黑墨在 18,18,18 的页面上
```

### 52.2 根因：**一个 `text_color`，两个不同的承载面**

主题的 `"check_box:checked"` 覆盖是：

```json
"check_box:checked": { "background": primary, "foreground": primary.contrast_color() }
```

这两个字段描述的是**盒子内部**（选中填充 + 其上可读的墨）。
但 `checkbox.rs` 把 `style.text_color` 同时用于：

1. **勾**（画在 primary 填充上）→ 用对比色**正确**；
2. **标签**（画在**页面**上，在盒子旁边）→ 用对比色**错误**。

暗色外观下 `primary.contrast_color()` 是**黑**，于是「一个勾得清清楚楚的框，
旁边那两个字是纯黑压在近黑页面上」——**对比度 1.12:1**。

### 52.3 修法：**两个承载面各自解墨**

- 新增 `page_surface()`：读主题的 `colors.background`（**不是** `style.background_color`，
  因为 `:checked` 已把它换成 primary 填充 —— 那描述的是盒子，不是标签所在的面）；
- 标签墨 = 请求的墨 `.legible_on(page, 4.5)`：**主题给的标签墨够清楚就保留**，不够就朝页面对比色推进。
  这样「主题写了自己想要的标签墨」不会被覆盖，而「选中态在黑页面上」这个组合被修复，
  且**不是**按外观打特例。

### 52.4 反向注入 — 两次都红，证据如下

```text
check_box : the label of a checked box must clear the AA floor on the page it sits on:
            Dark painted Color { r: 0, g: 0, b: 0, a: 255 } on Color { r: 18, g: 18, b: 18, a: 255 },
            a ratio of 1.12:1
radio_button: 同字（同根因）
```

✅ 两条断言都承重。

### 52.5 冰山法则：同一形状在**两个**控件上，不在四个

四个「锁存态」控件各有 `:checked` / `:selected` 覆盖，逐个核：

| 控件 | 标签画在 | `text_color` 用在哪里 | 裁定 |
|---|---|---|---|
| `check_box` | 页面 | 勾 **+** 标签 | ❌ 缺陷，已修 |
| `radio_button` | 页面 | 环/点 **+** 标签 | ❌ 缺陷，已修 |
| `switch` | — | 不画标签 | 不适用 |
| `chip` | **primary 填充上** | 填充 **+** 标签 | ✅ **正确**（标签就在那个填充上） |

**两个修、两个不动**，且不动的那两个有明确判据（标签与填充同面）。

## 44. 先量一件更重要的事：`frame` 的快照**根本没在测斜角**

```text
$ grep -n "frame_shadow" src/widget/base_widgets/frame.rs
:114  frame_shadow: FrameShadow::Plain,        # ← 默认 Plain
$ cat snapshots/svg/frame.svg
  <rect … fill="none" stroke="rgba(130,130,130,1.00)" stroke-width="1" />   # 单线，无斜角
```

**`frame` 默认 `Plain`**（只画一条描边），所以导出的快照**从不进入 `Raised`/`Sunken` 分支**。
这解释了两件事：

1. 那 20 处斜角字面量**为什么能活到今天** —— 没有任何快照、统计或门禁看到过它们；
2. **「迁移后快照逐字节不变」不能作为这次迁移的验收** —— 它是一句**什么都没证明**的话。

所以本轮改用**像素级断言**驱动那条分支（见 §45.4）。

## 45. 做了什么

### 45.1 新文件 `src/render/bevel.rs`（575 行，**只新增**）

`Bevel` 把「一个面朝哪边」从「两个几乎相同的代码块的**顺序**」变成**一个参数**：

```rust
pub enum BevelDirection { Raised, Inset }      // raised = 上/左受光；inset = 恰好交换
pub struct Bevel { light, shade, base, direction }
```

三个决定（都写进注释）：

| 决定 | 理由 |
|---|---|
| 保留 `base` 字段（不是只留两个 tone） | **内圈线从 base 派生**，不是从外圈 tone —— 见 §45.3 |
| 方向由 `leading_tone()`/`trailing_tone()` 解释 | 内圈与外圈**共用一个解释器**，所以内圈不可能跑到对面的边上 |
| `FromStr` 而非固有 `from_str` | clippy 的 `should_implement_trait` 抓到了：固有同名方法会**遮住** trait 的，使 `"inset".parse::<BevelDirection>()` 不可调用 |

### 45.2 `frame` 的 `Raised` 臂改为调用原语（**派生不变**）

```rust
let bevel = if plain { Bevel::from_tones(border, border, border) }   // 抑制斜角
            else if themed { Bevel::from_base(border) }              // 0.5 朝白/黑
            else { Bevel::from_tones(grey, WHITE, grey) };           // 无主题的历史硬编码对
bevel.stroke(context, rect, 1);                                      // 1 px = 原 draw_line
```

### 45.3 三个**真实发现**（都是被测试逼出来的）

| # | 发现 | 后果 |
|---|---|---|
| 1 | **`BEVEL_INNER_SHADE_WEIGHT = 0.75` 不是内圈，是第三/第四根线** | 我最初把 `0.25`/`0.75` 当成一对内圈常量搬过来。测试立刻报「inner shade must be softer than the outer one」——`0.75` 比外围的 `0.5` **更深**。根因：那对数来自一个**四线凹槽**（外高光、外阴影、再一圈更深的阴影），而两线斜角里没有这一层。改成对称的 `0.25`，并把这句「照抄数字但没照抄形状」写进常量注释 |
| 2 | **内圈从 tone 派生会变亮** | 第一版 `inner_tones` 从 `light` 再朝白 blend ⇒ 内圈**比外圈更亮**，读起来是「第二道更热的高光」而不是「厚度」。外面手写的代码本来就是 `border.blend(...)`（从 **base**）—— 它是对的，我的重构是错的 |
| 3 | **笔刷是跨在坐标上的** | `draw_line_with_width` 用 `-width/2 ..= width/2`，所以 3 px 的斜角在 `y=0` 会画到 `y=-1` 被裁掉。我的第一批测试因此在宽度 > 1 时测错 |

第 3 条也解释了为什么原语必须有 `width` 参数：手写的 `draw_line` **永远只有 1 px**，
所以一个 `line_width = 2` 的主题牌框会有 2 px 边框配 1 px 斜角。

### 45.4 验收：像素级断言，不是快照

`a_raised_box_frame_paints_the_hand_written_tones` 直接驱动 `Raised` 分支并读像素，
断言**外面手写的那两个表达式**：

```text
top/left     edge == border.blend(&WHITE, 0.5)
bottom/right edge == border.blend(&BLACK, 0.5)
且第二行不是高光（1 px 不外溢）
```

期望值在测试里**独立地**用 `Color::blend` 算出来，**不经过 `Bevel`** ——
所以原语内部被改坏时，期望值不会跟着一起动。

**反向注入**（把 directions 的两支对调）：`a_raised…` 与 `an_inset…` 立刻变红
（`left: rgb(60,70,80)` vs `right: rgb(188,198,208)` —— 后者正是 `120,140,160` 半程朝白的值）。

`frame` 快照（`frame.svg` / `frame.light.svg`）**未变**，因为默认仍是 `Plain`。

## 56. `keyboard`（A.3，P1）：按一个键，整块板**毫无反应**

### 56.1 实测

```text
$ grep -n "pressed_key\|is_pressed\|active_key" src/widget/input_widgets/keyboard.rs
（无输出）
```

`handle_event` 发完信号就结束，`draw` 没有任何「哪个键被按」的输入 ⇒
**按下与不按，屏幕完全一样**。

### 56.2 为什么不能直接用 `base.is_pressed()`

`BaseWidget` 记录的是**控件**被按下，而键盘是**一个网格里的多个独立目标**：
任一按键点亮整块板，比什么都不亮**更糟**——它在指错键。

故新增 `pressed_key: Option<(usize, usize)>`，**用位置而不是键码**：
同一个键码在数字行与键盘区各有一个键，键码无法指名要亮的那个。

### 56.3 修法

| 位置 | 改动 |
|---|---|
| 字段 | `pressed_key: Option<(row, col)>` |
| `MousePress` | 用 **`key_at_position`**（点击自己也用的那个函数）记下位置 |
| `MouseRelease` / `TouchEnd` | `take()` 清除 |
| `draw` | 该键 `kbg.blend(&ink, 0.25)`，比普通键再抬一阶 |

### 56.4 断言 + 反向注入

断言用「按键中心的矩形填充 ≠ 静止填充」，释放后**回退**（不锁存）。
反向注入（去掉高亮）：

```text
assertion `left != right` failed: the key under the pointer must be visible as pressed;
  left: "rgba(194,194,194,1.00)" / right 同
```

✅ 承重。

### 56.5 踩到的坑（记下，因为是同类工作的固定陷阱）

第一版 SVG 取样器用 `element.find("/>")` 做游标，结果**只解析出 2 个矩形、全是白色背景**
（实测打印：两次迭代都是 `320x160`）。改用 `svg.split("/>")` 逐元素切分后立刻正确。
**教训：游标式解析在自闭合标签上没有分节保证，而 `split` 有。**
（`list_view`/`table_widget` 的采样器从一开始就用 `split`，未重蹈。）

## 57. `list_view`（A.7.3，P0）：**连 `BaseWidget` 都没转发，行 hover 无从谈起**

### 57.1 实测

```rust
impl crate::event::EventHandler for ListView {
    fn handle_event(&mut self, event: &crate::event::Event) {
        if !self.base.is_enabled() { return; }          // ← 没调 base.handle_event
        match event { MousePress => select_row_at_point(..), ... }
```

两件事：

1. `handle_event` **从不转发给 `base`** ⇒ `MouseEnter/MouseLeave` 到不了基类，
 `widget_state()` 永远不是 `Hover`，主题的 `"list_view:hover"` **永久失效**；
2. 没有任何**行**级 hover 状态。

### 57.2 修法

- 头部补 `self.base.handle_event(event)`；
- 新增 `hovered_row: Option<usize>`，由 `MouseMove` 用 **`row_at_point`**（点击自己也用的那个）填；
- `MouseLeave` 清除（不锁存到「最后经过的那一行」）；
- `draw`：焦点行 `0.30`、**hover 行 `0.12`**，同一 accent 两个权重
 ⇒ 指针位置与已提交选中**不会互相竞争**；两者同真时焦点优先。

### 57.3 断言

`hovering_a_row_highlights_that_row_only`：三向断言——

1. 悬停行填充 ≠ 静止；
2. **另一行**填充 = 静止（否则高亮指向不明）；
3. `MouseLeave` 后回退。

反向注入（`else if false && ...`）→ 红：

```text
assertion `left != right` failed: the row under the pointer must be visible as hovered; both were rgba(255,255,255,1.00)
```

✅ 承重。

## 58. 🔴 `table_widget`（A.7.3，P0）：**点击选中的是「上面那一行」**

### 58.1 这是本轮最重的一条：一个**功能**缺陷

```rust
// draw（:410）
let row_h = 20;
let rows_top = content.y + header.height as i32;      // 从内容区（表头之下）算
let y = rows_top + row_h * r as i32;

// handle_event（:478）
let row_h = 20;                                        // 同一个 20，又写一遍
if pos.y >= rect.y {
    let index = ((pos.y - rect.y) / row_h) as usize;   // 却从控件顶边算
```

**画行从表头之下算、点行从控件顶边算**，`20` 写了两遍。于是：

> **点第 1 行，选中第 2 行。**

这与 BLUE21 在 `list_view` 修过的**是同一个缺陷**（`20` 字面量 + 两处不同原点），
`ListView::row_rect` 的注释甚至写了「a press on the first row selected the second」——
**但兄弟控件没跟着修**。冰山法则的又一处落位。

### 58.2 修法：抽 `rows_band` / `row_rect` / `row_at_point`（与 `list_view` 同形）

三个函数一处定义、四处消费（draw 行带、draw 分隔线、点击、hover）。
把两个 `let row_h = 20;` 改成常量 `TABLE_ROW_HEIGHT`，并把原点统一到 `rows_band()`。

### 58.3 连带发现：一条既有测试**因为缺陷才通过**

`test_disabled_state_blocks_events` 点 `(10, 15)`——修正后可算出那**落在表头里**
（inset 2 + 表头 20 ⇒ 内容行从 y=22 起）。它原本能选中 row 0，**全靠那个算错的原点**。

⇒ 测试的**采样点**随之修正到真实的内容行（`(10, 30)`），并在注释里写明原委。

> 这是「**测试与代码一起错**」的典型：测试写「按下应选中」，而它点的其实是表头。
> 修好代码后它变红，不是回归，是**它终于开始测量它声称测量的事**。

### 58.4 新断言写成**互为逆**，且反向注入给出定量证据

```rust
let box1 = tv.row_rect(1);                       // 取第 1 行
let point = box1 中点;
assert_eq!(tv.row_at_point(point), Some(1));     // 点 → 行
```

反向注入（还原旧命中测试）：

```text
assertion `left == right` failed: the press must select the row it is on
  left: Some(2)   right: Some(1)
```

**`Some(2)` vs `Some(1)`**：注入把「点第 1 行得第 1 行」变成「点第 1 行得第 2 行」，
**与缺陷描述逐字一致**。✅ 承重。

### 58.5 hover 一并接上

与 §57 同形：`MouseMove` → `row_at_point` → `hovered_row`；`hovered_bg = 0.12`。

## 62. 冰山法则扫同类：**写了一个脚本，而不是又看一眼**

```text
  对每个状态字段（selection / selected_rows / focused_row / hovered_row / hovered_cell / current_row）
  判断它是否出现在 `fn draw` 的**花括号体内**
  只在「有写入者、不在 draw 里」时报告
```

结果：

| 文件 | 字段 | 裁定 |
|---|---|---|
| `list_view.rs` | `selection` / `selected_rows` / `current_row` | **不适用** —— 它们是 `SelectionModel` 的内部，`focused_row` 是其投影且**就是**被画的那个 |
| `table_widget.rs` | 同上 | 同上（同一 `SelectionModel`） |
| `special_widgets/grid.rs` | `hovered_cell` | **不适用** —— 该控件**发布** `cell_hovered` 信号由宿主画，且它自己的测试连的就是那个信号 |
| `data_grid.rs` | （写入者存在、无读者） | ❌ **真缺陷**，已修（§61） |

**两条不动都有明确判据**，而不是「看着像就改了」。这与 §52.5 同一纪律：
**冰山扫出来的候选必须逐个裁定，扫出来不等于都要改。**

> 本法的一个局限，如实记：它是**括号体包含**判定，不分析控制流。
> 一个字段在 `if false` 分支里被读也会算「在 draw 里」。
> 它适合当**探针**（宁可多报），不适合当门禁。

## 77. `progress_circle`（A.4，P1/M3/M10）：转圈**读了墙钟**，且 0% 与满圈分不开

### 77.1 两个真缺陷（实测）

| # | 缺陷 | 证据 | 后果 |
|---|---|---|---|
| ① | 不确定态的旋转角在 `draw` 里读 `SystemTime::now()` | `progress_circle.rs:275-281`（旧） | 动画**没有驱动者**：外观是墙钟的函数，测试只能 `sleep`；空闲时也在「转」（实际是每帧重算），且无法参与 `Widget::tick` |
| ② | 无 `trackGap`（BLUE21 A.3.6，**至今未修**） | `value` 极小时弧与轨道同起点同色 | 0% 的圈与满圈**无法区分** |

第 ① 条与 BLUE23 §3.2 直接冲突：**「每帧推进动画，且无动画时不推进、不重绘」** ——
墙钟法把两半都违反了。

### 77.2 修法

1. 新增 `sweep: f32`（0..1 圈）+ `ProgressCircle::tick(delta_ms)`：
   `sweep = (sweep + delta/period).fract()`；`period` 取主题 `motion_tokens().2`（slow）
   × `SPIN_SLOW_MULTIPLE=5`（一整圈比一次状态过渡长得多，300 ms 转一圈是抖动不是进度）。
2. `impl Widget::tick` / `is_animating` 接上（§3.3 的一行接入）。
   **确定态不欠帧**（`tick` 返回 false），即 §3.2 的后半。
3. 加 `TRACK_GAP = 4.0`（主流 material 实现 `progress_indicator.dart:1636`）：
   弧起点 = −π/2 + `gap/radius`。写清「像素→弧度」在**绘制半径**上换算。

### 77.3 三条断言（§0.3 三帧判据）+ 双向反向注入

| 断言 | 形态 | 反向注入（改回旧写法） |

| `the_indeterminate_ring_turns_on_the_ticks_it_is_given` | `sweep_angle()` 单调 + **三帧文档互异** | `self.sweep = self.sweep` ⇒ **红**（`the ring must advance`） |

## 78. `rating`（A.4，P1/M10/M9）：`Float` 契约下的 `u32` 存储 —— 写 3.7 得 4

### 78.1 缺陷（BLUE21 A.4.5d，本轮实测确认仍在）

```text
schema:  "value" ⇒ Float
struct:  rating: u32                       ← 分数无处可存
set:     self.set_rating(value.round() as u32)   ← 静默取整
```

于是 `set("value", 3.5)` 画四颗满星、读回 `4.0` ——
**契约报告了一个它已经改掉的值**（原则 #1 禁止的形态）。
且「四星半」这个最常见的评分**根本无法表达**。

### 78.2 修法：分数入存储，整体数保留为投影

按原则 #21（不破坏既有签名）分成两层：

| 层 | 方法 | 语义 |
|---|---|---|
| **精确**（新） | `rating_exact() -> f32` / `set_rating_exact(f32)` | 存分数，`value` 属性与之往返 |
| **投影**（旧） | `rating() -> u32`（四舍五入）/ `set_rating(u32)` | 只用整星的调用方**行为不变** |
| **信号** | `rating_changed: Signal1<u32>` | **保持 `u32`**，订阅者签名不变；只在**整星投影变化**时发 |

`draw` 改为**逐星填充**：先画空心字形，再按 `star_fill(i)` 把实心字形
**clip 到该星格内评分所占的宽度**（整星不 clip、半星 clip 一半）。
`display_text` 保留分数（`"3.5 of 5"`），否则把刚补上的精度又在播报路径上丢掉。

### 78.3 断言 + 双向反向注入

| 断言 | 反向注入 | 结果 |
|---|---|---|
| `a_fractional_rating_round_trips_and_fills_one_star_partially` | `set_rating_exact(value.round())` | ✅ **红**：`left: Float(4.0) right: Float(3.5)` |
| `a_half_rated_star_is_painted_with_a_clip` | `filled_width = cell.width`（不按比例） | ✅ **红**：`left: 24 right: 12` |

> 第 2 条的第一版数 `★`/`☆` **字符**，得 `0 vs 5` —— 因为文本已改为
> **字形轮廓**（`<path d="M40 13h1v1h-1z…">`），SVG 里没有字符。
> 改数 **`<clipPath>` 的宽度**与两种填充色的 path 数才承重。

## 79. 同一形状的**整类**扫描：「动画由 Timer 事件驱动，不由 `tick`」

### 79.1 冰山法则：扫一遍，而不是又看一眼

`skeleton_loader` 修完后，按 §62 的纪律**扫同类**：全仓找「动画状态由 `Event::Timer` 推进」：

```text
$ grep -rn "Event::Timer" src/widget/ --include=*.rs | grep -v "test\|//"
display_widgets/skeleton_loader.rs:337
dialog/tooltip.rs:331
container_widgets/carousel.rs:1269
web_widgets/web_engine.rs:729   ← 平台能力（web 控件，本轮不管）
```

**四个命中，三个是真缺陷**（第四个是 web，用户指令 #6 明确除外）。
它们的共同形状与 §77 的 `progress_circle` **完全相同**：

> **一个动画的「时间」不是时间，而是「宿主多久推我一次」。**

| 控件 | 旧驱动 | 后果 |
|---|---|---|
| `skeleton_loader` | `Event::Timer` ⇒ `counter += 1`（20 帧一周期） | 脉冲速率随宿主而变；60 Hz 与 120 Hz 下快一倍 |
| `tooltip` | `TIMER_SHOW_ID` / `TIMER_HIDE_ID` ⇒ 立即 show/hide | **延迟根本不是延迟**；且**没有淡入淡出**（两态硬切） |
| `carousel` | `Event::Timer` ⇒ `advance_autoplay()`（每事件推进**一个 interval**） | 「每 3 秒换一页」变成「每 tick 换一页」 |

### 79.2 修法：统一为「`tick(delta_ms)` 是唯一时钟」

三个控件各加 `impl Widget::tick` + `is_animating`，时间由 `delta_ms` 决定：

| 控件 | `tick` 驱动什么 | `is_animating` |
|---|---|---|
| `skeleton_loader` | `phase += delta/period`（period 由主题 `slow` × 4） | `animated` |
| `tooltip` | `show_elapsed`/`hide_elapsed` 计时 + `fade: Transition` | pending 或 fade 未到位 |
| `carousel` | 把 `delta_ms` 交给**已有**的 `advance_autoplay_by(Duration)` | `autoplay_should_run()` |

```text
PROBE（注入=强制浅色盘）token_fill:
  light = ["rgba(0,0,0,1.00)", "rgba(105,50,27,1.00)", ...]
  dark  = ["rgba(181,181,181,1.00)", "rgba(221,172,152,1.00)", ...]

dark 的最小亮度 181 > light 的最大亮度 68   ← 即使两份盘**相同**
```

**渲染器把 token 的墨朝它所在的「场地」（field）混**，而 field 跟主题走 ——
所以两态的 token 填充**本来就不同**，与用哪份盘无关。这个断言测的是 **field 的差异**，
不是**盘的差异**。**又一次「测到的是别的东西」。**

换成**盘本身**的性质（不经过渲染器）：`every_dark_token_ink_is_lighter_than_its_light_counterpart`
—— 每个类别的暗盘墨都更亮、且在暗地面上对比度 ≥ 4.5。注入（`dark()` 返回 `light()`）：

```text
Plain must be a lighter ink in the dark palette: light=43,55,74 dark=43,55,74
```

✅ **承重**。教训成文（与 §71.4/§73.2/§77.3/§78.3 同一条，本轮第 5 次）：
**当像素是「输入 × 变换」的乘积时，要在能分离变量的那一层断言。**
这里能分离变量的一层是**盘**，不是**渲染结果**。

### 87.1 `canvas`（A.8.1b，P2）：指针事件**从未到达基类**

它自己维护 `set_mouse_pressed` 与四个信号（`mouse_pressed`/`mouse_released`/`mouse_moved`/
`double_clicked`），但**从没调 `self.base.handle_event(event)`**。
⇒ `widget_state()` 永远是 `Normal`，`"canvas:hover"` 是死键。

修法：在 `match` **之前**补一行 `self.base.handle_event(event)` ——
基类管状态事实（`hovered`/`grabbed`/焦点），控件管自己的四个信号，两者**互补而非互斥**。
