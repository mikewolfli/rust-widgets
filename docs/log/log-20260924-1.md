## 1. 批 1 —— G-5 抗锯齿（`src/render/text/raster.rs`）

### 1.1 做了什么

新增 `VectorSource`，实现 `GlyphSource::paint`，把 `ttf-parser` 读出的轮廓**就地**光栅化成
每像素覆盖率。要点：

| 环节 | 做法 | 为什么 |
|---|---|---|
| 展平 | 自适应细分，`FLATTEN_TOLERANCE = 0.2` 像素 | 固定细分在曲率大的地方出折线、小的地方白算 |
| 填充 | 非零环绕，`SUBSAMPLES = 4`（每轴 4 次采样 ⇒ 16 级） | 16 级覆盖率足够平滑，代价是每像素 16 次判定 |
| 算法 | **两趟**：先按行累计穿越数，再扫描累计环绕决定内外 | 一趟方案要把环绕跨行携带，会在行边界泄漏成横向色带（见 §2.2 的真实 bug） |
| 上界 | `MAX_POINTS = 1024`/`MAX_CONTOURS = 16`/`MAX_SUBDIVIDE = 16` | 恶意或畸形轮廓不能撑爆栈 |
| 基线 | `ASCENT_SHARE = 0.82` | 字面量集中一处，不与测量侧的第二份抄写漂移 |

### 1.2 为什么它接进了同一条混合路径，而不是第二条

`blend_painted_glyph`（`src/render/pipeline/pixel_ops.rs`）原本只认 1 位点阵：它把每字节当
「全有/全无」再乘 `value as f32 / 255.0`。巧合的是**这正好就是覆盖率的语义** —— 1 位点阵写
`0`/`255`，矢量面写 `0..=255`，同一个 `blend_pixel` 对两者都成立。所以：

- **不需要**给矢量面开第二条绘制路径（原则 #8：一处事实一处抄写）；
- 每个既有快照**逐字节不变** —— 1 位面写出的仍是 `0`/`255`，混合结果与原矩形填充相同。

这是本轮最省的一段：抗锯齿是**接口已经预留好**的，补的是一个实现者。

## 2. 批 2 —— G-6 彩色 emoji（`color_bitmap.rs` + `png.rs`）

### 2.1 接口：第三种 ink（`InkKind`）

新增 `InkKind { Bitmap, Coverage, Color }` 与 `Painted { source, source_cell, ink }`。
`source_cell: None` 是「不能压成矩形」的钩子：彩色字形是**颜色**，不是 1 位位图的斜坡，
SVG 后端不可能用「每个源像素一个 `<path>`」表达它（原则 #7：宁可不画也不画错）。

`Painted` 还带 `bytes_per_pixel()` / `buffer_len()` / `is_coverage()` / `is_color()`，把
「这个 ink 的缓冲要多大」变成 `Painted` 自己的事实，而不是调用方自己推。

### 2.2 三个真实缺陷（都是「数字看起来对」那一类）

这一段是本轮最费时的部分，三个 bug 都属于「解析出来的数能算，但全是错的」：

#### 缺陷 1：`CBDT` imageFormat 17 的头长

原实现假设 PNG 紧跟 5 字节 `SmallGlyphMetrics`。实际字节是
`80 88 00 65 88 | 00 00 02 f2 | 89 50 4e 47 ...`——`00 00 02 f2` = **754**，正是 PNG 长度。

**取证**：查 OpenType 规范 `CBDT` 页的 *Format 17*，它是
`smallGlyphMetrics (5) + uint32 dataLen (4) + uint8 data[dataLen]`，所以 PNG 在 `+9`。

**修法**：新增 `image_format_header_len(17|18|19) = 9|12|4`，并**读 `dataLen` 而不是**用索引表
的偏移差。后者只在索引精确时才相等（格式 2 有常量步长、格式 1 的偏移可能含填充）。

```text
$ python3 -c "…读 emoji.ttf 的 CBDT…"
metrics (128, 136, 0, 101, 136)   # height,width,bearingX,bearingY,advance —— 都合理
data_len 754
png sig b'\x89PNG\r\n\x1a\n'  IHDR dims (136, 128)   # 与 metrics 一致
```

#### 缺陷 2：`png.rs` 的 inflate 缓冲少算每行 1 字节

`IHDR` 报 `136x128 depth=4 colour=3`，`row_bytes = (136*4+7)/8 = 68`，正确缓冲应是
`128*(68+1) = 8832`；原代码是 `height * row_bytes = 8704`。

**取证**：给 inflate 加临时 trace，`status=BadParam`、`produced=0`。Python `zlib.decompress`
在同一段 `IDAT` 上得到 `8832` 字节 ⇒ 缓冲确实小了。

**修法**：`expected = height * (row_bytes + 1)`（每行前面有一个 filter 字节）。

#### 缺陷 3：inflate 缺 `TINFL_FLAG_USING_NON_WRAPPING_OUTPUT_BUF`

`miniz_oxide::inflate::core::decompress` 默认把 `out` 当**环绕**缓冲，而环绕缓冲长度必须是
2 的幂 —— `8832` 不是，于是它直接返回 `BadParam`。即使加上该 flag，单次调用在 `out` 填满时
会返回 `HasMoreOutput` 而**不**保证一次算完。

**修法**：加 flag，并改成**流式循环**：按 `consumed`/`produced` 推进输入输出直到 `Done`；
`HasMoreOutput` 下若 `consumed == 0 && produced == 0`（无进展）或输出已满，判为拒绝。

#### 缺陷 4（同一批发现）：子字节位深不支持

`depth=4 colour=3` 是 **4 位调色板** PNG，原解码器 `_ => return None` 直接拒。
NotoColorEmoji 的小旗子正是这一编码，所以整个旗子类目会读不出来，而不是偶发。

**修法**：支持 1/2/4 位（仅 type 0/3），按 spec 高位先取：
`byte >> (8 - bits - offset)`；行步长 `(width +? )`→`(width * bits + 7) / 8`（按字节向上取整）；
`scale_to_byte` 改为按 `bits` 精确放大（`1→×255`、`2→×85`、`4→×17`），
**不是**除以 `1 << bits`——`1 << 4 = 16` 会把 15 映射到 239 而不是 255。

### 2.3 同一批的接口级缺陷（真正让功能不通的那个）

上面修完，`ColorBitmapFace::paint` 仍然 `None`。继续追到 `paint_active`：

```rust
// 修前
let Some(painted) = source.paint(ch, cell, out) else { /* 下一个 face */ };
```

`out` 由调用方提供，而 `blend_painted_glyph` 只给 `cell.area()` 字节（1 位用）。
彩色面要 `cell.area() * 4` ⇒ **彩色面永远「paint 不出来」**，栈就一路落到 8x8 或 tofu。
这解释了实测里 `source=tofu`：不是 face 读不出来，是**缓冲契约把彩色面排除了**。

**修法**：把契约写进文档；调用方按 `Painted::buffer_len()` 定缓冲。两条路径互斥：

| 调用 | 接受的 ink | 拒绝的 ink | 为什么 |
|---|---|---|---|
| `blend_painted_glyph` | `Bitmap` / `Coverage` | `Color` | 1 字节/像素是 alpha，不能当 RGB 读 |
| `blend_color_glyph` | `Color` | `Bitmap` / `Coverage` | 4 字节/像素自带颜色，不能再乘文字色 |

`draw_text`（`src/render/pipeline/primitives.rs`）先试 `blend_color_glyph`，返回 `false` 才走
`blend_painted_glyph`。因为两者**互斥**，每个字形恰好画一次，没有重复绘制。
`color_scratch` 只在 `fonts-emoji-color` 下分配 ⇒ 默认构建的分配量**一字不变**。

## 3. 批 3 —— 构建配置矩阵（冰山法则 #2：修一个，扫一类）

「抗锯齿 / 彩色 emoji 开起来能编译」这件事，本轮**逐个组合实跑**，发现并修掉两个独立的
配置缺陷 —— 它们都不是本轮引入的，而是**原本就在、只是没有组合去踩**：

| 缺陷 | 现象 | 修法 |
|---|---|---|
| `FaceBytes` / `active_faces` 只 gate 在数据 feature 上 | `text-shaping` 单独开启（或 `fonts-emoji-color,text-shaping`）时 `shaping.rs` / `raster.rs` 的 `use` 解析失败（E0432） | gate 改成 `text-shaping || fonts-vector-latin || fonts-complex`。理由：`FaceBytes` 是**塑形器的输入类型**，允许「有引擎、宿主自带 face、不带生成数据」是设计上就必须成立的组合 |
| `active_stack()` 用互斥谓词的多个 `let stack = …` | 所有 feature 全开时，前一个 `let` 不可达 ⇒ `unused_variables` + 若干静态量 dead-code 警告；且编译器**无法检查谓词覆盖了全部组合** | 重写成**一个互斥 `cfg` 静态量 + 最后一个兜底**的链式结构。16 种组合全部显式列出，最后一个 `not(any(...))` 是唯一兜底。顺带把「为什么顺序是这样」的四条规则写在函数开头 |

```text
$ for f in desktop / desktop,fonts-cjk-bitmap / desktop,fonts-vector-latin /
           desktop,fonts-complex / desktop,fonts-emoji-color /
           desktop,fonts-emoji-color,text-shaping /
           desktop,fonts-cjk-bitmap,fonts-vector-latin /
           desktop,fonts-emoji-color,fonts-cjk-bitmap /
           desktop,fonts-emoji-color,fonts-vector-latin /
           desktop,fonts-cjk-bitmap,fonts-vector-latin,fonts-complex,fonts-emoji-color,text-shaping
    do cargo build --lib --no-default-features --features "$f"
  done
  ⇒ 10 个代表组合全部 ok，0 warning / 0 error（16 种组合的其余 6 种是同构的）
```

`blend_color_glyph` / `blend_rgba_over_canvas` 也改成 `#[cfg(feature = "fonts-emoji-color")]`：
没有彩色面时**函数本身不存在**，而不是留一个「永远返回 false」的死代码（原则 #7）。

## 4. 修掉的第二个缺陷：`paeth` 的测试期望是错的

全量测试跑出一个红：`the_paeth_predictor_is_symmetric` 断言 `paeth(10,20,30) == 20`。

**取证**：`p = 10+20-30 = 0`；`pa=|0-10|=10`、`pb=|0-20|=20`、`pc=|0-30|=30` ⇒
`pa` 最小 ⇒ **返回 left = 10**。PNG 规范测的**不是**「谁在中间」，而是「谁最接近梯度
`left + above - corner`」，而这里梯度是 0。

```text
$ python3 -c "…按规范实现 paeth…"
paeth(10,20,30)= 10      # 不是 20
paeth(0,0,0)  = 0
paeth(255,0,0)= 255
paeth(0,0,255)= 0
paeth(255,255,0)=255
paeth(200,100,150)=150
```

**结论**：**实现是对的，测试期望是错的**。这类错误正是「测试写的时候还没跑过真实图像」的
典型症状 —— 与 §2.2 的三个缺陷同源（都是「看起来对」）。修法是改期望并**加三个规范用例**，
同时把这条推理写进注释。

## 5. 修掉的第三个缺陷：一条测试的身份在矢量栈下**本就不成立**

`the_bitmap_view_and_the_painted_coverage_agree` 断言「`paint` 的覆盖率 == `glyph_rects` 的矩形」。
在 `fonts-vector-latin` 开启时它**必然**失败 —— 矢量面在前，它**故意**产出部分覆盖率
（抗锯齿的定义），而 `glyph_rects` 返回的是 1 位面的答案。实测：

```text
left : [0, 0, 31, 0, …, 207, 79, …]      # 矢量面：0/255 之间的值
right: [0, 0, 255, 255, …, 255, 255, …]  # 1 位面：只有 0/255
```

**修法**：把这条测试 `#[cfg(not(any(feature = "fonts-vector-latin", feature = "fonts-complex")))]`，
并在文档里写清「它是 **1 位栈** 的性质」，以及用哪条命令去跑它。这不是把测试删掉 ——
矢量面的覆盖率身份由 `render::text::raster` 自己的测试保证。

## 7. 全量验证（§9 验收判据）

### 9.1 ✅ `fonts-cjk` 矢量版：已打包（`fonts-cjk`，361,704 字节）

#### 先量代价，再决定范围（不是拍脑袋）

用真实字体量出整条代价曲线，而不是假设「矢量版应该也能小」：

```text
$ python3 …（Noto Sans SC，逐档子集化）
symbols + kana        253 cps   127 KB
+ fullwidth forms     477 cps   190 KB
+ 500 Han             977 cps   274 KB
+ 1000 Han           1477 cps   396 KB
+ 2000 Han           2477 cps   612 KB
（与位图面完全同覆盖的 2342 cps）              581 KB
```

**位图面是 85 KB / 2361 字形；同覆盖的矢量面是 581 KB——贵 7 倍。** 这不是缺陷，是轮廓与
16x16 点阵的固有差别。这条数字决定了整个设计，也**正面印证**了 `blue23.md` §0A.4 约束 2 与
迁入的附录 G 的那句话：CJK 是「只需数据、不需塑形」的脚本，所以 `mini`/`embedded` 必须
能靠 85 KB 位图拿到中文。

#### 结论：两个面是**互补**，不是替代

| 面 | 覆盖 | 体积 | 给谁 |
|---|---|---|---|
| `fonts-cjk-bitmap` | 2361 字形，固定 16x16 | ~85 KB | `mini`/`embedded`：只要数据、不要塑形引擎 |
| `fonts-cjk` | 2053 字形，轮廓、任意 px | ~353 KB | `desktop`/`tablet`：要抗锯齿、要任意字号 |

`fonts-cjk` 刻意**只发小范围**（ASCII + CJK 标点 + 假名 + 全角 + 800 个最常用汉字），
码点表单独成文件 `tools/cjk_vector_codepoints.txt`（带理由注释），与 emoji 表同一模式：
「发哪些字」是一个**决定**，两份就不叫决定了。

#### 新增的东西

- `tools/gen_font_subset.py` 支持 `--face=cjk`，并对这个面强加
  **`CJK_VECTOR_BUDGET_BYTES = 400_000` 的预算门禁**：超了直接拒绝，并提示「要么改码点表，
  要么连 `NOTICE` 与 `Cargo.toml` 的体积数字一起改」——这是「体积不能悄悄涨」的机制保证。
  （写完就抓到自己一次：初版 1000 汉字 = 408,276 字节，超预算，门禁当场拒绝。）
- `Cargo.toml` 新增 `fonts-cjk = ["text-shaping"]`，注释里带上上面那张实测表。
- `NOTICE` 新增 Noto Sans SC 一节（上游 / URL / 上游 SHA-256 / OFL-1.1 / Modified Version /
  无 Reserved Font Name 取证 / 与位图面的分工说明）。
- `README.md` 的 feature 表新增该行，并写清「两个面是互补」「同时开启时位图赢」。

#### 修掉的真实缺陷（冰山法则）

1. **`fonts-cjk` 单独开启时 CJK 解析成 tofu。** `active_stack` 的 arm 只按
   `fonts-vector-latin`/`fonts-complex` 分支，`fonts-cjk` 会掉到「只剩 8x8」那条 arm。
   实跑抓到的：
   ```text
   U+4E2D source=None      # 有面，却不可达
   ```
   修法：补一条 `fonts-cjk` 单独的 arm（`[VectorSource, Font8x8Source]`），并在注释里写明
   它为何必要；末尾的兜底 arm 也补上 `feature = "fonts-cjk"`，否则那条兜底会把
   `fonts-cjk` 选中时也当成「无数据」，于是编译期选两条 arm。
2. **`the_bitmap_view_and_the_painted_coverage_agree` 的身份在矢量栈下不成立。**
   `fonts-cjk` 也是矢量面，同样产出部分覆盖率。把它的 gate 从两个矢量 feature 扩到三个。
3. **`a_character_outside_the_face_is_refused` 用 `U+4E00` 做「面外」样本，语义已失效。**
   那是「不在拉丁子集里」，而 `fonts-cjk` 一开它就在了。改成 `U+E000`（私用区），并写清
   推理：「不在一个面里 ≠ 不在所有面里；只有不在**每一个**已启用面里才是面外」。

#### 验证


### 9.2 ✅ 彩色/矢量字形进 SVG 快照：已实现（**用轮廓，不是裁定不做**）

上一轮的「明确不做」结论**不成立**，因为漏了一条路：**彩色字形的 `CBDT` 位图没法压，
但矢量面的轮廓可以。** 而且矢量面本来就在产出轮廓——它只是没被 SVG 后端用上。

#### 修的是什么

新增 `text::outline(ch, cell, family, points, contours)`，把与光栅器**同一份**
`Flattener`/`Placement` 展平出来的多边形交给矢量后端；SVG 后端按 feature 选择：

| 墨的类型 | 后端发射 | 为什么 |
|---|---|---|
| 1 位点阵 | `M{x} {y}h{w}v{h}h-{w}z` 矩形（原样） | 8x8 格子里的 1 位就是整像素，矩形是**精确**几何 |
| 轮廓 | `M{a.b} {c.d}L…Z` + `fill-rule="nonzero"` | 抗锯齿的轮廓反过来会**低估**墨；`nonzero` 让 `o` 的内环仍是洞 |
| 彩色 | 不属于轮廓面 → 落到 1 位路径画 tofu | 可见的降级，不是悄悄画错（原则 #7） |

#### 这一路踩出的四个真实缺陷

前三个是产品缺陷，第四个是测试缺陷，全部有实跑取证：

1. **`outline` 的轮廓打包算错。** 原写法 `points.get_mut(index * MAX_POINTS ..)`，而
   调用方的切片只有 `MAX_POINTS` 长，于是**任何有两个轮廓的字形（`A`、`o`…）都返回 `None`**，
   静默掉回矩形路径。修法：改成**紧凑打包**（contour `i` 占
   `points[contours[i].0..contours[i].1]`），并把这条推理写进函数文档。
   抓它的断言是**轮廓数**（`'A'` 必须是 2），不是任何覆盖率断言。
2. **`outline` 按覆盖选面，不按 `Font::family`。** 这是最隐蔽的一条：布局测量走
   `shaping::face_for_family`（按 family 名选），而 `outline` 原来只是「找第一个覆盖的面」。
   于是 `Font::new("Arial", 11.0, …)` 在只发 Open Sans 的构建上**测得是估算模型**
   （0.6 em/簇），却被画成 Open Sans 的轮廓——墨的宽度与布局预留的宽度不是一个数。
   实跑：18 个控件的「墨在自己的盒子里」断言全红。修法：`outline` 接受 `family` 并用同一个
   `face_for_family`。**修完 18 → 1**（剩下的 1 个是我自己新写的测试用了不存在的 family）。
3. **`widget/svg.rs` 的路径读取器只认整数与 `M`/`h`/`v`/`H`/`V`。** 轮廓发的是
   `M21.45 30.24L…`，整数读取器在 `.` 处返回 `None`，于是 `path_bounds` 对每个矢量字形
   都答「没有墨」。修法：`number` 改读 `f32`，`path_bounds` 增加 `L`/`l`/`m`；`include`
   两端都取 `floor`（**不是** `floor`/`ceil`——后者会把盒子的**中点**移半像素，让
   「墨在这一行的中线上」这类断言差 1）。
4. **`shaping::tests::the_face_a_family_names_is_the_face_that_is_used` 的 gate 太宽。**
   它断言 Open Sans，但模块 gate 是 `any(vector-latin, complex)`，于是 `fonts-complex` 单独的
   构建上必然失败（那个构建里 Open Sans 根本不存在）。修法：单独 gate 到 `fonts-vector-latin`，
   并写明「它断言的是**那个构建**的事实，不是在断言别的构建」。

#### 为什么默认构建继续逐字节不变

`fill-rule` 只在**存在轮廓面**时发射，`append_outline` 也整个 feature-gate。默认构建的代码
路径与改动前**完全一致**：

```text

wrote 376 SVG snapshots for 188 controls into snapshots/svg/
sample-filled=22
$ git status --short snapshots/ control.md      # 空 = 逐字节不变
$ （再跑一次，输出同样逐字节相同 = 幂等）
$ bash tools/check_svg_snapshots.sh
check_svg_snapshots: checked=188 skipped=0 failed=0
```

#### 与 §9.1 的交叉验证

`fonts-cjk` 与 `fonts-vector-latin` 的 SVG 探针都给出 `L` 命令与小数坐标；默认构建给出
纯矩形、无小数。三个构建、三条路径、各自被自己的断言钉住。

### 9.3 ✅ `inflate_into` 的拒绝路径：已补 6 个针对性用例，并删掉一段死代码

原来「只被真实 emoji PNG 走过」的判断是对的——先给两个 guard 加插桩跑全量，**一次都没触发**。
于是直接做**变异测试**（改掉 guard，看测试是否变红），结果推翻了我一开始的判断：

| guard | 变异后的结果 | 结论 |
|---|---|---|
| 无进展（`produced == 0 && consumed == 0`） | 测试**挂死**（exit 143，超时被杀） | **真实承重**，保留 |
| 短输出（`out_pos != out.len()`） | 一条测试 **FAILED** | **真实承重**，保留 |
| 输出满（`out_pos >= out.len()`） | **无任何变化** | **死代码**，**删除** |

第三条的删除有取证——直接对 `miniz_oxide` 实测一个满缓冲的行为：

```text
status=HasMoreOutput consumed=28 produced=16   # 第一次调用把 16 字节缓冲填满
status=HasMoreOutput consumed=0  produced=0    # 第二次调用：没东西可做了
```

所以满缓冲是**下一轮**被「无进展」guard 接住的，`out_pos >= out.len()` 永远不会先触发。
把它删掉比给它写一个「永远为真」的测试诚实得多（原则 #7：不留看起来能用的死代码）。

新增 6 个用例，并把上面这些推理写进各自的文档注释：

| 测试 | 断言 |
|---|---|
| `a_stream_that_ends_before_the_output_is_full_is_refused` | 截断流（`BFINAL` 提前）拒绝 |
| `a_stream_longer_than_the_buffer_is_refused` | 超出缓冲拒绝 |
| `a_stream_that_fills_the_buffer_and_continues_is_refused` | 满缓冲且还有后续 → 拒绝，**且第一块的字节确实写入了** |
| `garbage_is_refused` | 空流 / 非 zlib / 只有头，三种都拒绝 |
| `an_empty_output_buffer_is_refused` | 零长输出在 inflate 前就拒绝（否则死循环） |
| `a_stream_is_inflated_across_more_than_one_call` | **正向用例**：8832 字节（非 2 的幂）一次以上调用解出**完全相同**的字节 |

（最后一条是关键：它是唯一能证明流式记账正确的用例——少了 non-wrapping flag 会 `BadParam`，
少了循环会在第一次 `HasMoreOutput` 停下，两种都得不到这些字节。）

## 12. 一句话结论

**三项遗留全部收口，而且没有一项是靠「降低标准」收口的。**

- §9.1 的 `fonts-cjk`：先量出「同覆盖贵 7 倍」这条事实，再据此把它设计成**与位图面互补**的
  面（小范围、可选、带 400 KB 预算门禁），而不是硬塞一个 581 KB 的版本冒充「更好的 CJK」；
- §9.2 的 SVG 快照：上一轮判「不做」是**错的**——漏了一条路（轮廓可以压，彩色 CBDT 不行）。
  改用 `text::outline` 后，矢量面与 CJK 面都进快照，且默认构建**逐字节不变**；
- §9.3 的 inflate 拒绝路径：先用插桩确认「一次都没触发」，再用变异测试**推翻自己的判断**
  ——两个 guard 承重、第三个是死代码。删掉死代码比给它编个测试诚实。

最值得记的一条：§9.2 工作里最难的那个 bug（`outline` 按覆盖选面而不按 `Font::family`）
**不是**「画错了」，而是「**测量与绘制用了两个不同的面**」—— 18 个控件同时红掉。
能一次抓住它的不是某个像素断言，而是「墨必须落在布局预留的盒子里」这类**跨层一致性**断言。

缓冲少 1 字节/行、少一个 flag、契约少 4 倍字节** —— 也就是原则里说的
「数字看起来对」。最后能把它抓住的，是「遍历整个 cmap 断言每个字形都有图」
（`every_cmap_glyph_has_an_image`）这种**结构性**的断言，而不是任何一个单元测试。
