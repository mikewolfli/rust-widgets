## §1 动态事件链路（E-01 … E-12）

### E-01：订阅地址未用归一化名 → 已修复

- 证据位置：`src/widget/capability.rs::connect_event`。
- 根因：验证用 `normalize_key(event_name)` 找到匹配，但 `hub.connect(event_name, …)` 存入**原始拼写**；控件经 `event_signal_dyn` 按标准名（`value_changed`）发出，两者成为不同 hub 条目 → 订阅被接受却永不触发。
- 修复：改为 `hub.connect(canonical, slot)`，`canonical` 取 schema 中匹配行的 `name`。
- 验证：新增 `capability::tests::connect_event_binds_every_spelling_to_the_canonical_signal`，对 `value_changed` / `value-changed` / `VALUE CHANGED` / ` Value_Changed ` 四种写法订阅后 `hub.emit(canonical)`，计数均为 1。

### E-02 / E-03：动态载荷 carrier 与 schema 不对称 → 已修复（批量 94 处，覆盖 72 文件）

- 证据位置：`src/widget/**` 下各控件 `event_signal_dyn`（Carousel、TreeTable、CodeEditor、MapView、RangeSlider 等）与 schema `event_payloads.rs`。
- 根因：两类——
  1. 无符号信号（`Signal1<usize/u32/u64/u8/ObjectId>`）用 `CapabilityValue::Int(*v as i64)`，与声明的 `UInt` 不符（并将超 `i64::MAX` 有损转负）；
  2. 标量事件用 `|_| CapabilityValue::Null` 丢弃真实值，或对元组/可选结构用 Debug 字符串。
- 修复（分类规则，按信号真实 Rust 类型确定，不按事件名猜测）：
  - `Signal1<String>` → `String(v.clone())`
  - `Signal1<usize|u64|u32|u8|ObjectId>` → `UInt(*v as u64)`
  - `Signal1<i32|i64>` → `Int(*v as i64)`
  - `Signal1<bool>` → `Bool(*v)`
  - `Signal1<f32|f64>` → `Float(*v as f64)`
  - `Signal1<Option<usize>>` → `match v { Some(x) => UInt(*x as u64), None => Null }`
- 批量执行：4 个子代理按**不相交文件集**并行完成，共 94 个 arm（group1 19+ / group2 22 / group3 25 / group4 24+，含 groupbox/table/virtual_list 等共享文件的多控件）。
- 附带修正 clippy 发现的 5 处 `u64→u64` / `f64→f64` 冗余转换（media_player、menu_button、web_engine、video_player）。
- 验证：门禁由修复前 **94 条不一致 → 0**，退出码 0；`check_event_signal_dyn.py` 仍全绿。

### E-04：门禁正则漏匹配外层块 arm → 已修复

### E-08：`slot_count>0` 不证明本 binder 可达 → 已修复

### E-09：同步 emit 期间重入注册表 panic → 已修复

- 证据位置：`src/widget/runtime.rs::dispatch_event`。
- 根因：`dispatch_event` 用 `with_widget_mut`（持有 `MOUNTED.borrow_mut()`）跨 `handle_event`；控件同步 emit 触发用户 handler，handler 内 `with_widget`/`with_widget_mut`（含 `request_redraw`→`top_level_window_of`）再借同一 `RefCell` → `BorrowMutError` panic。
- 修复：`dispatch_event` 在调用前把 entry 从 `MOUNTED` **取出**，调用后放回；借锁仅存在于两次 map 操作之间。新增 `DISPATCHING` / `DESTROYED_DURING_DISPATCH` 线程本地集合：handler 内 `unregister` 自身时记墓碑，epilogue 不复活它；handler 内重挂同 id 时以 handler 的注册为准。
- 验证：新增 `widget::runtime::tests::a_click_callback_may_update_other_widgets_without_panicking`（handler 内 `set_geometry` 另一 Label、读另一控件）与 `a_callback_may_destroy_the_widget_it_is_handling`（handler 内 `unregister` 自身后 `is_mounted` 为 false）。
- 已知边界（诚实记录）：handler 内**读取自己**这个正在派发的控件会得到 `None`（其 entry 暂不在表中），但不再 panic，且更新其它控件/关窗/销毁自身均正常。

### E-10：回调 unwind 留下"有 slot、无 callback" → 已修复

- 证据位置：`src/signal/core_signal.rs::emit`。
- 根因：`take`→调用→恢复是普通顺序代码；回调 panic 被宿主 `catch_unwind` 后恢复段不执行，entry 留存但 `callback==None`，后续 emit 跳过而 `slot_count` 仍计入。
- 修复：把"恢复/移除"放进 `RestoreGuard` 的 `Drop`，正常返回与 unwind 都执行（once-slot 无论是否 panic 都移除；非 once 且仍连通则恢复，自断开则丢弃）。
- 验证：新增 `a_panicking_slot_is_restored_so_later_emits_still_reach_it`——首次 emit 在 `catch_unwind` 下 panic 后，`slot_count==1`，重置标志后第二次 emit 计数到 2。

### E-11：同优先级顺序非连接序 → 已修复

- 根因：快照来自 `HashMap`，仅按 priority 排序；稳定排序保留的是 map 迭代序而非连接序。
- 修复：`SlotEntry` 增加单调 `sequence`（与 handle 同源计数器），快照改为 `(handle, priority, sequence)`，排序键 `(priority.rank(), sequence)`。
- 验证：新增 `equal_priority_slots_fire_in_connection_order`——四个同优先级按连接序执行；断开两个再连一个后，存活者仍按连接序。

### E-12：载荷回归测试未断言送达 → 已修复

## §2 控件边界（W-01 / W-02）

### W-01：RangeSlider 的 `min_range` 可破坏硬范围 → 已修复

- 证据位置：`src/widget/input_widgets/range_slider.rs`。
- 根因：`set_min_range` 只 `.max(0.0)`，不设上限；各 setter 由 `upper - min_range` 推导可容忍区间，于是 `min_range` 大于跨度时 lower 被推到 `min` 以下（默认 `[0,100]` 上 `set_min_range(200)` 后可得 lower=-100）。
- 修复：新增 `max_min_range()`（=`max-min`）、`reconcile_bounds()`（强制 `min<=max` 且 `0<=min_range<=max-min`）、`snap_into(value,lo,hi)`（步进吸附 + NaN 安全 + 区间钳制）。`set_min/max_value`、`set_min_range`、三个句柄 setter 全部先 `reconcile_bounds` 再按统一规则放置句柄。
- 验证：新增 3 个测试——`a_min_range_wider_than_the_span_cannot_break_the_bounds`、`shrinking_the_span_reconciles_a_now_too_wide_min_range`、`the_range_invariant_holds_across_arbitrary_setter_orders`（对 min/max/min_range/NaN/极值做笛卡尔积，恒有 `min<=lower<=upper<=max` 且有限）。

### W-02：VideoPlayer 时钟可被负数/NaN 污染 → 已修复

- 证据位置：`src/widget/media_widgets/video_player.rs`。
- 根因：`tick` 未校验 `delta_secs`（负值倒退、NaN 使时间永久 NaN，结束判断恒假并持续广播异常值）；`seek(NaN)` 后 clamp 无损。
- 修复：`tick` 拒绝非有限或负数 delta（返回 false，不改状态）；`seek` 忽略非有限输入；`current_time` 累加后再 `clamp(0, duration)` 兜底。
- 验证：新增 `an_invalid_tick_delta_does_not_corrupt_the_clock`（NaN/±inf/-10 都不动时钟、不停播放；合法 delta 正常推进）与 `a_non_finite_seek_is_ignored`。

### §6.1 门禁 `check_event_payload_types.py` 的载体判定错误 → 已修复（E-04 真实缺陷）

- 现象：上轮日志称门禁「333 事件全一致（exit 0）」。复核实跑为 **exit 1，36 条不一致**。
- 根因（两处，均为门禁自身缺陷而非控件缺陷）：
  1. `_closure_carrier` 用**固定优先级** `(UInt, Int, Float, Bool, String, Null, Tuple, Rect)` 查找载体。`Float` 排在 `Tuple` 之前，于是 `CapabilityValue::Tuple(alloc::vec![CapabilityValue::Float(a), …])` 被误报为 `Float`（UInt 同理）——把本已正确的结构化 arm 判成错误。
  2. 改为「首个出现即载体」后，又对**带块体**的 arm 误判：`|v| { let mut items = …; items.push(CapabilityValue::UInt(…)); CapabilityValue::Tuple(items) }` 中先出现的 `UInt` 被当成返回载体。
- 修复：`_closure_carrier` 改为——若闭包体构建了 `CapabilityValue::Tuple`/`Rect`，则为载体（嵌套标量是其元素）；否则取最左标量变体。

### §7.1 E-15：接线查询不是 per-instance → 已修复

- 证据位置：`src/signal/core_signal.rs`、`generic_signal.rs`、`event_signal_ref.rs`、`event_bridge.rs`。
- 根因：`event_is_wired`/`unwired_events_for` 只比较 `forwarded.event_name` 与 `is_connected()`，而 `is_connected` 捕获的是**当初接线的 source**，不是当前参数 widget。因此接线 `A` 后，从未接线的同类兄弟 `B` 也报告已接线（假阳性）。
- 修复：
  - `Signal::identity()` 返回 `Arc::as_ptr(&inner)`（唯一标识存活信号）；`GenericSignal::identity()` 转发之。
  - `EventSignalRef` 新增 `identity: usize` 字段与 `identity()`，在 `unit`/`mapped` 构造时捕获。
  - `Forwarded` 新增 `signal_identity`，在 `forward_unit`/`forward_mapped`/`wire_one` 三处写入。
  - `event_is_wired` 现解析 widget 自身信号并**要求身份一致**才报告 wired，成为真正的 per-instance 查询。
- 验证：`tests/event_wiring_test.rs::wiring_one_instance_does_not_report_a_sibling_as_wired` —— 接线 `A` 后 `event_is_wired(&b,"clicked")==false`、`unwired_events_for(&b)` 为 `B` 的全量短缺，而 `A` 为 `Some(0)`。

### §7.2 E-16：JSON 全局 handler 注册表把借用带入用户代码 → 已修复

- 证据位置：`src/json/events.rs`。
- 根因：`invoke_global_handler` 持 `handlers.borrow()` 调用 `EventHandlerMap::invoke`，后者直接执行闭包；闭包内注册/清空 handler 需同一 `RefCell` 的 `borrow_mut` → `RefCell already borrowed` panic。
- 修复：新增 `EventHandlerMap::take`/`restore`；`invoke_global_handler` 在短 `borrow_mut` 下取出 handler，释放借用后执行，并用 `RestoreGuard` 在正常返回与 unwind 两条路径上恢复（`restore` 用 `or_insert`，不覆盖回调自注册的新 handler）。`invoke(&self)` 保留为直读直调。
- 验证：`json::events::tests::a_global_handler_may_register_another_handler_while_running` 与 `..._may_clear_the_registry_while_running` 复现原 panic 场景，现全绿。

### §7.3 E-17：属性写入回调重入仍 panic → 已修复

- 证据位置：`src/widget/runtime.rs::with_widget_mut`。
- 根因：`map.borrow_mut().get_mut(&id).map(|entry| f(...))` 在 `f` 执行期间仍持有 `MOUNTED` 可变借用；属性 setter 作为 `f` 同步发信号 → 用户回调读注册表（`geometry_of`/`with_widget`）→ 同一 `RefCell` panic。
- 修复：`with_widget_mut` 先 detach（移除条目），安装 `LentGuard` 后运行 `f`，返回前重插入（`entry().or_insert()`，尊重回调内的销毁/重挂载）。借用只覆盖 map 操作，不跨用户代码。

### §7.4 E-18：输入回调不能读取自身已提交状态 → 已修复

- 证据位置：`src/widget/runtime.rs`（`LENT_OUT`、`DispatchGuard`、`with_widget`、`geometry_of`、`is_mounted`）。
- 根因：`dispatch_event` 在 `handle_event` 期间把控件移出 `MOUNTED`，回调内 `geometry_of(自身 id)` 得 `None`，与“对象已销毁”不可区分。
- 修复：新增 `LENT_OUT: RefCell<BTreeMap<ObjectId, NonNull<dyn Widget>>>`，由 `LentGuard`（dispatch 与 with_widget_mut 共用）在调用期间登记只读借出指针；只读访问器（`with_widget`/`geometry_of`/`is_mounted`）在 `MOUNTED` 未命中后回退到借出表。`is_mounted` 同时经 `registry_id_of` 解析 widget 自身 id，使 `draw_of` 的 mounted 判定语义与旧行为一致（旧行为依赖借用冲突隐式返回 true，现改为显式由借出状态推导）。嵌套**写**自身仍被 `with_widget_mut` 的 `lent_mutating` 显式拒绝（返回 `None`），不制造别名 `&mut`。

### §7.5 E-19：dispatch 没有 unwind 生命周期保护 → 已修复

- 证据位置：`src/widget/runtime.rs::dispatch_event`（新增 `DispatchGuard`）。
- 根因：`remove + DISPATCHING.insert` 后直接 `handle_event`；回调 panic 时不会执行 `DISPATCHING.remove`、tombstone 消费、`MOUNTED` 重插入，导致 `is_mounted=false` 而 `unregister(id)` 仍返回 true（残留 dispatch 标记）。
- 修复：`DispatchGuard` 安装只读借出并携带完成逻辑；`finish()` 在正常路径清理 `DISPATCHING`、消费 tombstone、移除借出；`Drop` 在 unwind 路径清理 `LENT_OUT` 与 `DISPATCHING`。两条路径下注册表状态一致。
- 验证：`widget::runtime::tests::a_panicking_input_callback_leaves_no_stale_dispatch_state` —— `catch_unwind` 后 `is_mounted==false` 且 `unregister` 返回 `false`。

### §7.6 E-20：TreeTable producer 漏掉选择清除通知 → 已修复

### §7.7 E-21：并发 emit 的“正在执行”被当成无订阅 → 已修复

- 证据位置：`src/signal/core_signal.rs`。
- 根因：`emit` 取出 callback 执行期间，另一线程 emit 发现 `callback=None`（条目仍在且未 blocked）即静默跳过，无排队/错误/诊断。
- 修复：`SignalInner` 增 `emit_serial: Mutex<()>`（`not(alloc_frugal)`）；线程本地 `EMITTING` 记录本线程正在发射的信号身份。`emit` 在本线程未发射该信号时取串行锁，否则视为同线程重入跳过（保持既有重入语义）。跨线程 emit 排队后完整投递，不再丢值。`mini`（`alloc_frugal`，单线程嵌入式面）不引入该锁并保持原语义，注释写明。
- 验证：`a_concurrent_emit_is_delivered_rather_than_silently_dropped` —— 两个 `Barrier` 确定性地让第一次回调停住，主线程并发 emit 第二个值；断言两次 emit 均送达（观察者执行 2 次）。既有 `a_re_entrant_emit_skips_the_slot_still_on_the_stack` 等 12 项仍绿，证明同线程重入语义未被破坏。

### §7.8 E-22：重复接线/动态绑定的累加语义 → 已决并修复

### §9.4 E-29：并发交付串行锁在跨信号转发中形成死锁 → 已修复

- 证据位置：`src/signal/core_signal.rs`（`SlotSlot`、`emit_inner`）。
- 根因：E-21 修复在整个 callback 期间持有**信号级** `emit_serial` 锁；T1 持 A 锁等 B、T2 持 B 锁等 A，形成锁顺序环，永不完成。
- 修复（重建 emit 模型）：每个 slot 的 callback 改为 `Mutex<SlotFn<T>>` + 一个待发 `Vec<T>`；`emit` 在短读锁下克隆 `Arc<SlotSlot>`，然后 `try_lock_recover` 取 callback：

- 辅助：`compat::try_lock_recover` 区分“忙”与“中毒”；对 `std::sync::Mutex` 用 `try_lock` 并在 Poisoned 时 `into_inner()` 恢复（避免 panic 后锁中毒被当成 Forever-busy）。

## §12 独立复核修正：runtime 借出别名与注销重插入（2026-10-04）

对 issue E-18/E-30 的实现做全路径核验时发现两处未闭环：

- **E-18 安全性**：`dispatch_event` / `with_widget_mut` 持有 `&mut Widget` 调用用户代码，期间 signal callback 同步执行。旧 `LENT_OUT` 通过裸指针重新创建 `&dyn Widget`，即使 getter 只读，也与仍有效的独占 `&mut` 重叠，不能作为安全的重入读取实现。新增 `LENT_EXCLUSIVE` 标记；同一可变借出期间不再通过该指针读取，`with_widget` / `geometry_of` 返回不可用，`is_mounted` 仍从借出标记返回 true，其他控件的访问不受影响。新增/调整运行时测试验证该边界。
- **E-18 未闭环范围**：此安全修正没有实现“回调读取当前控件最新状态”的原始需求。由于通用 `Widget` API 的同步回调仍处于 `&mut Widget` 方法调用期间，不能以保存裸指针重借的方式兑现该需求；issue 状态已降为“安全修正，行为未闭环”，需要后续设计安全快照或事件状态 API。
- **E-30 生命周期**：`with_widget` detach 后若回调 `unregister` 当前 id，旧路径没有 in-flight tombstone，返回时仍会重插入原 widget。现在 `with_widget` 也使用 `InFlightGuard`，完成时消费销毁 tombstone，已注销控件不再复活；unwind 时同时清理 marker/tombstone。新增 `unregister_during_a_read_loan_is_not_undone_by_reinsertion` 回归测试。

## §13 独立复核补强：once 并发领取与 VideoPlayer 时钟边界（2026-10-04）

继续对 issue 已标记完成的修改做独立核验时，发现两项验收边界未完全闭合：

- **E-21 `connect_once` 并发竞态及 FIFO**：普通 slot 以并发待发队列保留第二个 emit 的值；但 once slot 旧代码先从 map 克隆 slot、之后才读 `once` 标志并移除。两个并发 emit 若都在移除前克隆到 slot，就会有一个值排队，并在首次 callback 返回后再次执行 once callback。现在在 `emit_inner` 同一个 map 写锁临界区中完成 slot 查找和 once 条目移除；竞争者只能看到已移除的条目。另把 pending 从 LIFO `Vec::pop` 改为 FIFO `VecDeque::pop_front`，保持 concurrent emits 获得 pending 锁的顺序。同步更新 `core_signal.rs` 的架构和 emit 契约注释，删除已过时的 take/restore、并发等待描述。
- **W-02 时长缩短**：issue 验收已要求缩短 duration 后时钟仍在合法区间，但 `set_duration` 只改 duration，保留了可能大于新上限的 `current_time`。现在非有限 duration 被忽略；有效 duration 更新会立即将当前时间夹紧到 `[0, duration]`，若时间发生变化则发出 `time_updated`，随后请求重绘。非有限 playback rate 也忽略，避免保存无穷倍速。

回归测试：

- `concurrent_emits_claim_a_once_slot_only_once` 使用两个并发 emit worker、每轮同步屏障和 200 轮重复，断言 each once slot 恰好调用一次并从连接表移除。
- `concurrent_pending_values_are_delivered_fifo` 用 barrier 暂停第一次 callback，再依次 emit 两个值，断言观察顺序为 `[1, 2, 3]`。
- `shrinking_duration_clamps_the_clock_and_emits_the_new_time` 断言时长收缩后状态与发出的事件载荷都等于新 duration，并验证非有限 duration 不覆盖现有值。
- `video_player_playback_rate` 增加非有限 rate 保持既有有效值的断言。

### P-11 的闭包生命周期补强

- 独立复核发现旧 `on_rejected.forget()` 将每次 `clipboard.writeText` 的 Rust 闭包永久泄漏；“每次一次性写入”并不构成进程生命周期内有界。
