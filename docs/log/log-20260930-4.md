## §1 🔴🔴 设计器生成器：`create_for` **没有任何构造臂**（生成程序永远白屏）

### 1.1 现象

构造文档（`examples/probe_generator_roundtrip.rs`）：

```json
{ "main_window": { "width": 640, "height": 480, "title": "Demo",
    "background": "#ffffff", "padding": 8,
    "events": { "clicked": "on_save" },
    "children": [ { "id": "run", "widget": "btn", "text": "Run" } ] } }
```

实测（修复前）：

```
availability("main_window") = Local, constructor_type_name = "UnsupportedControl"
availability("btn")         = Local, constructor_type_name = "UnsupportedControl"
GenerationReport { nodes_emitted: 1, properties_emitted: 7, wires_emitted: 1,
                   unsupported: [], ... }        ← 报告「干净」

fn create_for(...) {
    let mut control = match widget {
        _ => None,        ← 一个构造臂都没有
    };
```

### 1.2 根因：两张表各写一份，且互不校验

| 环节 | 位置 | 用什么判定 |
|---|---|---|
| 可用性判定 | `availability_with` | `factory.create(name)` — **工厂解析别名** |
| 构造臂生成 | `constructor_path` | 手写 `match`，**只列正名** |
| 臂的过滤 | `assemble` | `if path.ends_with("UnsupportedControl") { continue; }` **静默跳过** |

`capability.rs:613-617` 把每个 alias 都 insert 进 `constructors`，所以 `create("btn")` 成功；
但 `constructor_path("btn")` 落到 `_` 分支。于是第 3 步静默 `continue`，报告
`unsupported: []` 仍然「干净」——**报告说成功、程序建不出任何控件**（原则 #18）。

`src/view/engine.rs:303` 的 `let Some(root_id) = create(&root) else {...}` 决定：
`create_for` 返回 `None` → 整棵树不挂载 → 白屏。

### 1.3 修复（两层）

1. **先生成器表与工厂表对齐**：`constructor_path` / `constructor_type_name` /
   `constructor_takes_text` 全部改为**先用 `WidgetFactory::canonical_name` 解析**再匹配，
   别名因此能到达其控件的臂。新增 `WidgetFactory::canonical_name` / `constructible_names` /
   `aliases_of` / `constructor_for`（单一定义源，原则 #54/#101）。
2. **`assemble` 的静默 `continue` 改为上报**：无法生成臂的名字进 `report.unsupported`，
   让「不支持的条目」这一列**能真实地非空**。

### 1.4 更深一层：168 个控件根本没有臂

新门禁（§6）一上线就报出真实规模：

```
[1] canonical `table` is constructible by the registry but the generator has no constructor type
[1] canonical `tree_view` …  [1] canonical `code_editor` …     共 168 条
```

生成器的表只覆盖 **20 / 188** 个已注册控件。**这类问题的正确修法不是补 168 个臂**
（必然再次漂移），而是让生成的 `create_for` **直接走注册表**：

```rust
let factory = rust_widgets::widget::capability::WidgetFactory::new_with_defaults();
let control = factory.create(node.widget.as_str(), geometry, text)?;
let id = rust_widgets::widget::runtime::register(control)?;
```

于是「注册表能建什么」与「生成程序能建什么」**按构造就是同一个事实**（原则 #101）。
`constructor_path` / `constructor_takes_text` 现在只服务 **stripped** 模板
（`mini`/`embedded` 没有 `full_widgets`，用不了工厂）。

### 1.5 验证

- `examples/probe_generator_roundtrip.rs`：`constructor_type_name("btn") == "Button"`。
- 生成的 `create_for` 实测为工厂调用，`ApplyReport { widgets_created: 3, errors: [] }`。
- `bash tools/check_generated_sources.sh` → **passed**（含其两项反向注入）。

## §2 🔴 生成器：根节点 `width`/`height` **写两次且四次全被拒绝**

### 2.1 取证

文档 5 个标量键，报告却 `properties_emitted: 7`（多出重复的 `width`/`height`）。
`Node::prop` 是 `self.props.insert(..)`（后写覆盖），`UInt` 那一对是死代码。
更关键：`WINDOW_PROPERTIES`（`properties_other.in.rs`）**没有 `width`/`height`**，
而 `geometry` 是**只读**（`properties_trait.rs:109` `ReadOnlyProperty`）。
→ 模式 1 能定尺寸（loader 的 `apply_geometry_shorthand`），模式 2 **不能**。

### 2.2 修复

- 删除根尺寸的 `prop("width"/"height")`；改为在 `resolved_at_generation` 记一行
  「root 由自身 geometry 定尺寸」，并把**根尺寸交给 loader-owned 路径**处理。
- 新增共享判定：生成器改为调用 **loader 自己的** `crate::json::is_loader_owned_key`
  （此前用的是 `is_style_only_property`，只列 CSS 内部词，**没有一个真实 JSON 键**），
  凡是 loader 结构化消费的键不再发成 `.prop(..)`，而是在报告里记明（原则 #12 不静默丢弃）。
- **例外（我在本轮自己踩到的坑）**：`text` / `title` 虽属 loader-owned，但生成的
  `create_for` 要用它们给构造函数传参，**必须保留**。第一版把它们一起丢掉，
  `a_changed_document_reports_updated` 立刻变红——那是对我过修的**反向验证**。
  新增 `carries_constructor_text()` 明确这一例外。

### 2.3 验证

报告 `properties_emitted: 1`（仅 `title`），5 个 loader-owned 键逐条记入
`resolved_at_generation`；`cargo test --lib -- designer` **41 passed; 0 failed**。

## §3 🔴 生成器：`__wire_*` 载体属性**从不清除**，每个已接线节点必报错

`WIRE_PROP_PREFIX` 的文档承诺「a prop with this prefix is **stripped** before the node is
used as a control description」，但 `create_for` 只**读**不**删**，而
`ViewEngine::write_declared_properties` 遍历**每一个** prop → 实测必报
`PropertyRefused { name: "__wire_events.clicked", reason: "UnknownProperty" }`。
提交的产物用 `let _ = report;` 掩盖。

**修复**：新增 `crate::view::is_generated_wire_prop`（单一定义），在**两个**写入点
（`engine::write_declared_properties`、`apply::insert_subtree`）跳过它。

**验证**：探针 `mount report` 的 `errors` 由 `[PropertyRefused{__wire_…}]` 变为 **`[]`**。

## §4 🟠 声明式层：`Host::Overlay`（portal）在 `update` 路径上**被忽略**

`mount` 路径（`engine.rs:518`）处理 `Host::Overlay`；`apply.rs` 全文**零 `Host` 引用**，
`insert_subtree` / `reparent` 无条件挂到声明父级。`update → Patch::Insert` 真实可达
（断点切换即产生 `Insert`），于是一个重建后才出现的 tooltip 会落进父级裁剪。

**修复（三处，缺一不可）**
1. `apply.rs` 新增 `OverlayHost` 解析器类型 + `apply_with_reserved_and_overlay`；
   `insert_subtree` 按 `node.host` 选 host。
2. `engine.rs` 的 `update` 传入 overlay 解析器（`Cell` 承载，避免 `&mut self` 借用冲突）。
3. **`reindex_by_identity` 也要认 portal** —— 否则它的布局父级是 overlay 层、按声明父级
   查不到，节点会从 `id_of_path` 掉出去，后续按路径寻址全报 `UnknownWidget`。
   为此给 `BoundJsonLayout` 新增 `overlay_root` / `set_overlay_root`
   （第二个 host root，显式命名而非「猜某个无父节点」）。

**验证**：新增 `a_portal_inserted_by_an_update_is_hosted_in_the_overlay_layer`，
并**反向验证**——把 `Host::Overlay => layout.overlay_root()` 改回 `parent_id`，该测试
**立刻变红**（`the portal keeps its declared path`），恢复后 32 passed。

## §5 🟠/🔴 事件生产链：`Event::KeyRelease` **在所有后端都没有生产者**

### 5.1 取证：门禁被测试脚手架骗过

`Event::KeyRelease` 有构造函数、有 `shortcut::Modifiers` 访问器、有消费方
（`widget/base.rs:939` → `key_up`），但 `grep -rn KeyRelease src/platform/` → **零命中**。
唯一「生产者」是 `src/test/harness.rs:70` 的 `send_key_release` ——
**而 `src/test/` 是生产模块**（`lib.rs` 的 `pub mod test;`，非 `#[cfg(test)]`），
于是门禁的 `helper_is_called` 把它算成生产者，变体「看起来可达」。

### 5.2 冰山：不止一处

| 后端 | OS 侧对应消息 | 修复前 |
|---|---|---|
| Windows | `WM_KEYUP` | 无臂 |
| Windows canvas | `WM_KEYUP` | 无臂 |
| Linux GTK canvas | `key-release-event` | 无连接 |
| Linux GTK 窗口 | `key-release-event` | 无连接 |
| macOS | `keyUp:` | 未注册 selector |
| HarmonyOS | `KEY_ACTION_UP` | 有代码但注释称「库里没有对应事件」而 return |

### 5.3 修复

六个后端全部补上 `KeyRelease` 生产；并修掉顺带发现的**第二个**缺陷：
Linux 窗口的 `KeyPress` 硬编码 `modifiers: 0`（Ctrl/Shift 快捷键永不生效，
与 `linux::canvas` 的行为不一致），改为调用共享的 `modifier_bits`。
HarmonyOS 那条**错误注释**（「库里没有对应事件」）一并改正。

**目标解析统一**：Windows 侧新增 `key_target_for` / `key_target_for_id`，
让 press 与 release 走同一份解析，不会投递到不同控件。

### 5.4 门禁加固（本轮的第二个「假通过」）

`tools/check_event_variants_have_a_producer.py` 有两处会被绕过：

1. `src/test/`（合成输入脚手架）被当成生产者；
2. **兄弟文件形式的测试模块**——`#[cfg(test)] mod tests;` 声明在**父文件**里，而
   `tests.rs` 自身没有 `#[cfg(test)]`，于是 `src/shortcut/tests.rs` 的构造被当成生产代码。

新增 `TEST_INJECTION_DIR` 与 `is_test_only_module()`，两处都排除。

**反向验证**：把六个真实生产者与脚手架全部改名后，门禁**由 PASS 变 FAIL** 并点名
`Event::KeyRelease`；恢复后重新 PASS。

## §7 🟠 Windows 平台：`WM_SETFOCUS` 缺失（`WM_KILLFOCUS` 的逆向）

Windows 窗口与 canvas 都在 `WM_KILLFOCUS` 上报 `Focused(false)`，但**没有任何地方报回来**。
后果：alt-tab 离开再回来后，焦点环与光标不再绘制；更糟的是 `WM_KEYDOWN` 的
`focused_widget().unwrap_or(window_id)` 回退到窗口，**按键不再进用户原本在输入的控件**。

**修复**：窗口与 canvas 各补 `WM_SETFOCUS` 臂（`Focused(true)` + 失效重绘）。

## §9 🔵 未增加既有破损：`mini` 档案的错误数**只减不增**

本轮改动触及 `windows/types.rs`，而 `mini` 档案在 Windows 上**基线即编译失败**（22 error，
历史存量，`wnd_proc` 引用了被 gate 掉的 `widget::runtime` / `super::canvas`）。
按「不增加既有破损」原则，我做了两件事：

1. 本轮**新增**的 `WM_KEYUP` / `WM_SETFOCUS` 臂与其辅助函数全部 gate 在
   `widgets_unstripped` 上，并相应 gate 它们的 Win32 导入（避免 stripped 档案的
   unused-import 警告）。
2. **顺带把既有**的 `WM_KILLFOCUS` 臂也 gate 上（它同样引用 `widget::runtime`）。

实测对比（`cargo check --no-default-features --features mini`）：

```
基线： 22 error, 1 warning
修复后：20 error, 1 warning     ← 只减不增
```

### 被修正的**测试所编码的错误契约**（重要）

`tests/mode_consistency_test.rs::both_modes_agree_on_property_values` 原断言
「文档里每个标量键都要在生成源码里出现 `.prop("name"`」——**这正是 §2 的缺陷本身**。
它把「发出去被拒绝」当成正确，所以 §2 修好之后它反而变红。已重写为按
`crate::json::is_loader_owned_key` 判定：loader-owned 键**必须不发**且**必须在报告里被记录**，
真实属性才要求 name+value 同时出现。
