## §1 🔴 macOS canvas 编译失败：`MousePhase` 匹配不穷尽（`--features desktop` 直接编不过）

### 1.1 现象

`src/platform/types.rs` 的 `MousePhase`（该枚举明确定位为「macOS 与 Windows canvas 共用，
不得各写一份」——原则 #54）有 6 个变体：`Press` / `Release` / `Drag` /
`SecondaryPress` / `SecondaryRelease` / `DoubleClick`。

Windows 的两个 backend **全部**消费 6 个变体；macOS canvas 的
`forward_mouse`（`src/platform/macos/canvas.rs:444`）**只有 3 个臂**：

```
error[E0004]: non-exhaustive patterns: `MousePhase::SecondaryPress`,
              `MousePhase::SecondaryRelease` and `MousePhase::DoubleClick` not covered
   --> src/platform/macos/canvas.rs:444:36
```

### 1.2 影响面（比「一个 error」严重得多）

macOS 上的 `--features desktop`（也就是 manifest 的 `default`）**根本编译不出来**。
实测波及的既有门禁：

| 门禁 | 失败原因 |
|---|---|
| `check_profiles.sh` | `[1/9] cargo check`（默认 desktop）编不过 |
| `check_designer_feature_gate.sh` | 探针 crate 依赖 desktop，编不过 |
| `check_designer_manifest_roundtrip.sh` | 同上 |
| `check_generated_sources.sh` / `check_generator_agrees_with_registry.sh` | 同上 |
| `check_generator_output_compiles.sh` / `check_mode_consistency.sh` | 同上 |
| `check_behavior_matrix.sh` / `check_binding_symbol_coverage.sh` | 同上 |
| `check_cjk_shards_cover_the_face.sh` / `check_icon_data_is_opt_in.sh` | 同上 |
| `check_runtime_fonts_is_opt_in.sh` / `check_theme_fixtures.sh` / `check_web_engine_honest.sh` | 同上 |
| `check_widget_registration_fidelity.sh` / `check_declaration_implementation_alignment.sh` | 同上 |
| `check_control_rendering.sh` / `check_svg_snapshots.sh` / `check_visual_regression.sh` | 同上 |

**20 个门禁失败里有 13 个是这一条根因**。这正是「一个缺陷长成一类」的冰山：
枚举加了 3 个变体，两个 backend 里只有一个跟着改。

### 1.3 修复

补全 3 个臂，与 `windows/canvas.rs:545-568` 语义对齐：

| 变体 | macOS 产出 |
|---|---|
| `SecondaryPress` | `Event::mouse_press_with(.., mouse_button::SECONDARY, modifiers)` |
| `SecondaryRelease` | `Event::MouseRelease { .., button: mouse_button::SECONDARY }` |
| `DoubleClick` | `Event::mouse_double_click(.., PRIMARY)` |

并把 focus 判定扩为 `Press | SecondaryPress | DoubleClick`（Windows 的窗口/canvas 两处
都是这个集合，macOS 原本只认 `Press`）。

### 1.4 更深一层：三个 AppKit selector **从未注册**

`forward_mouse` 有了臂还不够 —— `MousePhase` 的变体得有人**产生**。实测：

- `rightMouseDown:` / `rightMouseUp:` —— **未注册**。AppKit 右键有自己的 responder 方法，
  不注册就永远不会发出 `SecondaryPress`/`SecondaryRelease`，右键菜单在 macOS 上不可达。
- 双击 —— macOS 原本没有检测，`-mouseDown:` 一律报 `Press`。
  用 `NSEvent.clickCount`（Apple 自己定义双击区间的地方）判定 `>= 2`，
  不自己造一个时间阈值（原则 #37 精神：事实从平台取，不自造）。

新增 `right_mouse_down` / `right_mouse_up` / `click_count`，并在类声明里注册
`rightMouseDown:` / `rightMouseUp:`。

### 1.5 验证（定点）

```
$ cd /tmp/rwprobe && cargo check            # 依赖 rust_widgets --features desktop
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 9.03s
```

修复前同命令报 E0004（见 §1.1 原文），修复后 `Finished`。

## §2 🔴 macOS hover 完全失效：`mouseMoved:` 与 `mouseEntered:` 都缺

### 2.1 取证：tracking area 请求了，处理器没注册

`install_tracking_area`（`canvas.rs`）构造 `NSTrackingArea` 时请求了
`NSTrackingMouseEntered | NSTrackingMouseExited`，但类声明里**只注册了 `mouseExited:`**。

这不是「少一个事件」这么轻：

1. AppKit 对已实现 tracking-area 协议的视图，会在指针进入时发送 `-mouseEntered:`。
   视图没实现该 selector → `NSView` 默认实现走 `doesNotRecognizeSelector:` →
   抛 `NSInvalidArgumentException`。**外部异常无法穿过 Rust 栈展开，进程直接 abort。**
2. 语义上也是真缺口：`clear_hover` 在离开时执行，而**没有任何路径重新进入**，
   于是「指针从外部移入」时被悬停的控件不会再高亮。

### 2.2 冰山：`mouseMoved:` 也缺 —— hover 在 macOS 上**完全**不工作

更关键的一条：`NSTrackingMouseMoved` **没有**被请求，`mouseMoved:` **没有**被注册。

- Windows：`WM_MOUSEMOVE` → `MousePhase::Drag` → `Event::MouseMove`（**不需要按键按住**）
- GTK：`connect_motion_notify_event` → `Event::MouseMove`（同上）
- macOS：只有 `mouseDragged:`（**必须按住按键**）

而 hover 的全部来源就是一次普通的 move ——
`widget::runtime::dispatch_pointer_event` 每次都调 `dispatch_hover_transition`
（`src/widget/runtime.rs:802`），由它在 `MouseMove` 上合成 `MouseEnter`/`MouseLeave` 对。

所以 macOS 是**唯一**一个「指针在控件之间移动时永不产生任何事件」的后端，
即：**macOS 上没有任何控件会高亮**。

### 2.3 修复

1. 新增 `TRACKING_MOUSE_MOVED = 0x0004` 常量并加入 tracking area 的 options；
2. 新增 `mouse_moved` 处理器，注册 `mouseMoved:`；
3. 新增 `mouse_entered` 处理器，注册 `mouseEntered:`（`event_local_point` → 绝对坐标 →
   `route_pointer_event`，与一次 move 走同一条路由，两个 `MouseEnter` 不会重复）。

drag 与 move 共用 `MousePhase::Drag`（两者的 payload 都是 `Event::MouseMove`，
真正区分它们的是 AppKit 用哪个消息送来的，路由层并不关心），因此不复制一份翻译。

### 2.4 验证（定点）

```
$ cd /tmp/rwprobe && cargo check
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 3.98s
```

## §3 🔴 GTK 窗口：请求了 `POINTER_MOTION_MASK` / `SCROLL_MASK`，两个处理器都没接

### 3.1 取证

`src/platform/linux/platform_impl.rs` 的窗口 paint area：

```rust
paint_area.add_events(
    BUTTON_PRESS_MASK | BUTTON_RELEASE_MASK | POINTER_MOTION_MASK | SCROLL_MASK,
);
```

但整个 `platform_impl.rs` 里 **`connect_motion_notify_event` 与 `connect_scroll_event`
的命中数为 0**（`grep` 实测）。GTK 因此**真的在派发**这两个信号，结果被丢弃。

对照 `src/platform/linux/canvas.rs`：canvas **两个都接了**（`motion` 在 :155、`scroll` 在 :267）。

| 能力 | GTK canvas | GTK 窗口（修复前） |
|---|---|---|
| hover（`MouseMove`） | ✅ | ❌ |
| 滚轮（`Wheel`） | ✅ | ❌ |
| 离开清 hover | ✅ `leave_notify_event` | ❌ |

后果：**GTK 窗口上的控件永不显示 hover 高亮，scroll area 永不滚动**，
而同一个窗口里 mount 的 canvas 却可以 —— 正是该代码块自己文档里记的
「窗口/canvas 不对称」缺陷，往后漏了一条消息。

### 3.2 修复

1. 请求 `LEAVE_NOTIFY_MASK`（离开通道同样要 mask 才会送达）；
2. 新增 `connect_motion_notify_event` → `dispatch_pointer_event(.., MouseMove ..)`；
3. 新增 `connect_scroll_event` → `Event::Wheel`（`direction()` 优先于 `delta()`，
   与 canvas 的解码一致），投递给 `hovered_widget().unwrap_or(window_widget)`；
4. 新增 `connect_leave_notify_event` → `clear_hover(Point::new(0,0))`；
5. 补 `KEY_PRESS_MASK | KEY_RELEASE_MASK`（canvas 已请求；两个 surface 一致，
   避免下一轮再出现同族不对称）。

所有新处理器都走 `widget_id_for_host_window(id)` 做 platform id → widget id 翻译
（该文件已有详尽注释说明为什么必须翻译，否则一切静默 no-op）。

### 3.3 验证（定点）

```
$ cargo check --no-default-features --features "linux-gtk desktop-runtime desktop touch"
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 1.65s   # 0 error 0 warning
```

## §4 🔴 `designer` 特征图缺一条边：`desktop,no-declarative-view` 必然编译失败

### 4.1 现象

```
$ cargo check --no-default-features --features desktop,no-declarative-view --all-targets
error[E0433]: cannot find `view` in `crate`
   --> src/designer/mod.rs:94:20
    |
 94 | ...      crate::view::GENERATED_WIRE_PR...
    |                 ^^^^ could not find `view` in the crate root
note: found an item that was configured out
   --> src/lib.rs:276:9
    |
275 | #[cfg(declarative_view)]
276 | pub mod view;
```

### 4.2 根因：**特征图允许一个不可能的组合存在**

- `designer`（`= ["serde_json"]`）生成会命名 `crate::view` 的源码；
- `crate::view` 由 `build.rs` 的 `declarative_view` 别名门控，
  而该别名在 `no-declarative-view` 打开时为 **false**；
- 于是 `designer + no-declarative-view` 是一个**语法合法但语义矛盾**的组合，
  Cargo 不会拒绝它，直到编译器撞上 `pub mod designer` 里的 `crate::view`。

更隐蔽的是：**`--lib` 能编过**，只有 `--all-targets`（连带 `#[cfg(test)]` 的测试模块）
才炸。所以任何只跑 `--lib` 的验证都会漏掉它 —— 而 `no-declarative-view` 恰恰是
`check_profiles.sh` 专门列出的一个受支持组合。

### 4.3 修复（两层，缺一不可）

1. **在特征图上声明依赖边**（根因修复）：新增能力特征 `declarative-view = []`
   （正向拼写），令 `designer = ["serde_json", "declarative-view"]`。
   这样矛盾组合由 Cargo 自身消解：要 `designer` 就会把 `declarative-view` 拉进来。
2. **`build.rs` 的裁决规则保持单一**：`declarative-view` 不自己产生 `rustc-cfg`
   （`declarative_view` 仍只由 `no-declarative-view` 的**缺席**决定），
   于是 `designer + no-declarative-view` 下别名仍为 false、`mod view` 仍不编译、
   生成器**编译并在报告里说明**而不是发模板代码 —— 这正是
   `check_profiles.sh` 那一行想要的行为，也是诚实的结果（不下发它拿不到的层）。
   同时把 `declarative-view` 加入 `rerun-if-env-changed` 列表。
3. 把 `src/designer/mod.rs` 的 `wire_prefix_agreement_tests` 门控由 `cfg(test)`
   收紧为 `cfg(all(test, declarative_view))` —— 它断言的对象之一属于 `crate::view`，
   层不在时无物可比（原则 #53：能力缺失用一次门控表达，不写两套测试体）。

### 4.4 验证（定点）

```
$ cargo check --no-default-features --features desktop,no-declarative-view --all-targets
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 27.64s
$ cargo check --no-default-features --features tablet,designer --all-targets
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.66s
```

## §6 🟠 Wayland：「reports its size and input」是**文档欺骗**（原则 #18）

`src/platform/wayland/platform_impl.rs` 的 `supports_surfaces` 文档里写着该后端
"creates a real surface, and reports its size and **input**"。实测该后端
**不绑定 `wl_seat`**，没有 `wl_pointer` / `wl_keyboard`（`grep -n "wl_seat\|wl_pointer\|wl_keyboard"`
零命中），指针与键盘事件全部由**宿主**注入。

同一文件的 `capabilities()` 恰恰就因为同类问题被修过（`ime`/`accessibility` 曾谎报 true）——
说明这句话是移除 `wl_seat` 之前留下的**陈旧论断**，与它并排的那段修正注释自相矛盾。

**修复**：把该句改为「宿主通过 injected-trigger 通道回灌指针与键盘输入」，
并显式点明「这不是『本后端上报输入』」及其理由。不改行为，只消除不实陈述。

安全判据的**证据链**（避免 `NOT_YET_CONVERTED_REASON` 里警告的“错臂比无臂更糟”）：

1. 控制声明的 `pub <name>: GenericSignal`（或 `Signal1<T>`）字段名 **等于** 发布名 —— 不是
   `button` 那种 `clicked`→`clicked_signal` 的映射（那类必须人工写）；
2. 同一文件里存在 `<name>.emit(` 或 `self.<name>.emit(` —— 只声明不发射的信号不接线；
3. arm 的**名字参数**取自字段名（`EventSignalRef::unit("<name>", &self.<name>)`），
   于是 `EventSignalRef::name()` 与调用请求的名字必然一致（缺陷 #55 的修复让这一致性成为强制）；
4. 每批写入前先跑一遍**census 对照**：arm 的发布名集合必须与 `event_published_census.txt` 完全相等，
   不等就拒绝写入并打印差集。

载荷映射的统一约定（第 4/5 批）：`Int`/`Float`/`Bool`/`String` 分别对应数字/浮点/布尔/文本，
`Option<T>::None` → `Null`（与可选属性的缺席同构），`Vec<T>` 与结构体 → debug 拼写
（hub 的名字无类型，这是诚实的损失形式）。

顺带修好了**门禁本身的三个缺陷**（#57/#58/#63）：反向注入空转、多控件文件的
arm **并集**误报、以及不识别“转发式解析”——后两个原本会给出**删掉正确 arm**或
**把 arm 复制进包装器**的补全建议，是**比缺陷更危险**的东西。

## §11 本轮总结

**发现并完整修复 54 个缺陷**，其中：

- 🔴🔴 3 个（macOS `desktop` 编不过；模态框永久阻断输入；**Android 建不出任何控件**）
- 🔴 33 个（其他不完整/假实现/未接线/工具链断路/ABI 错配/文档欺骗）
- 🟠 17 个、🔵 2 个

**同时撤销了 5 个不成立的候选**（§8），全部附取证 —— 包括一份曾被当作「实现分歧」的
`normalize`/`normalize_key` 对比，逐字核对后确认**完全相同**。

**最高价值的一条不是单点 bug，而是两个根因收敛**：

1. 20 个门禁失败中有 13 个来自「`MousePhase` 枚举加了 3 个变体，两个后端只有一个跟着改」
   这一个缺口。修根因（而不是修 13 个症状）把门禁从 **PASS=88/FAIL=20** 带到
   **PASS=109/FAIL=0**。
2. Android 的 5 个缺陷全是「只会编译、不会运行」类。它们能存活，是因为**没有任何门禁
   会真的跑那个探针** —— 修法不是修 5 个点，而是新增 `check_android_runtime.sh`，
   让这类缺陷下一次无处可藏（原则 #2 冰山法则）。
3. 文档侧的两个缺陷（#35/#36）同属「问错了问题」：旧检查问的是「这个名字是不是 Rust
   导出的 JNI 入口」（是，全部都是），而正确的问题是两个 ——「那个工厂还在不在」与
   「这个示例所属的类有没有这个方法」。两道新检查各自带反向注入。
4. 第三个根因：`check_jni_signatures.py` 把返回类型读出来就丢了（`_rust_ret`），
   于是**四个 Java 接口文件里有 4 处返回类型与 Rust ABI 不符**（包括把 `jint` 声明成
   `String`）。补上比较后，门禁立刻报出全部 4 处 —— 其中两处是真实的 ABI 危隙。
   而「拉直返回类型」又直接暴露了另一个缺陷：构建脚本的 javac 行被 `\|\| true` 吞了
   退出码，所以探针里那个 `int` 赋给 `boolean` 的错误已存在很久而无人知。
5. **最深的一条**（#46）：Android 构建的 feature 集里没有 device profile，`build.rs` 的
   `full_widgets` 因此为 false，`mount_widget_of_kind` 走 `#[cfg(not(full_widgets))]`
   分支对**每一种控件都返回 0**。也就是说：**Android 上 `create_*` 全部失效**。
   它能存活这么久，是因为三件事同时成立：① 代码能编译（只是走另一条分支）；
   ② 旧探针只测 JNI 管道，从不创建控件；③ `check_android_cross.sh` 用的是**同一份错误
   配置**，于是“验证”的正是“建不出东西”的那份。把探针加深到真的建一个控件，它当场就报
   `create_window returned 0`。修好后是 `nativeWidgetSelfTest -> 63 (0b111111)`。
