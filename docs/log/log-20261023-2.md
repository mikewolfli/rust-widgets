#### N5-02 【✅已完成】view engine：同 key 插入配对错乱 + 同路径 Remove+Insert 跳过 on_unmount（P1，Scout B #1）

- 复核（全部源码取证）：
  1. **配对错乱（孤儿控件）**：`reserve_ids_for_inserts` 的 reservation 表以 `node.key.unwrap_or_default()` 为键——keyless 节点全部共享 `""`，同 key 的第二次插入**覆盖**第一次的 id。`apply` 的 `insert_subtree` 按同一 key 取走（旧代码 `remove`），于是第一个子树采用第二个的 id，第一个分配的控件永远不挂载——每次批次泄漏一个活控件。同一 key 出现在两个不同父节点下（合法声明）同样中招。
  2. **on_unmount 被跳过（hook 泄漏）**：`reserve` 在 `run_unmount_hooks_for_removals` **之前**向 `id_of_path` 写入新子树的 id。批次同时含 `Remove{id_old}` + `Insert{new}`（`child_if` 分支翻转、key 变更——diff 的常规输出，patch 序列实测为 `[Insert, Remove]`）时，被移除根的路径被新 id 遮蔽：遍历读到新 id ∉ removed，整棵被移除子树的 `on_unmount` 静默跳过，订阅/定时器泄漏。`Replace` 不受影响（不经 reserve），但 Insert+Remove 组合必中。
- 修复：
  1. `apply.rs`：reservation 值改为 `VecDeque<ObjectId>`（新别名 `ReservedIds`，从 `view::mod` 导出）。`reserve` 侧 `entry(key).or_default().push_back(id)`；`insert_subtree` 侧 `get_mut().and_then(pop_front)`。两侧遍历顺序相同（patch 顺序 × 子节点声明序），先进先出配对精确。
  2. `engine.rs`：批次同时含 `Insert` 与 `Remove/Replace` 时，在 reserve 之前快照 `id_of_path`，unmount 遍历改读快照（lookup 以参数贯穿 `run_unmount_hooks_for_removals/for_ids/run_unmount_hooks`）；非混合批次零开销（不克隆）。
- 证据：三个新测试——`two_keyless_inserts_in_one_batch_orphan_nothing`（「每个已创建 id 都已挂载」辅助断言）、`the_same_key_under_two_parents_in_one_batch_keeps_both_reservations`、`a_remove_plus_insert_at_the_same_path_still_runs_the_unmount_hook`。**反向注入（原则 #106）**：把 push 改回「clear+push」覆盖语义，两个孤儿测试都变红（old: FAILED 2），恢复后 54 passed；hook 测试在快照时序错误（reserve 后才快照）时同样变红，实测过。`cargo test --lib view::` 273 passed、`json::` 217 passed。
- 设计说明：第一个测试的初版（旧树同为 label）会被位置匹配吃掉第一个 keyless 节点，批次只含 1 个 Insert，注入下不红——已改为旧树子节点异型（button），确保两个 Insert 真正并发。这本身就是「侦察报告只作线索」的一例：位置匹配规则改变了缺陷的触发形状。

### 12.5 复核后驳回（不改，并写下理由）

| 候选 | 结论 |
|---|---|
| `flex` 把 `hints.*.max` 写进 `item.max_size` | **驳回，已回滚并加锁**。语义上像「上界对偶于下界」，但 `Hints::fixed`（min==pref==max）正是**框架自带 `Flex` 控件**描述每个子件的方式，一旦生效，所有可增长子件都被钉在名义宽度 —— 全量测试立刻抓到 `flex_distributes_weights_in_item_order` 失败。CSS 里 `flex-grow` 与 `max-width` 本就分属两条声明，本求解器只拥有前者。保留反向测试 `a_hint_ceiling_does_not_cap_a_growing_item`，防止后人「顺手修好」。 |

### 13.1 N12-01【✅已完成】pie_menu 暗色「糊」：环形用 1 px 描边拼出来的

**现象**（用户反馈）：暗色下面板“很糊”，看不出是环形菜单。

**根因（取证）**：`fill_ring` / `fill_slice` 不是填充，而是用**一像素圆/弧描边**近似：

```rust
let strips = ((outer_r - inner_r) * 0.5).clamp(4.0, 30.0) as u32;   // 每 2 px 带一条
… context.draw_line_stroke(a, b, color, 1);                          // 线宽只有 1 px
```

条带间距 = 带宽 × 0.5 ⇒ **每两条之间留 1 px 空白**。`snapshots/svg/pie_menu.svg`（改前）含 **2305 个 `<line>`**，色值 30,30,33（轨道）与 46,46,48（崩区）交替；暗色窗口是 18,18,18，于是空白处露出更深的窗口色，整体读作同心圆网点/斑驳——即“糊”。亮色下同样存在网点，只是对比不刺眼，所以只有暗色被报。

| 暗色改前 | 暗色改后 |
|---|---|
| ![before](assets/pie-menu-n11-dark-before.png) | ![after](assets/pie-menu-n11-dark.png) |

**修复**：用渲染层已有的真实填充 `RenderContext::fill_path_non_zero`（`FillPathNonZero`，SVG / 软件 / wgpu 三条后端都已支持）：

- `fill_ring`：**两条反向绕向**的轮廓（外圆 + 内圆洞），内圆反向绕行才能让非零规则把中心挖空；
- `fill_slice`：单个闭合轮廓（外弧向前 + 内弧回头）；原来为补缝而额外画的两条径向描边随多边形一并删除；
- 采样密度 `每 2 px 弧长一点`，钳制 32…256 点（实测 60 px 半径下垂高 < 0.05 px，肉眼无棱角）。

**效果（实测）**：`pie_menu.svg` 的 `<line>`+`<path>` 从 **2309 → 13**（`<line>` 2305 → 4，仅剩四条分隔；`<path>` 4 → 9：一个双轮廓轨道 + 四个崩区 + 四个标签字形）；边框仍是 4 个 `<circle>`。整盘为纯色填充，无条纹、无接缝。每帧命令数下降两个数量级，软件/GPU 光栅器的逐线开销一并消失。

**回归测试**：`the_ring_and_its_wedges_are_filled_shapes`——断言 `<path>` ≥ 4（轨道 + 三崩区样本）且 `<line>` ≤ 12。反向注入：改前快照为 2305 条 `<line>`，该断言必然失败（数据已在本文留档）。

### 13.2 N12-02【✅已完成：原则 #1/#18】控件分类：`unclassified` 清零 + 一处误归属

**现象**（用户反馈）：有一批控件没分类。`control.md`（生成物）的家族表最后一行是 `unclassified (5)`。

**根因（取证）**：不是文档缺失，而是生成器 `tools/generate_control_index.py` 的“构造器→控件类型”解析：

```python
boxed  = re.search(r"Box::new\(\s*([A-Z][A-Za-z0-9_]*)\s*::", body)     # ①
 direct = re.search(r"([A-Z][A-Za-z0-9_]*)\s*::\s*(?:new|with_)", body)     # ②
```

① 看不见**全路径**：`Box::new(crate::widget::dialog::AlertDialog::new(..))` 的 `\(` 后面是 `crate::`，于是①不命中；②从左取第一个匹配，拿到的是 `Box::new(` 里的 `Box`。类型名变成 `Box` 后在 `declared_types()` 里查不到 → 落到 `unclassified`。五个控件（about/alert/confirm_dialog、spacer、split_layout）都是这个形态。

② 还有一个副作用：①优先于②，而①会逮住**任意一层** `Box::new(X::`——包括给子件套壳。`create_swipe_to_dismiss` 因此被解成 `Label`（它给 wrapper 设的子件），于是出现在 `Base controls` 而不是 `Overlays`。

**修复**：

1. 构造模式改为识别**模块路径**，取路径最后一段：`(?:\w+::)*([A-Z]\w*)\s*::\s*(?:new|with_\w+)`；
2. 候选集改为「**源码树里声明过的类型**」（`declared_types()`），而不是硬编码包装器名字表。这一条是有咬的：`Arc` 在本仓是**真控件**（`create_arc` 建 `Arc::new(..)`），而 `Box`/`Vec`/`Rc` 不是——硬名单要么误删 `Arc`，要么被迫写长；问源码树就两条都对。

**效果（实测，逐控件对比 HEAD）**：只移动 6 个控件，全部是纠正：

|---|---|---|
| `about_dialog` | unclassified | Dialogs |
| `alert_dialog` | unclassified | Dialogs |
| `confirm_dialog` | unclassified | Dialogs |
| `spacer` | unclassified | Containers |
| `split_layout` | unclassified | Containers |
| `swipe_to_dismiss` | Base controls | Overlays |

家族数 17 → 17（`root` 保留），`unclassified` 组消失；`Base controls` 7→6，`Containers` 25→27，`Dialogs` 14→17，`Overlays` 4→5，合计仍为 **213**。
