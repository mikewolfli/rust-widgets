#### N5-02 【✅已完成】view engine：同 key 插入配对错乱 + 同路径 Remove+Insert 跳过 on_unmount（P1，Scout B #1）

- 复核（全部源码取证）：
  1. **配对错乱（孤儿控件）**：`reserve_ids_for_inserts` 的 reservation 表以 `node.key.unwrap_or_default()` 为键——keyless 节点全部共享 `""`，同 key 的第二次插入**覆盖**第一次的 id。`apply` 的 `insert_subtree` 按同一 key 取走（旧代码 `remove`），于是第一个子树采用第二个的 id，第一个分配的控件永远不挂载——每次批次泄漏一个活控件。同一 key 出现在两个不同父节点下（合法声明）同样中招。
  2. **on_unmount 被跳过（hook 泄漏）**：`reserve` 在 `run_unmount_hooks_for_removals` **之前**向 `id_of_path` 写入新子树的 id。批次同时含 `Remove{id_old}` + `Insert{new}`（`child_if` 分支翻转、key 变更——diff 的常规输出，patch 序列实测为 `[Insert, Remove]`）时，被移除根的路径被新 id 遮蔽：遍历读到新 id ∉ removed，整棵被移除子树的 `on_unmount` 静默跳过，订阅/定时器泄漏。`Replace` 不受影响（不经 reserve），但 Insert+Remove 组合必中。
- 修复：
  1. `apply.rs`：reservation 值改为 `VecDeque<ObjectId>`（新别名 `ReservedIds`，从 `view::mod` 导出）。`reserve` 侧 `entry(key).or_default().push_back(id)`；`insert_subtree` 侧 `get_mut().and_then(pop_front)`。两侧遍历顺序相同（patch 顺序 × 子节点声明序），先进先出配对精确。
  2. `engine.rs`：批次同时含 `Insert` 与 `Remove/Replace` 时，在 reserve 之前快照 `id_of_path`，unmount 遍历改读快照（lookup 以参数贯穿 `run_unmount_hooks_for_removals/for_ids/run_unmount_hooks`）；非混合批次零开销（不克隆）。
- 证据：三个新测试——`two_keyless_inserts_in_one_batch_orphan_nothing`（「每个已创建 id 都已挂载」辅助断言）、`the_same_key_under_two_parents_in_one_batch_keeps_both_reservations`、`a_remove_plus_insert_at_the_same_path_still_runs_the_unmount_hook`。**反向注入（原则 #106）**：把 push 改回「clear+push」覆盖语义，两个孤儿测试都变红（old: FAILED 2），恢复后 54 passed；hook 测试在快照时序错误（reserve 后才快照）时同样变红，实测过。`cargo test --lib view::` 273 passed、`json::` 217 passed。
- 设计说明：第一个测试的初版（旧树同为 label）会被位置匹配吃掉第一个 keyless 节点，批次只含 1 个 Insert，注入下不红——已改为旧树子节点异型（button），确保两个 Insert 真正并发。这本身就是「侦察报告只作线索」的一例：位置匹配规则改变了缺陷的触发形状。

#### N5-03 【✅已完成】wgpu 光栅器：退化几何的 i32 溢出与十亿步空转（P1，Scout B #3）

- 复核（`src/wgpu_backend/raster.rs` 全链路取证）：
