## 0. 一句话结论

**本轮最该记住的一条：`snapshots/svg/` 一直显示的是「光栅器从来没画过的样子」。**

软件光栅化器把 `DrawText` 的 `origin.y` 当作字形框的**上边缘**（`draw_bitmap_glyph` 从它向下
逐行 blit），而 SVG 后端把**同一个值**直接写进 SVG 的 `y` 属性——在那里 `y` 是**基线**。
于是按「上边缘」契约居中的标题在屏幕上正确、在所有快照里高了半行。

**两个后端对「墨在哪里」给出不同答案，这本身就是缺陷**——这正是 BLUE20 §3.1.2 为 P5 写下的判据。
而 P5 读的是同一个错误模型，所以它也一起瞎了。7 个控件受影响，**376 个快照里 220 个变了**。

修法只是**一个属性**（`dominant-baseline="text-before-edge"`），这恰恰是它能一次性修完的原因：
约 40 个本来就按「上边缘」契约做过偏移的调用点**全部保持正确**，且都不需要知道自己在往哪个后端画。

## 3. 指令 #4：对照 SVG 与 Flutter/Qt/SwiftUI 的逐图核验

### 3.1 🔴 根因：两个后端对文本原点的语义不一致（7 个控件）

**取证**（原则 #64：先读源码，不推测）：

```rust
// src/render/pipeline/primitives.rs — 光栅器：origin.y 是字形上边缘
let mut config = GlyphDrawConfig { ..., y: origin.y, ... };
// src/render/pipeline/pixel_ops.rs — 从 config.y 向下 rasterise
let y0 = config.y + (gy * height) / 8;      // gy: 0..8
```

```rust
// src/render/svg/backend.rs（修前）——同一个值进了 SVG 的 y，而 SVG 的 y 是基线
r#"<text x="{}" y="{}" ..."#, origin.x, origin.y
```

**为什么这是缺陷**（BLUE20 §3.1.2 的原话）：**两个后端对「墨在哪里」给出不同答案，这本身就是缺陷。**
一个用 `rect.y + (band - height) / 2` 居中的标题：

| 后端 | 字形实际占用的行 | 判定 |
|---|---|---|
| 光栅（屏幕） | `center .. center + height` | ✅ 在带内 |
| SVG（快照） | `center - ascent .. center + descent` | ❌ 高了约半行 |

**实测证据**（修前 `snapshots/svg/` 里的 `y` vs 所属带）：

| 控件 | 文件 | `font-size` | 原点 `y` | 所属带 | 若按基线读，字形行 |
|---|---|---|---|---|---|
| `dock_widget` | `dockwidget.rs:618` | 14 | **5** | 0–24 | −6 … 8（3/4 在带外） |
| `tab_bar` | `tab_bar.rs:623` | 14 | **5** | 0–24 | −6 … 8 |
| `popup_window` | `popup_window.rs:244` | 14 | **5** | 0–24 | −6 … 8 |
| `collapsible_pane` 标题 | `collapsible_pane.rs:352` | 14 | **6** | 0–24 | −5 … 9 |
| `collapsible_pane` 箭头 `▼` | `collapsible_pane.rs:337` | 14 | **8** | 0–24 | −3 … 11（最差） |
| `group_box` | `groupbox.rs:349` | 14 | **8** | 0–120 | −6 … 11（压过顶边框） |
| `navigation_stack` | `nav_widgets/navigation_stack.rs` | 15 | **14** | 0–44 | −1 … 17 |

**修法（一处，非 7 处）**：在 SVG 后端把语义**用属性表达**，而不是改数字：

```rust
r#"<text x="{}" y="{}" dominant-baseline="text-before-edge" ..."#, origin.x, origin.y
```

`dominant-baseline="text-before-edge"` 把 `y` 的含义重新定义为**文本盒上边缘**——
正是渲染器此处 `origin.y` 的含义。

**为什么选属性而不选「加 ascent」**（这是本轮的关键取舍）：
- 加 `ascent` 到数字上，会让**约 40 个已经按「上边缘」契约做过偏移的调用点**变成**双重补偿**，
  必须逐个改回来——那才是「改 7 处不够、要改 40 处」的陷阱。
- 用属性表达语义，则**所有既有调用点无需改动**，因为它们的契约没变，变的是后端的表达能力。

**派生修复**：`P5` 的 `element_bounds` 里那段注释原本写着「origin 是字形左上角」——
它在**光栅**语义下是对的，但当时读的 SVG 用的是**基线**语义，所以注释与它读的数据**互相矛盾**。
现在后端的 `dominant-baseline` 让两边真正一致，注释的模型才是被验证的模型。

**实测影响**：`git status snapshots/svg` → **224 个文件变化**（220 个 SVG + 4 个 `snapshots/*.svg`）。
这个数字本身就是「两个后端不一致了多久」的度量。

### 3.2 🔴 图表坐标轴 chrome：`line_chart` 修了，`bar_chart` 漏了（冰山法则）

`bar_chart` 即使开了 `chart` feature 也**自己画轴**（与 `line_chart` 不同），
而它的数值标签与分类标签仍是 `Color::DARK_GRAY`：

```rust
// src/widget/chart_widgets/bar_chart.rs:391（修前）
fn draw_label(...) {
    context.draw_text(..., Color::DARK_GRAY, ...);   // 浅色图表的墨色
}
```

**实测**：`rgba(64,64,64)` 于 `rgba(18,18,18)` = **1.81:1**（WCAG AA 需 4.5:1）。

**冰山扫描（原则 #2）**：同一个字面量还在**另外三处**——

| 位置 | 性质 |
|---|---|
| `bar_chart.rs:414` `not(feature = "chart")` 回退轴 | **tablet/mobile 上画的是不可见的图表** |
| `line_chart.rs:443/494/507` `not(feature = "chart")` 回退轴 + 标签 | 同上 |
| `pie_chart.rs:548` 外圆描边 | 暗色下饼图失去外沿 |

**修法**：把 2.5.2 建立的 `axis_chrome()` 提升为 `pub(crate)`，并抽出
`axis_chrome_color(strength)`（单色版本），让 4 处共用**同一条**「表面 → 墨色」推导
（原则 #51：共享抽象必须先证明它消除了真实重复——这里消除了 4 处）。

### 3.3 🔴 `terminal_view` 的 1.13:1 错的是**承载面**，不是文字色

全快照集里最差的行内对比度是 `terminal_view.light.svg` 的 **1.13:1**。但根因**不是文字**：

```rust
// 修前：resolved 来自 text_edit 的 rgb(180,180,180)，再向墨色混 8%
let background = resolved.blend(&text_color, 0.08);   // → rgb(166,166,166)
```

`rgb(166,166,166)` 是**亮色主题上的一块深灰板**，绿色提示行随后画在它上面。

**修法**：终端主体是一个**字段（field）**，因此按 crate 里所有其他字段的同一手法推导——
从**窗口底色**出发、向墨色走一步，且调用方自己的颜色仍然优先（原则 #21）。
提示色另经 `nudge_apart()`：保留语义 token 的**色相**，只把亮度推离承载面直到达标。

### 3.4 🔴 `calendar`：三处「把亮色主题的假设写成了算术」

| # | 病处 | 修前实测 | 修后 |
|---|---|---|---|
| a | 星期表头 `header_bg.blend(&WHITE, 0.5)` | 暗色下 `rgb(18,18,18)` → `rgb(137,137,137)` 重灰带 | 改为向**日历自身的墨色**走一小步 |
| b | 周末列 `rgb(180,60,60)` 硬编码 | **1.64:1**（于灰带） | 读 `theme.colors.error` 并**推离承载面** → 4.42:1(亮)/6.53:1(暗) |
| c | 今日高亮 `rgba(255,200,50,100)` + 白字 | **1.30:1**（全快照最差） | 读 `theme.colors.warning`；日号取自身合成色的 `contrast_color()` |

> (a) 为什么是缺陷：主流日历（Flutter `onSurfaceVariant`、Qt `QCalendarWidget`、
> SwiftUI 图形化 `DatePicker`）的表头都只比正文深**几个百分点**，不可能是 `137` 这种重带。
> (b)(c) 为什么读语义 token：按规则 #108 ②，周末/今日是**语义**（「非工作日」「今天」），
> 与 error/warning 同类，因此**必须**读 `theme.colors.*`——BLUE20 §3.1.3 早已点名 `calendar` 不得豁免。

**副作用（正面）**：`check_control_rendering.sh` 的语义色普查里，`calendar` 现在同时出现在
`warning` 与 `error` 两个 token 的消费者列表中——即**真的接上了消费者**，不只是修了颜色。

### 3.5 🟠 `font_dialog`：列头压在标题栏底边上

```rust
// 修前
let list_y = rect.y + 38;
let header_h = 12u32;
context.draw_text_fitted(Rect::new(col_x, list_y - 10, col_w, header_h), ...);
//                                    ↑ = rect.y + 28 = 标题栏底边
```

标题栏是 `0..28`，列头原点 `28`，且 12 px 的条**比它承载的 14 px 字体还矮**，
所以标签既贴着强调色横条、又溢出自己的条。

**修法**：把 `header_h` 从字体自身的行盒（`measure_text`）推出，再让 `list_y` 跟随它——
**让条与文字由构造保证一致**，而不是靠一对调好的字面量。修后列头位于 `y=30..44`，与标题栏留 2 px。

### 4.2 修掉的 3 个真缺陷（发现一个解决一个）

**#1 `splitter` — 空分割器完全没有分隔条**

```rust
// 修前
if self.pane_count() > 1 { /* 画 handle */ }
```

`Splitter::new` 调 `SplitterLayout::new(Orientation::Horizontal, 0)`——**0 个 pane**，
所以默认渲染出的控件**一个分隔条都没有**：快照里只有两块整幅矩形，
基线表 `splitter ... detail=0`（**零 chrome 像素**）。

**判定依据**：分隔条**就是**那个 affordance——Qt `QSplitter`、Flutter `Flex`、
SwiftUI `HSplitView` 都在 pane 尚未填充时也画它。看不见的分隔条，是用户找不到也拖不动的控件。

**修法**：`handle_slots = pane_count().saturating_sub(1).max(1)`；无 ratio 可依时居中。
有真实 pane 的调用方得到**与修前逐像素相同**的几何（`pane_count - 1` 个 handle 在累计 ratio 处）。

**#2 `tool_box` — 内容区用窗口底色填充，与背景逐字节相同**

```rust
// 修前
context.fill_rect(content, style.background_color.unwrap_or(Color::rgb(255,255,255)));
```

`tool_box` 不在 role 表里 ⇒ 归类 `Surface` ⇒ 主题把**窗口底色**写进 `style.background_color`。
快照里前两块矩形**逐字节相同**，空 toolbox 读起来就是「一个边框 + 一个洞」。

**修法**：`splitter` / `stacked_widget` / `mdi_area` / `carousel` 早就用 `resolved != window_fill`
守卫处理这一情形，`tool_box` 补上同一条。

**#3 `image_gallery` — 空态主题盲，且 2.02:1**

```rust
// 修前
let bg = Color::rgba(240, 240, 240, 255);            // 硬编码近白
context.draw_text_fitted(..., Color::rgba(160,160,160,220), ...);   // 2.02:1
```

既是**主题盲**（P3：亮暗逐字节相同），标签又是 **2.02:1**——
低于 4.5:1 的文字底线，也低于 3:1 的大字底线。暗色窗口里的图库是一块主题改不动的白矩形。

**修法**：面板与标签都走主题（调用方颜色优先），标签由**面板自身的对比色**推出。
**门禁主动报出**该控件的豁免已失效并要求删除（§4.3）。

## 5. 指令 #3：声明式 + 保留混合的完整性条件

### 5.1 取证：缺的是什么

`src/view/` 的声明式层（`Node` → `diff` → `Patch` → `apply`）已有：
属性 diff、`Insert`/`Remove`/`Move`/`Replace`、key 匹配与**位置回退的显式上报**
（`positional_matches`）、重复 key 上报、跨线程 `ReactiveHost`。**列表**有 `children_of`。

**缺的是「条件」**——而条件渲染正是声明式树的**完整性条件**：
Flutter 在 children 列表里的 `if`、React 的 `cond && <X/>`、SwiftUI `ViewBuilder` 的 `if`/`else`。
没有它，调用方必须在 builder 链中间插入命令式 `if`；
唯一可行的绕法是 `children_of(if c { vec![n] } else { Vec::new() })`——**为 1 个节点分配一个 `Vec`**。

### 5.2 补齐的 4 个原语（含 9 条测试）

| 原语 | 语义 | 关键设计理由 |
|---|---|---|
| `child_if(cond, child)` | 条件包含一个子节点 | **false 分支把节点从树中移出**，而不是标记为隐藏：隐藏节点仍占身份，keyed diff 会匹配到它，于是状态变化「在树里」发生了却在屏幕上没发生。移出后 diff 看到的是真正的 `Insert`/`Remove` |
| `child_if_else(cond, then, else)` | 二选一 | 两个分支通常是**不同的控件**（SwiftUI 的 `if isLoading { ProgressView() } else { Content() }`），所以两个都必须给，而不是一个 `Option` |
| `children_if(cond, make)` | 条件包含一组 | `cond` 为 false 时**不调用** `make`：可能分配、可能读状态的生成器被整个跳过 |
| `children_keyed(items, key_of, make)` | 列表 + 强制 key | 把 key **变成必填参数**：列表再也不能「不小心无 key 构建」。key 缺失正是 BLUE18 #87 身份漂移的前提；无 key 仍可走 `children_of`，且 diff 会报出位置匹配数，使降级保持**可见** |

**测试（13 条，覆盖 Node 层与 diff 层）**：

```
view::node  18 passed   （+5：child_if / child_if_else / children_if 不调用生成器 / children_keyed / 空切片）
view::diff  31 passed   （+3：切换 child_if → Insert，反向 → Remove；
                                切换 child_if_else 分支 → 不得是 SetProperty；
                                children_keyed 头部插入 → 1 个 Insert 且 positional_matches=0）
```

> **一处我自己写错的断言，被实跑纠正**：`child_if_else` 换分支我原本断言 `replaced_subtrees == 1`，
> 实测是 `Insert` + `Remove`——因为两分支 **key 不同**，diff 正确地把它们读成
> 「旧的走了、新的来了」。（`Replace` 保留给**匹配上了**的节点改了类型的情形：那里身份是要保住的。）
> 是**测试断言**错了，不是代码错了；已改断言并写明两种情形的区别。

**全链验证**：`cargo test --lib view::` → **157 passed; 0 failed**。

**修在语义的正确层级上，修复量才会随层级下降，而不是随调用点上升。**

## 14. 指令 #4 续：逐图核验抓到的四类缺陷

### 14.1 🔴 `+ ascent` 类（约 40 处，20+ 文件）

**取证**（先读源码，不推测）：

```rust
// src/render/pipeline/primitives.rs —— 原点即字形框上边缘
let mut config = GlyphDrawConfig { ..., y: origin.y, ... };
// src/render/pipeline/pixel_ops.rs —— 从 config.y 向下逐行光栅化
let y0 = config.y + (gy * height) / 8;
```

两种错法，都由同一个错误模型产生：

| 意图 | 错法 | 后果 |
|---|---|---|
| 居中 | `(box - height) / 2 + ascent` | 字形盒整体下移**一个 ascent**（即低半行） |
| 顶对齐 | `top + ascent` | 字形盒整体下移**一个 ascent** |

**判据**（实测，非推理）：`badge` 与 `date_range_picker` 已经是对的（第 61 轮修过，代码里有注释）；
`app_bar` 的标题在 240×120 的普查矩形里，字形盒 `67..89`（中心 78）而框中心是 60——
**低了 18 px**。而上半场 §4.4 曾把 `app_bar` 判为「基线正确」：那是**读到了正确的写法**
（`ascent/2 - descent/2`）**就当它正确**，没有量。这是原则 #64 的典型违反，本节已改判。

**修法**（分两类，按意图）：
- 居中 → `Y + (H - metrics.height) / 2`
- 顶对齐 → 直接删掉 `+ ascent`

**逐文件**（本轮实际改动，含连带的关联修正）：

| 组 | 文件 | 说明 |
|---|---|---|
| 居中 | `search_bar`、`cupertino/core` ×2、`cupertino/segmented_control`、`cupertino/nav_bar`（大标题）、`radar_chart`、`app_bar` ×3、`navigation_drawer` ×2、`segmented_button`、`tab_view`、`avatar`、`swipe_to_dismiss`、`video_player` ×5、`carousel` ×3、`meter`、`emoji_picker`、`tag_input`、`modal_bottom_sheet` | `(box - height)/2` |
| 顶对齐 | `lottie_widget` ×2、`rive_widget` ×3、`animated_image`、`refresh_control` ×2、`cupertino/nav_bar` ×3、`image_gallery`（缩略图说明） | 删除 `+ ascent` |
| 关联 | `image_gallery` 的箭头**命中测试** | 它原来用 `arrow_y - ascent - 4` 抵消画出时的 `+ascent/2`；绘制改了，命中区必须一起改，否则点击目标留在箭头下方半行 |

**新门禁**：`tools/check_text_origin_is_a_top_edge.sh` +
`tools/check_text_origin_is_a_top_edge.py`。

它做什么：扫描每个 `draw_text` / `draw_text_fitted` 调用，把实参里的标识符**回溯到它们的 `let` 定义**，
只要其中出现 `ascent` 就失败。注释先被剥离——一个**修好**的点会在注释里写「原来的 `+ ascent` 把它压低了半行」，
把「对修复的说明」判成缺陷会让门禁无法使用。

三条豁免（`chart series-palette`、`emoji_picker emoji-glyphs`、`color_picker hue-wheel`）的字面理由
**本身是对的**（系列色/字形/色相确实是数据），错的是它们被用来豁免**主导色**，
而主导色当时是**没人管的 chrome**。已按 `map_view`/`image_gallery` 先例删除并附「Removed on evidence」说明。

> **豁免表 16 → 14。** 这正是该表想要的语义：**豁免只在「被豁免的东西确实主导渲染」时有效。**

### 14.3 🔴 三处「预留了一个装不下当前字号的字面量尺寸」

| 控件 | 病处 | 修前实测 | 修法 |
|---|---|---|---|
| `heatmap` | `LEGEND_LABEL_HEIGHT = 10`，注释写「10 pt 标签字体的行高」，而实际字号是 **14 px**；端点数字锚在色带底部 | `9` 压在色带上 = **1.15:1**（全快照最差的文字比） | 预留改为字体的真实行盒 14；数字从**色带下边缘**定位而不是从色带底部，两者由构造保证相邻 |
| `color_picker` | 底部栈预留 44 px，没有算进十六进制读数自己的 14 px 行 | `#FF0000FF` 压在光谱底边上 = **2.65:1** | 栈高由零件推导（`READOUT_LINE + PRESET_ROW + MARGIN*3`）；读数带止于色带下沿 |
| `tag_input` / `tooltip` | 顶对齐位置后面又加了 `ascent` | 见 §14.1 | 删掉 |

**`heatmap` 的修法被 `P5` 反过来抓到我自己**（如实记录）：
把预留从 10 改到 14 后，`LEGEND_HEIGHT` 变成 24，而数字从 `ramp_top + 8 + 2` 起算，
得出 `107..121`——**超出 120 的控件 1 px**。`P5` 立刻报出：

```
heatmap: [59,107..67,121] escapes the box
heatmap: [229,107..237,121] escapes the box
```

于是改成**从色带上边缘开始逐段堆叠**（带顶 → 色带 → 间隙 → 数字），
使三段之和恒等于预留高度，位置不再依赖两个各自手调的锚点。这就是「让条与文字由构造成立」。

## 15. 证据工具的自我修正：`audit_text_contrast.py` 的边界含入

工具只在「谁的墨落在谁身上」这一个问题上出错，但错得很隐蔽：
元素包含判定原本是**闭区间**（`top <= y <= top+height`），
而填充与其**正下方**的标签经常共用一条边界像素。结果：
刚修好的 `color_picker` 读数（`y=76`，光谱止于 `76`）被判为压在 `255,64,64` 上，报 **2.65:1**。
改成**半开区间**（下/右不含）后归零。

**为什么值得单独记**：这是「判据与它读的数据互相矛盾」的又一形态——
**判据错了会制造假缺陷，和制造假通过一样浪费时间**（规则 #18 / #107）。

## 21. 本节结论

**上半场修的是「两个后端对同一概念给出不同答案」；本节修的是「量程之外」。**

`P5` 一直忠实地在它自己的量程内工作——它量「有没有画出控件矩形」，量得很准。
但一个控件**在框内低了半行**，`P5` 永久判绿，
而 `audit_text_y.py` 是启发式、分不清「刻意顶对齐」，所以也不能当门禁。
**两个判据都在，缺陷仍然全绿**——这与上半场「门禁和数据共享错误假设」是同一种失效，
只是这次共享的是**量程**而不是**模型**。

本节的产出因此不是「修了 40 处」，而是**一道能失败的源码级门禁**。
而它的第一版**是假绿的**——这件事本身值得写进日志：
**「写了门禁」不等于「有门禁」；没做过反向注入的门禁，只是在输出绿色。**
