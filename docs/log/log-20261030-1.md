### 1.3 F-6｜主题快照，消除"两处取锁"死锁形态

**根因**：`global_theme_manager()` 返回**不可重入**的 `MutexGuard`。在同一个表达式里读两个事实
（结构体字面量/元组/实参列表）会让第一个 guard 活到语句结束，第二次取锁即死锁；调用方只能靠
"记住"把每个读取拆成独立语句，这条规则没有任何门禁保护。

**改动**（`src/theme/manager.rs` + `src/theme/mod.rs`）
- 新增 `ThemeSnapshot`（`name/theme/colors/high_contrast/reduce_transparency/is_crossfading/
  theme_names/revision`）与 `pub fn theme_snapshot() -> ThemeSnapshot`：**一次取锁**、复制所需事实、
  在 guard 内读取 `theme_revision()`，保证快照内部自洽。
- 只读；写路径仍走 `global_theme_manager()`，文档写明分工。

**判定口径**：一个表达式内读取多个事实不再需要多次取锁；快照是拷贝（切换主题后旧快照不变）；
`revision()` 可用于判断是否过期。**未覆盖**：没有把 `global_theme_manager()` 改成可重入（那会
掩盖真实的锁序缺陷），也不改变既有写 API。

**用例**：`theme::manager::…::a_snapshot_answers_every_global_question_in_one_lock`
（同一表达式取 4 个事实 + 切换后旧快照不变 + 新快照可见切换 + 复原）。

### 2.2 F-3｜共享工厂的扩展入口

**根因**：`WidgetFactory::shared()` 是 `OnceLock`，套件（`form`/`form_set`）只能注册进自己新建的
工厂；而 `create_widget_of_kind`、JSON loader、设计器清单读的都是 `shared()` —— 两张表必然漂移
（#101）。

**改动**（`src/widget/capability.rs`）
```rust
pub type SharedFactoryExtension = fn(&mut WidgetFactory) -> Result<(), RegistrationError>;
pub enum SharedFactoryError { AlreadyBuilt }
pub fn register_shared_extension(ext: SharedFactoryExtension) -> Result<(), SharedFactoryError>;
pub fn shared_extension_failures() -> Vec<RegistrationError>;
impl WidgetFactory {
    pub fn new_with_extensions(exts: &[SharedFactoryExtension]) -> Result<Self, RegistrationError>;
}
```
- `shared()` 首次构建时：在**同一把锁**内置 `frozen = true` 并取出扩展列表 → 对列表执行扩展 →
  失败项 `log::error!` 并记入 `shared_extension_failures()`（可查询，#97 同精神）。
- 冻结后注册返回 `Err(AlreadyBuilt)`：**不接受"永不执行"的注册**。
- `new_with_extensions` 遇到第一个冲突即返回错误，不返回半成品表（顺序无关性）。
- `src/widget/mod.rs` / `src/lib.rs` 以 `#[cfg(full_widgets)]` 再导出。
- 扩展点与套件现有签名完全一致：`rust_widgets_suites::install` 可直接作为扩展传入。

**判定口径**：扩展后 `capability()` / `constructible_names()` / `create()` 三者都能看到新控件；
重名被拒；冻结后注册被拒且表不变。

**用例**（`src/widget/capability/tests.rs`）
- `an_extension_adds_its_control_to_the_extended_table`
- `an_extension_cannot_shadow_a_core_name`
- `registering_after_the_shared_table_is_built_is_refused`

**未覆盖**：没有把 `rust-widgets-suites` 自己改为自动注册 —— 依赖方向是套件依赖父 crate，
"谁来 install" 属于宿主启动顺序；本轮只提供入口并证明语义。

## 第 4 轮：F-1｜TreeIndex 支持宿主自己的 id

**根因**：`TreeIndex::build` 是 `pub(crate)`，唯一公开生产者绑在 `ViewEngine` 上（引擎只认识自己的
`ObjectId`）。设计画布不挂在引擎上、持有持久 `NodeId`，只能维护一份复刻索引 —— 两套实现必然漂移
（#101）。

**改动**（`src/view/identity.rs`）
- `pub trait IndexId: Copy + Eq + Hash + Ord`（blanket impl）：把"可索引的稳定身份"要求写一次。
- `pub struct TreeIndex<Id = ObjectId>`：全部 id 位置泛型化；**默认类型参数**让既有 `TreeIndex` /
  `&TreeIndex` 写法含义不变（引擎侧零改动）。
- `TreeIndex::build` 保持 crate 内部 —— 公开构造只有一条路：
  `pub struct TreeIndexBuilder<Id = ObjectId>`：
  `new()` / `generation(u64)` / `node(path, id, widget, key)` / `build()`。
- builder 从路径推导 parent/children/root，再**调用同一个 `build`**（键作用域与重复键规则不可能分叉）。
- 明确写下的边界：空路径即 root；父路径缺失的节点保留但无 parent（不进任何 children）；重复路径后者替换、
  重复 id 取最后给出的路径；children 按路径序。

**判定口径**：用**非 `ObjectId`** 的 `NodeId` 走完整查询面（root/id_at/id_of_key/path_of/parent_of/
children_of/widget_of/key_of/keys/generation），重复键规则与引擎一致。**未覆盖**：引擎自身仍用
`TreeIndex<ObjectId>`（默认参数），没有把引擎泛型化（无需求、徒增改动面）。

**用例（`src/view/identity.rs`）**
- `a_builder_indexes_a_host_tree_with_the_hosts_own_id_type`
- `the_builder_reports_a_duplicate_key_exactly_as_the_engine_does`
- `a_builder_links_a_child_declared_before_its_parent`
- `a_builder_keeps_a_node_whose_parent_path_is_absent`
- `a_repeated_path_replaces_the_node_it_addressed`

## 第 9 轮（用户追加）：`RenderCommand::DrawImageScaled`——延迟后端不再"重采样一次 + 复制一次"

### 9.1 缺口（第 8 轮留下的真实成本）

第 8 轮给缩放图像补了 `RenderContext::draw_image_scaled`，但 **bucket / 延迟记录路径**仍走
"可移植实现"：`blit_scaled` 先重采样出一个临时 `Vec`，再把结果包成 owned `DrawImage` 命令
（又一次拥有复制）。每帧每张缩放图因此付 **两次分配 + 两次拷贝**，而命令集里能表达缩放的只有
`DrawImageQuad`，它被 `3d` 特性门控——把图像缩放说成 3D 问题是不成立的。

### 9.2 改动（一处定义，所有后端共用）

| 位置 | 内容 |
|---|---|
| `src/render/core/command.rs` | 新变体 `DrawImageScaled { x, y, width, height, source_width, source_height, data }`；`bounds()` 与 `DrawImage` 合并到同一分支（目标矩形）。**不受 `3d` 门控**。 |
| `src/render/backend/paint.rs` | `PaintBackend::draw_image_scaled` 的默认实现改为**派发该命令**（一次拥有复制），不再重采样；恒等尺寸仍短路到 `draw_image`（零拷贝）。`SoftwarePaintBackend` 继续覆盖为 `blit_scaled_software`（边画边采样）。`route_command_to_surface` 新增该变体分支 → `blit_scaled_software`。 |
| `src/render/backend/surface.rs` | bucket 录制路径 `dispatch_owned(RenderCommand::DrawImageScaled)`，取代"先重采样再 `DrawImage`"。 |
| `src/render/svg/backend.rs` | 抽出 `push_image_element(...)`，`DrawImage` 与 `DrawImageScaled` 共用：栅格按**源尺寸**内嵌（不读越界），元素 `width`/`height` 带目标框，由查看器缩放。命令名分类表加入 `"DrawImageScaled"`。 |
| `src/widget/special_widgets/canvas.rs` | transform / snap / zone bounds 三处穷尽 match 均处理新变体。 |

## 第 10 轮（冰山法则 #2 追问）：同一缺陷类在**批处理回放**里也存在

### 10.1 发现过程

第 9 轮新增 `DrawImageScaled` 后，按"改一个→扫一类"的要求，对**所有消费 `RenderCommand` 的位置**
做穷尽核查（`paint.rs` / `surface.rs` / `svg/backend.rs` / `batch.rs` / `canvas.rs` / `wgpu_backend` /

- `wgpu_backend/bridge.rs` 只实现路径填充的窄桥，图像本就不在其中（`DrawImage` 同样会返回
  `Unsupported`），不是回归。
- `pdf` / `print` 不消费 `RenderCommand`（走自己的图像路径）。
- **`batch.rs` 的 `DrawImageSubrect` 翻译是同类缺陷**：它把源矩形裁剪成
  `crop_width × crop_height` 的紧致缓冲，却发出 `RenderCommand::DrawImage { width: dest.w, ... }`。
  回放时 `draw_image` 按**目标**步长读一个**裁剪**尺寸的缓冲——裁剪比目标小则什么都不画，
  比目标大则只画左上角。

### 10.2 修法（一处裁剪定义，两处使用）

- 新增 `clipped_source_rect(rect, source_w, source_h) -> Option<(left, top, w, h)>`：裁剪边界的
  **唯一**定义；`crop_source_rect` 与 translator 共用，不再各自重算。
- translator 以**裁剪后的实际尺寸**作源网格：尺寸相等 → 仍发零拷贝 `DrawImage`；不等 → 发
  `DrawImageScaled`（携带目标框 + 裁剪网格）。
- `BatchCommand::DrawImage` 无法修复也不猜测：图像缓存是 `HashMap<ObjectId, Arc<[u8]>>`，
  **不含尺寸**，translator 无法得知源网格。其契约因此保持"字节即为 `rect` 尺寸"，需要缩放的
  宿主应改用 `DrawImageSubrect`（它携带 `source_width/source_height`）。这是一个**契约边界**，
  不是遗漏；若将来要让 `DrawImage` 自己缩放，必须在 `register_image` 里同时登记尺寸——那是一个
  独立的 API 决策，未获确认前不做。

### 14.1 C 是什么（避免自我美化）

### 14.3 关键设计决定

1. **用 `textureLoad` 而不是 `textureSample`**：CPU 规则是 `src = floor(local * src_dim / dst_dim)` 的整数映射，
   sampler 会引入驱动相关的过滤与边界舍入。用带整数坐标的 `textureLoad` 才能做到**逐字节相等**。
2. **混合放在管线状态**：shader 输出直 alpha，管线用 `SrcAlpha/OneMinusSrcAlpha`（color）+ `One/OneMinusSrcAlpha`（alpha），
   与 `blend_pixel_with_mode` 的 source-over 同义。
3. **不合法 payload 不被调度**：否则同一帧在不同路径下会得到“报错”或“静默少画一张图”两种答案。
4. **scissor 而不是推 clip**：`PushClip/PopClip` 仍是流级状态（回退），但单条图像命令自带的 `clip` 是逐 draw 状态，
   用 `set_scissor_rect` 表达与 CPU 的 `effective_clip` exactly 一致。

### 14.4 用例（+4，均实跑通过，真 GPU：Intel Iris Xe / RTX 3080 Ti 可选）

- `a_scaled_image_draw_matches_the_software_rasteriser`：2×1 → 8×4，`assert_eq!(gpu, cpu)` **逐字节**，
  并逐点断言左右半区与目标框外的清零。
- `a_clipped_image_draw_matches_the_software_rasteriser`：带 `clip` 的同类断言（右边界开区间）。
- `a_malformed_image_payload_is_reported_instead_of_dispatched`：短路 payload 返回 CPU 的显式错误。
- `an_image_stream_is_claimed_by_the_gpu_dispatcher`：证明图像流**确实被 GPU 认领**（否则前两条在回退时也会通过）、
  短 payload 不被认领、`PushClip` 仍不认领。

### 16.2 一处必须承认的精度边界

## 第 18 轮（R2）：轴向渐变上 GPU（逐字节）+ 径向渐变仍未做

### 18.1 关键发现：CPU 的 stop 是“最近停靠点”而不是插值

`gradient_stop` 是 `idx = floor((stops-1)*t)` 的**最近停靠点整数查表**（不是线性插值）。这让
“把渐变当成 1 像素宽的图像画”成为可行且**逐字节**的方案：颜色仍由 CPU 同一函数按行（或列）算一次，
GPU 用图像管线的恒等整数映射把它复制到整个跨度。无需新着色器、无需新管线。

| 位置 | 改动 |
|---|---|
| `raster.rs` | 新增 `gradient_ramp(rect, data, axis)`：`Vertical` 产生 `height` 项、`Horizontal` 产生 `width` 项，`t` 与查表与 CPU 栅格化完全同式；`GradientAxis` 提为 `pub(crate)`。 |
| `encode.rs` | `DrawGradient` / `FillLinearGradient` 两个打包分支：生成色带 → `upload_image_draw` → `Scissor` + `Image`；调度表新增这两个变体。 |

**收益**：CPU 从“每像素一次查表”降为“每行（列）一次”，逐像素工作交给 GPU；且因为色带由 CPU 算，
结果与软件路径**逐字节相等**（实测）。

- `a_horizontal_gradient_matches_the_software_rasteriser`（2 个停靠点 + 裁剪，验证裁剪不重新相位）

## 第 19 轮（R2b）：径向渐变上 GPU（实测逐字节）

### 19.1 做法

径向渐变的颜色随**距离**连续变化，无法用“每行一项”的色带表达，所以 stop 表上传为 `N×1` 纹理，
着色器里算 `t = sqrt(dx²+dy²) · (1/radius)`、再按“最近停靠点”取色——与 CPU 完全同式。

| 位置 | 改动 |
|---|---|
| `shaders.rs` | `RADIAL_VS` / `RADIAL_FRAG`；`ShaderModule::RadialGradient` → `radial_fs` |

### 19.2 结果：**实测逐字节相同**

这是本轮唯一一个“着色器内做浮点运算”的切片，原本预计可能出现 ±1 或停靠点边界翻转。实测结果：

- 3 停靠点 / 18×16 矩形：`assert_eq!(gpu, cpu)` 通过；

## 第 20 轮（R3 前置调查）：模板缓冲的结论——不是“加个管线”，要改全部管线

### 20.1 先做的验证（已回退，不留半成品）

R3 需要模板缓冲（even-odd / non-zero 环绕数）。我先做了一个最小 spike：

1. 在 `RenderCache` 里加 `StencilTarget`（`Stencil8`，与颜色目标同尺寸，grow-only）；
2. 在 `encode_draw_commands_gpu` 的 render pass 里挂 `depth_stencil_attachment`（`LoadOp::Clear(0)`、`StoreOp::Discard`）；
3. 跑现有 86 条 GPU 用例。

结果：**21 条失败**，wgpu 校验错误原文：

```
wgpu error: Validation Error
  In a CommandEncoder, label = 'gpu_draw_commands_encoder'
    In a set_pipeline command
      Render pipeline targets are incompatible with render pass
        Incompatible depth-stencil attachment format: the RenderPass uses a texture with
        format Some(Stencil8) but the RenderPipeline with 'clear_pipeline' label uses an
        attachment with format None
```

### 20.2 这意味着什么

**pass 一旦带模板附件，所有在这个 pass 里用的管线都必须声明匹配的 `depth_stencil` 状态。**
本 pass 里现在有 **7 条**管线（clear / rect / circle / image / text / shape / radial），全部是
`depth_stencil: None`；再加路径需要 3 条（写模板的 fan、读模板的覆盖 quad、清零模板）。

也就是 R3 的真实工作量：

| 部分 | 内容 |
|---|---|
| 1 | 7 条已有管线各加一份 `Stencil8` 状态（`depth_write_enabled: false`、所有比较 `Always`、写入掩码 0） |
| 2 | CPU 侧把每个 contour 三角化成 fan（`p0, pi, pi+1`），复用增长型顶点缓冲 |
| 3 | `path_stencil` 管线：颜色写入掩码为空，正面 `IncrementWrap` / 背面 `DecrementWrap`（支持 non-zero 环绕）；even-odd 用单面 `Invert` |
| 4 | `path_cover` 管线：`NotEqual 0` 测试 + 填充色，四边形的路径 bbox |
| 5 | `path_clear` 管线：把刚用过的模板位清零（一个 pass 只能开头 clear 一次） |
| 6 | 验收口径：CPU 是扫线 + 整数规则，GPU 是三角形光栅；边界像素不可能逐字节相同 → 几何断言（内部点命中、外部点不命中、环绕/奇偶差异用例） |

### 20.3 为什么本轮先回退

我把它全部回退了（`encode.rs` / `resources.rs` 恢复到 R2b 的绿状态）。理由不是“不想写”，
而是：

- 只挂附件不挂消费者，等于每帧多分配一块模板纹理、多一次 clear，却没有任何功能——那是真实的回归；
- 完整 R3 要改 10 条管线 + 新的 plan 步骤 + fan 生成 + 3 类新用例，已超出单轮可验证的范围。

## 第 21 轮（R3 第一刀）：统一模板状态，四个 2D pass 挂上 `Stencil8`

### 21.1 做了什么

上一轮的校验错误说得很清楚：**pass 带模板附件时，里面用的每条管线都必须声明匹配的格式**。所以这一刀先把结构铺平：

| 位置 | 改动 |
|---|---|
| `renderer/frame.rs` | 新增 `passive_stencil_state()`：`Stencil8` + `depth_write_enabled`/`depth_compare` 均为 `None`（纯模板格式没有深度面）+ `StencilFaceState::IGNORE` + 读写掩码 0。**8 条 2D 管线**（clear/rect/transformed/circle/image/text/shape/radial）全部改用它。**blur 管线保持 `None`**（它渲染到自己的 ping-pong 目标、pass 不带模板）。 |
| `renderer/resources.rs` | 新增 `StencilTarget` + `ensure_stencil`（`Stencil8`，grow-only，与颜色目标同尺寸）。 |
| `renderer/encode.rs` | 四个 2D pass（rect / instances / circle / draw-commands）都挂上模板附件（`Clear(0)`、`Discard`）；`frame.rs` 的 `render_clear_gpu` pass 同样挂上。 |

过程中被测试抓到的两个遗漏（都是同一类校验错误，只是发生在别的 pass）：

1. `clear_pipeline` 还被 `render_clear_gpu` 的 pass 使用 → 那里也必须挂附件；
2. `transformed_pipeline` / `circle_pipeline` 各自也有独立 pass → 同样处理。

### 21.2 代价（写清楚）

每个 2D pass 现在多一块 `Stencil8` 纹理和一个 clear（`Discard` 不回读）。在路径填充落地之前，这部分是**纯开销**——这是为了 R3 必须付的账，不是免费的。等路径接上后它才有收益。

### 21.3 验收：现有用例必须全绿

这一刀的验收标准就是“行为零变化”：


### 21.4 下一步（R3 第二刀）

现在可以纯增量地接路径了：

1. CPU 侧把每个 contour 三角化成 fan（`p0, pi, pi+1`），复用增长型顶点缓冲；
2. `path_stencil` 管线：颜色写入掩码为空，正面 `IncrementWrap` / 背面 `DecrementWrap`（non-zero）；even-odd 用 `Invert`；
3. `path_cover` 管线：`NotEqual 0` + 填充色，quad 覆盖路径 bbox；
4. `path_clear` 管线：`Zero`，把一个 pass 内用过的模板位复位；

## 第 22 轮（R3-2）：路径填充上 GPU（奇偶 + 非零环绕）

### 22.1 做法：三次画同一个 fan

路径不能写成“一个 draw 一个形状”——奇偶与非零环绕都需要**逐像素的计数**。所以用模板缓冲：

1. **写模板**：CPU 把每个 contour 三角化成 fan（`p0, pi, pi+1`），颜色写入掩码为空；
   奇偶用 `Invert`，非零用正面 `IncrementWrap` / 背面 `DecrementWrap`；
2. **覆盖**：一个 bbox quad，`Stencil NotEqual 0` 通过才画，写直 alpha 的填充色；
3. **复位**：同一批 fan 再画一次，`pass_op = Zero`（一个 pass 只能在开头 clear 一次）。

| 位置 | 改动 |
|---|---|
| `shaders.rs` | `PATH_FAN_VS`、`PATH_STENCIL_FS`（颜色掩码关掉）、`PATH_COVER_VS`/`PATH_COVER_FS` |
| `renderer/frame.rs` | 4 条管线：`path_stencil_evenodd` / `path_stencil_nonzero` / `path_stencil_clear` / `path_cover`（后者 `NotEqual 0` + source-over） |
| `raster.rs` | `path_fan_vertices`（convex fan）、`path_bounds`（bbox，扩 1px 后与 framebuffer 求交） |
| `renderer/resources.rs` | `DrawStep::Path`、`PackScratch::path_vertices` |
| `renderer/uploads.rs` | `PathDraw` + `upload_path_cover`（bbox + 颜色） |
| `renderer/encode.rs` | 两个打包分支（`FillPathNonZero` / `DrawPath { filled: true }`）、调芝表、顶点上传（instances → circles → paths）、pass 三步 |

### 22.2 用例（+2，均实跑通过）

- `a_filled_path_paints_its_interior`：正方形内部填、左右上下都不填；
- `even_odd_and_nonzero_disagree_on_a_pentagram`：**同一个点串**分别用两种规则——五角星尖部两者都填，
  中心五边形奇偶为空、非零填充。这条用例同时验证了两条规则确实不同，而不是“都填了”。

## 第 23 轮（R4-1）：未模糊阴影上 GPU（逐字节）+ 模糊阴影为何仍是 CPU

### 23.1 可切的子集

CPU 的 `box_shadow_cpu_rgba8` 第一行就是：

```rust

    fill_rect_cpu_rgba8_blended(pixels, width, visible, color, blend);

```

即 `blur_radius == 0` 的阴影就是“把 rect 按 offset 平移后填一个矩形”。而 `visible` 正是

## 第 24 轮：一次性完整门控 —— 抓到一个由“中断的脚本”留下的真实破损

### 24.1 根因（不是本轮改动）

`tools/check_view_platform_gate.sh` 的工作方式是：**备份**已提交的 probe → 写入“强制无条件 import”的

## 第 25 轮（R4 旁支）：轴对齐线条上 GPU（逐字节），斜线留 CPU

### 25.1 为什么只做轴对齐

CPU 的 `draw_line_cpu_rgba8` 是 Bresenham + **方章**：每个步进点盖一个 `[-half_w+1, +half_w]`
（两端含）的正方形，`half_w = max(width/2, 1)`。沿**水平或垂直**方向，这些正方形恰好铺成一个矩形；
沿斜线则不是。所以：

- 轴对齐 → 精确矩形 → `push_instance`，**逐字节**；
- 斜线 → 若改用胶囊 SDF，形状会明显不同（对 UI 里的 1–2px 线尤其刺眼），所以**继续留在 CPU**。

这是一个刻意的“宁可少覆盖，也不改观感”的取舍。

### 25.2 改动

| 位置 | 改动 |
|---|---|
| `renderer/dispatch.rs` | `DrawLine { width > 0, from.y == to.y \|\| from.x == to.x }` 可调度 |
| `renderer/encode.rs` | 按方章的包含式范围构造矩形：`right = max_x + half_w + 1`（写成 `+half_w` 时测试立刻抓到差一列像素） |

- `a_diagonal_line_stays_on_the_cpu`（断言调度器**不**认领斜线，防止以后有人“顺手”接上）

## 第 28 轮（R4-2）：模糊阴影上 GPU —— 并因此抓到 CPU 合成器的“双重乘 alpha”缺陷

这是 C 路线里**唯一需要“离屏图层 + 流内多 pass”**的一条，也是之前一直挂在“只能统计验收”的原因。
实现后发现：只要把 CPU 侧一处真实缺陷修好，**模糊阴影可以逐字节比对**，不需要退成统计断言。

### 做法（数据流）

| 阶段 | 内容 |
|---|---|
| 打包 | `pack_blurred_shadow`（新模块 `renderer/shadow.rs`）算出 `body`（偏移后的矩形 ∩ framebuffer ∩ clip）、`paint_region`（clip ∩ framebuffer）、`layer` = `body ± radius` 再夹到 framebuffer（**与 CPU `box_shadow_cpu_rgba8` 的图层范围完全一致**），body 实例按**图层局部坐标**写入 `shadow_instances` |
| 图层池 | `RenderCache::ensure_shadow_targets`：每个阴影一张 `Rgba8Unorm` 图层 + 一张同尺寸 scratch，每层自带 body-mvp uniform、H/V 两个 blur bind group 与参数缓冲、composite bind group。数量与尺寸都不变时整组复用 |
| 前奏 pass | `encode_shadow_layers`：图层 clear + 用 `shadow_body_pipeline`（实例矩形管线去掉 stencil）画 body → H blur（层→scratch）→ V blur（scratch→层） |
| 主 pass | `DrawStep::Scissor(paint_region)` + `DrawStep::Shadow(i)`：用**图像管线**把图层 1:1 合成回帧（`dest`=图层矩形，`source`=图层尺寸，所以 shader 的 `local * s / d` 退化为恒等映射）；剪裁由 scissor 承担 |

### 为什么 blur 用新 shader 而不是复用背景模糊

背景模糊 `BLUR_FS` 是 `sigma = radius / 2` 的**高斯**；CPU 阴影用 `box_blur_layer_rgba8` 的**整数滑动平均**，窗口端点夹在图层边界并除以夹过的 tap 数。两者形状不同。新增 `SHADOW_BLUR_FS`：

```wgsl
start = clamp(center ∓ radius)          // 窗口只夹一次，端点夹到图层内
span  = min(center ± radius, dims-1) - start
sum   = Σ round(texel * 255)            // 取回 8-bit 整数
out   = vec4<f32>(sum / count) / 255    // 整数除法截断，与 CPU 一致
```

因为图层尺寸 = CPU 图层尺寸，“夹到纹理”与“夹到图层”是同一个边界，不需要额外的边界 uniform。

### 抓到的真实缺陷：CPU 侧 alpha 被乘了两次

第一版逐字节比对失败（GPU 偏好约 2 倍）。用“黑底 / 白底两张渲染反解 alpha”的办法定位：

```
alpha y=11:  gpu 0.21/0.34/0.42/0.49/0.61/0.73/0.85 ...
             cpu 0.05/0.11/0.18/0.24/0.37/0.53/0.73 ...     ← 恰好是 gpu 值的平方
```

即 GPU 的 0.85 正是理论值 `6*(1/7) ≈ 0.857`（body 6 行、窗口 7 行），而 CPU 把图层 alpha 既当作 src.a
又当作 coverage 传给了 `blend_cpu_rgba8`（内部 `src_a = color.a * coverage`），于是 alpha 被平方。
这是 `box_shadow_cpu_rgba8` 的合成缺陷（N-S-63 那条路径），不是 GPU 的差异：

```rust
// 修前：
blend_cpu_rgba8(pixels, width, x, y, src, alpha as f32 / 255.0);
// 修后（渐变本身就是 src alpha，只乘一次）：
blend_cpu_rgba8(pixels, width, x, y, src, 1.0);
```

影响：软件路径上所有模糊阴影的边缘会比以前**亮一点（正确）**。`alpha == 255` 分支（`blend_pixel_cpu_rgba8`，
REPLACE，保留 `SetBlendMode`）未动。SVG 快照不经过 wgpu 光栅器（`grep rasterize_draw_commands tools/ src/render/` 无命中），故不受影响。

### 验收（逐字节，不是统计）

| 用例 | 断言 |
|---|---|
| `a_blurred_shadow_matches_the_software_rasteriser` | 24×24、radius 3，**字节完全相等** |

## 第 30 轮（R6）：任意角度线条 / 描边路径上 GPU——最后一块“回退面”也闭合了

R5 的核实里发现：未认领的绘制命令只剩 **斜线** 与 **含斜线段的描边路径**（再除 `SetBlendMode ≠ Normal`）。
而它们之前被排除的理由——“冲压方块不成矩形，重画成胶囊会改变图形”——只说对了一半：**方块本身就是方块**。

CPU 的 `draw_line_cpu_rgba8` 是 Bresenham：每一步在中心冲压 `2*half_w` 的正方形（端点双向包含，
`centre-half+1 ..= centre+half`）。所以 GPU 只要**每步发一个实例矩形**，就是同一张图，而且是结构上的同一张，
不是“接近”。关键是先把 Bresenham 抽成唯一实现，避免两条路各写一份：

```rust
// raster/fills.rs
pub(crate) fn for_each_line_stamp(from, to, width, visit: impl FnMut(i64, i64, i64));
//  `draw_line_cpu_rgba8` 现在内部就是它 + 逐像素 blend；GPU 侧是它 + 一次 push_instance
```

两处**必须和 CPU 一致**的细节，否则字节就跑了：

| 细节 | CPU 行为 | GPU 侧如何对齐 |
|---|---|---|
| `DrawLine` 的走线范围 | 先用 `effective_clip(fb, rect_for_line, clip)` 夹出矩形，再 `clip_segment_to_rect` **把端点夹到可见矩形**（否则极端端点会走十亿步/溢出 err） | `push_line_instances` 做完全相同的两步，所以步进结果与代价都一致 |
| 描边路径的逐段窗口 | 每段用 `rect_for_line(seg) ∩ clip_window` 作为该段自己的 clip；`path_width == 0` 时 **什么都不画** | `pack_rect_command` 的 `DrawPath{filled:false}` 分支逐段同式计算；`width == 0` 直接返回 |

顺手修掉一个跟旧实现相关的隐性分叉：旧 GPU 分支对 `path_width == 0` 用了 `max(1)`，会画 2px 宽；
CPU 对 0 宽是一点不画。新实现选 CPU 语义（不画），并写进 `commands_gpu_dispatchable` 的注释。

删除：`axis_aligned_line_rect`、`stroke_is_axis_aligned`（两个为“只敢认轴对齐”而存在的函数），
`commands_gpu_dispatchable` 对 `DrawLine` / `DrawPath` 的判定变成“宽度 > 0 / 点数 ≥ 2”。

用例（改 2 加 2）：

| 用例 | 断言 |
|---|---|
| `a_diagonal_line_matches_the_software_rasteriser` | 两条斜线（一条带 clip，交叉），**字节完全相等** |
| `a_diagonal_stroke_path_matches_the_software_rasteriser` | 四段全斜的闭合路径，**字节完全相等** |
| `an_axis_aligned_stroke_path_matches_the_software_rasteriser` | 原用例保留 |
| `an_image_stream_is_claimed_by_the_gpu_dispatcher` | 把“paths still need the CPU”断言翻转为“任意角度都可认领” |
