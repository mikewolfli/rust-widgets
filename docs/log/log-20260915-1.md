## 0. 基线：Windows 上「编译都过不去」

计划 §2.1 记录的基线是三档 profile 全部 `Finished`。在 Windows 上重跑第一条命令即失败：

```text
$ cargo check --no-default-features --features desktop
error[E0599]: no function or associated item named `from_platform_caps` found for struct
              `platform::types::PlatformCapabilities`
   --> src\platform\windows\platform_impl.rs:387:40
warning: unused import: `crate::platform::windows::helpers::*`
  --> src\platform\windows\mod.rs:23:9
error: could not compile `rust_widgets` (lib) due to 1 previous error; 1 warning emitted
```

**根因（取证，非推测）**：第七轮把 `NativeCapabilityContract` 从「独立结构体 + 逐字段拷贝函数」
改为 `pub type` 别名（`src/platform/types.rs:203`，注释写明「the two types are interchangeable and
no conversion is possible to get wrong」），并删除了 `from_platform_caps`。**Linux/macOS 后端的调用点
被同步更新，Windows 后端漏改**：

```text
$ grep -rn "from_platform_caps" src/
src/platform/types.rs:196   （只剩文档注释里提到历史）
src/platform/windows/platform_impl.rs:387   ← 仍在调用已删函数
```

计划 §8「🎯 跨目标编译：从『不可验证』升为真实验证」列出了 4 个交叉编译目标，但
`x86_64-pc-windows-msvc` **不在其中**：该轮用的是 `aarch64-apple-ios*` 与
`wasm32-unknown-unknown`。所以「Windows 编译不过」既没被本机验证，也没被交叉编译验证命中。

> 计划 §10.2b 的自我审计结论是「OS 编译门禁现状比你担心的好很多」。就**门禁分布**而言成立；
> 但门禁为 0 不等于该平台能编译——缺的是一条「在 Windows 上真的跑一遍」的判据。

## 1. 阻断项修复

### 1.1 `from_platform_caps` 残留（阻断：Windows 桌面不可构建）

`WindowsPlatform` 覆盖 `native_capability_contract` / `embedded_capability_contract`
两个方法，而**全仓只有它这么做**（`grep -rn "fn native_capability_contract" src/` 只命中
trait 默认体与 Windows）。两处覆盖体与 trait 默认体语义完全一致（`family()` 返回 `Desktop`，
默认体即 `Some(self.capabilities())`），因此整体删除，与其余全部后端保持一致。

```text
$ cargo check --no-default-features --features desktop
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 8.70s
```

### 1.2 `windows/helpers.rs`——「保留备用」的空模块（原则 #59）

删除后暴露出 9 条 warning，逐条追根：

```text
$ cargo check --no-default-features --features desktop
warning: unused import: `crate::platform::windows::helpers::*`
  --> src\platform\windows\mod.rs:23:9
```

`src/platform/windows/helpers.rs` 全文 11 行、**零代码项**，其模块文档自述：

> 「The module is retained (empty of constructors) as the seam where per-kind Win32
> control construction would live again if a kind is ever promoted back to `NativePreferred`.」

这正是原则 #59 点名的形态（`保留备用` 模块 + `#[allow(dead_code)]` 类残留）。
处置：删除 `helpers.rs`、`mod helpers;` 与 glob 重导出，并同步清理
`tools/platform_impl_scan.py` 中指向该文件的陈旧条目。

```text
$ for f in $(find src/platform -name "*.rs"); do ...零代码项检测...; done
EMPTY: src/platform/windows/helpers.rs (11 lines)   ← 删除前，全 src/platform 唯一一处
```

删除 helpers 后，warning 列表把另外两个模块也照了出来：

```text
warning: function `present_native_dialog` is never used      --> src\platform\windows\dialogs.rs:16
warning: function `present_folder_picker` is never used      --> src\platform\windows\dialogs.rs:115
warning: method `to_accel` is never used                     --> src\platform\windows\accel.rs:44

warning: function `record_shortcut_text` is never used       --> src\platform\windows\accel.rs:85
warning: function `shortcut_text_for` is never used          --> src\platform\windows\accel.rs:95
warning: function `install_accelerator` is never used        --> src\platform\windows\accel.rs:104
warning: function `parse_accelerator` is never used          --> src\platform\windows\accel.rs:172
warning: function `virtual_key_for_token` is never used      --> src\platform\windows\accel.rs:211
```

两者都是**原生控件时代的实现**，BLUE15 删掉原生对照后成了孤儿：

| 模块 | 内容 | 为什么是孤儿（取证） |
|---|---|---|
| `windows/accel.rs` | 完整 Win32 `HACCEL` 加速键表（含 11 个单测） | `install_accelerator`（唯一的生产侧写入者）**零调用**，而消费侧 `accel_table_for` 仍在消息循环里被调用 → 表永远不存在，`try_translate_accelerator` 恒为 `false` |
| `windows/dialogs.rs` | `MessageBoxW`/`GetOpenFileNameW`/`ChooseColorW`/`ChooseFontW` + `IFileDialog` 文件夹选择 | `present_native_dialog` 零调用；其依赖的 `dialog_data` **从未被写入** |

关键判据：**Windows 后端已不再覆盖任何菜单/对话框方法**，即它继承的是「诚实默认体」：

```text
$ grep -n "fn create_menu\|fn menu_add_item\|fn create_message_box\|fn create_file_dialog\|\
fn create_color_dialog\|fn create_font_dialog\|fn create_directory_dialog" \
  src/platform/windows/platform_impl.rs src/platform/windows/types.rs
（无输出）
```

而对话框语义已由自绘路径承担（`control_backend/custom/create_widgets_dialog.in.rs` 挂载
`WidgetKind::MessageBox` 等）。因此这两个模块属 BLUE15「删除即删除」未完成的部分，
连同其**死引用**一并物理删除：

- `try_translate_accelerator` 调用点（消息泵）与方法本体
- `release_accelerator_table` 调用点
- `dialog_data` 字段、`Win32DialogData` 结构体及其在 `destroy_widget` 中的清理块
- `menu_owner_window` 字段（在 `destroy_widget` 中的清理块删除后，成为唯一引用）
- `mod accel;` / `mod dialogs;` 与相关文档注释

```text
$ cargo check --no-default-features --features desktop
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 12.98s   （0 warning）
```

## 3. Windows 专属测试失败（计划在非 Windows 宿主上不可能看到）

三档 profile 的**单元测试**在 Windows 上首跑：

```text
test result: FAILED. 4023 passed; 3 failed; 0 ignored
    platform::ime_windows::tests::test_tsf_available_initially_false_in_test
    shortcut::tests::command_modifier_bit_matches_primary_shortcut
    widget::input_widgets::lineedit::tests::lineedit_clipboard_copy_paste_cut
```

三条都不是「代码坏了」，而是**测试把某一个宿主的配置写成了断言**：

| 测试 | 根因（取证） | 处置 |
|---|---|---|
| `test_tsf_available_initially_false_in_test` | 断言 TSF 不可用；但 `WindowsImeBridge::new()` 会 `LoadLibrary("msctf.dll")` + `TF_GetThreadMgr`，在现代 Windows 上必然成功。测试注释自述「In test builds without the `windows` cfg active」——**该条件不存在** | 改写为断言真实契约：可用性标志必须与所创建的线程管理器一致，且桥初始为「无组合」 |
| `command_modifier_bit_matches_primary_shortcut` | 断言 Meta 位（`0b1000`）命中 `Shortcut::primary`。这是 **macOS 语义**；`lookup` 在 `Desktop` 风格下把 CTRL 提升为 PRIMARY，而 Meta 位不提升，故 Windows 上不命中。测试自身文档即写着「This is the link that makes typing **Cmd+Z on macOS**…」 | 按**运行时**风格（`PlatformShortcutStyle::current()`）分档断言，符合原则 #68（中间层不得用 `cfg(target_os)`） |
| `lineedit_clipboard_copy_paste_cut` | 偶发失败；隔离运行稳定通过 → 共享**真实系统剪贴板**。追查发现 `WindowsClipboard::set_contents` 缺 `EmptyClipboard()`（Win32 要求在 `OpenClipboard` 与 `SetClipboardData` 之间清空），使结果依赖剪贴板原有内容 | 补上 `EmptyClipboard()`（并导入符号） |

```text
$ cargo test --no-default-features --features desktop --lib -q
test result: ok. 4026 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out
```

## 4. QA 门禁：可移植性缺陷（本轮「卡死」的真凶）

按计划 §六 逐个跑门禁时大量失败，其中一个**挂起**。根因不是门禁逻辑，而是脚本假设了 Unix 环境：

```text
$ which python3
/c/Users/mikew/AppData/Local/Microsoft/WindowsApps/python3      ← Microsoft Store 执行别名
$ python3 --version
exit=49          ← 无输出、立即返回；无控制台时会等待 Store UI（即「卡死」）
$ which python ; python --version
/c/Tools/Python3/python
Python 3.12.10   ← 真正的解释器
```

11 个门禁脚本硬编码 `python3`（共 17 处调用）。**Windows 上这个名字是坏的**，
而脚本没有任何回退 → 门禁要么失败、要么挂起。此外 Python 在中文 Windows 上默认用 GBK：

```text
UnicodeDecodeError: 'gbk' codec can't decode byte 0x94 in position 151
UnicodeEncodeError: 'gbk' codec can't encode character '\u2705' in position 0
```

处置（一次性收口，原则 #58 的思路）：

1. 新增 `tools/lib_python.sh`：**实测**候选解释器（`python3` → `python` → `py`，只有真的能跑且是
   Python 3 才被接受，因此 Store 别名被自动跳过）；随后 `export PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8`，
   把「脚本输出含 ✅/❌、文档含中日文」这一类编码问题在唯一入口解决。
2. 11 个脚本改为 `. "$ROOT_DIR/tools/lib_python.sh"` + `"$PYTHON"`。
3. 两处 `open()` 补 `encoding="utf-8"`（`check_widget_kind_count.sh` 内联 Python、
   `generate_platform_capability_matrix.py`）。

## 5. 最大缺口：控件访问器与单一机制断链（Gap A，已修并已验证）

### 5.1 现象（探针取证）

`lib.rs` 的 48 个控件访问器（`set_widget_value`/`set_widget_checked`/`combo_box_add_item` …）
全部实现为 `platform::get_platform().…`。BLUE15 把宿主降级为「只提供绘制面」（规则 #56）后，
这些 trait 方法成为诚实默认体（返回 `false`/`None`），于是**访问器静默无效**；
而**同名的 C ABI 函数走 `get_control_backend()`，是可用的**。两条路径，一条什么都不做。

```text
PROBE cb.checked before        : Ok(Bool(false))
PROBE cb.checked after set     : Ok(Bool(false))     ← 句柄写了，控件没变
PROBE cb.tristate after set    : Ok(Bool(false))
PROBE slider.value after set   : Ok(Int(0))
PROBE label.text after set     : Ok(String("hello")) ← 连标签文本都没到控件
PROBE lineedit.read_only after : Ok(Bool(false))
```

同时确认**可用路径确实存在**：

```text
PROBE after backend.set_text: Ok(String("via-backend"))
PROBE after property write  : Ok(String("via-property"))
PROBE checkbox write checked -> Ok(()), readback Ok(Bool(true))
PROBE slider write value -> Ok(()), readback Ok(Int(42))
```

且这些访问器在**测试/示例/基准中零引用**（`grep` 只命中 `src/lib.rs` 定义处），
所以没有任何既有判据能发现它。

### 5.2 处置

| 家族 | 处置 | 依据 |
|---|---|---|
| 标签/可见/启用/几何/IME/无障碍 | 改走 **ControlBackend**（与 C ABI 一致） | 后端已有真实实现，实测可用 |
| 值/范围/步长/勾选/三态/只读/占位/最大长度/选中索引/滚动/方向/分组 | 改走**控件自身属性契约** | 规则 #67：控件状态由控件自己表达 |
| 窗口状态/最小尺寸/图标 | **保持 Platform** | §1.1 明确保留 OS 窗口管理 |

新增 crate 内部助手 `src/widget/capability/widget_access.rs`，用**探测候选属性名**的方式解析
（沿用后端已有的 `LABEL_PROPERTY_NAMES` 先例），并对数值做「整数优先、否则浮点」的表示协商
（滑块的 `value`/`minimum` 是 `i64`，组合框的 `current_index` 是 `u64`，`expect_*` 不跨整浮边界）。

属性名取自**实测真值**（`widget_property_names()` 打印），不是猜的：

```text
PROBE slider           -> ["minimum","maximum","value","single_step","page_step","orientation",...]
PROBE combo_box        -> ["item_count","current_index","current_text","editable",...]
PROBE list_box         -> ["item_count","selection_mode","current_row","item_height",...]
PROBE line_edit        -> ["text","placeholder_text","max_length","read_only","cursor_position",...]
PROBE radio_button     -> ["text","checked","group_id",...]
PROBE checkbox         -> ["text","state","checked","tristate_enabled",...]
PROBE scroll_area      -> ["widget_resizable","scroll_position_x","scroll_position_y",...]
```

> 注意真值与直觉不同：是 `placeholder_text` 而非 `placeholder`，是 `current_row`
> （ListBox）/`current_index`（ComboBox/TabBar）而非 `selected_index`，是 `single_step` 而非 `step`。
> 若凭直觉映射，会得到一批**静默 no-op**——这正是本轮坚持先取证再改的原因。

### 5.3 同类的「项操作」缺口（`ControlBackend` 声明未实现）

用脚本比对 trait 声明与单一机制（custom 后端）的实现，得到权威缺口的清单：

```text

  MISSING: combo_box_add_item    ← 控件级，需实现

  MISSING: create_widget
  MISSING: get_clipboard_text    ← 宿主能力
  MISSING: get_widget_geometry   ← 控件级
  MISSING: hide_widget           ← 控件级
  MISSING: inject_drop_event     ← 宿主能力
  MISSING: list_box_add_item     ← 控件级
  MISSING: list_box_remove_item  ← 控件级
  MISSING: list_box_clear_items  ← 控件级
  MISSING: poll_drop_event       ← 宿主能力
  MISSING: poll_widget_triggered ← 控件级
  MISSING: set_clipboard_text    ← 宿主能力
```

控件级的 9 个在 custom 后端补齐（项操作走能力层 `widget_as_mut` 下行转换，与属性钩子同一机制）；
顺带补齐 `combo_box_item_text` / `list_box_item_text`（此前**连 trait 都没声明**）。

### 5.4 菜单项没有「身份」——真缺陷

```text
src/control_backend/custom/create_widgets_menu.in.rs:
    return ObjectId::from(added);    ← added: bool ⇒ 恒为 0/1
```

`menu_add_item` 原本返回 `1`（`u64::from(true)`）：它**不指向任何菜单项**，还会与平台
从 `1` 开始分配的 id 空间碰撞。而菜单项是内存行（`MenuEntry`，非 widget），确实没有 id。
处置：给菜单项建立真实身份——后端分配 id 并把 `(菜单 widget id, 项下标)` 记入
`CustomControlState::menu_entries`，起始值 `FIRST_MENU_ENTRY_ID = 1 << 48` 以避开 widget id 空间；
`menu_item_shortcut` 据此反查该行自己的 `shortcut`（trait 新增该方法，默认 `None`）。

同时修掉一个**假能力**：`attach_menu_bar_to_window` 原本无条件 `return true`，
现改为校验两个 id 均存活并把菜单栏设为窗口子节点。

### 5.5 方法遮蔽：`native_handle()` 恒为 `None`

公共 API `rust_widgets::native_handle(id)` 走 trait 方法 `Platform::get_native_handle`，
而 `WindowsPlatform` 只定义了**同名固有方法**（`types.rs:135`），trait 方法保留默认 `None`
→ 对**明显有 HWND 的宿主窗口**也报「无原生对象」。已按「扫描固有方法 vs trait 方法同名」脚本
全仓核对，**仅此一处**；处置为在 trait impl 中显式委托给固有方法。

## 8. 未修复 / 未验证登记（原则 #16，不冒充完成）

### 8.1 🔴 Gap B：库创建的窗口没有宿主 HWND（**未修复，需架构决策**）

**证据**（探针，非推测）：

```text
PROBE backend            = WindowsPlatform
PROBE supports_surfaces  = true
PROBE create_window      = 6000285942072475649      ← 库 API 返回 widget runtime id
PROBE native_handle(win) = None                     ← 宿主注册表里没有它
PROBE is_mounted(win)    = true                     ← 但 widget runtime 里有
PROBE raw create_widget_of_kind(Button) -> 0        ← 因此在库窗口下承载控件失败
PROBE app new_checkbox raw_id -> 6000285942072475653 ← App 路径能建控件
```

**根因**：`rust_widgets::create_window` → `backend_for_kind(Window)` → custom 后端
→ `mount_widget_of_kind(WidgetKind::Window, …)` → **只**在 `widget::runtime` 注册一个
自绘 `Window` 控件，**从不调用 `Platform::create_window`**，因此没有 HWND。
而 `Platform::mount_surface` 需要 `get_native_handle(parent)`，于是 `create_widget_of_kind`
与 `WindowHandle::mount_surface`（TUTORIAL/文档中的自绘控件承载入口）在 Windows 上返回 0 / 报错。
两个 id 空间（平台 `state.create_widget` 与 `widget::runtime::register`）从未被连接。

**为什么本轮不动它**：候选修法都需要**跨全部后端的设计决定**，而本机只有
`x86_64-pc-windows-msvc` 一个 target，无法验证 macOS/Linux/移动端：

- 方案 A：`Platform` 增加语义化方法（如「在调用方指定的 id 上创建宿主窗口」），
  9 个后端各自实现或显式继承默认体（原则 #53）。
- 方案 B：`widget::runtime` 支持**指定 id 注册**，让宿主窗口 id 与窗口控件 id 合一。

两者都会改动核心 id 模型。在只能验证 1/9 个后端的情况下单方面实施，风险高于收益
（违反「绝对禁止不完整修复」）。**建议列入 BLUE16 首项**，并配一条
「库窗口可承载控件」的判据。

**影响面**：`App`/`WindowHandle` 的窗口显示、`WindowHandle::mount_surface`、
`create_widget_of_kind`；`demo/` 下使用 `App::new_window` 的示例。
`crate::create_window` 的 C ABI 同名函数同样受影响。

## 9. 结论

1. **BLUE15 在 Windows 上「未完成」**，且差距不是细节：删除面漏了两个模块、
   访问器整片断链、门禁在 Windows 上根本跑不起来、三条以上测试断言的是**别的宿主**的行为。
   这些在 macOS/Linux 上的取证里结构性看不见。

2. **根因是同一件事的三次重演**：BLUE15 删掉了「宿主拥有控件」这一层，
   但**调用方**没有全部改接到新路径——
   `from_platform_caps`（能力契约）、`menus/dialogs/accel`（原生控件实现）、
   `lib.rs` 48 个访问器 + `ControlBackend` 9 个方法（控件状态）。
   原则 #17「禁止迁移幻觉」正是为此设立，本轮把它逐条落实。

3. **本轮产出**：阻断项 1 个、删除面 3 个文件 + 全部死引用、
   访问器断链（48 个包装 + 9 个后端方法 + 菜单项身份 + `native_handle` 遮蔽）、
   10 条 clippy、61 条 rustdoc、4 类测试假设错误、1 处 Win32 API 误用（`EmptyClipboard`）、
   1 个跨平台测试脆弱点（CRLF）、11 个门禁脚本的可移植性。

4. **复验结果**：三档 profile **零 warning / 零失败**（desktop 4171、embedded 1518、mini 1442）、
   三档 clippy `-D warnings` 通过、`cargo doc -D warnings` 0 错误、
   与 CI 对齐的 Windows 特征组合通过、**门禁 15 PASS / 0 FAIL**、
   仓库自带单机制探针 **PASS**、新增 24 例访问器判据全绿。

5. **仍有一个功能性阻断未修**：Gap B（库窗口无宿主 HWND，见 §8.1）。
   它需要跨后端的设计决定，本轮**显式登记为未修复**，不做无验证支撑的改动。

## 10. 这些缺陷都与操作系统有关吗？（就地澄清，原则 #2）

**不。** 本轮因在 Windows 上跑而**显现**的缺陷，与因操作系统的**代码差异**而**存在**的缺陷，
是两类东西。判据不是「在哪台机器上看到的」，而是「出问题的那行代码有没有 `cfg(target_os)`／
是不是平台 API」。逐条取证后的分类如下。

### 10.1 真正与操作系统绑定（修在 `src/platform/` 内）

| 缺陷 | 绑定证据 |
|---|---|
| `from_platform_caps` 残留 | 位于 `windows/platform_impl.rs`（`#[cfg(target_os="windows")]` 文件）；`grep` 全仓只此一处 |
| `helpers.rs` / `accel.rs` / `dialogs.rs` | 均位于 `src/platform/windows/` |
| `EmptyClipboard` 缺失 | Win32 剪贴板 API 契约 |
| `Platform::get_native_handle` 被固有方法遮蔽 | `windows/types.rs`；“同名遮蔽”扫描全仓仅此一处 |
| GBK 编解码错误 | Windows 的 ANSI 代码页默认值 |

### 10.2 与操作系统**无关**（全平台同样坏，只是没人跑过）

| 缺陷 | 判据（可复现） |
|---|---|
| **Gap A 访问器断链**（48 包装 + 9 后端方法 + 菜单项身份） | `grep -c "cfg(target_os" src/control_backend/custom/*.rs src/control_backend/native.rs` → **全 0**；`lib.rs` 里 2 处 `target_os` 只在一个文档示例内 |
| **Gap B 窗口无 HWND** | 创建路径（`mount_widget_of_kind` → `mount_widget_object` → `mount_surface`）整层零 OS 分支 |
| 过时集成测试 + 探针示例 | 断言的是被删除的契约，与平台 API 无关 |
| 61 条 rustdoc 错误 | 路径/私有项链接，与平台无关 |
| `as_draw_mut` doctest 引用 `full_widgets` 门控模块 | 是 feature 门控，不是 OS 门控 |
| lifecycle 计时 flaky | 时钟刻度，与平台无关 |

> **为何这些在 macOS 上也没被发现？** 不是宿主问题，而是**取证口径**：
> 计划只跑了 `--lib`（V10/V11/V12 自登记为「未验证」），
> 而访问器表面在 `tests/`、`examples/`、`benches/` 中**零引用**——
> 没有任何判据能让它失败。Windows 只是把这些变成了**编译期可见**（death-code 警告）
> 与**可运行**（集成测试、示例、探针）而已。

### 10.3 属于「宿主/环境可移植性」，不是操作系统 API

| 缺陷 | 为何不能归为 OS 相关 |
|---|---|
| 门禁硬编码 `python3` | Windows 的 Store 执行别名是触发条件，但**一台只有 `python` 而无 `python3` 的 Linux 主机同样会坏**。这是脚本可移植性缺陷 |
| CRLF / `core.autocrlf` / 缺 `.gitattributes` | 触发条件是**宿主 git 配置** + 仓库缺跨平台规范；根因不是平台代码 |

### 10.4 属于「工具链版本」，且**本机无法定论**

10 条 clippy（`collapsible_match` ×9、`module_inception` ×1）。1.95 报、1.98 是否报**未验证**
（只装了一个工具链）。已按建议修正（行为不变），但成因不下结论。

### 10.5 一句话

> **操作系统的差异解释了「为何在 Windows 上第一次看见」，不解释「为何这些是缺陷」。**
> 真正由 OS 决定的只有 §10.1 那 5 项；**缺口的主体（§10.2）在任何平台上都一样存在**，
> 是「删了旧层、没接完调用方」（原则 #17）+「判据只跑 `--lib`」共同造成的。
