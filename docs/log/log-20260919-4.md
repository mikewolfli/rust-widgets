# 第 51 轮（2026-09-19）— 全库超级深度 + 超级广度扫描：发现一个修一个 → 版本 2.4.4

## 0. 一句话结论

基线 `cargo check --no-default-features --features desktop --all-targets` 为 `Finished`，
六路并行取证（假实现/死代码 · 平台门控 · 声明式+保留架构 · 别名/命名/重复定义 · 控件接线与事件 · FFI/绑定/JSON）
共挖出 **11 大类、40+ 个真实缺陷**。

本轮最重要的产出是**「整个 Windows 后端在会发布的配置里根本编译不过，而没有任何一个 CI 作业编译过它」**：

- `winapi::um::windef::RECT` 不存在（该符号在 `winapi::shared::windef`），2 处；
- `invalidate_surface_rect` 用 `super::canvas` 却没有 `widgets_unstripped` 门控（`macos` 侧同样有）；
- Windows/GTK/macOS 三个 canvas 无条件构造 `Event::Touch*`，而该变体受 `feature = "touch"` 门控；
- 整个 Windows 面用裸 `std` 的 `String`/`Vec`/`HashMap`，`mini` 的 `#![no_std]` 下有 **24 个错误**。

它们能存活的原因已定位并修复：唯一编译 Windows 的作业用的是**手写能力清单且不含任何 device profile**，
于是 `full_widgets` 为假，受 device 门控的那半边**也从未被编译**。

---

## 1. 方法论（原则 #1/#16/#56）

1. 先跑基线：`cargo check --no-default-features --features desktop --all-targets` → `Finished`。
2. 六路并行只读取证（子代理，各自 disjoint 范围），每条要求 `file:line` + 证据，不许推测。
3. **逐条复核子代理结论，不直接采信**。本轮复核出两处误报并记录在下文（§11）。
4. 每条修复都做**反向注入验证**：把修复去掉 → 观察测试按预期失败 → 恢复修复 → 观察通过。
5. 逐轮只跑「定点证据」，全量门禁留到最后一次性跑（原则 #56）。

### 2.2 为什么没有任何作业发现它

CI 的 `windows-cross-check`（`.github/workflows/ci.yml:585`）用的命令是：

```text
cargo check --target x86_64-pc-windows-msvc --no-default-features \
 --features "windows desktop-runtime wgpu touch i18n controls-native controls-custom
 serde serde_json advanced-widgets quality-management"
```

**这份清单里没有任何 device profile**（`desktop`/`tablet`/`mobile`），因此：

| cfg 别名 | 该命令下的值 | 后果 |
|---|---|---|
| `device_profile` | **false** | `full_widgets` 也为 false |
| `widgets_unstripped` | true | `canvas` 模块存在，掩盖 §2.1 第 1 条 |
| `full_widgets` | **false** | 受 device 门控的那半边 Windows 面**从未编译** |

而 `check_profiles.sh` 的五个 `cargo check` **全部跑在宿主 target 上**，Windows 面整片被 cfg 掉。
两边合起来，Windows 后端是**零覆盖**。

### 2.3 修复

1. `winapi::um::windef::RECT` → `winapi::shared::windef::RECT`（2 处）。
2. `invalidate_surface_rect` 补 `#[cfg(widgets_unstripped)]`（它的 5 个兄弟方法都有）。
3. `macos/platform_impl.rs::create_window` 里的 `super::canvas::install_resize_delegate` 同样补门控。
4. 三个 canvas 的 touch 路径整体按 `feature = "touch"` 门控（含 `RegisterTouchWindow` 与
 `WM_TOUCH` 分支），无能力时走 `DefWindowProcW`。
5. Windows 面的 `String`/`Vec`/`HashMap`/`format!`/`to_string` 全部改走 `crate::compat`
 （与 `platform/linux/types.rs` 既有写法一致），`lock()` 换成 `compat::lock`。

### 2.4 补齐门禁（根因修复）

`tools/check_profiles.sh` 新增 `[6b/9]`：对 `x86_64-pc-windows-msvc` 交叉检查
`desktop`/`embedded`/`mini` 三档 **加**「无 device profile 且无 touch」四种组合。
target 未安装时**明确报 SKIPPED 并给安装命令**，而不是静默通过
（与 `run_test_case`「过滤器不匹配任何测试即失败」同一理由）。

### 2.5 定点证据（修复后）

```text

 done
```

## 3. 🔴 声明式层：静默状态丢失（三条独立缺陷）

### 3.1 被删除的属性重置为 `Null`，而多数控件会拒绝它

```rust
// src/view/diff.rs:271-283（修复前）
for name in old.props.keys() {
 if !new.props.contains_key(name) {
 report.patches.push(Patch::SetProperty {
 id: old_id, name: name.clone(), value: CapabilityValue::Null,
 });
 }
}
```

注释声称「`set` 路径会决定 `Null` 的含义」。**这对多数属性是假的**：
全仓只有约 20 处显式处理 `CapabilityValue::Null`，其余走
`expect_i64`/`expect_usize`/… ，而这些对 `Null` 一律返回 `TypeMismatch`。

**可观测后果**：`scroll_position_x` 之类的属性被从视图里删掉后，控件**永久**保留旧值——
因为下一次 diff 在新树里找不到该键，**根本不会再发补丁**，唯一信号是被普遍忽略的
`ApplyReport::errors` 条目。

**修复**：`apply` 在写入前把 `Null` 替换为**能力 schema 声明的默认值**
（`default_widget_property_default_value`），即「未声明时该属性取什么值」的唯一真相源。
`resolve_null_reset` 从**活控件**读 kind，因为 `Node.widget` 是创建名而 schema 以 `WidgetKind` 为键，
且原则 #21 不允许给公开 `Node` 加字段。

**反向注入验证**：

```text
去掉修复后：
 panicked at src\view\apply.rs:455:
 a dropped property must not be refused;
 errors: [PropertyRefused { name: "text_visible", reason: TypeMismatch }]
恢复修复后：17 passed
```

### 3.2 重复兄弟 key：last-write-wins，且所有计数器都显示「一切正常」

```rust
// src/view/diff.rs:302-307（修复前）
for (i, child) in old.children.iter().enumerate() {
 if let Some(k) = child.key_str() {
 old_key_index.insert(k, i); // 重复 key 覆盖前一条
 }
}
```

`old = [A(k="dup"), B(k="dup"), C]`、`new = [B, A, C]` 时：两个新子节点都解析到 B 的下标；
第一个消费掉它，第二个发现已消费——而**带 key 的子节点按设计不回落到位次匹配**——
于是它被判为全新并 `Insert`，仍未消费的原节点被 `Remove`。

**可观测后果**：一个稳定列表（key 意外重复，如按非唯一字段做 key）会重建控件、
丢失焦点与滚动位置，而 `positional_matches` 与 `replaced_subtrees` **都是 0**，
即报告在**反向**暗示匹配质量最高。

**修复**：重复 key 记为**不可映射**（确定性走「新增」路径），并在 `DiffReport` 新增
`duplicate_keys` 字段让调用方看得见；`Node::duplicate_sibling_keys` 已经存在但**从无生产调用者**，
现在有了消费点。

### 3.3 别名拼写被当成类型变更 → `Replace`

`Node.widget` 是**创建名**，多个拼写指向同一 kind（`scrollarea` / `scroll_area` 都是 `ScrollArea`）。
按声明名字符串比较使「仅改拼写」被判定为类型变更，于是 `Replace` ——
销毁重建一个**根本没换类型**的控件，正是 `Patch::Replace` 文档要付出的焦点/滚动代价。

**修复**：新增 `same_control_kind`，经工厂自己的能力解析（`factory.capability(..).kind`）比较；
无注册表的构建回退到 `normalize_key`（更弱但不会把两个不同的控件判为同一个）。
位次匹配那一处同样改用它。

## 4. 🔴 `ModalBottomSheet` 拖拽关闭无法到达 + 4 个控件的「卡住拖拽」

```rust
// src/widget/dialog/modal_bottom_sheet.rs:334-336（修复前）
Event::MouseMove { pos: _ } => {
 // In a real integration, delta_y would be tracked from MousePress origin
}
```

`MousePress` 启动拖拽，但**没有任何事件**调用 `update_drag`，所以 `drag_offset` 恒为 `0.0`，
`end_drag` 的「超过 1/3 高度」阈值**不可满足**。既有单测直接调 `sheet.update_drag(80.0)`，
因此全绿。

**修复**：新增 `drag_to(y)`（记住按压原点、按原点重算而非累加）与 `cancel_drag()`；
`MousePress` 记录原点，`MouseMove` 调 `drag_to`，`MouseLeave` 调 `cancel_drag`。

**反向注入验证**：

```text
去掉 drag_to 调用后：
 panicked: dragging down must accumulate an offset, got 0
```

### 4.1 同类模式（冰山法则）：按压不清理，指针离开即失控

| 控件 | 泄漏的状态 | 可观测后果 |
|---|---|---|
| `NumberPicker` | `drag_origin_y` | **悬停即改值**（无按键），实测 50 → 42 → 35 |
| `Slider` | `mouse_pressed` | 悬停即拖动手柄 |
| `RangeSlider` | `dragging` | 悬停即移动把手 |
| `BezierCurveEditor` | `dragging` + base 按压位 | 悬停即移动控制点 |

四处都是同一成因：`MouseRelease` 只在**控件内部**被投递（运行时的命中测试对控件外返回 `None`），
因此「按住后移出再松开」永远不会送达 release。四者统一补 `Event::MouseLeave` 清理臂
（`KanbanBoard::cancel_drag` 是仓内正确范例）。

## 5. 🔴 C ABI 未发布 value-kind 判别值，导致三个绑定泄漏

`rw_get_widget_property` 写 `out_kind`，其取值来自 8 个变体：
`NULL/BOOL/INT/UINT/FLOAT/STRING/COLOR/RECT`。但**生成的 C 头里没有任何 `rw_value_kind`**——
生成器只输出函数声明。于是每个绑定自己手写常量，且**三个都停在 `RW_VALUE_STRING`**。

**可观测后果**（Python/Node/C++ 完全一致）：

```python
if kind.value == RW_VALUE_STRING:
 return self._decode_and_free(self.lib, text.value)
return None # ← kind 6/7 落到这里
```

读任何 `Color`/`Rect` 属性（`signature_pad.stroke_color`、`color_well.color`、
`depth_chart.bid_color` …）返回 `None`（与「无此属性」不可区分），**且 ABI 已分配的 `CString` 永不释放**
——每读一次泄漏一次。

**修复**：

1. `tools/generate_c_header.py` 新增 `parse_value_kinds`，**从 `binding_impl.rs` 解析**枚举
 （单一真相源）并输出 `typedef enum { … } rw_value_kind;`；解析不到任何常量则**报错退出**
 （空枚举正是本缺陷）。
2. 三个绑定补齐 6/7 并接受它们；**未知 kind 也释放 payload**，使未来新增 kind 不会重新引入泄漏。
3. Python 的 `__all__` 补上两个新常量。

**门禁根因修复**：`check_binding_symbol_coverage.py` 的 `SYMBOL_RE` 只匹配 `rw_*`，
**结构上不可能看见 `RW_VALUE_*`** —— 所以它此前打印「covers all 130 symbols」。
新增 `VALUE_KIND_RE` 与 `published_value_kinds`/`declared_value_kinds`，
对三个直接 FFI 绑定逐个比对。

**反向注入验证**（把 Python 的 `RW_VALUE_RECT` 整行删掉）：

```text
FAIL python ... cannot name 1/8 value kinds: RW_VALUE_RECT —
 a reader that cannot match a kind returns 'no such property' and leaks the payload
 it did not free
```

## 6. 🟠 JSON 声明式层：错 kind、假告警、无人发布的拼写

### 6.1 `infer_kind` 的 `_ => WidgetKind::Button` 把所有工厂路由名注册成 `Button`

`infer_kind` 是约 100 条的手写表，而工厂路由 **152 个规范名 + 170 个别名**。
表里没有的名字（`icon`、`chip`、`table`、`progress_bar`、`tag_input` …）统统注册为 `Button`，
于是 `LayoutInspector` 的诊断与 `by_kind` 查询都在**报告错误的 kind**。

**修复**：注册改读**活控件的 `kind()`**。`infer_kind` 退居 `#[cfg(test)]`
（两个测试要断言「活控件的 kind 与旧表回落值不同」来证明缺陷存在过）。

### 6.2 七个键被 arm 读取，却被告知「被忽略」

`is_loader_owned_key` 与 `create_widget` 的 arm 表分别维护。
`tristate`/`password`/`word_wrap`/`tab_shape`/`h_policy`/`v_policy`/`alpha`
被 arm 读取并**已生效**，但不在该列表里，于是 `apply_properties` 事后
`log::warn!("… no construction arm consumed it; the value was ignored")` ——
作者会去追一个不存在的 bug。

**修复**：补齐列表，并新增
`every_arm_consumed_key_is_either_published_or_loader_owned`
——它**从 loader 源码本身解析** arm 里的 `obj.get("…")`，因此不会再漂移。

> 注意：初次实现时我把不变量写错了（要求「必须在 `is_loader_owned_key` 里」），
> 实测报出 40 个键；复核后发现其中 33 个是控件**已发布**的属性、由名称驱动通道正确解析，
> 只有 7 个真正有缺陷。测试据此改为「已发布 **或** loader-owned」，才是真正的不变量。

### 6.3 `min`/`max` 无人发布，且与 `cupertino_slider` 语义冲突

四个 arm（slider/scrollbar/progressbar/spinbox）读 `min`/`max`，
但这四个控件发布的是 **`minimum`/`maximum`**；而 `min`/`max` **确实是** `cupertino_slider`
的公开属性，且类型是 **`Float`**。同一个拼写在四个控件上表示整数范围、在第五个上表示浮点对。

**修复**：新增 `read_json_range`，两种拼写都接受、**发布名优先**，四处 arm 统一调用。

### 6.4 `fontdialog` 的 `value` 被读取后丢弃

```rust
// src/json/loader.rs（修复前）
if let Some(_font_str) = obj.get("value").and_then(|v| v.as_str()) {
 // Font selection from string requires font parsing.
 // Default value used for now; full font parsing can be
 // added when Font::from_string or similar is available.
 fd.set_current_font(crate::core::Font::default());
}
```

`"Monospace 20"` 静默变成 Arial 14，无任何提示。注释的前提也已过时
（`Font` 早已有 builder/校验）。

**修复**：实现 `Font::parse`（`"<family> <size>[ bold][ italic]"`，
size 取**最后一个**可解析数字，使 `"Roboto 2020 12"` 仍解析为族 `"Roboto 2020"` + 12 号）；
解析失败时**告警并保留对话框自身字体**，而不是替换成默认值。
新增 6 个 `Font::parse` 单测 + 2 个 loader 侧测试。
（我的 `parse_keeps_a_family_that_contains_digits` 测试第一版就抓到了我自己实现里
「取第一个数字」的错误，已改为取最后一个。）

## 7. 🟠 别名与 capability 解析

### 7.1 `Panel` 和 `MenuItem` 的工厂名为空 → 主题静默跳过

两者都是合法 `WidgetKind` 且可构造，但都没有自己的 capability 行

## 8. 🟠 CSS 选择器：`menu_bar { … }` 匹配不到任何东西

```rust
// src/style/css.rs:76（修复前）
CssSelector::Kind(k) => k.eq_ignore_ascii_case(kind),
```

`kind` 是控件的 `Debug` 拼写（`"MenuBar"`），作者写的是**库各处发布的工厂名**
（`"menu_bar"`）。大小写折叠**不处理分隔符**，所以 `menu_bar` 匹配失败。

**关键在于它是静默的**：规则**解析成功**，因此「未知 kind」的告警分支根本不会执行，
用户只看到样式没生效。

同时另一条 CSS 入口（`to_selector` → `widget_kind_from_str`）用一张手写表，
`MenuBar`/`ToolBar`/`StatusBar`/`TabWidget`/`MenuButton` 全都不在表里——
两条入口对「`MenuBar` 是不是已知 kind」给出**不同答案**。

**修复**：

1. `matches` 改用 `crate::widget::capability::coercion::normalize_key`
 —— 全仓唯一的名称规范化器，于是选择器接受的拼写与工厂**完全一致**。
2. `widget_kind_from_str` 从手写 `match` 改为**覆盖表 + `normalize_key` 比较**，
 并按 `kind.rs` 的门控逐条标注 `#[cfg(widgets_unstripped)]` / `#[cfg(full_widgets)]`。

**反向注入验证**：`every_kind_selector_spelling_resolves` 在修复前报
`"MenuBar" must resolve to MenuBar, left: None`。

> ⚠️ 这一改动我第一次做错了：覆盖表里 17 个变体是 `widgets_unstripped` 门控的，
> 我却无条件列出，导致 `mini`/`embedded` **新增 47 个编译错误**。
> 实测发现后按 `kind.rs` 逐条补门控，并把测试用例同样门控。

## 9. 🟠 假测量值：`menu_config` 把硬编码 512MB 当作「检测到」

```rust
// src/menu_config/config.rs:73-80（修复前）
fn detect_gpu_memory() -> u32 {
 if let Ok(val) = std::env::var("RUST_WIDGETS_GPU_MEMORY_MB") { … }

}
```

该值既喂给 `estimate_gpu_performance` → `PerformanceLevel`（影响动画/模糊/阴影默认值），
又被 `MenuConfigDialog::gpu_description()` **直接打印给用户**：
`"NVIDIA (512 MB)"` —— 声称这是**检测到**的显存。

同文件 `detect_system_memory` 早已按原则 #36/#37 改成
`platform_facts().total_memory_mb().unwrap_or(4096)`，而显存这条路没有跟上。

**修复**：`gpu_memory_mb: Option<u32>` + `gpu_memory_is_measured: bool`；

## 11. 🟠 能力表 flags 与控件真实契约不符（第 3 轮补修）

`properties_tests.rs` 的 `schema_and_contract_publish_the_same_names` **故意跳过**
`readable: false, writable: false` 的行，理由写的是「它们不承诺任何东西，所以不是谎言」。

这个假设**掩盖了反方向的真实缺陷**。用运行时探针逐行核对（读活控件的 `kind()`
→取 capability →调 `widget_property_get`/`widget_property_set`）得到确凿结果：

```text
$ cargo run --features desktop --example __capflag_probe
file_dialog title / modal contract-get=Ok (flags say false,false)
scroll_area scroll_position_x / _y contract-get=Ok
scroll_area h/v_scroll_bar_policy contract-get=Ok
tab_widget tab_count / current_index contract-get=Ok
pie_menu item_count/radius/inner_radius/current_index contract-get=Ok
input_dialog title/label_text/mode/text_value/int_value/double_value contract-get=Ok
date_time_edit datetime/display_format/calendar_popup contract-get=Ok
… TOTAL rows whose control really serves them: 35
```

其中 31 行的写入也成功（`write=true`），4 行只读（`has_content`、`tab_count`、
`widget_count`、`subwindow_count`、`active_subwindow`、`docked`、`loading`、`view_mode`）。

**可观测后果**：`WidgetFactory::read_property`/`write_property` 对 `readable`/`writable`
为假的行直接返回 `UnsupportedOnWidget`/`ReadOnlyProperty`，因此**调用方无法读写控件明明支持的能力**
（`pie_menu.radius`、`scroll_area.scroll_position_x`、`input_dialog.text_value` …）。
设计工具、`capability_manifest()` 消费者会把字段当成不存在，从不提供它。

### 处置（31 行，逐行按实测结果纠正，不是批量改表）

- 读写均可 → `true, true`；只读可读 → `true, false`。
- 我第一轮改过头了 4 行（`message_box.modal`、`progress_dialog.value/minimum/maximum`），
 **既有门禁当场报错**：
 ```
 these controls have schema entries no contract answers, so the schema promises
 properties that cannot be read or written: [("message_box", "modal"),
 ("progress_dialog", "value"), ("progress_dialog", "minimum"), ("progress_dialog", "maximum")]
 ```
 已按实测回退为 `false,false`——这正说明该门禁是有效的。

### 新增门禁（补上缺失的那个方向）

`a_property_flagged_unservable_must_really_be_unservable`：
断言每个 `false,false` 行（`geometry` 除外，已文档化为例外）**确实两条方向都不服务**。

**反向注入验证**（把 `pie_menu.radius` 改回 `false,false`）：

```text
panicked at src\widget\capability\properties_tests.rs:760
→ FAILED（测试名与失败信息均指向被错误标记的行）
恢复后：ok
```

## 12. 复核出的误报（诚实记录）

子代理报告中有两条经实测判定为**不成立**，未按其建议修改：

1. **「`Panel` 在 `kind.rs` 的文档欺骗」**——正确（已修）。
 但同一报告附带的「`infer_kind("panel")` 应返回 `GroupBox`」不成立：
 `Panel` 是独立变体，只是没有 capability 行；已经核实 `kind.rs` 的
 `kind-role: base` 说明并据实修正文档。

2. **「`is_loader_owned_key` 漏了 40 个键」**——只有 7 个成立。
 其余 33 个是控件**已发布**的属性，名称驱动通道会正确解析，
 既不发告警也无数据丢失。测试的不变量已相应修正（§6.2）。

3. **`event_signal_bridge` 的「281 个事件全部不可达」**——机制描述正确，
 但严重度被高估为「每个事件都是缺陷」。实际是**一个结构性事实**：
 控件信号与 hub 命名空间是两个世界，**连接是宿主的职责**。
 未按「自动绑定」的方向修改（那会强制每个构造函数接收 hub，正是本项目避免的全局状态）；
 改为：① 把模块文档改写成**如实说明谁必须接线**；
 ② 新增 `EventSignalBinder::forward_widget_events`（一个控件一次调用，覆盖其 capability
 发布的可绑事件），让宿主**有**一条不靠手工列表的路；③ 新增 2 个测试证明它真的接通。
