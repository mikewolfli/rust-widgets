## 2. 🔴 头条 A：`mini` 是唯一开启 `#![no_std]` 的 profile，而三个组合长期不编译

### 2.1 取证（修复前，本机 macOS 实测）

```
$ cargo check --no-default-features --features "mini,macos"
error[E0425]: cannot find type `String` in this scope   (7 errors)

$ cargo check --no-default-features --features "mini,i18n"
error[E0425]: cannot find type `String` in this scope   (65 errors)

$ cargo check --no-default-features --features "mini,cocoa-legacy"
error[E0425]: cannot find type `String` in this scope   (17 errors)
```

### 2.2 为什么这是**必然**而非偶发

`build.rs:81` 在 `mini` 上发出 `cargo:rustc-cfg=alloc_frugal`，`src/lib.rs:23` 把它变成
`#![cfg_attr(feature = "mini", no_std)]`。`#![no_std]` **移除标准 prelude**，于是：

- 裸名 `String` / `Vec` 不再解析（契约要求走 `crate::compat`，`src/lib.rs:52` 已写明）；
- `Mutex::lock()` 返回的**不是 `Result`**（`compat::Mutex` 在 `alloc_frugal` 下是 `spin::Mutex`，
  无中毒概念），于是 `.lock().expect(..)` / `.lock().ok()?` 类型不匹配；
- `.to_string()` 不再解析（`ToString` 不在 alloc prelude 里，`src/lib.rs:56` 已写明）。

**关键不对称**：`embedded` **不**开 `no_std`（它只发 `embedded_surface`，另一条别名）。因此
`embedded,macos` 一直 PASS 而 `mini,macos` FAIL —— 这正是该缺陷能长期存活的原因：所有按 profile
抽样的人都抽到了 `embedded`，没人抽到 `mini`。

### 2.3 同类模式（冰山法则）：不是一个组合，是一整类

修复范围（逐文件、逐点）：

| 文件 | 缺陷 |
|---|---|
| `src/platform/macos_objc2/types.rs` | `use std::collections::HashMap/VecDeque`、`std::sync::Mutex`，裸 `String`/`Vec` |
| `src/platform/macos_objc2/platform_impl.rs` | 裸 `String`；`self.menus.lock().expect(..)` |
| `src/platform/state.rs` | `Vec` 未走 `compat` |
| `src/platform/clipboard_stubs.rs` | 两个 macOS 剪贴板分支均裸 `String` |
| `src/platform/mobile.rs` | `self.menus.lock().expect(..)` |
| `src/platform/macos/types.rs` | `std::collections::HashMap`、`std::sync::{Mutex, OnceLock}`，裸 `String`/`Vec`，4 处 `.lock().expect(..)` |
| `src/platform/macos/canvas.rs` | 4 处 `.lock().expect(..)` |
| `src/platform/accessibility/macos.rs` | `std::collections::HashMap`、`std::sync::Mutex`；4 处 `if let Ok(..) = ..lock()` |
| `src/i18n/{global,manager,types,options,watcher}.rs` | 裸 `String`/`Vec`；`ToString`；`GLOBAL_I18N.lock().unwrap_or_else(..)` ×6 |

### 2.4 修复：单一接缝

新增 `crate::compat::try_lock`（`src/compat.rs`），把「std 返回 `LockResult` / spin 直接返回 guard」
这一 profile 差异**只归一化一次**：

```rust
pub fn try_lock<T>(mutex: &Mutex<T>) -> Option<MutexGuard<'_, T>> {
    #[cfg(not(alloc_frugal))] { mutex.lock().ok() }
    #[cfg(alloc_frugal)]     { Some(mutex.lock()) }
}
```

已有的 `compat::lock` 覆盖「中毒恢复」语义，`try_lock` 覆盖「中毒短路」语义（调用点本身返回
`Option`/`bool`，想让中毒直接失败）。所有 9 处 `.lock().expect(..)` / `.lock().ok()?` 改走这两个名字，
调用点从此零 `cfg`。

### 2.5 根因修复：门禁补齐缺失的那一格

`tools/check_profiles.sh` 原本**只**跑 host 上的 `desktop/tablet/mobile/mini/embedded`，从不跑
`mini` × backend。新增 `[9b/9]` 段：对 `wasm android harmony ios windows linux-wayland`（Apple 主机
再加 `macos cocoa-legacy`）逐个跑 `cargo check --no-default-features --features "mini,<backend>"`，
外加 `mini,i18n`。**这是本条的根因修复**——模块再也不能静默回归。

## 3. 🔴 头条 B：`cocoa-legacy` 独自重演了 `macos` 已经修过的 `serde` 缺陷

### 3.1 取证（修复前）

```
$ cargo check --no-default-features --features "cocoa-legacy"
error[E0432]: unresolved import `serde`
  --> src/platform/macos_objc2/types.rs:13:5
error[E0433]: cannot find module or crate `serde_json`
error[E0599]: no method named `serialize_widget_snapshot` found for struct `BackendState<K>`
  --> src/platform/macos_objc2/types.rs:59:20
```

### 3.2 根因：修了一半

`Cargo.toml:190-195` 有一段注释明确记载了这个缺陷，并把 `serde`/`serde_json` 加进了 `macos` 的
依赖列表，理由写得很清楚：「objc2 后端的 handle 类型 derive `Serialize`，state snapshot 返回
`serde_json::Error`，所以这是硬依赖而非可选——它们原先从 `desktop` 继承，导致
`--features macos` 单独编译失败」。

但 `cocoa-legacy`（`Cargo.toml:299`）**只**声明 `["dep:cocoa", "dep:objc"]`。启用
`cocoa-legacy` 会同时编译 `src/platform/macos_objc2/`（两个 Apple 后端共用一个 gate），于是同一个
缺陷在同一个 commit 的「另一侧」原样复活。**这正是「修一个点必须扫同类模式」的典型案例**：
修的是 `macos` 这个**名字**，而不是「Apple 后端需要 serde」这个**事实**。

### 3.3 修复

`Cargo.toml`：`cocoa-legacy = ["dep:cocoa", "dep:objc", "serde", "serde_json"]`，并把
「为何是硬依赖」的理由写进该行旁边的注释（与 `macos` 那段对称），使下一个人不必再推一遍。

### 3.4 定点证据

```

macos-legacy      -> issues=0
mini,cocoa-legacy -> issues=0
```

## 4. 🔴 头条 C：门控漂移——`invalidate_surface_rect` 漏了 `widgets_unstripped`

### 4.1 取证

`src/platform/macos/canvas.rs` 的模块 gate 是
`#[cfg(all(feature = "cocoa-legacy", widgets_unstripped))]`，
而 `src/platform/macos/platform_impl.rs` 里紧邻的两个 `Platform` 方法：

```rust
#[cfg(widgets_unstripped)]                        // ← 有 gate
fn invalidate_surface(&self, id: ObjectId) -> bool { self.invalidate_surface_impl(id) }

fn invalidate_surface_rect(&self, id, rect) -> bool {   // ← 无 gate
    self.invalidate_surface_rect_impl(id, rect)
}
```

`mini,cocoa-legacy` 下 → `no method named invalidate_surface_rect_impl found for &MacOSPlatform`。

### 4.2 为何这是门控缺陷而非类型缺陷

修法有两条：给方法加 gate，或把 `canvas.rs` 的 gate 放宽。选前者，因为
`src/platform/macos/mod.rs:30-33` 的注释已经给出理由：「`mini`/`embedded` 没有
`widget::runtime`，而 canvas 建在它之上」。`invalidate_surface` 的 gate 正是这条理由的体现，
`invalidate_surface_rect` 只是漏抄——**修一个点必须扫同类模式：两个方法是一对，gate 必须成对。**

### 4.3 修复与证据

给 `invalidate_surface_rect` 补 `#[cfg(widgets_unstripped)]`，并在注释中写明它与
`invalidate_surface` 的 gate 关系。`mini,cocoa-legacy` 由 17 error → 0。

## 4o. 🔴 `Animation`：有限时长动画的进度永不饱和（两处独立缺陷）

### 4o.1 取证（实测）

```
raw=0.5    finite=0.5    infinite=0.5
raw=1      finite=0      infinite=0     ← 文档说“读过最后一次迭代的有限动画读 1.0”
raw=3      finite=0      infinite=0
```

两个独立原因叠加：

**① 钳位失效**：有限分支写的是 `(raw % 1.0).min(1.0)`——`min` 在 `%` **之后**，
永远不可能生效（`raw % 1.0` 恒 `< 1.0`），于是有限分支与无限分支**完全等价**。

而 `progress_inner()` 在「未运行」时返回 `0.0`，于是**已完成的动画读 0.0**——
绑在进度条上的控件会在填满那一刻跳回空。

`compute_progress`（`pause()` 冻结的那个）是**逐字重复**的同一段代码，带着同一个缺陷。

### 4o.2 修复

抽出单一接缝 `progress_inner()`（`progress` 与 `compute_progress` 共用，消除重复）；
有限分支改为 `raw.min(1.0)`；`progress()` 在运行检查**之前**先用 `is_completed()` 回答完成态。
