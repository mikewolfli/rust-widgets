## 2. 🔴 头条 A：`mini` 是唯一开启 `#![no_std]` 的 profile，而三个组合长期不编译

### 2.1 取证（修复前，本机 macOS 实测）

```
$ cargo check --no-default-features --features "mini,macos"
error[E0425]: cannot find type `String` in this scope   (7 errors)

$ cargo check --no-default-features --features "mini,i18n"
error[E0425]: cannot find type `String` in this scope   (65 errors)

$ cargo check --no-default-features --features "mini,cocoa-legacy"
error[E0425]: cannot find type `String` in this scope   (17 errors)
```

### 2.2 为什么这是**必然**而非偶发

`build.rs:81` 在 `mini` 上发出 `cargo:rustc-cfg=alloc_frugal`，`src/lib.rs:23` 把它变成
`#![cfg_attr(feature = "mini", no_std)]`。`#![no_std]` **移除标准 prelude**，于是：

- 裸名 `String` / `Vec` 不再解析（契约要求走 `crate::compat`，`src/lib.rs:52` 已写明）；
- `Mutex::lock()` 返回的**不是 `Result`**（`compat::Mutex` 在 `alloc_frugal` 下是 `spin::Mutex`，
  无中毒概念），于是 `.lock().expect(..)` / `.lock().ok()?` 类型不匹配；
- `.to_string()` 不再解析（`ToString` 不在 alloc prelude 里，`src/lib.rs:56` 已写明）。

**关键不对称**：`embedded` **不**开 `no_std`（它只发 `embedded_surface`，另一条别名）。因此
`embedded,macos` 一直 PASS 而 `mini,macos` FAIL —— 这正是该缺陷能长期存活的原因：所有按 profile
抽样的人都抽到了 `embedded`，没人抽到 `mini`。

### 2.3 同类模式（冰山法则）：不是一个组合，是一整类

修复范围（逐文件、逐点）：

| 文件 | 缺陷 |
|---|---|
| `src/platform/macos_objc2/types.rs` | `use std::collections::HashMap/VecDeque`、`std::sync::Mutex`，裸 `String`/`Vec` |
| `src/platform/macos_objc2/platform_impl.rs` | 裸 `String`；`self.menus.lock().expect(..)` |
| `src/platform/state.rs` | `Vec` 未走 `compat` |
| `src/platform/clipboard_stubs.rs` | 两个 macOS 剪贴板分支均裸 `String` |
| `src/platform/mobile.rs` | `self.menus.lock().expect(..)` |
| `src/platform/macos/types.rs` | `std::collections::HashMap`、`std::sync::{Mutex, OnceLock}`，裸 `String`/`Vec`，4 处 `.lock().expect(..)` |
| `src/platform/macos/canvas.rs` | 4 处 `.lock().expect(..)` |
| `src/platform/accessibility/macos.rs` | `std::collections::HashMap`、`std::sync::Mutex`；4 处 `if let Ok(..) = ..lock()` |
| `src/i18n/{global,manager,types,options,watcher}.rs` | 裸 `String`/`Vec`；`ToString`；`GLOBAL_I18N.lock().unwrap_or_else(..)` ×6 |

### 2.4 修复：单一接缝

新增 `crate::compat::try_lock`（`src/compat.rs`），把「std 返回 `LockResult` / spin 直接返回 guard」
这一 profile 差异**只归一化一次**：

```rust
pub fn try_lock<T>(mutex: &Mutex<T>) -> Option<MutexGuard<'_, T>> {
    #[cfg(not(alloc_frugal))] { mutex.lock().ok() }
    #[cfg(alloc_frugal)]     { Some(mutex.lock()) }
}
```

已有的 `compat::lock` 覆盖「中毒恢复」语义，`try_lock` 覆盖「中毒短路」语义（调用点本身返回
`Option`/`bool`，想让中毒直接失败）。所有 9 处 `.lock().expect(..)` / `.lock().ok()?` 改走这两个名字，
调用点从此零 `cfg`。

### 2.5 根因修复：门禁补齐缺失的那一格

`tools/check_profiles.sh` 原本**只**跑 host 上的 `desktop/tablet/mobile/mini/embedded`，从不跑
`mini` × backend。新增 `[9b/9]` 段：对 `wasm android harmony ios windows linux-wayland`（Apple 主机
再加 `macos cocoa-legacy`）逐个跑 `cargo check --no-default-features --features "mini,<backend>"`，
外加 `mini,i18n`。**这是本条的根因修复**——模块再也不能静默回归。

## 3. 🔴 头条 B：`cocoa-legacy` 独自重演了 `macos` 已经修过的 `serde` 缺陷

### 3.1 取证（修复前）

```
$ cargo check --no-default-features --features "cocoa-legacy"
error[E0432]: unresolved import `serde`
  --> src/platform/macos_objc2/types.rs:13:5
error[E0433]: cannot find module or crate `serde_json`
error[E0599]: no method named `serialize_widget_snapshot` found for struct `BackendState<K>`
  --> src/platform/macos_objc2/types.rs:59:20
```

### 3.2 根因：修了一半

`Cargo.toml:190-195` 有一段注释明确记载了这个缺陷，并把 `serde`/`serde_json` 加进了 `macos` 的
依赖列表，理由写得很清楚：「objc2 后端的 handle 类型 derive `Serialize`，state snapshot 返回
`serde_json::Error`，所以这是硬依赖而非可选——它们原先从 `desktop` 继承，导致
`--features macos` 单独编译失败」。

但 `cocoa-legacy`（`Cargo.toml:299`）**只**声明 `["dep:cocoa", "dep:objc"]`。启用
`cocoa-legacy` 会同时编译 `src/platform/macos_objc2/`（两个 Apple 后端共用一个 gate），于是同一个
缺陷在同一个 commit 的「另一侧」原样复活。**这正是「修一个点必须扫同类模式」的典型案例**：
修的是 `macos` 这个**名字**，而不是「Apple 后端需要 serde」这个**事实**。

### 3.3 修复

`Cargo.toml`：`cocoa-legacy = ["dep:cocoa", "dep:objc", "serde", "serde_json"]`，并把
「为何是硬依赖」的理由写进该行旁边的注释（与 `macos` 那段对称），使下一个人不必再推一遍。

### 3.4 定点证据

```

macos-legacy      -> issues=0
mini,cocoa-legacy -> issues=0
```

## 4. 🔴 头条 C：门控漂移——`invalidate_surface_rect` 漏了 `widgets_unstripped`

### 4.1 取证

`src/platform/macos/canvas.rs` 的模块 gate 是
`#[cfg(all(feature = "cocoa-legacy", widgets_unstripped))]`，
而 `src/platform/macos/platform_impl.rs` 里紧邻的两个 `Platform` 方法：

```rust
#[cfg(widgets_unstripped)]                        // ← 有 gate
fn invalidate_surface(&self, id: ObjectId) -> bool { self.invalidate_surface_impl(id) }

fn invalidate_surface_rect(&self, id, rect) -> bool {   // ← 无 gate
    self.invalidate_surface_rect_impl(id, rect)
}
```

`mini,cocoa-legacy` 下 → `no method named invalidate_surface_rect_impl found for &MacOSPlatform`。

### 4.2 为何这是门控缺陷而非类型缺陷

修法有两条：给方法加 gate，或把 `canvas.rs` 的 gate 放宽。选前者，因为
`src/platform/macos/mod.rs:30-33` 的注释已经给出理由：「`mini`/`embedded` 没有
`widget::runtime`，而 canvas 建在它之上」。`invalidate_surface` 的 gate 正是这条理由的体现，
`invalidate_surface_rect` 只是漏抄——**修一个点必须扫同类模式：两个方法是一对，gate 必须成对。**

### 4.3 修复与证据

给 `invalidate_surface_rect` 补 `#[cfg(widgets_unstripped)]`，并在注释中写明它与
`invalidate_surface` 的 gate 关系。`mini,cocoa-legacy` 由 17 error → 0。

## 4o. 🔴 `Animation`：有限时长动画的进度永不饱和（两处独立缺陷）

### 4o.1 取证（实测）

```
raw=0.5    finite=0.5    infinite=0.5
raw=1      finite=0      infinite=0     ← 文档说“读过最后一次迭代的有限动画读 1.0”
```

### 4o.2 修复

抽出单一接缝 `progress_inner()`（`progress` 与 `compute_progress` 共用，消除重复）；

```
PieMenu::new(center, 0.0) -> radius=0.0    set_inner_radius(1.0) -> 0     <-- 且几何为零尺寸
```

`new` 是 `radius` 的另一个写者，**不**做下界钳位。所以缺陷是**可达的**，且不止一处：

1. `.max(2.0).min(...)` 顺序错 → 下界不保证（`new` 路径可达）；
2. `new` 不做下界钳位 → 可造出零尺寸几何，任何 item 都无法命中（命中测试比的是
   到 `inner_radius`/`radius` 的距离，半径为 0 时没有任何点在其中）；
3. `new` 对 NaN/∞ 不设防。

修复：新增 `PieMenu::MIN_RADIUS`，`new` 与 `set_radius` **共用**同一下界；
`set_inner_radius` 改为 `.min(ceiling).max(floor)`（先上界后下界，使文档的区间定义成为权威）；
非有限输入被**拒绝**（保持原值）而非传播（`f32::max`/`min` 会返回非 NaN 操作数，
于是 NaN 输入静默变成某一侧的边界值——也不是调用者要的）。

实测（修复后）：12 档输入 × 上下边界**零违规**，NaN 被拒。4 个新测试，反向注入后 4 个全 FAILED。

### 4s.2 ✅ `WindowHandle` 的 icon/min_size 镜像 —— **真缺陷，已修**

镜像字段写入后**无人读取**，而 getter 只读平台。取证发现两个方向的缺陷：

**① 读取端缺回退**。只有 `stub` 与 `windows` 实现了 `window_icon`/`window_min_size`；
`macos` 实现了 size 对但**没实现 icon 对**；`linux-gtk`、`wayland`、`android`、`ios`、
`wasm`、`harmony` 全部继承 trait 默认（返回 `None`）。于是在这 6+1 个后端上，
`set_icon` 返回 `true` 之后 `icon()` 仍然报 `None`。同类 getter `is_maximized` 早已有
`mirrored_flag` 回退，这两个没有。**这是原则 #37「必须有 trait 兜底」的实例。**

**② 写入端在成功前就写镜像**。`set_icon`/`set_min_size` 先写镜像再问平台，
于是被平台**拒绝**的值也被记下来了——只要有人读镜像就会读到平台拒绝的值。
「字段无人读」碰巧掩盖了它。

修复：两个 setter 改为**成功才记镜像**；两个 getter 改为「平台 → 镜像 → 无」，
与 `is_maximized` 同构；新增 `mirrored_min_size()`。

**测试难点（诚实记录）**：本机 cocoa 实现了 size 对，所以最初写的测试**无法区分修复前后**
（反向注入后仍然通过）。改用 `platform::runtime::with_platform` 注入一个
「setter 成功但 reader 不实现」的替身后，测试才真正有判别力。反向注入两半各自验证：
- 回退 getter → `an_accepted_window_property_reads_back_without_platform_readers` FAILED
- 无条件写镜像 → `a_rejected_window_property_is_not_reported_by_a_later_read` FAILED

### 4s.3 ✅ `MiniVec`/`MiniString` 容量上限 —— **两个真缺陷 + 一处文档错误**

**① `into_mini` 在超长输入上丢失**整个**字符串**（不只是不截断）。实测：

```
tooltip: asked 500 bytes, got 0
```

根因已从 `heapless` 源码取证：`String::push_str` → `Vec::extend_from_slice`，
其契约是「won't fit in the `Vec`; **don't modify anything** and return an error」——
**原子失败**。而文档写的是「the longest whole-prefix of `s` that fits」。
所以实际行为比文档**更差**：不是截断，是全丢；而空 tooltip 与「没设 tooltip」无法区分。

修复：改为逐 `char` push，遇到第一个放不下就停 —— 这才让文档的「whole-char prefix」成真。
实测：500 → **256**（修复前 0）；CJK 600 字节 → **255** 字节且仍是合法 UTF-8
（256 恰好切在一个 3 字节字符中间，逐字节拷贝会留下孤立续字节）。

**② `add_child` 在 mini 下静默丢弃子控件**。实测：

```
added 100, stored 64        # add_child(65..100) 全部丢失，返回 ()，无日志
```

这与项目规则「禁止静默失败」直接冲突。修复：抽出 `try_add_child` 返回 `bool`，
并新增 `child_overflow_count()` 计数器 —— 即使调用者用旧的 `add_child`（签名不变，
原则 #21），丢失也**可观测**。新增 `child_capacity()` 让调用者提前判断。

**③ 文档错误**：cookbook 三个语言版本都写 `MiniString<128>`，代码是 `String<256>`。
已随本轮一并修正。

**④ 常量去重**：新增 `MINI_VEC_CAPACITY` / `MINI_STRING_CAPACITY`，
使类型定义与文档注释引用同一个名字，不可能再漂移。

新增 5 个测试（3 个在 `compat.rs`，2 个在 `base.rs`），在 `mini` 档实跑通过。
反向注入：`into_mini` 回退 → 2 个测试 FAILED（断言直接显示 `left: 0`，即空串）；
`add_child` 回退 → 计数器测试 FAILED。

## 4t. 第 6 轮 · 优先项 1：`events:` 声明 ↔ 真实发射点三方对齐（全部 297 对）

### 4t.1 方法

建立一个**机械核对**，而不是抽查：解析 `properties.rs` 里全部 187 个 capability 的
`events: &[...]`，对每一对 (capability, event) 检查三件事是否一致：

1. 发布的**名字**；
2. 该名字能解析到的**信号字段/访问器**；
3. 该信号在**控件自己的 impl 里**有 `.emit(..)` 调用点。

### 4t.2 第一轮结论：名字解析全部通过

```

pairs with NO matching signal field: 0
```

### 4t.3 第二轮结论：**6 个真实缺陷**（第三边不一致）

加入「发射点」检查后，暴露出 6 对**有信号、但控件从不发射**的事件 —— 全部实测确认：

| capability | 发布名 | 真实信号 | 控件实际发射 |
|---|---|---|---|
| `auto_complete_edit` | `changed` | `text_changed` | `text_changed` ✓ |
| `auto_complete_edit` | `selected` | `suggestion_selected` | `suggestion_selected` ✓ |
| `animated_image` | `finished` | `animation_finished` | `animation_finished`, `frame_changed` |
| `lottie_widget` | `finished` | `animation_finished` | `animation_finished` |
| `rive_widget` | `finished` | `animation_finished` | `animation_finished` |
| `video_player` | `finished` | （无此信号） | `playback_started` / `paused` / `ended` / `time_updated` |

**为什么这是用户可见缺陷**（实测取证）：

```rust
factory.connect_event("auto_complete_edit", "changed", &hub, || {})
  -> Ok(...)     // 通过校验
```

`connect_event`（`capability.rs:920-942`）先用 `capability.events` 校验名字，
再 `hub.connect(event_name, slot)` 注册订阅。所以一个「表里发布、信号不背」的名字会得到
一个**看起来活的订阅**——句柄有效、hub 正常，但**没有任何代码路径会调 `hub.emit` 到这个名下**。
不是报错，是静默永不触发。

`video_player` 尤其明显：发布名 `finished` 与该控件四个信号**一个都不匹配**。

### 4t.4 修复

按实测信号名重写这 6 处发布名（`video_player` 改为发布其真实四个信号）。
字段与控件代码**未改**——错的是契约表，不是实现。

### 4t.5 新增门禁（根因修复）

`tools/check_capability_events_are_emitted.{py,sh}`，`run_all_gates.sh` 自动发现（`tools/check_*.sh`）。

**门禁自身的两轮返工（诚实记录）**：

  实测**漏报**——删掉 `Switch` 唯一的 `self.toggled.emit(..)` 后仍然 PASS，

### 4t.6 同时补强既有测试的盲区

## 4v. 第 7 轮 · 优先项 3：`WindowHandle` 镜像 vs 平台权威源（逐个判定）

### 4v.1 先取证：每个镜像字段是否被读

对 `WindowState` 的 13 个字段逐个统计**生产代码**（排除 `Debug`/`Default`/测试）中的读取点：

```
x 5   y 5   w 4   h 4   icon 2   min_w 3   min_h 3
maximized 2   minimized 2   fullscreen 2   resizable 2   decorated 2   close_callback 2
```

**结论：13 个字段全部有生产读取点**。`icon`/`min_w`/`min_h` 在本轮之前是 0，
正是上一轮修复（读取端补回退 + 写入端改为成功才写）补上的。

### 4v.2 逐字段判定：保留为回退，而非删除

保留的**判据是两条必须同时成立**（已写入测试文档）：

1. **至少 6 个后端读不回来**：`window_min_size`/`window_icon` 在
   `linux-gtk`、`wayland`、`android`、`ios`、`wasm`、`harmony` 上继承 trait 默认返回 `None`；
   `macos` 实现了尺寸对但**没实现**图标对。这些后端上 setter 返回 `true` 而 getter 是 `None`。
2. **`apply_window_layout` 在任何后端都需要窗口尺寸**——包括原生对象尚未创建的构造期，
   这正是 `record_created_geometry` 的文档理由。

不同时满足两条的字段应当**删除**；本类型没有这样的字段。

### 4v.3 顺带发现并修复：5 个 flag setter 与 2 个 value setter 语义不一致

`set_min_size`/`set_icon` 是「**平台接受才写镜像**」，
而 `set_maximized`/`set_minimized`/`set_fullscreen`/`set_resizable`/`set_decorated`
是「**无条件写镜像、丢弃平台返回值**」。

实测后果：对一个**不存在的窗口**调 `set_maximized(true)` 后，`is_maximized()` 报 `true`
（平台返回 `None` → 回退到被无条件写入的镜像）。这是一个「报告了并未发生的事」的缺陷。

修复：5 个 setter 统一为先问平台、**接受才写镜像**。新增测试
`every_mirror_backed_getter_defers_to_the_platform_first` 锁住这一统一契约
（反向注入 → FAILED）。另加 `the_window_geometry_mirror_reaches_the_layout_path`
防止 `x/y/w/h` 被后续重构孤立。

## 10.1 【已修·确认可达 panic】`SliderHandle::set_range` 交叉区间崩溃

- **文件**：`src/app/handle.rs`
- **缺陷**：`set_range(min, max)` 把两个值直接写进镜像后，用 `state.value.clamp(state.min, state.max)` 钳位。
  `min`/`max` 是**可变字段**而非常量，`i32::clamp` 在 `min > max` 时**panic**。
  `set_range(100, 0)`（一个完全正常的**降序滑块**）会当场把进程打挂。
- **实测取证**（探针输出）：
  ```
  [PROBE] SLIDER set_range(100,0) [on default 0..100] -> panic=true
  [PROBE] SLIDER set_range(0,100); set_range(100,0)  -> panic=true
  ```
  panic 位置：`src/app/handle.rs:1547:39`，消息 `min > max. min = 100, max = 0`。
- **修复**：改用 `ordered_clamp_i32(value, min, max)`（`src/widget/numeric.rs`，本类缺陷的既有标准解），
  对两个界先排序再钳位；**区间本身仍按调用者给定顺序转发给后端**，
  因为「哪端是最小值」是调用者的选择，不该被静默改写。
- **反向注入验证**：还原为 `clamp` → `slider_accepts_crossed_range_without_panicking` **FAILED**
  （复现原始 panic）→ 恢复修复 → PASS。

## 10.2 【已修·确认可达 panic】`SpinBoxHandle::set_range` 同类缺陷

- **文件**：`src/app/handle.rs`
- **实测取证**：`[PROBE] SPINBOX set_range(0,100); set_range(100,0) -> panic=true`
  （panic 位置 `src/app/handle.rs:2303:39`，消息 `min > max. min = 100, max = 0`）。
- **修复**：同 10.1，`set_value` 与 `set_range` 两处均改用 `ordered_clamp_i32`。
- **反向注入验证**：还原 → `spinner_accepts_crossed_range_without_panicking` **FAILED** → 恢复 → PASS。

## 10.3 【已修·静默写入反向区间】`ProgressBarHandle::set_min` / `set_max`

- **文件**：`src/app/handle.rs`
- **缺陷**：`set_min(100)`（默认区间仍是 `0..100`）时，`state.value.clamp(state.min, state.max)`
  **不会** panic（调用点恰好已经把排序用上了），但它把**未排序**的 `(100, 0)` 通过
  `set_widget_range` 写进了后端状态——`widget_range()` 会原样读回一个**反向区间**。
  这与 `src/platform/state.rs:545` 自身的约定（`value.clamp(min.min(max), max.max(min))`，
  即后端自己都要排序）不一致。
- **修复**：一次排序，钳位与写后端**共用同一个有序对** `(min.min(max), min.max(max))`。
- **行为澄清（实测）**：交叉后区间**塌缩**，值被拉到塌缩后的唯一端点——
  `set_min(100)` 使区间塌缩为 `[100, 100]`，值 `40 → 100`；`set_max(0)` 塌缩为 `[0, 0]`，值 `40 → 0`。
  这是交叉区间的**数学必然结果**，且与不 panic 的契约一致，已写成断言固化。

## 10.4 【已修·确认可达 panic】`InputDialog::get_int` 交叉 `min`/`max` 构造即崩溃

- **文件**：`src/widget/dialog/input_dialog.rs`
- **关键点**：`min`/`max` 是 `get_int` 的**公开参数**（无 setter/getter），
  所以 `get_int(.., value, 100, 0, ..)` 是调用者可以写出的合法调用。
- **实测取证**：`[PROBE] get_int(value=500, min=100, max=0) -> panic=true`
  ——**在对话框构造过程中就 panic**，对象都还没交回调用者。
- **修复**：在赋值处一次性排序（`d.int_min = min.min(max); d.int_max = min.max(max);`），
  再用**已排序**的两界钳位 `value`。
- **同时修复同文件另两处同类隐患**：
  - `set_int_value`：`v.clamp(self.int_min, self.int_max)` → `ordered_clamp_i64(...)`
  - `set_double_value`：`v.clamp(self.double_min, self.double_max)` → `ordered_clamp_f64(...)`
    （`NaN` 仍按原逻辑**直接拒绝**，不参与钳位——本次未改动该语义，只加断言固化）
- **新增基础件**：`src/widget/numeric.rs` 新增 `ordered_clamp_i64`（`i32` 版的 `i64` 对应物），
  **因为** `InputDialog` 的界是 `i64`，原先把 `i32` 版硬套会静默截断。同处补齐单测。
- **反向注入验证**：见 10.7 汇总表。

## 10.5 【取证澄清·低置信项关闭】`PieMenu::set_inner_radius` 钳位顺序

- **原状态**：第 9 节第 3 条列为「未证明可达，未改」。
- **本轮取证方式**：不靠推理，**穷举实测**——对 `radius ∈ {-1e9, 0, 1, 2, 2.105, 5, 10, 1e6, +∞, NaN}`
  各取 `set_inner_radius(-5.0)` 与 `set_inner_radius(1e9)` 两个极端：
  ```
  new(-1000000000): radius=10  inner(lo)=2 inner(hi)=9.5      floor_ok=true ceil_ok=true
  new(0):           radius=10  inner(lo)=2 inner(hi)=9.5      floor_ok=true ceil_ok=true
  new(2.105):       radius=10  inner(lo)=2 inner(hi)=9.5      floor_ok=true ceil_ok=true
  new(1e6):         radius=1000000 inner(lo)=2 inner(hi)=950000 floor_ok=true ceil_ok=true
  new(NaN):         radius=10  inner(lo)=2 inner(hi)=9.5      floor_ok=true ceil_ok=true
  ```
  **结论**：文档承诺的 `2.0 ..= 0.95 * radius` 频带**不可打破**。
  原因是该带本身可满足的前提是 `radius >= ~2.105`，而 `new` 与 `set_radius`
  **两个**写者都已把 `radius` 下限钳到 `MIN_RADIUS = 10.0`，所以两者不可能交叉。
  `min` 后 `max` 的顺序让频带自身的定义成为权威，这正是原注释的主张，现已**实测坐实**。
- **本轮动作**：不是「改」，而是**把这个不变量固化成穷举测试**（原注释只是断言，无测试背书）：
  - 新增 `pie_menu_inner_radius_band_is_unbreakable`

## 11.3 【取证关闭·非缺陷】跨手势序列的状态复位

- **取证**：`tap.rs:40-46` 的 `TouchEnd` 分支**先**执行
  `if self.touch_id != Some(*touch_id) { return None; }` —— **触摸 id 不匹配即返回**，

- **判定**：**设计正确，非缺陷**，无需修改。

## 12.2 【已修·根因】给门禁补上**反方向**检查（防复发）

只修表不改门禁 = 下轮复发。故给 `tools/check_capability_events_are_emitted.py`
补了**反方向**检查，与既有 `PRODUCER_ELSEWHERE`/`SHARED_PRODUCERS`/别名解析**复用同一套归属逻辑**：

- 新增 `collect_struct_declares()`：解析每个 `pub struct` 体内 `pub … : …Signal…` 字段；
- 主流程新增 `unpublished` 列表：**自己声明 ∩ 自己发射 − 已发布** 即命中；
- 排除 `DATA_SOURCE_SIGNALS`（模型侧信号）；
- 输出解释「控件发射并文档化，但 `connect_event` 回 `UnknownCommand`」。

**为什么只算「自己声明 ∩ 自己发射」**：框架噪声必须排除。
`BaseWidget` 的 `hover`/`mouse_down`/`focus_gained` 是 `BaseWidget` 声明并**由 `BaseWidget` 发射**的，
不归任何 capability 所有 —— 这把 41 个「未发布的信号声明」收敛到真正属于控件的 24 个。

**反向注入验证**（证明新检查真的抓得到缺陷）：
```

   slider: slider_pressed  (struct `Slider`)
   slider: slider_released  (struct `Slider`)

```
恢复后 → **PASS**。

## 12.3 【已修·文档与实现不符】`EventSignalBinder` 模块文档两处失实

核对 `forward_widget_events` 时发现**模块文档承诺与实现不符**（这是本轮审计顺带挖到的真实缺陷）：

1. **`event_bridge.rs:63`** 原文称 `forward_widget_events`
   「one call per control, **covering every name that control's capability publishes**」。
   **实现根本不是**：`event_bridge.rs:176-183` 只在 capability 含 `clicked` 时
   `forward_unit("clicked", …)` 并 `return 1`，**只代理 `clicked` 一个名字**。
   （方法自身的 doc 146-153 是**准确**的，是模块级 doc 说错了。）
   风险：宿主读模块文档会以为其余事件已自动接线，实际 `value_changed`/`toggled` 等
   全都要自己调 `forward_mapped` —— 于是**订阅了但永远不响**，且无从察觉。
   → 已改写为准确说明：只接 `clicked`，其余需在控件构造处用 `forward_mapped`。

2. **`event_bridge.rs:72`** 原文称「Exhaustiveness is stated by
   `tests/event_signal_bridge_test.rs`, which requires every name a capability publishes to be
   forwardable, so an event added to a capability without a forwarding site is caught」。
   **实测该测试没有这个能力**：它只断言每个已发布名字
   `event_is_subscribable(...)` 成立（**可订阅**），
   **从未检查是否真的存在对应的转发调用**。
   → 已改写为准确说明：它证明「每个已发布名字**可以**被转发（有 hub 目的地）」，
   而非「本 crate **已经**为它转发」；并明确「未转发的事件仍然是有效但惰性的」。

> 这两处属于「文档比实现承诺得多」——正是本项目原则里点名的
> 「reported success for something that did not happen」。**已修**。
