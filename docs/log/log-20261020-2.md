## 2. §0.1：`embedded` profile 不能编译（已修）

### 2.1 修复前

```text
$ cargo check --no-default-features --features embedded --lib
error[E0599]: no variant, associated function, or constant named `TabWidget`
  found for enum `WidgetKind`
   --> src/lib.rs:891:42
error[E0599]: ... `Splitter` ... src/lib.rs:905:42
error[E0599]: ... `Grid` ...     src/lib.rs:918:42
error[E0599]: ... `Dialog` ...   src/lib.rs:933:42
error: could not compile `rust_widgets` (lib) due to 4 previous errors
```

### 2.2 根因与修复

`create_tab_widget`/`create_splitter`/`create_grid_widget`/`create_dialog` 用
`#[cfg(not(alloc_frugal))]`，而 `WidgetKind::{TabWidget,Splitter,Grid,Dialog}` 用
`#[cfg(widgets_unstripped)]`。`embedded` 的 `alloc_frugal = false`、`widgets_unstripped = false`，
于是构造器存在、变体不存在。

四个构造器改为与变体相同的 `#[cfg(widgets_unstripped)]`，并逐个写明理由。`app` 模块本身是
`full_widgets`，所以 handle 调用点在 `embedded` 下不参与编译。

### 2.3 修复后

```text
$ cargo check --no-default-features --features embedded --lib
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 3.98s
```

CI 的 profile 循环（`.github/workflows/ci.yml`）已经包含
`cargo check --no-default-features --features embedded`，本轮无需新增组合。

## 3. §0.4：`create_widget_of_kind` 在没有 per-widget surface 的后端返回 0（已修）

根因是入口先走 `mount_widget_object`，它要求 `Platform::mount_surface` 成功；失败后控件已被
`unregister` 并丢弃，无法再回退。修复：

- `supports_surfaces() == false` 时**先**走 `ControlBackend::mount_widget_box`，也就是所有
  typed `create_*` 使用的同一挂载路径；
- 非 `Window` 类型要求父 id 是已挂载容器，与 `mount_named_widget` 的拒绝规则一致；
- surface 路径保持不变。

`tests/control_backend_routing_test.rs` 的 no-surface 分支从“必须返回 0”改为
“必须返回已挂载的控件 id”，这正是反馈要求的同一成功判据。

### 4.2 双击（GTK）

新增 `canvas::DoubleClickTracker`：用 `gtk::Settings` 的 `gtk-double-click-time` /
`gtk-double-click-distance`（缺失时 400 ms / 5 px）判断第二次主键按下；命中后发送
`Event::MouseDoubleClick`，否则发送普通 `MousePress`。窗口树路径（`platform_impl.rs`）和

## 5. §0.5 + 组合控件扫描（发现并修复 6 个缺陷）

### 5.1 GTK：子控件 invalidate 没有解析到窗口

`platform/linux/canvas.rs::paint_area_for` 原来只做
`host_window_for(id).unwrap_or(id)`，而 `host_window_for` 只对 **window id** 回答。子控件的
`request_repaint` 因此找不到 `window_painters`，返回 `false`，模型变了但窗口不重绘。

修复：先 `top_level_window_of(id)`，再 `host_window_for(window)`。这正是反馈 §0.5 的根因：
`list_box_clear_items`/`list_box_add_item` 成功、`list_box_item_count` 正确，但画面不更新。
macOS 的 `invalidate_surface_impl` 已有 `window_canvas_for(id)`，同一语义无需改动。

### 5.2 `StackedWidget`：所有页同时绘制

`add_widget`/`insert_widget` 只 `add_child_linked`，从未写可见性或几何；树遍历会把每个可见
子控件都画出来，于是“堆叠”控件看起来像同时展示所有子面板。

修复：新增 `sync_pages`（选中页可见、其余隐藏）与 `place_current_page`（选中页填满控件），
在增删页、切换索引、`set_geometry` 时同步。

### 5.3 `ToolBox`：页未放置 + 内容区按“容量”而不是“实际 tab 数”预留

- 与 `StackedWidget` 同样缺少页可见性/几何同步；已补 `sync_pages`/`place_current_page`。
- `content_rect` 原来用 `capacity * ITEM_HEIGHT`（容量）而不是
  `min(item_count, capacity) * ITEM_HEIGHT`。300 px 高、2 个 tab 时页从 y=256 开始、只有 44 px，
  上方 192 px 是空条带。已改为按实际 tab 数预留：页从 y=64 开始、高 236 px。

### 5.4 `CollapsiblePane`：折叠后内容仍可点击

裁剪只影响像素；命中测试看几何与 `visible`。折叠到底后子控件仍然 `visible`，因此不可见却
能接收点击。修复：`sync_content_state` 在 `open == 0` 时隐藏内容、重新打开时显示；同时把
主树路径的几何写入补到 `crate::set_widget_geometry`（此前只写 registry 路径），并在
`tick`/`set_geometry`/`set_content` 中同步。

### 5.5 `TabView`：无 registry 时内容不绘制

`TabView` 过去只在 host 设置了 registry 时绘制选中页内容；没有 registry 时内容区是纯色块。
现在无 registry 时由控件自己绘制**选中页**（带内容区裁剪与偏移），非选中页不参与该帧。
有 registry 时保持既有 `content_widget_id` + `draw_widget` 契约。

### 5.6 `DockWidget`：内容只在 registry 路径上放置

`DockWidget` 的 `Draw` 与事件转发都只在 `registry` 存在时写子控件几何；窗口树路径
（`render_frame_tree`）不会执行 `Draw` 里的放置，所以 dock 的内容停在其构造矩形。新增
`place_content()`，在 `set_widget`/`set_registry`/`set_dock_location`/`Widget::set_geometry`
时同时写 registry 与公共几何入口。

### 5.7 高级控件外观审计

用 `tools/audit_appearance.py` 与逐文件统计复查 `advanced_widgets/` 与
`container_widgets/`：

```text
=== files with a Draw impl: 183 ===
=== Draw files reading no style colour, only literals: 10 (5%) ===
```

这 10 个文件全部是媒体/图表/`widget::runtime`，**没有一个是**
`advanced_widgets/` 或 `container_widgets/` 下的控件；因此本轮请求的两类控件没有
“完全不读主题色”的外观缺陷。`TabBar`/`RibbonBar`/`Calendar`/`Dial` 等的颜色字面量都是
style 解析失败后的 fallback，不是唯一取色路径。布局/内容模型的真实缺陷集中在 §5.2–§5.5。

## 6. Tab 系列单页语义（用户第 3 项）

统一后的契约（与 wxWidgets `wxNotebook` 一致）：

1. 页是父容器的子控件，且一次只有**一个**页是 active；
2. active 页被放置到内容矩形，其余页 `visible = false`；
3. 切换标签只改变可见性/几何，不重新创建页面；
4. 隐藏页不参与绘制，也不参与命中测试（`widget_at` 跳过不可见子树）。

实现位置：

| 控件 | 实现 |
|---|---|
| `TabWidget` | 既有 `sync_pages`/`place_current_page`（2.8.11 已修），本轮回归测试保留 |
| `StackedWidget` | 新增 `sync_pages`/`place_current_page`/`set_geometry` |
| `ToolBox` | 新增 `sync_pages`/`place_current_page`/`set_geometry`，并修正 `content_rect` |
| `TabView` | 只绘制选中页；无 registry 时直接绘制，非选中页不绘制 |
| `CollapsiblePane` | 折叠态隐藏内容 |
| `DockWidget` | 内容在公共几何入口与 registry 两条路径上放置 |

**新增集成测试**（`cargo test --features desktop --test composite_handle_api_test`）：


## 7. 全局性能（用户第 4 项）

### 7.1 三项结构性改动

1. **树遍历每个节点一次 registry loan。**
   `render_frame_tree` 原来对每个节点调用 `is_visible`、`with_widget_mut`、
   `direct_children_of` 三次；每次 loan 都会把控件从 `MOUNTED` 取出、安装 4 个 loan 标记再放回。
   现在可见性、子列表、祖先裁剪和 `draw` 在同一次 `with_widget_mut` 中读取。根节点也从
   2 次 loan 降为 1 次。
2. **loan 标记从小树结构改为小向量。**
   `DISPATCHING`/`DESTROYED_DURING_DISPATCH`/`LENT_MUTATING`/`LENT_EXCLUSIVE` 从
   `BTreeSet` 改为 `IdSet`（线性扫描的 `Vec`）。这些集合的基数就是回调嵌套深度，实际为 1–2；
   容量在多次 drive 之间复用。
3. **帧缓冲移动而不是复制。**
   `render_frame`/`render_frame_incremental`/`render_frame_tree` 现在调用
   `SoftwarePaintBackend::into_frame_rgba()`，把 `front` 缓冲区 move 给调用方。1280×800 每帧
   少一次 4 MB `memcpy`（此前 `frame_rgba().to_vec()`）。

### 7.2 指针移动不再无条件全窗重绘（macOS / Windows / GTK）

`forward_mouse` 原来对每个鼠标事件都 `setNeedsDisplay: YES`。macOS 的 tracking area 会在无按键
移动时持续发送 `mouseMoved:`，因此**鼠标划过静止窗口**就会每个采样重绘整个软件帧。新增
`MousePhase::Move`：无按键移动只在 `hovered_widget()` 变化时重绘；拖拽（`Drag`）仍逐采样重绘。
控件若在 `MouseMove` 中主动调用 `request_redraw`，仍会照常 invalidate。

Win32 侧原本把所有 `WM_MOUSEMOVE` 当成 `Drag`，即每次移动都 `InvalidateRect` 整个客户区；
GTK 侧同样没有无按键分支。本轮把同一判据接到两个平台：

- Windows：新增 `windows::canvas::move_phase()`，用 `GetKeyState(VK_LBUTTON/VK_RBUTTON/VK_MBUTTON)`
  区分拖拽与悬停；`canvas.rs` 与 `types.rs` 两个鼠标入口共用它，并共用“hover 目标未变则不重绘”。
- GTK：新增 `linux::canvas::pointer_button_down(gdk::ModifierType)`（判 `BUTTON1..5_MASK`）；
  canvas 的 `motion_notify_event` 与 window 的 `paint_area` 两个入口共用它，同样只在 hover 目标
  改变时 `queue_draw`。新增单测 `motion_with_a_held_button_is_a_drag`（Linux CI 执行）。
- 无论 `Drag` 还是 `Move`，`TrackMouseEvent(TME_LEAVE)` 仍每次重新登记——否则 `WM_MOUSELEAVE`
  永远不会到达，悬停会粘在最后一个控件上（这一条是 Win32 的硬约束，不是可优化项）。
- 副产物：交叉检查发现的 `warning: variant Move is never constructed` 消失，`-D warnings` 在
  Windows 上也为 0。

### 8.1 Windows 交叉构建（补充轮）——全部实跑通过

环境：`~/.xwin` 提供 MSVC CRT + Windows SDK 10.0.26100（`crt/include`、
`sdk/include/{ucrt,um,shared}`、`sdk/lib/ucrt/x86_64`、`sdk/lib/um/x86_64`），
`llvm` 23.1.1 提供 `clang`/`llvm-lib`。`cc` crate 需要三个环境变量才能找到它们
（只改构建环境，未改 `Cargo.toml`/`build.rs`）：

```sh
export CFLAGS_x86_64_pc_windows_msvc="-isystem $(clang -print-resource-dir)/include \
  -isystem $HOME/.xwin/crt/include \
  -isystem $HOME/.xwin/sdk/include/ucrt -isystem $HOME/.xwin/sdk/include/um \
  -isystem $HOME/.xwin/sdk/include/shared"
export CC_x86_64_pc_windows_msvc=/opt/homebrew/opt/llvm/bin/clang
export AR_x86_64_pc_windows_msvc=/opt/homebrew/opt/llvm/bin/llvm-lib
```

注意 `-isystem $(clang -print-resource-dir)/include` **必须排第一**：`~/.xwin/crt/include`
里有 MSVC 自带的 `intrin.h`/`emmintrin.h`，一旦排在前面就会遮蔽 clang 的内建 intrinsic 头，
让 SSE 内联退化成外部调用。这条是链接轮才暴露的（`check` 不做代码生成，看不出来），
根因与对照实验见 §8.1.2。

```text
cargo clippy --target x86_64-pc-windows-msvc --no-default-features --features desktop --lib -- -D warnings
  Finished（0 warning）
cargo check --target x86_64-pc-windows-msvc --no-default-features --features tablet  --lib
  Finished dev 16.92s
cargo check --target x86_64-pc-windows-msvc --no-default-features --features mobile  --lib
  Finished dev  6.47s
cargo check --target x86_64-pc-windows-msvc --no-default-features --features mini    --lib
  Finished dev  4.83s
cargo check --target x86_64-pc-windows-msvc --no-default-features --features embedded --lib
  Finished dev  2.16s
cargo check --target x86_64-pc-windows-msvc --no-default-features --features desktop --all-targets
  Finished dev 20.38s
```

首次运行时暴露了一个真实缺口并已修（非环境问题）：Win32 两个鼠标入口把每个 `WM_MOUSEMOVE`
都当 `Drag`，`MousePhase::Move` 在 Windows 上是死变量——既没有悬停/拖拽区分，也让每次移动都
整窗重绘。修复见 §7.2。

这一条如果不修，`.github/workflows/ci.yml` 的 `windows-cross-check` job **会变红**：它以
`-- -D warnings` 跑 clippy，而 `MousePhase` 的定义门控（`widgets_unstripped` + Windows）在该
job 的 feature 集下成立，`variant Move is never constructed` 会直接升级为 error。

需要说明：该 job 跑在 `ubuntu-latest` 上、只做 `check`/`clippy`，且 feature 列表为
`windows desktop-runtime wgpu touch i18n controls-native controls-custom serde serde_json
advanced-widgets quality-management`——**不含 `audio`**。所以它既不会链接，也不会构建
`minimp3`；本节补充轮用 `desktop` 全特性集，覆盖面比 CI 那个 job 更宽，也因此才会碰到
§8.1.2 的问题。

#### 8.1.1 链接层验证（`lld-link`）——三档产物全部实链

`cargo check` 只产出 `.rmeta`，`cargo build --lib` 产出的是 rlib（由 `llvm-lib` 归档），
两者都不经过 `lld-link`。要真正触达链接器，必须产出 DLL/EXE。用 `--crate-type=cdylib`
让 lib 直接产出 DLL：

```sh
export CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_LINKER=/opt/homebrew/bin/lld-link
export LIB="/Users/mikewolfli/.xwin/crt/lib/x86_64;/Users/mikewolfli/.xwin/sdk/lib/ucrt/x86_64;/Users/mikewolfli/.xwin/sdk/lib/um/x86_64"
```

`LIB` 用 `;` 分隔在本机（macOS 宿主）实测可用。等价的显式形式是 target 专属
`RUSTFLAGS="-Clink-arg=/LIBPATH:…"`（target 专属，不会污染宿主构建脚本），本轮两种都跑过。

```text
$ cargo rustc --target x86_64-pc-windows-msvc --no-default-features --features mini --lib --crate-type=cdylib
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 4.73s
$ cargo rustc --target x86_64-pc-windows-msvc --no-default-features --features desktop --lib --crate-type=cdylib
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 41.72s
$ cargo test --target x86_64-pc-windows-msvc --no-default-features --features desktop --lib --no-run
    Finished `test` profile [unoptimized + debuginfo] target(s) in 11.99s
  Executable unittests src/lib.rs (target/x86_64-pc-windows-msvc/debug/deps/rust_widgets-a1fa6768220f68e6.exe)
```

产物核验（`llvm-readobj` / `llvm-pdbutil`）：

| 产物 | 大小 | 形态 | 关键证据 |
|---|---|---|---|
| `rust_widgets.dll`（mini） | 155 KB | `COFF-x86-64`, `IMAGE_FILE_DLL` | 导入 `VCRUNTIME140.dll`、`api-ms-win-crt-runtime-l1-1-0.dll` |
| `rust_widgets.dll`（desktop） | 35 MB | `COFF-x86-64`, `IMAGE_FILE_DLL` | 导入 `user32/gdi32/dwrite/COMCTL32/COMDLG32/SHELL32/combase` 全 GUI 面 |
| `rust_widgets-a1fa6768….exe` | 87 MB | `COFF-x86-64`, `IMAGE_SUBSYSTEM_WINDOWS_CUI` | 导入 `dxgi/opengl32/dwrite/setupapi/bcrypt`（wgpu + 平台后端） |

链接器身份不是推断：三份 PDB 的 GUID 尾部都是 `4C4C44205044422E`，即 ASCII `"LLD PDB."`
——这是 `lld` 写 PDB 的固定签名（MSVC `link.exe` 用时间戳 GUID）；PE 的
`MajorLinkerVersion = 14` 是 lld 对 MSVC 14 的兼容值。导入表里出现 `VCRUNTIME140.dll` /
`api-ms-win-crt-*` 则证明 `~/.xwin` 的 CRT 导入库确实被解析到。

**口径：`link-verified`（链接成功、导入表正确），不是 `runtime-verified`**——本机没有
Windows 主机或 VM，`.exe` 未被执行。

#### 8.1.2 链接轮暴露的真实缺陷：`minimp3-sys` 的 SSE 内联失效

`--no-run` 的测试 harness 链接首跑失败：

```text
lld-link: error: undefined symbol: _mm_packs_epi32
  >>> referenced by minimp3.h:1513
  >>> libminimp3_sys-*.rlib(db3b6bfb95261072-minimp3.o):(mp3d_synth)
lld-link: error: undefined symbol: _mm_extract_epi16
  >>> referenced by minimp3.h:1515
...
error: could not compile `rust_widgets` (lib test) due to 1 previous error
```

根因（A/B 对照实验定位，非猜测）：

- `~/.xwin/crt/include` 里带 **MSVC 工具链自带的 `intrin.h` / `emmintrin.h`**；
- 最初的 `CFLAGS_…` 把它放在 `-isystem` **首位**，于是 `#include <intrin.h>` 命中 MSVC 版本；
- MSVC 的 `intrin.h` 里 `_mm_packs_epi32` 等只是**声明**，clang 不把它们当内建 intrinsic，
  于是生成外部调用而不是内联指令；这些符号在 msvc 运行库里不存在 → 未定义。

对照实验（同一份 `minimp3.c`，只改 `-isystem` 顺序）：

```text
A（xwin/crt/include 在前）→ llvm-nm 报 13 个 U _mm_*：
    _mm_add_ps _mm_cvtps_epi32 _mm_extract_epi16 _mm_loadu_ps _mm_max_ps _mm_min_ps
    _mm_mul_ps _mm_packs_epi32 _mm_set_ps1 _mm_shuffle_ps _mm_storel_pi _mm_storeu_ps _mm_sub_ps
B（clang 资源头在前）      → 0 个 U _mm_*
```

修复只改环境变量（未改 `Cargo.toml`/`build.rs`，符合原则 #43）：把 clang 自己的资源头目录
放到 `-isystem` 最前（形式见 §8.1 的 `CFLAGS` 块），并清掉被缓存的 build-script 输出：

```sh
cargo clean -p minimp3-sys --target x86_64-pc-windows-msvc
```

修复后 `--no-run` 一次通过（见 §8.1.1）。

**为什么之前一直没发现**：`cargo check` 不做代码生成，内建 intrinsic 的内联与降级差异完全
不可见；而 CI 的 `windows-cross-check` 既不链接、也不含 `audio`，所以这条路径从未被执行。
它不是产品缺陷，而是“非 Windows 宿主 + clang + xwin + `desktop` 全特性”这一组合的构
建陷阱，记在此处以免下轮重蹈。

改序后回跑既有门控，确认没有回退（`cargo check` 期间 cc 仍会执行 build script，所以这一步
必要）：

```text
cargo check --target x86_64-pc-windows-msvc --no-default-features --features "windows desktop-runtime wgpu touch i18n controls-native controls-custom serde serde_json advanced-widgets quality-management"
  Finished dev 12.43s
cargo clippy（同上 feature 集）-- -D warnings
  Finished（0 warning）
cargo check --target x86_64-pc-windows-msvc --no-default-features --features desktop --all-targets
  Finished dev 6.26s
```

### 8.2 Linux / GTK 交叉检查（补充轮）——全部实跑通过

本机已有 `gtk+3 3.24.52` 与 `pkg-config`，因此 GTK 后端可以真正类型检查，不再只有语法证据。
两个障碍及解法（未改 `Cargo.toml`/`build.rs`）：

1. `pkg-config` 拒绝交叉编译 → `PKG_CONFIG_ALLOW_CROSS=1`。
2. 本机 `gdk-3.0.pc` 是 macOS 版本，带 `-Wl,-framework,Cocoa`，linux 目标拒收 →
   `tools/pkgconfig_linux_cross_shim.sh` 在 pkg-config 输出上过滤这些标志。
   **只用于 `check`/`clippy`，不用于 `build`。**

```sh
export PKG_CONFIG_ALLOW_CROSS=1
export PKG_CONFIG="$PWD/tools/pkgconfig_linux_cross_shim.sh"
```

```text
cargo check  --target x86_64-unknown-linux-gnu --no-default-features --features "tablet,gtk-native" --lib
  Finished dev 12.29s
cargo clippy --target x86_64-unknown-linux-gnu --no-default-features --features "tablet,gtk-native" --lib -- -D warnings
  Finished（0 warning）
cargo check  --target x86_64-unknown-linux-gnu --no-default-features --features "mobile,gtk-native" --lib
  Finished dev  6.66s
```

为什么用 `tablet` 而不是 `desktop`：`desktop` 包含 `audio` → `minimp3_fixed`，它的 build script 需要
**目标平台**的 C 头文件（Linux 的 libc），本机没有 Linux sysroot。而 `src/platform/linux/*.rs`
里的 feature 门控只有 `gtk-native` 与 `touch` 两种，`tablet` 两者都开，所以 `tablet,gtk-native`
编译到的 GTK 文件集合与 `desktop` 相同。

**仍未覆盖（如实记录）：**

- ⚠️ `--all-targets` 在 linux 目标上不可用：dev-dependency `criterion` → `alloca` 需要
  `x86_64-linux-gnu-gcc`。因此新增的 GTK 单测 `motion_with_a_held_button_is_a_drag` 在本机只能
  靠 `cargo fmt` 校验语法；实际编译与执行由 `linux-gtk` job 覆盖（它先
  `apt-get install libgtk-3-dev`，再跑 `cargo test --features "desktop,gtk-native"`）。
- ⚠️ Windows 只到链接层（§8.1.1），`.exe`/`.dll` 未在 Windows 主机或 VM 上执行；本机无 Windows
  运行环境，故不能声称 `runtime-verified`。
- ⚠️ 两个平台都没有真实窗口（GUI）运行证据：本机是 macOS，无 Linux 桌面会话，Windows 无法启动。

## 10. 版本号：2.8.11 → 2.8.12

本轮改动收尾时把 crate 版本升到 `2.8.12`。口径由仓库自带门禁
`tools/check_version_consistency.sh` 定义（[1] `Cargo.toml`；[2] 20 份发布文档必须点名当前
版本；[3] 两份 CHANGELOG 的最新条目必须是当前版本；[4] 4 个 lockfile 必须钉住当前版本），
所以按这四项一起改：
