## 1. §十一 macOS：剪贴板承载“应用自定义 MIME 类型”（cocoa + objc2）

### 1.1 实测发现的平台事实（与反馈的假设不同，必须记下来）

反馈建议“macOS（`NSPasteboard` 的自定义 type）后端以各自的原生机制实现”，隐含“把 MIME 名原样当 pasteboard
type 名写进去”。**实机证实这条假设不成立**：macOS 的 pasteboard type 是 **UTI（Uniform Type Identifier）**，
现代 `NSPasteboardItem` API（`setData:forType:` + `writeObjects:`）会校验并**拒绝**不是合法 UTI 的字符串。

探针枚举（临时脚本，见 §7 的“枚举证据”，已删除）：

| 候选 type 字符串 | `NSPasteboardItem setData:forType:` | legacy `declareTypes:`+`setData:forType:` |
|---|---|---|
| `application/vnd.rustage.nodes+json` | ❌ `NO`（AppKit: `not a valid UTI string`） | ✅ `YES`，`dataForType:` 原样字节读回 |
| `application/vnd.rustage.nodes` | ❌ `NO` | ✅ `YES` |
| `vnd.rustage.nodes` | ✅ `YES` | ✅ `YES` |
| `com.rustage.nodes+json` | ❌ `NO` | ✅ `YES` |
| `com.rustage.nodes.json` | ✅ `YES` | ✅ `YES` |
| `text/html` | ❌ `NO` | ✅ `YES` |
| `public.html` | ✅ `YES` | ✅ `YES` |

结论（实测，不是推断）：**MIME（含 `/`、`+`）不是合法 UTI**，因此 item API 会拒绝原样 MIME 名；
而 `NSPasteboard` 自身的 **legacy `declareTypes:owner:` / `setData:forType:` / `dataForType:`** 通道
**接受任意 type 字符串并逐字节往返**。这正是“把调用方的类型名原样承载”所需的机制。

### 1.2 落点

**cocoa 后端**（`src/platform/clipboard_stubs.rs::macos::MacOsClipboard`，即 `desktop` 构建下
`MacOSPlatform::clipboard_backend()` 返回的实现）：

1. `set_contents(ClipboardContent::Custom { content_type, data })` 改走 pasteboard 自身的
   `declareTypes:owner:` + `setData:forType:`（不再经 `NSPasteboardItem`），使 MIME 名**原样**成为 pasteboard type。
2. 新增 `get_contents_for_type(&str)` 覆写：`text/plain` / `text/html` 走各自 UTI 的既有读取；**其他类型**
   （含应用自定义 MIME）走 pasteboard 自身的 `dataForType:`，字节逐字节取回。
3. `has_format(&str)` 增补 `pasteboard_type_name` 映射：`text/plain→public.utf8-plain-text`、
   `text/html→public.html`，其余原样——修正了一处既有缺口：库的 `content_type()` 回答 `text/plain`，
   而此前 `has_format("text/plain")` 直接拿 MIME 去问 pasteboard，因而在真有文本时也返回 `false`。

**objc2 后端**（`clipboard_stubs::objc2_macos::MacOsObjc2Clipboard`）：同一机制、同一 `pasteboard_type_name`
映射（原则 #2 冰山 / #101 单一机制）。两者差异只在消息发送的绑定（`objc` vs `objc2`）。

### 1.3 证据（真会话探针）

`examples/probe_clipboard_custom.rs` 扩展为在 macOS（cocoa 或 objc2）上暂存，实测：

```text
$ RW_GUI_PROBE_OK=1 cargo run --no-default-features --features desktop --example probe_clipboard_custom
backend: cocoa
A. set_contents_with_type / has_format      -> true / true   (OK, OK)
B. get_contents_for_type                    -> 46 byte(s), 字节逐字节一致 (OK);  text/plain -> None (OK)
C. set_contents(Custom)                     -> true, 按名可读, 字节一致 (OK, OK)
=== 0 check(s) failed ===

$ RW_GUI_PROBE_OK=1 cargo run --no-default-features --features macos --example probe_clipboard_custom
backend: macos-objc2-preview
=== 0 check(s) failed ===
```

**修复前的对照**：同一探针在 cocoa 上（改前实现）5 项全 FAIL，AppKit 逐条打印
`'application/vnd.rustage.nodes+json' is not a valid UTI string. Cannot set data for an invalid UTI.`
——即“按反馈字面实现（item API 直写 MIME）”会失败，故采用了上表的 legacy 通道。

## 2. §十二 macOS：显示器枚举的实机核查（抓到并修掉一处真缺陷）

### 2.1 `displays()` 在真机上成立

```text
$ RW_GUI_PROBE_OK=1 cargo run --no-default-features --features desktop --example probe_displays
backend: cocoa
A. displays()          count: 1  id=1 bounds=(0,0) 1710x1112 work=(0,85) 1710x983 scale=2 primary=true
B. display_of_window   window … is on display Some(DisplayId(1))
C. display_generation  10264847135600646622（非 0）
=== 0 check(s) failed ===
```

`scale=2`（Retina，**不是恒 1.0**）、工作区比边界矮 129px（真实菜单栏），窗口归属与枚举一致——即反馈
“真实会话上 `displays()` 至少返回一项、能把窗口对到某块屏、改 DPI 后 `scale` 如实变化”的读数判据在本机成立。

### 2.2 真缺陷（实机才暴露）：`display_of_window` 查错了 id 空间

**现象**：`displays()` 正常，但 `display_of_window(window)` 对刚创建并显示的窗口返回 `None`
（`probe_displays` 的 B 项 FAIL）。

**根因（源码 + 实测定位）**：cocoa 的 `display_of_window` 直接用请求 id 去查本后端句柄表
`self.handles`，而该表**以 platform id 为键**；宿主手里的却是 **widget-registry id**。实测该表只有 `[1]`
（platform 窗口 id），而宿主持有的是 `6000285942072475648…`（widget id），故查不到。上一轮（`log-20261016-1.md`
§5.1）只做了**跨编译**验证，**没有**运行，因此这个纯运行期缺陷当时不可见。

**修法（镜像 Windows 后端，原则 #2/#101）**：新增 `translate_widget_id`（`not(alloc_frugal)` 下取
`widget::runtime::host_window_for`，`alloc_frugal` 下返回 `None`），`display_of_window` 先试 platform id、
再经它转 widget id。与 Linux/GTK、Windows 的同一方法同形（两者都做了这一步，cocoa 独缺）。

### 2.3 附带修复：上一轮引入的 `mini,cocoa-legacy` 编译回归

`displays.rs` / `platform_impl.rs::displays` / 剪贴板的 `Vec<u8>` 读入口都用到了 `Vec`，而
`mini`（`#![no_std]`）移除 prelude，且 `clipboard_stubs::macos` 文档声明其“reachable from `mini,cocoa-legacy`”。
上一轮只按 `desktop` 编译，未覆盖该组合。实测修复前后：

```text
修复前  cargo check --lib --no-default-features --features "mini,cocoa-legacy"
        error[E0425]/[E0433]: cannot find type `Vec` in this scope  ×6（displays.rs / platform_impl.rs / clipboard_stubs.rs）
修复后  Finished dev … （零错误、零警告）；--features "mini,macos" 同样 Finished
```

修法是补 `use crate::compat::Vec;`（`compat` 桥，`String` 已是同样写法）。

## 3. §十.2 cocoa 有界会话“不 tick”（本轮修复）

### 3.1 复现与根因

反馈：`--launch --exit-after-ms 300` 在 macOS 上“一次帧回调都没有”，进程 20s 后仍在跑。实机复核发现：

1. cocoa 的帧回调曾是**按窗口**装的重复 `NSTimer`（在 `create_window` 里，随窗口的 resize delegate 装），
   因此**没有任何窗口的会话根本没有 tick**，排队的停止请求（`platform::stop`）没有读者。
2. 即便有窗口，停止也要等某一帧真的到来。修复前实测跨线程停止的时延约 **2.19s**（会话期限 400ms 之后还多
   1.8s），说明“靠某一帧兑现停止”不可靠。

### 3.2 修法

1. **把帧心跳从“按窗口”搬到“按循环”**（`src/platform/macos/canvas.rs` + `platform_impl.rs::run`）：
   新增 `frame_tick_class`（`RustWidgetsFrameTimer`，只含 `tick:`→`drive_frame`）与
   `install_frame_heartbeat()`，由 `run()` 在进入 `-[NSApplication run]` **之前**无条件安装一次。
   `install_resize_delegate` 保留（只负责 `windowDidResize:`），**不再**装 timer——保证全进程**只有一个**帧驱动
   （原则 #101；两个 timer 会把动画按双倍速率推进）。
2. **`quit()` 补唤醒事件**：`-[NSApplication stop:]` 只置一个标志，循环下次从 `nextEventMatchingMask:`
   返回时才看它；当循环忙于服务 timer（正是帧心跳造成的）而非等待事件时，这个返回可能被无限拖延。故在
   `stop:` 之后 `postEvent:`（`NSEventTypeApplicationDefined`）一个事件唤醒循环——这是 `stop:` 在该情形下的
   文档化配套动作。

### 3.3 证据（真会话）

```text
有窗口（probe_cross_thread_quit，B 段，watcher 400ms 请求停止）：
  修复前  run() returned after 2.186s
  修复后  run() returned after 0.417s     # 期限 + 一帧
自调度（同探针 E 段，schedule_on_main(300ms, quit)）：
  修复后  run() returned after 0.303s
无任何窗口（临时脚本，已删除）：
  修复后  no-window run() returned after 0.306s   # loop_has_ticked=true；修复前此会话根本不 tick
```

即反馈判据“约期限内退出、`startup-session` 变 ready”在可可后端成立；无窗口会话也不再是不可停止的窗口。

## 9. 未覆盖与边界（逐条写明，不用“只剩具名项”糊过去）

1. **物理拔屏 / 改 DPI 的现场判据**：需人在屏前（拔插副屏、切主屏、改 DPI）。本轮证明“枚举出一块真实屏
   （含 `scale=2`）、窗口对到它、版本号可读”；**未**证明“物理拔掉副屏后列表变短”。
2. **§十一 的其余平台**：iOS（`UIPasteboard`）/Android（`ClipboardManager`）/HarmonyOS（`OH_Pasteboard` + UDMF）
   的**自定义**类型承载仍**如实拒绝**（`set_contents_with_type` 返回 `false`，见各后端 `other =>` 分支）。
   需要各自一轮 + 实机/模拟器，未凭 API 名盲写（原则 #1/#38）。
3. **objc2 后端的 `displays()`**：仍走 trait 诚实默认（空列表）。该后端是迁移预览、其
   `PlatformCapabilities::dpi_scaling` 本就为 `false`，且当前无消费者；按原则 #37/#53 以“继承诚实默认”表达能力缺失，
   **不**在无消费者的预览后端上新增未经实机验证的 `NSScreen` FFI。解除条件：objc2 成为默认后端或有消费者时一并实现。
4. **枚举脚本已删除**：§1.1 的临时脚本未留在仓库；“原样保留任意 MIME 名”这一平台事实由 `clipboard_stubs.rs`
   的两处模块注释记录，避免后人再以 item API 直写 MIME 而踩同一坑。
5. **rustage 侧迁移不在本轮**：本文件只做上游（rust-widgets）改进；re-pin 后的宿主迁移另议。

* **§十.2 闭合**：cocoa 帧心跳改为进程级（无窗口也 tick），`quit()` 补唤醒事件——有界会话在期限后一帧内结束
  （0.417s/0.303s/无窗口 0.306s），且全进程仍只有一个帧驱动；
* **附带修复上一轮引入的编译回归**：`mini,cocoa-legacy` / `mini,macos` 因缺失 `compat::Vec` 而 6 处 `E0425/E0433`，现已零错误零警告；
* **不改 ABI、不新增能力位、不破坏既有 API**；全量单测 **7359/0**、`clippy --all-targets`（desktop）与
  `clippy --lib`（macos）零警告、三份真会话探针 0 失败。

## 11. 演示时发现并修复的上游既有缺陷：cocoa 没有窗口级绘制器（窗口白板）

本节不是反馈条目，是用户要求“显示一个让我看看”时在**实机**上暴露的：macOS cocoa 窗口打开后是**一块白板**，
标签/按钮一个都不显示。

### 11.1 根因（这是早先已记录的缺口，不是本轮引入）

`docs/log/archive/log-20260930-3.md`（2026-09-30）原文就记着：

> **macOS cocoa / objc2 无窗口级绘制器**：`grep render_frame_tree src/platform/macos*/` **零匹配**。唯一会画的是
> `mount_surface` 里创建的 canvas 视图… 即 macOS 下“创建控件但不 mount surface”也会**白板**… **无 Apple 主机，
> 本机无法编译/验证**。

2026-10-03 只给 **objc2** 后端补上了窗口绘制器（`log-20261003-1.md` P-01：`create_ns_window` 把画布装为
`contentView`）；**cocoa 一直没补**。Linux/GTK（`connect_draw`）与 Windows（`WM_PAINT`→`paint_window_tree`）都
有——`grep -rn render_frame_tree src/platform/` 的四个命中正是这四个后端（本轮修完 cocoa 后的结果）。

具体到代码：`create_window` 装的是**普通 `NSView`** 作 contentView，而 `draw_rect` 只会
`render_frame_cached(widget_id)`（**单个**控件），从不走 `render_frame_tree`（走子列表）。普通控件
（`create_button`/`create_label`…）走 custom 控制后端 → `adopt_widget_box` → 只是**树节点**、不是 mounted surface，
于是谁都不画它们。

### 11.2 修法（照 objc2 同形，原则 #2/#101）

1. `canvas.rs` 新增窗口画布：关联对象上的 “window canvas” 标记 + `window_canvases()` 侧表（按 **host** id 键，
   与 surface 的 `mounted_views` **分开**，避免 `resize/unmount_surface` 误触窗口画布）+ `make_window_canvas`。
2. `draw_rect` 分叉：窗口画布 → 经 `widget_id_for_host_window` 翻译后 `render_frame_tree`（画窗口自身 chrome + 全部
   子控件）；mounted surface 仍 `render_frame_cached`（不变）。
3. `invalidate_surface_impl` 增补解析：一个 repaint 请求若命中的是**窗口/窗口内任一控件**（它们都没有自己的 canvas），
   经 `host_window_for`/`top_level_window_of` 归到窗口画布——否则库侧 `request_repaint_subtree` 的请求**落到空气里**。
4. `create_window` 改在 `register_handle`（拿到 id）之后把画布装为 contentView；`mini/embedded`（无 canvas）仍装普通
   `NSView`（那条路径的 `NSView` 导入按 `cfg` 收窄）。

### 11.3 证据（真机）

```text
$ RW_GUI_PROBE_OK=1 … --example show_macos_window        # 本机 detached 运行
backend: cocoa
window shown: 6000285942072475648
window tree frame: 1276800 bytes, non-white pixels=319200 distinct_rgb=138
```

`760×420×4 = 1 276 800` 字节；**每个像素都被画**（319200 = 全部像素），**138 种不同 RGB**——即窗口背景、标签文字、
按钮边框都在帧里。这正是窗口画布逐像素 blit 的那一帧；用户现场确认“现在正常了”（修复前为白板，`probe_displays` /
`probe_cross_thread_quit` 当时只验证到“窗口被创建”，未验证“窗口有内容”）。

回归面：`tests/window_tree_paints_visible_controls_test.rs` **5/5**（库层 `render_frame_tree` 含子控件）；
全量单测 **7359/0**；`clippy --all-targets`（desktop）零警告；`check_apple_thread_safety` /
`check_no_native_control_creation` / `check_single_frame_driver` 均 PASS。

### 11.4 边界

`show_macos_window.rs` 是**演示用 example**（非反馈交付），可删。四个“窗口级绘制器”后端之外的后端见 §9 的第 3 条
与下一条：那些是 **host-pull** 模型（宿主自己按 mounted surface 渲染），机制不同，本轮未触碰。

### 11.5 “所有平台都能显示吗？”——逐后端口径（用户提问）

| 后端 | 机制 | 普通 `create_*` 控件能否显示 | 依据 |
|---|---|---|---|
| Linux/GTK | 窗口级绘制器（GDK `connect_draw`→`render_frame_tree`） | ✅ | 代码 + 门禁 |
| Windows | 窗口级绘制器（`WM_PAINT`→`paint_window_tree`→`render_frame_tree`） | ✅ | 代码 |
| macOS objc2 | 窗口级绘制器（画布为 contentView，`is_window`） | ✅ | 代码 |
| macOS cocoa | 窗口级绘制器（本轮补上） | ✅ | **本机实跑 + 用户现场确认** |
| Android / iOS / HarmonyOS+mobile | **host-pull**：库不画，宿主拥有像素；库按 **mounted surface** 逐个出帧 | ⚠️ 仅宿主显式 `mount_surface` 的控件；C ABI 无“整窗”入口 | `src/platform/*/status.md` + `rw_render_surface_frame` 实现 |
| Wayland / WASM | 同上（host-pull，`render_frame_cached` 逐 surface） | ⚠️ 同上 | 同上 |
| portable / mini / embedded | 无窗口（surface-only / 无后端） | ⛔ 不适用 | `supports_surfaces`/profile |

**结论（诚实口径）**：**不是“所有平台用同一条路径都能显示”**。四个桌面窗口后端已能显示整棵子树；
**host-pull** 后端（Android/iOS/Harmony/Wayland/WASM）只能显示**被显式 mount 的那个控件**——因为 C ABI 只有
`rw_render_surface_frame`（`render_frame_cached`，**单控件**），**没有**渲染整窗树的入口；它们的 `status.md` 也就把
“逐个 mount_surface 再逐个 render”写成宿主契约。手机端本机**无设备/模拟器**，那几行是**代码 + ABI 取证**，不是设备实测。

若要让手机/Web/Wayland 也“一个窗口画整棵树”，需新增一条 ABI（如 `rw_render_window_frame` → `render_frame_tree`）
并各自一轮验证；本轮**未做**，不在此计闭合。
