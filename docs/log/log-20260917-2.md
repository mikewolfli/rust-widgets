## 2. Phase B — 对外能力可达（三条线的核心）

### B-1 ✅ 通用构造入口（一次接通全部 kind）

新增两个 C ABI 函数：

```c
uint64_t rw_create_widget_of_kind(uint64_t parent, const char* kind_name,
                                  const char* text, int x, int y,
                                  unsigned int w, unsigned int h);
unsigned int rw_widget_kind_names(char* out, unsigned int cap);
```

**不暴露 `WidgetKind` 整数判别值**（§B-1 的设计决定已落地）：`kind_name` 是稳定字符串契约。

**执行中的关键发现（真缺陷）**：`CustomPaintControlBackend` **根本没有覆写** trait 的
name-based `create_widget`（trait 默认返回 `0`），只有 `native.rs` 实现了它且只认 23 个名字。
本轮在 `src/control_backend/custom/create_widgets.rs` 补上覆写，转发到 `WidgetFactory`。

**由此又抓出第二个真缺陷**：第一版实现经 `mount_widget_of_kind(kind)` 上溯，
而 `mount_widget_of_kind` 把 **kind 反解为单个 canonical 名**——
`chart` / `timeline_widget` / `gantt_widget` 共享 `WidgetKind::Chart`，
因此 `rw_create_widget_of_kind(.., "timeline_widget", ..)` **造出来的是 `chart`**。

由新测试 `c_abi_widget_property_names_lists_the_controls_contract` 抓出：

```text
item_count must be published: chart_type point_count label_count enabled visible tooltip geometry
```

**修复**：新增 `mount_named_widget(name, ...)`，创建路径保留**调用方给出的名字**而不是 kind。
`mount_widget_of_kind` 改为委托（typed `create_*` 方法里 kind 就是完整请求，语义不变）。

### B-2 ✅ 通用属性层（一次接通全部属性名）

```c
typedef enum { RW_VALUE_NULL=0, RW_VALUE_BOOL=1, RW_VALUE_INT=2,
               RW_VALUE_UINT=3, RW_VALUE_FLOAT=4, RW_VALUE_STRING=5 } rw_value_kind;
bool rw_get_widget_property(uint64_t widget_id, const char* name,
                            int* out_kind, int64_t* out_num, char** out_str);
bool rw_set_widget_property(uint64_t widget_id, const char* name,
                            int kind, int64_t num, const char* str);
unsigned int rw_widget_property_names(uint64_t widget_id, char* out, unsigned int cap);
```

- 转发到既有的 `read_widget_property_by_id` / `write_widget_property_by_id`；
- **不用 C union**：`out_num` / `out_str` 独立，调用方可忽略不需要的那个（§8.2 风险缓解已落地）；
- `FLOAT` 以 **bit pattern** 走同一个 `int64_t`（`f64::to_bits`），调用方重解释而非转换，
  避免精度丢失；
- 错误经新函数 `error::ffi::record_capability_error` 映射到既有 `rw_error_code` /
  `rw_error_message`（原先不存在这个映射，本轮补上，见 §3.2）。

### B-3 ⬜ 集合与布局 ABI —— **本轮未做**

`rw_widget_list_add` / `rw_widget_set_layout` / `rw_widget_set_scroll_position` 未新增。
理由（诚实登记，不冒充完成）：这三项**能经 B-2 的通用属性层做到一部分**
（如 `Meter::set_range` 型的集合操作在 §3 已改为逐属性可达），
但"加一项"本质是**动作而非赋值**，不宜硬塞进属性层；
正确形状需要单独设计（`rw_widget_list_add` 一族），属独立工作项。
触发条件：出现真实 C/Python/Java 消费者需要动态填充列表。

### B-4 ✅ 样式与主题入口

```c
bool rw_set_theme(const char* name);
unsigned int rw_theme_names(char* out, unsigned int cap);
void rw_set_high_contrast(int mode);
```

**执行中的关键改进**：主题切换必须**对已存在的控件生效**，而非只影响此后创建的控件。
为此新增：

- `widget::runtime::for_each_mounted_widget()` —— 遍历本线程已挂载控件；
- `crate::reapply_active_theme()` —— 对全部在册控件重跑 `theme::apply_active_theme`。

`rw_set_theme` / `rw_set_high_contrast` 成功后调用它，因此主题切换**当场可见**。

**不暴露 `rw_register_stylesheet`（CSS 文本）**：理由见 `blue16.md` §6.2，本轮维持该判例。

### E-3 ✅ 新增 `check_widget_registration_fidelity.sh`

**目的**：机器阻断"有 `pub struct` + `pub use`、却未注册进工厂"的控件。

**判据（与 §12.7 的第三次更正一致）**：不用后缀启发式（会误报
`ToastItem` / `ChartSeries` / `WebEngineSettings`），而是用 **`WidgetKind` 枚举本身**
作为"这是控件"的权威清单。每个 kind 必须命中且仅命中三态之一：

| 态 | 判据 |
|---|---|
| `Registered` | 工厂的 canonical 名或 alias 携带它（**由编译后的注册表判定**，非 grep 源码）|
| `AliasOf(other)` | `src/widget/mod.rs` 的 `pub type X = Y;`，且 `Y` 已 `Registered` |
| `BaseOrChild(role)` | `src/widget/kind.rs` 中变体旁的 `// kind-role: base\|child` 标记 |

**关键设计决定**：`Registered` 由**运行中的注册表**回答，不是 grep 源码——
源码里一个只在注释或 `#[cfg]` 死分支里出现的名字会被 grep 误判为"已注册"，
而"看起来注册了但实际没有"正是本缺陷的成因。
实现方式：`examples/widget_reachability.rs` 打印一份 JSON 注册表报告，门禁读取它。

**`kind-role` 标记为何必须显式**：当前"这是基类"只存在于开发者头脑与注释里，
机器无法区分"有意不注册"与"忘了注册"——这正是 §12.7 连错两次的根本原因。

**结果**：

```bash
$ bash tools/check_widget_registration_fidelity.sh
✅ widget registration fidelity: 167 kinds classified (436 registered names, 23 aliases, 14 role markers)
```

**反例注入验证（原则 #19）**，两种注入方式都做了：

```bash
# ① 删掉一条 pub type 别名
$ sed -i 's|^pub type ColumnView = TreeView;|// OUT|' src/widget/mod.rs
$ bash tools/check_widget_registration_fidelity.sh
❌ ColumnView (no registration, alias or kind-role marker)

# ② 新增一个未归类的 kind
$ sed -i 's|^    GridTable,|    GridTable,\n    ProbeKind,|' src/widget/kind.rs
$ cargo check --example widget_reachability
error[E0004]: non-exhaustive patterns: `WidgetKind::ProbeKind` not covered
```

**第 ② 项是刻意加固的**：`all_kinds()` 是 `vec!`，加变体不会编译失败（静默逃过门禁）。
因此 `examples/widget_reachability.rs` 里另写了一个 **`match`**，
使"加了 kind 不归类"变成**硬编译错误**——这正是 §12.7 想要的"机器可读标记"。

### E-4 ✅ 双向断言（规则 #77）

`schema_and_contract_publish_the_same_names` 从**单向**（只查 `published ⊆ declared`）
改为**双向**（同时查 `declared ⊆ published`，跳过 `readable:false && writable:false`
的别名占位条目）。

**双向断言立刻抓出 18 个幻影属性**（`blue16.md` §11.3 #1 的实例，比我预估的多）：

```text

properties that cannot be read or written (widget, property):
```

**逐项处置（方式二选一，不得悬置）**：

| 类 | 处置 | 例 |
|---|---|---|
| **实现缺失** | **补实现**（控件本有该状态，只是访问器没发布） | `Meter` 有 `set_range(min,max)` 却无 `minimum()`/`maximum()` → **补上两个访问器**；`ToolBar` 有 `items()` → 发布 `item_count`；`Chip` 有 `focused_index()`/`selected_ids()` → 发布；`GridWidget` 的 6 个访问器全部存在却未发布 → 全部发布 |

**顺带修掉 4 处 `UnsupportedOnWidget` 误用**（`blue16.md` §11.3 #7 登记项）：

## 4. Phase C-1 — 强制可达性表态（规则 #72）

新增门禁 `check_module_reachability.sh`：解析每个模块文档的 `# Reachability` 段落，
- 声称「Production callers」→ 段落里的每个 `file:line` 必须**存在**且该文件**确实提到该模块名**；

- 声称「Reserved」→ 必须给出**非空理由**（≥15 字符）；

## 11. 方法论记录（原则 #64：写错就地更正并保留）

### 11.1 我自己的 9 处不准确表态被新门禁抓出

见 §4。**教训**：可达性证据不能凭印象写。门禁要求 `file:line` **存在且该文件真的提到模块名**，
这比"我记得它有消费者"强得多——它把"我以为是"变成"可复核"。

### 11.2 C++ 头文件的判据第一版写错

`check_binding_symbol_coverage.sh` 第一版只做纯文本 grep，把 C++ 头报成"缺 6 个符号"。
**但 C++ 头是故意不重复声明的**（重复声明正是缺陷来源），符号经 `#include` 可达。
**判据修正**为跟随 `#include`。

**教训**：门禁的判据必须与它所检查的设计一致。"文本里出现"与"对该绑定用户可达"不是同一件事。

### 11.3 `mount_widget_of_kind` 的 kind→name 反解是个隐藏陷阱

第一版 B-1 实现走 `mount_widget_of_kind(kind)`，测试立刻报出
`timeline_widget` 回答的是 `chart` 的属性。
**根因**：共享 kind 的控件反解只能得到一个名字。
**教训**：当"名字"是调用方的输入时，整条链路都必须保留它，任何一处反解都会丢失信息。

### 11.5 ❌ 我关于 `index` 与 `json::element` 重复的主张——**复跑后推翻**

我在给用户的建议里提出：

> 「`index`（218 行，登记为 Reserved）与 `element.rs` 的 `widget_by_name` 是同一件事的两种实现——这才是本轮该合并的重复对。」

**复跑后推翻。** 两者方向不同，且**都是 `loader.rs` 的同一次加载里在用的**：

```rust
// src/json/loader.rs:68-69 —— 两个容器同时建立
let mut registry = crate::index::WidgetRegistry::new();   // id → metadata
let mut binding  = BoundJsonLayout::new();                // name → id

// src/json/loader.rs:205,213 —— 两个容器同时写入
registry.register(crate::index::WidgetEntry { id, kind, parent, label });
if !id_str.is_empty() { binding.register(id_str, widget_id); }
```

| | `index::WidgetRegistry` | `json::BoundJsonLayout` |
|---|---|---|
| 键 | `ObjectId` | `String`（JSON 的 `"id"`）|
| 值 | `WidgetEntry { kind, parent, label }` | `ObjectId` |
| 回答的问题 | 「这个 id 是什么控件、父是谁」| 「名字叫 btn 的控件是哪個 id」|
| 反向索引 | 有（`by_kind`、`children_of`）| 无 |

`BoundJsonLayout::widget_by_name` 需要的是 **name → id**，`WidgetRegistry` 根本没有名字索引
（`WidgetEntry.label` 是给人看的字符串，不是查找键，且它在 loader 里被写成
`format!("{widget_type}_{widget_id}")`——id 为空时才用）。
要合并，得给 `WidgetRegistry` 加一个 `name → id` 索引，那是**给一个模块塞进另一个模块的职责**，
而非消除重复（违反原则 #51：无真实重复就不接入）。

**教训（第二次同型错误）**：我在 §11.3 刚写下「当『名字』是调用方的输入时，任何一处反解都会丢失信息」，
随即就用「名字有点像」把两个服务**不同方向**的结构当成重复。
**判据必须是「是否真的回答了同一个问题」，而不是「名字是否相似」。**

### 11.6 ❌ 我关于 `index` 有重复 `WidgetKind` 枚举的怀疑——**读源码后推翻**

`src/index/registry.rs:16` 写的是：

```rust
pub use crate::widget::WidgetKind;
```

即**上层 re-export 下层定义**——正是原则 #54 要求的形态，没有副本。

### 20.1 用户追问：「是否是 json 和 css 的功能重复？」——**复跑后答：不重复**

```rust
// src/widget/widget_trait.rs:527 —— apply_css 只是薄转发
fn apply_css(&mut self, css: &str, class: Option<&str>) -> Result<(), String> {
```

## 42. 新增 3 个控件（`WidgetKind` 171 → **174**）

### 42.1 `ColorPicker` 独立 kind —— 修语义，非加功能

原本 `ColorPicker` 的 `BaseWidget` 声明 `WidgetKind::ColorDialog`，导致：

| 受影响面 | 错误答案 |
|---|---|
| 工厂反查名 | `color_picker` 的 kind 是 dialog |
| 可访问性角色 | “对话框”（实际上是个无窗口的内嵌控件）|

> **这是本轮最重要的发现**：拆 kind 不是单向的。`color_dialog` 原本只是
> `color_picker` 的**别名**，因为一个 capability 同时服务两者。一旦把 picker 挪到
> 自己的 kind，dialog 就**没有任何注册名了** —— `kind_factory_name(ColorDialog)` 解析到

它可构造但每个属性读写都返回 `UnsupportedOnWidget`。已补上，含 `current_color`（只读，

### 42.2 `Toast` —— 从 `ToastStack` 拆出

新增 `src/widget/special_widgets/toast.rs` 中的 `Toast`（与 `ToastStack` 同模块，共享 `ToastLevel`）。

| 设计决定 | 理由 |
|---|---|
| **不自行定时消失** | 本库没有可信时钟；自行消失的控件不可测。`ttl_ms` 是**给宿主的数据**而非行为，宿主调 `dismiss()` |
| `dismiss()` 无条件发信号 | `dismissible` 控制的是“是否给**用户**一个关闭按钮”，不是“程序能否结束它” |

### 42.3 `SplashScreen` —— 新增 `src/widget/overlay_widgets/splash_screen.rs`

| 设计决定 | 理由 |

## 44. 局部重绘完整接线（BLUE16 phase F）

### 44.1 现状：已实现、已宣传、未接线

### 44.2 三态策略（而非布尔开关）

新增 `widget::runtime::RepaintMode`：

| 态 | 行为 |
|---|---|
| `Full` | **默认**，与旧行为完全一致 |
| `Dirty` | 只重绘损坏区域 |
| `Adaptive` | 损坏面积接近整屏时**逐帧**退回 `Full` |

**为何是可选项而非替换**：脏区域不是无条件更快。控件少变、窗口大时它赢；
动画/滚动/视频时损坏矩形并集涨到整屏，而追踪器**还要付合并与裁剪的开销**。
`Adaptive` 的退回是逐帧而非单向锁存，所以“动画一秒后静下来”会自行恢复局部重绘。

### 44.3 新增 API

| API | 作用 |
|---|---|
| `set_repaint_mode(id, mode) -> bool` | 未挂载时返回 `false`；切回 `Full` 会**清掉陈旧损坏** |
| `repaint_mode(id)` | 未配置时报 `Full`（即它实际得到的），而非“未配置”态 |
| `mark_dirty_rect(id, rect) -> bool` | `Full` 下**有意不记录**（该模式永不读） |
| `dirty_rects(id)` | 供 GPU 后端取裁剪矩形 |
| `render_frame_incremental(id, size, clear, previous)` | 增量渲染 |
| `SoftwarePaintBackend::seed_from(frame) -> bool` | 用前一帧播种 back buffer；长度不符时拒绝 |

## 50. 项 7：`Adaptive` 改为按**面积**判定

### 旧规则错在哪

旧条件是「超过 16 个区域就回退」，它度量的是**区域个数**：

| 输入 | 旧规则 | 覆盖面积 | 正确答案 |
|---|---|---|---|
| 16 个小区域散在 4K 窗口 | 回退（>16）| ~0.01% | 不该回退 |
| 20 个小区域散在 200×200 | 回退 | 1.25% | 不该回退 |
| 2 个不重叠区域拼满整屏 | **不回退** | 100% | 应该回退 |

两个方向都错。新规则按覆盖面积比例：

```rust
pub const FULL_REPAINT_AREA_RATIO: f32 = 0.5;
let too_large = (covered as f32) >= (frame_area as f32) * FULL_REPAINT_AREA_RATIO;
```

**为何是一半**：局部重绘仍要遍历整棵控件树并重发绘制命令，clip 只是丢弃输出。当存活像素
接近全部时，被丢弃的工作就是全部成本。一半被丢弃的工作等于被保留的工作，是取舍开始
**无歧义**的最早点。

### 新增 6 条断言「绘制次数」的测试

`render_dirty_regions` 无返回值，所以「是否回退」只能通过**绘制了几次**观察：

| 测试 | 断言 |
|---|---|
| `no_damage_paints_nothing` | 0 次 |
| `small_regions_in_a_large_frame_are_painted_separately` | 3 个区域 → 3 次 |
| `damage_covering_the_frame_collapses_to_one_pass` | 2 个不重叠大区域 → **1** 次 |
| `the_fallback_applies_at_the_documented_ratio` | 正好 50% 时回退 |
| `many_small_regions_do_not_trigger_the_fallback` | 40 个小区域 → 40 次 |
| `test_render_dirty_regions_large_damage_falls_back` | 拼满帧的 2 区域 → 1 次 |

**旧测试 `test_render_dirty_regions_too_many` 断言的是旧行为**（20 个小区域 → 1 次），
已改写并在注释里写明为何改：它当时断言的是“回退”，而新规则下 1.25% 的损坏不该回退。

## 51. 项 2：`rw_widget_set_style` —— 一个**故意的语义分歧**

### 设计：文本而非逐值编码

```c
bool rw_widget_set_style(uint64_t widget_id, const char* declaration);
// "background-color: #FF0000" / "border-radius: 4"
```

复用 `CssParser`，而不是为 ABI 写第二套值编码。

### ⚠️ 测试抓出的真问题：拼错的属性被静默接受

`apply_one` 的兜底是：

```rust
_ => {
    // Unknown property — ignore (CSS spec: ignore unknown properties)
}
```

**这对样式表是正确的**（CSS 规范要求一份为渲染器 A 写的表能在支持属性更少的 B 中加载），
但让 `"backgrond-color: #FF0000"` 被当作**成功**返回。

我的测试直接断言「拼错必须被拒绝」并失败 —— 这是**测试先于代码发现语义分歧**。

**修法不是改 `apply_one`**（那会破坏 CSS 语义），而是让 ABI 层能区分：

| 层 | 策略 | 理由 |
|---|---|---|
| 样式表 | 忽略未知属性 | CSS 规范 |
| ABI 单属性写 | **拒绝未知属性** | 调用方只指定了一个属性，沉默会让拼写错误当作成功 |

新增 `CssParser::is_known_property`，并由一条**双向一致性测试**背书：
`known_property_list_matches_what_apply_one_handles` 逐个应用名单里的每个属性，
断言**样式真的变了**（而非读源码）。

> 这测试也自己抓到一个错：我把 `background-gradient` 的测试值写成 `#FFF`，
> 而它只接受 `linear-gradient(<angle>deg, ...)`。是**测试数据错**，不是代码错。

### 错误文本要保留

新增 `error::ffi::record_message_error`：能力层拒绝用**固定文本**（因为拒绝类型本身
已说明问题），而样式解析错误必须**转发解析器原文** —— 调用方递进来一个字符串，
有用的回答是「它哪一段没解析成功」。

## 53. 项 6：局部重绘接入三个真实后端

### 架构决定：**不改 `invalidate_surface` 签名**

计划里没规定怎么做。分析后选的是**新增可选方法** `invalidate_surface_rect(id, rect)`：

| 方案 | 代价 |
|---|---|
| 改 `invalidate_surface` 签名 | 触及 **10 个后端**，而其中多数无法表达子矩形；也破坏 BLUE15 「6 个必需方法」的成果 |
| 新增可选方法 | 只需实现能做的后端；其余继承 trait 默认 |

**默认返回 `false` 而非自己回退重绘**是有意的：一个忽略返回值的调用方仍然得到正确画面，
因为回退就是它本来就有的那个调用；反过来假如默认“静默成功”，后端没做而调用方以为做了，
那是一个更糟的 bug。

### 三个桌面后端的实现

| 后端 | 机制 | 额外处理 |
|---|---|---|
| **Linux/GTK** | `WidgetExt::queue_draw_area` | 坐标从 surface 空间转为控件局部（减 `allocation`）；拒绝落在控件外的矩形（GTK 不检查，会报成功）|
| **Windows/Win32** | `InvalidateRect(hwnd, &RECT, 0)` | `GetClientRect` 预检；拒绝空矩形与完全在客户区外的矩形 |
| **macOS/AppKit** | `setNeedsDisplayInRect:` | 查 `isFlipped`：非翻转视图的 y 原点在**底部**，必须镜像（直传会失效到对面边）|

三个都交叉编译验证过：

```bash
cargo check --target aarch64-apple-darwin  --features "macos-legacy,software,controls-custom,quality-management"  # Finished
cargo check --target x86_64-pc-windows-msvc --features "windows,software,controls-custom,quality-management"       # Finished
```
✅ 已复跑

### 测试基础设施：可观察后端的失效

「是否告诉了平台」从外部不可见：追踪器只说明记录了什么，不说明后端被要求做什么。
进程全局 platform 是 `OnceLock` 换不掉，而触及真后端又要么无效要么碰显示器。

新增 `platform::RecordingInvalidations` + `with_recorded_invalidations`：

- 线程局部 override，`get_platform` 先查它；
- 记录 `(id, None)` = 整面失效、`(id, Some(rect))` = 窄化失效，**一张表里能区分两者**；
- `refusing_narrowing()` 模一个不支持窄化的后端，用来验证**回退路径真的触发**。

新增 2 条测试：

| 测试 | 断言 |
|---|---|
| `recording_damage_asks_the_platform_to_repaint` | 记录损坏 → 后端收到 `(id, Some(rect))`；`Full` 模式 → 后端**没收到任何东西** |
| `a_backend_that_cannot_narrow_gets_a_whole_surface_repaint` | 拒绝窄化时收到 `(id, None)` |

## 54. 项 1：布局上移 —— **实际是修了一个真 bug**

### 分析阶段的两次自我推翻（保留记录）

| 我的判断 | 实际 | 依据 |
|---|---|---|
| 「`json/layout.rs` 无任何引用者」 | **错**。`loader.rs` 第 31 行 import、第 160/172/173 行调用 | 第一次只搜了 `layout::`，漏了 import 行 |
| 「`apply_layout` 是完整引擎但 loader 从不用它」 | **错**。loader 确实在用 | 同上 |

> 两次都是同一个手法：**`grep` 模式太窄就得出“不存在”**。这已是第三次（前两次见 §13.3、§14.2）。

### 真正的发现：`store_layout` 在子控件循环**之后**

两处都是这个顺序（`"layout"` 伪控件分支与 window 的 inline layout 分支）：

```rust
// 修复前
for child in children {
    add_widget_to_layout(child_id, attrs.stretch, parent);  // ← 布局还不存在，静默 no-op
}
store_layout(parent, layout);   // ← 太晚了
apply_layout(parent, rect);     // ← 对空布局计算
```

后果：**声明式布局能解析、能建布局对象、能跑 `apply_layout`，但一个控件都不会移动**，
且任何地方都不报错。所有既有测试通过，因为它们断言的是“加载成功”而非“控件在哪”。

### 上移的形态：**按依赖拆，不按感觉拆**

原计划说“把解析逻辑上移到 `src/layout/declarative.rs`”。实测发现 `json/layout.rs`
依赖 `serde_json`，整体上移会把 serde 带进 `layout` 模块。

所以拆的是**依赖边界**：

| 模块 | 内容 | 依赖 |
|---|---|---|
| **`layout/declarative.rs`**（新）| 注册表 + `store/forget/has` + `add/remove/spacer` + `apply` + `preview` | 仅 `crate::layout` 与控件运行时 |
| **`json/layout.rs`** | `serde_json` → layout-kind 翻译 | `serde_json` |

`json/layout.rs` 的运行时部分改为 **`pub use` 转发**，不是拷贝 —— 两份“存布局并移动子控件”
的实现最终会对 spacer 哨兵或线程亲和性产生分歧。

### 顺带修好的小缺陷

| 缺陷 | 修法 |
|---|---|
| `add_widget_to_layout` 收一个 `_layout` 参数却**忽略它**（按 parent id 查找）| 移除该参数；它是个误导性的承诺 |
| `add_spacer_to_layout` 收 `_stretch` 却**硬编码 `add_widget(u64::MAX, 0)`** | 传递 stretch；返回 `bool` |
| `toast_stack` 风格的空操作无返回值 | 新增 `add/remove/spacer` 返回 `bool`，调用方能区分“做到了”与“没有布局” |
| 无卸载路径 | 新增 `forget_layout` / `remove_widget_from_layout` |

### C ABI：7 个布局入口（B-3 的真正目的）

```c
bool rw_widget_set_layout(uint64_t parent, const char* kind_name, int spacing, int margin);
bool rw_widget_layout_add(uint64_t parent, uint64_t child, unsigned int stretch);
bool rw_widget_layout_add_spacer(uint64_t parent, unsigned int stretch);
bool rw_widget_layout_remove(uint64_t parent, uint64_t child);
bool rw_widget_layout_clear(uint64_t parent);
unsigned int rw_widget_layout_apply(uint64_t parent, int x, int y, unsigned int w, unsigned int h);
unsigned int rw_widget_layout_child_count(uint64_t parent);
```

`kind_name` 使用与声明式文档**相同拼写**，所以一个名字两处通用。**未知 kind 被拒绝**
而非默认：拼错 `"hbox"` 得到纵向盒且看起来“就是不对但找不到原因”是最难查的错。

### 测试：两条端到端 + 反向注入

| 测试 | 断言 |
|---|---|
| `a_vbox_layout_positions_its_children_below_one_another` | 第二个子控件在第一个**下方**且同列 |
| `an_hbox_layout_positions_its_children_side_by_side` | 左→右且同行 |
| `c_abi_layout_entry_points_move_the_widgets` | `geometry()` **真的变了**，且在 vbox 中第二个 y 更大；未知 kind / 无布局父控件均被拒 |

**⚠️ 第一步反向注入失败（保留记录）**：我把 `store_layout` 移到子控件后面，**测试仍通过**。
原因是两处：

1. 第一次注入的替换字符串没匹配上（注释里的破折号字符），实际未注入 —— 我用 `grep -c INJECTED` 发现为 0；
2. 第二次注入了**错误的分支**（pseudo-widget 分支），而测试走的是 **window 的 inline layout 分支**。

修正注入位置后：

```
assertion `left == right` failed: both children must reach the layout;
an empty list means they were added before it existed
```

两条测试都失败 —— 反向注入验证通过（原则 #19）。

## 57. 一句话结论

用户要求「一步一步完成所有」，五项全部落地：

1. **阈值按面积** —— 修正了一个**两个方向都错**的判据，6 条断言绘制次数的测试；
2. **`rw_widget_set_style`** —— 复用 CSS 解析器，并在测试推动下做出了一个**有意的语义分歧**（样式表忽略未知属性，单属性写拒绝）；
3. **能力矩阵 C 列** —— 派生而非手维，22 / 174；
4. **局部重绘入后端** —— 新增**可选**方法而非改签名，GTK / Win32 / AppKit 三个实现均交叉编译通过，并建立可观察后端失效的测试基础设施；
5. **布局上移** —— 拆出 `layout/declarative.rs`，**并修好一个静默 bug**：`store_layout` 晚于子控件注册，导致声明式布局“能解析、能应用、一个控件都不动”。

**测试 4299 → 4340（+41）**；ABI 119 → **126**；门禁 26 个仍 25 PASS。

**本轮最值得记住的一点**：那条布局 bug 存活至今，是因为所有测试都问“加载成功了吗”，
而没有一个问“控件在哪”。**断言产物而非返回值**在这轮三个不同的地方各抓到一次
（拼错的样式属性、未损坏区域的像素、布局未注册的子控件）。
