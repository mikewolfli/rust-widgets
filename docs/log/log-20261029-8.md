## 2. §3 — `Layout` 的破坏性变更登记（P1）

### 2.1 事实核对

`src/layout/types.rs` 确认三项**没有默认实现**：

- `fn arrange(&self, rect, children: &[ChildInfo], out: ...)`（`:228`）
- `fn arrange_with_context(&self, rect, children, context: &LayoutContext, out: ...)`（`:247`）
- `fn update_with_context(&self, rect, context: &LayoutContext, widgets: ...)`（`:324`）

`impl_layout_forward!(inner)` / `impl_layout_forward!(inner, adjust_rect)` 为导出的迁移宏
（`:373` 起），生成四条转发。因此反馈所说的下游 `E0046` 是真实契约，而 changelog 的
“No other public signature ... changed” 是错误描述。

### 2.2 文档修正（两份副本同步）

`CHANGELOG.md` → 3.0.0 → *API changes* 现在包含：

- 三条方法“**required**”的事实与 `E0046` 症状；
- **G-403 原因**：继承默认会静默退回 `update`，丢掉 `ChildInfo` hint 通道与设备上下文；
- 迁移示例两种形态：
  ```rust
  impl Layout for Wrapper {
      impl_layout_forward!(inner);          // 四条全转发
  }
  // 或 impl_layout_forward!(inner, adjust_rect);  // 先变换矩形
  ```
- 以及“无法消费 hint 的布局要自己明说”（`Area` 型 workbench 的写法）这一判定点；
- “No other public signature…” 一句保留原措辞但**现在成立**（3.0.0 的破坏性变更恰为这两处）。

同步：`cp CHANGELOG.md docs/reports/CHANGELOG.md`，`tools/check_changelog_sync.sh` → 字节一致。

## 3. §4 — 示例尺寸与 `--check` 一致性（P2）

### 3.1 根因

- 文档 `examples/generated_project/project.json` 声明 `window.width=640, height=480`；
- `tools/designer_generate.rs` 的 CLI 默认是 1280×800，且**只**从命令行取解算尺寸；
- 门禁 `tools/check_generated_sources.sh` 显式传 `--width 640 --height 480`，所以门禁绿、读者手跑红。

即“同一事实（解算尺寸）有两个来源”。修复方向取反馈的第一选项：**文档为唯一来源**。

### 3.2 实现

| 位置 | 改动 |
|---|---|
| `src/json/project.rs` | 新增 `JsonProject::window_size() -> Option<(u32, u32)>`：读根节点 `width`/`height`；任一侧缺失/非正 → `None`（半张矩形不是客户区）。附 2 条单测（读得到 / 缺失与 0 → None） |
| `tools/designer_generate.rs` | `Options.width/height` 改为 `Option<u32>`；新增 `solve_size(&self, json)`：命令行 > 文档 > `FALLBACK_WIDTH/HEIGHT`（1280×800）；`--check` 与写入路径都用解算结果；usage 与模块头示例改为无 flag 形态 |
| `tools/check_generated_sources.sh` | `GENERATE` 不再传 `--width/--height`；三条重生成提示同步简化。门禁因此**持续覆盖**文档默认尺寸这条路径 |

### 3.3 证据

