### 1.2 🔴 缺陷类 A：删除**靠前**的元素会静默切换可见内容（`carousel` / `tab_view` / `ribbon_bar`）

**取证**（探针实测，`[A,B,C,D]`，当前为 `C`，删除**无关的** 0 号页）：

```text
PROBE carousel current=2 (expect still C, i.e. 1)
PROBE tab_view current=2 (expect still C, i.e. 1)
```

三处的 `remove_*` 只在索引**越界**时修正，从不因“删点在前面”而下移：

```rust
// carousel.rs（修前）
let last = self.pages.len().saturating_sub(1);
if self.current_index > last { self.current_index = last; ... }   // 只治越界
```

⇒ 用户正看着 C，删掉一个**与它无关的**更早的页后，屏幕上换成 D，且**不发** `page_changed`。
这是“静默上下文切换”——原则 #12/#13 所禁。

**修法**：删点在当前之前 ⇒ 索引减一（继续指向同一页）；删点即当前或其后 ⇒ 越界时钳到末页；
两种情况都发变更信号 + 重绘。`ribbon_bar` 另外补了 `request_redraw`（它的 `tab_changed`
还写错了信号名，实际字段是 `current_tab_changed` —— 编译期即抓出）。

对照：`mdiarea::remove_sub_window` 本来就是对的（双向修正），本轮只给它补了重绘。

### 1.3 🔴 缺陷类 B：`insert_*` 越界**panic**（3 处），而同类兄弟都 clamp

**取证**（探针实测，`insert_*(9)` 于长度 2 的列表）：

```text
thread 'probe_insert_tab_out_of_range_panics' panicked at tabwidget.rs:240:
  insertion index (is 9) should be <= len (is 2)
thread 'probe_insert_widget_out_of_range_panics' panicked at stackedwidget.rs:59
thread 'probe_insert_item_out_of_range_panics' panicked at toolbox.rs:163
```

同族**本已**确立“越界即追加”契约（`tab_bar.rs:190`、`pie_menu.rs:251`、`kanban_board.rs:307`、
`combobox.rs:468`、`listbox.rs:145` 全部 `index.min(len)`）。⇒ 这三处是**漏改**。

**修法**：三处 `let index = index.min(<collection>.len());`，并写明契约。

### 1.4 🔴 缺陷类 C：`splitter` 的分隔条**不在两栏之间**（draw / 命中 / 拖动三处同错）

**取证**（探针实测：两个等权重栏、300px 控件）：

```text
PROBE ratio(0)=Some(1.0) ratio(1)=Some(1.0)
PROBE draw-handle0-x=300        ← 手柄被画在右边缘**之外**
PROBE pane rects = [(1, ..width: 150), (2, x: 150, ..)]   ← 真正的边界在 150
```

根因是**两套推导**：`SplitterLayout::update` 把 ratio 当**相对权重**读
（`weights[i] / sum`），而 `draw` / `begin_handle_drag` 直接累加 `ratio(i) * extent`：

```rust
// layout/splitter.rs:157（布局，正确）
let total_ratio = self.ratios.iter().copied().sum::<f32>().max(0.01);
let ratio = self.ratios.get(index).copied().unwrap_or(1.0) / total_ratio;
// splitter.rs（绘制/拖动，错的）  x += total_width * ratio;   // 未除 sum
```

而 `add_pane` 存的是**原始** `stretch`（`layout/splitter.rs:62` 文档明说），只有拖动**松手**才归一化
⇒ 除了“权重恰好和为 1”的巧合，手柄永远画错位置，且**拖不到**。

**修法（原则 #101 同一概念一条路径）**：新增 `divider_center(index)` / `divider_centers()`，
它**向布局要**各栏矩形，取第 `index` 栏与第 `index + 1` 栏之间的间隙中点
（`pane[i].end + spacing / 2`）；`draw`、`begin_handle_drag`、以及（原有的）`active_pane` 命中
全部改读它。少于两栏时给一个控件中心的手柄（保留“分隔条即可供性”的既有裁定）。

**修后实测**：

```text
PROBE press@150 opens drag = true     ← 手柄在真边界上，且抓得住
```

### 1.5 🔴 缺陷类 D：写入被绘制状态却不请求重绘（§9.4 同一类，上轮只扫了 `list_box`/`combo_box`）

| 控件 | setter / mutator | 后果 |
|---|---|---|
| `tree_view` | `select_node` / `clear_selection` / `set_focused_node` / `clear_focused_node` | 选中/焦点高亮要等无关事件才出现 |
| `list_view` | `select_row` / `clear_selection` / `set_focused_row` / `clear_focused_row` | 同上 |
| `table_widget` | 同上 | 同上 |
| `mdi_area` | `add_sub_window` / `remove_sub_window` | 加/删子窗口不更新画面 |
| `tool_bar` | `add_action` / `add_separator` / `clear` | 加/清空工具项不更新画面 |
| `ribbon_bar` | `add_tab` / `remove_tab` | 加/删页签不更新画面 |

同族兄弟（`tree_table` / `virtual_list` / `property_grid` / `grid_table`）**本来就调用**
`request_redraw`，`tree_view` 自己的 `MouseMove` 悬停分支也调用 —— 说明这是**漏写**而非设计。

**修法**：逐处补 `request_redraw()`，并在真无变化时提前返回（避免无谓重绘）。每处都写清“为何重绘”。

## 2. 第二轮：`Modifiers` 端到端接线（把“假 Extended 选择”变成真实现）

### 2.1 取证：鼠标按下事件**根本不携带修饰键**

`Event::MousePress { pos, button }` 只有两个字段，而 `Event::KeyPress`/`Wheel` 都有
`modifiers: u32`。⇒ `SelectionMode::Extended` 文档承诺的 “`Ctrl`/`Primary` toggles,
`Shift` extends” **在物理上无法实现**：平台层的修饰键状态没有任何路径能到达控件层。

这解释了为何 `listbox.rs:297-298` 已修而 `SelectionModel` 未修 —— 后者是**接收不到**输入。

### 2.2 实施

| 层 | 改动 |
|---|---|
| `src/event/types.rs` | `MousePress` 增 `modifiers: u32`；新增 `Event::mouse_press_with(x, y, button, modifiers)`（平台层用）与 `Event::modifiers()`（统一读取） |
| 调用点 | 全仓 **130+** 处 struct literal 补 `modifiers: 0`（测试夹具，无修饰键）；所有 `_pattern_` 改为 `..` |
| Windows | `forward_mouse` 的 press 改走 `mouse_press_with(.., current_modifiers())`（已存在的 `GetKeyState` 助手） |
| macOS | 新增 `ns_event_modifier_flags`（读 `NSEvent.modifierFlags`）+ 把 `map_key_modifiers` 拆出可复用的 `map_modifiers`，使指针与键盘**同一映射** |
| Linux GTK | 把 `modifier_bits` 拆出 `modifier_state_bits(gdk::ModifierType)`，两处 press 站点都传真实状态 |

### 2.3 `SelectionModel::Extended` 真实现

| 接口 | 行为 |
|---|---|
| `select_row` | `Extended` 下**替换**选择并立 anchor（原为无条件 push，等于 `Multi` 且允许重复） |
| `select_with_modifiers(row, mods)` | `Shift` ⇒ anchor..row 闭区间；`Ctrl` ⇒ 切换单行并重置 anchor；无修饰 ⇒ `select_row` |
| `anchor()` | 新增读回口 |
| `set_mode` | 离开 `Extended` 时清 anchor（避免跨模式悬空） |

`ListView::select_row_with_modifiers` / `TableWidget::select_row_with_modifiers` 新增；
两控件的 press 处理改为从事件读 `modifiers` 并交给它。

**探针实测（修后）**：

PROBE shift  -> [2, 3, 4, 5]   （区间）
PROBE ctrl   -> [2, 3, 5]      （切换，无重复）

### 2.4 新门禁：`check_mousepress_carries_modifiers`

检查两件事：

1. `src/` + `tests/` 中**每个** `MousePress` struct literal 都带 `modifiers`，

### 7.2 🔴 第六轮：24 条预存在失败 —— **同一根因，已全部修复**

上一节把这 24 条列为“本轮范围外”。用户要求继续，于是逐条取证，结果它们**几乎全部是同一个缺陷**。

#### 7.2.1 取证：两条入口点给出不同几何

`layout::flex` 的 4 条失败：

```text
left:  {2: Rect { x: 68, y: 0,  width: 40, height: 30 }, 1: ... height: 30 }
right: {2: Rect { x: 68, y: -1, width: 40, height: 32 }, 1: ... height: 32 }
```

差 2 px 高与 1 px 偏移。探针实测（`[A,B]`，300×200）：

```text
PROBE update  = [(1, Rect { x: 0, y: 0, width: 60, height: 50 })]   ← 无触摸下限，撑满 50
PROBE arrange = [(1, Rect { x: 0, y: -1, width: 60, height: 32 })]  ← 应用了 32px 下限并居中
PROBE min_touch_size = Size { width: 32, height: 32 }
```

**根因**：`arrange_body`（`arrange`/`arrange_with_context` 共用体）无条件套用
`grow_to_min_touch_size`，而 `FlexLayout::update`（旧路径，用 `compute_rects`）不套。

但直接给 `update` 加上下限会破 **10 条**测试——说明“`update` 不套下限”是**有意契约**，
而 `Layout::arrange` 的默认实现文档明文写着它必须**转发给 `update`**（“一个没学过设备的
布局就按自己的名义尺寸排”）。因此正确方向是**反过来**：`arrange`（无上下文）不得套下限。

#### 7.2.2 修法一：下限只在拿到设备上下文时生效

新增 `apply_touch_floor: bool` 参数：

| 入口 | 传入 | 理由 |
|---|---|---|
| `arrange_with_context` | `true` | 手上有真实 `LayoutContext` |
| `arrange` | `false` | 与 `update` 逐字节一致（默认实现所承诺）|
| `update_with_context` | `true` | 同上 |

#### 7.2.3 修法二：已被**声明**的尺寸不因下限而变

`a_size_the_composite_stated_is_not_inflated_by_the_touch_floor` 与
`a_plain_child_is_grown_to_the_profiles_touch_floor` 这两条测试**共同定义**了区分标准：
`Hints::fixed`（`min == max`）就是 `add_sized`/`add_flexible` 注册的形状 —— 即
“**复合控件明确声明的尺寸**”，它豁免于下限（否则 split button 的 22px 列会被撑成 32，不再拼接）；
而 `add` 注册的是控件自己的宽松 `hints()`（`min 0`），是**愿望**而非声明，下限照常。

新增 `size_is_stated(index)` 判定，准确复用这一语义。

#### 7.2.4 修法三：增长不得把子控件推出它的容器（§B.6 rule 2）

`the_layout_owns_placement_and_padding_is_removed_first` 期望 `x == padding.left == 10`，
而 16px 宽的 label 愿望被下限长成 32px 后**居中**，把 `x` 拉到 `2`：

```text
PROBE composite placed = [(1, Rect { x: 2, y: -3, width: 32, height: 32 }), ...]
```

**两条测试都是对的**，区别在于**槽位是否已经占满带**：

| 测试 | 槽位 vs 带 | 期望 |
|---|---|---|
| `flex_layout_update_with_context_scales_gap_and_padding` | 槽位 **=** 带（满高行子项）| 保持居中溢出（无空间可滑）|
| `the_layout_owns_placement_and_padding_is_removed_first` | 槽位 **<** 带（小 label 在大带里）| 滑回带内 |

只有当带**比增长后的盒子更大**时才存在“滑回去”的位置；此时把原点夹回带内，
**尺寸不变**（缩小就废掉了下限本身）。槽位已占满带时无可滑之处，保留对称溢出。
