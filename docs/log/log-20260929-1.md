### 1.2 🔴 缺陷类 A：删除**靠前**的元素会静默切换可见内容（`carousel` / `tab_view` / `ribbon_bar`）

**取证**（探针实测，`[A,B,C,D]`，当前为 `C`，删除**无关的** 0 号页）：

```text
PROBE carousel current=2 (expect still C, i.e. 1)
PROBE tab_view current=2 (expect still C, i.e. 1)
```

三处的 `remove_*` 只在索引**越界**时修正，从不因“删点在前面”而下移：

```rust
// carousel.rs（修前）
let last = self.pages.len().saturating_sub(1);
if self.current_index > last { self.current_index = last; ... }   // 只治越界
```

⇒ 用户正看着 C，删掉一个**与它无关的**更早的页后，屏幕上换成 D，且**不发** `page_changed`。
这是“静默上下文切换”——原则 #12/#13 所禁。

**修法**：删点在当前之前 ⇒ 索引减一（继续指向同一页）；删点即当前或其后 ⇒ 越界时钳到末页；
两种情况都发变更信号 + 重绘。`ribbon_bar` 另外补了 `request_redraw`（它的 `tab_changed`
还写错了信号名，实际字段是 `current_tab_changed` —— 编译期即抓出）。

对照：`mdiarea::remove_sub_window` 本来就是对的（双向修正），本轮只给它补了重绘。

### 1.3 🔴 缺陷类 B：`insert_*` 越界**panic**（3 处），而同类兄弟都 clamp

**取证**（探针实测，`insert_*(9)` 于长度 2 的列表）：

```text
thread 'probe_insert_tab_out_of_range_panics' panicked at tabwidget.rs:240:
  insertion index (is 9) should be <= len (is 2)
thread 'probe_insert_widget_out_of_range_panics' panicked at stackedwidget.rs:59
thread 'probe_insert_item_out_of_range_panics' panicked at toolbox.rs:163
```

同族**本已**确立“越界即追加”契约（`tab_bar.rs:190`、`pie_menu.rs:251`、`kanban_board.rs:307`、
`combobox.rs:468`、`listbox.rs:145` 全部 `index.min(len)`）。⇒ 这三处是**漏改**。

**修法**：三处 `let index = index.min(<collection>.len());`，并写明契约。

### 1.4 🔴 缺陷类 C：`splitter` 的分隔条**不在两栏之间**（draw / 命中 / 拖动三处同错）

**取证**（探针实测：两个等权重栏、300px 控件）：

```text
PROBE ratio(0)=Some(1.0) ratio(1)=Some(1.0)
PROBE draw-handle0-x=300        ← 手柄被画在右边缘**之外**
PROBE pane rects = [(1, ..width: 150), (2, x: 150, ..)]   ← 真正的边界在 150
```

根因是**两套推导**：`SplitterLayout::update` 把 ratio 当**相对权重**读
（`weights[i] / sum`），而 `draw` / `begin_handle_drag` 直接累加 `ratio(i) * extent`：

```rust
// layout/splitter.rs:157（布局，正确）
let total_ratio = self.ratios.iter().copied().sum::<f32>().max(0.01);
let ratio = self.ratios.get(index).copied().unwrap_or(1.0) / total_ratio;
// splitter.rs（绘制/拖动，错的）  x += total_width * ratio;   // 未除 sum
```

而 `add_pane` 存的是**原始** `stretch`（`layout/splitter.rs:62` 文档明说），只有拖动**松手**才归一化
⇒ 除了“权重恰好和为 1”的巧合，手柄永远画错位置，且**拖不到**。

**修法（原则 #101 同一概念一条路径）**：新增 `divider_center(index)` / `divider_centers()`，
它**向布局要**各栏矩形，取第 `index` 栏与第 `index + 1` 栏之间的间隙中点
（`pane[i].end + spacing / 2`）；`draw`、`begin_handle_drag`、以及（原有的）`active_pane` 命中
全部改读它。少于两栏时给一个控件中心的手柄（保留“分隔条即可供性”的既有裁定）。

**修后实测**：

```text
PROBE press@150 opens drag = true     ← 手柄在真边界上，且抓得住
```

### 1.5 🔴 缺陷类 D：写入被绘制状态却不请求重绘（§9.4 同一类，上轮只扫了 `list_box`/`combo_box`）

| 控件 | setter / mutator | 后果 |
|---|---|---|
| `tree_view` | `select_node` / `clear_selection` / `set_focused_node` / `clear_focused_node` | 选中/焦点高亮要等无关事件才出现 |
| `list_view` | `select_row` / `clear_selection` / `set_focused_row` / `clear_focused_row` | 同上 |
| `table_widget` | 同上 | 同上 |

## 2. 第二轮：`Modifiers` 端到端接线（把“假 Extended 选择”变成真实现）

### 2.1 取证：鼠标按下事件**根本不携带修饰键**

`Event::MousePress { pos, button }` 只有两个字段，而 `Event::KeyPress`/`Wheel` 都有
`modifiers: u32`。⇒ `SelectionMode::Extended` 文档承诺的 “`Ctrl`/`Primary` toggles,
`Shift` extends” **在物理上无法实现**：平台层的修饰键状态没有任何路径能到达控件层。

这解释了为何 `listbox.rs:297-298` 已修而 `SelectionModel` 未修 —— 后者是**接收不到**输入。

### 2.2 实施

| 层 | 改动 |
|---|---|
| `src/event/types.rs` | `MousePress` 增 `modifiers: u32`；新增 `Event::mouse_press_with(x, y, button, modifiers)`（平台层用）与 `Event::modifiers()`（统一读取） |
| 调用点 | 全仓 **130+** 处 struct literal 补 `modifiers: 0`（测试夹具，无修饰键）；所有 `_pattern_` 改为 `..` |
| Windows | `forward_mouse` 的 press 改走 `mouse_press_with(.., current_modifiers())`（已存在的 `GetKeyState` 助手） |
| macOS | 新增 `ns_event_modifier_flags`（读 `NSEvent.modifierFlags`）+ 把 `map_key_modifiers` 拆出可复用的 `map_modifiers`，使指针与键盘**同一映射** |
| Linux GTK | 把 `modifier_bits` 拆出 `modifier_state_bits(gdk::ModifierType)`，两处 press 站点都传真实状态 |

### 2.3 `SelectionModel::Extended` 真实现

| 接口 | 行为 |
|---|---|
| `select_row` | `Extended` 下**替换**选择并立 anchor（原为无条件 push，等于 `Multi` 且允许重复） |
| `select_with_modifiers(row, mods)` | `Shift` ⇒ anchor..row 闭区间；`Ctrl` ⇒ 切换单行并重置 anchor；无修饰 ⇒ `select_row` |
| `anchor()` | 新增读回口 |
| `set_mode` | 离开 `Extended` 时清 anchor（避免跨模式悬空） |

`ListView::select_row_with_modifiers` / `TableWidget::select_row_with_modifiers` 新增；
两控件的 press 处理改为从事件读 `modifiers` 并交给它。

PROBE ctrl   -> [2, 3, 5]      （切换，无重复）

### 2.4 新门禁：`check_mousepress_carries_modifiers`

### 7.2 🔴 第六轮：24 条预存在失败 —— **同一根因，已全部修复**

上一节把这 24 条列为“本轮范围外”。用户要求继续，于是逐条取证，结果它们**几乎全部是同一个缺陷**。

#### 7.2.1 取证：两条入口点给出不同几何

`layout::flex` 的 4 条失败：

```text
left:  {2: Rect { x: 68, y: 0,  width: 40, height: 30 }, 1: ... height: 30 }
right: {2: Rect { x: 68, y: -1, width: 40, height: 32 }, 1: ... height: 32 }
```

差 2 px 高与 1 px 偏移。探针实测（`[A,B]`，300×200）：

```text
PROBE update  = [(1, Rect { x: 0, y: 0, width: 60, height: 50 })]   ← 无触摸下限，撑满 50
PROBE arrange = [(1, Rect { x: 0, y: -1, width: 60, height: 32 })]  ← 应用了 32px 下限并居中
PROBE min_touch_size = Size { width: 32, height: 32 }
```

**根因**：`arrange_body`（`arrange`/`arrange_with_context` 共用体）无条件套用
`grow_to_min_touch_size`，而 `FlexLayout::update`（旧路径，用 `compute_rects`）不套。

但直接给 `update` 加上下限会破 **10 条**测试——说明“`update` 不套下限”是**有意契约**，
而 `Layout::arrange` 的默认实现文档明文写着它必须**转发给 `update`**（“一个没学过设备的
布局就按自己的名义尺寸排”）。因此正确方向是**反过来**：`arrange`（无上下文）不得套下限。

#### 7.2.2 修法一：下限只在拿到设备上下文时生效

新增 `apply_touch_floor: bool` 参数：

| 入口 | 传入 | 理由 |
|---|---|---|
| `arrange_with_context` | `true` | 手上有真实 `LayoutContext` |
| `arrange` | `false` | 与 `update` 逐字节一致（默认实现所承诺）|
| `update_with_context` | `true` | 同上 |

#### 7.2.3 修法二：已被**声明**的尺寸不因下限而变

`a_size_the_composite_stated_is_not_inflated_by_the_touch_floor` 与
`a_plain_child_is_grown_to_the_profiles_touch_floor` 这两条测试**共同定义**了区分标准：
`Hints::fixed`（`min == max`）就是 `add_sized`/`add_flexible` 注册的形状 —— 即
“**复合控件明确声明的尺寸**”，它豁免于下限（否则 split button 的 22px 列会被撑成 32，不再拼接）；
而 `add` 注册的是控件自己的宽松 `hints()`（`min 0`），是**愿望**而非声明，下限照常。

新增 `size_is_stated(index)` 判定，准确复用这一语义。

#### 7.2.4 修法三：增长不得把子控件推出它的容器（§B.6 rule 2）

`the_layout_owns_placement_and_padding_is_removed_first` 期望 `x == padding.left == 10`，
而 16px 宽的 label 愿望被下限长成 32px 后**居中**，把 `x` 拉到 `2`：

```text
PROBE composite placed = [(1, Rect { x: 2, y: -3, width: 32, height: 32 }), ...]
```

**两条测试都是对的**，区别在于**槽位是否已经占满带**：

| 测试 | 槽位 vs 带 | 期望 |
|---|---|---|
| `flex_layout_update_with_context_scales_gap_and_padding` | 槽位 **=** 带（满高行子项）| 保持居中溢出（无空间可滑）|
| `the_layout_owns_placement_and_padding_is_removed_first` | 槽位 **<** 带（小 label 在大带里）| 滑回带内 |

只有当带**比增长后的盒子更大**时才存在“滑回去”的位置；此时把原点夹回带内，
**尺寸不变**（缩小就废掉了下限本身）。槽位已占满带时无可滑之处，保留对称溢出。

#### 7.2.5 结果

```text
desktop --lib ：6180 passed / **1 failed**
```

从 **24 条** 降到 **1 条**，且剩下这条是已记录的 `avatar` 主题竞态 flake
（单跑 3/3 绿、全量并行偶发红，`log-20260928-2.md` §8 早已归档为预存在）。

修复的具体失败（23 条）：`flex` ×4 · `composite` ×2 · `groupbox` ×2 · `scrollarea` ×1 ·
`combobox` ×2 · `spinbox` ×2 · `menu` ×1 · `status_bar` ×3 · `tool_bar` ×3 · `split_button` ×3。

> 这三条修法**互相约束**，缺一不可：只做 7.2.2 会破 7.2.3；只做 7.2.3 会破 7.2.4；
> 只做 7.2.4 会破 7.2.2。它们共同把“下限”“声明”“布置权”三者的边界定清楚了——
> 这正是这 24 条失败一直在等的那次澄清（原则 #101：同一概念只能有一条实现路径）。

## 2. 🔴 缺陷：`process_reload_events` 的自反馈（不终止）

原实现（`watcher.rs:115`）在 `while let Ok(event) = receiver.try_recv()` 循环体内调用 `manager.reload_translation(language)`；
而 `reload_translation` 成功后会**向同一个 channel 再发一个 `TranslationReloaded`**（`manager.rs:132-139`）。

于是：被处理的事件 → 重载 → 再广播 → 被同一个 `while` 立刻读回 → 再处理 ……

### 2.1 反向注入实测（这是判定性证据，不是推测）

```text
$ # 同时去掉「去重」与「quiet」两个守卫后：
$ timeout 25 cargo test --lib 'process_reload_events_does_not' -- --nocapture
Terminated
EXIT=143      # 25s 超时被 kill ⇒ 循环不终止，原文的"自反馈"判断成立
```

### 2.2 修法（根因，不是绕过）

- `manager.rs`：把「重读文件」与「广播」拆开
  - `reload_translation_quiet(lang)` —— 只重载，**不广播**（重入安全的那一半）
  - `announce_reload(lang)` —— 私有，只广播
  - `reload_translation(lang)` = quiet + announce（显式重载仍需可观测）
- `check_and_reload` 改走 `reload_translation_quiet`：它的**返回值本身**就是通知，再广播就是同一件事送两遍
- `watcher.rs::process_reload_events` 改走 `reload_translation_quiet`，并对本轮语言去重（编辑器一次保存常产生一串事件）

### 2.3 守卫分工（如实说明谁在兜底）

单语言场景下，**去重表**已足以终止循环（再广播被 `languages_seen` 跳过），`quiet` 消除的是重复无用功；
两者都在，才是「一次公告 = 恰好一次应用」的完整保证。

## 3. 热加载接入默认运行时

| 改动 | 文件 | 说明 |
|---|---|---|
| 每帧泵（Step 4） | `src/widget/runtime.rs` | `drive_frame` 中 `#[cfg(feature = "i18n")] crate::i18n::pump_hot_reload();`，置于动画步之后、重绘计数之前 |
| 启动 watcher | `src/platform/profile.rs` | `init_optional_subsystems` 读 `RUST_WIDGETS_I18N_DIR`，非空则 `enable_global_hot_reload` |

| Reachability 补记 | `src/i18n/watcher.rs` | 原模块缺 `# Reachability`，本次补齐 |

### 3.1 为什么泵放在 `drive_frame`

- 各平台循环（linux/macos/windows/android/ios/harmony/wasm）**每 tick 都调用** `drive_frame`，这是唯一共享的帧入口；
- 顺序放在动画步之后：应用重载可能使文本失效并提交重绘，先取计数会把该重绘算到下一帧；
- 热加载关闭时开销为「一次加锁 + 一次 `None` 判断」，不值得为此按 profile 分叉帧驱动；
- 与 `tools/check_single_frame_driver.sh` 不冲突：该门禁只断言 `tick_animations` / `drain_triggers` 的唯一驱动，i18n 泵是同帧内的附加步骤，非竞争驱动。

### 3.2 为什么用环境变量而非 `AppConfig` 字段

目录是**部署事实**（这一版随包发了哪套词条），不是应用身份（`app_name` 那类）；`AppConfig` 是公开结构体且文档里按位置构造，
加字段会动到那个面。环境变量与该库既有的运行时覆盖（`RUST_WIDGETS_CPU_UTIL` 等）一致。

### 3.3 `enable_global_hot_reload` 先加载再监听

watcher 只报「变化」，启动时就存在的文件不算变化 —— 所以先 `load_translations` 扫一遍目录，再挂 watcher，否则初始词条要等第一次被编辑才生效。

## 12.3 §11.1 遗留第 4 项：`line_edit` 的键盘与指针选择

`lineedit` 是 `select_with_modifiers` 家族里唯一还没有这个入口的文本控件（`listbox`/`list_view`
第 79 轮已做）。核查发现它不止“缺一个方法”，而是**四类真实缺陷**：

### a) 指针点击不定位光标（功能缺失）

`Event::MousePress` 分支的全部内容是 `self.set_focused(true)`。而 `set_text` 把光标留在**末尾**，
所以「打开表单 → 点进已有内容的中间 → 打字」的结果是**追加到行尾**，不是插入。
且完全没有指针选择——没有任何代码从 `x` 反算索引。

**修法**：新增 `byte_index_at_x(x)`，把像素可靠地映射到字节偏移：

- 用渲染器**自己的** shaper（`RenderContext::shape_text`，即 `render/text/line.rs` 的
  `shape_line`）量出整串 advance，与 `fitted_origin` 放字用的是同一个调用；
- `dx * chars / advance` 在等宽面（本仓默认面）上恰好等于「点到的第几个字符」，在非等宽面上
  是一个按 advance 加权的字符索引；**两种情况同一个表达式**，没有「是否等宽」的分支要跟绘制同步；
- 距离先夹到值**自己**的盒子里（`decoration_layout().value`），所以点在 value 右侧的空白
  会落到 value 边界而不是变成负数索引；
- 结果经 `floor_char_boundary` 落到字符边界——多字节值时不会把光标插进字符中间。

### b) `normalize_selection` 在**手势开始时**清掉了锚点（真 bug，本轮新引入后当场修掉）

我第一版让 `press_at` 走 `normalize_selection()`，它在「press 正好落在光标上」时会判定
「零宽 = 无选择」而把刚设的锚点删掉。后果：**从 value 右侧往回拖选不上任何东西**。
锚点是**手势的起点**，不是**结果**：起点必须活到拖拽结束。修法是把归一化从 `press_at` 移到
`end_drag`（手势结束时才判定零宽）。

### c) Shift+点击 / Shift+方向键的锚点语义（真 bug）

`press_at` 的 Shift 分支只改锚点**不改光标**，于是 Shift+点击是一个只换锚点的空操作——
「按住 Shift 点到行首」什么都选不上。修法：Shift 分支在保留锚点（无锚点时先采纳当前光标为锚点）
的同时，**把光标移到按下点**。

同一处还有一组语义修正（`select_with_modifiers` / `Home` / `End`）：

- 锚点只在**第一次** extend 时采纳光标，之后固定不动。第一版每次 Shift 移动都重新采纳，
  导致 `Shift+Home` 之后接 `Shift+End` 会从错的一端长——即**扩展不可逆**；
- 扩展是**可逆**的：`Shift+Home`（锚 5）选中 `0..=5`，紧接的 `Shift+End` 选中 `5..=8`，
  范围在锚点另一侧，而不是被改写成 `5..=len`。这条正是「Home/End 不能像方向键那样先重设锚点」
  的判据，已单独立测；
- 到边界时的**去选择**不能再走 `select_with_modifiers(0, mods)`：锚点存在时它会把范围写成
  `0..=0` 并把光标拖到 0。改为直接 `clear_selection()`——边界处方向键**移动不了光标**，
  只欠用户一个去选择。

### d) 未映射按键被当成文字输入（真 bug）

catch-all 分支把**每一个**未映射按键都当字符插入，只排除了它自己列出的那几组快捷键。
后果：`Ctrl+B` 插入 `b`、`Ctrl+Z` 插入 `z`（`Primary+Z` 的 undo 在它**前面**，所以 undo 本身没错，
但 Ctrl+Z 同时打进了 `z`）。修法是两步：

1. 控制组合（Ctrl/Alt/Meta）一律不进文字分支；
2. 再加 `!ch.is_control()`，`Tab`(9)/`LF`(10)/`CR`(13)/`NUL`(0) 这些控制码同样不是内容。

> **这里挖出并修掉了一个更容易被忽略的坑**：`Modifiers::contains` 比较的是**掩码的值**，
> 不是「某一位是否置位」。所以 `contains(CTRL | ALT | META)` 只在**三者同时按下**时为真——
> 单独的 `Ctrl+B` 携带 `CTRL`，**被合并写法判为 false**，照样插入 `b`。
> 这正是这个分支要修的缺陷本身，等于白修。判据改成三次独立的 `contains`。
> （取证方式：在 guard 前 `eprintln` 打印 `bits` / `contains(0b1110)`，得到
> `mod=0b10 contains=false`，一目了然。）

### e) 顺带把「左方向键在行首的去选择」补上

`if cursor > 0 { … }` 让行首的 Left 被整个丢弃，连去选择都没有——`listbox` 早已修的同类问题
在文本控件上还在。现在边界分支会执行去选择。

## 13.1 取证：这个控件到底缺什么

`textarea.rs` 的原始状态：**只有一个 `cursor_pos: usize`**，没有任何选择字段。

逐个验证的结论：

| # | 缺陷 | 取证 |
|---|---|---|
| T1 | **完全没有选择** | `grep -c selection_start` = 0。没有键盘选择、没有锚点 |
| T2 | **`Delete` 键会打出 `.`** | `Delete` 未出现在 match 臂里，键码 46 落到 catch-all，而 46 是 ASCII `.` |
| T3 | **`Home`/`End` 打出 `$`/`#`** | 键码 36/35 未处理，同样落进 catch-all |
| T4 | **`Up`/`Down` 打出 `&`/`(`** | 键码 38/40 未处理 |
| T5 | **指针点击不定位光标** | `MousePress` 分支只有 `set_focused`；`set_text` 把光标留在末尾 ⇒ 点进文档中间打字会**追加到末尾** |
| T6 | **控制组合键被打成文字** | catch-all 无任何修饰键判断；`Primary+B` 插入 `b` |
| T7 | 无 `insert_str`（粘贴） | 公开 API 只有单字符 `insert` |
| T8 | 无 `selected_text`/`select_all` | 无法读取或设置选择 |

T2–T4 是同一根因的三个实例（**冰山法则**：一个未处理的键码 → 检查全部未处理键码），
一并修掉。

## 13.2 修法（以 `line_edit` §12.3 的设计为基准，保持两控件语义一致）

新增字段与核心 API：

- `selection_anchor: Option<usize>` —— **只存锚点，范围由 `selection_range()` 派生**。
  与 `line_edit` 同构，这样一个多行和一个单行控件不可能对"什么是选择"有两种理解。
- `dragging_selection: bool` —— 拖拽标志（`MouseMove` 对纯悬停也会投递）。
- `select_with_modifiers(target, mods)` —— **唯一**的键盘移动入口，Left/Right/Up/Down/
  Home/End 全部经过它，Shift 语义只写一遍（原则 #101）。
- `selection_range` / `selected_text` / `selection_anchor` / `clear_selection` /
  `select_all` / `select_line` / `insert_str` / `delete_forward`。
- `press_at` / `drag_to` / `end_drag` —— 指针手势，与键盘共用同一锚点规则。
- `byte_index_at(pos)` —— 像素→偏移，**复用绘制用的同一组常量**（`CHAR_W`、`LINE_H`、
  新增的命名常量 `FIRST_LINE_INSET`，从 `draw` 里的字面量 `4` 提升出来）。

### 三处关键语义决定（都写了理由在代码里）

1. **`press_at` 不做 `normalize_selection`**。落在光标上的按压会得到零宽锚点/光标对，
   但那是**手势的起点**不是**结果**——起点必须活到拖拽结束。归一化放在 `end_drag`。
   （这正是 §12.3 (b) 在 `line_edit` 上踩过的同一个坑。）
2. **锚点在整个 extend 手势中不动**，只在无 Shift 的按压时重设。这样 `Shift+Home`
   之后接 `Shift+End` 会在锚点**另一侧**扫回来，扩展是**可逆**的。
3. **`Home`/`End` 是行边界，`Primary+Home`/`Primary+End` 才是文档边界**。多行控件里
   Home 跳到文档头会让这个键对"回到本行行首"完全无用。

### 编辑路径统一走 `replace_selection` + `record_edit`

`insert` / `insert_str` / `delete_char` / `delete_forward` 四条路径都先消费选择，
再通过 `record_edit` 记**一次**撤销快照并发射 `changed`。这样：
- 打字覆盖选择是"一个动作一次撤销"，不是"删 + 插"两次；
- `insert_str`（粘贴）是**一个**撤销步，而不是每个字符一步。

### 选择的绘制

在文字**之前**按行绘制色带（每条逻辑行一块），所以墨迹压在选择之上。
颜色由控件自己的 ink/fill 派生（两步 blend），而不是硬编码蓝色——这样亮/暗外观都成立，
也不需要第二个主题 token。

## 14.3 修法

`masked_edit` 有**两个坐标空间**：用户输入的 `raw_text`，和插入 mask 字面量后的
`display_text`。光标本来就活在 display 空间（那是用户看到并指向的东西），所以
**锚点也在 display 空间**，raw 的翻译只在一个地方发生：

- `selection_range()` → display 的 `(start, end)`
- `selection_raw_range()` → raw 的 `(start, end)`，两端**各自**用 `display_to_raw_index` 翻译

代码注释里写明了为什么不能"除以/减去字面量个数"：mask 字面量**插在字符之间**，
display 5 可能是 raw 2 也可能是 raw 3，平均值或差值会落到错误的数字上。

其余与 §12.3/§13 同构：`select_with_modifiers` / `press_at` / `drag_to` / `end_drag` /
`select_all` / `clear_selection` / `delete_selection`，以及
`display_position_at_x`（像素→display 位置，与绘制的 `char_width` 同源）
和 `selection_color`（从 ink/fill 派生，不硬编码蓝色）。

绘制：选择色带**逐段**在被选中的 segment 上先画，墨迹后画——所以数字仍然可读。

## 15.1 探针取证（先证明，再动手）

两条都是**缺陷**，而且形状明确：

| # | 缺陷 | 探针证据 | 根因 |
|---|---|---|---|
| R1 | **Shift 被静默忽略** | `Shift+Right` ⇒ `Some((1,1))`：光标**动了**、范围是**零宽** | 六个移动臂各自带 `if *modifiers == 0` 守卫 ⇒ 按住 Shift 时该臂**完全不执行**，于是"键做了事，但不是它说的那件事" |
| R2 | **指针点击不定位光标** | `press(60,20)` ⇒ `Some((0,0))` | `MousePress` 臂只做 `set_mouse_pressed(true)`，没有任何从 `x`/`y` 反算偏移的代码 |

> 当成"已经支持 Shift"而永远不被发现。探针把"读起来像"和"跑起来是"分开了。

## 15.2 修法

- `select_with_modifiers(target, mods)` —— 六个移动臂统一入口，Shift 语义只写一遍。
- `byte_offset_at_x(line, x)` / `byte_offset_at_point(pos)` —— 像素→字节偏移。
  **复用 `estimate_text_width`**（绘制与光标用的是同一个宽度模型），
  而不是除以一个假定字宽——文件自己的注释已经记录过这个教训
  （旧的 `col * 7` 注释写着 "rough char width"）。
- 指针：`MousePress` 现在把光标放到按下点。

## 15.3 一个真实的设计缺陷：有序对存不住"哪端是光标"

`selection` 是 `Option<(start, end)>`（**有序对**），而 `cursor_position()` 返回 `start`。
于是**哪一端是光标在数据结构上无法表达**。第一版实现据此推导锚点，测试立刻抓出来：

```
第一个 Shift+Right 得到 Some((1, 1))，而 (0, 1) 才对
```

即：零宽范围 `(0,0)` 不携带"光标曾在 0"这一信息，`unwrap_or((target,target))`
把锚点取成了**新目标**，范围当场塌陷。

**修法**：新增 `extend_caret: usize` 显式记录光标所在端，所有移动路径都更新它。
同一处还修了 `handle_event` 里 `cursor` 的来源——它原来读 `selection.start`，
而范围向右扩展时 `start` 恒等于锚点，导致 `Shift+Right` 反复算出同一个 `next`
（**又一次同样的病**：把"有序对的一端"当成"光标"）。

> 这已经是**第 4 次**在同一个模式上出错（`line_edit` §12.3(b)、`textarea` §13、
> `masked_edit` §14.4、此处）。规律已经很清楚：
> **"光标位置"和"选择范围"是两件事，任何把它们压成一个值的表示都会在某处丢掉信息。**
> 四个控件现在都把这条写进了各自的文档。

# 第 86 轮：`textarea` 的滚动 —— 2026-09-29

> 承接 §14.6/§15.7 第 3 项。先探针确认它到底是什么问题，结果**改变了我原来的判断**。

## 17.1 探针：原来我把它写错了

我在 §14.6 写的待办是「`textarea` 无滚动/**裁剪**：行数超出高度时下半部分不可见」。
探针测出来的是**只有后半句对**：

```rust
// 20 行文本放进 60 px 高的控件
PROBE ink_box = Some((13, 5, 43, 16))   // 仍然在 0..60 之内
PROBE control height = 60
```

**裁剪早就在**：`draw` 里的 `if y + LINE_H > rect.y + rect.height { break }` 让绘制在最后一个
完整行处停下，所以值不会画出自己的矩形。**缺的只有"滚动"** —— 没有任何办法看到被跳过的那些行。

> 又是一次量程/表述的问题：我上轮把"看不到被跳过的行"写成了"下半部分画到外面去了"。
> 探针把两个不同的断言分开了。**探针的价值就在这里：它把"我以为"变成"我测到"。**

## 17.2 修法

新增 `first_visible_line: usize`（**行索引**，不是像素偏移）：

- 行是固定 `LINE_H` 网格，所以行索引**就是**"滚动位置 ÷ 行高"，而且当值在视口上下增删时
  仍然正确——像素偏移则要在内容高度变化后重新推导。
- `scroll_caret_into_view()`：**最小滚动**，只在光标跑到窗口上方或下方时移动视口。
  这样在文档上半部阅读时字段不会乱跳。
- `visible_line_index(row)` / `line_count()`：绘制路径与像素→偏移映射**共用同一个查找**，
  所以滚动后点击和它落在的字形不可能分属不同行。
- 挂钩点：`record_edit`（所有编辑都经过它）与 `select_with_modifiers`（所有移动都经过它）。
  放在这两个漏斗里而不是各调用点，是为了让**下一个**新增的编辑路径不会忘记它——
  而漏掉的症状（写进看不见的行）在快照测试里是**不可见**的。

同步修改：`cursor_screen_y` 改为相对视口测量（否则滚动后光标画在字段之上或之下）；
`byte_index_at` 把视口行翻译为逻辑行（否则点击解析到用户看不见的那一行）。

## 18.3 关键设计：折行表（这是本轮的技术核心）

这个控件会**自动换行**，断点是逐字符量宽决定的，**不记录**位置。
所以"像素 → 偏移"无法直接算 —— 必须先有断行表。

**决策：让折行规则只写一遍，产出 `Vec<RowSpan>`，绘制与命中测试共用。**

```
布局规则（rows_for）──┬─→ draw：按行绘制
                     └─→ offset_at_point：像素 → 偏移
```

`RowSpan { start, end }` 是**半开字节区间**，所以一行可以被寻址而无需重新折行。

配套：
- `layout_rows()` / `row_of_offset()` / `offset_at_point()` / `offset_in_row()`
- 绘制路径改为**从 `RowSpan` 取字节**，不再自己走 `text.chars()`

> **这解决了我在 83 轮说的三个硬约束中的第三个**（"自动换行下没有可逆映射"）。
> 办法不是避免换行，而是**把换行结果记下来**。

## 18.4 顺带解决的两个约束

- **撤销粒度**：所有编辑路径（`insert_str`/`backspace`/`delete_forward`）都经
  `record_edit` 记**一次**快照。打字覆盖选择是**一个**撤销步（原来每字符一步）。
  已立测：`typing_over_a_selection_replaces_it_in_one_undo_step`。
- **光标默认在末尾**：`set_text` 后光标落到末尾，所以**只做追加的调用方行为不变**。
  这是本轮唯一的兼容性保证，已立测：`typing_with_an_untouched_caret_still_appends`。

## 18.5 过程中发现的**真实设计冲突**（我自己的代码）

第一版在 `set_text` 末尾同时做了两件互相打架的事：

## 19.1 第 1 项：焦点门控 —— 而且我漏了一个控件

### 取证（一次 grep 就推翻了我 §18.9 的说法）

```

```

**所以缺焦点的是两个控件，不是一个。** 我在 §18.9 的待办表里只写了 `rich_edit`，
是把上一步的扫描结果当成了全部。

### 为什么这是正确性问题（不是"设计选择"）

`KeyPress` 分支**不检查任何前置条件**，所以：

- 一个**从未被点击过**的编辑器照样吃键盘 —— 同一页上两个编辑器，一次按键**同时编辑两个**；
- 一个用户从未到达的控件会**吞掉宿主的加速键**。

框架侧其实是完备的：`runtime.rs:472` 明确「Delivers the `FocusLost` / `FocusGained` pair itself」，
`FocusReason` 也随 payload 下发。所以事实**一直可得**，只是这两个控件没有字段记录它。

### 修法（两个控件同样）

```rust
focused: bool,                                    // 默认 false
Event::FocusGained { .. } => { self.focused = true; ... }
FocusLost => { self.focused = false; ... }
MousePress => { self.focused = true; ... }        // 指针是用户到达控件的路径
KeyPress => { if !self.focused { return; } ... }  // 未聚焦不拥有键盘
```

默认 `false`：未被聚焦的控件不消费按键；点一下就聚焦。已立测：
`an_unfocused_editor_ignores_the_keyboard`（含 FocusLost 后再次拒绝）、`a_press_focuses_the_editor`。

### 副产物：**14 个既有测试因此失败，而且它们失败得对**

加门控后 `rich_edit` 5 个、`textedit` 12 个测试变红。逐个核查，**全部是"测试自己没给焦点"**——
即这些测试一直在**未聚焦的状态下驱动键盘**，也就是在测一个**用户不可能处于的状态**。

修法是给 fixture 加焦点（`textedit` 的 `editor()` 与 `rich_edit` 的 `focused()`），
而不是放宽门控。其中两个值得单独说：

- `delete_removes_a_whole_multibyte_character` 断言 `"éa" → "a"`（删掉整个 `é`）——**期望是对的**，
  它只是没焦点；
- `the_right_arrow_moves_past_a_multibyte_character` 报 `18446744073709551615`（即 `usize::MAX`），
  那是测试用 `AtomicUsize::new(usize::MAX)` 当哨兵，信号没发出所以读到哨兵 —— **不是下溢 bug**。

> **教训：门控/前置条件类的修复会让"一直在非法状态下跑的测试"集体变红。
> 这时要逐个判断"是代码错了还是测试站错了位置"，不能为了让测试变绿而放宽门控。**

## 19.2 第 2 项：`textarea` 的度量 —— 我在注释里写的"同源"是**错的**

### 取证（探针实测）

我在 `textarea` 的注释里写过「命中测试与绘制用的是同一组常量，所以二者自洽」。
探针一测就发现**绘制根本不用那组常量**：

```rust
// 绘制：走渲染器
context.draw_text(...)                    // 渲染器自己的字形 advance
// 命中：走常量
let column = ((pos.x - origin_x).max(0) / CHAR_W) as usize;   // CHAR_W = 8
```

实测偏差（`Font::default()`，14 px）：

| 文本 | 渲染器实测 | `CHAR_W` × n | 偏差 |
|---|---|---|---|
| `"i"` | 4 | 8 | +4 |
| `"M"` | 11 | 8 | −3 |
| `"中文"` | 28 | 16 | **−12** |
| `"abcdefghij"` | 68 | 80 | **+12** |

`CHAR_W = 8` 是**等宽单字假设**。所以点击与绘制的**不是同一套模型** —— 注释是错的，
而且这正是我在 `lineedit`/`textedit` 上已经修过的同一类缺陷（"第四份宽度模型"）。

### 修法

- **删除 `CHAR_W`**（编译器立刻报 `never used`，正是它该消失的证明）。
- 新增 `text_advance(&str)` / `char_advance_at(...)` / `column_at_x(...)`：
  全部通过 `measure_text`（渲染器自己的入口）实测。
- `cursor_screen_x` 改为量光标前缀的实测宽度，不再 `col * CHAR_W`。
- `byte_index_at` 的列由 `column_at_x` 逐字符量前缀 + 中点判定得出。
- 选择色带的左右边缘同样改为实测（原本用 `first_col * CHAR_W`）。
- **`LINE_H` 保留**，并在文档里写明区别：行高是**控件自己的布局决定**（行间距），
  不是对任何字形的测量，所以一个常量在这里是正确的，而且绘制与命中共享它。

### 副产物：测试也在用那个错误的模型

11 个测试引用 `CHAR_W` —— 它们等于在**用被测对象去测它自己**。改为新增测试辅助
`x_of_char(line, n)`（走渲染器实测），这样点击才是"瞄准第 n 个字符"，而不是"瞄准 8 的倍数"。

## 19.3 第 3 项：`textedit` 的折行宽度

同一类问题：`rows_for` 的测量闭包原来传 `estimate_text_width`（`size * 0.6` 的字宽模型）。
改为 `char_advance`（渲染器实测），并新增 `text_advance`。

理由写在代码里：`estimate` 对 CJK（约两倍）和比例字形（`i` 只有 `w` 的三分之一）都不对，
所以**断点位置**可能与绘制实际折行处不同 —— 而断点是命中测试的坐标系。

## 20.3 裁定判据的修正

原判据"字段是否在文件任意 `fn draw` 里出现"**会误报**：它把 `Slider::minimum` 判成"被 draw 读"，
而真正的读取在 `impl Draw for Slider` 之外。收紧为**只看该控件自己的 `impl Draw` 块**后，
再分两类：

- **被自己的 `draw` 读 且 setter 不重绘** → 真缺陷（改了看不见）；
- 不被读 → 该字段变了本来就不影响画面，无重绘义务。

### `Slider` 那一组值得单说

它调了 `set_value(self.value)` 来重新夹紧，看上去"已经重绘了" —— 但 `set_value` 在值不变时**早退**。
所以只改边界、当前值仍在范围内时，**一次重绘都不会发生**。这正是"重绘被藏在一次会早退的委派后面"，
单看 setter 体是看不出来的。

## 20.5 冰山扫描：新写了一个"兄弟 setter 不对称"探针

`TabBar::set_tab_max_width` 的形态很特别：它紧邻的 `set_tab_min_width` **正确重绘**，
两个是同一对边界的两个端点，一个做了另一个忘了。

为此新写 `tools/probe_asymmetric_sibling_setters.py`：在**同一个 `impl` 块内**寻找
"一个 `set_X` 重绘、而它的反义/成对兄弟 `set_Y` 不重绘"。
