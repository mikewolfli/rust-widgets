## 0. 基线：HarmonyOS 目标**完全不可构建**

> 取证顺序刻意从「最朴素的命令」开始——这是第 16/17 轮共同的教训：
> 计划的取证口径决定了它能看到什么。

先确认工具链真的可用（否则后续结论会被误读为环境问题）：

```text
$ rustup target list --installed | grep ohos
aarch64-unknown-linux-ohos

$ $OHOS_SDK/native/llvm/bin/clang --version
OHOS (dev) clang version 15.0.4 (llvm-project bb5cdf0f93bfb5316dd3cc2a80d12ab829e49b43)
Target: x86_64-unknown-linux-gnu

$ ls $OHOS_SDK/native/llvm/bin/ | grep aarch64-unknown-linux-ohos
aarch64-unknown-linux-ohos-clang
aarch64-unknown-linux-ohos-clang++
```

然后跑 `status.md` 里自己写的验收命令：

```text
$ export CARGO_TARGET_AARCH64_UNKNOWN_LINUX_OHOS_LINKER=\
      $OHOS_SDK/native/llvm/bin/aarch64-unknown-linux-ohos-clang
$ cargo check --target aarch64-unknown-linux-ohos --no-default-features \
    --features "harmony controls-custom controls-native serde serde_json"
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 6.63s
```

**表面通过**。但这正是本轮最重要的方法论点：**这条命令带着 `harmony` feature**——
它验证的是「在非鸿蒙宿主上强制选鸿蒙后端」，而**真实鸿蒙应用不会带这个 feature**。
去掉它，模拟真实产物：

```text
$ cargo check --target aarch64-unknown-linux-ohos --no-default-features --features desktop
error[E0425]: cannot find value `create_native_platform` in this scope
   --> src/platform/runtime.rs:255:26
    |
255 |     PLATFORM.get_or_init(create_native_platform).as_ref()
    |                          ^^^^^^^^^^^^^^^^^^^^^^ not found in this scope
error: could not compile `rust_widgets` (lib) due to 1 previous error
```

**即：为 HarmonyOS 构建时，平台后端选择器一个定义都没有。**
不是「选错后端」，是**选不出后端**。

## 1. 根因：`target_os = "ohos"` 永不匹配

取证（`rustc` 自己报的 `cfg`，不是推测）：

```text
$ rustc --target aarch64-unknown-linux-ohos --print cfg | grep -E '^target_(os|env|family|abi)'
target_abi=""
target_env="ohos"        ← 唯一的判别字段
target_family="unix"
target_os="linux"        ← 名字叫 ohos，OS 字段却是 linux
```

OpenHarmony 的 4 个 Rust 目标（`aarch64` / `armv7` / `x86_64` / `loongarch64`
`-unknown-linux-ohos`）**全部**如此：`target_os = "linux"`，`target_env = "ohos"`。

而全库的后端选择用的是：

```text
$ grep -rn 'target_os = "ohos"' src/
src/platform/mod.rs:17:   #[cfg(any(target_os = "ohos", feature = "harmony"))]
src/platform/runtime.rs:15:  any(target_os = "ohos", feature = "harmony"),
src/platform/runtime.rs:192: any(target_os = "ohos", feature = "harmony"),
src/platform/runtime.rs:220: not(any(target_os = "ohos", feature = "harmony")),
```

**6 处字面量，没有一处能匹配。**

### 1.1 为什么它一直没被发现

三个维度**同时**挡住了它，任何一个单独成立都足以让它不可见：

| 维度 | 为何掩盖了它 |
|---|---|
| **判据口径** | `status.md` 的验收命令带 `harmony` feature → 走的是 feature 臂，`target_os` 那条根本没被求值 |
| **CI 覆盖** | `cargo test --all-features` 在 **Linux 宿主**上求值：`feature = "harmony"` 为真 → 命中，但宿主是 linux，**不是 ohos target** |
| **交叉目标** | 第 16/17 轮的交叉验证列表是 windows / wasm32 / android / iOS，**不含 ohos** |

换句话说：**`feature = "harmony"` 这个开发用开关，一直在替真实目标「代为通过」。**
这与第 16 轮 `from_platform_caps`（删了函数、漏改一个调用点）和第 17 轮 `canvas` 门控漂移
是同一个病（原则 #17「迁移幻觉」），只是这次漂移的是**目标判别字段**。

### 1.2 一个更大的隐患：Linux 臂会抢走 HarmonyOS

即使把 harmony 臂改成 `target_env`，仍有第二个冲突：三条 Linux 臂的条件是
`target_os = "linux"`，而 **OpenHarmony 也是 `target_os = "linux"`** → 两者同时命中
→ `create_native_platform` 重定义（`E0428`）。

更糟的是若只改 harmony 臂而不管 Linux 臂：在**不启用** `harmony` feature 的真实鸿蒙构建里，
Linux 臂会独占命中 → **静默选到 `LinuxPlatform`**（一个依赖 GTK 的后端，鸿蒙上根本不存在），
而这恰恰是「加载即崩」而不是「编译失败」那一类更难查的故障。

## 2. 修复

### 2.1 判别字段改为 `target_env`，并建立单一真相

新增 `src/platform/profile.rs::is_openharmony_target()`，把「鸿蒙怎么拼」这件事收进一处
（原则 #57/#58 的同一思路）：

```rust
/// `true` when this build targets OpenHarmony / HarmonyOS.
///
/// Every OpenHarmony Rust target is spelled `*-unknown-linux-ohos`. Despite the
/// name, rustc reports `target_os = "linux"` for them, so a
/// `cfg(target_os = "ohos")` test can never match. The honest discriminator is
/// `target_env`, which is exactly the field OpenHarmony's target spec overrides.
pub const fn is_openharmony_target() -> bool {
    cfg!(target_env = "ohos")
}
```

6 处选择点全部改用 `target_env = "ohos"`，并把三条 `target_os = "linux"` 臂
（`LinuxPlatform` import、Wayland import、`is_wayland_session`、两条 `create_native_platform`）
补上 `not(target_env = "ohos")`，使「鸿蒙」与「Linux」互斥。

```text
$ grep -rn 'target_os = "ohos"' src/platform/runtime.rs
203:/// targets report `target_os = "linux"`, so a `target_os = "ohos"` arm here   ← 仅注释
```

### 2.2 验证（修复前 / 修复后对照）

```text
# 修复前
$ cargo check --target aarch64-unknown-linux-ohos --no-default-features --features desktop
error[E0425]: cannot find value `create_native_platform` in this scope

# 修复后 —— 真实鸿蒙产物（不带 harmony feature）
$ cargo check --target aarch64-unknown-linux-ohos --no-default-features --features desktop
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 7.12s   （0 warning）

# 宽接触面
$ cargo check --target aarch64-unknown-linux-ohos --no-default-features \
    --features "desktop,harmony,touch,i18n,serde,serde_json,advanced-widgets,controls-custom,controls-native"
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 3.49s   （0 warning）

# 裁剪档
$ cargo check --target aarch64-unknown-linux-ohos --no-default-features --features embedded
    Finished …                                                            （0 warning）

# lint
$ cargo clippy --target aarch64-unknown-linux-ohos --no-default-features \
    --features "desktop,harmony" --all-targets -- -D warnings
```

## 3. 回归判据（**已证明能失败**，原则 #19）

新增 2 条测试：

| 测试 | 断言 |
|---|---|
| `openharmony_predicate_tracks_the_target_env_field` | `is_openharmony_target()` 恒等于 `cfg!(target_env="ohos")`；且在鸿蒙目标上 `target_os` 必须是 `linux`（`const {}` 块，编译期求值）|
| `the_serving_backend_matches_the_target_family` | **行为判据**：鸿蒙产物上服务后端必须以 `harmony` 开头；非鸿蒙宿主上不得冒充 harmony（除非 feature 要求）|

第二条刻意写成**运行时事实**而非 `cfg`：它问的是「实际在服务的是哪个后端」，
与宿主无关，因此不会像第 17 轮 §7 那样退化成「把某个宿主的配置当断言」。

**反向验证**：把 `runtime.rs` 改回历史拼法，确认判据确实会红：

```text
$ python3 -c "...replace('any(target_env = \"ohos\", ...)', 'any(target_os = \"ohos\", ...)')"
$ bash tools/check_harmony_cross.sh
error[E0425]: cannot find value `create_native_platform` in this scope
   --> src/platform/runtime.rs:255:26
（还原后）All HarmonyOS cross-target checks passed.
```

两次都如实失败/通过，说明门禁不是恒真断言。

## 4. 新增门禁：`tools/check_harmony_cross.sh`（5 步）

把 `status.md` 里那条「带 feature」的命令换成**真实产物口径**，并把前提本身钉住：

```text
[1/5] target-identification premise (aarch64-unknown-linux-ohos)
  ok: target_env=ohos, target_os=linux (so `target_env` is the discriminator)
[2/5] backend auto-selected from the target (no 'harmony' feature)
[3/5] full feature contact surface
[4/5] stripped profile
[5/5] clippy (deny warnings)
All HarmonyOS cross-target checks passed.
```

**第 1 步是本轮设计的核心**：它断言的不是「代码对不对」，而是**「前提是否仍成立」**。
若 rustc 将来把 OpenHarmony 改成 `target_os = "ohos"`，这一步会先红，
而不是等到某个后端的 cfg 悄悄失配。

**宿主门控（设计如此）**：SDK 缺失时 `exit 2` 并打印安装指引，**不冒充通过**：

```text
$ env -u OHOS_SDK bash tools/check_harmony_cross.sh
HOST-GATED: OHOS_SDK is unset or does not point at an OpenHarmony SDK
  expected a directory containing native/llvm/bin (got '<unset>')
exit=2
```

## 5. CI：新增 `harmony-cross-check` job（原为**零覆盖**）

`.github/workflows/ci.yml` 新增一个 job，共 6 步。**SDK 安装步骤经实测取证**，
不是凭 API 名称推测：

| 项 | 取证 |
|---|---|
| 镜像可达性 | `curl -I` → **HTTP 200**，`Content-Length: 3158455868` |
| 校验 | 上游 `.sha256` = `26f8e0a5…5b4cd`，与本地已解压的同版本 SDK 一致 |
| **归档结构** | `tar -tzf` → `ohos-sdk/linux/{ets,js,native,previewer,toolchains}-linux-x64-6.0.0.46-Beta1.zip` |
| **嵌套陷阱** | 归档里是**每组件一个 zip**，只解 tar 得到的是 zip 而不是头文件/二进制 |

最后一行是本步骤唯一的非显然点：若照「解 tar 即可用」的直觉写，CI 会在后续
`cargo check` 时才失败，且错误会指向「找不到 clang」而掩盖真实原因。故 CI 显式
解出 `native` 组件，并断言 `native/llvm/bin/aarch64-unknown-linux-ohos-clang` 存在。

job 结构（CI yaml 解析：`jobs=16`）：

```text
Checkout → Install Rust (aarch64-unknown-linux-ohos) → Cache cargo
  → Install OpenHarmony SDK (native toolchain)   ← 含 sha256 校验
  → Configure OpenHarmony linker
  → HarmonyOS cross-target gate                  ← 调用 tools/check_harmony_cross.sh
```

> **设计取舍**：具体检查逻辑放在**门禁脚本**里，CI 只负责准备工具链并调用它。
> 理由是同一组命令必须在「本机」与「CI」上逐字一致——第 16/17 轮反复出现的
> 「CI 与本地口径漂移」正是这样产生的。

## 6. 顺带修掉的真缺陷（原则 #2 冰山法则）

在鸿蒙 target 上跑 clippy，暴露出一个**只在 OpenHarmony 上触发**的既有缺陷：

```text
$ cargo clippy --target aarch64-unknown-linux-ohos … -- -D warnings
error: initializer for `thread_local` value can be made `const`
  --> src/widget/runtime.rs:87:1   （整个 thread_local! 块）
```

**取证：它不是本轮引入的。** 用 `git stash` 把本轮的 `src/platform/` 改动全部移开后重跑，
同一 lint 依旧报出；且它在 host / windows / android 三个目标上**均为 0 例**：

```text
$ cargo clippy … -- -D warnings | grep -c "initializer for"
desktop (host)         0
windows-msvc           0
aarch64-linux-android  0
aarch64-unknown-linux-ohos  1      ← 仅此目标
```

成因：`clippy::missing_const_for_thread_local` 建议把 `RefCell::new(HashMap::new())`
提到 `const {}`，但 `std::collections::HashMap::new()` **不是 `const fn`**——该建议在此
**不成立、照做则编译不过**。宿主的 clippy 能解析 `HashMap` 因而正确地不报；
OpenHarmony 的 std 上它解析不到，于是误报。

处置：把 `allow` 精确加在三个 cell 上（而非 crate 级），并写明「为何这个建议是错的」，
避免后人「按提示修」而把代码改坏。

## 11. 这些缺陷都与操作系统有关吗？（就地澄清，原则 #2）

**部分是。** 沿用第 16/17 轮的判据：「出问题的那行代码有没有 `cfg(target_os)`」。

### 11.1 真正与目标平台绑定

| 缺陷 | 绑定证据 |
|---|---|
| `target_os = "ohos"` 判别失效 | 判别字段本身就是平台标识；`rustc --print cfg` 是唯一权威 |
| 与 `target_os = "linux"` 臂冲突 | 同因：OpenHarmony 复用 `linux` 的 OS 名 |
| `thread_local` clippy 误报 | 仅在 OpenHarmony 的 std 上解析失败 |
| SDK 嵌套 zip 布局 | OpenHarmony 打包约定 |

### 11.2 与操作系统**无关**

| 缺陷 | 判据 |
|---|---|
| **验收命令带 feature 因而掩盖缺陷** | 这是**判据口径**问题。同一个错误（用开发开关代替真实配置）在任何平台都会掩盖同类缺陷 |
| 判别字段无单一真相（6 处字面量） | 与平台无关的重复问题（原则 #54） |
| CI 零覆盖 | 覆盖缺口，非平台缺陷 |

### 11.3 一句话

> **前三轮（macOS 取证 → Windows → Linux）扩的是「宿主」，本轮扩的是「构建目标」。**
> 三个维度的共同结论始终如一：**缺口的主体不是「某个平台特有的 bug」，
> 而是「删了旧层/换了新层、没有在全部维度上接完调用方」（原则 #17）——
> 只是这次漏掉的那个维度叫「为鸿蒙构建」。**

## 12. 结论

1. **BLUE15 在 HarmonyOS 上此前「完全不可构建」**，且这是**功能阻断项**，
   不是体验回退：`create_native_platform` 在鸿蒙目标上一个定义都不存在。
   它被隐藏的方式极具代表性——**`status.md` 自带的验收命令带着 `harmony` feature**，
   于是「开发用开关」长期替「真实目标」通过验收。

2. **根因仍是原则 #17 的同一形态，第四次**：
   - 第 16 轮：`from_platform_caps`（删了函数、漏改 1 个调用点）；
   - 第 17 轮：`canvas` 门控漂移、剪贴板未接线、Wayland 菜单缺生产者；
   - **本轮：目标判别字段写错，6 处字面量全部失效**。
   **共同点始终是「改了/加了新层，没有在全部维度上接完调用方」。**

3. **本轮产出**：1 个功能阻断项根除（鸿蒙目标从不可构建到 0 warning）、
   1 个潜在阻断项（Linux 臂抢占）消除、判别逻辑收敛为单一真相、
   1 个既有 clippy 潜伏缺陷（仅鸿蒙目标）修复、
   新增 1 个 CI job + 1 个门禁脚本（含「前提断言」这一新判据形态）、
   2 条回归测试（**已验证能失败**）、1 份状态文档与代码对齐。

4. **复验结果**：三档 profile + 5 个 feature 组合 + `--all-features` 零 warning / 零失败；
   4 个配置 clippy `-D warnings` 全通过；`cargo fmt --check` 通过；
   **门禁全部 PASS（17 个脚本）**；鸿蒙交叉目标 5/5 全绿；CI yaml 解析通过（16 jobs）。

5. **剩余不可验证项已显式登记**（§10）：鸿蒙产物的**运行时**验证需 devkit/模拟器；
   CI 下载步骤的端到端运行未在本机验证。**均不冒充完成。**
   （原登记的「其余三个鸿蒙 target 未安装」已在 **§13** 收尾：两个已验证通过，
   `loongarch64` 已取证为**不可构建且根因在 SDK**。）

6. **一句话总结**：本轮把 BLUE15 的验证面从「**3 profile × 2 宿主 × 6 feature 组合**」
   扩展到含「**1 个真实交叉目标（OpenHarmony）**」，并因此抓到前两轮**结构性不可能看见**的
   功能阻断项——因为前两轮的所有判据都在「宿主」这一维度上取值，
   而这次的缺陷只在「构建目标」这一维度上显形。

### 13.4 loongarch64：❌ 不可构建，但**两重根因都在 SDK/tier**

先把阻碍逐层剥开（每层都有原样输出，不靠推测）：

**第 1 层 — rustup 无预编译 std（Tier 3）**。已由 §13.1 取证。

**第 2 层 — SDK sysroot 没有 loongarch64 libc**：

```text
$ ls $OHOS_SDK/native/sysroot/usr/lib/
  aarch64-linux-ohos   arm-linux-ohos   x86_64-linux-ohos      ← 没有 loongarch64
$ find $OHOS_SDK -type d -name "*loong*"
  …/native/sysroot/usr/include/asm-loongarch                    ← 只有头子目录的残片
```

**第 3 层 — 用 nightly `-Zbuild-std` 绕过 std 后，连 C 头文件都不完整**：

```text
$ cargo +nightly check --target loongarch64-unknown-linux-ohos -Zbuild-std=std,panic_abort
cargo:warning=…/sysroot/usr/include/stdint.h:20:10: fatal error:
              'bits/alltypes.h' file not found
```

**第 4 层 — 即便前两层都补上，链接仍会失败**（提前把结论钉死，避免“再试一下就好”的错觉）：

```text
$ cargo +nightly build --target loongarch64-unknown-linux-ohos -Zbuild-std=std,panic_abort
ld.lld: error: cannot open crti.o: No such file or directory
ld.lld: error: cannot open crtbeginS.o: No such file or directory
ld.lld: error: unable to find library -lunwind
ld.lld: error: unable to find library -lc
ld.lld: error: cannot open crtendS.o: No such file or directory
ld.lld: error: cannot open crtn.o: No such file or directory
```

**结论**：`loongarch64-unknown-linux-ohos` 在当前 SDK（6.0.0.46 Beta1）下**无法产出可链接产物**，
且原因**全部在 SDK 打包与 rustc tier 策略**，不是本 crate 的代码缺陷——
`cargo check` 的失败点落在 `minimp3-sys`（C 依赖）的**头文件包含**，与 Rust 代码无关。

> 顺带修复了一个环境问题：本机 `nightly` 工具链当时是**损坏的**
> （`error: missing manifest in toolchain 'nightly-…'`，导致 `-Zbuild-std` 连启动都不行）。
> 已 `uninstall` + 重装（`rustup toolchain install nightly --profile minimal` →
> `rustc 1.100.0-nightly (215a8af4b 2026-09-15)`），**否则第 3/4 层根本无法取证**，
> 会误得出“nightly 不可用所以整件事做不了”的错误结论（原则 #2：先排除环境）。

### 13.5 门禁与 CI 同步升级（不只加命令，而是加**断言**）

`tools/check_harmony_cross.sh` 从 5 步扩到 6 步，且第 1 步与第 6 步是**新形态的判据**：

| 步 | 内容 | 形态 |

| [1] | **四个**目标的 `target_env`/`target_os` 前提 | 断言「前提仍成立」，而非「代码对」|
| [2]–[4] | aarch64 / armv7 / x86_64 各跑三步 | 常规构建判据 |

## 14. 第三轮：`cargo-ohos` 到位后的重新核查（用户提示「鸿蒙的 cargo.toml 要用鸿蒙的 llvm」）

用户安装 `cargo-ohos` 并提示「Cargo.toml 要用鸿蒙的 llvm」。重新核查后发现：
**提示指向的方向是对的，但真正的缺口在「环境变量名 + 链接而非仅检查」，不在 `Cargo.toml` 内容**。

### 14.1 根因一：环境变量名用错了（`OHOS_SDK` vs `OHOS_SDK_NATIVE`）

`cargo-ohos` 读的是 **`OHOS_SDK_NATIVE`**，且它必须指向 SDK 的 **`native` 子目录**：

```text
$ grep -n "OHOS_SDK_NATIVE" ~/.cargo/registry/src/…/cargo-ohos-0.3.2/src/sdk.rs
20:    "OHOS_SDK_NATIVE",
…
$ cargo ohos env -t aarch64   # 正确设置后
"OHOS_SDK_NATIVE": "/home/mikeli/harmonypc/ohos-sdk/linux/native",
"CARGO_OHOS_API_LEVEL": "20",
```

而此前（§1–§13）用的是 `OHOS_SDK=.../ohos-sdk/linux`（**上级目录**），并且靠**手写**环境变量
模拟交叉环境。两者差别不是“写法不同”，而是**手写的那套漏掉了 sysroot**：

| | 手写（之前） | `cargo ohos`（现在） |
|---|---|---|
| 链接器 | `CARGO_TARGET_*_LINKER` 指向 per-target clang wrapper | `…/native/llvm/bin/clang` + 显式 `--target`/`--sysroot` |
| C 依赖编译 | **无 sysroot、无 `-D__MUSL__`** | `TARGET_CFLAGS` 含 `--sysroot=… -D__MUSL__` |
| bindgen | 未设置 | `BINDGEN_EXTRA_CLANG_ARGS_*` |
| pkg-config | 未设置 | `PKG_CONFIG_PATH_*` / `PKG_CONFIG_SYSROOT_DIR_*` |
| cmake | 未设置 | `CMAKE_TOOLCHAIN_FILE_*`（自动生成 `ohos.toolchain.cmake`）|

### 14.2 根因二：之前只跑到 `check`，**从未真正链接**

这是本轮最重要的方法论修正。§1–§13 全部用的是 `cargo check`，而 **`check` 不链接**——
所以它**结构上不可能**发现「C 依赖拿着宿主头文件编译」这类问题：

```text
错误形态 1（手写环境、只设 linker）：
  Relocations in generic ELF (EM: 183)  /  file in wrong format   ← ld 读不了异构对象

错误形态 2（无 sysroot）：
  …/sysroot/usr/include/stdint.h:20:10: fatal error:
  'bits/alltypes.h' file not found                                ← 拿了不全的头文件
```

换成 `cargo ohos build` 后，**三个目标全部产出真实的 `.so`**，且 ELF machine 与 triple 一致：

```text
aarch64-unknown-linux-ohos  librust_widgets.so  Machine=AArch64                        275M  ✓
armv7-unknown-linux-ohos    librust_widgets.so  Machine=ARM                            252M  ✓
x86_64-unknown-linux-ohos   librust_widgets.so  Machine=Advanced Micro Devices X86-64  277M  ✓
```

并确认它是**真的鸿蒙产物**（而非恰好能链接的宿主库）：

```text
$ llvm-readelf -h target/aarch64-unknown-linux-ohos/debug/librust_widgets.so
  Class:  ELF64      Machine: AArch64      Type: DYN (Shared object file)
$ llvm-readelf -d …
  NEEDED  libtime_service_ndk.so      ← OpenHarmony 系统库（由 `time` crate 的 ohos 支持引入）
  NEEDED  libc.so
```

> `libtime_service_ndk.so` 是决定性判据：它是 **OpenHarmony 专有** NDK 库，
> 宿主 Linux 上不存在——能链接出这个依赖，说明整条链路真的走对了。

### 14.3 `Cargo.toml`：确实是错的，但错法与预期不同

用户的提示把我引到了 `Cargo.toml`。核查结果：**那里确实有一个死配置**，
但它不是「该用鸿蒙 llvm 却没用」，而是**一个永远不可能匹配的空依赖段**：

```toml
[target.'cfg(target_os = "harmony")'.dependencies]      ← 第 424 行，下面是空的
```

**三重取证它永不生效**：

```text
① rustc 实测：鸿蒙目标报 target_os="linux"（四个目标全部），"harmony" 从不是 target_os 的值
② 该段**无任何内容**（`awk NR==424,425` 只见标题行与空行）
③ 全仓引用只有 Cargo.toml 自身 + `docs/plans/blue10.md:233` 把它登记为已发现的缺陷
```

且**实测鸿蒙后端根本不需要额外 crate**：它链接的 NDK 库
（`libtime_service_ndk.so`）由工具链 sysroot 解析，`cargo ohos` 已把 sysroot 指对。

处置：删除该死段，原位改为注释说明「为何此处故意没有鸿蒙依赖段」，
防止后人「好心」再加一个 `cfg(target_os = "harmony")` 的段（同样无效）。
同时在门禁 [1] 步新增反向断言：任一 ohos 目标的 `target_os` 若变成 `"harmony"`，即报错提醒注释已过时。

### 14.4 门禁升级：从 `check` 到 `build` + **架构校验**

`tools/check_harmony_cross.sh` 新增 **[4b]** 步：不只是 `cargo ohos build`，
还要用 `llvm-readelf` 读出产物的 `Machine` **与 triple 对账**，不符即 FAIL。

理由：如果只断言「build 成功」，一个被静默换成宿主工具链的构建仍会通过；
而**机器类型对账**能抓住它。这与第 17 轮 `gtk-native` 的
「注入真回归，确认门禁会红」是同一思路。

```text
[4b/6] aarch64-unknown-linux-ohos: build + verify the linked artifact is the right machine
  librust_widgets.so: Machine=AArch64, 275M  ✓
…
[6/6] loongarch64-unknown-linux-ohos: Tier 3 target (no prebuilt std, SDK libc incomplete)
  rustc knows the triple — Tier 3, so no prebuilt std ✓
  rustup has no std for it (Tier 3: 'official builds are not available') ✓
All HarmonyOS cross-target checks passed.          GATE_EXIT=0
```

**环境变量兼容性**：门禁接受两种写法（`OHOS_SDK_NATIVE` 为准，或从旧的 `OHOS_SDK` 推导出 `native/`），
并已在两种方式下实跑验证。

### 14.5 与 `cargo-ohos` 的**独立互证**（原则 #19）

`cargo-ohos` 源码里对 `loongarch64` 的注释，**独立地证实了 §13 的结论**——
即那是 SDK 的限制，而不是本 crate 的问题：

```rust
// cargo-ohos-0.3.2/src/target.rs:74
/// `loongarch64` is not supported in the latest SDK (CMake) at the time of
/// writing. This will cause a configure fail in the CMake, if CMake is
/// used, but should start working once the upstream toolchain file supports
/// LoongArch64.
```

即：§13 我从「rustup 无 std + SDK 无 libc + 头文件不全」三层实测得出「不可构建」，
现由一个**独立的第三方工具**（面向鸿蒙的官方生态工具）在源码中写下同一结论。
两条互不依赖的证据链指向同一事实。

**Phase I-1 — 焦点接线（`FocusManager` 成为唯一真相）**

**Phase I-2 — 命中测试（坐标 → 控件）**

新增 `widget_at(root, point)` 与 `dispatch_pointer_event(root, event, point)`：
沿 `Widget::children()` 逐层下钻，**后加入的兄弟优先**（与渲染“后画在上”一致），
跳过隐藏控件，返回**最深的命中控件**。

> **本轮最重要的发现（原计划的方向是错的）**：
> 我最初按「父相对坐标」实现（下降时逐层减去子控件原点），测试失败。
> 追到根后发现：**本库的控件几何是绝对的**，不是相对的——
> `src/layout/box_layout.rs:158-173` 给子控件的是**由父绝对矩形派生的绝对 rect**，
> 且控件自身调 `contains_point` 时传的是**原始事件坐标**
> （`video_player.rs:475,495` 用 `rect.contains_point(*pos)`）。
> 用 `Label` 单测坐实了这一点：
>
> ```text
> Label::new(rect(150,10,100,50)).contains_point((10,10))   -> false
> Label::new(rect(150,10,100,50)).contains_point((159,19))  -> true   ← 绝对坐标
> ```
>
> 所以命中测试**不做任何坐标变换**；若按“相对”写，每个嵌套控件都会偏移一个父原点。
> 这是**取证优先于直觉**的又一例证（原则 #2/#19）。

### 15.4 平台接线（Phase I-3，本轮完成）

上一轮把"焦点与命中测试"的**引擎**修好并测住，但**传动轴没装**。本轮装上了。

**新增 `Platform::route_pointer_event`**（语义化名字，不带机制词汇，符合 #52）：

```rust
fn route_pointer_event(&self, root, event, point) -> bool {
    // 默认体：按控件树命中测试后投递
    crate::widget::runtime::dispatch_pointer_event(root, event, point)
}
```

放在 `Platform` trait 上而不是写在 canvas 里，是因为：
① 上层不需要知道"用什么机制投递"；② `mini` 档没有 widget registry，默认体诚实返回 `false`

关键细节（都是“做错就静默错位”的点）：

- **Windows 的 origin 必须随 `resize_canvas` 更新**，否则移动后命中测试会偏移一个 resize 差值；

### 15.10 移动家族（iOS / Android / HarmonyOS / mobile）的 widget 承载面（本轮完成）

**取证**：四个移动家族后端都**没有实现** `mount_surface`，继承 trait 默认体并继承默认的
`supports_surfaces() == false`。

```text
$ grep -n "mount_surface\|supports_surfaces" src/platform/{mobile.rs,ios,android,harmony}/…
src/platform/harmony/platform_impl.rs:170:  fn supports_surfaces(&self) -> bool { false }
（其余三个：无任何 surface 方法）
```

**为何这是真缺口而不是“诚实的能力缺失”**：它们的 `attach_to_native_view(handle)`
已经记录了宿主交出的原生视图（`mobile.rs:300`），而 `render_frame(id, size, clear)`
是**纯计算**（`widget/runtime.rs:701`，宿主来拉帧）。
即：宿主本来就能呈现像素，缺的只是“哪些控件正在被显示 + 何时变脏”这本账。

**实现（共享一份，不复制四遍——原则 #54）**：在 `BackendState` 上新增：

| 方法 | 语义 |
|---|---|
| `mount_surface_record(id, rect)` | 记录 id 在某个表面范围内被显示；**未知 id 拒绝** |
| `resize_surface_record` / `surface_rect` | 改/读该范围 |
| `unmount_surface_record` | 忘记它，**并清掉其待重绘请求** |
| `invalidate_surface_record` | 入队一次重绘，**合并重复**（同一帧内两次 = 一次）|
| `take_pending_repaint` / `pending_repaint_count` | 宿主按序抽干 |

四个后端各自覆写 `mount_surface` / `resize_surface` / `unmount_surface` /
`invalidate_surface` / `supports_surfaces`，全部委托这一份实现。

**重点：这是“能力”而不是“声明”**。把 `supports_surfaces()` 从 `false` 改为 `true`
本身就是一次**能力声称**，所以每个后端都配了实跑判据：

| 测试 | 钉住的行为 |
|---|---|
| Harmony `widget_surfaces_are_advertised_and_round_trip` | 挂载→读回 rect→失效→**合并**→抽取→resize→卸载 |
| iOS `ios_hosts_widget_surfaces_and_queues_repaints` | 同上链路 |
| Android `android_hosts_widget_surfaces_and_queues_repaints` | 同上链路（含 resize）|
| mobile `mobile_backend_hosts_widget_surfaces` | 同上链路 + 合并断言 |
| 各自 `*_refuses_a_surface_for_an_unknown_widget` | 未知 id 一律拒绝，且不污染计数 |

> **一处诚实性修正**：Harmony 原本有一条测试

### 15.11 剩余的“零调用者”公共组件（本轮完成）

#### A. `IdleTask` 接入事件循环

`EventLoop` 新增 `idle_tasks: Vec<IdleTask>`，在 **Phase 1e** 与 Idle 事件**共用同一个 5ms 预算**：

```text
Phase 0  原生事件泵
Phase 1a 抽干队列 → 按 High/Normal/Idle 分桶
Phase 1b High 优先
Phase 1c Normal 次之
Phase 1d Idle 事件（5ms 预算）
Phase 1e Idle 任务 tick（同一个 5ms 预算）← 本轮新增
Phase 2  无工作则 sleep 1ms
```

配套 API：`add_idle_task` / `remove_idle_task` / `idle_task_count`。
两个刻意的设计：

1. **`start()` 后再注册返回 `false`**：任务在 `start` 时移到 loop 线程，
   后注册的任务永远跑不了；接受它就等于“报告成功而实际无事发生”。
2. **相同 id 重复注册是替换而非累加**：否则一个重复注册会让回调发两次。
3. **任务 panic 不拖垮 loop**：用 `catch_unwind` 包住，并记录任务 id。

新增 `set_focus_traversal(strategy)` 与 `set_focusable_position(id, x, y)`，

位置没有存储价值（也就是“不假装记录成功”）。

### 16.6 🔴 顺带抓出的两个真缺陷（原则 #2 冰山法则）

核验「`Profile and optimize file I/O`（已完成）」时复跑打印测试，**发现它其实是红的**。

#### A. `spawn_print_job` 提交后立即删除作业文件 → **静默丢纸**

`print_to_printer` 的顺序是「写文件 → 提交 → **删除文件**」。而上游提交用的是：

```rust
// 修复前
match std::process::Command::new(program).arg(job_file).spawn() {
    Ok(_child) => return Ok(()),      // ← 子进程刚被 fork，还没读文件
```

`spawn` 只保证**进程已创建**，不保证它读过文件。于是**有 `lpr` 的机器上每一次打印都丢**，
而函数返回 `Ok(())` —— 失败只在 spooler 自己的 stderr 里。

**反向注入验证**（原则 #19）：造一个假的 `lpr`（先 `sleep 0.2` 再读文件），
用**调用方原样的下一步**删除文件：

```text
# 修复前（spawn-only）
spawn_print_job -> Ok(())
remove_file     -> Ok(())
spooler read    -> ""            ← 什么都没读到
lpr: cannot open /tmp/rw_spool_probe/job.txt
RESULT: FAIL

# 修复后（等待子进程）
spawn_print_job -> Ok(())
remove_file     -> Ok(())
spooler read    -> "rust_widgets print job\npage:1\n"
RESULT: PASS
```

**修复**：改用 `.output()` 等待子进程结束，并**校验退出状态**——
spooler 拒绝作业时把它的 stderr 带回给调用方，而不是伪装成功。
同时把「未安装」与「拒绝作业」区分开（`SpoolerFailure::{Unavailable, Rejected}`），
因为「两个都没有」应当报 `no print spooler found`，而不是报某个程序拒绝。

#### B. 作业文件名在使用者进程内不唯一 → **并发互相覆盖**

第 18 轮给文件名加了 `pid`，解决的是**跨进程**冲突。但同一进程内
`毫秒 + pid` 仍然碰撞。这不是理论问题：`cargo test` 并行跑两条测试即复现。

```text
$ for i in 1..6; do cargo test … -q print_job 2>&1 | grep "test result"; done
test result: ok. 7 passed; 0 failed
...
[2] FAILED. 6 passed; 1 failed     ← 间歇
...
[4] FAILED. 6 passed; 1 failed     ← 且失败点还会变（读不到文件 / 读到别人的内容）
```

失败点漂移正说明是**共享路径**：一个测试**打开并截断**另一个测试正在读的文件。

**修复**：文件名补 `AtomicU64` 进程内序号，并用 `create_new(true)` 打开——
名字碰撞从此是**报错**而非静默覆盖（原则 #12：不允许假修复）。

```rust
static JOB_SEQ: AtomicU64 = AtomicU64::new(0);
path.push(format!("rw_print_job_{}_{ts}_{seq}.txt", std::process::id()));
opts.write(true).create_new(true);
```

**反向注入验证**：把序号去掉、`create_new` 改回 `truncate` 后，
**新加的回归测试当场失败**并指出正确原因：

```text
print_job_files_written_back_to_back_do_not_share_a_path_or_a_body --- FAILED
assertion `left != right` failed: back-to-back jobs must not share a path
print_job_file_streams_header_and_commands --- FAILED
```

#### C. 一个「测试把 bug 判为可接受」的形态

`print_job_reports_failure_for_a_missing_spooler_or_file` 原文是：

```rust
// Either there is no spooler (an error) or there is one and it rejected
// the missing file asynchronously (Ok from `spawn`). Both are acceptable;
// what must not happen is a panic.
let _ = result;
```

它**接受了任何结果**，理由正是那个已被证伪的假设（「spooler 异步拒绝文件」）。
这个宽容度就是 A 能长期存活的直接原因。已改为断言 `is_err()`，并新增一条
**用假 spooler 正向钉住「返回前必须读完」**的测试。

### 18.7 关于那 3186 条 rustdoc 警告（登记，不冒充完成）

`#![allow(missing_docs)]` **保持原样**。原因不是「不做」，而是：

1. **它不是用户级 API 文档**（用户已指明后者在 cookbook），价值低于 cookbook；

3. 与 cookbook 的缺口不同，它不会导致用户照错文档写代码。

若将来要做，正确做法就是本轮的教训反过来用：**先让编译器看着它**
