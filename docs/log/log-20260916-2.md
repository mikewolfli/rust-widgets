## 0. 基线：HarmonyOS 目标**完全不可构建**

> 取证顺序刻意从「最朴素的命令」开始——这是第 16/17 轮共同的教训：
> 计划的取证口径决定了它能看到什么。

先确认工具链真的可用（否则后续结论会被误读为环境问题）：

```text
$ rustup target list --installed | grep ohos
aarch64-unknown-linux-ohos

$ $OHOS_SDK/native/llvm/bin/clang --version
OHOS (dev) clang version 15.0.4 (llvm-project bb5cdf0f93bfb5316dd3cc2a80d12ab829e49b43)
Target: x86_64-unknown-linux-gnu

$ ls $OHOS_SDK/native/llvm/bin/ | grep aarch64-unknown-linux-ohos
aarch64-unknown-linux-ohos-clang
aarch64-unknown-linux-ohos-clang++
```

然后跑 `status.md` 里自己写的验收命令：

```text
$ export CARGO_TARGET_AARCH64_UNKNOWN_LINUX_OHOS_LINKER=\
      $OHOS_SDK/native/llvm/bin/aarch64-unknown-linux-ohos-clang
$ cargo check --target aarch64-unknown-linux-ohos --no-default-features \
    --features "harmony controls-custom controls-native serde serde_json"
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 6.63s
```

**表面通过**。但这正是本轮最重要的方法论点：**这条命令带着 `harmony` feature**——
它验证的是「在非鸿蒙宿主上强制选鸿蒙后端」，而**真实鸿蒙应用不会带这个 feature**。
去掉它，模拟真实产物：

```text
$ cargo check --target aarch64-unknown-linux-ohos --no-default-features --features desktop
error[E0425]: cannot find value `create_native_platform` in this scope
   --> src/platform/runtime.rs:255:26
    |
255 |     PLATFORM.get_or_init(create_native_platform).as_ref()
    |                          ^^^^^^^^^^^^^^^^^^^^^^ not found in this scope
error: could not compile `rust_widgets` (lib) due to 1 previous error
```

**即：为 HarmonyOS 构建时，平台后端选择器一个定义都没有。**
不是「选错后端」，是**选不出后端**。

## 1. 根因：`target_os = "ohos"` 永不匹配

取证（`rustc` 自己报的 `cfg`，不是推测）：

```text
$ rustc --target aarch64-unknown-linux-ohos --print cfg | grep -E '^target_(os|env|family|abi)'
target_abi=""
target_env="ohos"        ← 唯一的判别字段
target_family="unix"
target_os="linux"        ← 名字叫 ohos，OS 字段却是 linux
```

OpenHarmony 的 4 个 Rust 目标（`aarch64` / `armv7` / `x86_64` / `loongarch64`
`-unknown-linux-ohos`）**全部**如此：`target_os = "linux"`，`target_env = "ohos"`。

而全库的后端选择用的是：

```text
$ grep -rn 'target_os = "ohos"' src/
src/platform/mod.rs:17:   #[cfg(any(target_os = "ohos", feature = "harmony"))]
src/platform/runtime.rs:15:  any(target_os = "ohos", feature = "harmony"),
src/platform/runtime.rs:192: any(target_os = "ohos", feature = "harmony"),
src/platform/runtime.rs:220: not(any(target_os = "ohos", feature = "harmony")),
```

**6 处字面量，没有一处能匹配。**

### 1.1 为什么它一直没被发现

三个维度**同时**挡住了它，任何一个单独成立都足以让它不可见：

| 维度 | 为何掩盖了它 |
|---|---|
| **判据口径** | `status.md` 的验收命令带 `harmony` feature → 走的是 feature 臂，`target_os` 那条根本没被求值 |
| **CI 覆盖** | `cargo test --all-features` 在 **Linux 宿主**上求值：`feature = "harmony"` 为真 → 命中，但宿主是 linux，**不是 ohos target** |
| **交叉目标** | 第 16/17 轮的交叉验证列表是 windows / wasm32 / android / iOS，**不含 ohos** |

换句话说：**`feature = "harmony"` 这个开发用开关，一直在替真实目标「代为通过」。**
这与第 16 轮 `from_platform_caps`（删了函数、漏改一个调用点）和第 17 轮 `canvas` 门控漂移
是同一个病（原则 #17「迁移幻觉」），只是这次漂移的是**目标判别字段**。

### 1.2 一个更大的隐患：Linux 臂会抢走 HarmonyOS

即使把 harmony 臂改成 `target_env`，仍有第二个冲突：三条 Linux 臂的条件是
`target_os = "linux"`，而 **OpenHarmony 也是 `target_os = "linux"`** → 两者同时命中
→ `create_native_platform` 重定义（`E0428`）。

更糟的是若只改 harmony 臂而不管 Linux 臂：在**不启用** `harmony` feature 的真实鸿蒙构建里，
Linux 臂会独占命中 → **静默选到 `LinuxPlatform`**（一个依赖 GTK 的后端，鸿蒙上根本不存在），
而这恰恰是「加载即崩」而不是「编译失败」那一类更难查的故障。

## 2. 修复

### 2.1 判别字段改为 `target_env`，并建立单一真相

新增 `src/platform/profile.rs::is_openharmony_target()`，把「鸿蒙怎么拼」这件事收进一处
（原则 #57/#58 的同一思路）：

```rust
/// `true` when this build targets OpenHarmony / HarmonyOS.
///
/// Every OpenHarmony Rust target is spelled `*-unknown-linux-ohos`. Despite the
/// name, rustc reports `target_os = "linux"` for them, so a
/// `cfg(target_os = "ohos")` test can never match. The honest discriminator is
/// `target_env`, which is exactly the field OpenHarmony's target spec overrides.
pub const fn is_openharmony_target() -> bool {
    cfg!(target_env = "ohos")
}
```

6 处选择点全部改用 `target_env = "ohos"`，并把三条 `target_os = "linux"` 臂
（`LinuxPlatform` import、Wayland import、`is_wayland_session`、两条 `create_native_platform`）
补上 `not(target_env = "ohos")`，使「鸿蒙」与「Linux」互斥。

```text
$ grep -rn 'target_os = "ohos"' src/platform/runtime.rs
203:/// targets report `target_os = "linux"`, so a `target_os = "ohos"` arm here   ← 仅注释
```

### 2.2 验证（修复前 / 修复后对照）

```text
# 修复前
$ cargo check --target aarch64-unknown-linux-ohos --no-default-features --features desktop
error[E0425]: cannot find value `create_native_platform` in this scope

# 修复后 —— 真实鸿蒙产物（不带 harmony feature）
$ cargo check --target aarch64-unknown-linux-ohos --no-default-features --features desktop
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 7.12s   （0 warning）

# 宽接触面
$ cargo check --target aarch64-unknown-linux-ohos --no-default-features \
    --features "desktop,harmony,touch,i18n,serde,serde_json,advanced-widgets,controls-custom,controls-native"
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 3.49s   （0 warning）

# 裁剪档
$ cargo check --target aarch64-unknown-linux-ohos --no-default-features --features embedded
    Finished …                                                            （0 warning）

# lint
$ cargo clippy --target aarch64-unknown-linux-ohos --no-default-features \
    --features "desktop,harmony" --all-targets -- -D warnings
```

## 3. 回归判据（**已证明能失败**，原则 #19）

新增 2 条测试：

| 测试 | 断言 |
|---|---|
| `openharmony_predicate_tracks_the_target_env_field` | `is_openharmony_target()` 恒等于 `cfg!(target_env="ohos")`；且在鸿蒙目标上 `target_os` 必须是 `linux`（`const {}` 块，编译期求值）|
| `the_serving_backend_matches_the_target_family` | **行为判据**：鸿蒙产物上服务后端必须以 `harmony` 开头；非鸿蒙宿主上不得冒充 harmony（除非 feature 要求）|

第二条刻意写成**运行时事实**而非 `cfg`：它问的是「实际在服务的是哪个后端」，
与宿主无关，因此不会像第 17 轮 §7 那样退化成「把某个宿主的配置当断言」。

**反向验证**：把 `runtime.rs` 改回历史拼法，确认判据确实会红：

```text
$ python3 -c "...replace('any(target_env = \"ohos\", ...)', 'any(target_os = \"ohos\", ...)')"
$ bash tools/check_harmony_cross.sh
error[E0425]: cannot find value `create_native_platform` in this scope
   --> src/platform/runtime.rs:255:26
（还原后）All HarmonyOS cross-target checks passed.
```

两次都如实失败/通过，说明门禁不是恒真断言。

## 4. 新增门禁：`tools/check_harmony_cross.sh`（5 步）

把 `status.md` 里那条「带 feature」的命令换成**真实产物口径**，并把前提本身钉住：

```text
[1/5] target-identification premise (aarch64-unknown-linux-ohos)
  ok: target_env=ohos, target_os=linux (so `target_env` is the discriminator)
[2/5] backend auto-selected from the target (no 'harmony' feature)
[3/5] full feature contact surface
[4/5] stripped profile
[5/5] clippy (deny warnings)
All HarmonyOS cross-target checks passed.
```

**第 1 步是本轮设计的核心**：它断言的不是「代码对不对」，而是**「前提是否仍成立」**。
若 rustc 将来把 OpenHarmony 改成 `target_os = "ohos"`，这一步会先红，
而不是等到某个后端的 cfg 悄悄失配。

**宿主门控（设计如此）**：SDK 缺失时 `exit 2` 并打印安装指引，**不冒充通过**：

```text
$ env -u OHOS_SDK bash tools/check_harmony_cross.sh
HOST-GATED: OHOS_SDK is unset or does not point at an OpenHarmony SDK
  expected a directory containing native/llvm/bin (got '<unset>')
exit=2
```

## 5. CI：新增 `harmony-cross-check` job（原为**零覆盖**）

`.github/workflows/ci.yml` 新增一个 job，共 6 步。**SDK 安装步骤经实测取证**，
不是凭 API 名称推测：

| 项 | 取证 |
|---|---|
| 镜像可达性 | `curl -I` → **HTTP 200**，`Content-Length: 3158455868` |
| 校验 | 上游 `.sha256` = `26f8e0a5…5b4cd`，与本地已解压的同版本 SDK 一致 |
| **归档结构** | `tar -tzf` → `ohos-sdk/linux/{ets,js,native,previewer,toolchains}-linux-x64-6.0.0.46-Beta1.zip` |
| **嵌套陷阱** | 归档里是**每组件一个 zip**，只解 tar 得到的是 zip 而不是头文件/二进制 |

最后一行是本步骤唯一的非显然点：若照「解 tar 即可用」的直觉写，CI 会在后续
`cargo check` 时才失败，且错误会指向「找不到 clang」而掩盖真实原因。故 CI 显式
解出 `native` 组件，并断言 `native/llvm/bin/aarch64-unknown-linux-ohos-clang` 存在。

job 结构（CI yaml 解析：`jobs=16`）：

```text
Checkout → Install Rust (aarch64-unknown-linux-ohos) → Cache cargo
  → Install OpenHarmony SDK (native toolchain)   ← 含 sha256 校验
  → Configure OpenHarmony linker
  → HarmonyOS cross-target gate                  ← 调用 tools/check_harmony_cross.sh
```

> **设计取舍**：具体检查逻辑放在**门禁脚本**里，CI 只负责准备工具链并调用它。
> 理由是同一组命令必须在「本机」与「CI」上逐字一致——第 16/17 轮反复出现的
> 「CI 与本地口径漂移」正是这样产生的。

## 6. 顺带修掉的真缺陷（原则 #2 冰山法则）

在鸿蒙 target 上跑 clippy，暴露出一个**只在 OpenHarmony 上触发**的既有缺陷：

```text
$ cargo clippy --target aarch64-unknown-linux-ohos … -- -D warnings
error: initializer for `thread_local` value can be made `const`
  --> src/widget/runtime.rs:87:1   （整个 thread_local! 块）
```

**取证：它不是本轮引入的。** 用 `git stash` 把本轮的 `src/platform/` 改动全部移开后重跑，
同一 lint 依旧报出；且它在 host / windows / android 三个目标上**均为 0 例**：

```text
$ cargo clippy … -- -D warnings | grep -c "initializer for"
desktop (host)         0
windows-msvc           0
aarch64-linux-android  0
aarch64-unknown-linux-ohos  1      ← 仅此目标
```

成因：`clippy::missing_const_for_thread_local` 建议把 `RefCell::new(HashMap::new())`
提到 `const {}`，但 `std::collections::HashMap::new()` **不是 `const fn`**——该建议在此
**不成立、照做则编译不过**。宿主的 clippy 能解析 `HashMap` 因而正确地不报；
OpenHarmony 的 std 上它解析不到，于是误报。

处置：把 `allow` 精确加在三个 cell 上（而非 crate 级），并写明「为何这个建议是错的」，
避免后人「按提示修」而把代码改坏。

## 11. 这些缺陷都与操作系统有关吗？（就地澄清，原则 #2）

**部分是。** 沿用第 16/17 轮的判据：「出问题的那行代码有没有 `cfg(target_os)`」。

### 11.1 真正与目标平台绑定

| 缺陷 | 绑定证据 |
|---|---|
| `target_os = "ohos"` 判别失效 | 判别字段本身就是平台标识；`rustc --print cfg` 是唯一权威 |
| 与 `target_os = "linux"` 臂冲突 | 同因：OpenHarmony 复用 `linux` 的 OS 名 |
| `thread_local` clippy 误报 | 仅在 OpenHarmony 的 std 上解析失败 |
| SDK 嵌套 zip 布局 | OpenHarmony 打包约定 |

### 11.2 与操作系统**无关**

| 缺陷 | 判据 |
|---|---|
| **验收命令带 feature 因而掩盖缺陷** | 这是**判据口径**问题。同一个错误（用开发开关代替真实配置）在任何平台都会掩盖同类缺陷 |
| 判别字段无单一真相（6 处字面量） | 与平台无关的重复问题（原则 #54） |
| CI 零覆盖 | 覆盖缺口，非平台缺陷 |

### 11.3 一句话

> **前三轮（macOS 取证 → Windows → Linux）扩的是「宿主」，本轮扩的是「构建目标」。**
> 三个维度的共同结论始终如一：**缺口的主体不是「某个平台特有的 bug」，
> 而是「删了旧层/换了新层、没有在全部维度上接完调用方」（原则 #17）——
> 只是这次漏掉的那个维度叫「为鸿蒙构建」。**

---

## 12. 结论

1. **BLUE15 在 HarmonyOS 上此前「完全不可构建」**，且这是**功能阻断项**，
   不是体验回退：`create_native_platform` 在鸿蒙目标上一个定义都不存在。
   它被隐藏的方式极具代表性——**`status.md` 自带的验收命令带着 `harmony` feature**，
   于是「开发用开关」长期替「真实目标」通过验收。

2. **根因仍是原则 #17 的同一形态，第四次**：
   - 第 16 轮：`from_platform_caps`（删了函数、漏改 1 个调用点）；
   - 第 17 轮：`canvas` 门控漂移、剪贴板未接线、Wayland 菜单缺生产者；
   - **本轮：目标判别字段写错，6 处字面量全部失效**。
   **共同点始终是「改了/加了新层，没有在全部维度上接完调用方」。**

3. **本轮产出**：1 个功能阻断项根除（鸿蒙目标从不可构建到 0 warning）、
   1 个潜在阻断项（Linux 臂抢占）消除、判别逻辑收敛为单一真相、
   1 个既有 clippy 潜伏缺陷（仅鸿蒙目标）修复、
   新增 1 个 CI job + 1 个门禁脚本（含「前提断言」这一新判据形态）、
   2 条回归测试（**已验证能失败**）、1 份状态文档与代码对齐。

4. **复验结果**：三档 profile + 5 个 feature 组合 + `--all-features` 零 warning / 零失败；
   4 个配置 clippy `-D warnings` 全通过；`cargo fmt --check` 通过；
   **门禁全部 PASS（17 个脚本）**；鸿蒙交叉目标 5/5 全绿；CI yaml 解析通过（16 jobs）。

5. **剩余不可验证项已显式登记**（§10）：鸿蒙产物的**运行时**验证需 devkit/模拟器；
   `armv7`/`x86_64`/`loongarch64` 鸿蒙目标未安装；CI 下载步骤的端到端运行未在本机验证。
   **均不冒充完成。**

6. **一句话总结**：本轮把 BLUE15 的验证面从「**3 profile × 2 宿主 × 6 feature 组合**」
   扩展到含「**1 个真实交叉目标（OpenHarmony）**」，并因此抓到前两轮**结构性不可能看见**的
   功能阻断项——因为前两轮的所有判据都在「宿主」这一维度上取值，
   而这次的缺陷只在「构建目标」这一维度上显形。
