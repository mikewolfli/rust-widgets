## 3. 发现并修复的真实缺陷（六类）

### 3.1 JS 引擎：文档承诺了「算术」，实际 `1 + 2` 返回 `undefined` 🔴

**发现路径**：我在为第 5 层写「JS 能力不受影响」的测试时，断言 `evaluate_javascript("1 + 2")`
返回 `Number(3.0)`，测试失败。

**取证**（写临时探针，逐个输入实跑）：

```
42                   -> Ok(Number(42.0))
1 + 2                -> Ok(Undefined)      <-- 文档说支持算术
1+2                  -> Ok(Undefined)
var a = 3; a + 1     -> Ok(Undefined)
(1 + 2) * 3          -> Ok(Undefined)
```

**根因**：`eval_stmt` 的兜底是 `parse_value`，而它**只解析字面量**：`"1 + 2"` 不是数字、
不是变量名，于是落到 `JsValue::Undefined`。`src/web/js_engine.rs` 的模块文档写着
「supports … `parseInt`, `parseFloat` … 但没有原型查找、没有闭包」——**算术从未被实现，
而读者会认为它有**。这与 BLUE20 第 2 层要抓的「声明与实现不一致」是同一类，
只是发生在文档与代码之间。

**修复**：补一个真正的表达式求值器（`eval_expression` + `find_top_level_operator` +
`apply_operator` + `split_top_level` + `parse_call`）：

- 优先级：`||` → `&&` → `== != === !==` → `< <= > >=` → `+ -` → `* / %` → 一元 `- !`；
- 结合性：`find_top_level_operator` **从右往左**扫描，保证 `1 - 2 - 3` 算作 `(1-2)-3`；
- 一元判定：`-3 + 1` 的 `-` 前面没有操作数，跳过，不在 index 0 处分割；
- `+` 在任一侧为字符串时做拼接（ECMAScript 规则）；
- 短路：`&&`/`||` 不计算不必要的一侧，且返回**操作数本身**而非布尔。

**修复过程中我自己引入了两个缺陷，也一并修掉**：

| 缺陷 | 现象 | 根因 | 修法 |
|---|---|---|---|
| 函数体无限递归 | `function add(a,b){return a+b;}` → **栈溢出**（不是报错） | `eval_block` 切分出「单块且等于输入」时又去调 `evaluate`，后者见 `;` 再进 `eval_block` | 单块情形改走 `eval_stmt`（块包装没带来信息） |
| `1 == 1` 被当成赋值 | 返回 `Undefined` | `evaluate` 把无 `;` 的脚本交给 `eval_stmt`，其兜底 `find('=')` 命中 `==` 的第一个 `=` | 加 `starts_a_statement()` 路由：语句形态走 `eval_stmt`，其余走表达式求值器 |

**验证**（21 个新测试 + 追加到 `web::js_engine`）：

```
arithmetic_evaluates_instead_of_returning_undefined   ok   (10 组：+ - * / %、括号、结合性、一元)
comparison_is_not_mistaken_for_a_declaration          ok   (8 组：== != < <= > >=)
every_statement_in_a_script_runs                      ok
string_concatenation_and_variable_lookup_agree        ok
a_function_body_does_not_recurse_forever              ok
logical_operators_short_circuit_and_yield_an_operand  ok
test result: ok. 20 passed
```

**文档同步**：模块文档补上「支持算术/比较/逻辑运算符」并**新增一节「What it does not do」**，
写明 `f(a + 1)` 这类「参数本身是表达式」不求值、字符串无转义、无箭头函数——
把边界写在文档里，而不是留给读者猜。

### 3.2 三个 profile 在上一版就是坏的 🔴（78 个编译错误）

**取证**（关键：**用 git stash 回到 HEAD 复验**，不靠推测）：

```bash
$ git stash push -- src/widget src/style/theme.rs examples tests src/theme src/lib.rs Cargo.toml
$ cargo check --no-default-features --features "windows desktop-runtime controls-native controls-custom"
# → 78 errors at HEAD
```

同样地，`--features mini` 与 `--features embedded` 在 HEAD 上也失败：

```
error[E0433]: cannot find `theme` in `crate`
   --> src\widget\display_widgets\mini_canvas.rs:192:28
192 |         let theme = crate::theme::resolved_theme_style("mini_canvas")
```

**根因（一次门控条件与实际依赖不匹配）**：

| 事实 | 值 |
|---|---|
| `crate::theme` 的门控 | `#[cfg(device_profile)]` |
| `mini`/`embedded` 是否设 `device_profile` | ❌ 否（它们是 `stripped_widgets`） |
| `windows+controls-custom` 是否设 | ❌ 否（无任何 device profile） |
| 引用 `crate::theme` 的控件文件数 | **~120** |

即：**「谁引用了 theme」与「谁编译了 theme」两个集合不相等**，而没有任何门禁检查这件事——
因为单跑 `--features desktop` 永远看不到。

**为什么不能简单放宽 theme 的门控**：我实测过三次，每次都撞到新的真实依赖，
且都不是可以绕过的：

1. `types.rs` 需要 `serde`（`mini` 与 `windows mixed` 都没有）；
2. `apply.rs` 需要 capability registry（`widgets_unstripped`）；
3. `manager.rs` 需要平台 singleton（`alloc_frugal` 没有）。

所以**正确的修法是提供一条「任何 profile 都存在」的入口**，而不是放宽模块本身。

**修复（根因，非逐点补丁）**：

| 动作 | 位置 | 说明 |
|---|---|---|
| 新增 4 个 always-available 入口 | `src/style/theme.rs` | `resolved_theme_style`、`resolved_theme_style_for`、`theme_manager`、`semantic_color`；有 theme 时**转发**（单一实现），无 theme 时返回 `None` |
| 常量路径批量替换 | 111 个文件 / 129 处 | `crate::theme::resolved_theme_style` → `crate::style::resolved_theme_style` |
| 同上 | 72 个文件 / 90 处 | `global_theme_manager` → `style::theme_manager` |
| 同上 | 21 个文件 / 30 处 | `semantic_color` / `SemanticColor` → `style::*` |
| 补 4 处 profile 分支 | `slider`/`switch`/`keyboard`/`window` | 这 4 个文件真的编译在 `mini` 里，其主题阶梯需显式给出 `not(device_profile)` 臂，取值与 `None` 臂相同的字面量 |
| 修正 `census` 门控 | `src/widget/mod.rs` | 原用 `widgets_unstripped`，但该模块需要**主题**（`device_profile`）→ 改 `full_widgets`（两者之合，规则 #47） |
| `theme_manager()` 的占位返回 | `src/style/theme.rs` | `not(device_profile)` 下返回 `None`，不是伪造调色板——规则 #37「能力缺失只能诚实报告」 |

**为什么「返回 `None`」是对的**：每个调用点**本来就**是
`match manager.current_theme() { Some(active) => 主题色, None => 字面量 }` 的结构，
所以「没有主题」这个事实走的是既有分支，控件回落到自己的字面量（**可见地**无主题），
而不是看起来有主题却匹配不上任何用户配置。

```bash
tablet     0 errors
mobile     0 errors
```

### 3.3 两处「声明与实现」不一致（第 2 层抓到）🔴

**（a）`message_box::modal` 声明不可读、控件却实现了**

```rust
// properties_dialog.in.rs（修前）
PropertySchema::new("modal", PropertyValueKind::Bool, false, false),  // 承诺「什么都不是」
// 而 message_box.rs 有：pub fn is_modal(&self) -> bool / pub fn set_modal(&mut self, bool)
```

**为什么是缺陷**：`readable: false, writable: false` 在既有约定里表示
「这是给**兄弟控件**占的名字，本控件不负责」。但这里控件**有能力**，
于是设计器会**隐藏一个能用的属性**——用户看不到它，而它其实可读可写。

**修复**：schema 改 `true, true`；`get`/`set` 各补 `"modal"` 分支；`property_names` 补上名字。

**（b）`order_book::show_spread` 的只读答案取决于传入类型**

```rust
// 修前
"show_spread" => {
    let CapabilityValue::Bool(_) = value else { return Err(TypeMismatch) };  // 非 bool → 类型错
    Err(ReadOnlyProperty)                                                    // bool   → 只读
}
```

**为什么是缺陷**：schema 声明 `writable: false`。传 `Null` 的调用方被告知
「**类型错了**」，这诱导他改成 `Bool` 再试——然后才被告知「其实只读」。
答案取决于一个**永远不可能成功**的写入的值。

**修复**：不检查类型，**无条件**返回 `ReadOnlyProperty`。

### 3.5 我自己的第 3 层差点重犯「假通过」🔴（重要）

**`check_svg_snapshots.sh` 第一版存在一个与第 58 轮同构的假通过**：

```bash

cargo run --example export_control_svgs   # 就地重新生成
```

**为什么必然假通过**：导出器**先**把改动覆盖掉了，`git diff` 看到的是刚生成的内容。

```bash

```

```
exit=1
```

> 这条与规则 #107（「不得把跳过报成通过」）同源：**门禁的假通过比没有门禁更坏**，
> 因为它会让人以为覆盖了。第 58 轮的「窗口建在 (0,0) 使偏移为 0」和这里的
> 「先覆盖再比较」是同一个形状：**判据依赖了一个偶然为真的条件**。

### 3.6 剪贴板测试 flake（并行下的进程级资源竞争）🟡

**现象**：`lineedit_clipboard_copy_paste_cut` 在整套并行跑时**偶发失败**，单跑必过。

**取证**：连跑 3 次全量，观察失败出现与否：

```
test result: FAILED. 5243 passed; 1 failed     ← 全量偶发
$ cargo test ... --lib lineedit_clipboard
test result: ok. 1 passed                       ← 单跑必过
```

**根因**：剪贴板是**系统级唯一资源**，两个测试同时 copy/paste 会互相看到对方的文本——
与「两个测试都切主题」同类，只是资源不同。

**修复**：加 `clipboard::clipboard_test_guard()`（与既有 `theme_test_guard` 同构），
并让该测试持有它。**注意**：实现必须走 `compat::lock`，因为 `compat::Mutex` 的两个
profile 分支分别是 `spin::Mutex`（`lock()` 直接返回 guard）与 `std::sync::Mutex`
（返回 `Result`）——直接调 `.lock()` 会在某一 profile 上编译失败（我第一版就撞到了，
由 `check_generator_output_compiles.sh` 的 mini 用例抓出）。

**验证**：连跑 3 次全量，**3 次全绿**（5244 passed）。

**颜色分类（规则 #108）**：色带是 **③ 数据色**——它**编码数值**，换主题色会抹掉信息。
因此色带用常量端点，**不读** `style.*`；而外框（背景/边框/标签/图例）**是** chrome，
**读** `style.*`。这样控件既响应主题，又不篡改自己的数据。

### 4.2 `spin_box` 浮点支持（第 4 层 R-4c）

**为什么加在 `spin_box` 上而不是新增 `double_spin_box`**：`double_spin_box` **已经是**
`spin_box` 的别名（capability 别名表），新增会造成两个几乎相同的控件长期并存并漂移。

**关键设计决策与取证**：

| 决策 | 理由 | 取证 |
|---|---|---|
| 值存 `f64`，`decimals` 决定精度，默认 0 | `decimals == 0` 即整数模式，**既有调用方完全不受影响**（规则 #21） | 17 个既有整数测试 0 回退 |
| 属性类型新增 `PropertyValueKind::Number` | `decimals==0` 返回 `Int`、`>0` 返回 `Float`；声明 `Int` 在浮点模式下是谎，声明 `Float` 在整数模式下是谎 | 见下 |
| `Number` **必须进 wire 规则表** | 否则设计器会把连到 `spin_box` 的每一条连线都置灰（白名单表「未列即拒绝」） | 加 `Int/UInt/Float → Number` 与 `Number → String` |
| 舍入走**十进制文本** | `(x*10ⁿ).round()/10ⁿ` 与 `format!("{:.n}")` **会不一致**——实测 `2.0965×1000 = 2096.5000000000005`，前者得 `2.097`，后者得 `2.096` | `spinbox_stored_value_equals_the_printed_value` |

**两处我自己的错误假设，实测纠正**（写进测试注释，避免后人重犯）：

1. 我最初断言 `1.005` 应舍入为 `1.01`。**错**——`1.005` 这个 `f64` 字面量
   **就是** `1.00499999999999989`，所以 `1.00` 是**正确**答案。
   任何舍入方案都变不出输入里没有的位数。
2. 我最初断言 `2.675` 同样如此。**也错**——它同样是 `2.6749999...`。
   实测扫描 200 万个点，只有 2 个点在 4 位精度下会让两种实现分歧
   （`2.0965` 与 `5.7235`）。

**新增 `PropertyValueKind::Number` 的连带修复**（冰山法则）：
`designer_manifest` 的 token 双向映射、`json/properties.rs` 的强制转换、
`wire_rules` 的 5 条新规则、以及一个**因为 `"number"` 变成合法 token 而失效的测试**
（它原本拿 `"number"` 当"未知类型"的哨兵，已改用 `"quaternion"`）。

## 5. 别名与命名（指令 #6）

### 5.1 `checkbox` 别名：**计划 §1.7 的前提是错的**

计划把 `checkbox` 记为第 4 层的**唯一真缺口**，修法是「给 `check_box` 补 `"checkbox"` 别名」。
我照做后，`capability_alias_hygiene_test` **立刻失败**：

```
these aliases normalise to their own canonical name, so `normalize_key` already
reached them and the row changes nothing — it only inflates the published alias
list and hides the aliases that carry information: [("check_box", "checkbox")]
```

**取证**（写临时探针实跑，不看代码猜）：

```
checkbox     creates=true canonical=check_box
check_box    creates=true canonical=check_box
checkBox     creates=true canonical=check_box
CHECKBOX     creates=true canonical=check_box
```

**根因**：`WidgetFactory` 用 `normalize_key` 存名字，它**剥掉 `_`、`-`、空格并小写**。
所以 `"checkbox"` 与 `"check_box"` **本来就是同一个 key**，`create("checkbox")` 一直可用。

⇒ **这不是代码缺口，是判据缺口**（规则 #110 的第三种情形）：
`audit_platform_create_coverage.py` 用**字面相等**比较，而工厂用的是**归一化后**比较。

**修复**：**回退别名**（它是 no-op，且会破坏门禁），改**脚本判据**：按 `normalize_key`
归一化后再查表，并让输出写明 `normalised name -> check_box` 而不是笼统报 `capability`。
结果：`UNRESOLVED (0)`，且**反向注入仍能抓住真缺口**（把 canonical 改名后立刻报 `UNRESOLVED`）。

> 这条与计划反复强调的教训同源：**「名字不在表里」≠「功能不存在」**。
> 计划自己在 `context_menu` 上犯过一次，在 `create_web_engine` 上犯过一次，
> 这是第三次——只是这次错在"把可达当成不可达"。

### 5.2 `heatmap` 的别名

`set_data`/`set_cell`/`clear` 之外的**名字**层面：`heat_map` **不列为别名**
（它归一化后等于 `heatmap`，属 no-op）；只保留 `heatmap_chart`（归一化后不同，真有信息）。

### 5.3 `normalize_key` 的两条约束（已写入门禁）

- 别名**不得**归一化后等于自己的 canonical name（否则是 no-op）；
- 任何名字不得归一化后等于**另一个**控件的 canonical name（否则查询结果依赖注册顺序）。

## 12. 一句话结论

**计划的判断被证实，且比计划预期的收获更大。**

计划说「补上渲染维度，一条 P3 判据覆盖 1457 处硬编码」，这在第 1 层实现了；
但真正的收获是**新维度立刻找出了计划本身没预料到的缺陷**——
一个**文档承诺了却不存在的算术能力**、**三套在上一版就编译不过的构建**、
**两处声明与实现不一致**、以及**我自己在第 3 层差点重犯的假通过**。

**五条方法论在本轮全部再次兑现**：

1. **按名字遍历**（180 个 kind 会被漏 19 个控件）——第 1/2/3 层都按 188 个 canonical name 走；
2. **判据分类不齐一**（外观色 / 语义色 / 数据色）——`heatmap` 的色带是数据色，不读 `style.*`，但外框读；
3. **豁免必须附理由**——20 条数据色豁免每条写明"为什么这是数据"，`banner` 等 4 个语义色控件被**拒绝**入表；
4. **跨层缺口先判"补还是删"**——`checkbox` 是第三种情形（**改判据**，不是补别名也不是删）；
5. **反向注入**——每条断言都有实测 FAIL 记录，其中一条（SVG 门禁）**真的抓出了我自己的假通过**。

**最该记住的一条**：**「计划里的数字也会过期」。**
计划 §1.4 写「4 个语义 token 被引用 0 次」，本轮实跑是每个 ~10 个消费者；
计划 §1.7 写「唯一真缺口是 `checkbox`」，本轮实跑发现它根本不可达性成立、是判据错。
按规则 #64，**开工前先复跑，不照抄**——这一条本轮两次救我于把"已修的"当成"待修的"、
把"可达的"当成"缺失的"。
