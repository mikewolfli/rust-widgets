## 2. 本轮实际改动（按 BLUE21 条目）

### 2.1 阶段 1 — 抽原语（P0-1）

在 `src/render/backend/surface.rs` 新增：

```rust
pub enum VerticalAlignment { Top, Center, Bottom } // Default = Center
pub fn text_line(band, font, alignment, ctx) -> Rect // 自由函数
impl RenderContext {
 pub fn text_line(&self, band, font) -> Rect // 居中行盒
 pub fn text_line_aligned(&self, band, font, alignment) -> Rect
 pub fn draw_text_line(&mut self, bounds, text, font, color, alignment) -> String
}
```

**为什么先做这一步**（原则 #51）：A 组 25 条若逐控件调数字 = 76 次返工；
先立原语 = **1 处新增 + 76 处机械替换**。

**等价性证明**：先把本仓已有的正确写法 `find_replace_dialog.rs::text_line` 改为委托新原语，
重新导出全部 376 个快照，**逐字节零差异** ⇒ 原语与既有正确写法语义等价，不是「又一个版本」。

**单测覆盖 4 类退化输入**：色带高 < 行高 / 色带高 0 / 负原点 / 色带比行盒窄，均不 panic、
不产生负 `y`（负 `y` 是绘制指令，不是优雅降级）。

### 9.1 阻塞点：`button::tick` 永远返回 `true` ⇒ 无限重绘

**现象**：`the_interaction_transition_settles_and_reports_so` 失败：

```
panicked: the transition must terminate rather than tick forever
```

**排查过程（原则 #58：中间轮次只做定点证据，不跑全量）**：

1. 先用 `--list` 列出测试（189 个，瞬间返回）⇒ 排除「测试二进制损坏」。
2. 再单独跑目标测试（`0.00s` 失败）⇒ **排除「测试本身挂死」**。
 之前几次 `cargo test` 「超时」实为 **cargo 编译 + 文件锁等待**，非挂死。
3. 加临时探针（`BUTTON_TICK_DEBUG`）打印每帧实际值，一次命中根因：

```
TICK delta=30 from=0 target=0.5 observed=0.074999996 ← 正常
TICK delta=1000 from=0.074999996 target=0.5 observed=0.074999996 ← 卡住
```

**根因（两条）**：

| # | 缺陷 | 位置 |
|---|---|---|
| **1** | 闭包按 `move` 捕获 `observed`，外层读的是 **move 之前的旧值**（编译器已警告 `value assigned to observed is never read`，但我先前误判为「闭包没被调用」） | `button.rs::tick` |
| **2** | 🔴 **引擎真缺陷**：动画在某一帧**完成**时，`advance_by`/`update` 会把 `is_running` 置 `false`，而快照用 `filter(is_running)` ⇒ **完成帧的 tick 回调被整个丢弃** | `style/animation.rs` |

**缺陷 2 是「同一事实两个消费者」的又一例**（对照 §7.5）：`advance_by`（delta 驱动）与
`advance`（时钟驱动）**两条路径写法完全相同，因此缺陷也完全相同**。只修一条会留下另一条。

**修法**：两条路径都改为**先记录「本次推进前仍在运行」的 id 集合**，快照基于该集合而非
推进后的 `is_running`。语义上也更对：快照要回答的是「本帧开始时它在动吗」。

```rust
// 推进前记录（关键：先于 advance）
let was_running: Vec<AnimationId> = self.animations.iter()
 .filter(|(_, e)| e.anim.is_running()).map(|(&id, _)| id).collect();
// 快照基于 was_running，而非推进后的 is_running
let snap = was_running.iter()
 .filter_map(|id| self.animations.get(id).map(|e| (*id, e.anim.progress())))
 .collect();
```

**反向注入验证**（把快照改回 `filter(is_running)`）：

```
$ cargo test --lib a_completing_animation_still_delivers_its_final_value
assertion `left == right` failed: the completing frame must deliver the end value
 left: None ← 回调一次也没触发
 right: Some(1.0)

$ cargo test --lib the_interaction_transition_settles_and_reports_so
panicked: the transition must terminate rather than tick forever
```

**两条测试同时变红**，证明修复是承重的。修复后：

```
TICK delta=30 from=0 target=0.5 observed=0.074999996
TICK delta=1000 from=0.074999996 target=0.5 observed=0.5 ← 精确落到目标
ok
```

**新增回归测试**：`a_completing_animation_still_delivers_its_final_value`
（同时覆盖 `advance_by` 与时钟驱动的 `advance`，因为两者同形）。

### 9.2 C8 + 冰山扫描：死绑定

`candlestick_chart::draw_price_labels` 在函数首部绑定 `bar`，仅在循环末尾用 `let _ = bar;`
消费一次，且注释声称精度取自「first bar's prices」——**实际 `inferred_decimals()` 走的是整条序列**。

**修法**：删除死绑定与 `let _ =`，注释改为真实语义。

**冰山扫描**（原则：修一处扫同类）`grep -rn "let _ = "` 另发现 **4 处同形**：

| 位置 | 性质 | 处理 |
|---|---|---|
| `order_book.rs` | 参数本已在使用，`let _ = value;` 是多余语句 | 删除（保留原注释意图） |
| `indicator_chart.rs` | `for (position, pane)` 中 `position` 从未使用 | 改为 `for pane in series.iter()` |
| `diff.rs` ×3 | `(Some(id), None)` 未用 `id`；循环未用 `child`；栈元组未用 `index` | 分别改 `Some(_id)`、`_child`、从元组移除 `index` |

### 9.3 P2-3 光标闪烁（AR8）：新增共享原语并接入 4 个控件

**实测**：`grep blink` 全仓只命中 3 处**注释**，零 `Duration`、零 `tick`、零重绘调度。
其中 `tag_input.rs` 的 `/// Cursor blink interval in milliseconds.` 是**孤立注释**（下面没有常量）。

**修法（原则：同一事实只允许一套推导）**——不在每个控件里各写一个计时器，而是新增共享类型：

```rust
pub const CURSOR_BLINK_HALF_PERIOD_MS: u32 = 500;

pub struct CursorBlink { elapsed_in_half: u32, visible: bool, running: bool }
impl CursorBlink {
 pub fn start(&mut self); // 聚焦：可见 + 开始
 pub fn stop(&mut self); // 失焦：**保持可见**（失焦仍显示编辑点，隐藏反而像渲染错误）
 pub fn is_visible(&self) -> bool;
 pub fn tick(&mut self, delta_ms: u32) -> bool; // 遵循全仓 tick 契约
}
```

**接入的 4 个控件**（各自持有字段 + 转发 `tick` + 绘制处按 `is_visible()` 门控）：

| 控件 | 驱动条件 | 入口 |
|---|---|---|
| `lineedit` | `focused && !read_only` | `set_focused` |
| `inplace_editor` | `is_editing` | `start_edit` / `finish_edit` |
| `tag_input` | `focused` | `set_focused` |
| `code_editor` | `!read_only` | 构造期即启动（该控件无 focus 概念） |

**大 `delta_ms` 的正确处理**：`tick` 内部用 `while` **逐半周期**消账，而不是「大 delta ⇒ 只翻一次」。
否则卡顿后的帧循环恢复时会**丢失若干次翻转**、相位错乱。测试直接钉住这一点：
连续 `tick(3 × half)` 与 `tick(half)` 的结果必须不同。

**同时把 `code_editor::accessible_value` 覆写为「选区文本，无选区则为光标所在行」**——
因为该控件不发布 `value` 属性（缓冲区太大，不适合每次朗读时读取）。

### 9.4 P2-8 a11y：补结构 + 让 `value` 真正可达

**结构缺口**：`A11yState` 有 `value` 但从无控件填充；且缺 `checked`/`mixed`。

```rust
// 新增
pub checked: Option<bool>, // None = 该角色没有勾选态（不是「未勾选」）
pub mixed: bool, // 三态父节点的部分选中
```

**`None` 与 `Some(false)` 必须分开**：合并成一个 bool 会让屏幕阅读器对「不可勾选的按钮」
朗读「未勾选」——即把「没有这个状态」说成了「状态为否」。

**value 的解析走属性契约**（与 `accessible_name` 同构，可在不修改 trait 方法的前提下支持新控件）：

```rust
pub(crate) const VALUE_PROPERTY_NAMES: &[&str] = &["value", "progress", "rating", "level"];
pub(crate) fn widget_value_property_name(props) -> Option<&'static str>;
fn Widget::accessible_value(&self) -> String; // 默认走契约，无 value 概念则返回空
```

**`text` 刻意不在列表里**——这一点是**被测试逼出来的**：
初版把 `text` 作为兜底（想让「内容即值」的输入框自动生效），结果测试立刻变红：

```
assertion failed: a button has no value; its label is its name
 left: "Open" right: ""
```

`text` 是本仓最常见的**标签**拼写，放进 value 链会让每个按钮/菜单项/标签**把标题朗读两遍**
（name 一次、value 一次）。真正的解法是：**通用链不猜**；确实「内容即值」的控件自己覆写
`accessible_value`。

**数值的朗读形态**新增 `CapabilityValue::to_announcement_string()`：

- 整值浮点按整数朗读（`3.0` ⇒ `"3"`，因为控件就是这么画的）
- `Color`/`Rect` 渲染为空（无可朗读形态，且**逐变体写出**而非用通配符，
 以便将来新增变体时必须显式表态）
- `Null` ⇒ 空串（「未设置」不能与「值为 0」混同）

### 9.6 本轮反模式记录（补充 §7）

7. **「两条路径写法相同 ⇒ 缺陷也相同」。** `advance` 与 `advance_by` 是同一段逻辑的时钟版与

9. **`cargo test` 的「超时」要先排除编译与文件锁。** 本轮多次出现

 不是死循环。**先用 `--list` / 直接跑测试二进制来区分「编译慢」与「真的挂死」。**
10. **兜底链的每一环都要问「这会不会把标签当成值」。** a11y 的测试之所以有价值，
 是因为它同时断言了**否命题**（按钮不朗读 value）。只测「滑块能朗读」会放过把每个
 按钮标题朗读两遍的版本。

### 10.3 对标后最重要的发现（已写入 blue22 §0）

**本仓真正的问题不是「画错了」，而是「没有度量体系」。**

- 参考工具包的标记语言：`implicitWidth = max(背景隐式宽 + inset, 内容隐式宽 + padding)`（`reference: the button's implicit-size formula and padding cascade`，**已实测引用**）
 ⇒ **背景是「最小可点区地板」**，所以 5px 文字仍是 100×40 的按钮。
- 本仓：控件把外部 `rect` 当**绘制指令**，于是 `CENSUS_RECT = 240×120` 把开关画成体育场、
 单选画成 `r=30`、进度条画成一块板。

**因此 BLUE22 的顺序是「先立体系（P0）→ 再刷外形（P1）→ 最后装饰（P2）」**，
与「先加 `outline` 等 token」的直觉相反——在错误的几何上刷更漂亮的漆是浪费。

### 10.8 补充：组合控件组装体系（blue22 §6B）

用户追加要求：「**尤其是组合控件，如何由基本控件布局（layout + create）完成**」。
这一问促使我对本仓的组合机制做了取证，结果发现**第二根断链**（与 §10.3 的单控件度量并列）：

**实跑取证**：

```text
$ grep -rln "BoxLayout::new|FlexLayout::new|GridLayout::new" src/ --include=*.rs
src/json/layout.rs src/app/handle.rs src/layout/*.rs
→ src/widget/ 下一个都没有（组合控件不通过 Layout 排布）

$ grep -rn "store_layout|add_widget_to_layout|apply_layout" src/ examples/ | grep -v declarative.rs
src/json/loader.rs:32,265,299,306,437,471,479 ← 唯一消费者是 JSON 加载

$ grep -rln "fn size_hint" src/widget/ | wc -l → 176
$ grep -rn "size_hint" src/layout/ → 只有 flow.rs 读它
```

**三条缺口**（已写入 blue22 §6B.2–B.4）：

| 缺口 | 事实 |
|---|---|
| ① 组合控件手算几何 | 从 `self.geometry()` 逐个子控件算，不用已有的 **15 种**布局 |
| ② `Layout::update` 拿不到尺寸 | 签名只有 `ObjectId`，没有 `&dyn Widget`；唯一例外是 `flow.rs`（它直接存 `Box<dyn Widget>`）——**这恰好证明「读得到」与「读不到」是两套代码** |
| ③ `create` 与 `layout` 之间没有桥 | JSON 路径三段齐全，**代码路径没有等价 API** |

**方案**（blue22 §6B.5）：新增 `CompositeBuilder`（`src/widget/composite.rs`，约 150 行），
只做「持有 + 测量 + 转发」，实际排布**必须**委托给已有布局；关键是让固有尺寸沿子控件传播
——即 参考工具包的标记语言 `implicitWidth = max(background, content + padding)`（`reference: the button's implicit-size formula and padding cascade`）的机械。

**最优价值的一条洞察**（blue22 §6B.9）：
参考工具包的标记语言 的 `reference: padding derived from the sibling's own width` 里子控件留白**由兄弟宽度推导**（`leftPadding: padding + up.width`），
而本仓写死数字 ⇒ 按钮变宽/字变大时文本区不会让位，导致重叠或溢出。
**组合控件的「美观」定义就是：每一段留白都由兄弟的实际尺寸推导。**

**优先级调整**：新增 **P0-1b（组合体系）**、**P1-1b（11 个组合控件逐个改造）**，
并把 §6B 提为与 §6 并列的顶层章节（理由：本仓过半控件是组合控件，
不在组合层立规范就会在 11 个控件里各写一遍几何——与 BLUE21 付出 76 次返工的形态相同）。

### 10.9 补充：组合体系对标 外部对标 / 参考工具包 —— **我先前给的方案被否决并重写**

用户追问：「**组合体系能否借鉴一下 the material reference 和 qt**」。
这一问迫使我把「组合体系」从「凭经验设计」改成「对标取证」，
结果**否决了我 10.8 里提出的 `CompositeBuilder` 方案**。

**两个并行子代理分别精读 主流 material 实现 渲染协议与 参考工具包 布局，结论一致且可验证：**

| 事实 | 主流 material 实现 | 参考工具包 | 本仓 |
|---|---|---|---|
| 尺寸提示的**形状** | `getMinIntrinsicWidth(double height)`（`box.dart:1651`）——**带对轴参数** | 每轴 **3 值** min/pref/max（`reference-toolkit layout.cpp:1176` 真值表） | `size_hint() -> Size`，**无参数无地板无上限** |
| 布局**向谁**要尺寸 | 向子 render object（`layout_helper.dart:64`） | 向子 item（`reference-toolkit dialogbuttonbox.cpp:349`） | **向自己存的变量** |

**本仓那条断链的真正形状**（这是我上一轮没看透的）：

```rust
// src/layout/flex.rs:167
/// Set the child size hints (call before update for proper sizing).
pub fn set_child_sizes(&mut self, sizes: Vec<Size>);
```

布局**无法问控件**，于是只能反过来要求调用方**提前把尺寸塞给自己**。
同一形态还有 `wrap.rs:106`、`absolute.rs:320`。

> **所以「176 个实现、1 个消费者」的原因不是「没人用」，而是「布局问不到」。**
> `flow.rs` 之所以是唯一消费者，只是因为它把 `Box<dyn Widget>` 存在自己身上。

**为什么原方案是错的**：`CompositeBuilder` 即使写出来，也只能把「手算尺寸」
从控件**搬进构建器**——缺陷位置变了，性质没变。**这是「移动缺陷」而不是修复。**

**重写后的方案**（blue22 §B.5.2）：
1. **根因修复**：`Widget::hints()` 替 `size_hint()`；`Layout::arrange(rect, &[ChildInfo], out)`
 —— `ChildInfo` 携带子控件的 `Hints` 与 `LayoutParams`。
2. `arrange` **带默认实现并转发旧 `update`**，让 15 个布局不必同时改完
 （直接吸取 BLUE21 「76 处机械迁移」的教训）。
3. `CompositeBuilder` **降级为装配器**：只做「创建 + 收集提示 + 问布局 + 回写」，**零布局算法**。

**两个具体的设计取舍**（都在 blue22 里写了理由）：

- **选 参考工具包 的 min/pref/max，不选 主流 material 实现 的 4 个对轴函数**：因为本仓缺的正是**地板**（`min`），
 而 主流 material 实现 的形态要另包一层才能表达地板；且 主流 material 实现 自己文档承认 `IntrinsicWidth`
 是「O(N²) in the depth of the tree」（`basic.dart:3804-3807`）。
 额外好处：不支持宽高联动，就**没有** 参考工具包 那种「循环重排」需要封顶的风险
 （参考工具包 不得不把 polish 循环封顶在 2 次，`reference-toolkit layout.cpp:866`）。
- **`fill`（该不该被拉长）与 `min`（能压到多小）必须分开声明**：滑块的 `pref` 与按钮的
 `pref` 都可能是固定值，但滑块**该**被拉宽、按钮**不该**；无法从尺寸区分。
 参考工具包 用 `Layout.fillWidth` 表达（`reference-toolkit layout.cpp:303`）。

**明确不抄**（写进 blue22 §B.6.1，共 6 项）：`BoxConstraints` 全套约束下发（会连带
`parentUsesSize`/relayout boundary/`sizedByParent` 约 3500 行）、`polish()` 延迟管线、
附着属性（attached properties）、`QLayoutPolicy` 全体位标志（**整棵树只用到 `GrowFlag` 一位**）、
锚点约束系统（与布局互相冲突，参考工具包 自己必须检测并警告）、参考工具包 的 `-1`/`+inf`/`NaN` 三种「未设」惯例。

**优先级更新**：新增 **P0-1b（尺寸通道 + 三值提示，根因）**、**P0-1c（`CompositeBuilder`，装配器）**；
§0.1 的「两根」改写为「**四根，其中②③ 是根因、④ 是结果**」。
