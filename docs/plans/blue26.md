# BLUE26 — Rustage 设计器所需的上游契约补齐

> 对照来源：`~/Desktop/workspace/rustage/docs/plan/roadmap.md`（规划 v0.3，2026-10-11）
> 与本仓库现有 API、模块和文档核对；这是针对 rust-widgets 的补充计划，不是 Rustage
> 宿主实施计划。roadmap 当前标注为待实施、待基线核验，本文件不把其需求视为已验收事实。

## 0. 范围与判断原则

Rustage 的桌面设计器依赖 rust-widgets 提供控件能力、布局、运行时预览和生成语义。上游只补
**库中可复用的控件/运行时契约**；工程文件、编辑器工作台与系统服务留在 Rustage 宿主。

1. 先用实际 API、profile 构建和可运行探针确认缺口，再实施；不得仅凭 roadmap 或 API 名称断言
   缺失/支持。
2. 复用现有 capability、Layout、JSON/View 和 generator；不另建一份控件表或布局算法。
3. 公共 API 仅作向后兼容的增补；格式变化带版本和迁移策略，未知/不支持能力必须显式报告。
4. 每个新增能力同时验证运行时 JSON 路径和静态 Rust 生成路径；只适用部分 profile 时准确标注。
5. 本计划中的任务是提案，不表示实现已经开始或完成；Rustage roadmap 的正式支持仍须按其目标
   OS、profile、triple、SDK 和设备分别取证。

## 1. 已有能力：保留并复用，不重复造轮子

| Rustage 所需基础 | 当前已有实现 | 结论 |
|---|---|---|
| 控件、属性、事件及默认值的可发现描述 | `widget::capability` 有属性 schema、默认值、事件载荷类型/形状、命令名；`DesignerManifest` 有稳定 JSON 导出/解析及往返门禁 | 扩展现有 manifest；不维护宿主侧手写控件清单 |
| 类型化属性读写和事件载荷 | `CapabilityValue`、`PropertySchema`、`EventSchema`、`WIRE_RULES` | 继续作为类型校验基础；补足未声明的约束，而非再造类型系统 |
| JSON/CSS 结构运行与预览更新 | `json` 加载路径与 `view::{Node, diff, apply, ViewEngine}` 已提供树构建、差异应用和错误报告 | Rustage 复用现有语义；不在库内实现设计器画布/事务工作台 |
| 静态 Rust 生成 | `designer::generator` 已有运行时/stripped 两种生成路径、布局求解、CSS 内联、容量及不可生成项报告 | 扩展并验证现有生成器；不另写第二个生成模板系统 |
| 布局计算 | `layout::Layout`、`Hints`、`ChildInfo` 与多个布局实现已支持尺寸提示和计算 | 共用真实布局引擎；补设计器需要的描述/诊断接缝，不复制求解器 |
| 外观与常用运行时基础 | CSS/主题、资源、i18n、文本方向、a11y、焦点和输入等模块已存在 | 以针对 Rustage 用户旅程的正反例验证；不把宿主设置界面移入控件库 |

## 2. 上游需要补齐或先核验的事项

### P0 — 设计器正确性所依赖的契约

| ID | 补充项 | 当前差距/核验重点 | 交付与验收 |
|---|---|---|---|
| B26.01 | 带版本和目标范围的能力快照 | 当前设计器 manifest 描述控件、属性、事件、命令，但没有完整表达 Rustage 所需的库/manifest 版本、构建 profile 和目标支持证据；生成器的 `TargetProfile` 以 `Default`/`Stripped` 概括目标，且跨 profile 结果可能只是 caveat | 增加兼容的 manifest 协议版本与库版本字段；目标事实至少分开记录 profile、target triple 和验证级别。对未知、未验证、可用、不支持给出不同结果。相同输入稳定序列化；旧格式可读，未知版本显式拒绝或降级为只读 |
| B26.02 | 可校验且适合编辑器呈现的属性 schema | `PropertySchema` 已表达类型、读写、枚举 token；仍需核对 roadmap 属性编辑所需的范围/精度/单位、必填性、显示分组、资源引用及目标限制哪些由真实控件约束 | 只为实际存在且运行时可校验的约束增加元数据；同一验证器服务于 capability 写入、JSON 加载与生成预检。错误含属性名和拒绝原因；每个 schema 的合法/边界/非法值都有测试，默认值与实际新建控件一致 |
| B26.03 | 带参数 schema 的命令能力 | `WidgetCapability.commands` 目前是命令名列表；Rustage 需要校验事件到命令/动作的绑定，单有名称不足以验证参数形状 | 定义最小的类型化命令描述（参数名/类型/必需性及副作用类别）；无参数旧命令保持兼容。只公布真实可调用命令；有效/无效参数、别名及未知命令通过统一契约测试。权限审批仍由宿主负责 |
| B26.04 | 稳定设计节点到运行实例的可查询映射 | `view::Node` 有 key；JSON `ProjectNode` 在无显式 key 时按路径派生；`ViewEngine` 的活动树实例索引目前不是公开的稳定 NodeId/source-map 契约。Rustage 需要运行检查器把选择、布局和值定位回模型 | 先确定 key 唯一性、生命周期和重建规则；为已应用树提供只读查询（稳定 key/路径 ↔ `ObjectId`、节点类型/父子关系），删除或替换后旧映射立即失效。覆盖插入、移动、删除、替换、重复 key、失败应用和多树实例；不要把 `ObjectId` 当作可持久化 NodeId |
| B26.05 | 可编辑布局描述与真实布局诊断 | 求解与尺寸 hints 已有；Rustage 还需检查布局种类、参数、子项约束及为何得到某个几何结果。确认现有 JSON 布局描述是否覆盖布局检查器所需且能无损往返 | 对已有布局种类提供可发现、可校验的参数/子项 schema，以及复用同一 `Layout` 求解器的几何结果和诊断来源。非法转换报告丢失/不支持字段，不静默转成坐标布局。用同一工程输入比对 JSON 运行和静态生成几何 |
| B26.06 | profile 精确的控件/属性/事件可用性探测 | 控件注册和生成器的可用性查询已存在，但跨 profile 查询可能只能给出不确定结果；Rustage 不可用推测的桌面结果宣称 mini/embedded 可生成 | 增加/明确目标探测结果类型，携带实际验证 profile 与限制；区分“当前构建可查”“目标已实构建验证”“未知”。建立 desktop/tablet/mobile/mini/embedded 的代表性探针，并将可构建清单与 feature gates 对照；不支持组合拒绝且附原因 |
| B26.07 | 增量更新的定位与失败观测 | `ViewEngine` 已能 diff/apply 并返回报告；需要确认 Rustage 能否从报告关联受影响稳定节点、识别失效映射及区分部分应用错误 | 在不改变既有 `mount/update` 行为的前提下，补充必要的只读映射/报告信息；验证属性拒绝、未知控件、创建失败、重复更新与 unmount。错误不得被转换成成功态；订阅与生命周期不随重复应用累积 |

### P1 — 依赖目标基线验证后再排入

| ID | 补充项 | 触发条件 | 交付与验收 |
|---|---|---|---|
| B26.08 | 编辑器文本与源码定位原语 | 按 Rustage T00.02 的真实代码编辑探针确认现有 CodeEditor 是否缺少其调用所需的文本版本、范围坐标、编辑/选择操作或诊断定位；不因 roadmap 提及 LSP 就扩成 IDE | 只添加复用性强的编辑原语和准确版本/坐标约定；Unicode、多行、缓存、线程和失效版本测试；LSP、工程索引、工作区符号与双向合并归宿主 |
| B26.09 | 集合/复合数据的类型化接口 | 若 T13/T27 的真实控件能力证明当前标量/tuple 属性无法表达行、列、角色、编辑器提交/取消等数据，不得以 JSON 字符串冒充类型安全 | 先用具体控件和数据流定义最小类型；稳定项身份、行列移动、校验失败、异步取消及生成一致性测试。若业务数据由应用提供，优先定义应用接缝而不在控件库持有业务状态 |
| B26.10 | CSS 计算值及来源检查接缝 | 若运行时探针确认 CSS API 无法提供 Rustage 检查器所需的计算值/获胜规则来源；不得在设计器与库各维护一套级联 | 暴露只读计算结果与来源位置（若底层保留该信息），支持无效规则错误；比较运行预览与生成期内联结果。CSS 编辑器、三方文本合并和模型事务由宿主实现 |
| B26.11 | RTL 与多语言文本验证 | Rustage T24.10 要求复数、RTL、伪本地化验收；当前有 i18n/文本方向/塑形模块，但必须实测具体 shaping、绘制、截断、布局和输入链路 | 增加 Arabic/Hebrew 与扩展文本回归用例，覆盖 bidi、混排、长串、字体缺失和换行；只有发现库层行为缺口才增补引擎，翻译键提取、资源清单和伪本地化工作流留给宿主 |
| B26.12 | 逻辑资源引用接缝 | Rustage T12.09 要求同一资源身份用于运行时与静态包。先核对现有 `asset`/`image` 读取路径能否解析宿主逻辑资源，而不是假设缺资产系统 | 若确有差距，增设平台无关的逻辑资源标识/解析接口，并将文件监视、导入转换、许可、打包和来源索引留在 Rustage；验证缺失、重名、移动及嵌入/外部资源解析不串号 |

## 3. 明确留在 Rustage 宿主的工作

以下是 roadmap 的产品责任，不应转嫁给 rust-widgets：多根/多 Cargo package 工作区与依赖审阅；
工程模型、JSON/CSS 编辑器、稳定 NodeId 的持久化、ChangeSet/撤销/三方合并与源码 span；
画布选择/拖拽事务、属性检查器 UI、项目资源导入和打包、LSP/代码导航、终端/PTY、任务 DAG、
构建与运行进程、Git、调试适配器、测试报告、权限与信任、扩展管理、AI 工作区、设置同步、
CI/headless CLI 和发布签名。

库只负责给这些宿主服务真实、可测试、版本化的控件和运行时契约；不得把网络、工程文件写入、
Cargo 命令、平台凭据或 AI 请求塞入 widget 层。

## 4. 实施顺序与门禁

1. **基线先行（Rustage T00.01–T00.05）**：固定 rust-widgets 修订；对现有 manifest、布局、
   ViewEngine、生成器和 profile 做调用探针；标注 `已有/局部/缺失/未验证`，并记录失败输入与
   对应源位置。未复现的候选项不实施。
2. **契约补齐（B26.01–B26.07）**：先定向后向兼容协议，再增补属性/命令/目标/映射/布局查询；
   每个行为同时测 JSON 与静态生成，不让 Rustage 手抄库内事实。
3. **场景补齐（B26.08–B26.12）**：仅由实际用户旅程及探针触发；RTL、复合数据和资源路径以
   正反例证明差异，不为尚未选择的方案预留空 API。
4. **Rustage 接入验收**：至少覆盖控件插入、属性拒绝、事件接线、约束布局、多视口更新、运行树
   检查、生成 diff 与五种 profile 的适用性；版本/目标未经实测的一律记未验证。

## 5. 完成标准

- 每项采纳工作对应 Rustage roadmap 的任务 ID、用户旅程及宿主集成证据；延期/不做项记录理由。
- 同一能力只有一个事实来源；无并行控件清单、布局求解器或第二套属性验证器。
- Manifest、Node key 和生成产物有明确版本/稳定性规则；旧工程不会无提示丢字段或改变解释。
- 每项支持结论有精确目标、profile、triple 和测试级别；未知能力不会显示为可发布。
- 变更通过相关单元/集成测试与受影响 profile 的 `cargo check`/生成构建验证；不能构建或缺少
  设备环境必须作为阻塞证据记录，不能改标通过。
- 文档只描述已经验证的 API；本计划本身不构成完成率或 Rustage 支持承诺。
