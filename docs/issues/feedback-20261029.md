## 2. 缺口：Windows embedded 的 `ToOwned` 导入（P1）

**现象。** 在 macOS 宿主上用 xwin 执行：

```text
cargo build --manifest-path <rust-widgets>/Cargo.toml --target x86_64-pc-windows-msvc \
    --no-default-features --features embedded --lib
```

失败：

```text
error[E0599]: no method named `to_owned` found for reference `&'static str` in the current scope
   --> src/platform/external.rs:139:59
    |
139 |     match std::thread::Builder::new().name("rw-open-reap".to_owned()).spawn(move || {
    |                                                           ^^^^^^^^ method not found in `&'static str`
```

编译器提示 `ToOwned` 未在作用域内。该文件顶部只导入了 `crate::platform::types::OpenError` 与
`std::path::Path`；在 std profile 下 `ToOwned` 由 std prelude 提供，而 embedded/no_std 的
core prelude 不包含它，因此 Windows 的 embedded 构建在这一行暴露。

**期望。** 在 `src/platform/external.rs` 的 embedded/no_std 组合下导入
`crate::alloc::borrow::ToOwned`（或把线程名参数改为不需要 `to_owned()` 的形状）；并补一条
`--target x86_64-pc-windows-msvc --features embedded` 的编译门禁，避免该组合只在 Windows
目标上暴露。

**宿主侧处理。** 支持矩阵不把 `windows × embedded` 写成通过；该格保持 `unverified` 并记录
准确错误。宿主没有打 patch、没有换第二个修订绕过。

## 3. 文档/门禁缺口：3.0.0 changelog 未列出 `Layout` trait 的破坏性变更（P1）

**现象。** `CHANGELOG.md` 的 3.0.0 “API changes” 只列出
`ShortcutManager::set_focus_chain_lookup`，并声明 “No other public signature ... changed”。
但同一修订把 `Layout` 的 `arrange`、`arrange_with_context`、`update_with_context` 从有默认
实现改成**必需方法**：

- `src/layout/types.rs`：`fn arrange(...)`、`fn arrange_with_context(...)`、
  `fn update_with_context(...)` 均无默认体，注释说明这是为消除 G-403 的静默丢参；
- 宿主两个 `impl Layout`（`workbench_layout.rs`、`workbench_scene.rs`）在 3.0.0 上直接
  `E0046: not all trait items implemented`，2.8.12 上同一代码可编译。

**期望。** 把这三项列为 3.0.0 的 API 变更（或在 changelog 中说明由 `impl_layout_forward!`
迁移），并给出下游 wrapper 的迁移示例。否则 changelog 的“无其他 public signature 变化”
会让下游误判升级风险。

**宿主侧处理。** 宿主按新契约补了三个入口：`arrange`/`arrange_with_context` 明确转发到
`update`，`update_with_context` 转发到 `update`；宿主布局的依据是 `Area`/设计坐标而不是
`ChildInfo`，注释写明了为什么忽略 hint 与 context。没有为了消除编译错误而伪造 hint 使用。

## 4. 门禁缺口：示例 `--check` 与默认尺寸不一致（P2）

**现象。** 上游 `examples/generated_project/src/generated/*.rs` 是按 640x480 生成的（首行注释
写 “against 640x480”），而 3.0.0 的 `designer_generate` 默认尺寸是 1280x800。直接执行：

```text
cargo run --no-default-features --features desktop,designer --example designer_generate -- \
    --project examples/generated_project/project.json --root examples/generated_project --check
```

报两个文件 `stale`；加 `--width 640 --height 480` 后 `--check` 通过，生成内容与提交文件字节
一致（差异只在布局尺寸与由它推导的常量坐标）。

**期望。** 示例的提交产物、README 的检查命令与生成器默认尺寸三者保持一致；或让 `--check`
从生成文件头部记录的尺寸读回默认值。当前形状会让第一次照 README 跑门禁的读者得到假失败。

**宿主侧处理。** 宿主在复验时显式传 `--width 640 --height 480`，记录为“在该参数下通过”，
没有把默认参数下的失败写成生成器正确。

### 6.1 对反馈中“宿主机处理”的确认

- 宿主机没有伪造 hint 使用、没有换修订绕过、没有把默认参数下的失败写成生成器正确——这些判断与上游修复后的契约一致。
- 迁移方式：若你的 `impl Layout` 是**包装另一个布局**，用 `impl_layout_forward!(inner)`（或 `(inner, adjust_rect)`）即可；
  若是 `Area`/设计坐标型布局，则显式把 `arrange`/`arrange_with_context` 转发到 `update`，并在注释里写明为何不消费 hint——
  这正是 3.0.0 去掉默认实现的目的（G-403）。
