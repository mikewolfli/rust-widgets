## 第 1 章 平台与帧驱动（PL3-）

**PL3-1 GTK 心跳 idle 档把 100ms 间隔当动画 delta，动画起始帧一次性跳 6 帧**
- **1级** `linux/platform_impl.rs:84` `arm_frame_heartbeat` 的闭包无条件 `crate::drive_frame(interval_ms as u32)`，而 idle 档 `interval_ms = IDLE_FRAME_INTERVAL_MS = 100`（`platform/types/values.rs:27-31`）。静止窗口上输入事件由 GTK 信号处理器**同步分发**（`linux/platform_impl.rs:1331-1469` 直接调 `dispatch_pointer_event`），动画在两次心跳之间启动；下一拍 idle tick 到来时 `drive_frame(100)` 把刚起步的动画一次性推进 100ms（`widget/runtime/frame.rs:288-292` 直接以 delta 调 `tick`）——hover 渐变 120ms 的首帧直接画在 ~83% 处，用户看到"瞬间完成"而非渐变；主题 crossfade 同型。
- **2级** delta 与唤醒节奏解耦：闭包恒传名义步长 `crate::drive_frame(crate::platform::types::FRAME_INTERVAL_MS as u32)`（FRAME 档本就是 16，行为不变；idle 档动画起始帧回到 16ms，下一拍 `needs_another_frame=true` 已把节奏切回快档）。文件头 `:53-58` 的"sleep 与 delta 必须同值"注释同步改为"delta 恒为名义步长，两档间隔只控唤醒频率"。

**PL3-2 拖拽缩放期间心跳节奏只看动画位、不看排队触发，resize 布局以 ≤10Hz 跟随（多后端同病）**
- **1级** 节奏降档判据处处只有 `outcome.needs_another_frame`（纯动画总线事实，`widget/runtime/frame.rs:309-310` 不含触发器信息）：GTK `linux/platform_impl.rs:85-93` `wanted = if needs_another_frame {16} else {100}`；macOS 心跳同判据（`macos_heartbeat.rs:185-195`，`needs_another_frame=false` 即 `retarget_in(IDLE=100ms)`）。而 `Resized` 触发从不启动动画：布局重排只产生 repaint。于是拖拽期间（无动画在跑）每拍排空一次队列、重排一次布局，节奏 = idle 档 100ms——**模式问题修好了，但跟随率只有 10Hz**；且拖拽首帧最晚还要再等一个 idle 间隔才被注意到（`macos_heartbeat.rs:161-164` 自述 "a tenth of a second"）。触发源持续入队：cocoa `windowDidResize:`（`macos/canvas.rs:1913-1917`）、objc2 `setFrameSize`（`macos_objc2/native.rs:1289-1295`）、GTK size-allocate（`linux/platform_impl.rs:1574-1576`）。
- **2级** (a) 两处判据改为 `needs_another_frame || outcome.events_dispatched > 0`——复用 `FrameOutcome` 既有字段（`frame.rs:25`），拖拽期每拍都有 Resized 被排空故维持 16ms，拖拽结束一拍后自然回 idle；单次程序化 resize 只多付一个快拍，无新 API。(b) 首帧滞后：`macos_heartbeat` 增设 `pub(crate) fn expedite()`（保存 retained timer 引用后把下一火拉到 ~1ms 内）；GTK 的 size-allocate 处理器在 idle 档时直接 `arm_frame_heartbeat(&slot, FRAME_INTERVAL_MS)` 重挂快源（该函数 `:78-97` 已具备按需重挂语义）。Windows modal 档已由 `SetTimer(16ms)` 括住（`windows/types.rs:444-470`，`WM_EXITSIZEMOVE` KillTimer），不动。

**PL3-3 objc2 主循环不消费 presented-time deadline/delta：固定栅格自由跑 vs 显示相位漂移，已声明的 vsync 能力空转**
- **1级** `macos_objc2/platform_impl.rs:1111` `drive_frame(FRAME_INTERVAL_MS as u32)`（恒名义 16）+ `:1115-1118` `pause_between_frames_with`（固定栅格），而同一 impl 声明 `supports_vsync_frame()=true`、`next_vsync_deadline()` 转发 display link（`:312-328`）；带完整测试的 `pause_between_frames_with_vsync`（`frame_wait.rs:386-438`、测试 `:684-806`）至今 `#[allow(dead_code)]`。后果：自由 16ms 栅格与真实 vsync（60.0/59.94/120Hz）相位持续漂移，周期性落入"双跳/丢拍" beat 卡顿；ProMotion 120Hz 帧率上限被钉死在 62.5fps；display-link 每次回调的 `frame_wait::wake()`（`display_link.rs:396`）在该后端无任何接收者（泵阻塞在 `nextEventMatchingMask`，`native.rs:2666-2671`，不在 condvar 上）。cocoa 后端已用 `presented_delta_ms`（`macos_heartbeat.rs:172-174`），objc2 是唯一开了 vsync 却没吃的路径。
- **2级** `run` 循环改用既有入口并闭环 delta：`let next_delta = pause_between_frames_with_vsync(outcome.needs_another_frame, || display_link::next_deadline(), pump_native_event_until).unwrap_or(FRAME_INTERVAL_MS as u32)`，下一轮 `drive_frame(next_delta)`（delta 从栅格时长改为跨迭代变量）。泵仍以 deadline 剩余量作 untilDate，输入即时性不变；`note_frame_demand` 原样保留；`#[allow(dead_code)]` 与 `presented_delta_ms` 的 macOS-only 注释（`frame_wait.rs:281`）随之更新。零新机制，纯复用已测试代码。

**PL3-4 跨线程 `wake()` 在四个桌面工具包循环上是空操作，三处注释与实现矛盾；display-link 每秒 ~60 次无效唤醒**
- **1级** `frame_wait::wake()` 只 bump condvar generation + `notify_all`（`frame_wait.rs:83-90`），而四个桌面循环无一在 condvar 上等待：Windows 阻塞于 `MsgWaitForMultipleObjectsEx(0, null, …, QS_ALLINPUT)`（`frame_wait.rs:441-461`，只响应输入消息，condvar 通知不产生消息）；cocoa 主线程在 `-[NSApplication run]`（`macos/platform_impl.rs:616-618`）；GTK 靠 glib timeout 心跳（`linux/platform_impl.rs:883-896`）；objc2 阻塞在 AppKit 事件队列（`native.rs:2666`）。但注释声称会"立即醒"：`stop.rs:70-72`、`main_thread.rs:127-129`、`windows/platform_impl.rs:1937-1941`。后果：Windows/cocoa/GTK 上跨线程 `stop::request()` 与 `schedule_in` 实际延迟 = idle backstop ≤100ms，与三处文档矛盾；`display_link_callback` 的 wake（`display_link.rs:396`）在动画期间以 60Hz 白付一次 SeqCst RMW + mutex 锁/notify，无人消费。另 `main_thread.rs:24-27` 的 "granularity is one frame interval (~16 ms) … the loops tick unconditionally" 是 G-503 两档化之前的陈旧契约（静止窗粒度 = idle backstop）。
- **2级** 给 wake 一条真通道，按成本排序：(a) Windows——`block_for` 把 `nCount` 从 0 改 1，传入进程级 auto-reset event handle，`wake()` 置位即让 `MsgWaitForMultipleObjectsEx` 立即返回（单点改动，输入唤醒语义不变）；(b) GTK——每后端 wake 钩子用 `glib::MainContext::default().invoke(...)`（线程安全、立即叫醒主 context）；(c) macOS 保持既有契约（主线程 quit 已有 app-defined event 快路径），移除 `display_link_callback` 中的无效 `wake()`（或注明消费者为空），并把 `stop.rs`/`main_thread.rs`/`windows/platform_impl.rs` 三处表述改为与两档节奏一致的事实。轮询态后端（android/harmony/ios/wayland/wasm/redox/mobile）的 condvar 通道继续有效。

## 第 2 章 app/handle 与 layout 链（LY3-）

**LY3-01 `dispatch_trigger(Moved)` 每 tick 全树重求解，`apply_window_layout` 无「已应用」守卫**
- **1级** `dispatch_trigger` 的 Moved 分支无条件调 `apply_window_layout`（`app/handle/types.rs:1890-1896`）；而 `apply_window_layout`（`app/handle/window.rs:850-922`）没有 unchanged 守卫，每次执行完整流程：`:857` 构造 context、`:860-862` 写 `LAYOUT_CONTEXT_SCALES`、`:885-891` 根布局全量求解、`:897-920` 每子 `set_widget_geometry` + 递归 panel/declarative 子树求解。布局是纯函数（`window.rs:817-821` 自述 "stays a pure function of its input"），`LayoutContext` 字段只有 layout_scale/font_scale/min_touch_size（`layout/types.rs:153-157`），**无窗口位置输入**；Moved 不改 w/h 也不改 scale，重跑结果逐字节相同。后果：用户拖拽移动窗口期间每个 move tick 对整棵布局树做一次无效重排——flex/wrap 靠 cache key 命中幸免，absolute 无缓存全量重算（与 LY3-02 叠加），declarative 路径每次重解并逐子写 geometry。
- **2级** 给 `WindowState`（`window.rs:1100-1118`）增加 `applied: Option<(u32, u32)>`，`apply_window_layout` 开头比较 `(w, h)` 与 `LAYOUT_CONTEXT_SCALES` 中已存的 scale（复用 `:860-862` 现有表，保证像素尺寸不变的 DPI 切换仍触发重排）三元组，未变则早退。**必须同步失效**：`WindowHandle::set_layout`（`window.rs:781-787`）与 declarative 根 `store_layout` 注册新布局时清除该记录（提 `pub(crate) fn invalidate_applied_layout(window_id)`），否则新注册的布局会被守卫吞掉、直到下次 resize 才生效。Moved 分支保留调用（变 no-op），不改公开行为。

**LY3-02 `AbsoluteLayout` 是 9 个布局中唯一无 LAY-005 式缓存的，no-op pass 全量重算**
- **1级** `AbsoluteLayout::update`（`layout/absolute.rs:914-921`）每次直接 `self.layout(rect)`（`:696-711`：`Vec::new()` + 逐子 `position.resolve`/push）全量求解，无 last_layout/cache；其余布局均有同型缓存（`constraint.rs:167`、`splitter.rs:28-39` 双缓存、`flow.rs:259-273` revision 键控、`flex_cache_key` 等）。触发场景：LY3-01 的 Moved 每 tick、嵌套面板在父 pass 中 rect 未变仍被 `apply_panel_geometry_bounded` 逐子重入（`app/handle/pointer.rs:1560-1578` 对每个 emitted child 无条件重解）、同尺寸重复 Resized。absolute 是 loader 支持的常用声明容器（`json/loader.rs:3492+` 有专项测试）。

**RT3-01 动画稳态下派遣命中 memo 每帧失效（全局 epoch 粒度击穿 PL-05）**
- **1级** `dispatch_widget_at` 的 memo 键用全局 epoch（`widget/runtime/pointer.rs:700` 调 `renderable_epoch()`，键结构 `:656`）；而 `mark_dirty_rect` 每次损害提交**无条件**先 bump 全局 `TREE_FRAME_EPOCH` 再 bump 窗口级（`widget/runtime/repaint.rs:759-767`）。`cache.rs:81-88` 注释自认全局计数器只为无窗口键的 `widget_at_point` 点缓存保留——但有窗口键（root 在键内，`pointer.rs:704`）的 `LAST_DISPATCH_HIT` 也在用全局。窗口级读取器 `renderable_epoch_for(window)` 现成（`cache.rs:162-169`）。后果：任一控件动画（spinner/时钟/进度条，每帧一次 damage）⇒ 全局 epoch 每帧 +1 ⇒ memo 每帧失效 ⇒ 每次 mouse move 全树下降，240 控件规模下 PL-05 在动画稳态完全失效。

**RT3-02 空过滤器链每事件仍付 `catch_unwind` 屏障**

### 18.5 本轮自纠（写用例时发现，已修复并回归）

1. **`lineedit/model.rs` `masked_raw_index_after_caret` 的"反向映射"是错的。**
   18.1 表中该函数的初版用"逐个 raw 前缀 `format` 后比较长度"来定位字符，但
   `MaskEngine::format` 会把空位补成占位符，**任何**非空前缀都格式化成整个掩码宽度，

   **光标之前**的 `1`（`"234-56_"`），而不是之后的 `2`。
   修法：把反演放回掌握语法的引擎——新增 `MaskEngine::raw_index_at_or_after(raw, display_offset)`，
   按段偏移（含字面量的 `len_utf8`）回答"光标右侧第一个输入单元格是第几个原始字符"。
   这同时把 `MaskedEdit` 与 `LineEdit` 的掩码语义收在同一处，不会再次各自漂移。
2. **`icon.rs` 的分支内导入让 `mini`/`embedded` 构建失败。**
   `HorizontalAlignment` 的 `use` 挂在 `#[cfg(widgets_unstripped)]` 下，而新增的
   `draw_unknown_in` 在**所有** profile 都编译（正是给 combo / rating 之类内联图标用的），
   `cargo check --no-default-features -F mini` 报 E0433。改为无条件导入（该类型在小 profile
   也确实被使用，不会产生 unused 告警）。
