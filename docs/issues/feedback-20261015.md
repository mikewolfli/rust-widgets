## 三、原生 Linux 桌面会话上的新证据（不是缺口）

固定修订上，Linux 的原生桌面路径由上游 feature `gtk-native` 选择，而**同一个进程用不用它**决定
`runtime_gui_mode()` 的答案，进而决定宿主能不能声称"会话已启动"。本轮实测：

```text
$ cargo build --features linux-native
$ ./target/debug/rustage --probe-host target/audit-20261015/host-gtk3
rustage host readiness (linux/x86_64 · gtk (NativeInteractive) · rust_widgets c957fdec7f30 @ 0.1.0)
session: native interactive: the checks ran against a real desktop session
startup-session     ready        a separate process ended exit code 0; it printed:
                                 INFO host::startup: backend gtk initialised, gui mode NativeInteractive (+13 ms)
                                 INFO host::startup: window 6000285942072475648 created 1280x800 (+13 ms)
                                 INFO host::platform: entering the event loop for a bounded session (+13 ms)
summary: 13 ready, 1 gap, 1 not verified
```

这不是缺口，但它是一条**宿主必须写进记录的事实**：同一台 Linux 机器、同一条探针命令，在默认构建下
是 `12 ready / 1 gap / 2 not-verified`（`startup-session` = not-verified），在 `--features linux-native`
下是 `13 ready / 1 gap / 1 not-verified`。rustage 已把两种构建分别写进
[`host-probe.md`](../plan/host-probe.md)。

**同一个缺口在 Windows 后端上也复现（本轮三次实测）**：`--probe-host` 在 Windows PE（Wine 下运行，
见第七次记录的第二次记录）同样报 `native-file-dialog -> gap`（`create_file_dialog(0, 0, 0, 640, 420)
-> 0`）。三次实测（状态后端、GTK 原生会话、Windows PE）一致，因此这条不是某个后端的配置问题。

**在原生会话上复现的既有缺口**：`native-file-dialog` 仍是 `gap`——
`create_file_dialog(0, 0, 0, 640, 420)` 在 GTK 原生会话里同样返回 `0`。这条把
[`feedback-20261013.md`](feedback-20261013.md) §8.1 从"状态后端上的推断"升级为"原生会话上的实测"，
其修法在本地 HEAD（`choose_path`）已经就位。

## 四、固定修订上的缺口：`quit()` 在 GTK 与 Windows 后端没有线程检查（本地 HEAD 已修）

**现象（可复现，源码级）**：在 `--features linux-native`（`gtk-native`）构建上，从非主线程调用
`rust_widgets::quit()`：

- `src/platform/linux/platform_impl.rs:395`（固定修订）的实现把 `runtime.running` 置为 `false`，然后
  **无条件**调用 `gtk::main_quit()`：

  ```rust
  fn quit(&self) {
      self.runtime.running.store(false, Ordering::SeqCst);
      #[cfg(all(target_os = "linux", feature = "gtk-native"))]
      {
          gtk::main_quit();
      }
  }
  ```

- 而 GTK 构建的 `run()` 只由 `gtk::main_quit()` 结束（`glib::timeout_add_local` 的闭包无条件返回
  `ControlFlow::Continue`），**没有一处读 `runtime.running`**——那个原子只被同一文件里 *非* GTK 的轮询
  分支读取。于是从别的线程 `quit()` 的效果是：标志没人看，`gtk::main_quit()` 在错误的线程上被调用。

**为什么算问题（两条独立理由）**：

1. **与同一文件的既定规则不一致。** 该文件自己的模块文档写着"GTK 把进程绑在一个主线程上；从别的线程
   构建控件会中止进程，所以 surface 方法检查 `gtk::is_initialized_main_thread()` 并拒绝而不是崩溃"，
   并且有 6 处这样的检查（`platform_impl.rs:160/265/321/481/879/928`）。`quit()` 是唯一绕过它的
   GTK 入口。macOS 后端的同一方法反而**是**有守卫的（`platform_impl.rs:211-216`：`quit skipped:
   not on the AppKit main thread` + `return`）。
2. **调用方拿不到答案。** 返回类型是 `()`，于是"请求已生效"与"请求被忽略"在类型上不可区分——这正是
   原则 #22/#29 禁止的形状，也是 rustage 在 [`feedback-20261013.md`](feedback-20261013.md) §6 里
   记录的那条（固定修订上"跨线程退出"根本没有可用路径）。

**同一个缺口在 Windows 后端也成立（本轮新增证据）**：`src/platform/windows/platform_impl.rs:784`（固定
修订）把 `runtime_running` 置为 `false` 后**无条件**调用 `PostQuitMessage(0)`，而 Win32 的
`PostQuitMessage` 是**线程相关**的：它把消息投给**调用线程**的消息队列。于是从 watcher 线程调用它，
投的是那个线程的队列，窗口线程的消息泵不会收到——会话照旧不结束，而且没有任何地方报告这件事。
上游 `src/platform/stop.rs` 的模块文档把这条限制写得很清楚（"a Win32 `PostQuitMessage` is
thread-affine"），固定修订却仍在两个后端上直调它。

**三个后端三种行为**（固定修订）：

| 后端 | 从非主线程 `quit()` 的结果 | 源码 |
|---|---|---|
| macOS | **拒绝**并留一条 `quit skipped: not on the AppKit main thread` | `src/platform/macos/platform_impl.rs:211-216` |
| GTK | 直调 `gtk::main_quit()`（跨线程触碰主循环栈；`runtime.running` 无人读） | `src/platform/linux/platform_impl.rs:395-401` |
| Windows | 直调 `PostQuitMessage(0)`（投给错误的线程队列；`runtime_running` 同样无人读） | `src/platform/windows/platform_impl.rs:784-791` |

**本地 HEAD 已实现（因此本轮不再请求改动）**：

* `quit()` 的返回类型改为 `bool`（调用方终于能知道"这次请求有没有读者"）；
* GTK 与 Windows 的 `quit()` 说明写明：`runtime.running` 是各自的循环真正读取的标志，由帧回调
  （`crate::platform::stop`）在循环线程上完成停止；`gtk_main_quit`/`PostQuitMessage` 只作为唤醒手段；
* macOS 的守卫保留。

也就是说：固定修订上的这三条差异，正是 `feedback-20261013.md` §6 与本节描述的现象，而它们在
**本地 HEAD（`bc51a9e1`）** 已经按上面第 2、3 条建议处理完。rustage 的绕行（watcher 线程 + 结束进程）
与"会话跑在子进程里"因此在 re-pin 之后需要重新复核，见第七节。

**rustage 侧绕行（已采用并记录）**：有界会话不让库结束进程，而是在到点时由宿主自己的 watcher 线程
记录一条 `WARN` 后结束进程；并且**宿主不在自己的进程里启动会话**（见第五节）。

## 五、不是上游问题，但由本轮发现并修掉的宿主缺陷：探针在原生会话里自毁

记录在这里是因为它**看起来像**上游问题（"库不让我结束循环"），而根因在宿主侧：

- `--probe-host` 的 `startup-session` 检查曾经在**探针自己的进程里**调用 `startup::launch()`。在状态
  后端上这没问题（`launch` 在创建任何东西之前就拒绝），但在原生会话里它会真的进入事件循环，而
  `--launch --exit-after-ms` 到点是由 watcher 线程 `std::process::exit(0)` 结束**进程**的——于是探针在
  写报告之前就死了：实测只打出 4 行日志、没有 `host-readiness.json`、退出码 **0**（一个真开了窗口的
  会话，被记成了一次截断的成功）。
- 修法是让会话跑在**子进程**里（`rustage --launch --log-level info --exit-after-ms <ms>`），父进程读它
  的退出码与输出当证据。这既修掉了自毁，也让证据更强："一个独立的进程真的创建了窗口"。
- 这条**不请求上游改动**：即便上游按 §6/第四节的建议提供跨线程停止，宿主把会话放在子进程里观察仍然
  是对的（报告要在会话之后活着）。

第七节要求把五条宿主侧绕行“换成上游接缝，或写明为什么继续保留”。本节的结论：
**两条换成接缝，三条写明保留理由**。

**已换成接缝（各自独立验证，见 [第四次开发记录](../log/log-20261015-4.md)）**：

1. **`host::watch` → `ChangeKind`。** `WatchEvent::Changed` 现在携带 `rust_widgets::asset::ChangeKind`
   而不是 `os_kind: String`；删除与改名因此可观察，`host::watch` 模块文档里“删除在上游被丢弃”的
   段落随之删除。新增两个用例（创建携带种类、删除被归为 `Removed`）且 512 项全过；`--probe-host` 的
   `directory-watch` 证据现在含“该文件被归类为 Modified”。这同时是 T03.05 的外部修改/删除检测的输入。
2. **`host::clipboard` → `clipboard_text() -> Option<String>`。** 无 rich 后端时不再用
   `get_clipboard_text()` 的空串判断（它把“无文本”与“非文本”合并），改问 `clipboard_text()`；
   `None` 与 `Some("")` 不再混同。主机探针的存/还原也改用该访问器。

**写明保留理由（未迁移）**：

3. **`host::open_url`（对应 `Platform::open_external`）——分层保留。** 该接缝可用，但它是*即发即忘*：
   文档明写“返回即已交出、不等于已打开”，且只提供 `Unsupported`/`InvalidTarget`/`NoHandler` 三种
   退出，**不提供处理器存在性查询**，也不回传子进程句柄。直接迁移会让宿主丢掉两项现有已验证的事实：
   （a）`url-handler` 探针当前能验证“`xdg-open` 在 `PATH` 上”（`is_on_path`）；（b）宿主能区分
   “已开始 / 已失败并带退出码与 stderr / 仍在运行”。若改问 `capabilities().open_external`（Linux 上
   为硬编码 `true`），探针会把“后端有这个接缝”当成“处理器已安装”，正是原则 #45 禁止的形状。
   按原则 #38（若不能消除真实重复，应保留简单实现并记录分层原因），保留宿主实现并把“缺一个
   处理器存在性查询”作为下面的新请求；换接缝留待该查询到位后再做（届时探针证据不降级）。
4. **`host::platform` 的依赖面计数——保留。** 它只用来把“何时该重看这个文件”说清楚，不是一个能力
   声明；换成能力查询收益小、触面大，且现有注释已说明它服务于修订升级（决策 U1）。
5. **`host::dialog` 的原生选择器采用——保留待 F26。** 该绕行不在第三次记录的 §9.1 内，但它同样属于
   第七节第 2 步：`choose_path` 是*阻塞模态*调用，而宿主现有 `FileChooser` 是 `PendingChoice`
   异步接口；采用它需要改该接口，并依赖 F26（设计器自己的文件列表）决定原生/自绘的分工。模块文档
   已把这点记为后续工作，本轮不动。

### 九.1 新请求：暴露“系统处理器是否存在”

**现象**：`Platform::open_external` 的文档说 `OpenError::NoHandler` 是“宿主配置事实，调用方可能想
报告它”，但调用方只能在**真的交出一个目标**（也就是真的打开它）时才知道。`capabilities().open_external`
回答的是“这个后端有没有 `open_external` 实现”（Linux 后端硬编码 `true`），不是“处理器程序是否
已安装”。

**影响**：宿主想在“打开文档”动作失败时把责任分清（“这台机器没装处理器” vs “这个 URL 有问题”），
却没有无副作用的提问方式——而这正是原则 #45“区分命令可启动与命令成功完成”、#22“失败必须显式可诊断”
要求的判据。

**建议**：新增无副作用的查询（其一即可）：`Platform::has_external_handler() -> bool`，或让
`PlatformCapabilities::open_external` 如实反映“处理器程序在 `PATH` 上”（而不是“后端有该方法”），
或在 `platform::external` 暴露一个“本平台的处理器程序名/可用性”查询。到位后，`host::open_url`
即可无损地迁到 `Platform::open_external`，本项目的 `url-handler` 探针也能保持现有证据强度。

## 十、macOS 实机上的三件事（2026-10-15，第五次记录）

本节记录第一次在 **macOS 实机**上构建与运行 `rustage` 时得到的三项事实。第一项是**已闭合**的旧缺口
（新修订已修），后两项是**新的上游请求**，都来自 `--launch`/`--probe-host` 的实机输出。

### 十.1 已闭合：`58012c05` 的 macOS 后端不能编译（`8178d048` 已修）

**现象**：把依赖固定在 `58012c05` 时，macOS 上**连编译都过不去**：

```text
src/platform/macos/file_picker.rs:65:71: error[E0054]: cannot cast `i32` as `bool`
src/platform/macos/file_picker.rs:68:65: error[E0054]: cannot cast `i32` as `bool`
```

`msg_send![panel, setCanChooseFiles: NO]` 的返回值被当作 `bool` 使用，而 Objective-C 的 `BOOL` 是
`i32`/`i8`。本次把依赖升到本地 HEAD = `origin/main` 的 `8178d048`，该修订把三处调用改成
`let _: () = msg_send![…]`，macOS 构建即通过（`cargo build` 零错误、零警告）。**这一项不需要上游
再做什么**，仅作为“固定修订在 macOS 上不可构建”的记录，以及本次 re-pin 的直接原因。

### 十.2 新请求：cocoa 后端的有界会话不会结束（事件循环不 tick）

**现象**（`rustage --launch --exit-after-ms 300`，macOS，`--probe-host` 的 `startup-session` 判为
`gap`）：

```text
INFO host::startup: backend cocoa initialised, gui mode NativeInteractive (+42 ms)
INFO host::startup: window 6000285942072475648 created 1280x800 (+43 ms)
INFO host::platform: entering the event loop for a bounded session (+43 ms)
INFO host::platform: session deadline 300ms reached; asked the loop to stop
                     (no loop had ticked yet; the request is recorded for the next loop) (+351 ms)
```

进程在 25 秒后**仍在运行**（`--probe-host` 侧记的是“a separate process was still running after 20s
and was stopped”）。宿主把停止请求排进循环自己的队列（第三次记录 §6 的 `quit()` 接缝），**但 cocoa
的事件循环一次帧回调都没有发生**，所以排进去的请求永远不会被兑现。

**影响**：`--launch --exit-after-ms` 在 macOS 上不是“有界会话”，而是一个不会退出的窗口；T01.01 的
“基线桌面真实启动**和退出**”因此只在 Linux 一侧成立。这也让任何“靠一次帧回调兑现停止”的宿主机制
（自动保存定时、恢复副本节拍）在 cocoa 上失效。

**建议**：让 cocoa 后端的事件循环在运行期间**至少按后台节拍调用帧回调**（把已排队的 main-thread
工作耗尽），或提供一个与平台无关的“结束循环”接缝，使 `quit()` 不必依赖某一帧真的到来。判据：
`rustage --launch --exit-after-ms 300` 在 macOS 上约 300ms 内退出，且 `--probe-host` 的
`startup-session` 变 `ready`。

### 十.3 新请求：FSEvents 后端把“删除”报成 `Modified`

**现象**：删除一个被监视目录中的文件后，`AssetEvent::FileChanged` 的 `kind` 在 macOS 上是
`ChangeKind::Modified`，而不是 `Removed`（Linux 的 inotify 报 `Removed`，宿主用例
`a_deletion_is_observable_and_classified_as_the_backend_reports_it` 因此按平台分别断言）。

**影响**：T03.05 的“外部删除/重建”检测在 macOS 上拿不到 `Removed`，只能看到“该路径被改动”；
第三次记录 §6 里“删除与改名可观察”这句话在 macOS 上目前为假（宿主已把它按平台收窄并在模块文档
写明，见第五次记录）。

**建议**：让 `change_kind_of` 的判决带上路径证据——一个 `notify` 事件被判为 `Modify` 但其路径在
事件到达时**已不存在**时，映射为 `ChangeKind::Removed`（路径在调用点已经可得，只是现在没有被用来
判断）。这样 FSEvents 的删除与其他后端一致，宿主无需按平台分支。判据：在 macOS 上删除一个被监视
文件后，轮询能看到该路径被归为 `Removed`（与现有 Linux 用例同一断言）。

## 十一、新请求：剪贴板不能承载“应用自定义 MIME 类型”（2026-10-16，第六次记录）

本节记录设计器侧 T05.06（`app::clipboard`）落地时遇到的一条上游缺口，证据与命令见
[2026-10-16 第一次开发记录](../log/log-20261016-1.md) §4。

**现象**：固定修订（`8178d048`）的富剪贴板后端 `RichClipboardBackend` 能承载五类内容——
`Text`/`Html`/`Rtf`/`Image`/`Files`，各自的 MIME 由 `ClipboardContent::content_type()` 给出
（`text/plain`、`text/html`、`text/rtf`、`image/png`、`text/uri-list`），`has_format(&str)` 也按这些
固定名字回答。但**没有任何入口写入或读取一个“应用自定义”的 MIME 类型**：`set_contents` 只接受
`ClipboardContent` 的这几个变体，`get_contents` 也只会在这几个变体里认出一个。

**影响**：设计器复制一个**节点子树**或**资源引用**时，它携带的是设计器自己的类型
`application/vnd.rustage.nodes+json` / `application/vnd.rustage.resource+json`。因为库不接受自定义
类型，宿主只能把整份载荷编成一个 JSON 信封、当**普通文本**放进剪贴板（`text/plain`）。后果有两个：

1. **往返不再有类型保证。** 读回时剪贴板只报告 `text/plain`，无法区分“用户复制的普通文本”与
   “设计器的节点载荷”，设计器只能**嗅探**正文里是否带自己的 `vendor`/`format`/`kind` 字段。
   这是可工作的，但把一个本该由类型回答的问题变成了猜字符串。
2. **富粘贴不可协商。** 与该库支持的类型（如 `text/html`）不同，自定义类型无法被别的应用按类型
   请求，也无法回答 `has_format("application/vnd.rustage.nodes+json")`，因此跨应用或跨进程的
   富粘贴没有可协商的接缝。

**建议**（其一即可）：

- 给 `ClipboardContent` 增加一个自定义变体/入口，例如
  `Custom { content_type: String, data: Vec<u8> }`，并让 `content_type()` 如实回传 `content_type`；或
- 在 `RichClipboardBackend` 上加一对按类型收发的入口，例如
  `set_contents_with_type(&str, &[u8]) -> bool` 与 `get_contents_for_type(&str) -> Option<Vec<u8>>`。

判据：写入一份带 `application/vnd.rustage.nodes+json` 的字节后，`has_format` 对该类型回答 `true`，
且 `get_contents`（或按类型的读入口）能原样取回；Linux（X11/Wayland 的 selection target）与
macOS（`NSPasteboard` 的自定义 type）后端都以各自的原生机制实现。到位后，`app::clipboard`
可以把 `decode` 的嗅探换成按 MIME 读取，宿主侧“把载荷当文本携带”的说明即可删除。

**宿主侧绕行（已采用并记录）**：`app::clipboard` 把节点/资源载荷编成带 `vendor: "rustage"` 的 JSON
信封，走剪贴板的文本通道；`decode` 先嗅探信封，命中则按 `kind` 解析，否则原样当作文本（见
[2026-10-16 第一次开发记录](../log/log-20261016-1.md) §4 与 `src/app/commands/clipboard.rs` 的模块文档）。

## 十二、新请求：没有显示器枚举、窗口所在显示器查询与显示器变更通知（2026-10-16，第六次记录）

本节记录设计器侧 T04.06（`app::windows`）落地时遇到的一条上游缺口，证据与命令见
[2026-10-16 第一次开发记录](../log/log-20261016-1.md) §6。

**现象**：固定修订（`8178d048`）从 `Platform` 接口只暴露一个**单一**的 DPI 比例因子
`dpi_scale_factor() -> f32` 与一个能力标志 `PlatformCapabilities::dpi_scaling`。除此之外，没有任何
方式**枚举显示器**：既拿不到屏幕列表与其边界/工作区，也查不了“某个窗口在哪个显示器上”，更没有
显示器集合变化（拔插显示器、切换主显示器、改 DPI）的通知或重新查询入口。

**影响**：T04.06 的验收词是“拔显示器/改 DPI 后窗口仍可见”。这条判据需要把“窗口现在所在的那块屏幕”
与“现在还有哪些屏幕”放在一起比对，而两者在本修订上都读不到。后果：

1. **无法在真机上验证。** `app::windows` 的 reconcile 规则可以建模并用测试证明（见开发记录 §6），
   但无法与真实屏幕对证：没有读数可供对账，因此“真机上拔掉一块屏”这条只能标为未验证。
2. **无法把窗口放到指定显示器。** 新建“工程新视图窗口/浮动面板”时，宿主只能选一个任意的位置，
   不能按“与主窗口同一块屏”这类规则放置（这正是 T04.06 的“主窗口归属”）。
3. **DPI 变化无事件。** `dpi_scale_factor()` 是一个当前值，没有“它变了”的通知；一个不每帧轮询的
   宿主无法在切换 DPI 时及时把窗口拉回屏内。

**建议**（其一或全部）：

- 枚举接口：`Platform::displays() -> Vec<Display>`，`Display { id, bounds, work_area, scale }`；
- 窗口归属：`Platform::display_of(window) -> Option<DisplayId>`（或窗口几何查询）；
- 变更通知：一个“显示器集合变了”的事件/回调，或一个可重查的版本号（类似现有 `AssetWatcher` 的
  变更信号），使宿主无需轮询。

判据：在真实桌面会话上 `displays()` 至少返回一项；拔掉一块副屏后列表变短，且据此能把一个窗口移到
剩余屏幕上并保持可见；改 DPI 后 `scale` 如实变化（而不是恒为 `1.0`）。这与上游 `platform/types.rs`
的 `dpi_scaling` 标志方向一致，只是把它从一个布尔扩展为可读、可观察的事实。

**宿主侧绕行（已采用并记录）**：`app::windows` 把显示器集合当作**输入**（`Displays`），由调用方扮演
平台角色；没有显示器时 `Windows::reconcile` 如实报 `NoDisplay` 而不虚构一块屏来“保住可见”
（原则 #45）。CLI 的 `--display` 即此输入；无 `--display` 时为了命令可用，用一块**明说**的临时显示器
（`1280x800 @1.0`）并在输出里注明，未冒充为真实读数。

**结论：** 运行时无新增阻塞；API 命名/文档一致性问题见 §十六。

## 十六、`create_window` 的文档与实际效果不一致（2026-10-19，第十次记录）

这是本轮唯一新增的上游请求，按本文件既有格式记录。

**现象。** 固定修订 `8178d048`、`gtk-native`、GTK3/X11 下：

```text
let id = rust_widgets::create_window("rustage", 0, 0, 1280, 800);
rust_widgets::show_widget(id);
// xwininfo -root -tree 只看到 0x... "rustage" 10x10+10+10，没有 1280x800 的顶层窗口。
```

`create_window` 的文档标题是 “Create a top-level window”，示例也只调用了它；但
`backend_for_kind(WidgetKind::Window)` 路由到 custom control backend，其 `create_window` 只
`mount_widget_of_kind` 一个模型，不构造 OS 对象。真正的 native 建窗入口是
`platform::get_platform().create_window(...)`。两个同名入口，一个返回有效 id 却不可见。

**期望。** 二选一，但不能保持现状：

1. `rust_widgets::create_window` 在 native profile 上真正构造 platform toplevel；或
2. 文档与示例明确写成两步契约：`platform::get_platform().create_window` 建 OS 窗口，
   `runtime::register`/`runtime::set_host_window`/`show_widget` 挂载并显示 widget；并说明
   `show_widget` 单独调用不能让 OS 窗口出现。

**判据。** 在 GTK3/X11 会话中，按文档示例调用 `create_window(...)` + `show_widget(id)` 后，
`xwininfo -root -tree` 能看到对应尺寸的映射顶层窗口；若两步 API 才是预期契约，则示例必须展示
两步，且 `create_window` 的名称/文档不再暗示单一调用即可建窗。

**宿主侧绕行（已采用并验证）。** `src/host/platform.rs` 显式调用
`rust_widgets::platform::get_platform().create_window`，再 `runtime::register` +
`runtime::set_host_window` + `show_widget`；`close_window` 先 `hide_widget` 再解除关联。证据见
[2026-10-19 第一次开发记录](../log/log-20261019-1.md) §5.7 与 `host/platform.rs` 的
`creating_a_window_mounts_its_widget_associates_the_host_and_shows_it` 测试。

**结论：** 请求一项 API/文档一致性修正；不要求新增能力。此前开放的上游点（§四、§九.1、
§十.2、§十.3、§十一、§十二）状态不变。

## 十七、GTK 窗口的键盘焦点从未建立（2026-10-19，第十一次记录）

**现象。** 固定修订 `8178d048`、`gtk-native`、GTK3/X11 下，真实 XTest 点击 smoke 的
`LineEdit` 后，再 `XSetInputFocus` 到 1280×800 顶层窗口并发送 `Tab` + `abc`，宿主没有收到任何
`smoke field changed`；同一会话里的按钮点击正常，并能把事件送进业务进程。

代码路径上有两处缺口，任一都足以阻断键盘：

1. `widget::runtime::dispatch_pointer_event`（`runtime.rs:866`）在指针按下时只做 capture 与
   dispatch，**不调用** `focus_on_pointer_press`。这个“pointer routing should call”的入口
   （`runtime.rs:605`）在生产代码里没有任何调用者，grep 只能找到定义与测试。
2. GTK 窗口的 `paint_area` 在按键处理前调用 `set_can_focus(true)`
   （`platform/linux/platform_impl.rs:774`、`:956`），但**从未** `grab_focus()`。旁边的注释已经
   写明“without the grab, keys would go to the window and typing into a `LineEdit` would do
   nothing”，代码却缺少那一步。

**期望。** 两处至少修一处，最好都修：

- `dispatch_pointer_event` 在 press 命中可聚焦控件时调用 `focus_on_pointer_press(target)`；
- `paint_area` 在窗口显示或首次指针按下时 `grab_focus()`，使 `key_press_event` /
  `key_release_event` 能到达它已连接的 handler。

**判据。** GTK3/X11 下：点击 `LineEdit` → 注入 `abc` → 控件文本变为 `abc`；同时按钮点击次数
保持不变（1 次）。回调是否触发见下面的附带观察。

**验证（临时 worktree，未进入仓库）。** 在 `~/workspace/rust-widgets` 的临时 worktree
`/tmp/rust-widgets-keyboard`（HEAD 仍为 `6c6af71e`）上加了 18 行，只做上面两点；用该副本
构建 `rustage --features linux-native` 后，`tools/gui-smoke/run.py --keys` 通过：

```text
gui-smoke: keyboard input verified with the upstream focus fix
INFO host::platform: smoke field final: "abc"
```

随后 worktree 已删除，项目 `Cargo.toml`/`Cargo.lock` 恢复为固定 git 修订；这证明了修复的
充分性，但也意味着固定修订下键盘仍不可用。默认 `run.py` 不启用 `--keys`，不会把未修复的
上游写成通过。

**附带观察（建议同轮确认）。** 补丁后文本框内容确实变成 `"abc"`，但
`WindowHandle::on_value_changed` 的回调**没有**触发（没有 `smoke field changed: abc`）。按键
已经到达控件并改变了文本，所以这不是焦点问题；需要确认 `LineEdit` 编辑后是否应
`inject_widget_trigger_event(ValueChanged)`，以及 `drive_frame`/`drain_triggers` 是否应把它
送达 `VALUE_CALLBACKS`。宿主目前用循环结束后的 `get_widget_text` 直接读值。

**宿主侧绕行（已采用，但不足以完成键盘）。** `rustage` 在 smoke 控件创建后调用
`runtime::focus_widget(field_id)`，这只设置路由器焦点；GTK 仍不把键事件送到 `paint_area`，
所以 `tools/gui-smoke/run.py` 默认不把键盘写成通过。IME 的 preedit 同样依赖这条焦点链；
上游修复后需要再用 fcitx/ibus 做一次 preedit 往返。

**结论：** 请求上述焦点修正；不要求新增控件或 IME API。此前开放的上游点状态不变。

### 十七补充（2026-10-19 第十二次记录）：宿主绕行已让固定修订跑通键盘/IME；上游缺口仍在

**现象复核。** 固定修订下，宿主在 `show_widget` 之后对 `paint_area` 调用 `grab_focus()`，并在
X 层 `XSetInputFocus` 到真实 toplevel，键盘即可到达 `paint_area`；`tools/gui-smoke/run.py --keys`
不再需要临时 worktree 补丁，直接得到：

```text
INFO host::platform: smoke field changed: abc
INFO host::gui-smoke: event accepted: Field/change (text="abc") -> node 2: call edit (call)
INFO host::platform: smoke field final: "abc"
```

**但这仍不是上游修复。** 指针按下移动焦点的入口 `focus_on_pointer_press` 依然没有生产调用者，
`paint_area` 依然只 `set_can_focus(true)` 而不 `grab_focus()`；宿主必须知道 GTK 内部哪个
`DrawingArea` 是画布，这在真实多窗口/嵌入式场景不可扩展。请求保持不变：

1. `dispatch_pointer_event` 在 press 命中可聚焦控件时调用 `focus_on_pointer_press(target)`；
2. `paint_area` 在窗口显示或首次指针按下时 `grab_focus()`。

**`ValueChanged` 观察更新。** 在本轮多次 `--keys` 运行中，`WindowHandle::on_value_changed` 仍未
被观察到触发；文本变化是通过宿主每 100 ms 读取 `get_widget_text` 去重后发现的。键盘事件确实
到达了控件（文本从 `""` 变为 `"abc"`），所以这仍是一个独立的触发/回调缺口。请求：`LineEdit`
的键路径在文本实际变化后注入 `ValueChanged`，并让 `drive_frame`/`drain_triggers` 把它送到
`VALUE_CALLBACKS`；宿主不应被迫轮询才能观察编辑。

**IME 的真实 preedit（新增请求）。** 宿主自己创建 `gtk::IMMulticontext`、阻断库自带 key
handler、调用 `filter_keypress`，再通过现有 `platform::ime::deliver_composition` /
`deliver_commit` 投递，才能在固定修订上得到真实合成：

```text
INFO host::platform: smoke IME client window: ... context=Some("fcitx5"), gtk-im-module=Some("")

INFO host::platform: smoke IME commit: 你好
```

这说明 `platform::ime` 的投递 API 是可用的，缺的是**平台层接管 toolkit IM context 的文档化入口**：

- **期望：** `gtk-native` 的窗口/`LineEdit` 在获得焦点时创建并 `focus_in` 一个 `IMMulticontext`，
  在 `key_press_event` 里先 `filter_keypress`，把 `preedit_changed`/`commit` 通过
  `platform::ime` 的现有函数投递；库自带 handler 不得再插入同一批字符。
- **判据：** fcitx5 处于激活的 `pinyin` 时，输入 `nihao` 应在 `LineEdit` 上依次看到
  `n → ni → ni h → ni ha → ni hao` 的 preedit，空格后得到 `你好`；fcitx 处于 `keyboard-us`
  或未激活时逐键 commit 是正确行为，不应被当作该入口的失败。
- **宿主绕行：** 目前由 `rustage --ime` 创建 context、阻断库 handler、自己 `filter_keypress` 并
  投递；连续 8 次真实运行（harness 修复前 5、后 3）通过（[log-20261019-1.md](../log/log-20261019-1.md) §11.1）。该绕行
  依赖 GTK 内部结构与单窗口 smoke，不是产品级接缝。
