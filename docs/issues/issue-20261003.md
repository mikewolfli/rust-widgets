### P-01：objc2 surface 能力声明与真实呈现路径不一致

- 证据：[挂载实现](../../src/platform/macos_objc2/platform_impl.rs#L176)、[失效请求](../../src/platform/macos_objc2/platform_impl.rs#L199)、[能力返回](../../src/platform/macos_objc2/platform_impl.rs#L208)、[原生窗口创建](../../src/platform/macos_objc2/native.rs#L90)。
- `mount_surface` 记录挂载，`invalidate_surface` 记录重绘请求，`supports_surfaces()` 却返回 `true`；该后端未覆盖 [trait 的重绘消费默认实现](../../src/platform/types.rs#L773)，默认返回 `None`。原生创建路径没有接入画布视图/呈现消费者。
- 触发：选择 objc2 后端，成功挂载控件后请求刷新。成功的状态记录不能兑现为可见像素更新。
- 选择条件已核对：[bridge selector](../../src/platform/macos/macos_bridge.rs) 在 `macos` feature 存在时优先选择 objc2；`desktop` 单独选择 legacy，`desktop,macos` 即使同时带 `cocoa-legacy` 也选择 objc2。不是仅检查了未使用的替代模块。
- [现有测试](../../src/platform/macos_objc2/tests.rs#L153)覆盖记录操作，不证明实际绘制。`desktop,macos` 编译通过也不证明此行为。
- 原则：#5、#12、#13、#37。
- 后续验收：macOS 主线程真实挂载并修改控件状态，观察像素更新及请求消费；未实现时应诚实报告能力缺失。

### P-02：Win32 一个顶层窗口关闭导致整个消息循环退出

- 证据：[WM_DESTROY](../../src/platform/windows/types.rs#L447)、[WM_QUIT 消费](../../src/platform/windows/platform_impl.rs#L740)、[可重复创建窗口的路径](../../src/platform/windows/platform_impl.rs#L959)。
- 使用 `RustWidgetsWindowClass` 创建的每个后端顶层窗口收到 `WM_DESTROY` 都无条件 `PostQuitMessage(0)`；消息循环收到 `WM_QUIT` 后停止，而非检查仍存活的其他窗口。canvas 的独立窗口类和外部自行创建的 HWND 不在这条结论范围内。
- 触发：同时打开两个窗口，关闭一个；其余窗口仍存在，但输入/绘制消息不再正常处理。
- 原则：#5、#13。
- 后续验收：关闭一个窗口后另一个仍响应输入和重绘；最后一个窗口关闭时再按约定退出。

### P-03：Wayland 原生关闭请求没有实际消费者

- 证据：[xdg_toplevel::Event::Close 分支](../../src/platform/wayland/platform_impl.rs#L1113)。
- 分支仅调用 `log::info!`，没有销毁窗口、退出循环或排入宿主可读取的关闭通知。
- 触发：compositor 请求关闭窗口，库没有兑现关闭语义。`mobile,wayland-native` 的交叉 `cargo check` 已通过，故问题不是这段代码是否可编译。
- 原则：#5、#13。
- 后续验收：compositor 关闭动作能到达宿主，按既定策略关闭并清理；不得只观察到日志。

### P-04：objc2 窗口从逻辑注册表删除，不等于从 AppKit 关闭

- 证据：[显示窗口](../../src/platform/macos_objc2/native.rs#L114)、[destroy_widget](../../src/platform/macos_objc2/platform_impl.rs#L281)、[remove_native_view](../../src/platform/macos_objc2/native.rs#L57)。
- 对窗口调用通用 `remove_native_view`，只尝试 `removeFromSuperview` 并释放注册表引用；`NSWindow` 不是普通子视图，没有发送 `close` 或 `orderOut`。
- 影响：逻辑 id 消失不保证窗口从屏幕/AppKit 活动列表消失；资源残留的具体表现仍需原生实测，不能将其直接量化为泄漏量。
- 原则：#5、#13、#30。
- 后续验收：创建/销毁后检查屏幕及 AppKit 窗口列表，多轮检查没有残留。

### P-05：短路布尔表达式使销毁清理不完整

- 证据：[宿主状态清理](../../src/control_backend/custom/create_widgets.rs#L166)。
- `ime_enabled.remove(...).is_some() || accessibility_names.remove(...).is_some() || window_client_sizes.remove(...).is_some()` 会短路：第一份存在时，后两次 `remove` 根本不执行。
- 触发：同一个 id 同时有 IME 与辅助名称/客户区尺寸记录；销毁后仍有旧状态，后续销毁还可能继续报告存在。
- 原则：#13、#30、#99。
- 后续验收：一次销毁后逐个 map 均无该 id，第二次销毁不应因残留状态再次返回成功。

### P-06：线程预算比不是进程 CPU 利用率

- 证据：[Linux 内核共享探测](../../src/platform/os_probes.rs#L96)、[Platform 的 CPU 契约](../../src/platform/types.rs#L910)、[CPU 压力消费者](../../src/gpu/performance.rs#L365)。
- 实现返回 `Threads / (available_cores * 2)`，没有读取任何 CPU 时间或采样时间差。相同线程数下，全部阻塞等待和持续忙碌会返回同一数字。
- Android/OHOS/Linux/Wayland 共用此探测。虽然模块注释诚实写了“estimate”，trait 和消费者仍将返回值解释为 CPU utilization；大量空闲线程可误报压力，单个忙碌线程又可低报实际负载。
- 无法取得核心数时还默认 4.0，进一步把未知事实变成具体测量结果。
- 原则：#18、#37、#38。
- 后续验收：分别用等待线程和忙碌线程测量，与 OS 进程 CPU accounting 对照；无法可靠测量时返回 None，线程预算应另设语义。

### P-07：未知平台测量被解释为无压力

- 证据：[平台返回 None 的约定](../../src/platform/types.rs#L898)、[内存消费](../../src/gpu/performance.rs#L233)、[CPU 消费](../../src/gpu/performance.rs#L257)。
- trait 要求调用者不要将 None 当成零/空闲；两条消费路径在没有平台来源时都只写 debug 日志并返回 0.0。
- 结果是“没有可靠测量”被写入正常 performance sample，随后压力阈值判断把未知平台视为没有压力。此问题独立于某个 backend 是否提供可靠测量。
- 原则：#18、#37。
- 后续验收：None 与真实 0.0 在采样与质量决策中可区分；无来源时不能宣称已测得无压力。

### E-01：归一化只做了验证，没有用于实际订阅地址

- 证据：[connect_event](../../src/widget/capability.rs#L1131)、[normalize_key](../../src/widget/capability/coercion.rs#L836)、[wire_one](../../src/signal/event_bridge.rs#L403)、[hub.emit](../../src/signal/hub.rs#L45)。
- `connect_event("slider", "value-changed", ...)` 根据归一化结果验证通过，却调用 `hub.connect(event_name, slot)`，保存 `"value-changed"`。
- `forward_all` 根据 schema/动态引用的标准名发出 `"value_changed"`，hub 按字符串精确查找，两者不是同一项。大小写与空格容错也存在同类断链。
- 原则：#13、#97、#98。
- 后续验收：标准名、连字符、大小写、空格写法都绑定到唯一标准名；同一次真实控件变化恰好送达一次。

### E-02：无符号事件类型在动态转换处改变

- 证据：[Carousel 的 Signal1<usize>](../../src/widget/container_widgets/carousel.rs#L303)、[动态转换](../../src/widget/container_widgets/carousel.rs#L665)；[TreeTable 信号声明](../../src/widget/view_widgets/tree_table.rs#L58)、[动态转换](../../src/widget/view_widgets/tree_table.rs#L330)、[对应 schema](../../src/widget/capability/event_payloads.rs#L402)。
- `page_changed`、`projection_changed`、`selection_changed` 的声明为 UInt/OptionalScalar，但转换使用 `CapabilityValue::Int(*v as i64)`。
- 普通值就会改变 enum carrier；64 位无符号超出 `i64::MAX` 时还会产生有损转为负数。后者是转换边界，不表示用户可通过普通 UI 创建如此多项。
- 广度扫描得到 39 个同类候选（包括导航、分页、菜单、列表、表格、Web 页索引），按根因合并记录，不声称全部已经运行复现。
- 原则：#29、#31、#95。
- 后续验收：对每个动态引用订阅后检查收到的是 `UInt`；可选空值是 `Null`，非空值仍为 `UInt`。

### E-03：schema 的结构化类型与动态边界实际值不对称

- 证据：[RangeSlider schema](../../src/widget/capability/event_payloads.rs#L255)、[RangeSlider 转换](../../src/widget/input_widgets/range_slider.rs#L446)、[MapView 转换](../../src/widget/special_widgets/map_view.rs#L301)、[CodeEditor 转换](../../src/widget/special_widgets/code_editor/editor.rs#L4425)、[CapabilityValue 的现有变体](../../src/widget/capability/types.rs#L23)。
- `range_changed` 声明 Float/Tuple2，却发送 `String("(lower, upper)")`；`center_changed` 同样把坐标对变为字符串；CodeEditor 的可选 Rect 也把非空值变为 Debug 字符串而非 `Rect`。
- 这不是 JSON 往返的稳定结构协议，消费者不能按 schema 的数值/矩形类型直接读取；Debug 拼写不能作为结构化载荷的类型证明。
- 同类候选包含 Cascader、Grid、GridTable、DataGrid、VirtualList 等。门控主动接受部分结构体的 String 兜底，不能用门控通过否定此差距。
- 原则：#31、#95、#96。
- 后续验收：声明、动态实际载荷、序列化协议三者对齐；对元组/列表/可选值逐项断言，不只断言“收到事件”。

### E-04：payload delivery 门控漏查外层块 arm

- 证据：[delivery_failures 的正则](../../tools/check_event_payload_types.py#L156)、[一个未匹配的 Carousel arm](../../src/widget/container_widgets/carousel.rs#L668)、[TreeTable arm](../../src/widget/view_widgets/tree_table.rs#L333)。
- 正则要求 `"name" => Some(EventSignalRef::...)`，不允许箭头后出现 `{`；大量实现采用 `"name" => { Some(...) }`，会被整个跳过。
- 文本普查的 327 个该形式 arm 中，188 个带外层块（57.5%），139 个直接返回。此数字是匹配形式计数，含共享文件中的实现，不等于 333 个 schema 的完整逐项覆盖率。
- E-02 中 Carousel/TreeTable 的错误转换正好位于被跳过的形态。门控没有对实际比较数量设置全量覆盖断言。
- 原则：#16、#19、#95、#100。
- 后续验收：两种 arm 写法都能识别；分别在两种写法上注入错误必须失败；明确输出比较数和未比较条目。

### E-05：JSON 发布名路径仍把不同事件接到同一泛化回调

- 证据：[发布名分类](../../src/json/event_route.rs#L273)、[bind_published_event](../../src/json/event_route.rs#L428)、[JsonLoader::bind_one](../../src/json/loader.rs#L176)、[handle 连接 base.clicked](../../src/app/handle.rs#L588)、[Button 的动态信号](../../src/widget/base_widgets/button.rs#L510)。
- 发布名最终只决定 click/value/close 等 marker；bind_one 没有用发布名解析 `event_signal_dyn`。
- 例如 Button 的 `pressed`、`released`、`canceled` 都是不同信号，但无载荷未知 marker 回退为 Clicked，JSON handlers 均连接 `base.clicked`：实际点击时错误地调用多个 handler，真正取消时 `canceled` handler 不会按取消信号触发。
- ColorWell 的 `event_signal_dyn("clicked")` 指向其独立 `self.clicked`，实际 [MousePress](../../src/widget/display_widgets/color_well.rs#L288) 也发送该信号；handle 仍订阅 `base.clicked`。这条链上没有语义桥接，[BaseWidget](../../src/widget/base.rs#L881) 明确不自动发出语义 click。
- 正确的动态能力已经存在，但发布名路径与旧 callback table 并行，发生真实语义漂移。
- 原则：#13、#97、#98、#101。
- 后续验收：以真实 press/release/cancel 分别驱动，JSON handler 只响应声明的那个信号；ColorWell 的 JSON 与动态订阅行为一致。

### E-06：载荷没有到达 JSON handler，文档所述读取入口不存在

- 证据：[wire_one 丢弃 _value](../../src/signal/event_bridge.rs#L428)、[forward_all 的载荷文档](../../src/signal/event_bridge.rs#L221)、[JSON 丢弃 _value](../../src/json/loader.rs#L222)、[EventHandlerContext 字段](../../src/json/events.rs#L17)、[value dispatch](../../src/app/handle.rs#L894)。
- bridge 文档声称需要载荷的消费者可通过 `connect_event` 从 binding event object 读取，但该 API 的 slot 是 `FnMut()`，hub 也是零参数，context 只有 trigger 和 user_data，没有载荷字段。
- JSON value 回调即使获得字符串也丢弃；handle value dispatch 读取 `get_widget_text`，其 [后端实现](../../src/control_backend/custom/create_widgets_helpers.in.rs#L184) 明确读 label/text/title/message，并非刚刚发出的数值载荷。
- 零参数 legacy hub 本身可以是有意设计；问题是不能据此声称设计器的类型化载荷已交付，也不能让 JSON 类型连线以旧的无值通道冒充完成。
- 原则：#18、#95、#98、#101。
- 后续验收：真实滑块变化的数值进入 handler，值与 schema 一致；不能以控件 caption 或调用次数代替载荷。

### E-07：短缺台账把历史记录当成当前活跃连接

- 证据：[全局 ledger](../../src/signal/event_bridge.rs#L136)、[record 的 max](../../src/signal/event_bridge.rs#L298)、[accumulate 的加法](../../src/signal/event_bridge.rs#L323)、[查询](../../src/signal/event_bridge.rs#L349)、[unbind_all](../../src/signal/event_bridge.rs#L579)。
- 台账以 `(WidgetKind, published_count)` 为键，而非实例/事件名/当前连接；record 取历史最大值，accumulate 将重复连接也累加至 published。
- 触发一：完整接线后解绑/drop，账本不减少，查询仍可能返回 `Some(0)`；触发二：新建同 kind 实例读到旧实例记录；触发三：反复 forward_one 同一个事件直到计数饱和，其他事件完全未连接也被报告为零短缺。

- 原则：#18、#97、#99、#100。
- 后续验收：实例独立、按不同事件去重；解绑后按定义报告未接线；若保留历史统计，应与活跃状态查询分开。

### E-08：slot_count 不能证明本 binder 的 hub 可达

- 证据：[event_is_wired](../../src/signal/event_bridge.rs#L458)、[EventSignalRef::slot_count](../../src/signal/event_signal_ref.rs#L136)。
- 给控件的真实 signal 接一个普通观察者即可使 slot_count > 0，即使没有任何向当前 hub 的转发；绑定到 hub A 后，面向 hub B 的查询也会得到 true。
- blocked slot 同样计入总数。应区分“信号有观察者”与“当前订阅目的地可收到该事件”，不能用前者证明 `connect_event` 的订阅会响。
- 原则：#97、#100。
- 后续验收：只有直连观察者/连接到别的 hub/连接已 blocked 的三个案例中，目的地可达性必须有准确且明确的查询语义。

### E-09：控件同步 emit 时，handle 回调重入注册表会 panic

- 证据：[with_widget_mut](../../src/widget/runtime.rs#L1853)、[with_widget](../../src/widget/runtime.rs#L1863)、[dispatch_event](../../src/widget/runtime.rs#L1881)、[Button release 发信号](../../src/widget/base_widgets/button.rs#L695)、[register_click_callback 同步执行用户回调](../../src/app/handle.rs#L588)。
- dispatch_event 在 MOUNTED 的全局 `RefCell` 可变借用仍存活时调用 handle_event；控件同步 emit 进而调用用户 handler。
- handler 内读取/修改本控件或其他控件会再次 borrow 同一个注册表，不是只有“重入同一控件”才有风险。`try_with` 只处理线程局部存储访问，不会消除内部 `borrow()`/`borrow_mut()` 的冲突 panic。
- 原则：#5、#13、#29。
- 后续验收：真实按钮回调读取自身属性、更新另一个 Label、关闭窗口等常规动作不 panic；重入策略必须显式且不破坏所有权。

### E-10：回调 unwind 会留下“有 slot、无 callback”的信号

- 证据：[Signal::emit 的 take/invoke/restore](../../src/signal/core_signal.rs#L303)、[slot_count](../../src/signal/core_signal.rs#L345)。
- callback 先从 map 中 take，再执行，正常返回后才放回；若 callback panic 并被宿主 catch_unwind，恢复段不会执行。
- 该 entry 仍存在但 callback 永久为 None，后续 emit 跳过它，slot_count 却仍计入它；E-08 的查询会继续报告有接线。
- 原则：#13、#97。
- 后续验收：捕获一次用户回调 unwind 后，slot 按明确定义恢复或移除，并确保计数/可达查询与实际一致。

### E-11：同优先级连接顺序与文档不一致

- 证据：[模块顺序承诺](../../src/signal/core_signal.rs#L22)、[snapshot 和排序](../../src/signal/core_signal.rs#L287)。
- snapshot 来自 HashMap 的迭代顺序，只按 priority 排序；稳定排序只能保留 HashMap 的原顺序，不能恢复连接顺序。
- 影响：相同 priority 的业务 handler 顺序不可靠，不能依赖“先连接先执行”。
- 原则：#18、#29。
- 后续验收：固定多个同优先级连接，跨不同 map 布局/重复运行验证连接顺序；或明确改变公开顺序契约。

### E-12：payload 回归测试通过，不能证明载荷送达

- 证据：[one_call_wires_a_payload_carrying_event](../../tests/event_wiring_test.rs#L69)、[converted_controls_wire_every_published_event](../../src/signal/event_bridge.rs#L664)。

- 第二个“每个事件可达”检查只比较接线数量/历史短缺，没有逐个驱动真正事件并观察交付。
- 本轮实际运行两个 integration test 文件，17 个测试全部通过；这条记录指明现有绿灯的证明边界，**不是声称有测试失败**。
- 原则：#1、#16、#19、#98、#100。

### W-01：RangeSlider 的 min_range 可以破坏硬范围

- 级别：P1；源码确认，置信度 100%；未执行新增 Rust 复现测试。

### W-02：VideoPlayer 的时钟允许负数/NaN 污染并发送异常事件值

### P-10：共享状态销毁不回收关联队列/表面记录

- 原则：#5、#13、#30。
- 后续验收：mount/inject → destroy → poll/resize/unmount，确认无残留；若需宿主显式拆除，必须在销毁契约中明确并保证实际调用链完成。

### P-11：浏览器 clipboard 的异步结果与同步镜像脱节

- 证据：[set_clipboard_text](../../src/platform/wasm/platform_impl.rs#L290)、[get_clipboard_text](../../src/platform/wasm/platform_impl.rs#L300)。

- 原则：#12、#36、#99。
- 后续验收：成功写入/读回、权限拒绝、失去用户激活三类场景都能明确区分已完成、失败与未知。

### P-13：portable 的 checked 范围校验发生在行长度溢出之后

### P-15：XComponent 重绑定的旧回调没有隔离（候选）

- 若 A 仍活着时再绑定 B，A 的后续输入/销毁可能作用于 B 的当前挂载对象/表面。**尚未证明产品允许这条生命周期**：如果契约严格保证只绑定一次，本项应转为公开约束/拒绝重绑定的验证项。

- 原则：#12、#35、#37。
- 后续验收：绑定 A → 绑定 B → A 输入/销毁，确认新组件不受污染，或第二次绑定被明确拒绝。

### P-16：TouchPoint 语义字段丢失（候选，不是布局错误）
