### P-01：objc2 surface 能力声明与真实呈现路径不一致

- 证据：[挂载实现](../../src/platform/macos_objc2/platform_impl.rs#L176)、[失效请求](../../src/platform/macos_objc2/platform_impl.rs#L199)、[能力返回](../../src/platform/macos_objc2/platform_impl.rs#L208)、[原生窗口创建](../../src/platform/macos_objc2/native.rs#L90)。
- `mount_surface` 记录挂载，`invalidate_surface` 记录重绘请求，`supports_surfaces()` 却返回 `true`；该后端未覆盖 [trait 的重绘消费默认实现](../../src/platform/types.rs#L773)，默认返回 `None`。原生创建路径没有接入画布视图/呈现消费者。
- 触发：选择 objc2 后端，成功挂载控件后请求刷新。成功的状态记录不能兑现为可见像素更新。
- 选择条件已核对：[bridge selector](../../src/platform/macos/macos_bridge.rs) 在 `macos` feature 存在时优先选择 objc2；`desktop` 单独选择 legacy，`desktop,macos` 即使同时带 `cocoa-legacy` 也选择 objc2。不是仅检查了未使用的替代模块。
- [现有测试](../../src/platform/macos_objc2/tests.rs#L153)覆盖记录操作，不证明实际绘制。`desktop,macos` 编译通过也不证明此行为。
- 原则：#5、#12、#13、#37。
- 后续验收：macOS 主线程真实挂载并修改控件状态，观察像素更新及请求消费；未实现时应诚实报告能力缺失。

### P-02：Win32 一个顶层窗口关闭导致整个消息循环退出

- 证据：[WM_DESTROY](../../src/platform/windows/types.rs#L447)、[WM_QUIT 消费](../../src/platform/windows/platform_impl.rs#L740)、[可重复创建窗口的路径](../../src/platform/windows/platform_impl.rs#L959)。
- 使用 `RustWidgetsWindowClass` 创建的每个后端顶层窗口收到 `WM_DESTROY` 都无条件 `PostQuitMessage(0)`；消息循环收到 `WM_QUIT` 后停止，而非检查仍存活的其他窗口。canvas 的独立窗口类和外部自行创建的 HWND 不在这条结论范围内。
- 触发：同时打开两个窗口，关闭一个；其余窗口仍存在，但输入/绘制消息不再正常处理。
- 原则：#5、#13。
- 后续验收：关闭一个窗口后另一个仍响应输入和重绘；最后一个窗口关闭时再按约定退出。

### P-03：Wayland 原生关闭请求没有实际消费者

- 证据：[xdg_toplevel::Event::Close 分支](../../src/platform/wayland/platform_impl.rs#L1113)。
- 分支仅调用 `log::info!`，没有销毁窗口、退出循环或排入宿主可读取的关闭通知。
- 触发：compositor 请求关闭窗口，库没有兑现关闭语义。`mobile,wayland-native` 的交叉 `cargo check` 已通过，故问题不是这段代码是否可编译。
- 原则：#5、#13。
- 后续验收：compositor 关闭动作能到达宿主，按既定策略关闭并清理；不得只观察到日志。

### P-04：objc2 窗口从逻辑注册表删除，不等于从 AppKit 关闭

- 证据：[显示窗口](../../src/platform/macos_objc2/native.rs#L114)、[destroy_widget](../../src/platform/macos_objc2/platform_impl.rs#L281)、[remove_native_view](../../src/platform/macos_objc2/native.rs#L57)。
- 对窗口调用通用 `remove_native_view`，只尝试 `removeFromSuperview` 并释放注册表引用；`NSWindow` 不是普通子视图，没有发送 `close` 或 `orderOut`。
- 影响：逻辑 id 消失不保证窗口从屏幕/AppKit 活动列表消失；资源残留的具体表现仍需原生实测，不能将其直接量化为泄漏量。
- 原则：#5、#13、#30。
- 后续验收：创建/销毁后检查屏幕及 AppKit 窗口列表，多轮检查没有残留。

### P-05：短路布尔表达式使销毁清理不完整

- 证据：[宿主状态清理](../../src/control_backend/custom/create_widgets.rs#L166)。
- `ime_enabled.remove(...).is_some() || accessibility_names.remove(...).is_some() || window_client_sizes.remove(...).is_some()` 会短路：第一份存在时，后两次 `remove` 根本不执行。
- 触发：同一个 id 同时有 IME 与辅助名称/客户区尺寸记录；销毁后仍有旧状态，后续销毁还可能继续报告存在。
- 原则：#13、#30、#99。
- 后续验收：一次销毁后逐个 map 均无该 id，第二次销毁不应因残留状态再次返回成功。

### P-06：线程预算比不是进程 CPU 利用率

- 证据：[Linux 内核共享探测](../../src/platform/os_probes.rs#L96)、[Platform 的 CPU 契约](../../src/platform/types.rs#L910)、[CPU 压力消费者](../../src/gpu/performance.rs#L365)。
- 实现返回 `Threads / (available_cores * 2)`，没有读取任何 CPU 时间或采样时间差。相同线程数下，全部阻塞等待和持续忙碌会返回同一数字。
- Android/OHOS/Linux/Wayland 共用此探测。虽然模块注释诚实写了“estimate”，trait 和消费者仍将返回值解释为 CPU utilization；大量空闲线程可误报压力，单个忙碌线程又可低报实际负载。
- 无法取得核心数时还默认 4.0，进一步把未知事实变成具体测量结果。
- 原则：#18、#37、#38。
- 后续验收：分别用等待线程和忙碌线程测量，与 OS 进程 CPU accounting 对照；无法可靠测量时返回 None，线程预算应另设语义。

### P-07：未知平台测量被解释为无压力

- 证据：[平台返回 None 的约定](../../src/platform/types.rs#L898)、[内存消费](../../src/gpu/performance.rs#L233)、[CPU 消费](../../src/gpu/performance.rs#L257)。
- trait 要求调用者不要将 None 当成零/空闲；两条消费路径在没有平台来源时都只写 debug 日志并返回 0.0。
- 结果是“没有可靠测量”被写入正常 performance sample，随后压力阈值判断把未知平台视为没有压力。此问题独立于某个 backend 是否提供可靠测量。
- 原则：#18、#37。
- 后续验收：None 与真实 0.0 在采样与质量决策中可区分；无来源时不能宣称已测得无压力。

### E-01：归一化只做了验证，没有用于实际订阅地址

- 证据：[connect_event](../../src/widget/capability.rs#L1131)、[normalize_key](../../src/widget/capability/coercion.rs#L836)、[wire_one](../../src/signal/event_bridge.rs#L403)、[hub.emit](../../src/signal/hub.rs#L45)。

### E-02：无符号事件类型在动态转换处改变

- 证据：[Carousel 的 Signal1<usize>](../../src/widget/container_widgets/carousel.rs#L303)、[动态转换](../../src/widget/container_widgets/carousel.rs#L665)；[TreeTable 信号声明](../../src/widget/view_widgets/tree_table.rs#L58)、[动态转换](../../src/widget/view_widgets/tree_table.rs#L330)、[对应 schema](../../src/widget/capability/event_payloads.rs#L402)。

- 原则：#29、#31、#95。
- 后续验收：对每个动态引用订阅后检查收到的是 `UInt`；可选空值是 `Null`，非空值仍为 `UInt`。

### E-03：schema 的结构化类型与动态边界实际值不对称

- 证据：[RangeSlider schema](../../src/widget/capability/event_payloads.rs#L255)、[RangeSlider 转换](../../src/widget/input_widgets/range_slider.rs#L446)、[MapView 转换](../../src/widget/special_widgets/map_view.rs#L301)、[CodeEditor 转换](../../src/widget/special_widgets/code_editor/editor.rs#L4425)、[CapabilityValue 的现有变体](../../src/widget/capability/types.rs#L23)。

- 原则：#31、#95、#96。
- 后续验收：声明、动态实际载荷、序列化协议三者对齐；对元组/列表/可选值逐项断言，不只断言“收到事件”。

### E-04：payload delivery 门控漏查外层块 arm

### E-05：JSON 发布名路径仍把不同事件接到同一泛化回调

### E-07：短缺台账把历史记录当成当前活跃连接

### E-08：slot_count 不能证明本 binder 的 hub 可达

- 证据：[event_is_wired](../../src/signal/event_bridge.rs#L458)、[EventSignalRef::slot_count](../../src/signal/event_signal_ref.rs#L136)。
- 给控件的真实 signal 接一个普通观察者即可使 slot_count > 0，即使没有任何向当前 hub 的转发；绑定到 hub A 后，面向 hub B 的查询也会得到 true。
- blocked slot 同样计入总数。应区分“信号有观察者”与“当前订阅目的地可收到该事件”，不能用前者证明 `connect_event` 的订阅会响。
- 原则：#97、#100。
- 后续验收：只有直连观察者/连接到别的 hub/连接已 blocked 的三个案例中，目的地可达性必须有准确且明确的查询语义。

### E-09：控件同步 emit 时，handle 回调重入注册表会 panic

- 证据：[with_widget_mut](../../src/widget/runtime.rs#L1853)、[with_widget](../../src/widget/runtime.rs#L1863)、[dispatch_event](../../src/widget/runtime.rs#L1881)、[Button release 发信号](../../src/widget/base_widgets/button.rs#L695)、[register_click_callback 同步执行用户回调](../../src/app/handle.rs#L588)。
- dispatch_event 在 MOUNTED 的全局 `RefCell` 可变借用仍存活时调用 handle_event；控件同步 emit 进而调用用户 handler。
- handler 内读取/修改本控件或其他控件会再次 borrow 同一个注册表，不是只有“重入同一控件”才有风险。`try_with` 只处理线程局部存储访问，不会消除内部 `borrow()`/`borrow_mut()` 的冲突 panic。
- 原则：#5、#13、#29。
- 后续验收：真实按钮回调读取自身属性、更新另一个 Label、关闭窗口等常规动作不 panic；重入策略必须显式且不破坏所有权。

### E-10：回调 unwind 会留下“有 slot、无 callback”的信号

- 证据：[Signal::emit 的 take/invoke/restore](../../src/signal/core_signal.rs#L303)、[slot_count](../../src/signal/core_signal.rs#L345)。
- callback 先从 map 中 take，再执行，正常返回后才放回；若 callback panic 并被宿主 catch_unwind，恢复段不会执行。
- 该 entry 仍存在但 callback 永久为 None，后续 emit 跳过它，slot_count 却仍计入它；E-08 的查询会继续报告有接线。
- 原则：#13、#97。
- 后续验收：捕获一次用户回调 unwind 后，slot 按明确定义恢复或移除，并确保计数/可达查询与实际一致。

### E-11：同优先级连接顺序与文档不一致

- 证据：[模块顺序承诺](../../src/signal/core_signal.rs#L22)、[snapshot 和排序](../../src/signal/core_signal.rs#L287)。
- snapshot 来自 HashMap 的迭代顺序，只按 priority 排序；稳定排序只能保留 HashMap 的原顺序，不能恢复连接顺序。
- 影响：相同 priority 的业务 handler 顺序不可靠，不能依赖“先连接先执行”。
- 原则：#18、#29。
- 后续验收：固定多个同优先级连接，跨不同 map 布局/重复运行验证连接顺序；或明确改变公开顺序契约。

### P-11：浏览器 clipboard 的异步结果与同步镜像脱节

- 原则：#12、#36、#99。

- 若 A 仍活着时再绑定 B，A 的后续输入/销毁可能作用于 B 的当前挂载对象/表面。**尚未证明产品允许这条生命周期**：如果契约严格保证只绑定一次，本项应转为公开约束/拒绝重绑定的验证项。
- SDK 20 没有这些普通回调的注销 API，因此只补“调用注销”不是已验证方案；可以另评估身份过滤或明确拒绝重复绑定。
- 原则：#12、#35、#37。
- 后续验收：绑定 A → 绑定 B → A 输入/销毁，确认新组件不受污染，或第二次绑定被明确拒绝。

### P-16：TouchPoint 语义字段丢失（候选，不是布局错误）

- 证据：[Rust TouchPoint](../../src/platform/harmony/xcomponent.rs#L206)、[触点分发](../../src/platform/harmony/xcomponent.rs#L900)、[统一外层类型](../../src/platform/harmony/xcomponent.rs#L909)。
- SDK 20 `native_interface_xcomponent.h:225` 中 TouchPoint 与 TouchEvent 都有 type。Rust 为布局兼容省略触点自己的 type，分发对每个触点都使用外层 event_type。
- **布局对照没有发现此处 ABI 错位**；省略字段由对齐空间承接。风险是语义丢失：若一次多点记录中各触点类型不同，所有触点会被转换成同一种 Down/Up/Move。
- 原则：#5、#12。
- 后续验收：收集 SDK 含混合触点类型的记录，按各点 type 转换并验证手势生命周期；若 SDK 保证类型相同，需补该保证的正式依据再关闭此候选。

### E-15：接线查询仍不是 per-instance

- 证据：[event_is_wired](../../src/signal/event_bridge.rs#L382)、[unwired_events_for](../../src/signal/event_bridge.rs#L258)。
- 它解析了待查询 widget 的 reference，却仅比较 `forwarded.event_name` 与 `forwarded.is_connected()`；后者捕获的是当初接线的 source，不是当前参数 widget。reference 的存在/名称相同不能证明两者是同一 signal。
- 复现：建立 A/B 两个 Button，仅 forward_all(A)。B.clicked 的 slot_count=0，但 event_is_wired(B,"clicked")=true、unwired_events_for(B)=Some(0)。
- 这是查询假阳性，不是名称 hub 的广播语义；即便宿主有意广播，未接线 B 也不该报告自己有线。
- 原则：#97、#100。后续验收：同类 A/B、共享 kind 的不同 capability、不同 binder/hub、解绑后的实例查询都以真实 source 身份判断。

### E-16：JSON 全局 handler 注册表把借用带入用户代码

- 证据：[invoke_global_handler](../../src/json/events.rs#L193)、[register_global_handler](../../src/json/events.rs#L183)、[clear_global_handlers](../../src/json/events.rs#L198)。
- invoke 持 `handlers.borrow()` 调用 EventHandlerMap::invoke，后者直接执行闭包；闭包注册其他 handler/清空布局 handlers 时需要同一 RefCell 的 borrow_mut。
- 实际捕获 `RefCell already borrowed` panic：outer handler 内 register_global_handler("inner", ...)。
- 原则：#5、#13。后续验收：handler 内注册、替换、清空、嵌套 invoke；不能只验证普通 invoke。

### E-17：属性写入回调重入仍会 panic

- 证据：[with_widget_mut](../../src/widget/runtime.rs#L1886)、[共享访问](../../src/widget/runtime.rs#L1897)、[JSON 真实属性驱动测试](../../tests/json_event_route_test.rs#L261)。
- dispatch_event 的 detach 修复没有改变 with_widget_mut：后者仍在 map.borrow_mut() 内调用 f。write_widget_property_by_id 通过此路径修改控件，setter 同步发 signal。
- 复现：挂载 Slider，对动态 value_changed 订阅一个 geometry_of(id) 读取；属性 value 写入 42 在回调中 panic。读取其他 id 也会重借同一个全局 map，而非只有自身风险。
- 原则：#5、#13、#101。后续验收：JSON handler 收到 value 后读/写自身和其他控件，直接 handle setter/属性 API 路径都覆盖，不只鼠标 dispatch。

### E-18：输入回调不能读取自身已提交状态

- 证据：[dispatch_event 的 remove](../../src/widget/runtime.rs#L1935)、[geometry_of](../../src/widget/runtime.rs#L1831)。
- remove 持续整个 handle_event；用户回调执行期间控件不在 MOUNTED。更新其他控件的旧测试可通过，但这不证明当前控件可读。
- 实际 press/release 触发 clicked 时 geometry_of(自身 id)=None；回调结束后 is_mounted 又为 true。JSON payload 虽可带值，但 handler 的其他状态读取仍不能使用普通注册表 API。
- 原则：#18、#37、#99。后续验收：回调内自身 getter 读取最新状态、setter 的明确允许/拒绝语义；不能用“查不到”冒充对象已销毁。

### E-19：dispatch 没有 unwind 生命周期保护

- 证据：[handler 调用及尾部清理](../../src/widget/runtime.rs#L1947)、[in-flight unregister](../../src/widget/runtime.rs#L475)。
- remove + DISPATCHING.insert 后直接 handle_event；用户 callback panic 时，不会执行 DISPATCHING.remove、tombstone 消费、MOUNTED 重插入。
- 宿主 catch_unwind 后真实复现：is_mounted(id)=false，接着 unregister(id) 却仍返回 true（残留 dispatch 标记）。控件被栈 unwind 丢弃，而其他注册表状态未走完整 teardown。
- signal 自身的 RestoreGuard 已保护 slot，不等于 widget dispatch 也有恢复。跨 FFI 不允许 unwind 的目标可能直接终止；本复现限定 Rust 宿主主动捕获 unwind。
- 原则：#5、#13、#30。后续验收：input handler unwind、销毁期间 unwind、同 id 重挂载，确保所有状态恢复/清理一致。

### E-20：TreeTable producer 漏掉选择清除通知

- 证据：[set_model](../../src/widget/view_widgets/tree_table.rs#L82)、[collapse_row](../../src/widget/view_widgets/tree_table.rs#L198)、[rebuild_projection](../../src/widget/view_widgets/tree_table.rs#L238)。
- collapse 重建投影用 filter 把不可见的 selected_row 清掉，只发 projection_changed；set_model 直接 selected_row=None，同样没有 selection_changed。
- 复现：模型有一根一子，展开根并选子，订阅 selection_changed 后收起根：selected_row 从 Some(1) 变 None，通知次数=0。选根后换模型：选择再次清零，次数没有增加。
- clear_model 却明确发 selection_changed(None)，说明不是该控件统一采用“只在用户选择时通知”的语义。
- 原则：#95、#97、#101。后续验收：选择对象隐藏/删除/模型更换分别发准确的 OptionalScalar；也评估行索引未变但所指节点变化的身份契约。

### E-21：并发 emit 的“正在执行”被当成无订阅

- 证据：[callback.take](../../src/signal/core_signal.rs#L330)、[并发支持声明](../../src/signal/mod.rs#L32)。
- emit 暂时取出 callback；另一个线程此时 emit，entry 仍连着且未 blocked，但 callback=None，于是该次值直接被跳过，无排队、错误或诊断。
- 确定性复现：用两个 Barrier 把第一个回调停住；主线程 emit 第二个值并返回，再放行第一个。两次 emit，观察者只执行一次。不是测试时序概率，也不是特意递归调用自己。
- 同线程 re-entry 跳过栈上 slot 已有明确文档和测试；并发吞值不能自动沿用“同一调用栈”的解释。线程安全声明只证明可并发访问，不足以告知调用方会丢事件。
- 原则：#18、#37、#97。后续验收：明确并发交付/串行化/丢弃策略；若不保证逐次交付，必须公开限制并可观测，不能仅称并发 emit 安全。

### 14.3 E-27：普通动态绑定遗忘 token，控件销毁后信号仍被保活（P2，实际复现）

- 证据：[bind_one](../../src/json/loader.rs#L186) 使用 `core::mem::forget(token)`；[release closure](../../src/json/loader.rs#L343) 捕获重新取得的 EventSignalRef，后者拥有真实信号的克隆；[DynamicBinding](../../src/json/event_route.rs#L435) 持有该堆分配闭包。
- 这虽然避免调用结束立即解绑，却把 token 及其拥有的信号引用永久遗忘；并非“控件销毁后自然释放整个绑定”的正常生命周期。普通 JSON `events` 也走这条 bool 接口。
- 实际复现带对照：给 Button.clicked 连接一个持有 Drop 计数器的观察者，销毁挂载控件并释放外部 signal clone。不调用 bind_one 时观察者捕获值析构 1 次；调用 bind_one 后同样 teardown，析构为 0，证明遗忘的 token 仍保留整个信号及其他 slot 的捕获资源。
- [可释放绑定测试](../../tests/json_event_route_test.rs#L556) 通过只证明 token 接口有效，不能证明无 token 的普通加载路径没有泄漏。
- 原则：#30、#97、#101。后续验收：保留 load-time 订阅但不泄漏释放闭包/信号引用；控件销毁且外部观察者引用释放后，slot 捕获资源必须析构。不能用立即 Drop token 的方式使加载后的事件失效。

### 15.1 E-28：clear_global_handlers 在回调内不等于清空全部注册（待决）

- 证据：[invoke_global_handler](../../src/json/events.rs#L230)、[RestoreGuard](../../src/json/events.rs#L238)、[clear_global_handlers](../../src/json/events.rs#L258)、[现有清空重入测试](../../src/json/events.rs#L544)。
- invoke 将当前 handler 暂时取出 map；callback 调用 clear 时只能清除 map 中其他项。invoke 返回或 unwind 时，guard 将执行中的 handler 再插回去，clear 没有作废这次恢复操作。
- 实际复现：注册 `clear` handler，其闭包调用 clear_global_handlers；第一次 invoke 返回 true，第二次 invoke 仍返回 true。只有在 callback 外再次 clear 后，invoke 才返回 false。
- 现有测试**主动要求恢复**当前 handler，所以不把它表述为没有任何文档依据的确定实现缺陷；这是已确认的生命周期契约差异：API 说明“Clear all registered global handlers”，但回调内布局 teardown 的清空不会移除正在执行的注册。
- 风险：销毁/重载在 callback 内清空 registry 时，旧 handler 及其捕获资源继续保留；后续同名事件仍可能执行旧注册。与 E-27 的 token 保活是不同所有权路径。
- 原则：#13、#18、#30。后续需明确选择：clear 包含正在执行的注册，或明确其例外并提供真正的 teardown 入口；验收需覆盖正常返回、panic/unwind、清空后同名重新注册及嵌套 invoke，避免恢复旧 handler 覆盖新注册。

### 15.2 E-29：并发交付串行锁在跨信号转发中形成死锁（P1）

- 证据：[每个信号的 emit_serial](../../src/signal/core_signal.rs#L102)、[emit 持锁进入 callback](../../src/signal/core_signal.rs#L411)、[同线程豁免只检查当前信号](../../src/signal/core_signal.rs#L419)。
- E-21 修复在整个 callback 执行期间持有信号的串行锁。线程 T1 正在执行 A 的 callback 并向 B emit，同时 T2 正在执行 B 的 callback 并向 A emit：T1 持 A 等 B，T2 持 B 等 A。同线程 reentry 检查不能解除另一线程持有的锁。
- 实际复现：A/B 各连接一个转发 slot，仅 payload=1 时转发 payload=2（避免业务递归无限循环）。两个线程分别 emit(1)，通过三方 Barrier 确认两个 callback 均已进入，随后互向另一 signal emit(2)。两次 ready 通知均收到，两个完成通知在各 1 秒 recv_timeout 中均未收到。结合源码锁顺序可确定相互等待，而不是将一般耗时猜成死锁。
- 程序为独立测试进程，等待有界，测试结束后进程退出；没有在宿主留下阻塞线程或后台服务。单个信号并发交付的现有测试通过，不覆盖这一双信号场景。
- 原则：#5、#13、#97。后续验收：保留 E-21 不吞并发值的保证，同时双信号跨线程转发必须有界完成；同线程重入、优先级、解绑、panic 恢复均不得回退。不能仅解除串行锁回到静默丢值，也不能把跨信号转发一律当成无限递归。

### 15.3 E-30：只读入口 with_widget 仍持 RefCell 借用跨用户代码（P1）

- 证据：[with_widget](../../src/widget/runtime.rs#L2028) 在 `map.borrow().get(...).map(|entry| f(...))` 内执行用户闭包；[with_widget_mut](../../src/widget/runtime.rs#L1953) 即使只做短暂 remove，也需要同一个 map 的 borrow_mut。
- 修复 E-17/E-18 已改善 setter/dispatch 的入口，但并未消除只读入口上的相同持借用模式。读取共享 widget 后同步触发其信号是合法的 `&self` 操作；事件 callback 更新另一个控件时仍重借整个 registry。
- 实际复现：挂载 Button A/B；A.clicked 的 slot 调用 with_widget_mut(B) 修改可见性；在 with_widget(A) 的闭包内执行 `w.base().clicked.emit()`。catch_unwind 捕获 RefCell 借用 panic；A/B 均仍 mounted，可正常 unregister。这里不涉及修改正在读取的 A，不是“嵌套写自身”被拒绝的正常契约。
- 原则：#5、#13、#97。后续验收：此入口驱动的 callback 写其他控件不 panic；同时不得通过无保护的裸指针解除借用后允许销毁当前共享引用的对象，需保留 Rust 引用与生命周期安全。对当前对象的删除、嵌套写及 callback unwind 均应单独明确契约。
