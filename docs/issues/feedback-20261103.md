## RW-101｜Windows 构建：`WA_INACTIVE` 类型不匹配（P1，仍阻断 M-3）

**状态：✅ 已修复（log-20261103-1 §1）。** 两侧同型为 `u16`，并新增非 Windows 宿主可跑的 `tablet@windows` 门控单元。

**位置。** `rust_widgets` 4.0.0（`1a30785`）
`src/platform/windows/types.rs:540`：

```rust
let active = (wparam & 0xFFFF) as u32 != WA_INACTIVE;
```

`wparam & 0xFFFF` 被转成 `u32`，而 `WA_INACTIVE`（`windows-sys`）是 `u16`；该文件由 Windows
后端所有 profile 共享。

**复现。** 2026-11-03 的 macOS 宿主记录（[feedback-20261101.md](feedback-20261101.md) 第六轮）：
`cargo xwin build --bin rustage --target x86_64-pc-windows-msvc` 在该行失败。

**本机限制。** 本机 Linux 只安装了独立的 `xwin 0.10.0`，没有 `cargo-xwin` 子命令，无法重跑同一
交叉构建；但源码行在 4.0.0 中未变，属于同一缺陷。**修好后请用 Windows xwin 重新验证五 profile
`--lib` 与 `--bin rustage`，再回写 support-matrix。**

**建议修法。** 让两侧同型即可：

```rust
let active = (wparam & 0xFFFF) as u16 != WA_INACTIVE;
```

并补一条 `--target x86_64-pc-windows-msvc --no-default-features --features embedded --lib` 的
编译门禁，使该组合在非 Windows 宿主也能暴露。

## RW-103｜`DesignerCommand` 的 enum 参数没有可选值（P2）

**状态：✅ 已修复（log §3）。** `DesignerCommand.tokens`，值来自对应属性的 `accepted_tokens`；协议 7。

**位置。** `src/widget/capability/designer_manifest.rs` 的 `DesignerCommand` 只有
`kind: Option<PropertyValueKind>`，没有 `tokens`。当命令参数是枚举时，manifest 无法表达合法取值。

**现象。** 宿主 `--catalog schema:panel` 输出：

```text
command set_alignment: value alignment: enum (mutates-control)
```

`enum` 后的括号为空；同一属性的 **property** 行却有完整取值：

```text
alignment: enum(left,centre,right,top,bottom) = left [left|centre|right|top|bottom]
```

**影响。** 设计器可以从属性 manifest 生成枚举下拉框，却无法为方法参数生成同样的选择器；只能
退回自由文本，再让方法拒绝非法值。这与原则 #54（能力描述可往返）和 #55（不得把未知当成功）的
精神不一致。

**建议修法（任一）。**
1. 给 `DesignerCommand` 增加 `tokens: Vec<String>`，在 `kind == Enum` 时填写；
2. 或把参数改为 `Option<DesignerProperty>`（名称、kind、tokens、constraints 都在一处），
   让属性与方法参数共享同一个类型化 schema。

**验证。** 修好后 `set_alignment`、`set_tab_position`、`set_tab_shape` 等枚举参数应能列出
与对应属性相同的 tokens。

## RW-104｜无事件/无命令控件清单：请确认是否为有意（P3）

**状态：✅ 已处理（log §4）。** `swipe_to_dismiss` / `axis_picker` 已补命令；其余确认有意，已写入 `docs/PRESENTATION_ONLY_CONTROLS.md` 并由测试固定。

**来源。** 宿主 `--catalog show` / `--catalog audit` 对 4.0.0（protocol 6）242 个 kind 的实测。

**没有声明事件的 21 个控件：**

```text
align aspect_ratio center divider drawer_section_header expanded flexible font_preview
frame group_avatar icon ime_preedit intrinsic_width line padding qr_code safe_area
sized_box skeleton_loader spacer tooltip
```

**没有声明命令的 7 个控件：**


**要确认的不是“必须补”，而是“是否有意”。** 多数布局容器/展示控件没有事件或命令是合理的；
但 `swipe_to_dismiss` 没有命令、`axis_picker` 作为可交互容器没有命令，看起来可能是契约缺口。
宿主不会为避免空列表而自造方法或事件（原则 #25）。

**建议。** 若其中有非有意项，请补对应的 `commands`/`events`；若都属有意，请在控件文档中
标注“presentation-only”，让消费方不需要每轮重新判断。

## RW-105｜suites 中 4 个控件的 designer manifest 无法导出（P1，阻断宿主启用 maps/project/devtools）

**状态：✅ 已修复（log §5）。** 四个控件的默认值补齐，并新增 suites 侧 manifest 完整性测试。

**位置。** `rust-widgets-suites` 4.0.0（`1a30785`）：

- `crates/rust-widgets-suites/src/maps/capability.rs` 的 `default_property_value()` 没有
  `map_overview` / `map_attribution` 分支（只有 `map_view`、`tile_loader`、`zoom_control`、
  `scale_bar`、`compass`）；
- `crates/rust-widgets-suites/src/project/` 的 `gantt_task_grid`；
- `crates/rust-widgets-suites/src/devtools/capability.rs` 的 `terminal_find_bar`。

**现象。** 在宿主启用这三个分组后，`rustage --catalog audit` 报告：

```text
problem: gantt_task_grid: the designer manifest could not be read
problem: map_attribution: the designer manifest could not be read
problem: map_overview: the designer manifest could not be read
problem: terminal_find_bar: the designer manifest could not be read
rustage：4 catalog audit problem(s)
```

**原因。** `designer_manifest()`（父 crate `src/widget/capability/designer_manifest.rs:1780-1787`）
对每个属性调用 `factory.default_property_value(canonical_name, name)`；缺一个默认值就返回
`ManifestExportError::IncompleteDefaults`，整个控件的 manifest 不可读。这四个控件在 suites 里已
`try_register`，所以目录能看到它们，但属性默认值没有登记。

**影响。** 宿主无法在不破坏 `--catalog audit` 门禁的前提下启用 `maps` / `project` / `devtools`；
这三个分组里已创建的控制（地图、甘特、看板、时间线、终端视图、diff 等）在设计器目录中不可见。
宿主当前只启用 `form`/`webview`/`finance`/`media-playback`，并在 `Cargo.toml` 注释与本文件登记原因。

**建议修法。** 给三个分组的 `default_property_value` 补齐这四个控件的全部属性分支，值与构造器
初始值一致；然后加一条 suites 侧门禁：对每个 `try_register` 的 canonical name 调用
`designer_manifest` 并断言 `Ok`，阻止“注册了但 manifest 读不出”的新控件再次进入。
验证命令：宿主启用全部分组后 `cargo run -- --catalog audit` 必须退出 0。

## RW-107｜manifest 不表达伴件与宿主的配对（P3，设计期能力缺口）

**状态：✅ 已修复（log §7）。** `DesignerManifest.companion_of`，协议 8。

**位置。** `src/widget/capability/types.rs:1092-1116` 的 `WidgetCapability` 只有 `kind`、
`canonical_name`、`aliases`、`properties`、`events`、`commands`；`DesignerManifest` 同样没有配对字段。

**现象。** 4.0.0 的配合控件（`media_transport_bar`、`media_scrubber`、`subtitle_bar`、
`chapter_list_panel`、`web_history_panel`、`chart_crosshair`、`chart_data_table`、`zoom_strip`、
`axis_picker`、`tooltip_manager` 等）在目录里只有类别（`companion` / `media` / `special` / `external`），
没有“它服务于哪个宿主”的信息。设计器知道把 `video_player` 拖进画布，却不知道该把它与
`media_transport_bar`/`chapter_list_panel` 配对；运行时的 `attach_*` 是 Rust API，文档无法表达。

**影响。** 原则 #54（能力描述可往返）与 #55（接线合法 ≠ 接线生效）：设计器可以把伴件和宿主都插入，
但不能生成把两者连起来的代码，也不能诊断“伴件未附加”。

**建议修法（任一）。**
1. 在 `WidgetCapability` 增加 `companion_of: Option<&'static str>`（或 `attaches_to: &'static [&'static str]`），
   并在 `DesignerManifest` 同步导出；
2. 或在 manifest 增加一个 `attachment` 对象（宿主名、attach 方法名、方向），与现有 `commands` 同一层。

验证：`--catalog schema:media_transport_bar` 应能读出 `companion_of = video_player`（或等价字段）。

## RW-109｜声明式文档无法表达每节点尺寸约束（P1，阻断 T10.03 的“约束进生成”）

**状态：✅ 已修复（log §9）。** 新 child 属性 `min/pref/max_w/h`、`margin`、`overflow`；求解经 `ChildInfo` 提示通道；`overflow` 无载体，已在报告中显式说明。

**位置。** `rust_widgets` 4.0.0（`1a30785`）：

- `src/json/layout_schema.rs:266-274` 的 `CHILD_ATTR_SCHEMA` 只有
  `stretch` / `col` / `row` / `col_span` / `row_span` / `region` / `extent`；
- 容器参数按 kind 固定（如 `hbox`/`vbox` 只有 `spacing`、`margin`，:135-160）；
- `src/designer/generator.rs:1951-1998` 只读上表那几个 child 属性，
  `plan_geometry`（:2223）用它们求解子节点矩形；
- 文档层没有任何字段对应 `Hints.min/pref/max`、每节点 `margin`、`overflow`。

**影响。** 宿主 roadmap T10.03 的模型是“最小/最大/首选尺寸、伸缩、边距、间距、溢出”（以 `Hints`
与 `ControlMetrics` 为准）。其中只有 `stretch`/`spacing`/`margin`（容器级）能进入生成；`min/max/pref`
和 `overflow`、每节点 `margin` 没有文档拼写，宿主只能：

1. 不把面板里的这些约束写进文档（面板就成了第二事实来源，违反 #59），或
2. 写进宿主自有字段并在生成时**拒绝**（保持诚实，但 T10.03 永远进不了生成）。

**建议修法。** 扩展 `CHILD_ATTR_SCHEMA`（生成器已按同一张表读，新增即被消费并纳入
`validate_child_attrs` 的诊断）：

| 新 child 属性 | 类型 | 映射 |
|---|---|---|
| `min_width` / `min_height` | uint | `Hints.min` |
| `pref_width` / `pref_height` | uint | `Hints.pref` |
| `max_width` / `max_height` | uint | `Hints.max` |
| `margin` | 四元 uint 数组 | `Inset` |
| `overflow` | `clip` / `visible` / `scroll` 令牌 | `Overflow` |

并在 `LAYOUT_KIND_SCHEMAS` 为各容器补充 `padding` / `align` / `justify`（若该 kind 确实读取它们）。
验证：`--catalog` 之外，用 `designer::generate` 生成一个声明 `max_width` 的文件，生成物应含对应
`Hints` 赋值，且 `GenerationReport.layout_issues` 为空。

**若属有意不支持，请明确。** 宿主会把 `panel.layout` 的尺寸约束标为“仅预览、生成拒绝”，并保持
`layout` 成员在 `unconsumed_by_generator()` 中。

## RW-110｜4.0.0 已落地：`json::JsonViewSession` 把 JSON 文档接到 ViewEngine（关闭 RW-43）

**状态：✅ 已核实（log §10）。** 上游无动作；宿主侧迁移属 rustage 改造。

**位置。** `rust_widgets` 4.0.0（`1a30785`）`src/json/view_session.rs`：

- `JsonViewSession`（:290）拥有一个 `ViewEngine`，`mount(json)` / `update(json)` / `reload(json)` /
  `mount_with` / `update_with`（:324-400）把 JSON 文档转换成 `Node` 树后交给引擎；
- 文档自述（:280-292）：**身份是引擎的**——两份描述同一个 key 节点的文档产生同一个 `Node` 声明，
  引擎因此不发补丁、活动控件保留 id，焦点/滚动/选择都不丢；消失的节点产出删除并报告 id；
- `json::json_to_view_tree(json)`（:128）是同一转换的纯函数入口；`view::apply` 则对
  `BoundJsonLayout` 做补丁。

**结论。** RW-43（“JSON loader 未接 ViewEngine，G-406”）在 4.0.0 已解决；宿主未采用的只是这条路径。
这对 `panel.layout` 的“预览与生成同一份文档”是直接支撑：宿主预览若改为 `JsonViewSession` +
`generate::document::to_library_document` 的产物，则预览与生成消费**同一份**库 JSON，布局约束
只被解释一次（#14/#59）。

**宿主侧剩余工作量（非上游）。** `Preview` 现在用宿主自己的 `preview::Document` + `View` 实现
（`preview/preview_service.rs::mount_view`），热更新 `apply_update` 也在这个模型上；迁移到
`JsonViewSession` 需要同时搬动 T14.02 的活体编辑路径与 T14.03 的状态保持断言，属于结构改造，
因此本轮只登记、不在未确认前动手。

## RW-111｜默认产物不带已求解的布局坐标，文件头却声称已求解（P1）

**状态：✅ 已修复（log §11）。** 默认产物头与 `GenerationReport.layout_geometry_gaps` 明确声明不携带坐标；stripped 不变。

**位置。** `rust_widgets` 4.0.0（`1a30785`）`src/designer/generator.rs`：

- `plan_geometry`（:2223）用 `JsonProject::layout_declaration()` 求出每个节点矩形；
- **只有 stripped 产物**把它们写成常量：`emit_stripped_node` 里 `let rect = geometry.rect_for(path, depth)`
  （:1784）→ `Label::new(String::from("Hello"), Rect::new(4, 4, 312, 192))`；
- **默认产物**（`Node` + `ViewEngine` 模板）的 `view::Node` 没有 geometry 字段，`geometry` 参数在
  `emit_default_mode`/`emit_node` 里不参与子节点发射；生成文件头却仍写
  “the document's layout was solved into constant coordinates”。

**复现。** 宿主页面（format v6）根节点声明 `{"type": "vbox", "spacing": 8, "margin": 4}`，一个子节点：

```text
--generate … target:default write:/tmp/layout-demo.rs
→ 文件里没有任何 Rect；头注释仍写 “layout was solved into constant coordinates”
--generate … target:stripped write:/tmp/layout-stripped.rs
→ Label::new(String::from("Hello"), Rect::new(4, 4, 312, 192))   ← 声明确实生效
```

两产物 `layout issues` 都是 0，`resolved at generation time` 计数一致。

**影响。** 设计器无法诚实地告诉用户“默认产物会按这份布局摆放”：声明只影响 stripped 产物与诊断。
宿主的 `panel.layout` 因此逐行标注这一点（而不是声称两个产物都消费）。

**建议修法（任一）。**
1. 默认产物也把求解结果带进树：给 `view::Node` 增加 geometry（或等价的 `rect` 属性），`emit_node`
   写入 `Rect`，`ViewEngine` 建控件时使用它；
2. 若默认产物有意不做布局（交给根控件运行时布局），请把文件头改成“this product does not carry the
   solved coordinates”，并在 `GenerationReport` 里增加一条这样的 gap，让宿主能呈现而不是靠猜。

**验证建议。** 对同一文档分别生成两种产物，断言：stripped 含 `Rect::new(4, 4, 312, 192)`；
默认产物要么含等价坐标，要么文件头/报告明确说明不含。
