## 0.1 2.8.11 的新缺陷：embedded profile 不能编译

`cargo build --manifest-path <rust-widgets>/Cargo.toml --no-default-features --features embedded --lib`
在 2.8.11 上失败，四个错误形状相同：

```text
error[E0599]: no variant, associated function, or constant named `TabWidget` found for enum `WidgetKind`
  --> src/lib.rs:891:42
(同样出现在 `Splitter`、`Grid`、`Dialog`)
```

**源码定位。** `lib.rs` 的 `create_tab_widget`/`create_splitter`/`create_grid_widget`/`create_dialog`
用 `#[cfg(not(alloc_frugal))]` 门控，但 `widget/kind.rs` 的 `WidgetKind::{TabWidget,Splitter,Grid,Dialog}`
变体用 `#[cfg(widgets_unstripped)]` 门控。`embedded` 的 `alloc_frugal` 为假、`widgets_unstripped` 也为假，
所以构造器被编译、变体不存在。`mini` 因 `alloc_frugal` 为真而绕过了这四个构造器，因此只有 embedded 暴露。

**期望。** 四个构造器与变体使用同一门控（例如 `#[cfg(widgets_unstripped)]`），或把四个函数体也
放进 `not(alloc_frugal)` + `widgets_unstripped` 的合取；并补 `--no-default-features --features embedded`
的 CI 组合（原则 #51 的互斥 feature 组合）。

**宿主侧影响。** `tools/generated-project/run.py --profile embedded` 无法构建消费者 crate；
支持矩阵的 embedded 格标为 `unsupported`，Linux 四格（desktop/tablet/mobile/mini）仍为 2.8.11
`build-verified`。宿主没有用 patch 或第二个修订绕过，也没有把失败写成通过。

## 0.2 2.8.11 的新缺陷：GTK 把 GDK keyval 原样送给控件层

**现象。** 工作台的命令面板在真实 GTK/X11 窗口里可以打开、输入过滤、点击 Run 执行；
但在查询框里按 Enter 不运行、按 Escape 不关闭。`LineEdit` 的 `return_pressed` 与
`editing_finished` 都收到 0 次（宿主在订阅成功时不会打印告警，运行日志也没有对应事件）。

**源码证据。** `platform/linux/canvas.rs` 在非打印键上构造
`Event::KeyPress { key: *event.keyval(), modifiers }`，注释称这是控件层期望的值；
但 GDK 的 `Return` 是 `0xFF0D`（65293）、`Escape` 是 `0xFF1B`（65307），而
`widget/input_widgets/lineedit.rs` 的 `handle_key` 匹配 `13`/`27`。打印字符之所以工作，
是因为 `printable_text` 先把它变成 `Event::TextInput`，没有经过这套键码匹配。

**期望。** 在平台边界把 GDK keyval 规范化为控件层使用的逻辑键码（至少 Return/Enter、
Escape、Backspace、Delete、方向键、Home/End），或让控件层接受两套键码并在一个地方映射；
用真实 `gdk::EventKey` 的键值补测试，而不是只用 `Event::key_press(13, 0)`。

**宿主侧影响。** 命令面板保留真实输入过滤、行选择、Run 与 Close，但键盘 Enter/Escape
无法作为证据；`tools/gui-smoke/palette.py` 把这两项标为 `blk`，不写成通过。宿主没有直接
调用 `dispatch_event` 或伪造 `return_pressed` 来冒充按键。

## 0.3 2.8.11 的 GTK 指针路径不合成 MouseDoubleClick

**现象。** `ListBox` 的 `item_activated` 在真实 GTK 窗口里不会因双击触发（`LineEdit` 的
双击选词同样无法验证）；`--workbench-gui` 的属性面板因此不把“双击属性行进入编辑”当作
已实现，而是使用始终可见的值字段。

**源码证据。** `widget/input_widgets/listbox.rs` 只在 `Event::MouseDoubleClick` 上调用
`activate_at_pos`；`platform/linux/` 的指针路径只产生 `MousePress`/`MouseMove`/`MouseRelease`，
没有生成 `MouseDoubleClick`（也无 GDK 多击计数读取）。因此双击被当成两次普通按下。

**期望。** 在 Linux/GTK 指针翻译里按 GDK 的多击判定合成 `Event::MouseDoubleClick`，或在
平台适配层把两次快速按下合并；用真实 X11 双击与 Enter（键码修复后）分别验证
`item_activated`。

## 0.4 2.8.11 的 `create_widget_of_kind` 在原生桌面后端返回 0

**现象。** 工作台需要一个真实 `Canvas` 控件。按 `lib.rs` 文档，`create_widget_of_kind` 是
“the single, mechanism-free creation entry”；传入 `WidgetKind::Canvas` 和已构造的
`Some(Box::new(Canvas::new(rect)))` 时，它在 Linux/GTK 窗口里返回 0，随后
`subscribe_unit` 只能报告 `control 0 publishes no mouse_pressed signal`。

**源码定位。** `create_widget_of_kind` 走 `mount_widget_object`，后者要求
`platform::get_platform().mount_surface(...)` 成功；`Platform` 的默认
`supports_surfaces()` 是 `false`（`platform/types.rs`），原生桌面后端没有每个控件一个的
platform surface。库自己的 `create_*` 函数不走这条路径，而是
`control_backend::get_control_backend_for_widget(kind).create_canvas(...)`，由 custom backend
的 `mount_widget_of_kind` 注册控件。

**期望。** 让 `create_widget_of_kind` 在 `supports_surfaces() == false` 时回退到 control
backend 的挂载路径（这正是库内 `create_*` 使用的路径），或明确文档说明该入口只适用于
提供 per-widget surface 的平台；两者选一时，库内的两条创建路径应给出同一个成功/失败判据。

**宿主侧处理。** 工作台改用 `get_control_backend_for_widget(WidgetKind::Canvas)
.create_canvas(...)`；没有绕过控件层直接 `dispatch_event`。真实窗口里画布收到
press/move/release 并完成点击与框选，见 `tools/gui-smoke/scene.py`。

## 0.5 2.8.11 从主循环定时器重建的 ListBox 不重绘

**现象。** 工作台调试面板原先用 `ListBox` 显示会话快照。worker 把 7 行交给 GUI 后，
`list_box_clear_items` 与 7 次 `list_box_add_item` 都返回成功，宿主日志也确认 `7/7 row(s)`，
但真实窗口仍显示面板创建时的首行 `no debug session; press Start`。随后
`invalidate_surface(list)` 与 `invalidate_surface(window)` 都没有触发重绘；
`list_box_set_current_index(list, 0)` 也不行。状态栏的 `set_widget_text` 会重绘，说明
主循环与绘制路径本身是活的。

**源码定位。** `CustomPaintControlBackend::list_box_add_item` / `list_box_clear_items` 在成功后
调用 `widget::runtime::request_repaint(widget_id)`（`control_backend/custom/create_widgets_helpers.in.rs`）。
该调用对从输入事件内更新的列表（Outline 选中、palette 过滤）有效；从
`schedule_on_main` 的回调里更新同一个 `ListBox` 时，模型确实变了，但宿主窗口的帧没有被重画。
根因未在本轮继续下沉到 runtime 的 dirty-region 层；已确认不是 id 错误（clear/add 都成功，
`iwinfo`/截图中的列表区域仍是首行）。

**期望。** 控件内容变化应使宿主 surface 的对应区域变为 dirty；`request_repaint` 与
`invalidate_surface` 在“回调来自主循环定时器”和“回调来自输入事件”两种来源下应一致。
建议补一个真实窗口测试：主循环定时器更新 `ListBox` 后，`xwd` 必须看到新行，而不是只看
`list_box_item_count`。

**宿主侧处理。** 调试面板改为 7 个固定 `Label`（一行一个），用与状态栏相同的
`set_widget_text` 路径更新；`tools/gui-smoke/debug.py` 以 host log 的
`debug rows shown: 7/7` 与各行的真实内容作为证据。没有把“模型有行”写成“画面有行”。

## 3. 可选改进（不阻塞当前里程碑）

以下两项不是缺陷，也不会阻止宿主继续；记录是因为它们直接影响“设计器界面随窗口缩放”的
实现方式，且能减少宿主自写布局：

1. **面板级子控件构造器。** 当前 `PanelHandle::set_layout` 可以按 id 给子控件安排位置，
   即使这些控件是用 `WindowHandle::new_label/new_list_box` 创建的；本轮工作台就是这样让面板
   标题与列表跟随面板缩放。建议提供 `PanelHandle::new_label/new_list_box/...`（或明确文档
   说明“面板布局可以定位由父窗口创建的控件”），这样面板的布局、父子关系与裁剪语义一致，
   不必让宿主知道这个隐式契约。
2. **固定轨道/边框式布局。** 工作台的顶部工具栏、左右侧栏、底部面板和状态栏需要“固定像素
   高度 + 中间弹性区域”的二维布局。现有 `BoxLayout` 是单轴，`GridLayout` 的列宽按 stretch
   比例分配（没有固定像素轨道），所以本轮在宿主实现了 `WorkbenchLayout`。若库提供
   `BorderLayout` 或支持固定轨道的 `GridLayout`，设计器可以少一个宿主侧布局实现，并复用
   库对 DPI/文本缩放的 `LayoutContext` 处理。

这两项只是改进建议；本轮没有因为缺少它们而伪造布局或绕过库的文档布局语义。

3. **GTK 窗口在 resize 后不重绘（缺陷，不只是建议）。**

   **现象。** `--workbench-gui` 的真实 GTK 窗口从 1280x800 用 `wmctrl -r ... -e` 调到
   1000x700 后，宿主日志确认布局已按 1000x700 重算：
   `workbench layout for 1000x700: 26 widget(s), 1 editor group(s)`；但 `xwd` 抓到的窗口内容仍是
   1280 宽度的旧帧，直到再点一下工具栏（触发一次可见状态变化）才显示新布局。

   **源码证据。** `platform/linux/types.rs` 的 `native.window_painters` 在
   `platform_impl.rs:1307` 写入、在 `:767` 删除，但**没有任何读取点**；
   `Platform::invalidate_surface` 走 `canvas::repaint_canvas`，只看 `native.canvases`
   （由 `mount_surface` 写入的子表面），所以对窗口 id 返回 `false`。
   `app/handle.rs` 的 `WidgetTriggerKind::Resized` 只调用 `apply_window_layout`，没有对窗口
   paint area 执行 `queue_draw`。

   **期望。** `invalidate_surface(window_id)` 能解析窗体的 paint area 并 `queue_draw`（读
   `window_painters`），或 `Resized` 分支在布局后主动 queue；或者把窗口 paint area 注册到
   `canvases`。

   **判据。** 上述 `wmctrl` 缩放后，无需任何指针/键盘事件，窗口内容即显示新布局；
   `invalidate_surface(window_id)` 返回 `true`。

   **本仓库的处理。** 2.8.11 已修复：宿主用 `wmctrl` 把真实窗口从 1280x800 缩到 1000x700 后不再
   发送任何输入事件，`xwd` 捕获的内容即为新布局（右侧栏贴右边缘、状态栏在底部）；
   `WorkbenchLayout` 的区域分配也已改用 `BorderLayout`。证据见
   [`log-20261020-3.md`](../log/log-20261020-3.md)。
