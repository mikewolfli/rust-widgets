## 架构决策（2026-11-05 已确认）：树地基 + 分层架构

> **状态**：已确认并开始实施。本节是后续实施的总口径；与第 2 章 C2 系列、第 7 章 GX 系列冲突时以本节的分层原则为准。

### 决策

**保留本项目独有的「运行时树 + ObjectId」地基，在其上补成熟控件框架已验证的分层；不照搬其对象模型。**

- **保留（树地基）**：`widget::runtime` 的挂载表、`BaseWidget` 父子链、树绘制器（`widget/runtime/render.rs`）、平台命中测试、`crate::set_widget_geometry` / `crate::set_widget_visible`、`ObjectId` 寻址。这些是 designer / JSON manifest / C ABI / 多后端绑定所依赖的能力，**不替换**。
- **补层（分层分工，不照搬框架类型）**：
  1. **布局对象作为唯一几何权威**——几何策略从各容器手写数学提升为 `src/layout` 的 `Layout` 实现 + `layout::declarative::apply_layout*` 这一条 solve→apply 链；容器只声明“用哪种布局”。
  2. **事件 accept/ignore**——控件可声明“我不处理这类事件”，路由器把它交给父链，而不是让事件消失在无兴趣的控件里。
  3. **z-order + 逐子裁剪**——兄弟按 `z_index` 决定绘制与命中优先级；容器用 `children_clip` 把后代裁到自己的内容框。
  4. **不引入**：QObject 元对象/字符串信号槽（本仓已有类型化 `Signal`）、裸指针所有权、父析构删子、隐式全局状态。

## 第 1 章 全局与引擎级问题（运行时 / 渲染 / 平台 / API）

> 本章条目影响面为全控件或整个子系统，优先级高于控件级条目。1.1 运行时，1.2 渲染，1.3 平台与 API 面。

### 1.1 运行时（RT2-）

**RT2-01 事件循环对每个事件无条件整体 clone（含 String/Vec 变体的每键堆分配）**
- **1级** `dispatch_one` 对**每个**事件执行 `let canonical = if event.is_legacy_alias() { event.clone().into_canonical() } else { event.clone() };`（`src/event/loop.rs:969-973`）——现代（非 alias）事件也被整体 clone。`Event` 仅有 `#[derive(Debug, Clone)]`（`src/event/types.rs:121-126`），其中 `TextInput`/`ImePreedit`/`ImeCommit` 携带 `String`（types.rs:245-262）、`Custom` 携带 `Cow<'static, str>` + `Vec<u8>`（types.rs:302-312）：每次按键、每次 IME 提交、每条 Custom 事件在热路径多付一次堆分配+拷贝，其余 POD 变体也白付整枚举 memcpy。clone 的**所有权**只有 legacy-alias 路径需要（`into_canonical(self)` 消费 self，types.rs:918-922）；现代事件的全部消费者都只借引用——`observe_input_event(&canonical)`（loop.rs:986）、`dispatch_window_key(target, &canonical)`（:990）、shortcut 钩子（:1016）、`key_ref.note_press`（:1053-1060）、双击判定（:1075）、gesture 喂入（:1114-1155），投递本身就借**原事件**（:1087、:1110 的 `_ => event` 臂）。已复核属实。
- **2级** alias 才持有 owned：`let canonical_owned: Option<Event> = event.is_legacy_alias().then(|| event.clone().into_canonical()); let canonical: &Event = canonical_owned.as_ref().unwrap_or(event);`，后续全部消费者签名不变。同库先例：`single_click_replay`「Declared without an initialiser so the allocation only happens on the arm that needs it」（loop.rs:1067-1072）、RT-02（issue-20261104）「payload clone 移到 early-return 之后」同一纪律。

**RT2-02 窗口销毁不清 `SURFACES_BY_WINDOW` 以窗口为键的条目（thread-local 表只增不减）**
- **1级** `unregister`（`src/widget/runtime/registry.rs:293-302`）只处理「被销毁 id **是 surface**」的方向：从 `SURFACE_WINDOWS` 删除并把它从所属窗口的列表里 retain 掉。当被销毁的是**窗口本身**时，`SURFACES_BY_WINDOWS`（定义于 `state.rs:228-232`，键为窗口 id、值为 `Vec<ObjectId>`）中该窗口的条目无人删除：(a) 列表已空时，空 `Vec` 条目随窗口 id 永久残留；(b) 窗口先于其 mounted surface 销毁时，条目内留有指向已失联 surface 的 id——`surfaces_of(window)`（`window_map.rs:53-60`）仍会返回它们（读取端因 `with_widget` 答 `None` 而跳过，功能无损，但表只增不减）。后果：以「开/关带 surface 的窗口」为主循环的应用（多标签、弹出面板宿主）缓慢累积死键，属 destroy 链清理遗漏。
- **2级** 在 `unregister` 中对窗口 id 补一刀 `SURFACES_BY_WINDOW.borrow_mut().remove(&id)`（连带空 Vec 一并回收）。同库先例：`forget_cached_frame` 在注销路径按窗口键删除 `TREE_FRAME_EPOCHS` 条目（`render.rs:551-558`，「dropping it keeps the table at the windows that still hold a frame」）、`HOST_WINDOWS`/`HOST_TO_WIDGET` 双向清理的两面纪律（registry.rs:280-292）。

**BD-01 生成热路径 O(n²)：`GeometryPlan::rect_for` 线性查找且每节点多次调用**
- **1级** `rect_for` 用 `self.rects.iter().find(|(p, _)| p.as_slice() == path)` 逐元素比较 `Vec<usize>` 路径（`src/designer/generator.rs:2317-2327`，已复核）；调用点：`generate()` 构 `report.node_rects` 每节点一次（`generator.rs:661-667`）、逐节点发射再调一次（`:1861`）、`plan_geometry` 容器配对同型线性扫（`:2452-2459`）。`rects` 长度 ≈ n，每次生成为 O(n²) 次路径比较。后果：生成是设计器保存与门禁 `tools/check_generated_sources.sh` [2/4] 步必经路径，文档树增大时生成时间超线性膨胀。

**BD-02 `finalize_anchors` 每锚点全前缀重扫换行，总开销 O(锚点数 × 源字节数)**
