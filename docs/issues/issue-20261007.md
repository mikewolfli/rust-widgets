## 1. render 分区（N-R，6 条）

#### N-R-01 · P2 · 全透明源把目标像素清零（source-over 语义错误） — ✅ 已完成

- 位置：[pixel_ops.rs](../../src/render/pipeline/pixel_ops.rs)，608～619 行。`blend_pixel_with_mode` 在 `src_a <= 0.0` 时执行 `frame[idx..+4] = 0; return;`，而 `color.a == 0`（完全透明源）时 source-over 应是无操作，此处却把已绘制像素清成 `[0,0,0,0]`。
- 证据：覆盖 `blend_pixel_clipped!`/公共 `blend_pixel` 分支，静态推导。仅当 `color.a == 0` 命中。
- 验收建议：该分支改 `return;`，仅在“透明即清除”的明确语义处显式清除；原则 #5/#18。

#### N-R-02 · P2 · `BoxShadow` 的 spread 运算存在 i32 溢出（公共 API 入参） — ✅ 已完成

- 位置：[paint.rs](../../src/render/backend/paint.rs)，205～209 行；[svg/backend.rs](../../src/render/svg/backend.rs)，1194～1197 行。`spread`/`offset_*`/`rect` 坐标以 `*spread*2`、`rect.width as i32 + *spread*2`、`rect.x + offset_x - *spread` 等形式做未饱和算术。
- 证据：`i32::MAX` 级别或反号组合触发 debug panic / release 环绕（被 `.max(0) as u32` 吞成错误矩形）；静态推导，未运行。
- 验收建议：改 `saturating_*`/`checked_*`，软硬两后端保持一致；原则 #5/#13/#18。

#### N-R-03 · P3 · 批处理 `SetOpacity`/颜色透明度携带 NaN 时经 `as u8` 静默归零 — ✅ 已完成

- 位置：[batch.rs](../../src/render/backend/batch.rs)，377～384、499～502 行。`state.opacity *= opacity` 后 `(color.a as f32 * self.opacity).round() as u8` 无 `clamp`/`is_finite` 防护；`translate_command` 的图像 alpha 路径（445～447 行）已有 `.clamp(0.0, 255.0)`，此处遗漏。
- 证据：`opacity = NaN` 令图像无声变透明，`Infinity` 饱和；静态推导。
- 验收建议：`as u8` 前加 `.clamp(0.0, 255.0)`，对 `SetOpacity` 入参 `is_finite` 校验；原则 #5/#13。

#### N-R-04 · P3 · `rgba_to_bmp` 中 `width * height` 先按 u32 再转 usize，大图环绕 — ✅ 已完成

- 位置：[svg/backend.rs](../../src/render/svg/backend.rs)，612 行。`(width * height) as usize == source_pixels as usize` 在 `width*height > u32::MAX` 时先环绕，导致 BMP 步长/尺寸错乱。
- 证据：`RenderCommand::DrawImage` 的 `width/height` 为公开 u32 入参；静态推导。
- 验收建议：`(width as usize) * (height as usize)` 或 usize 域 compare；原则 #5/#18。

#### N-R-05 · P3 · PNG 解码 `expected` 长度用未 checked 的乘法 — ✅ 已完成

- 位置：[png.rs](../../src/render/text/png.rs)，117 行。`header.height as usize * (row_bytes + 1)` 普通乘法，同函数 `row_bytes` 推导线已用 `checked_mul`/`checked_add`，此处遗漏。
- 证据：恶意 PNG 声明极大 height 时 `expected` 环绕成小值，分配不足绕过长度校验；静态推导。
- 验收建议：`checked_mul` + width/height 上限拒绝；原则 #5/#18。

#### N-R-06 · P2 · `Bevel::stroke_inner` 超大线宽窄化并在尺寸计算时溢出 — ✅ 已完成

- 位置：[bevel.rs](../../src/render/bevel.rs)，268～275 行。公开 `width: u32` 先 `as i32` 用作坐标 inset，随后 `width * 2` 再传入 `saturating_sub`。
- 证据：`width > i32::MAX` 时 inset 窄化为负数；且 `width > u32::MAX / 2` 时 `width * 2` 在 debug 溢出 panic、release 回绕，导致内框坐标/尺寸错误。与 `BoxShadow` 是不同 API 入口；静态推导。
- 验收建议：先校验或安全转换 `width`，并用 checked/saturating 倍增；非法宽度应拒绝或有界处理。

## 11. Web 实现程度评估与建议范围

### 当前实现到什么程度

从源码可证的行为看，项目目前提供的是**模拟 WebView 控件和可选 HTTP 文本预览**，不是能显示实际网页的嵌入式浏览器：

- [web_engine.rs](../../src/widget/web_widgets/web_engine.rs) 将控件明确标为模拟实现：绘制浏览器样式外壳并维护导航状态，没有 DOM 布局或页面网络栈。启用 `js-engine` 后的 Boa 只执行控件单独收到的脚本，并未接入所加载 HTML 的 DOM 或资源。
- [web_core.rs](../../src/web/web_core.rs) 的 `web-http` 分支同步发起 HTTP(S) 请求、读取响应文本并尝试提取 `<title>`；`file://` 仍走模拟进度。它不加载子资源、不解析/布局 HTML/CSS，也不提供浏览器页面渲染。
- [web_view.rs](../../src/web/web_view.rs) 只绘制标题和最多约 200 字节的内容片段，不绘制网页。
- [types.rs](../../src/platform/types.rs) 的 WebEngine capability 当前对平台返回不支持；README 也说明没有真实 Web 引擎。该“诚实报告不支持”的行为应保留，不能把模拟模式伪装成真实网页加载。
- `web-http` 的同步抓取、独立 JavaScript 求值器，以及 Cookie/隐私/插件等状态模型不能单独视为完整浏览器功能；本轮检查未发现它们共同组成实际页面加载、渲染和安全策略链路。

因此，当前最准确的定位是**模拟浏览器控件 / HTTP 文本预览**，不应称为可用的嵌入式 WebView。`wasm32` 上应用运行在浏览器中，也不等同于应用控件已经实现了内嵌网页视图。

### 建议目标与边界

若产品目标是让应用真正展示用户指定的网页，建议实现**平台原生 WebView 的适配层**，而不是在本项目中从头编写 HTML/CSS/JavaScript 浏览器引擎。建议分阶段：

1. **确定承诺范围**：选定首个目标平台及真实引擎，并逐项决定是否支持脚本、Cookie/隐私策略、证书错误、下载和多页面等能力。未实现的平台继续报告不支持。
2. **打通一个真实后端**：通过明确的 WebView 平台接口创建和销毁引擎实例；完成实际页面绘制、导航、异步加载/完成/失败通知、标题与 URL 更新、尺寸变化、键鼠输入及焦点生命周期。真实后端不可用时明确报错，不以模拟成功替代。
3. **落实可见的安全语义**：每个公开设置必须确实传递给引擎并能验证，或明确返回“不支持”；不能只保存开关而不影响请求、页面或脚本执行。
4. **再扩展平台与集成验证**：按平台逐个增加适配器；覆盖能力报告、加载成功/失败、取消/销毁、输入与安全设置的后端集成验证。纯模拟模式可保留用于控件状态测试，但应与真实引擎状态清楚区分。

除非产品明确要求独立浏览器，否则不建议把完整 Web 标准实现、插件生态或自研 JS/DOM 引擎列入目标。`web-http` 可作为独立文本抓取能力保留，但不能作为 WebView 的实现替代品。具体先支持哪个平台及哪些安全/浏览器能力仍需产品决策，本记录不替代该决策。

### Web 源码问题

#### N-WEB-01 · P2 · `web-http` 在导航调用中同步阻塞 — ✅ 已完成

- 位置：[web_core.rs](../../src/web/web_core.rs)，246 行。`ureq::get(&url).call()` 和随后响应体读取都在 `set_url` 的调用路径同步执行；慢响应期间调用线程无法处理后续 UI 事件，也无法及时响应取消或关闭。
- 验收建议：真实网络加载采用异步/后台任务并经事件回送状态；取消或销毁视图后不得再向失效视图派发结果。若该 feature 仅用于同步抓取，应明确限制其用途，不把它作为交互式 WebView 加载。

#### N-WEB-02 · P2 · HTTP 加载失败被报告为完成，响应体读取失败还会走成功收尾 — ✅ 已完成

- 位置：[web_core.rs](../../src/web/web_core.rs)，251～299 行。请求失败分支只记录日志，却发出 `loading_finished`，没有发出错误信号，且进度保留在 10%；响应体读取失败也只记录日志，随后继续执行 100% 进度及完成通知。
- 验收建议：请求/读取失败须进入明确失败状态并发出错误通知；失败不能同时表现为成功完成。覆盖 HTTP 请求失败、响应体读取失败及成功加载的状态与信号断言。

#### N-WEB-03 · P2 · `NavigationHistory::entries()` 环绕后只暴露 deque 的一个连续片段 — ✅ 已完成

- 位置：[navigation.rs](../../src/web/navigation.rs)，125～127 行。返回 `VecDeque::as_slices().0`；环绕后另一片段中的条目无法通过此方法访问，故 `len()` 可能大于 `entries().len()`。现有文档也记录了这一限制，但公开的“全部条目”访问语义仍不完整。
- 验收建议：提供能按时间顺序遍历所有保留条目的接口，且环绕后遍历数量与 `len()` 一致。

#### N-WEB-04 · P3 · `NavigationHistory::new(0)` 仍保留最近一次 push — ✅ 已完成

- 位置：[navigation.rs](../../src/web/navigation.rs)，43～45、57～69 行。构造文档明确说 `max_size == 0` 时每次 push 都丢弃；实际代码仍执行 `push_back`，所以会保留一条记录并把游标设为该条。
- 验收建议：零容量历史 push 后仍为空、游标为空且前进/后退均不可用；或在 API 层拒绝零容量，并同步修正文档契约。
