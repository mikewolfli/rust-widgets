## 4. 新发现：Linux target 上的 `mini` profile 不能编译（2026-10-19）

**现象。** 固定修订 `504698fe`，在 macOS 宿主上交叉编译 Linux target：

```text
cargo build --manifest-path <rust-widgets>/Cargo.toml \
  --target x86_64-unknown-linux-gnu --no-default-features --features mini --lib
```

失败：

```text
error[E0425]: cannot find function `from_environment` in module `crate::platform::locale`
   --> src/platform/linux/platform_impl.rs:378:66
error[E0425]: cannot find type `Vec` in this scope
   --> src/platform/linux/platform_impl.rs:398:31
error[E0433]: cannot find type `Vec` in this scope
   --> src/platform/linux/platform_impl.rs:399:9
```

**判断。** `mini` 是 `no_std`/`alloc` profile（`#![cfg_attr(feature = "mini", no_std)]`），
但 `platform/linux/platform_impl.rs` 仍被编进来，并直接用了 `Vec` 与 `locale::from_environment`。
同一命令在 `aarch64-apple-darwin` 与 `x86_64-pc-windows-msvc` 上通过，所以不是本次 re-pin 的
全平台回归，而是 **Linux target + mini 的组合**。

**期望。** Linux 后端在 `mini`（或更一般地 `alloc_frugal`）下不应编译，或者模块内使用
`crate::compat::{Vec, ...}` 并给 `from_environment` 提供 `mini` 下的显式空实现。
判据：上述命令在 Linux target 上以 `Finished` 结束。

**本仓库的处理。** 没有改上游，也没有用临时 patch 把矩阵写成通过；`linux × mini` 保持
`unverified`，本条是新请求。

**本轮新发现并修复（不属于原 §4/§5 请求，但由 Linux 实跑暴露）**：

1. **2.8.9 的 GTK 后端不能编译**（4 个错误：`i32::round`、`Propagation` vs `bool`、

2. **自定义后端的 `destroy_widget` 不销毁 platform host window**：Windows/GTK 每销毁一个窗口
   泄漏一条记录；Android 的“一 Activity 一窗口”规则直接拒绝后续 `create_window`，统一诊断
   探针因此报 `display_of_window returned None`。修复后模拟器探针 12 项 9 pass / 2 skip /

3. **Android 宿主把 `skip` 当 `fail`**：新增 JNI `nativePlatformProbeFailures()`，Java 按

4. **`crate::quit()` 可能记录两个 stop 请求**：GTK 非主线程分支与包装层各记录一次，第二个会
   停掉**下一个** session。已改为“后端执行失败时才记录”。
5. **README 矩阵与 Linux 剪贴板能力不一致**：README 行是构建事实，后端回答的是会话事实；
