### 1.1 渲染与文本管线（RD-）

**RD-X01 彩色 emoji 每帧重走 strike 表查找 + PNG 全量解码（无任何缓存）**
- **1级** `color_bitmap.rs:188-210` `image()` 每次调用重跑 `strike()`（CBLC 表目录线性扫描 L160-185 + record 线性扫描 L197-204）；`paint()` L337-353 每 emoji 每帧执行 `vec![0u8; decoded_len]`（L349）+ 完整 PNG inflate/unfilter + `scale_rgba`，随后即弃。绘制路径 `primitives.rs:1442-1449` `blend_color_glyph` 每 emoji 每帧调用；glyph atlas（raster.rs CoverageKey）只覆盖 Coverage ink，彩色 ink 完全在缓存之外。grep `EMOJI_CACHE|emoji_cache|decoded_cache|png_cache|COLOR_GLYPH_CACHE|color_glyph_cache|COLOR_ATLAS|color_atlas|COLOR_BITMAP_CACHE|COLOR_INK_CACHE` 全库 0 匹配。后果：一屏 20 个 emoji @60fps ≈ 1200 次 PNG inflate/秒。
- **2级** 增加有界 FIFO 缓存（对齐 `GRADIENT_LUT_CACHE_LIMIT`/`BAKED_IMAGE_CACHE_LIMIT` 既有模式，32 条），key=`(face 身份, glyph_id, cell.width, cell.height)` → `Rc<[u8]>`（scale 后的 cell RGBA）；`paint()` 先查缓存，命中直接拷入 `out`。`Strike` 解析结果按 face 身份缓存（含负结果，同 `SHAPED_RUNS` 的 `Option` 缓存模式）。L331-333「never resident」约束由「有界+逐出」化解：常数级驻留而非无界驻留，不违背该注释的内存意图。

**RD-X02 fonts-emoji-color 下非彩色 glyph 每帧白做一次完整光栅化**
- **1级** `primitives.rs:1442-1449` 对**每个** glyph 无条件先调 `blend_color_glyph`；`pixel_ops.rs:554-562` 其内部先 `paint_active` 把 glyph 完整光栅化进 color_scratch（L554），之后才检查 `painted.is_color()` 并对 Coverage ink 返回 false（L560-561）。普通文本（全部非彩色）每 glyph 每帧浪费一次栈解析+完整光栅化+scratch 写入，随后 atlas/直接绘制路径再画一次；atlas 稳态命中时这次浪费是**每帧稳态成本**。
- **2级** ink 种类是来源的静态属性（`Painted.ink` L127、`InkKind` L137-155，仅 `ColorBitmapSource` 产 Color）：给 `GlyphSource` 加 `fn paints_color(&self) -> bool { false }`（ColorBitmapSource 覆写 `true`），新增栈级谓词走 `covers()` 判定（`FontStack::resolve` L510-517 已证明可不 paint 解析来源）；`primitives.rs:1442` 用谓词门控 `blend_color_glyph`。语义不变：color miss 仍走原 fallback，字节输出不变。

**RD-X03 静态图标路径缓存：全局 Mutex + VecDeque 线性扫描（且 miss 时二次扫描）**
- **1级** `flatten.rs:268-296` `parse_static_cached` 每次 icon path paint：全局 `Mutex<VecDeque>` 上锁 + ≤128 项线性地址比较（命中 L276-282；miss 插入前 L285-290 **再扫一遍**）。图标多的界面（工具栏/列表/图例）每帧付出 N_paths × O(128) × 2 次扫描 + 全局锁。
- **2级** key 改 `OnceLock<Mutex<HashMap<(usize, usize), Arc<[Subpath]>>>>`（地址+长度，`&'static str` 地址永久稳定唯一），O(1) 命中；容量界限保留 128，超限逐出任意项（纯内容缓存，地址不变性保证正确性，逐出顺序无语义）。可进一步对齐动态缓存设计改 thread-local（`parse_dynamic_cached` L180 先例）去掉 Mutex。

**RD-X04 elide 宽度版二分每探针分配 String（且每探针 O(n) 字符走查）**
- **1级** `text_utils.rs:316-325`（middle）与 373-381（end）：二分每探针 `String::with_capacity`+push_str+push'…'+measure，每帧每个省略标签 ~log2(n) 次分配/释放；`byte_index_of_char`（L113-118）每探针从 0 重走字符迭代，合计 O(n log n) 字符步。长路径/URL 列表场景每帧多标签放大。
- **2级** 循环外建一个 `String::with_capacity(text.len() + 3)`，每探针 `clear()` 后重建 candidate（结果字节不变）；head/tail 字节索引随 low 递增做增量游标推进（同序计算，输出不变），最终 Owned 结果仅在收尾构建一次。

**RD-X05 draw_mesh_3d 每帧分配投影三角形 Vec**
- **1级** `mesh3d.rs:464-491` `project_mesh` 每调用 `Vec::with_capacity(triangle_count)`（L472）；`pipeline/mesh.rs:50-60` `draw_mesh_3d` 每帧每 3D 控件调用（`svg/backend.rs:975` 为导出路径，非热）。顶点多的 mesh 每帧堆分配+释放。
- **2级** `SoftwareSurface` 增加 `projected_triangles_scratch: Vec<ProjectedTriangle>`（镜像 `text_coverage_scratch` 模式：surface.rs:477-481 声明 + primitives.rs:1389/1479-1483 的 take/return）；新增 `project_mesh_into(mesh, …, &mut Vec)`，`project_mesh` 保留为新建 Vec 的薄包装（公开 API 不变）。逐像素 `edge()`（mesh.rs:163-165）增量步进**不做**——会改变浮点求值序，违反本 crate byte-identical 纪律。

### 1.2 平台层资源泄漏与正确性（PF-）

**PF-X01 Windows `set_window_icon` 的 HICON 永不销毁（GDI 句柄泄漏）**
- **1级** `platform/windows/platform_impl.rs:744-765` 每次 `LoadImageW(LR_LOADFROMFILE)` 产生 +1 归属调用方的 HICON，经 `WM_SETICON` 交给窗口；全库 grep `DestroyIcon` 为 **0 命中**（src/ 全树）。再次设置图标时旧句柄不被替换销毁，窗口 `WM_DESTROY`（types.rs:534）也不释放——每次换图标泄漏 1 个 GDI 句柄，进程 GDI 上限（默认 10000）耗尽后整个 UI 停止绘制。
- **2级** 在 backend 记录每窗口当前 HICON（`state` 或 `handles` 旁表）：`WM_SETICON` 成功后对旧句柄 `DestroyIcon`；`WM_DESTROY`/`destroy_widget` 时销毁现存句柄；同一句柄设 ICON_BIG+ICON_SMALL 后只销毁一次。

**PF-X02 Windows `set_clipboard_text` 失败路径泄漏 HGLOBAL（与富剪贴板行为分叉）**
- **1级** `platform/windows/platform_impl.rs:2165-2167`：`SetClipboardData` 返回 0 时只 `CloseClipboard` 后返回 false——系统未接管 `h_mem`，调用方仍持有所有权，缺 `GlobalFree`。同库富剪贴板 Windows 臂（`clipboard_native.rs:560-570` 注释「allocated above is still ours to free」）已正确处理失败路径——同语义两套实现分叉。
- **2级** 单一实现：把 `clipboard_native` 的所有权规则上收——`SetClipboardData` 失败即 `GlobalFree(h_mem)`；或让 `set_clipboard_text` 直接委托富剪贴板实现，消除第二份 GlobalAlloc/GlobalLock 序列。

**PF-X03 cocoa-legacy macOS：canvas view 引用计数失衡 + `window_canvases` 旁表只增不清**
- **1级** `platform/macos/canvas.rs:1423-1437` mount 与 :1355-1366 make_window_canvas 均 `alloc+initWithFrame:` 持 +1，`addSubview:`/`setContentView:` 后该 +1 从不 release；`unmount_surface_impl`（:1599-1620）只 `removeFromSuperview`——**每挂载/卸载循环泄漏一个 NSView**。objc2 后端已修过同一缺陷并留有症状记录（`macos_objc2/native.rs:746-763`：「RSS 增长 ~6KB/widget, without bound」），legacy 未同步。且 `window_canvases` 表（:1322）只有 insert（:1366）、全文件 0 处 remove，窗口关闭后条目连同陈旧 view 指针永存，repaint 可能路由到已脱离窗口的旧视图。
- **2级** 对齐 objc2 的事实标准：挂载后 release alloc 引用（superview 持有）；unmount 先 `removeFromSuperview` 再补 release（对齐 native.rs 的 retain/release 对）；`destroy_widget` 关窗路径（`platform_impl.rs:705-726`）同步清 `window_canvases` 条目。

**PF-X04 macOS 富剪贴板每次写入泄漏一个 NSPasteboardItem**
- **1级** `clipboard_native.rs:212-250`：Text 与 Html 两臂均 `alloc`+`init` 构造 item 后交给 `writeObjects:`（pasteboard 只 retain，不接管调用方的 +1），全函数无 release/autorelease——同文件 :144-149 的 `nsstring()` 注释证明此处遵循手工引用计数纪律，item 漏网。每次复制操作泄漏 1 个对象。
- **2级** 构造处改为 `.autorelease()`（与同函数 `nsstring` 同一模式），或 `writeObjects:` 返回后 `msg_send![item, release]`；两个臂同改。

**PF-X05 Linux IBus 桥：焦点切换在 UI 线程同步等待 DBus 往返**
- **1级** `ime_linux.rs:145-162`：`call_input_context` 在**调用线程** `recv_timeout(IBUS_REPLY_TIMEOUT=16ms)` 等待 worker 的 DBus 回执；`focus_in` 顺序发 `SetCapabilities`+`FocusIn` 两次往返（:438-452），`focus_out` 再一次（:463-470）。调用方是 UI 线程：`widget/runtime.rs:954-957` 的 `notify_ime_focus_in` 在每次焦点移动时触发——Tab 遍历控件每次吞 2 次同步会话总线往返（IBus 卡顿时每次焦点移动最坏 32ms）。这正是 G-602 为剪贴板确立的「UI 线程不等待 DBus」纪律的漏网点（彼时立项的是 portal/剪贴板，非 IBus）。
- **2级** 改为 fire-and-forget：`call_input_context` 增加无回执变体（job 直接提交 worker，UI 线程零等待）；`focus_in/focus_out/set_cursor_location` 全部走该变体；仅 `ProcessKeyEvent`（需要布尔回执，且当前运行时无调用方）保留有界等待。

**PF-X08 `open_external` 在 Unix 上每开一个链接遗留一个僵尸进程**
- **1级** `platform/external.rs:136-140`：`command.spawn().map(|_child| ())`——`Child` 句柄即弃，Rust std 丢弃不 reap，`xdg-open` 退出后成为 zombie 挂在进程表直到宿主退出。对比同库 `os_probes::spawn_print_job` 明确注释「The child is reaped here」（os_probes.rs:203-214）——同一 spawn 纪律两处不一致。长期运行的 GUI 应用累计打开外部链接即累积僵尸。
- **2级** spawn 后将 Child 交给一次性收割线程：`std::thread::Builder::new().name("rw-open-reap").spawn(move || { let _ = child.wait(); })`（UI 线程零阻塞，进程组隔离 `in_own_group` 保持不变）。

### 1.3 平台呈现效率（PF-）

**PF-X06 macOS-objc2 呈现路径每 drawRect 重建全帧位图上下文 + 逐像素 3 次整除预乘**

- **2级** 呈现阶段消费损伤矩形：Windows 用缓存 BGRA 缓冲（G-601 已有 BLIT_BUFFER）+ `StretchDIBits` 仅呈送 `rcPaint` 源/目的矩形；macOS `CGContextClipToRect(dirty)` 后 `draw_image`；Linux `context.rectangle(dirty)+clip()` 再 surface 绘制。转换循环可按脏行界跳过。

### 1.4 事件循环与契约（EV- / RT-）

**EV-X01 threaded `stop()` 不重置 `key_state`/`double_click`，与 mini 分支不对称**
- **1级** `event/loop.rs` L1310-1323（threaded `stop`：仅清 running + timer_manager，无 input 状态清理）对照 L1331-1338（mini `stop`：`self.key_state.reset()` + `self.double_click.reset()`，注释明言 "A key held across the stop boundary must not turn its next press into a phantom repeat"）。threaded 循环 stop 后复用同一 `EventLoop` 时，跨 stop 边界的 held key 产生幻影 repeat、click run 跨场景存活。
- **2级** threaded `stop()` 在 `handle.join()` 前补同样两行：`self.key_state.reset(); self.double_click.reset();`，与 mini 分支语义对齐（沿用现有方法名）。

**EV-X02 每事件 `event.clone().into_canonical()` 全量克隆；为此设计的 `is_legacy_alias` 闸门零调用**
- **1级** `event/loop.rs` L887（threaded dispatch）与 L1256（`pump_once`）对每条分发事件执行 `event.clone().into_canonical()`；`into_canonical(self)`（types.rs L918-929）对非 legacy 事件原样返回，克隆纯属浪费。`is_legacy_alias`（types.rs L933-937）doc 明言就是给 dispatch 的廉价判定闸门，但全库 grep 仅定义+自身测试（L1054-1059）两处命中——write-only。
- **2级** 两处调用点改为：`let canonical = if event.is_legacy_alias() { event.clone().into_canonical() } else { event.clone() }`（legacy 变体仅 MouseDown/Up/MouseMoveLegacy/KeyDown/Up 元组，占热路径极小比例）。

**EV-X03 `DoubleClickTracker::forget` 零调用方：widget 销毁后 last-press 残留**
- **1级** `event/double_click.rs` L202-211，`forget` doc 明言 "this entry point is for teardown, where keeping state for an id that no longer exists would be a leak in everything but name"。全库 grep `.forget(` / `DoubleClickTracker` / `double_click_tracker` 三变体：仅 wasm `Closure::forget`、`cancelled_anim_frames.forget(id)`（loop.rs L1380）、popup 同名方法与测试——tracker 的 `forget` 无一调用。`ObjectId` 可复用（create_widgets_base.in.rs L14-20 注释明言），新控件复用 id 后 400ms 内同位置首击被误判 double-click。
- **2级** 在 widget 注销链（与 G-901 timer 清理同链路）调用 `double_click.forget(target)`；`EventLoop` 已持有 tracker 字段（loop.rs L565-569），补一条注销回调即可。

**EV-X04 `FocusManager.widget_positions` 注销不清理：无界增长 + 陈旧位置参与排序**
- **1级** `event/focus.rs` L191-215 `unregister_focusable` 清 `registered`/`registration_order`/`focusable_widgets`+`positions`/`policies`，唯独不动 `widget_positions`；全文件 5 个触点（L85-89 声明、L108-118 初始化、L390-395 仅 insert、L411-415 与 L421-425 读取）证实无任何删除路径。控件反复创建销毁时 map 无界增长；且 `reorder_by_strategy` 以 `unwrap_or((0,0))` 读它——复用 id 的新控件继承死者坐标或被当 (0,0) 错排。
- **2级** `unregister_focusable` 中 `self.policies.remove(&id)` 之后加一行 `self.widget_positions.remove(&id);`，一行修复、与既有清理序列一致。

**EV-X05 filter 链与 shortcut 钩子无 panic 屏障：panic 杀死循环线程**

> 全部条目为最终态方案，遵循现有命名，无「先加后删」路径；性能类方案优先复用库内既有池化/缓存模式（thread_local scratch、bounded FIFO、revision 键控缓存），不引入新机制词汇。
