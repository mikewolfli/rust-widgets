## 1. 用户点名问题核查结论

### 1.1 「主窗体拉大缩小，顶层 layout 没变化」→ 定位到 2 个活缺陷（§2 R-01 / R-03）

库层主干链路**健康**（全部后端逐一核过）：后端 resize 回调 → `queue_resize_trigger` → control_backend 每窗口 pending 去重（`src/control_backend/custom/create_widgets_helpers.in.rs:72-96`，注释记录修复前 20 步拖拽 263 次布局的实测）→ 帧循环 `drive_frame` → `drain_triggers` → `Resized` 分支（`src/app/handle/types.rs:1886-1940`）→ `apply_window_layout`（`src/app/handle/window.rs:880-956`，LAYOUTS + declarative 双注册表、LY3-01 同尺寸去重）。三个桌面 demo 顶层均走 `win.set_layout(...)` 注册（`demo/control/src/app.rs:809-819` 等），无用法缺陷。

缺口在两个非主干位置：
- **R-01（高）**：`macos-legacy` 后端 resize 投递的平台 host id **未翻译**（§2.1）；
- **R-03（中）**：`demo/wasm_gallery` 从未接线任何 resize 通道（§2.1）；
- 另有 **R-02（中）**：wasm 平台自建窗口的 resize 事件永远到不了布局层（§2.1）。

Linux/GTK 路径（本机默认平台）静态审计健康；若用户在本机仍可复现"顶层不动"，结合 1.3 的结论，**最高概率根因是 R-04（code_editor 后台轮询线程偷走 Resized 事件）**，而非库的缩放链。

### 1.2 「Scaffold 统一移动范式 + SDI/MDI 桌面范式，分类分组」→ 控件层已具备，范式层有缺口（§2.3）

- `AdaptiveScaffold`（`src/widget/nav_widgets/adaptive_scaffold.rs`，~2700 行）已具备：AppBar、每目的地常驻 body（IndexedStack 语义）、Material3 底栏（badge）、双抽屉（动画+scrim+Esc）、FAB、宽度断点自适应（≤599 底栏 / 600–839 rail / ≥840 抽屉，`:66-73`）、JSON 槽位全接线（`src/json/loader.rs:529-623`）。缺口：snackbar/bottomSheet 退化（设了就常驻）、无 persistentFooter、无 builder 类型。
- `MdiArea`（`src/widget/container_widgets/mdiarea.rs`，~3700 行）已具备：子窗增删/激活/级联/平铺/最大最小化/Tab 模式/激活顺序/状态往返/视口平移。缺口：子窗关闭**不可拦截**（顶层窗有 `set_close_handler`+`WindowCloseRequest` 否决，子窗没有对应物）。
- **SDI：无范式入口**。只有 `App::new_window` + `WindowOptions` 裸 API（`src/app/app_core.rs:350-356`、`src/app/handle/window.rs:49-156`）；app 层无顶层窗级联/平铺；全库零 SDI 类型、零 SDI demo；README 对三范式零提及。
- 分类分组本身**已合规**：lib.rs 双导出各归 nav_widgets/container_widgets 组，kind.rs 各归其类带 css_name。
- 结论：用户 11.2 的"放进 rust-widgets 分类分组"这一半已完成；"统一开发范式"这一半缺端到端示范（§2.3 缺口 4/5）。

### 1.3 「demo 还是卡顿、没反应」→ 定位到 1 个确定性根因 + 1 个次要因素（§2.2 / §2.5）

**R-04（高，确定性）**：`demo/code_editor` 的后台轮询线程与主线程帧泵**争抢同一条触发队列**（§2.2）。它按库的唤醒协议被"优先"唤醒，偷走 `Resized`/`Moved`/`Closed` 事件且只记日志不派发——resize 布局因此间歇性不重跑；菜单命令则在后台线程落到 thread-local 注册表的空集上，**必然静默 no-op**。这是与用户"卡顿、没反应"症状吻合度最高的实锤。

**R-19（低）**：三个 demo 启动路径同步扫描 CJK 字体（几百 ms 启动延迟，非运行期卡顿）。

其余三个 demo（control/finance/wasm_gallery）与库的帧泵/平台循环/绘制/启动路径经逐项核查**未发现可致卡顿的机制性问题**（§3）。若用户在 control demo 上仍可复现卡顿，需提供平台+操作序列才能继续定位，当前证据不支持"普遍卡顿"。

### 1.4 「创建的应用卡顿无反应，全面核查」→ 库层热路径系统性健康，遗留 5 个可量化改进点（§2.4）

三大热路径（渲染/布局/事件）已被系统性优化过（G-xxx/LY-xxx/RD-xxx 修复注释遍布且质量高）：animating-registry 驱动帧、dirty-rect 三模式 + 单次分桶遍历、128 槽 LRU-clock 层缓存、全帧缓存、scratch 跨帧复用、布局 (w,h,scale) 守卫、同帧 MouseMove 合并、hit-test memo。教科书式缺陷（每帧全量重绘/全树扫描/无界缓存/热路径阻塞 I/O）**基本不存在**。真实遗留：每帧图片 memcmp（R-07）、wgpu 纹理缓存 FIFO 驱逐（R-08）、`set_geometry` 全局丢层（R-09）等，详见 §2.4。

## 2. 新发现问题清单（本轮立项）

严重度：🔴 高（功能失效/用户症状根因）｜🟠 中高｜🟡 中｜🔵 低。每条附 file:line 证据与修复方向（**本轮不改代码**）。

### 2.1 窗口缩放事件投递链（对应 1.1）

**R-01 🔴 macos-legacy `windowDidResize:` 投递平台 host id，未做 id 翻译** — `src/platform/macos/canvas.rs:1895-1921`
`associated_widget_id` 取得的是 `create_window` 返回的 **host id**（`src/platform/macos/platform_impl.rs:835-843,862-863`，平台本地 id 空间自 1 起增），直接 `crate::queue_resize_trigger(widget_id, ...)`，**没有** `widget_id_for_host_window` 翻译；返回值被 `;` 丢弃、无告警。同文件绘制路径**做了**翻译（`canvas.rs:1254-1262` 注释自证"the same boundary the objc2 backend translates at"）——同一边界两处不一致。影响：id 错位时（第二窗口、窗口创建前挂过其它控件）`is_mounted(host_id)` 拒绝 → 事件静默消失、布局永不重跑（**与用户报告症状同形**）；或尺寸记到错误 widget 名下。与 Windows `WM_SIZE` 历史 bug 同类（该 bug 的书面教训在 `src/platform/windows/types.rs:405-408`）。修复方向：对齐 objc2 后端在 `native.rs:1676-1692` 的翻译 + 对齐 Windows 侧拒绝即 `log::warn!`。范围仅 `--features macos-legacy` 构建；默认 objc2 后端已正确。

**R-02 🟡 WasmPlatform 自建窗口的 resize 永远到不了布局层，且注释与实现相反** — `src/platform/wasm/platform_impl.rs:630-650, 843-853`
`create_window` 只进平台自己的 `BackendState`，不进 widget 注册表；`queue_resize_trigger` 先写本地 geometry 再调 crate 入口，而 crate 侧 `is_mounted` 必然拒绝 → helper（`create_widgets_helpers.in.rs:78-81`）**立即 return false，什么都不入队**，连 `window_client_sizes` 记录都不写（拒绝在 insert 之前）。但 `platform_impl.rs:838-842` 注释声称"the control backend queues its own event in that case"——与实现相反，属文档欺骗形态（原则 #18）。经 control backend 创建的 wasm 窗口不受影响。主线程复核：已亲读三处源码确认。

**R-03 🟡 `demo/wasm_gallery` 无任何 resize 接线** — `demo/wasm_gallery/src/app.rs:629-653, 736-764`
host 模块只装 rAF 循环 + `drive_frame(16)`，从不调用库已提供的 `observe_canvas_resize`，也不调 `queue_resize_trigger`；canvas/blit 固定 `WIDTH×HEIGHT`。浏览器窗口变化不产生任何 Resized——wasm 上与用户报告症状同形。固定画布属有意设计，但该 demo 无法演示自适应，且未消费现成能力。

**R-20 🔵 iOS 库内零 resize 投递（已文档化的宿主契约，记录备查）** — `src/platform/ios/platform_impl.rs:729-750`
文档明说由宿主在 `viewDidLayoutSubviews`/`orientationDidChangeNotification` 调 `queue_resize_trigger`。与 android（JNI 入口 `platform/android_jni.rs:2246-2258`）、harmony（xcomponent 回调 `platform/harmony/xcomponent.rs:897-913`）相比缺一个内部接线层；宿主不接线时旋转/分屏布局不跟随。非静默缺陷，列为观察项。

**健康面（不再立项）**：linux/GTK（`platform_impl.rs:1678-1688` + `expedite_frame_heartbeat`）、windows 主窗+canvas（`types.rs:421-444`、`canvas.rs:266-278`）、macos objc2（`native.rs:1283-1296`）、wayland（`platform_impl.rs:2090-2114`）、redox（`platform_impl.rs:474-516`）、harmony、android 均投递正确；拖拽期节奏机制完整（Windows `WM_TIMER` 16ms 心跳、macOS display link + ModalLoopsOnly、wayland frame-owed 1ms poll、GTK 16/100ms 双档），resize 回调内无同步重绘，队列级 coalescing + LY3-01 双层去重，无卡顿路径。

### 2.2 demo 卡顿/无反应（对应 1.3）

**R-04 🔴 code_editor 后台轮询线程与主线程帧泵争抢同一条触发队列：偷走窗口事件并丢弃，菜单命令必然失效** — `demo/code_editor/src/app.rs:1142-1198`（主线程复核确认）
证据链：
1. 库的契约明文：`drain_triggers` 是"**单线程事件循环**想要的排空"（`src/api/control.rs:616-621`）。
2. 主线程：GTK 循环每帧 `drive_frame` → `drain_triggers`（`api/control.rs:684-736`）。demo 构建下 `get_control_backend()` 恒返回自绘后端（`src/control_backend/dispatcher.rs:268-277`）。
3. 后台线程：poller 循环调 `rust_widgets::poll_widget_trigger_event()`（app.rs:1168）与 `poll_menu_triggered()`（app.rs:1158）——pop 的是**同一个** `widget_trigger_queue`（`create_widgets_helpers.in.rs:37-41`）。demo 内注释（app.rs:1108-1109 "poll 只读队列可安全后台运行"）与契约矛盾：poll 是**取出**不是窥视。
4. 唤醒时序：poller 挂在 `wait_for_host_events`（app.rs:1195）等 frame_wait generation，而 generation 在每次输入入队/触发注入/repaint 时 bump（`src/event/event_queue.rs:68-70`、`src/platform/state.rs:1077`、`src/widget/runtime/repaint.rs:257-261`）——交互期间 poller 被持续唤醒，只要它的检查落在"push 之后、主线程心跳 drain 之前"，事件即被吃掉。
5. 偷到后只 `poll_log.append(format!("[Widget] ..."))` 然后**丢弃**（app.rs:1168-1175），从不调 `dispatch_trigger`。Resized 一经 pop 即消失，无补救路径。
6. 确定性部分：菜单事件走 `menu_trigger_queue`（`create_widgets_menu.in.rs:269-271`），主线程 `drain_triggers` 只消费 widget 队列——菜单队列**唯一消费者就是 poller**；poller 里 `dispatch_menu_event`（app.rs:665-681）→ `Command::dispatch` → `with_widget_mut`（`src/widget/runtime/access.rs:138-148`）查 thread-local MOUNTED 注册表，后台线程查不到 → 命令全部变成日志里的 `-> no-op`。
用户可见后果：拖拽/缩放后布局间歇性不重跑（code_editor 恰好**依赖**这条路径，app.rs:1111-1117 注释自证"后端报 resize 就会跑完整棵布局树"）；菜单项全灭。**与用户 11.3/11.4 症状吻合度最高的实锤。**
修复方向：删除 poller 线程，菜单/触发消费移回主线程（库的帧钩子或 idle 回调）；库侧可让 `poll_widget_trigger_event` 在非主线程调用时拒绝或告警，使契约可执行。

**R-19 🔵 三个 demo 启动路径同步扫描 CJK 字体** — `demo/control/src/app.rs:1810-1826`、`demo/finance/src/app.rs:1250-1293`、`demo/code_editor/src/app.rs:830-918`
`register_system_cjk_font()` 在 `build_window` 最先同步调用（注释自认读 20MB 集合）。延迟的是窗口创建之前的启动阶段（几百 ms），非运行期卡顿。修复方向：后台线程预热 + 首帧前 join，或惰性加载。对照：`App::run` 的系统字体预热已在后台线程（`src/app/app_core.rs:323-336`）。

### 2.4 热路径性能（对应 1.4；用户目标 10"有必要上缓冲池/多级缓存"）

**R-12 🟡 `recorded_image` 每次命中做全图 memcmp** — `src/render/backend/surface.rs:789-800`（主线程复核确认）
命中判定 `(ptr,len,width,height)` 之后还要 `entry.data.as_ref() == data` 整块像素比较——为"内容可能被原地改写"的安全设计（注释 `:782-788` 自证），但 widget 层 blit（`src/widget/runtime/render.rs:1315-1322`）也走这条路，dirty-rect 快路径每帧每个图片/层付全量 memcmp（1000×600 层=2.4MB，10 层≈每帧 20+MB 比较）。修复方向（§2.4 候选 1）：首次内容哈希 + (ptr,len,hash) 命中即信，或内容 generation 计数。

**R-13 🟡 wgpu `TextureCache`/`TextCoverageCache` FIFO 驱逐且容量偏小** — `src/wgpu_backend/renderer/resources.rs:690`（LIMIT=32）、`:791`（LIMIT=64）
N+1 轮换负载（33+ 图标同屏、视频帧流、轮播）下命中率趋近 0——每帧全部纹理重新上传 GPU。修复方向（候选 2）：FIFO→LRU，容量 32/64→64/128，与现有结构同形只换驱逐策略。

**R-14 🔵 任何 `set_geometry` 全局丢弃全部 widget 层** — `src/widget/runtime/access.rs:108-118` → `cache.rs:267-269`
`invalidate_widget_layers()` 丢线程上全部 128 层；resize/重排期间每帧触发，下一帧全子树从 miss 起重新光栅化。缓解因素确认：动画 tick 不走 `set_geometry`（`interaction_fade.rs:83-87` 矩形失效）；保守取舍有注释依据（`:113-114`）。修复方向（候选 4）：按 (old∪new rect) 矩形失效替代全局 bump，需处理"子收缩出父层 rect"分支。

**R-15 🔵 `PATH_POINT_CACHE` 线性扫描 + 全内容比较** — `surface.rs:2412-2443`（深度 16）、`:712`（标签，深度 64）；仅立即绘制路径受影响，bucket-recording 已用 frame arena（`:2489-2496`，G-802）。

**R-16 🔵 `with_widget_mut` 每次访问 = HashMap remove+insert** — `access.rs:138-145`；借出防重入设计的固有代价（千控件窗口每帧数千次哈希操作）。修复方向（候选 3）：`Slab`/`VecMap` + 借用位图，涉及面广、需基准确认。
**缓存候选 5（防御性）**：层缓存按槽位数（128）而非字节预算封顶——128 个 4MB 层=512MB 最坏情形，大窗口高分屏真实风险；可参照 `image/cache.rs:53-77` 现成的字节预算 LRU 模式。
