### 1.1 运行时（RT-）

**RT-01 分组 SegmentedButton 的每次选择变化触发进程级全局重绘**
- **1级** `publish_group_selection` 在每次组内选择变化时无条件调用 `arm_global_repaint()`（`src/widget/misc_widgets/segmented_button.rs:400-401`；`set_selected_index`/`set_selected_indices` 两入口都经此处，`:410-417`、`:432-439`）。arm 只 bump 世代（`src/widget/runtime/repaint.rs:257-261`），实际失效发生在下一帧 `drive_frame` 的 `flush_global_repaint`（`src/widget/runtime/frame.rs:271-277`）：它遍历**全部 MOUNTED** 条目、分配两个 `Vec`，对每个窗口/表面逐一 `mark_dirty_rect` + `request_repaint_because`（`repaint.rs:297-319`）——每个窗口的整帧缓存全部作废、下一帧全部窗口整窗重栅格化。失效范围是全进程所有窗口，与该组无关的窗口也被一并重绘。分组选择是分段按钮的常规用法，这是每次交互的稳态成本，不是罕见事件。已复核属实。
- **2级** 沿用现有 `segmented_groups()` 存储（`segmented_button.rs:392-399`）：组条目登记组内成员 registry id（`set_group_id` 时写入，`:362-369`），`publish_group_selection` 改为对成员 id 逐个走现有 `request_redraw()`/`note_renderable_change_for(id)` 路径（`repaint.rs:759-769` 已具备按 id 失效能力）；成员集合为空或含未挂载 id 时保留 `arm_global_repaint()` 兜底。`flush_global_repaint` 保持原状，继续服务主题/语言等真正的全局输入（`src/theme/manager.rs:72-80`、`src/i18n/global.rs:144-147`）。

**RT-02 拖拽期间每个 mouse move 一次 O(全部挂载控件) 扫描 + DragPayload 深拷贝**
- **1级** `DragCoordinator::update` 在拖拽激活后的**每个 move** 都先 `session.payload().clone()` 再 `widget_at_point(pos, viewport)`（`src/widget/runtime/pointer.rs:489-495`）。`LAST_POINT_HIT` 单槽缓存以精确坐标为键（`:592-607`），拖拽中每个 move 坐标必然不同，缓存恒 miss；回落 `scan_widget_at_point_buffered` 对 `MOUNTED` 全表迭代、每控件一次 `contains_point` 虚调用（`:628-665`）。payload 的 clone 不小：`DragPayload` 持有三个 `String` 与 `Vec<DragItem>`（`src/event/dnd.rs:166-174`），而 clone 结果仅在 `target != self.hovered` 分支才被使用（`:512-513`）。`finish` 释放时还有一次同样的全表扫描（`:530-540`）。`TabWidget`/`ListBox`/`VirtualList` 已接入该协调器（`src/widget/container_widgets/tabwidget.rs:1949-1970`、`src/widget/input_widgets/listbox.rs:1378-1389`）。
- **2级** 两步，均沿用现有命名：① payload 的 clone 下移到 `target == self.hovered` 早退之后（一行位置调整，语义不变）；② `update`/`finish` 的命中判定改走树下降命中（`widget_at` 一族：窗口→子树递归、复用 child buffer），替代 `scan_widget_at_point_buffered` 的全表扁平扫描；后者保留给无窗口/嵌套 hit-rule 的通用场景。

**RT-03 每个有重绘的帧为帧账本多做一次 Vec 分配**
- **1级** `take_frame_repaint_reasons` 对每帧重绘原因先 `mem::take` 出 `BTreeMap`，随即 `.into_iter().collect()` 成新 `Vec`（`src/widget/runtime/frame.rs:613-617`）。该 `Vec` 随 `FrameStats` 每帧整体 replace 进 `LAST_FRAME_STATS`（`:337-350`）——**每个发生了重绘的帧**固定多付一次堆分配。本 crate 已把「每帧一次分配」逐个修掉（同文件 `:678-683` G-37、`src/performance/render_dirty.rs:49-53` G-72），此处属同类残留。

### 1.2 平台后端（PL-）

**PL-01 Windows 主窗口「每事件全窗失效 → 全窗 blit」：一次按键 = 整窗像素重转重传**
- **1级** 主窗事件分支在每次成功派遣后调用 `invalidate_window(hwnd)`，它用 null RECT 失效**整个客户区**（`src/platform/windows/types.rs:806-809`），调用点覆盖按键（`:200-202`）、鼠标（`:231-233`）、hover 变化（`:903-905`）、滚轮（`:986-988`）、字符（`:1036-1038`）、焦点（`:325-353`）。随后 `WM_PAINT` 走 `blit_frame` 全幅 blit（`types.rs:698` → `canvas.rs:512-519`），`blit_frame_region` 对**整个窗口**做 RGBA→BGRA 逐像素转换 + `StretchDIBits` 全幅传输（`canvas.rs:594-609`）。4K 窗口每次按键或 hover 跨控件 ≈ 33 MB 像素工作/事件——Windows 桌面「卡顿」的直接主因。canvas 侧画家已证明区域路径可用（`render_frame_cached_shared` + `blit_frame_region(paint.rcPaint)`，`canvas.rs:459-481`），主窗未接同款。
- **2级** `invalidate_window` 改为消费 runtime 已有的 pending damage 矩形（`mark_widget_damage`/`mark_dirty_rect` 管线已在，`take_pending_repaint` 已在 crate 根 re-export，`lib.rs:336-340`），无 damage 时回退全幅；blit 侧零改动（`blit_frame` 已委托 `blit_frame_region`，传入 RECT 即 `rcPaint`）。缓存帧只转损坏行的安全性与 macOS 同款论证（`macos/canvas.rs:1230-1234`）。

**PL-02 Linux 每次 expose 全帧 RGBA→BGRA 逐像素转换，clip 只挡合成不挡转换**
- **1级** `blit_rgba` 注释自认「The frame-to-surface conversion **stays whole-frame**」（`src/platform/linux/canvas.rs:580-585`），随后无条件对全帧逐像素循环换通道（`:640-651`），尽管 clip 已收窄到损坏区（`:586-596`）。窗口树画家与 surface 画家共用它（`:565-567`）。1px 光标闪烁也要转换整窗像素；GTK 拖拽 resize 每帧全窗 expose 时最痛（`BLIT_SURFACE` 按尺寸重建本身必要、缓存在位 G-601 `:598-625`，但重建之外仍叠加全帧转换）。macOS 是健康对照——`dirty_row_range` 只转脏行（`macos/canvas.rs:1167-1177`、`:1230-1234`）。
- **2级** 对齐 macOS：`blit_rgba` 增 damage 矩形入参，转换循环只覆盖该行带（行外数据本不参与合成，`set_source_surface` 受 clip 约束）；resize 时 damage = 全帧自然整转，静态尺寸下小损坏立即受益。函数签名沿用 `blit_rgba` 现名。

**PL-03 GTK-native 无条件 16ms 心跳：默认 desktop 构建的恒定 60Hz 主线程唤醒**
- **1级** `glib::timeout_add_local(FRAME_INTERVAL_MS, || { drive_frame; Continue })` 无条件永续（`src/platform/linux/platform_impl.rs:864-867`），注释 `:859-863` 自辩「unconditional heartbeat affordable」。但 macOS legacy 对同一权衡已立项反例：G-503 明文「a still window does not need 60 wakeups a second」并 retarget 到 `IDLE_FRAME_INTERVAL_MS`（`macos/canvas.rs:1964-1973`）。`desktop` 默认 feature 含 gtk-native（`Cargo.toml:152-160`）——Linux 桌面应用即使完全静止，主线程仍被 60 次/秒唤醒跑 `drive_frame`。
- **2级** 闭包按 `outcome.needs_another_frame` 在两档间重挂：无帧时 `glib::source_remove` + `timeout_add_local(IDLE_FRAME_INTERVAL_MS)`，有帧回到 `FRAME_INTERVAL_MS`（SourceId 存 `Cell`）；100ms 背板仍照常 drain trigger，语义对齐 `canvas.rs:1964-1973`。沿用 `IDLE_FRAME_INTERVAL_MS` 现名与 G-503 既有命名。

**PL-04 CVDisplayLink 启动后永不停：回调线程全程 60/120Hz 唤醒，即使零动画零窗口**
- **1级** 真实实现在 `src/platform/display_link.rs`。`start()` 创建链接并装回调（`:176-204`），objc2 在 `init()` 无条件启动（`macos_objc2/platform_impl.rs:1039-1049`），仅 `quit()` 停（`:1117-1119`）；legacy 在 `install_frame_heartbeat` 启动（`macos/canvas.rs:1801-1811`）后**无任何 stop 路径**。回调在 CoreVideo 线程按显示器刷新率（ProMotion 120Hz）整进程生命期触发：每 vsync 两次原子 store + `frame_wait::wake()`（`display_link.rs:343-363`）。两后端主线程均不停在 `block_for`（legacy 走 `NSApp().run` `:616-618`；objc2 走 NSRunLoop，`native.rs:2637-2639`），故 `wake()` 无等待者——一根专用线程每秒被内核唤醒 60–120 次做无谓原子工作，电池机型可测。

## 第 2 章 布局与 resize 链（用户报告「顶层 layout 没变化」的根因链）

**LY-01 JSON 声明式根布局在 resize 后永不重算（用户报告 #1/#4 的主根因）**
- **1级** JSON 加载路径的所有布局都存入 `declarative::LAYOUT_MAP`（`src/json/loader.rs:708` `store_layout`、`:979-989` 内联 layout 分支、`src/json/view_session.rs:899-903`、C ABI `c_abi_widgets.rs:266-269`），而 resize 入口 `apply_window_layout`（`src/app/handle/window.rs:814-864`）只查 `LAYOUTS`（`:827-830`，miss 即返回空 Vec，`:843` 的子循环整体不执行）。`LAYOUTS` 的生产写入点仅 `WindowHandle::set_layout`（`window.rs:745-750`，grep 全库核实无其它 insert），`JsonLoader::load` 路径从不调用它。`window.rs:855-862` 的 `else if declarative::has_layout` 只对「窗口布局放置出的子 widget」生效——root 的 layout 不是任何布局的 child，永不进该分支。加载时唯一一次求解是 `loader.rs:758` 用 JSON 声明尺寸 `apply_layout(layout_parent, json_geometry(obj))`，之后 OS 窗口实际尺寸变化无人重放。后果：`JsonLoader::load` / C ABI 创建的「window + layout」应用，用户拉大缩小后根布局不重算，子控件保持加载时几何——与用户报告完全吻合。已复核属实。（`JsonViewSession` 预览路径有 `set_viewport_rect`→`solve_layouts`（`view_session.rs:726-731`），不受此影响；失效面精确为 JsonLoader/C ABI 宿主。）
- **2级** `apply_window_layout` 在 `LAYOUTS` miss 后补 fallback：若 `crate::layout::declarative::has_layout(window_id)` 则对 `Rect::new(0, 0, width, height)` 调 `declarative::apply_layout(window_id, …)`（沿用现有命名，单路径原则：root 声明式布局以 LAYOUT_MAP 为唯一存储，不镜像第二份进 `LAYOUTS`）。或等价地在 `JsonLoader` 解析 window 根 `layout` 时按 `WindowHandle::set_layout` 语义注册进 `LAYOUTS`——二选一，避免双注册表双写。

**LY-02 两个布局注册表互不递归、else-if 丢分支**
- **1级** 三处遍历把 `PANEL_LAYOUTS` 与 `declarative::LAYOUT_MAP` 当互斥集合：`window.rs:855-862` 与 `pointer.rs:1535-1542` 均为 `if widget_hosts_a_layout(…) else if declarative::has_layout(…)`——同一 widget 同时持有两表条目时 declarative 侧被跳过；`declarative.rs:550-551` 的递归只判 `has_layout(*child_id)`，从不查 `widget_hosts_a_layout`——声明式容器里的 panel 被移到新矩形后，panel 自己的 `PANEL_LAYOUTS` 布局不会重跑（`set_widget_geometry` 是纯状态写，无触发链）。后果：混合嵌套（JSON 容器内嵌 panel、panel 内声明式容器再嵌 panel）时深层子树停留旧几何。
- **2级** 统一递归协议：`window.rs:855-862`、`pointer.rs:1535-1542` 改为两个独立 `if`（两表都有则都应用，顺序固定并写入文档）；`declarative.rs:550-551` 的递归在 `has_layout` 判断外补 `widget_hosts_a_layout(*child_id)` → `apply_panel_geometry_bounded(*child_id, *child_rect, depth+1, max_depth)`（复用 `pointer.rs:1489` 的 64 层 bound，共享同一深度语义）。

**LY-03 LayoutContext 从未到达 9+1 处求解入口：9 个布局丢弃 context，声明式路径整体不传 context**
- **1级** `apply_window_layout`/`apply_panel_geometry_bounded` 每次从设备事实构造 `LayoutContext`（`window.rs:821`、`pointer.rs:1514`）并发布 scale（`window.rs:824-826`），但 9 个布局的 `update_with_context` 首行 `let _ = context;` 直接丢弃：absolute.rs:882-885、aspect_ratio.rs:201-213、center.rs:169-172、constraint.rs:502-505、form.rs:672-675、grid.rs:1442-1454、splitter.rs:520-528、stack.rs:189-197、uniform_grid.rs:235-247（box/flex/wrap/border/flow 正常消费，box_layout.rs:805-841、border.rs:671-683）。此外声明式求解 `apply_layout_bounded` 调用的是 `layout.update(rect, …)`（`declarative.rs:529`）而非 `update_with_context`——连实现了 context 的 5 种布局经 JSON 路径也拿不到 context。后果：这 9 种布局做 window/panel/JSON 顶层时 min_touch_size、text_scale/字阶缩放在 resize 重排中全部失效。
- **2级** 沿 G-403 既定形态补齐：9 个 impl 让 `update_with_context` 把 `context` 真正传入各自求解（context 参与 `Hints::clamp_to` 与 min_touch_size 路径，复用 hints.rs:139-143）；`declarative.rs:529` 改调 `update_with_context`，与 `window.rs:821`/`pointer.rs:1514` 共用同一构造点（建议提为单一 helper，避免第三处 `LayoutContext::default()` 散点）。

**LY-04 纯 ViewEngine/ReactiveHost 路径同 tier resize 无任何布局跟随机制（第二条独立成因）**
- **1级** `ReactiveHost::resize`（`src/view/reactive.rs:370-376`）先 `engine.set_viewport(size)`，tier 未变即 `return false`（同 tier 不 rebuild 是文档化的有意行为）；`ViewEngine::set_viewport`（`engine.rs:265-274`）只存尺寸并比较 tier，`:314-318` 的构建复用键 `(revision, viewport)` 使同尺寸重建也被跳过；engine 的 `layout` 字段是 `BoundJsonLayout`（`:145-155`）——名字→id 映射，无求解能力。全库只有 `JsonViewSession::set_viewport_rect`→`solve_layouts`（`view_session.rs:726-731`）会重解布局。后果：直接用 `ViewEngine::mount`/`ReactiveHost` 的宿主（examples/view_adaptive.rs、generated_project 模式），窗口同一 tier 内拉大缩小时，挂载的容器/子布局永远保持挂载时矩形。

**LY-05 `JsonViewSession::solve_layouts` 每次 set_viewport_rect 全量重解 + O(声明×子控件) 线性去重**
- **1级** `set_viewport_rect`（`view_session.rs:726-731`）文档定位为 paint 路径每帧入口（`:57-58`、`:718-719`），每次调用：`:953-954` 重建 `declarations` Vec 且逐 layout `path.clone()`；`:972` 对每条声明全量 `apply_layout`（无脏标记，rect 未变也重解）；`:974-977` 去重用 `geometry.iter_mut().find` 线性扫，O(声明数×子控件数)；`:730` 再 `geometry.clone()` 一份返回。大文档每帧 O(n²) 查找 + 多次分配，resize 拖动期间持续烧帧。
