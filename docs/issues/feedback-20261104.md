## RW-117｜JSON 声明式预览不消费根节点 `layout`，也没有断点子树（P1，阻塞 H-29 的完整形态）

**事实。**

1. `json::JsonLoader::load`（完整装载路径）会 `store_layout` 并 `apply_layout`，因此控件有几何。
2. 4.0.1 的增量视图路径 `json::json_to_view_tree` → `ViewEngine::mount_tree` **跳过** 节点的
   `layout` 属性（`src/json/view_session.rs` 的 `convert_node` 注释："The layout declaration is
   structure …"，随后 `continue`），也不在装载后调用 `layout::declarative::apply_layout`。
   结果：宿主 `Preview::mount_json` 挂载的控件保持 `create` 时的矩形；`--preview paint:<w>x<h>`
   只改变画布大小，子控件不会按根 `layout` 重新求解。
3. `ViewEngine::set_viewport` 只影响 `Breakpoint::current()` 与 `View::build` 的子树选择，不改
   已挂载控件的几何。
4. 声明式 JSON 文档没有 breakpoint / tier 子树字段（`Node::breakpoint` 只存在于 Rust `View` API）。

**影响。** 模式 1 的“结构或样式修改立即反映”在布局层面仍不成立：宿主页面文档的根 `layout`
（页面格式 v6/v7）只有**生成**路径消费，预览路径不消费。宿主不能用自己实现的布局补齐
（原则 #14 禁止分叉），也不能加一个生成不消费的 breakpoint 字段（原则 #13/#26）。

**建议。**

- `JsonViewSession`/`ViewEngine::mount_tree` 在挂载后按宿主的视口矩形调用
  `layout::declarative::apply_layout(root, rect)`，并提供 `set_viewport_rect(Rect)` 或等价入口，
  使 `set_viewport` 同时更新几何；根节点的 `layout` 声明应成为可查询的布局状态，而不是被丢弃。
- 声明式文档增加 per-node breakpoint 可见性（如 `"breakpoints": ["compact","medium"]` 或
  `Node::breakpoint` 的 JSON 拼写），并与 `ViewEngine::set_viewport` 的 tier 选择对齐；不支持的
  字段应在 generation/report 或 JSON 诊断中具名，而不是静默忽略。
- 在此之前宿主按 H-29 的可行部分实现 `--preview tiers:<page>`：用生成期 solve
  （`GenerationReport::node_rects`）报告同一文档在 compact/medium/expanded 三档宽度下的真实
  矩形，并明确写出“分档子树尚不可表达”。

## RW-119｜Harmony NAPI 流程文档未说明“必须带设备 profile”的构建前提（P3，文档）

**位置。** `examples/harmony_napi_bridge_flow.md`（4.0.1）只列了 `rw_*` 调用顺序，没有给出构
建特性；`src/lib.rs` 的 `bindings` 模块门控是
`all(any(feature = "desktop", feature = "jni", feature = "mobile-api"), not(alloc_frugal))`。

**观察。** 以 `--no-default-features --features "harmony xcomponent touch i18n controls-native
desktop-runtime runtime-fonts"` 构建的 `librust_widgets.so` 只导出 13 个 `rw_harmony_*` 符号，

导出 165 个 `rw_*`，宿主脚手架的 13 个未定义符号全部解析。

**建议。** 在该流程文档开头写出可直接复制的构建命令（含 `desktop` 或 `jni`/`mobile-api`），
或在 `bindings` 文档里明确“只开 `harmony` 特性时 C ABI 不在库中”；这能避免下一位集成者重复
同样的踩坑。宿主侧已在 `packaging/harmonyos/entry/libs/arm64-v8a/README.md` 记录正确命令与
`-Wl,--no-undefined` 的检查方法。

## RW-120｜`CodeEditor::set_text` 压入撤销检查点，缺一个“加载文档”入口（P3，建议）

**事实。** 4.0.1 的 `CodeEditor::set_text`（`editor/document.rs`）先推一条
`ValueCommand("Edit text")` 再换文本，即**加载文档本身是一个可撤销编辑**。宿主把文档装进控件后
必须自己调 `clear_history()`，否则启动/切标签后的第一次 Ctrl+Z 会“撤销加载”把缓冲区清空；
若宿主再把控件文本回写模型（本仓库本轮修的就是这条路径），空文本会一路写进模型。

**建议。** 提供一个语义化的加载入口（例如 `load_document(text)` / `set_text_without_history(text)`），
内部只换文本、不压检查点，并在文档里点名“宿主加载时用它，`set_text` 用于用户级替换”。
这样宿主的正确用法不依赖记得额外调用一个方法；或者至少在 `set_text` 的文档注释里给出
“加载后必须 `clear_history()`”的可复制示例。

**宿主侧已做。** `sync_editors` 在 `set_text` 之后立即 `clear_history()`（log-20261103-2 §15）。
本项不是缺陷，是易踩的 API 形状问题。

## RW-121｜`CodeEditor` 的共享文档只能构造期指定，已挂载视图无法接入（P2，宿主阻塞点）

**事实。** 4.0.1 提供 `CodeEditorDocument`（共享缓冲区/版本/历史）与
`CodeEditor::with_document(geometry, document)`（`editor/document.rs:292`），但**只在构造时**接受
文档；公开的 `document()` / `into_document()` 只能读/交出句柄，`adopt_document` 是私有。

**影响。** 宿主用库推荐的 `WindowHandle::mount_widget_by_name("code_editor", …)` 创建编辑器后，
无法把它接到一个已存在的 `CodeEditorDocument`。两个分组展示同一文档时只能各自持一份文本：
在一边输入后另一边要到下一次宿主回写才一致（本仓库已把“不一致”降到“下一次命令前”）。
可以用 `mount_surface(Box::new(CodeEditor::with_document(..)), rect)` 绕过，但视图在标签切换时
要重建控件，光标/滚动/折叠全丢，代价高于收益。

**建议。** 公开一个把**已挂载**视图接到文档的入口（`fn link_document(&mut self, document: &CodeEditorDocument)`
或 `set_document`），语义与 `with_document` 一致（视图状态重置、历史限随文档）。

## RW-122｜没有“这段文字是用户输入”的能力标志，也没有通用选中读写对（P2）

**事实。** 预览重建需要保留用户输入（T14.03）。库能读写任意控件的 `text` 属性，但无法区分
“控件显示的就是声明值”与“这是人刚改过的值”；声明未写 `text` 的控件也无从判断。宿主目前只能用
“当前文字 ≠ 页面声明”作判据（可复核、但覆盖不到声明没提到 `text` 的输入控件）。
同理，选中没有通用读写对（`CodeEditor` 有自己的一套，其余控件无），所以预览的“选中保留”
仍未实现。

**建议。** 二选一：在能力表/`PropertySchema` 上标注 `text` 是用户可编辑的（例如
`user_input: true`），或区分“声明写入”与“用户输入”两个信号（现有 `text_changed` 对两者都触发）。
选中则提供一个与 `scroll_row` 同形的通用属性/入口，宿主就能像滚动一样捕获/恢复。

## RW-123｜`MessageBox` 标准按钮的文案无法由宿主本地化（P3）

**事实。** `MessageBox` 用 `StandardButton` 画按钮，文案由 `translated_label()` 解析
`common.button.*`（`dialog/message_box.rs`）——它读的是**库的** i18n 目录。
`i18n::init_with_options` 只内置 **English**（`EMBEDDED_EN_JSON`），其余语言来自宿主的
`preload_dir`。所以宿主不带 `common.button.*` 时，中文界面下这三个按钮会显示英文；而
`MessageBox` 没有自定义按钮文案的入口（只有 `StandardButton`）。

**影响。** 本仓库想给“关窗/退出”对话框加第三个动作（保存全部后退出），只能用
`MessageBox` 的 `Save/Discard/Cancel`，于是要么接受英文按钮，要么自造对话框（被禁止）。
当前实现仍是宿主自绘两动作的 `ConfirmDialog`（文案可本地化）。

**建议。** 二选一：（a）`MessageBox::set_button_text(StandardButton, impl Into<String>)`；
或（b）把所有内置语言包嵌入库（不只 English），或在文档里明说“宿主必须把自己的语言包
补上 `common.button.*`”。有（a）时宿主就能在保留本地化文案的前提下提供三动作。

## RW-124｜画布内置网格/标尺无法表达模型空间（P2，阻塞“把变换交给控件”）

**事实（4.0.1）。**

1. `Canvas::set_show_grid` 的绘制（`canvas/widget.rs` 的 `Draw` 实现）在**表面像素**里从控件矩形
   原点起每 `grid_step` 像素画一条线；`set_grid_space(GridSpace::Model)` 只改变**吸附**的计算空间，
   不改变画法。
2. `draw_rulers` 用表面像素刻度、没有标签，也不看变换。
3. `draw_decorations`（引导线/覆盖层/标尺）会对覆盖层命令应用 `self.transform`，但标尺本身仍是
   表面刻度。

**影响。** 宿主是一个带缩放/平移的设计画布。它想要“每 16 个设计单位一条线、对齐设计原点”的网格
和“每 100 设计单位一个刻度带标签”的标尺，只能自己画（本仓库现状，`log-20261103-2` §15.6/§17）。
这又反过来堵住了一件事：把绘制改成模型坐标并 `set_transform`（让库的变换/引导线/吸附/`hit_test_tagged`/
拖放 model 坐标全部生效），因为那样命令会被变换，而内置网格/标尺仍是表面刻度 → 可见不一致。

**建议（任一即可解锁）。**

- 让 `set_show_grid` 按 `GridSpace::Model` 绘制：网格线位置取模型单位的 `grid_step` 倍数、经变换映射，
  并保证线宽仍为 1 表面像素；
- 标尺增加“单位 + 标签”策略：例如 `set_ruler_unit(u32)`，或公开 `ruler_ticks() -> Vec<(i32, String)>`
  让宿主自己画标签而不必重算刻度间距；
- 或直接在文档里写明“模型空间的网格/标尺不由控件提供”，宿主的自绘就是官方做法（那就把这条
  从“复制库实现”改为“已声明的分工”）。

**宿主当前做法。** 网格/标尺自绘于表面坐标（T09.05 已把设计↔控件映射换成库的 `CanvasTransform`，
只剩“谁来施加变换”未交出）。拿到上述任一能力后，迁移步骤已写在 `CanvasView::transform` 的注释里。
