### 2.1 🔴 高

**W7-01 🔴 image_view draw 入口按 `ImageFormat` 判存：任何经 `from_bytes`/`from_file` 装入的 JPEG/PNG/BMP 一律画 "?" 占位——解码 RGBA 数据在手却被格式门挡回**（用户报告"截图不显示图片"的 draw 侧根因）✅主
- 证据链（全部亲读）：`src/widget/display_widgets/image_view.rs:1470-1474`——`let data = if self.image.format() == ImageFormat::Rgba8 { self.image.rgba8_data()… } else { None }`，非 Rgba8 格式直接落 :1498 起的占位分支；`src/image/decoder.rs:1183`——`DecodedImage::new(ImageFormat::Jpeg, ImageData::Rgba8(pixels), …)`（PNG/BMP 同型），即**解码产物是"原格式名 + Rgba8 数据"**；`src/image/image_impl.rs:103-107`——`rgba8_data()` 本按**数据变体**判存，与格式名无关；`src/image/image_impl.rs:48-51/:116-120`——`from_bytes`/`from_file` 正是运行时装图的主路径。
- 后果：`Image::from_bytes(jpg_bytes)` → `format()==Jpeg` → 门挡回 → 整格 "?"。image_gallery 不受影响（`view_widgets/image_gallery.rs:1134/:1380` 按数据判存）；avatar 的图片路径走 `image::cache` 直取 RGBA（`misc_widgets/avatar.rs:686-708`），同样不受影响。全仓 grep 该模式仅 image_view 一处。
- 冰山说明：`paint_pixels`（:858-958）内部就按数据取用，仅 draw 入口多套了一层错误格式门。既有占位测试用 `Image::new()`（空数据），删除格式门不影响其语义。
- 修复：`image_view.rs:1470-1474` 改为 `let data = self.image.rgba8_data().filter(|d| !d.is_empty());`（一行；照 gallery/avatar 的数据判存口径）。**执行顺序必须先于 W7-02 的 sample 改造**：先修 draw 门、再换 sample 臂为真照片，否则 sample 从"32×32 棋盘"变成"整格 ?"。
